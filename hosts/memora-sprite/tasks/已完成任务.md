| ID | 问题 | 修复方式 |

**关键技术决策**：

1. **fast-fail 与优雅降级平衡**：P0-8.1 保留 `getRequiredElement` 的 fast-fail 设计（不进入半初始化状态），但在抛异常前渲染错误卡片到 document.body，让用户看到明确错误信息而非空白。错误仍然 rethrow，让上层 catch 感知。
2. **IPC 监听器时序**：P1-7.1 把 `initIpcListeners` 提前到 `onAgentReadyCallback` 赋值之后，确保所有回调依赖（memoryController/settingsController/sessionController）已创建。注册时机从"DOMContentLoaded 中段"提前到"controllers 创建后立即"。

> 来源：阶段 A 稳定基线后的 P2 优化项，按 A→B→C→D 迭代路径执行。

| P2-UI-6.2 | modal.ts 全局 Escape 监听排除 `#confirm-modal` 但未排除 `#prompt-modal`，触发两次 onCancel | modal.ts 选择器改为 `.modal:not(.hidden):not(#confirm-modal):not(#prompt-modal)`，与 #confirm-modal 同模式排除有独立 onKeydown 的 #prompt-modal |
| P2-UI-6.4 | 弹窗焦点管理 `previousFocusEl` 单例字段，嵌套弹窗场景下内层覆盖外层焦点，关闭外层时恢复到内层已隐藏元素 | modal.ts 将单例改为 `previousFocusStack` 栈结构 + `pushFocus`/`popFocus` 辅助方法；showConfirmDialog/showInputDialog 的 cleanup 路径补充 popFocus 恢复焦点（原 cleanup 未恢复焦点，关闭弹窗后焦点丢失到 body） |
| P2-UI-1.2 | 切换到 settings 面板时不刷新配置表单，用户在其他途径变更配置后表单显示旧数据 | renderer.ts `onPanelSwitch` 回调中添加 settings 面板的 `loadConfig` + `loadLlmConfig` 刷新；switchPanel 已在切走 settings 时检查 dirty，切到 settings 时 dirty 必为 false，刷新安全 |

**关键技术决策**：

1. **ResizeObserver 防御性检查**：P2-2.1 中 `initInputAreaResizeObserver` 添加 `typeof ResizeObserver === 'undefined'` 检查。ResizeObserver 是浏览器 API，jsdom 测试环境不提供，缺失时静默降级（保持原静态 140px 回退值），不阻断 UIManager 初始化。此修复解决了阶段 B 初次验证时 90 个 ui.test.ts 连锁失败（ResizeObserver is not defined → UIManager 构造失败 → afterEach cleanup 崩溃）。
2. **焦点栈而非单例**：P2-UI-6.4 将 `previousFocusEl` 单例改为 `previousFocusStack` 栈结构。栈中元素类型为 `(HTMLElement | null)`——document.activeElement 在无焦点时为 null，栈中保留 null 条目以保证 pop 时栈深度正确（即使焦点无法恢复也不破坏栈平衡）。
3. **cleanup 路径焦点恢复**：P2-UI-6.4 发现 showConfirmDialog/showInputDialog 的 cleanup 路径（onOk/onCancel）只 add('hidden') + removeEventListener，未恢复焦点。原设计中 cleanup 不调用 hideModal（避免副作用），所以焦点恢复需在 cleanup 中显式调用 popFocus。这与 showModal/hideModal 路径的 popFocus 互斥（confirm/prompt 走 cleanup，其他弹窗走 hideModal），栈自然平衡。
4. **视图切换令牌**：P2-UI-3.2 的 `viewSwitchToken` 是轻量竞态防护——每次 switchView 递增令牌，setTimeout 回调检查令牌是否过期。比 abort Controller 或 cancelable promise 更简洁，适合单线程 JS 的异步竞态场景。
5. **settings 刷新时机安全性**：P2-UI-1.2 的 onPanelSwitch 回调中，切到 settings 时直接调用 loadConfig/loadLlmConfig 不检查 dirty。原因是 switchPanel 已在切走 settings 时检查 dirty（有未保存修改会提示用户），切到 settings 时 dirty 必为 false（用户要么保存了，要么离开时被重置了），刷新不会覆盖用户编辑。

**验证结果**：sprite typecheck（tsc -p tsconfig.electron.json --noEmit）报告 2 个预先存在的错误（settingsController.ts:187 shortcuts 字段缺失 TS2741、settingsPanelManager.ts:528 KeyboardEvent 类型不匹配 TS2345），与本次修改无关；sprite 全量 1941 tests passed / 4 failed（errorHelpers.test.ts × 2 + patternDetector.test.ts × 2，均为预先存在的失败，与本次修改无关）。本次修改涉及的 ui.test.ts 90 个测试全部通过（阶段 B 初次验证时因 ResizeObserver 未定义连锁失败 90 个，修复后全部恢复）。

## jsonlAppender flaky test 修复（2026-06-27）

> Iteration 17。单任务迭代：QC-FLAKY-JSONL 修复 jsonlAppender 并发写入竞态导致的 flaky test。
> sprite 宿主 typecheck + eslint 全绿 + vitest 1389 测试 58 文件连续 2 次全量通过（flaky test 修复确认稳定）。

| ID | 范围 | 覆盖内容 | 测试数 |
|----|------|---------|--------|
| QC-FLAKY-JSONL | sprite 宿主 jsonlAppender.ts + jsonlAppender.test.ts | 修复并发写入竞态：原 append() 是 fire-and-forget，多个 appendFile 和 truncateIfNeeded 并发交错，truncateIfNeeded 的 read-modify-write 不原子（读取文件后、重写文件前若另一个 appendFile 写入新行，该行被重写覆盖丢失）。引入 writeChain Promise 链串行化所有文件写入操作（append + truncateIfNeeded + clear），确保不会交错执行 | +2（1387→1389） |

**关键技术决策**：

1. **writeChain 串行化方案**：引入 `private writeChain: Promise<void> = Promise.resolve()` 字段，每次 append/clear 将操作链接到链尾。append 内部 `appendFile + truncateIfNeeded` 作为一个原子单元串行执行，不会与其他 append 交错。
2. **错误隔离**：append 的 catch 恢复 writeChain 为 resolved 状态，单个写入失败不阻塞后续写入。clear 的错误通过 `clearPromise` 抛给调用方，但 `writeChain = clearPromise.catch(() => {})` 恢复链为 resolved，避免 clear 失败阻塞后续 append。
3. **clear 串行化设计**：clear 排队到 writeChain 末尾（等待之前排队的 append 完成），新的 append 会链接到 clear 之后。`await clearPromise` 确保调用方返回时文件已清空。
4. **readRecent 不串行化**：读取操作可容忍中间状态（部分行未落盘），且原实现也有此特性。串行化读取会增加延迟无实际收益。
5. **测试修复**：getWriteCount 测试原为同步函数，串行化后需 `await flushWrites()` 等待 writeChain 排空，避免 afterEach 删除 tmpDir 后 pending 操作报 ENOENT 错误。
6. **新增 2 个串行化验证测试**：① 快速连续 append 20 条验证写入顺序完整（无乱序无丢失）② 并发 append + truncate 10 条验证 maxEntries=5 时完整保留最近 5 条（核心修复验证，复现原 flaky 场景）。
7. **性能影响可忽略**：串行化后写入排队执行，但审计日志和追踪日志是低频操作，延迟可忽略。收益是保证写入顺序和截断正确性。
