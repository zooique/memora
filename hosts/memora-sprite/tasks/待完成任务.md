### 🟡 P3 记忆治理 LLM 介入（需方案设计 + LLM 能力依赖）

> 来源：2026-07-15 设计
> 定位：补全模块是"消费侧"（纯代码检索排序，零 LLM）；以下任务属于"生产侧"（记忆治理），需 LLM 异步介入
> 架构基础：内核已预留 Manager 体系（MemoryDecayManager / MemoryInspector / MemoryAdvisor / RelationBuilder）
> 共性约束：后台异步处理（秒级可接受），不在用户输入热路径，LLM 成本可控
> 实施路径：L1（去重）→ L2（时效）→ L3（冲突）→ L4（压缩），每项独立可回滚

| ID | 任务 | 痛点 | LLM 解法 | 介入 Manager |
|----|------|------|---------|-------------|
| MEM-0715-L1 | 语义去重 | "喜欢深色主题" vs "偏好暗色模式" → LIKE 匹配无法识别为同一条记忆，导致记忆库膨胀 + 补全候选重复 | LLM 判断语义等价，合并为一条，保留更高相关度的表达 | MemoryInspector |
| MEM-0715-L2 | 记忆时效性评估 | "最近在学 Rust"（3 个月前）→ 仍有效吗？静态 decay 规则无法区分"已完成"和"持续进行" | LLM 结合时间跨度 + 上下文判断是否仍适用，输出 keep/archive/delete 三态 | MemoryDecayManager |
| MEM-0715-L3 | 记忆冲突检测 | "喜欢简洁风格" vs "偏好详细注释" → 是否矛盾？当前无冲突感知，补全时可能同时出现两条相反建议 | LLM 判断是否需要标注上下文边界（如"代码风格偏好简洁，文档偏好详细"），非真冲突则合并 | MemoryAdvisor |
| MEM-0715-L4 | 归档压缩 | 50 条散落记忆 → 能否合并为 10 条高质量洞察？当前归档只做时间维度压缩，无语义压缩 | LLM 综合提炼，跨多条相关记忆生成高密度洞察，原记忆降权 | SessionArchiver |
