# 经典案例：Electron + nut-js 获取 Windows 窗口标题中文乱码的根因分析与修复

> **适用场景**：Electron 桌面应用中使用 nut-js / libnut 等第三方库获取前台窗口标题时，中文（及其他非 ASCII 字符）显示为乱码。
>
> **技术栈**：Electron + Node.js + TypeScript + nut-js + PowerShell + Win32 API
>
> **难度**：★★★★☆（跨语言、跨编码、跨进程的多层编码链路排查）

---

## 一、设计需求

Memora Sprite 是一个 Electron 桌面精灵应用，核心交互之一是**快速输入浮窗**：用户通过全局快捷键呼出浮窗，输入内容后自动粘贴到之前聚焦的应用中。

为了实现"自动粘贴到目标应用"，需要在浮窗弹出前捕获前台窗口信息，包括：

1. **窗口句柄**（HWND）—— 用于后续恢复焦点 + 模拟 Ctrl+V
2. **窗口标题**（Title）—— 用于在浮窗顶部显示"聚焦：{应用名}"，并提取应用名

技术选型上，使用 `@nut-tree-fork/nut-js`（v4.2.6）库来获取前台窗口。该库底层调用 Windows 原生 API，封装了 `getActiveWindow()` 等便捷接口。

---

## 二、问题现象

在中文 Windows 系统上，当聚焦的窗口标题包含中文时，nut-js 返回的标题出现乱码：

```
实际标题：无标题 - 记事本
nut-js 返回：无标题 - ����
```

日志中的典型表现：
```json
{"nutJsTitle":"������","psTitle":"㧝䶝캚","msg":"nut-js 标题乱码，已通过 PowerShell 修复"}
```

注意 `psTitle`（PowerShell 修复后的标题）**也不是正确的中文**，但代码认为"已修复"，因为它只检测了 U+FFFD 替换字符。

---

## 三、根因分析

### 第一层：nut-js 的 ANSI 编码 bug

通过阅读 nut-js 底层依赖 `@nut-tree-fork/libnut-win32` 的类型定义，发现了关键线索：

```typescript
// libnut-win32/index.d.ts
export function getWindowTitle(handle: number): string;
```

该函数在原生 C++ 层调用的是 **`GetWindowTextA`**（ANSI 版本），而非 `GetWindowTextW`（Unicode 版本）。

在中文 Windows 上，ANSI 代码页 = GBK（CP936）。编码链路如下：

```
Win32 GetWindowTextA → 返回 GBK 字节 → nut-js native addon → Node.js napi_create_string_utf8
                                                              ↑
                                              误将 GBK 字节当作 UTF-8 解码
                                                              ↓
                                              非法字节序列 → U+FFFD 替换字符
```

**这是不可逆的编码损坏**——一旦 GBK 字节被当作 UTF-8 解码并替换为 U+FFFD，原始信息就永久丢失了。

### 第二层：PowerShell stdout 编码污染

为了绕过 nut-js 的 bug，采用了 PowerShell fallback 方案：通过 `execSync` 调用 PowerShell 脚本，使用 `GetWindowTextW`（Unicode 版本）获取标题。

最初的方案使用 **base64 编码 + stdout 传递**：

```typescript
// PowerShell 端：UTF-16LE → base64 → stdout
[Convert]::ToBase64String([System.Text.Encoding]::Unicode.GetBytes($s.ToString()))

// Node.js 端：stdout → UTF-8 解码 → base64 解码 → UTF-16LE 解码
const result = execSync(`powershell ...`, { encoding: 'utf8' });
const title = Buffer.from(result.trim(), 'base64').toString('utf16le');
```

理论上 base64 是纯 ASCII，不应受编码影响。但实际运行中，`psTitle` 输出了 `"㧝䶝캚"` 这样的乱码——不是 U+FFFD，而是合法的 Unicode 字符（U+3A1D、U+4D9D、U+CE9A），说明 **base64 字符串在传输过程中被系统代码页编码层污染**。

可能的污染点：
- PowerShell 的 stdout 管道受系统 OEM 代码页影响
- `execSync` 的 `encoding: 'utf8'` 与实际输出编码不一致
- 管道传输中引入了不可见的 BOM 或前缀字节

### 第三层：竞态条件

旧方案的时序：

```
1. nut-js captureActiveWindow() → 拿到 Window 对象
2. await window.title → 获取标题（检测到 U+FFFD 乱码）
3. execSync('powershell GetForegroundWindow()...') → 重新获取前台窗口标题
```

步骤 2 和步骤 3 之间存在时间窗口。如果系统中的通知、弹窗或其他进程在此间隙切换了前台窗口，步骤 3 的 `GetForegroundWindow()` 拿到的就不是目标窗口了。

---

## 四、旧方案为什么修了很多次都修不彻底

| 修复尝试 | 思路 | 为什么失败 |
|---------|------|-----------|
| 检测 U+FFFD 后用 PowerShell 修复 | 绕过 nut-js 编码 bug | PowerShell stdout 编码污染，返回的标题仍然乱码 |
| base64 编码绕过 stdout 编码 | 纯 ASCII 不受代码页影响 | 管道传输中仍有隐蔽的编码层污染 |
| `-EncodedCommand` 传递脚本 | 避免引号转义问题 | 脚本传递没问题，但输出回来的路径仍有问题 |
| `Add-Type -TypeDefinition` + 显式 W 后缀 | 双重保险确保调用 Unicode API | API 调用正确了，但结果传递回来的链路坏了 |

**根本原因**：一直在修"检测乱码"和"PowerShell 编码"这些**下游症状**，但根因在上游——nut-js 的原生插件调用了 ANSI 版本的 Win32 API，而 PowerShell 的 stdout 管道在 Electron 环境下不可靠。

---

## 五、最终解决方案

### 核心思路：提取 HWND + 文件 I/O

不再依赖 nut-js 获取标题，也不通过 stdout 传递结果。改为：

```
nut-js（仅用于窗口捕获，拿 HWND）
    ↓
PowerShell GetWindowTextW(hwnd) → 写入临时文件（UTF-16LE 字节）
    ↓
Node.js fs.readFileSync → .toString('utf16le') → 正确的 Unicode 标题
```

### 关键改动

**1. 从 nut-js Window 对象提取 HWND**

nut-js 的 `Window` 类内部存储了 `windowHandle`（即 Win32 HWND）。虽然声明为 `private`，但运行时可以安全访问：

```typescript
// inputInjector.ts
export interface ActiveWindow {
  readonly title: Promise<string>;
  readonly region: Promise<{ left: number; top: number; width: number; height: number }>;
  focus: () => Promise<void>;
  readonly hwnd?: number; // 新增：Win32 窗口句柄
}

// getDefaultInputInjector 中提取 HWND
getActiveWindow: async () => {
  const win = await nutJs.getActiveWindow();
  return {
    title: win.title,
    region: win.region,
    focus: async () => { await win.focus(); },
    hwnd: (win as unknown as { windowHandle?: number }).windowHandle,
  };
},
```

**2. PowerShell 脚本接受 HWND 参数 + 写入临时文件**

```typescript
// pasteCoordinator.ts
function getWindowTitleViaPS(hwnd: number): string | null {
  const tmpFile = path.join(os.tmpdir(), `memora_title_${process.pid}_${Date.now()}.bin`);
  try {
    const script = `Add-Type -TypeDefinition @"
using System;
using System.Runtime.InteropServices;
using System.Text;
public static class Win32Title {
    [DllImport("user32.dll", CharSet = CharSet.Unicode)]
    public static extern int GetWindowTextW(IntPtr hWnd, StringBuilder lpString, int nMaxCount);
    [DllImport("user32.dll", CharSet = CharSet.Unicode)]
    public static extern int GetWindowTextLengthW(IntPtr hWnd);
}
"@
$h=[IntPtr]::new(${hwnd})
$l=[Win32Title]::GetWindowTextLengthW($h)
if ($l -eq 0) { exit }
$s=New-Object System.Text.StringBuilder($l+1)
[Win32Title]::GetWindowTextW($h,$s,$s.Capacity)
$bytes=[System.Text.Encoding]::Unicode.GetBytes($s.ToString())
[System.IO.File]::WriteAllBytes("${escapedPath}", $bytes)`;

    const encoded = Buffer.from(script, 'utf16le').toString('base64');
    execSync(`powershell -NoProfile -EncodedCommand ${encoded}`, {
      timeout: 3000, stdio: 'ignore',
    });

    const buf = fs.readFileSync(tmpFile);
    return buf.toString('utf16le') || null;
  } finally {
    try { fs.unlinkSync(tmpFile); } catch { /* ignore */ }
  }
}
```

### 为什么这个方案能彻底解决

| 旧方案缺陷 | 新方案如何消除 |
|-----------|--------------|
| **竞态条件**：`GetForegroundWindow()` 可能拿到错误窗口 | 直接用捕获时的 HWND，100% 定位目标窗口 |
| **stdout 编码污染**：base64 在管道传输中被系统代码页破坏 | 文件 I/O 直写 UTF-16LE 字节，Node.js 直接读取，零编码转换 |
| **双层依赖叠加**：nut-js + PowerShell 各有编码问题 | nut-js 仅负责窗口捕获（可靠），标题获取完全绕过它 |

## 六、编码问题排查方法论

这个案例暴露了多层编码转换链路中常见的陷阱。以下是排查思路：

### 1. 画出完整的编码链路图

```
数据源 → 编码A → 传输层 → 编码B → 解码层 → 编码C → 最终使用
```

每一层转换都可能出问题。本案例的链路：

```
Win32 API → GBK/UTF-16LE → native addon → napi → UTF-8 → JavaScript
                                                       ↑
                                              这里断了（GBK 误作 UTF-8）
```

### 2. 识别"不可逆损坏点"

U+FFFD 替换字符是 UTF-8 解码器遇到非法字节序列时的"垃圾桶"。一旦出现，原始信息就永久丢失了。**不要试图从 U+FFFD 反推原始数据**，而是要找到产生它的上游环节。

### 3. 绕过而非修补

当一个库的底层实现有编码 bug 时：
- **修补方案**（检测乱码 + fallback）：脆弱，因为 fallback 链路本身也可能有编码问题
- **绕过方案**（提取原始数据 + 自己处理编码）：可靠，因为控制了整条链路

本案例中，nut-js 的 `GetWindowTextA` 调用是根因，无法修改（第三方库）。但 nut-js 的 `Window` 对象内部存储了 HWND——**提取这个原始数据，自己调用正确的 API**，是最可靠的方案。

### 4. 进程间通信的编码陷阱

`child_process.execSync` 的 `encoding: 'utf8'` 选项假设子进程输出 UTF-8，但：
- PowerShell 的默认输出编码受系统代码页影响
- 即使输出纯 ASCII（如 base64），管道传输中仍可能引入 BOM 或编码层前缀
- **文件 I/O 是最可靠的跨进程数据传递方式**——直接写字节，读字节，零编码转换

---

## 七、关键收获

1. **第三方库的编码 bug 可能无法修复，但可以绕过**——提取原始数据（HWND），自己调用正确的 API
2. **stdout 管道在 Electron + PowerShell 环境下不可靠**——优先使用文件 I/O 传递二进制数据
3. **竞态条件在异步代码中无处不在**——`await` 前后，前台窗口可能已经切换
4. **不要只修下游症状**——检测乱码 + fallback 是"补丁思维"，找到并绕过上游根因才是"架构思维"
5. **编码链路要画图分析**——每多一层转换，就多一个故障点；能减少转换层数就减少
