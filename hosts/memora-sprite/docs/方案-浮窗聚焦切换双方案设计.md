## 一、问题

### 当前行为

浮窗唤起时（Ctrl+Shift+C），`capturePreviousWindow()` 在浮窗显示前捕获当前前台窗口。此后所有 Tab 提交的粘贴目标都固定为这个被捕获的窗口。**浮窗在锁定模式（🔒）下保持打开，但无法切换粘贴目标。**

### 用户场景

1. 用户在 VS Code 中唤起浮窗 → 输入 → 粘贴到 VS Code ✅
2. 浮窗锁定 → 用户点击切换到浏览器 → **再次 Tab 提交仍然粘贴到 VS Code** ❌
3. 想粘贴到浏览器 → 必须关闭浮窗 → 点浏览器 → 重新快捷键唤起

每次切换目标都要"关闭 → 切窗口 → 再唤起"，打断连续工作流。

## 二、方案设计

### 核心思路：两种重捕获入口互补

```
┌─────────────────────────────────────────────────┐
│             浮窗聚焦切换方案                       │
├──────────────────┬──────────────────────────────┤
│  blur 自动重捕获  │  聚焦栏手动重捕获               │
│  (零步操作)      │  (显式操作)                    │
├──────────────────┼──────────────────────────────┤
│ 触发：blur 事件   │  触发：点击聚焦栏               │
│ 用户感知：无      │  用户感知：点击→刷新            │
│ 适用：常规窗口切换 │  适用：不确定性场景              │
│ 风险：误触发      │  风险：无                      │
└──────────────────┴──────────────────────────────┘
```

### 方案 A：blur 自动重捕获（主方案）

**原理**：锁定模式下浮窗失焦不关闭。当用户点击另一个应用时：

```
用户点击 VS Code
  → 浮窗 blur 事件触发
  → 此时浮窗已不是前台，GetForegroundWindow() = VS Code
  → captureActiveWindow() 捕获 VS Code
  → IPC 推送 → 渲染进程更新聚焦栏 "VS Code"
```

**关键约束**：`blur` 触发时浮窗已不是前台窗口，无需先隐藏再捕获（与 `show()` 中的时序不同）。

**守卫条件**：

| 条件 | 说明 |
|------|------|
| `pinnedMode === true` | 仅锁定模式下启用自动重捕获 |
| `pasteInProgress === false` | paste 期间 blur 已被抑制，此处作为双重保险 |
| `captureActiveWindow` 返回非 null | 排除浮窗自身、桌面、任务栏等无效窗口 |

**误触发风险与对策**：

| 误触发场景 | 对策 |
|-----------|------|
| 点击桌面/任务栏空白区 | `captureActiveWindow` 内部通过 HWND 排除（桌面 HWND 通过 `GetShellWindow` 判断），返回 null 则忽略 |
| 点击浮窗自身的 footer/按钮 | `captureActiveWindow` 已有 `floatWindowHwnd` 排除逻辑 |
| 短暂点击（<200ms，如误触） | 加 200ms 防抖：blur 后 200ms 内 focus 回来则取消重捕获 |

### 方案 B：聚焦栏手动重捕获（补充方案）

**原理**：聚焦提示栏本身变为可点击按钮，点击后通过 koffi FFI 直接调用 `GetForegroundWindow()` 获取当前前台窗口 HWND，零闪烁（无需 hide/show 浮窗）。

```
用户点击聚焦栏 "VS Code ▼"
  → koffi GetForegroundWindow() 同步获取前台 HWND（<1ms）
  → 排除浮窗自身（HWND 比对）和桌面（GetShellWindow）
  → koffi GetWindowTextW() 同步获取准确标题（<1ms，零编码损失）
  → 更新 cachedHwnd + cachedAccurateTitle
  → nut-js 异步获取 ActiveWindow（用于 paste 焦点恢复，失败不影响显示）
  → IPC 推送 → 渲染进程更新聚焦栏
```

**关键优势（相比原 hide/show 方案）**：
- 零闪烁：不隐藏浮窗，用户视觉无感知
- 零焦点丢失：输入框焦点和未提交内容保持完整
- 零延迟：koffi 同步调用 < 1ms，仅 nut-js 异步部分有延迟

**UI 设计**：

```
┌──────────────────────────────────────┐
│  聚焦：VS Code  ▼              [✕]  │  ← 应用名右侧加 ▼ 作为可点击提示
└──────────────────────────────────────┘
```

- 正常态：显示应用名 + 微弱 ▼ 图标
- hover：文字变亮 + ▼ 旋转或变色，title="点击重新捕获当前前台窗口"
- 点击后：短暂显示 "重新捕获中…" → 更新为新应用名
- 捕获失败：聚焦栏短暂显示 "未捕获到窗口" → 保持上次值

### 两种方案共存策略

1. **blur 自动重捕获**：静默运行，不打断用户，覆盖 80%+ 的切换场景
2. **聚焦栏手动重捕获**：显式入口，覆盖 blur 被 debounce 过滤掉或用户想确认切换的场景
3. 手动重捕获期间通过 `recaptureInProgress` 标志暂停 blur 自动重捕获（避免并发）

### 核心实现要点

**PasteCoordinator.recapture()**（koffi 零闪烁方案）：

```typescript
// 流程：koffi 同步获取 HWND → 排除浮窗/桌面 → koffi 获取标题 → 更新缓存 → nut-js 异步获取 ActiveWindow
async recapture(floatHwnd?: number): Promise<{ appName: string | null } | null> {
  const fgHwnd = GetForegroundWindow() as number;           // koffi 同步 <1ms
  if (!fgHwnd) return null;
  if (floatHwnd !== undefined && fgHwnd === floatHwnd) return null; // 排除浮窗自身
  if (fgHwnd === GetShellWindow()) return null;              // 排除桌面
  const title = getWindowTitle(fgHwnd);                      // koffi 同步 <1ms
  if (!title) return null;
  this.cachedHwnd = fgHwnd;
  this.cachedAccurateTitle = title;                          // 优先更新标题缓存
  // nut-js 异步获取 ActiveWindow（失败不影响标题显示）
  try { this.previousWindow = await this.inputInjector.captureActiveWindow(floatHwnd); } catch {}
  return { appName: extractAppName(title) };
}
```

**getCapturedAppName() 优先使用 koffi 缓存**：

```typescript
async getCapturedAppName(): Promise<string | null> {
  if (this.cachedAccurateTitle) return extractAppName(this.cachedAccurateTitle); // 优先
  const win = this.previousWindow;
  if (!win) return null;
  return extractAppName(await win.title); // 降级：nut-js 标题（可能含乱码）
}
```

**quickInputWindow.ts 防抖与互斥**：

```typescript
// 字段
private recaptureInProgress = false;              // 手动重捕获互斥标志
private recaptureDebounceTimer: NodeJS.Timeout | null = null; // 防抖定时器

// blur handler（pinned 模式分支）
win.on('blur', () => {
  if (this.pasteInProgress || this.recaptureInProgress) return;
  if (this.pinnedMode) { this.scheduleAutoRecapture(); return; }
  this.scheduleBlurClose();
});

// focus handler（取消防抖）
win.on('focus', () => { this.cancelAutoRecapture(); });

// 手动重捕获 IPC handler（recaptureInProgress 互斥）
ipcMain.handle(IPC_CHANNELS.RECAPTURE_TARGET, async () => {
  this.recaptureInProgress = true;
  try {
    const result = await this.pasteCoordinator.recapture(this.getFloatHwnd());
    if (result) this.win!.webContents.send(..., result.appName);
    return result;
  } finally { this.recaptureInProgress = false; }
});
```

### 防抖与去重

| 机制 | 参数 | 说明 |
|------|------|------|
| blur 自动重捕获防抖 | 200ms | `scheduleAutoRecapture()` → `setTimeout` 200ms，focus 恢复时 `cancelAutoRecapture()` 清除 |
| 聚焦栏点击防抖 | 300ms leading | 渲染进程 `quickInput.ts` 中 `bindFocusBarClick()` 使用 lodash-style leading-edge debounce |
| 手动/自动互斥 | `recaptureInProgress` | 手动重捕获期间 blur 自动重捕获被跳过（`recaptureInProgress` 检查） |
| paste/recapture 互斥 | `pasteInProgress` | paste 期间 blur 不触发自动重捕获（已有检查） |

## 四、边界场景

| 场景 | 预期行为 |
|------|---------|
| 锁定模式 + 点击桌面 | `captureActiveWindow` 返回 null → 忽略，聚焦栏保持上一次值 |
| 锁定模式 + paste 进行中 + blur | `pasteInProgress` 守卫 → 跳过自动重捕获 |
| 锁定模式 + 快速连续点击两个窗口 | 200ms 防抖 → 仅最后一次 blur 触发的捕获生效 |
| 非锁定模式 + blur | 现有行为不变（scheduleBlurClose） |
| 手动重捕获时捕获失败 | 聚焦栏短暂显示 "未捕获到窗口" → 回退到上次值 |
| 目标窗口已关闭 | `captureActiveWindow` 可能返回下一个前台窗口或 null，聚焦栏更新即可 |

---

## 五、不做的方案

| 方案 | 原因 |
|------|------|
| 轮询 `GetForegroundWindow`（setInterval） | 浪费 CPU，Electron 打包环境应避免不必要的系统调用 |
| Win32 `SetWinEventHook` 监听焦点变化 | 需要独立消息循环或 native addon，过度工程化 |
| 完全移除手动重捕获、仅用 blur | blur 无法覆盖"聚焦栏点一下确认当前目标"的场景 |

## 六、排雷报告（2026-07-20）

> 基于当前代码库实际状态（koffi FFI 已替代 PowerShell 标题获取）进行逐项风险排查。

### 雷 1（高）方案未反映 koffi FFI 架构变更

**现状**：qoder 已将标题获取从 PowerShell `Add-Type` 改为 `koffi` FFI 直接调用 `GetWindowTextW`（见 [pasteCoordinator.ts §L22-35](file:///f:/zooique/memora/hosts/memora-sprite/src/electron/windows/pasteCoordinator.ts#L22-L35)）。调用链为 `koffi.load('user32.dll') → GetWindowTextLengthW(hwnd) → GetWindowTextW(hwnd, buf, len)`，零进程启动、零编译开销（<1ms）。

**影响**：方案中所有提到"PowerShell 获取标题"的描述均需更新。`recapture()` 方法应直接使用 koffi `getWindowTitle(hwnd)`，而非走 nut-js title → 检测 U+FFFD → PowerShell fallback 的旧路径。

**建议**：更新 §三 关键代码骨架，将 `recapture()` 中的标题获取改为 koffi 直接调用。`getWindowTitle()` 已是 pasteCoordinator.ts 的模块级函数，可直接复用。

---

### 雷 2（高）方案 B hide/show 闪烁 + 丢失输入焦点

**现状**：方案 B 设计为"短暂隐藏浮窗（win.hide()，~50ms）→ 等待焦点稳定（~100ms）→ captureActiveWindow() → 恢复浮窗（win.show() + win.focus()）"。总计约 150ms hide→show 周期。

**问题**：
1. **可见闪烁**：150ms 的 hide→show 对用户可见，体验差
2. **丢失输入焦点**：如果用户正在浮窗中输入文字，hide 会丢失输入框焦点和未提交的输入内容
3. **不必要的复杂度**：有了 koffi FFI，获取前台窗口标题不需要隐藏浮窗

**建议**：用 koffi 替代 hide→show 方案：
```typescript
// 不隐藏浮窗，直接用 koffi 获取前台窗口标题
async recapture(floatHwnd: number): Promise<{ appName: string | null } | null> {
  // 用 koffi GetForegroundWindow 获取前台 HWND（需新增 koffi 绑定）
  const fgHwnd = GetForegroundWindow() as number;
  if (!fgHwnd || fgHwnd === floatHwnd) return null; // 排除浮窗自身和桌面
  // 获取准确标题
  const title = getWindowTitle(fgHwnd);
  if (!title) return null;
  // 更新缓存
  this.cachedHwnd = fgHwnd;
  this.cachedAccurateTitle = title;
  // 提取应用名
  const parts = title.split(' - ');
  const appName = parts.length > 1 ? (parts[parts.length - 1]?.trim() ?? title) : title;
  return { appName };
}
```
此方案零闪烁、零焦点丢失，且不需要 hide/show 时序。

**需新增 koffi 绑定**：
```typescript
const GetForegroundWindow = user32.func('int GetForegroundWindow()');
```

### 雷 3（高）PasteCoordinator 缺少 recapture() 方法设计细节

**现状**：方案 §三 提到 `PasteCoordinator.recapture()` 但只有骨架注释，缺少以下关键细节：

| 缺失项 | 说明 |
|--------|------|
| `previousWindow` 更新 | 重捕获后 paste 目标应指向新窗口，但 `previousWindow` 是 `ActiveWindow` 类型（含 `focus()` 方法），仅靠 koffi HWND 无法构造 |
| `cachedHwnd` 更新 | 需同步更新，否则 paste 时仍用旧 HWND |
| `cachedAccurateTitle` 更新 | 需同步更新，否则聚焦栏仍显示旧应用名 |
| 返回类型 | 方案定义为 `{ appName: string \| null } \| null`，但调用方（quickInputWindow）还需要知道是否成功以决定是否推送 IPC |

**建议**：`recapture()` 需要同时更新 nut-js `ActiveWindow`（用于 paste 时恢复焦点）和 koffi 标题缓存（用于显示）。完整流程：
1. koffi `GetForegroundWindow()` → 新 HWND
2. 排除浮窗自身和桌面
3. koffi `getWindowTitle(hwnd)` → 准确标题
4. nut-js `getActiveWindow()` → 新 `ActiveWindow`（用于 paste 恢复焦点）
5. 更新 `previousWindow`、`cachedHwnd`、`cachedAccurateTitle`
6. 返回 `{ appName, success }` 或 null

### 雷 4（中）方案 A blur 重捕获的 HWND 来源竞态

**现状**：方案 A 的 blur 事件触发时，浮窗已不是前台窗口。但 nut-js 的 `getActiveWindow()` 是异步的，在 `await` 期间前台窗口可能再次切换。

**建议**：在 blur 处理中，应先用 koffi `GetForegroundWindow()` 同步获取 HWND（零延迟），再异步调用 nut-js `getActiveWindow()` 获取 `ActiveWindow` 对象。HWND 用于标题获取（同步），`ActiveWindow` 用于 paste 焦点恢复（异步）。

---

### 雷 5（中）防抖 200ms 与 nut-js 异步延迟叠加

**现状**：方案设计 blur 后 200ms 防抖，防抖结束后调用 `captureActiveWindow()`。但 nut-js `getActiveWindow()` 本身需要 50-200ms（动态 import + native 调用）。实际用户感知延迟 = 200ms（防抖）+ 50-200ms（nut-js）= 250-400ms。

**建议**：
1. 防抖期间可以预取 HWND（koffi 同步，<1ms），只在防抖结束后做 nut-js 调用
2. 或者将防抖缩短到 100ms（koffi 已消除标题获取延迟，唯一延迟来自 nut-js）

### 雷 7（中）pasteInProgress 守卫存在时序窗口

**现状**：方案 A 在 blur 事件处理器中检查 `pasteInProgress`，但 paste 可能在防抖 200ms 期间启动。

**时序图**：
```
blur → 开始 200ms 防抖 → (150ms) paste 开始 → pasteInProgress=true
                                              → (200ms) 防抖到期 → 检查 pasteInProgress
```

如果 paste 在 150ms 时启动，防抖在 200ms 到期时能检测到 `pasteInProgress=true`，正确跳过。但如果 paste 在 210ms 时启动（防抖刚结束），则重捕获会与 paste 并发。

**建议**：在防抖回调执行时（而非 blur 时）检查 `pasteInProgress`，并在重捕获期间设置 `recaptureInProgress` 标志，paste 前检查此标志。

### 雷 8（中）手动重捕获与自动重捕获的互斥未细化

**现状**：方案提到"手动重捕获期间暂停 blur 自动重捕获（避免 hide() → show() 触发 blur 导致重复捕获）"，但未给出实现细节。

**建议**：如果采用雷 2 的建议（不 hide 浮窗），则手动重捕获不会触发 blur 事件，此问题自然消失。如果保留 hide/show 方案，需添加 `recaptureInProgress` 标志：

## 七、v2 修复记录（2026-07-20）

### 修复 1：recapture 后 paste 降级为 copy

**根因**：`recapture()` 中 nut-js `captureActiveWindow()` 在浮窗 `alwaysOnTop: true` 时返回浮窗自身（HWND 匹配 → 返回 null），导致 `previousWindow` 从未更新。paste 始终指向原始捕获窗口，切换焦点后无法粘贴到新窗口。

**修复**：`recapture()` 不再依赖 nut-js `captureActiveWindow`，改用 koffi `SetForegroundWindow` 直接构造合成 `ActiveWindow`：

```typescript
// 新增 koffi 绑定
const SetForegroundWindow = user32.func('bool SetForegroundWindow(int hWnd)');

// recapture() 中构造合成 ActiveWindow（绕过 nut-js 在 alwaysOnTop 时的 bug）
const syntheticWindow: ActiveWindow = {
  hwnd: fgHwnd,
  title: Promise.resolve(title),
  region: Promise.resolve({ left: 0, top: 0, width: 0, height: 0 }),
  focus: async () => { SetForegroundWindow(fgHwnd); },
};
this.previousWindow = syntheticWindow;
```

**影响**：recapture 后 `previousWindow.focus()` 通过 koffi 直接调用 Win32 `SetForegroundWindow`，彻底绕过 nut-js 的 `getActiveWindow()` 在 `alwaysOnTop` 场景下的 bug。

### 修复 2：简化标题显示

**变更**：删除 `extractAppName()` 函数（截取 "文档 - 应用名" 格式中的末段），`recapture()` 和 `getCapturedAppName()` 直接返回完整窗口标题。

**影响范围**：

| 文件 | 变更 |
|------|------|
| `pasteCoordinator.ts` | 删除 `extractAppName()`；`recapture()` 返回 `{ title }` 替代 `{ appName }`；`getCapturedAppName()` 返回完整标题 |
| `quickInputWindow.ts` | `result.appName` → `result.title` |
| `quickInput.ts` | `result.appName` → `result.title`；`QuickInputElectronAPI` 类型更新 |
| `preloadQuickInput.ts` | `recaptureTarget()` 返回类型更新 |
| `pasteCoordinator.test.ts` | 全部 `appName` 期望值更新为完整标题 |

## 八、v3 修复记录（2026-07-20）

### 修复 3：焦点切换只生效一次

**根因**：自动重捕获完全依赖浮窗 `blur` 事件。但 `blur` 只在浮窗自身失去焦点时触发——paste 后 `win.focus()` 在 `alwaysOnTop` 浮窗下焦点恢复不可靠，浮窗未真正获焦时后续点击不触发 blur，自动重捕获链断裂。

**设计思路**（qoder 风格）：不修 blur 事件（在不可靠机制上修 bug 是死循环），改用完全独立的检测机制——**koffi 轮询 `GetForegroundWindow()`**。

**修复**：

1. **`pasteCoordinator.checkAndRecapture(floatHwnd)`** — 同步方法，供 `setInterval` 轮询：
   - koffi `GetForegroundWindow()` 获取前台 HWND（同步，<1ms）
   - 与 `cachedHwnd` 比对，未变化直接返回 null（零开销）
   - 变化时执行完整重捕获 + 构造合成 `ActiveWindow`
   - 返回新标题或 null

2. **`quickInputWindow` 轮询机制**：
   - `startPolling()`：pinned 模式启动时开始 300ms 间隔轮询
   - `stopPolling()`：退出 pinned 模式 / hide / destroy 时停止
   - `pollAndRecapture()`：轮询回调，检查 `pasteInProgress`/`recaptureInProgress` 互斥

**架构关系**：blur 事件保留作为快速路径（~0ms 响应），轮询作为可靠性兜底（最坏 300ms 延迟）。两者独立，互不干扰。

**新增测试**：5 个 `checkAndRecapture` 测试覆盖——变化捕获、未变化跳过、浮窗排除、桌面排除、连续切换。
