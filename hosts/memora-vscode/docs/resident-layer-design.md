# 常驻层（作品投影的 resident 字段）设计定稿

> 状态：**已定稿**（九条决策已拍板直接落地）；本文档只描述设计与边界，不含实现代码。
> 定位：设计 + 排雷结论。现状均为实测并带**符号引用**（文件 + 函数 / 类 / 成员名）。
> 日期：2026-11-08
> 一句话：作品投影条目加一个布尔字段——`true` 的条目正文每轮注入 system prompt 固定段并永久生效；`false` / 缺失者维持原能力（只给简介，模型按需 `read_file`）。
> **引用口径**：本文档引用代码一律用**符号**（文件 + 函数 / 类 / 成员名），**不写行号**——行号随实现漂移，符号不会。

### 1.3 system prompt 层结构（注入位置的证据）

`buildSystemPromptPrefix` 的分段顺序（实测，`src/agent/assembler.ts`）：

```
① rolePackPrompt      ← 角色包段（personaPrompt；角色 rules 在 personaPrompt 内）
② globalSkillList
③ SKILL_WRITE_LOCATION_PROMPT
④ workProjectionContext
⑤ environmentContext
⑥ 当前时间
⑦ TURN_START_STRATEGY_PROMPT
--- 分隔线 ---
```

- **角色 rules 在哪（关键）**：角色包的 `## 规则` 段由 `strategyResolver.ts` 拼进 `personaPrompt`，`personaPrompt` 再作为 `rolePackPrompt`（第 ① 段）传入。故「角色 rules 之后」= **插入点在第 ① 段之后**。
- **工具描述在哪**：工具描述**不在** `buildSystemPromptPrefix` 里。system message = `prefix + buildSystemPrompt(memories)`，工具描述在**后段**的 `## 可用工具` 里（`src/agent/loop.ts`，拼接点 `src/agent/loop.ts`）。
- **结论**：常驻段插在 ① 与 ② 之间，天然满足「角色 rules 之后、工具描述之前」。

## 2. 目标与非目标

### 2.1 目标（收敛为三件事）

1. **作品投影条目上多一个布尔字段** `resident`：`false` / 缺失 = 原能力（只提供简介、模型自行决定是否读）；`true` = 被「项目级文件加锁」取用，**正文每轮永久注入**。
2. **每轮按常驻清单读正文**，注入 **system prompt 固定段**（不是当附件塞进对话）。
3. **读不到就说读不到**：条目指向的文件不存在时**可见失效**，禁止静默跳过。

其余硬要求（全部保留，不在本节扩张）：

- 只接受**工作区相对路径** + **工作区信任门**（§7.1-1、§7.1-2）。信任态由**宿主作为新入参**传给内核；装配期内核不做 `isTrusted` 现读（内核无此态）。
- 两种锁**视觉可分**（§8）。
- **优先级写死**：项目常驻 > 角色 rules > 资料；< 安全铁律（§4.3）。
- **单条 6000 字符 / 合计 15000 字符上限**；添加或置常驻时**当场拒绝**并回报占用。装配期因外部改动：**单条超限 ⇒ 剔该条 + 汇总提示**；**仅合计超限 ⇒ 整段不注入 + 一条显式提示**；两者都不阻断发送（§6.1）。
- **顺序 = 清单数组顺序**（先添加者优先；删除条目后其余顺延前移）（§3.3）。
- 凭据防护：**复用已导出的判据面**（`isBlockedPath` / `matchBlockedPathPattern`，P0-a 落地），禁止复制第二份；**本期只防凭据路径，内容夹带不防**（§7.1-4）。
- 项目级变更**对所有会话实例生效**（§5.8、§10）。
- **失效判定只用文件存在性判断 + 与清单声明集合比对，不引入任何 git 调用**（§6.2）。

### 2.2 非目标（边界）

- **不另立清单文件**（推翻上一轮 `.memora/resident-rules.json`，见 §11.2）。
- **不改变非 `resident` 条目的任何行为**：索引渲染对它们逐字不变。
- **不做规则引擎**：无通配符、无 glob、无目录扫描、无条件判断、无自动发现。
- 不改变临时锁（`pinned`）的任何行为。
- 不做**会话级**常驻、不做**文本来源**常驻、不做**技能常驻**。
- 不做**独立清单面板**、不做**跨面板角标**（本期以命令回执承载反馈，§10）。
- 不做本轮之外的一切覆盖（完整清单见 §7 设计边界）。

### 2.3 文本来源被砍的后果（必须写明，避免后人误以为漏做）

- 用户此前**每天手打**的规则句（例如「遵守 SSOT / 自然生长 / 不带伤」）今后**不能再直接粘进输入框**变成常驻规则。
- 想永久生效，必须：**先把规则落到一个工作区文件**（如 `docs/<你的规则文件>.md` 或任意已有文档；此处是示例占位，不是本稿引用的文件），再把该文件「提升为项目规则」（`resident = true`，§8.1）。
- **不存在**「常驻规则文本输入框」；这是**已拍板的裁剪**，不是待补项。

## 3. 数据模型

### 3.1 条目形状（在既有三字段上增一个布尔）

```
WorkProjectionEntry {
  name: string          // 必填；读取过滤器依赖，缺失即整条被丢弃（§5.4）
  description: string   // 必填；常驻后只服务清单展示（§5.6）
  source: string        // 必填；首根相对规范形（relativeUnderPrimaryRoot，§7.1-1）
  resident?: boolean    // 新增；只有严格 `=== true` 才算常驻（§5.5 fail-closed）
}
```

顺序由清单数组天然表达，不另存顺序字段（§3.3）。

> **术语锚点（防撞车）**：本稿 `resident` = **项目规则常驻**（条目正文每轮注入）。
> 代码另有 `capabilityState.kind === 'residentOnly'`（**常驻工具**，宿主 `capabilityState.ts`、`roleBadgeView.ts`），**两者语义无关**。命名 / 注释 / 文案不得用同一个「常驻」把二者折叠（本仓「措辞折叠」纪律）。

### 3.2 两态语义（不是三态）

| `resident` | 语义 | 消费面 |
| --- | --- | --- |
| 缺失 / `false` / 任何非 `true` 值 | 原作品投影 | 只进【项目索引】注入块，模型按需 `read_file` |
| 严格 `true` | 项目常驻规则 | 正文进「项目常驻规则」固定段；**不进索引注入块**（§4.4） |

### 3.3 顺序与删除

- **顺序真源 = 清单数组顺序**（先添加者在前）；常驻段渲染、清单展示、优先级「靠前者优先」全部读同一个顺序。
- **删除条目后其余顺延前移**（不保留空位）——上一轮「保留稳定序号」的要求**已作废**：跨时间稳定的身份是 `source`，不是序号。
- 取消常驻（`resident → false`）不移动数组位置；重新置常驻回到它当前的数组位置。

## 4. 注入位置与优先级

### 4.1 注入位置（定稿）

```
systemPromptPrefix:
 ① rolePackPrompt（personaPrompt，含角色包 ## 规则）
 ② 【项目常驻规则段】← 唯一新增
 ③ globalSkillList
 ④ SKILL_WRITE_LOCATION_PROMPT
 ⑤ workProjectionContext（索引注入块；常驻项已从该块剔除）
 ⑥ environmentContext
 ⑦ 当前时间
 ⑧ TURN_START_STRATEGY_PROMPT
 --- 分隔线 ---
system message 后段：记忆设定段 → 回应骨架 → ## 可用工具（工具描述）→ 工具叙事纪律 → 只读态事实段
```

- 插在 ① 之后 = **角色 rules 之后**；在 ② 之后才是工具描述所在的后段 = **工具描述之前**。
- **禁止**追加到 `buildSystemPrompt` 尾部（那会让规则落到工具描述之后，语义降级为资料）。

**实现口径**：`buildSystemPromptPrefix` 增**第 6 个可选参数** `residentRulesContext`，但**渲染位置固定排在 `rolePackPrompt` 之后**——参数放尾部只为不动既有 5 个位置参数调用点（`assembler.ts`、`agent.ts`；实测均为位置传参）。

**每轮刷新口径（实测依据，订正）**：每轮重建前缀的真落点是 `prepare.run()` 里的 `refreshAssemblyForRolePack(...)`（`src/agent/seed/prepare.ts`），它内部调 `deps.refreshRolePackPrefixForRound`（同文件的自由函数，**不是**独立的每轮重建）。位置关键：`prepare.run` 在 `await contextPreparer.assembleContext(input)` **之前**调用 `refreshAssemblyForRolePack`。因此「每轮按清单读正文」的落点是：在 `refreshAssemblyForRolePack` 之前先 `await` 一次「刷新常驻上下文」（重读清单 JSON + 每个常驻正文进缓存），再由同步重建收口。**按旧稿字面插在 `refreshAssemblyForRolePack` 内部会首轮用旧缓存、规则晚一轮生效**。不得在同步函数里做磁盘 IO。

### 4.2 段内格式（定稿）

```
## 项目常驻规则（本仓库具体约束；按清单顺序，靠前者优先）
- 适用范围：仅「具体约束」冲突；不改变角色职责与工具边界（角色是只读审查员时，本段不会让它变成改码角色）。
```

### 4.3 优先级（写死 + 理由成文）

**项目常驻规则 > 角色包 rules > 技能清单等资料；但 < 安全铁律 / 硬约束。**

**适用边界（与 §4.2 段首文案同源）**：本优先级只解决**同一事项的具体约束冲突**，不改变**角色职责与工具边界**——职责冲突（如角色是只读审查员、常驻规则要求改代码）不属于本优先级的裁量范围，不得据此把角色架空。

> 已订正原因：范围变了（P1 把「优先级声明句」拉入本批），非原稿写错——原稿把「高于角色包 rules」写成了无限定全称句，会让常驻层被读成可以覆盖角色职责。

理由：

1. **为什么高于角色包 rules**：角色包是**跨项目复用的通用模板**，项目常驻规则是**针对本仓库的具体约束**。具体优先于通用——否则换个角色包就会把本仓库的约束稀释掉。位置上也自洽：常驻段排在角色段**之后**，物理上更靠近用户消息。
2. **为什么低于安全铁律 / 硬约束**：安全铁律在本仓**由代码闸门执行**（权限档位 / deny 判据 / 工作区信任门 / 只读态事实段），**不靠 prompt 文本自证**。任何 prompt 层文本（包括常驻规则）都**不可能绕过代码闸门**；因此「低于安全铁律」是执行面的硬事实——常驻规则只能约束「闸门之内怎么写」，不能放宽闸门。
3. **同层内的顺序**：**清单中靠前者优先**（先添加者优先）。**只在段首写声明（§4.2 那三句）**，不逐条重复标注（逐条重复更稳但费 token，本期不采用）。
   - 残余风险（登记）：LLM 注意力天然偏向靠近用户消息的文本（即靠后的条目）。若实测仍偏移，缓解项是逐条重复标注（本期不做，登记为已知偏差）。

### 4.4 两个展示面分开：注入块剔除，界面照常列出

必须把两件事分开读，否则会误以为「常驻项隐身」：

| 面 | 常驻项（`resident === true`） | 非常驻项 |
| --- | --- | --- |
| **注入块的【项目索引】** | **剔除**（不出现） | 照常出现一行简介 |
| **清单（临时 QuickPick）** | **照常列出**，并打「**项目规则**」标记 | 照常列出，无标记 |
| **右键入口** | **只反映当前文件状态**（菜单项变「取消项目规则」） | 只反映当前文件状态（菜单项变「提升为项目规则」） |

> 右键菜单**列不出清单**——它只对「被点的那个文件」呈现状态，不是清单展示面；清单由 QuickPick 承载（§8）。

**为什么注入块剔除**：

1. **两份真相**：同一文件若既以简介出现在索引、又以全文出现在常驻段，模型会看到同一对象的两种描述；按简介再 `read_file` 一次的概率上升，token 与行为都翻倍。
2. **语义冲突**：索引的语义是「目录，按需读取」，常驻的语义是「正文已在此，无需读取」。把常驻项留在索引等于告诉模型它还该按需读。
3. **「只留『已常驻』标记」同样不可取**：那仍制造第二处引用，且标记本身不携带任何决策信息（全文就在下一段）。

**为什么清单不能剔除**：条目仍在清单里，用户必须看得见、能取消——清单隐身 = 用户失去解除能力。两个面读同一份数据，只是渲染规则不同。

## 5. 复用作品投影：四条取证 + 五道前置闸

### 5.1 为什么复用同一份文件

- 用户拍板：省一个文件，且「常驻」天然是投影条目的一个属性，不是第二个实体。
- 上一轮判「不复用」的两条理由（整文件重写导致并发覆盖、读取方按全投影解析）**不是不可跨越的边界，而是待解决缺陷**。本稿把它们升为**前置闸**（§5.3、§5.4、§5.5）后，复用成立。
- 不掩盖结论变更：上一轮的取证没有错，错的是「用避开缺陷换安全」的取向；本轮改为「先修缺陷再接」。

### 5.2 四条取证（复核，本轮结论：**复用，条件成立**）

| # | 取证项 | 实测结果 | 对本设计的影响 | 位置 |
| --- | --- | --- | --- | --- |
| 1 | schema 是否有「类型 / 用途」判别字段 | **没有**类型字段；但本设计只需一个二值判别（常驻 / 非常驻），一个布尔字段即可表达，不需要多类型体系 | 可扩展：加 `resident` 足够 | `workProjection.ts` |
| 2 | 写入方与方式（**决定性**） | **整文件重写**；`registerWork` 先 `refresh()` 读全量进内存 → 合并/追加 → 把整份内存数组写回。写入已在模块级 `withFileWriteQueue` 内串行（P0-b） | 持久化形态可复用（闸 A 已落地） | `workProjection.ts` 的 `registerWork` 与 `withFileWriteQueue` |
| 3 | 读取方与误读面 | `filter(e => e && e.source && e.name)` 会**静默丢弃缺字段条目**；`contextBlock()` 把每条一律渲染成投影行 | **新条目必须补齐 name/source**（闸 B）；**常驻项必须从注入块剔除**（闸 D） | 过滤在 `refresh`；渲染在 `contextBlock` |
| 4 | 原子写 / 损坏 fail-safe / 并发写 | 有 `atomicWriteFile` 与损坏拒写；**进程内写已串行**（P0-b）；实例每会话一个 | 持久化形态可复用；跨进程并发仍不覆盖（§5.3） | `workProjection.ts` 的写盘段与损坏 fail-safe；实例 `assembler.ts` |

**判定标准（写进设计，供同类问题复用）**：

- 结构天然可扩展 + 写入可串行化或已是局部更新 + 误读面可列全 ⇒ **可复用**。
- 写入整文件重写且**无法**串行化，或存在无法修正的「全投影」消费方 ⇒ 不复用，另立清单。
- 证据不足 ⇒ 写「未查实」，列明需要什么证据，**不许猜**。

### 5.3 前置闸 A（决定性）：写路径必须先串行化

**事实三条（实测）**：

1. 写入是整文件重写（`workProjection.ts`）。
2. 实例是每会话一个（`extension.ts` 按 sessionId 取 Agent；`assembler.ts` 每 Agent 新建 manager），全部指向同一文件。
3. 工具层已有写串行闸（`diskWrite:'opaque'`，`loop.ts`），但**只在单个 AgentLoop 内生效**；宿主命令直调 `agent.works.registerWork`（`registerWork.ts`），**绕过闸门**。

**后果（推断，依据代码结构；未跑实测复现）**：两个会话，或「某会话的模型工具 + 用户右键命令」并发时——A 读盘 → B 读盘 → A 写 → B 写 ⇒ A 的 `resident: true` 被 B 的旧快照覆盖。

**方案对比**：

| 方案 | 覆盖实测面（同进程多会话 + 宿主命令） | 覆盖跨进程 | 代价 | 取舍 |
| --- | --- | --- | --- | --- |
| **进程内「按文件路径的 Promise 队列」+ 临界区 reread** | ✅ | ❌ | 零依赖，约十几行 | **采用** |
| 单实例注入（每项目一个 manager 共享） | ✅ | ❌ | 要改 Agent 装配链（`assembler.ts` 每会话建）与公开面 | 不采用：改动面更大，收益相同 |
| 真文件锁（`proper-lockfile` 等） | ✅ | ✅ | 新增三方依赖 + 锁残留/超时语义 | 不采用：内核口径为零三方依赖（`workProjection.ts` 注释），且锁失效的代价高于丢失一次勾选 |
| 只加「写前 reread」（无互斥） | ❌ | ❌ | 最小 | 不采用：读-改-写窗口无互斥，交错照旧 |

**选定落地细节**：

1. **锁键 = 绝对文件路径**；队列容器放**模块级 Map**（不是实例字段）——实例每会话一个，实例级队列等于没锁。
2. 临界区顺序固定：**锁 → `refresh()` 重读盘 → 合并 → `atomicWriteFile`**。
3. **所有写函数都必须走同一队列**：`registerWork` 与新增 `setResident`；**禁止**出现第三个写盘点（宿主、webview、设置页一律只调用这两个）。
4. 失败语义沿用工具层口径：队列任务异常不毒化后续（同 `loop.ts` 的「链尾吞失败」）。
5. 损坏 fail-safe 保持在临界区内先判（`refresh` 置 `fileWasMalformed` → `registerWork` 先判）：文件坏 ⇒ 拒写，不覆盖用户原索引。

**跨进程：本期不做，但必须有可见兜底**：

- 覆盖范围只有**本 extension host 进程内**。同一文件夹开两个 VS Code 窗口、或用编辑器同时改 JSON，后写会覆盖先写。
- **兜底（新增一小段检测，不是解决）**：每轮以磁盘为准重读；**与「清单声明的常驻集合」比对**（不是与上一轮快照比对），并**分开判定**：
  - **声明有、读不到**（`resident === true` 但文件不存在 / 非文本）⇒ 该条**失效**，装配段首汇总一行。
  - **声明没有、盘上无关**（清单里 `resident` 已为 `false` 或条目已删）⇒ **正常操作**，不报警。
  - ⚠️ 旧写法「与上一轮集合做差」有两个洞：① 差集方向不会误报「全部失效」（重启后上一轮为空、结果为空），但**检测盲区**是「重启期间与新会话内发生的丢失」查不到；② 差集无法区分「被覆盖丢失」与「另一窗口主动取消」，后者会**假报警**。改为对清单声明的集合判定即同时解掉这两点。
- 因此这是「**可见的丢失**」，不是「已解决」：那一轮规则确实没生效，但用户能看到哪一条没了、能重新置常驻。**不得**把它写成「并发已解决」。
- 验收用例（**已落地，P0-b**）：N 个不同 `source` 并发 `registerWork` ⇒ 盘上 N 条；同 `source` 并发 ⇒ 单条且未知字段保留。`setResident` 与 `registerWork` 并发用例待 `setResident` 落地后补。

### 5.4 前置闸 B：新入口必须补齐 `name` 与 `source`

**事实**：读取入口 `refresh` 的 `filter(e => e && e.source && e.name)`——缺字段 = **整条记录消失**，不是「未常驻」。

**落地规则**：

1. 条目创建**只允许**走 `registerWork`（它负责 `name` / `source` 规范化）。
2. `setResident(sourcePath, resident)` **只翻字段**：返回**六态结果**（§6.1），条目不存在时 `reason: 'not-found'`，**绝不创建**；置 `true` 时先读正文判两道上限（未信任先拒、不读），置 `false` 不读正文、不判上限。
3. 用户「置常驻」对**未登记**文件：先走登记（含 LLM 描述）→ 再 `setResident(true)`；两条写各自进同一队列（可合并为一次临界区，非必需）。**右键快捷入口按同一顺序执行**（§8.1），不得反过来先置位再补登记。

**A 级缺口（**已修，P0-b 已落地**）**：

- **事实（修复前）**：`registerWork` 对已存在的 `source` 是**整条替换**，新对象只带原三字段 `name` / `description` / `source` ⇒ 既有条目的 `resident: true` 与任何未来新增字段**被静默丢弃**。
- **触发者包括本版本的模型工具 `register_work`**（不是只有手改才会发生）：模型对同一文件再登记一次，项目规则就没了，且**无任何提示**。
- **处置（已落地）**：`registerWork` 已改为**合并式 upsert**——命中同 `source` 时**保留既有 `resident` 与未知字段**，只覆盖 `name` / `description`。
- **测试（已落地）**：见 `workProjection.test.ts` 的「`registerWork` upsert（保留未知字段）」两条——已常驻条目再登记后 `resident === true` 仍在；手工塞入未知字段 `x-extra` 重登记后仍保留。

**显式用例（必须落成测试）**：

- 反例钉死：手工写 `[{ "source": "<工作区内的某个 .md 文件>", "resident": true }]`（无 `name`）⇒ 重新加载后该条**消失**。
- 正例：登记 → 置常驻 → 重新加载后仍在，且 `name` / `source` 齐全。
- 越界反例：`setResident` 对不存在的 `source` **不得**产生新条目（尤其不得产生「只有 path + resident」的条目）。

### 5.5 前置闸 C：`resident` fail-closed

**判据唯一写法**：`entry.resident === true`（严格相等）。

| 输入 | 结果 |
| --- | --- |
| 字段缺失 | `false`（原投影） |
| `false` / `null` / `0` / `""` | `false` |
| `"true"`（字符串） / `1` / 对象 / 数组 | `false` |
| 严格 `true` | 常驻 |

- **禁止**把 `resident` 加进 `refresh` 的加载 filter——那会把「字段缺失」从 `false` 变成「记录消失」。
- **禁止** `Boolean(entry.resident)`（`"false"` 会变 `true`）。
- 用例：上表每种畸变输入 ⇒ 条目仍在清单 / 索引中、常驻段不出现。

### 5.6 前置闸 D：`description` 定位与自动总结

**`description` 定位**（由 §4.4 决定）：常驻项不进注入块 ⇒ 模型侧不消费 ⇒ **只服务界面展示**。

**自动总结仅发生在首次登记**：

- ✅ **首次登记**（文件尚未进清单）必然触发既有 LLM 总结（`registerWork.ts`）——这是既有能力，不需要新机制。
- ❌ **已登记条目转常驻不再触发**：文件内容未变，description 已存在，重复调用只会多花一次 LLM 调用、只改界面文案，对模型行为零收益。
- 可选（不进必做）：若 description 曾由文件名兜底（LLM 失败时走 `registerWork.ts` 的文件名兜底段），可在首次置常驻时复用**同一条**生成通道重试一次。

### 5.7 兼容面（旧读取方与旧数据）

| 面 | 结论 | 依据 |
| --- | --- | --- |
| 旧数据（无 `resident`） | `=== true` 不成立 ⇒ `false` ⇒ 索引输出**逐字不变** | 渲染只看 `name/description/source`（`contextBlock`） |
| 旧读取方 | `filter` 不看 `resident`；注入块的剔除只影响 `true` 条目 | `refresh` 的 filter、`contextBlock` |
| 公开成员面 | 新增 `setResident` 会与守卫基线冲突 ⇒ **必须同笔更新基线**，否则测试红 | `publicMemberSurfaceGuard.test.ts` |
| 文档漂移 | `docs/architecture/work-projection.md` 现写「全部条目进索引」；实现时须同步（本稿不改该文件） | 该文件非本笔改动范围 |
| 工具描述 | `register_work` 描述需补一句「是否常驻由用户开关控制」 | `builtinTools.ts` |

### 5.8 唯一真源规则

1. **清单文件唯一**：`work-projections.json`；不另立第二份。
2. **写函数唯一**：所有变更经同一队列 + `registerWork` / `setResident` 两个入口。
3. **常驻判据唯一**：`=== true` 只写在一处（导出成单函数，其余读同一函数）。
4. **顺序真源唯一**：清单数组顺序（不另存顺序字段、不派生第二套排序）。
5. **注入块与清单展示面同源同文件，但渲染规则不同**（§4.4）。
6. **项目级变更对所有会话实例生效**：语义生效靠「每轮读盘」（§4.1），不依赖推送通道。

## 6. 上限与失效（两组硬判据）

### 6.1 字符上限：两道闸（缺一即未收口）

| 闸 | 时机 | 行为 | 判据 |
| --- | --- | --- | --- |
| **主闸（写路径）** | `setResident`（内核）置常驻时先读正文统计 | 超限 ⇒ **内核当场拒绝**（六态结果，`message` 给计量构成与差额）；宿主只显示该 `message` | `resident` 保持 `false`；无静默截断；未信任先拒（`untrusted`），不读正文 |
| **保底闸·单条** | 每轮装配前，按磁盘最新内容复核 | **单条超限** ⇒ **只剔该条** + 段首汇总一行（其余常驻项照常注入） | 明示「某条超限未注入」；不得整段陪葬 |
| **保底闸·合计** | 同上 | **仅当合计超限**（单条都在线） ⇒ **常驻段整段不注入 + 一条显式提示**，不阻断本轮发送 | 提示上屏 + 明示「本轮常驻规则未生效」；不得只截前半段当规则 |

**口径（必须标注）**：

- **单条上限 6000 字符、合计上限 15000 字符**——这两个数是**可调政策线，不是实测结论**。
- **重算口径一句话**：先把「常驻段允许占用的上下文比例」定死（建议 ≤ 上下文窗口的 20%），再用实测的「字符 → token」换算修正这两个数；每次修订都要带「时点 + 重算依据」，否则就是裸快照。
- **判据只用字符数**（`String.length`），**不把 token 估算作为闸门**——两把尺子会得出两个「超限」结论。
- **禁止**把 `registerWork.ts` 那套「截前 8000 字」的描述用裁切混进正文读取。
- **粒度不打架（订正）**：单条超限 ≠ 合计超限。单条超限只剔该条（§6.2 与「单条失效」同处置）；只有**合计**超限才整段停用。旧稿写「超限 ⇒ 整段不注入」与 §6.2「单条失效只剔该条」冲突，已拆开。
- **常量只活在内核**：6000 / 15000 是内核私有常量，**不从包根导出**；宿主不参与判断、也不需要知道数值，只显示 `setResident` 返回的 `message`。将来界面若要在按钮上预判「点了会超限」，做成内核方法返回**同构结果**，仍不导出裸数字。
- **拒绝文案必须给差额**：`too-long` / `total-too-long` 的 `message` = 「实际计量（含构成）+ 上限 + 差额」。例：`该文件含标题行共 6021 字符，超过单条 6000 上限 21 字符`。只报「超限」会让用户以为系统算错（他的正文可能只有 5960 字符）。

**计量口径（定稿）**：

- **合计 15000 = 最终注入段的字符数**（段标题 + 优先级文案 + 各条渲染块 + 失效汇总行），**不是「各正文长度之和」**——上限的目的是控制上下文占用，占额度的是实际发出去的东西，不是清单里的理想值。
- **单条 6000 同口径**：按**该条渲染块**（`### 来源文件：<path>` 标题行 + 正文）算，不按裸正文算。两把尺子会让同一文件在边界上得出两个结论。
- 计量单位一律 `String.length`（UTF-16 码元），不引 token 估算。
- **不含**段间分隔符（`\n\n---\n\n` 由 `buildSystemPromptPrefix` 拼接，不属于本段）。
- **求值顺序（消循环依赖）**：① 先定逐条失效集合（路径 / 二进制 / 单条上限，均不依赖总数）→ ② 按该集合渲染整段 → ③ 再判整段长度 → ④ 合计超限 ⇒ **整段降级为一条状态行**。因合计超限被拿掉的条目**不进失效汇总**（那是降级后果、不是失效）；否则汇总行长度反向影响总数判定，形成循环。

> **有意例外（不得「修正」）：沿用缓存时追加的「本次读取失败，沿用上次内容」一行不计入 15000 预算。**
> **原因（自噬链）**：若计入——上次渲染贴着 15000 ⇒ 本次读失败追加标注 ⇒ 越限 ⇒ 整段降级 ⇒ 常驻规则被抹掉，恰好反噬「已有缓存必须沿用」这条自身。因此看到「段实际长度超过 15000 且带失败标注」是**设计预期**，不是越限；把它算进预算的「修复」会让降级路径静默抹掉规则。
> 边界：例外**只**覆盖那一行标注；其余段首文案（标题、优先级、失效汇总行）照常计入。

### 6.2 失效可见（禁止静默跳过）

| 失效场景 | 检测点 | 处置 |
| --- | --- | --- |
| 文件被删除 / 改名 / 移动 | 装配前 stat（复用 `refProbe.ts` 的 stat 思路） | 该条**标失效**、**正文不注入**；装配段首**一行汇总条数与路径**（模型可见）；界面红点属 UI 批次 |
| 文件无法读取（权限 / IO 错误） | 读盘异常 | 同上 |
| 文件变成二进制 / 非 UTF-8（登记后才变） | 装配期读盘时做一次 **fatal UTF-8 解码复核**（§7.1-9） | 该条判失效、正文不注入；段首汇总 |
| 被移出工作区 / 变成绝对路径 / `..` 逃逸 | 每次装配都过 `resolveUnderPrimaryRoot`（与写入侧 `relativeUnderPrimaryRoot` 同一文件、互逆，`refPath.ts`） | 判为失效；**拒绝读盘** |
| 符号链接指向工作区外 | realpath 复核——`resolveRealpath` 已导出（P0-a），复用同一实现（禁止复制第二份，`pathGuard.ts`） | 判为失效 / 拒绝；不得按字符串路径放行 |
| 条目被外部覆盖 / 另一窗口主动取消 | **与「清单声明的常驻集合」比对**（不是与上一轮快照比对）：声明有、读不到 ⇒ 失效；声明没有、盘上无关 ⇒ 正常取消，不报警 | 失效者段首汇总 + 命令回执；正常取消**不报警**（§5.3 兜底） |
| 工作区未信任 | **宿主传入的信任态（新入参）**——内核无 `isTrusted` 态，装配期不能现读（§1.5） | **整层不装配** + 显式提示，不是「跳过某条」 |

> 「失效」与「未信任」都必须是**被记录的错误态**；未信任的工作区里静默不带规则，会重演「静默失败 = 假阴性」。
>
> **用户可见面的边界（本批做不到的必须写明）**：未信任 ⇒ 由宿主既有 `syncTrustNotice` 状态栏提示承担（已在册）；**失效汇总的段首一行是给模型看的**，界面红点 / 用户可见的降级提示属 **UI 批次**。验收时不得拿段首标注当「已告知用户」。

**读盘失败的三分支（fail-closed 与「不静默抹掉规则」并存）**

| 状态 | 行为 | 理由 |
| --- | --- | --- |
| 未信任 | 清空缓存 + 空段 | fail-closed 的硬面，与读盘成败无关 |
| 已信任 + 读失败 + 有缓存 | **沿用缓存** + 段首追加「本次读取失败，沿用上次内容」 | 一次 IO 抖动抹掉项目约束，比内容过期危险得多；该行不入 15000 预算（§6.1 有意例外） |
| 已信任 + 读失败 + 无缓存 | 空段 + 日志 | 没有可沿用的内容 |

读盘异常**不得中断** prepare / resume：降级后照常继续本轮（这是把「每轮读一次」引入新失败点的对价）。

> 已订正原因：范围变了（P1 把正文注入与读盘失败兜底拉入本批），非原稿写错——原稿未区分「未信任」与「已信任但读失败」两种降级。
>
> **失效判定的唯一手段 = 普通文件存在性判断**（stat / 读盘 ENOENT / 上面的路径守卫），**禁止**为此引入任何 git 调用：文件是否被版本控制跟踪与本能力无关。
>
> 与 §6.1 保底闸的区别（订正后）：**单条超限 / 单条失效 ⇒ 只剔该条 + 段首汇总**；**仅合计超限 ⇒ 整段不注入**。两者都报错，都不阻断发送。

| 7 | **工作区外路径** | 绝对路径 / UNC / `..` 一律不可登记、不可常驻 | 有：命令报错「只支持工作区内相对路径」 |

### 7.1 硬拒绝项（不接受的东西）

1. **只接受工作区相对路径、且为规范形**：**统一调用宿主单点判据 `toWorkspaceRelativePath`**（`workspaceRelativePath.ts`，判据委托 `refPath.ts` 的 `relativeUnderPrimaryRoot` / `resolveUnderPrimaryRoot`），`undefined` **当场拒绝**；绝对路径 / UNC / 任何 `..` 段 / 非规范形一律拒。⚠️ 内核写入守卫 `resolveSafePath`（`workProjection.ts`）是**另一层**（防写出项目根），不得当作与宿主生成侧同源。
2. **受工作区信任门约束**：信任态由**宿主作为新入参**传入内核（未信任 ⇒ 整层 fail-closed）。内核侧无 `isTrusted` 态，装配期现读在物理上做不到；这是**内核公开面变更（minor）**，不是文档能自行实现的。
3. **符号链接逃逸**：`relativeUnderPrimaryRoot` 不 realpath ⇒ 读盘前必须 realpath 复核仍在首根内。`resolveRealpath` 已导出（P0-a），复用同一实现，**禁止复制第二份**。这是安全闸，不因「子模块/链接语义」未覆盖而放宽。
4. **凭据类路径拒绝（复用已导出判据）**：`pathGuard.ts` 的黑名单常量是模块私有，但**判据已导出**（`matchBlockedPathPattern` / `isBlockedPath`，P0-a 落地）⇒ 复用同一实现，禁止复制第二份。即使在工作区内，也不该把 `.env` / `.npmrc` / `.git-credentials` 每轮读进 prompt；常驻比索引更危险（**永久**注入）。⚠️ **它只匹配路径**——证据不足时**不敢写「已防凭据内容」**：本期只防凭据路径，正文内容夹带不防（§7-15）。
5. **不做规则引擎**：无通配符、无 glob、无目录扫描、无条件判断、无自动发现；一个条目只对应一个具体文件。
6. **不自动迁移**：不做 `.memora/rules.md` 迁移，不把临时锁自动转常驻。
7. **禁止绕过写队列**：宿主、webview、设置页一律不得直接读写 `work-projections.json`；手改文件属外部写入，只由损坏 fail-safe 与「**与清单声明集比对**的失效检测」兜底。
8. **禁止同一文件两处注入**：常驻项不得同时留在【项目索引】注入块（§4.4）。
9. **非文本文件拒绝（作用域仅限新入口「提升为项目规则」）**：
   - **判据（最小化，二选一命中即拒）**：读取内容**含 NUL 字节**（`buf.includes(0x00)`）；或**按 UTF-8 解码失败**（`new TextDecoder('utf-8', { fatal: true })` 抛错）⇒ 提示「该文件不是文本文件，不能作为项目规则」。
   - **原子性**：**不登记、不置位、不留半成品**；不做扩展名 / 魔数嗅探（§7-9 已改口径）。
   - **执行点（两侧都要）**：① 新入口的宿主命令读取段（与 `registerWork.ts` 同层），在调 `registerWork` / `setResident` **之前**；② **装配期读正文时再做一次 fatal 解码复核**（登记后文件可能变成二进制 / GBK，装配期不复核就会每轮注入乱码，§6.2）。**判据不放内核登记路径**——放内核会同时作用到既有登记路径，违背本节的作用域限定。
   - ⚠️ 既有「登记作品投影」路径**本轮不动**、两处都未加同一判据（该洞仍在，另计 §10-3）。
10. **`registerWork` 必须 upsert，不得抹掉 `resident`**：同 `source` 重登记时**保留既有 `resident` 与未知字段**，只覆盖 `name` / `description`（§5.4 A 级缺口）。触发者是模型工具 `register_work`，不是假设场景。

## 8. 两种锁视觉可分 + 单一命令（快捷面 / 管理面）

| 锁 | 语义 | 生命周期 | 呈现（定稿要求） |
| --- | --- | --- | --- |
| **临时锁**（现状） | 本轮之后不清，仍以指针进信封 | **重启消失** | 保持现有 🔒 形态 |
| **项目常驻**（新增） | 投影条目 `resident: true`，正文进 system prompt | **跨重启、跨会话都在** | 清单里打 **「项目规则」标记 + 不同配色**，与临时锁视觉可分 |

**为什么必须可分（具体后果）**：两者若长得一样，用户会把「临时锁」误当「项目常驻」——以为规则已永久生效，重启后发现规则消失，而**模型在未生效期间的回答没有任何提示**。

**命令面（定稿，订正改动面）**：写路径仍是**同一套**（`registerWork` + `setResident`），但命令层是**新增行为，不是「沿用现有」**：

- **现状**：`memora.registerWork`（`registerWork.ts`）在**无 uri** 时直接 `showWarningMessage` 退出（`execute` 无 uri 分支）——**没有任何清单视图**；右键菜单只有「登记」一条、无状态（`package.json`）。
- **本期新增**：① 无 uri ⇒ 打开临时 QuickPick 清单；② 右键两条互斥菜单项（提升 / 取消）；③ `setContext` 状态键；④ `commandPalette` 里按状态隐藏不合状态的项。
- **命令面板旧标题处置（必须定稿）**：`memora.registerWork` 的 title 从「登记作品投影」改为「**管理项目规则（登记 / 开关）**」，**命令 ID 不变**（保留既有键绑定与调用入口）；原「无 uri ⇒ 警告退出」分支**删除**，改为打开 QuickPick。
- **右键菜单用独立 command ID**：`memora.promoteProjectRule`（title「提升为项目规则」）/ `memora.demoteProjectRule`（title「取消项目规则」），`when` 互斥，同一位置只出现一条。**不得用同一个 ID 期待标题随状态变化**——VS Code 菜单项标题不支持动态改。
- `explorer/context` 与 `editor/context` **两处都要**按同一 `when` 规则加（现有登记命令就在这两处，`package.json`）。

| 调用方式 | 结果 |
| --- | --- |
| 右键某个文件（**快捷面**） | 按 `source` 查重：未登记 ⇒ 登记 + 置常驻；已登记 ⇒ 只翻开关（§8.1） |
| 不带文件上下文（**管理面**） | 弹出**临时 QuickPick 清单**，逐条显示「项目规则」标记，可逐条切换 |

- 清单 UI 是**临时 QuickPick**，不是常驻面板；关掉即无视图（§7-5）。
- 取消常驻 = `setResident(false)`，条目留在清单（回到「简介 + 按需读」）；取消不读正文、不判上限。
- 本期不做跨面板角标，反馈全部由命令回执承载（§10）。

### 8.1 右键快捷入口「提升为项目规则」（定稿）

> 用户已确认采纳：把「在清单里翻开关」优化为右键直达。

- **性质 = 同一写入路径上的新组合调用**：不是第二条写入路径，也**不是「沿用现有行为」**（现有无 uri 分支是警告退出，§8）。实现语义固定为：

  ```
  按 source 查重
    ├─ 已存在 → setResident(true)                       （只翻字段）
    └─ 不存在 → registerWork(...) → setResident(true)    （先登记，再翻）
  ```

  不新增平行的登记 / 写盘逻辑；写盘仍只有 `workProjection.ts` 一处（§5.3、§5.8）。

- **必须先查重（顺序不可反）**：`registerWork` 按 `source` 做**合并式 upsert**——`description` 被覆盖、未知字段（含 `resident`）保留（`workProjection.ts`，P0-b 已落地）。
  🔴 **反例（必须防）**：对已登记文件点右键却走「重新登记」⇒ 覆盖用户已手改的简介 + 白跑一次 LLM 总结（多花钱、更慢、简介还可能被改坏）。已存在时**只翻 `resident`**，不重跑登记、不重跑自动总结（§5.6）。
- **全有或全无（动手前拦截）**：超上限（单条 6000 / 合计 15000 字符）、命中 `BLOCKED_PATTERNS`、路径在工作区外、**非文本文件**（§7.1-9）⇒ 一律在**写盘前**拒绝。不允许出现「提示失败但清单里多了一条半成品」的中间态。
- **菜单按状态变文案，同一位置只出现一条**（不并列三个选项）：

  | 当前状态 | 菜单项 | 点击结果 |
  | --- | --- | --- |
  | 未登记 | **提升为项目规则** | 登记（首次 LLM 简介）→ 置 `resident = true` |
  | 已登记、非常驻 | **提升为项目规则** | 仅翻 `resident = true`（不重登记） |
  | 已常驻 | **取消项目规则** | `resident = false`（条目保留在清单） |

  **实现取向（有实测先例）**：VS Code 菜单项标题不能动态改 ⇒ 用 `setContext` 暴露「当前文件登记/常驻状态」上下文键，注册**两个独立 command ID** 的菜单项，`when` **互斥**。先例：宿主 `fileChangeView.ts`（`setContext` + `when` 控 `editor/title` 显隐）；`explorer/context` 用同一机制。命令 ID / 标题的完整处置见 §8。

- **文案口径**：菜单与回执一律「提升为项目规则 / 取消项目规则」，清单行状态标记同步写「**项目规则**」；**不使用「设为常驻」「加锁」这类内部词**。设计层与代码仍用「常驻 / `resident`」表达持久语义——这是**概念名与界面文案的分工，不是两套能力**。
- **失败路径**：简介生成失败（LLM 失败 / 超时）时仍要**成功开启常驻**（简介只服务界面、不参与注入），但必须明确告知「简介已用文件名兜底」（`registerWork.ts`），**不得静默降级**。
- **与清单开关的关系**：QuickPick 里的逐条开关是**管理面**，右键是**快捷面**；两者写同一个 `resident` 字段、同一份清单、同一写入队列。**不是两条并行能力，也不存在第二个真相源**。

## 9. 排雷结论

### 9.1 SSOT

| 问题 | 结论 | 判据 |
| --- | --- | --- |
| 「哪些文件常驻」唯一真源 | **`work-projections.json` 里的 `resident` 字段**（一份文件） | 同一路径不得同时出现在 webview 本地数组 / 会话 meta / 设置页副本 |

| 正文与磁盘的关系 | **每轮装配重读**（truth = disk） | 外部改文件后下一轮即生效；不得把正文缓存在 webview |
| 清单缓存 | manager 内存缓存只作读缓存，**写只写磁盘** | 写路径单一；缓存失效可重建（`agent.ts` 读缓存，异步段刷新） |
| 写路径 | **唯一队列 + 唯一写函数**（§5.3、§5.8） | 任何第三写盘点即未收口 |
| 顺序 | **清单数组顺序**（不另存顺序字段） | 删除即顺延，不存在需要维护的编号 |
| 两个入口（右键 / 清单开关）会不会双真源 | **不会**：右键 = `查重 → registerWork → setResident` 的组合调用，写同一字段、同一文件、同一队列（§8.1） | 不出现第二个写入面；「快捷面 / 管理面」只是两个触发方式 |
| 术语撞车（`resident`） | 本稿 `resident` = **项目规则常驻**；代码里另有 `capabilityState.kind === 'residentOnly'`（**常驻工具**，宿主 `capabilityState.ts`、`roleBadgeView.ts`），**两者无关** | 见 §3.1 术语锚点；命名 / 注释不得混用「常驻」指工具 |

**真未决**：

1. **上限政策线的实测校准**：6000 / 15000 是政策线，字符 ≠ token；需按「常驻段允许占用的上下文比例」实测后带「时点 + 重算依据」修订一次。
2. **多根工作区若将来要支持**：首根之外的文件如何归属（按打开文件夹顺序？按清单写入方所在根？）未定；本期直接拒绝（§7-12）。⚠️ P0-c 已把宿主侧生成改为单点拒绝，但**旧条目中可能已存在的 `asRelativePath` 撒谎指针不会因本批消失**（无迁移）。
3. **用户可见的降级提示**：失效条目的界面红点、整段降级 / 读盘失败的用户通知均属 **UI 批次**；本批只做到段首汇总（模型可见）。验收不得把段首标注当「已告知用户」（§6.2）。
4. **渲染长度计量的实测**：15000 现按「最终注入段字符数」判（§6.1），而字符 ≠ token；该口径下的真实上下文占用尚未实测，须与第 1 条同批带「时点 + 重算依据」修订。
5. **晋升延迟**：`setResident` 需读正文测长才能判两道上限，大文件下的操作延迟未实测；若可感知，再评估是否拆成「预检 + 异步确认」（本期不做）。

已定处置（不再挂未决）：既有「登记作品投影」路径**不加**二进制判据——§7.1-9 已裁定，装配期 fatal UTF-8 复核关闭了「每轮注入乱码」的后果，剩余洞仅「登记当时不报错」；上限常量**不导出**——两道上限内聚 `setResident`，宿主不需要数值（§6.1）。

**已定边界（不得「修复」为宽容解析）——手改 JSON 的 `resident` 只认布尔 `true`**：

- 字符串 `"true"` / 数值 `1` 等**一律视为未开启**（不进常驻段、不报错、不进失效汇总）；判据 `=== true` 是 fail-closed 的有意选择——宁可不生效，也不猜用户意图；宽容解析会把「写错」变成「看起来能用」，比不生效更坏。
- 该行为**没有用户可见信号**（合法语义的静默分支），故**界面批次必须给出可读提示**（提示形态随 UI 批次定，不在本批加解析宽容）。
- 观测口径：若用户报告「配了但不生效」，先查 JSON 里是不是字符串（本条是排查入口）。

## 11. 替代关系

### 11.1 取代固定 `.memora/rules.md`

- 旧提案：**系统规定路径**的单一整文件 `.memora/rules.md`。
- 本设计：**用户自选任意工作区文件**升级成项目级 rules。
- 因此 `.memora/rules.md` 从「系统规定路径」**降级为「用户自选文件之一」**——用户可以恰好选中它，也可以选任何别的文件，系统不再硬编码路径。
- 旧形态天然无法表达：逐项启停、逐项上限、逐项失效可见；且固定路径由系统规定，用户无法自选文件。

### 11.2 推翻上一轮的独立清单（`resident-rules.json`）

- **省一个文件**：同一实体不拆两份存储——两份存储就是两套写入、两套失效检测、两套迁移。
- **结论为何翻转**：上一轮判「不复用」的前提是「并发覆盖不可解」。本稿把可解的缺陷升为**前置闸 A**（§5.3）后，前提不再成立，故复用成立。上一轮取证没有错，错的是取向（用避开缺陷换安全 → 先修缺陷再接）。
- **仍未改的东西**：路径守卫、原子写、损坏 fail-safe 全部沿用（§9.2 复用表）。
- **上一轮的独立清单文件与迁移表全部作废**，不留兼容层。

### 11.3 与作品投影的关系：同一实体，两个消费面（不是「分工」）

| 形态 | 固定段放什么 | 正文来源 | 现状 |
| --- | --- | --- | --- |
| **非常驻投影**（`resident` 缺失/false） | 清单一行的 `name + description + source` | 模型按需 `read_file` | 保持不动 |
| **常驻投影**（`resident === true`） | **正文** | 每轮读盘 | 新增 |

判据：**进固定段的是正文 ⇒ 规则；进固定段的是指针 ⇒ 资料。** 两者同文件、同写入路径、同守卫，只在**消费面**上分开——这不是「两个系统」，也不存在「常驻层 vs 作品投影」的数据边界。

### 12.1 边界

- **不许单独留字段**：若该批因故拆分，`workspaceTrusted` 必须连同最小消费面一起走。单独留下的入参是**假象源**——后来者看到它，会以为信任门已存在，照着它写读盘而不加闸。
- 只做「信任态从宿主穿到内核 + 首条读盘路径的闸」：内核新增**入参 + fail-closed 判据 + 该判据的第一个消费者**。**本批一并含**：`resident` 字段读取、`setResident` 写路径（同一写队列 + 两道上限 + 六态结果）、正文注入与失效兜底汇总（段首）。**不在本批**：界面红点 / 用户可见的降级提示（**UI 批次**，§10-3）。
- 不做多根工作区支持、不做旧数据迁移、不做任何 UI 文案。
- 信任真源仍是宿主 `vscode.workspace.isTrusted`（**现读**，不自存副本）；内核侧**不得**现读该值（内核无此态，§1.5）。
- 状态文案只能写「**入参与消费面同批落地**」；**禁止**写「信任门已实现」——那只在闸与消费者都在册时才勉强成立，且会被读成「常驻层完工」。

> 已订正原因：范围变了（P1 把 `resident` 读取 / `setResident` / 正文注入 / 失效兜底拉入本批），非原稿写错——原稿按「P0-d 一批 + 常驻层本体另一批」写。

### 12.2 判据（单点，fail-closed）

- 入参建议名 `workspaceTrusted?: boolean`：与宿主既有 `projectAssetDirsFor({ isTrusted })` 同一语义面；不用 `resident*` 前缀，避免与「常驻工具 `residentOnly`」撞词（§3.1）。
- **只有严格 `=== true` 放行**；`undefined` / `false` / 任何非 `true` 值 ⇒ 常驻层不装配。与 §5.5 的 `resident === true` 同一纪律。
- 判据只落**一处**（单点函数），消费面一律调它；禁止在装配点与每轮刷新点各写一遍 `if (trusted)`。

**信任判定的分层结论（已查调用时机，非推断）**

- 现状两处直读 `isTrusted`：`readProjectAssetDirs`（调用时现读）、`syncTrustNotice`（activate 首次调用 + **授予信任监听器内再次调用** ⇒ 本来就是现读，不是一次采样）。
- ⇒ 并进 `readWorkspaceTrusted()` **不改变读取时机、不改变行为**：激活期仍显示提示；授予信任后监听器仍会重跑它并隐藏提示；不存在「该显示却被现读吞掉」的新场景。
- activate 期的「快照」是另一件事：`projectDirsAtActivation` 是给面板展示的目录快照，与信任判据无关，**不动**。
- 结论：三处收敛成一个读口。兜底条件：开工时若复核发现 `syncTrustNotice` 新增调用点、或依赖「只在 activate 读一次」，则**退回「只收敛 `readProjectAssetDirs` + P0-d 两处」**，并在此登记不并入的原因——少收一处是退让，硬收一处不查语义是造 bug。

- **不合并成一个开关**：注入物不同（资产目录 vs 常驻正文），合并会让某一侧将来放宽时另一侧静默扩权。
- **分叉触发条件**（写明，防后人凭感觉复制判据）：仅当 ① VS Code 出现按功能域/按目录的信任，或 ② 某消费面需要比工作区信任**更严**的门（如常驻正文额外叠加 `isBlockedPath`）时才分叉。届时形态 = 「信任读口不变 + 该消费面叠加自有门」，**不是**复制一份信任判定。

**信任态变化：授予后重建装配（同一监听器内追加）**

- 监听**已存在**：`vscode.workspace.onDidGrantWorkspaceTrust`（`extension.ts`，当前分支做「补注入项目资产 + 两面板清单重推」）。本批在**该监听器内**追加重建装配，**不新开第二个 listener**——同一事件两条处理路就是渲染路正在修的「同一次重建两条路」的同型病。
- 重建装配**复用唯一装配入口** `assembleAgentForSession`（经 `AgentRegistry.createAgentForSession` 的 factory）。⚠️ 实测：该入口命中已登记即返回同实例，**没有淘汰/重建能力** ⇒ 最小扩张 = 给同一方法加**可选**重建参数（契约扩张走可选字段），**不新增 `rebuildAgent` 方法、不复制装配循环**。
- **重建参数只有一个合法调用口** = 信任监听器分支。落地要求：参数不用裸 `boolean`，用**字面量来源**（如 `rebuild?: { source: 'workspace-trust' }`）——让「谁传的」在类型与日志里都留痕、可 grep；方法 JSDoc 顶部写死约定标记 `UNIQUE-CALLER: onDidGrantWorkspaceTrust`，并在每次触发时记日志（含 `source`）。新增任何传 `source` 的调用方**先报用户**；提交前按 grep 复核「非该监听器无调用点」。仅靠注释约束不住，所以这条进提交前复核清单。
  - **通用做法（同类场景照此办）**：凡「唯一调用口」要求，一律用字面量来源参数把约定做进**类型事实**；不靠注释约定、不靠评审记忆。（裸布尔只能靠人守，来源进类型后可断言、可 grep、可日志。）
- 未信任 ⇒ 不注入任何常驻正文（fail-closed，宁可不给）。
- **反向刷新不实现**：VS Code 的信任只能 untrusted → trusted，撤销信任须重开窗口 ⇒ 运行期不存在「撤销」事件。写明原因，防后人「补全」一个不存在的场景。
- 在途装配：命中 `inflight` 时先等其落定再重建；重建前关闭旧实例须确认不丢未落盘数据（验证点见 §12.5）。
- **忙碌态不得硬切**：`agent.isBusy` 为真时重建会打断在途 turn ⇒ 按既有配置热重载纪律「busy 时暂存、收尾补执行」，禁止「先关旧实例再建新实例」在 busy 时执行。
- **暂存不许静默**：暂存那一刻必须留一条**用户可见**记录（输出通道 + 状态栏/通知其一；文案说明「已授予信任，项目常驻规则将在本轮对话结束后生效」），收尾补重建成功后**清除**该记录；补重建失败则记录**不得**消失。合格判据：界面与日志都能看到，只在代码里有分支 = 不合格。

### 12.5 测试

- 内核：`undefined` / `false` ⇒ 判据 false（fail-closed）；`true` ⇒ 判据 true；字段从 `AgentOptions` 透到装配产物取值一致。
- 内核消费面：未信任时首条读盘路径**零调用**（读盘替身计数断言，不是只看返回值）；信任时正常读取。
- 宿主读口：用计数器替身证明 `readProjectAssetDirs` / `syncTrustNotice` / `buildAssembleOptions` 三条路径都经过 `readWorkspaceTrusted`，且**没有**第二处直接读 `vscode.workspace.isTrusted`。
- 宿主取值：`isTrusted` 两种取值下 `buildAssembleOptions` 产出对应布尔；未打开工作区不臆造 `true`。
- 授予信任：监听器触发后，已登记会话各重建**一次**（factory 调用计数），零登记时不重建；重建后装配选项 `workspaceTrusted === true`。
- 忙碌态：busy 会话收到授予信任时**不重建**（factory 零调用），收尾后再补（按暂存标记断言）；暂存时断言**可观察记录已写入**，补重建成功后断言记录被清除；补重建失败时断言记录**仍在**。
- 唯一调用口：grep 复核除信任监听器外无 `source: 'workspace-trust'` 调用点；能静态化就加成单测断言，不能则列为提交前人工复核项（不假装有测试）。
- 判据收敛等价：`syncTrustNotice` 合并前后调用点集合不变（activate + 授予监听器两处），不新增读取时机。
- **可测性前置**：`extension.ts` 属**零测试覆盖区** ⇒「哪些会话要重建、busy 时如何暂存」的判定不得写在监听器闭包里，必须下沉到 `host/agentRegistry.ts` 或同层可测模块，监听器只做接线；否则整条链路只剩零覆盖。
- 重建数据安全：重建后该会话历史 / 轮次不丢（真实存储用例，不用内存替身）。
- 信任撤销：**不写用例**——VS Code 无该事件，给它造替身等于给不存在的场景留证据。
