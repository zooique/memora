### 1.2 会话级钉住（临时锁，0.10.0 已落地；本层不改动它）

| 环节 | 实现 | 位置 |
| --- | --- | --- |
| 引用结构 | `ChatRef = { path, kind: 'file' \| 'folder', range?, pinned?, missing? }`，只挂指针不携内容 | `hosts/memora-vscode/src/shared/protocol.ts` |
| 「临时锁」= `pinned` | `pinned?: boolean` **进协议**：W→E 随 `input` 上行（`kind='pin'`），E→W 随 `addRef` 回种。旧注释「pinned 纯 UI 状态，不进协议/内核」**已作废** | `hosts/memora-vscode/src/shared/protocol.ts`、`chatView.ts` |
| 发送后保留 | `currentRefs` 只留 `pinned` 条目——未锁的发送即清 | `hosts/memora-vscode/src/webview/scripts/chatView.ts` |
| 切锁 / 上浮 | 🔒 按钮切 `pinned`；渲染时钉住上浮 | `hosts/memora-vscode/src/webview/scripts/chatView.ts`（chip 渲染段） |
| 落盘面（0.10.0） | 指针写进 `SessionMeta.pinnedItems`（判别联合：file / folder 带 `path` + `range?`，skill 带 `name`）；**只存指针、不存正文** | `src/memory/sessionStore.ts`；写入 `hosts/memora-vscode/src/extension/host/pinnedContext.ts` |
| 回种面（0.10.0） | 切会话 / 重开面板 / 重启后按元数据**单向回种** composer（`addRef` + `skills_loaded.pinnedSkillName`）；形状不对的条目跳过并给 `notice` | `pinnedContext.ts` 的 `pushPinnedRefsTo` / `seedPinnedRefs` |
| 测试口径 | 现口径 = 「锁是动作、动作即落盘；切会话清空后按元数据回种」 | `chatView.test.ts`、`chatPanelInput.test.ts`、`pinnedContext.test.ts` |
| 入信封形态 | 发送时拼 `[参考文件/目录]` 块（仅路径 + 行区间读取参数） | `hosts/memora-vscode/src/webview/helpers/docContext.ts` |
| 宿主拼信封 | 发送时刻 `buildRefContextBlock` + `buildInjectedContextEnvelope` | `hosts/memora-vscode/src/webview/panels/chatPanel.ts` |
| 发送前失效核实 | `collectMissingFileRefPaths` 对文件引用 stat，失效者降级为「裸指针 + 标记」 | `hosts/memora-vscode/src/extension/host/refProbe.ts` |

**生命周期结论（0.10.0 落地后）**：锁是**动作**，动作发生即落盘——宿主收到 `input.kind='pin'` 直接把钉住清单写进会话元数据（`SessionMeta.pinnedItems`，只存指针），不等发送；切会话 / 重开面板 / 重启后由宿主按元数据**单向回种**（`pushPinnedRefsTo`）。**跨重启：成立。**

⚠️ **已知限制（草稿期）**：会话尚未建立（`_currentSessionId` 为空、无元数据载体）时 `writePinnedItems` 直接返回 ⇒ 该次加锁**不落盘**，要等首条消息把草稿 flush 成会话后由宿主补落（`chatPanel.handleInput` 的 send 分支）；「草稿期锁了、没发就关窗」**会白锁**。

### 1.3 system prompt 层结构（注入位置的证据）

`buildSystemPromptPrefix` 的分段顺序（实测，`src/agent/assembler.ts`）：

```
① rolePackPrompt      ← 角色包段（personaPrompt；角色 rules 在 personaPrompt 内）
② globalSkillList
③ SKILL_WRITE_LOCATION_PROMPT
④ workProjectionContext
⑤ environmentContext
⑥ 当前时间
⑦ TURN_START_STRATEGY_PROMPT
--- 分隔线 ---
```

- **角色 rules 在哪（关键）**：角色包的 `## 规则` 段由 `strategyResolver.ts` 拼进 `personaPrompt`，`personaPrompt` 再作为 `rolePackPrompt`（第 ① 段）传入。故「角色 rules 之后」= **插入点在第 ① 段之后**。
- **工具描述在哪**：工具描述**不在** `buildSystemPromptPrefix` 里。system message = `prefix + buildSystemPrompt(memories)`，工具描述在**后段**的 `## 可用工具` 里（`src/agent/loop.ts`，拼接点 `src/agent/loop.ts`）。
- **结论**：项目规则段插在 ① 与 ② 之间，天然满足「角色 rules 之后、工具描述之前」。

## 2. 目标与非目标

### 2.1 目标（收敛为三件事）

1. **作品投影条目上多一个布尔字段** `resident`：`false` / 缺失 = 原能力（只提供简介、模型自行决定是否读）；`true` = 被「项目级文件加锁」取用，**正文每轮永久注入**。
2. **每轮按项目规则清单读正文**，注入 **system prompt 固定段**（不是当附件塞进对话）。
3. **读不到就说读不到**：条目指向的文件不存在时**可见失效**，禁止静默跳过。

其余硬要求（全部保留，不在本节扩张）：

- 只接受**工作区相对路径** + **工作区信任门**（§7.1-1、§7.1-2）。信任态由**宿主作为新入参**传给内核；装配期内核不做 `isTrusted` 现读（内核无此态）。
- 两种锁**视觉可分**（§8）。
- **优先级写死**：项目规则 > 角色 rules > 资料；< 安全铁律（§4.3）。
- **单条 5000 字符 / 合计 10000 字符上限**（**合计 = 单条 × 2**，可解释预算：最坏容得下两篇顶格规则）；添加或置为项目规则时**当场拒绝**并回报占用。装配期因外部改动：**单条超限 ⇒ 剔该条 + 汇总提示**；**合计超限 ⇒ 按清单顺序逐条丢弃靠后条目直到装得下**，并在段首显式列出**丢弃清单**（哪篇、因合计超限）；两者都不阻断发送（§6.1）。
- **顺序 = 清单数组顺序**（先添加者优先；删除条目后其余顺延前移）（§3.3）。
- 凭据防护：**复用已导出的判据面**（`isBlockedPath` / `matchBlockedPathPattern`，P0-a 落地），禁止复制第二份；**本期只防凭据路径，内容夹带不防**（§7.1-4）。
- 项目级变更**对所有会话实例生效**（§5.8、§10）。
- **失效判定只用文件存在性判断 + 与清单声明集合比对，不引入任何 git 调用**（§6.2）。

### 2.2 非目标（边界）

- **不另立清单文件**（推翻上一轮 `.memora/resident-rules.json`，见 §11.2）。
- **不改变非 `resident` 条目的任何行为**：索引渲染对它们逐字不变。
- **不做规则引擎**：无通配符、无 glob、无目录扫描、无条件判断、无自动发现。
- **本项目规则层不改动会话级钉住（`pinned`）**：钉住自身的落盘 / 回种已由 0.10.0 宿主批落地（§1.2），与本层是两套能力，本层不回归、不接管。
- 不做**会话级规则**（钉住跨重启保留的只是「钉住清单」本身，正文仍按需读，**不是**每轮注入的规则）、不做**文本来源规则**、不做**技能正文注入**（技能钉住只保留「选中哪个技能」）。
- 不做**独立 Webview 清单面板**、不做**跨面板角标**；清单的常看面是**设置面板「作品和规则」选项卡**（§8.2），管理面是临时 QuickPick，反馈由命令回执与「作品和规则」页行徽标承载（§10）。
- 不做本轮之外的一切覆盖（完整清单见 §7 设计边界）。

### 2.3 文本来源被砍的后果（必须写明，避免后人误以为漏做）

- 用户此前**每天手打**的规则句（例如「遵守 SSOT / 自然生长 / 不带伤」）今后**不能再直接粘进输入框**变成项目规则。
- 想永久生效，必须：**先把规则落到一个工作区文件**（如 `docs/<你的规则文件>.md` 或任意已有文档；此处是示例占位，不是本稿引用的文件），再把该文件「切换为项目规则」（`resident = true`，§8.1）。
- **不存在**「项目规则文本输入框」；这是**已拍板的裁剪**，不是待补项。

## 3. 数据模型

### 3.1 条目形状（在既有三字段上增一个布尔）

```
WorkProjectionEntry {
  name: string          // 必填；读取过滤器依赖，缺失即整条被丢弃（§5.4）
  description: string   // 必填；设为项目规则后只服务清单展示（§5.6）
  source: string        // 必填；首根相对规范形（relativeUnderPrimaryRoot，§7.1-1）
  resident?: boolean    // 新增；只有严格 `=== true` 才算项目规则（§5.5 fail-closed）
}
```

顺序由清单数组天然表达，不另存顺序字段（§3.3）。

> **术语锚点（防撞车）**：本稿 `resident` = **项目规则**（条目正文每轮注入）。
> 代码另有 `capabilityState.kind === 'residentOnly'`（**常驻工具**，宿主 `capabilityState.ts`、`roleBadgeView.ts`）——`resident` 与 `residentOnly` 只是拼写相近，**语义无关**。命名 / 注释 / 文案不得把「项目规则」与「常驻工具」折叠成同一个词（本仓「措辞折叠」纪律）。

### 3.2 两态语义（不是三态）

| `resident` | 语义 | 消费面 |
| --- | --- | --- |
| 缺失 / `false` / 任何非 `true` 值 | 原作品投影 | 只进【项目索引】注入块，模型按需 `read_file` |
| 严格 `true` | 项目规则 | 正文进「项目规则」固定段；**不进索引注入块**（§4.4） |

### 3.3 顺序与删除

- **顺序真源 = 清单数组顺序**（先添加者在前）；项目规则段渲染、清单展示、优先级「靠前者优先」全部读同一个顺序。
- **删除条目后其余顺延前移**（不保留空位）——上一轮「保留稳定序号」的要求**已作废**：跨时间稳定的身份是 `source`，不是序号。
- 取消项目规则（`resident → false`）不移动数组位置；重新置为项目规则回到它当前的数组位置。

## 4. 注入位置与优先级

### 4.1 注入位置（定稿）

```
systemPromptPrefix:
 ① rolePackPrompt（personaPrompt，含角色包 ## 规则）
 ② 【项目规则段】← 唯一新增
 ③ globalSkillList
 ④ SKILL_WRITE_LOCATION_PROMPT
 ⑤ workProjectionContext（索引注入块；项目规则条目已从该块剔除）
 ⑥ environmentContext
 ⑦ 当前时间
 ⑧ TURN_START_STRATEGY_PROMPT
 --- 分隔线 ---
system message 后段：记忆设定段 → 回应骨架 → ## 可用工具（工具描述）→ 工具叙事纪律 → 只读态事实段
```

- 插在 ① 之后 = **角色 rules 之后**；在 ② 之后才是工具描述所在的后段 = **工具描述之前**。
- **禁止**追加到 `buildSystemPrompt` 尾部（那会让规则落到工具描述之后，语义降级为资料）。

**实现口径**：`buildSystemPromptPrefix` 增**第 6 个可选参数** `residentRulesContext`，但**渲染位置固定排在 `rolePackPrompt` 之后**——参数放尾部只为不动既有 5 个位置参数调用点（`assembler.ts`、`agent.ts`；实测均为位置传参）。

**每轮刷新口径（实测依据，订正）**：每轮重建前缀的真落点是 `prepare.run()` 里的 `refreshAssemblyForRolePack(...)`（`src/agent/seed/prepare.ts`），它内部调 `deps.refreshRolePackPrefixForRound`（同文件的自由函数，**不是**独立的每轮重建）。位置关键：`prepare.run` 在 `await contextPreparer.assembleContext(input)` **之前**调用 `refreshAssemblyForRolePack`。因此「每轮按清单读正文」的落点是：在 `refreshAssemblyForRolePack` 之前先 `await` 一次「刷新项目规则上下文」（重读清单 JSON + 逐个读项目规则正文并渲染本段；**不保留跨轮正文缓存**），再由同步重建收口。**按旧稿字面插在 `refreshAssemblyForRolePack` 内部会首轮用旧结果、规则晚一轮生效**。不得在同步函数里做磁盘 IO。

### 4.2 段内格式（定稿）

```
## 项目规则（本仓库具体约束；按清单顺序，靠前者优先）
- 适用范围：仅「具体约束」冲突；不改变角色职责与工具边界（角色是只读审查员时，本段不会让它变成改码角色）。
- 优先级：本段 > 角色包规则 > 技能清单等资料；但不得放宽任何代码闸门（权限 / deny / 工作区信任 / 只读态），冲突时以闸门为准。
（以下 N 条本次未注入（读取失败，下轮重试）：路径…）← 仅当存在读失败条目
（以下 N 条本次未注入（单文件超上限，需拆分）：路径…）← 仅当存在单条超限条目
（以下 N 条因合计超限未注入：路径…；已按清单顺序丢弃靠后条目，靠前者优先）← 仅当发生丢弃

### 来源文件：docs/agent-rules.md
<文件正文>

### 来源文件：docs/xxx.md
<文件正文>
```

未注入条目一律不注入正文，只在段首分类汇总（§6.2）；三类汇总行分写，是因为读失败要**下轮重试**、单条超限要**拆分文件**、合计超限要**精简别的条目**——处置方向不同，合并成一句会让模型与排障者用错动作。

> 已订正原因：范围变了（P1 把「优先级声明句」拉入本批），非原稿写错——原稿只写「段首一句声明」，未给具体文案。

### 4.3 优先级（写死 + 理由成文）

**项目规则 > 角色包 rules > 技能清单等资料；但 < 安全铁律 / 硬约束。**

**适用边界（与 §4.2 段首文案同源）**：本优先级只解决**同一事项的具体约束冲突**，不改变**角色职责与工具边界**——职责冲突（如角色是只读审查员、项目规则要求改代码）不属于本优先级的裁量范围，不得据此把角色架空。

> 已订正原因：范围变了（P1 把「优先级声明句」拉入本批），非原稿写错——原稿把「高于角色包 rules」写成了无限定全称句，会让项目规则层被读成可以覆盖角色职责。

理由：

1. **为什么高于角色包 rules**：角色包是**跨项目复用的通用模板**，项目规则是**针对本仓库的具体约束**。具体优先于通用——否则换个角色包就会把本仓库的约束稀释掉。位置上也自洽：项目规则段排在角色段**之后**，物理上更靠近用户消息。
2. **为什么低于安全铁律 / 硬约束**：安全铁律在本仓**由代码闸门执行**（权限档位 / deny 判据 / 工作区信任门 / 只读态事实段），**不靠 prompt 文本自证**。任何 prompt 层文本（包括项目规则）都**不可能绕过代码闸门**；因此「低于安全铁律」是执行面的硬事实——项目规则只能约束「闸门之内怎么写」，不能放宽闸门。
3. **同层内的顺序**：**清单中靠前者优先**（先添加者优先）。**只在段首写声明（§4.2 那三句）**，不逐条重复标注（逐条重复更稳但费 token，本期不采用）。
   - 残余风险（登记）：LLM 注意力天然偏向靠近用户消息的文本（即靠后的条目）。若实测仍偏移，缓解项是逐条重复标注（本期不做，登记为已知偏差）。

### 4.4 两个展示面分开：注入块剔除，界面照常列出

必须把两件事分开读，否则会误以为「项目规则条目隐身」：

| 面 | 项目规则条目（`resident === true`） | 非项目规则条目 |
| --- | --- | --- |
| **注入块的【项目索引】** | **剔除**（不出现） | 照常出现一行简介 |
| **清单（临时 QuickPick）** | **照常列出**，并打「**项目规则**」标记 | 照常列出，无标记 |
| **右键入口** | 不显示状态（平台限制：菜单标题静态，见 §8）；点击后由内核回执如实播报当前态 | 同上（中性标题「切换项目规则」） |

> 右键菜单**列不出清单**，也**显示不了状态**（标题静态，§8）——它只对「被点的那个文件」执行切换；清单与逐项状态由 QuickPick 承载（§8）。

**为什么注入块剔除**：

1. **两份真相**：同一文件若既以简介出现在索引、又以全文出现在项目规则段，模型会看到同一对象的两种描述；按简介再 `read_file` 一次的概率上升，token 与行为都翻倍。
2. **语义冲突**：索引的语义是「目录，按需读取」，项目规则的语义是「正文已在此，无需读取」。把项目规则条目留在索引等于告诉模型它还该按需读。
3. **「只留『已设为项目规则』标记」同样不可取**：那仍制造第二处引用，且标记本身不携带任何决策信息（全文就在下一段）。

**为什么清单不能剔除**：条目仍在清单里，用户必须看得见、能取消——清单隐身 = 用户失去解除能力。两个面读同一份数据，只是渲染规则不同。

## 5. 复用作品投影：四条取证 + 五道前置闸

### 5.1 为什么复用同一份文件

- 用户拍板：省一个文件，且「项目规则」天然是投影条目的一个属性，不是第二个实体。
- 上一轮判「不复用」的两条理由（整文件重写导致并发覆盖、读取方按全投影解析）**不是不可跨越的边界，而是待解决缺陷**。本稿把它们升为**前置闸**（§5.3、§5.4、§5.5）后，复用成立。
- 不掩盖结论变更：上一轮的取证没有错，错的是「用避开缺陷换安全」的取向；本轮改为「先修缺陷再接」。

### 5.2 四条取证（复核，本轮结论：**复用，条件成立**）

| # | 取证项 | 实测结果 | 对本设计的影响 | 位置 |
| --- | --- | --- | --- | --- |
| 1 | schema 是否有「类型 / 用途」判别字段 | **没有**类型字段；但本设计只需一个二值判别（项目规则 / 非项目规则），一个布尔字段即可表达，不需要多类型体系 | 可扩展：加 `resident` 足够 | `workProjection.ts` |
| 2 | 写入方与方式（**决定性**） | **整文件重写**；`registerWork` 先 `refresh()` 读全量进内存 → 合并/追加 → 把整份内存数组写回。写入已在模块级 `withFileWriteQueue` 内串行（P0-b） | 持久化形态可复用（闸 A 已落地） | `workProjection.ts` 的 `registerWork` 与 `withFileWriteQueue` |
| 3 | 读取方与误读面 | `filter(e => e && e.source && e.name)` 会**静默丢弃缺字段条目**；`contextBlock()` 把每条一律渲染成投影行 | **新条目必须补齐 name/source**（闸 B）；**项目规则条目必须从注入块剔除**（闸 D） | 过滤在 `refresh`；渲染在 `contextBlock` |
| 4 | 原子写 / 损坏 fail-safe / 并发写 | 有 `atomicWriteFile` 与损坏拒写；**进程内写已串行**（P0-b）；实例每会话一个 | 持久化形态可复用；跨进程并发仍不覆盖（§5.3） | `workProjection.ts` 的写盘段与损坏 fail-safe；实例 `assembler.ts` |

**判定标准（写进设计，供同类问题复用）**：

- 结构天然可扩展 + 写入可串行化或已是局部更新 + 误读面可列全 ⇒ **可复用**。
- 写入整文件重写且**无法**串行化，或存在无法修正的「全投影」消费方 ⇒ 不复用，另立清单。
- 证据不足 ⇒ 写「未查实」，列明需要什么证据，**不许猜**。

### 5.3 前置闸 A（决定性）：写路径必须先串行化

**事实三条（实测）**：

1. 写入是整文件重写（`workProjection.ts`）。
2. 实例是每会话一个（`extension.ts` 按 sessionId 取 Agent；`assembler.ts` 每 Agent 新建 manager），全部指向同一文件。
3. 工具层已有写串行闸（`diskWrite:'opaque'`，`loop.ts`），但**只在单个 AgentLoop 内生效**；宿主命令直调 `agent.works.registerWork`（`registerWork.ts`），**绕过闸门**。

**后果（推断，依据代码结构；未跑实测复现）**：两个会话，或「某会话的模型工具 + 用户右键命令」并发时——A 读盘 → B 读盘 → A 写 → B 写 ⇒ A 的 `resident: true` 被 B 的旧快照覆盖。

**方案对比**：

| 方案 | 覆盖实测面（同进程多会话 + 宿主命令） | 覆盖跨进程 | 代价 | 取舍 |
| --- | --- | --- | --- | --- |
| **进程内「按文件路径的 Promise 队列」+ 临界区 reread** | ✅ | ❌ | 零依赖，约十几行 | **采用** |
| 单实例注入（每项目一个 manager 共享） | ✅ | ❌ | 要改 Agent 装配链（`assembler.ts` 每会话建）与公开面 | 不采用：改动面更大，收益相同 |
| 真文件锁（`proper-lockfile` 等） | ✅ | ✅ | 新增三方依赖 + 锁残留/超时语义 | 不采用：内核口径为零三方依赖（`workProjection.ts` 注释），且锁失效的代价高于丢失一次勾选 |
| 只加「写前 reread」（无互斥） | ❌ | ❌ | 最小 | 不采用：读-改-写窗口无互斥，交错照旧 |

**选定落地细节**：

1. **锁键 = 绝对文件路径**；队列容器放**模块级 Map**（不是实例字段）——实例每会话一个，实例级队列等于没锁。
2. 临界区顺序固定：**锁 → `refresh()` 重读盘 → 合并 → `atomicWriteFile`**。
3. **所有写函数都必须走同一队列**：`registerWork` 与新增 `setResident`；**禁止**出现第三个写盘点（宿主、webview、设置页一律只调用这两个）。
4. 失败语义沿用工具层口径：队列任务异常不毒化后续（同 `loop.ts` 的「链尾吞失败」）。
5. 损坏 fail-safe 保持在临界区内先判（`refresh` 置 `fileWasMalformed` → `registerWork` 先判）：文件坏 ⇒ 拒写，不覆盖用户原索引。

**跨进程：本期不做，但必须有可见兜底**：

- 覆盖范围只有**本 extension host 进程内**。同一文件夹开两个 VS Code 窗口、或用编辑器同时改 JSON，后写会覆盖先写。
- **兜底（新增一小段检测，不是解决）**：每轮以磁盘为准重读；**与「清单声明的项目规则集合」比对**（不是与上一轮快照比对），并**分开判定**：
  - **声明有、读不到**（`resident === true` 但文件不存在 / 非文本）⇒ 该条**失效**，装配段首汇总一行。
  - **声明没有、盘上无关**（清单里 `resident` 已为 `false` 或条目已删）⇒ **正常操作**，不报警。
  - ⚠️ 旧写法「与上一轮集合做差」有两个洞：① 差集方向不会误报「全部失效」（重启后上一轮为空、结果为空），但**检测盲区**是「重启期间与新会话内发生的丢失」查不到；② 差集无法区分「被覆盖丢失」与「另一窗口主动取消」，后者会**假报警**。改为对清单声明的集合判定即同时解掉这两点。
- 因此这是「**可见的丢失**」，不是「已解决」：那一轮规则确实没生效，但用户能看到哪一条没了、能重新置为项目规则。**不得**把它写成「并发已解决」。
- 验收用例（**已落地，P0-b**）：N 个不同 `source` 并发 `registerWork` ⇒ 盘上 N 条；同 `source` 并发 ⇒ 单条且未知字段保留。`setResident` 与 `registerWork` 并发用例待 `setResident` 落地后补。

### 5.4 前置闸 B：新入口必须补齐 `name` 与 `source`

**事实**：读取入口 `refresh` 的 `filter(e => e && e.source && e.name)`——缺字段 = **整条记录消失**，不是「未设为项目规则」。

**落地规则**：

1. 条目创建**只允许**走 `registerWork`（它负责 `name` / `source` 规范化）。
2. `setResident(sourcePath, resident)` **只翻字段**：返回**失败四态 + 成功两态**（§6.1），条目不存在时 `reason: 'not-found'`，**绝不创建**；置 `true` 时先读正文判两道上限（未信任先拒、不读），置 `false` 不读正文、不判上限。
3. 用户「置为项目规则」对**未登记**文件：先走登记（含 LLM 描述）→ 再 `setResident(true)`；两条写各自进同一队列（可合并为一次临界区，非必需）。**右键快捷入口按同一顺序执行**（§8.1），不得反过来先置位再补登记。

**A 级缺口（**已修，P0-b 已落地**）**：

- **事实（修复前）**：`registerWork` 对已存在的 `source` 是**整条替换**，新对象只带原三字段 `name` / `description` / `source` ⇒ 既有条目的 `resident: true` 与任何未来新增字段**被静默丢弃**。
- **触发者包括本版本的模型工具 `register_work`**（不是只有手改才会发生）：模型对同一文件再登记一次，项目规则就没了，且**无任何提示**。
- **处置（已落地）**：`registerWork` 已改为**合并式 upsert**——命中同 `source` 时**保留既有 `resident` 与未知字段**，只覆盖 `name` / `description`。
- **测试（已落地）**：见 `workProjection.test.ts` 的「`registerWork` upsert（保留未知字段）」两条——已设为项目规则的条目再登记后 `resident === true` 仍在；手工塞入未知字段 `x-extra` 重登记后仍保留。

**显式用例（必须落成测试）**：

- 反例钉死：手工写 `[{ "source": "<工作区内的某个 .md 文件>", "resident": true }]`（无 `name`）⇒ 重新加载后该条**消失**。
- 正例：登记 → 置为项目规则 → 重新加载后仍在，且 `name` / `source` 齐全。
- 越界反例：`setResident` 对不存在的 `source` **不得**产生新条目（尤其不得产生「只有 path + resident」的条目）。

### 5.5 前置闸 C：`resident` fail-closed

**判据唯一写法**：`entry.resident === true`（严格相等）。

| 输入 | 结果 |
| --- | --- |
| 字段缺失 | `false`（原投影） |
| `false` / `null` / `0` / `""` | `false` |
| `"true"`（字符串） / `1` / 对象 / 数组 | `false` |
| 严格 `true` | 项目规则 |

- **禁止**把 `resident` 加进 `refresh` 的加载 filter——那会把「字段缺失」从 `false` 变成「记录消失」。
- **禁止** `Boolean(entry.resident)`（`"false"` 会变 `true`）。
- 用例：上表每种畸变输入 ⇒ 条目仍在清单 / 索引中、项目规则段不出现。

### 5.6 前置闸 D：`description` 定位与自动总结

**`description` 定位**（由 §4.4 决定）：项目规则条目不进注入块 ⇒ 模型侧不消费 ⇒ **只服务界面展示**。

**自动总结仅发生在首次登记**：

- ✅ **首次登记**（文件尚未进清单）必然触发既有 LLM 总结（`registerWork.ts`）——这是既有能力，不需要新机制。
- ❌ **已登记条目转为项目规则不再触发**：文件内容未变，description 已存在，重复调用只会多花一次 LLM 调用、只改界面文案，对模型行为零收益。
- 可选（不进必做）：若 description 曾由文件名兜底（LLM 失败时走 `registerWork.ts` 的文件名兜底段），可在首次置为项目规则时复用**同一条**生成通道重试一次。

### 5.7 兼容面（旧读取方与旧数据）

| 面 | 结论 | 依据 |
| --- | --- | --- |
| 旧数据（无 `resident`） | `=== true` 不成立 ⇒ `false` ⇒ 索引输出**逐字不变** | 渲染只看 `name/description/source`（`contextBlock`） |
| 旧读取方 | `filter` 不看 `resident`；注入块的剔除只影响 `true` 条目 | `refresh` 的 filter、`contextBlock` |
| 公开成员面 | 新增 `setResident` 会与守卫基线冲突 ⇒ **必须同笔更新基线**，否则测试红 | `publicMemberSurfaceGuard.test.ts` |
| 文档漂移 | `docs/architecture/work-projection.md` 现写「全部条目进索引」；实现时须同步（本稿不改该文件） | 该文件非本笔改动范围 |
| 工具描述 | `register_work` 描述需补一句「是否设为项目规则由用户开关控制」 | `builtinTools.ts` |

### 5.8 唯一真源规则

1. **清单文件唯一**：`work-projections.json`；不另立第二份。
2. **写函数唯一**：所有变更经同一队列 + `registerWork` / `setResident` 两个入口。
3. **项目规则判据唯一**：`=== true` 只写在一处（导出成单函数，其余读同一函数）。
4. **顺序真源唯一**：清单数组顺序（不另存顺序字段、不派生第二套排序）。
5. **注入块与清单展示面同源同文件，但渲染规则不同**（§4.4）。
6. **项目级变更对所有会话实例生效**：语义生效靠「每轮读盘」（§4.1），不依赖推送通道。

## 6. 上限与失效（两组硬判据）

### 6.1 字符上限：两道闸（缺一即未收口）

| 闸 | 时机 | 行为 | 判据 |
| --- | --- | --- | --- |
| **主闸（写路径）** | `setResident`（内核）置为项目规则时先读正文统计 | 超限 ⇒ **内核当场拒绝**（失败四态，`message` 给计量构成与差额）；宿主只显示该 `message` | `resident` 保持 `false`；无静默截断；未信任先拒（`untrusted`），不读正文 |
| **保底闸·单条** | 每轮装配前，按磁盘最新内容复核 | **单条超限** ⇒ **只剔该条** + 段首汇总一行（其余项目规则条目照常注入） | 明示「某条超限未注入」；不得整段陪葬 |
| **保底闸·合计** | 同上 | **合计超限** ⇒ **按清单顺序从末尾逐条丢弃**（靠前者优先），丢到装得下为止；段首**显式列出丢弃清单**（哪篇、因合计超限） | 不阻断本轮发送；**不得整段停用、不得截前半段当规则**；丢弃条目**不进未注入汇总行**（丢弃 ≠ 失效） |

**口径（必须标注）**：

- **单条上限 5000 字符、合计上限 10000 字符**（2026-11-08 两次调整：6000 → 10000 → 5000 / 15000 → 20000 → 10000，用户拍板）——这两个数是**可调政策线，不是实测结论**。
- **合计 = 单条 × 2**：这不是巧合数值，是**可解释的预算关系**——最坏情况容得下「两篇各自顶格的规则」，第三篇顶格规则加入时必然触发按序丢弃。改单条线必须同笔改合计线，否则这条解释变成假话。
- **重算口径一句话**：先把「项目规则段允许占用的上下文比例」定死（建议 ≤ 上下文窗口的 20%），再用实测的「字符 → token」换算修正这两个数；每次修订都要带「时点 + 重算依据」，否则就是裸快照。
- **判据只用字符数**（`String.length`），**不把 token 估算作为闸门**——两把尺子会得出两个「超限」结论。
- **禁止**把 `registerWork.ts` 那套「截前 8000 字」的描述用裁切混进正文读取。
- **粒度不打架（2026-11-08 二次订正）**：单条超限 ≠ 合计超限。单条超限只剔该条（§6.2 与「单条失效」同处置）；**合计超限只丢清单靠后的条目**，靠前者照常注入、**不再整段停用**。旧稿写「超限 ⇒ 整段不注入」与 §6.2「单条失效只剔该条」冲突，已拆开。
- **常量只活在内核**：5000 / 10000 是内核私有常量，**不从包根导出**；宿主不参与判断、也不需要知道数值，只显示 `setResident` 返回的 `message`。将来界面若要在按钮上预判「点了会超限」，做成内核方法返回**同构结果**，仍不导出裸数字。
- **拒绝文案必须给差额与处置**：单条超限的 `message` = 「实际计量（含构成）+ 上限 + 差额 + **单文件超上限，请拆分该文件**」。例：`该文件含标题行共 5021 字符，超过单条 5000 上限 21 字符；单文件超上限，请拆分该文件后再置为项目规则`。只报「超限」会让用户以为系统算错（他的正文可能只有 4960 字符）；把处置写成「让合计迁就」则会把单篇问题摊给全体项目规则。
- **写路径合计拒绝的文案**：不只报「合计超限」，还要列出**会被挤掉的已设为项目规则的条目**（`setResident` 用同一个求值函数算丢弃清单），否则宿主面对的是一个没有解释的拒绝。

**计量口径（定稿）**：

- **合计 10000 = 最终注入段的字符数**（段标题 + 优先级文案 + 适用范围 + 各条渲染块 + 未注入汇总行（读失败 / 单条超限） + **丢弃清单行**），**不是「各正文长度之和」**——上限的目的是控制上下文占用，占额度的是实际发出去的东西，不是清单里的理想值。
- **单条 5000 同口径**：按**该条渲染块**（`### 来源文件：<path>` 标题行 + 正文）算，不按裸正文算。两把尺子会让同一文件在边界上得出两个结论。
- 计量单位一律 `String.length`（UTF-16 码元），不引 token 估算。
- **不含**段间分隔符（`\n\n---\n\n` 由 `buildSystemPromptPrefix` 拼接，不属于本段）。
- **求值顺序（消循环依赖）**：① 先定逐条失效集合（路径 / 二进制 / 单条上限，均不依赖总数）→ ② 按该集合渲染整段 → ③ 判整段长度 → ④ 合计超限 ⇒ **从清单末尾逐条丢弃、每丢一条重算一次**，直到装得下；丢光仍超限（只可能由路径清单撑爆段首）才退到一条状态行。失效与丢弃**分两列**：失效 = 这条自己有问题，丢弃 = 这条没问题、只是预算不够。
- **丢弃顺序的定义（可预测、可解释，不许随机）**：顺序真源 = **清单数组顺序**（段首文案已写死「按清单顺序，靠前者优先」）。合计超限时**丢弃靠后条目**，靠前者优先保留。**不引入 `priority` 字段**——那会与清单顺序形成第二套排序真源，冲突时无法解释「听谁的」，还要用户手填数字。
- **丢弃清单行计入预算，但不会形成循环**：每丢一条，正文少一个块（块 ≥ 路径 + `### 来源文件：` 标题），段首只多一个路径 + 一个分隔符 ⇒ 总长单调下降，循环上界 = 条目数。



### 6.2 失效可见（禁止静默跳过）

| 失效场景 | 检测点 | 处置 |
| --- | --- | --- |
| 文件被删除 / 改名 / 移动 | 装配前 stat（复用 `refProbe.ts` 的 stat 思路） | 该条**标失效**、**正文不注入**；装配段首**一行汇总条数与路径**（模型可见）；用户可见面由设置「作品和规则」页的**行徽标**承载（§8.2） |
| 文件无法读取（权限 / IO 错误） | 读盘异常 | 同上 |
| 文件变成二进制 / 非 UTF-8（登记后才变） | 装配期读盘时做一次 **fatal UTF-8 解码复核**（§7.1-9） | 该条判失效、正文不注入；段首汇总 |
| 被移出工作区 / 变成绝对路径 / `..` 逃逸 | 每次装配都过 `resolveUnderPrimaryRoot`（与写入侧 `relativeUnderPrimaryRoot` 同一文件、互逆，`refPath.ts`） | 判为失效；**拒绝读盘** |
| 符号链接指向工作区外 | realpath 复核——`resolveRealpath` 已导出（P0-a），复用同一实现（禁止复制第二份，`pathGuard.ts`） | 判为失效 / 拒绝；不得按字符串路径放行 |
| 条目被外部覆盖 / 另一窗口主动取消 | **与「清单声明的项目规则集合」比对**（不是与上一轮快照比对）：声明有、读不到 ⇒ 失效；声明没有、盘上无关 ⇒ 正常取消，不报警 | 失效者段首汇总 + 命令回执；正常取消**不报警**（§5.3 兜底） |
| 工作区未信任 | **宿主传入的信任态（新入参）**——内核无 `isTrusted` 态，装配期不能现读（§1.5） | **整层不装配** + 显式提示，不是「跳过某条」 |

> 「失效」与「未信任」都必须是**被记录的错误态**；未信任的工作区里静默不带规则，会重演「静默失败 = 假阴性」。
>
> **用户可见面的边界**：未信任 ⇒ 由宿主既有 `syncTrustNotice` 状态栏提示承担（已在册）；**未注入汇总的段首一行是给模型看的**，用户可见面由设置「作品和规则」页的行徽标 + 报告说明行承载（§8.2）。验收时不得拿段首标注当「已告知用户」。

**读盘失败的两分支（fail-closed 与「不静默」并存）**

| 状态 | 行为 | 理由 |
| --- | --- | --- |
| 未信任 | 空段（不读任何正文） | fail-closed 的硬面，与读盘成败无关 |
| 已信任 + 清单读失败 | 空段 + 内核日志（本轮不注入任何规则，下轮重试） | **不缓存、不沿用上次内容**——沿用会把「过期内容」伪装成「当前规则」，还要为它单开一条预算例外（§6.1） |

- **条目级读失败**（清单读到了、个别源文件读不到）：该条本轮不进段，其余条目照常注入。**段首只投影两类**（`read-failed` 读盘失败、`too-long` 单条超限）；非布尔误配不进段首（§10 已定边界），合计丢弃走独立丢弃清单行。**失败即不注入**：本层不保留任何跨轮正文缓存，每轮以磁盘为准重新求值。
- 读盘异常**不得中断** prepare / resume：降级后照常继续本轮（这是把「每轮读一次」引入新失败点的对价）。

> 已订正原因：范围变了（P1 把正文注入与读盘失败兜底拉入本批），非原稿写错——原稿未区分「未信任」与「已信任但读失败」两种降级。
>
> **失效判定的唯一手段 = 普通文件存在性判断**（stat / 读盘 ENOENT / 上面的路径守卫），**禁止**为此引入任何 git 调用：文件是否被版本控制跟踪与本能力无关。
>
> 与 §6.1 保底闸的区别（2026-11-08 二次订正）：**单条超限 / 单条失效 ⇒ 只剔该条 + 段首汇总**；**合计超限 ⇒ 按清单顺序丢弃靠后条目 + 段首丢弃清单**（不再整段不注入）。两者都报错，都不阻断发送。
>
> **丢弃清单**：随注入段进入模型可见面，同时由内核写一条结构化日志（含 `dropped` 路径数组）；宿主经 `agent.residentSegmentReport.dropped` 在「作品和规则」页行内显示「未注入（合计超限）」（§8.2）。

## 7. 设计边界（本版明确不覆盖什么）

| # | 不覆盖项 | 后果 | 用户能看到的信号 |
| --- | --- | --- | --- |
| 1 | **钉住 ≠ 规则** | 钉住只保证「引用留在本会话 + 清单跨重启恢复」，**不等于**正文每轮注入；要永久注入必须设为项目规则 | 有：钉住 🔒 形态与「项目规则」标记**视觉不同**（§8） |
| 2 | **技能正文注入** | 技能钉住只保留「选中的是哪个技能」（单槽），不把技能正文永久注入 system prompt | **部分有**：钉住标记可见，但「正文未注入」无专门信号（技能面板没有「项目规则」类标记） |
| 3 | **粘贴文本规则** | 输入框里的规则句不会被当作项目规则；必须落成文件 | **无信号**（不存在文本规则入口，等于没有入口可点） |
| 4 | **跨进程并发**（两窗口同开同一文件夹 / 编辑器手改 JSON） | 后写覆盖先写，可能丢掉一条项目规则标记 | 有：下一轮**与清单声明集合比对** → 段首未注入汇总 + 回执（**可见的丢失，不是已解决**，§5.3） |
| 5 | **独立 Webview 清单面板** | 不做常驻面板项目；清单常看面 = **设置「作品和规则」选项卡**，管理面 = 临时 QuickPick（§8.2） | 有：设置页常驻可见（关掉设置 tab 即消失）；不做面板内搜索 / 过滤 |
| 6 | **跨面板角标** | 同一项目的另一个会话面板不会即时刷新「项目规则」标记 | **无信号**（面板无角标）；语义在下一轮读盘时生效 |
| 7 | **工作区外路径** | 绝对路径 / UNC / `..` 一律不可登记、不可设为项目规则 | 有：命令报错「只支持工作区内相对路径」 |
| 8 | **符号链接与子模块** | 指向工作区外的符号链接需 realpath 闸拒绝；`resolveRealpath` 已导出（P0-a），可直接接；子模块被当普通目录，不识别其独立仓库语义 | 部分有：外链被拒有报错；子模块**无信号** |
| 9 | **二进制 / 超大文件** | **新入口已覆盖**（NUL / UTF-8 解码失败即拒）+ **装配期也做一次 fatal 复核**；**既有「登记作品投影」路径两条都没加**——小于单条上限（当前 5000）字符的二进制仍会被当文本登记并注入乱码 | 有（新入口明确拒绝 + 装配期判失效）；既有登记路径**无专门信号** |
| 10 | **非 UTF-8 编码** | **新入口 + 装配期已覆盖**（fatal 解码失败即拒 / 判失效）；既有登记路径仍一律按 UTF-8 读，GBK 文件会乱码 | 有（新入口与装配期明确拒绝）；既有路径**无信号** |
| 11 | **只读文件系统** | 写清单失败（原子替换不可写） | 有：命令报错（写失败） |
| 12 | **多根工作区下的相对路径歧义** | 只认**首个工作区根**（`relativeUnderPrimaryRoot` 语义）；其他根的文件不可用。宿主生成侧已收口到单点 `toWorkspaceRelativePath`（P0-c 落地，当场拒绝并给可读原因） | 有：非首根文件登记 / 置为项目规则时报错；**旧条目里已存在的撒谎指针无信号**（本批不做数据迁移） |
| 13 | **`.memora/` 被用户仓库忽略或未提交** | 他人 clone 后可能没有这份清单；本地与他人环境不一致 | **无信号**（界面只显示本机磁盘实际内容，不做来源或共享标注） |
| 14 | **右键与清单两个入口同时存在** | 两处都能改同一个 `resident` 字段：右键是**快捷面**，清单 QuickPick 是**管理面**（§8.1）。不覆盖：另一面板/另一窗口不会即时看到改动；跨进程并发覆盖仍按 §7-4 处理 | 有（同字段同文件，下一轮读盘后一致；无「两个开关互不同步」歧义）；跨面板即时同步**无信号**（§7-6） |
| 15 | **凭据内容夹带** | **只防凭据路径**（`BLOCKED_PATTERNS` 只匹配路径）；文件正文里写死的 token / 私钥**不防**——全库唯一密钥相关处理是日志脱敏，**内容侧零防线** | **无信号**（正文照常注入 prompt；不做内容扫描） |

### 7.1 硬拒绝项（不接受的东西）

1. **只接受工作区相对路径、且为规范形**：**统一调用宿主单点判据 `toWorkspaceRelativePath`**（`workspaceRelativePath.ts`，判据委托 `refPath.ts` 的 `relativeUnderPrimaryRoot` / `resolveUnderPrimaryRoot`），`undefined` **当场拒绝**；绝对路径 / UNC / 任何 `..` 段 / 非规范形一律拒。⚠️ 内核写入守卫 `resolveSafePath`（`workProjection.ts`）是**另一层**（防写出项目根），不得当作与宿主生成侧同源。
2. **受工作区信任门约束**：信任态由**宿主作为新入参**传入内核（未信任 ⇒ 整层 fail-closed）。内核侧无 `isTrusted` 态，装配期现读在物理上做不到；这是**内核公开面变更（minor）**，不是文档能自行实现的。
3. **符号链接逃逸**：`relativeUnderPrimaryRoot` 不 realpath ⇒ 读盘前必须 realpath 复核仍在首根内。`resolveRealpath` 已导出（P0-a），复用同一实现，**禁止复制第二份**。这是安全闸，不因「子模块/链接语义」未覆盖而放宽。
4. **凭据类路径拒绝（复用已导出判据）**：`pathGuard.ts` 的黑名单常量是模块私有，但**判据已导出**（`matchBlockedPathPattern` / `isBlockedPath`，P0-a 落地）⇒ 复用同一实现，禁止复制第二份。即使在工作区内，也不该把 `.env` / `.npmrc` / `.git-credentials` 每轮读进 prompt；项目规则比索引更危险（**永久**注入）。⚠️ **它只匹配路径**——证据不足时**不敢写「已防凭据内容」**：本期只防凭据路径，正文内容夹带不防（§7-15）。
5. **不做规则引擎**：无通配符、无 glob、无目录扫描、无条件判断、无自动发现；一个条目只对应一个具体文件。
6. **不自动迁移**：不做 `.memora/rules.md` 迁移，不把临时锁自动转为项目规则。
7. **禁止绕过写队列**：宿主、webview、设置页一律不得直接读写 `work-projections.json`；手改文件属外部写入，只由损坏 fail-safe 与「**与清单声明集比对**的失效检测」兜底。
8. **禁止同一文件两处注入**：项目规则条目不得同时留在【项目索引】注入块（§4.4）。
9. **非文本文件拒绝（作用域仅限新入口「切换项目规则」）**：
   - **判据（最小化，二选一命中即拒）**：读取内容**含 NUL 字节**（`buf.includes(0x00)`）；或**按 UTF-8 解码失败**（`new TextDecoder('utf-8', { fatal: true })` 抛错）⇒ 提示「该文件不是文本文件，不能作为项目规则」。
   - **原子性**：**不登记、不置位、不留半成品**；不做扩展名 / 魔数嗅探（§7-9 已改口径）。
   - **执行点（两侧都要）**：① 新入口的宿主命令读取段（与 `registerWork.ts` 同层），在调 `registerWork` / `setResident` **之前**；② **装配期读正文时再做一次 fatal 解码复核**（登记后文件可能变成二进制 / GBK，装配期不复核就会每轮注入乱码，§6.2）。**判据不放内核登记路径**——放内核会同时作用到既有登记路径，违背本节的作用域限定。
   - ⚠️ 既有「登记作品投影」路径**本轮不动**、两处都未加同一判据（该洞仍在，见 §7-9 与 §10「已定处置」）。
10. **`registerWork` 必须 upsert，不得抹掉 `resident`**：同 `source` 重登记时**保留既有 `resident` 与未知字段**，只覆盖 `name` / `description`（§5.4 A 级缺口）。触发者是模型工具 `register_work`，不是假设场景。

## 8. 两种锁视觉可分 + 单一命令（快捷面 / 管理面）

| 锁 | 语义 | 生命周期 | 呈现（定稿要求） |
| --- | --- | --- | --- |
| **会话级钉住**（0.10.0） | 本轮之后不清，仍以**指针**进信封（正文不注入） | **跨轮保留 + 跨重启恢复清单**（`SessionMeta.pinnedItems`；草稿期白锁为已知限制） | 保持现有 🔒 形态 |
| **项目规则**（新增） | 投影条目 `resident: true`，正文进 system prompt | **跨重启、跨会话都在** | 清单（QuickPick）打 **「项目规则」标记**；「作品和规则」页行内用**勾选图标 +「项目规则」后缀**，与临时锁 🔒 视觉可分（§8.2） |

**为什么必须可分（具体后果）**：两者的持久性都已成立，差别在**消费面**——钉住让「指针留在信封里（模型按需 `read_file`）」，项目规则让「正文每轮进 system prompt」。若呈现长得一样，用户会把钉住误当项目规则，以为正文已注入、模型必读；实际模型只收到了路径、可能整轮不读。这类误读**没有任何信号**（回答照常产出），代价是「以为有约束、其实没有」；反向误读（把项目规则当钉住）的代价是多付一次不必要的永久注入预算。

**命令面（已落地，按实现订正）**：写路径仍是**同一套**（`registerWork` + `setResident`），但命令层是**新增行为**，不是修改既有登记命令：

- **既有命令不动**：`memora.registerWork`（`registerWork.ts`）保持 title「Memora: 登记作品投影」与「无 uri ⇒ 警告退出」分支——它只负责登记，不承担清单视图。
- **新增两条命令**（`hosts/memora-vscode/src/extension/commands/residentRules.ts`）：
  - `memora.toggleResidentRule`（title「**Memora: 切换项目规则**」）：右键文件 / 编辑器标签切换该文件的常驻态；无 uri ⇒ 提示「请在文件上右键」。
  - `memora.manageResidentRules`（title「**Memora: 管理项目规则**」）：QuickPick 管理整份清单（回车切换、条目按钮「移除登记」——只解登记，不删源文件）。
- **标题必须中性（三条平台限制理由）**：① `package.json` 的菜单 `title` 是**静态贡献**，同一 ID 无法按状态改文案；② `when` 只能读**上下文键**，读不到「被点那一项」的逐项 `resident`；③ 用 `setContext` 存「最后选中文件」的态，在多根 / 多选区 / 连续右键不同文件时会**把 A 的态套到 B**（显示错状态）。故**不按状态变文案、不做 `setContext`**：当前态由点击后的内核回执（文案原样展示）与 QuickPick 的勾选后缀如实呈现。
- **注册位置**：`explorer/context` 与 `editor/title/context` 两处都挂 `memora.toggleResidentRule`；管理命令从命令面板进入（`package.json`）。

| 调用方式 | 结果 |
| --- | --- |
| 右键某个文件（**快捷面**） | 先读当前态：未登记 ⇒ 不新建条目，回执提示先「登记作品投影」；已登记 ⇒ 只翻开关（§8.1） |
| 不带文件上下文（**管理面**） | 弹出**临时 QuickPick 清单**，逐条显示「项目规则」标记，可逐条切换 |

- 清单的管理面是**临时 QuickPick**；常看面是设置「作品和规则」选项卡（行内切换/移除，§8.2）。
- 取消项目规则 = `setResident(false)`，条目留在清单（回到「简介 + 按需读」）；取消不读正文、不判上限。
- 本期不做跨面板角标；反馈由命令回执 + 「作品和规则」页行徽标承载（§8.2、§10）。

### 8.1 右键快捷入口「切换项目规则」（定稿）

> 用户已确认采纳：把「在清单里翻开关」优化为右键直达。

- **性质 = 同一写入路径上的新组合调用**：不是第二条写入路径（写盘仍只有 `workProjection.ts` 一处），也不是「沿用现有行为」（现有 `registerWork` 的无 uri 分支是警告退出，与切换无关）。实现语义固定为：

  ```
  读当前态（内核 listManagedWorks，宿主不自行判断）
    ├─ 已登记、非项目规则 → setResident(true)    （只翻字段）
    ├─ 已登记、已是项目规则 → setResident(false)  （只翻字段，条目留在清单）
    └─ 未登记 → setResident 回 not-found + 指路文案
                 （**绝不新建条目**：先「登记作品投影」，再切换）
  ```

  不新增平行的登记 / 写盘逻辑；`setResident` 自身也不创建条目（内核结果码 `not-found` 的语义即「清单无该条目登记」）。

- **必须先读当前态（顺序不可反）**：先读内核归一后的清单再决定翻向哪边——否则同一个中性命令会把「开启」误发成「关闭」。
  🔴 **反例（必须防）**：对已登记文件点右键却走「重新登记」⇒ 覆盖用户已手改的简介 + 白跑一次 LLM 总结（多花钱、更慢、简介还可能被改坏）。故切换路径**不调 `registerWork`**；登记与切换是两个入口（§5.6）。
- **全有或全无（动手前拦截）**：超上限（单条 5000 / 合计 10000 字符；合计按「加入后是否会丢弃任何条目（含本条自身）」判）、命中 `BLOCKED_PATTERNS`、路径在工作区外、**非文本文件**（§7.1-9）⇒ 一律在**写盘前**拒绝。不允许出现「提示失败但清单里多了一条半成品」的中间态，也不允许「置成功却静默挤掉别人」。
- **菜单标题中性、状态由回执呈现**（同一位置只出现一条，不并列多个选项）：

  | 当前状态 | 菜单项（静态标题） | 点击结果 |
  | --- | --- | --- |
  | 未登记 | **切换项目规则** | 不新建条目：回执提示「先登记作品投影」（`not-found`） |
  | 已登记、非项目规则 | **切换项目规则** | 仅翻 `resident = true`（不重登记） |
  | 已设为项目规则 | **切换项目规则** | `resident = false`（条目保留在清单） |

  **实现取向（按落地实现）**：VS Code 菜单标题是静态贡献、`when` 读不到逐项状态、`setContext` 在多根 / 多选区下会显示错状态 ⇒ **不做按状态变文案的方案**，只注册单一中性命令 `memora.toggleResidentRule`；「当前落在哪一态」由点击后的内核回执（成功 `enabled` / `disabled`）如实播报，清单面则用勾选后缀。三条平台限制理由的完整写法见 §8。

- **文案口径**：**对外统一叫「项目规则」**（菜单、回执、清单标记、段标题、提示语全用这一套），**不使用「加锁」这类内部词**。代码标识符保持 `residentRules` / `resident` 不变——**只统一对外文案，不做大范围重命名**（理由：会话级「钉住」是另一套能力，两个都叫「常驻」会让排查来回猜）。
- **失败路径**：简介生成失败（LLM 失败 / 超时）时仍要**成功开启项目规则**（简介只服务界面、不参与注入），但必须明确告知「简介已用文件名兜底」（`registerWork.ts`），**不得静默降级**。
- **与清单开关的关系**：QuickPick 里的逐条开关是**管理面**，右键是**快捷面**；两者写同一个 `resident` 字段、同一份清单、同一写入队列。**不是两条并行能力，也不存在第二个真相源**。

## 9. 排雷结论

### 9.1 SSOT

| 问题 | 结论 | 判据 |
| --- | --- | --- |
| 「哪些文件设为项目规则」唯一真源 | **`work-projections.json` 里的 `resident` 字段**（一份文件） | 同一路径不得同时出现在 webview 本地数组 / 会话 meta / 设置页副本 |
| 会不会双真源（索引 vs 项目规则段） | 不会：同源同文件，只是**两个渲染规则不同的消费面**（§4.4） | 注入块剔除 `=== true`；项目规则段只取 `=== true` |
| 正文与磁盘的关系 | **每轮装配重读**（truth = disk） | 外部改文件后下一轮即生效；不得把正文缓存在 webview |
| 清单缓存 | manager 内存缓存只作读缓存，**写只写磁盘** | 写路径单一；缓存失效可重建（`agent.ts` 读缓存，异步段刷新） |
| 写路径 | **唯一队列 + 唯一写函数**（§5.3、§5.8） | 任何第三写盘点即未收口 |
| 顺序 | **清单数组顺序**（不另存顺序字段） | 删除即顺延，不存在需要维护的编号 |
| 两个入口（右键 / 清单开关）会不会双真源 | **不会**：右键 = `查重 → registerWork → setResident` 的组合调用，写同一字段、同一文件、同一队列（§8.1） | 不出现第二个写入面；「快捷面 / 管理面」只是两个触发方式 |
| 术语撞车（`resident`） | 本稿 `resident` = **项目规则**；代码里另有 `capabilityState.kind === 'residentOnly'`（**常驻工具**，宿主 `capabilityState.ts`、`roleBadgeView.ts`），**两者无关** | 见 §3.1 术语锚点；命名 / 注释不得把「项目规则」与「常驻工具」混用 |

- **索引块保留同属设计正确**：字符串 `"true"` 未被认作项目规则 ⇒ 该条目仍按普通条目进【项目索引】（2026-11-08 手改实测 C 组），**不是「漏剔除」缺陷**——开关与剔除是同一把判据 `isResidentEntry`（`=== true`）：认成项目规则才剔除，没认成就不剔除，两条分支不可能分叉。

- 现状两处直读 `isTrusted`：`readProjectAssetDirs`（调用时现读）、`syncTrustNotice`（activate 首次调用 + **授予信任监听器内再次调用** ⇒ 本来就是现读，不是一次采样）。

- 结论：三处收敛成一个读口。兜底条件：开工时若复核发现 `syncTrustNotice` 新增调用点、或依赖「只在 activate 读一次」，则**退回「只收敛 `readProjectAssetDirs` + P0-d 两处」**，并在此登记不并入的原因——少收一处是退让，硬收一处不查语义是造 bug。

- **不合并成一个开关**：注入物不同（资产目录 vs 项目规则正文），合并会让某一侧将来放宽时另一侧静默扩权。
- **分叉触发条件**（写明，防后人凭感觉复制判据）：仅当 ① VS Code 出现按功能域/按目录的信任，或 ② 某消费面需要比工作区信任**更严**的门（如项目规则正文额外叠加 `isBlockedPath`）时才分叉。届时形态 = 「信任读口不变 + 该消费面叠加自有门」，**不是**复制一份信任判定。

**信任态变化：授予后重建装配（同一监听器内追加）**

- 监听**已存在**：`vscode.workspace.onDidGrantWorkspaceTrust`（`extension.ts`，当前分支做「补注入项目资产 + 两面板清单重推」）。本批在**该监听器内**追加重建装配，**不新开第二个 listener**——同一事件两条处理路就是渲染路正在修的「同一次重建两条路」的同型病。
- 重建装配**复用唯一装配入口** `assembleAgentForSession`（经 `AgentRegistry.createAgentForSession` 的 factory）。⚠️ 实测：该入口命中已登记即返回同实例，**没有淘汰/重建能力** ⇒ 最小扩张 = 给同一方法加**可选**重建参数（契约扩张走可选字段），**不新增 `rebuildAgent` 方法、不复制装配循环**。
- **重建参数只有一个合法调用口** = 信任监听器分支。落地要求：参数不用裸 `boolean`，用**字面量来源**（如 `rebuild?: { source: 'workspace-trust' }`）——让「谁传的」在类型与日志里都留痕、可 grep；方法 JSDoc 顶部写死约定标记 `UNIQUE-CALLER: onDidGrantWorkspaceTrust`，并在每次触发时记日志（含 `source`）。新增任何传 `source` 的调用方**先报用户**；提交前按 grep 复核「非该监听器无调用点」。仅靠注释约束不住，所以这条进提交前复核清单。
  - **通用做法（同类场景照此办）**：凡「唯一调用口」要求，一律用字面量来源参数把约定做进**类型事实**；不靠注释约定、不靠评审记忆。（裸布尔只能靠人守，来源进类型后可断言、可 grep、可日志。）
- 未信任 ⇒ 不注入任何项目规则正文（fail-closed，宁可不给）。
- **反向刷新不实现**：VS Code 的信任只能 untrusted → trusted，撤销信任须重开窗口 ⇒ 运行期不存在「撤销」事件。写明原因，防后人「补全」一个不存在的场景。
- 在途装配：命中 `inflight` 时先等其落定再重建；重建前关闭旧实例须确认不丢未落盘数据（验证点见 §12.5）。
- **忙碌态不得硬切**：`agent.isBusy` 为真时重建会打断在途 turn ⇒ 按既有配置热重载纪律「busy 时暂存、收尾补执行」，禁止「先关旧实例再建新实例」在 busy 时执行。
- **暂存不许静默**：暂存那一刻必须留一条**用户可见**记录（输出通道 + 状态栏/通知其一；文案说明「已授予信任，项目规则将在本轮对话结束后生效」），收尾补重建成功后**清除**该记录；补重建失败则记录**不得**消失。合格判据：界面与日志都能看到，只在代码里有分支 = 不合格。
- **面板绑定必须跟随**：重建后要让 `chatPanel` 的**既有**绑定入口（`setAgent` / `getAgent` getter 委托 / `_sessionAgents`）指到新实例，否则「内核换了、面板还读旧实例」= 新的静默失效。
  - **文件身份（已核实）**：全仓只有一个 `chatPanel.ts` = `hosts/memora-vscode/src/webview/panels/chatPanel.ts`（4242 行上限所指就是它；`src/extension/host/chatPanel.ts` 不存在），`setAgent` / `_sessionAgents` 都在该文件内。
  - ⇒ 本批**只准调用它的既有公开方法**，**不得改该文件一行**；若发现必须改它才能跟随绑定，**先报用户**，不得自行开刀（该域属渲染路在途）。
- **行数余量不是可支配空间**：`chatPanel.ts` 现 4071 行（上限 4242）是渲染路**搬走方法之后**的数字，那 171 行正被该路第 2 步（渲染顺序）吃掉 ⇒ **禁止按「还有 171 行」规划任何新逻辑**；P0-d 的新代码一律落**独立模块**，该文件只调既有公开方法、零新增行。

### 12.5 测试

- 内核：`undefined` / `false` ⇒ 判据 false（fail-closed）；`true` ⇒ 判据 true；字段从 `AgentOptions` 透到装配产物取值一致。
- 内核消费面：未信任时首条读盘路径**零调用**（读盘替身计数断言，不是只看返回值）；信任时正常读取。
- 宿主读口：用计数器替身证明 `readProjectAssetDirs` / `syncTrustNotice` / `buildAssembleOptions` 三条路径都经过 `readWorkspaceTrusted`，且**没有**第二处直接读 `vscode.workspace.isTrusted`。
- 宿主取值：`isTrusted` 两种取值下 `buildAssembleOptions` 产出对应布尔；未打开工作区不臆造 `true`。
- 授予信任：监听器触发后，已登记会话各重建**一次**（factory 调用计数），零登记时不重建；重建后装配选项 `workspaceTrusted === true`。
- 忙碌态：busy 会话收到授予信任时**不重建**（factory 零调用），收尾后再补（按暂存标记断言）；暂存时断言**可观察记录已写入**，补重建成功后断言记录被清除；补重建失败时断言记录**仍在**。
- 唯一调用口：grep 复核除信任监听器外无 `source: 'workspace-trust'` 调用点；能静态化就加成单测断言，不能则列为提交前人工复核项（不假装有测试）。
- 判据收敛等价：`syncTrustNotice` 合并前后调用点集合不变（activate + 授予监听器两处），不新增读取时机。
- **可测性前置**：`extension.ts` 属**零测试覆盖区** ⇒「哪些会话要重建、busy 时如何暂存」的判定不得写在监听器闭包里，必须下沉到 `host/agentRegistry.ts` 或同层可测模块，监听器只做接线；否则整条链路只剩零覆盖。
- 重建数据安全：重建后该会话历史 / 轮次不丢（真实存储用例，不用内存替身）。
- 信任撤销：**不写用例**——VS Code 无该事件，给它造替身等于给不存在的场景留证据。

### 12.6 dist 次序（硬约束）

1. 内核 `src/` 改完：根仓库 `npm run build:clean`（官方清后建；**不用裸 `npm run build`**，避免孤儿产物）。

3. 根仓库 `npm run verify:dist-contract` 三项全绿。
4. `npm run ci:local -- --preset=fast` 全绿后提交。
