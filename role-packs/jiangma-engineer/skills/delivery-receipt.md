# 收尾交付

## 用途

改动完成、准备交付与汇报时使用。收尾的目标不是「看起来做完了」，是让另一个人能独立判断做没做完。

## 零、落地后回扫（交付前必做）

| 原则 | 回扫问题 | 不过就改 |
| --- | --- | --- |
| SSOT | 有没有复制执行链 / 判据 / 真源表？有没有第二份数据？ | 合并回真理源 |
| 自然生长 | 新入口是否只写了差异段？接管的旧形态是否退役干净？ | 退役旧形态 |
| 不带伤 | 有没有半成品、假事实、未核当已核、为过闸放宽标准？ | 补齐或挂账 |

回扫不过不交付；挂账项写进汇报的「未闭合」，不藏在正文里。

## 一、变更面清单

逐项写清：

1. 改了哪些文件（新增 / 修改 / 删除）
2. 影响哪些入口（按钮、命令、监听器、协议、公开接口）
3. 影响哪些公开面（导出符号、配置键、文案、持久化格式）
4. 有没有未覆盖的同类点

入口类改动必须附完整入口表；公开面变更必须列全，不许「大概就这些」。

## 二、同批入账

- 项目若维护任务台账或变更记录：**同一批改完**，不攒到最后；已完成项留册标记，不直接删除。
- 项目若没有：跳过，不为了「看起来规范」硬造一份。

## 三、提交纪律

- **未获明确的提交指令前不提交**；获指令后**逐文件**暂存：一次一个路径，禁止 add -A、add .、commit -a 这类一把抓。
- 禁用 --no-verify 及一切绕过门禁的手段；门禁红了查原因改到能过，不降断言、不加跳过、不放宽阈值。
- 获提交指令后**默认只提交、不推送**；推送与发布属不可逆操作，交回用户。
- 提交信息只写做了什么与为什么，不写处数统计。

## 四、汇报四段

| 段 | 要求 |
| --- | --- |
| 结论 | 先行、可独立判断：成了 / 部分成了 / 没成 |
| 证据 | 测试文件数 + 用例数、命令与结果、关键日志；每条标来源 |
| 未闭合 | 单列，不藏在正文里；写清为什么没闭合 |
| 下一步 | 可执行，标明是否需要用户拍板 |

- 数字与「已核 / 未核」必须紧跟来源；贴不出来源就写「未核」。
- 不用「应该 / 大概 / 可能 / 没问题」当结论。
- 收据只证明命令跑过，不等于结果成立；没有独立证据面就不要说「已验收」。

## 校验清单

- [ ] 落地后三原则是否回扫过（SSOT / 自然生长 / 不带伤）？
- [ ] 变更面是否列全（文件 / 入口 / 公开面）？
- [ ] 台账与变更记录是否同批更新？
- [ ] 是否在获提交指令前保持未提交、获指令后逐文件暂存且未推送？
- [ ] 汇报是否四段齐全、数字带来源？
