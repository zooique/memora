# 网络养分与土壤验毒

## 用途

非平凡设计、技术选型、报错无解时使用。搜索是吸收养分，不是方案照搬；先营养，后构思。

## 何时搜

- 要做非平凡设计或选型
- 遇到没见过的报错、版本行为变化
- 怀疑自己的经验已经过期
- 需要用户拍板的设计分叉（先搜主流做法，再给推荐项）

## 搜什么

1. 官方文档与规范（版本、限制、废弃项）
2. 主流实现怎么做（至少两个独立来源）
3. 社区踩坑与已知缺陷
4. 变更日志（判断「文档旧」还是「我记错」）

## 种子过滤（三档）

| 档位 | 条件 | 处置 |
| --- | --- | --- |
| 弃用 / 改造 | 与最小单元或现有架构冲突 | 不用原方案，只取其中可用的局部 |
| 吸收为依据 | 已被验证的最佳实践，且与最小单元兼容 | 写进设计决策 |
| 仅记录来源 | 有参考价值但依赖未验证 | 记来源，不做硬依赖 |

**吸收但不进设计 = 白吸收**：搜索结论必须落到某个设计选择上。

## 土壤验毒

「请求成功」只证明这条链路有人回答，不证明目标服务如此回答。

- **响应不等于真值**：代理、企业网关、DNS 改写真会返回成功。
- **反证法**：拿一个必然不成立的输入做对照（不存在的版本 / 路径），期望失败或空；对照也「成功」⇒ 之前的成功全部作废。
- **区分「还没生效」与「没有生效」**：CDN 与索引有传播窗口，窗口内的旧值不是结论。
- **留痕先于结论**：先记请求时刻、响应头、实际地址，再下判断。

## 产出

养分清单：来源 → 结论 → 采用档位 → 落进哪个设计决策。缺最后一列就是没吸收。需要拍板的，另给推荐项、理由与不选其他项的原因。

## 校验清单

- [ ] 是否至少两个独立来源？
- [ ] 外部方案是否过了种子过滤？
- [ ] 关键事实是否做了反证或留痕？
- [ ] 结论是否进设计决策？
- [ ] 需要拍板时是否给了推荐项与理由？
