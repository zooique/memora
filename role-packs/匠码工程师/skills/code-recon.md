# 定向侦察

## 用途

在改任何文件、类型、字段或生命周期之前，用最小阅读预算建立一张可靠的现场图。侦察不是「多读点」，是「只读该读的，并读对」。

## 本技能不做什么

只负责看清现场，不判伤、不改码：发现可疑处记为「待排雷」，交 `pre-change-audit` 判定；修复归 `root-cause-fix` / `ssot-growth`。

## 三条读取律

1. **先清单、后定向**：先列目录 / 读索引，判定哪些文件值得读、哪些跳过；不盲读整个仓库。
2. **分区读、按需续**：大文件分段读；被截断时明确自己看到第几行，只续读真正需要的区间，不重读已覆盖段。
3. **读一段、记一段**：每读完一段，把要点压缩成自己的清单（结论、符号、风险），最后基于清单设计，而不是回头再读原文。

## 前置：先读结构怎么描述它自己

改类型、字段或生命周期前，先读它的 JSDoc 或不变量注释——那是它对自己下的判据。

- 注释里写的「非空 ⇔ …」「仅当 … 才 …」往往直接决定改法；
- **注释与实现冲突时，冲突本身就是待查缺陷**：先证伪，不许以「注释大概过时了」为由无视。

## 四个必答问题

| 问题 | 动作 |
| --- | --- |
| 符号在哪定义？ | 跳到定义处，确认所属模块与依赖方向 |
| 谁在调用？ | 检索全部调用点，逐个核对入参形态 |
| 数据从哪来、到哪去？ | 顺着生产点 → 存储 → 消费面走一遍 |
| 谁是唯一写者？ | 找出全部写入点；不止一处就不是「唯一」 |

## 产出

一份侦察清单：涉及文件、关键符号、调用点、不变量、已知风险、待确认项。清单写给自己看；进结论时只留必要项。

## 校验清单

- [ ] 是否读了目标结构的不变量注释？
- [ ] 调用点是全量检索，不是凭印象？
- [ ] 写入点是否穷举过？
- [ ] 未覆盖的区域是否如实标注？
