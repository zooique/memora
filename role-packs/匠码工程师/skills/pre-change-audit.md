# 动手前排雷

## 用途

任何非平凡改动的**落地前**，先把「这次改动会带出来的伤」找出来。对象不止代码——设计、文档与结论同样要排：结论要查证据是否成立，文档要查断言是否与实现同源。排雷的产出不是「应该没事」，是**逐条可指认的结论**：真带伤 / 良性 / 已收敛。

## 本技能不做什么

不定位实现、不写修复：现场图归 `code-recon`，修复归 `root-cause-fix` / `ssot-growth`。

## 五类带伤模式

| # | 模式 | 识别信号 | 取证动作 |
| --- | --- | --- | --- |
| 1 | **残留旧形态** | 新入口接管了旧路径，旧判据、旧文案、旧分支还在 | 搜旧形态的判据与文案，确认是否仍被调用 |
| 2 | **谎报位点** | 面向使用者的描述与实际执行路径不一致 | 三方对照：描述 ↔ 实际执行 ↔ 文案，任一不一致即假事实 |
| 3 | **真源双份** | 同一条判据 / 常量 / 真源表在两个地方各写一遍 | 搜该判据的全部出现点，确认是否存在第二份 |
| 4 | **静默失败** | 解析、装配、配置出错时跳过且无诊断 | 检查「跳过」分支是否留可见告警；无告警即静默降级 |
| 5 | **措辞折叠** | 「共用 / 统一 / 一致 / 恒 / 全部」这类全称词 | 回到调用点核对覆盖面；措辞宽度必须与最大作用域齐宽 |

文档与结论额外查一条：**断言是否有可指认的来源**；拿不出来源就按「真带伤」处理，不按「大概对」放行。

## 结论三分

- **真带伤**：有可指认的现症与影响面 → 先修，再继续原任务；修不动就在结论里挂账。
- **良性**：现状是有意设计，能说清理由 → 不动，但要在结论里写一句「为什么不改」。
- **已收敛**：已有守卫或测试覆盖 → 引用守卫位置，不重复造机制。

## 三条纪律

1. **推翻了原判断，先报告**：结论与任务前提冲突时，先说明「原话是什么、实测是什么、依据在哪」，再决定是否继续。
2. **排雷阶段一次列全**：同型点全部列出并标注位点，不留给修复阶段零散补。
3. **不许「看起来更准确」就改**：改写必须能指到代码落点；指不到就归「待定」，不猜。

## 产出

排雷表：模式 → 位点 → 证据 → 判定 → 处置。真带伤项决定是否继续原任务。

## 校验清单

- [ ] 每条「真带伤」是否带位点与证据？
- [ ] 文档与结论的断言是否都指到了来源？
- [ ] 同型问题是否全量检索？
- [ ] 推翻任务前提时是否先报告？
