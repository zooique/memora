# Memora 3.0.0 发版前设计缺口评估（大白话版）

> 评估日期：2026-09-23
> 方法：第一性原理 + 对抗式审查。结论均经源码/grep/台账实证，非凭记忆。
> 一句话定位：memora 是**零第三方运行时依赖的纯逻辑 Agent 内核**（宿主注入持久化/沙箱/UI），核心是 turn⊃loop⊃step 闭环 + 治理型记忆 + 角色包插卡。3.0.0 = 架构收敛后的首个稳定发布基线。

---

## 一、我吸收了哪些 2026 年的 agent 养分（外部对标）

来源：Anthropic 官方 agent 工程指南（2025-09 / 2026 续更）、Mem0 / MemGPT(现 Letta) / 多家生产实践复盘。共识版：

1. **分层记忆 + 混合检索（关键词 + 向量）是 2026 生产默认**。纯关键词召回是少数派/简化形态。
2. **Recall-before-act**：生成回复前必须先检索记忆，否则就是"裸模型"，必然幻觉。
3. **上下文工程 > 提示词工程**：压缩(compaction)而非截断、冻结前缀做缓存、工具按需渐进披露。
4. **工具即公共 API**：动词命名、窄职责、结构化错误、失败优雅降级。
5. **持续评估**：用 eval 量化"记忆是否真的改善了回复"。
6. **遗忘/衰减**：过期记忆比没有记忆更糟（模型会自信地用错的旧事实）。

memora 已对齐的：compaction 压缩（非空截断）、工具渐进披露（skill 两级）、治理（去重/冲突/supersede）、统一记忆模型、零依赖。这些是真护城河。

## 二、直接回答你的问题

**有没有"必须先解决才能发布"的设计缺口？**

**没有设计层的硬阻塞。** 唯一的真门闸是**验证缺口**（不是设计问题）：skill 系统在 VS Code 宿主上**没跑过真机调用**（tasks/待完成任务.md §3.0.0 ⑥，用户已决策：先提交、不打标、待宿主验证）。这个不做，发版等于盲发。

**但有一个必须"决策 + 对外讲清"的设计张力**，和两个建议补强的护城河动作——它们不阻塞发版，但带着"记忆内核"的营销发版、而内核实际只交付关键词召回、文档又没讲清边界，用户踩坑后会反噬品牌。

## 三、对抗式缺口清单（按严重度分级）

### 🔴 缺口1：纯关键词召回 vs 2026 混合检索标准 —— 最大、且当前台账未记录

**实证（非推断）：**
- `src/memory/storageInterface.ts:70-76` —— `search()` 明确是"关键词搜索，Intl.Segmenter 分词 + LIKE 匹配"，**接口形状就是关键词**。
- `docs`/架构规则 #6 + README L102 + tasks 英文 README 漂移修复（2026-09-21）—— 语义向量通道已于 B0（2026-09-18）**物理移除**。
- grep `recallBeforeAct|autoRecall|preRecall` 在 `src/` **零命中**——无语义检索 API。

**影响：**
- 开箱即用，memora 的招牌"跨会话长期记忆"只能按**字面对齐**召回，不能"概念性"召回（例："我们是否标记过这笔可疑交易"靠语义而非字面，纯关键词做不到）。
- 弱模型 / 非原生 function-calling 模型（如你正在用的 mimo-v2.5-pro）连 `search_memories` 都未必调得动（见 TC-1 P0），记忆实际形同虚设。

**是否阻塞发布：不阻塞。** 理由：零依赖铁律（ADR-002）下，向量要引 better-sqlite3 / embedding API 会破戒；且 host-owns-strategy 原则下，检索策略本就该宿主注入。

**但必须做一件事（发版前）**：把"语义召回归谁"写进契约/README。三选一：
- (a) 在内核之外明确给出"宿主如何挂语义召回"的契约与示例；
- (b) VS Code 宿主发版即带一个向量后端参考实现；
- (c) README 明说"内核只做关键词，语义召回是宿主能力"。
现在 README 把 memora 当"记忆内核"营销，召回能力却实际是宿主能力——**对外契约与实现对不齐**，是隐性坑。

### 🟡 缺口2：无 recall-before-act 兜底 —— 与 TC-1 同一根因

**实证：** grep `autoRecall` / `recallBeforeAct` 在 `src/` 零命中。检索纯靠 LLM 自觉调用 `search_memories`。

**影响：** 模型不调 → 零记忆 → 与"记忆内核"承诺直接不符。弱模型尤甚（这正是 TC-1 静默失败的上游根因之一）。

**是否阻塞：不阻塞**（host-owns-strategy）。但内核可加一个**可选 `autoRecaller` 钩子**（每轮注入 top-K 相关记忆，宿主显式开启），把"记忆内核"的承诺从"靠模型自觉"变成"内核可兜底"。这是低风险、把护城河做实的动作。

### 🟡 缺口3：无过期/衰减，完全靠 supersede —— 已知限制但 README 没讲清

**实证：** `MemoryDecayScheduler` 已移除（架构规则 #8）；只 `supersededBy` + `accessedAt` 命中刷新。

**影响：** 用户改了事实但没触发 supersede → 新旧并存 → 模型随机选 → 自信幻觉（memstore #4 明说 stale > no memory）。

**是否阻塞：不阻塞**（哲学选择：自然遗忘优于完美记忆）。但 README/文档应把"记忆**不会自动过期**，需治理工具或 supersede"作为**明确限制**写出，否则用户踩坑会怪内核。

### 🟢 不视为缺口（对抗后推翻）
- **单 Agent（ADR-004）**：2026 多 Agent 是趋势，但 memora 定位内核 + 角色包隔离，刻意单 Agent，合理。
- **无 prompt-caching / 前缀冻结**：属宿主装配职责，内核不越界，合理。
- **无 agent 级 eval**：内核 unit test（2700+）已足，agent 行为评估归宿主，合理。

### ⚪ 发版包小瑕疵（质量门顺手修）
- README L9/L258 写"2700+ 通过 / **1 skip**"，但 2026-09-21 审计实测 **2733 passed / 4 skipped** → "1 skip" 已失真。`docs:links` 不查数字，需手动订正。

## 四、优先级动作清单（大白话，照做顺序）

| 序 | 动作 | 性质 | 阻塞发版？ |

## 五、结论

- **设计层没有必须修才能发的硬伤。** 内核架构（零依赖、治理型记忆、角色包隔离、单 Agent）在 2026 标准下依然成立，护城河清晰。
- **真正的发版闸门是 skill 宿主真机验证**（第 1 项），这是测试覆盖问题不是设计问题。
- **最该警惕的是"对外契约与实现对不齐"**：memora 以"记忆内核"立身，但召回能力实际是宿主能力（纯关键词 + 无语义 + 无自动召回兜底）。发版前不把这个边界讲清，用户按"记忆内核"预期用、发现只能关键词召回且弱模型下记不住， backlash 会直接打在"治理型记忆"这个核心卖点上。
- 建议：第 1 项必做；第 2 项在发版前至少落到文档层面；3/4/5 可在 3.0.0 或 3.1.0 补。
