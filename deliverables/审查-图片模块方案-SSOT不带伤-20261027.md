## 三、SSOT 评估：这个"引用派"是不是最优解

**主流三派：**
- **内联派（Cline / Roo）**：base64 直接塞进消息体。
- **脱水/复水派（WorkBuddy）**：落盘存 `{blob_id, mime, size, path}`，发请求前还原成 data URL。
- **引用派（本方案）**：存 `ImageRef{sha256,mime,width,height,bytes,name}`，base64 只在 `formatMessages`（唯一序列化边界）派生。

**对 memora 的硬约束：** ① 每轮整对象 JSON 原子重写落盘（F3）；② 内核零三方依赖（D16）。

- 内联派在约束①下直接爆——5 张 2MB 图 × 20 轮 ≈ 200MB 反复搬运，且 token 估算会把 1MB 图虚报成 26 万 token（方案 §5.2 四连爆成立）。所以内联被排除**是对的**。
- 本方案 = WorkBuddy 脱水/复水形的**同构适配**：单真相源 = 磁盘文件（sha256 为键），重负载（base64）在唯一边界派生；不进持久化消息、不进摘要/截断/记忆（这些都只读 `content`，结构上不可能漏图）。

**判定：在 memora 的约束下，这是 SSOT 最优解。** 依据：
- 没有另开存储（复用 `.memora/attachments/` + 既有 `RoundMessage` 落盘）；
- 没有新消息类型（走既有 `send` 输入，用 `kind` 判别不撞协议计数，§6.1 避坑成立）；
- 没有新协议通道；
- sha256 是贯穿 5 类载体 / 3 跳投影的**唯一键**，没有第二真相源。

方案**吸收得当**：没硬抄 Cline/Roo 内联（会爆存储模型），取了 WorkBuddy 的脱水/复水形，再按 memora 约束做减法（不转码、不 canvas 压缩、fail-closed 能力门禁）。这不是原创，但是是**对本项目约束最贴的解**。

## 四、不带伤评估：剩下的"伤"在哪

1. **【方案完整性缺口 · P0 必须补】token 估算"全仓单点"是过期的。**
   内核 `estimateTokensMessages` 是单点没错，但宿主 `chatPanel.ts:2214` 自己又调一次 `estimateTokensMessages(history)` 做对话 token 显示，且 `chatPanel.ts:3130` 注释自认 injected-block 估算是"**第二真理源**"。方案 §5.9 只接了内核侧，**完全没审宿主显示侧**。图片 token 分支若只进内核估算器，而 chatPanel 传入的 `history` 不带 attachments，或没走带图分支，就会出现：**用户看到"还剩 8k"其实已经爆窗**。P0 验收前必须确认 chatPanel 的 dialogue-token 显示传入带 attachments 的 history 且走同一带图估算器。

2. **【结构伤 · 靠纪律不靠结构】** 图片要穿过 5 类载体 + 3 跳显式白名单投影，漏一跳图片静默消失、编译不红、测试不红。方案用快照测试 + 枚举扫描兜底。这是"用测试买的干净"，不是"结构保证的干净"——未来加第 6 个消费点（如导出功能）仍可能静默掉图。方案选择顺着现有架构走（正确，没去硬改架构），代价是安全靠测试纪律，要接受。

3. **【冗余伤 · 轻微 · 可争议】** `ImageRef` 把 `bytes/width/height` 也存进 `RoundMessage` JSON。这些是文件的派生事实，磁盘上本就有（sha256 为键）。方案用 D20 三值交叉校验（sha+mime+bytes）防漂移——必要，但本质是"存一份派生副本 + 读时回填校验"。更纯的 SSOT 是只持久化 `sha256+mime+name`，`bytes/width/height` 发送时从文件现算（窗口仅 4 轮、resolver 缓存已预填，现算很便宜）。方案选"存下来省一次读头"，可争议，不是错。

4. **【旧伤未修 · 知情推迟】** 能力位链今天就有 bug：`supportsToolCalling` 只在 `provider==='local'` 时显示、云端恒 `undefined`（`configView.ts:160`，已核）。方案 P0-5 正确"不照抄"给 `supportsVision`。但方案明确"不顺手改它"——结果 P0 上线后，能力位子系统出现**两种不一致规则**（工具调用只本地可配、图片全模型可配）。建议至少在台账记一笔，别烂在暗处。

5. **【顺序依赖 · 未钉死】** 窗口衰减（§5.12，在 `loadRoundBasedMessages` 投影时剥掉老轮 attachments）与 token 估算（§5.9）的顺序没写死。若估算发生在衰减之前，会多算老轮图片 → 当前轮被误截断。方案应补一句不变量："`estimateTokensMessages` 必须在衰减之后、发送之前对同一份消息集调用"。

6. **【P1 潜伏联动】** `loadRoundBasedMessages` 当前只展开 `userMessage + assistantMessage`，不展开 `interactiveInputs`。P0 的 D13 说插话不带图，所以一致。但 P1 的 G1（生成中插话带图）要做时，`interactiveInputs` 要带图，届时 §5.12 衰减代码（按 `roundIds` 算索引）和本函数展开面都要改。方案把 G1 标"独立设计"是对的，但没提示"P1 改这里会连带动 §5.12 衰减"。

## 五、结论（直接判断）

- **方向对、吸收对、约束拿捏对。** 在 memora 的"整对象 JSON 落盘 + 零依赖"约束下，引用派（脱水/复水形）是 SSOT 最优解，没有更优的。
- **"不带伤"在落地前还差临门一脚**：宿主 token 显示侧（chatPanel）没接图，是方案 §5.9 的真缺口；另有两个已知旧伤被主动推迟（能力位链不一致、P1 G1↔§5.12 联动）。
- **别被"定稿"骗了**：定稿只代表设计讨论结束，不代表能直接无伤落地。

**判定词：设计层面符合 SSOT 最优解；"不带伤"在 P0 验收前差一条（宿主 token 显示接入带图 history），且主动推迟了两个已知伤。所以它是"设计最优、落地前差一条验收项"，不是"已不带伤"。**

**P0 派工建议补两条：**
1. chatPanel 对话 token 显示必须传入带 attachments 的 history，并确认走带图分支的同一 `estimateTokensMessages`（堵缺口 1）。
2. 台账登记：① 能力位链 local-only 旧伤（supportsToolCalling vs supportsVision 规则不一致）；② P1 G1 与 §5.12 衰减的联动前因后果。
