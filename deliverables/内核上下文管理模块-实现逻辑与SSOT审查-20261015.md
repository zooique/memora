> 日期：2026-10-15 ｜ 范围：`src/agent/`（contextPreparer / budget / contextManager / compaction / loop 相关收口）
> 性质：**只读审查，零代码改动** ｜ 方法：第一性原理 + 对抗式审查（claim → evidence → conclusion）

## 一、大白话：这个模块到底在干什么

**一句话**：每次要回答问题之前，它负责把「能塞进模型窗口的料」装进篮子——塞得下的装进去，塞不下的砍掉、压缩、或换成摘要。它的唯一 KPI 是：**既不撑爆模型窗口，又尽量别丢上下文。**

它由四条线串成（另有一条旁挂通道）：

| 层 | 文件 | 大白话职责 |
| --- | --- | --- |
| ① 装配层 | `contextPreparer.ts` | 每轮开工前：算预算、把最近对话拼成一段文字塞进去、记一笔"这轮花了多少" |
| ② 预算层 | `budget.ts` | 纯算术。窗口多大 → 扣掉固定开销 → 扣掉本轮输入 → 剩下的按 90% 当"对话能装的额度" |
| ③ 窗口层 | `contextManager.ts` | 数 token（中文按 1.5 字符/token）、超了就砍中间、生成一段摘要补偿、判定"该收尾了" |
| ④ 压缩层 | `compaction.ts` | 两级：旧轮次正文换成它自己的记忆摘要；旧工具结果换成 `[Previous: used x]` 占位符 |
| 旁挂 | `loop.appendToolMessage` | 单条工具结果超 6000 token → 原文落盘，上下文只留"路径 + 预览" |

### 关键数字（都在 `constants.ts`，不散落）

- `DEFAULT_MAX_CONTEXT_TOKENS = 120_000`（窗口兜底，真源在 `constants.ts:40`）
- `CHARS_PER_TOKEN = 3` / `CJK_CHARS_PER_TOKEN = 1.5`（估算密度，`:85` / `:98`）
- `CONTEXT_TOKENS_BUFFER_RATIO = 0.9`（截断线保留比例，`:120`）
- `SUMMARY_LAYER_TOKEN_RATIO = 0.3`（摘要层占 30% 即判饱和，`:132`）
- `SINGLE_TOOL_RESULT_MAX_TOKENS = 6_000`（入口关阈值，`:151`）
- 装配线输出预留 `0.15` / 对话填充 `0.9`（`budget.ts:31` / `:34`）

### ⚠️ 一条容易被人误判成"缺口"的设计：两条线刻意不统一

- **装配线**（`budget.ts:31`）：`可用 = 窗口 × (1 − 0.15) − 固定开销` → 语义是"**预留 15%**"，**减法**。
- **截断线**（`constants.ts:120`）：`保留到窗口 × 0.9` → 语义是"**保留 90%**"，**乘法**。

两者恰好互余（0.15 + 0.9 ≈ 1）纯属巧合。注释（`budget.ts:25-29`）已明确论证「阶段与依据均不同，勿据此推导关联或试图统一」。**这不是缺口，是刻意的双线分离**——装配线决定"主动装多少"，截断线决定"超了兜底砍到多少"。

### 三个容易忽略的正确设计

1. `restoreHistory`（`loop.ts:3275`）把"历史被整体替换"这个事实作为**摘要缓存的唯一失效点**收口，而不是从 `messages.length` 差值反推。注释（`contextManager.ts:447-455`）明确解释了为什么不改成 `Math.abs`——因为正常裁剪也会让消息变少，而那时摘要恰恰该保留。**这是 SSOT 收口的正面样本。**
2. 截断触发阈值（`shouldTruncate`，用 `maxContextTokens`）与截断执行阈值（`truncateMessages`，内部同样用 `maxContextTokens` 判定是否 return）**同源一致**，不存在"判据说超了、执行说没超"的分叉。
3. 压缩链只改 `this.messages`，但 `safeMessages` 是浅拷贝共享元素引用 → 压缩对发送视图同样生效；`resultMsg.content = ...` 原地改也生效。**注释（`loop.ts:1564-1566`）主动交代了这条引用共享链路**，属诚实声明。

## 三、设计边界缺口清单

> 定级说明：**P0 = 会崩/会脏数据/静默错误**；**P1 = 声明与实现不符、或存在真实但不致命的错误语义**；**P2 = 口径分裂 / 脆弱判据 / 缺护栏**。
> **本模块无 P0。** 全部缺口（1–8）**均无测试拦截**——这是最值得警惕的共性。

### 🔴 P1-1｜占用快照（ContextOccupancy）名不副实

- **claim**：`budget.ts:84-87` 声明「各段为 prepare 期**实际占用** token，互斥分段**拼满整个窗口容量**」，共 5 段（角色包基础 / 对话 / 输入锚点 / 输出预留 / 剩余）。
- **evidence**：`contextPreparer.ts` 实际只统计 3 类——
  - `rolePackBaseTokens` = `estimateTokens([messages[0]])`（**仅首条** system，`:97-98`）
  - `dialogueTokens` = `estimateTokens(getConversationMessages())`（**仅 user+assistant**，`:155`；`getConversationMessages` 在 `loop.ts:3179` 明确过滤掉 system/tool）
  - `inputAnchorTokens` = 本轮输入（`:171`）
- **后果**：**所有非首条 system 动态注入**——`[Recent conversation]`（`contextPreparer.ts:141`）、情报区（`loop.ts:3481`）、任务表（`loop.ts:1633`）、软上限/压力提示（`loop.ts:1601`/`:1613`）、搜索收敛提示（`:1584`）、planNudge（`:1643`）、reflection/selfReview/duplicateWarning、teamContext（`seed/prepare.ts:56`）——**全部不计入任何分段**，被静默算进 `freeTokens`（`budget.ts:135`）。
- **结论**：`freeTokens` 语义是"剩余可用"，但这些注入**已经占用了上下文** → **free 系统性偏大**，UI 圆环显示的"空闲空间"比真实的虚高。这是"声明与实现不符"的带伤，符合本仓"措辞折叠"血训同族（读者信了，测试不拦）。
- **处置建议**：要么把快照补一个 `dynamicSystemTokens` 分段（从 `messages` 里按"非首条 system"聚合），要么把声明改成"仅统计 4 个主分段的近似占用"。**不能维持现状两边都不改。**

### 🔴 P1-2｜估算器有实测数据、无校准消费者

- **claim**：全部截断/预算/软上限判据都基于字符数估算（`CHARS_PER_TOKEN=3` / `CJK=1.5`）。
- **evidence**：`llmCaller.ts:305` 采集服务端真实 `usage.inputTokens` → `metrics.actualInputTokens`（`loopMetrics.ts:14`）→ 经 `loop.getMetrics()`（`loop.ts:3087`）+ span（`llmCaller.ts:307`）透出。**全仓无一处在消费它做校准或偏差告警**（`roundStore.ts:168` 注释自认"实测值在 actualInputTokens，宿主取证面未消费"）。
- **后果**：估算密度是启发式。对代码 / JSON / URL 等高密度 ASCII 文本，真实 token 密度高于 `3 字符/token`（可能 2–4）→ **低估** → 判定"没超窗"而实际超窗 → 请求被 API 拒。虽有 `truncationRecoveryCount` 事后补救，但那是被动挨打。
- **处置建议**：这是"零三方依赖"哲学下的自觉取舍，**可接受**；但应把 `actualInputTokens` 接一个消费者——**做偏差监控**（估算 vs 实测比值超阈值即 warn/span 标记），把"隐形风险"变成"可见信号"。有数据不消费 = 观测断链。

### 🟡 P2-3｜截断层内部存在**第二套 token 口径**

- **claim**：`contextManager.ts:130-140` 声明估算器"单一真理源……与逐条取整再求和**不等价**"。
- **evidence**：`truncateMessages` 内部**恰恰**是逐条取整再求和——
  - tail 收集：`const msgTokens = this.estimateTokens([msg]); tailTokens += msgTokens;`（`:350`、`:358`）
  - 关键消息提取：`tokens: this.estimateTokens([msg])` + 贪心累加（`:417`、`:431`）
  - 而 `shouldTruncate`（`:237`）、软上限（`:255`）、占用（`contextPreparer.ts:155`）用的是**一次性** `estimateTokens(messages)`。
- **结论**：同一物理量（这段消息占多少 token）在系统里存在**两个口径**，且注释宣称只有一个。逐条求和 ≥ 一次性 ceil（系统性高估，`contextManager.ts:133` 自认），所以截断比全局判据**更保守**（少装内容）。方向安全，但**是 SSOT 违例**。
- **处置建议**：注释加一句"分区填充用逐条口径是为可独立累加，与总量口径差异方向为高估（安全侧）"，把隐含事实显式化；否则就是"注释撒谎"。

### 🟡 P2-4｜截断后**无二次收敛**，summary/placeholder 不进预算

- **evidence**：`truncateMessages`（`:328-329`）`availableTokens = floor(max × 0.9) − systemTokens`；tail 与 keyMessages 共用该额度；但最终组装 `truncated = [systemMsg, summary?, ...keyMessages, placeholder, ...tail]`（`:381-387`）中，**`summary` 与 `placeholder` 从未计入预算**，末尾只 `logger.info` 不校验（`:389-401`）。
- **实证**：测试 `contextManager.test.ts:490-501` 标题写"不超过 maxContextTokens（含 10% 缓冲）"，断言却是 `newTokens <= 100 * 1.1`——**上界 110 > 设计声称的 90，也 > max 100**。宽松上界掩盖了"可能超"。
- **后果**：常规下 `summary` 受 `SUMMARY_MAX_TOKENS=150` 约束，溢出可忽略；但 `roundSummaryLoader` 返回的"已存 round-summary"**不受该上限约束**（宿主存的整轮摘要可能上千 token）→ 溢出量放大。
- **处置建议**：截断末尾加一条 `newEstimated ≤ maxContextTokens` 的守卫（超则再裁 tail），或至少 `logger.warn`。**当前是"无断言、无告警、测试用宽上界"三重静默。**

### 🟡 P2-5｜摘要层识别靠**文本子串匹配**

- **evidence**：`contextManager.ts:260-264` 用 `m.content.includes(SOFT_LIMIT_SUMMARY_MARKER_ROUND)` / `..._COMPRESS` 来筛选"哪条消息是摘要"。
- **问题**：`Message` 无 `kind` 结构化字段 → "这条是摘要"这个**结构事实**被表达成"内容里含某段魔法字符串"。任何工具输出 / 用户贴入的文本里偶然包含 `Round summary · roundId:` 即被误判为摘要消息 → 污染摘要层 token 统计 → 误触软上限（`contextManager.ts:272`）。
- **处置建议**：中期给 `Message` 加 `kind?: 'summary' | 'compressed'`，让判据回归结构。短期至少把 marker 换成不可能自然出现的形态（如带 `\u0000` 前缀）并在注释登记风险。

### 🟡 P2-6｜两级同类提示的**幂等口径分裂**

- **evidence**：
  - 软上限：用实例 flag `softLimitWrapupInjected`（`loop.ts:1598`/`:1600`）判重 → 结构化判据。
  - 压力提示：用 `this.messages.some(m => m.content.includes('上下文空间提示'))`（`loop.ts:1612`）判重 → **硬编码中文子串**。
- **问题**：同一处、同一族的两级提示用了两种幂等口径。且判据字符串只存在于 `loop.ts`，文案真源在 `constants.ts:214`——改文案不改判据即幂等失效（刷屏）。`constants.test.ts:167` 只断言"常量含该串"，**不能**保证 loop 判据与常量同源（改测试比改判据更省事 → 弱守卫）。
- **处置建议**：统一为 flag（`pressureHintInjected`），与软上限同口径。

### 🟡 P2-7｜`minRecentRounds` 强制保留区**无上限、无告警**

- **evidence**：`contextManager.ts:337-346` 统计 `forcedTailCount`，`:352` 明确 `inForced` 的消息**不参与 token 上限判断**；构造时只 `Math.max(0, Math.floor(...))`（`:205`），**无上界 clamp**。宿主侧可任意放宽（注释 `:70-73` 鼓励按 KV cache 能力放宽）。
- **后果**：宿主传入的强制轮次若自身 token 超过窗口 → 截断后仍超窗，且因"强制区不计上限"的设计**不会被自身机制纠正**。
- **处置建议**：加"强制区 ≥ availableTokens 时 warn + 截到 availableTokens"的护栏。

### 🟡 P2-8｜`_prepareContext` 尾部注入**延迟一个迭代生效**（未声明）

- **evidence**：`_prepareContext` 先算 `safeMessages`（`:1551`）并作为返回值交给 LLM（`:1648`），**之后**才执行软上限注入（`:1601`）、压力提示（`:1613`）、任务表替换（`:1630-1633`）、情报区（`:1575`）、planNudge（`:1643`）——这些 `appendSystemMessage` 只进 `this.messages`，**不在本轮发送视图内**。
- **后果**：软上限提示的意图是"让 LLM **本轮**收敛"，实际要等下一迭代 `_prepareContext` 重算才进 `safeMessages`。情报区的同类时序已在 `loop.ts:3475-3478` 诚实声明，但**软上限/压力提示未声明该延迟**。
- **处置建议**：把这几处注入移到 `safeMessages` 计算之前，或在注释显式登记"注入延迟一迭代"。当前是"部分声明、部分沉默"。

## 四、处置优先级（建议顺序）

| 顺序 | 项 | 动作 | 理由 |
| --- | --- | --- | --- |
| 1 | P1-1 占用快照 | 补 `dynamicSystemTokens` 分段 **或** 改声明 | 声明与实现二选一改齐，是"措辞折叠"同族，成本最低 |
| 2 | P1-2 估算校准 | 让 `actualInputTokens` 接一个偏差告警消费者 | 有数据无消费者 = 观测断链 |
| 3 | P2-3 / P2-5 / P2-6 | 注释显式化 + 判据结构化（`Message.kind`）+ 幂等统一为 flag | 同属"判据形态"问题，可一并收口 |
| 4 | P2-4 / P2-7 / P2-8 | 补收敛守卫 / 加 clamp / 移注入顺序 | 补护栏，非结构改动 |
