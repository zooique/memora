## 三、🔴 SSOT 违例（必修）

### P1-1 · 台账分区与定档口径双源 —— 3.1.0 区不是 3.1.0 内容的 SSOT

- **claim**：3.1.0 区不是「3.1.0 全部内容」的单一真源，双向断裂。
- **evidence**：
  - 台账 line 12 自定升档规则：「观察区拍板定档 → 升 3.1.0」。
  - 但观察区有 **3 条自带已定档标记却未升区**：`SCRIPT-1`（line 248）、`MEM-1`（line 290）、`TOP-UI-1`（line 335），均标「⏳ 延期 3.1.0（2026-09-19 Go/No-Go 拍板）」。

- **conclusion**：3.1.0 排期若只读 3.1.0 区，会同时漏掉「3 条已定档待办」与「9 条已落地待发」。**两个方向都不完整**。
- **修法（零代码风险）**：①三条已定档项升入 3.1.0 区；②3.1.0 区加一行指针「已落地未发版内容以 CHANGELOG `[Unreleased] · 内核` 为准，本区不转写防双真相」。

- **claim**：`eed62d49`（2026-10-06，最新提交）未同步台账，与相邻批次纪律不一致。

## 五、🟢 测试基线 = **官方串行口径全绿**（审查中途两度自纠）

> ⚠️ 本节在审查过程中**被实测推翻两次**，最终结论与初稿相反。保留修订过程，因为它本身就是「不带伤」方法学的实证。

| 口径 | 命令 | 结果 |
| :--- | :--- | :--- |
| **并行**（我最初的跑法） | `vitest run` | **1031 passed / 3 failed / 2 skipped**（56 文件，3m42s）；`AssertionError` = **0**，3 处全 timeout |
| **官方串行** | `npm test` = `vitest run --no-file-parallelism` | **1034 passed / 2 skipped（1036），56/56 文件全过，exit 0**（201s） |

`1034 − 1031 = 3` ⇒ 并行失败的 3 条（`hostIntegration` Hook / `allowedPaths` Hook / `projectSearchProvider`「500 文件」Test）在串行下**全部通过**，**零真缺陷**。

**结论**：不是用例脆弱、不是环境劣化，是**跑法差异**——并行下 I/O 密集用例相互争用。`hosts/memora-vscode/package.json#scripts.test` **自带** `--no-file-parallelism`，官方口径本就串行。

### 🔴 防造伤（本节最大价值）

初稿把 `projectSearchProvider` 定性为「用例脆弱，待拍板放宽用例级 timeout」——**已被双口径实测证伪**：串行官方口径下它稳定通过 ⇒ **放宽 timeout / 改判据 = 为不存在的问题动刀 = 造伤**。

若照初稿执行，就会为一次「跑错口径」付出「改判据」的代价。这正是「不带伤」三条件里最难守的一条：**观测不到位时，改判据看起来像修 bug**。

### 两次自纠（如实留档）

1. 初稿写「确定性超时」→ 被同日早次记录（隔离复跑**通过**）推翻 → 改判「负载敏感型波动」。
2. 「波动」仍不准 → 用官方串行口径复跑发现**全绿** → 最终定性为**跑法差异**。
   **教训**：单次观测不得写成全称结论（`HOST-S11` 同族）；**判红前先确认用什么口径**。

### 已做（仅注释层，零判据改动）

该用例注释删去「隔离态 ≈0.9s」这一**可证伪的时点数字**，改为登记「判红前先确认口径 + 并行假红不得作为改判据依据 + 30s 上限够用」。追踪条目 `TEST-ENV-TIMEOUT-1`。
