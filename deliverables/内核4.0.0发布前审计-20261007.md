## 二、SSOT / 不带伤 落地审查（对抗式）

**总判断**：方向对（见下方正面范本），但**仍有 3 处带伤/失真未清**，其中 1 处作者自承「不动带伤」。

### 🔴 带伤 1（最严重）：`loop.ts:1783` 自承「不动带伤」——重试分类回读文本前缀

- **证据**：`loop.ts:1783-1788` 注释原文
  > 重试轴 vs 计数轴分离（**不动带伤**）……文本前缀在此只作「错误类别渲染面」，不参与失败计数。非 SCRIPT-2 双轨残留（B5 后 `isToolFailure` 已物理删除……）
- **事实**：失败计数已单源（`outcome.status` 三值，`loop.ts:1785` 确认）；但重试分类 `loop.ts:1789-1791` 仍 `isRetryableToolError(m.content)` 解析文本 `[ERR:TOOL:…]`。
- **根因**：`ToolOutcome`（`toolCallHelpers.ts:185-194`）只带 `status/text/blockedReason`，**不带 `errorCode`**。错误码被编码进文本前缀后又被回读，形成「结构化丢码 → 文本编码 → 再解析」的来回双源——正是项目铁律反对的「并列镜像」。
- **作者辩解不成立**：辩称「正交轴」。目的确实正交（计数 vs 重试），但**同一个错误事实**用 `status` + 文本前缀两种形式承载、必须保持同步。改前缀即静默破重试（隐藏字符串契约）。
- **4.0.0 该修的时点**：major 允许破坏性变更，本次已删 53 导出、弃 `search()`。修法：给 `ToolOutcome` 加 `errorCode?`；`failedOutcome` 收 `errorCode`；`isRetryableToolError` 改读 `outcome.errorCode`；文本前缀退化为纯渲染。

### 🟡 带伤 2：`toolExecutor.ts:1606` 注释与代码不符（文档级失真残留）

- **证据**：注释「双轨期编排层仍按 `[ERR:COMMAND_DECLINE]` 文本算 failed（已知口径分歧，B4 裁决）」。
- **事实**：内核范围内 `[ERR:COMMAND_DECLINE]` 仅出现在 emit（`toolExecutor.ts:1603`）与测试；计数走 `outcome.status`（`loop.ts:1785`），此处 decline 已 `emitOutcome?.(blockedOutcome(...))`（`status='blocked'`），**不会被计为 failed**。内核已无按文本计 failed 的生产代码。
- **判定**：该注释描述的是 B4 前的旧态/宿主侧，对内核是**过时失真**——与本项目自己揪出的「共用裁决链」文档谎言同类。删掉或订正。

### 🟡 带伤 3：`memoryInspector.ts:187` `search()` 僵尸方法——`@deprecated` 却仍公开

- **证据**：`memoryInspector.ts:187-189` `@deprecated 本同步通道已退役……当前无生产/宿主消费方，勿新增调用`；但 `api-reference.md:360 / 928` 仍把它当正常公共方法列出（`.search()`）。
- **判定**：4.0.0 是 major，正是清僵尸的窗口。要么从 `api-reference` 显标 `@deprecated`，要么直接删（REL-3.1 已删 53 个，逻辑一致）。当前「代码弃用、文档照列」是半吊子。

### ✅ 正面范本（说明团队懂 SSOT，带伤是局部而非全局）

- `confirmEntries.ts`：执行面→确认入口**单一真源**登记表 + 穷举守卫测试（`confirmEntry.test.ts`）。
- `strategyResolver.ts:113` 复用 `mergeStrategy` 单一 SSOT，消两处手写同形实现（双轨漂移隐患）。
- `publicApiSurfaceGuard`（`536c54fa`）：公共导出双向机器对账，防幻影/僵尸导出。

## 三、文档-代码对齐审查

**总判断**：REL-3.1 导出收敛已同步进 `api-reference`（删 `AgentProjectEntry`/`BOOST_*`/`extractKeywords`/`SkillMatch`、加 `safeSearchProjectFiles`），但 **4.0.0 头号新能力漏文档**。

### 🔴 缺口 1：后台任务宿主 API 未进 `api-reference`

- **证据**：`index.ts:221-225` 导出 `BackgroundTask` 类型 + `BACKGROUND_TASK_STATUS_LABELS`，注释「宿主 UI 列表出口 `agent.listBackgroundTasks()` / `killBackgroundTask()`」；`agent.ts:1173` / `agent.ts:1187` 确为真实 Agent 方法；`api-reference.md` 全篇 grep `listBackgroundTasks|killBackgroundTask` = **0 命中**，Agent 方法表（§6.3 / 行 924-930）无此二项。
- **判定**：4.0.0 头号特性（后台任务）在**随包发布**的契约文档里完全缺席。补一节「后台任务（`agent.listBackgroundTasks` / `killBackgroundTask`）」。

### 🟡 缺口 2：`search()` 弃用状态未反映

- 见带伤 3：`api-reference` 仍列 `.search()` 为正常方法，未标 `@deprecated`。

### 🟡 缺口 3（轻微）：`outcome.status` 三值语义未作为契约显式说明

- 这是 SCRIPT-2 的核心契约变更，`api-reference` 未提。虽主要面向内核内部/宿主，但作为 4.0.0 行为契约值得在「工具执行」节点明（尤其 `blocked ≠ failed` 的口径，B4 决策）。
