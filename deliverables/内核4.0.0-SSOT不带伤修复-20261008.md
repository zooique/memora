## 一、核实结论（4 条全部坐实）

| # | 审计主张 | 核实方式 | 结论 |
|---|---------|---------|------|
| 1 | `ToolOutcome` 无 `errorCode`，重试分类回读文本 | 读 `toolCallHelpers.ts` / `toolRunner.ts:132` / `loop.ts:1789` | 🔴 **坐实** |
| 2 | `toolExecutor.ts` 注释称「编排层仍按文本算 failed」 | grep `COMMAND_DECLINE` 全树 | 🟡 **坐实（注释失真）** |
| 3 | `search()` 僵尸方法仍被文档当正常方法 | grep 宿主 `memory.search*` + 内核消费点 | 🟡 **坐实（零消费）** |
| 4 | 后台任务 API 未文档化 | grep `api-reference.md`（background/outcome/ToolOutcome） | 🔴 **坐实（零命中）** |

**关键实锤（比审计更深一层）**：`toolRunner.ts` 的 MemoraError 分支**已经算出了 `code`**（`err.errorCode ?? 'UNKNOWN'`，`MemoraError` 自身就带 `errorCode` 字段），
却只把它拼进文本、结构化面**丢弃**——`failedOutcome(result)` 不带码。于是重试分类只能回头解析自己刚写出去的文本。
这正是 `ToolStatus` 自述文档（toolCallHelpers.ts 119-140 行）**亲口痛批**的「判据与渲染耦合」反模式：文档反对什么，代码就在做什么。

## 二、修复（claim → evidence → conclusion）

### 🔴 修复1：**错误码收口为单一构造点**（带伤1）

| 项 | 内容 |
|---|---|
| claim | 错误码应有且只有一个产出点，文本前缀是它的**派生渲染面**；重试分类读**字段**而非解析文本 |
| evidence | 旧态：15 处（toolExecutor NOT_AVAILABLE 等）**各自手抄** `[ERR:TOOL:XXX]`。漂移后果 = 改一处漏一处 ⇒ `isRetryableToolError` 取不到码 ⇒ Reflection **静默失效**（该重试的不再重试，无报错、无红灯） |
| conclusion | 收口到 `failedOutcomeWithCode(code, detail)` |

**改动**：
- `ToolOutcome` 新增 `errorCode?: ToolErrorCodeValue`。
- 新增 `failedOutcomeWithCode(code, detail)`：`` text = `[ERR:TOOL:${code}] ${detail}` `` **由 code 派生**，code 与前缀**同源产出一次**。
- `failedOutcome(text)` 保留，**仅用于无码失败**，并在注释写明边界。
- `ToolErrorCode` 枚举补 **`NOT_AVAILABLE`**（**非可重试**：缺的是宿主装配，重试只会空转烧迭代）。
- 收口 15 处 toolExecutor + 2 处 toolRunner（MemoraError / UNKNOWN），**文本逐字不变**（由测试守卫）。
- `executeToolCalls` **回流 `outcomes`**（返回 `{ aborted, outcomes }`，仅 1 个调用点）⇒ loop 重试判定改读 `execResult.outcomes`，**不再反切 messages 文本**。
  - 附带修掉一个隐患：原按 `effectiveToolCalls.length` 反切 messages，`toolStepLimit` 截断时切错会把**上一轮**残留错误吸进窗口误注入反思提示；回流后天然只含本轮。
- `isRetryableToolError(input: ToolOutcome \| string)`：**优先读 `errorCode` 字段**，无码才回退解析文本（兼容 `ABORTED` 与测试桩裸文本 outcome）。
- 重写 `loop.ts` 原「重试轴 vs 计数轴分离（**不动带伤**）」注释——不再是"带着伤不修"。

**刻意不入错误码体系的（勿"补全"）**：
- `ABORTED` —— toolRunner 注释明载「不入错误码体系，不触发 Reflection」；
- `READONLY_DENIED` / `PERMISSION_DENIED` —— 是 **blocked 路径**，由 `blockedReason` 回答「为什么」，与 `errorCode` 正交。

### 🟡 修复2：订正失真注释（带伤2）

`toolExecutor.ts` 原注释称「双轨期编排层仍按 `[ERR:COMMAND_DECLINE]` 文本算 failed（已知口径分歧）」——
内核**无任何生产代码**这么做（失败计数唯一判据面是 `outcome.status`）。改写为如实描述，并**留痕说明旧说法为何不成立**（防后人再去找那处并不存在的文本判据）。

### 🟡 修复3：删除僵尸 `search()`（带伤3）

实测零生产消费、零宿主消费（宿主只用 `searchByKeyword`）⇒ 4.0.0 major 删除方法 + 其 5 条测试。
截断（120 + '…'）覆盖由 `searchByKeyword` 既有用例继承，未丢覆盖。

### 🔴 修复4：文档对齐（含审计未覆盖的**新发现**）

- **新发现 🔴：`TOOL_TIMEOUT` 死条目**——`api-reference.md` §14.1 长期列着它（标可重试），但枚举**早已删除**
  （`errors.test.ts` 注释载明「TOOL_TIMEOUT 删除后 retryable 从 5 → 4」）。已移除 + 加订正说明。
  ⇒ **枚举类文档会腐化成死条目**，已把「改枚举必回扫文档」写入项目长期记忆。
- 新增 **§14.3 `ToolOutcome` 结果契约**：status 三值语义 + 是否计入 `toolFailureCount` + 4 条纪律（含「判成败一律读 status，不得解析 text」）。
- 新增 **§8.7 后台命令任务**：`listBackgroundTasks()` / `killBackgroundTask(taskId)` / `BackgroundTask` 类型 + 寿命边界（结果不自动进上下文 / 无 timeoutMs 则无上限 / 退出 VS Code 随扩展终止）+ 注册表为何**只出方法不出类**。
- §十二 API 一览表补「后台任务」行；§4.2 由已删 `search()` 改写为 `searchByKeyword()`；§2.4 移除 `.search()` 列举。

## 三、关键教训：守卫必须跟着搬家（否则反成假绿）

收口后 `toolFailurePrefixGuard` 红了 3 条。**这是守卫在尽职，不是回归**：
`[ERR:TOOL:${code}]` 模板已从 `toolRunner.ts` 搬进 `toolCallHelpers.ts`，守卫的 `PRODUCER_FILES` 还盯着老文件 ⇒ 对新增产出点**失明**（反向对账假绿）。

- 修法：把 `agent/managers/toolCallHelpers.ts` 加入 `PRODUCER_FILES`（7 → 8），**不是**放宽判据。
- `errors.test.ts` 计数同步（9 → 10 种；4 retryable + 5 → 6 non-retryable），补 `NOT_AVAILABLE` 不可重试用例。
