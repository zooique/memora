## 〇、先说三件必须先说的事（对抗式审查）

1. **「体验」不是「愿景」。** 两路扫描共报 15 条候选，我逐条回源码核到触发前提，拦下 6 条——多数是**有意设计被当缺口**（抽屉不轮询、助手窗不显示插话区、落定队列重启不补发）。能不能进清单，标准是「用户真会遇到、且现实现与代码注释/同类范式自相矛盾」，不是「看起来能更好」。
2. **memora 宝的判据链本身这轮没有新安全洞。** 本批全是体验一致性 / 反馈缺口，无 P1 fail-open。真机方案 T1–T8 回填仍是宣告全量闭环的硬前置——**UI 清单不替代真机**。
3. **「触发条件」是重量所在。** 每条都写清「什么情况下才值得动」；没到触发就动手 = D6 禁止的预支复杂度。列出来 ≠ 现在该做。

### 三问 + 本轮体验镜头
- **A** 数据已算出但界面没接；**B** 同类模块有正确范式、这处漏了；**C** 操作流断点 / 状态边界不对称。
- 体验镜头：点了没反应 / 卡住不知道在干嘛 / 被文案误导 / 要多点一次 / 两处说法不一致 / 空列表什么都不说 / 关掉后状态没更新 / 看不到当前状态。

## 一、真候选（8 条，全部触发制）

### 1. 助手窗待发送条「清空 / 删除」按钮点了没反应 ★本批最硬的操作断点
- **大白话**：助手窗连发两条消息后，底部冒出「待发送 2 条」条，带「清空」和每条的「×」。你点清空——**什么都没发生**。原因：消息确实发上去了（`clear_pending_queue` / `remove_pending_item`），但 `hostedSeat` 把这两类上行**显式 `return` 吞掉**，注释理由是「助手窗不渲染待发送区」。可实际上 `chatView` 收到 `turn_update.pendingQueue` 会无条件渲染这条 bar，CSS 也没有任何针对助手形态隐藏它的规则。**注释说「不渲染」，代码却在渲染，按钮就成了死键。**
- **坐标**：`webview/helpers/hostedSeat.ts` 的 `handleMessage`（两分支显式忽略）；`webview/scripts/chatView.ts` 的 `turn_update` 分发（`if (msg.pendingQueue)` 无条件更新）；`webview/scripts/statusBarsView.ts` 的 `updatePendingQueue`；`webview/helpers/turnUiState.ts` 的助手形态 interjection 判据；`webview/styles/chatStyles.ts` 的 `.pending-queue-bar`（无 `data-form='assistant'` 隐藏规则）。
- **分类**：**C**（操作流断点 + 注释与实现互相矛盾）｜镜头：点了没反应
- **触发条件**：助手会话运行中连发 ≥2 条形成待发送队列，用户尝试清空 / 删除某条。**真机 T1–T8 未覆盖这个组合**，需在助手窗复现。
- **为何现在不做**：两条修法互斥——「按注释意图把 bar 在助手形态藏掉」（改动小、符合微信式脱手心智）vs「按助手会话真投递这两类上行」（给用户管理能力）。**属产品口径待定**，不是纯技术修补。
- **优先级**：**P2 架构一致**（死键是确定性体验伤，触发即该修；口径一旦拍板改动很小）。

### 2. 工作台抽屉是独立面板的「半截投影」：丢明细、丢来源、空态粗化
- **大白话**：你在助手页点顶部「工作台」就地展开抽屉，同一条活这里只显示光秃秃一个状态徽标（如「已中止」），独立工作台面板却写明「被你停止 / 超时 / 异常终止：原因」。`queued`（已交接未开始）、`unsettled`（上次没跑完）这些副行说明也没了。抽屉文件头白纸黑字承诺「复用 `describeStatus`、不另写一套文案、逐字同源」——实际只取了 `.badge`，把 `.detail` 丢了。空态同理：独立面板细分「N 条找不到 / 更早历史没读 / 有 N 条但没代理在驱动」，抽屉一律说「还没有交给助手的活」。
- **坐标**：`webview/helpers/assistantWorkbenchDrawer.ts` 的 `renderJob`（只取 `describeStatus(job.status).badge`）、`render`（空态三档）；对照 `webview/scripts/workbenchView.ts` 的 `renderJob`（消费 `described.detail`）、`renderJobs`（空态分档）。
- **分类**：**B**（同类范式只实现一半 + SSOT 承诺未兑现）｜镜头：两处说法不一致 / 空列表什么都不说
- **触发条件**：用户就地展开抽屉、且活处于停止 / 未收场 / 读不全等需要副行说明的状态；或空 workspace 想搞清楚「到底没有活还是没读全」。
- **为何现在不做**：抽屉是只读快照、点击才构建，设计上刻意轻量（台账 2026-11-18 拍板**不做 3 秒后台轮询**——这是有意设计，见 §二）。补齐明细是纯渲染层复用、无判据风险，但属「两处对齐」而非阻断；真机 T6 跑抽屉恢复时顺带看用户是否需要副行。
- **优先级**：**P2 架构一致**（逐字同源是 SSOT 承诺，破损即该记账；改动集中在渲染层）。

### 3. 助手窗顶部状态签的「正在思考…」档在实时流期间不可达
- **大白话**：助手窗顶部状态签有四档，其中「正在思考…」的判据是查本轮过程事件里的 `thinking`。但助手窗按 `bubbleOnly` 取景，广播器把 `process_event` 明确列入丢弃名单——助手窗的 `currentEvents` 在实时流期间拿不到这些事件。结果：助手跑了再多步，顶部永远只显示默认档「正在推进…」，思考档不亮；只有重放那一瞬事件才被整批填上。状态签注释还声称「与消息流相位行同一判据」——在助手窗这个判据的数据源被取景层掐断了。
- **坐标**：`webview/scripts/hostedStatusView.ts` 的 `deriveHostedStatus` / `STATUS_LABEL`；`webview/panels/hostedPanel.ts` 的 `open`（`bubbleOnly: true`）；`webview/helpers/viewBroadcaster.ts` 的 `BUBBLE_DENIED_TYPES`（含 `process_event`）；`webview/scripts/chatView.ts` 的 `getEvents`（`currentEvents` 由 `process_event` 增量填充）。
- **分类**：**A + C**（数据被取景层挡掉 + 注释承诺与运行时不符）｜镜头：看不到当前状态 / 两处说法不一致
- **触发条件**：助手会话实时流式运行、用户正看着助手窗；若侧栏同时开着同一会话，就会出现「侧栏说思考、助手窗说推进」的不一致。
- **为何现在不做**：`process_event` 被丢是微信化取景的有意设计（过程轨迹不能倒灌助手窗）。要修得给状态签单独开一条轻量相位信号通道，属主动加机制而非接线，需先定「状态概括是否值得例外于过程隔离」。
- **优先级**：P3 自然生长。

### 4. 提问卡提交没有「等待态」，与确认卡成熟范式不对称
- **大白话**：确认卡点「确认 / 拒绝」后会进专门等待态——按钮置灰、卡片半透明、提示「已确认，等待下一步…」，专门消除「两帧空档闪烁 + 重复提交静默丢弃」。提问卡（`ask_user` 内联）点「提交答案」却是直接 `box.remove()`，没有等待提示、按钮没有 disabled 过渡。你点完提交、卡片瞬间消失，到宿主推来下一状态之间有一段「界面什么都没发生」的空窗，处理慢时会以为没点上。
- **坐标**：`webview/scripts/askInlineView.ts` 的 `render`（`onSubmit` 后直接移除）；对照 `webview/scripts/writeConfirmCardView.ts` 的 `enterAwaitingNext` / `exitAwaitingNext`。
- **分类**：**B**（同类有正确范式、这处漏了）｜镜头：点了没反应 / 卡住不知道在干嘛
- **触发条件**：助手窗或侧栏回答 `ask_user`，宿主处理 / 下一轮投影有可感知延迟时。
- **为何现在不做**：提交后 `pendingWaitView` 很快显示「正在准备回答」，有间接反馈；提问卡是一次性销毁（不复用节点），照搬确认卡的复用式等待态要重设计生命周期。真机 T7 看确认卡时顺带感受提问卡这段空窗。
- **优先级**：P3 自然生长。

### 5. 待办汇报条数 `pendingReportCount` 算得出、注释要求「必须能读出」，全生产面零消费
- **大白话**：子会话跑完了、结论压进了待办队列，但宝当时正忙 / 你正在打字 / 实例没装配，这条结果就一直「压着没送」。此时工作台和助手窗都只显示当前清单，空态还会说「还没有交给助手的活」——你完全看不到「其实有 N 条结果在路上」。函数注释自己写着「这条事实必须能被读出，否则容易把『压着没送』误说成『没有结果』」，但全仓只有测试在读它，`WorkbenchSnapshot` 没有对应字段。
- **坐标**：`webview/helpers/hostedSessionNotice.ts` 的 `HostedSessionNotifier.pendingReportCount`（对照其模块头注释的「必须能读出」纪律）；`shared/workbenchDto.ts` 的 `WorkbenchSnapshot`（无对应字段）。
- **分类**：**A**（数据算出、外层没接）｜镜头：界面状态和实际不一致 / 空列表什么都不说
- **触发条件**：创建者忙时子会话落定，且暂态持续到用户查看工作台（一般一轮收场就 `flushPending` 浮现，窗口很短）。
- **为何现在不做**：待办是进程内内存态（重启刻意不补发），暴露到 UI 要加 DTO 字段 + 改两个视图；且是高频暂态，多数情况自然浮现，露出去反而制造焦虑。**注意豁免**：这与台账「无人用的账」不同——本条注释明确要求可读，属承诺未兑现，不是死代码。
- **优先级**：P3 自然生长（真机 T1 派活时若出现「会话完成了却没汇报」，优先查这里）。

### 6. 助手窗顶部状态签没有「等你确认」档
- **大白话**：状态签四档是「推进 / 思考 / 等你回答 / 已暂停」，判据只读 `SkeletonState.phase`。确认卡（`write_confirm_request`）会在助手窗弹出，但「等确认」不进 `SkeletonState`，状态签也不问确认态。于是确认卡正等你拍板时，顶部可能显示「正在推进…」甚至空——与实际「卡在你这里」相反。
- **坐标**：`webview/scripts/hostedStatusView.ts` 的 `deriveHostedStatus` / `HostedStatusKind`；`webview/helpers/turnUiState.ts` 的 `SkeletonState`。
- **分类**：**A**（确认等待态没投影到状态签）｜镜头：看不到当前状态 / 被文案误导
- **触发条件**：托管会话弹 `write_confirm_request` 等待裁决、用户看向顶部状态签期间。
- **为何现在不做**：状态签设计上刻意只留一句微信式概括、过程明细不进链路；加确认档要把确认等待投影进 `SkeletonState`，牵动骨架判据单点，属结构性扩展。真机 T7 可顺带确认这个不一致是否真的困扰用户。
- **优先级**：P3 自然生长。

### 7. 重启恢复提示「发第一条消息就开始」，消息已发、活已在跑仍不改口
- **大白话**：重开窗口后，工作台座位行告诉你「已恢复，发第一条消息就开始工作」。你已经发了、宝也派活开跑了，这句提示还挂着——它说的是启动前那一瞬的状态，之后再不更新。根因：`restored` 是事件标签，只在 `set()` / 删除时清除；首次发消息走 `handleHostedInput`，不经过会清标记的 `set()`。
- **坐标**：`extension/host/sessionModeStore.ts` 的 `isRestored` / `restored` / `set` / `markAgentDriven`；`webview/scripts/workbenchView.ts` 的 `seatStateText`（`seatSource === 'restored'` 的措辞）。
- **分类**：**C**（状态标签只标记不清除）｜镜头：界面状态和实际不一致
- **触发条件**：重启恢复后、助手会话已发过消息，且用户盯着座位来源提示看。
- **为何现在不做**：注释把 `restored` 定位为「恢复这件事值得被看见一次」的**事件标签（单次叙述）**，不是实时状态；且 `seatSource` 在面板 open 时快照一次。改口要在首次发送时清标记 + 重推快照，牵动座位档判据，得权衡「恢复可见一次」的意图。真机 T6 正在测恢复，顺带看用户是否被误导。
- **优先级**：P4 测试质量 / 文案一致性。

### 8. 两个「打开」命令的错误提示比同类弱：一个不兜底、一个用裸 `String(err)`
- **大白话**：右键「添加到助手 / 添加到对话」，若聚焦那一步出错，命令面板里就是「点了没反应」——注册 handler 没 `catch`，Promise rejection 冒泡成通用失败或静默。打开助手窗若失败，只给一句光秃秃的 `String(err)`（可能 `[object Object]`）；而打开工作台失败时给的是完整原因 + 建议。同一个「打开面板」动作，三处告诉你的信息量差一档。
- **坐标**：`extension/commands/addToChat.ts` 的 `registerAddToChatCommand` / `addToAssistant`（注册无 `catch`）；`extension/commands/openHosted.ts` 的 `registerOpenHostedCommand`（`String(err)`）；对照 `extension/commands/openWorkbench.ts` 的 try/catch + `toNoticeText`；`extension/host/noticeText.ts` 的 `toNoticeText`（自称宿主 catch 转通知文本的「唯一出口」）。
- **分类**：**B**（同类范式未覆盖）｜镜头：点了命令没反应 / 操作失败没告诉为什么
- **触发条件**：`addToChatCommand` 里 `executeCommand(focusCommand)` 抛错，或 `MemoraHostedPanel.open()` 抛 `MemoraError`（带 `detail`/`suggestions`）被压成裸标题。
- **为何现在不做**：`addToChat` 主路径已有 `showWarningMessage`（uri 为空 / 超主根），只剩聚焦窄口；`open()` 抛结构化异常概率低。补 try/catch + 复用 `toNoticeText` 是低风险清理，但无真实报错反馈不预支。**注意 SSOT**：`noticeText.ts` 已声明唯一出口，这里属漏接，不是新造文案。
- **优先级**：P4 测试质量（文案一致性小修）。

## 三、本批账（SSOT / 自然生长 / 不带伤三原则裁决）

- **两路共报 15 条 → 去重合并 1 条（`pendingReportCount`）→ 拦下 6 条有意设计 / 已登记 → 真候选 8 条。**
- **现在值得做（口径一拍板即可小改）：候选 1（助手窗待发送条死键，P2）与候选 2（抽屉半截投影，P2）**——前者是确定性操作伤 + 注释与实现矛盾，后者是 SSOT「逐字同源」承诺破损。两者都只差一个产品口径 / 一次渲染层复用，不触判据。
- **附条件 / 等真机触发：3–7（状态签两档、提问卡等待态、pendingReportCount、恢复提示）**——真机 T1/T6/T7 跑的时候顺带观察，用户真被困扰再动。
- **小修排队：8（命令错误文案，P4）**——无真实报错反馈不预支。
- **判据链零新增安全洞**：本批无 P1 fail-open；memora 宝是否全量闭环仍由真机 T1–T8 回填决定，UI 清单只负责把「下一批长哪里」提前看清。

**原始扫描不落地**：done discovery 时未改源码/台账。见 §六——按「大众普通用户心智」二次排雷后，已定向落地 2 条硬伤。

## 六、大众普通用户心智 · 二次排雷与落地（2026-11-19 同日）
