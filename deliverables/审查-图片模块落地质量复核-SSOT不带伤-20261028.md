## 一、P0（致命）：能力位与解析器**注入链路根本没打通**

### 现象
`supportsVision` 恒为 `false`、`imageResolver` 恒为 `undefined`。功能在当前形态下 **100% 不可用**。

### 证据链（4 条，逐条源码核实）
1. `src/llm/factory.ts` 的 `ProviderConfig` 接口**只有** `supportsToolCalling` / `supportsStructuredOutput` 两个能力位，
   **没有** `supportsVision`、也没有 `imageResolver`。
2. `createProviderFromConfig` 建 `OpenAICompatibleProvider` 时只透传那两个字段，新加的两个字段**在这建不動、也传不进去**。
3. 该文件头部注释自述：`createProviderFromConfig —— 【规范入口】`；`createLlmProvider` 内部也调它 ⇒ **两条建造路径同源堵死**。
4. 宿主**全部**建房 provider 的路径都走这个入口：
   `extension/host/llmConfig.ts:28`（前台）／`:56`／`:81`（background）／`providers/providerStore.ts:480`（连接测试）。
   宿主自身的测试 `llmConfig.test.ts:6` 更是明写：**「该分支是能力位进入内核的唯一通路」**。

### 后果（不是"以后再说"，是现在就把路走死了）
- 一旦宿主真的开始发图，我上一轮加的**一级门禁会 100% 拦死**（判据读 `supportsVision`，而它永远拿不到 true）。
- 更恶劣的是错误提示引导用户去**一个并不存在的选项**："请在设置中勾选支持视觉（supportsVision）的模型" ——
  设置面板里**根本没有这个复选框**（`settingsPanelHtml.ts` 只有 `f-toolcalling`）。⇒ **死循环引导，用户永远无法自助解决**。
- 即使有人把门禁放宽，`imageResolver` 仍恒为 undefined ⇒ 图全部走二级降级**静默丢弃**，
  用户看到的是"我发了图，AI 像没看见"。这是典型的**静默失败**。

### 根因：这不是单纯的疏忽，是**双轨分工的接缝落空**（更值得记的教训）

把范围放大看会发现——这条链路**两边都没接管**：

- `IMG-1`（内核轴）的默认心智模型是"能力位定义在 `provider.ts`，由 `openaiCompatible` 接收即可" ⇒ **没意识到中间还有一个「建房入口」要同步**；
- `IMG-2`（宿主轴）登记的"落点四跳"（台账 516 行）是
  **DTO → 表单 → `providerStore` → `llmConfig` 前台+background** —— **全是宿主侧，同样不含 `factory.ts`**。

而真实链路是 **5 跳**，中间多了一跳谁都没算进清单：

```
宿主 DTO → 表单 → providerStore → host/llmConfig
                                        ↓
                        内核 factory.ts · ProviderConfig   ← 🔴 真空地带，两边都没接管
                                        ↓
                        内核 OpenAICompatibleProvider
```

宿主把字段辛辛苦苦传到 `llmConfig` 的最后一米，`createProviderFromConfig` 悄无声息把它吃掉，
**编译器看不见、测试也不会红** —— 这是 SSOT 最难防的一类伤：**断链发生在"谁来传值"这条社会学路径上，类型系统全绿。**

⇒ 结论有两层：**表层**是上一轮照清单执行时没把这一跳做完；**根因**是
**双轨规则（ADR-033）的边界定义没能覆盖 `factory.ts` 这一跳**。修完连接实现的同时，**两侧的清单本身也需订正**，
否则下一种能力位（或下一个人）会同一个洞。

需要说清楚的是，**方案其实已经逼近了这个点**（§6.3、F5、第 700 行），并且给出了完整的踩位点：

> 「- **宿主契约面（代码核实）**：能力位不在内核 `LlmProvider` 一处——宿主侧另有三跳，全部要进清单：
> `src/shared/protocol.ts` · `LlmProviderConfig`（DTO 真源）→ `extension/providers/providerStore.ts`（透传）
> → `extension/host/llmConfig.ts`（**前台 + background 两处构造**，漏 background ⇒ 后台任务模型没有能力位，
> 症状是「主对话能发图、后台摘要静默降级」）。」

台账 `IMG-1` 的条目内容**未提及** factory / 注入链路。
⇒ **文档有、实现无**。这是本项目红线「文档迁就实现 = 撒谎」的反向形态：**有文档指路却没照着做完，还宣了"落地"**。

对照已完成的能力位 `supportsToolCalling`，更能看出新能力位只接了一半：

| 环节 | `supportsToolCalling`（完整） | `supportsVision` / `imageResolver`（残缺） |
|---|---|---|
| 宿主 DTO（`shared/protocol.ts`） | ✅ 有字段 | ❌ 无 |
| 宿主 UI 入口 | ✅ `f-toolcalling` 复选框 | ❌ 无 |
| 宿主透传（`providerStore` / `llmConfig`） | ✅ 前台 + background | ❌ 无 |
| 内核工厂（`factory.ts` `ProviderConfig`） | ✅ 有且透传 | ❌ **无** ← 断在这里 |
| 内核 provider（`OpenAICompatibleProvider`） | ✅ | ✅（只做了这层） |

**最危险的不一致就长这样**：看起来一样，实际通不了电。

### 修法（最小且必须）
1. `src/llm/factory.ts`：`ProviderConfig` 加 `supportsVision?: boolean` / `imageResolver?: ImageResolver`，并在构造处透传。
2. 宿主三跳同步：`shared/protocol.ts` DTO → `providerStore` 透传 → `host/llmConfig.ts` **前台 + background 两处**（方案点名不许漏 background）。
3. UI：`settingsPanelHtml.ts` / `configView.ts` 给视觉能力一个复选框入口（否则错误提示继续误导用户）。

## 二、中等 #1：单图 token 上界 1568 硬编码，**注释承诺了并不存在的配置项**

`IMAGE_TOKEN_UPPER_BOUND = 1568` 是写死的常量，**没有任何配置/注入通道可以覆盖**。
而我在它的注释里写："OpenAI high detail ≈ 2125，实测后端为 OpenAI high 时**应上调配置**" ——
**注释承诺了灵活性，实现却没给。这是自己制造的文档债**（同属「注释与实现漂移」）。

实际影响：对接 OpenAI high detail 时，每张图低估约 (2125−1568)/2125 ≈ **26%**，累积到多图会显著低估占用。

> 建议：要么加注入项（跟随 provider 配置），要么**删掉注释里那句"应上调配置"**（承认写死）。二者选一，**不许保持现状**。

## 三、中等 #2：`RETAIN_IMAGE_ROUNDS` 一个常量承载两个语义

同一个常量同时是：
- 上下文装配的**保留窗口**（最近 4 轮的图进模型上下文）；
- 宿主会话加载期的**预读量上限**（方案 §5.4.1）。

这是我自己在注释里写的（"同一常量亦为预读量上限"）。当前二者恰好都是 4 所以不痛，
但**一旦要分别调整（窗口 4 轮、预读 6 张），就必须拆常量**。
违反本项目「复杂度守恒 + 单一语义」精神，属**抗变更性缺口**，非当前 bug。

## 四、疑点（待确认，非定案）：占用环存在两个数据口径

同一个 UI 元素（`context_occupancy`）有两条来源：
- `postHistoryOccupancy()`（chatPanel:2204）= **宿主重算**：`collectHistoryMessages()` → `estimateTokensMessages()`（我修的那条）；
- `postContextOccupancy()`（chatPanel:4252）= **内核透传**：直接用 `AgentMetrics.context.occupancy`（prepare 期真实用量）。

从注释看是**按时机分工**（切历史会话重算 / 每轮结束透传），未必是错的；但同一指示器两口径存在跳变可能。
**需实测确认**：内核那条 `ctx.occupancy` 在**本轮发了图之后**是否已计入图片 token（取决于 contextPreparer 喂进去的 messages 是否带 `attachments`）。
若未计入，则出现「切会话看得到图占用、本轮结束后占用反而掉回去」的怪现象。

## 六、审查判据：为什么门禁全绿却没抓住 P0

上一轮跑出的结果是：内核 `tsc`/`build` 绿、全量 3054 通过、宿主 tsc 绿、`docs:links`/`ledger:hygiene`/`ledger:fold` 绿。
**没有一个门会红**，因为：

- 表面守卫（`publicMemberSurfaceGuard` / `publicApiSurfaceGuard`）只管"符号登记"，**不管"符号能不能被注入进来"**；
- 类型系统是本地可见的 —— `OpenAICompatibleConfig` 有这两个字段，类型全通过；
  **断链发生在"谁来填这两个字段"这条社会学路径上，编译器看不见**。

这正是本项目既有的教训复现：**门禁绿 ≠ 结构完整**（`user MEMORY.md`：曾两次出现标题被吞、七类全绿）。
⇒ **建议补一条变异级守卫**：断言「宿主 `LlmProviderConfig` 的能力位 ⊆ 工厂 `ProviderConfig` 的能力位 ∩ `OpenAICompatibleConfig`」，
  或至少断言宿主透传了对 `supportsVision` 的实体引用（能让"漏接 Inheritance"直接变红）。
