## 0. 要点总结

1. **思路方向站得住，当前文档形态不宜照此落地。** 「内核只给 allow-only 机制、宿主会话层承接模式/关系/调度、角色包只管身份、主控不干活、子会话是普通会话」是本仓最贴 SSOT/自然生长的一条路线；但文档已长成「论证 + 实施规格 + 验收判据 + 排期」混合体，与它自己声明的「路线推演、不新增台账条目、不另立第二份真源」不符。
2. **至少 5 处可证的内部矛盾 / 1 处代码事实错判 / 1 处未闭合安全契约。** 最重的是：#6 父子关系的内核/宿主归属三处打架；#7「后台代答不留痕」与 `ConfirmCoordinator._logDecision` 实际行为相反；「默认全代点」把 `classifyCommand` 恒弹 + 30 分钟 fail-closed 变成模型自证授权。
3. **自然生长做得比 SSOT 好。** 三拒（拒第四套 `mutating` 真源、拒「包声明 + 宿主开关」两把钥匙、拒「包名→模式」映射）是对的；但 #7 若照文档落地会并列第二套审计通道，恰好破坏 `_logDecision` 的「唯一发点」不变量。
4. **不带伤的最大缺口是门禁成本没进九件清单**：`protocolGuard`（类型计数 + AGENT_EVENTS 消费对账）、`publicMemberSurfaceGuard`（冻结成员面）、`max-lines`（只降不升）、`HOST-SESSION-OUTCOME-1` 已登记的「不写 `SessionMeta`」理由，文档均未计入验收。
5. **建议：先收口再立项。** 拍 `git push` 例外 + 把授权判据改成可机检 → 一次定死 #6 归属 → 把 §14 的判据/排期折成台账条目 → 订正 #7 与 §3.2 旧快照 → 才按 §13.10 分期推进。

## 3. 五处硬发现（逐条展开）

### H1 · 文档形态与自我定位不符（第二真源已形成）

§9 写「**引入新不变式 = 必须单独立项，本文只做路线与口径，不预支实现**」，文末写「**不新增台账条目、不占 ADR、不进索引**、不在本文另立第二份真源」。但 §14 已产出：九件缺口清单、8 硬前置/1 可后置的裁决、按内核/宿主分层、三个发版批次、**§14.17.3 验收判据**、§13.11 工具签名与 §14.20 装配顺序。这些是实施规格与判据，不是论证。

同时台账已经派生 5 条带「完成判据：」的条目，且命名体系是「自助模式前置 P1/P2/P5/P6」，文档用的是「托管 / 主控 / 九件 #1–#9」。**同一批前置件在两处挂了两套名字与两套判据**，这是「同一事实两处登记必漂移」的活样本。按 `memora-doc-reality-audit` 铁律五，审计结论必须转台账条目；本轮只读评估未改台账，条目建议见 §7。

### H2 · #6 父子关系归属三处矛盾，内核改动范围从 1 项膨胀到 5 项

- §13.9：**「内核（只一项）K1 封闭工具面；其余零改动：会话实体在宿主，内核不需要认识父子关系」**，H3 关系表是宿主级 `{childSid, parentSid, parentRequestId, dispatchedRoundId}`。
- §14.2 F：**「唯一落点是宿主侧表」**。
- §14.6：**「内核动五处：… #6 parent 字段」**。
- §14.15.1 / §14.17.1 / §14.15.5：**#6 跨层**，「内核要给子会话分配 id / 记 parent」，且 #2 的 DTO 依赖 #6 先冻结 `parentSessionId`。

没有一处给出「为什么 §13.9 的宿主级表不够、必须升格为内核字段」的裁决记录。这是**真源归属未定**，不是文档笔误：它决定内核是否要认识父子关系、是否要改 `SessionMeta` 冻结成员面、是否必须内核+宿主同版发版。**判断**：按复杂度守恒与既有分层（内核管机制、宿主管策略），应回到 §13.9 的「内核只 K1」，关系表全放宿主；若坚持内核字段，必须先写成一条独立裁决并同步 §13.9 / §14.2 / §14.6 / §14.15 四处。

### H3 · #7「后台代答不留痕」与代码事实相反（且行号已漂到别的函数）

文档主张（§14.13.1 A5、§14.14 #4/#7）：「后台代答现在**不写** `_logDecision`（`confirmCoordinator.ts:413-415` 只在会话正是前台时记录）」⇒ 据此把 **#7 后台审计列为「新造 · 硬前置」**，并要求新增审计通道或扩展日志门控。

代码事实：

- `answerFor(sessionId, requestId, approved)` 第 490 行调 `this._logDecision(entry, approved ? 'approved' : 'declined', sessionId)`，**按会话寻址**。
- `_logDecision` 对后台会话走 `if (sessionId !== this._foreground) { this._stateFor(sessionId).pendingDecisions.push(notice); return; }` ⇒ **留痕，只是不上屏**，切前台由 `_flushPendingDecisions` 补发。源码注释明写「既不会写进当前屏幕，也不会『后台代答/超时』整条丢失」，且「决策留痕唯一发点 `_logDecision`」。
- 文档引用的 `413-415` 实际落在 `_settle`（清 timer / `state.current = null` / `onPendingChanged`），不是 `_logDecision` ⇒ 溯源错位，正是文档自己警告的「行号会漂移」。

**准确裁量**（别一刀切）：#4/#9 的「`answerFor` 只认 `current`、排队项丢弃」**属实**（源码第 471–473 注释与 486–487 实现一致）；错的是把「不上屏」推成「不留痕」。真正缺的只有三样：① 读 pending payload 的公开入口；② 答队列项的入口；③ 代批记录的主语区分（必须写「托管代批」，不得写「用户批准」）+ 早报读法。**#7 不是「新造审计通道」，而是「复用唯一发点、加主语与读法」**；照文档落地会并列第二套审计，且与「唯一发点」不变量正面冲突。

### H4 · 代答击穿确认链已拍板语义，且判据退化成不可机检

既有链（取证）：`classifyCommand` 的 deny 恒拦 / always-ask 恒弹（`ALWAYS_ASK_COMMAND_PREFIXES` 派生正则表，`confirmEntries.ts` 明写「判据与 command 面同一个函数」）→ `ConfirmCoordinator` 只推前台、`_show` 才起 timer → 30 分钟超时 `resolve(false)` fail-closed。后台会话确认只入队、永不上屏 ⇒ 设计文档 §7.2 / 口径文件 §1.1 的死锁推论成立（v1 子 agent 靠 deny 轴从根上不给写工具避开，这一条是**对的**）。

设计主张（§14.16.7）：**「默认所有交互按代点处理：ask、运行命令确认、工具确认，一律代点」**，授权清单是可选收窄项；§14.16.2 自认「**托管默认代点会代答这张卡，兜底因此失效**」，§14.16.7 自认「`git push` 不代批」与「默认全代点」冲突且**待裁决**。

三条后果：

1. 恒弹卡被代答 ⇒ `classifyCommand` 的裁决结果被模型二次覆盖，恒弹语义名存实亡；`ALWAYS_ASK` 含 `git clean` 这类不可逆动作的护栏随之失效。
2. 卡一生成即被代答 ⇒ timer 从未启动 / 立刻清掉，`CONFIRM_TIMEOUT_MS` 的 fail-closed 从「超时拒」变成「模型批」；后台队列的「不上屏不计时」语义被绕开。
3. §14.16.3 明写「**授权判据是模型判断，不是代码可验证**」。这与 §14.8.6「防护顺序：结构性闸 > 配额计数 > 提示词。任何只靠提示词『不要重复派』的方案都无效」自相矛盾——代答恰好只靠提示词。项目判据纪律要求可回源、可变异验证、单一判据点；模型自述「用户哪句话授权了」不可证伪。

**判断**：这是**未闭合的安全契约空洞**，不是待优化细节。所有后续排期都应 BLOCK 在这一条上。

## 4. 站得住、不要推翻的部分

- **三拒**：拒绝 `mutating` 第四套真源（§14.8.1）、撤回 `session:manage` 两把钥匙（§14.8.5）、取消包名→模式映射（§14.19）。每一拒都在减真源，是本设计的骨架。
