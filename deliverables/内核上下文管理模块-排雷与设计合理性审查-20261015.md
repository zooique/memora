## 一、排雷明细（逐条对抗式复核）

### ✅ P1-1 占用快照名不副实 —— 成立，且**升级**

**上一轮的保留意见是"取决于宿主怎么消费"**。现在取证完毕：

| 环节 | 证据 |
| --- | --- |
| 宿主读取 | `chatPanel.ts:4023 postContextOccupancy()` → `:4025 const ctx = this._agent.getMetrics().context` → `:4026 const occ = ctx.occupancy` |
| 宿主推送 | `:4033-4041` 组装 `context_occupancy` 推给 webview |
| webview 计算 | `chatView.ts:5072` `usedPct = ((total − occ.freeTokens) / total) * 100` → `setRingFill` + `occPercent` 文本 |
| webview 渲染 | `chatView.ts:4962 renderOccupancySegments` 渲染**五段构成条**；`:4933 buildOccupancyTipText` 渲染 hover 明细 |
| 用户可见 | 输入区常驻圆环 + 构成条 + hover 明细（`chatPanel.ts:4280` 骨架） |

**误导方向坐实**：`freeTokens` 系统性偏大（`budget.ts:135` 把所有未统计的动态注入算进 free）⇒ `usedPct` 偏小 ⇒ **用户看到"还剩很多空间"，实际已被动态注入占掉**。

**加强点（新发现）**：这句不实声明**被复制到宿主协议层**——`protocol.ts:731` 原样写着「各段为 prepare 期**真实用量** token，互斥分段拼满窗口总容量 totalTokens」，与内核 `budget.ts:84-87` 是同一句假话。**内核一处、宿主一处，共两处**。这正是本仓「谎报位点」纪律的典型形态：修一处不算完，同一位点须扫全。

UI 文案更直接——`chatView.ts:4956` 注释自称「四段**真实**占用 + 剩余」，「真实」二字站不住。

### ✅ P1-2 `actualInputTokens` 有采集无消费者 —— 成立

- 采集：`llmCaller.ts:305` `metrics.actualInputTokens += chunk.usage.inputTokens`；`:307` 写 span 属性。
- 透出：`loop.ts:3087` 经 `getMetrics()`；`roundStore.ts:168` 注释自认「实测值在 actualInputTokens，**宿主取证面未消费**」。
- **宿主生产代码零消费**：全 `hosts/memora-vscode/src` 唯一命中是 `hostIntegration.test.ts:130` 的 mock（`span.setAttribute('actualInputTokens', 792)`）。
- 结论：估算器（`CHARS_PER_TOKEN=3` / `CJK=1.5`）无任何实测反馈闭环 → 高密度文本低估无告警。**有数据不消费 = 观测断链。**

### ✅ P2-3 双 token 口径 —— 成立，**表述订正**

上一轮说"方向安全（高估）"，不够精确。精确形态是**两个不同用途各用一个口径**：

| 用途 | 口径 | 证据 |
| --- | --- | --- |
| **触发**（超没超窗） | 一次性 `ceil(Σ字符/密度)` | `contextManager.ts:237 shouldTruncate`、`:308` 截断入口 |
| **填充**（每段装多少） | 逐条 `Σ ceil(每条字符/密度)` | `:350` tail 累加、`:358`、`:417`/`:431` keyMessages 贪心 |

两者**不等价**（`contextManager.ts:130-133` 注释自己声明"后者系统性高估"）。后果：触发后实际裁得比"按触发口径预期"更狠。**注释宣称 SSOT 单点，代码在填充路径上另起一套口径。**

### ✅ P2-4 截断后无二次收敛 —— 成立，**加强**

- 组装 `truncated = [systemMsg, summary?, ...keyMessages, placeholder, ...tail]`（`contextManager.ts:381-387`），**`summary` 与 `placeholder` 不计入 `availableTokens`**（`:328-329` 只扣了 system），末尾仅 `logger.info`（`:389-401`）。
- **加强**：`summary` 来自 `assembler.ts:575 roundSummaryLoader`，它拼的是**最多 5 条已存 round-summary**（`assembler.ts:41 ROUND_SUMMARY_LOADER_MAX = 5`、`:589`），**不受 `SUMMARY_MAX_TOKENS = 150` 约束** → 溢出量可达上千 token，不是上一轮估计的"可忽略 200 token"。
- 测试 `contextManager.test.ts:490-501` 只断言 `newTokens <= 100 * 1.1`（上界 110 > 设计声称的 90），**用宽松上界掩盖**。

### ✅ P2-5 / P2-6 —— 成立（无订正）

- P2-5：`contextManager.ts:260-264` 用 `content.includes(SOFT_LIMIT_SUMMARY_MARKER_ROUND/_COMPRESS)` 识别摘要消息；`Message` 无 `kind` 字段。
- P2-6：软上限用 flag（`loop.ts:1598`/`:1600`），压力提示用硬编码中文子串（`loop.ts:1612` `includes('上下文空间提示')`，字符串真源在 `constants.ts:214`）。同族两级、两种口径。

### 🔻 P2-7 `minRecentRounds` —— **降级为 P3（预留键）**

排雷发现上一轮**高估了它的现实性**：

- `minRecentRounds` 只存在于 `types`/`loop`/`contextManager` 三处**定义与透传**；
- **`assembler.ts:599-657` 构造 `AgentLoop` 时根本不传该键** ⇒ 恒 `0` ⇒ `contextManager.ts:337` 那条强制保留分支**生产永不进入**；
- 测试中 `minRecentRounds` **零匹配**（`grep` 于 `src/agent/__tests__`）⇒ 该分支零覆盖。

按本仓「预留键 vs 僵尸键」原则（`single-truth-source-mindset.md:37`）：它有明确设计意图（KV cache 放宽），属**预留键**；但缺陷（`contextManager.ts:205` 只 `Math.max(0,...)`、`:343-352` 强制区不计 token 上限）**只在启用时才暴露**。→ **降级**：当前非现实缺口，但启用前须补 clamp + 用例。

### 🔻 P2-8 尾部注入延迟 —— **收窄 + 部分撤回**

上一轮写"延迟一个迭代生效"，并指控"软上限未声明该延迟"。**两条都不准**：

1. **只在截断轮发生**。未截断时 `truncateMessages` 直接 `return messages`（`contextManager.ts:309-310`）⇒ `safeMessages === this.messages`（**同一数组引用**）⇒ 之后 `appendSystemMessage` 的 `push` **即时反映**到 `safeMessages`。只有截断轮 `replaceContext([...safeMessages])`（`loop.ts:1556`）产生新数组，后续注入才落在 `safeMessages` 之外。
2. **已有声明**。`loop.ts:3475-3478` 注释明确写：「在**截断轮**里，本轮被发送的 `safeMessages` 不含本情报区……**此与 search 收敛提示 / taskTable 等所有既有动态注入提示的时序一致（库级既有行为）**」。软上限/压力提示属同一类，**已被这句覆盖** ⇒「未声明」的指控**撤回**。

→ 从缺口清单移除，归入"设计特性说明"。

### 🆕 N1 协议层 `dialogueTokens` 语义与实现不符（新增）

- **协议注释**（`protocol.ts:741`）：`dialogueTokens` = 「完整对话层实际占用（**最近轮次注入正文**）」。
- **实现**（`contextPreparer.ts:155`）：`loop.estimateTokens(loop.getConversationMessages())` —— `getConversationMessages` 在 `loop.ts:3179-3185` 过滤 `role === 'user' || role === 'assistant'`，即**全量问答闭环**，**不是**"最近轮次注入正文"。
- 且内核注释 `contextPreparer.ts:148-162` 专门论证了这次改动：「**统一全量**后 prepare 与刷新共用同一估算器、同一数据源（SSOT），杜绝口径分叉」——**内核改了，宿主协议注释没跟上**。
- 这是「文档漂移」：宿主注释描述的是已废弃的 fixed/hybrid 子集语义。**测试不拦**。

### 🆕 N2 占用契约跨包复制、无守卫（新增）

- 内核 `budget.ts:89-104 ContextOccupancy` 与宿主 `protocol.ts:736-755 context_occupancy.occupancy` 是**两份手写结构**（7 字段），且都各自复述了一遍那句不实声明。
- 无任何守卫保证两者字段集双向相等（对比：内核 `confirmEntries.ts` 有 `confirmEntry.test.ts` 做键集双向守卫，这里没有对等物）。
- 后果：内核加/删分段字段，宿主不报错、静默漏渲染。**同族伤在本仓已有先例（`toolFailurePrefixGuard.PRODUCER_FILES` 漏配即失明）。**

## 二、使用角度：设计合理性评估

### 做对的地方（不吝认可）

1. **方向正确**：把"看不见的上下文开销"变成输入区常驻圆环 + 构成条 + hover 明细。Agent 产品的核心 UX 是"用户敢不敢让它做"，上下文预算可视化是信任基础设施（`architecture_philosophy_rules.md` §13）。
2. **失败给可执行指引**：装配前判负时 emit `inputTooLarge` + hint「内容过大，建议放进文件用 read_file 读」（`contextPreparer.ts:112-117`）——不是一句"超限了"，而是给下一步动作。
3. **两级压缩自动执行**：替换（LRU 换已存摘要）+ 占位（旧 tool_result），用户无需手动清上下文。
4. **有回调通道**：`onContextTruncated` / `onContextCompressed` 让宿主可感知（是否呈现未展开）。

### 使用角度的真问题

| # | 问题 | 影响 | 证据 |
| --- | --- | --- | --- |
| U1 | **仪表盘读数偏乐观** | 用户按圆环判断"还能贴多少内容"必踩坑。按 §13「置信度可视化」，**可视化错 = 信任 -N** | `chatView.ts:5072` usedPct；P1-1 |
| U2 | **"真实占用"话术名不副实** | hover 明细里"剩余 X token"虚高，用户越信越亏 | `chatView.ts:4956` 注释；`protocol.ts:731` |
| U3 | **最近对话双份呈现** | `assembleContext` 把最近 N 轮拼成 `[Recent conversation]` system 注入（`contextPreparer.ts:136-141`），而这些轮的**原文仍在 `this.messages` 里**（`getRecentHistoryWithinBudget` 取自同一批消息）⇒ 同一内容进窗口两遍。**中等历史长度时浪费最大**（原文未被裁 + 拼接文本全在） | `contextPreparer.ts:126-141` |
| U4 | **软上限"收敛指令"在截断轮延迟一次 LLM 调用** | 用户观感"该收尾了还在调工具"，实为机制固有延迟（非 bug） | `loop.ts:1551`/`:1601` |
| U5 | **两级压缩静默** | 用户看不到"系统压了多少、丢了什么" | 仅回调给宿主 `onContextCompressed`（`loop.ts:2467`） |
| U6 | **`minRecentRounds` 旋钮停在纸面** | 想用 KV cache 优化的宿主没有开箱旋钮，须改内核装配器 | P2-7 |

**U3 值得专门说**：把最近对话"提升"为 system 消息，若目的是**强化权重**，那它只对"权重"有价值；若目的是**省 token**，它反而是反效果（双份）。当前注释只说"提供结构化视图，避免 LLM 丢失上下文连续性"——但原文就在上下文里，结构化视图的边际价值有限。**这是一个应当被重新论证的遗留设计**，不是纯 bug。

### 3.2 正面样本（该表扬的要表扬）

1. **`restoreHistory` 的失效 chokepoint**（`loop.ts:3275-3301`）：把"历史被整体替换"这一**事实**作为摘要缓存 + `replacedRoundIds` 的统一失效点，拒绝从 `messages.length` 差值反推（`contextManager.ts:447-455` 论证了为什么 `Math.abs` 是错的）。**这是全模块最漂亮的 SSOT 收口。**
2. **双线预留比例不统一**：有论证、有 ⚠️ 标注、有"勿统一"的显式纪律（`budget.ts:25-29`）。**这是"刻意分歧"的教科书写法。**
3. **`compaction.ts:134-135` 的 `isContextTruncated` 双保险**：`shouldCompact` 和 `compact` 都判一次，注释说明理由（错位替换危害更大）。防御性设计到位。
4. **`contextPreparer.ts:148-162` 那段"为什么必须全量"的论证**：把一次口径统一的历史决策完整留痕。**可惜宿主协议没同步**（N1）。

### 3.3 质量审查结论

**代码主体是干净的**：判据收敛、chokepoint 明确、刻意分歧有纪律。真正的伤集中在**两类**：

1. **声明与实现不符（谎报同族）**：P1-1（两处）、N1（一处）。共同特征——**测试不拦、读者信了**。这正是本仓血训里最贵的一类。
2. **判据形态脆弱（结构化不足）**：P2-3（口径）、P2-5（文本当结构）、P2-6（两种幂等口径）、N2（跨包结构复制无守卫）。共同特征——**能跑，但"靠约定"而非"靠结构"**。

## 五、本次排雷的方法论留痕

- 上一轮标注"**未覆盖：宿主侧消费**"——那正是**误判风险最高**的一处。本轮补齐后：P1-1 从"取决于宿主"变成"坐实且升级"，并新挖出 N1/N2 两条。
- 同时**主动降级/撤回**了两条自己的结论（P2-7 降 P3、P2-8 部分撤回）——排雷不是"把结论证成"，是"把结论证准"。
- 教训：**凡结论依赖"消费方行为"的，必须先取证消费方**，否则就是在猜。这一条与 `single-truth-source-mindset.md` 的「措辞折叠」纪律同源。
