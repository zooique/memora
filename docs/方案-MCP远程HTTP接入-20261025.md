## 0. 一句话结论

现有运行时只有**一条**通道：在家拉起子进程（stdio）。于是**凡是没有本地包、只发托管 URL 的 server（Notion / Sentry / Linear / GitHub 远端等）一台也接不上**——不是「体验差一点」，是这类 server 在这台客户端上**不存在**。

立项补的正是这条通道：**Streamable HTTP + OAuth 2.1**。主流四家（Claude Code / VS Code / Cursor / Cline）已全部支持；再不支持 = 生态覆盖面腰斩。

## 1. 立项依据（2026-10-25 网络核实，非传闻）

### 1.1 主流客户端现状

| 客户端 | 远程支持形态 | 认证归谁 |
| --- | --- | --- |
| **Claude Code** | `--transport http`（Streamable HTTP）；**SSE 传输已于 2026-04-01 停止接受新连接** | 客户端走 OAuth 2.1，浏览器授权 |

**判定**：远程 HTTP 已是事实标准。不做，等于自愿放弃无本地包的那一半生态。

### 1.2 规范硬要求（这些决定实现形态，不是可选项）

| 规范版本 | 变化 | 对本方案的硬约束 |
| --- | --- | --- |
| **2025-06-18** | 授权改为 OAuth 2.1 + PKCE；MCP server 降级为 **OAuth 资源服务器**（不签发令牌）；必须实现 RFC 9728 受保护资源元数据；客户端必须发 RFC 8707 `resource` 参数；禁 implicit / ROPC / 令牌进 query；**redirect URI 必须是 localhost 或 HTTPS** | ① 不能自己拼 `/authorize` 端点，必须走元数据发现（SDK 已实现，宿主别重写）；② **回调不能用 `vscode://`**（scheme 非 http(s)）⇒ 必须 `http://127.0.0.1:<port>`（§5.3） |
| **2025-11-25** | 加 OIDC discovery、增量 scope 挑战 | 「缺 scope」会以 401 + `WWW-Authenticate: scope=` 形式再来一次 ⇒ 状态机要允许「已授权但 scope 不足」再授权一次，不能当成永久失败 |
| **2026-07-28** | DCR（RFC 7591）**弃用**，转 CIMD（`client_id` 是 HTTPS URL，指向客户端自己托管的元数据文档）；加 RFC 9207 issuer 校验 | **扩展托管不了 HTTPS 静态文档** ⇒ CIMD 走不通；主路是 DCR（多数 AS 仍兼容），补路是手填预注册 `client_id`（§6-R2） |

## 3. 三条判据（贯穿全案，冲突时以本节的推导为准）

**J1 · 传输形态 = 「谁在执行」的分界。**
stdio = **在本机拉起一个进程**（授权面：允许一条命令在你机器上执行）。http = **连一个远端服务**（**数据外流面**：允许把你的工具参数与结果发给这个域名）。
两者代价不同质 ⇒ 授权点文案、失败诊断、审计口径**都不能复用同一套说法**。把远程说成「和本地一样，只是不用装」就是撒谎。

**J2 · 一份配置一种形态。**
`command` 与 `url` 互斥。判据**单点** = `configProblem` 扩展；禁在 `connectionManager` / 表单 / 导入各写一份（那是本仓反复踩的判据散点）。

**J3 · 凭据按「谁能看见」分存。**
用户手填的 `headers`（用户自己写的，愿意落 `settings.json`）与机器换来的 OAuth 令牌（**必须** `SecretStorage`）分两个面。禁第三条路——尤其禁「把 token 写进 `headers` 一起落设置」。

## 4. 协议成本实测（订正上一轮判断）

上一轮我判断「加远程要新增 webview 通道 ⇒ 必须先做协议面治理」。**实测推翻，这个判断是错的**：

```
当前去重类型数 = 129      （阈值 130，余量 1）
加 op 后    = 129  差值 0
加 state 后 = 129  差值 0
加字段后    = 129  差值 0
```

- 探针与 `protocolGuard.test.ts` **同一段正则**（剥块注释 → 剥行注释 → 只数 `type: '...'`），只是不落盘；`protocolGuard` 实跑 4/4 绿，读数 129。
- 原因：`McpWritePayload` 的 `op:` 与 `McpServerState` 的字面量**不是** `type:` 形式 ⇒ 不计入通道数。

**结论**：远程接入用 `字段 + op + 状态值` 三样即可，**129/130 的余量仍为 1，不阻塞、不需要先治理协议面**。

⚠ 但「不加类型」≠「不加通道语义」：新增的 op 仍是一条真实的 webview→host 指令路径，必须进 `docs/方案-MCP工具接入-20261023.md` §10 登记表并给测试钉子（§7 每片带）。

## 5. 形态定案（技术建议）

### 5.1 配置形状

```jsonc
// 远程（新增）
{ "name": "notion", "transport": "http", "url": "https://mcp.notion.com/mcp", "headers": { "X-Foo": "bar" }, "enabled": true }
// 本地（现状，一字不改）
{ "name": "fs", "command": "npx", "args": ["-y", "@modelcontextprotocol/server-filesystem", "."] }
```

- `transport?: 'stdio' | 'http'`，**缺省 = stdio** ⇒ **老配置零迁移**（这是「不带伤」的硬要求：不给存量配置制造一次全网重写）。
- `http`：必填 `url`；`url` 只认 `http:` / `https:`（非回环地址强制 `https:`，回环允许 `http:` 便于本地网关）；**禁填** `command` / `args` / `cwd` / `env`（不是静默忽略——忽略 = 用户以为生效了，判据见 §5.1.1「互斥 = 报错」）。
- `stdio`：必填 `command`；**禁填** `url` / `headers`。
- 判据实现：`configProblem` 内按 `transport` 分派，返回第一处问题的中文原因（沿用现有「缺少 name」「缺少 command」的文案风格）。

#### 5.1.1 类型面与判据补拍（2026-10-25 · S1 前置，用户授权「按推荐思路推进」）

S1 的真实动作不是「DTO 加 3 个字段」，而是**把 `command` 从必填改为可选**——不改这一步，远程配置在类型层根本写不出来。连带面由编译期强制暴露，一处不能漏：

| # | 位置 | 改动 |
| --- | --- | --- |
| 1 | `src/shared/protocol.ts` 的 `McpServerDraftDto` / `McpServerStatusDto` | `command: string` → `command?: string`；新增 `transport?` / `url?` / `headers?` |
| 2 | `host/mcp/connectionManager.ts` 的 `McpServerConfig` | 随 `extends McpServerDraftDto` 自动继承，无需重复声明 |
| 3 | `webview/panels/mcpServerOps.ts` 的 `draftToConfig` / `parseImportEntry` | 保留 / 映射远程字段（别名口径见下） |
| 4 | `webview/scripts/mcpView.ts` 的 `draftOf` / `summaryOf` | `server.command ?? ''`；空命令卡片副标题显示 `transport` 而非空串 |
| 5 | `host/mcp/statusView.ts` | 保持显式挑字段构造；**不新增下发 `headers`** |
| 6 | 既有测试 | stdio 用例必须全绿（反向护栏，见 §7 切片纪律） |

- **S1 含 webview 最小改动**：远程卡片在 S1–S2 期间**不可经表单编辑**——保存校验 `!draft.command` 会拦住并提示「名称与命令都不能为空」。这是诚实拦截（不静默改写远程字段），不是缺陷；S3 才给远程表单。登记于 §10。
- **别名口径（定案：读取点不收别名）**：外部格式（VS Code `mcp.json` / Claude Code）用 `type`，本仓用 `transport`。**读取点认 `type` 会让同一语义有两个字段名 = 双真源**；故只由**导入通道**做一次 `type → transport` 映射，写盘只存 `transport`。手写 `type` 的用户由 `configProblem` 指路：「未知字段 type：远程配置请写 transport: "http"，或从导入通道粘贴」。
- **跨形态互斥 = 报错，不忽略**：`http` 带 `command`/`args`/`cwd`/`env`、`stdio` 带 `url`/`headers` ⇒ `configProblem` 返回问题（卡片 invalid + 原因）。静默丢弃会让用户以为字段生效。
- **未知 `transport` 值（含 `sse`）**：文案必须点名「暂不支持 SSE 传输（已定案不做，见 §5.5-1）」，不得退化成「未知值 / 语法错误」——那会让用户把定案当成拼写问题。
- **`headers` 形态校验**：`readMcpServers` 不做字段裁剪（既有设计、有测试钉住）⇒ `headers` 类型上仍是 `unknown`；`configProblem` 必须校验「是对象 + 值均为 string + 值不含 CR/LF」，不合法即报问题。同时**`headers` 不下发 webview**（`deriveMcpServerStatus` 显式挑字段，加断言钉住，防止将来改成展开而把明文令牌推进消息）。
- **类内最小守卫（不是第二套判据）**：`asStdioConfig()` / `asHttpConfig()` 的断言依赖 `configProblem` 已通过，但 `McpConnection` 自身不调 `configProblem`。两个分支入口各加一句存在性 `throw`（`!url` / `!command`），保证「直接 new 的连接」不会把 `undefined` 塞进 SDK。它只守「字段在不在」，不重复形态裁决。
- **401 归因（S1 期间）**：S2 之前无 OAuth，401 → `failed`，文案必须是「服务器要求授权（OAuth 支持在后续版本）」，不得显示「连接失败」——否则用户去查 url 拼写。

### 5.2 连接层（改动全部关在 `connectionManager` 内）

- `connect()` 先分派：`connectStdio()` / `connectHttp()`；**握手之后的逻辑完全不复制**——capabilities 断言（无 `tools` 能力即失败）、`fetchAllTools` 分页、`listChanged` 订阅、`close`/`onClosed` 语义，两个分支共用同一份（**`stderr` 例外**：HTTP transport 上没有该字段，见下条）。
- 类型收窄：`asStdioConfig()` / `asHttpConfig()` **只做类型断言**（判据在 `configProblem`），外加一句字段存在性守卫（§5.1.1），**不写第二套判据**。
- 超时与上限**复用现有常量**：握手 20s、单次调用 60s、分页 50 页。禁为远程造第二套数值。
- `commandProbe` 只在 stdio 分支调用。
- **`stderr` 接线只在 stdio**：`StdioClientTransport.stderr` 在 HTTP transport 上不存在，「握手后共用」从 `transport` 构造完成处才开始；共用段里对 `stderr` 的接线必须按分支，不得写成 `as StdioClientTransport` 断言。
- **HTTP 断线语义（S1 定案）**：`onclose` 共用，但**不自动重连**——远程断流即 `failed` + 注销工具，文案分派为「与远程服务器的连接已断开」；恢复入口 = 改配置（差分重连）或重载窗口，S3 再给「重新连接」按钮。**不得**共用「子进程退出」措辞（HTTP 没有子进程）。

### 5.3 OAuth（最小闭环，不追求全覆盖）

- `McpOAuthProvider implements OAuthClientProvider`：`clientMetadata`（`client_name: "Memora"`，`redirect_uris` 见下）、`clientInformation()` 与 `tokens()` 读写**全部走 `secretsAccess`**、`state()` 随机。
- **回调形态单点**：一次登录起一个 `127.0.0.1:<随机端口>` 临时 HTTP server，**只接受一个** `GET /callback`，取到 `code` 立刻关端口。
  - 为什么不用 `vscode.window.registerUriHandler`（VS Code 官方给自有 IdP 的推荐做法）：规范要求 redirect URI 是 **localhost 或 HTTPS**，`vscode://` 是第三种 scheme，一部分授权服务器会直接拒。**不并行两种回调**，只保留一种（SSOT）。
  - 远程 / Codespaces 场景：回调地址经 `vscode.env.asExternalUri(http://127.0.0.1:<port>/callback)` 转换（官方文档明确支持 http 端口转发），拿到的完整 URI 原样交给 provider，不自拼。
- 登录态流转（**不得跳步**）：
  ```
  连接 → 401 → 有令牌则尝试刷新 → 刷新失败/无令牌 → state = needs-auth（不是 failed）
  用户点「登录」 → mcp_write{op:'login'} → 打开浏览器 → 回调 → finishAuth → ack{ok} → 自动重连一次
  用户点「撤销」 → mcp_write{op:'logout'} → 删 SecretStorage 条目 → 断开
  ```
- 令牌 key 单点：`mcpOAuthSecretKey(serverName)` 一处生成，`serverName` 复用 `normalizeServerName()`（禁再造归一化）。
- 已授权但 scope 不足（2025-11-25 的增量 scope 挑战）：按「再授权一次」处理，不判永久失败；上限一次，避免无限弹窗。

### 5.4 状态面（第六态）

- 新增 `McpServerState = ... | 'needs-auth'`：配置合法、启用、**尝试连接**时 server 返回 401 且无可用令牌。
- 与 `failed` 的边界写进 JSDoc：`failed` = 试过但**非认证原因**失败；`needs-auth` = **明确要用户授权**。混成一个的后果是用户看到「启动失败」去查 `command` 拼写，而真正要做的是点登录。
- 必须同步 `STATE_LABELS` 等 Record（穷尽 ⇒ 漏配 = **tsc 红**）。这里是护栏而非负担：加态不红才是危险信号。

### 5.5 定案（2026-10-25 · 按「推荐」列落定）

> **授权来源**：用户当轮「按你的推荐思路推进」⇒ 表中三项按推荐值**定案**，不是 AI 自推自批。重开须先改判据（如出现**具名** SSE-only server）。**第四项（配置作用域）同日单独拍板，见 §5.5.4。**

| # | 取舍 | 定案 | 理由 | 不做 / 反转的代价 |
| --- | --- | --- | --- | --- |
| 1 | **是否支持 SSE** | **不做** | SDK 自己标 `@deprecated`、Claude Code 已停收、规范主推 Streamable HTTP。支持它 = 第二个传输面 + 第二套测试，换来的是一批正在退场的 server | 少数老 server 接不上。**重开条件** = 出现「只有 SSE 且无法升级」的真实 server（须具名，不接受假设） |
| 2 | **`headers` 是否明文存 `settings.json`** | **接受明文**，并在卡片上标注 | 与 VS Code / Claude Code 一致；用户手写的东西进用户级设置最直观；`SecretStorage` 只放机器换来的令牌（J3） | 加密需新键 + UI 改写 + 与手编冲突，成本翻倍；作用域已定为 `machine`（§5.5.4）⇒ 不参与 Settings Sync，明文令牌不外溢，加密的边际收益再降一档 |
| 3 | **是否加「远程 = 数据外流」提示** | **加**：server 卡片标「远程」+ 首次连接写一条日志（**S1 即落地**，成本近零）；完整提示句在 S3 | J1：远程的代价不是「执行命令」而是「上下文出本机」。不说清就是把新面藏起来——这正是本仓「不谎报能力」的反面；能力先于告知 = 沉默式撒谎，最低成本的一半先提前 | 用户以为与本地 server 同质，把内部代码片段喂给第三方域名而不自知 |

**5.5.4 第四项 · 配置作用域取值（已定案 `machine` 并落地 · 2026-10-25）**：`memora.mcpServers` / `mcpToolAllowlist` 原为 `scope: application`，会随 VS Code Settings Sync 把 `headers` 明文令牌与 allowlist 批准同步到同账号的其他设备——批准的语义是「本机用户同意本机进程」，跨机继承等于替 B 机点同意。现改为 **`machine`**：仍只读用户 / 远程设置（工作区写入照样被忽略，`.mcp.json` 红线不变），但不参与同步；代价 = 每台机器各配一次。落地 = `package.json` 两键 + `mcpConfig.test.ts` 断言 + `mcp-setup.md` 同步说明 + 两键 description 补一句「不随 Settings Sync 同步」。**授权来源**：用户当轮「按推荐思路拍板推进落地」（翻的是 2026-10-25「都这么定」的第 2 条，故须用户点头后才动，不自推自批）。

| R1 | `redirect_uri` 硬约束 ⇒ 必须起本地端口；端口占用 / 防火墙 / 公司代理可能失败 | 失败文案必须可操作（「无法在 127.0.0.1 起回调端口，请检查安全软件」），**不许**退化成 `MCP error -32000: Connection closed`（2026-10-24 已踩过这个坑的同类） |

| R5 | 远端副作用不在本机：远程 server 改的是远端状态，本机 `@git-changes` 结构上看不见 | `diskWrite` 定案不变（对 custom 恒不生效）；文档必须写「这不是 bug，是边界」 |

### 7.1 S1 落地实况（2026-10-25 · 代码事实，`af212f56`）

**为什么在 S1 与 S2 之间插 S1.5**（三条事实，不是偏好）：

1. **S1 的远程链路没有一个字节的真实 HTTP**（R12）——假 transport 只证分派，不证协议。OAuth 是整条协议最绕的一段（元数据发现 / PKCE / 回调 / 刷新 / scope 挑战），用假传输调它等于蒙眼走迷宫。
2. **SDK 自带服务器侧 Streamable HTTP 传输**（`@modelcontextprotocol/sdk@1.32.1` 的 `dist/esm/server/streamableHttp.js`、`webStandardStreamableHttp.js` 实测在册）⇒ 可在 `127.0.0.1` 起真服务器，零外网、确定性，成本极低。
3. **S2 的登录按钮要挂在卡片上**，而 S1 的远程卡片在面板里**建不出来**（只能手改 settings.json）⇒ 表单是 S2 的前置落点，不是纯 UI 糖。

**S1 落地要点（按判据归档）**：

| 面 | 落点 | 单一性说明 |
| --- | --- | --- |
| 类型面 | `shared/protocol.ts`：`command?` 可选 + `transport`/`url`/`headers`；`MCP_TRANSPORTS` 为**运行期真源**，`McpTransport` 由它派生 | 取值集合只此一份；`package.json` 的 `enum` 由 `mcpConfig.test.ts` 对拍钉住 |
| 判据 | `mcpConfigGuard.ts` 的 `configProblem`（启动 / 热更 / 面板保存共用） | 缺省值只在 `resolveTransportMode`；跨形态互斥报错而非静默丢弃；未知值（含 `sse`）点名「已定案不做」 |
| 连接 | `connectionManager.ts`：`createTransport(mode)` 为唯一分派点；`stderr` 只在 stdio 分支接线；401 归「服务器要求授权（OAuth 支持在后续版本）」；断线文案按形态分派且不自动重连 | 握手后逻辑（capabilities 断言 / 分页 / listChanged / close）两个分支共用，未复制 |
| 通道 | 导入通道做**唯一一次** `type → transport` 映射；`statusView` 显式挑字段，`headers` 刻意不下发 | 「新增字段默认外发」的风险见 R11 |
| 落盘形状 | 导入路径：stdio 不写 `transport`（老配置零迁移）；表单路径：显式写入（`http → stdio` 切换必须覆盖旧值） | 两条路径形状不同**各有理由**，不是双真源 |

**同轮问诊炼化（五处）**：`MCP_TRANSPORTS` 单点（原「类型字面量 + 函数体白名单 + JSON enum」三份）｜6 处 `'stdio' | 'http'` 字面量改类型别名｜`draftToConfig` 撤掉自筛判据（原会把脏值静默吞掉，让用户拿到「缺少 command」这种错原因）｜`mcpView` 两处形态判断收口为 `isRemote()`｜新增 `package.json` 的 `enum`/`default` ↔ 代码真源对拍测试。

**同型扫描结论**：`package.json` 里还有两个枚举（会话归档模式、搜索结果解析策略）同样处于「JSON 引不到 TS」的双真源状态，**同类补齐**已登记（§10）。

## 9. 不做（各有理由 / 重开条件）

- **安装器 · 本地入库目录**（Cline 模式：下载 → `npm install` → 构建 → 写配置）：等于在客户端里维护一个包管理器。三笔账：① 依赖冲突与构建失败全变成「Memora 装不上」；② `npm install` 会执行包的生命周期脚本 = **又一次任意代码执行**，且把授权点从「读配置时」挪到「装包时」，更难审计；③ 版本漂移无人能定位。**重开条件** = 用户明确要求离线一键装（且接受上述三笔）。
- **SSE 传输**：见 §5.5-1。
- **工作区级远程配置**：与 §4.4 ② 直接冲突，不讨论。
- **远程写盘追踪**：磁盘在远端，本机采集器结构上无解。
- **本地脚本文件选择器向导**（上一轮提的 P1）：与本方案无关，**也不消耗协议**（复用表单既有字段）。单列后续小刀，不并进本方案——并进来会让「远程」这个切片边界变模糊。
