# 方案 · 任务项边界产出时机前移（plan_item_boundary）

> 状态：已落地（2026-09-26）；自动化验证通过，待真机复验。
> 决策日期：2026-09-26
> 触发：真机观察「触发任务表后，step 没收进任务项折叠块；任务结束重渲染后看起来收进去了」。

---

## 一、问题：不是「运行时 vs 收尾」两处不一致

先打掉一个误判。宿主两条渲染路径共用同一个归组判据 `planItemContainerFor`：

- 运行时：`renderProcessFlow`（容器 = `.process-flow`）
- 收尾：`renderRoundBlock`（容器 = `.round-block__details`）

实测（临时探针，3 迭代 / 2 任务项 / 真实递增 `ts`）：

```
[迭代1末] 分组=0（边界还没到）
[流式]    分组=2  tool 组内 t2,t3 / 游离 t1   thought 2/1   narrate 1/0
[finalize] 分组=2  tool 组内 t2,t3 / 游离 t1   thought 2/1   narrate 1/0
```

**两路径逐字相同。** 不存在「运行时不收、收尾收」的机制差异。

真机观感之所以像「收尾才收进去」：运行时看到的是「开头一小块散在外面 + 折叠块刚冒出来还是空的」；
任务跑完折叠块里塞进了后续所有迭代，视觉上像收进去了。

## 二、根因：边界产在它本该罩住的内容之后

`AgentLoop` 的边界产出点在**本迭代工具落定之后**：

- 工具分支：`handleToolCalls` 返回后走 `_emitStepBoundary`，其内部先调 `_maybeEmitPlanItemBoundary()`；
- 无工具分支：`handleTextResponse` 前单独调一次 `_maybeEmitPlanItemBoundary()`。

宿主判据 `planItemContainerFor` 是 `b.ts < ts || (b.ts === ts && b.seq <= seq)` —— **只能向前找边界**。
边界在自己后面 → 找不到 → 回退顶层容器。

于是：**每个任务项的首个迭代（思考 + 首批工具）恒在折叠块外**，运行时与收尾都一样。

宿主侧还有个放大器：批块首次插入时即定位容器、之后只刷标题不搬家，
所以首个迭代的内容一旦落到顶层，边界来了也收不回去。

一句话：**边界的语义是「从这里开始属于任务项 X」，代码却把它放在了内容之后。这是 off-by-one，不是运行时 bug。**

## 三、不带伤判定（五类逐条）

| 伤类 | 方案 A 的表现 | 判定 |
|---|---|---|
| 双轨镜像 | 现状**两处**产出（无工具分支单独调 + `_emitStepBoundary` 内调）→ 收敛为**一处**（迭代开始） | 🟢 净减伤 |
| 降级兜底残留 | 现状边界产在内容**之后** → 每条边界都可能无内容：末尾那条边界之后已无事件，只剩标题的**空折叠块**；前移后边界必然罩住本迭代内容 | 🟢 净减伤 |
| 类型 hack | 无类型变更（`AgentChunk` 联合、payload 形状均不动） | 🟢 无伤 |
| 重复实现 | 无新增实现，只搬调用点 | 🟢 无伤 |
| 僵尸声明 | 两个方法都仍有消费；但**注释必须同步回扫**，否则留文档伤 | 🟡 有成本，必做 |

**结论：属不带伤方案，且是净减伤。**

同时消掉的隐性收益：宿主判据**不需要放宽**。
备选方案 B（宿主允许归入紧随其后的一条边界）是典型的「拿实现迁就显示」——
判据与内核语义对不上，会形成双判据。**否决。**

## 四、方案：产出点前移到「迭代开始、LLM 调用之前」

落点：`handleIteration` 内，`_handleInterrupt` 之后、`_prepareContext` 之前。

```
迭代开始
  ├─ _handleInterrupt            （挂起/中止在此返回，不产边界）
  ├─ _maybeEmitPlanItemBoundary  ← 新落点
  ├─ _prepareContext             （含任务表注入）
  ├─ LLM 调用 → thinking / thought
  └─ 工具执行 → narrate / tool_start / tool_result → step_boundary
```

### 为什么必须是「LLM 调用前」，而不是「LLM 调用后、工具前」

后者是 `onPlanItemBoundary`（写 planItemLog）所在的时刻。若把边界放那儿，
边界会插在本 step 的思考流**之后**、工具**之前** —— 把「本 step 的思考」和「本 step 的工具」
劈进两个任务项容器。虽然 `stepBoundary.test.ts` 的 STEP-BUCKET-1 断言（thought 区间内不夹边界）
仍会通过，但语义已错：思考应当和它驱动的工具同组。

放在 LLM 调用前，边界严格落在两个 step 之间，零劈裂风险。

### 可行性依据

`getActivePlanItemMeta` 读的是 `sessionManager.getCheckpoint()?.plan`（会话级真相源），
**任何时刻都可读**，不依赖迭代阶段。前移后首个迭代即可读到已存在的 active 任务项。

### 调用次数不变（不是新增开销）

原实现每迭代调一次（工具分支经 `_emitStepBoundary` 内调 / 无工具分支单独调），前移后仍是每迭代一次
（迭代开头调）。挂起/中止的迭代因 `_handleInterrupt` 提前 `return` 而不调——与原来一致。

**注意（防误述）**：**终态迭代仍会产边界**，旧实现同样会——工具分支里的
`_maybeEmitPlanItemBoundary()` 原本就是**无条件**调用，只有 `step_boundary` 才条件化。
本次改的是边界的**位置**（内容之前），不是有无。

### 同步删除

- 无工具分支里那次单独调用；
- `_emitStepBoundary` 内部对 `_maybeEmitPlanItemBoundary()` 的调用 —— 删掉后该方法
  只剩 `step_boundary`，**方法名与产出事件名从此同阵营**（既有一直强调的命名纪律）。

## 五、语义后果（诚实声明，不是缺陷）

任务表若是本轮第 k 次迭代的工具**新建**的，第 k 次迭代仍留在组外 ——
因为**那个时刻任务表还不存在**。这是正确语义：建表动作先于任务表本身。

方案 A 修的是「任务表在本轮开始前就已存在」的场景：
续会恢复、prepare 预置骨架、上一 turn 遗留、checkpoint 恢复。**这正是真机观察到的场景。**

## 七、验证

1. 变异验证：先加上述新断言 → 预期红（现状边界在工具之后）→ 再改实现 → 转绿。
2. 内核：`tsc --noEmit` + `eslint --max-warnings 0` + `vitest run`（`stepBoundary` / `metrics` / `loop` 相关）。
3. 宿主：类型未变，跑 `chatView.test.ts` 确认零回归（判据不动）。
4. 真机：带任务表的多迭代任务，确认首个迭代的思考与工具已进任务项折叠块，且无空折叠块。

## 八、回退

单点回退：把 `_maybeEmitPlanItemBoundary()` 调用挪回 `_emitStepBoundary` 内 + 无工具分支两处即可。
无数据迁移（边界事件形状未变，只是顺序变；旧落盘数据不含新序，回放仍按事件 `ts` 归组，不受影响）。

## 九、邻域缺口（已知，本次不改）

`lastBoundaryPlanItemId` 跨 turn 不重置 → 第 2 个 turn 及之后的 round 内
若无任务项推进，就没有边界事件 → 宿主该轮平铺、无任务项折叠块。

这是既有刻意设计（防同任务项重复分组），**不在本次范围**，不擅自扩大改动。
若后续真机确认「多 turn 续做同一任务项」是高频场景且平铺观感差，再单独立项。
