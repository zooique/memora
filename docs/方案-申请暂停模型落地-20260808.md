## 1. 任务表模型（概念）

- 任务表 = 以 loop 回合为单位的任务清单：**普通任务**（单轮闭环，默认）/ **难度任务**（单轮演化 loop 任务表逐条推进）。
- 渐进式：单轮问答是基础，loop 是自然叠加；**任务可实时追加**（本轮发现更复杂 → 追加条目，同一会话内多次演化 = 追加 + 重排 order，不创建多个任务表）。
- 简单轮无任务表 → 无暂停按钮（resumable 门控天然吻合）。
- **双通道原则**：任务表 = **LLM 可见的上下文**（LLM 可读写状态）+ **用户可操作的 UI**——对标 Claude Code TODO / Cursor plan mode / OpenAI Task。
- **SSOT 铁律**：任务表数据**唯一真理源 = `checkpoint.plan`**；LLM 注入版与 UI 展示版**同源渲染**（见 §1.5 环节 2），禁止任何第二份任务表数据。

## 1.5 任务表生命周期（四环节闭环，SSOT 收口）

**1. 生成（Phase 2.5，保守判定）**：
- LLM 复杂度判定——composer 补全链输出 `needsLoop: boolean`。`true` 时首次 `updatePlan` 写入（**首个生产调用点**）。
- **保守策略**：LLM 倾向于不生成任务表（needsLoop 默认 false，仅在明确多步需求时才 true）；误判规避——对标 Cursor plan mode（用户确认），memora 首版自动生成时通过 `SPRITE_STREAM_TOOL_START` 类 chunk 通知渲染层"正在生成任务"，面板出现时附带"接受/简化"入口（留口，首版自动接受）。
- **Phase 1 纯只读**：Phase 1 **不接入 LLM needsLoop 判定**——面板仅读取 checkpoint 已有 plan 数据；LLM 生成任务表留 Phase 2.5 单独评估。Phase 1 可用测试预置 plan 验证面板渲染。

**2. 注入（单一渲染函数）**：
- `renderTaskTable(plan, roundLog): string` 导出为**唯一渲染函数**——模块：`src/agent/taskTableRenderer.ts`（纯函数，与 sessionManager 解耦）。loop 组装上下文（任务表态 + roundLog 段）与 UI 面板 IPC `SESSION_GET_WORK_CONTEXT` 返回的渲染串**都调它**（SSOT：一处渲染逻辑）。注入段显式标注"状态/历史信息，非当前指令"防误执行。

**3. 推进（单一原子入口）**：
- `SessionManager.completeRound(stepId, outcome)`——**任务完成的唯一写点**：一次调用 = `plan.status='done'` + roundLog 追加 + heartbeat（原子）。
- `advancePlan` 由 loop 迭代边界驱动；追加任务 = `updatePlan` append + 重排 order。
- **多任务表场景**：同一会话内多次"简单→复杂"演化，追加到已有 plan（不创建第二份任务表），order 从头递增重排——保证 pauseBeforeOrder（见 §3）不因追加而产生语义偏移。

**4. 归档**：
- 会话 content 归档（`SessionArchiver`）扩展为**包含 plan 快照 + roundLog**（关键发现③缺口）——任务表随会话沉淀为记忆。

**接线影响**：`hasPendingPlan` 从恒 false 变真实——多轮任务 resumable 正确为 true，暂停按钮正确出现。

## 2. 交互语义 · 待定草稿区（SSOT：草稿区=唯一真理源）

**待定输入的真理源 = 草稿区列表（渲染层组件）**；输入框只是**编辑暂存**（发送时被消费，自身不是真理源）。

| 状态 | 输入框 → 按钮 | 行为 |
|---|---|---|
| RUNNING | 输入框 → **发送** | 立即注入：清空输入框，排队下一轮问答前 |
| PAUSED | 输入框 → **加入待定**（按钮文案改变，见 §3 矩阵） | 追加到草稿区列表（可自由增删/编辑/清空），输入框保留可继续编辑 |
| PAUSED | 草稿区 → **继续** | 批量提交：草稿合并 → `resumeExecution(合并内容)`；空草稿 → `resumeExecution(undefined)` 原路径 |

- **草稿计数反馈**：面板/按钮显示草稿条数徽标，点「加入待定」后立即可见。
- **停止按钮行为（P1 修复）**：点停止（CHAT_ABORT）→ **清空草稿区**（草稿与当前暂停态绑定，停止=重置）+ **任务表保留不丢失**（任务表是会话级数据，停止仅影响工作通道）。
- **停止后重启交互（盲区修复）**：停止→清空草稿→回 idle；重新发送新消息 = 全新对话轮次，草稿区为空，无残留。
- **与当前代码差异**：`inputAreaManager` paused 分支从"发送 → processEvent → 内核 auto-resume 注入"改为"发送 → 追加草稿区"。
- **分层契约**：内核 `processEvent` 的 PAUSED auto-resume **保留**（P4 澄清回答依赖）；sprite 改走"留草稿 + resumeExecution"是宿主 UI 策略——双入口并存。

## 3. 暂停语义统一 · 单一入口 + 可反悔（SSOT + 心智对齐）

**暂停唯一入口 = `SESSION_PAUSE`**，内部统一分发：

```
SESSION_PAUSE(reason):
  if 存在未推进任务（plan 有 pending）:
    setPauseBeforeOrder(下一 pending 任务的 order)  # 预约：当前回合结束即命中挂起
  else:
    requestPause()                                    # 无任务表/计划完成：回退即时申请
```

- **暂停点基于 order 而非 id（P1 修复）**：用户追加/删除任务 → order 重排 → 暂停点语义天然跟随（"停在 order=N 前"）。setPauseBeforeOrder(order: number)，loop 迭代边界检测 `getActiveStep().order === pauseBeforeOrder` → 命中挂起 + 清标记。避免基于 id 的方案在任务增删时出现 id 不存在或索引偏移。

| 场景 | 行为 |
|---|---|
| 运行中（任务 N 正在跑）点暂停 | 预约在下一 pending 任务前（当前回合完成即命中挂起） |
| 任务表某未推进任务前点暂停 | 同一入口参数化：`setPauseBeforeOrder(该任务 order)` |
| 暂停点命中 | loop 迭代边界检测命中 → 挂起 + 清标记 |
| 点「继续」 | **清暂停点（幂等）** + **`cancelPauseRequest()`（若申请中）** + 提交草稿区 → 继续推进 |
| 简单轮（无任务表） | 无暂停按钮（resumable=false 时 hide），只给停止 |

- **内核新增 `cancelPauseRequest()`**：清 `loop.pauseRequested`（申请暂停后、回合未结束前点继续 = 反悔取消）。**时序窗口（盲区修复）**：`handleIteration` 入口检查 pauseRequested——若 LLM 调用中 cancel，需等到下一迭代边界才生效。loop 迭代循环每轮开始时都重新检查（当前代码已实现，仅需确保 cancel 不遗漏）。
- **实现**：checkpoint 增 `pauseBeforeOrder?: number`；`SessionManager` 加 `setPauseBeforeOrder(order?)` / `getPauseBeforeOrder()`。

**按钮四态文案矩阵**：

| 状态 | 主按钮 | 副按钮 | 草稿区 |
|---|---|---|---|
| idle | 发送 | — | 隐藏 |
| RUNNING（可续跑） | 暂停（预约） | 停止 | 隐藏 |
| RUNNING（简单轮，resumable=false） | —（hide） | 停止 | 隐藏 |
| PAUSED | **继续**（确认草稿+推进） | 停止 | **可见：草稿列表 + 条数徽标 + 逐条删除** |
| PAUSED 输入后 | 主按钮文案变「**加入待定**」 | 停止 | 追加计数即时反馈 |
| 暂停申请中（回合未结束） | 继续（=取消申请+反悔） | 停止 | 待定 |

## 4. Phase 1 · 任务表面板（常驻可开合，纯只读）

**改动**：
1. **新 IPC `SESSION_GET_WORK_CONTEXT`**（chatHandlers.ts）：返回 `{ currentGoal, goalVersion, plan, mainGoal, pauseBeforeOrder, draftCount }`。复用 `getCheckpoint()`。

## 8. 风险与对抗式审查

- **⚠ 任务表接线面大**：plan 变活涉及 loop 边界 + 上下文组装 + hasPendingPlan 回归——**最小接线先行**（Phase 1 纯只读面板，advance/complete 留 Phase 2，LLM 生成留 Phase 2.5）。
- **⚠ 待定区语义迁移**：PAUSED 发送改「加入待定」+ 停止清空草稿——同步更新阶段 0 测试/文档（内核 auto-resume 保留为 API 契约勿删）。
- **⚠ SESSION_PAUSE 统一是行为变更**：现有测试断言 requestPause 直接调用需更新为 setPauseBeforeOrder/回退分支断言。
- **⚠ cancelPauseRequest 时序窗口**：LLM 调用中 cancel 需到下一迭代边界生效（handleIteration 入口每轮检查，当前代码已满足；loop.continueAfterPause 同路径）。
- **⚠ 复杂度守恒**：生命周期四环节全部复用 checkpoint/plan/SessionArchiver 管线，不新增 Manager/存储；completeRound/renderTaskTable 是收口非新抽象。
- **⚠ 双通道一致性**：注入版与 UI 版必须同源 `renderTaskTable`（`src/agent/taskTableRenderer.ts`），禁止两处独立渲染。
- **⚠ 暂停点 order 稳定性**：追加/删除任务时重排 order → 暂停点语义跟随（无漂移，SSOT：order 是唯一定位锚）。
- **已知搁置**：RESTORE_CHECKPOINT 断点续跑 UI、独立 WorkLoop 重构。

## 9. 执行顺序建议

Phase 1 纯只读面板 + 草稿区 + 按钮文案（含 SESSION_PAUSE 统一 + cancelPauseRequest）→ Phase 2 completeRound + 暂停点 order + 推进接线 → Phase 2.5 LLM 生成任务表 → Phase 3 归档扩展。每阶段独立提交（PowerShell，LEFTHOOK=0 门已验），不打 tag、推送由用户指示。
