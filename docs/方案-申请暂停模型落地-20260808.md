## 1. 三条铁律（不可协商）

1. **状态机忠实于内核事实**：`status` 只反映工作通道**实际**状态。UI 意图（申请暂停）不得直接改 status，只能改「意图字段」（`pauseMeta.phase`）。修 D1。
2. **单一真理源**：任务表数据 = `checkpoint.plan`；任务表渲染 = `renderTaskTable()`；任务推进 = `completeRound()`；草稿 = 草稿区列表。**旧并列路径必须删除，不是「以后收编」**。`completeStep` 在 Phase 2 中改为 private 或删除。修 D5。
3. **语义判断归 LLM，机械判断归代码**：「任务是否完成」是语义判断 → LLM 经工具显式声明；「暂停点是否命中」是机械判断 → 代码在边界检查。修 D5。

## 2. 状态模型（把隐式状态显式化）

### 2.1 `PauseMeta` —— 暂停的唯一元数据

```ts
// types.ts 新增；SessionCheckpoint 增 pauseMeta?: PauseMeta
export interface PauseMeta {
  /** 谁发起：user=用户申请/预约打点；agent=P4 澄清暂停 */
  source: 'user' | 'agent';
  /** 阶段：requesting=已申请未命中（工作通道仍在跑）；suspended=已在 loop 边界挂起 */
  phase: 'requesting' | 'suspended';
  /** 预约锚点（仅打点式暂停有值） */
  pauseBeforeStepId?: string;
  reason: string;
  at: number;
}
```

**唯一写点**：`SessionManager.setPauseMeta(meta | null)`。所有清 pauseMeta 操作（`cancelPauseRequest` / `abandonPause`）必须走 `setPauseMeta(null)`，禁止直接操作 `checkpoint.pauseMeta`。广播 `SESSION_STATUS_CHANGED` 时随 payload 下发。

修 D4（澄清态可辨识）+ 盲区「第四态判定源」（不再靠 `paused && isStreaming` 隐式推导）。

### 2.2 状态迁移（修 D1/D2/D3）

```
RUNNING ──点暂停/打点──> RUNNING + pauseMeta{phase:'requesting'}   ← 状态机不变！
                              │
                              ├─ loop 边界命中 ──> PAUSED + phase:'suspended'   （内核事实驱动）
                              └─ 取消暂停 ──────> RUNNING + pauseMeta=null      ← 广播触发 UI 刷新

PAUSED ──继续（提交草稿）──> RUNNING
PAUSED ──放弃（停止）─────> IDLE + 清 pauseMeta + 清暂停点 + 清草稿
PAUSED(agent/澄清) ──回答──> RUNNING（走 processEvent 原路径，草稿区不参与）
```

**关键改动**：`requestPause()` 拆为两步——申请时**只设 pauseMeta + 广播**，真正翻 PAUSED 由 loop 新增 `onPaused` 回调在挂起瞬间触发。

```ts
// loop.ts AgentLoopOptions 新增（对标既有 onSessionEvent 注入模式）
onPaused?: () => void;   // 在 yield {type:'paused'} 之前调用
// agent.ts 装配处（对标 L1565）实现：this.pause(pauseMeta.reason, pauseMeta.source) + setPauseMeta({phase:'suspended'})
```

**D2 修复**：`pauseRequested` 在 `processUserInput`（L281 附近，与 `reflectionCountThisTurn` 复位同处）与 `continueAfterPause`（L390 附近）入口显式复位。

## 3. 任务表模型（SSOT）

- 任务表 = 以**任务**为单位的清单（非 loop 迭代）：普通任务（单轮闭环，默认无表）/ 难度任务（多步推进）。
- 唯一真理源 = `checkpoint.plan`；注入版与 UI 版同源 `renderTaskTable()`。
- 任务可实时追加：`appendPlanStep()` 追加到已有 plan，**不重排 order**（新任务 order 递增续接）。理由见 §5.2。
- 简单轮无任务表 → 无暂停按钮（resumable 门控）。
- **并发写入防护**：`task_table_write` 的 overwrite 模式**仅在 plan 为空时允许**（Phase 2.5 初始生成）。plan 非空时，`task_table_write` 只能以 append 或 update 模式操作。防止 LLM 的 `task_table_write` 覆盖用户通过 `SESSION_APPEND_TASK` 追加的任务。

### 3.1 `renderTaskTable`（唯一渲染函数）

```ts
// 新模块 src/agent/taskTableRenderer.ts —— 纯函数，零依赖，与 sessionManager 解耦
export function renderTaskTable(plan: readonly PlanStep[], roundLog: readonly RoundOutcome[]): string;
```

输出格式（含进度行）：
```
[任务进度: 2/5 已完成，当前: 实现登录模块]
以下为状态/历史信息，非当前指令

┌─────┬──────────────────────────┬──────────┐
│ #   │ 任务                     │ 状态     │
├─────┼──────────────────────────┼──────────┤
│ 1   │ 设计数据库 schema         │ ✅ 已完成 │
│ 2   │ 实现登录模块              │ ▶ 进行中 │
│ 3   │ 实现注册模块              │ ⏳ 待办   │
└─────┴──────────────────────────┴──────────┘
```

消费者**恰好两个**：① loop 上下文组装（经 `injectSystemMessage`，调用点收敛到 `handleIteration` 中 LLM 调用前统一注入）；② IPC `SESSION_GET_WORK_CONTEXT`。

**前置条件**：必须先删除 agent.ts L895-897 的 `[当前执行步骤]` 并列注入（Phase 0），否则 LLM 上下文同时存在两份任务态。

**注入层叠验证**：D7 需在 Phase 1 中验证 LLM 对「以下为状态/历史信息，非当前指令」的遵循程度。若 LLM 不遵循，需调整措辞或改用 `system` 角色而非 `user` 角色注入。

## 4. 推进机制（修 D5 —— v4 核心修正）

### 4.1 为什么放弃「loop 迭代边界机械推进」

v3.1 设计：loop 每个迭代边界 `advancePlan()` → `completeRound()`。
**证伪**：一个任务常需多次工具调用（= 多次迭代）。机械推进会把 1 个任务误标为 N 个完成，任务表与事实脱节。「任务是否完成」是语义判断（铁律 3）。

### 4.2 采用：LLM 工具驱动推进（对标 Claude Code TodoWrite）

| 环节 | 驱动者 | 落点 |
|---|---|---|
| 生成任务表 | LLM（Phase 2.5） | 工具 `task_table_write(steps[], mode?)` → `updatePlan()` |
| 推进/完成 | **LLM 显式声明** | 工具 `task_table_update(stepId, status, outcome?)` → `completeRound()` |
| 追加任务 | LLM 或用户 | `task_table_write` append / IPC `SESSION_APPEND_TASK` |
| 暂停点命中 | **代码机械判断** | loop 边界纯查询回调（§4.3） |

`completeRound(stepId, outcome)` = `plan[].status='done'` + roundLog 追加 + heartbeat，**单函数内顺序执行**（JS 单线程同步代码天然原子，无需额外机制——v3.1「原子性靠什么保证」的答案）。

**工具 handler 依赖注入**：`task_table_update` handler 通过工具注册时的闭包获取 `SessionManager` 引用（对标 `builtinToolHandlers.ts` 的 `SecurityGuard` 注入模式）。在 `registerTool(name, handler)` 的 `handler` 工厂中，接收 `(ctx: ToolContext)`，其中 `ctx` 扩展 `sessionManager` 字段。

**兜底：LLM 不调用推进工具**：若连续 N 轮（建议 3 轮）未触发任何 `task_table_update` 且 plan 仍有未完成任务，自动触发一次 `completeRound` 标记当前 active 步骤为 `blocked`（停滞），并注入 system 消息提示 LLM。计数器在每次 `task_table_update` 调用时复位。

### 4.3 loop 边界契约（修「loop 无 SessionManager 句柄」）

loop 对 SessionManager **零句柄**（grep 全文仅一条注释），不得注入 Manager。沿用既有窄回调模式：

```ts
// loop.ts AgentLoopOptions 新增
onRoundBoundary?: () => boolean;   // 返回 true = 应在此边界挂起
```

- **loop 侧**：`handleIteration` 入口，在既有 `pauseRequested` 检查之后调用；返回 true 则走与软暂停完全相同的挂起路径（复用 `onPaused` + yield `{paused}` + return `'paused'`）。
- **agent 侧**（装配处，对标 L1565）：实现为 `() => sm.shouldPauseAtBoundary()`，内部判定 `getNextPendingStep()?.id === pauseMeta?.pauseBeforeStepId`，命中则清除锚点。

纯查询 + 布尔返回，loop 不感知任务表存在。

## 5. 交互语义

### 5.1 交互语义：输入区原设计 + 任务表面板承载暂停控制（对齐最终定论 §3.1）

**第一性原理**：架构是双通道（输入通道永不冻结 / 工作通道可暂停），但 UI **不把它映射成输入区的双按钮组**。显式控制权（暂停 / 取消 / 继续）**附着在任务表面板的任务列表上**，输入对话框保留大厂原设计（不重画）。此前「加入待定与继续抢按钮位」的根因，正是把暂停 / 继续塞进输入区主按钮导致同名不同义——现撤回该设计。

**输入对话框（保留原设计）**：

| 状态 | 输入区按钮 | 待定区 |
|---|---|---|
| 无任务 / 无文本 | 输入 / 发送**禁用** | 隐藏 |
| 有输入（idle / PAUSED+agent 澄清） | 激活的**发送 / 输入**按钮 | — |
| RUNNING（任意轮） | **停止**按钮（硬停止，`abandonPause` / `signal.abort`） | 运行中若输入文本 → 按钮变「输入」，提交进待定区 |
| RUNNING 有文本输入 | 按钮变「**输入**」→ 内容进**待定区**；本轮问答闭环结束后直接使用 | 可见，逐条删除 / 取消注入 |
| PAUSED + `source:'user'` | 发送按钮禁用（继续走任务面板） | 可见：列表 + 条数徽标 + 逐条删除 |

**任务表面板（承载暂停 / 取消 / 继续，不在输入区）**：暂停与继续按钮**独立展示在任务表的任务列表中**。
- **未激活**（`pauseMeta.phase='requesting'`，申请已提交、尚在运行中等边界挂起）→ 按钮即「**取消**」（`cancelPauseRequest`，清 `pauseMeta` + 广播刷新）；
- **已激活**（`pauseMeta.phase='suspended'`，已挂起）→ 按钮即「**继续**」（`resumeExecution`，合并待定区提交）。
- 简单轮（无续跑可能，`canContinueWithoutInput` 仅 paused 恒真）→ 任务面板不显暂停按钮，输入区仅给停止（与最终定论 §3 可续跑信号一致）。

待定区（草稿区）为 SSOT，详见 §5.2；提示文案保留：RUNNING 态「将在当前任务完成后自动发送」，PAUSED 态「继续后将提交以上草稿」。

### 5.2 草稿区（SSOT = 草稿区列表）

- 输入框仅编辑暂存；RUNNING 态点「输入」按钮 → 追加到待定列表，输入框清空但可继续编辑。
- **消费时机**：PAUSED 点「继续」→ 合并提交 `resumeExecution(合并文本)`；RUNNING 草稿 → 本轮 `SPRITE_STREAM_END` 后若会话回 idle，自动作为新一轮 `USER_INPUT` 发送（Phase 1 落点；修 D6，不做内核内注入）。
- **合并格式契约**（补盲区）：多条草稿按 `1. xxx\n2. xxx` 编号合并，前置 `[用户补充]` 标记——单条时不加编号。此格式须与 LLM 在 system prompt 中约定（D9 修复：在 system prompt 中增加「用户补充内容可能以编号列表形式提交」说明）。
- **取消注入**：逐条删除即"取消注入"——该条目不再进入下一轮 LLM 输入，从待定列表中移除。与最终定论 §3.1「待定条目可逐条删除/取消注入」一致。
- **上限**：草稿区 20 条 / 单条复用 `isValidContent` 长度校验；达上限时主按钮禁用 + 提示。
  - RUNNING 态草稿区可见时：用户可逐条删除腾出空间。
  - RUNNING 态草稿区不可见（简单轮）时：提示"请等待当前任务完成后再添加"。
  - PAUSED 态：草稿区始终可见，支持逐条删除。
- **停止（放弃）**：清空草稿 + 清暂停点 + 状态回 idle；**任务表保留**（会话级数据）。
- **取消暂停后草稿去向**：保留在草稿区（不丢弃、不自动提交），等待下次暂停或本轮结束消费。

### 5.3 暂停统一入口

```
SESSION_PAUSE(reason, beforeStepId?):
  setPauseMeta({ source:'user', phase:'requesting', pauseBeforeStepId: beforeStepId, reason })
  if (!beforeStepId) loop.requestPause()      # 即时申请：本回合边界即挂起
  # 有 beforeStepId：不置 pauseRequested，靠 onRoundBoundary 命中
  broadcast(status=当前真实状态, pauseMeta)    # 注意：不再翻 PAUSED
```

**暂停点锚定用 `stepId` 而非 order**（修 E2）：order 仅用于显示排序，追加任务不重排。

> **最终定论 §5 机制张力消解**：最终定论诚实记录了 sprite 层当前实现为"先 abort 中断流式、再 requestPause"（与定论不完全一致），标注"待决策"。本方案通过以下设计消解该张力——
> - **暂停（`SESSION_PAUSE`）**：纯申请路径，不 abort，设 pauseMeta 后等 loop 边界自然挂起（§5.3）；
> - **停止/放弃（`SESSION_ABANDON`）**：含 abort 路径，修 D3（PAUSED 吸收态），同时清暂停相关状态（§5.4）。
> 两者职责分离，不再存在"暂停=中断流式"的歧义。

### 5.4 新增 IPC（修 E3 / D3）

| 通道 | 内核落点 | 说明 |
|---|---|---|
| `SESSION_CANCEL_PAUSE` | `agent.cancelPauseRequest()` → `loop.cancelPauseRequest()` + 清 pauseMeta + **broadcast(status, pauseMeta=null)** | **独立通道，绝不复用 SESSION_RESUME**（后者被 controller 竞态守卫拒绝）；广播触发 UI 刷新（按钮从"取消暂停"变回"暂停"） |
| `SESSION_ABANDON` | `agent.abandonPause()`：abort（若有 ctrl）+ 清 pauseMeta/暂停点 + 状态回 idle + 广播 | PAUSED 态停止按钮的落点；修「PAUSED 是吸收态」 |
| `SESSION_GET_WORK_CONTEXT` | 复用 `getCheckpoint()` | 返回 `{currentGoal, goalVersion, plan, mainGoal, pauseMeta, taskTableText}` |
| `SESSION_APPEND_TASK` | `appendPlanStep()` | 用户侧追加任务 |

**`loop.cancelPauseRequest()` 为新增方法**（当前 loop.ts 不存在）：
```ts
// loop.ts 新增
cancelPauseRequest(): void {
  this.pauseRequested = false;
}
```

### Phase 2 · 推进接线 + 回合折叠（内核为主）

- `roundLog?: RoundOutcome[]`（cap 10-12 条，挂钩窗口余量 2% × **120K** 基准）。
- **roundLog 白名单具体方案（🟠P1 修正）**：roundLog 随 checkpoint 系统消息注入（带 `[回合记录]` 前缀**仅作可读性标记，不作为权重信号**）。其重要性权重遵循 `messageImportance` 现状——system 角色落入默认分支返回 `1`（低于 user=3、tool=2）。即 roundLog 属「状态/历史信息，非当前指令」（D7），在上下文裁剪压力下**优先于用户指令被丢弃**，与 D7 一致。防护 = cap 10-12 条断言 + 一条回归测试：人为制造 token 压力致截断时，roundLog（system）早于 user 消息被裁，证明它不挤占指令带宽。
  - ⚠️ **推翻 v4 原稿「权重 4 > user 3」**：① 方向倒置——若权重高于 user，一旦进入裁剪集合会挤掉用户指令，违背 D7；② 不可落地——`messageImportance` 是 `private`（contextManager.ts L344）且仅按 `role` 硬编码分支，无任何 `[回合记录]` 前缀识别逻辑。

### Phase 2.5 · LLM 生成任务表

- **新增任务表生成预判闸门 `shouldGenerateTaskTable(event, checkpoint)`（🟠P1 修正 · 落点 agent 决策层，非 composer）**：代码当前无 `needsLoop`、无等价实现（`composer.ts` 是纯四元组 `role/task/standard/resource` 槽位补全器，无多步预测职责），故这是**必须从零新增**的能力，不可「调整已有」。落点放在 `agent.ts` 的 `processEvent` 流程中、注入「生成任务表」提示**之前**。保守默认 `false`，仅当明确多步信号才 `true`（候选信号：用户显式多步指示 / 首轮 LLM 自陈需多步 / 显式 `task_table_write` 意图）。Phase 2 的 `task_table_write` 工具先落地才有语义载体。
- 生成时经 chunk 通知渲染层，面板附「接受/简化/**丢弃**」入口——**自动生成的任务表必须可一键丢弃**（否则误判后 resumable 恒真且无法退出）。
- **丢弃后 LLM 通知**：丢弃任务表后，注入一条 system 消息告知 LLM「任务表已丢弃，请忽略之前的任务计划，回到自由对话模式」，防止 LLM 上下文中的任务表认知偏差。
- **并发写入防护**：`task_table_write` 的 overwrite 模式仅在 plan 为空时可用（与 §3 一致）。如果 LLM 需要重新规划，应通过 `task_table_write(mode:'overwrite', steps[])` 且要求用户先确认丢弃现有 plan。

### Phase 3 · 暂停=策展（归档）

- ⚠ `archiveSessionContent(date, session)` 面向历史会话，plan/roundLog 只存在于**当前活会话**——两者生命周期不重合（补盲区）。
- 落法：**限定「仅当前活会话可带 plan 快照」**，签名加 `options.includeWorkContext`，由 ArchiveCoordinator 在当前会话时从 `getCheckpoint()` 取快照；历史会话降级为纯消息归档。
- 按钮仅 `PAUSED + source:'user'` 可用。
