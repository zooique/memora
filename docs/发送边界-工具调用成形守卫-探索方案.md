# 发送边界 · 工具调用成形守卫（探索方案）

## 0. 一句话

把「发往 LLM 服务端的 tool_call 批次必须成形」这一不变量，从**散点补丁 + 服务端 400 兜底**，收敛为**发送边界一道确定性守卫（fail-fast + 精确诊断）**——坏批次在本地被拦下、被如实报出，而不是被服务端 400 整轮掐断、白烧 token。

> 本版（2026-09-15 · 拍板收窄）：**只做「守卫 + 诊断」，不做「自纠回喂」。** 理由见 §3.4。

## 1. 背景与要解决的真问题

### 1.1 同一个病，四个破口

内核与 OpenAI 兼容服务端对话时，服务端对工具调用批次极严格（逐条配对、名字合法、id 唯一），任一不满足即 400 掐断整轮。一天内四破口被连续撞出，**同属一条不变量**「assistant.tool_calls 必须成形」：

| 破口 | 症状 | 当前处置 |
|---|---|---|
| FAIL-1 | 空 name/空 args 幻影条目 | 构造期丢弃（llmCaller 唯一进入点） |
| G1 | ask 同批非 ask 调用缺配对结果 | 占位 `[ASK_SUSPENDED]` 闭合 |
| G2 | name >64 字符 | 判据并入长度上界 |
| G3 | 缺 id 回退 `call_<idx>` 跨批重复 | 实例自增唯一化 |

**现状：散点补丁，无统一关卡。** 每处各挡各的，最后兜底仍是「服务端骂回 400」，而那一骂 = 整轮崩、几十万 token 白烧（FAIL-1 故障轮即 12 次调用累计 18 万 tokenIn 后中 turn 死亡）。散点一旦漏（未来新破口），又回到「莫名 400、中 turn 中断、用户无从诊断」。

### 1.2 哲学张力与裁决（SSOT 视角）

初版方案想加「回喂自纠」让模型自改。**拍板时被 SSOT 砍掉**，理由：

- 当前散点已**按构造正确**保证这条不变量（写历史前过滤、占位闭合、id 唯一化）+ 测试助手 `expectWellFormedToolPairing` 双向守护 → **发送边界审计在健康态「永不触发」**。
- 因此审计一旦命中 = **某个散点回归 = 内核 bug**，绝不是"模型偶尔手滑"。
- 若做「自纠回喂」，会把**内核 bug 伪装成模型偶发失误、被静默自愈**——掩盖根因、降低诊断信噪比，正违 memora 的带伤审查文化（异常路径诚实暴露，不用恢复通道掩盖），且凭空新增一条「审计→自纠→再发送」状态链路（违 SSOT「不预支复杂度」）。

**结论：要的是一道 fail-fast 守卫，不是一条恢复通道。** 命中 = 宁愿响亮失败、给出精确诊断，也不要装"反正能自纠"。

## 3. 方案设计（不带伤 · fail-fast）

### 3.0 设计原则

1. **单一真理源**：不变量谓词只写一处（生产纯函数），测试断言从它派生（薄壳），杜绝「断言口径 ≠ 实现」复发。
2. **零新机制、零新状态**：守卫为纯函数；命中走既有收场（logger + 不发送），不造重试/旋钮/状态链路。
3. **发送边界唯一进入点**：挂 `llmCaller.ts`（FAIL-1 已立 SSOT 进入点），**不碰 `formatMessages`**——守 FAIL-1 否决与「掩盖」语义。
4. **诚实、fail-fast**：命中即响亮诊断（不静默、不自愈），把「服务端 400 莫名整车废」转成「本地可控、可诊断、token 不浪费的拒绝」。

### 3.1 单一谓词（SSOT，把测试助手提升为生产单源）

新增生产纯函数 `auditToolCallPairing`——**落 `src/agent/managers/toolCallHelpers.ts`**（与名字 SSOT `isCallableToolName`/`TOOL_NAME_MAX_LENGTH` **同模块**）：复用同源长度常量、避免新建生产文件造成 README 生产数漂移、与既有「工具调用形状纯函数面」自然共处。代码如下：[toolCallHelpers.ts `auditToolCallPairing`](../src/agent/managers/toolCallHelpers.ts)。

```ts
/** 违规之一：只读、无状态，逐一携带「id + 违反的约束」用于精确诊断 */
type PairingViolation =
  | { kind: 'unpairedAssistantCall'; toolCallId: string }  // 有调用无结果
  | { kind: 'orphanToolMessage'; toolCallId: string }      // 有结果无调用
  | { kind: 'emptyName'; toolCallId: string }
  | { kind: 'nameTooLong'; toolCallId: string; length: number }  // 超 TOOL_NAME_MAX_LENGTH
  | { kind: 'duplicateId'; toolCallId: string };

export function auditToolCallPairing(
  messages: readonly { role: string; toolCalls?: readonly { id: string; function: { name: string } }[]; toolCallId?: string }[],
): PairingViolation[];
```

**SSOT 落法**：现有测试助手 `expectWellFormedToolPairing`（`src/agent/__tests__/toolCallPairing.ts`）改为**两行薄壳**——调用本谓词、`violations.length>0` 则报错并列出违规（附带**具体约束文案**，如「工具名长度 65 超服务端上界 64」）。实现判据与测试断言同源。长度上界 `TOOL_NAME_MAX_LENGTH` 复用 `toolCallHelpers`，不重复声明。

### 3.2 检测点 = 发送边界（唯一进入点，fail-fast）

在 `llmCaller.ts` **现有 FAIL-1 过滤之后、`provider.chat()` 之前**，对要发出的**整批历史消息**跑 `auditToolCallPairing`：

- **通过** → 正常发（健康态零成本：散点已构造正确，循环 O(1)）。
- **命中** → **不调用 `provider.chat()`**：`logger.error`（带全部违规明细，逐条 `id + 违反的约束`），返回失败让 loop 走既有收场。**绝不让坏批次上线路**。

命中 = 散点 bug 的信号，就是要它**响亮、可定位**：开发者在日志里一眼看到「哪条 id、违反哪条约束」，而不是猜"服务端为什么又 400"。token 在这一轮前已止损。

### 3.3 不做的部分（明确划出，防泄漏）

- ❌ **不做自纠回喂**：不注入 corrective tool 结果、不重发、不造「审计→自纠→再发」状态链路。命中 = bug，recover 会掩盖根因。
- ❌ **不加重试上限旋钮**：复用既有 `maxIterations`/`stepBudget` 收场，不新增独立"auditRetryN"。
- ❌ **不进 `formatMessages`**：守卫与收场都在 `llmCaller`/loop 层，映射层保持纯映射（守 FAIL-1 裁决）。

### 3.4 与 FAIL-1 否决的对抗论证

> 判别题：这是「映射层静默过滤」（违 FAIL-1），还是「发送边界确定性守卫」（本方案）？

| 维度 | FAIL-1 否决的（映射层静默过滤） | 本方案（发送边界守卫） |
|---|---|---|
| 落点 | `formatMessages` / 映射层 | `llmCaller`（已立 SSOT 进入点） |
| 动作 | **静默丢弃**坏条目 | **拦截 + logger.error 精确违规** |
| 对模型可见性 | 不可见（掩盖） | Fail-fast（不掩盖，直接收场报错） |
| 副作用 | 偷偷丢「本想调用」的意图 | 不发 + 止损；意图不静默丢（构造期本就不会产生坏意图） |
| 状态 | — | 纯函数 + 既有收场，零新状态 |

**一句话**：FAIL-1 否的是「把配对语义塞进映射层偷偷过滤」；本方案在**发送边界**做**确定性守卫 + 响亮诊断**——是网，不是创可贴，更不是掩盖；触发即为一等公民的 bug 信号。

### 3.5 可判定验收

- **健康态零触发**：全量测试下守卫恒 `ok`（散点已保证）——断言证明「持久态不假红」。
- **变异红**：人为去掉某散点保护 → 守卫返回对应 violation，测试红，且失败输出即**具体违规文案**（如 `expected [] to contain [{kind:'unpairedAssistantCall',...}]`）。
- **不发坏批次**：任一违规命中时 `provider.chat()` 计数为 0（mock 断言）。
- **fail-fast 有界**：命中即收场（走既有收场路径），无新死循环。

## 4. 落地路径（顺序不可换）

- **Step 1（硬化准绳 · 零行为变更）**：新增 `auditToolCallPairing` 生产纯函数 + 单元测试（五种违规，**变异验证**）；测试助手改薄壳指向它（**SSOT 闭合**）。此步不改任何发送路径。
- **Step 2（挂守卫）✅ 已落（2026-09-15）**：在 `llmCaller` 发送前置（重试循环前）挂 `const violations = auditToolCallPairing(safeMessages); if(len) { metrics.llmPairingGuardFires++; logger.error(违规明细); throw 守卫错误; }`——**绝不上线路**；守卫恒定性由 Step 1 测试断言证明（无需生产灰度期——无自纠通道，就不存在"偶尔假阳性要不要放行"的分裂态；假阳性=散点 bug，正该失败）。新增守卫单测 2（畸形→拒发抛错/provider.chat 零调用/计数+1；健康→照发/计数 0）。**上线即抓到真阳性**：`maxIterations` 用例原 fixture `Array(5).fill(toolCall)` 在单响应塞 5 个同 id 畸形批次，被守卫正确拦截（真阳性）→ 修正 fixture 为单条 tool call（跨迭代复用 id 属跨消息、守卫不判），保留「逼迭代上限」本意。全量 **3039 passed**。
- **Step 3（真机复验）✅ 已落（2026-09-15）**：`scripts/test-pairing-guard-real.ts` 真实模型（mimo-v2.5）复验——真实模型发起 `read_file`（path 正确）→ 内核执行并配对 → 第 2 次 LLM 调用真实重发 → 服务端**接受（无 400）**、工具 0 失败、5 判据全过、守卫**未抛**（健康态真零触发）。证明 mock 恒绿并非无条件——真实模型 + 真实服务端校验下守卫零假阳性。**收口**：三步全落且被生产（`llmCaller`）真实消费，满足固化触发；**2026-09-15 用户拍板维持探索、暂不写 ADR**（待后续真实触发再定案）。

## 5. 不作为 / 风险自检

- **不为常态路径设计**：守卫是「网」，健康态不该触发；若常态化触发 = 散点系统性漏 = 当新破口根治，**不是**把它当主路径。
- **不自造恢复通道**：命中即 fail-fast 收场，不含"自纠重试"（防掩盖根因 + 防"审计→自纠→再触发"隐性死循环）。
- **不碰 `formatMessages`**（守 FAIL-1 裁决）；**不新增旋钮/状态**（复用既有收场）。
- **文档/计数**：谓词落已有的 `managers/toolCallHelpers.ts`（**不新增生产文件**，README 生产数无漂移）；`__tests__/toolCallPairing.ts` 仍测试辅助（已在「排除整目录」口径内）。
