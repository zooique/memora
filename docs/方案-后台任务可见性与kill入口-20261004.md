# 后台任务可见性与 kill 入口（CMD-1 阶段 2 缺口清偿）

> **来源**：2026-10-04 落地质量审查 → CMD-1 半截工程。CHANGELOG 自陈「未做：后台任务**运行态列表**（UI 零可见）、无用户侧 `kill_command` 入口」。
> **纪律**：设计决策先文档化为闭合闭环，再开始代码实现。本文件是实施规格真源。

---

## 一、缺口实锤（排雷，非推断）

| 项 | 证据 | 结论 |
| --- | --- | --- |
| 内核零导出 | `grep -n "BackgroundTask\|reapAll" src/index.ts` → **0 命中** | 宿主拿不到后台任务数据 |
| 注册表能力已齐 | `src/agent/backgroundTasks.ts`：已有 `list()` / `get(taskId)` / `kill(taskId)` / `reapAll()`，且 `list()` 返回**只读投影**（`projection()` 剥掉 `killNow`/`peek` 句柄，不泄漏进程） | **不是缺实现，是缺出口** |
| 宿主消费面只有 1 类 | `hosts/memora-vscode/src` 含 `background_report` 仅 `chatPanel.ts` / `chatView.ts` / 测试三处，全在渲染**收尾报告** | 运行态对用户零可见 |
| kill 无 UI 入口 | 宿主 `grep kill_command` 只命中 `toolNameMap.ts`（中文名）+ `chatView.ts`（叙述）+ 测试 | 用户看不见、砍不了；只有**模型**能砍 |

**根因判词**：这不是「宿主没画 UI」，是**数据通道不存在**。先把出口开出来，UI 才是可选项而非空中楼阁。

**刻意不做（防过度设计）**：不做事件流镜像。`BackgroundTaskRegistry.setCompletionListener` 是**单点 setter** 且已被 loop 占用（回流队列）；若让宿主另起一份镜像表 = 第二真理源，两侧漂移。宿主只做**只读拉取**。

## 二、设计定案

### 2.1 内核侧：开两个只读/委托出口（公共面 +2）

| 新增 | 位置 | 形态 | 说明 |
| --- | --- | --- | --- |
| `listBackgroundTasks()` | `agent.ts` 门面 | `(): readonly BackgroundTask[]` | 委托 `loop.getBackgroundTasks()` → `registry.list() ?? []`。**纯读**，零行为变化 |
| `killBackgroundTask(taskId)` | `agent.ts` 门面 | `(taskId: string) => BackgroundTask \| null` | 委托 `registry.kill()`，返回终态投影（任务不存在 → `null`）。**零新逻辑** |
| 类型导出 | `src/index.ts` | `BackgroundTask` / `BackgroundTaskStatus` | 只读投影类型，无进程句柄字段 |

**为何是委托而非新逻辑**：`BackgroundTaskRegistry` 已把「身份 / 生命周期 / 投影」收为单点（`backgroundTasks.ts` 文件头注释即此定案）。门面只做**透传**，不复制任何判据——复制即第二真理源。

**为何挂 Agent 而非直接导出 registry 类**：registry 是**实例**且必须按 Agent 实例隔离（文件头注释：单例会让 `kill_command` 杀掉别的会话起的进程）。导出类 = 把实例化权交给宿主 = 破坏隔离不变量。只导出**方法**，宿主无从碰实例。

**未初始化语义**：与既有门面同构——`assertInitialized` 早退，返回空数组 / `null`，不抛。

### 2.2 宿主侧：协议 +2 通道（105 → 107）

| 通道 | 方向 | 载荷 | 说明 |
| --- | --- | --- | --- |
| `background_tasks` | 下行 | `{ items: BackgroundTaskView[] }` | 快照推送；`BackgroundTaskView` = `{ taskId, command, startedAt, status }`（**不含 `result`**——输出体量大，UI 不呈现，避免无谓搬运） |
| `background_kill` | 上行 | `{ taskId: string }` | 用户点 kill → extension 调 `agent.killBackgroundTask()` → 回推一次快照 |

通道数 105 → 107，远低于 130 治理阈值（`protocolGuard.test.ts`）。

### 2.3 UI 形态：StatusDock chip + 浮层（**待用户拍板**）

- **入口**：沿用既有 `status-dock__chip` 机制（`chatView.ts:2533`），新增「后台 N」chip
- **可见性**：**仅当 N > 0 时显示**（无后台任务时零占用，不制造常驻噪音）
- **浮层**：点击展开列表，每行 = 命令原文 + 状态标签 + 「终止」按钮（终态行无按钮）
- **状态词表**：复用内核 `STATUS_LABELS`（运行中 / 已完成 / 超时被终止 / 已终止）——**宿主不自建词表**，防双源漂移（同 `CompressTarget` 标签表定案）

### 2.4 刷新时机

候选：

| 方案 | 机制 | 代价 | 评价 |
| --- | --- | --- | --- |
| A · 条件轮询 | 仅当存在 `running` 任务时按 1s 拉取，全部终态即停 | 一个 `setInterval`，需生命周期管理（dispose 不当即泄漏） | 简单但引入常驻定时器 |
| B · 内核事件回调 | 内核新增「状态变化」回调给宿主 | 改 `setCompletionListener` 单点 setter 为多播，公共面再 +1 | 精确但侵入内核既有定案，**否决** |
| C · 只在收尾报告时更新 | 复用 `background_report` | 运行态仍不可见 = 没解决缺口 | **否决** |
| **D · 宿主侧事件点推送（**实施采纳**）** | 在宿主**已有**的两个事件点推送：`background_report` 到达（终态批量变化）+ `background_kill` 处理后强制回推 | 零定时器、零生命周期负担 | 简单性最优（why not simpler） |

**实施修订（2026-10-04，刀 2 落地时）**：原定案 A，实施时发现 D 更简——宿主本就有
`background_report` 消费点（收尾报告），顺带推一次快照即可覆盖「终态变化」；
kill 后强制回推覆盖「用户主动终止」。**无定时器即无泄漏面**，内核零感知。

⚠️ **D 的已知缺口（随刀 3 处理）**：后台任务**刚启动**时无推送点（启动发生在
`run_command` 工具执行路径，宿主尚未在工具事件上挂推送）⇒ 浮层要等第一个
`background_report` 才出现。刀 3（webview UI）时在工具叙述落点补一次推送，
或改由 tool 事件驱动——到时按「触发驱动」再定，本刀不做预支设计。

## 四、验收口径

- 内核：`tsc --noEmit` 0 + `eslint --max-warnings 0` + 新增用例全绿 + **变异验证**（委托去掉 → 对应用例转红）
- 宿主：`tsc --noEmit` 0（须先重建内核 dist）+ 协议守卫通道数 107 < 130
- 真机：`npm run compile` 重建宿主 dist 后，起一个长后台命令 → dock 出现「后台 1」→ 点开可见 → 点「终止」→ 状态转「已终止」

## 五、刻意不做

- 后台任务**输出内容**在 UI 呈现（体量大，且 `kill_command` 已把输出交给模型）
- 跨会话 / 跨 Agent 的后台任务管理（注册表按实例隔离是硬不变量）
- 后台任务运行时长、进度百分比（内核不持有进度语义，编造即说谎）
- 命令前缀 allow 白名单、`.ps1` 运行时档（CMD-1 阶段 2 的另两项，独立立项）
