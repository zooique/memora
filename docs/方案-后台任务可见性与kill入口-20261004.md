# 后台任务可见性与 kill 入口（CMD-1 阶段 2 缺口清偿）

> **来源**：2026-10-04 落地质量审查 → CMD-1 半截工程。CHANGELOG 自陈「未做：后台任务**运行态列表**（UI 零可见）、无用户侧 `kill_command` 入口」。
> **纪律**：设计决策先文档化为闭合闭环，再开始代码实现。本文件是实施规格真源。

---

## 一、缺口实锤（排雷，非推断）

| 项 | 证据 | 结论 |
| --- | --- | --- |
| 内核零导出 | `grep -n "BackgroundTask\|reapAll" src/index.ts` → **0 命中** | 宿主拿不到后台任务数据 |
| 注册表能力已齐 | `src/agent/backgroundTasks.ts`：已有 `list()` / `get(taskId)` / `kill(taskId)` / `reapAll()`，且 `list()` 返回**只读投影**（`projection()` 剥掉 `killNow`/`peek` 句柄，不泄漏进程） | **不是缺实现，是缺出口** |
| 宿主消费面只有 1 类 | `hosts/memora-vscode/src` 含 `background_report` 仅 `chatPanel.ts` / `chatView.ts` / 测试三处，全在渲染**收尾报告** | 运行态对用户零可见 |
| kill 无 UI 入口 | 宿主 `grep kill_command` 只命中 `toolNameMap.ts`（中文名）+ `chatView.ts`（叙述）+ 测试 | 用户看不见、砍不了；只有**模型**能砍 |

**根因判词**：这不是「宿主没画 UI」，是**数据通道不存在**。先把出口开出来，UI 才是可选项而非空中楼阁。

**刻意不做（防过度设计）**：不做事件流镜像。`BackgroundTaskRegistry.setCompletionListener` 是**单点 setter** 且已被 loop 占用（回流队列）；若让宿主另起一份镜像表 = 第二真理源，两侧漂移。宿主只做**只读拉取**。

## 二、设计定案

### 2.1 内核侧：开两个只读/委托出口（公共面 +2）

| 新增 | 位置 | 形态 | 说明 |
| --- | --- | --- | --- |
| `listBackgroundTasks()` | `agent.ts` 门面 | `(): readonly BackgroundTask[]` | 委托 `loop.getBackgroundTasks()` → `registry.list() ?? []`。**纯读**，零行为变化 |
| `killBackgroundTask(taskId)` | `agent.ts` 门面 | `(taskId: string) => BackgroundTask \| null` | 委托 `registry.kill()`，返回终态投影（任务不存在 → `null`）。**零新逻辑** |
| 类型导出 | `src/index.ts` | `BackgroundTask` / `BackgroundTaskStatus` | 只读投影类型，无进程句柄字段 |

**为何是委托而非新逻辑**：`BackgroundTaskRegistry` 已把「身份 / 生命周期 / 投影」收为单点（`backgroundTasks.ts` 文件头注释即此定案）。门面只做**透传**，不复制任何判据——复制即第二真理源。

**为何挂 Agent 而非直接导出 registry 类**：registry 是**实例**且必须按 Agent 实例隔离（文件头注释：单例会让 `kill_command` 杀掉别的会话起的进程）。导出类 = 把实例化权交给宿主 = 破坏隔离不变量。只导出**方法**，宿主无从碰实例。

**未初始化语义**：与既有门面同构——`assertInitialized` 早退，返回空数组 / `null`，不抛。

### 2.2 宿主侧：协议 +2 通道（105 → 107）

| 通道 | 方向 | 载荷 | 说明 |
| --- | --- | --- | --- |
| `background_tasks` | 下行 | `{ items: BackgroundTaskView[] }` | 快照推送；`BackgroundTaskView` = `{ taskId, command, startedAt, status }`（**不含 `result`**——输出体量大，UI 不呈现，避免无谓搬运） |
| `background_kill` | 上行 | `{ taskId: string }` | 用户点 kill → extension 调 `agent.killBackgroundTask()` → 回推一次快照 |

通道数 105 → 107，远低于 130 治理阈值（`protocolGuard.test.ts`）。

### 2.3 UI 形态：StatusDock **第四条**（复用既有「+N」chip，不新增第二个 chip）

- **入口**：注册为 StatusDock 第 4 条（`DOCK_PRIORITY` += `background: 0`）
- **可见性**：**仅当 N > 0 时显示**（无后台任务时零占用，不制造常驻噪音）
- **浮层**：**复用既有 `+N` chip + `status-dock__panel`**，不另造第二个 chip
- **行形态**：命令原文（过长截断，`title` 悬停看全文）+ 状态标签 + 「终止」按钮（`running` 行才有按钮，终态行无按钮）
- **状态词表**：消费内核 **`BACKGROUND_TASK_STATUS_LABELS`**（运行中 / 已完成 / 超时被终止 / 已终止）——**宿主不自建词表**，防双源漂移（同 `COMPRESS_TARGET_LABELS` 定案）
  - ⚠️ **2026-10-04 自审订正**：本文初稿写的是「复用内核 `STATUS_LABELS`」，而该标识符当时是 `backgroundTasks.ts` 的**模块私有常量、内核零导出** ⇒ 属于「引用了不存在导出的文档失真」（与旧台账虚构标识符 `inlinePlanBoard` 同型）。已随刀 3 前置提交把该表改名为 `BACKGROUND_TASK_STATUS_LABELS` 并**公开导出**，`formatBackgroundTaskNotice` 同步改用同一张表（回流通知与 UI 无第二套文案）

**⚠️ 实施修订（2026-10-04，刀 3 落地时）**：初稿定「新增『后台 N』chip」，实施时读穿
`resolveDock()` 后**否决**——既有机制已完备：任何非主位条自动进 `+N` chip / panel，
chip 的 `+N` 计数与展开态 `_dockExpanded` 已是 SSOT 单点。再造一个「后台 N」chip =
两个 chip、两套展开态、两套显隐裁决，纯负收益（why not simpler）。

代价与取舍（如实登记）：后台条收纳进 `+N` 时，用户先看到的是无语义的 `+1`，
需点开才知是后台任务——与 fileChanges / pendingQueue **同一取舍**，不为其破例。

**优先级为何取 `0`（最低）**：`activity` 承载「正在思考/执行」主状态，被顶掉即主状态失踪。
后台任务在**轮次收尾后仍在跑**时恰好成为唯一活跃条 ⇒ 自动升为主位、列表与「终止」按钮
直接可见（正是最需要它的场景）；轮次进行中则收纳进 `+N`，不抢主状态位。

### 2.4 刷新时机

候选：

| 方案 | 机制 | 代价 | 评价 |
| --- | --- | --- | --- |
| A · 条件轮询 | 仅当存在 `running` 任务时按 1s 拉取，全部终态即停 | 一个 `setInterval`，需生命周期管理（dispose 不当即泄漏） | 简单但引入常驻定时器 |
| B · 内核事件回调 | 内核新增「状态变化」回调给宿主 | 改 `setCompletionListener` 单点 setter 为多播，公共面再 +1 | 精确但侵入内核既有定案，**否决** |
| C · 只在收尾报告时更新 | 复用 `background_report` | 运行态仍不可见 = 没解决缺口 | **否决** |
| **D · 宿主侧事件点推送（**实施采纳**）** | 在宿主**已有**的两个事件点推送：`background_report` 到达（终态批量变化）+ `background_kill` 处理后强制回推 | 零定时器、零生命周期负担 | 简单性最优（why not simpler） |

**实施修订（2026-10-04，刀 2 落地时）**：原定案 A，实施时发现 D 更简——宿主本就有
`background_report` 消费点（收尾报告），顺带推一次快照即可覆盖「终态变化」；
kill 后强制回推覆盖「用户主动终止」。**无定时器即无泄漏面**，内核零感知。

⚠️ **D 的已知缺口**：后台任务**刚启动**时无推送点（启动发生在 `run_command`
工具执行路径）⇒ 浮层要等第一个 `background_report` 才出现。

**实施修订（2026-10-04，刀 3 落地时）**：补 **`step_boundary` 一个推送点**即可闭合——
step = 一次 LLM 迭代 + 其工具执行，后台命令必然在某 step 内启动，step 边界到达时
快照已含它。零新事件、零定时器、零内核改动（触发驱动，不预支设计）。

**推送去重（防 IPC 噪音）**：step 边界频次虽低（非 chunk 级），但无任务时逐 step 推空快照
纯属浪费 ⇒ `postBackgroundTasks()` 内加**内容签名守卫**（`taskId:status` 拼接串，
变化才推）。签名而非长度，是因 `kill` 后 `running → killed` **条数不变而内容变**——
长度守卫会把这次关键刷新判成 no-op（同 `syncPendingQueue` 长度守卫的反向教训）。

**⓿ 第四个推送点：webview ready 全量对齐（刀 3 落地时补，带伤自审第 4 条）**

上述三个点全是**周期性 / 事件驱动**推送，漏了**时间面**（本项目已踩四次的那一面）：
webview 折叠 / 关闭再打开 ⇒ 新 webview 实例从未收到过 `background_tasks` ⇒
**后台任务条凭空消失，而进程还在跑、用户也看不到更砍不掉**——恰是本条 UI 的核心价值场景
（轮次收尾后 activity 归位、后台条升主位）。

修法**不是**简单加一行：`handleWebviewReady` 补推时，签名 `_backgroundSignature` 存于
extension 实例、**跨 webview 重建残留** ⇒ 补推会被自己的去重守卫判成 no-op 吞掉。
故 `postBackgroundTasks` 拆两语义：`dedup`（周期降噪，默认）/ `force`（视图重建后对齐）。
参照物在隔壁：`pushFileChanges()` 的 ready 补推之所以生效，正是因为它**没有**签名守卫。

**刀 3 落地时的自审订正（4 处，全部是我自己引入的）**：

| # | 我犯的错 | 判据 | 处置 |
| --- | --- | --- | --- |
| 1 | 协议 Pick 了 `startedAt`，UI 三个消费点零消费 | 预支复杂度 = 僵尸载荷字段 | 删字段（真需要「启动时间」识别卡死任务时按触发驱动再加） |
| 2 | CSS 写了 `var(--status-running, …)` 与 `var(--font-mono, …)` | `tokensClosure` 守卫：令牌必须在 `tokens.ts` 有定义，否则恒走 fallback、**不跟随主题** | 改用既有 `--accent` + 等宽字面量（同 code 块写法） |
| 3 | `postBackgroundTasks()` 无条件调 `listBackgroundTasks()`，把 `chatAgentStub` 打断 | 替身缺方法 → 抛错中断整个 `consumeFlow`（本仓**第三次**同型事故，前两次是 `isPausePending` / `getEffectiveMaxTokens`） | 补桩，**不加 `?.()` 兜底**——给替身违约打掩护会把真实契约缺口藏进 optional 链 |
| 4 | **只推事件点、不在 webview ready 补推** | **时间面漏面**（本项目已踩四次）：webview 折叠/关闭再打开 ⇒ 新 webview 从未收到 `background_tasks` ⇒ **条凭空消失，而进程还在跑、用户也砍不掉**。且签名 `_backgroundSignature` 存于 extension 实例、**跨重建残留** ⇒ 光加一行补推会被自己的去重守卫吞掉 | `handleWebviewReady` 加 `postBackgroundTasks('force')`；方法拆 `dedup`（周期降噪）/ `force`（视图重建后对齐）两语义，**不合并成一条判据** |

> #4 的教训值得单列：**加了去重守卫之后，任何「周期性推」都会连带把「重建后对齐」也一起吞掉**——
> 守卫的判据是「内容变了没」，而重建后对齐的触发条件是「视图换了」，两者正交。
> 参照物就在隔壁：`pushFileChanges()` 之所以能补推生效，正是因为它**没有**签名守卫。

⚠️ **变异验证时抓到的「因错误的原因通过」**：`force 绕过去重` 那条用例初版断言「总共推了 N 条」，
被两种不同错误实现同时满足（dedup 退化成不设限 / force 也被去重）⇒ 变异下仍然绿。
改为断言**增量恰为 1** 后才变锐。同批另一处变异教训：`'force' as 'dedup'` 是**类型断言**、
运行时值不变 ⇒ 变异**根本没生效**，差点误判成「守卫无效」。

## 五、刻意不做

- 后台任务**输出内容**在 UI 呈现（体量大，且 `kill_command` 已把输出交给模型）
- 跨会话 / 跨 Agent 的后台任务管理（注册表按实例隔离是硬不变量）
- 后台任务运行时长、进度百分比（内核不持有进度语义，编造即说谎）
- 命令前缀 allow 白名单、`.ps1` 运行时档（CMD-1 阶段 2 的另两项，独立立项）
