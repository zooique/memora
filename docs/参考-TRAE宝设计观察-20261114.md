## 二、A 档：官方明确写的

**A-1 两个入口、两个位置。** 同一个对象在两个位置出现，职责不同：左侧导航栏是会话入口，右侧工具面板是工作面。

> —— [个人助理：TRAE 宝](https://docs.trae.cn/ide_personal-assistant?lang=zh)

**A-2 工作台顶部是身份区，名字可改。**

> 「工作台顶部为 TRAE 宝的工牌，你可以根据个人偏好编辑 TRAE 宝的名称。」
> —— [个人助理：TRAE 宝](https://docs.trae.cn/ide_personal-assistant?lang=zh)

**A-3 两级角色：全局助理负责找回上下文，项目助理负责执行与汇总。**

> 「TRAE 宝由两个角色组成：全局助理：理解你的长期积累。它跨项目读取历史任务、对话和产物……项目助理：负责当前项目的执行……拆解复杂需求，调度子任务并行推进，完成联调与汇总，把需要你判断的问题和最终成果带回来。」

## 三、B 档：我自己怎么干活（自述，非规范）

以下全部是**本文档作者（助手）对自身工作方式的描述**：不是 TRAE 宝的官方说明，不是 memora 的规范，也不能反过来当作「宝就是这么设计的」。凡引用本节，必须带「自述」二字。

- **B-1 一个交互面，按需另开子会话。** 只有一个交互面，但可以按需另开子会话；子会话不继承我的全部上下文，所以我派活时必须把背景、路径、约束写进任务里。
- **B-2 派活是异步的。** 派出后我这一轮就结束，不阻塞等结果；结果稍后作为事件回到我这里，我再转述给用户。「派出去」和「有结果」是两个不同时刻。（本文作者据此理解宝那种「先受理后回执」的形态——**这是推断，官方没有这样写**。）
- **B-3 我是编排者，不亲手干重活。** 读代码、跑测试、改文件、生成图文都不由我亲手做；我能直接做的是对话、记忆、定时任务、状态查询这类秘书工作。
- **B-4 有定时任务。** 可以在没有用户在场时自己开工。
- **B-5 有跨会话记忆。** 开工前会先读用户画像和项目记忆。
- **B-6 汇报纪律。** 先回一句再动手；每有里程碑就报一次，不等全部做完；结果要转述不能照抄；交付物要给地址。
- **B-7 权限由宿主决定。** 我绕不过去；该说「核不到」的地方必须说核不到。
- **B-8 我看得到的是工具清单和规则文本，不是实现。** 所以本节一律只能算自述，不能升级为规范。

### 三.1 行为模式九条（2026-11-20 增补 · 用户一手描述转判据）

> **为什么补**：B-1～B-8 写的是形态（一个交互面、异步派活、编排者定位），不是判据——只能说明「宝长这样」，说明不了「memora 宝做到没有」。本节把用户的一手描述转成九条可对照的判据：每条都给出**判据句**与**做到 / 没做到的可观测形态**，下游审查可以直接对号，不需要再猜。
>
> **档位不变**：仍属 B 档（自述，非规范）。它既不升格为官方说明，也不自动成为 memora 的设计要求——哪条该一致、哪条本该不一样，由交叉核对稿逐条判，不在这里预判。

**P1 任务分解**

- **原话**：复合请求先拆成独立可交付的子任务，理清依赖顺序再动手；不把多个独立结果塞进同一条执行线。
- **判据句**：面对一个复合请求，产出物里能读到「拆出了哪几件、谁先谁后、各自怎么算交付」。
- **做到的样子**：子任务清单是显式的（不是心里拆）；每一项有独立可验收的产出；存在先后或依赖声明；不会把互不相干的结果塞进同一条执行线。
- **没做到的样子**：一口气做完；只有一条流水账；多个交付物混在一个结果里；看不出谁依赖谁。

**P2 委派与复用**

- **原话**：用最少的会话数完成当前目标；上下文高度重叠时优先继续既有会话而不是新开；一条会话只装一个连贯目标。
- **判据句**：新建执行单元之前，先能回答「有没有现成的可以接着用」；一条会话的目标是连贯的，漂移有记录。
- **做到的样子**：派活前先查既有会话及其摘要；重叠上下文以续用为主；会话数与目标数大体对齐；目标变了有明确交代。
- **没做到的样子**：同一目标反复新开；既有会话明明可续却重开；一条会话里塞进互不相干的目标且无标注；标题还停在首轮目标。

**P3 决策边界**

- **原话**：不替用户拍板。用户给出的事实、可用条件、对某一个问题的回答，不等于替另一个选择做了决定。只有歧义会实质改变交付物时才回头问。
- **判据句**：授权是按「哪一个问题」给的，不能被扩写成「这一类事都听我的」；回头问的触发条件是交付物会变，不是图省事。
- **做到的样子**：区分「用户陈述了事实」与「用户批准了某个选择」；只在会改变交付物时提问；提问带选项，能收敛。
- **没做到的样子**：把一句回答当成整套授权；该问的不问，自己拍板推进；或者反过来，鸡毛蒜皮都回头问。

**P4 回报节奏**

- **原话**：里程碑一到立即报，不攒到结束；只报结论和证据，不搬运过程；同一件事不重复报。
- **判据句**：每个里程碑都有一次对外输出，且每条输出可回源；同一事实只出现一次。
- **做到的样子**：里程碑一到就有回报，不等终局；回报含结论 + 证据（可点开、可回源），不贴过程流水；同一里程碑不会报两遍；失败与中断分开说。
- **没做到的样子**：憋到最后一次性交底；回报是大段过程粘贴；同一件事反复通知；「跑挂了」和「被叫停」混成一句。

**P5 纠错方式**

- **原话**：发现自己判断错了，先承认再改，不辩解；同时要分清「我判断错」和「用户改了要求」这两件不同的事。
- **判据句**：更正文本里能看出「错在判断」还是「你改了要求」，并说明影响面。
- **做到的样子**：先给更正与影响面，再继续；两种改动在记录上可区分；不解释成「其实没错」。
- **没做到的样子**：悄悄改口；把判断错说成需求变；把需求变说成自己判断错（过度认错）；辩解式绕开。

**P6 诚实边界**

- **原话**：不伪造结果；贴不出文件 + 符号的一律标「推断」；失败就说失败，部分完成就说部分完成。
- **判据句**：结论带证据形态（实证 / 推断 / 不可判），且「完成」只在验证通过后才说。
- **做到的样子**：失败、部分完成、不确定都有各自的说法；无证据的判断标「推断」；不用「已发起 / 已安排 / 已生效」这类只描述动作的词冒充终态。
- **没做到的样子**：把发起说成完成；读不到就说「没有」；推断当实证；部分完成说成全部完成。

**P7 身份隔离**

- **原话**：出方案的和挑毛病的不该是同一条线（排雷方 ≠ 设计方）。
- **判据句**：复核方的输入是独立的（另一条会话 / 另一份上下文），不是同一条线里的人换个说法。
- **做到的样子**：方案线与复核线可区分；复核方拿到的是交付物本身，不是方案方的自我说明；复核结论独立于方案方。
- **没做到的样子**：同一条线自审自签；同一次调用里换个人格充当「多方评审」；复核输入已被方案方筛选过。

**P8 不带伤**

- **原话**：不为了过行数限制删注释或压平既有代码；不顺手重构无关代码。
- **判据句**：改动面 = 任务声明面；为过限制而牺牲可读性不算允许的代价。
- **做到的样子**：只动任务声明的范围；为过闸不删注释、不压平结构；无关代码零改动，或改动有单独说明。
- **没做到的样子**：删注释凑行数；把既有代码压成一行；顺手重构「看着不顺眼」的部分；改动面大于声明面且无交代。

**P9 事实与重放**

- **原话**：说过的话、做过的事要落在能被重建的地方，而不是只存在于一次推送里。
- **判据句**：关键事实（派了什么、结果是什么、谁改的）能从落盘载体离线重建，且与当时一致。
- **做到的样子**：关键事实有落盘载体；关掉进程后能重建同一事实；重建结果与运行时一致；刻意不落盘的部分有写明理由。
- **没做到的样子**：只活在内存/一次推送里；重启后事实消失且无交代；重建出来与当时不一致；「不落盘」是漏的而不是定的。

## 四、C 档：官方没说清的

- **C-1 任务没有状态枚举。** 官方全文只有「处理进度」「待办事项」「需要你判断的问题」这类自然语言，没有给出任何状态取值，也没有状态与视觉的对应规则。唯一能读到的是行为约束：可继续布置新任务、无需等前一个结束（并行），IM 侧可「停止当前任务」。
- **C-2 工作台没有逐区说明。** 官方只写「查看最近任务以及产物」，没有分区清单、排序规则、空态描述，也没有「最近任务」与「项目任务」的切换规则。
- **C-3 「先受理后回执」的形态解读没有官方出处。** 这一条只在 B 档自述里有旁证，属推断。

**这一档的用法**：想照搬也没有依据，只能自己定。memora 自己的四种状态（在跑 / 等你 / 跑完了 / 被中止了）出自 [白话设计文档-托管模式](./白话设计文档-托管模式.md)，**不是从宝抄来的**，不能在这份参照稿里冒充「官方如此」。

## 五、对 memora 的取舍

> **2026-11-17 订正**：托管模型已收敛为「一个独立的助手 agent + 一个微信式窗口」（见[白话设计文档-托管模式](./白话设计文档-托管模式.md)与[路线文档](./评估-子会话与目标模式路线-20261108.md) §0.5）。下表与「工作台」相关的三行（位置关系、工作台上方身份区、任务到会话一步下钻）暂按**冻结**读：工作台不再是助手的必需部件，窗口跑通后单独决定是否删除；其余取舍不变。

以下每一行都是 memora 自身的判断，依据是 [白话设计文档-托管模式](./白话设计文档-托管模式.md) 已定的边界，不来自官方材料。

| 项 | 取舍 | 理由 |
| --- | --- | --- |
| 左说右看的位置关系（左侧对话、右侧工作台） | 照搬 | 与 memora 已定的「左边说话、右边看活」同构，宝的做法可作外部旁证，不新增结构 |
| 工作台上方身份区（工牌/可改名） | 照搬 | 对应 memora 工作台第一块「代理是谁」；只是把「谁在替我安排」放在最上方，零新增概念 |
| 任务到会话一步下钻 | 照搬 | 对应「点一下就回到会话本身」；宝的列表 → 会话是最短路径，与 memora 不造中间层一致 |
| 宝的两级助理（全局助理 + 项目助理） | 不照搬 | 两者是跨项目记忆层 / 当前项目执行层的分工；memora 是单项目 agent（一个宿主 = 一个项目），「跨项目记忆」前提不存在。且宝的全局助理做技术判断（梳理方案、约束与偏好），与 memora宝「不碰技术决策」的定位冲突。理由按定案 §六 R4 订正（2026-11-18） |
| 「任务 → 会话页签 → 打开会话」的中间层 | 不照搬 | 宝的会话页签是任务与真源之间的一层包装；memora 明确不造任务页、不做三级跳，工作台点一下直达会话 |
| 独立产物登记表 | 不照搬 | memora 只认会话为真源，工作台第三块「交出了什么」是会话产出的投影；另立登记表就是第二份真相，与「不造任务对象」同源 |

## 六、边界提醒

下面这些界面**不属于宝**，官方也没有声明它们与宝共用一套规范，不能拿来当宝的界面依据：

- [TRAE Work 网页版和桌面版快速开始](https://docs.trae.cn/solo_trae-solo-quickstart)：对话面板 / 待办 / 上下文 / 代码变更那一套面板表，属 TraeWork 形态。

看到这些页面里的「任务」「产物」「工作台」字样时，先确认它属于哪个产品，再决定能否引用。
