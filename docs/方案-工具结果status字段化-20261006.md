> **台账**：`tasks/待完成任务.md` 的 `SCRIPT-2`（本方案为其唯一实现指针）
> **前置**：`SCRIPT-1` / `METRICS-PREFIX-1`①② 已于 2026-10-06 落地（判据收敛为 `isToolFailure`）

## 一、为什么要做（根因，不是"还有 bug"）

`SCRIPT-1` 已把失败判据收敛到单点 `toolCallHelpers.isToolFailure`，但**判据读的是文本**：

```
执行器 ──产出──▶ "[COMMAND_ERROR] 命令执行失败（退出码: 1）"  ← 纯字符串
                                            │
判据 isToolFailure(result) ◀──正则扫前缀────┘
```

**语义寄生在文本里**，带来三个结构性代价（全部已实测，不是推演）：

| 代价 | 实锤 | 性质 |
|:--|:--|:--|
| **判据与渲染耦合** | 前缀一改（改文案 / 加装饰 / 换语言），判据静默失效 | 文本是渲染面，语义不该寄生在上面 |
| **行首归属是隐性契约** | `kill_command` 把 `[TASK_ALREADY_SETTLED]` 放行首，内嵌 `[COMMAND_ERROR]` 落到第二行 ⇒ 失败被判成功（2026-10-06 已修，但契约本身仍在） | 同一个返回值里两个事实抢行首 |
| **守卫只能扫文本** | 拼接型产出**扫不到**：`toolExecutor` 75 行 / `skillScriptRunner` 14 行 / `backgroundTasks` 4 行 / `toolRunner` 5 行 = **98 处**含插值模板串对前缀守卫失明（2026-10-06 实测，见 `toolFailurePrefixGuard.test.ts` 末条用例） | 守卫有 98 处方形的盲区 |

**结论**：现有三个修补（判据收敛 / 双向对账守卫 / 行首归属修复）都是在**加固一个错误承载体**。
本方案换承载体 —— 让失败成为**结构化字段**，文本降为纯渲染面。

## 二、目标形态

```
执行器 ──产出──▶ { status: 'failed', text: "命令执行失败（退出码: 1）\nstdout: …" }
                                            │
判据 ◀──读 status 字段──────────────────────┘   ← 不再读文本
```

| | 现状 | 目标 |
|:--|:--|:--|
| 失败语义载体 | 文本前缀（`[ERR…` / `[X_ERROR]` / `[X_TIMEOUT]`） | `status: 'ok' \| 'failed' \| 'blocked'` 字段 |
| 判据实现 | 正则扫行首 | 读字段（三值穷尽，**编译期可封**） |
| 前缀的地位 | 事实载体 | **纯渲染面**（LLM 可读性需要，但不再是判据） |
| 拼接盲区 | 98 处 | **0**（判据不读文本） |
| 行首归属契约 | 存在且易破 | **不存在**（顺序无关） |
| 前缀守卫 | 源码扫描（有盲区） | 退化为**渲染面回归测试**（可选保留） |

## 四、双轨并行期的不变量（**这是本方案最容易带伤的地方**）

B1–B3 双轨批次期间**新旧两条判据并存**，必须钉死三条不变量，否则会出现"部分工具切了、部分没切 ⇒ 口径分裂"：

1. **一致性断言**：对每个已切族的每个 case，`status === 'failed'` ⟺ `isToolFailure(text)`。
   不等即红 —— 这是双轨期的**核心守卫**，缺它整个方案就是在造口径分裂。
2. **未切族零变更**：未接 `status` 的工具，其 `ok` 判定**逐字沿用** `isToolFailure`（不新增分支）。
3. **`status` 是唯一权威**：`ok` 字段的最终值一律取自 `status`（不是"两者取或"）。
   双轨期 `isToolFailure` 只做**交叉验证**，不做决策。

> ⚠️ **退役注（2026-10-06·B5 落地后）**：上述三条不变量仅约束 B1–B3 双轨并存期。B5 已将剩余 12 个内联族逐族 outcome 化、`isToolFailure` 与 `TOOL_FAILURE_PATTERNS` 物理删除，双轨不再并存 ⇒ 本节约束自动失效，留作历史记录。失败语义唯一承载 = `ToolOutcome.status`；文本前缀仅余渲染面职能（含 `isRetryableToolError` 读 `[ERR:TOOL:…]` 做**重试分类**，属独立于计数的「错误类别轴」，非判据残留）。

## 六、关键设计决策（2026-10-06 拍板）

### 决策一：`read_failed` 用独立维度，不用第四个 status 值

**问题**：「主动挡下」经盘点共 **11 种语义**，都产出
`blocked=true` 这个**单一布尔**。但它们并不同质——

| 来源 | 语义 | 该不该算失败 |
|:--|:--|:--|
| `search_limit` | 搜索次数用完，没必要再搜 | 不该 |
| `ask_limit` | 提问次数用完，问不动了 | 不该 |
| `write_loop` | 检测到写死循环，主动停手 | 不该 |
| `read_dedup` | 同内容已在上下文，重复读无意义 | 不该 |
| `ledger_stub` | 台账替身：用摘要顶替整读 | 不该 |
| `no_compress_target` | `compress_context` 目标不存在 | 不该 |
| `invalid_intel_note` | `remember_intel` 参数为空 | 不该 |
| `permission_denied` | 宿主审批拒绝 | 不该 |
| `readonly_denied` | 只读模式禁写工具 | 不该 |
| `idempotent_skip` | outbox 幂等：已执行过 | 不该 |
| **`read_failed`** | **读文件连续失败达上限，系统判定再试也没用而停手** | ⚠️ **有争议** |

**决策（用户拍板：加独立维度）**：

- ❌ **不加第四个 status 值**（如 `blocked_stuck`）。理由：那会让「这次到底算不算失败」
  **永远无法回答**（每个 blocked 子类都得再判一次），且随护栏增加持续膨胀（11 条 → 11 个值）。
- ✅ **加正交的原因维度** `blockedReason` + 一个布尔 `hasRealFailure`。
  理由：这 11 种**全都是「没成功」，没有一种例外**。它们之间的差异回答的是
  **「为什么没成功」**，不是「有没有成功」—— **两个正交问题，硬塞进一个字段必然拧巴**。

**`read_failed` 的处置**：归 `blocked`（status 保持三值判据干净）+ 置 `hasRealFailure=true`。
失败真值由独立计数 `toolBlockedWithFailureCount` 承载，**不并入 `toolFailureCount`**
（并入会让 blocked 同时表达「主动停手」与「真失败」= 回到「一个数字两套语义」的老问题）。

**附带收益**：UI 现在只能说「已拦截」，用户不知是搜超了还是撞循环了；`blockedReason` 补上后可原样透出。

### 决策二：口径一并改（Breaking，已拍板）

**执行层闸门（宿主 denied / 只读拒绝 / 幂等跳过）自 B4（判据切换批次）起不再计入 `toolFailureCount`。**

**依据不是偏好，是指标语义**：`toolFailureCount` 的用途是判断「这次任务是不是因为工具能力
不足而失败」。把「我们主动不跑」混进去，会让这个数字**同时表达两件相反的事**
（能力不足 vs 主动收敛）⇒ 指标失去判别力。

**代码里已有先例证明这个方向本来是对的**：`tool_result` chunk 的 `blocked` 字段 JSDoc
原文写着「`ok=false + blocked=true`：区别于『执行失败』，UI 显示『已拦截』，
**不计成功数亦不计失败数**」—— **只是这个正确建模只覆盖了 loop 护栏，没覆盖执行层**。
这是历史遗漏，不是有意设计。

⇒ 新增 `toolBlockedCount`（主动挡下总数）+ `toolBlockedWithFailureCount`（其子集）。
⚠️ **`toolFailureCount` 数字会下降且与历史不可比**，须 CHANGELOG 登记
（处置范式同 `SCRIPT-1`：口径变更 + 明确历史不可比边界）。

### 决策三：护栏原因必须**穷尽登记**，不许兜底

`GuardRailId`（5 值）与 `BlockedReason`（11 值）是两个独立演进的枚举。若用 `as` 强转或
`??` 兜底，**新增护栏时会静默落进兜底值** ⇒ 「新增护栏却说不出为什么被挡」——
正是 `blockedReason` 要消灭的病症复发。

⇒ `Record<GuardRailId, BlockedReason>` 映射表 + **未登记即抛错并点名该 id**。
（`noUncheckedIndexedAccess` 使 `Record` 取值仍带 `undefined`，TS 无法证明完备 ——
故显式处理该分支，`as`/`??` 都会让「新增护栏漏登记」静默通过。）

**新增原因值时禁止硬塞既有值**：`no_compress_target` 曾想塞进 `search_limit`
（都是「不必再试」），但语义不同 ⇒ 硬塞会让原因字段退化成第二个 `status`（值多但无信息）。

### 决策四：旁路方法改返回 `ToolOutcome`（类型强制表态）

`compressContext` / `handleRememberIntel` 原本返回 `Promise<string>`，四种结局
（成功 / 无目标 / 失败 / 异常）在类型上**完全同形** ⇒ 调用方无从区分，只能扫文本前缀。

⇒ 改返回 `Promise<ToolOutcome>`。**类型层面强制每条路径表态**，实测当场抓出两条
被漏掉的返回点（"目标已不在当前上下文"）—— 这是改返回类型的直接价值。

### 实施批次

按 B1 → B2 → B3 → B4 推进（批次定义见 §三）。每批只动 1–2 个文件，
门禁绿后才进下一批；发现破损立即全量回滚，不留破损工作区。

**关键前置**：P1 期的双轨核对设施（`stepOutcomes` / `_crossCheckOutcome` /
两个观测集 / `_settleStepOutcomeObservations` / `onToolSettled` 回调）
与 **B4 判据切换同批整体退役** —— 切换后它们失去被核对对象，留着即僵尸设施
（这正是本方案在消灭的病症）。

### B2 施工细则（2026-10-06 拍板：拆 a/b 两子批，边界三决策见下）
