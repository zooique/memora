# Memora + Sprite 共生迭代规划

> **版本**：v1.0（排雷优化版）
> **日期**：2026-06-24
> **范围**：v0.3 → v1.0 四条主线
> **定位**：大厂做宽度（通用 Agent），我们做深度（记忆驱动的持久化伙伴）
> **前提**：Sprite 是 Memora 发芽的根，两者共生，但 Memora 内核保持领域无关

---

## 设计边界总览

在展开四条主线之前，先明确不可违反的边界。这些边界来自项目规则体系（ADR-002/004/006 + 架构哲学 + 后端分层规范），是所有迭代的硬约束。

| # | 边界 | 来源 | 违反后果 |
|---|------|------|---------|
| B1 | Memory 接口 7 字段不变，不向 Memory 类型添加任何新字段 | ADR-004 | 破坏基元驱动模型，退回概念驱动 |
| B2 | 新数据结构必须是独立的侧车（sidecar），不可侵入 Memory 本体 | ADR-004 | 记忆系统膨胀，维护成本指数增长 |
| B3 | 封闭枚举只允许已有的（ToolErrorCode 等），新概念必须用开放字符串 | ADR-004 | 扩展性丧失，每加一种类型需改代码 |
| B4 | Memora 内核零 native 依赖，不引入任何新 runtime 依赖 | ADR-002 | 破坏纯逻辑库定位 |
| B5 | 核心库提供"机制"，宿主提供"策略"——领域相关逻辑只在 Sprite 层 | 后端分层规范 | 核心库耦合领域，无法接入其他宿主 |
| B6 | LLM 负责不确定性判断，代码负责确定性流程 | 架构哲学 §4 | LLM 决策不可控，代码退化为胶水 |
| B7 | 护栏不阻断对话，降级优先 | ADR-006 | 安全机制导致用户无法使用 |
| B8 | 代码与模型分工：不让 LLM 决定"要不要检索更多"，不让代码做"判断情绪" | 架构哲学 §4 | 职责混乱，调试困难 |

## Phase 1：记忆从"列表"进化为"网络"

> **目标**：让记忆之间有关系，让矛盾自动发现，让用户看到记忆的全貌
> **时间**：当前 → v0.3
> **差异化价值**：大厂的 Memory 是扁平的向量存储，你的记忆有因果结构

### 1.1 记忆关系图谱（MemoryRelation）

#### 原始方案

在 `Memory` 类型中新增 `relations` 字段，定义 `contradicts` / `supports` / `follows` / `refines` 四种关系类型。

#### 排雷发现

| # | 雷区 | 严重度 | 依据 |
|---|------|--------|------|
| 🔴 R1 | `relations` 字段侵入 Memory 7 字段模型 | 致命 | B1：ADR-004 明确 Memory 是 7 字段基元，不可扩展 |
| 🔴 R2 | 四种关系类型是封闭枚举 | 致命 | B3：ADR-004 核心决策是"source 开放字符串替代封闭枚举"，关系类型同理 |
| 🟡 R3 | 关系数据的存储未规划——IMemoryStorage 无 relations 方法 | 中 | 接口不完整，宿主无法实现 |
| 🟡 R4 | 关系图谱的构建时机未定义——每轮对话后？用户手动？LLM 自动？ | 中 | 流程缺失会导致数据质量不可控 |

#### 优化方案

**核心原则**：MemoryRelation 是独立的侧车数据结构，与 Memory 平行存在，互不侵入。

**1. 类型定义（memora 内核 `src/memory/types.ts`）**

```typescript
// 关系类型是开放字符串，不是枚举
// 预设建议值：'contradicts' | 'supports' | 'follows' | 'refines' | 'caused' | 'related'
// 宿主可自由扩展，如 'derived-from'、'supersedes'
export interface MemoryRelation {
  sourceId: string;       // 关系起点（Memory.id）
  targetId: string;       // 关系终点（Memory.id）
  type: string;           // 开放字符串，非枚举
  weight: number;         // 关系强度 0-1
  createdAt: string;      // ISO 8601
}
```

**2. 存储接口（memora 内核 `src/memory/relationStore.ts`）**

```typescript
// 独立于 IMemoryStorage 的侧车接口
// 宿主项目注入实现（如 SqliteStorage 扩展 memory_relations 表）
export interface IMemoryRelationStore {
  addRelation(relation: MemoryRelation): void;
  getRelations(memoryId: string): MemoryRelation[];
  getRelationsByType(type: string): MemoryRelation[];
  removeRelation(sourceId: string, targetId: string, type: string): void;
}
```

**3. 构建时机（Sprite 层，不进内核）**

```
InsightExtractor.extract() 完成后（fire-and-forget）
  → 代码层：对新提取的 insight，召回 top-5 相关记忆
  → LLM 层：判断新 insight 与每条相关记忆的关系类型
  → 代码层：写入 IMemoryRelationStore
```

遵循降级优先（B7）：关系构建失败不阻塞对话，仅记录日志。

**4. 需要新增的 ADR**

ADR-014：记忆关系图谱——独立侧车模型，开放字符串关系类型，IMemoryRelationStore 接口注入。

### 1.2 冲突检测与解决

#### 原始方案

在 InsightExtractor 中增加冲突检测步骤，LLM 判断新信息是否与已有记忆矛盾。

#### 排雷发现

| # | 雷区 | 严重度 | 依据 |
|---|------|--------|------|
| 🟡 R5 | 冲突检测增加 LLM 调用次数，每轮从 1 次变 2 次 | 中 | 成本和延迟增加 |
| 🟡 R6 | "矛盾"的判定标准未定义——语义矛盾 vs 事实矛盾 vs 观点变化 | 中 | LLM 判断不稳定 |
| 🟢 R7 | 冲突解决后的旧记忆处理未定义 | 低 | 衰减？标记？删除？ |

#### 优化方案

**原则**：冲突检测嵌入现有的 InsightExtractor 流程，不新建独立管线。

**流程**：

```
InsightExtractor.extract() 现有流程：
  1. LLM 提取 insight（是否值得记忆 + 摘要）
  → 新增步骤 2：代码层召回相关记忆（top-5，关键词匹配）
  → 新增步骤 3：同一次 LLM 调用中，追加判断"是否与已有记忆矛盾"
     （利用 LLM 的上下文窗口，不额外调用）
  → 步骤 4：若矛盾，调用 IMemoryRelationStore.addRelation(type='contradicts')
  → 步骤 5：旧记忆 score 降低 0.1（复用现有 decay 机制，不引入新机制）
```

**关键设计**：不增加 LLM 调用次数——在现有 extract() 的 LLM 调用中，将相关记忆作为上下文注入，让 LLM 一次性完成提取+冲突判断。

**冲突判定标准**（注入 system prompt）：

```
判断标准：
- 事实矛盾："我喜欢咖啡" vs "我不喝咖啡了" → contradicts
- 观点演化："React 最好" vs "Vue 也不错" → refines（不是矛盾）
- 时间推移："今天下雨" vs "明天晴天" → 不是矛盾（不同时间）
```

## Phase 2：从"工具"到"伙伴"——情感与成长

> **目标**：让精灵有情感基调，让用户感知到"越来越懂我"
> **时间**：v0.3 → v0.5
> **差异化价值**：大厂的 AI 必须保持"中立无个性"，你的精灵有温度

### 2.1 情感基调系统（AffectTone）

#### 原始方案

定义 `warmth` / `playfulness` / `directness` / `initiative` 四维情感模型，从记忆中推断。

#### 排雷发现

| # | 雷区 | 严重度 | 依据 |
|---|------|--------|------|
| 🔴 R10 | 若 AffectTone 放在核心库 `src/`，违反领域无关原则 | 致命 | B5：情感是精灵特有的领域概念，不是所有 Agent 都需要 |
| 🔴 R11 | 四维模型是封闭的"概念"，不是基元 | 致命 | ADR-004：基元驱动 > 概念驱动，4 个浮点数构成的新子系统 |
| 🟡 R12 | 情感推断依赖 LLM，但推断频率未定义——每次对话？每天？ | 中 | 成本控制 |
| 🟡 R13 | 情感值的持久化方式未定义 | 中 | 重启后情感值丢失 |

#### 优化方案

**核心原则**：AffectTone 不是新的数据结构，而是从现有记忆数据中**实时推导**的指标。

**实现位置**：`hosts/memora-sprite/src/sprite/controllers/affectController.ts`（新建）

**推导逻辑（纯代码，不依赖 LLM）**：

```typescript
// 从现有记忆数据推导，不新增任何存储
function deriveAffect(memories: Memory[], metrics: AgentMetrics): AffectState {
  // 温暖度：基于交互频率（profile 记忆数量 + 连续交互天数）
  const profileCount = memories.filter(m => m.source === 'profile').length;
  const warmth = Math.min(1, profileCount / 20);

  // 直接度：从用户画像中提取（如果用户画像中有"偏好简洁"的记录）
  const prefersDirect = memories.some(m =>
    m.source === 'profile' && m.content.includes('简洁')
  );
  const directness = prefersDirect ? 0.8 : 0.5;

  // 主动度：基于主动提示接受率（metrics 中已有）
  const initiative = metrics.proactive.acceptanceRate ?? 0.5;

  // 调皮度：从 persona 配置中读取（角色定义时已声明）
  const playfulness = currentPersona?.traits?.playfulness ?? 0.3;

  return { warmth, playfulness, directness, initiative };
}
```

**关键设计**：
- 不存储 AffectTone——每次从记忆实时推导（遵循"代码负责确定性"B6）
- 不在核心库实现——纯宿主层逻辑（B5）
- 不引入新数据结构——复用现有 Memory 和 AgentMetrics（B1）
- 推导频率：每次对话前推导一次（成本为零，纯代码计算）

**注入方式**：AffectController 在 Sprite.wakeup() 前调用，将推导结果注入 Agent system prompt 的 persona 层之后。

### 2.2 默契度评分（RapportScore）

#### 原始方案

定义 5 维度评分公式，量化"精灵了解用户的程度"。

#### 排雷发现

| # | 雷区 | 严重度 | 依据 |
|---|------|--------|------|
| 🔴 R14 | 默契度是新的"概念"，引入了独立的评分子系统 | 致命 | ADR-004：不创建独立子系统 |
| 🟡 R15 | 5 维度中部分指标在当前接口中不可用（如"记忆被遗忘速度"） | 中 | 接口缺失 |
| 🟡 R16 | 评分公式是硬编码的魔法数字 | 中 | 可维护性差 |

#### 优化方案

**核心改变**：不创建 RapportScore 子系统，而是将"默契度"表达为**记忆仪表盘的一个聚合指标**。

**实现方式**：

```typescript
// 复用现有 DashboardData，新增一个 computed 字段
// hosts/memora-sprite/src/sprite/controllers/memoryController.ts
function rapportLevel(dashboard: DashboardData): {
  level: 'stranger' | 'acquaintance' | 'familiar' | 'close';
  description: string;
  factors: string[];
} {
  const totalMemories = dashboard.total;
  const profileCount = dashboard.bySource['profile'] ?? 0;
  const insightCount = dashboard.bySource['insight'] ?? 0;

  // 简单阈值判定（代码负责确定性工作）
  if (totalMemories < 5) return { level: 'stranger', ... };
  if (profileCount < 10) return { level: 'acquaintance', ... };
  if (insightCount < 50) return { level: 'familiar', ... };
  return { level: 'close', ... };
}
```

**关键设计**：
- 不是新数据结构——复用现有 DashboardData 的聚合计算
- 不是 LLM 推断——纯代码阈值判定（B6）
- 4 级离散值，不是连续浮点数——用户更容易理解
- 展示位置：Sprite 仪表盘面板中，作为卡片展示

### 2.3 里程碑事件

#### 原始方案

硬编码"第 100 条记忆"、"首次发现矛盾"、"连续 7 天交互"等里程碑。

#### 排雷发现

| # | 雷区 | 严重度 | 依据 |
|---|------|--------|------|
| 🔴 R17 | 硬编码里程碑阈值是概念驱动，违反基元驱动原则 | 致命 | ADR-004：不要用封闭枚举定义里程碑类型 |
| 🟡 R18 | "连续 7 天交互"需要额外的交互日志存储 | 中 | 新增存储需求 |
| 🟢 R19 | 里程碑触发后的行为（特殊对话）是纯宿主层逻辑 | 无 | 符合分层规范 |

#### 优化方案

**核心改变**：里程碑不硬编码，而是从现有数据中**模式匹配**触发。

**实现方式**：在 ProactiveEngine 中增加模式检测（不新建子系统）。

```typescript
// hosts/memora-sprite/src/sprite/controllers/proactiveEngine.ts 扩展
// 新增模式检测方法，复用现有的 addNotice 机制
function detectMilestones(dashboard: DashboardData, memories: Memory[]): string[] {
  const triggers: string[] = [];

  // 模式 1：记忆量级突破（不硬编码具体数字，用数量级）
  const magnitude = Math.floor(Math.log10(dashboard.total));
  if (magnitude >= 2 && !this.noticedMagnitudes.has(magnitude)) {
    triggers.push(`memory_magnitude_${magnitude}`); // "积累了数百条记忆"
    this.noticedMagnitudes.add(magnitude);
  }

  // 模式 2：新 source 类型首次出现（从记忆数据中检测）
  const seenSources = new Set(memories.map(m => m.source));
  for (const source of seenSources) {
    if (!this.knownSources.has(source)) {
      triggers.push(`new_source_${source}`); // "第一次从 XXX 中提取了记忆"
      this.knownSources.add(source);
    }
  }

  // 模式 3：关系图谱首次出现矛盾（从 Phase 1 的 RelationStore 检测）
  // ... 由 RelationStore.getRelationsByType('contradicts') 驱动

  return triggers;
}
```

**关键设计**：
- 里程碑不是硬编码的类型枚举，而是从数据模式中自然涌现
- 复用 ProactiveEngine 现有的事件累积 + 提示生成机制
- 不新增存储——seenMagnitudes / knownSources 存在 ProactiveEngine 内存中（重启重置，符合"自然遗忘"原则）

### 3.1 剪贴板感知（ClipboardAwareness）

#### 原始方案

检测剪贴板变化，精灵浮窗提示"这段代码有潜在问题"。

#### 排雷发现

| # | 雷区 | 严重度 | 依据 |
|---|------|--------|------|
| 🔴 R20 | 持续监听剪贴板是隐私风险——用户不知道精灵在"看"什么 | 致命 | B7：ADR-006 安全模型，"不监听键盘不截屏"是核心卖点 |
| 🔴 R21 | 剪贴板内容自动存为记忆——未经用户确认的写入 | 致命 | ADR-006：写入二次确认 |
| 🟡 R22 | 剪贴板可能包含密码、token 等敏感信息 | 中 | 安全风险 |

#### 优化方案

**核心原则**：被动检测 + 主动触发 + 用户确认，三重保护。

**1. 被动检测（不读取内容）**

```typescript
// hosts/memora-sprite/src/electron/main.ts
// 只检测剪贴板"是否有变化"，不读取内容
clipboard.on('text-change', () => {
  // 仅通知渲染进程"剪贴板有变化"
  // 不传递内容，不存储，不发送给 LLM
  mainWindow.webContents.send('clipboard:changed');
});
```

**2. 主动触发（用户点击）**

```
剪贴板变化 → 浮窗显示"剪贴板有新内容，需要分析吗？"
  → 用户点击"分析" → 读取剪贴板内容
  → 内容经过输入护栏检查（ADR-006 内容护栏）
  → 展示给用户确认："要将以下内容存为记忆吗？"
  → 用户确认后才写入
```

**3. 敏感内容过滤（代码层）**

```typescript
// 检测剪贴板内容是否包含敏感信息

  // 密码模式：连续 8+ 位字母数字特殊字符混合

  // 信用卡模式：16 位数字
  // 命中任一模式 → 不提示分析，静默忽略
```

### 3.2 工作状态感知（PresenceAwareness）

#### 原始方案

检测 IDE 运行状态、终端编译状态、用户离开/回来。

#### 排雷发现

| # | 雷区 | 严重度 | 依据 |
|---|------|--------|------|
| 🟡 R23 | "检测到 IDE 正在运行"需要枚举 IDE 进程名 | 低 | B3：用配置文件定义，不硬编码 |
| 🟡 R24 | "检测到终端在编译"实现复杂，可能误判 | 中 | 实现难度高于预期 |
| 🟢 R25 | 无操作检测 + 窗口焦点检测是标准 Electron API | 无 | powerMonitor + focus/blur 事件 |

#### 优化方案

**分层实现**（先简单后复杂）：

**第一批（v0.5，低复杂度）**：
- 用户离开/回来检测：`powerMonitor` + 鼠标/键盘无操作计时器
- 窗口焦点检测：`app.on('browser-window-blur')` / `focus`
- 与 ProactiveEngine 集成：用户回来时检查是否有待提示的累积事件

**第二批（v0.6，中复杂度）**：
- 应用感知：通过配置文件定义"关联应用列表"（非硬编码）
- 配置项：`sprite.json` 中新增 `associatedApps: ['code', 'webstorm', 'terminal']`
- 检测方式：`child_process.exec('tasklist')` 过滤进程名

**第三批（v0.7，按需）**：
- 编译状态检测：暂不实现，等有 3 个以上用户反馈再做（自然生长原则）

### 4.2 存储层适配器独立

#### 原始方案

将 SqliteStorage 从 Sprite 中提取为独立包 `@memora/storage-sqlite`。

#### 排雷发现

| # | 雷区 | 严重度 | 依据 |
|---|------|--------|------|
| 🟡 R30 | 独立包意味着 monorepo 管理或独立仓库 | 中 | 工程复杂度增加 |
| 🟡 R31 | SqliteStorage 当前耦合 Sprite 的一些配置（如 FTS5 开关） | 中 | 需要抽象 |
| 🟢 R32 | IMemoryStorage 接口已存在，提取是自然的 | 无 | ADR-002 已规划 |

#### 优化方案

**分步提取**（不做 monorepo，先做内部分包）：

1. **第一步（v0.7）**：将 `hosts/memora-sprite/src/storage/sqliteStorage.ts` 提取为 `packages/storage-sqlite/`
2. **第二步（v0.8）**：在 Sprite 和 CLI 宿主中同时使用 `packages/storage-sqlite/`
3. **第三步（v1.0）**：如有外部需求，发布为 npm 包 `@memora/storage-sqlite`

**接口对齐**：确保 SqliteStorage 严格实现 IMemoryStorage，不添加额外的公共方法。额外能力（如 FTS5）通过构造选项启用，不影响接口契约。

### 4.3 技能文件加载标准化

#### 原始方案

拖入 `.memora-skill.js` 文件安装技能。

#### 排雷发现

| # | 雷区 | 严重度 | 依据 |
|---|------|--------|------|
| 🟡 R33 | `.js` 文件直接执行有安全风险——可能包含恶意代码 | 中 | ADR-006 安全模型 |
| 🟡 R34 | 现有 SkillManager 只加载 `.md` 文件，不支持 `.js` | 中 | 需要扩展 |
| 🟢 R35 | 技能加载机制已存在（configDir/skills/ 扫描） | 无 | 扩展现有机制即可 |

#### 优化方案

**不做插件市场**（v1.0 前不成熟），只做**文件拖入安装**：

1. **技能格式标准化**：技能继续使用 `.md` 文件（frontmatter 定义元数据 + Markdown 正文定义 prompt）
2. **安装流程**：用户将 `.md` 文件拖入 Sprite 窗口 → Sprite 复制到 `configDir/skills/` → SkillManager 重新扫描
3. **安全检查**：文件拖入时检查文件大小（< 100KB）和格式（必须有合法 frontmatter）
4. **不支持 `.js` 技能**——保持纯 Markdown 技能定义，通过 prompt 注入扩展能力，不执行任意代码

## 迭代链路

```
Phase 1（记忆拓扑）
  └→ 关系图谱 + 冲突检测 → 可视化
       │
Phase 2（情感伙伴）
  └→ 从关系图谱中推导情感 → 默契度 → 里程碑
       │
Phase 3（桌面壁垒）
  └→ 剪贴板 + 工作感知 + 快捷键
       │
Phase 4（生态准备）
  └→ 文档 + 存储独立 + 技能安装
```

Phase 1 是基础（关系数据为 Phase 2 的情感推导提供输入）。
Phase 2 和 Phase 3 可部分并行（情感系统和桌面能力互不依赖）。
Phase 4 在前三者稳定后自然展开。
