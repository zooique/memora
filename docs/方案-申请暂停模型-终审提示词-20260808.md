## 审查要求

按以下 8 个角度逐一审查，**每个角度输出 ≤3 条发现**（不求多，求精）。每条发现标注优先级（🔴P0 阻塞 / 🟠P1 高风险 / 🟡P2 改进建议）。

| # | 角度 | 审什么 |
|---|---|---|
| 1 | **架构完整性** | 方案是否覆盖所有关键路径？有没有"用户一定会走但方案没描述"的路径？（如：有任务表→无任务表的退化、草稿区→停止按钮清空行为、任务表生成后立即追加任务的竞态） |
| 2 | **实施可行性** | 每个改动是否有明确代码落点（文件+方法）？有没有"方案写了但代码里找不到挂载点"的描述？（如：completeRound 原子性靠什么机制保证？renderTaskTable 的导出放在哪个模块？） |
| 3 | **边界条件** | 极端/异常路径：任务表为空→生成→立即追加→暂停打点（四步在一轮内完成）、暂停申请中 cancelPauseRequest 的时序窗口、草稿区达到上限的行为 |
| 4 | **SSOT 审计** | 是否存在隐蔽的数据多写点、多渲染源、或"并列"结构？是否还有未收敛为单一真理源的逻辑？（特别关注：plan 与 roundLog 除了 completeRound 外是否还有其他写入路径、任务表注入段与 UI 面板是否真的同源渲染） |
| 5 | **测试覆盖** | 验收标准是否可量化？关键行为变更（SESSION_PAUSE 统一分发、PAUSED 发送→「加入待定」、cancelPauseRequest）是否有对应测试覆盖？是否存在"改了必引回归但在方案 §7 验收里没列"的测试面？ |
| 6 | **风险收敛** | 已知风险（§8）的缓解措施是否充分？有没有"方案写了风险但没写怎么防"的描述？（如"接线面大→最小接线先行"是策略而非工程防护） |
| 7 | **先例对标** | 与其他先例（Claude interrupt / Cursor plan mode / OpenAI Task / Trae 待输入形态）对比，memora 的设计是否有"做了别人已验证不该做的事"？或者"别人做了但 memora 漏掉"的能力？ |
| 8 | **心智一致性** | 方案附录的"按钮四态文案矩阵"是否忠实还原了用户设计的 pause/continue/inject 心智？有没有文案与行为定义矛盾的地方？（如"加入待定"按钮与"继续"按钮共存时的用户认知） |
