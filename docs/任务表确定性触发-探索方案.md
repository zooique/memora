# 任务表确定性触发 — 探索方案

> 状态：**探索中**（探索期可逆决策，先落 docs 验证，验证稳定被真实场景复现消费后再固化为 ADR；不占 ADR 编号，见 `.trae/rules/exploration-decision-sedimentation-rules.md` S1）
> **坐标**：正文行号为**撰写时点快照**，实施前须按符号名复核，勿直接照行号定位。
> 定位：解决"任务表从未被 LLM 触发"的根因。任务表是 memora 的 **plan_item_boundary 源**（驱动思考折叠 / per-step 会议切换 / 进度看板），长期空转会连带布局骨血空转，因此修正必须落在触发端。

## 1. 问题与根因

### 1.1 现象
真机回归中 LLM 从不调用 `task_table_write`，直接一步步执行；`getActivePlanItemMeta` 返回 null，plan_item_boundary 永不产出，thinking 折叠退化为整轮一块。

### 1.2 根因（已定位）
任务表触发的**唯一引导**是软提示：`src/agent/assembler.ts` 的 `TURN_START_STRATEGY_PROMPT`（L68-71）一句"任务需要多步推进时，使用任务表工具规划执行"，与"简单问题直接回答"并列。

- **无任何代码级检测 / 强制 / 阀门**：项目记忆声称的"第一步边界约束（多步用任务表）"没有 enforce 点，纯靠模型自觉。
- 工具箱、状态机、plan_item_boundary、渲染全已就位，唯独**建表这一步无人点火**——整条任务表链路是"建造成型、从未触发的僵尸链"。
- `loop.ts` L978-997 的 plan_item_boundary 依赖 `getActivePlanItemMeta`（assembler L359-365）返回 active step；plan 为空 → null → 不产边界。

## 2. 主流养分（吸收与过滤摘要）

| 来源 | 可吸收机制 | memora 判断 |
|---|---|---|
| Claude Code `TaskCreate/Update/Get/List` | 状态机 `pending→in_progress→completed`；一次仅一 active；禁止跳级；完成需验收证据 | **已达标/参考**：memora 状态机已单 active 自维护（见 §4 排雷），仅需把 lifted 到描述层 |

| OpenAI Codex `update_plan` | 简单任务不灌 padding；计划后不复制全文（渲染交给 harness） | 采纳：确定性判定需"选择性"，避免噪音 |
| Cursor/Copilot | 独立 Plan 阶段 + plan 文件真理源 | **不照搬**：宿主 TRAE 已自带 Spec/Plan 工作流（`.trae/specs/`、`.trae/documents/`），内核再造 = 重复造轮子 |
| TraeWork Spec/Plan/Goal | 按复杂度分档；"较复杂时自动列 Todo" | 采纳判断、不照搬机制：仅吸收"较复杂才引导/触发"的分档思想 |

## 3. 排雷结论（基于真实代码核查）

### 雷 1 — 状态机"跳级"隐患：**已解除，无需新建约束**
`src/agent/managers/sessionManager.ts` L799-843：
- `updatePlanItemStatus` 是 plan 状态**唯一写点**；
- 写后自动 `ensureActiveStep()`（L826-843）**保证任一时刻恰好一个 active step**（SSOT 自维护，注释明示）；
- `task_table_update` 描述（`builtinTools.ts` L521-529）已限定 LLM 只能标 `done`/`blocked`，`active/pending` 由系统推进。

⇒ **"一次一 active"已满足；"pending→done 跳级"在 LLM 通道被描述限制，系统通道被 ensureActiveStep 兜住。** 层 2 真正要做的只是"描述命令式强化 + 一次一步"，不是加状态机逻辑。

### 雷 2 — needsPlanning 注入时机：**可行，systemPromptPrefix 可变、每轮读取**
- `loop.ts` L2069 每轮从 `this.opts.systemPromptPrefix` 读前缀，L2042 可变刷新 ⇒ 前缀是**动态字段**；
- 但 per-turn 判定若改前缀会持续污染后续轮。
- **最优落点**：仿照 `getTaskTable`（assembler L368-374，每轮注入 system message 的既有机制），新增**首轮一次性 nudge 注入**回调，只在首个 LLM 迭代前注入，不污染后续轮、不新建引擎。

### 雷 3 — 差异化注入是否破坏现有单真源：**受限**
`TURN_START_STRATEGY_PROMPT` 是 `buildSystemPromptPrefix`（assembler L93-120）唯一真源。改造禁拆散该常量；正确做法是保留常量 + 新增**可选的 needsPlanning 判定 + 首轮 nudge**，两条输入并行而非分裂。

### 雷 4 — 指标与真机落点：**明确**
- `loop.ts` `getMetrics()`（L2143）扩展指标字段；
- 真机脚本 `scripts/test-observability.ts`（L190-233）为验收落点；
- plan_item_boundary 计数源在 `loop.ts` L983-997。

### 雷 5 — 无 plan 折叠退化：**已知，属下游可观测问题**
getActivePlanItemMeta 为 null 时 chatView 整轮一组（已有注释）。触发修复后此退化自然消失；无需另改。

## 4. 最终方案

**原则**：三层收敛 + 一条边界线；全部长在现有 task 表 / updatePlanItemStatus / getTaskTable / plan_item_boundary 这棵树上，**不新增独立模块、不复活被收敛的 loop**（目标模式："较复杂时才引导触发，简单任务零打扰"）。

### 层 0 — 观测前置（无度量则无实证）
- `getMetrics()`（`loop.ts` L2143）新增两个计数：**任务表使用率**（本 round 是否调用 `task_table_write`）、**plan_item_boundary 产出数**。
- `scripts/test-observability.ts` L190 附近补两断言。
- 目的：先实证"从没触发"是真实存在的，并验证层 1/2 是否起效。

### 层 1 — 触发确定性化（核心修复）
新增轻量 `needsPlanning` 判定（turn 起始，`processUserInput` 首段），输入：工具调用密度 / 请求是否含多步骤连词 / 是否命令式工程指令。
- **判定为真** → 首轮注入**命令式强引导 nudge**（仿 `getTaskTable` 机制，首迭代一次性注入，不污染后续轮；天然感知 plan 是否为空）；`task_table_write` 高亮/显式声明。
- **判定为假** → 维持"直接答"，零噪音（Codex 反对 padding）。
- 判定做成确定性规则 + 一个可被宿主覆盖的钩子；`TURN_START_STRATEGY_PROMPT` 常量**保持不动**（SSOT）。

### 层 2 — 状态机语义收敛（防"建了也不维护"，大幅缩减）
经雷 1，状态机主体已达标，只补：
- `task_table_write` / `task_table_update` 描述**命令式强化** + 明确**一次只更新一步**；
- 可选加强：`updatePlanItemStatus` 入口加非法流转防御（防御性，非必须）。

### 边界线 — 内核不自造工作流文档化（划清责任）
借鉴 TraeWork 判断、不搬 Spec/Plan/Goal 机制。内核 task_table **只做 step 状态机，不膨胀成 spec.md/tasks.md/checklist.md**——那套文档化工作流宿主 TRAE 环境已自带（`.trae/specs/`、`.trae/documents/`），内核再造即重复造轮子。

### 采纳矩阵

| 提案 | 决策 | 落地 |
|---|---|---|
| 命令式引导 nudge（when needsPlanning） | ✅ 层1 | 仿 getTaskTable 首轮注入 |
| needsPlanning 判定 | ✅ 层1 | 新增轻量函数 + host 覆盖钩子 |
| 任务表使用率 / plan_item_boundary 指标 | ✅ 层0 | getMetrics + test-observability |
| task_table 描述命令式 + 一次一步 | ✅ 层2 | builtinTools 描述 |
| 状态机跳级约束 | ⚪ 已达标 | ensureActiveStep 已覆盖，仅可选入口防御 |
| Spec/Plan/Goal 工作流 | ❌ 边界 | 宿主自带，内核不造 |

## 6. 实证记录（2026-09-14 真机验证）

脚本 `scripts/test-tasktable-real.ts`（真实 LLM `mimo-v2.5` + `BUILTIN_TOOLS` + 简易 toolExecutor，跑强命令多步任务，仅靠 loop 可写装配回调 `getActivePlanItemMeta`/`getTaskTable`，无需 sessionManager 完整集成）。

1. **触发确定化生效**：多步任务输入命中 needsPlanning → 首迭代注入命令式 nudge（日志 `任务表触发：needsPlanning 命中，已注入命令式强引导`）。LLM 工具序列出现 `task_table_write`（1 次）并逐步 `task_table_update`——`metrics.plan.taskTableWriteCount` 由 0 变为 1，任务表从"从未触发"的僵尸链变为真实建表并被维护。
2. **plan_item_boundary 苏醒**：注入 `getActivePlanItemMeta` 后，active 步骤随 update 推进（`b8685edb → 6f589943`），`metrics.plan.planItemBoundaryCount` 产出 2，思考折叠/进度看板（布局骨血）联动生效。

两头实证说明层 1（触发确定性化）已达预期：**真实 LLM 愿意建表 + 分步推进**，不再是"靠模型自觉"。

## 7. 反模式自查（防偏离）

- ❌ 拆散 `TURN_START_STRATEGY_PROMPT` 或双写引导 → 保持单真源 + 并行 nudge
- ❌ 把 nudge 注入所有轮 → 必须仅在首迭代 & needsPlanning 为真
- ❌ 复活持续运行 loop（Goal 化）→ 坚持 turn 结束即 done
- ❌ 内核写 spec/tasks/checklist 文件 → 宿主已负责
