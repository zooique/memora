# memora 的白话运行机制

## 一次完整对话，从用户敲下一句话开始

### 第一步：对话前的装配（外部输入触发）

你发一句话进来，系统开始**搭台子**，装四样东西：

1. **常驻设定**——这个角色是谁（persona）、规矩是什么（rules）、会哪些技能、能用哪些工具。这层是固定的，角色没换就不变。
2. **本轮你的输入**——就是你刚打的那句话。**它是整件事的"根"，从预算里独立划走一块空间，永不压缩**（稍后细说）。
3. **召回的记忆**——根据你这句话，从历史里把最相关的旧记忆捞出来。**捞多少，由角色包的「记忆百分比」封顶**：完整对话先优先装，剩下的空间才会塞旧摘要，而且塞的量不超过这个百分比。如果一句记忆都没捞到，就用 `minFallback` 兜底，塞几条最近的记忆凑数。**注意：这一步只在「新输入进来」时做，loop 自己循环时不做。**
4. **完整对话记录**——当前会话聊过的话。从最近往回装，能装几轮装几轮（装到预算满为止）。**其中第一条问答必然在场**（它是这次会话的起点背景）。

> **两条铁律，先说清楚：**
> - **记忆百分比是"天花板"不是"份额"**：完整对话永远优先装，记忆摘要是"剩下的缝里塞一些"，不会反过来挤掉对话。
> - **触发输入和它触发的第一段回答是顶级锚点**：从预算最上游独立划走空间，loop 怎么跑都不压它。如果输入本身大到连这点空间都留不住，那系统在装配前就先拦住（下面第四步会说）。

### 第二步：loop 启动与运行（一个目标，连跑多轮）

如果你一句话是复杂任务（比如"帮我修那个 bug"），系统会进入 **loop 模式**：一轮接一轮地干活。

关键点：**loop 的每一步内部循环，都不再召回记忆、也不再重新装配四件套**，只在拼好的上下文物件后面继续追加"这轮刚干完的事"。也就是说——**第一次的那个记忆召回结果是整个 loop 一直复用的一份**，不重复捞。

**锚点分级**在这一步生效：

- **触发 loop 的那句用户输入 + 第一个回答**，是整件事的"根"，**永不压缩**，还独立占一块空间。因为 loop 里每步都在朝它定义的目标推进，目标不能被吃掉。
- **第一条问答闭环**，正常在场上，但当上下文实在挤到极限时，**它允许被牺牲**（替换成摘要）——它是背景，不是当前目标。
- **其余所有执行闭环正文**，溢出时最先被收。

### 第三步：两级空间管理（先替换，再压缩）

loop 跑多了，上下文会满。空间的自我维护分**两级**，有明确的先后顺序和裁决归属：

**第一级 · 替换（内核自动做，几乎零成本）**
- 每个完成的问题，收尾时都会存下一条记忆摘要。所以空间不够时，**系统自己按"最早的先换"的顺序，把最旧的一轮对话正文，换成它自己那条已存好的摘要**——不是重新写，是从库里拿现成的，几乎不花算力。
- **这是系统的机械动作，不用 LLM 出手**，也不用把它变成工具暴露给 LLM。最早的先换，纯按时间顺序来，确定、快。只有当某轮被替换后摘要太短、可能让上下文有点断时，系统才提示一句"细节可回溯"。

**第二级 · 压缩（替换无可换时，LLM 才捡起）**
- 作用对象是**还没有摘要可换**的东西——loop 中途还没收尾的步骤、超大号的工具结果。
- 先把超长工具结果悄悄换成一句话占位（比如"之前用过 read_file"），这是**微压缩层**。
- 还不够，就由 LLM 主动调**压缩摘要工具**，把这些中途内容压成一条临时摘要。这叫**压缩摘要**，是 loop 里的**临时产物**，**loop 一结束就扔掉**，进不了记忆库。

> **一句话分清楚**：能换的，系统用现成摘要**替换**（LRU，最早先换，内核自动）；没得换的，LLM 才现场**压缩**。替换和压缩是同一个能力的两级，不是一个对另一个。真正的记忆摘要，是在 loop 收尾后，由系统后端偷偷沉淀的那一条（见第五步）——压缩摘要和它不是一回事。

> **顺带说一句替换的脾气**：替换不是"一满就换"，而是"**最近的几轮（默认 5 轮）先原样留着**，超过这个数，最老的那些才按先来后到换掉"。这样对话开头的连续性有保障，又不至于让旧内容无限占地方。另外，如果上下文被系统**截断**过（把中间剪掉重排），替换就暂时歇手——因为这时"哪轮对哪份摘要"的账目容易对乱，宁可不换，也别换错。

> **顺带说一句边界**：替换和压缩都**只碰"你刚说的话之前"的旧内容**——你当前发的那句输入是整件事的"根"，永远不动。极端情况（比如你一句话刚发出去、loop 才刚开始，上下文就满到要压缩了）下，系统**不会**把你那句"根"压掉，而是直接说"没得压了"——这时它走的是"收尾"（见第四步软上限）：让模型把当前能给的结论交付出来，然后等你下一句。也就是说：**压不到根的时候，就该收尾了，不会硬压着根继续跑。**

> **顺带说一句互斥**：也许你担心"被替换成摘要的那轮，会不会下次又被召回一遍"？不会。召回只在"每次新输入进来"那一刻做一次，而且做之前先把"已经在场的东西（原文或替换后的摘要都算）"剔掉；替换发生在运行中，运行时不召回。所以被替换的轮次，下次装配时系统已经把它排除在外了，绝不重复装两遍。这套是代码里天然保证的，不用额外加机制。

### 第四步：loop 终止

loop 什么时候停？总共看几个信号，哪个先到按哪个：

1. **硬上限**——角色包设了「最多跑 N 轮」，到了 N 轮强制停下来（防死循环烧钱）。**但这不是硬切断**：它会报告"做到哪了、还剩什么没做"，然后等你再输入继续。你接着说一句，它按记忆重新接上。
2. **软上限**——loop 一路替换/压缩，压到最后，**除了顶级锚点，正文基本都变摘要了，摘要层也装满了**。这时候系统主动注入一个"收尾信号"，让 LLM 收敛，给出最终结论，停下来等用户。**这是"空间被摘要塞满"这个物理条件触发的，不是数轮数数出来的。**
3. **自然结束**——任务自己干完了，LLM 交付就停。

**还有一个"还没开始就拦下"的判负**，比较特殊：

- 你贴了一大段特别长的内容当输入。大厂的做法是**输入框限长度**，超长就让你放文件里，用 `read_file` 读（**源头第一道防线**）。
- 就算没拦，系统**装配前会用公式算一遍**：输入勾起的一块空间 + 标准开销，够不够跑至少一轮？不够 → 直接提示"内容太大，建议放进文件读"，而不是让它硬跑起来然后误报成"摘要满了"（**装配前判负**，第二道防线）。输入端过大和"loop 把空间跑没了"，是两码事，分两条路处理。

### 第五步：记忆系统的沉淀（loop 之后）

loop 结束或简单一句问答结束，进入**收尾**：

- 系统在**这次用户输入对应的整段问答闭环结束**时，产出一条**记忆摘要**（一两句这个任务干了啥）。这条是**跨会话持久态**，真正存进记忆库，下次别处能召回。
- 记忆摘要在"问答闭环"级产出；loop 内部的每一步执行闭环**不单产记忆**，只有最后收尾来一条。这样就不容易有历史垃圾。

## 延伸到真正长久的会话（20、30 轮）

上面讲的是"一个复杂 loop"。但对话可能连续聊 20、30 轮，每轮都是独立问答，**根本没有一个"触发整个任务的输入"**——这时锚点分级退场，靠的是**第一步的装配 + 第三步的替换**自然运转：

- 每轮进来照常装：最近的完整对话 + 记忆摘要填充缝。聊得越多，**装不下的旧轮次就自然被"替换"成它自己那份摘要**，让较新的对话始终优先在场。
- 于是体验是**渐变**的：前面十几轮原文都在（好），中间十几轮开始有些被换成摘要（还行，靠召回补），到了 30 轮，早前细节基本摘要化了（能跑，但早期代码 diff、具体数值这种细节会模糊）。
- 这是所有"摘要即记忆"系统的**物理极限**，不是 bug——它换来的是"永远装得下、不会突然崩"，代价是"早期细节逐渐变摘要"。真正重要的东西（用户偏好、结论、决策）被摘要保住了；极强的过程细节本来就不该占死上下文。

## 一句话合起来

> **一句话进来 → 搭好台（常驻设定 + 你的输入[顶级锚点独立划块] + 按百分比封顶召回的旧记忆 + 尽量多塞的最近对话）→ 要复杂就跑 loop，loop 里只追加不重装配 → 空间满了先"替换"成现成记忆摘要、没得换才"压缩"临时腾地方 → 四种结局（到轮数 / 摘要塞满 / 干完 / 输入太大预先拦下）→ 收尾时整段问答产出一条真记忆，loop 内的压缩摘要当场丢掉。长会话就反复用第一、三步自然运转，体验从"全原文"平滑退化成"摘要对话"。**
