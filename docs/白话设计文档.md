# memora 的白话运行机制

> 颗粒口径（2026-09-04 收敛定案）：**turn（问答闭环）** = 一次「用户输入 → 最终回答」的最小完整单元（一个 roundId）；**step** = turn 回答中阶段的一次 LLM 调用 + 可选工具执行；**loop（step 循环）** = 单个 turn 回答中阶段对 step 的编排（把"想一步 → 调工具 → 看结果 → 再想一步"串起来，收敛后所有复杂度在这里生长）；~~**多 turn 任务编排** = 一个复杂目标拆成多个 turn 串联（规划 turn → 步 turn 序列 → 收尾 turn）——已废弃，复杂任务在一个 turn 内的 step 循环里驱动。~~ 白话里尽量说"一次问答 / 一步思考-行动 / 一次回答内部 / 复杂任务在一次回答里逐步推进"，避免术语歧义。

## 一次完整对话，从用户敲下一句话开始

### 第一步：对话前的装配（外部输入触发）

你发一句话进来，系统开始**搭台子**，装四样东西：

1. **常驻设定**——这个角色是谁（persona）、规矩是什么（rules）、会哪些技能、能用哪些工具。这层是固定的，角色没换就不变。
2. **本轮你的输入**——就是你刚打的那句话。**它是整件事的"根"，从预算里独立划走一块空间，永不压缩**（稍后细说）。
3. **召回的记忆**——根据你这句话，从历史里把最相关的旧记忆捞出来。**捞多少，由角色包的「记忆百分比」封顶**：完整对话先优先装，剩下的空间才会塞旧摘要，而且塞的量不超过这个百分比。如果一句记忆都没捞到，就用 `minFallback` 兜底，塞几条最近的记忆凑数。**注意：这一步只在「新输入进来」时做——每次新输入就是新一次问答（新 turn）的开始，才重新装配；同一次回答内部的 step 循环不再重复捞。**
4. **完整对话记录**——当前会话聊过的话。从最近往回装，能装几轮装几轮（装到预算满为止）。**其中第一条问答必然在场**（它是这次会话的起点背景）。

> **两条铁律，先说清楚：**
> - **记忆百分比是"天花板"不是"份额"**：完整对话永远优先装，记忆摘要是"剩下的缝里塞一些"，不会反过来挤掉对话。
> - **触发输入和它触发的第一段回答是顶级锚点**：从预算最上游独立划走空间，同一次问答怎么推进都不压它。如果输入本身大到连这点空间都留不住，那系统在装配前就先拦住（下面第四步会说）。

### 第二步：一次回答内部怎么推进（loop：想一步 → 做一步 → 再看一步）

你一句话进来，系统先回答。**一次回答（一个问答闭环/turn）内部**，往往不是一口气说完的：先想一步、可能需要调工具、看到工具结果、再想下一步……

- **每一步 = 一次"想 + 可选行动"**：LLM 推理一次，必要时调用一个工具（读文件、搜网页、执行代码……），拿到结果再继续。这就是 **step**。
- **串起这些 step 的就是 loop**：loop 在"这次回答"内部反复拉起 step——推理 → 工具 → 回填 → 再推理，直到该收尾。**loop 只存在于一次回答内部，它不是"一轮接一轮地做多个任务"。**

关键点：**同一次回答内部的 step 循环，都不再召回记忆、也不再重新装配四件套**，只在拼好的上下文物件后面继续追加"这一步刚干完的事"。也就是说——**第一次的那个记忆召回结果是整次回答一直复用的一份**，不重复捞。换新目标、重新搭台，那是下一次新输入（新一次问答）的事。

**多 step 的目标锚定**：触发这次问答的那句用户输入 + 第一个回答，是整件事的"根"，**永不压缩**，还独立占一块空间。因为 loop 里的每个 step 都在朝它定义的目标推进，目标不能被吃掉。

### ~~第三步：复杂任务怎么拆（多 turn 任务编排：规划 → 分步做 → 收尾）~~（历史记录 · 2026-09-04 废弃）

> **收敛后的现状（2026-09-04）**：复杂任务不再拆成多个独立问答闭环串联。**所有复杂度（含任务表、会议多角色、动态进度追踪）在一个回答内部的 step 循环里自然生长**。步骤循环（想一步 → 调工具 → 看结果 → 再想一步）就是承载一切复杂任务的引擎——LLM 在循环里自主决定要不要建任务表（调 `task_table_write`）、要不要切换角色包（会议机制）、要不要暂停等用户输入。没有强制前置规划，没有跨 turn 串联，**一次外部输入 → 一个 turn → 一条摘要**。任务表工具全部保留，只是从"跨 turn 编排驱动"变为"单 turn step 循环内的动态进度追踪"。

如果一句话是复杂任务（比如"帮我修那个 bug"），一次回答装不下整个活儿。系统把这次输入**拆成多次问答闭环（多个 turn）串联**来推进：

1. **规划**（一个问答闭环）：LLM 先建一张任务表——要修 bug，先拆成"定位问题 / 改代码 / 跑测试"几步。
2. **逐步执行**（每个任务表步骤 = 一次独立问答闭环）：每做一步，就是一次新问答（独立 roundId、独立装配），只围绕这一步的目标。做完一步再拉起下一步。
3. **收尾汇报**（最后一个问答闭环）：所有步骤做完，系统跑一次收尾总结，产出最终报告。

这整套叫 **多 turn 任务编排**（代码里是 `externalTaskLoop`/`completeExternalTask`）。它和"一次回答内部的 loop"是**两码事**：

- **loop（step 编排）** = 一次回答内部把多个 step 串起来（"这一步有多深"），上限由角色包工具步数约束；
- **多 turn 任务编排** = 一个复杂目标把多个问答闭环串起来（"整个任务分几段做"），上限由角色包 `taskLoopLimit` 约束。

> **一句话分清楚**：loop 是"回答内部的推进"，任务编排是"问答之间的推进"。前者不动装配、不换目标；后者每段都是一次全新的问答闭环（重新装配、独立锚点）。把这两者混成一个"loop 跑多轮"，正是早先颗粒理解偏差的来源。

### 第四步：两级空间管理（先替换，再压缩）

无论一次回答内跑多少个 step、复杂任务分几段做，上下文总量有限，跑多了会满。空间的自我维护分**两级**，有明确的先后顺序和裁决归属：

**第一级 · 替换（内核自动做，几乎零成本）**
- 每个完成的问答闭环，收尾时都会存下一条记忆摘要。所以空间不够时，**系统自己按"最早的先换"的顺序，把最旧的一轮对话正文，换成它自己那条已存好的摘要**——不是重新写，是从库里拿现成的，几乎不花算力。
- **这是系统的机械动作，不用 LLM 出手**，也不用把它变成工具暴露给 LLM。最早的先换，纯按时间顺序来，确定、快。只有当某轮被替换后摘要太短、可能让上下文有点断时，系统才提示一句"细节可回溯"。

**第二级 · 压缩（替换无可换时，LLM 才捡起）**
- 作用对象是**还没有摘要可换的东西**——一次问答中途还没收尾的 step 现场、超大号的工具结果。
- 先把超长工具结果悄悄换成一句话占位（比如"之前用过 read_file"），这是**微压缩层**。
- 还不够，就由 LLM 主动调**压缩摘要工具**，把这些中途内容压成一条临时摘要。这叫**压缩摘要**，是当前问答闭环里的**临时产物**，**这次问答一结束就扔掉**，进不了记忆库。

> **一句话分清楚**：能换的，系统用现成摘要**替换**（LRU，最早先换，内核自动）；没得换的，LLM 才现场**压缩**。替换和压缩是同一个能力的两级，不是一个对另一个。真正的记忆摘要，是在一次问答闭环收尾后，由系统后端偷偷沉淀的那一条（见第六步）——压缩摘要和它不是一回事。

> **顺带说一句替换的脾气**：替换不是"一满就换"，而是"**最近的几轮先原样留着**——具体留几轮看上下文预算（预算够就多留、不够才换最老的），最老的那些再按先来后到换掉"。这样对话开头的连续性有保障，又不至于让旧内容无限占地方。另外，如果上下文被系统**截断**过（把中间剪掉重排），替换就暂时歇手——因为这时"哪轮对哪份摘要"的账目容易对乱，宁可不换，也别换错。

> **顺带说一句边界**：替换和压缩都**只碰"你刚说的话之前"的旧内容**——你当前发的那句输入是整件事的"根"，永远不动。极端情况（比如你一句话刚发出去、回答才刚开始，上下文就满到要压缩了）下，系统**不会**把你那句"根"压掉，而是直接说"没得压了"——这时它走的是"收尾"（见第五步软上限）：让模型把当前能给的结论交付出来，然后等你下一句。也就是说：**压不到根的时候，就该收尾了，不会硬压着根继续跑。**

> **顺带说一句互斥**：也许你担心"被替换成摘要的那轮，会不会下次又被召回一遍"？不会。召回只在"每次新输入进来"那一刻做一次，而且做之前先把"已经在场的东西（原文或替换后的摘要都算）"剔掉；替换发生在运行中，运行时不召回。所以被替换的轮次，下次装配时系统已经把它排除在外了，绝不重复装两遍。这套是代码里天然保证的，不用额外加机制。

### 第五步：回答/任务什么时候停

一次回答（或一个复杂任务的多段推进）什么时候停？总共看几个信号，哪个先到按哪个：

1. **硬上限**——复杂任务拆段时，角色包设了「最多跑 N 段（N 个问答闭环）」，到了 N 强制停下来（防死循环烧钱）。**但这不是硬切断**：它会报告"做到哪了、还剩什么没做"，然后等你再输入继续。你接着说一句，它按记忆重新接上。
2. **软上限**——上下文一路替换/压缩，压到最后，**除了顶级锚点，正文基本都变摘要了，摘要层也装满了**。这时候系统主动注入一个"收尾信号"，让 LLM 收敛，给出最终结论，停下来等用户。**这是"空间被摘要塞满"这个物理条件触发的，不是数段数数出来的。**
3. **自然结束**——任务自己干完了，LLM 交付就停。

**还有一个"还没开始就拦下"的判负**，比较特殊：

- 你贴了一大段特别长的内容当输入。大厂的做法是**输入框限长度**，超长就让你放文件里，用 `read_file` 读（**源头第一道防线**）。
- 就算没拦，系统**装配前会用公式算一遍**：输入勾起的一块空间 + 标准开销，够不够跑至少一段（一次问答闭环）？不够 → 直接提示"内容太大，建议放进文件读"，而不是让它硬跑起来然后误报成"摘要满了"（**装配前判负**，第二道防线）。输入端过大和"上下文把空间跑没了"，是两码事，分两条路处理。

### 第六步：记忆系统的沉淀（问答闭环收尾之后）

一次问答闭环结束（简单一句问答，或复杂任务的收尾汇报段），进入**收尾**：

- 系统在**这次用户输入对应的整段问答闭环结束**时，产出一条**记忆摘要**（一两句这个任务干了啥）。这条是**跨会话持久态**，真正存进记忆库，下次别处能召回。
- 记忆摘要在"问答闭环"级产出；一次回答内部的每个 step **不单产记忆**；复杂任务分多段做时，**只有收尾汇报那一段产唯一摘要**（规划段、中间执行段不单产，防历史垃圾）。这样就不容易有历史垃圾。

## 延伸到真正长久的会话（20、30 轮）

上面讲的是"一次输入的处理"。但对话可能连续聊 20、30 轮，每轮都是独立问答（独立问答闭环），**根本没有一个"触发整个任务的输入"**——这时锚点分级退场，靠的是**第一步的装配 + 第四步的替换**自然运转：

- 每轮进来照常装：最近的完整对话 + 记忆摘要填充缝。聊得越多，**装不下的旧轮次就自然被"替换"成它自己那份摘要**，让较新的对话始终优先在场。
- 于是体验是**渐变**的：前面十几轮原文都在（好），中间十几轮开始有些被换成摘要（还行，靠召回补），到了 30 轮，早前细节基本摘要化了（能跑，但早期代码 diff、具体数值这种细节会模糊）。
- 这是所有"摘要即记忆"系统的**物理极限**，不是 bug——它换来的是"永远装得下、不会突然崩"，代价是"早期细节逐渐变摘要"。真正重要的东西（用户偏好、结论、决策）被摘要保住了；极强的过程细节本来就不该占死上下文。

## 一句话合起来

> **一句话进来 → 搭好台（常驻设定 + 你的输入[顶级锚点独立划块] + 按百分比封顶召回的旧记忆 + 尽量多塞的最近对话）→ 一次回答内部由 loop 反复推进（想一步→做一步→再看一步，只追加不重装配）；太复杂的活儿拆成多段问答闭环来做（规划 → 分步 → 收尾汇报）→ 空间满了先"替换"成现成记忆摘要、没得换才"压缩"临时腾地方 → 三种结局（任务段数到顶 / 摘要塞满收尾 / 干完交付，输入太大则预先拦下）→ 每段问答闭环收尾时产出一条真记忆（复杂任务仅收尾段产），回答内部的压缩摘要当场丢掉。长会话就反复用第一、四步自然运转，体验从"全原文"平滑退化成"摘要对话"。**
