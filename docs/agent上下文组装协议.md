# Memora — Agent 上下文组装协议

> **定位**：Memora 的"脑子"——定义最终提示词如何拼装、记忆如何召回、话题如何归档  
> **关系**：本文档是 [agent设计.md](./agent设计.md) 的核心子系统细化，聚焦"记忆召回"和"上下文组装"  
> **参考**：[agent横向对比分析.md](./agent横向对比分析.md) 为本方案与主流 Agent 系统的底层逻辑横向对比  
> **核心公式**：`上下文（每轮提交给 API）= 用户主动输入 + Agent 记忆召回结果 + Agent Loop 工作记忆`  
> **核心哲学**：万物皆是记忆——人格、规则、技能、历史都是记忆，只是永久性不同  
> **日期**：2026-06-02 | **状态**：设计阶段

## 一、核心模型：三层模型（对外两层）

### 1.1 公式

```
上下文（每轮提交给 API）= 用户主动输入 + Agent 记忆召回结果 + Agent Loop 工作记忆
```

三层。不是两层，是三层。但对外（用户视角）仍然是两层——用户只关心"我说了什么"和"你找到了什么"。"Agent Loop 工作记忆"是 Agent 内部执行循环中产生的中间产物（工具调用结果、模型推理中间步骤），用户不需要感知。

### 1.2 三层定义

| 层 | 来源 | 内容 | 谁决定 | 生命周期 |
|----|------|------|--------|---------|
| **用户主动输入** | 用户 | 提示词文本 + 用户主动提及/引用的已知文本 | 用户 | 每轮刷新 |
| **Agent 记忆召回结果** | Agent 从记忆系统召回 | 永驻记忆 + 领域记忆 + 话题记忆 + 能力记忆 | Agent | 见 1.5 节 |
| **Agent Loop 工作记忆** | Agent Loop 执行产物 | 工具调用结果 + 模型中间回复 + 增量召回的上下文 | 模型自主产生 | Loop 内存在，Loop 结束后写入话题文件 |

### 1.3 为什么对外是两层

用户视角下只有两层：

1. 我说了什么（用户主动输入）
2. 你有没有找到相关的上下文（agent 记忆召回）

Agent Loop 工作记忆是 agent 内部执行循环的中间产物，用户不需要感知。就像你不需要知道搜索引擎在找到结果前访问了多少个索引分片。

**三层模型承认了一个事实：agent 的记忆系统有静态部分（预召回）和动态部分（执行中产生）。** 对外暴露两层（用户输入的 + 系统帮你找的），对内是三层（+ 执行中间产物）。

### 1.4 记忆召回结果的内部生命周期

记忆召回结果虽然对外是一层，但内部的四种记忆有截然不同的生命周期：

| 记忆类型 | 永久性 | 加载时机 | 刷新频率 | 变更触发 |
|---------|--------|---------|---------|---------|
| 人格记忆 | `always` | 启动时加载 | 永不刷新 | 仅当人格文件被手动修改后重新启动 |
| 规则记忆 | `always`/`domain` | 启动时加载 | 永不刷新（永驻规则）/ 领域切换时刷新（领域规则） | 仅当规则文件被手动修改后重新启动 |
| 话题记忆 | `topic` | 每轮对话前 | 每轮刷新 | 当前话题变化或话题漂移检测触发重填 |
| 能力记忆 | `on-demand` | 任务类型切换时 | 任务切换时刷新 | 用户切换技能或上下文触发工具集变更 |

**开发者调试指南**：
- 想测试不同人格 → 只需重启并加载不同的人格文件，话题记忆不受影响
- 想排查话题记忆加载错误 → 可以冻结永驻记忆，单独重填话题记忆
- 想测试不同技能 → 可以在运行时切换能力记忆，不重建整个记忆召回结果

### 1.5 Agent Loop 工作记忆的生命周期

工作记忆是 Agent Loop 执行过程中产生的瞬时记忆，生命周期最短：

| 记忆内容 | 产生时机 | 生命周期 | 最终去向 |
|---------|---------|---------|---------|
| 模型中间回复 | Loop 中每轮推理 | Loop 内存在 | Loop 结束后写入话题文件（作为话题记忆） |
| 工具调用结果 | 代码执行工具后 | Loop 内存在 | Loop 结束后写入话题文件（作为话题记忆） |
| 增量召回的上下文 | 模型调用记忆检索工具后 | Loop 内存在 | Loop 结束后标记为"已召回"，避免下次重复召回 |

**关键**：工作记忆不是独立存储的记忆类型——它是话题记忆在 Loop 内的"瞬时态"。Loop 结束后，工作记忆转为话题记忆的持久化记录。如果在 Loop 中崩溃，工作记忆丢失，但下次会话可通过话题记忆恢复大部分上下文。

## 二、Agent 记忆召回文档

### 2.1 概念

Agent 记忆召回文档是一个**独立的内存空间**，在对话启动时加载，在整个对话过程中**按永久性分级动态召回**。

它不是静态的模板，而是一个**活的文档**——每次对话轮次都根据当前任务从记忆系统中召回相关内容，按永久性从高到低填充到固定结构中。

### 2.2 文档结构

```
┌─────────────────────────────────────────────────────────┐
│              Agent 记忆召回文档                           │
│         (启动时加载到内存，按永久性分级动态召回)             │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  [永驻记忆] 人格 + 核心规则                               │
│  ├─ Agent 人格设定（permanence: always）                 │
│  └─ 全局常驻规则（permanence: always）                    │
│                                                         │
│  [领域记忆] 领域适配规则                                  │
│  └─ 领域规则（permanence: domain，按领域标签匹配召回）      │
│                                                         │
│  [话题记忆] 当前话题上下文 ← 按话题相似度动态召回           │
│  ├─ 同话题近期对话原文（最近 N 轮）                       │
│  ├─ 同话题历史话题报告（本周/本月）                     │
│  └─ 跨话题关联记忆（关键词检索召回）                       │
│                                                         │
│  [能力记忆] 当前可用的技能 + 工具描述                      │
│  ├─ 激活的技能说明文案（permanence: on-demand）           │
│  ├─ 可用工具的函数 Schema（permanence: on-demand）        │
│  └─ Few-shot 示例（可选）                                │
│                                                         │
├─────────────────────────────────────────────────────────┤
│  [工作记忆] Agent Loop 执行中的瞬时上下文                  │
│  ├─ 模型中间回复 + tool_call（Loop 内动态产生）            │
│  ├─ 工具调用结果 + 增量召回的上下文（Loop 内动态产生）       │
│  └─ 不占记忆召回文档配额，使用独立的工作记忆预算            │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

### 2.3 按永久性分级填充

记忆召回文档不是"塞满为止"，而是**按永久性分级填充**：

| 记忆类型 | 永久性 | 建议占比 | 填充策略 |
|---------|--------|---------|---------|
| 永驻记忆 | `always` | ≤ 10% | 启动时加载，对话期间不可变——Agent 人格设定 |
| 领域记忆 | `domain` | ≤ 15% | 启动时加载，对话期间不可变——全局规则 + 领域规则 |
| 话题记忆 | `topic` | 40%-60% | 每轮动态从记忆系统召回，按话题相关度排序 |
| 能力记忆 | `on-demand` | ≤ 10% | 按当前任务类型召回对应技能/工具 |
| **记忆召回文档合计** | — | **≤ 85%** | **为 Agent Loop 工作记忆预留 ≥ 15% 空间** |
| 工作记忆 | 瞬时 | ≤ 20% | Agent Loop 中动态产生，独立预算，不占记忆召回文档配额 |

**关键设计**：记忆召回文档最多占上下文窗口的 85%，剩余 ≥ 15% 预留给 Agent Loop 的工作记忆（工具结果、模型回复等）。工作记忆的实际使用上限为窗口的 20%，超出时触发上下文压缩（见 7.6 节）。

**比例不是硬编码，而是根据模型上下文窗口动态计算。** 128K 窗口和 1M 窗口的填充策略不同——但比例关系保持一致。用例：128K 窗口 → 记忆召回文档 ≤ 108.8K tokens，工作记忆预留 ≥ 19.2K tokens。

### 2.4 启动与执行流程

**阶段一：启动（记忆召回）**

```
1. 召回永驻记忆 → Agent 人格 + 核心规则（permanence: always，直接加载）
2. 召回领域记忆 → 领域规则（permanence: domain，按领域标签匹配）
3. 识别当前话题 → 从记忆系统检索同话题内容
4. 召回初始话题记忆 → 最近 N 轮对话原文（快速上下文预热）
5. 召回初始能力记忆 → 按当前任务类型匹配技能 + 工具（仅注入简短描述，不注入完整文案）
6. 校验 Token 预算 → 确保记忆召回文档 ≤ 上下文窗口的 85%
```

**阶段二：对话执行（Agent Loop）**

```
7. 记忆召回文档 + 用户输入 → 组装为 messages → 提交 API
8. 进入 Agent Loop → 模型推理 → 如有 tool_call（业务工具/记忆检索工具）则执行并回填结果 → 循环
9. 模型输出纯文本 → 循环结束 → 后置处理 → 记忆写入与沉淀
```

详见 [agent设计.md](./agent设计.md) 5.1-5.3 节。

## 三、记忆系统

记忆的定义和分层原则见 [agent设计.md](./agent设计.md) 第三章。

### 3.1 记忆的存储粒度

**以对话轮次为记录单元，以话题为组织维度。**

存储路径由初始化时的 `storageRoot` 和 `projectId` 共同决定：`<storageRoot>/projects/<projectId>/`。以下为单个项目内的目录结构：

```
<storageRoot>/projects/<projectId>/   # 由 Agent 初始化参数决定
├── session.json                      # 当前会话元信息
├── topics/                           # 话题文件目录
│   ├── topic-001.md                  # 话题 A 的完整对话记录
│   ├── topic-002.md                  # 话题 B 的完整对话记录
│   └── ...
├── agent.db                          # SQLite 数据库（FTS5 索引 + 向量索引）
└── archive/                          # 归档目录
    ├── 2026-06/                      # 按月
    │   ├── week-22/                  # 按周
    │   │   └── topic-001.md          # 封存的话题文件
    │   └── ...
    └── index.json                    # 归档索引
```

**多项目隔离**：不同 `projectId` 对应不同的子目录，各自拥有独立的 `topics/`、`archive/`、`agent.db`。详见 [agent设计.md](./agent设计.md) 9.4 节。

### 3.2 话题文件格式

每个话题文件是一个 Markdown 文档，以对话轮次为单位记录：

```markdown
# 话题：<话题摘要>

> 创建时间：2026-06-02 14:30
> 最后更新：2026-06-02 16:45
> 关联文件：file-a.md, file-b.md
> 关键词：关键词A, 关键词B, 关键词C

## 2026-06-02 14:30 | <轮次摘要>

**用户**：<用户输入内容>

**Agent**：<Agent 回复内容>

---

## 2026-06-02 14:45 | <轮次摘要>

**用户**：<用户输入内容>

**Agent**：<Agent 回复内容>

---
```

### 3.3 话题报告：陈旧话题的炼化形式

**当话题冷却后，原始对话原文不再是最高效的形式。** agent 不需要看到 37 轮原始问答，只需要知道：讨论了什么、决定了什么、当前状态是什么。

话题报告是**从原始对话中炼化出的结构化文档**，信息密度远高于对话原文：

```markdown
# 话题报告：<话题名>

> 覆盖时间：2026-06-02 ~ 2026-06-09
> 原始对话轮次：37 轮
> 关键词：关键词A, 关键词B, 关键词C

## 话题概要
一段话总结这个话题讨论了什么核心问题。

## 关键决策
- 决策1：<描述>
- 决策2：<描述>

## 当前状态
当前达成的结论或所处的阶段。

## 关键事实
- 事实1
- 事实2

## 关联文件
- file-a.md
- file-b.md

## 待解决问题
- 尚未解决的问题1
- 尚未解决的问题2
```

**对比原始对话**：
- 原始对话 37 轮可能 8000+ 字，agent 需要自行从中提取有用信息
- 话题报告 500-800 字，agent 直接拿到结构化的事实和决策
- **信息密度差一个数量级**

**炼化时机**：每日归档时，由 LLM 将当日对话原文炼化为话题报告。同一话题的多次炼化结果按以下策略合并：

**合并策略**：采用 **LLM 读取旧报告 + 新对话原文 → 重新整合** 模式。

1. 将旧话题报告（当前生效版本）和当日新对话原文一并提交给 LLM
2. LLM 输出一份**更新后的话题报告**（非增量补丁，是完整报告）
3. 更新后的报告进入**待确认区**（见 3.4 节），旧报告自动成为历史版本
4. 如果 LLM 整合失败（API 超时/返回格式错误），跳过当日合并，次日重试时包含两日的新对话原文

**冲突处理**：
- 如果新旧报告存在矛盾（如旧报告说"决定 A"，新对话原文显示"推翻了 A 改为 B"），LLM 应在更新报告中同时保留"历史决策：A（已推翻）"和"当前决策：B"
- 代码侧做关键词冲突检测（`决定`、`推翻`、`改为`），标记为"需人工复核"
- 用户确认时可以看到变更摘要：`[新增] 决策 B | [推翻] 决策 A | [保留] 事实 C`

**为什么不用"追加合并"**：追加会导致关键决策列表无限增长、互相矛盾。**为什么不用"全文替换"**：全文替换丢失了历史决策脉络，agent 无法理解"为什么从 A 变成了 B"。

**存储策略**：
- 工作记忆和短期记忆 → 保留对话原文（agent 需要精确的问答流）
- 中期记忆及更早 → 只用话题报告（agent 只需要事实和决策）
- 对话原文在炼化为话题报告后封存到归档目录，不再参与日常上下文填充

### 3.4 话题报告质量保障

**话题报告是单向门——一旦生成，原始对话原文封存归档，日常上下文不再加载。** 因此话题报告的质量直接决定 agent 的中长期记忆准确性。以下机制对抗 LLM 炼化时的幻觉风险：

**确认机制**：话题报告生成后，先进入**待确认区**（staging），不直接生效。用户在下一次打开相关话题时，agent 提示"检测到新的话题报告，是否确认？"用户确认后报告才进入活跃记忆池。未确认的报告在 7 天后自动过期删除。

**版本历史**：每份话题报告保留最近 3 个版本。用户确认新版时，旧版自动归档为历史版本。如果发现新版有问题，用户可以回退到任一历史版本。回退操作记录在报告元信息中（`> 回退自：v2 → v1，原因：关键决策错误`）。

**决策溯源**：话题报告中的每项"关键决策"必须标注来源轮次：
```markdown
## 关键决策
- 决策1：采用方案 B 作为主路由策略
  > 来源：2026-06-03 15:20 轮次，经 3 轮讨论后确认
```

这让用户和 agent 都能追溯"这个决策是从哪来的"。如果发现决策有误，可以定位到原始对话进行核实。

**原文索引保留**：对话原文封存后，归档目录保留一份 `原文索引.json`，记录每个话题文件的存储位置和关键元信息。紧急情况下（如话题报告全部损坏），可通过索引手工找回原文重新炼化。索引文件极小（每个话题约 200 字节），不构成存储负担。

**错误传播阻断**：每日归档时，如果 LLM 炼化结果与旧话题报告存在显著矛盾（如将"倾向 A"变为"决定 B"），代码侧做一次简单的关键词冲突检测（`倾向` vs `决定`），标记为"需人工复核"放入待确认区，而非自动合并。

### 3.5 话题切换与漂移检测

**不让 LLM 实时判断话题切换。** 采用纯文本计算的分层检测机制，零 API 调用，毫秒级完成。

#### 检测方式

每轮用户输入后，代码侧提取当前轮的关键词（TF-IDF），与当前话题标题及最近 5 轮的关键词做 Jaccard 相似度计算。根据相似度分层响应：

| 相似度区间 | 判定 | 响应 |
|-----------|------|------|
| ≥ 0.3 | 同一话题 | 默认延续，正常追加到当前话题文件 |
| 0.2 ~ 0.3 | 疑似漂移 | 话题记忆按**双轨制**填充：50% 旧话题上下文 + 50% 新话题探索（从全局话题索引中检索与当前轮关键词最匹配的话题报告）。继续延续旧话题文件，不提前分叉 |
| < 0.2 | 大概率新话题 | 主动提示用户"这似乎是一个新话题，是否切换？"——用户确认后归档旧话题、开启新话题文件；用户拒绝则延续旧话题 |

#### 其他触发方式

| 触发方式 | 说明 |
|---------|------|
| **显式切换** | 用户主动说"换个话题"、"另外问个事" → 直接归档当前话题，开启新话题文件 |
| **连续漂移自动切换** | 连续 3 轮落在"疑似漂移"区间（0.2~0.3）→ 自动归档旧话题，开启新话题文件 |
| **周期性整理** | 后台异步运行，批量归并话题，决定哪些轮次应归到已有话题、哪些应单独成题 |

#### 为什么不用 LLM 判断

LLM 判断话题切换的成本高、延迟高、可能反复横跳。文本相似度计算在毫秒级完成，零 API 调用。误判的代价是话题记忆多加载了 50% 无关内容——相比于"用完全错误的上下文回答"，这是可以接受的降级。

**关键**：周期性整理不影响实时对话，只影响归档结构。

## 四、话题记忆动态填充逻辑

### 4.1 填充策略

话题记忆是记忆召回文档的核心动态部分。每轮对话开始时，Agent 从记忆系统中召回与当前话题相关的内容。

填充优先级基于 [agent设计.md](./agent设计.md) 3.3 节定义的记忆分层体系（工作记忆 > 短期记忆 > 中期记忆 > 长期记忆 > 归档记忆），此处定义各层在话题记忆中的填充策略：

| 优先级 | 内容 | 来源 | 存储形式 |
|--------|------|------|---------|
| 1 | 同话题最近 N 轮对话原文 | 当前话题文件 | 原文 |
| 2 | 同话题昨日对话原文 | 当前话题文件 | 原文 |
| 3 | 同话题本周话题报告 | 每日归档产出 | 结构化话题报告 |
| 4 | 跨话题关联记忆 | 关键词检索召回 | 话题报告 + 索引 |
| 5 | 同话题归档话题报告 | 归档索引 | 话题报告 |

**自适应加载策略**：根据记忆总量动态选择全量加载或检索召回——

- **全量加载模式**：当总记忆量 ≤ 上下文窗口的 30% 时，跳过检索，将优先级 1-5 的全部内容加载到话题记忆。零检索延迟、零召回误差。适用于小规模项目或新 Agent
- **检索召回模式**：当总记忆量 > 上下文窗口的 30% 时，启动检索召回，按优先级从高到低填充，直到达到话题记忆配额上限。适用于大规模项目或长期运行的 Agent
- **切换判断**：在填充前计算总记忆量（所有话题文件的原文 + 所有话题报告的总 Token 数），与当前模型上下文窗口的 30% 比较。一次会话内不切换模式（避免填充策略抖动）

**设计理由**：Claude Code 采用"全量加载"（CLAUDE.md 全部注入上下文），在 1M token 窗口时代全量加载的可行性快速提升。但本方案面向通用场景，记忆总量可能远超代码 Agent 的 CLAUDE.md 文件。自适应策略在小规模时获得全量加载的可靠性，在大规模时保留检索召回的扩展性。

### 4.2 填充比例（自适应）

话题记忆内部按以下优先级填充，但比例**自适应**——当某个优先级无内容时，配额转移给下一个优先级：

```
默认比例（当所有内容均可用时）：

当前话题原文（最近 N 轮）  ████████████████████  60%
当前话题历史话题报告       ████████              25%
跨话题关联话题报告         ████                  15%
```

**自适应策略**：
- 无话题报告时（新话题）：当前话题原文占 85%，跨话题关联占 15%
- 无跨话题关联时：当前话题原文占 75%，话题报告占 25%
- 两者皆无时：当前话题原文占 100%，触发冷启动补白（见 4.3 节）

当 Token 预算不足时，按当前生效的比例**等比例压缩**——不是"先裁关联记忆再裁历史"，而是保持各区比例不变，等比例缩短。

### 4.3 冷启动补白

**新话题没有历史上下文。** 话题记忆按填充优先级检索后可能近乎空白，导致 agent 在缺乏上下文的条件下回答——表现骤然下降。

**补白策略**（仅当话题记忆填充后总 Token 低于话题记忆配额的 30% 时触发）：

| 优先级 | 补白内容 | 来源 |
|--------|---------|------|
| 1 | 领域规则摘要（最近的领域约束要点） | 领域记忆 → 领域规则文件 |
| 2 | 当前项目内热门话题报告摘要（从项目内话题索引中检索） | 项目归档索引 |
| 3 | 提示用户简述背景（"这似乎是一个新话题，能否简单说说你在做什么？"）| agent 主动询问 |

补白内容标注 `[冷启动补白]` 前缀，让 agent 知道这些不是精确的历史上下文，降低回答的确定性级别。

**用户可跳过**：如果用户明确说"不需要背景"或"直接回答"，跳过补白，直接基于用户输入和永驻记忆回答。

### 4.4 跨话题关联记忆召回

**不只按时间召回，还按关键词相似度召回。** 用户当前的问题可能跟几周前的话题更相关，而非昨天。

召回方式：
- FTS5 全文索引（关键词匹配）— 第一版实现
- Embedding 向量相似度（语义匹配）— 第二版实现

**向量检索技术选型（第二版）**：
- Embedding 模型：OpenAI `text-embedding-3-small` 或等价的本地模型（如 BGE-small-zh），选型标准为 512 维以上、中文语义理解良好
- 向量存储：SQLite 的向量扩展方案或轻量级 ChromaDB，优先选 SQLite 扩展以保持单文件无服务的架构一致性
- 更新策略：归档时同步更新向量索引（与话题报告炼化同批次执行），不额外增加 LLM API 调用
- 相似度计算：余弦相似度，阈值 0.7 以上纳入召回候选

**FTS5 中文分词说明**：SQLite FTS5 无内置中文分词器。第一版采用**简单二字分词**（每两个相邻字符作为一个 token），配合 ICU tokenizer 处理标点过滤。精度不高但零外部依赖，满足初期话题级检索需求。

## 五、与用户主动输入的边界

### 5.1 什么属于用户主动输入

| 内容 | 归属 | 理由 |
|------|------|------|
| 用户直接输入的提示词文本 | 用户主动输入 | 用户明确说的 |
| 用户主动提及的文本（选中、引用、粘贴） | 用户主动输入 | 用户明确指给 agent 看的 |
| 用户主动附带的文件/链接 | 用户主动输入 | 用户明确提供的 |

### 5.2 什么属于 Agent 记忆召回

| 内容 | 归属 | 理由 |
|------|------|------|
| Agent 基础设定/人格 | Agent 记忆召回 | 不是用户说的，是系统召回的人格记忆 |
| 常驻规则 | Agent 记忆召回 | 不是用户说的，是系统召回的规则记忆 |
| 话题上下文（记忆） | Agent 记忆召回 | 用户没有主动提及，是 agent 自己召回的话题记忆 |
| Skill 激活说明 | Agent 记忆召回 | 用户没有主动加载，是 agent 按需召回的能力记忆 |
| 工具描述 | Agent 记忆召回 | 用户没有列工具清单，是 agent 自己召回的 |
| Few-shot 示例 | Agent 记忆召回 | 用户没有提供示例，是 agent 从记忆中取的 |

### 5.3 边界判断原则

**一条铁律**：用户明确说出来的 → 用户主动输入。其余一切 → Agent 记忆召回。

如果有人问"那用户引用的文本需要附带元信息（文件名、行号），这些算谁？"——这些元信息是 agent 为了理解用户输入而自动附加的，属于 Agent 记忆召回。用户只提供了"这段文本"，agent 自己补充了"这段文本在哪"。

## 六、记忆类型的统一视图

### 6.1 万物皆是记忆

人格、规则、技能、工具、对话历史——都是记忆。区别仅在于永久性和召回确定性：

| 记忆类型 | 永久性 | 定义 | 加载时机 | 在记忆召回文档中的位置 |
|---------|--------|------|---------|----------------------|
| **人格记忆** | `always` | 行为准则、人格、原则 | 启动时加载，永驻 | 永驻记忆 |
| **规则记忆** | `always`/`domain` | 行为约束、专业规范 | 启动时加载/领域匹配时召回 | 永驻记忆/领域记忆 |
| **能力记忆** | `on-demand` | 技能（prompt 级）+ 工具（函数级） | 按需召回 | 能力记忆 |
| **话题记忆** | `topic` | 历史对话内容 | 按话题动态召回 | 话题记忆 |

### 6.2 技能记忆与工具记忆的本质区别

| 维度 | 技能记忆 | 工具记忆 |
|------|---------|---------|
| 层级 | Prompt 级别 | 函数级别 |
| 作用 | 改变"思考方式" | 提供"执行能力" |
| 调用通道 | 通过 prompt 引导 | 通过 Function Calling |
| 永久性 | `on-demand` | `on-demand` |

### 6.3 统一索引

所有记忆类型共享同一个 SQLite 索引表（见 [agent设计.md](./agent设计.md) 4.3 节）。这意味着：
- 一套检索逻辑服务所有记忆类型
- 跨类型检索成为可能（如"找到所有关于'数据库'的记忆"，包括规则、技能、对话历史）
- 索引维护只需一套管道

## 七、记忆的写入与压缩

### 7.1 写入策略

**实时写入 + 异步炼化。**

| 操作 | 时机 | 方式 |
|------|------|------|
| 追加对话原文 | 每轮对话结束 | 同步追加到话题文件 |
| 生成话题报告 | 后台异步 | 不阻塞对话 |
| 话题文件封存 | 达到封存阈值时 | 自动封存并新建文件 |

**实时写入的理由**：对话内容丢失是不可接受的。哪怕慢一点，也要保证写入。

**异步炼化的理由**：话题报告生成可以慢，不影响当前对话体验。

### 7.1.1 Agent Loop 中的上下文增长控制

Agent Loop 每轮工具调用结果会追加到上下文中，可能导致上下文突破配额。控制策略：

- **工具结果预算**：Agent Loop 中所有工具结果（含增量记忆检索结果）的 Token 总量不超过上下文窗口的 20%，来自 2.3 节为工作记忆预留的空间。记忆召回文档占 ≤ 85%，工作记忆预算 ≤ 20%——两者不重叠
- **单次工具结果截断**：单次工具调用结果超过 2000 字时截断（见 7.6 层级 1），确保单次结果不会独占预算
- **预算耗尽时**：工作记忆预算耗尽后，Agent Loop 不再执行新的工具调用，模型基于已有结果生成最终回答
- **配额恢复**：Agent Loop 结束后，工作记忆随对话历史一起写入话题文件，下一轮对话重新按配额分配

### 7.2 话题文件封存

同一话题文件超过以下阈值时封存，新建同名 `_v2` 文件：

| 触发条件 | 阈值 |
|---------|------|
| 对话轮次 | ≥ 50 轮 |
| 文件字数 | ≥ 10,000 字 |

满足任一条件即触发封存。

### 7.3 归档结构

```
archive/
├── 2026-06/                    # 按月
│   ├── week-22/                # 按周
│   │   └── topic-001.md        # 封存的话题文件
│   ├── week-23/
│   └── ...
├── 2026-07/
└── index.json                  # 全局归档索引
```

归档索引记录每个话题文件的元信息，供跨话题检索使用。

### 7.4 剪枝策略

**封存控制单文件大小，剪枝控制归档总量。** 没有剪枝的系统是只进不出的貔貅，磁盘迟早撑爆。

| 策略 | 触发条件 | 动作 |
|------|---------|------|
| **时间剪枝** | 归档文件超过 6 个月未访问 | 标记为"可剪枝"，下次归档时自动删除 |
| **容量剪枝** | 归档文件总数超过 1000 个 | 按最后访问时间淘汰最旧的 20%，优先淘汰无话题报告关联的原始对话 |
| **话题报告过期** | 话题报告超过 12 个月无任何会话引用 | 自动删除话题报告，保留原始对话索引（极端情况下可恢复） |
| **用户手动清理** | 用户主动触发 | 可按话题、按时间范围选择性删除 |

**保护机制**：
- 剪枝前 7 天发出通知，用户可取消
- 被剪枝的话题报告保留一个"墓碑记录"（话题名 + 关键词 + 删除时间），确保 FTS5 索引中不会出现"已删除但索引还在"的脏数据
- 话题报告被剪枝后，关联的原始对话原文一并删除（封存满 6 个月且无话题报告引用时）
- 用户手动标记为"永久保留"的话题免于自动剪枝

### 7.5 关键词生成

话题文件和话题报告中的关键词字段由以下流程生成：

**生成时机**：每日归档时，LLM 炼化话题报告的同时顺带生成关键词（≤ 5 个）。

**去重与归一化**：代码侧对 LLM 输出的关键词做去重和同义词归一化（如"数据库"和"DB"归一化为"数据库"），避免同一概念的关键词分散导致检索漏召回。

**人工可编辑**：关键词字段存储在话题文件的 frontmatter 中，用户可手动修改。如果用户手动设置了关键词，每日归档时 LLM 生成的关键词不覆盖用户设置。

**关键词与 FTS5 的关系**：关键词字段用于话题级检索（"找到所有关于'数据库'的话题"），FTS5 全文索引用于对话内容级检索（"找到所有提到'B+树'的对话"）。两者互补，不互相替代。

### 7.6 上下文压缩触发条件与上下文腐烂应对

**压缩触发条件**（借鉴 Claude Code 的五层压缩管道）：

| 层级 | 触发条件 | 动作 | 开销 |
|------|---------|------|------|
| 1 - 预算削减 | 单次工具调用结果超过 2000 字 | 截断工具输出，保留前 2000 字 + 末尾 500 字 | 低 |
| 2 - 轻量修剪 | 上下文利用率达到 85% | 移除话题记忆中优先级 4-5 的内容（跨话题关联 + 归档话题报告） | 低 |
| 3 - 等比例压缩 | 上下文利用率达到 92% **且** 剩余 Token 不足以容纳 2 轮完整对话 | 按 4.2 节比例（60%/25%/15%）等比例压缩话题记忆所有内容 | 中 |
| 4 - 实时炼化 | 单次对话超过 30 轮 | 将前 20 轮对话原文炼化为一个临时摘要（关键决策 + 当前状态），替换原文，保留最近 10 轮原文 | 高（需额外 API 调用） |
| 5 - 完全压缩 | 上下文利用率达到 98% | 将全部对话历史压缩为摘要，仅保留永驻记忆 + 最近 5 轮原文 + 摘要 | 高（需额外 API 调用） |

**设计原则**：先应用最不具破坏性的压缩，仅在更便宜的压缩策略不足时才升级。这与 Claude Code 的"惰性降级"策略一致。

**压缩粒度**：轮次级。压缩时以完整对话轮次为最小单位，不截断单轮对话（避免"上半句在上下文、下半句被压缩"的语义断裂）。

**压缩后恢复**：压缩后的上下文不可逆（对话原文已封存归档）。但归档的原文保留完整索引，用户可通过检索功能找回被压缩的内容。

**上下文腐烂应对**（借鉴 Cline 的 Focus Chain 策略）：

长对话中，模型可能因"Lost in the Middle"效应而迷失方向。引入**焦点注入**机制：

- **触发条件**：上下文利用率达到 50%（而非固定轮次数），之后每增加 15% 再次触发。50% 时注入初始焦点，65% 时刷新焦点，80% 时最后注入——在模型迷失之前就开始引导方向
- **注入方式**：在话题记忆顶部注入当前任务焦点摘要（"你正在做 X，当前进度 Y，下一步 Z"），确保模型不偏离主线
- **摘要来源**：首次注入从上下文组装时提取任务描述；后续注入从 Agent Loop 中动态生成——模型在 Loop 中产生的中间推理自然包含当前状态，代码侧提取关键句作为焦点摘要
- **与层级 4 实时炼化的配合**：当层级 4（30 轮实时炼化）触发时，焦点摘要由炼化产物提供，精度更高
- **注入预算**：焦点摘要控制在 200-300 字内，不挤占话题记忆配额（与"话题记忆注入前言"合并为同一消息）

**为什么用上下文利用率而非轮次**：30 轮对话在 8K 窗口和 128K 窗口中含义完全不同。128K 窗口中，30 轮对话可能只占 15% 的利用率，模型还远未迷失。用利用率触发能适配不同大小的上下文窗口。

## 八、跨会话记忆共享

**同一项目内的不同会话共享同一话题层的记忆。**

- 话题文件存储在项目级工作目录（`<storageRoot>/projects/<projectId>/topics/`）
- 同一项目的不同会话通过话题 ID 共享同一话题文件
- 写入时加锁（项目级别锁），避免同一项目内并发冲突

这允许用户在同一项目的不同会话中讨论同一话题时，agent 能自动关联之前的讨论内容。

**跨项目记忆不共享**：不同 `projectId` 拥有独立的存储目录，记忆数据完全隔离。如果用户需要在多个项目间共享某些话题记忆，可通过显式配置"共享话题"实现（未来功能）。

## 九、故障容错与降级策略

### 9.1 文件写入容错

| 风险 | 策略 |
|------|------|
| 写入中断（断电/崩溃） | 先写临时文件（`.tmp`），写入完成后校验 MD5，校验通过后原子重命名覆盖目标文件 |
| 磁盘空间不足 | 写入前检查可用空间（< 100MB 时拒绝写入，通知用户清理） |
| 文件权限异常 | 写入失败后重试 3 次（间隔 1 秒），3 次失败后降级为内存缓存，通知用户 |

### 9.2 数据库容错

| 风险 | 策略 |
|------|------|
| SQLite 数据库文件损坏 | 每日自动备份数据库文件（保留最近 7 天），损坏时从最近备份恢复 |
| 数据库锁超时 | 设置 30 秒锁超时，超时后记录日志并跳过本次索引更新，次日归档时自动补更 |
| FTS5 索引损坏 | 归档时做索引完整性校验（`SELECT count(*) FROM fts_table`），异常时自动重建 |

### 9.3 LLM API 容错

| 风险 | 策略 |
|------|------|
| API 调用超时/返回错误 | 重试 3 次（间隔递增：1s / 3s / 9s），3 次均失败则跳过当日归档 |
| 当日归档未执行 | 次日归档时合并两日的对话原文一起处理，最多累积 3 日（超过 3 日则只处理最近 3 日） |
| 话题报告格式错误（非标准 Markdown） | 代码侧校验输出格式，不符合模板的标记为"格式异常"，放入待确认区，不自动生效 |
| Token 超限（对话原文过长） | 按 4.2 节比例压缩对话原文后再提交 LLM 炼化 |

### 9.4 降级策略

当记忆系统核心组件不可用时，agent 进入**降级模式**：

| 故障组件 | 降级行为 | 用户体验 |
|---------|---------|---------|
| 话题文件不可读写 | 仅使用当前会话的对话原文（内存），不做持久化 | 功能受限但可对话，每次重启丢失上下文 |
| SQLite 不可用 | 停用 FTS5 检索，跨话题关联记忆召回降级为纯文件名匹配 | 检索精度下降，但不影响当前话题内对话 |
| LLM 归档连续失败 3 天 | 自动暂停归档，通知用户手动触发 | 话题报告不更新，对话原文继续写入 |
| 磁盘空间不足 | 暂停归档和封存，仅写入当前话题文件 | 历史记忆不再增长，当前对话不受影响 |

### 9.5 监控与恢复

- 每次归档执行后记录一条运行日志（时间、成功/失败、处理的话题数、错误详情）
- 连续失败时在 UI 中显示警告图标，点击可查看错误详情和手动重试入口
- 手动重试支持"仅重试失败的话题"和"全部重新归档"两种模式
