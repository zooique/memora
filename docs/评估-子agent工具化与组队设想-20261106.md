- 日期后缀对齐 `评估-memora设计质量-20260910.md` 的既有写法；不带 `-探索`，因为它不是开放探索，而是对一份已成形设想的核证与处置。
- 分工：`run_team_meeting-探索方案.md` 记已落地的单轮会议；`未来迭代方案-探索.md` 记多 agent 方向与开放点；`结论-工具分类与多会话拓扑-20261105.md` 记工具分类/多会话拓扑结论与「四样缺」；`目标模式生长探索-分层阶段化.md` 记 spawn fresh runChat 的阶段原型。本文只补它们没有的三件：① 本设想逐条对代码核证；② 跨包权限绑定的否决理由；③ 三个硬缺陷（中断那条已实测）。
- 证据纪律：只写符号名，不写行号；「已实现」= 代码在册，「前置」= 代码里尚不存在。

## 1. 这份文档是什么，为什么现在不落

它不是方案、不占 ADR、不进索引。现在不落有三条硬理由，任何一条未闭合就做，等于把缺陷放大成机制：

1. 它依赖「第二执行流 / 多会话并发」的地基。当前单 Agent 单活跃会话单把聊天锁；没有会话增删改查工具、没有会话完成事件、没有正交权限轴（见 `结论-工具分类与多会话拓扑-20261105.md` §2「四样缺」）。
2. 权限那一条已被否决（§7）。带着它落地，会把「人格与工具面不一致」固化成内核契约。
3. 三个硬缺陷（§8）：中断停不住（**已闭合**，2026-11-06 订正见 §8 第 1 条）、无递归深度、子轮次无归处。它们不是子 agent 才出现，前两个今天就能伤到用户。

**与台账 Step 3 的关系**：台账 Step 3 已登记「子 agent = 异步 fork 独立副本」并保持观察（2026-10-30 拍板不进 0.5.0），四个前置（写记忆 / 递归深度 / 工具子集与权限 / 成本）悬置。本文评估的是同一目标下的**同步工具形态**（父等子拿结果），**不替代 Step 3 的形态定案**；将来启动时默认仍选异步 fork，同步形态只做最小验证。因此本文不新增「子 agent 总体立项」的第二个真源，递归深度也不另立条目（归 Step 3 四件事②）。

## 2. 用户设想的原始表述（照登要点，不改写、不美化）

1. 子 agent 是**一个工具**：LLM 调用它创建一个子 agent、委派任务，等它做完，拿回提炼后的结果。
2. 子 agent 有**独立上下文空间**，等于独立运行，最后只回传提炼结果。
3. 结合**角色包组队**：用队友的角色包设定与规则创建子 agent；**能力继承队长**。例如白话方案设计师当队长，组了 memora 助手与共鸣小说家当队友，就能以队友的设计/规则/名字创建子 agent 去干活。
4. 没组队时，创建一个**空白**子 agent（不带设定与规则）。

## 3. `run_team_meeting` 的现状边界

- 入口是内置工具 `run_team_meeting`（只读工具），处理器是 `runTeamMeetingAssessment`。
- persona 来源：`RolePackManager.buildSystemPrompt(name)`，返回该角色的 persona、规则与技能清单；**不携带 capabilities，也不携带 L2 行为策略**。
- 上下文**不共享**：只拼一条 system（多角色 persona）＋一条 user（会议主题），不读当前会话历史。
- **单轮、无工具、无工具循环**：一次 `provider.chat()` 完成，不进入 `AgentLoop`。
- 返回**全文**：经 `sanitizeExternalText` 后截断到 `MEETING_RESULT_MAX_LEN`（20,000 字）。
- 同 step 并发**无上限**：`AgentLoop.executeToolCalls` 用 `Promise.all` 并发本批全部工具，没有信号量或队列。
- 结论：它是「只读单轮会议」的极简版，不是子 agent。设想真正新增的是四件：① 独立 `AgentLoop` 与工具执行；② 生命周期与中断；③ 子轮落盘；④ 结果提炼。

## 4. 组队现状

- `RolePackTeam { leader, members }` 类型已在册（`role-pack/types.ts`），并有校验函数与成员上限。
- 数据源是宿主设置 `memora.rolePackTeams`，经 `RolePackManager.setRolePackTeams` 注入，由 `RolePackManager.getActiveTeam` / 按组长名解析读取。
- 角色包 manifest **没有** `teams` 键（`validateManifest` 的允许键集合不含它）。
- 推论：组队是**全局一份**，不跟角色包走；换角色包不换队伍。用户说的「队长/队友」不是新词，但「用队友角色包创建子 agent」的**绑定规则是新的**。

## 5. 判定「半生长」+ 逐条依据（对八问）

**判定：半生长。** 团队容器、persona 取值、共享存储与回收能复用；「子 agent 作为独立实例的工具化」是另一套机制。

1. **`run_team_meeting` 边界**：见 §3。可复用 persona 取值与只读会议形态；新增四件，均为新机制。
2. **组队是否存在**：存在，但只是宿主级「全局一份」；manifest 无 `teams` 键。
3. **多实例地基能否直接支撑**：用户所称 E1–E6，代码中可核到的是——按会话的跨进程锁 `CrossProcessSessionLock`、共享的 `sessionStore` / `roundStore` 单例、GC 单调度点（`GCService` / `autoStartGc`）、`Agent` 按实例绑定事件、`AgentRegistry` 登记表。可复用的部分成立；但 `createAgentForSession` 不存在、`AgentRegistry.unregister` 零调用、`get` 未接线，且注册键按用户会话名。差：创建工厂、子会话标识、销毁、注册键。不能「登记即用」。
4. **父等子**：`FIRST_CHUNK_TIMEOUT_MS` / `INTER_CHUNK_TIMEOUT_MS` / `EVENT_STALL_TIMEOUT_MS` / `DEFAULT_TIMEOUT_MS` / `mergeAbortSignals` 都是单次请求的分段看门狗，不是工具总墙钟；工具执行本身没有总超时。`ToolRunner.raceToolWithSignal` 只负责「让调用方先拿到 ABORTED」，不负责杀执行；`runTeamMeetingAssessment` 的嵌套 `provider.chat()` 也不传 signal。所以「子 agent 跑几分钟」与超时链不冲突，冲突在「用户以为停了，实际没停」。
5. **递归**：全库没有 subagent / depth 概念（`list_dir` 的 depth 是目录深度，不是派生深度）；只有每个 loop 的 `L2RuntimeStrategy.stepBudget` / `toolStepLimit`。树状派生没有上界。
6. **权限归属**：唯一链是「激活包 capabilities → `Agent` 的 `resolveCapabilityTools` → `ToolExecutor.setToolWhitelist`」。三态语义：`undefined` = 全开、`[]` = 仅常驻、数组 = 白名单。`buildSystemPrompt(name)` 不带 capabilities / L2。所以「队友 persona + 队长 capabilities」两头错，见 §7。
7. **上下文隔离落点**：轮次先 `roundStore.save`，再由 `MessageHistory` 调 `sessionStore.appendRoundId` 登记进用户会话。复用父会话 → 用户会话列表多出子轮；不复用 → 孤儿轮。回收：启动时 `roundStore.sweepOrphans(DEFAULT_SWEEP_MIN_AGE_MS)`（24h 孤儿保护）、`GCService`（`minAgeMs` 5 分钟、`GC_INTERVAL_MS` 24h 扫描）、宿主 `.trash` 保留 7 天。所以「24h」是孤儿保护/扫描周期，不是总保留期；真正的「隐藏子会话」不存在。
8. **结果回传形态**：现形态是全文（20k 截断）。可接的提炼真源是 Reflect 阶段的 `RoundSummaryGenerator.generate`（绑 round 与事件），或 loop 内的临时 `compressContext`（收尾即弃）。前者不能直接当工具返回值，需要定义「子轮摘要 → 工具结果」映射。

## 6. 五条新造机制（指名）

1. **子 Agent 创建 / 销毁 / 注册**：工厂、注册键、子会话标识、生命周期。
2. **跨角色包的权限绑定**：人格 A + 权限 B 时谁裁决。
3. **子轮摘要 → 工具结果协议**：摘要形态、截断、错误态。
4. **递归深度 / 派生配额 / 树总预算**。
5. **隐藏子会话存储形态**（或明确的孤儿轮策略）。

## 7. 权限那条为何否掉

今天权限只有一个真源：**当前激活角色包的 capabilities**，由 `resolveCapabilityTools` 计算、`setToolWhitelist` 执行。

把「人格来自队友包、权限来自队长包」拆开后，两份声明冲突时**没有裁决点**。代码只能选一边，等于在真源之外新造第二份判据。更具体地说：

- 队长 `undefined` = 全开：队友人设说「我是只读设计师」，子 agent 却拿到写文件/跑命令能力——**放大**。
- 队长受限：队友本来会写的能力被裁掉——**缩小**，队友角色直接废掉。
- 无论放大还是缩小，LLM 看到的人设与可用工具面互相打脸：人设说不能，工具说能。这不是权限大小问题，是「谎报位点」同族——读者（模型与用户）信了，测试不会拦。

若一定要做，唯一站得住的规则是**取交集**（队长有效白名单 ∩ 队友自身声明能力），且 `undefined` 不得折叠成全开。但那已经不是「继承队长」，而是另立判据，需要单独设计与测试。所以现在否决这一条，不是「以后再说」。

## 8. 三个硬缺陷

1. **中断停不住**（今天就伤用户，已实测）：实测用真实 `ToolRunner` + `runShellCommand`，子命令睡 5 秒后写探针文件。对照组不中断：5.4s 返回 ok，文件写出；实验组 1.5s 中断：1.7s 返回 ABORTED，但 5 秒后探针文件**仍然写出** ⇒ 子进程没有随中断终止。受影响面：`run_command`、`run_project_script`、`run_skill_script`、`run_code`、宿主注册的自定义/MCP 工具。根因是工具执行签名不接 `AbortSignal`，`raceToolWithSignal` 中断胜出后 execute 仍在后台跑，结果被丢弃、动作继续。
   **2026-11-06 订正**：本条已由 `TOOL-ABORT-KILL-1` 落地闭合——`signal` 已贯穿到四个**子进程面**（`run_command` / `run_project_script` / `run_skill_script` / 宿主 `run_code`），中断先杀进程树再返回，终止未确认时结果带 `terminationError` 如实上报。**但自定义工具 / 内置文件工具等进程内面杀不掉**：只能经 `ctx.signal` 协作式感知，1.8s 宽限后由编排层兜底返回 ABORTED——这一段仍是本条的残留边界，不是「全部面已免疫」。
2. **无递归深度**：今天不存在派生概念，所以它不是「当前缺陷」，是**子 agent 前置**。但一旦允许子 agent 调子 agent，只有 per-loop 的 stepBudget，没有树总预算 / 派生数 / 深度，成本和中断都收不住。
3. **子轮次无归处**：也是**前置**。没有隐藏子会话；写父会话会污染用户会话列表，不写就是孤儿轮，只能靠 24h / 5min GC 与 `.trash` 7 天兜底，子轮生命周期无法被产品语义描述。

## 9. 最小可行第一步（若将来启动）

只做一条最小闭环：**无组队、无角色设定、只读工具、depth=1、结果为子轮摘要**。

- 复用：`Agent` 类本身（不另写第二套 loop）、共享 `sessionStore` / `roundStore`、GC 单点。
- 新增：一个子 Agent 创建工厂 + 一个工具入口；子轮不登记进用户会话（按孤儿轮交给既有 GC）；工具白名单 = 父有效白名单 ∩ 只读工具；中断沿工具 → 子 Agent 传播。
- 工作量三要素：约 6–8 个文件；**碰公开面**（新增 LLM 工具契约，可能需要扩 `AgentOptions`）；**无迁移**（沿用现有 round 格式，不新增持久化字段）。
- 这一步只验证「父等子、子独立跑、结果摘要回传、停止能停」，不验证组队与权限。

## 10. 明确不做清单

1. 队友 persona + 队长 capabilities（§7 已否决）。
2. 组队跟角色包走（manifest `teams`）。
3. 同 step 并发生多个子 agent。
4. 子会话的 UI 展示与持久化产品面。
5. 子 agent 再派生子 agent（depth > 1）。
6. 新存储格式 / 新协议 op / 新事件类型。
7. 无设定且默认全权的「空白子 agent」——默认 `undefined` = 全开，是最危险的组合；第一步不提供。

## 11. 触发条件（满足任意一组才重启评估）

0. **总闸**：台账 Step 3 的「重新评估触发」先成立（基础面收口、无更高优先级结构缺口）——本文不另造总闸，也不抢 Step 3 的形态定案。
1. **地基接线完成**：出现生产调用的 `createAgentForSession`，`AgentRegistry.get/unregister` 有实际使用，且多会话并发锁可用——才谈子 Agent 实例化。
2. **真实需求累计 ≥3 次（暂定 · 待复核 · 2026-11-12）**：用户连续要求「让另一个角色独立做完再给结论」，或 `run_team_meeting` 因「需要工具/多步」而失败的真实案例 ≥3 次（在台账登记，不凭印象）。**门槛位置暂定从「重启评估前」挪到「定案前」**——1 例真实需求即可重启评估并开只读排查，但「下结论 + 动共享结构」仍须累计 ≥3 例。本暂定决策按 SSOT + 自然生长 + 不带伤原则作出，待用户复核后升格为正式规则（台账 `DISCIPLINE-3CASE-THRESHOLD-1`）。
3. **组队需要跟包走**：出现「换角色包要换队伍」的真实用户诉求，或需要把队伍随角色包分发给别人。
4. **权限交集规则单独拍板**：有明确判据与测试，覆盖 `undefined` 不折叠成全开——否则 §7 的否决不解除。
5. 若 Step 3 的异步 fork 已落地，则本文的同步工具形态不再实现，直接复用同一执行入口，避免第二套执行面。
