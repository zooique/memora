# Memora — Agent 方案横向对比分析

> **定位**：本方案与主流 Agent 系统的底层逻辑横向对比，识别差距与优势  
> **对比对象**：Claude Code、OpenClaw (QClaw)、Trae、Cline  
> **日期**：2026-06-02 | **状态**：设计阶段

---

## 一、结论先行

**方案在"记忆系统"和"上下文组装"两个维度上达到了大厂水准甚至更优，但在"Agent 执行循环"和"工具系统"上还停留在增强型对话助手的阶段。**

如果目标是"最强的通用 Agent 系统"，Agent
Loop 是必须补上的结构性拼图。除此之外，方案在话题维度的记忆组织、话题报告炼化机制、两层 Prompt 模型、冷热分离存储、故障容错设计等方面表现突出。

**本次对比的核心发现已转化为设计改进，更新到 [agent设计.md](./agent设计.md) 和
[agent上下文组装协议.md](./agent上下文组装协议.md)。**

---

## 二、八大维度横向对比

### 维度 1：Agent 循环（核心差异）

| 系统            | 循环模型                     | 关键特征                                                        |
| --------------- | ---------------------------- | --------------------------------------------------------------- |
| **Claude Code** | `while-true` 单线程主循环    | 模型输出 tool call → 执行 → 结果回填 → 继续循环，直到纯文本输出 |
| **OpenClaw**    | 触发式 Agentic Loop          | 每次消息/心跳触发一次完整循环，tool-use 内部循环                |
| **Trae**        | 无固定 Plan 阶段的自适应循环 | 去掉了 Proposal 阶段，模型自主决定何时推理、何时执行            |
| **Cline**       | 递归执行引擎                 | 循环调用工具直到任务完成，Plan/Act 双模式                       |
| **本方案**      | ❌ 无 Agent 循环（已修复）   | 原为线性管线，现已增加 Agent Loop 层                            |

**核心差异**：大厂 Agent 系统拼装完上下文后，会进入一个 while 循环——模型可以调用工具，工具结果回填到上下文，模型再决定下一步做什么，循环往复直到任务完成。本方案原先只有"一次性对话"的增强版，现已补充 Agent
Loop 层。

> **已更新至** [agent设计.md](./agent设计.md)
> 第二章"整体架构总纲"和第五章"核心运行模块"。

### 维度 2：记忆系统

| 系统            | 记忆架构                                | 存储方式                        | 检索方式                                |
| --------------- | --------------------------------------- | ------------------------------- | --------------------------------------- |
| **Claude Code** | CLAUDE.md 四层层级 + Memory Tool        | 纯 Markdown 文件                | 无检索——全部加载到上下文                |
| **OpenClaw**    | 对话历史 + 语义嵌入 + 压缩摘要          | SQLite + sqlite-vec             | 混合检索（语义 + 关键词）               |
| **Trae**        | 长时记忆 + 会话记忆 + 代码知识图谱      | 分层存储                        | CKG 知识图谱 + 语义检索                 |
| **Cline**       | 无独立记忆系统，依赖上下文历史          | 会话转录                        | 无                                      |
| **本方案**      | ✅ 五层记忆（工作→短期→中期→长期→归档） | MD 文件 + SQLite（FTS5 + 向量） | 话题文件全量 + 话题报告 + 关键词 + 向量 |

**本方案在记忆系统上是最细腻的。**
五个层级的分层、话题报告炼化、冷热分离存储、剪枝策略——这些设计比 Claude
Code 的"全部塞进 CLAUDE.md"更精细，比 OpenClaw 的"一律存入 SQLite"更结构化。

**关键差异**：

- Claude
  Code 的记忆是"全部加载"的——零检索延迟、零召回误差，但容量受上下文窗口限制
- 本方案依赖检索召回——更大的记忆容量，但引入了"召回不准确"的风险

**已优化**：增加了自适应加载策略——小规模全量加载，大规模检索召回。详见
[agent上下文组装协议.md](./agent上下文组装协议.md) 4.1 节。

### 维度 3：上下文窗口管理

| 系统            | 压缩策略                    | 关键机制                                                                                                       |
| --------------- | --------------------------- | -------------------------------------------------------------------------------------------------------------- |
| **Claude Code** | 五层渐进式压缩管道          | Budget Reduction → Snip → Microcompact → Context Collapse → Auto-compact（92% 利用率触发）                     |
| **OpenClaw**    | 自动压缩 + 摘要替换         | 旧轮次摘要化，最近 N 轮保留原文                                                                                |
| **Trae**        | 上下文编辑 + Prompt Caching | 自动清除过时工具结果，缓存不变部分                                                                             |
| **Cline**       | 会话转录持久化              | 追加式 JSONL，不主动压缩                                                                                       |
| **本方案**      | ✅ 五层渐进式压缩管道       | 层级 1 预算削减 + 层级 2 轻量修剪 + 层级 3 等比例压缩（话题区 60%/25%/15%）+ 层级 4 实时炼化 + 层级 5 完全压缩 |

**本方案的压缩策略**借鉴 Claude
Code 的渐进式思想，但内部实现保持话题区结构完整性——层级 3 的等比例压缩确保"紧急压缩"不破坏话题记忆内部比例。

**已优化**：补充了压缩触发条件（92% 利用率 + 剩余 Token 不足 2 轮时触发）、压缩粒度（轮次级）、压缩后恢复策略、上下文腐烂应对（焦点注入）。详见
[agent上下文组装协议.md v3.3](./agent上下文组装协议.md) 7.6 节。

### 维度 4：Prompt 组装策略

| 系统            | 组装方式                                                                                             | 特点                                                          |
| --------------- | ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| **Claude Code** | 系统提示 + 工具 schema + 历史 + 用户输入                                                             | 单层扁平结构，CLAUDE.md 作为 user message 而非 system prompt  |
| **OpenClaw**    | SOUL.md + HEARTBEAT.md + 记忆 + 触发输入                                                             | 固定身份 + 任务清单 + 动态记忆                                |
| **Trae**        | 系统提示 + 工具池 + 上下文缓存 + 用户输入                                                            | Prompt Caching 优化成本，双层上下文窗口                       |
| **Cline**       | 系统提示 + 自定义指令 + 对话历史 + 工具定义                                                          | 流式拼装                                                      |
| **本方案**      | ✅ 三层模型（对外两层）：用户输入 + 记忆召回文档（永驻区/领域区/话题区/能力区）+ Agent Loop 工作记忆 | 四区比例填充（≤85% 召回 + ≥15% 工作记忆预留），按比例动态计算 |

**本方案的三层模型（对外两层）是这里面最优雅的抽象。**
对外只暴露"用户输入"和"Agent 找到的上下文"两层；内部承认"Loop 工作记忆"是动态产生的瞬时态。用户视角的简洁性与内部模型的完整性兼得。

**关键差异**：Claude Code 把 CLAUDE.md 作为 user
message 传递（概率性遵从），本方案把固定区放在 system
prompt 中（更高优先级遵从）。两种选择各有利弊，本方案的选择更适合"规则驱动"的场景。

### 维度 5：规划与执行

| 系统            | 规划模式                                   | 执行模式             |
| --------------- | ------------------------------------------ | -------------------- |
| **Claude Code** | 无显式规划阶段，TODO 式自组织              | 单线程循环执行       |
| **OpenClaw**    | HEARTBEAT.md 定义例行任务清单              | 心跳触发式           |
| **Trae**        | 已移除固定 Proposal，模型自主决定何时规划  | 统一 Agent 模式      |
| **Cline**       | Deep Planning（4 步：探查→澄清→规划→交接） | Plan/Act 双模式      |
| **本方案**      | 任务规划模块（大模型驱动）                 | Agent Loop（已补充） |

**Trae 从 2.0 开始去掉了固定的 Proposal 阶段**，理由是"刚性早期规划有时会让模型走上错误的路径"。Cline 则往相反方向走——Deep
Planning 的四步流程非常重。这两种策略的共存说明：**规划策略没有银弹，取决于目标场景。**

本方案定位为"通用 Agent"（而非纯代码 Agent），Trae 的"模型自主决定何时规划"策略更适合——因为通用场景的任务类型差异太大，固定规划流程反而会碍事。

### 维度 6：工具/扩展系统

| 系统            | 工具架构                                          | 扩展机制                                                     |
| --------------- | ------------------------------------------------- | ------------------------------------------------------------ |
| **Claude Code** | 19 无条件 + 35 条件 + MCP                         | 4 种扩展：MCP / Plugins / Skills / Hooks（按上下文成本分层） |
| **OpenClaw**    | 内置工具 + ClawHub Skills                         | 社区 Skill 注册表                                            |
| **Trae**        | MCP 协议 + 内置工具                               | MCP 生态                                                     |
| **Cline**       | 文件操作 + 终端 + 浏览器 + MCP                    | MCP 集成                                                     |
| **本方案**      | Skill 技能库（关键词路由）+ Function Calling 工具 | 三级规则体系 + Skill 库                                      |

**本方案在工具/扩展系统上目前是最薄弱的。** 大厂当前的共识是 **MCP（Model
Context Protocol）作为工具集成标准**。Claude Code、Trae、Cline 全部支持 MCP。

不过，如果本方案的 Agent 定位是"通用对话助手"而非"代码执行引擎"，工具集的需求本身就比代码 Agent 少得多。Skill 库设计（关键词路由 + 按需激活）对于轻度工具场景是合理的。后期应考虑 MCP 集成以扩展工具生态。

---

### 维度 7：安全与权限

| 系统            | 安全模型                                                    |
| --------------- | ----------------------------------------------------------- |
| **Claude Code** | 七层独立安全层 + Deny-First 规则 + ML 分类器 + 7 种权限模式 |
| **OpenClaw**    | 网关级身份认证 + 每代理允许/拒绝列表                        |
| **Trae**        | 沙盒执行 + 用户审批                                         |
| **Cline**       | Auto-Approval 系统 + 可配置权限                             |
| **本方案**      | ❌ 无安全/权限设计                                          |

**本方案完全没有安全设计。**
如果 Agent 是单用户本地运行的对话助手，安全需求确实很低。但如果涉及多会话并发写入、Skill 执行（如代码执行、文件操作），就需要考虑权限控制。这是阶段三需要补充的设计。

---

### 维度 8：主动性与自主性

| 系统            | 主动能力                                       |
| --------------- | ---------------------------------------------- |
| **Claude Code** | 纯反应式（用户触发）                           |
| **OpenClaw**    | 心跳机制：每 30 分钟主动检查任务清单，自动执行 |
| **Trae**        | 纯反应式                                       |
| **Cline**       | 纯反应式                                       |
| **本方案**      | ✅ 冥想机制（夜间归档）                        |

本方案的"冥想机制"借鉴了 OpenClaw 的心跳概念，但实现的是不同的东西——OpenClaw 的心跳是对外主动执行任务，本方案的冥想是对内维护记忆。两者不冲突，可以共存。未来可考虑增加类似 OpenClaw 心跳的对外主动任务检查机制。

## 三、本方案的优势（比大厂做得更好的地方）

1. **话题为维度的记忆组织**：大厂几乎都是"时间维度"或"会话维度"组织记忆，本方案按"话题"组织——同一个话题的对话聚合在一起，天然支持话题切换和跨会话关联。这是对的，因为人类的记忆也是按话题/主题组织的，不是按时间组织的。

2. **话题报告炼化机制**：从对话原文到话题报告的"信息密度跃升"。Claude
   Code 的 auto-compact 是类似的思路，但本方案的话题报告更结构化（关键决策、当前状态、待解决问题），信息密度更高。

3. **两层 Prompt 模型**：`最终提示词 = 用户主动输入 + Agent 智能提炼文档`——这个抽象在所有系统中是最干净的。其他系统都是"一堆东西拼在一起"，本方案从用户视角出发定义了清晰的边界。

4. **冷热分离存储**：文件承载本体 + 数据库承载索引——比 Claude
   Code 的"纯文件"更灵活，比 OpenClaw 的"纯 SQLite"更可读可编辑。

5. **故障容错设计**：本方案在容错方面的考虑（临时文件写入、MD5 校验、重试策略、降级模式）比大多数大厂方案的公开文档更细致。

## 四、已执行的改进

| 问题                   | 严重程度        | 改进措施                                     | 更新位置                      |
| ---------------------- | --------------- | -------------------------------------------- | ----------------------------- |
| 缺少 Agent Loop        | 🔴 结构性缺陷   | 增加 Agent Loop 层，定义工具调用循环         | agent设计.md 2.1 节、5.3 节   |
| 缺少压缩触发条件       | 🟡 工程细节缺失 | 定义 92% 利用率触发、轮次级压缩粒度          | agent上下文组装协议.md 7.6 节 |
| 话题切换过于保守       | 🟡 体验问题     | 增加每轮轻量级话题匹配，低阈值直接提示切换   | agent上下文组装协议.md 3.5 节 |
| 全量 vs 召回策略未区分 | 🟡 策略缺失     | 增加自适应加载策略：小规模全量，大规模检索   | agent上下文组装协议.md 4.1 节 |
| 缺少上下文腐烂应对     | 🟡 长期质量问题 | 增加长对话上下文重置机制（实时话题报告炼化） | agent上下文组装协议.md 7.6 节 |
| Skill 路由策略过于初级 | 🟢 阶段性问题   | 明确区分"Skill 选择"和"工具调用"两个阶段     | agent设计.md 4.3 节           |
