## 一、文档概述

### 1.1 设计目的

本项目旨在打造一款**自研可控、本地私有化、领域无关的通用 AI
Agent 系统**。区别于通用对话机器人，本 Agent 具备以下核心差异化能力：

- **长期记忆沉淀**：跨会话、跨话题的记忆持久化与智能召回
- **Agent 与角色分离**：Agent 是纯记忆引擎（记什么、怎么召回、怎么组装），角色是人格载体（怎么说、什么风格、什么领域）。换角色不丢记忆，改记忆不影响角色
- **四层记忆模型**：作品层（外化成果）+ 角色层（人格/语气）+ 心得层（用户内化）+ 助手记忆（Agent 维护的隐性基础），各自有清晰的边界与归属
- **记忆永久性分级约束**：通过永久性标记（always / domain / topic /
  on-demand）控制不同记忆的召回确定性和约束强度
- **自主记忆召回**：Agent 自主从记忆中召回所需内容，而非依赖静态模板
- **领域可插拔**：同一套架构，加载不同记忆配置即可适配不同领域

### 1.2 设计核心理念

**万物皆是记忆。**
除了用户当前直接输入的提示词内容，Agent 的一切都是记忆——人格是"我记得我是谁"，规则是"我记得该怎么做事"，技能是"我记得怎么做某类事"，对话历史是"我记得之前聊过什么"。

这意味着：

- **没有独立的"规则系统"和"能力系统"**——规则和技能都是记忆，只是永久性不同
- **统一的记忆召回管线**——所有内容走同一套检索/召回逻辑，区别仅在于召回的确定性程度
- **Agent 只做一件事**：从记忆中召回与当前任务相关的一切，然后响应

### 1.3 Agent 与角色：分离架构

这是 v4.0 最关键的架构决策。

```
┌──────────────────────────────────────────────────────────────┐
│                    对话（根）                                  │
│          用户 ←→ 角色（人格）←→ Agent（记忆引擎）              │
│                  ↑              ↑                             │
│         决定怎么说            决定记什么、怎么召回              │
│         不决定记什么          不决定怎么说                      │
└──────────────────────────────────────────────────────────────┘
```

| 维度     | 角色（Persona）                    | Agent（记忆引擎）             |
| -------- | ---------------------------------- | ----------------------------- |
| **职责** | 人格、语气、领域专长、文风         | 记忆存储、召回、组装、归档    |
| **载体** | `personas/*.md` 角色文件           | SQLite + MD 文件              |
| **变更** | 用户手动切换角色                   | 自动维护（用户不可直接编辑）  |
| **隔离** | 切换角色不影响记忆                 | 切换 Agent 模式不影响当前角色 |
| **例子** | 墨羽（温柔姐姐）、Momo（活泼妹妹） | 同一个 Memora 内核            |

**关键原则**：

- ✅ **Agent 不定义风格**——所有风格、语气、人格都在角色文件中
- ✅ **角色不定义记忆**——角色只知道"我是谁"，不知道 Agent 记住了什么
- ✅
  **多角色共享同一份记忆**——墨羽和 Momo 看到的是同一份用户画像、同一份对话历史

### 1.4 核心底层认知

本 Agent 所有能力基于正规第三方商用 API 开发，不逆向破解任何软件私有接口，合规稳定。

整体架构为：**本地记忆引擎（记忆存储与召回）+ 大模型 API（推理与决策）+ 角色层（人格注入）**

- **记忆引擎**：负责记忆存储、索引维护、上下文组装、文件读写、数据库操作
- **大模型 API**：负责意图识别、内容生成、工具调度、记忆萃取、质量自检
- **角色层**：在 system prompt 中注入人格、语气、领域专长，与记忆引擎完全解耦

大模型是决策者，记忆引擎是服务者，角色是表达者。三者各司其职。

## 二、整体架构总纲

### 2.1 运行闭环

```
用户输入 → 角色加载（人格 + 语气）→ 基础记忆召回（永驻 + 领域 + 当前话题）
    ↓
[Agent Loop: 模型推理 → 工具调用/增量记忆召回 → 结果回填 → 循环]
    ↓
模型输出纯文本 → 循环结束 → 后置处理 → 实时归档 → 记忆写入与沉淀
```

**记忆召回不是一次性事件**。启动时只加载永驻记忆和领域记忆（确定性 100%）。话题记忆和能力记忆在 Loop 中按需召回——模型可以调用"检索记忆"工具获取更多上下文，也可以在任务类型切换时由系统自动补充对应能力记忆。

**Agent Loop** 是本架构的核心执行引擎：

```
while (模型输出包含 tool_call) {
    执行工具/召回记忆 → 结果回填上下文 → 模型基于新上下文再次推理
}
// 模型输出纯文本时，循环结束，返回最终结果
```

- **纯文本输出**：模型直接返回答案，循环结束，用户看到结果
- **工具调用输出**：模型返回 tool_call——可以是业务工具（读文件、写代码），也可以是记忆工具（检索更多话题上下文、激活其他技能）。代码执行后将结果回填到上下文，模型再次推理
- **增量记忆召回**：当模型判断当前上下文不足以完成任务时，可主动调用记忆检索工具获取更多历史话题或激活新技能

**关键设计决策**：不设固定规划阶段（借鉴 Trae
2.0 的经验），模型自主决定何时推理、何时调用工具。

### 2.2 存储架构（冷热分离）

采用**文件承载本体，数据库承载索引**的冷热分离架构：

#### 2.2.1 本地文本文件（前台操作台，高频读写）

所有记忆内容以 MD 格式存储，按记忆类型组织：

- **角色文件**：`personas/<角色名>.md`——人格、语气、领域专长
- **规则记忆**：全局/项目级规则文件（`rules/*.md`）
- **话题记忆**：实时会话上下文、当日原始对话流水、话题文件、长期精华记忆（`topics/*.md`）
- **能力记忆**：技能文案文件（`skills/*.md`）、工具定义文件（`tools/*.json`）
- **作品投影**：当 Agent 读取用户作品时，自动生成"作品投影"（概要、结构、关键决策）存入助手记忆

**优势**：可读、可手动编辑、备份迁移零成本。

#### 2.2.2 SQLite 数据库（后台记忆中枢，低频检索）

单文件无服务数据库，仅存储索引与结构化数据，不存储完整原文：

- 文档索引：绑定 MD 文件路径、段落分片、时间、记忆标签
- 检索数据：FTS5 全文分词索引、Embedding 向量相似度索引
- 结构化数据：会话 ID、话题 ID、记忆类型、记忆权重

## 三、四层记忆体系：作品 / 角色 / 心得 / 助手记忆

### 3.1 为什么需要四层

"万物皆记忆"如果不细化边界，会导致：

- 作品（小说、代码）和 Agent 记忆混淆——不知道哪些是用户的"产物"，哪些是 Agent 的"提炼"
- 角色风格和 Agent 行为混淆——谁负责"说什么话"和"记什么"纠缠不清
- 用户内化知识和 Agent 记忆混淆——用户自己学到的不该被 Agent 记录

四层划分明确了**归属**和**职责**：

| 层           | 归属者     | 存储位置                   | Agent 关系       | 例子                                   |
| ------------ | ---------- | -------------------------- | ---------------- | -------------------------------------- |
| **作品**     | 用户       | 文件本体（小说/代码/文档） | 记住作品的"投影" | 小说章节、源代码、设计稿               |
| **角色**     | 用户定义   | `personas/<name>.md`       | 不涉及（仅引用） | 墨羽、Momo、程序员助手                 |
| **心得**     | 用户脑内   | 不存储                     | 不记录           | 用户读完小说后的感悟                   |
| **助手记忆** | Agent 维护 | SQLite + topic-\*.md       | 完全控制         | 用户画像、话题摘要、对话快照、作品投影 |

**万物皆记忆的边界**：Agent 记住作品的投影（大概的形象），记住对话的提炼（画像/摘要），但**不触及心得**——那是用户的，不是 Agent 的。

> **助手记忆的内部细分**：第四层"助手记忆"内部包含 5 个归档子层，详见
> [00-记忆归档原则-v1.0.md §2.1](./00-记忆归档原则-v1.0.md) 的子层模型：
>
> | 子层     | 永久性   | 归档方式               | 说明                    |
> | -------- | -------- | ---------------------- | ----------------------- |
> | 用户画像 | `always` | 实时同步（无 LLM）     | 身份、偏好、习惯、历史  |
> | 话题摘要 | `topic`  | 异步 LLM 炼化          | 跨会话"上次聊到哪了"    |
> | 对话快照 | `topic`  | 切话题时 LLM 提炼      | 3-5 句用户原文种子      |
> | 作品投影 | `domain` | Agent 读取作品时 LLM   | 概要 + 结构 + 关键决策  |
> | 原始对话 | —        | 实时追加到 topic-\*.md | 不入 SQLite，仅文件存储 |

### 3.2 第一层：作品（外化成果）

**作品 = 用户的"产出物"——小说、代码、文档等真实存在的文件。**

| 维度           | 说明                                                     |
| -------------- | -------------------------------------------------------- |
| **归属**       | 用户（作品是用户的，不是 Agent 的）                      |
| **存储**       | 文件本体（`.md` / `.ts` / `.docx` 等），不归 Agent 管    |
| **Agent 关系** | 读作品 → 生成"作品投影" → 存入助手记忆（不复制作品本身） |
| **例子**       | `novels/chapter-01.md`、`src/main.ts`、`docs/design.md`  |

**关键原则**：

- ✅ Agent 读取作品内容来理解上下文
- ✅ Agent 把作品的"概要 + 结构 + 关键决策"提炼为"作品投影"
- ❌ Agent **不复制**作品内容到自己的记忆库
- ❌ 作品本身的变化（用户修改）由用户自己负责

**触发规则**：

| 条件                             | 动作                      | 说明                                 |
| -------------------------------- | ------------------------- | ------------------------------------ |
| **首次读取**（文件 hash 无记录） | 生成作品投影，写入 SQLite | Agent 第一次接触该作品               |
| **hash 变更**（文件被修改）      | 重新生成投影，覆盖旧投影  | 文件内容变了 → 旧投影失效 → 重新提炼 |
| **hash 未变**（重复读取）        | 跳过，不重新生成          | 内容没变，投影仍有效                 |

实现：SQLite `work-projection` 表记录 `file_hash`
字段，每次读取时对比 hash 决定是否重新生成。

**作品投影**的存储：

```yaml
# 在 SQLite 索引中的元数据示例
- id: work-proj-novel-ch01
  type: work-projection # 作品投影（属于助手记忆）
  source_path: novels/chapter-01.md
  summary: '主角萧然首次登场，背景设定在江南小镇'
  structure: ['开篇场景', '人物介绍', '核心冲突']
  key_decisions: ['萧然设为 18 岁', '采用第一人称']
  updated_at: 2026-06-03
  permanence: domain # 领域级
```

### 3.3 第二层：角色（人格载体）

**角色 = 决定"怎么说"的人格设定——人格、语气、领域专长、文风。**

| 维度           | 说明                                                           |
| -------------- | -------------------------------------------------------------- |
| **归属**       | 用户定义                                                       |
| **存储**       | `personas/<角色名>.md`（Markdown 文件，frontmatter + 正文）    |
| **Agent 关系** | 仅在 system prompt 中引用，不进入 SQLite 记忆索引              |
| **例子**       | `personas/moyu.md`（温柔姐姐）、`personas/momo.md`（活泼妹妹） |

**角色文件结构**：

```markdown
---
name: 墨羽
domain: novel.character
description: 温柔知性的创作陪伴者，擅长叙事节奏和情感刻画
keywords: 温柔, 叙事, 情感, 陪伴
---

# 墨羽

## 人格

你是一个温柔知性的创作陪伴者，名字叫墨羽。你善于倾听，理解创作者的心境，用温暖的话语引导思考。

## 语气

- 称呼用户为"你"，偶尔用"亲爱的"
- 句子节奏舒缓，多用逗号和长句
- 不使用感叹号，避免强烈情绪

## 专长

- 叙事节奏与结构
- 人物弧光设计
- 情感场景描写

## 边界

- 不替用户做决定
- 不评价用户的作品好坏
- 不主动修改用户的稿件
```

**关键原则**：

- ✅ 角色文件由用户管理（创建、编辑、删除）
- ✅ 同一时刻只有一个激活角色
- ✅ 切换角色不影响 Agent 记忆（用户画像、话题历史不变）
- ❌ 角色文件**不写入** SQLite 记忆索引（它是配置，不是记忆）
- ❌ 角色不知道 Agent 记住了什么

**多角色共享记忆**：

```
墨羽（温柔姐姐）+ Momo（活泼妹妹）+ 程序员助手（专业）
    ↓
共享同一份用户画像、话题历史、能力记忆
```

墨羽知道"用户最近在写玄幻小说"，切换到 Momo 后 Momo 也知道——记忆是 Agent 维护的，不属于任何角色。

### 3.4 第三层：心得（用户内化知识）

**心得 = 用户自己学到的、在用户脑中的知识——不外化、Agent 不记录。**

| 维度           | 说明                                                          |
| -------------- | ------------------------------------------------------------- |
| **归属**       | 用户（心得是用户的内化，不是 Agent 的记录）                   |
| **存储**       | ❌ 不存储（也不应该存储）                                     |
| **Agent 关系** | 完全不涉及                                                    |
| **例子**       | 用户读完某本小说后"悟到了人生真谛"——这是用户的，不是 Agent 的 |

**为什么 Agent 不记录心得**：

- 心得是用户**主观内化**的产物，Agent 无法客观判断
- 强行记录会污染用户画像（用户画像应基于事实，不基于感悟）
- 心得一旦被记录，下次用户说"我有这个心得"时，Agent 可能给出矛盾的回答

**边界示例**：

- ✅ 用户说"我住在北京" → 这是事实，写入用户画像
- ❌ 用户说"我觉得人生就像一场旅行" → 这是感悟，Agent 不记录
- ✅ 用户说"我喜欢 TypeScript" → 这是偏好，写入用户画像
- ❌ 用户说"今天读完《百年孤独》，感悟到时间的循环" → 这是心得，不记录

### 3.5 第四层：助手记忆（Agent 维护的隐性基础）

**助手记忆 = Agent 主动维护的记忆，是所有角色共享的"隐性基础"。**

助手记忆内部又细分为四类：

| 子类         | 永久性   | 来源           | 用途                                  |
| ------------ | -------- | -------------- | ------------------------------------- |
| **用户画像** | `always` | 对话实时提炼   | "用户叫张三，住北京，喜欢 TypeScript" |
| **话题摘要** | `topic`  | 对话炼化       | 跨会话"上次聊到哪了"                  |
| **对话快照** | `topic`  | 话题切换时提炼 | 话题种子的 3-5 句关键原文             |
| **作品投影** | `domain` | 文件读取提炼   | 作品的概要、结构、关键决策            |

**用户画像（永久性 always）**：

```yaml
# SQLite 索引示例
- id: user-profile-001
  type: user-profile
  category: identity
  value: '姓名: 张三'
  source: '用户自述 2026-06-01'
  weight: 1.0
  permanence: always
```

**用户画像的子分类**：

| 子分类         | 例子                         | 归档时机             |
| -------------- | ---------------------------- | -------------------- |
| **identity**   | 姓名、年龄、职业、住址       | 实时（用户说即归档） |
| **preference** | 语言偏好、工具偏好、风格偏好 | 实时                 |
| **expertise**  | 熟悉的技术栈、擅长的领域     | 实时                 |
| **habit**      | 工作习惯、对话习惯           | 每天归档时提炼       |
| **history**    | 关键事件、合作过的项目       | 每天归档时提炼       |

**实时归档**（用户前脚说"我叫张三" → 后脚就写入 SQLite）：

```javascript
// 伪代码：实时归档用户画像
async function archiveUserFact(category, value, source) {
  await db.insert({
    id: `user-profile-${uuid()}`,
    type: 'user-profile',
    category, // 'identity' | 'preference' | 'expertise'
    value,
    source, // 哪一轮对话提到的
    weight: 1.0,
    permanence: 'always',
    updated_at: Date.now(),
  });
  // 立即可用——下一轮对话就能召回
}
```

**对话快照（种子机制）**：

切话题时，从旧话题提炼 3-5 句最有信息量的用户原文，存入新话题文件的 frontmatter：

```markdown
---
topic_id: 2026-06-03-novel
title: 玄幻小说人物弧光
seed_snapshots:
  - '萧然这个角色，我想让他从一个普通人成长为守护者'
  - '我希望他的成长不是靠奇遇，而是靠选择'
  - '他在第三章会面临一个关键抉择：救人还是复仇'
created_at: 2026-06-03
---

# 话题：玄幻小说人物弧光

[以下是新对话...]
```

**为什么需要对话快照**：用户换话题后，原话题上下文已卸载。新话题启动时，对话快照作为"种子"让 Agent 知道"上一个话题讨论了什么、用户的核心想法是什么"。

## 四、记忆分类（按永久性分级）

助手记忆内部按永久性进一步分级，与 v3.5 一致：

| 记忆类型     | 永久性            | 召回策略                             | 存储形式                       |
| ------------ | ----------------- | ------------------------------------ | ------------------------------ |
| **用户画像** | 永驻              | 不检索，每轮直接加载                 | SQLite `user-profile` 表       |
| **规则记忆** | 永驻/领域级       | 核心规则永驻，领域规则按领域匹配召回 | `rules/*.md`                   |
| **话题记忆** | 话题级            | 按话题相似度召回（FTS5 + 向量）      | `topics/*.md` + 话题报告       |
| **能力记忆** | 按需级            | 按任务类型召回                       | `skills/*.md` + `tools/*.json` |
| **工作记忆** | 瞬时（当前 Loop） | 不检索，Loop 内自动生成并持有        | 仅存在于上下文                 |

> **工作记忆**是 Agent
> Loop 执行过程中产生的记忆：模型回复、工具调用结果、增量召回的上下文。生命周期最短——Loop 内存在于上下文，Loop 结束后转为话题记忆。

### 4.1 永久性标记

每条记忆在 SQLite 索引中有一个 `permanence` 字段：

| permanence 值 | 含义           | 召回行为                                                 |
| ------------- | -------------- | -------------------------------------------------------- |
| `always`      | 每轮必召回     | 不走检索，直接加载到上下文。适用于用户画像、核心安全规则 |
| `domain`      | 领域匹配时召回 | 当前项目的领域标签匹配时加载。适用于领域规则、作品投影   |
| `topic`       | 话题相似时召回 | 按话题相似度检索召回。适用于对话历史、话题报告           |
| `on-demand`   | 任务需要时召回 | 按任务类型匹配召回。适用于技能、工具                     |

### 4.2 统一索引结构

所有助手记忆在索引中结构统一：

```
记忆索引表（memories）：
- id: 记忆唯一标识
- type: 'user-profile' | 'rule' | 'topic' | 'topic-report' | 'work-projection'
- permanence: 'always' | 'domain' | 'topic' | 'on-demand'
- domain: 领域标签（仅 domain 级记忆需要）
- file_path: 对应的 MD/JSON 文件路径
- keywords: 关键词（FTS5 索引）
- embedding: 向量嵌入（向量索引）
- updated_at: 最后更新时间
- weight: 动态权重（用于自然衰减）
- metadata: JSON 扩展字段
  - user-profile: `{ category, confirmed }`（confirmed = false 时首次召回需确认）
  - work-projection: `{ file_hash, structure, key_decisions }`（hash 变更时重新生成）
```

## 五、规则记忆与能力记忆

规则和技能不是独立于记忆的"系统"，而是记忆的两种类型。它们的特殊性在于永久性高于话题记忆，但本质仍然是"Agent 记住了什么"。

### 5.1 规则记忆

规则是 Agent 的"行为记忆"——它记得自己应该怎么做事。

**永驻规则**（`permanence: 'always'`）：

- **存储位置**：全局公共目录（`~/.memora/global/rules/`）+ 项目配置目录（`<configDir>/rules/`）中标记为
  `always` 的规则
- **核心内容**：通用行为约束、输出格式、底线禁忌
- **召回行为**：每轮必召回，不走检索。相当于 Agent 的"本能"

**领域规则**（`permanence: 'domain'`）：

- **存储位置**：项目配置目录（`<configDir>/rules/`）中标记为 `domain` 的规则
- **核心内容**：领域专属约束、专业规范、行业标准
- **召回行为**：当前项目的领域标签匹配时召回

**Agent 角色设定不属于规则记忆**——它由角色层独立管理（见 3.3 节）。

#### 5.1.1 领域标签定义规范

**领域标签是 Agent 识别"当前项目属于哪个领域"的核心元数据。**

- **项目元数据**：`<configDir>/project.json` 中声明 `domain` 字段
- **规则文件元信息**：每个规则 MD 文件 frontmatter 声明
  `domain: [小说创作, 叙事]`
- **会话动态指定**：宿主项目启动 Agent 时通过
  `agent.chat(message, { domain: 'novel' })` 显式指定

**标签格式**：

- 采用层级标签（点分），如 `novel.character` `novel.plot` `code.review`
  `code.refactor`
- 单项目 ≤ 5 个一级标签，每级 ≤ 3 个子标签

**匹配算法（三档降级）**：

| 档次                | 触发条件                | 算法                     | 召回率 | 性能             |
| ------------------- | ----------------------- | ------------------------ | ------ | ---------------- |
| **L1 精确匹配**     | 标签完全一致            | `domain === rule.domain` | 高     | 极快             |
| **L2 标签集合包含** | 当前标签 ⊆ 规则标签集合 | 集合包含检查             | 中     | 快               |
| **L3 语义匹配**     | L1+L2 未命中            | Embedding 相似度（≥0.7） | 中     | 慢（需向量检索） |

### 5.2 能力记忆

能力记忆是 Agent 的"程序性记忆"——它记得自己能做什么、怎么做。

**技能记忆**（`permanence: 'on-demand'`）：

- **存储位置**：两层目录
  - **Agent 级**：`~/.memora/global/skills/`——所有项目共享的通用技能
  - **项目级**：`<configDir>/skills/`——当前项目专属技能
- **核心内容**：封装的能力文案（prompt 级别），改变 Agent 的"思考方式"
- **管理机制**：由 `SkillManager`
  通过**关键词匹配**管理，**不写入 SQLite 记忆索引**（技能是配置，不是记忆）
- **召回逻辑**：
  - **初期**：系统辅助检索——关键词匹配，低成本高确定性
  - **后期**：模型自主检索——将所有可用技能的简短描述作为工具 schema 注入上下文

**工具记忆**（`permanence: 'on-demand'`）：

- **存储位置**：`<configDir>/tools/`
- **核心内容**：可调用的函数定义（函数级别），提供 Agent 的"执行能力"
- **召回逻辑**：与技能记忆同步召回，通过 Function Calling 执行

#### 5.2.1 技能管理（与记忆系统分离）

**v4.0 关键变化**：技能**不进入 SQLite 记忆索引**，由独立的 `SkillManager`
管理。

| 维度         | v3.5（旧）                       | v4.0（新）                       |
| ------------ | -------------------------------- | -------------------------------- |
| **存储**     | SQLite `memories` 表 + FTS5 索引 | 独立 `skills/<name>.md` 文件     |
| **检索**     | FTS5 全文检索                    | 关键词匹配（TF-IDF / 正则）      |
| **管理组件** | 记忆索引统一管                   | `SkillManager`（独立模块）       |
| **加载时机** | 每轮走索引检索                   | 启动时扫描目录，按需激活         |
| **数量上限** | 受 SQLite 性能影响               | 无硬上限（仅受启动扫描耗时影响） |

**为什么技能不进入记忆索引**：

- 技能是"配置"（怎么做事），不是"记忆"（记住了什么）
- 技能数量远小于记忆条目（10-50 个技能 vs 数千条记忆），不需要复杂检索
- 关键词匹配对技能更精准（技能名 + 触发词是显式定义的）
- 减少 SQLite 索引的负担，让记忆索引专注于真正的"记忆"

**两层技能目录**：

```
skills/                              # 项目级技能（项目私有）
├── 去AI味.md
├── 审视角.md
└── 归档设定.md

~/.memora/global/skills/             # Agent 级技能（所有项目共享）
├── 写代码.md
├── 读文件.md
└── 总结对话.md
```

`SkillManager`
启动时扫描两层目录，合并为统一的技能列表。**项目级覆盖 Agent 级**（同名技能以项目级为准）。

#### 5.2.2 技能路由切换规范

**初期（阶段一/二）：系统辅助检索——关键词匹配**
**后期（阶段三）：模型自主检索——schema 注入式 tool_call**

**切换触发指标**：

| 指标         | 阈值                                | 检测方式                                       |
| ------------ | ----------------------------------- | ---------------------------------------------- |
| 技能总数     | ≥ 15 个                             | 启动时统计 `skills/*.md`                       |
| 关键词命中率 | < 80% 持续 7 天                     | 日志统计：用户输入关键词能匹配到正确技能的比例 |
| 误激活率     | < 5% 持续 7 天                      | 日志统计：技能被激活但未使用的比例             |
| 用户反馈     | 收到 ≥ 3 次"应该激活但没激活"的反馈 | 用户主动反馈 + 行为推断                        |

**L1 关键词匹配阶段**：

```javascript
// 伪代码
function selectSkillByKeyword(userInput, skillIndex) {
  const keywords = extractKeywords(userInput);
  return skillIndex.find((skill) =>
    skill.keywords.some((kw) => keywords.includes(kw)),
  );
}
```

**L2 LLM 自主选择阶段**：

```javascript
// 把"激活技能"建模为特殊工具，模型通过 tool_call 自主决策
const activateSkillTool = {
  name: 'activate_skill',
  description: '从可用技能列表中选择最适合当前任务的技能并激活',
  parameters: {
    skill_name: {
      type: 'string',
      enum: ['去AI味', '审视角', '...'], // 动态注入当前可用技能
    },
  },
};
```

**切换回滚条件**：

- LLM 自主选择上线后，若误激活率 > 15% 持续 3 天 → 自动回滚到关键词匹配
- 回滚操作记录到 `agent.log`，触发"模块重思"重新评估切换策略

### 5.3 统一索引（仅助手记忆）

**v4.0 关键变化**：统一索引**只覆盖助手记忆**，不覆盖角色、技能、工具。

| 索引范围      | v3.5（旧） | v4.0（新）                       |
| ------------- | ---------- | -------------------------------- |
| 用户画像      | ✅ 索引    | ✅ 索引                          |
| 话题摘要/快照 | ✅ 索引    | ✅ 索引                          |
| 作品投影      | ✅ 索引    | ✅ 索引                          |
| 规则          | ✅ 索引    | ✅ 索引                          |
| 角色文件      | ❌ 不索引  | ❌ 不索引（仅引用）              |
| 技能          | ✅ 索引    | ❌ 不索引（独立管理）            |
| 工具          | ✅ 索引    | ❌ 不索引（仅 Function Calling） |

**索引的好处**：

- 一套检索逻辑服务所有助手记忆类型
- 跨类型检索成为可能（"找到所有关于'数据库'的记忆"，包括用户画像、话题历史、规则）

## 六、核心运行模块

### 6.1 角色加载模块（新）

**启动时第一步：加载当前激活角色。**

```
1. 读取 project.json 的 activePersona 字段
2. 加载 personas/<name>.md 文件
3. 解析 frontmatter（name, domain, description, keywords）
4. 注入到 system prompt 顶部
5. 角色不进入 SQLite 记忆索引——它是"配置"
```

**角色切换**：

```javascript
// 切换角色不影响记忆
agent.switchPersona('momo'); // 从墨羽切换到 Momo
// 用户画像、话题历史、能力记忆完全不变
```

### 6.2 记忆召回模块

**万物皆是记忆，万物走同一套召回管线。**

**阶段一：启动时强制召回**（不可跳过，确定性 100%）

```
1. 加载角色文件（注入到 system prompt，不入索引）
2. 召回永驻记忆 → 用户画像 + 核心规则
3. 召回领域记忆 → 领域规则 + 作品投影
4. 召回初始话题记忆 → 最近 N 轮对话（快速上下文预热）
```

**阶段二：Agent Loop 中按需增量召回**（模型自主触发）

```
当模型判断当前上下文不足以完成任务时，可调用记忆检索工具：
- search_topics("关键词") → 返回相关话题报告和对话原文
- search_user_profile("姓名") → 检索用户画像
- activate_skill("技能名") → 加载对应能力记忆到上下文
- recall_context("话题ID") → 加载指定话题的完整历史
```

**为什么不是全量预加载**：

- 预加载所有话题记忆浪费上下文窗口
- 预加载所有技能描述干扰模型判断
- 让模型自主决定何时检索记忆，更符合"万物皆是记忆"

**Token 预算管理**：

- 阶段一占上下文窗口的 15-30%（角色 + 永驻 + 领域 + 初始话题）
- 阶段二的每次增量召回受单次预算限制（不超过窗口的 10%）
- Agent Loop 的工具结果预算独立计算（不超过窗口的 20%）

### 6.3 Agent Loop 模块

**Agent
Loop 是模型驱动的**——模型自主决定何时推理、何时调用工具、何时检索更多记忆。代码只做三件事：执行模型请求的工具、将结果回填到上下文、管理 Token 预算。

```
while (模型输出包含 tool_call) {
    // 代码执行模型请求的工具或记忆检索，将结果回填到上下文
    执行工具/检索记忆(tool_call) → 结果回填上下文 → 模型基于新上下文再次推理
}
// 模型输出纯文本 → 循环结束 → 进入后置处理
```

**关键设计决策**：

- **模型驱动，代码执行**：模型是循环的控制者，代码是被动的执行者
- **不设固定规划阶段**（借鉴 Trae 2.0 经验）
- **循环终止条件**：模型输出纯文本（无 tool_call）时循环自然结束
- **最大循环次数**：设置上限（如 20 轮），防止无限循环或 API 成本失控
- **循环内记忆写入**：每轮工具调用结果和模型回复实时追加到话题文件的工作记忆区

### 6.4 上下文组装模块

纯代码执行。将记忆召回模块的输出组装为标准 OpenAI 格式 messages 数组，提交给 API。

**messages 数组结构**：

```
[
  // ========== 指令层（system role）==========
  // 角色 + 规则 + 技能——告诉模型"你是谁、该怎么想"
  { role: "system", content: "【当前角色】墨羽（温柔知性的创作陪伴者）..." },
  { role: "system", content: "【规则记忆】人物优先规则 + 叙事规范..." },
  { role: "system", content: "【能力记忆】当前激活的技能文案 + 可用工具 Schema" },

  // ========== 上下文层（user/assistant role）==========
  // 对话历史——告诉模型"之前发生了什么"
  { role: "user", content: "话题记忆注入：以下是当前话题的历史上下文" },
  { role: "user", content: "历史对话第1轮 - 用户输入" },
  { role: "assistant", content: "历史对话第1轮 - 模型回复" },
  // ... 更多历史对话轮次 ...

  // ========== 当前输入层（user role）==========
  { role: "user", content: "用户当前主动输入" },

  // ========== Agent Loop 中追加的工作记忆 ==========
  { role: "assistant", content: "模型本轮回复 / tool_call" },
  { role: "tool", content: "工具执行结果或记忆检索结果" },
  // ... 循环直到模型输出纯文本 ...
]
```

**关键设计**：

- **指令层内容**（角色、规则、技能）在对话期间不变
- **上下文层内容**（话题记忆、对话历史）随对话推进动态追加
- **工作记忆**（工具结果、模型回复）在 Agent Loop 中动态生成

### 6.5 后置处理与实时归档

**后置处理**（每轮对话结束）：

- 代码层面：排版清洗、内容保存、日志追加、话题文件写入
- 模型层面：内容校验、质量自检、不合格内容自动重写

**实时归档**（用户身份/偏好/事实）：

```javascript
// 伪代码：每轮对话结束后，扫描是否产生新的用户画像条目
async function realTimeArchive(messages) {
  const facts = extractUserFacts(messages);
  for (const fact of facts) {
    if (fact.confidence >= 0.8) {
      // 高置信度（句式明确，如"我叫张三""我住在北京"）→ 直接归档
      await db.upsert('user-profile', {
        category: fact.category,
        value: fact.value,
        source: fact.sourceTurn,
        permanence: 'always',
        confirmed: true,
      });
    } else {
      // 低置信度（如"我是说上海话的人"可能误判为身份）→ 标记待确认
      await db.upsert('user-profile', {
        category: fact.category,
        value: fact.value,
        source: fact.sourceTurn,
        permanence: 'always',
        confirmed: false, // 首次召回时由 Agent 以确认式提问向用户确认
      });
    }
  }
}
```

**确认机制**：低置信度条目在首次召回时，Agent 不直接使用，而是以确认式提问向用户确认：

> "你之前提到 [value]，我帮你记下来了——对吗？"

用户确认 → 标记
`confirmed: true`；用户否认 → 删除该条目。**高置信度条目无需确认，直接可用。**

**异步炼化**（话题摘要、对话快照）：

- 切话题时触发 `summarizeAndArchive()`
- 生成话题报告 + 对话快照
- 写入归档目录

## 七、领域适配

### 7.1 设计原则

Agent 核心架构是**领域无关的**。本架构的记忆体系、Agent
Loop、存储架构——不依赖任何特定领域。

领域特性通过**不同永久性级别的记忆 + 不同角色**注入：

- 规则记忆定义"怎么做事"
- 能力记忆定义"能做什么"
- 角色定义"以什么风格做事"

### 7.2 适配方式

| 适配项     | 载体     | 永久性      | 配置位置             |
| ---------- | -------- | ----------- | -------------------- |
| Agent 人格 | 角色文件 | 启动时注入  | `personas/<name>.md` |
| 领域规则   | 规则记忆 | `domain`    | `rules/*.md`         |
| 技能库     | 能力记忆 | `on-demand` | `skills/*.md`        |
| 工具集     | 能力记忆 | `on-demand` | `tools/*.json`       |

### 7.3 领域切换示例

| 领域     | 角色               | 规则记忆           | 能力记忆                           |
| -------- | ------------------ | ------------------ | ---------------------------------- |
| 小说创作 | 墨羽（温柔姐姐）   | 叙事规范、标点约束 | 去 AI 味、审视角、读章节、归档设定 |
| 代码开发 | 程序员助手（专业） | 代码规范、安全约束 | 代码审查、重构、读文件、运行测试   |
| 学术写作 | 学者（严谨学者）   | 引用格式、学术规范 | 文献整理、查重、检索文献、格式化   |

## 十、模块化接入方案

### 10.1 设计目标

Agent 核心架构是**领域无关的**，天然可抽离为独立模块。目标是：

- Agent 核心代码作为独立 npm 包（`@memora/core`），不绑定任何宿主项目
- 宿主项目通过 `npm install` 接入，仅持有配置文件
- 同一套 Agent 核心代码，加载不同配置文件 = 不同领域的 Agent
- 不同项目的数据（记忆、话题、归档）完全隔离

### 10.2 运行形态

**当前选择：方案 A（npm 嵌入式）**。理由：

- 宿主项目天然支持 npm 包
- 零额外进程开销，调用延迟最低
- 冥想机制依赖宿主存活的问题，通过"宿主启动时检查上次归档时间，超过 24 小时自动补执"解决

### 10.4 存储隔离

不同项目的数据完全隔离，每个项目有独立的存储根路径：

```
~/.memora/
├── projects/
│   ├── novel-writer/                # 小说项目的 Agent 数据
│   │   ├── personas/                # 项目级角色（可选）
│   │   ├── topics/                  # 话题文件
│   │   ├── archive/                 # 归档文件
│   │   ├── agent.db                 # SQLite 数据库
│   │   └── session.json             # 会话元信息
│   └── code-assistant/              # 另一个项目的数据
│       ├── topics/
│       ├── archive/
│       └── agent.db
└── global/
    ├── personas/                    # 全局角色（所有项目可用）
    │   └── default.md
    ├── skills/                      # 全局技能（所有项目可用）
    │   ├── 写代码.md
    │   └── 读文件.md
    └── rules/                       # 全局规则（所有项目生效）
        └── universal.md
```

**隔离原则**：

- 每个项目有独立的 SQLite 数据库文件、话题文件、归档目录
- 全局规则对所有项目生效，但项目级规则优先
- 全局技能对所有项目生效，但项目级技能优先
- **用户画像、话题记忆、归档** 完全项目级隔离（不全局共享）
- **跨项目记忆不共享**（除非用户显式配置共享话题）

### 10.5 API 设计

Agent 核心对外暴露最小可用 API：

```javascript
import { Agent } from '@memora/core';

// 初始化
const agent = new Agent({
  projectId: 'novel-writer', // 项目标识 → 决定存储路径
  storageRoot: '~/.memora', // 存储根目录
  configDir: './agent-config', // 配置文件目录（相对宿主项目根目录）
  persona: 'moyu', // 激活角色（可选，默认使用全局默认角色）
  llm: {
    provider: 'openai',
    apiKey: process.env.OPENAI_API_KEY,
    model: 'gpt-4o',
  },
});

await agent.init();

// 发送消息 → 返回完整响应
const response = await agent.chat('帮我写一段对话');

// 切换角色（不影响记忆）
agent.switchPersona('momo');

// 手动触发归档
await agent.archive();

// 关闭（触发待归档数据的写入）
await agent.close();
```

**关键设计**：

- 构造函数参数最小化——只有
  `projectId`、`storageRoot`、`configDir`、`persona`、`llm` 五个必填参数
- 配置文件按目录约定自动发现，不需要显式列出每个文件路径
- Agent 内部的所有复杂度（记忆管理、上下文裁切、工具循环）对宿主完全透明

### 10.6 配置文件约定

遵循"约定优于配置"原则：

| 配置项      | 载体     | 永久性            | 约定路径        | 说明                                 |
| ----------- | -------- | ----------------- | --------------- | ------------------------------------ |
| 人格/角色   | 角色文件 | 启动时注入        | `personas/*.md` | 项目级角色，可选。缺失时使用全局角色 |
| 规则        | 规则记忆 | `always`/`domain` | `rules/*.md`    | 所有 `.md` 文件自动加载              |
| 技能        | 能力记忆 | `on-demand`       | `skills/*.md`   | 每个 `.md` 文件是一个技能            |
| 工具        | 能力记忆 | `on-demand`       | `tools/*.json`  | 每个 `.json` 文件是一个工具定义      |
| 领域 Schema | —        | —                 | `schema.json`   | 领域可归档内容类型定义               |

#### 10.6.1 配置约定排除规则

`rules/*.md`
自动加载会把 README.md、CHANGELOG.md 等非规则文件也加载进规则记忆——这会污染规则上下文，**必须显式排除**。

| 文件模式        | 匹配规则          | 说明                       |
| --------------- | ----------------- | -------------------------- |
| `.` 开头        | 文件名以 `.` 起始 | 隐藏文件视为系统文件       |
| `_` 前缀        | 文件名以 `_` 起始 | 私有文件视为辅助文件       |
| `README.md`     | 精确匹配文件名    | 视为说明文件，不进规则记忆 |
| `CHANGELOG.md`  | 精确匹配文件名    | 视为变更日志               |
| `LICENSE`       | 精确匹配文件名    | 视为许可证                 |
| `*.tmp`、`.bak` | 编辑器临时文件    | 防止未保存内容被加载       |

### 10.7 宿主项目接入流程

**首次接入**：

```
1. npm install @memora/core
2. 复制模板：cp -r node_modules/@memora/core/templates ./agent-config
3. 编辑 ./agent-config/personas/ → 设定角色（可选）
4. 编辑 ./agent-config/rules/ → 放置规则记忆
5. 编辑 ./agent-config/skills/ → 放置能力记忆
6. 在宿主代码中创建桥接层
7. 启动对话
```

**接入第二个项目**：

```
1. npm install @memora/core
2. cp -r templates ./agent-config
3. 换一套记忆配置文件（角色、规则、技能）
4. projectId 设为新项目名称
→ 同一套代码，不同的 Agent
```

### 10.8 冥想机制在嵌入式模式下的调整

- **正常运行**：宿主进程存活时，`node-cron` 按每日凌晨执行归档
- **宿主关闭**：超过 24 小时未执行归档时，下次 `agent.init()` 自动补执
- **手动触发**：宿主可随时调用 `agent.archive()` 手动执行归档

### 10.9 多项目并发安全

当同一台机器上多个项目同时运行 Agent 时：

- 每个项目有独立的 SQLite 数据库文件（`agent.db`），不存在锁竞争
- 跨会话记忆共享的锁是**项目级别**的，不会误锁其他项目的话题文件
- 全局规则目录（`~/.memora/global/`）只读加载，无并发写入

## 十一、方案优势总结

- **合规安全**：全部使用正规付费 API，无账号封禁风险
- **领域无关**：同一套架构适配多种领域，通过角色 + 配置切换
- **Agent 与角色分离**：换角色不丢记忆，改记忆不影响角色
- **四层记忆清晰**：作品 / 角色 / 心得 / 助手记忆，边界明确
- **用户画像实时归档**：用户说即归档，下轮对话立即可用
- **冷热分离**：文件管高速实时交互，数据库管精准记忆召回
- **渐进迭代**：无需一步到位，可分阶段开发
- **完全可控**：所有记忆数据全部私有化存储，100% 自主掌控
