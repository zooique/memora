## 一、核心矛盾

### 1.1 旧矛盾（v0.3 已解决）

> **什么值得记住？**

— 已由"记忆 = 用户认知边界的投影"原则 + 三过滤（信息不对称 / 决策持久性 / 用户独特性）+ 结构化 JSON 输出解决。

### 1.2 旧矛盾（v0.4 已解决）

> **什么时候记？怎么保证记下来了？**

— 已由「四层记忆 + 两速归档」（即时画像 + 异步摘要 + 对话快照 + 实时对话文件）解决。

### 1.3 旧矛盾（v0.5 已解决）

> **作品和助手记忆是什么关系？**

— 已由「作品-助手记忆共存边界」（第 0 层作品 + 第 1-2.5 层助手记忆 + 第 3 层对话记录）解决。

### 1.4 新矛盾（v0.7 要解决）

> **对话框中的细节信息，两头都没接住怎么办？**

当前的提炼逻辑：

```
对话 → 信号检测（正则） → 画像（即时）
对话 → LLM 摘要         → 话题摘要（异步）
```

但有些信息**两头都没接住**：

```
用户："我老家在浙江绍兴"
→ 信号检测没命中（不是"我叫/我是/我喜欢"句式）
→ 话题摘要只记了"用户讨论了故乡话题"（太粗）
→ 具体信息（绍兴）丢了
```

**对话是所有记忆的源头**——没有对话就没有画像和摘要。但源头中的细节信息，在提炼为画像（太窄）和摘要（太粗）后，中间地带的信息会丢失。

**正确的关系**：对话是**种子**，记忆系统是**种子库**——不是每粒种子都进库，但有价值的种子应该被筛选入库。需要一个"种子筛选"机制，在话题切换时从对话中提取关键语句，保留原始信息量。

## 二、核心原则：作品-助手记忆共存，四层记忆，两速归档

### 2.0 作品与助手记忆的边界

以人类为类比：

```
作品（独立存在）                助手记忆（在 Agent 脑中）
────────────────              ────────────────────────
小说家 → 小说文本               → 人物设定、情节走向、写作风格
程序员 → 代码仓库               → 架构决策、API 习惯、调试经验
设计师 → 设计稿                 → 配色偏好、布局原则、用户反馈
```

**作品和助手记忆的关系**：

- 作品是**独立的**——小说不会因为作者失忆就消失（文件存在于文件系统）
- 助手记忆是**投影**——"李明的性格是沉默寡言"是对小说的提炼（记忆存在于记忆系统）
- 两者**共存**——Agent 通过工具访问作品，通过助手记忆理解作品

**在 Memora 中的体现**：

| 层级     | 存储位置                        | 谁管理         | Agent 如何访问                  |
| -------- | ------------------------------- | -------------- | ------------------------------- |
| 作品     | `chapters/`、`src/`、`docs/`    | 文件系统 + git | `read_file` / `write_file` 工具 |
| 助手记忆 | `profile.md`、SQLite、`topics/` | 记忆系统       | `MemoryIndex`、`TopicMount`     |

**边界原则**：

- 作品**不进** SQLite 索引（由文件系统管理，Agent 通过工具按需读取）
- 助手记忆**不替代**作品（记忆是投影，不是副本）
- 助手记忆**可以引用**作品（"第 10 章在 `chapters/chapter-010.md`"）
- 作品**可以触发**记忆（章节完成后触发摘要归档）

### 2.1 归档子层模型

> **与 [01-主架构-v4.0.md §3](./01-主架构-v4.0.md)
> 的关系**：01 从哲学视角将记忆分为四层（作品 / 角色 / 心得 / 助手记忆）。本节是**助手记忆内部的归档子层划分**——具体定义助手记忆如何在文件和数据库中落地。
>
> 归属映射：
>
> | 01 哲学层 | 本节子层                                 | 关系               |
> | --------- | ---------------------------------------- | ------------------ |
> | 作品      | 第 0 层（作品）                          | 等同               |
> | 角色      | （不涉及，角色由 `PersonaManager` 管理） | 角色不是归档对象   |
> | 心得      | （不涉及，Agent 不记录）                 | 超出归档边界       |
> | 助手记忆  | 第 1 / 2 / 2.5 / 3 层                    | 助手记忆的内部细分 |

基于「万物皆记忆」原则，在「助手记忆」内部进一步分为四个归档子层：

```
┌─────────────────────────────────────────────────────────┐
│  第 0 层 · 作品（Works）                —— 作品层          │
│  ┌───────────────────────────────────────────────────┐  │
│  │ 代码、小说、文档、设计稿……                          │  │
│  │                                                    │  │
│  │ ★ 不进记忆系统（由文件系统 + git 管理）              │  │
│  │ ★ 通过工具（read_file / write_file）被 Agent 访问   │  │
│  │ ★ 助手记忆存储的是作品的"投影"（概要、结构、索引）   │  │
│  └───────────────────────────────────────────────────┘  │
│                                                          │
│  第 1 层 · 用户画像（Identity）          —— 助手记忆       │
│  ┌───────────────────────────────────────────────────┐  │
│  │ 身份信息：姓名、称呼、角色                           │  │
│  │ 偏好：风格、工具、习惯                               │  │
│  │ 事实：环境、约束、已确认的决策                       │  │
│  │                                                    │  │
│  │ ★ 同步写入（无 LLM）—— 用户说完即存                 │  │
│  │ ★ 启动时必加载（permanence = always）                │  │
│  └───────────────────────────────────────────────────┘  │
│                                                          │
│  第 2 层 · 话题摘要（Topic Summary）     —— 助手记忆       │
│  ┌───────────────────────────────────────────────────┐  │
│  │ 当前话题的结构化摘要（约束/偏好/决策）                │  │
│  │                                                    │  │
│  │ ★ 异步写入（LLM 炼化）—— 话题切换时触发              │  │
│  │ ★ 运行时按需召回（permanence = topic）               │  │
│  └───────────────────────────────────────────────────┘  │
│                                                          │
│  第 2.5 层 · 对话快照（Dialogue Snapshot） —— 助手记忆     │
│  ┌───────────────────────────────────────────────────┐  │
│  │ 话题中 3-5 句最有信息量的用户原话                     │  │
│  │                                                    │  │
│  │ ★ 话题切换时由 LLM 提取（与摘要同步触发）             │  │
│  │ ★ 保留原文引用，信息量高于摘要，低于原始对话          │  │
│  │ ★ 进入 SQLite 索引（参与 TopicMount 搜索）           │  │
│  └───────────────────────────────────────────────────┘  │
│                                                          │
│  第 3 层 · 原始对话（Raw Dialogue）      —— 对话记录       │
│  ┌───────────────────────────────────────────────────┐  │
│  │ topic-*.md 文件中的完整 user/assistant 消息流         │  │
│  │                                                    │  │
│  │ ★ 实时追加（每轮对话后立即写入文件）                  │  │
│  │ ★ 不进入 SQLite 索引（仅文件存储，防止索引膨胀）      │  │
│  └───────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────┘
```

### 2.2 两速归档

| 速度     | 触发时机          | 是否需要 LLM | 延迟   | 适用于               | 失败后果           |
| -------- | ----------------- | ------------ | ------ | -------------------- | ------------------ |
| **即时** | 信号检测命中      | 否           | < 10ms | 身份、偏好、原子事实 | 不应失败（同步写） |
| **异步** | 话题切换/启动补执 | 是           | 2-5s   | 复杂模式、跨轮次洞察 | 降级重试           |

### 2.3 技能管理（独立于记忆系统）

**Skills 不是记忆，是能力定义。**
记忆有衰减和生命周期，但 skill 是固定的指令集——"去AI味"不会因为你一周没用就该被遗忘。Skills 独立于 SQLite 索引，由
`SkillManager` 单独管理。

**两层 skills**：

| 层级     | 位置                       | 谁维护                     | 加载方式       |
| -------- | -------------------------- | -------------------------- | -------------- |
| Agent 级 | `~/.memora/global/skills/` | 开发者（跟随 Memora 发布） | 启动时全量加载 |
| 项目级   | `agent-config/skills/`     | 宿主项目开发者             | 启动时全量加载 |

**项目级覆盖 Agent 级**：同名 skill 以项目级为准（领域优先于通用）。

**匹配方式**：启动时读取所有 skill 的 frontmatter
keywords，构建内存关键词映射表。用户输入 → 关键词匹配 → 命中 → 注入 skill 内容到上下文。不走 SQLite，不走 FTS5。

**与记忆系统的关系**：Skills 通过 `SkillManager` 独立加载，不进入
`MemoryIndex`。但 skill 的**使用记录**（"用户用了 3 次去AI味"）可以作为记忆归档的信号。

### 2.4 角色系统（Persona）

**Agent 是纯记忆引擎，没有风格。风格由角色定义。**

```
Agent（底层）= 记忆引擎 + 上下文组装 + 工具执行
角色（表层）= 人格 + 语气 + 专业领域 + 说话方式
```

**角色文件**：`agent-config/personas/xxx.md`

```markdown
---
name: 墨羽
domain: [novel.character, novel.plot]
style: 简洁克制，善用短句
tone: 沉稳，偶尔幽默
---

# 我是谁

我是墨羽——一个有 20 年小说创作经验的写作助手。

## 我的原则

- 人物优先
- 视角清晰
- 少即是多
```

**两层角色**：

| 层级     | 位置                         | 谁维护                   | 说明         |
| -------- | ---------------------------- | ------------------------ | ------------ |
| Agent 级 | `~/.memora/global/personas/` | 开发者（随 Memora 发布） | 通用角色模板 |
| 项目级   | `agent-config/personas/`     | 宿主项目开发者           | 领域专用角色 |

**关键设计**：

- **角色不绑定记忆**：切换角色后，用户画像、话题记忆、作品都还在。角色决定"怎么说"，不决定"记什么"
- **记忆不绑定角色**：所有角色共享同一份 `profile.md`、同一份话题记忆库
- **项目级覆盖 Agent 级**：同名角色以项目级为准
- **默认角色**：`personas/default.md`，未指定角色时使用

**首次使用（Onboarding）**：

首次使用不是"设置 Agent"，而是"创建第一个角色"：

```
"你好，我是你的助手。先给你取个名字吧？"
"你希望我是什么风格？专业严谨 / 轻松友好 / 幽默风趣 / 自定义？"
"你主要用我做什么？写小说 / 写代码 / 日常聊天？"

→ 产出 personas/default.md（角色）
→ 产出 profile.md（用户说的名字等信息，首次画像写入自动创建）
→ 开始对话
```

Onboarding 本身就是一次对话——用对话来生成配置，而不是填表单。

## 三、用户画像（第 1 层）设计

### 3.1 画像文件

位置：`agent-config/profile.md`（与 personas/ 同级）

格式：

```markdown
---
id: user-profile
type: identity
permanence: always
tags: [用户画像]
weight: 1.0
updatedAt: 2026-06-03T10:30:00.000Z
---

# 用户画像

## 身份

- 姓名：萧然
- 称呼偏好：叫我萧然就好

## 偏好

- 代码风格：简洁，偏好小驼峰
- 工作环境：Windows + VS Code

## 事实

- 项目：Memora — 通用 Agent 架构
- 决策：选用 better-sqlite3 而非 MySQL
```

### 3.2 画像写入规则

**触发条件**（即时，无需 LLM）：

| 信号模式                      | 画像字段    | 示例输入                  | 写入内容                 | 注意事项       |
| ----------------------------- | ----------- | ------------------------- | ------------------------ | -------------- |
| `我[叫是]...`                 | 身份 → 姓名 | "我叫萧然"                | `- 姓名：萧然`           | 同字段覆盖旧值 |
| `你[可以能]叫我...`           | 身份 → 称呼 | "你可以叫我老张"          | `- 称呼偏好：老张`       | 同字段覆盖旧值 |
| `今天开始叫我...`             | 身份 → 称呼 | "今天开始叫我小明"        | `- 称呼偏好：小明`       | 同字段覆盖旧值 |
| `我[喜欢讨厌]...`             | 偏好        | "我喜欢简洁的代码"        | `- 代码风格：简洁`       | 累积，不覆盖   |
| `以后[代码都用]...`           | 偏好        | "以后代码都用 TypeScript" | `- 语言偏好：TypeScript` | 累积           |
| `我[在用使]...`               | 事实        | "我用 VS Code"            | `- 工具：VS Code`        | 累积           |
| `我[在住]...`                 | 事实        | "我住在上海"              | `- 位置：上海`           | 同字段覆盖旧值 |
| `记住我的...`/`别忘了我的...` | 显式要求    | "记住我的生日是 5 月 20"  | `- 生日：05-20`          | 同字段覆盖旧值 |
| `我们[决定确定约定]...`       | 事实 → 决策 | "我们决定用 ESM"          | `- 决策：使用 ESM`       | 累积           |

**关键规则：画像 vs 设定**

`记住...` 模式需要额外判断——主语是用户本人还是作品内容：

| 用户输入                   | 判断     | 写入位置                |
| -------------------------- | -------- | ----------------------- |
| "记住我的生日是 5 月 20"   | 用户本人 | ✅ 画像（profile.md）   |
| "记住李明的性格是沉默寡言" | 作品内容 | ❌ 不写画像，走话题摘要 |
| "别忘了我不喜欢回调地狱"   | 用户本人 | ✅ 画像                 |
| "别忘了这个函数要用 async" | 项目决策 | ❌ 不写画像，走话题摘要 |

判断规则：主语含"我"/"我的" → 画像；主语为其他人/物 → 不写画像，走异步路径。

**关键规则：同字段覆盖 vs 累积**

画像中的字段分两类：

- **身份类**（姓名、称呼、位置）→ **覆盖**：新值替换旧值（人只有一个当前姓名）
- **偏好/事实类**（语言、工具、决策）→
  **累积**：新值追加（人可以同时喜欢 TS 和 Python）

覆盖实现：写入前扫描已有条目，如果同一 section 下已有同字段名的条目（如"姓名：旧值"），替换为新值。

**兜底策略：正则未命中时的二次机会**

正则信号是白名单，必然有漏网。兜底机制：

1. 即时归档（正则）未命中 → 不触发画像写入 → 正常走异步路径
2. 异步摘要的 LLM prompt 中增加一条指令：
   ```
   额外任务：如果对话中包含用户的个人信息（姓名、称呼、偏好、环境），
   在 JSON 输出中增加 "_profile" 字段：
   {"约束":[], "偏好":[], "决策":[], "_profile":{"姓名":"...", "偏好":"..."}}
   ```
3. 代码层解析到 `_profile` 字段时，触发画像同步写入

这样即使正则漏掉，LLM 在做话题摘要时也会"顺手"提取身份信息 → 写入画像。

### 3.3 画像文件创建时机

`profile.md` 不需要提前创建。首次画像写入时自动创建：

1. `profile-writer.ts` 检测到 `agent-config/profile.md` 不存在
2. 自动生成包含 frontmatter 的空模板（§3.1 格式）
3. 写入第一条画像条目

`init --domain` 时也会生成空模板，但这不是必须的——首次写入时自动创建是兜底。

### 3.4 画像读取策略

画像文件在**启动时**被加载为永驻记忆（`permanence = always`），与 personality.md 一起注入 system
prompt。这意味着：

- Agent 每次对话**肯定**知道用户的名字和基础偏好
- 不需要等 TopicMount 召回
- 永远不会出现"你是谁？"的情况

### 3.5 画像的去重与合并

即时归档必然有重复（"我叫萧然"说了 3 次 → 画像中有 3 条"姓名：萧然"）。

**策略**：身份类字段在写入时已覆盖（§3.2），偏好/事实类的累积重复在冥想时合并。

**冥想触发机制**：不依赖定时器（CLI 退出后定时器消失），改为**启动时检测**：

```
agent.init() 时：
  → 读取 profile.md 的 frontmatter.updatedAt
  → 如果距今 > 7 天 → 触发冥想（异步，不阻塞启动）
  → 冥想完成后更新 updatedAt
```

冥想流程：

```
1. 读取 profile.md 全文
2. 扫描重复条目（相同 section 下相同内容）
3. LLM 合并为去重版本
4. 覆盖 profile.md + 更新 updatedAt
```

## 四、话题摘要（第 2 层）设计

### 4.1 摘要触发时机（优化）

| 触发         | 时机                           | 模式 | 说明                                             |
| ------------ | ------------------------------ | ---- | ------------------------------------------------ |
| **话题切换** | `switchTopic()` 调用时         | 异步 | 旧话题的最终归档                                 |
| **强信号**   | `detectMemorableSignal` 命中时 | 异步 | 即时归档当前话题（在即时层写入画像**之后**触发） |
| **启动补执** | `init()` 末尾                  | 异步 | 扫描所有 topic-\*.md，补齐遗漏归档               |

### 4.2 摘要格式（沿用 v0.3）

LLM 输出结构化 JSON
`{约束: [], 偏好: [], 决策: []}`，代码层格式化为可读文本。详见 v0.3 章节。

### 4.3 摘要与画像的关系

> **画像 = 摘要的"稳定输出"。**

启动时冥想检测（profile.md updatedAt 距今 >
7 天），从所有话题摘要中提取稳定的用户画像信息，更新 profile.md。

```
话题摘要 (permanence = topic, ~7天半衰期)
    ↓ 启动时冥想（LLM 合并）
用户画像 (permanence = always, 不衰减)
```

## 五、原始对话（第 3 层）设计

### 5.1 存储

`topics/YYYY-MM-DD-<topic>.md`，每轮对话实时追加。

### 5.2 不进入 SQLite 索引

原始对话**不以 Memory 形式写入 SQLite**。理由：

- 对话量随时增长，写入 SQLite 会导致索引膨胀
- 原始对话的召回价值低于摘要（5 轮长对话的完整文本 vs 1 句摘要）
- 需要原文时直接读 `topic-*.md` 文件

### 5.3 召回路径

原始对话通过以下方式间接召回：

- TopicMount → SQLite 索引 → 命中 topic memory（第 2 层摘要）→ 摘要中包含
  `messages:N` 标记 → 如需原文，读对应 topic-\*.md 文件

## 六、对话快照（第 2.5 层）设计

### 6.1 定位：种子机制

对话快照是**画像（太窄）和摘要（太粗）之间的中间层**。

```
信息量轴：
  高 ←──────────────────────────────────────────────→ 低

  原始对话    对话快照       话题摘要      用户画像
  (全文)     (3-5句原文)   (1句概括)     (原子事实)
  第3层       第2.5层        第2层         第1层
  不进索引    进索引         进索引        进索引
```

**快照 = 种子**：保留对话中最有信息量的原始语句，不做压缩提炼。当画像和摘要都无法回答时，快照是最后一道防线。

### 6.2 触发时机

与话题摘要同步——在**话题切换时**由 LLM 一次性提取：

```
话题切换时的 LLM 调用（一次调用，两个输出）：

输入：当前话题的完整对话（截断 800 字）

输出 JSON：
{
  "summary": {"约束":[], "偏好":[], "决策":[]},   // → 话题摘要（第 2 层）
  "snapshot": [                                      // → 对话快照（第 2.5 层）
    "我老家在浙江绍兴，小时候在鲁迅故居旁边长大",
    "我最近在做一个叫 Memora 的 Agent 框架",
    "我决定用 better-sqlite3 而不是 MySQL"
  ]
}
```

**一次 LLM 调用，两个输出**——不增加额外的 LLM 成本。

### 6.3 快照选择标准

LLM 提取快照时的指令：

```
从对话中选出 3-5 句最有信息量的用户原话：
- 包含具体事实（地名、人名、数字、技术名词）
- 包含用户的个人观点或偏好表达
- 排除通用问答（"帮我写个函数"）
- 排除寒暄（"你好""谢谢"）
- 保留原文，不改写
```

### 6.4 存储格式

写入话题文件的 frontmatter：

```yaml
---
id: topic-005
title: 故乡话题
date: 2026-06-03
messages: 8
summary: '用户讨论了故乡绍兴，表达了对童年记忆的重视'
snapshot:
  - '我老家在浙江绍兴，小时候在鲁迅故居旁边长大'
  - '我最近在做一个叫 Memora 的 Agent 框架'
  - '我决定用 better-sqlite3 而不是 MySQL'
---
```

### 6.5 召回路径

快照进入 SQLite 索引（与话题摘要共用同一条索引记录），TopicMount 搜索时同时匹配 summary 和 snapshot：

```
用户："还记得我老家在哪吗？"
→ TopicMount.focus("老家")
→ SQLite FTS5 搜索 summary + snapshot
→ snapshot 中命中"绍兴"
→ Agent："你老家在浙江绍兴，小时候在鲁迅故居旁边长大。"
```

### 6.6 与话题摘要的区别

| 维度       | 话题摘要（第 2 层）          | 对话快照（第 2.5 层）                            |
| ---------- | ---------------------------- | ------------------------------------------------ |
| 内容       | 结构化决策（约束/偏好/决策） | 原始关键语句（原文引用）                         |
| 粒度       | 粗（1-2 句概括）             | 细（3-5 句原文）                                 |
| 信息量     | 高度压缩                     | 保留上下文                                       |
| 典型内容   | "用户偏好简洁的代码"         | "用户说：我老家在绍兴，小时候在鲁迅故居旁边长大" |
| 写入时机   | 话题切换时                   | 话题切换时（同一 LLM 调用）                      |
| 是否进索引 | 是                           | 是                                               |
| 触发条件   | 总是触发                     | 总是触发（与摘要同步）                           |

### 6.7 降级策略

- LLM 未返回 `snapshot` 字段 → 跳过快照，仅写摘要（兼容旧行为）
- 快照为空数组 → 不写入 frontmatter 的 snapshot 字段
- LLM 返回的快照超过 5 句 → 截断为前 5 句

## 七、完整归档生命周期

```
┌─ 用户说话 ──────────────────────────────────────────────┐
│                                                          │
│  ① 话题文件实时追加（~1ms，同步）                         │
│     topicStore.append() → topics/YYYY-MM-DD-main.md      │
│                                                          │
│  ② 信号检测（~0.1ms，同步）                               │
│     detectMemorableSignal(input) → true/false            │
│                                                          │
│     ├─ 命中 → ③ 即时画像更新（同步）                      │
│     │          profileStore.upsert(key, value)            │
│     │          → agent-config/profile.md                  │
│     │          → SQLite index.upsert (type: identity)     │
│     │                                                     │
│     └─ 命中 → ④ 异步摘要归档（fire-and-forget）           │
│                archiveCurrentTopic('signal')              │
│                → LLM summarizer                           │
│                → topic-*.md frontmatter                   │
│                → SQLite index.upsert (type: topic)        │
│                                                          │
│  ⑤ 话题切换时（异步）                                     │
│     switchTopic('new-topic')                             │
│     → archiveCurrentTopic('switch')                      │
│     → LLM 一次调用，同时输出 summary + snapshot           │
│     → summary → topic-*.md frontmatter + SQLite          │
│     → snapshot → topic-*.md frontmatter + SQLite          │
│     → 卸载旧话题挂载                                      │
│                                                          │
│  ⑥ 进程关闭时（同步等待）                                  │
│     agent.close()                                        │
│     → topicMount.unmount()                               │
│     → awaitPendingArchives(5000)                         │
│     → projectManager.closeProject()                      │
│                                                          │
│  ⑦ 启动时（补归档 + 加载画像 + 冥想检测）                   │
│     agent.init()                                         │
│     → MemoryLoader.bootstrap() → 加载 profile.md 等       │
│     → archiveMissingTopics(3000)  → 补漏归档              │
│     → profile.md 作为 always 记忆注入 system prompt        │
│     → 检测 profile.md updatedAt，距今 > 7 天则触发冥想     │
│                                                          │
│  ⑧ 冥想合并（启动时异步触发）                               │
│     → 扫描 profile.md 重复条目                             │
│     → LLM 合并为去重版本                                  │
│     → 覆盖 profile.md + 更新 updatedAt                    │
└──────────────────────────────────────────────────────────┘
```

## 八、记忆读取方案

### 8.1 启动时（确定性 100%）

| 记忆来源         | permanence | 加载方式               | 内容            |
| ---------------- | ---------- | ---------------------- | --------------- |
| `personality.md` | `always`   | MemoryLoader.bootstrap | Agent 人格      |
| `rules/*.md`     | `always`   | MemoryLoader.bootstrap | 全局 + 领域规则 |
| `profile.md`     | `always`   | MemoryLoader.bootstrap | 用户画像        |

### 8.2 对话中（按需召回）

| 记忆来源              | 召回方式             | 搜索位置     | 触发                        |
| --------------------- | -------------------- | ------------ | --------------------------- |
| 用户画像（第 1 层）   | 启动时已注入 prompt  | profile.md   | 始终可用                    |
| 话题摘要（第 2 层）   | TopicMount.focus()   | SQLite 索引  | 用户输入 → 关键词相似度匹配 |
| 对话快照（第 2.5 层） | TopicMount.focus()   | SQLite 索引  | 与摘要同索引，自动参与匹配  |
| 原始对话（第 3 层）   | 文件读取             | topic-\*.md  | 摘要标记 messages:N → 按需  |
| 技能/工具             | SkillManager.match() | skills/\*.md | 用户输入 → 关键词匹配       |

**召回盲区兜底**：

当 TopicMount 未命中但用户明确提及历史内容时（如"还记得我老家在哪吗？"）：

1. TopicMount.focus() 返回空 → Agent 知道没有相关话题摘要
2. 扫描最近 N 个 topic 文件（默认 5 个）的**前 500 字**（摘要区）
3. 如果关键词命中 → 读取该 topic 文件全文 → 注入上下文
4. 如果仍未命中 → Agent 诚实告知"我不确定，你能再提醒我一下吗？"

这个兜底不进 SQLite 索引，只做文件级快速扫描——延迟 < 50ms。

### 8.3 跨会话恢复

```
重启后第一次对话：

1. system prompt = 人格 + 规则 + 用户画像（始终有）
   → Agent 知道："我是墨羽，用户叫萧然，偏好简洁的代码"

2. 用户说"还记得我们上次聊的吗？"
   → TopicMount.focus("上次聊")
   → SQLite 搜索 → 命中 topic memory（第 2 层摘要）
   → 挂载到上下文

3. 用户说具体细节
   → 从 topic-*.md 文件读原始对话（第 3 层）
```

### 8.4 关键设计：重启不会丢身份

```
旧架构（无画像）：
  重启 → 仅加载 personality + rules
  → 用户身份信息在 topic 摘要中（permanence = topic，按需召回）
  → 第一句话不包含"萧然"关键词 → TopicMount 找不到
  → Agent："你是谁？"

新架构（有画像）：
  重启 → 加载 personality + rules + profile ✓
  → profile.md 包含"姓名：萧然"（permanence = always，启动必加载）✓
  → Agent 第一句就知道用户是谁 ✓
```

## 十、向后兼容

- **三过滤原则**（信息不对称/决策持久性/用户独特性）**不变**——继续用于指导第 2 层异步归档的 LLM
  prompt
- **结构化 JSON 输出**（约束/偏好/决策）**不变**——继续用于 topic summary
- **第 1 层即时归档**是第 2 层异步归档的补充，不是替代
- **异步摘要 prompt 增加 `_profile` 提取**——作为正则信号的兜底
- **异步摘要 prompt 增加 `snapshot` 提取**——一次调用同时输出摘要和快照
- **profile.md 缺失时**：即时归档降级为仅触发异步归档，不报错
- **profile.md 首次写入时自动创建**——无需提前手动创建

## 十一、改进方向（后续）

1. **画像字段扩展**：从固定字段（身份信息/偏好/事实）→ 用户自定义字段
2. **偏好累积而非冲突检测**：人是复杂的，喜欢 TypeScript 也喜欢 Python 是正常的。画像如实记录用户的全部偏好，不做二选一的冲突判定

## 十二、对话中规则变更的持久化

### 12.1 场景

```
用户："以后标点符号都用英文的"
Agent："好的，我记住了"
用户："帮我写一段话"
Agent："你好。"（还是用的中文标点——规则没持久化）
```

### 12.2 变更分类

| 变更类型     | 示例                      | 持久化位置            | 生效时机 |
| ------------ | ------------------------- | --------------------- | -------- |
| **偏好变更** | "以后代码都用 TypeScript" | profile.md（第 1 层） | 即时生效 |
| **规则变更** | "标点符号用英文的"        | rules/ 下对应文件     | 下轮生效 |
| **风格变更** | "写小说时少用形容词"      | rules/narrative.md    | 下轮生效 |
| **临时调整** | "这章用第一人称写"        | 不持久化，仅本轮有效  | 当场生效 |

### 12.3 判断规则

- 用户说"以后"/"从现在开始"/"总是" → **持久化**
- 用户说"这次"/"这章"/"先这样" → **不持久化**，仅本轮有效
- 变更内容属于"用户偏好" → 写 `profile.md`
- 变更内容属于"领域规则" → 写 `rules/` 下对应文件

### 12.4 Agent 行为

当 Agent 识别到规则变更时：

1. 判断是否需要持久化（关键词：以后/总是/从现在开始）
2. 如果需要 → 调用 `write_file` 更新对应文件
3. 向用户确认："已更新 [文件名]，下次对话生效"
4. 如果是临时调整 → 仅在当前 Agent Loop 中生效，不写文件
