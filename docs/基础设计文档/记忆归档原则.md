# 记忆归档原则 v0.3

> **状态**：已落地（结构化归档） **日期**：2026-06-03（v0.2 → v0.3）
> **来源**：v0.1 起始于「问诊：斩木除根」→ v0.2 落地三步判断 →
> v0.3 在「问诊：结构化归档」中升级为 JSON 结构化输出

## 核心矛盾

**什么值得记住？**

Agent 与用户的对话中，大量内容是 LLM 已知的通用信息。如果归档策略只是"总结对话"，会产生大量低价值记忆，淹没真正有价值的信号。

## 核心原则：记忆 = 用户认知边界的投影

大模型知道通用信息，用户也知道通用信息。**真正有价值的记忆，是用户认知边界上的东西**——用户知道但大模型不知道的（领域约束、偏好、项目上下文），以及用户不知道但通过提问暴露出的认知缺口。

## 三个过滤原则

| 原则       | 判断标准                   | ✅ 值得归档                 | ❌ 不值得归档      |
| ---------- | -------------------------- | --------------------------- | ------------------ |
| 信息不对称 | 这个信息是大模型不知道的吗 | "我的项目用 better-sqlite3" | "什么是 SQLite"    |
| 决策持久性 | 这个决策会影响未来的交互吗 | "用事件驱动替代 cron"       | "帮我写个排序函数" |
| 用户独特性 | 这个信息是用户独有的吗     | "我的部署环境不支持 Docker" | "Docker 怎么用"    |

## 记忆价值分层

```
┌─────────────────────────────────────────────────────┐
│  高价值记忆（值得归档）                               │
│  ┌───────────────────────────────────────────────┐  │
│  │ 1. 用户的领域知识 / 偏好 / 约束                │  │
│  │    "我的项目用 Vue3 + Vite"                     │  │
│  │    "我讨厌回调地狱，偏好 async/await"           │  │
│  │    "部署环境是 ARM64"                           │  │
│  │                                                │  │
│  │ 2. 用户提出的独特问题 / 罕见场景                │  │
│  │    "如何在 sqlite-vec 中做混合搜索？"           │  │
│  │    "我的路径白名单需要支持符号链接"              │  │
│  │                                                │  │
│  │ 3. 用户与 agent 共同达成的决策                  │  │
│  │    "我们决定用事件驱动替代 node-cron"            │  │
│  │    "覆盖率阈值从 80% 降到 75%"                  │  │
│  └───────────────────────────────────────────────┘  │
│                                                     │
│  低价值记忆（不值得归档）                             │
│  ┌───────────────────────────────────────────────┐  │
│  │ × LLM 的通用回答（大模型已知的通用信息）        │  │
│  │ × "递归函数怎么写" → 标准教科书回答             │  │
│  │ × "什么是 REST API" → 通用解释                  │  │
│  │                                                │  │
│  │ × 闲聊 / 寒暄                                  │  │
│  │ × 用户随口一问但未深入的话题                    │  │
│  └───────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────┘
```

## 对当前归档策略的反思

当前 `createTopicSummarizer` 的策略是：收集 user 消息 → 让 LLM 总结。

**问题**：可能把"帮我写个递归函数"总结成"用户请求了递归函数实现"，这种总结毫无价值——它既不是用户的领域约束，也不是持久决策。

## v0.2 实现方案（已落地）

**改造文件**：`cli/repl.ts` · `agent/message-history.ts` ·
`agent/__tests__/message-history.test.ts`

### 三步归档流程

```
createTopicSummarizer 的 LLM prompt 分三步：
┌────────────────────────────────────────────────────┐
│ 【第一步：判断价值】                                  │
│   分析用户提问是否具有：                               │
│   - 信息不对称（透露了大模型不知道的项目信息）           │
│   - 决策持久性（做出了会影响未来的决策）                │
│   - 用户独特性（是用户特有的场景，非通用问答）           │
│                                                      │
│   → 低价值对话 → 返回 SKIP，跳过归档                   │
│   → 高价值对话 → 继续第二步                            │
│                                                      │
│ 【第二步：精炼核心】                                   │
│   提取用户提问/观点中最有价值的信息                      │
│                                                      │
│ 【第三步：收敛回答】                                   │
│   提取 Agent 回答中与核心相关的关键要点                  │
│                                                      │
│ 输出：1-2 句中文精炼记忆，或 SKIP                       │
└────────────────────────────────────────────────────┘
```

### 技术细节

| 机制      | 说明                                                                       |
| --------- | -------------------------------------------------------------------------- |
| SKIP 信号 | `TopicSummarizer` 返回 `null` → `summarizeAndArchive` 跳过 `appendSummary` |
| 输入优化  | 从"只取 user 消息"改为"收集完整对话"（user + assistant），截断 800 字      |
| 输出解析  | 检查 `SKIP`（大小写不敏感）或空白 → 返回 null                              |

### 测试覆盖

- summarizer 返回 `null`：话题文件不写入 summary
- summarizer 返回高价值内容：正常写入 summary
- 已有 11 用例，新增 2 用例（低价值跳过 + 高价值归档），增量无回归

## v0.3 结构化升级（已落地）

**改造文件**：`cli/repl.ts`（prompt + JSON 解析）

### 核心变化：从自由文本 → 结构化 JSON

v0.2 的 LLM 输出是 1-2 句自然语言文本，虽然可读但不利于程序化检索（如"搜索所有关于部署环境的约束"）。

v0.3 将 LLM 输出改为结构化 JSON，按三个维度归类：

| 维度 | 含义                               | 示例                             |
| ---- | ---------------------------------- | -------------------------------- |
| 约束 | 用户的技术栈、环境限制、项目配置   | "系统为 Windows，命令连接符用 ;" |
| 偏好 | 代码风格、工作流、审美、命名习惯   | "偏好小驼峰命名法"               |
| 决策 | 会影响未来交互的架构选型、策略决定 | "选用 better-sqlite3 而非 mysql" |

### LLM Prompt 设计

```
你是记忆价值评估与结构化提取助手。分析以下对话，提取用户独有的信息。

判断标准（记忆归档原则 v0.3 · 结构化）：
- 约束：用户透露的技术栈、环境限制、项目配置（大模型不知道的信息）
- 偏好：用户的代码风格偏好、工作流偏好、审美偏好、命名习惯
- 决策：用户做出的会影响未来交互的架构选型、策略决定

输出格式（严格 JSON，不含 markdown 代码块标记）：
- 对话全是通用问答/闲聊，无任何独有信息 → 只输出 SKIP
- 否则输出：{"约束":["..."], "偏好":["..."], "决策":["..."]}
- 空数组的字段可省略
- 每条 10-20 字，只提取用户独有的信息，不包含 LLM 已知的通用知识
```

### 解析与格式化

LLM 返回的 JSON 在代码层被解析并格式化为可读文本存储：

```
输入：{"约束":["Windows 系统；命令连接符用 ;"], "偏好":["代码需加注释；小驼峰命名"]}
输出：约束：Windows 系统；命令连接符用 ; | 偏好：代码需加注释；小驼峰命名
```

### 降级策略

- LLM 返回 `SKIP` 或空白 → 返回 `null`，跳过归档（不变）
- JSON 解析失败（如 LLM 输出格式错误）→ 降级为原始文本存储（兼容 v0.2）
- 空数组字段自动省略（如 `{"约束":[],"偏好":["..."]}` → 只输出 `偏好：...`）

### 技术细节（v0.2 + v0.3 合并）

| 机制       | 说明                                                                       |
| ---------- | -------------------------------------------------------------------------- | ---------- |
| SKIP 信号  | `TopicSummarizer` 返回 `null` → `summarizeAndArchive` 跳过 `appendSummary` |
| 输入优化   | 收集完整对话（user + assistant），截断 800 字                              |
| 结构化提取 | LLM 输出 JSON `{约束/偏好/决策}` → 代码层格式化为 `约束：...               | 偏好：...` |
| 降级兜底   | JSON 解析失败 → 降级为原始文本；不阻塞对话                                 |

### 测试覆盖

- summarizer 返回 `null`：话题文件不写入 summary
- summarizer 返回结构化 JSON：解析后格式化为可读文本，正常写入
- summarizer 返回非 JSON 文本：降级为原始文本存储
- 已有 11 用例，v0.2 新增 2 用例，v0.3 无新增用例（prompt 变更由已有测试覆盖）

## 改进方向（后续）

1. **增量覆盖**：在实际使用中验证结构化提取的准确率，持续优化 prompt
2. **程序化检索**：基于 `约束/偏好/决策` 三维标签，支持按维度搜索记忆
3. **升级 ADR**：当"结构化归档"模式在实际使用中出现 3 次以上，升级为正式 ADR

## 何时升级为 ADR

遵循自然生长原则：当"总结无用"的模式在实际使用中出现 3 次以上，再提取为正式 ADR。当前作为设计思考文档存档，指导后续实践。
