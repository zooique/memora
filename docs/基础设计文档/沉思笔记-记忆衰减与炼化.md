# Memora — 沉思笔记：记忆衰减与炼化

> **定位**：从"应无所住而生其心"哲学推论出的 4 个设计提案，当前 P0 已实现（设计 1+2），P1 沉淀待触发条件成熟
> **关系**：本文档是 [agent上下文组装协议.md](./agent上下文组装协议.md)
> §7.6压缩策略的"哲学深化版" **状态**：P0 已实施 / P1 待触发
> **日期**：2026-06-03

## 哲学内核 → 设计推论

「应无所住而生其心」可以拆解为两个动作：

```
应无所住  =  不堆积，不预载，不留恋
而生其心  =  当下即用，精准挂载，用后即卸
```

对照当前系统：

| 动作            | 是否已有 | 缺失什么                               |
| --------------- | -------- | -------------------------------------- |
| 挂载（mount）   | 隐式有   | 没有形式化生命周期，没有多话题同时挂载 |
| 卸载（unmount） | 隐式有   | 没有上下文压力驱动的自动卸载           |
| 炼化（refine）  | 一级     | 只有话题级摘要，没有跨话题提炼         |

---

## ✅ 设计 1：上下文压力感知 + 自动卸载（P0 已实现）

**推论来源**：「应无所住」就要求 Agent 不囤积上下文。当前系统有 `maxIterations`
上限，但不管窗口还剩多少空间。

**设计**：在 Agent Loop 内嵌一个 `ContextPressureMonitor`：

- 触发条件：上下文 token 总数 > `maxContextTokens × 0.7`
- 卸载策略：按「最近访问时间 × 与当前查询的相关度」评分，得分最低者优先卸载
- 卸载目标：压力降到 `0.5` 以下，单次最多卸载 3 个
- 卸载后状态：原记忆仍存 SQLite，只是从 messages 移除

**代码位置**：[src/memory/context-pressure-monitor.ts](../../src/memory/context-pressure-monitor.ts)

**哲学含义**：**「不生不灭」**——话题文件不删除，只是从上下文卸载。TopicMount 会在下一轮重新召回需要的——这是「生」，卸载是「不生」。

**实现要点**：

- 监控器是 Agent Loop 内的"轻量管家"，热路径上不依赖 segmenter
- onUnmount 钩子由外部传入（解耦）
- 卸载时记录日志，透明可观测

**待办**：在 AgentLoop 接入点（[src/agent/loop.ts](../../src/agent/loop.ts)）每轮迭代前调用
`pressureMonitor.check()`。当前监控器已就绪，**AgentLoop 的接入需要决策点**（设计 1 的"不直接接入"是有意为之——避免改动核心循环，需要先有真实长对话样本验证阈值）。

## ✅ 设计 2：记忆权重自然衰减（P0 已实现）

**推论来源**：「应无所住」的另一个面——不用的记忆应该自然淡出。当前系统 `weight`
是静态的（写在 frontmatter 里），从不更新。

**设计**：SQLite 索引中的 `weight` 字段变为动态值。

| 永久性      | 半衰期 | 含义                     |
| ----------- | ------ | ------------------------ |
| `always`    | 永不   | 人格和核心规则不衰减     |
| `domain`    | ~90 天 | 领域知识缓慢退潮         |
| `topic`     | ~7 天  | 一周不碰的话题权重自然降 |
| `on-demand` | ~3 天  | 不用的技能快速退场       |

**召回时的交互**：每次 `search()` 命中某条记忆时，将其 `weight`
重置为 1.0（重置衰减时钟）。这就是「而生其心」——被当下需要时重新"活过来"。

**代码位置**：[src/memory/index.ts](../../src/memory/index.ts) 的 `touch()` 和
`applyDecay()` 方法

**哲学含义**：记忆不是"被删除"的，是"不被想起而自然淡出"的。佛家讲「诸法无我」——记忆本身没有永恒自性，它的存在完全由当下的召回决定。

**实现要点**：

- `weight` 不降到 0（保留最小值 `0.05`），避免 bootstrap 时 loaded 记忆消失
- `applyDecay()` 是全表扫描，**不放在热路径**——应由定时任务或 `memora archive`
  触发
- `touch()` 在 `search()` 命中后 fire-and-forget 调用，不阻塞搜索返回
- `always` 永久性的记忆在 `applyDecay()` 中**早退**（半衰期 = Infinity）

**待办**：在 [src/agent/agent.ts](../../src/agent/agent.ts) 的 `init()`
中连接一个定时任务（每天凌晨 3 点跑
`applyDecay()`），当前未做是为了避免引入调度器依赖。CLI 暂时用 `memora decay`
手动触发（待命令实现）。

## ⏸ 设计 3：多级炼化管道（P1 待触发）

**推论来源**：「而生其心」——心不是从积累的记忆中产生的，是从记忆的提炼中产生的。当前只有一级炼化（话题摘要），但真正有价值的是**跨话题的模式识别**。

**设计**：三级炼化管道：

| 级别        | 触发     | 延迟                   | 用户感知     |
| ----------- | -------- | ---------------------- | ------------ |
| L1 话题卸载 | 实时     | 无感知（已有）         | 上下文轻量化 |
| L2 每周凌晨 | ~5 分钟  | 异步，下次启动可见     | 周报式回顾   |
| L3 每月     | ~30 分钟 | 异步，生成后向用户提案 | 模式识别     |

**关键**：L2/L3 不是自动生效的——L3 产出的是「建议」，需要用户确认后才写入规则。这是保持「用户独特性」的方式（[记忆归档原则.md](./记忆归档原则.md)：大模型不知道的信息才是值得归档的）。

**为什么暂缓**：

- L2/L3 涉及 LLM 调用和"用户确认"流程
- 阶段一 CLI 都没有通知机制，提案给用户看需要 UI 升级
- 当前 5k 条记忆 < 5ms 不需要 L2/L3 优化
- 触发条件：累计 100+ 话题记录后才有价值

**实施前置条件**：

- ⏳ 设计 1+2 实跑 1 个月，积累真实数据
- ⏳ CLI 通知机制（如 `memora notify` 或启动 banner）
- ⏳ 阶段二"多宿主项目"完成后，再评估"用户确认 UI"

## ⏸ 设计 4：话题指纹 + 轻量关系图（P1 待触发）

**推论来源**：挂载器的核心问题是「该挂载哪个话题」——需要一种比 FTS5 更快、但不要求精确的方式。

**设计**：每个话题在归档（L1 炼化）时生成一个「指纹」：

```
指纹 = 话题名 + 关键词（≤ 5 个） + 时间衰减向量
```

**存储**：SQLite 一个轻量表（`topic_fingerprints`），不算 FTS5，查询时：

```sql
SELECT topic_id FROM topic_fingerprints
WHERE keywords MATCH ?
ORDER BY decay_score DESC
LIMIT 10;
```

**关系图**：`prevTopic / nextTopic`
自然形成一条话题链。多次对话后，话题链变成话题图——Agent 可以沿图遍历："用户上次讨论完角色设定后，接着讨论了什么？"

**为什么暂缓**：

- **当前 5k 条记录 < 5ms 不构成瓶颈**——这是优化而非补缺
- 话题指纹本质上是把 TopicMount 现有的关键词比较升级为更结构化方案
- FTS5（设计文档 §4.4 阶段二）尚未启用，**先解决 FTS5 再说指纹**
- 关系图需要 TopicStore 改造（`topic-001.md` 增加 `prev/next`
  字段），这是数据迁移级改动

**实施前置条件**：

- ⏳ FTS5 启用（[agent上下文组装协议.md §4.4.1](./agent上下文组装协议.md)）
- ⏳ 累计 1000+ 话题后再评估"关系图"价值
- ⏳
  jieba 分词引入后（[agent上下文组装协议.md §4.4.1 L2](./agent上下文组装协议.md)），再做关键词匹配层

## 优先级回顾

| 设计                | 哲学对应             | 状态      | 改动量                  | 效果           |
| ------------------- | -------------------- | --------- | ----------------------- | -------------- |
| 1 上下文压力感知    | 「应无所住」         | ✅ 已实现 | 中（~150 行新文件）     | 长对话稳定性   |
| 2 记忆权重衰减      | 「无所住」的淡化面   | ✅ 已实现 | 小（~80 行方法）        | 搜索结果更精准 |
| 3 多级炼化管道      | 「而生其心」的提炼面 | ⏸ 待触发  | 大（新模块 + LLM 调用） | 记忆质量提升   |
| 4 话题指纹 + 关系图 | 挂载决策基础         | ⏸ 待触发  | 中（新 SQLite 表）      | 召回速度提升   |

**P0 价值**：用 ~230 行代码最大化哲学一致性——不动核心架构，在现有管线里补两个钩子。

**P1 价值**：需要"真实使用 1 个月 + 阶段二基础设施"前置条件，盲目实现是浪费。
