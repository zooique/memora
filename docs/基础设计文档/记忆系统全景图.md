# Memora — 记忆系统全景图：万物皆记忆的真正含义

> **定位**：回答一个根本问题——"**万物皆记忆**到底是把所有东西塞进 SQLite，还是另有深意？"
> **关系**：本文档是 [agent上下文组装协议.md](./agent上下文组装协议.md)
> 的"哲学澄清" **状态**：✅ 哲学沉淀（已纠正之前的过度工程化理解）
> **日期**：2026-06-03

---

## 一、核心澄清

### 1.1 "万物皆记忆"的真正含义

> **不是**："所有信息都要存到 SQLite `memories` 表里"
> **而是**："所有 agent 用来决策的信息，都按统一的 `memory_type + permanence`
> 模型管理"

### 1.2 之前理解的偏差

❌ **错误理解**："刚才聊过的话"也是"记忆"，需要归档到 SQLite 让 TopicMount 召回

✅ **正确理解**：

- "刚才聊过的话"是**工作记忆**（在 `messages` 数组里）—— LLM 上下文自然包含
- **不需要**额外写 SQLite、读 SQLite、过滤 SQLite 来"挂载"
- 这是**负优化**（多写多读多过滤，信息量零增加）

### 1.3 教训

**把"哲学口号"当工程机制直接落地** = 过度工程化。

记忆类型是**决策模型的分类**，不是**存储位置的定义**。同一份"记忆"在生命周期不同阶段可能出现在不同位置，但**分类不变**。

## 二、Memora 的 4 层记忆架构

每层**各管各的**，互不重复：

### 2.1 第 1 层：工作记忆（短命）

| 属性                | 值                                                              |
| ------------------- | --------------------------------------------------------------- |
| **存储位置**        | `messages: Message[]`（AgentLoop 内存）                         |
| **生命周期**        | 单次 Agent 进程内                                               |
| **谁消费**          | LLM 当下决策                                                    |
| **永久性**          | 极短（对话结束消失）                                            |
| **典型内容**        | "用户刚才说萧然"、"墨羽刚才回了一句..."                         |
| **Memora 中的实现** | [src/agent/loop.ts](../../src/agent/loop.ts) 的 `messages` 数组 |
| **进入路径**        | 每次 `chat(input)` 时 `push` 一条 user + 一条 assistant         |

**关键原则**：

- ✅ LLM 当下看得到（已经在 system/user/assistant 角色里）
- ❌ **不写** SQLite（避免重复）
- ❌ **不进** TopicMount（避免负优化）

### 2.2 第 2 层：Bootstrap 记忆（永驻）

| 属性                | 值                                                                                          |
| ------------------- | ------------------------------------------------------------------------------------------- |
| **存储位置**        | SQLite `memories` 表，type ∈ {personality, rule, skill, tool}                               |
| **永久性**          | `always`（永驻）/ `domain`（领域级）                                                        |
| **生命周期**        | 启动时 100% 加载，进程内常驻                                                                |
| **谁消费**          | LLM 上下文注入（system prompt）                                                             |
| **典型内容**        | "墨羽人格"、"人物优先规则"                                                                  |
| **Memora 中的实现** | [src/memory/project-manager.ts](../../src/memory/project-manager.ts) 的 `bootstrapMemories` |
| **进入路径**        | `init()` 时 `loadAllByPermanence(['always', 'domain'])`                                     |

**关键原则**：

- ✅ 启动时一次加载（快）
- ❌ 不需要按话题召回（已经在上下文）
- ❌ 不需要"挂载"（不离开上下文）

### 2.3 第 3 层：话题归档记忆（跨会话）

| 属性                | 值                                                                                                                                        |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| **存储位置**        | `topic-*.md` 文件（TopicStore）                                                                                                           |
| **永久性**          | `topic`（按时间衰减）                                                                                                                     |
| **生命周期**        | 切话题时归档，下一会话可被召回                                                                                                            |
| **谁消费**          | 切话题时的"对话回顾"（通过 `TopicSummarizer` 提炼）                                                                                       |
| **典型内容**        | "2026-06-02 讨论了角色弧光的三个核心问题..."                                                                                              |
| **Memora 中的实现** | [src/agent/topic-summarizer.ts](../../src/agent/topic-summarizer.ts) + [src/agent/message-history.ts](../../src/agent/message-history.ts) |
| **进入路径**        | `switchTopic()` 触发 `summarizeAndArchive()`                                                                                              |

**关键原则**：

- ✅ 是**跨会话**的（"上次我们聊到哪"）
- ❌ **不是同会话**的（"刚才聊过什么"由工作记忆管）
- 📝 归档是**轻量**的（只存摘要，不存全文）

### 2.4 第 4 层：话题挂载记忆（跨会话召回）

| 属性                | 值                                                           |
| ------------------- | ------------------------------------------------------------ |
| **存储位置**        | `TopicMount.mounted: Memory[]`（内存缓存）                   |
| **永久性**          | 临时（生命周期 = 进程内）                                    |
| **生命周期**        | 用户开口 → 关键词比对 → 召回/复用/重召                       |
| **谁消费**          | LLM 上下文注入（`topicMemories` 参数）                       |
| **典型内容**        | "上次关于'小说结构'聊过的 3 个相关话题"                      |
| **Memora 中的实现** | [src/memory/topic-mount.ts](../../src/memory/topic-mount.ts) |
| **进入路径**        | `agent.chat()` → `topicMount.focus()` → 注入 LLM             |

**关键原则**：

- ✅ 跨会话（"上上次聊过的相似话题"）
- ❌ **不管同会话**（"刚才聊过的"在工作记忆里）
- ⚠️ 召回的是**结构化数据**（来自 Bootstrap 层的 `type='topic'`
  记忆，**不是**从 topic-\*.md 反向读）

### 2.5 重要澄清：第 3 层和第 4 层的关系

> 第 3 层归档（topic-\*.md）和 第 4 层挂载（TopicMount 召回的内容），
> **不是同一个数据流的入口和出口**。

| 层          | 数据源                                    |
| ----------- | ----------------------------------------- |
| 第 3 层归档 | 写 `topic-*.md`（TopicStore）             |
| 第 4 层召回 | 查 SQLite `memories` 表（`type='topic'`） |

**为什么会是这样**：

- `topic-*.md` 是**人类可读**的对话日志（每条对话原文）
- SQLite `type='topic'` 是**结构化**的归档记忆（摘要 + 关键词 + 元数据）
- 两者**内容可能不同**——后者是前者的 LLM 提炼

**问题来了**：当前 `MessageHistory.summarizeAndArchive()` 写完 `topic-*.md`
之后，**没有把摘要同步到 SQLite**。

这是**已有的设计缺口**，但**不是 P0 修复项**——因为：

1. 阶段一 **没有人**会运行超过 1 次会话（CLI 还在跑 demo）
2. 即便归档了，也需要 `Bootstrap` 加载 `type='topic'` 时按当前话题筛
3. 真正能复现这个 bug 之前，**不要补这个洞**（避免引入新债）

## 三、决策树：什么该归档，什么不该

```
某条信息
  │
  ├─ 属于当前会话的工作记忆？
  │   └─ ✅ 直接进 messages 数组（不归档）
  │
  ├─ 是人格/核心规则（跨所有话题、跨所有项目）？
  │   └─ ✅ 写到 SQLite type='personality' / type='rule'，permanence='always'
  │
  ├─ 是领域知识（程序员 / 作家 / 父亲等领域专有）？
  │   └─ ✅ 写到 SQLite type='rule' / type='skill'，permanence='domain'
  │
  ├─ 是工具/技能定义（按需使用）？
  │   └─ ✅ 写到 SQLite type='tool' / type='skill'，permanence='on-demand'
  │
  └─ 是话题级经验（仅在特定话题上下文中相关）？
      │
      ├─ 跨会话可复用（"上次我们讨论了 X 的 3 种结构"）？
      │   └─ ✅ 切换话题时 → summarizeAndArchive() 写到 topic-*.md
      │       ⚠️ 同步到 SQLite type='topic' 是设计缺口（暂不修）
      │
      └─ 仅同会话相关（"我刚才说错话了"）？
          └─ ❌ 不归档——这是工作记忆，不进记忆系统
```

## 四、UI 层的真实问题

测试发现的"挂载提示不刷新"是**前端 UX 问题**，不是记忆架构问题。

### 4.1 真实流程

1. 用户第一次输入 → `topicMount.focus(input)` → 关键词提取 → 查 SQLite
2. SQLite 里**没有相关 topic 记忆**（因为没人归档过）→ 召回空
3. TopicMount 返回 `[]` → 不挂载
4. Web UI 显示"尚无挂载的话题记忆"
5. 用户再输入 → **同样的查询** → 同样的空结果 → 同样的提示
6. UI **没刷新**，看起来像"bug"

### 4.2 三种修复路径（选哪个？）

| 路径                                                   | 改动                                                        | 适用                            |
| ------------------------------------------------------ | ----------------------------------------------------------- | ------------------------------- |
| **A. 修 UI 实时反馈**                                  | Web UI 监听 `chat` 完成事件，主动重新 fetch `/api/memories` | ✅ 最小修改，立刻可见           |
| **B. 修前端判断逻辑**                                  | 首次对话显示"首次对话，暂无历史" vs 非首次显示"挂载 N 条"   | ✅ 更友好，但要前端状态机       |
| **C. 让 TopicMount 启动时就挂载 Bootstrap 里的 topic** | `topicMount.focus('') → 加载所有 type='topic'`              | ❌ 违反"应无所住"（启动不预载） |

**推荐 A + B 组合**——前端 0.5 小时改完，但**属于 demo 体验优化，不是核心架构**。

## 五、之前被回滚的方案

### 5.1 TopicArchiver（已被删除）

**当时想做的**：

```
每轮对话后（fire-and-forget）：
  1. 把 "user + assistant" 这对消息合并
  2. 用 LLM 生成一句话摘要
  3. 写入 SQLite type='topic' 记忆
  4. 下次对话 → TopicMount 自动召回并挂载
```

**为什么是错的**：

1. **重复造轮子**：`messages` 数组里已有完整对话，再写一次 SQLite 无信息增量
2. **违反哲学**：把"同会话"提升到"跨会话"，混淆了第 1 层和第 3 层
3. **LLM 调用成本**：每轮一次摘要 → 真实模式下费用翻倍
4. **污染索引**：所有闲聊都会被"归档"，召回时被噪声淹没

### 5.2 教训总结

**当一个方案看起来"补缺口"时，先问**：

- 这个缺口是**架构级**的，还是**机制级**的？
- 填补它**真的会改变用户行为**吗？
- 还是只是**让"看起来更完整"**？

回滚的 TopicArchiver 是典型的"看起来更完整，但实际是负优化"。
