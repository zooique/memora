## 一、核心模型：三层模型（对外两层）

### 1.1 公式

```
上下文（每轮提交给 API）= 用户主动输入 + Agent 记忆召回结果 + Agent Loop 工作记忆
```

三层。不是两层，是三层。但对外（用户视角）仍然是两层——用户只关心"我说了什么"和"你找到了什么"。"Agent
Loop 工作记忆"是 Agent 内部执行循环中产生的中间产物（工具调用结果、模型推理中间步骤），用户不需要感知。

### 1.2 三层定义

| 层                      | 来源                 | 内容                                               | 谁决定       | 生命周期                             |
| ----------------------- | -------------------- | -------------------------------------------------- | ------------ | ------------------------------------ |
| **用户主动输入**        | 用户                 | 提示词文本 + 用户主动提及/引用/粘贴的已知文本      | 用户         | 每轮刷新                             |
| **Agent 记忆召回结果**  | Agent 从记忆系统召回 | 角色层 + 永驻记忆 + 领域记忆 + 话题记忆 + 能力记忆 | Agent        | 见 1.4 节                            |
| **Agent Loop 工作记忆** | Agent Loop 执行产物  | 工具调用结果 + 模型中间回复 + 增量召回的上下文     | 模型自主产生 | Loop 内存在，Loop 结束后写入话题文件 |

### 1.3 为什么对外是两层

用户视角下只有两层：

1. 我说了什么（用户主动输入）
2. 你有没有找到相关的上下文（agent 记忆召回）

Agent
Loop 工作记忆是 agent 内部执行循环的中间产物，用户不需要感知。就像你不需要知道搜索引擎在找到结果前访问了多少个索引分片。

**三层模型承认了一个事实：agent 的记忆系统有静态部分（预召回）和动态部分（执行中产生）。**
对外暴露两层（用户输入的 + 系统帮你找的），对内是三层（+ 执行中间产物）。

### 1.4 记忆召回结果的内部生命周期

记忆召回结果虽然对外是一层，但内部的五种记忆有截然不同的生命周期：

| 记忆类型     | 永久性      | 加载时机       | 刷新频率                                         | 变更触发                             |
| ------------ | ----------- | -------------- | ------------------------------------------------ | ------------------------------------ |
| **角色层**   | —           | 启动时加载     | 用户手动切换角色时刷新                           | `agent.switchPersona()` 或启动时变更 |
| **永驻记忆** | `always`    | 启动时加载     | 永不刷新                                         | 仅当文件被手动修改后重新启动         |
| **领域记忆** | `domain`    | 启动时加载     | 领域切换时刷新（领域规则）/ 永不刷新（永驻规则） | 领域标签变更时刷新领域规则部分       |
| **话题记忆** | `topic`     | 每轮对话前     | 每轮刷新                                         | 当前话题变化或话题漂移检测触发重填   |
| **能力记忆** | `on-demand` | 任务类型切换时 | 任务切换时刷新                                   | 用户切换技能或上下文触发工具集变更   |

> **角色层是 v4.0 新增的固定区**。它不属于"记忆"，而是"配置"——在启动时通过
> `PersonaManager` 加载到 system
> prompt，不进入 SQLite 记忆索引。角色层与人格记忆（v3.5 旧概念）的区别：人格记忆是 Agent 自身的"我是谁"设定，角色层是用户在对话中选择的"你以什么身份跟我说话"——两者解耦后，Agent 可以承载多个不同人设的角色而不丢失自身记忆。

**开发者调试指南**：

- 想测试不同角色 → 调用 `agent.switchPersona('momo')`，不影响话题记忆
- 想测试不同技能 → 可以在运行时切换能力记忆，不重建整个记忆召回结果
- 想排查话题记忆加载错误 → 可以冻结永驻记忆，单独重填话题记忆

### 1.5 Agent Loop 工作记忆的生命周期

工作记忆是 Agent Loop 执行过程中产生的瞬时记忆，生命周期最短：

| 记忆内容         | 产生时机               | 生命周期    | 最终去向                                    |
| ---------------- | ---------------------- | ----------- | ------------------------------------------- |
| 模型中间回复     | Loop 中每轮推理        | Loop 内存在 | Loop 结束后写入话题文件（作为话题记忆）     |
| 工具调用结果     | 代码执行工具后         | Loop 内存在 | Loop 结束后写入话题文件（作为话题记忆）     |
| 增量召回的上下文 | 模型调用记忆检索工具后 | Loop 内存在 | Loop 结束后标记为"已召回"，避免下次重复召回 |

**关键**：工作记忆不是独立存储的记忆类型——它是话题记忆在 Loop 内的"瞬时态"。Loop 结束后，工作记忆转为话题记忆的持久化记录。如果在 Loop 中崩溃，工作记忆丢失，但下次会话可通过话题记忆恢复大部分上下文。

### 1.6 工作记忆与话题记忆的分界

上节定义了工作记忆的"瞬时态"特性，但**与话题记忆的边界**仍需明确——这是配额计算（85% +
15%）不重复的关键。

#### 1.6.1 分界表

| 内容                                          | 归属         | 存储位置             | 配额占用                      | 生命周期                    |
| --------------------------------------------- | ------------ | -------------------- | ----------------------------- | --------------------------- |
| Loop 内 tool 调用结果                         | **工作记忆** | 仅上下文（不入文件） | 工作记忆 20%                  | Loop 结束丢弃               |
| Loop 内模型中间回复                           | **工作记忆** | 仅上下文（不入文件） | 工作记忆 20%                  | Loop 结束丢弃               |
| Loop 结束时的最终模型回复                     | **话题记忆** | 追加到话题文件       | 下次刷新时进入话题记忆 40-60% | 持久化                      |
| 上一轮对话原文（已落盘）                      | **话题记忆** | 话题文件             | 话题记忆 40-60%               | 永久（封存/归档后变更存储） |
| 模型调用 `search_topics` 检索出的相关话题报告 | **话题记忆** | 话题文件 + 索引      | 话题记忆 40-60%               | 按引用规则                  |
| 模型调用 `activate_skill` 后注入的技能 prompt | **工作记忆** | 仅上下文             | 工作记忆 20%                  | Loop 结束丢弃               |

#### 1.6.2 关键边界原则

**"是否已落盘"是工作记忆与话题记忆的分界**：

```
            ┌────────────────────┐
   Loop 启动 │  上轮对话已落盘     │ ← 话题记忆（40-60%）
            │  (读取自话题文件)   │
            ├────────────────────┤
            │  本轮 system 注入   │ ← 指令层（人格+规则+技能）不属于"工作/话题"任一方
            ├────────────────────┤
            │  本轮 user 输入     │ ← 用户主动输入（不在配额计算中）
            ├────────────────────┤
            │  Loop 中产生:       │
            │  • 模型中间回复     │ ← 工作记忆（20%）
            │  • tool 调用结果    │ ← 工作记忆（20%）
            │  • 增量检索结果     │ ← 工作记忆（20%）
            └────────────────────┘
            ┌────────────────────┐
   Loop 结束 │  本轮最终回复       │ → 落盘为话题记忆
            │  (追加到话题文件)   │   (进入下轮 40-60% 配额)
            └────────────────────┘
```

#### 1.6.3 配额计算规则

**话题记忆配额（40-60%）只计算"已落盘且会被本轮加载"的内容**：

- ✅ 当前话题文件最近 N 轮对话原文（已落盘，会被加载）
- ✅ 检索召回的话题报告（已落盘，会被加载）
- ❌ Loop 内产生的 tool 结果（未落盘，不被加载）
- ❌ Loop 内模型中间回复（未落盘，不被加载）

**工作记忆配额（20%）独立计算**：

- 包含 Loop 内所有动态产生的内容
- 与话题记忆配额**完全不重叠**——避免双重计算

#### 1.6.4 落盘时机

| 落盘内容             | 时机        | 触发                             |
| -------------------- | ----------- | -------------------------------- |
| 模型最终回复         | Loop 结束时 | 代码自动追加到话题文件           |
| 工具执行结果摘要     | Loop 结束时 | 仅在后续对话可能引用时落盘       |
| 增量召回的上下文标记 | Loop 结束时 | 标记为"已召回"，避免下次重复召回 |

**反例（不应落盘）**：

- Loop 中间因 tool 调用错误产生的重试过程——只在最终回复中体现"已完成 X"
- 模型推理的中间草稿——不落盘，避免污染话题记忆
- 用户输入的临时引用——用户主动提供的文本本就在用户主动输入层

## 二、Agent 记忆召回文档

### 2.1 概念

Agent 记忆召回文档是一个**独立的内存空间**，在对话启动时加载，在整个对话过程中**按永久性分级动态召回**。

它不是静态的模板，而是一个**活的文档**——每次对话轮次都根据当前任务从记忆系统中召回相关内容，按永久性从高到低填充到固定结构中。

### 2.2 文档结构

```
┌─────────────────────────────────────────────────────────┐
│              Agent 记忆召回文档                           │
│         (启动时加载到内存，按永久性分级动态召回)             │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  [角色层] 当前激活角色 ← 启动时注入到 system prompt 顶部   │
│  └─ personas/<name>.md（人格 + 语气 + 专长）             │
│                                                         │
│  [永驻记忆] 用户画像 + 全局规则                           │
│  ├─ 用户画像（permanence: always，SQLite user-profile）   │
│  └─ 全局常驻规则（permanence: always）                    │
│                                                         │
│  [领域记忆] 领域规则 + 作品投影                            │
│  ├─ 领域规则（permanence: domain，按领域标签匹配召回）      │
│  └─ 作品投影（permanence: domain，从用户作品提炼的概要）   │
│                                                         │
│  [话题记忆] 当前话题上下文 ← 按话题相似度动态召回           │
│  ├─ 同话题近期对话原文（最近 N 轮）                       │
│  ├─ 对话快照（seed_snapshots，从旧话题提炼的种子）         │
│  ├─ 同话题历史话题报告（本周/本月）                     │
│  └─ 跨话题关联记忆（关键词检索召回）                       │
│                                                         │
│  [能力记忆] 当前可用的技能 + 工具描述                      │
│  ├─ 激活的技能说明文案（permanence: on-demand）           │
│  ├─ 可用工具的函数 Schema（permanence: on-demand）        │
│  └─ Few-shot 示例（可选）                                │
│                                                         │
├─────────────────────────────────────────────────────────┤
│  [工作记忆] Agent Loop 执行中的瞬时上下文                  │
│  ├─ 模型中间回复 + tool_call（Loop 内动态产生）            │
│  ├─ 工具调用结果 + 增量召回的上下文（Loop 内动态产生）       │
│  └─ 不占记忆召回文档配额，使用独立的工作记忆预算            │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

### 2.3 按永久性分级填充

记忆召回文档不是"塞满为止"，而是**按永久性分级填充**：

| 记忆类型             | 永久性      | 建议占比  | 填充策略                                              |
| -------------------- | ----------- | --------- | ----------------------------------------------------- |
| **角色层**           | —           | ≤ 5%      | 启动时加载，对话期间不可变——人格、语气、专长          |
| **永驻记忆**         | `always`    | ≤ 10%     | 启动时加载，对话期间不可变——用户画像 + 全局规则       |
| **领域记忆**         | `domain`    | ≤ 15%     | 启动时加载，对话期间不可变——领域规则 + 作品投影       |
| **话题记忆**         | `topic`     | 40%-60%   | 每轮动态从记忆系统召回，按话题相关度排序              |
| **能力记忆**         | `on-demand` | ≤ 10%     | 按当前任务类型召回对应技能/工具                       |
| **记忆召回文档合计** | —           | **≤ 85%** | **为 Agent Loop 工作记忆预留 ≥ 15% 空间**             |
| 工作记忆             | 瞬时        | ≤ 20%     | Agent Loop 中动态产生，独立预算，不占记忆召回文档配额 |

**关键设计**：记忆召回文档最多占上下文窗口的 85%，剩余 ≥ 15% 预留给 Agent
Loop 的工作记忆（工具结果、模型回复等）。工作记忆的实际使用上限为窗口的 20%，超出时触发上下文压缩（见 7.6 节）。

**比例不是硬编码，而是根据模型上下文窗口动态计算。**
128K 窗口和 1M 窗口的填充策略不同——但比例关系保持一致。用例：128K 窗口 → 记忆召回文档 ≤
108.8K tokens，工作记忆预留 ≥ 19.2K tokens。

### 2.4 启动与执行流程

**阶段一：启动（记忆召回）**

```
1. 加载角色层 → 读取 personas/<activePersona>.md（注入到 system prompt 顶部，不入索引）
2. 召回永驻记忆 → 用户画像（identity/preference/expertise）+ 全局规则
3. 召回领域记忆 → 领域规则（按领域标签匹配）+ 作品投影
4. 识别当前话题 → 从记忆系统检索同话题内容
5. 召回初始话题记忆 → 最近 N 轮对话原文 + 对话快照（从旧话题提炼的种子）
6. 召回初始能力记忆 → 按当前任务类型匹配技能 + 工具（仅注入简短描述，不注入完整文案）
7. 校验 Token 预算 → 确保记忆召回文档 ≤ 上下文窗口的 85%
```

**阶段二：对话执行（Agent Loop）**

```
7. 记忆召回文档 + 用户输入 → 组装为 messages → 提交 API
8. 进入 Agent Loop → 模型推理 → 如有 tool_call（业务工具/记忆检索工具）则执行并回填结果 → 循环
9. 模型输出纯文本 → 循环结束 → 后置处理 → 记忆写入与沉淀
```

详见 [01-主架构-v4.0.md](./01-主架构-v4.0.md) 5.1-5.3 节。

## 三、记忆系统

记忆的定义和分层原则见 [01-主架构-v4.0.md](./01-主架构-v4.0.md) 第三章。

### 3.1 记忆的存储粒度

**以对话轮次为记录单元，以话题为组织维度。**

存储路径由初始化时的 `storageRoot` 和 `projectId`
共同决定：`<storageRoot>/projects/<projectId>/`。以下为单个项目内的目录结构：

```
<storageRoot>/projects/<projectId>/   # 由 Agent 初始化参数决定
├── session.json                      # 当前会话元信息
├── topics/                           # 话题文件目录
│   ├── topic-001.md                  # 话题 A 的完整对话记录
│   ├── topic-002.md                  # 话题 B 的完整对话记录
│   └── ...
├── agent.db                          # SQLite 数据库（FTS5 索引 + 向量索引）
└── archive/                          # 归档目录
    ├── 2026-06/                      # 按月
    │   ├── week-22/                  # 按周
    │   │   └── topic-001.md          # 封存的话题文件
    │   └── ...
    └── index.json                    # 归档索引
```

**多项目隔离**：不同 `projectId` 对应不同的子目录，各自拥有独立的
`topics/`、`archive/`、`agent.db`。详见 [01-主架构-v4.0.md](./01-主架构-v4.0.md)
9.4 节。

### 3.2 话题文件格式

每个话题文件是一个 Markdown 文档，以对话轮次为单位记录：

```markdown
# 话题：<话题摘要>

> 创建时间：2026-06-02 14:30最后更新：2026-06-02 16:45关联文件：file-a.md,
> file-b.md关键词：关键词A, 关键词B, 关键词C

## 2026-06-02 14:30 | <轮次摘要>

**用户**：<用户输入内容>

**Agent**：<Agent 回复内容>

---

## 2026-06-02 14:45 | <轮次摘要>

**用户**：<用户输入内容>

**Agent**：<Agent 回复内容>

---
```

### 3.3 话题报告：陈旧话题的炼化形式

**当话题冷却后，原始对话原文不再是最高效的形式。**
agent 不需要看到 37 轮原始问答，只需要知道：讨论了什么、决定了什么、当前状态是什么。

话题报告是**从原始对话中炼化出的结构化文档**，信息密度远高于对话原文：

```markdown
# 话题报告：<话题名>

> 覆盖时间：2026-06-02 ~
> 2026-06-09原始对话轮次：37 轮关键词：关键词A, 关键词B, 关键词C

## 话题概要

一段话总结这个话题讨论了什么核心问题。

## 关键决策

- 决策1：<描述>
- 决策2：<描述>

## 当前状态

当前达成的结论或所处的阶段。

## 关键事实

- 事实1
- 事实2

## 关联文件

- file-a.md
- file-b.md

## 待解决问题

- 尚未解决的问题1
- 尚未解决的问题2
```

**对比原始对话**：

- 原始对话 37 轮可能 8000+ 字，agent 需要自行从中提取有用信息
- 话题报告 500-800 字，agent 直接拿到结构化的事实和决策
- **信息密度差一个数量级**

**炼化时机**：每日归档时，由 LLM 将当日对话原文炼化为话题报告。同一话题的多次炼化结果按以下策略合并：

**合并策略**：采用 **LLM 读取旧报告 + 新对话原文 → 重新整合** 模式。

1. 将旧话题报告（当前生效版本）和当日新对话原文一并提交给 LLM
2. LLM 输出一份**更新后的话题报告**（非增量补丁，是完整报告）
3. 更新后的报告进入**待确认区**（见 3.4 节），旧报告自动成为历史版本
4. 如果 LLM 整合失败（API 超时/返回格式错误），跳过当日合并，次日重试时包含两日的新对话原文

**冲突处理**：

- 如果新旧报告存在矛盾（如旧报告说"决定 A"，新对话原文显示"推翻了 A 改为 B"），LLM 应在更新报告中同时保留"历史决策：A（已推翻）"和"当前决策：B"
- 代码侧做关键词冲突检测（`决定`、`推翻`、`改为`），标记为"需人工复核"
- 用户确认时可以看到变更摘要：`[新增] 决策 B | [推翻] 决策 A | [保留] 事实 C`

**为什么不用"追加合并"**：追加会导致关键决策列表无限增长、互相矛盾。**为什么不用"全文替换"**：全文替换丢失了历史决策脉络，agent 无法理解"为什么从 A 变成了 B"。

**存储策略**：

- 工作记忆和短期记忆 → 保留对话原文（agent 需要精确的问答流）
- 中期记忆及更早 → 只用话题报告（agent 只需要事实和决策）
- 对话原文在炼化为话题报告后封存到归档目录，不再参与日常上下文填充

### 3.4 话题报告质量保障

**话题报告是单向门——一旦生成，原始对话原文封存归档，日常上下文不再加载。**
因此话题报告的质量直接决定 agent 的中长期记忆准确性。以下机制对抗 LLM 炼化时的幻觉风险：

**确认机制**：话题报告生成后，先进入**待确认区**（staging），不直接生效。用户在下一次打开相关话题时，agent 提示"检测到新的话题报告，是否确认？"用户确认后报告才进入活跃记忆池。未确认的报告在 7 天后自动过期删除。

**版本历史**：每份话题报告保留最近 3 个版本。用户确认新版时，旧版自动归档为历史版本。如果发现新版有问题，用户可以回退到任一历史版本。回退操作记录在报告元信息中（`> 回退自：v2 → v1，原因：关键决策错误`）。

**决策溯源**：话题报告中的每项"关键决策"必须标注来源轮次：

```markdown
## 关键决策

- 决策1：采用方案 B 作为主路由策略
  > 来源：2026-06-03 15:20 轮次，经 3 轮讨论后确认
```

这让用户和 agent 都能追溯"这个决策是从哪来的"。如果发现决策有误，可以定位到原始对话进行核实。

**原文索引保留**：对话原文封存后，归档目录保留一份
`原文索引.json`，记录每个话题文件的存储位置和关键元信息。紧急情况下（如话题报告全部损坏），可通过索引手工找回原文重新炼化。索引文件极小（每个话题约 200 字节），不构成存储负担。

**错误传播阻断**：每日归档时，如果 LLM 炼化结果与旧话题报告存在显著矛盾（如将"倾向 A"变为"决定 B"），代码侧做一次简单的关键词冲突检测（`倾向`
vs `决定`），标记为"需人工复核"放入待确认区，而非自动合并。

### 3.5 话题切换与漂移检测

**不让 LLM 实时判断话题切换。**
采用纯文本计算的分层检测机制，零 API 调用，毫秒级完成。

#### 检测方式

每轮用户输入后，代码侧提取当前轮的关键词（TF-IDF），与当前话题标题及最近 5 轮的关键词做 Jaccard 相似度计算。根据相似度分层响应：

| 相似度区间 | 判定         | 响应                                                                                                                                              |
| ---------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| ≥ 0.3      | 同一话题     | 默认延续，正常追加到当前话题文件                                                                                                                  |
| 0.2 ~ 0.3  | 疑似漂移     | 话题记忆按**双轨制**填充：50% 旧话题上下文 + 50% 新话题探索（从全局话题索引中检索与当前轮关键词最匹配的话题报告）。继续延续旧话题文件，不提前分叉 |
| < 0.2      | 大概率新话题 | 主动提示用户"这似乎是一个新话题，是否切换？"——用户确认后归档旧话题、开启新话题文件；用户拒绝则延续旧话题                                          |

#### 其他触发方式

| 触发方式             | 说明                                                                   |
| -------------------- | ---------------------------------------------------------------------- |
| **显式切换**         | 用户主动说"换个话题"、"另外问个事" → 直接归档当前话题，开启新话题文件  |
| **连续漂移自动切换** | 连续 3 轮落在"疑似漂移"区间（0.2~0.3）→ 自动归档旧话题，开启新话题文件 |
| **周期性整理**       | 后台异步运行，批量归并话题，决定哪些轮次应归到已有话题、哪些应单独成题 |

#### 为什么不用 LLM 判断

LLM 判断话题切换的成本高、延迟高、可能反复横跳。文本相似度计算在毫秒级完成，零 API 调用。误判的代价是话题记忆多加载了 50% 无关内容——相比于"用完全错误的上下文回答"，这是可以接受的降级。

**关键**：周期性整理不影响实时对话，只影响归档结构。

#### 3.5.2 阈值表来源与调整机制

##### 当前阈值（v3.2）

| 相似度区间 | 判定         | 响应         |
| ---------- | ------------ | ------------ |
| ≥ 0.3      | 同一话题     | 延续当前话题 |
| 0.2 ~ 0.3  | 疑似漂移     | 双轨制填充   |
| < 0.2      | 大概率新话题 | 提示用户切换 |

##### 阈值来源

**当前阈值为初始经验值**——基于 TF-IDF 关键词在中文短文本中的典型 Jaccard 分布估算。**未经实测验证**。

**为什么是经验值**：

- 阶段一/二还没有足够的真实会话样本做统计
- 阶段一项目为新项目，从零开始数据积累
- 阈值需要在 100+ 真实样本后才能精准

##### 实测调整方案

```
阶段一（极简版）        阶段二（轻量实用版）         阶段三（完整版）
    │                          │                          │
    ▼                          ▼                          ▼
  固定经验值              累计 100 样本             累计 500 样本
  (0.3 / 0.2)            第一次网格搜索调整         每季度调整
                          (步长 0.05)              (持续优化)
```

**网格搜索伪代码**：

```python
# 阶段二启动时执行
def grid_search_threshold(samples, labels):
    best_threshold = None
    best_f1 = 0

    for upper in [0.15, 0.20, 0.25, 0.30, 0.35, 0.40]:
        for lower in [0.05, 0.10, 0.15, 0.20, 0.25, 0.30]:
            if lower >= upper:
                continue
            predictions = predict_with_thresholds(samples, upper, lower)
            f1 = calculate_f1(predictions, labels)
            if f1 > best_f1:
                best_f1 = f1
                best_threshold = (upper, lower)

    return best_threshold
```

##### 调整触发条件

| 触发条件                                 | 动作                     |
| ---------------------------------------- | ------------------------ |
| 阶段二实施后第一个月                     | 固定 30 天后做第一次调整 |
| 累计 ≥ 500 样本                          | 每季度调整一次           |
| 用户反馈 ≥ 5 次"误判"                    | 立即触发调整             |
| 误判率（误切换 + 漏切换）> 15% 持续 7 天 | 立即触发调整             |

**人工标注数据来源**：

- 用户主动反馈："这不是同一个话题" / "这是同一个话题"——记录为正/负样本
- 用户主动切换话题：标记为"已切话题"——上一轮的相似度作为负样本
- 周期性整理结果：批量异步运行归并算法，差异 > 30% 的样本进入待复核区

## 四、话题记忆动态填充逻辑

### 4.1 填充策略

话题记忆是记忆召回文档的核心动态部分。每轮对话开始时，Agent 从记忆系统中召回与当前话题相关的内容。

填充优先级基于 [01-主架构-v4.0.md](./01-主架构-v4.0.md)
3.3 节定义的记忆分层体系（工作记忆 > 短期记忆 > 中期记忆 > 长期记忆 > 归档记忆），此处定义各层在话题记忆中的填充策略：

| 优先级 | 内容                    | 来源           | 存储形式        |
| ------ | ----------------------- | -------------- | --------------- |
| 1      | 同话题最近 N 轮对话原文 | 当前话题文件   | 原文            |
| 2      | 同话题昨日对话原文      | 当前话题文件   | 原文            |
| 3      | 同话题本周话题报告      | 每日归档产出   | 结构化话题报告  |
| 4      | 跨话题关联记忆          | 关键词检索召回 | 话题报告 + 索引 |
| 5      | 同话题归档话题报告      | 归档索引       | 话题报告        |

**自适应加载策略**：根据记忆总量动态选择全量加载或检索召回——

- **全量加载模式**：当总记忆量 ≤ 上下文窗口的 30% 时，跳过检索，将优先级 1-5 的全部内容加载到话题记忆。零检索延迟、零召回误差。适用于小规模项目或新 Agent
- **检索召回模式**：当总记忆量 > 上下文窗口的 30% 时，启动检索召回，按优先级从高到低填充，直到达到话题记忆配额上限。适用于大规模项目或长期运行的 Agent
- **切换判断**：在填充前计算总记忆量（所有话题文件的原文 + 所有话题报告的总 Token 数），与当前模型上下文窗口的 30% 比较。一次会话内不切换模式（避免填充策略抖动）

**设计理由**：Claude Code 采用"全量加载"（CLAUDE.md 全部注入上下文），在 1M
token 窗口时代全量加载的可行性快速提升。但本方案面向通用场景，记忆总量可能远超代码 Agent 的 CLAUDE.md 文件。自适应策略在小规模时获得全量加载的可靠性，在大规模时保留检索召回的扩展性。

### 4.2 填充比例（自适应）

话题记忆内部按以下优先级填充，但比例**自适应**——当某个优先级无内容时，配额转移给下一个优先级：

```
默认比例（当所有内容均可用时）：

当前话题原文（最近 N 轮）  ████████████████████  60%
当前话题历史话题报告       ████████              25%
跨话题关联话题报告         ████                  15%
```

**自适应策略**：

- 无话题报告时（新话题）：当前话题原文占 85%，跨话题关联占 15%
- 无跨话题关联时：当前话题原文占 75%，话题报告占 25%
- 两者皆无时：当前话题原文占 100%，触发冷启动补白（见 4.3 节）

当 Token 预算不足时，按当前生效的比例**等比例压缩**——不是"先裁关联记忆再裁历史"，而是保持各区比例不变，等比例缩短。

### 4.3 冷启动补白

**新话题没有历史上下文。**
话题记忆按填充优先级检索后可能近乎空白，导致 agent 在缺乏上下文的条件下回答——表现骤然下降。

**补白策略**（仅当话题记忆填充后总 Token 低于话题记忆配额的 30% 时触发）：

| 优先级 | 补白内容                                                           | 来源                    |
| ------ | ------------------------------------------------------------------ | ----------------------- |
| 1      | 领域规则摘要（最近的领域约束要点）                                 | 领域记忆 → 领域规则文件 |
| 2      | 当前项目内热门话题报告摘要（从项目内话题索引中检索）               | 项目归档索引            |
| 3      | 提示用户简述背景（"这似乎是一个新话题，能否简单说说你在做什么？"） | agent 主动询问          |

补白内容标注 `[冷启动补白]`
前缀，让 agent 知道这些不是精确的历史上下文，降低回答的确定性级别。

**用户可跳过**：如果用户明确说"不需要背景"或"直接回答"，跳过补白，直接基于用户输入和永驻记忆回答。

### 4.4 跨话题关联记忆召回

**不只按时间召回，还按关键词相似度召回。**
用户当前的问题可能跟几周前的话题更相关，而非昨天。

召回方式：

- FTS5 全文索引（关键词匹配）— 第一版实现
- Embedding 向量相似度（语义匹配）— 第二版实现

**向量检索技术选型（第二版）**：

- Embedding 模型：OpenAI `text-embedding-3-small`
  或等价的本地模型（如 BGE-small-zh），选型标准为 512 维以上、中文语义理解良好
- 向量存储：SQLite 的向量扩展方案或轻量级 ChromaDB，优先选 SQLite 扩展以保持单文件无服务的架构一致性
- 更新策略：归档时同步更新向量索引（与话题报告炼化同批次执行），不额外增加 LLM
  API 调用
- 相似度计算：余弦相似度，阈值 0.7 以上纳入召回候选

**FTS5 中文分词说明**：SQLite
FTS5 无内置中文分词器。第一版采用**简单二字分词**（每两个相邻字符作为一个 token），配合 ICU
tokenizer 处理标点过滤。精度不高但零外部依赖，满足初期话题级检索需求。

#### 4.4.1 中文检索三档降级方案

简单二字分词的精度问题在阶段二会成为痛点。**改为三档降级**，每阶段启用不同档次：

| 档次              | 实现                                       | 召回率         | 性能 | 适用阶段  | 外部依赖                          |
| ----------------- | ------------------------------------------ | -------------- | ---- | --------- | --------------------------------- |
| **L1 文件名匹配** | 话题文件标题 + 关键词 frontmatter 精确匹配 | 高（人工设定） | 极快 | 阶段一/二 | 零                                |
| **L2 关键词匹配** | jieba/Intl.Segmenter 分词 + FTS5 索引      | 中             | 快   | 阶段二    | jieba（Node.js 端口 `nodejieba`） |
| **L3 语义匹配**   | Embedding 向量相似度                       | 中-高          | 慢   | 阶段三    | Embedding 模型 + 向量库           |

##### 阶段化启用策略

**阶段一（极简版）**：**只用 L1**——文件名匹配。

- 零依赖、零成本、零精度问题
- 话题文件命名由代码生成（`topic-{ID}.md`）+ 用户/Agent 在 frontmatter 中设置关键词
- 召回完全靠关键词 frontmatter 命中——比"简单二字分词"更准

**阶段二（轻量实用版）**：**L1 + L2**——引入 jieba 替代简单二字分词。

- 引入 `nodejieba`（约 10MB）
- FTS5 表使用 jieba 分词后的 token 列表填充
- 关键词匹配升级为分词级别的 token 匹配

**阶段三（完整版）**：**L1 + L2 + L3**——叠加 Embedding 向量检索。

- 见 4.4.2 向量库选型

##### 为什么 L1 已能覆盖阶段一

阶段一的项目话题文件数量 <
50 个（24 小时内的新对话）——**完全可以用关键词 frontmatter 匹配**。

- 用户在创建话题时由 Agent 建议关键词
- Agent 在每次对话结束时自动补充关键词到 frontmatter
- 话题切换时由 Agent 主动建议新关键词

这种"半人工、半自动"的关键词管理，比"全自动 FTS5 分词"更精准——因为关键词是 Agent 推荐的语义凝练。

##### L2 阶段的 jieba 集成示例

```javascript
// 阶段二伪代码：FTS5 索引填充
const jieba = require('nodejieba');

function buildFtsIndex(topicFilePath) {
  const content = readFile(topicFilePath);
  const tokens = jieba.cut(content); // ['今天', '天气', '不错', ...]
  return tokens.join(' '); // FTS5 存储格式
}

// 查询时
function searchTopics(query) {
  const queryTokens = jieba.cut(query);
  return db.query(
    `
    SELECT * FROM topic_reports 
    WHERE fts_content MATCH ?
  `,
    [queryTokens.join(' ')],
  );
}
```

#### 4.4.2 Embedding 向量库选型对比

阶段三启用 L3 语义匹配时，向量库的选型直接影响"单文件无服务"架构的纯度。

| 方案                    | 优势                               | 劣势                                 | 维护成本 | 单文件无服务 | 推荐度     |
| ----------------------- | ---------------------------------- | ------------------------------------ | -------- | ------------ | ---------- |
| **sqlite-vec**          | 与 SQLite 原生集成、单文件、查询快 | 生产可用性待验证、生态年轻           | 低       | ✓            | ⭐⭐⭐⭐⭐ |
| **ChromaDB**            | 成熟、社区活跃、文档完善           | 需要独立进程、破坏单文件无服务       | 中       | ✗            | ⭐⭐       |
| **LanceDB**             | Rust 性能好、嵌入式                | Node.js 绑定不成熟、文档少           | 中       | 部分         | ⭐⭐       |
| **本地文件 + 内存索引** | 零依赖、完全可控                   | 重启后需重建索引、大数据集内存占用大 | 低       | ✓            | ⭐⭐⭐     |

##### 当前倾向：sqlite-vec

**理由**：

1. **保持架构一致性**——现有 SQLite 索引已经承载了 FTS5 和结构化数据，sqlite-vec 扩展无缝衔接
2. **单文件无服务**——所有数据（包括向量）都在 `agent.db` 中，备份/迁移零成本
3. **性能**——对于 1 万条以内的向量数据，sqlite-vec 的查询延迟 < 10ms
4. **跨平台**——Windows/macOS/Linux 一致

##### PoC 计划（阶段三启动前必做）

```
1. 准备 1000 个真实话题文件（来自阶段二积累）
2. 用 sqlite-vec、ChromaDB、本地文件三方案各做一遍
3. 测 5 个指标：
   - 插入速度（每条 512 维向量的写入耗时）
   - 查询速度（Top-10 余弦相似度查询耗时）
   - 内存占用（运行时 RSS）
   - 索引大小（存储在磁盘上的体积）
   - 冷启动时间（重启后加载索引耗时）
4. 出 PoC 报告
5. 综合"单文件无服务"约束，决定最终选型
```

##### Embedding 模型选型

| 模型                              | 维度 | 中文支持 | 部署方式         | 推荐度   |
| --------------------------------- | ---- | -------- | ---------------- | -------- |
| **OpenAI text-embedding-3-small** | 1536 | 良好     | API（需联网）    | ⭐⭐⭐⭐ |
| **BGE-small-zh**                  | 512  | 优秀     | 本地（CPU 推理） | ⭐⭐⭐⭐ |
| **BGE-large-zh**                  | 1024 | 优秀     | 本地（GPU 推理） | ⭐⭐⭐   |
| **M3E**                           | 768  | 优秀     | 本地             | ⭐⭐⭐   |

**当前倾向**：BGE-small-zh——纯本地、不依赖外部 API、中文支持优秀、512 维性能与存储平衡。

**隐私考量**：如果用户对数据隐私敏感（对话内容不外泄），必须选本地模型；如果只是工具型 Agent（不涉及核心对话），可选 OpenAI
API 降低成本。

## 五、与用户主动输入的边界

### 5.1 什么属于用户主动输入

| 内容                                   | 归属         | 理由                    |
| -------------------------------------- | ------------ | ----------------------- |
| 用户直接输入的提示词文本               | 用户主动输入 | 用户明确说的            |
| 用户主动提及的文本（选中、引用、粘贴） | 用户主动输入 | 用户明确指给 agent 看的 |
| 用户主动附带的文件/链接                | 用户主动输入 | 用户明确提供的          |

### 5.2 什么属于 Agent 记忆召回

| 内容                | 归属           | 理由                                          |
| ------------------- | -------------- | --------------------------------------------- |
| Agent 基础设定/人格 | Agent 记忆召回 | 不是用户说的，是系统召回的人格记忆            |
| 常驻规则            | Agent 记忆召回 | 不是用户说的，是系统召回的规则记忆            |
| 话题上下文（记忆）  | Agent 记忆召回 | 用户没有主动提及，是 agent 自己召回的话题记忆 |
| Skill 激活说明      | Agent 记忆召回 | 用户没有主动加载，是 agent 按需召回的能力记忆 |
| 工具描述            | Agent 记忆召回 | 用户没有列工具清单，是 agent 自己召回的       |
| Few-shot 示例       | Agent 记忆召回 | 用户没有提供示例，是 agent 从记忆中取的       |

### 5.3 边界判断原则

**一条铁律**：用户明确说出来的 → 用户主动输入。其余一切 → Agent 记忆召回。

如果有人问"那用户引用的文本需要附带元信息（文件名、行号），这些算谁？"——这些元信息是 agent 为了理解用户输入而自动附加的，属于 Agent 记忆召回。用户只提供了"这段文本"，agent 自己补充了"这段文本在哪"。

## 六、记忆类型的统一视图

### 6.1 四层划分（v4.0 对齐）

**万物皆是记忆，但不是所有东西都进记忆索引。**
v4.0 将 Memora 处理的所有信息划分为四层，每层有清晰的归属与边界：

| 层           | 归属者     | 是否进 SQLite 索引 | 何时进入上下文                                  | Agent 的关系      |
| ------------ | ---------- | ------------------ | ----------------------------------------------- | ----------------- |
| **作品**     | 用户       | ❌（只进作品投影） | 仅在 Agent 读取用户作品时按需注入               | 读作品 → 生成投影 |
| **角色**     | 用户定义   | ❌（仅引用）       | 启动时注入到 system prompt 顶部                 | 不涉及 Agent 记忆 |
| **心得**     | 用户脑内   | ❌（不存储）       | —                                               | 完全不涉及        |
| **助手记忆** | Agent 维护 | ✅                 | 启动时（永驻/领域）+ 每轮（话题）+ 按需（能力） | 完全控制          |

**核心边界**：

- ✅ Agent 记住作品的"投影"（概要 + 结构 + 关键决策），不复制作品本身
- ✅ Agent 加载角色文件的人格/语气/专长，但角色不知道 Agent 记住了什么
- ✅ Agent 维护用户画像、话题摘要、对话快照、作品投影、规则
- ❌ Agent 不记录用户心得（主观内化，超出 Agent 能力边界）

### 6.2 助手记忆内部子分类

助手记忆内部按永久性和功能进一步细分：

| 子类         | 永久性              | 存储形式                            | 加载时机         | 备注                                             |
| ------------ | ------------------- | ----------------------------------- | ---------------- | ------------------------------------------------ |
| **用户画像** | `always`            | SQLite `user-profile`               | 启动时全量加载   | 含 identity/preference/expertise/habit/history   |
| **规则记忆** | `always` / `domain` | `rules/*.md`                        | 启动时加载       | 永驻规则 + 领域规则                              |
| **话题摘要** | `topic`             | `topics/*.md`                       | 按话题相似度召回 | 跨会话"上次聊到哪了"                             |
| **对话快照** | `topic`             | 新话题 frontmatter `seed_snapshots` | 切话题时载入     | 3-5 句用户原文作为种子                           |
| **作品投影** | `domain`            | SQLite `work-projection`            | 领域匹配时加载   | 概要 + 结构 + 关键决策                           |
| **能力记忆** | `on-demand`         | `skills/*.md` + `tools/*.json`      | 按任务类型召回   | 技能不进入 SQLite 索引，由 SkillManager 单独管理 |
| **工作记忆** | 瞬时                | 仅内存                              | Loop 内存在      | Loop 结束后转为话题记忆                          |

### 6.3 技能记忆与工具记忆的本质区别

| 维度     | 技能记忆                      | 工具记忆              |
| -------- | ----------------------------- | --------------------- |
| 层级     | Prompt 级别                   | 函数级别              |
| 作用     | 改变"思考方式"                | 提供"执行能力"        |
| 调用通道 | 通过 prompt 引导 + 关键词匹配 | 通过 Function Calling |
| 永久性   | `on-demand`                   | `on-demand`           |
| 管理组件 | `SkillManager`                | Function Calling 框架 |
| 是否索引 | ❌（独立管理）                | ❌（仅 schema 注入）  |

### 6.4 统一索引（仅覆盖助手记忆）

**v4.0 关键变化**：统一索引**只覆盖助手记忆**，不覆盖角色、技能、工具。

| 索引范围      | v3.5（旧） | v4.0（新）                       |
| ------------- | ---------- | -------------------------------- |
| 用户画像      | ✅ 索引    | ✅ 索引                          |
| 话题摘要/快照 | ✅ 索引    | ✅ 索引                          |
| 作品投影      | ✅ 索引    | ✅ 索引                          |
| 规则          | ✅ 索引    | ✅ 索引                          |
| 角色文件      | ❌ 不索引  | ❌ 不索引（仅引用）              |
| 技能          | ✅ 索引    | ❌ 不索引（独立管理）            |
| 工具          | ✅ 索引    | ❌ 不索引（仅 Function Calling） |

**索引的好处**：

- 一套检索逻辑服务所有助手记忆类型
- 跨类型检索成为可能（"找到所有关于'数据库'的记忆"，包括用户画像、话题历史、规则）

## 七、记忆的写入与压缩

### 7.1 写入策略

**实时归档 + 实时写入 + 异步炼化（三轨并行）。**

| 操作                 | 时机             | 方式                 | 落盘位置                            |
| -------------------- | ---------------- | -------------------- | ----------------------------------- |
| 追加对话原文         | 每轮对话结束     | 同步追加到话题文件   | `topics/*.md`                       |
| **用户画像实时归档** | 每轮对话结束     | 同步小模型/规则提取  | SQLite `user-profile`               |
| 生成话题报告         | 后台异步         | 不阻塞对话           | 归档目录                            |
| **对话快照提炼**     | 切话题时         | 同步 LLM 提炼 3-5 句 | 新话题 frontmatter `seed_snapshots` |
| 作品投影更新         | Agent 读取作品时 | 同步 LLM 提炼概要    | SQLite `work-projection`            |
| 话题文件封存         | 达到封存阈值时   | 自动封存并新建文件   | 归档目录                            |

**三轨并行的理由**：

- **用户画像实时归档**：用户前脚说"我叫张三"
  → 后脚就写入 SQLite，下轮对话立即可用。如果异步处理，用户重启进程后会丢失短期内的身份信息（这是 v1.0 修复的核心 bug）
- **实时写入的理由**：对话内容丢失是不可接受的。哪怕慢一点，也要保证写入
- **异步炼化的理由**：话题报告生成可以慢，不影响当前对话体验
- **对话快照的理由**：切话题时同步提炼快照（3-5 句用户原文），保证换话题后 Agent 仍记得"上一个话题的核心想法"

#### 7.1.0 用户画像实时归档（核心机制）

```javascript
// 伪代码：每轮对话结束后，扫描是否产生新的用户画像条目
async function realTimeArchive(messages) {
  const facts = extractUserFacts(messages);
  for (const fact of facts) {
    if (fact.confidence >= 0.8) {
      // 高置信度（"我叫张三""我住在北京"）→ 直接归档，立即可用
      await db.upsert('user-profile', {
        category: fact.category,
        value: fact.value,
        source: fact.sourceTurn,
        weight: 1.0,
        permanence: 'always',
        confirmed: true,
      });
    } else {
      // 低置信度 → 标记待确认，首次召回时 Agent 向用户确认
      await db.upsert('user-profile', {
        category: fact.category,
        value: fact.value,
        source: fact.sourceTurn,
        weight: 1.0,
        permanence: 'always',
        confirmed: false,
      });
    }
  }
}
```

**确认机制**（详见
[01-主架构-v4.0.md §6.5](./01-主架构-v4.0.md)）：低置信度条目首次召回时，Agent 以确认式提问向用户核实；确认 →
`confirmed: true`，否认 → 删除。高置信度条目直接可用。

**用户画像子分类与归档时机**：

| 子分类         | 例子                         | 归档时机             |
| -------------- | ---------------------------- | -------------------- |
| **identity**   | 姓名、年龄、职业、住址       | 实时（用户说即归档） |
| **preference** | 语言偏好、工具偏好、风格偏好 | 实时                 |
| **expertise**  | 熟悉的技术栈、擅长的领域     | 实时                 |
| **habit**      | 工作习惯、对话习惯           | 每天归档时提炼       |
| **history**    | 关键事件、合作过的项目       | 每天归档时提炼       |

#### 7.1.1 对话快照（切话题时同步提炼）

切话题时，从旧话题提炼 3-5 句最有信息量的用户原文，存入新话题文件的 frontmatter：

```javascript
// 伪代码：切话题时同步提炼对话快照
async function extractDialogueSnapshots(oldTopicFile) {
  const userTurns = parseUserTurns(oldTopicFile);
  const seedSnapshots = await llm.complete({
    prompt: `从以下用户发言中选出 3-5 句最能代表其核心想法的原文：\n${userTurns}`,
    maxTokens: 300,
  });
  return seedSnapshots; // 数组形式
}
```

**存储格式**（新话题 frontmatter）：

```yaml
---
topic_id: 2026-06-03-novel
title: 玄幻小说人物弧光
seed_snapshots:
  - '萧然这个角色，我想让他从一个普通人成长为守护者'
  - '我希望他的成长不是靠奇遇，而是靠选择'
  - '他在第三章会面临一个关键抉择：救人还是复仇'
created_at: 2026-06-03
---
```

#### 7.1.2 Agent Loop 中的上下文增长控制

Agent Loop 每轮工具调用结果会追加到上下文中，可能导致上下文突破配额。控制策略：

- **工具结果预算**：Agent
  Loop 中所有工具结果（含增量记忆检索结果）的 Token 总量不超过上下文窗口的 20%，来自 2.3 节为工作记忆预留的空间。记忆召回文档占 ≤
  85%，工作记忆预算 ≤ 20%——两者不重叠
- **单次工具结果截断**：单次工具调用结果超过 2000 字时截断（见 7.6 层级 1），确保单次结果不会独占预算
- **预算耗尽时**：工作记忆预算耗尽后，Agent
  Loop 不再执行新的工具调用，模型基于已有结果生成最终回答
- **配额恢复**：Agent
  Loop 结束后，工作记忆随对话历史一起写入话题文件，下一轮对话重新按配额分配

### 7.2 话题文件封存

同一话题文件超过以下阈值时封存，新建同名 `_v2` 文件：

| 触发条件 | 阈值        |
| -------- | ----------- |
| 对话轮次 | ≥ 50 轮     |
| 文件字数 | ≥ 10,000 字 |

满足任一条件即触发封存。

### 7.3 归档结构

```
archive/
├── 2026-06/                    # 按月
│   ├── week-22/                # 按周
│   │   └── topic-001.md        # 封存的话题文件
│   ├── week-23/
│   └── ...
├── 2026-07/
└── index.json                  # 全局归档索引
```

归档索引记录每个话题文件的元信息，供跨话题检索使用。

### 7.4 剪枝策略

**封存控制单文件大小，剪枝控制归档总量。**
没有剪枝的系统是只进不出的貔貅，磁盘迟早撑爆。

| 策略             | 触发条件                           | 动作                                                           |
| ---------------- | ---------------------------------- | -------------------------------------------------------------- |
| **时间剪枝**     | 归档文件超过 6 个月未访问          | 标记为"可剪枝"，下次归档时自动删除                             |
| **容量剪枝**     | 归档文件总数超过 1000 个           | 按最后访问时间淘汰最旧的 20%，优先淘汰无话题报告关联的原始对话 |
| **话题报告过期** | 话题报告超过 12 个月无任何会话引用 | 自动删除话题报告，保留原始对话索引（极端情况下可恢复）         |
| **用户手动清理** | 用户主动触发                       | 可按话题、按时间范围选择性删除                                 |

**保护机制**：

- 剪枝前 7 天发出通知，用户可取消
- 被剪枝的话题报告保留一个"墓碑记录"（话题名 + 关键词 + 删除时间），确保 FTS5 索引中不会出现"已删除但索引还在"的脏数据
- 话题报告被剪枝后，关联的原始对话原文一并删除（封存满 6 个月且无话题报告引用时）
- 用户手动标记为"永久保留"的话题免于自动剪枝

### 7.5 关键词生成

话题文件和话题报告中的关键词字段由以下流程生成：

**生成时机**：每日归档时，LLM 炼化话题报告的同时顺带生成关键词（≤ 5 个）。

**去重与归一化**：代码侧对 LLM 输出的关键词做去重和同义词归一化（如"数据库"和"DB"归一化为"数据库"），避免同一概念的关键词分散导致检索漏召回。

**人工可编辑**：关键词字段存储在话题文件的 frontmatter 中，用户可手动修改。如果用户手动设置了关键词，每日归档时 LLM 生成的关键词不覆盖用户设置。

**关键词与 FTS5 的关系**：关键词字段用于话题级检索（"找到所有关于'数据库'的话题"），FTS5 全文索引用于对话内容级检索（"找到所有提到'B+树'的对话"）。两者互补，不互相替代。

### 7.6 上下文压缩触发条件与上下文腐烂应对

**压缩触发条件**（借鉴 Claude Code 的五层压缩管道）：

| 层级           | 触发条件                                                       | 动作                                                                                      | 开销                  |
| -------------- | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------- | --------------------- |
| 1 - 预算削减   | 单次工具调用结果超过 2000 字                                   | 截断工具输出，保留前 2000 字 + 末尾 500 字                                                | 低                    |
| 2 - 轻量修剪   | 上下文利用率达到 85%                                           | 移除话题记忆中优先级 4-5 的内容（跨话题关联 + 归档话题报告）                              | 低                    |
| 3 - 等比例压缩 | 上下文利用率达到 92% **且** 剩余 Token 不足以容纳 2 轮完整对话 | 按 4.2 节比例（60%/25%/15%）等比例压缩话题记忆所有内容                                    | 中                    |
| 4 - 实时炼化   | 单次对话超过 30 轮                                             | 将前 20 轮对话原文炼化为一个临时摘要（关键决策 + 当前状态），替换原文，保留最近 10 轮原文 | 高（需额外 API 调用） |
| 5 - 完全压缩   | 上下文利用率达到 98%                                           | 将全部对话历史压缩为摘要，仅保留永驻记忆 + 最近 5 轮原文 + 摘要                           | 高（需额外 API 调用） |

**设计原则**：先应用最不具破坏性的压缩，仅在更便宜的压缩策略不足时才升级。这与 Claude
Code 的"惰性降级"策略一致。

**压缩粒度**：轮次级。压缩时以完整对话轮次为最小单位，不截断单轮对话（避免"上半句在上下文、下半句被压缩"的语义断裂）。

**压缩后恢复**：压缩后的上下文不可逆（对话原文已封存归档）。但归档的原文保留完整索引，用户可通过检索功能找回被压缩的内容。

**上下文腐烂应对**（借鉴 Cline 的 Focus Chain 策略）：

长对话中，模型可能因"Lost in the Middle"效应而迷失方向。引入**焦点注入**机制：

- **触发条件**：上下文利用率达到 50%（而非固定轮次数），之后每增加 15% 再次触发。50% 时注入初始焦点，65% 时刷新焦点，80% 时最后注入——在模型迷失之前就开始引导方向
- **注入方式**：在话题记忆顶部注入当前任务焦点摘要（"你正在做 X，当前进度 Y，下一步 Z"），确保模型不偏离主线
- **摘要来源**：首次注入从上下文组装时提取任务描述；后续注入从 Agent
  Loop 中动态生成——模型在 Loop 中产生的中间推理自然包含当前状态，代码侧提取关键句作为焦点摘要
- **与层级 4 实时炼化的配合**：当层级 4（30 轮实时炼化）触发时，焦点摘要由炼化产物提供，精度更高
- **注入预算**：焦点摘要控制在 200-300 字内，不挤占话题记忆配额（与"话题记忆注入前言"合并为同一消息）

**为什么用上下文利用率而非轮次**：30 轮对话在 8K 窗口和 128K 窗口中含义完全不同。128K 窗口中，30 轮对话可能只占 15% 的利用率，模型还远未迷失。用利用率触发能适配不同大小的上下文窗口。

## 八、跨会话记忆共享

**同一项目内的不同会话共享同一话题层的记忆。**

- 话题文件存储在项目级工作目录（`<storageRoot>/projects/<projectId>/topics/`）
- 同一项目的不同会话通过话题 ID 共享同一话题文件
- 写入时加锁（项目级别锁），避免同一项目内并发冲突

这允许用户在同一项目的不同会话中讨论同一话题时，agent 能自动关联之前的讨论内容。

**跨项目记忆不共享**：不同 `projectId`
拥有独立的存储目录，记忆数据完全隔离。如果用户需要在多个项目间共享某些话题记忆，可通过显式配置"共享话题"实现（未来功能）。

## 九、故障容错与降级策略

### 9.1 文件写入容错

| 风险                  | 策略                                                                         |
| --------------------- | ---------------------------------------------------------------------------- |
| 写入中断（断电/崩溃） | 先写临时文件（`.tmp`），写入完成后校验 MD5，校验通过后原子重命名覆盖目标文件 |
| 磁盘空间不足          | 写入前检查可用空间（< 100MB 时拒绝写入，通知用户清理）                       |
| 文件权限异常          | 写入失败后重试 3 次（间隔 1 秒），3 次失败后降级为内存缓存，通知用户         |

### 9.2 数据库容错

| 风险                  | 策略                                                                       |
| --------------------- | -------------------------------------------------------------------------- |
| SQLite 数据库文件损坏 | 每日自动备份数据库文件（保留最近 7 天），损坏时从最近备份恢复              |
| 数据库锁超时          | 设置 30 秒锁超时，超时后记录日志并跳过本次索引更新，次日归档时自动补更     |
| FTS5 索引损坏         | 归档时做索引完整性校验（`SELECT count(*) FROM fts_table`），异常时自动重建 |

### 9.3 LLM API 容错

| 风险                                | 策略                                                                              |
| ----------------------------------- | --------------------------------------------------------------------------------- |
| API 调用超时/返回错误               | 重试 3 次（间隔递增：1s / 3s / 9s），3 次均失败则跳过当日归档                     |
| 当日归档未执行                      | 次日归档时合并两日的对话原文一起处理，最多累积 3 日（超过 3 日则只处理最近 3 日） |
| 话题报告格式错误（非标准 Markdown） | 代码侧校验输出格式，不符合模板的标记为"格式异常"，放入待确认区，不自动生效        |
| Token 超限（对话原文过长）          | 按 4.2 节比例压缩对话原文后再提交 LLM 炼化                                        |

### 9.4 降级策略

当记忆系统核心组件不可用时，agent 进入**降级模式**：

| 故障组件              | 降级行为                                             | 用户体验                             |
| --------------------- | ---------------------------------------------------- | ------------------------------------ |
| 话题文件不可读写      | 仅使用当前会话的对话原文（内存），不做持久化         | 功能受限但可对话，每次重启丢失上下文 |
| SQLite 不可用         | 停用 FTS5 检索，跨话题关联记忆召回降级为纯文件名匹配 | 检索精度下降，但不影响当前话题内对话 |
| LLM 归档连续失败 3 天 | 自动暂停归档，通知用户手动触发                       | 话题报告不更新，对话原文继续写入     |
| 磁盘空间不足          | 暂停归档和封存，仅写入当前话题文件                   | 历史记忆不再增长，当前对话不受影响   |

### 9.5 监控与恢复

- 每次归档执行后记录一条运行日志（时间、成功/失败、处理的话题数、错误详情）
- 连续失败时在 UI 中显示警告图标，点击可查看错误详情和手动重试入口
- 手动重试支持"仅重试失败的话题"和"全部重新归档"两种模式
