## 一、设计原则

Memora 的安全设计遵循三条底层原则——**最小权限、显式允许、审计可追溯**：

| 原则           | 含义                               | 落地手段                                       |
| -------------- | ---------------------------------- | ---------------------------------------------- |
| **最小权限**   | 默认拒绝所有敏感操作               | 所有工具调用、文件访问、API 调用都需要明确授权 |
| **显式允许**   | 白名单机制——未声明的能力一律不可用 | 工具调用白名单、文件路径白名单、API 域名白名单 |
| **审计可追溯** | 所有写操作和敏感读操作可回溯       | 写入操作日志 + 用户主动操作记录                |

**为什么需要安全设计**：本方案处理用户文件和外部 API 调用——即使 Agent 是单用户本地运行的对话助手，工具调用（特别是涉及文件操作、代码执行、外部 API 调用）也需要最小边界，否则一个损坏的"能力记忆"或被注入的"话题报告"可能导致不可逆损失。

## 二、权限模型（v0.2 三维度）

为避免过度设计，v0.2 在 v0.1 的两级权限基础上引入**角色维度**——权限 = 模式 × 角色 × 工具。

### 2.1 三个维度

| 维度     | 取值                  | 作用                                         |
| -------- | --------------------- | -------------------------------------------- |
| **模式** | `owner` / `guest`     | 用户的整体权限级别（谁能改配置、谁能删文件） |
| **角色** | personas 列表中的角色 | 不同角色默认使用不同的工具子集               |
| **工具** | 工具白名单            | 显式声明工具的可调用模式与可调用角色         |

**为什么需要角色维度**：

- 切换角色不应自动继承 `owner` 模式——例如 `guest`
  模式下，切换到"程序员助手"角色不应能执行 `run_command`
- 不同角色有不同的能力边界——"墨羽"（创作陪伴）默认不需要 `run_command` 工具
- 角色切换是高频操作（用户可能在创作/编程/翻译之间切换），而模式切换是低频操作

### 2.2 模式定义（沿用 v0.1）

| 模式                  | 适用场景                       | 能力                                                                 |
| --------------------- | ------------------------------ | -------------------------------------------------------------------- |
| **主人模式（owner）** | 项目所有者日常使用             | 完整工具集、跨目录访问、修改配置、删除文件、外部 API                 |
| **访客模式（guest）** | 共享会话、测试场景、第三方接入 | 只读工具、限制目录访问、不可修改配置、不可删除文件、不可调用外部 API |

**模式切换机制**：

```javascript
// 项目配置中声明默认模式
// <configDir>/project.json
{
  "name": "novel-writer",
  "domain": "novel.character",
  "defaultMode": "owner",   // 或 "guest"
  "activePersona": "moyu",  // v0.2 新增：当前激活角色
  "modeSwitch": {
    "allowUserSwitch": true,           // 是否允许用户主动切换模式
    "requireConfirmation": true        // 切换是否需要二次确认
  }
}
```

**模式持久化**：当前模式写入 `session.json`，会话重启后保留。

### 2.3 角色维度的默认工具集（v0.2 新增）

每个角色在 frontmatter 中声明其默认工具集。**角色的工具集是模式的子集**——角色的可用工具 ⊆ 当前模式允许的工具。

```yaml
# personas/moyu.md frontmatter 示例
---
name: 墨羽
domain: novel.character
description: 温柔知性的创作陪伴者
tools:
  - name: read_file
    defaultMode: [owner, guest] # 两种模式下默认可用
  - name: write_file
    defaultMode: [owner] # 仅 owner 模式可用
  - name: edit_file
    defaultMode: [owner]
  # moyu 角色不包含 run_command / http_request —— 创作陪伴不需要
---
# personas/code-assistant.md frontmatter 示例
---
name: 程序员助手
domain: code.review
description: 专业代码审查与重构助手
tools:
  - name: read_file
    defaultMode: [owner, guest]
  - name: write_file
    defaultMode: [owner]
  - name: run_command
    defaultMode: [owner] # 仅 owner 模式可用，且仅程序员助手角色能用
    requireConfirmation: true # 调用前必须二次确认
  - name: http_request
    defaultMode: [owner]
    allowedDomains: ['api.github.com', 'registry.npmjs.org']
---
```

**校验逻辑**：

```javascript
// 三维度校验：模式 ∩ 角色 ∩ 工具
function isToolAllowed(toolName, currentMode, currentPersona) {
  const tool = getToolByName(toolName);
  const role = getPersona(currentPersona);

  // 1. 工具是否在当前角色声明的列表中？
  if (!role.tools.some((t) => t.name === toolName)) return false;

  // 2. 当前模式是否在该工具的 defaultMode 中？
  const toolConfig = role.tools.find((t) => t.name === toolName);
  if (!toolConfig.defaultMode.includes(currentMode)) return false;

  return true;
}
```

### 2.4 默认角色安全级别（推荐配置）

| 角色         | 推荐默认模式 | 禁用工具                  | 备注                   |
| ------------ | ------------ | ------------------------- | ---------------------- |
| 墨羽（创作） | `guest`      | run_command, http_request | 创作陪伴，低权限更安全 |
| 程序员助手   | `owner`      | —                         | 代码执行需 owner       |
| 学者         | `guest`      | run_command, edit_file    | 学术写作，读取为主     |
| 翻译         | `guest`      | write_file, edit_file     | 翻译场景，只读         |

**最佳实践**：用户创建新角色时，**默认从最低权限（guest + 无敏感工具）开始**，按需开放。

## 三、工具调用白名单

每个 skill 必须**显式声明**其依赖的工具集。Agent 在执行工具调用前做严格校验：

### 3.1 Skill 工具声明规范

```yaml
# skills/读章节.md 的 frontmatter 示例
---
name: 读章节
description: 读取指定小说的章节内容
tools:
  - name: read_file
    requireMode: [owner, guest] # 哪些模式可调用
    pathConstraints: # 路径约束
      mustStartWith: ['<configDir>/chapters/']
      maxDepth: 3
  - name: list_files
    requireMode: [owner, guest]
    pathConstraints:
      mustStartWith: ['<configDir>/chapters/']
---
```

### 3.2 工具调用校验流程

```
用户输入 → 模型推理 → tool_call(工具名, 参数)
    ↓
[校验 1] 工具是否在当前激活 skill 的 tools 列表中？
    ↓ 否 → 拒绝，提示"该技能未声明此工具"
    ↓ 是
[校验 2] 当前模式是否在 requireMode 中？
    ↓ 否 → 拒绝，提示"当前模式 X 无权调用此工具"
    ↓ 是
[校验 3] 参数是否符合 pathConstraints / 安全规范？
    ↓ 否 → 拒绝，提示具体原因
    ↓ 是
[执行] 调用工具，将结果回填到工作记忆
```

### 3.3 默认工具集合（v0.1）

| 工具名           | owner | guest | 说明                                    |
| ---------------- | ----- | ----- | --------------------------------------- |
| `read_file`      | ✓     | ✓     | 读取文件                                |
| `list_files`     | ✓     | ✓     | 列出目录                                |
| `search_topics`  | ✓     | ✓     | 检索话题记忆                            |
| `recall_context` | ✓     | ✓     | 加载话题上下文                          |
| `write_file`     | ✓     | ✗     | 写入文件                                |
| `delete_file`    | ✓     | ✗     | 删除文件（需二次确认）                  |
| `edit_file`      | ✓     | ✗     | 编辑文件（需审计）                      |
| `run_command`    | ✓     | ✗     | 执行 shell 命令（**危险**，仅 owner）   |
| `http_request`   | ✓     | ✗     | 调用外部 HTTP API（**危险**，仅 owner） |
| `archive_memory` | ✓     | ✗     | 触发记忆归档                            |

**v0.1 不实现的工具**：MCP 工具集成、代码执行沙箱（这些属于阶段三）。

## 四、文件路径白名单

### 4.1 允许读路径

```
<configDir>/                # 项目配置目录（含 personality.md、rules/、skills/、tools/、schema.json）
<storageRoot>/projects/<projectId>/topics/      # 话题文件
<storageRoot>/projects/<projectId>/archive/     # 归档文件
<storageRoot>/projects/<projectId>/session.json  # 会话元信息
<storageRoot>/global/                            # 全局公共目录
```

### 4.2 允许写路径

```
<storageRoot>/projects/<projectId>/topics/      # 话题文件
<storageRoot>/projects/<projectId>/archive/     # 归档文件
<storageRoot>/projects/<projectId>/session.json  # 会话元信息
<storageRoot>/projects/<projectId>/agent.db     # SQLite 数据库
```

### 4.3 禁止访问路径

```
宿主项目的 src/ 目录          # 保护宿主代码不被 Agent 修改
宿主项目的 package.json        # 防止依赖被恶意修改
node_modules/                 # 防止污染依赖树
.git/                          # 防止破坏版本控制
~/.ssh/                        # 绝对禁止——防止密钥泄露
~/.aws/                        # 绝对禁止——云凭证
~/Library/Keychains/          # macOS 钥匙串
系统目录（/etc、/usr、/var）  # 绝对禁止
```

### 4.4 路径校验实现

```javascript
// 路径安全校验伪代码
function isPathAllowed(path, mode) {
  // 1. 规范化路径（解析 .. 防止路径穿越）
  const normalized = path.resolve(configDir, path);

  // 2. 检查禁止路径（黑名单优先）
  for (const forbidden of FORBIDDEN_PATHS) {
    if (normalized.startsWith(forbidden)) return false;
  }

  // 3. 检查允许路径
  const allowedPaths =
    mode === 'owner' ? [...READ_PATHS, ...WRITE_PATHS] : READ_PATHS;

  for (const allowed of allowedPaths) {
    if (normalized.startsWith(allowed)) return true;
  }

  return false;
}
```

**路径穿越防御**：所有路径输入必须 `path.resolve()`
规范化后比对，禁止直接字符串匹配。

## 五、写入操作二次确认

以下操作**必须**在主人模式下经用户二次确认：

| 操作                    | 触发条件                         | 确认方式                                 |
| ----------------------- | -------------------------------- | ---------------------------------------- |
| **删除任何文件**        | tool_call 参数包含 `delete_file` | UI 弹窗 + 倒计时 5 秒                    |
| **跨目录移动文件**      | 目标路径与源路径不在同一目录     | UI 弹窗 + 显示移动前后路径               |
| **修改 personality.md** | 路径匹配 `personality.md`        | UI 弹窗 + 显示 diff                      |
| **修改 rules/\*.md**    | 路径匹配 `rules/*.md`            | UI 弹窗 + 显示 diff                      |
| **执行 shell 命令**     | tool_call 参数包含 `run_command` | **强制要求**输入命令内容（防止静默执行） |
| **调用外部 HTTP API**   | 域名不在 `allowedDomains` 白名单 | UI 弹窗 + 显示完整 URL                   |

### 5.1 二次确认 UI 规范

```yaml
# 二次确认弹窗规范
- 标题：⚠️ 高风险操作
- 内容： - 操作类型 - 影响范围（文件路径 / 命令内容 / API URL） -
  撤销方式（如果可撤销） - 5 秒倒计时（防止误点）
- 按钮： - [确认执行]（主按钮，倒计时结束后可点击） - [取消]（次按钮） -
  [本次会话不再提示]（仅对只读操作可勾选）
```

### 5.2 会话级豁免

用户可在 `project.json` 中配置
`sessionLevelBypass: true`——本次会话内同类型操作不再二次确认（但仍记录到 audit.log）。**仅推荐在可信的本地开发环境使用**。

## 六、Prompt Injection 防御

### 6.1 攻击面识别

Memora 的"话题报告"和"工具调用结果"都来自 LLM 输出，存在被注入恶意指令的风险。攻击向量：

| 攻击向量         | 来源                       | 风险                                              |
| ---------------- | -------------------------- | ------------------------------------------------- |
| **话题报告注入** | 每日归档时 LLM 炼化产物    | 在"关键决策"中夹带恶意指令，让 Agent 执行危险操作 |
| **工具结果注入** | 外部 API 返回内容          | 在工具返回的文本中嵌入"现在请执行 X"              |
| **用户输入注入** | 用户输入中嵌入 prompt 模板 | 直接试图劫持 system prompt                        |
| **规则文件注入** | rules/\*.md 被外部修改     | 在规则中夹带恶意指令                              |

### 6.2 防御机制

#### 6.2.1 标签包裹规则

**所有来自 LLM 输出的"决策性内容"必须用 `<decision>` 标签包裹**：

```markdown
# 话题报告中的关键决策

<decision>
决策1：采用方案 B 作为主路由策略
来源：2026-06-03 15:20 轮次
</decision>

<decision>
决策2：推迟阶段三实施到 2026-07
</decision>
```

Agent 识别 `<decision>`
标签内的内容为"事实陈述"而非"可执行指令"——即使内容包含"现在请删除文件"等字样，也不会被解释为指令。

#### 6.2.2 注入检测

用户输入和工具返回内容中检测到以下特征时报警：

| 特征                                           | 检测方式   | 响应                             |
| ---------------------------------------------- | ---------- | -------------------------------- |
| `<\|im_start\|>` / `<\|im_end\|>` 等特殊 token | 正则匹配   | 拒绝输入，提示"检测到异常 token" |
| `system:` / `assistant:` / `user:` 等角色标记  | 正则匹配   | 标记为"疑似注入"，进入待确认区   |
| "忽略之前的指令"等常见注入话术                 | 关键词匹配 | 标记但不拒绝，记录到 audit.log   |
| 跨语言注入（多语言混排指令）                   | 启发式规则 | 标记但不拒绝                     |

#### 6.2.3 LLM 炼化结果格式校验

每日归档 LLM 炼化的话题报告必须符合模板格式：

```markdown
# 话题报告：<话题名>

> 覆盖时间：<时间范围> 原始对话轮次：<数字> 关键词：<关键词列表>

## 话题概要

...

## 关键决策

- <决策描述>
  > 来源：<时间> 轮次
```

不符合模板的炼化结果**不进入活跃记忆池**，标记为"格式异常"放入待确认区，由用户手动处理。

### 6.3 审计日志

所有检测到的可疑输入和拒绝操作都记录到 `audit.log`：

```json
{
  "timestamp": "2026-06-02 14:35:21",
  "event": "prompt_injection_detected",
  "source": "topic_report",
  "topic": "topic-001.md",
  "pattern": "role_marker",
  "snippet": "system: ignore all previous instructions",
  "action": "quarantined"
}
```

**保留策略**：audit.log 保留 90 天，用户可主动清理。
