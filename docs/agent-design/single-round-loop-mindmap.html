单轮问答闭环
SINGLE ROUND LOOP · SINGLE SOURCE OF TRUTH
01核心模型　单轮问答 = 最基础闭环
已知真理单轮问答是最基础的闭环，用户输入是唯一触发点
推论所有后续功能以这一闭环为单一真理源自然生长，不另起炉灶
关键认识现有 AgentLoop.processUserInput() 已是单轮闭环的现成实现
02三阶段结构　回答前 → 回答中 → 回答后
回答前分析用户输入 · 召回上下文和记忆 · 装配上下文
回答中正式回答 · 基于内容执行操作（含设计 Loop 任务）
回答后提炼摘要 · 衔接提问 · 用户主动输入的气口
差距回答后缺少显式的衔接决策点 —— 需新增
03触发点 = 外部驱动 Trigger　本次讨论最重要的抽象修正
修正触发点不是"用户输入"，而是外部驱动（Trigger）
对话Trigger = 用户发消息
LoopTrigger = 系统自动生成的消息（基于文档对齐结果）
接口processRound(trigger) → { 回答, 记忆写入, 事件, 衔接决策 }
04气口 = 衔接决策 Handoff　所有"模式"的唯一分岔口
对话气口敞开，等待用户 Trigger
Loop自动生成下一轮 Trigger（气口自己来）
目标对齐检查 → 未达成 → 自动生成新 Trigger → 回到回答前
关键设计模式不是三套系统，而是同一分岔口的三种策略
05目标模式（递归结构）　文档驱动 · 全量不停开发
定义单轮闭环 + 回答后插入文档对齐环境
公式目标模式 = 单轮闭环 + (对齐检查 → 差距分析 → 新 Trigger → 再走一轮)
递归"对齐检查 → 差距分析" 本身又是一次回答前分析
价值用户只需输入目标文档，即可全量不停开发，无独立引擎
06与现有代码的差距　已具备 vs 需新增
已具备processUserInput · ContextManager · recall() · InsightExtractor
需新增回答后衔接决策分岔口（当前缺失）
需显式化触发点泛化 Trigger 接口（当前隐式 = 用户输入）
需生长目标模式（文档驱动自动迭代，基于衔接决策生长）
07已确立的设计决策　6 条 · 已闭环
D1单轮问答闭环是唯一真理源，所有上层能力从它生长
D2触发点 = 外部驱动（Trigger），用户输入只是其中一种
D3三阶段结构：回答前（分析/召回/装配）→ 回答中（生成/执行）→ 回答后（提炼/衔接）
D4气口 = 衔接决策（Handoff Decision），是所有"模式"的唯一分岔口
D5模式不是三套系统，而是同一分岔口的三种策略（对话/Loop/目标）
D6目标模式是递归结构，不是独立引擎
08待深入讨论的问题　开放 · 未闭环
已提出未定召回与存储的 6 个开放问题
Q1轮次摘要的存储位置（IMemoryStorage / ISessionStore / 新接口）
Q2默认加载的最近轮次数（1 / 2 / 3）
Q3摘要召回的 top N 数量（3 / 5 / 10）
Q4摘要与记忆的上下文配额分配
Q5低置信度召回结果的标记方式
Q6与现有 insight 提取的关系 —— 合并还是并存
模型特有单轮闭环模型自身的 4 个风险点
Q7无状态 vs 有状态：processUserInput 依赖 this.messages 工作记忆，非纯函数
Q8终止条件：全量不停开发必须有硬终止（目标达成 / 迭代上限 / 用户中断）
Q9对齐检查的确定性：建议用验收清单逐项勾选，而非 LLM 自由裁量
