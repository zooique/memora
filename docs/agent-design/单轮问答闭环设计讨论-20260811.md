# 单轮问答闭环设计讨论（2026-08-11）

> 设计讨论文档 —— 以"单轮问答闭环"为单一真理源，讨论所有上层能力（Loop、目标模式）如何从这一闭环自然生长。

> 关联：`tasks/无限对话方案讨论-20260811.md`（早期记录，已并入本文档核心结论）

## 一、核心模型：单轮问答闭环 = 单一真理源

**已知真理**：单轮问答是最基础的闭环。

**推论**：所有后续功能都以这个基础闭环为单一真理源自然生长，不另起炉灶。

```
     ┌─────────────────────────────────────┐
     │          单轮问答闭环                │
     │                                     │
     │   回答前 → 回答中 → 回答后          │
     │      │                     │        │
     │      └─── 循环（气口）────┘         │
     └─────────────────────────────────────┘
```

**用户输入是触发点**（需泛化，见第三节）。

---

## 二、单轮闭环的三阶段结构

| 阶段 | 职责 | 现有代码对应 |
|------|------|-------------|
| **回答前** | 分析用户输入、召回上下文和记忆、装配上下文 | `AgentLoop.processUserInput` 入口 + `ContextManager` 装配 |
| **回答中** | 正式回答，基于内容执行各种操作（含设计 Loop 任务） | `AgentLoop` 主循环：LLM 调用 + 工具执行 |
| **回答后** | 提炼摘要、衔接给用户的提问和用户主动输入的气口 | `InsightExtractor` 提取 + 摘要生成（需新增：显式衔接决策） |

### 关键认识：现有代码已经是"单轮闭环"

`AgentLoop.processUserInput()` 就是单轮闭环的现成实现：

```
用户输入 → 上下文组装 → LLM调用 + 工具执行 → insight提取 → 事件发射
   └── 回答前 ──┘   └── 回答中 ────────┘   └── 回答后 ──┘
```

宿主（sprite）每次用户输入就是调用一次 `processUserInput()`。
**Loop 已经是"单轮闭环的外部循环"** —— 这个模型不是新建的东西，而是现有架构的显性化。

---

## 三、触发点抽象：从"用户输入"到"外部驱动"（Trigger）

**修正**：触发点不是"用户输入"，而是"外部驱动"（Trigger）。用户输入只是其中一种 Trigger。

- **对话模式**：Trigger = 用户发消息
- **Loop 模式**：Trigger = 系统自动生成的消息（基于文档对齐结果）

修正后，单轮闭环的接口变为：

```
processRound(trigger) → { 回答, 记忆写入, 事件, 衔接决策 }
```

**这是本次讨论最重要的抽象修正。** 不修正则目标模式与"用户输入是触发点"自相矛盾。

---

## 四、气口 = 衔接决策（Handoff Decision）

"回答后衔接给用户的提问和用户主动输入的气口" —— 本质是一个**衔接决策**：回答结束后，决定下一轮由谁触发。

```
回答后
  ├── 对话模式：等待用户（气口敞开，等待 Trigger）
  ├── Loop 模式：自动生成下一轮 Trigger（气口自己来）
  └── 目标模式：对齐检查 → 未达成 → 自动生成新 Trigger → 回到回答前
```

**关键设计**：模式不是三套系统，而是同一个分岔口的三种策略。
现有代码回答后做 insight 提取 + 摘要，**没有显式的衔接决策点** —— 这是要新增的部分。

---

## 五、目标模式：递归结构

目标模式 = 单轮闭环 + 回答后插入"文档对齐环境"：

```
目标模式 = 单轮闭环 + (回答后: 对齐检查 → 差距分析 → 生成新 Trigger → 再走一轮)
```

- "对齐检查 → 差距分析"本身又是一次"回答前分析" —— **递归**。
- 目标模式下，用户只需输入目标文档，即可全量不停开发。
- 这让"单一真理源"真正成立：没有为自动化单独造一套引擎。

---

## 六、与现有代码的差距清单

| 能力 | 现状 | 差距 |
|------|------|------|
| 单轮闭环 | ✅ `processUserInput` | 无 |
| 回答前（分析+召回+装配） | ✅ `ContextManager` + `recall()` | 无 |
| 回答中（LLM+工具执行） | ✅ `AgentLoop` 主循环 | 无 |
| 回答后（insight+摘要） | ✅ `InsightExtractor` + `generateContextSummary` | 无 |
| 回答后（**衔接决策**） | ❌ 不存在 | **需新增：分岔口** |
| 触发点泛化（Trigger） | ⚠️ 隐式 = 用户输入 | **需显式化接口** |
| 目标模式（文档驱动自动迭代） | ❌ 不存在 | 需基于衔接决策生长 |

---

## 七、已确立的设计决策

1. **单轮问答闭环是唯一真理源**，所有上层能力从它生长。
2. **触发点 = 外部驱动（Trigger）**，用户输入只是其中一种。
3. **三阶段结构**：回答前（分析/召回/装配）→ 回答中（生成/执行）→ 回答后（提炼/衔接）。
4. **气口 = 衔接决策（Handoff Decision）**，是所有"模式"的唯一分岔口。
5. **模式不是三套系统**，而是同一分岔口的三种策略（对话/Loop/目标）。
6. **目标模式是递归结构**，不是独立引擎。

## 九、远期设想：子 Agent 套娃（当前不实施）

> **当前阶段：纯设想，不动代码。** 等当前架构（Trigger + 三阶段 + 气口）稳定后，再评估是否需要。

### 核心思路：真理源套娃

子 Agent = 本 Agent 自身（同一个单轮闭环），不是独立引擎。真理源只有一个，自然生长。

### 三种拉起方式

| 方式 | 拉起时机 | 同步/异步 | 是否副本 | 说明 |
|------|---------|----------|---------|------|
| ① 用户拉起 | 用户主动输入 | **同步** | 否（主线程） | 根调用，原始交互方式，复用同一工作记忆 |
| ② 气口/目标拉起 | 问答后气口决策 Loop，或目标对齐未达成 | **同步** | 否（主线程） | 同步生成新 Trigger，复用同一工作记忆 |
| ③ 过程中 fork | 问答中遇到复杂子任务需分解 | **异步** | **是（独立副本）** | fork 副本持独立工作记忆，完成后仅结果汇合回主流程，避免并行写冲突 |

### 为什么③必须是副本

①② 是同步串行执行，复用同一工作记忆没有问题。但 ③ 发生在问答过程中——主流程还在跑，如果子 Agent 直接复用主流程的工作记忆实例（`this.messages` 等），会造成**并行写冲突**和**工作记忆污染**。

所以 ③ 必须是 fork 副本：用 `forkSession()` 创建独立会话上下文，在副本里跑完子闭环后，**只返回最终结果**给主流程，不把副本的工作记忆内容合并回主流程。

### 对 SSOT 的影响

三种拉起方式虽然调度不同，但执行的是同一个单轮闭环。真理源只有一个，符合 SSOT 原则。
