# Memora Agent 设计 —— 以单轮问答闭环为种子

> 这是一篇关于 Agent 内核设计的长文。它以"单轮问答闭环"为种子，用文字逐步推导出完整的设计：从基础模型出发，论述它如何生长出 Loop 与目标模式，再回到闭环内部，分层精雕回答前、回答中、回答后三个阶段的每一处细节。目标不是罗列功能，而是呈现一个 Agent 完整的运行闭环——让读者理解：一切复杂性，都从这一条最朴素的闭环中自然生长出来。

---

## 序言：从一条公理出发

我们面对一个朴素的疑问：一个 Agent 系统，复杂如自动编码、自主规划、长期记忆、多智能体协作，它们的本质到底是什么？

剥开层层封装，答案只有一个——**单轮问答闭环**。

无论多复杂的系统，最终都以"一次提问，一次回答"为基本单元。自动化是它的重复，规划是它的预演，记忆是它的沉淀。如果我们接受"单轮问答闭环"作为公理，那么整个 Agent 的设计就不再是堆积功能，而是一次严谨的推导。

本文遵循的正是这条路径：

1. **立论**：定义单轮问答闭环——Agent 的最小完整单元。
2. **生长**：论证如何从它长出 Loop 与目标模式，而不另起炉灶。
3. **精雕**：回到闭环内部，分层设计回答前、回答中、回答后。
4. **运行**：论述支撑闭环运转的状态、异常与资源机制。
5. **展望**：以三根远期锚点（目标模式、子 Agent 套娃、插卡式角色包）验证公理的延展性。

**文档定位**：本文是概念层设计——论证"为什么"与"是什么"，不含实现代码。文中出现的少量接口名（如 ConfigResourceManager、processUserInput）仅为锚定现有代码位置，签名细节在实现阶段定义。远期锚点章节（第十三章）是设计空间全景，当前不实现，但约束接口形状。

# 第一部分 立论：单轮问答闭环

## 第一章 闭环：Agent 的最小完整单元

### 1.1 为什么是"单轮"

Agent 系统的复杂度常来自"多轮""多步""多智能体"。但我们追问一层：这些复杂概念的最小载体是什么？

- 多轮对话 = 多个单轮问答的**序列**
- 多步推理 = 单轮问答内部工具调用的**循环**
- 多智能体 = 多个单轮问答的**分工**

序列、循环、分工，都是**结构**，而非**单元**。真正的单元，必须满足三个条件：**自足、可重复、可观察**。

- **自足**：一次触发，一次回答，内部完整。
- **可重复**：同一单元可被反复调用，且每次独立。
- **可观察**：单元的执行过程对外可见，可被记录、可被测试。

满足这三个条件的，正是**单轮问答闭环**。它是 Agent 的最小完整单元——如同细胞之于生命，函数之于程序。

### 1.2 闭环的三阶段结构

一个完整的单轮闭环，由三个阶段首尾相接构成：

```
     ┌──────────────────────────────────────────┐
     │            单轮问答闭环                     │
     │                                          │
     │  回答前 → 回答中 → 回答后                  │
     │     │                    │               │
     │     └──── 气口（衔接）───┘               │
     └──────────────────────────────────────────┘
```

- **回答前（Prepare）**：理解触发、装配上下文。这是"认知"阶段——Agent 先想清楚自己拥有什么、需要什么。
- **回答中（Act）**：生成与执行。这是"行动"阶段——Agent 输出回答，并在需要时调用工具。
- **回答后（Reflect）**：提炼与衔接。这是"沉淀"阶段——Agent 把本轮变成记忆，并决定下一轮由谁触发。

三阶段的划分不是随意的。它对应着人类认知的完整周期：**理解 → 行动 → 反思**。任何一次有效的问答，都必然经历这三个时刻。跳过任何一环，闭环就不完整。

### 1.3 闭环的两个开口

闭环需要与外界交换信息，因此有两个开口：

- **入口：Trigger（触发）**——拉起一轮闭环的外部驱动。
- **出口：Handoff（气口/衔接）**——一轮结束后，决定下一轮如何发生。

这两个开口是闭环唯一与外界接触的点。它们的设计质量，决定了闭环是"孤立的问答"还是"生长的系统"。我们在第二章详述。

### 1.4 公理的检验

要验证"单轮闭环是公理"，只需看它能否承载系统的全部复杂性。我们对照一个真实 Agent 的全部能力：

| 系统能力 | 在闭环中的位置 |
|---------|---------------|
| 理解用户意图 | 回答前：输入分析 |
| 长上下文管理 | 回答前：上下文装配 |
| 记忆调用 | 回答前：召回 |
| 多步推理 | 回答中：工具循环 |
| 工具调用 | 回答中：执行 |
| 洞察沉淀 | 回答后：提炼 |
| 会话延续 | 回答后：衔接 |

没有一项能力溢出闭环之外。这就是公理的验证——**一切都能在闭环中找到位置，而闭环不需要为任何一项单独扩张**。

## 第二章 触发与衔接：闭环的两个开口

### 2.1 Trigger：从"用户输入"到"外部驱动"

最早的设计直觉是：用户输入拉起闭环。但很快我们发现一个矛盾——如果闭环只接受用户输入，那么"自动化"从何而来？

答案是：**用户输入只是触发的一种，不是唯一的一种**。

我们把触发抽象为 **Trigger（外部驱动）**：

- **对话模式**：Trigger = 用户发消息
- **Loop 模式**：Trigger = 系统基于上次结果自动生成
- **目标模式**（远期）：Trigger = 目标对齐检查的差距分析

三者本质上都是"一件事请求闭环执行一次"。触发来源的多样性，正是系统复杂度生长的土壤。而闭环本身——只认 Trigger，不认 Trigger 的来源——因此获得了与复杂度无关的稳定性。

这就是第一个抽象的力量：**把"谁触发"从"怎么执行"中剥离**。

### 2.2 Handoff：回答后的衔接决策

一轮回答结束后，Agent 面临三个选择：

1. **等待**：把控制权交还用户（对话模式）。
2. **Loop**：基于本轮结果自动发起下一轮（自动化模式）。
3. **结束**：任务完成，闭环终止。

我们把"回答后选择下一轮由谁触发"的决策，命名为 **Handoff（衔接决策）**。

Handoff 是闭环的出口，也是整个系统的分岔口。所有模式——对话、Loop、目标——在这里分道扬镳。但分岔的是**策略**，不是**引擎**。闭环只有一套，策略可以有多套。

### 2.3 一个重要的既有事实：输入待定与气口接受

在进入更深入的设计之前，必须先确认一个已被验证的机制：**用户输入待定，气口自动接受**。

这是"执行中用户突然发消息"问题的答案。它不是真正的并发，而是：

1. 用户在任何时刻发消息，进入**待定**状态。
2. 闭环在**迭代边界**检测到待定输入，软暂停（挂起而非中止）。
3. 用户输入在气口处被接受，闭环从暂停点**续跑**。

这个机制保证了闭环的串行性——任何时刻只有一个闭环在执行——同时不阻塞用户的任何输入。它已经被完整实现并验证，是本文后续设计的地基之一。

**注**：13.3 行为策略中的"输入中断 allow/block"是角色级策略覆盖——默认 allow（执行中随时接受，走软暂停），角色可设 block（执行期间用户输入排队到下一轮）。前者是全局机制，后者是角色的局部收紧，两者不矛盾。

# 第二部分 生长：从闭环到系统

## 第三章 从单轮到 Loop：闭环的重复

### 3.1 Loop 是什么

单轮闭环解决"一次问答"。但很多任务需要多次问答：先理解目标，再拆解步骤，再逐步执行。

**Loop（循环）** 就是单轮闭环的重复。但重复有两种，必须区分：

- **循环内重复**：单轮闭环**内部**的工具调用循环（回答中阶段多步执行）。
- **循环间重复**：多个单轮闭环**之间**的串联（每一轮是独立的闭环实例）。

我们讨论的 Loop，是**循环间重复**——它是闭环的序列，不是闭环的放大。

### 3.2 为什么 Loop 复用单轮

有人会问：循环不是需要自己的引擎吗？答案是否定的。

Loop 的每一轮，都是一次完整的单轮闭环。它有自己的回答前（分析当前状态）、回答中（执行一步）、回答后（判断是否继续）。Loop 所做的，只是在每一轮的 Handoff 处选择"继续"——**Loop 就是"气口永远选择自动续跑"的对话**。

这带来三个直接好处：

1. **无需第二套引擎**：Loop 与对话共享全部能力（记忆、工具、状态机）。
2. **可暂停可恢复**：Loop 的每一轮边界都是天然的暂停点。
3. **可观察可测试**：每一轮是独立闭环，可单独记录、回放、调试。

### 3.3 Loop 的终止

Loop 必须有终止条件，否则在目标模糊时会无限循环。终止条件有三类：

- **目标达成**：本轮回答确认任务完成（确定性校验）。
- **迭代上限**：达到最大轮数（资源保护）。
- **用户中断**：用户在任何边界暂停或中止。

终止条件属于 Handoff 的一部分——**Handoff 不只是"决定下一轮由谁触发"，还决定"是否还有下一轮"**。

## 第四章 从 Loop 到目标模式：递归的涌现

> 定位说明：本章论证目标模式**在逻辑上**如何从单轮闭环长出；它当前**不实现**，属于远期锚点（第十三章）。逻辑推导在前、实现时机在后——先想清楚"能长成什么样"，再决定"何时动手"。

### 4.1 目标模式的定义

目标模式是更进一步的自动化：用户只提供一份**目标文档**，Agent 持续工作直到目标达成，全程不需要用户干预。

它的工作方式是：

```
目标文档 → 对齐检查 → 差距分析 → 生成新 Trigger → 再走一轮 → 再对齐 ...
```

**关键洞察**：目标模式不是新的引擎，而是一个**递归结构**——在单轮闭环的"回答后"插入一个**对齐环节**（对齐检查 → 差距分析 → 生成新 Trigger）。其中"差距分析"本质上就是一次**回答前分析**，为下一轮装配"还差什么"的上下文。因此：目标模式 = 单轮闭环 + 回答后插入的对齐环节。

### 4.2 递归的边界：对齐的确定性

目标模式有一个必须正视的风险：**对齐检查的确定性**。

如果用 LLM 自由判断"目标完成度"，它可能永远觉得"还有改进空间"，导致无限循环烧资源。因此：

- 目标文档必须包含**确定性验收锚点**（如逐项可勾选的清单）。
- 对齐检查应优先使用**确定性校验**（文件存在、测试通过、检查项完成）。
- LLM 仅在确定性校验无法覆盖时，才参与判断，并需结合资源预算（第十一章）。
- 双保险：验收锚点保证"知道何时完成"，资源预算保证"即使不知道也能终止"——前者防无限循环，后者防烧钱失控。

这是目标模式设计的核心纪律：**自动化越激进，终止条件越必须确定**。

### 4.3 公理的再次验证

目标模式看似与单轮闭环无关，但它完全由闭环生长而来：

- 每一轮工作 = 一个单轮闭环。
- 对齐检查 = 回答后新增的对齐环节（检查"还差什么"）。
- 差距分析 = 回答前的一种特殊输入分析（为下一轮装配"差什么"的上下文）。
- 新 Trigger = 由系统生成，而非用户。

**目标模式不是单轮闭环的例外，而是它最彻底的应用。** 这正是公理的力量：最复杂的系统，不过是基础单元最极致的重复。

## 第五章 模式统一论：同一个分岔口

回顾第二、三、四章，我们得到一条统一的认识：

**对话、Loop、目标模式，不是三套系统，而是同一个分岔口（Handoff）的三种策略。**

| 模式 | Trigger 来源 | Handoff 策略 | 终止 |
|------|-------------|--------------|------|
| 对话 | 用户 | 等待用户 | 用户结束 |
| Loop | 系统自动 | 自动续跑 | 目标/上限/中断 |
| 目标（远期） | 对齐差距分析 | 自动续跑直至对齐 | 验收清单完成 |

这一统一带来了整个系统最重要的性质——**单一真理源（SSOT）**：

- 一套闭环，承载所有模式。
- 一套记忆，服务所有模式。
- 一套状态机，贯穿所有模式。
- 一套测试，覆盖所有模式。

模式的增多不增加系统复杂度，只增加分岔口的策略条目。这就是生长的正确姿态：**复杂度向外生长，而核心保持简单**。

# 第三部分 精雕：闭环内部的三阶段设计

## 第六章 回答前：从混沌到有序

回答前的职责，是把一次原始的触发，转化为一个可执行的上下文。它分三步：**理解输入 → 召回相关 → 装配上下文**。

### 6.1 理解输入

第一步，Agent 必须理解"用户这次到底要什么"。这包括：

- **意图识别**：用户是提问、指令、闲聊，还是需要执行任务？
- **任务分类**：本轮属于简单问答、复杂推理、代码任务，还是摘要生成？（这决定后续 Provider 路由）
- **资源预估**：本轮任务需要多长的上下文、多少步工具调用？

理解输入的质量，决定了整个闭环的走向。一次错误的意图判断，会污染后续所有环节。

### 6.2 召回相关

理解输入之后，Agent 需要获取"回答这个问题所需的知识"。知识来自两个通道：

- **记忆召回**：基于用户输入，从长期记忆中检索相关片段。记忆是事实级的知识（用户偏好、历史决策、项目事实）。
- **摘要召回**：基于用户输入，从历史轮次摘要中检索相关对话。摘要是对话级的记录（之前聊过什么、结论是什么）。

两个通道并行触发，互不阻塞。召回不是简单搜索，而是"以当前问题为线索，寻找历史中与之相关的部分"。

### 6.3 装配上下文

最后，Agent 把各来源的信息装配成一个有序的上下文：

```
上下文 = 系统提示（身份与规则）
       + 最近 N 轮完整对话（固定加载，保证连续性）
       + 记忆召回结果（事实知识）
       + 摘要召回结果（历史对话片段）
```

装配的纪律：

- **固定加载**优先于**动态召回**：最近轮次保证连续性，召回结果作为补充。
- **配额制**：记忆与摘要各占固定份额，避免一方挤占另一方。
- **标记不确定**：低置信度召回结果需显式标记，避免被当作确定事实使用。

回答前装配出的上下文，就是回答中的"认知基础"。它决定 Agent"知道什么"——而一个 Agent 能回答到什么程度，本质上由它"知道什么"决定。

### 6.4 装配的载体：角色包（远期锚点）

装配上下文时，"身份、规则、技能"从哪里来？当前主流做法是**散点管理**——角色设定、技能、规则各自独立装载，简单粗暴地拼进系统提示。但这里存在一个更本质的问题：**设定内容的组织单元是什么？**

本文的答案是：**角色包（Role Pack）**——以"角色"为单位的固定文本范式，把身份设定、技能、规则组织成可装载的整体。它的设计灵感来自**插卡式游戏机**：机器（Agent 内核）提供固定卡槽，卡（角色包）自含全部内容，插卡即玩、换卡即变。

角色包是**编排清单**，不是**大文件**：

```
角色包（Role Pack）· 编排单元
├── frontmatter（元数据）：名称 / 描述 / 触发词 / 版本 —— 用于匹配与传播
├── persona 段：身份设定（我是谁、风格、价值观）
├── rule 段：确定性契约（安全规则，装载时全量注入，不可丢失）
├── skill 段：技能清单（运行时按输入匹配激活）
└── 知识引用：外部资料引用（按需召回）
```

**关键纪律**：角色包**不推翻**分级路径——它内部仍然遵循"契约走注入、技能走匹配、知识走召回"的分级原则，只是把散落的单点设定组织成**可创造、可传播、可复用**的整体。角色包的内容层设计见 13.2，行为层（角色如何影响程序运行）见 13.3。

## 第七章 回答中：从思考到行动

回答中的职责，是产出回答并完成必要的执行。它由两个能力构成：**生成**与**工具**。

### 7.1 生成：从上下文到回答

Agent 基于装配好的上下文，调用 LLM 生成回答。生成过程的纪律：

- **流式输出**：回答逐字产出，用户可以实时看到思考过程。
- **路由选择**：根据任务分类（简单/推理/代码/摘要），路由到最合适的模型。简单任务用轻量模型，复杂任务用强模型。
- **可中断**：任何时刻可被软暂停（挂起）或硬中止（放弃）。

### 7.2 工具：从思考到行动

有些任务，仅靠生成无法完成——需要读取文件、搜索网络、执行代码。Agent 通过工具调用扩展行动能力：

- **工具声明**：Agent 感知可用的工具清单及其能力。
- **决策与调用**：在生成过程中，Agent 判断"是否需要工具"并调用。
- **结果回填**：工具执行结果回到上下文，供后续生成使用。

工具调用是回答中的**内循环**：生成 → 判断 → 调用 → 回填 → 再生成。它让单轮闭环具备了多步行动能力，而闭环本身保持单轮的结构。

### 7.3 内循环与外循环：深与长的配比

第三章已区分两种循环——内循环（回答中）与外循环（回答间）。本章从配比视角补一个关键认识：**内循环决定"一轮有多深"，外循环决定"一次任务有多长"**。

两者是**可配比的资源**，而非固定结构：

- 一个复杂的单步任务，可能内循环深（多次工具调用）、外循环短（一轮完成）。
- 一个简单的多步任务，可能内循环浅（每轮一步）、外循环长（多轮串联）。
- 极端情况下，一次任务甚至可以是"深内循环 + 长外循环"的组合。

这个配比正是第十三章行为策略（工具步数上限、Loop 续跑开关）的物理基础——**角色通过策略选择深与长的配比，而不需要改变闭环结构**。

## 第八章 回答后：从输出到沉淀

回答后的职责，是让这一轮产生长期价值。它分两步：**提炼沉淀**与**衔接决策**。

### 8.1 提炼：把对话变成记忆

一轮回答结束后，对话内容需要被转化为可复用的资产：

- **洞察提取（Insight）**：从本轮对话中提取**事实级记忆**——用户的偏好、做出的决策、确认的事实。洞察是去噪的、长期的，只保留有记忆价值的片段。
- **轮次摘要**：为这一轮生成**对话级摘要**——用户问了什么、Agent 答了什么、结论是什么。摘要是保真的、可检索的，用于未来召回。

洞察与摘要的区分至关重要：

| 维度 | 洞察（Insight） | 轮次摘要 |
|------|----------------|---------|
| 层级 | 事实级 | 对话级 |
| 时长 | 长期保留 | 随轮次积累 |
| 用途 | 回答未来问题 | 还原过去对话 |
| 处理 | 去噪去重 | 保真可检索 |

两者并存，互不替代：洞察回答"用户是谁"，摘要回答"之前聊了什么"。

### 8.2 衔接：让闭环继续生长

提炼完成后，闭环来到出口——Handoff（衔接决策）。Handoff 决定三件事：

1. **是否有下一轮**（继续 or 结束）。
2. **下一轮由谁触发**（用户 or 系统）。
3. **以什么姿态触发**（等待输入 or 自动续跑）。

Handoff 的决策应尽量确定性：

- 对话模式：等待用户。
- Loop 模式：自动续跑，检查终止条件。
- 目标模式：对齐检查，未达成则生成新 Trigger。

**Handoff 是整个闭环中，唯一决定"系统如何演化"的点。** 回答前决定"这轮知道什么"，回答中决定"这轮做了什么"，回答后决定"系统接下来去哪"。

# 第四部分 运行：闭环的支撑机制

## 第九章 状态：闭环运行的骨架

单轮闭环不是无状态的纯函数——它依赖会话级状态。状态由**状态机**统一管理：

```
RUNNING ──pause──▶ PAUSED ──resume──▶ RUNNING
   │                                    │
   └──error──▶ ERROR ──recover──▶ RUNNING
```

- **RUNNING**：闭环正在执行。
- **PAUSED**：软暂停（迭代边界挂起，可续跑）。
- **ERROR**：异常（需恢复校验）。

状态机的纪律：

- **单一真理**：状态只存一处（状态机），不散落于各模块。
- **合法转换**：非法转换（如 PAUSED→ERROR）被拒绝。
- **可追溯**：每次转换记录原因与来源。

状态机是闭环运行的骨架——它保证无论发生什么，系统都能回答"现在处于什么状态"。

## 第十章 异常：闭环的容错

闭环在真实环境运行，必然遇到异常：

- **LLM 失败**：超时、限流、返回空——重试 + 指数退避。
- **工具失败**：执行异常——上报错误，不影响闭环结构。
- **用户中断**：软暂停（可续跑）或硬中止（放弃）。

异常处理的纪律：

- **软硬分离**：软暂停保留状态（可续跑），硬中止放弃状态（不可续跑）。
- **不掩盖**：异常明确上报，而非静默吞掉——让问题可见，才能被修复。
- **恢复校验**：从异常恢复前，确认原因已解除。

## 第十一章 资源：闭环的边界

闭环需要显式的资源意识，尤其在自动化场景（Loop、目标模式）：

- **Token 预算**：每轮消耗的 token 上限。
- **步骤预算**：每轮工具调用的步数上限。
- **成本预算**：单次任务的总成本上限。

资源预算在对话模式中压力不大（用户实时控制），但在目标模式中至关重要——没有预算的自动循环，在数学上是无限循环。

## 第十二章 并发：闭环的串行保证

闭环的并发模型是**严格串行**——任何时刻只有一个闭环在执行。这一机制的实现（待定输入、迭代边界软暂停、气口续跑）已在 2.3 确认并验证，本章论述它的设计价值而非重复实现细节。

串行模型带来两个对立的收益：

- **串行让系统可预测**：任何时刻只有一个闭环写工作记忆，不存在并行写冲突，状态始终一致。
- **边界让用户不阻塞**：虽然串行，但用户输入在迭代边界被接受，交互始终流畅。

这一模型回答了并发设计最危险的问题——"多个事件同时发生时，谁优先"。答案是：**没有并行，只有排队与挂起**。串行不是能力的妥协，而是状态一致性的保证。

# 第五部分 展望：公理的延展

## 第十三章 远期锚点：从单一到可扩展

在收尾之前，我们必须承认：单一真理源不等于单一形态。当公理被推至更远的场景，它会长出新的形态。本文确立**三根远期锚点**——它们当前不实现，但设计上必须为它们预留生长点：

- **目标模式**（第四章已述）：文档驱动的全自动迭代。
- **子 Agent（套娃）**：单轮闭环的递归，异步 fork 独立副本。
- **角色包（插卡式）**：本章重点——让 Agent 本身变得可插拔。

### 13.1 子 Agent：单轮闭环的递归

当一轮任务足够复杂，可以把它**分解为子任务，分发给子 Agent 并行执行**。但子 Agent 不是新的智能体——它就是本 Agent 自身，是单轮闭环的递归调用。

- **同步拉起**：用户触发、Handoff 触发——主线程复用工作记忆，串行执行。
- **异步 fork**：回答中触发——必须 fork 独立副本，异步执行，完成后仅结果汇合。

异步 fork 必须使用副本的原因：主流程仍在执行，如果子 Agent 复用主流程的工作记忆，会造成**并行写冲突**与**状态污染**。副本保证子 Agent 有自己的上下文，只向主流程返回结果。

### 13.2 角色包：插卡式 Agent

如果说子 Agent 是"闭环在纵向上的递归"，那么角色包就是"闭环在横向上的变形"。

**插卡式**的设计愿景是：用户像选择游戏卡带一样，装载不同的角色包来执行任务。内核只提供固定卡槽（装载接口），角色包自含全部内容（身份、规则、技能、知识引用）。

```
角色池（Role Pool）
├── 角色包 A（工程师）  ──┐
├── 角色包 B（项目总监） ──┼──▶ 用户手动选择 / 系统按输入自动匹配 ──▶ 装载进卡槽
├── 角色包 C（翻译）    ──┘
└── ...（可下载、可共享、可传播）
```

**装载方式**：
- **手动装载**：用户显式选择角色包。
- **自动装载**：系统根据用户输入的关键词/语义，自动匹配并装载最合适的角色包。

**与现有架构的自然过渡**（这是三根锚点中，唯一需要在**近期**就提供指导的）：

| 阶段 | 内容 | 理由 |
|------|------|------|
| **近期（M1）** | 装配层引入"角色包清单"数据形状——把"角色 + 技能 + 规则"从三个独立源收拢为一个清单的读取抽象 | 行为不变，但装配层只认"清单"不认"来源"，未来扩展角色包文件时无需重构装配层 |
| **中期（M2）** | 角色包文件格式 + 角色包管理器（复用 ConfigResourceManager 基类） | 继承式扩展，不动基类 |
| **远期** | 角色池（下载 / 共享 / 手动选择 / 自动选择） | 完整插卡式体验 |

**为什么近期必须做**：现在的装载通道是"两个独立接口"（persona 通道 + skill 通道）。如果在 M1 阶段不把装配层收拢为"清单"形状，未来引入角色包时就必须重构装配层——这正是"最后大规模重构"的隐患。**M1 的清单抽象，就是为插卡式预留的生长点。**

**待深入问题**：多角色包冲突裁决——当用户同时装载"工程师"与"项目总监"时，rule 冲突如何裁决？这是角色包成为主流方案前必须回答的问题。（13.3 设计纪律第 3 条给出了部分答案：全局安全规则不可被角色覆盖；但同级角色之间的规则冲突裁决规则尚未定论。）

### 13.3 行为策略全景：三阶段的完整枚举

插卡式的真正价值，在于角色不仅能改变 Agent **说什么**（内容层），还能改变 Agent **怎么做**（行为层）。角色包的完整结构是三层：

```
角色包三层结构
├── L1 内容层（文本）：persona / rule / skill / 知识引用 —— 13.2，本文档已有设计
├── L2 策略层（枚举）：行为开关，角色只"选择"不"定义" —— 本节
└── L3 代码层（扩展）：自定义钩子 —— 远期，需沙箱隔离，当前不设计
```

- **L1 内容层**：角色的知识资产（已设计，见 13.2）。
- **L2 策略层**：角色的行为偏好——本节枚举全部候选维度。**它是"触及程序运行而不触及代码"的边界**。
- **L3 代码层**：允许角色携带自定义逻辑，但这是远期设想（需沙箱隔离防恶意代码），当前不设计，仅在此预留。

**这不是当前实现清单，而是设计空间的全景**——目的是在架构定型前把行为维度想全，让接口为未来预留生长点，避免后续想加某个行为时被迫重构。

#### 回答前（Prepare）：认知策略

| 策略维度 | 可选值 | 含义 | 说明 |
|---------|--------|------|------|
| 理解确认 | off / echo / confirm | 回答前如何处理用户输入 | off=直接进入生成；echo=先复述理解但不等待确认；confirm=先总结输入→**预检停顿**提问"是否这样理解"→用户确认/澄清后进入回答中 |
| 上下文装配 | fixed / query / hybrid | 最近轮次加载策略 | fixed=固定最近N轮；query=按输入召回；hybrid=两者 |
| 最近轮次数 | 1 / 2 / 3 / N | 固定加载的轮数 | 决定上下文连续性强度 |
| 记忆召回 | full / limited / none | 是否召回长期记忆 | none=本角色不依赖记忆（如一次性翻译） |
| 记忆召回配额 | token 数 | 记忆占用上限 | 防止记忆挤占对话空间 |
| 摘要召回 | on / off | 是否召回历史轮次摘要 | 支撑跨会话连续性的能力 |
| 召回置信度 | 0.0~1.0 | 召回结果的相似度阈值 | 低于阈值丢弃，防止噪声污染 |
| 任务分类 | keyword / semantic / llm | 判断任务复杂度的方式 | 决定 Provider 路由的输入 |
| 角色自动匹配 | on / off | 是否按输入自动换角色 | off=仅手动装载，角色固定 |

#### 回答中（Act）：行动策略

| 策略维度 | 可选值 | 含义 | 说明 |
|---------|--------|------|------|
| 工具调用 | allow / block | 回答中是否允许调用工具 | **block=只回答不执行**，纯问答角色 |
| 工具白名单 | 工具名列表 | 仅允许的工具 | 限制角色可用的能力面 |
| 工具黑名单 | 工具名列表 | 禁止的工具 | 高权限角色禁用危险工具 |
| 工具批准 | auto / confirm | 工具调用是否需要用户确认 | confirm=执行前征询（高风险操作） |
| 工具只读 | readonly / full | 是否仅允许只读操作 | readonly=禁止写操作（文件/数据库） |
| 工具步数上限 | N | 单轮工具调用次数上限 | 防死循环 |
| 生成流式 | streaming / non-streaming | 输出方式 | 影响 UI 实时性 |
| 生成温度 | 0.0~2.0 | 回答随机性 | 创作角色偏高，翻译角色偏低 |
| 输出上限 | token 数 | 单轮回答长度上限 | 约束长文输出 |
| Provider 路由 | auto / fixed | 是否按任务类型换模型 | auto=简单/推理/代码分模型 |
| 多步推理 | auto / manual | 是否自动展开多步推理 | auto=深度思考，manual=快速回答 |
| 输入中断 | allow / block | 执行中是否接受新输入 | block=执行期间用户输入排队等待 |

#### 回答后（Reflect）：沉淀策略

| 策略维度 | 可选值 | 含义 | 说明 |
|---------|--------|------|------|
| 结束衔接 | wait / loop / end | 回答后如何收尾（对齐 2.2 的 Handoff 三选一） | wait=暂停等用户（对话）；loop=自动续跑（Loop）；end=任务完成即终止 |
| Loop 续跑 | on / off | 是否支持自动续跑 | off=每次回答后必停（保守角色） |
| 洞察提取 | on / off | 是否从本轮提炼长期记忆 | off=不沉淀（隐私敏感场景） |
| 摘要生成 | on / off | 是否为本轮生成摘要 | off=不生成（一次性对话） |
| 记忆写入 | auto / confirm | 写入长期记忆前是否确认 | confirm=用户可审查写入内容 |
| 会话归档 | auto / manual | 结束后会话归档方式 | 决定跨会话连续性 |
| 用户追问 | ask / silent | 结束后是否主动提问题 | ask=引导对话继续，silent=只等输入 |

#### 跨阶段：全局策略

| 策略维度 | 可选值 | 含义 | 说明 |
|---------|--------|------|------|
| Token 预算 | N | 每轮总 token 上限 | 自动化场景防烧钱 |
| 步骤预算 | N | 每轮工具步数上限 | 防死循环 |
| 成本预算 | 金额 | 单任务总成本上限 | 目标模式必需 |
| 错误处理 | retry / degrade / stop | 异常时的策略 | retry=重试；degrade=降级；stop=终止 |
| 安全规则 | 继承/覆盖 | 是否允许角色覆盖全局 rule | 安全规则默认不可被角色覆盖 |

#### 设计纪律

1. **策略是枚举，不是代码**：所有行为维度都是预定义的可选值，角色只做"选择"，不做"定义"。这保证角色包可安全传播——下载的角色包不会携带任意逻辑。
2. **默认值收敛**：未配置的行为维度使用全局默认值，角色包可以只声明它想改变的部分——**最小角色包**即一个含 frontmatter 的声明文件。
3. **安全优先级**：全局安全规则（rule）优先级高于角色策略——角色不能关闭"禁止删除文件"这类安全契约。
4. **扩展性保证**：即使某个维度现在不实现，枚举的**名称与可选值**必须现在定型，因为它是未来角色包格式的字段契约。

这个设想验证了公理的延展性：**最复杂的系统（多智能体），依然只是最基础的单元（单轮闭环）的递归；而最灵活的系统（可插拔），也只是对同一单元的换装。** 一切复杂都从这里来，也终将回到这里。

---

## 结语：一切复杂，源于一简

回到序言的问题：一个 Agent 系统，它的本质是什么？

答案是：**单轮问答闭环，及其一切自然的生长。**

- 多轮对话，是闭环的重复。
- 自动执行，是闭环的自主衔接。
- 长期记忆，是闭环的沉淀。
- 多智能体，是闭环的递归。
- 可插拔角色，是闭环的换装。
- 行为策略，是闭环的调校——同一闭环，可被角色塑造成不同的行为形态。

这篇文章的每一章，都从同一条公理推导而出。这不是巧合，而是设计的纪律：**当一个系统的所有复杂性都能从最小单元自然生长，这个系统才是真正可维护、可扩展、可理解的。**

Memora 的内核，遵循的正是这条道路。它把一切复杂收敛到"单轮问答闭环"这一条朴素的公理上，然后让系统自由生长。

| 角色包（Role Pack） | 以角色为单位的固定范式：L1 内容 + L2 行为策略（+远期 L3 代码），可插拔的整体 |
| 角色池（Role Pool） | 角色包的集合：可下载、可共享，手动或自动装载 |
| 插卡式 | 内核提供固定卡槽，角色包自含内容，换卡即变 |
| 行为策略 | L2 策略层的枚举项：角色的行为开关（如理解确认、工具权限、记忆模式） |
| 预检停顿 | 回答前的确认点：先总结输入→提问确认→用户确认后进入回答中 |
| 验收锚点 | 目标文档中的确定性检查项（文件存在、测试通过、清单勾选） |
| 远期锚点 | 不实现、但约束接口形状的未来目标（目标模式、子 Agent、角色包） |
