# 方案：工具异步——长任务挂起与结果回流

> **状态：机制已由首个消费者落地（部分定案）**——挂起 / 队列化回流 / 跨轮留存 / 实例终态杀树随 CMD-1 `run_command` 后台化三阶段上线，定案沉淀 **ADR-036**；§0 设想的通用 `async` 声明位与 `wait_tool_results` 工具经 0922 §14.4 改判：首个消费者走 `background` 参数 + 自动回流特化实现，**泛化面待第二个 async 消费者（如子 agent）真实需求触发，防僵尸机制面**。登记日 2026-09-30 · 定案沉淀 ADR-036（2026-10-04）。
> **触发**：用户命题——未来引入 `run_command`（CMD-1）与子 agent 工具后必然出现超长运行任务，工具需要异步化：长工具后台运行，主 agent 先干别的，主动挂起等待，结果回流续跑。
> **实现哲学**：不造新引擎。生长素材 = 现有 **ask 挂起链路**（主）+ **插话队列**（辅）+ **watchdog 超时语义**（借其兜底）。

## §0 结论速览

| # | 问题 | 拍板 |
| --- | --- | --- |
| 1 | 谁声明工具可异步 | 工具定义加**可选 `async` 声明位**，默认 false = 现状零变化 |
| 2 | 结果回流时 LLM 没在等 | **队列化**（对齐 pendingInterjections 模式），下一个气口作输入补充注入，不打断不丢弃 |
| 3 | LLM 主动挂起的载体 | **新工具 `wait_tool_results`（显式调用）**，复用 ask 挂起全链路；watchdog 需区分挂起原因，挂起等工具**不受** 30 分钟用户暂停超时管辖 |
| 4 | step 定义是否破 | **不破**：异步工具「执行」切两段——发起段（step 内受理 + 占位回执）/ 完成段（结果回流 = 新输入事件，后续 step 消费） |
| 5 | 何时实现 | **不提前实现**。与第一个 async 消费者（CMD-1 或子 agent 工具）同批上线，防僵尸机制面 |

## §1 动机

1. **CMD-1 `run_command`**（已定档 3.1.0）：任意命令（构建/测试/git）运行时长不可控，同步等待 = 整轮卡死。
2. **子 agent 工具**（远期）：子 agent 跑一个完整 turn 编排，必然远长于普通工具。
3. 共同诉求：**长任务的等待时间不阻塞主 agent**，LLM 可并行处理其他任务项，需要时主动等待结果。

## §2 现状盘点（2026-09-30 读码实锤）

### 2.1 ask 挂起全链路（结构同构先例）

| 环节 | 位置 | 行为 |
| --- | --- | --- |
| 挂起入口 | `loop.ts` `handleAskUser`（≈1482-1520） | LLM 调 ask_user → 提问落地为工具轮 + 保存 pendingAsk → **同批未执行工具补 `[ASK_SUSPENDED]` 占位** → `yield paused` 挂起 |
| 回流 | `loop.ts` `answerQuestion`（≈1523-1554） | 用户回答写入 `ASK_ANSWER` tool result；`takeAnsweredAsk` 供续跑取走快照 |
| 续跑 | `loop.ts` `continueAfterPause`（≈623-642） | 清理临时状态 + 追加补充输入 + 重置 turn 计数 → 复用 `runIterationLoop` |
| 编排 | `seed/orchestrator.ts` `runResume`（≈101-150） | 处理 ask 超时/回答输入、落盘交互历史、调 continueAfterPause |

**同构性**：挂起者 = LLM 主动发起；外部事件 = 用户回答（异步工具场景 = 后台工具结果）；唤醒通路 = continueAfterPause。三要素与「等异步工具」一一对应。

### 2.2 watchdog 边界（拍板 3 的硬依据）

- `PAUSE_TIMEOUT_MS` = 30 分钟（`constants.ts:52`）；超时检查**仅对 paused 态**（`sessionManager.ts:1093-1099`，从 pausedAt 起算）→ 超时 `markSessionTimedOut` 归档。
- ask 挂起轮 `yield paused` ⇒ **与用户暂停共用 paused 形态 ⇒ 挂起轮 30 分钟必被归档**。长命令 40 分钟 + 挂起等待 = 结果回来轮已死。**现状语义不可直接复用，必须区分挂起原因。**

### 2.3 工具执行与 step 边界（拍板 4 的硬依据）

- 工具并发：`executeToolCalls`（`loop.ts` ≈1697-1868）`yield tool_start` 后 **Promise.all 统一 await** 全部工具，再按原始顺序产出 tool_result。
- `step_boundary` 产出点：`_emitStepBoundary(toolResult)`（`loop.ts:1121`）→ `result === 'continue'` 才 yield（`:1189-1192`）——**在工具执行完、拿到 toolResult 之后**。
- 推论：异步工具发起时回填「受理占位」作 toolResult ⇒ step_boundary 照常产出 ⇒ **step 原子定义不破**。

## §3 拍板（四点逐一）

### 拍板 1：异步能力声明在工具侧（`async` 可选声明位）

- **问题**：LLM 凭什么知道这次该异步受理而非同步等待？
- **拍板**：`ToolDefinition` 增**可选** `async?: boolean`。默认缺省 = 同步语义，全部存量工具零变化。
- **先例**：CMD-2 的 `supportedLanguages` 能力如实声明位；`web_search`/`search_project` 的「未注入则条件性不暴露」——能力面由提供方声明，消费方（loop）按声明分派。
- **消费点**：`executeToolCalls` 分派处——async 工具不进 Promise.all，发起 → 登记 turn 级后台表 → 立即回填占位 toolResult。

### 拍板 2：回流结果永远排队，不打断不丢弃

- **问题**：工具结果先到、LLM 还在干别的（或用户插话中），结果怎么办？
- **拍板**：turn 级 pending 回流队列（**对齐 pendingInterjections 模式**）。注入时机 = 下一个气口（step 间隙/续跑点），形态 = 输入补充（类 ASK_ANSWER tool result 追加）。**绝不打断当前推理流**。
- **轮已收场的兜底**：结果随 `Round.evidence` 落盘（现有通道），下一 turn 召回可见——不造新通道。
- **反模式排除**：强制打断 = 破坏推理原子性；静默丢弃 = 结果丢失违反异步契约。

### 拍板 3：LLM 主动挂起 = 显式 `wait_tool_results` 工具 + watchdog 区分挂起原因

- **问题**：LLM「主动暂停等」的载体是什么？挂起轮被 30 分钟 watchdog 误杀怎么办？
- **拍板**：
  1. 新增**显式工具** `wait_tool_results`：LLM 调用即表达「我在等后台工具」→ 走 handleAskUser 同款挂起通路（pendingWait）→ 全部后台工具完成（或各自超时）→ 结果按序回流 → continueAfterPause 续跑。
  2. **隐式自动挂起不做**——违反「重配置对象只被显式调用」纪律（single-truth-source-mindset 设计陷阱条款）；LLM 必须可观察可决策自己在等什么。
  3. **watchdog 区分挂起原因**：`pausedByUser`（30 分钟归档，现状不变）vs `pausedForTool`（不受用户暂停超时管辖；后台工具自带超时，超时 = 以错误结果「完成」回流，对齐 codeExecutor 三态）。挂起等工具另有总兜底上限（对齐 ask 超时语义，值待实现期定）。
- **用户原话校准**：「主动按暂停等」的意图正确，载体修正——不是 session 级 pause（那是用户触发的形态，混用即带伤），是 ask 式挂起。

### 拍板 4：step 定义不破——执行切两段

- **问题**：工具执行跨 step 悬挂，step = 「一次 LLM 调用 + 该次调用触发的工具执行」还成立吗？step_boundary/thought/metrics/limit 全受牵动。
- **拍板**：异步工具的「执行」语义切两段：
  - **发起段（step 内完成）**：受理 + 占位 toolResult（「后台运行中」回执）→ step_boundary 照常落盘（产出点在 toolResult 后，占位即 toolResult，链路零改动）→ thought.stepIndex 归属发起 step。
  - **完成段（新输入事件）**：真实结果回流 = turn 内新输入 → 后续 step 消费（tokenOut 计在消费 step）。
- **配套**：
  - 落盘：占位回执落 round；真实结果走 `toolResultOffload` 现有卸载通道（超阈原文落盘 + 上下文留引用）。
  - `toolStepLimit`：async 工具发起不占 Promise.all 并发槽（已脱离 step），后台运行登记 turn 级后台表，上限独立管理。
  - metrics：后台时长独立计时，不计入发起 step。

## §4 机制数据流（一图流）

```
LLM step N：发起 async 工具 ──→ loop：登记后台表 + 回填占位 toolResult
             │                                        │
             │                                        └─→ step_boundary 照常落盘（step N 闭合）
             └─→ 继续 step N+1…（干别的）
                        │
        （分叉 A）LLM 调 wait_tool_results ──→ pendingWait 挂起（pausedForTool）
        （分叉 B）LLM 还在干别的 ──→ 结果进 pending 回流队列，下个气口注入
                        │
后台工具完成/超时 ──→ 结果回流（真实结果走 offload 落盘）
                        │
             └─→ continueAfterPause / 气口注入 ──→ 后续 step 消费结果
```

## §5 刻意不做

| 不做 | 理由 |
| --- | --- |
| 通用多任务并行编排 | 子 agent 的活；主 agent 的异步只服务「长工具 + 等结果」最小闭环 |
| LLM 无感知的全自动异步 | 隐式切换反模式；挂起必须显式（wait_tool_results） |
| 跨 turn 后台工具 | turn 收场工具还在跑 = 孤儿结果。收口在 turn 内；跨 turn 是子 agent 编排的需求 |
| 提前实现机制面 | 无 async 消费者时整套 = 僵尸声明（能力位恒 false 零消费先例）。**与第一个消费者同批上线** |
