# 白话设计文档 · 助手（Trae 宝）

> **本文讲什么**：这个「助手」是什么、窗口长什么样、它替你做什么、哪些事明确不做。**读者不需要懂代码。**
>
> **一句话**：系统里多了一个**独立的助手 agent**——它有自己的会话、自己的窗口，像一个替你安排工作的 Trae 宝。工作会话还是原来的普通会话，**自助模式一个字不改**。
>
> **术语**：本文用「助手」指这个 agent；代码里仍叫 `hosted` / 托管。术语的唯一定义在[术语锚点](../.trae/rules/terminology-anchor-rules.md)，本文不另立定义。
>
> **分工**：本文讲**体验与模型**；技术判据、分期与历史裁决见[子会话与目标模式路线](./评估-子会话与目标模式路线-20261108.md)，两稿不互相复制同一段话。外部参照见[TRAE 宝设计观察](./参考-TRAE宝设计观察-20261114.md)。

## 一、三个实体，两条关系

| 实体 | 是什么 |
| --- | --- |
| **用户** | 你 |
| **助手** | **唯一**一个独立 agent：有自己的会话（就是那个窗口），固定装配会话管理工具与身份 |
| **工作会话** | 普通会话，和今天自助模式里的会话**没有任何区别** |

关系只有两条：

- **用户 ⇄ 助手**：在窗口里对话，提需求、看结论、拍板。
- **助手 → 工作会话**：单向操作（建会话、写提示词、开任务、停 / 暂停 / 恢复、代答提问）。工作会话不能反向操作助手。

用户 ⇄ 工作会话那条（原自助）**一个字不改**。

## 二、心智模型：一切照旧，只多一个操作人

- **工作会话就是普通会话**：列表、历史、切换、工具、确认——全按自助模式。
- **助手是额外的操作人**：它理解你的需求，建会话、选角色包、写提示词、开任务。
- **它发起的东西盖章**：`origin='hosted'` + 发送者名 + 派发归属。盖章只为一件事——**区分「这活是助手派的」**，并让岔子能找回它。
- **助手自己那条会话不盖章**：它按「用户开的」记来源；只有它派出去的轮和工作会话才带戳。否则「盖章」就分不清是它自己还是它派的活。
- **自助行为不变**：你自己会话的提问、确认、停止、历史，全部照旧；只有**带戳的轮**才会把岔子交给助手。

**打标不是权限。** 不能因为「这是助手开的会话」就不许它做某件事——那等于把托管和自助分成两种东西。反过来，有些事助手不能做（比如去停你亲手发起的那一轮），不是因为它头上的标记不够，而是**它本来就没有替你做主的资格**。

**也不存在「托管态」这个状态。** 会话只有「谁开的」这一条出生记录；某一轮只有「谁发起的」这一条来源记录。两条记录都不会中途改变，所以能拿来当判据；而「现在还在不在托管」这种会变的属性，本模型里根本不存在。

## 三、助手就是一个 Trae 宝

### 1. 它的工作方式

你告诉它要什么 → 它理解 → 建工作会话（选角色包）→ 写提示词开任务 → 盯住 → 遇到要人介入的环节自己接 → 在窗口里汇报结论 → 该拍板的它拍板，继续开下一个任务。

它只做**会话层**的事：不读文件、不跑命令、不改代码。真正干活的是它派出去的工作会话。

### 2. 它可以同时管多条活

一个助手 ≠ 一条活。它可以在同一时间管理多条工作会话：并行跑、各自推进，它自己排优先级、汇总汇报。

并行不改变自助模式的规矩：你在侧栏照样能进任何一条工作会话、自己发消息、自己停。**助手多开几条活，不等于它把工作区锁给你了。**

### 3. 开活前先说动哪块

它准备开一条新活时，会先说明这条活要动哪些文件或目录。如果和正在进行的活撞了同一处，这次就不开，并把「撞上哪条活、撞在哪」告诉你，由它自己决定等一等还是缩小范围。声明整个工作区等于自愿独占——保守到什么程度由它自己选，不是一刀切只许一条活跑。

范围记在会话自己身上，跟会话标题一起存着，重启、翻旧账都读得到，不靠「翻最近几十条对话」去猜。

### 4. 它只有一个

不存在「第二个助手」。你不能通过「新建会话」再造一个出来——新建会话永远是自助会话。助手只通过**打开助手窗**这一个入口在场。

## 四、窗口：微信式对话

### 1. 只有三类内容

- **你的话**：右侧气泡。
- **助手的结论**：左侧气泡。
- **它转交给你拍板的卡**：只有它主动把决策交给你时才出现，不是工作会话卡片的透传。

工具调用、命令、思考、diff、阶段行——**不上屏，而且在宿主就不发给这个窗口**。要看过程，从**工作台**那一行点「查看运行情况」进入对应的工作会话——工作会话是代理调度用的会话，不进侧栏列表。

### 2. 顶部的「正在输入…」

窗口顶部挂一句状态：正在推进… / 正在思考… / 等你拍板。对应微信里的「对方正在输入…」。它不是过程日志，只是一句状态。

### 3. 图片：按微信的样子

- **输入区保留图片入口**：可以选图、粘贴、拖入，一次多张。
- **发出后是气泡里的缩略图条**：点开预览，文件名退到悬停提示——就是微信里「你发了一张图」的样子。
- **图属于这条对话**：图随消息进助手会话，不另存一份。
- **模型不支持视觉时如实说**：给可见提示，不假装看懂了。
- **助手不产图**：它的回复气泡只出文字；工具读到的图走过程区缩略图，不混进聊天气泡。要让助手也回图，是一次新的能力扩展，不是拨一个开关。
- **派活通道目前不收图**：你发给助手的图留在助手会话里，不能随 `send_to_session` 转给工作会话。这是当前限制，不假装能转。

### 4. 历史与绑定

- 窗口固定绑**助手会话**：打开就铺出这条会话的**全部历史**。
- 侧栏切到任何工作会话，窗口的标题和内容**一字不变**。
- 助手会话**不在侧栏列表里**（2026-11-17 定案：助手会话与托管工作会话同属代理侧，不占用户的导航面）；窗口是它唯一的视图。真机实测亦证实侧栏搜不到这两类会话。
- 这条会话是不是助手，**由持久指针认定**，不由内容或「谁先打开」推测；通知器按同一指针找人，指针错了通知会被静默丢掉。

### 5. 入口只有一个

**「打开助手窗」是唯一入口。** 原来「新建会话时选托管模式」退役——助手只有一个，不是用户可选的会话模式。

侧栏的「新建会话」照常是自助会话，和今天一样。两者不冲突：一个是「我自己聊」，一个是「我找助手安排」。

### 6. 第一次打开

还没有助手会话时，窗口是空的，可以输入；**第一次发送才真正建会话**（和侧栏空白页同一套草稿语义），建好后记下「助手会话是哪条」。

这个指针只回答「窗口上次显示哪条会话」，不回答「这条会话归谁」。指针失效（会话被删）就清掉、回空态，不拿一条别的会话冒充。

## 五、它怎么接住工作

### 1. 开场：建会话、写提示词

它理解你的意图，挑角色包、建工作会话、写好第一条任务说明，然后交出去。它不转发消息，也不新建消息通道——用的就是原来那套通路，**只是说话的人换了**。

### 2. 中场：提问、确认、结束

工作会话跑到一半会停下来等人，冒出三类事：

| 事 | 原来 | 现在 |
| --- | --- | --- |
| 要你回答的**提问** | 只能等你答 | 带戳的轮 ⇒ **同时叫助手**；你在侧栏也照样能自己答 |
| 要人点头的**确认** | 只能等你点 | 带戳的轮 ⇒ **助手自己处理，不在窗口弹卡**（§六） |
| 这一轮**跑完 / 失败 / 被中止** | 只能你自己去翻 | 带戳的轮 ⇒ **同时告诉助手**，由它在窗口汇报 |

**判据按轮，不按会话。** 同一个会话里两种轮可以混着：助手派下去的那几轮，岔子找它；你亲手发的那几轮，还是找你。

**「叫你」不是「改道给它」。** 提问和结果都是**在你之外多叫了它一个**——该问你的还是问你，你随时能插手。确认这一档是例外：带戳的轮由它自己处理，不再塞给你一张会过期的卡。

### 3. 收场：看结论、汇报、下一个

轮结束叫它之后，它读结论，在窗口里用一两句话汇报给你：成了什么、卡在哪、下一步建议。需要拍板的，它替你做执行层的决定，继续开下一个任务；涉及「做什么、不做什么、发不发版」这类产品决定，仍然是你说了算。

多条活同时在跑时，它汇报的是**汇总**：哪条完成了、哪条在等你、哪条被中止了，而不是把每条活的过程都倒给你。

## 六、确认与授权：软约束，不是弹卡门禁

**带戳的轮，确认键统一不需要你点击**：写文件、跑命令、跑脚本，助手自己处理，窗口里不弹工作会话的确认卡。

安全不靠硬门禁，靠三条：

1. **软约束写进助手的提示词**：不推送、不发布；遇到这类动作**先提醒你**；你明确要求（相当于授权）才执行。
2. **审计可见（边界如实写）**：它**做了什么**留在工作会话的轮记录里，随时从工作台进去能看到；它**替你批了什么**只活在当前会话时间线（宿主没有持久审计 sink，重启即失）。所以「动作可追溯」成立，「审批决策可追溯」只在本次进程内成立。
3. **内核恒拦不放开**：`rm -rf /`、格式化磁盘、读写凭据这类从来不在「问你一下」的范围里，授权也解不开。

**范围严格限定在带戳的轮。** 你自己发起的那几轮，确认行为一点不动——该弹卡还是弹卡，该等你还是等你。

**为什么不硬卡**：Trae 宝的价值是「你不用盯着」。硬卡会把「你不用盯着」变成「你必须守着」。代价是「它擅自执行」只能靠提示词、提醒和审计兜底——这条风险照实写在 §九。

**窗口里的卡**只在助手主动把决策转交给你时出现：比如它判断这件事该由你拍板，或者软约束要求它先问你。它不是工作会话确认卡的转发通道。

### 用户介入边界（2026-11-17 定案，钉死三层）

助手不是你本人，它只是你委托的操作人。三类交互的边界必须钉死（之前分散在 §五.3 和本节，容易产生"全程不用介入"的歧义）：

| 交互类型 | 助手能不能代劳 | 你需不需要介入 | 例子 |
| --- | --- | --- | --- |
| **执行层确认** | ✅ 能代劳，一律不弹卡 | ❌ 不需要 | 写文件、跑命令、跑脚本的确认卡 |
| **决策层提问** | ❌ **不能替你答**，只能把问题**转达给你** | ✅ 必须你自己答 | Worker 发出 `ask_user`（选方案、拍板需求、回答"你要 A 还是 B"） |
| **不可逆操作** | ⚠️ 不能自动做，软约束拦住 | ✅ 必须你说"推/发布/发版"才执行 | git push、发 npm 包、发布版本 |

**助手自己不做不可逆操作的判断**：P1 期间 Worker（助手派出去的工作会话）不做不可逆操作，由 `workOrder`（派活时的语义边界）显式声明"本条不触发推送/发布"；P2 Hand back 机制落地后再放开。

## 七、标记：两条不变的事实

标记分两级，**它们是两条不同的事实，不是同一件事存两遍**：

1. **会话级：这个会话是谁开的。** 助手创建的**工作会话**打戳，用途只有一个——让你一眼看出「这个不是我开的」。
2. **轮级：这一轮是谁发起的。** 只有助手自己发起的那一轮打戳；你亲手发的轮不打戳。同一会话里两种可以并存。

**轮级戳是唯一会被运行期读取的标记**：它决定这一轮的岔子叫谁（§五.2）。会话级戳从不参与判断。

**戳永久保留、不回填、不是「托管态」**：你接手继续用，历史记录上的戳不消失；旧数据没有戳的，按「用户创建 / 用户输入」看待，不按今天的猜测改写过去。

## 八、明确不做的事

| 不做 | 为什么 |
| --- | --- |
| 不造「任务」对象 | 真源是会话。**结论不变，但解释更新（2026-11-17 定案）**：不给再造平行 Ticket 实体（因为"再造就要维护对应关系"），而是**给工作会话加三个可选字段**（workOrder = 语义边界 / workStatus = 工作状态 / subscribed = 事件订阅）——会话本身同时是 Worker + Ticket，维护对应关系 = 0。这是 SSOT 原则的正确落地：复用同一份数据的四问（谁写怎么写 / 能力还是数据 / 要不要造新词 / 删除测试）全部过，不是因为"怕维护对应关系"才不造，是因为"不需要造"。 |
| 不建父子树 | 助手只有一层，深度恒为 1。不做「助手再派助手」的多级结构。 |
| 不转发消息、不新建消息通道 | 助手是「代写提示词」，不是「中转站」。消息走原来的通路，只是说话的人换了。 |
| 不加深度限制闸 | 既然只有一层，就没有可递归的深度，不需要为此加一道闸。 |
| 不把助手的工作会话做成特殊会话类型 | 它就是普通会话，只是带了来源标记。特殊类型会让所有既有逻辑都要分叉。 |
| 不造第二个助手 | 助手只有一个，入口只有一个。 |
| 不做常驻后台服务 | 它只活在当前编辑器进程里；关掉编辑器就下班。 |
| 不把工作台当作助手的必需部件 | 工作台 + 助手汇报已经覆盖「交出去之后还能看见什么」；工作台冻结，窗口跑通后单独决定是否删除。 |

## 九、已知限制（照实写）

- **只有一层**：不能让助手再派助手。更复杂的任务在工作会话内部逐步推进，不在助手层继续分包。
- **没有「托管态」这个状态**：想让它别动，办法是停掉那一轮——那是轮级动作，一直都有；「收回托管」不存在。
- **关掉编辑器，助手就下班**：它不是常驻后台服务，只活在当前这个编辑器进程里。重启之后，盘上的轮还在，但在跑的轮随进程消失，结果也没人来收；它得像重新上班一样被叫起来、重新建立清单。
- **重启后它自己的上下文会断**：历史戳还在，它也能从历史重建「开过哪些会话」，但对话上下文里对「我还管着哪些」的记忆不会自动续上。
- **窗口不呈现工作过程**：它只汇报结论；要看工具行、命令、diff，从工作台那一行点「查看运行情况」进入对应的工作会话。
- **助手只回文字，不回图**：你能发图给它、图在气泡里按微信形态展示；但它的回复气泡不产图。
- **派活通道不收图**：你发给助手的图留在助手会话里，不能转给工作会话。
- **并发有既有约束**：多条活可以并行，但仍受工作区写线与「开活前先说动哪块」的范围声明约束。
- **存量不回填**：旧会话和旧轮次没有戳，一律按「用户创建 / 用户输入」看待。
- **软约束不是结构保证**：确认改为助手自行处理后，「它擅自执行」只能靠提示词、提醒和审计兜底。内核恒拦仍然拦得住最危险的一类，但恒询问清单里的操作不再有物理门禁。**这条是用户明确选择的取舍**，不包装成「更安全」。
- **批决策不持久**：宿主当前没有持久审计 sink；「谁批的」只在当前会话时间线，重启即失。动作本身在轮记录里，能还原「做了什么」，不能还原「谁批的」。要持久审计是另一个工程量，别把现在的审计当合规证据。

## 十、一句话合起来

> **助手 = 一个独立的 Trae 宝 agent + 一条自己的微信式会话 + 两级标记。** 工作会话还是普通会话，自助一个字不改；它替你开会话、写提示词、同时管多条活、接住自己那几轮的岔子、把结论汇报给你。确认不弹卡，靠软约束与你的明确授权；过程不上屏，只交结果。助手只有一个，入口只有一个——打开助手窗。

## 十一、落地进展

### P1：Router/Worker 分层（2026-11-17 已落地）

**做了什么**：给工作会话扩了两个可选字段（`workOrder` = 语义边界 / `workStatus` = 工作状态），宿主事件钩子消费后写状态，工作台状态优先读本字段。

**改动量**：9 个文件，+217/-11 行。宿主全量单测 213 文件 3261 通过 + 0 失败。内核守卫测试 5/5 通过。

**为什么这就是"工作会话本身就是 Worker + Ticket"**：
- 没有造平行 Ticket 实体——Worker 会话的 `SessionMeta` 同时承载会话真源和工作状态真源
- 会话创建时同批写入三个字段（`workOrder` + `workStatus='working'` + 既有 `origin='hosted'`）——Worker 身份在创建时就确定，不后补
- 自助会话 `workStatus` 永远 undefined（`origin='hosted'` 守卫）——自助模式零改动

**三原则验证**：
| 原则 | 结论 |
|---|---|
| SSOT | 全部在既有真源（SessionMeta / customTools / 事件钩子）上长，没造平行实体 |
| 自然生长 | Worker loop 零直接写入 SessionMeta（宿主事件钩子写）；入口层 schema 只加 `mandate`（语义边界）不加技术方向 |
| 不带伤 | 自助会话 `workStatus` 永远 undefined；AgentLoop / toolExecutor / confirmCoordinator 自助路径零改动 |

**真机验收订正（2026-11-17，两轮）**：

- **V1（吞 mandate）**：装配层手抄 6 参箭头函数吞掉第 7 个可选参数 `mandate`，TS 不报错（可选参数使 6 参可赋给 7 参签名），旧单测又都直连面板绕开了装配层。
- **V2（this 丢失，V1 修复引入）**：工厂 resolve 返回 `chatProvider.createHostedSession` 裸方法引用，裸调用时 `this === undefined`——方法内部第一行就是 `this.sessionModes.isManaged()`，崩成 `E_HOST`。TS 仍不报错（函数类型不检查接收者绑定）。

两次都是**测试替身与真实形状不同构**导致全绿漏过：V1 用 vi.fn（裸函数、无接收者），V2 签名虽返回 owner 但工厂内部裸调用方法引用。修法：factory 签名强制 resolve 返回 **owner 对象**（不是裸函数/方法引用），内部以 `owner.method(...)` 调用——this 随 owner 走，不靠 bind 或箭头函数。测试改用带 this 依赖的 owner 假对象，并加变异验证（签名回退成裸函数形态时 6/7 必红）。

### P2：Hand back 机制（骨架已钉 · Worker 触发 + 助手决策待真实案例）

**已钉骨架（2026-11-17 落地）**：
- 纯文本固定格式：`[HAND_BACK] reason: <一句话> | suggestion: <可选> | payload: <可选 JSON>`（设计文档 B6/B9 同源）
- 宿主正则解析器 + 格式化器（`hostedWorkStatus.ts` 同定位的 `handBackMessage.ts` 纯函数，25 条单元测试全绿）
- 宿主 Hand back 消费者（`HandBackConsumer` 类：解析 → 幂等守卫 → 找助手 loop → `enqueueCommandResult` 注入，和 `HostedSessionNotifier` 同一条通道）

**等真实案例钉的部分**：
- Worker 侧怎么产出 Hand back（可能通道 A：run_command 输出正则识别；B：Worker loop Hand back hook；C：ask_user 内容识别）——≥3 个真实案例后钉死一条
- 助手侧收到 Hand back 后的决策分支（转新活 / 合并 / 转述用户）——必须靠真实 Hand back 消息来定

**为什么骨架先钉（跳过了"真实案例 ≥3 个"约束）**：通道和格式是设计文档 B6/B9 已钉的边界，不靠推演也能定。Worker 触发条件和助手决策逻辑才是推演不准的部分，留到案例来。

### P3：Subscription 消费（未落地）

**要做什么**：Worker 会话可以订阅事件源（git commit、CI 状态、Issue 评论），相关事件自动流进 Worker 上下文，不需要用户手动转发。

**为什么放远期**：memora宝当前是被动的（用户找它才启动），关掉编辑器就下班——Subscription 在常驻后台场景下才是生命线，被动模式下优先级没那么高。P3 前先评估：如果 memora宝 一直不做常驻，Subscription 可以延后或放弃。
