## 二、命题一 · 会话「留存区」（用户原词：归档存放地）

### 2.1 现状实锤（删一次会话到底删了什么）

| 层 | 落地真相 | 证据 |
|---|---|---|
| 会话本体 | `.memora/sessions.json` 的 `metas` + `roundIdsStore` 条目抹除 | `sessionStore.ts:56/136-152` |
| **对话原文** | `.memora/rounds/{roundId}.json` **物理删文件**（`unlinkSync`） | `workspaceRoundStore.ts:309-317` |
| 该轮记忆摘要 | **软删**进回收站（可恢复），非物理删 | `chatPanel.ts:1531-1536` |
| SessionMeta（summary/keyTopics） | 随 metas 一并删除 | `chatPanel.ts:1525-1526` |

第二个物理删口：`delete_turn`（单问答删除）→ `sessionStore.ts:171 truncateFrom`，同样是 `decrementRef` + 物理删。

`.gitignore:47` 已忽略 `.memora/` ⇒ 留存落此目录不污染 git。

### 2.2 用户的判断：对一半

- **对**：Round 原文是「记忆产生的原文」——删了就等于**只留结论、烧掉证据**；且 G35（记忆溯源跳转）还没落地，删掉就永远补不上。这是真痛点。
- **需纠正**：不要把「删会话」说成「删记忆」。摘要只是软删可恢复，**真正不可逆的是对话原文**。两件事不许混为一谈。

### 2.3 三个必须写进方案的坑（不写必炸）

1. **24h 孤儿清扫会静默吃掉「物理搬走」的留存**
   `extension.ts:255` 每次启动跑 `sweepOrphans(DEFAULT_SWEEP_MIN_AGE_MS = 24h)`，判据 = `refCount === 0` 且超龄（`workspaceRoundStore.ts:356-381/427`）。
   ⇒ 若归档实现为「把 Round 搬到专属目录且引用归零」，**超过 24 小时会被自家保洁机制清掉**。这是最贵的坑。
2. **不清引用即天然免疫**
   归档只搬 sessions.json 的「归属」，**不调 `decrementRef`、不删 Round 文件** ⇒ `refCount > 0` ⇒ sweep 天然不碰 ⇒ 溯源链完好。**这是成本最低形态**。
3. **术语撞车——不要叫「归档」**
   仓库已有四处占用：`SessionArchiver`（`src/agent/managers/sessionArchiver.ts`，实为会话摘要/自动命名）、`archiveMode`（ADR-015 记忆归档模式二态）、记忆回收站（`deletedAt` 软删）、`protocol.ts:127` 注释已把「会话进历史列表」叫归档。**再加第五个必然乱**。
   ⇒ 见 §6 待拍板 ①。

### 2.4 定案（2026-10-01 用户拍板）：**不做独立查看 UI，= 会话列表的两个显示区域**

**决策**：删除按钮保持不变（物理删 + 摘要进回收站，现有语义一字不动），其旁新增一个「存入留存区」按钮；留存区**不是新面板**，而是历史浮层里的**第二个分组**；组内条目同样带「彻底删除」。

**为什么「单独做一个查看 UI」是错的**（嫁接 vs 并列）：

- **查看会话的能力已经存在且只有一套**：点条目 → `switch_session`（`protocol.ts:146`）→ `chatPanel.handleSwitchSession`（`:831`）→ `replayCurrentSession`（`:1701`）回放进对话区。再造一个「留存区查看面板」= 第二套 transcript 渲染，纯并列重资产。
- **落点实锤（决定成本的关键证据）**：

| 环节 | 单点在哪 | 分区成本 |
|---|---|---|
| 数据源 | `chatPanel.pushSessionList`（`:1460-1473`），唯一出口，过滤掉当前会话后按 `updatedAt` 降序 | payload 加一个 `archivedIds` 字段即可，零新通道 |
| 渲染 | `chatView.renderHistoryMenu`（`:4879-4915`）**手写 DOM**，借 `.treedd__item` 类名 | **天然支持多分组**——它走 `initDropdowns` 基于 class + `dataset.treeddId` 的**全局委托**（`:4966 __historyOnSelect`），加一组标题 + 第二段循环即可，**不需要第二套委托、不需要动 treedd 组件** |
| 删除动作 | `handleDeleteSession`（`:1485`），已有 modal 确认 + 摘要软删联动 | 复用；只需追加「从 archivedIds 摘除」一步 |

### 2.4a UI 形态定案（2026-10-01）：**浮层顶部 tab，但实现必须是「单列表 + 过滤器」**

**（1）本质定性（用户拍板，写死防漂移）**

> **留存区 = 列表的一个分组标签（视图属性），不是封存状态（数据属性）。**
> 它解决的问题只有一个：**会话记录要保留（Round 原文是摘要记忆的溯源原文），但不应该污染近期列表。**

数据层因此**不加状态机**，只加一个视图标记 `archivedIds: string[]`。

**（2）为什么用 tab 而不用「默认折叠的分组」——实锤依据**

`components/dropdown.ts:110-113`：

```ts
function menuItems(el: HTMLElement): HTMLElement[] {
  const menu = el.querySelector('.treedd__menu');
  return menu ? Array.from(menu.querySelectorAll<HTMLElement>('.treedd__item')) : [];
}
```

**`menuItems` 只按类名取，完全不过滤隐藏/不可见元素**。而它服务于 `:170-194` 的键盘导航（ArrowDown / ArrowUp / Home / End 用 `items[i].focus()`）。

⇒ **任何「两套 DOM 同时存在、靠显隐切换」的方案都会踩雷**：隐藏那一组的 `.treedd__item` 仍在导航集合里 ⇒ 方向键 / Home / End 会把焦点移到**看不见的条目**上（`focus()` 落在不可聚焦元素上，导航静默失效）。

| 候选形态 | 是否同时渲染两组 DOM | 判定 |
|---|---|---|
| 双段分组 + 留存区默认折叠 | 是 | ❌ 踩 menuItems 隐藏项陷阱（除非懒插入 DOM，多一层状态）|
| 照抄 settings 的 `.tabs` 多容器显隐 | 是 | ❌ 同上；且 settings 那套是为「多子视图各自取数」设计的，会话场景用不上 |
| **视觉 tab + 单列表过滤（定案）** | **否** | ✅ 一次只渲染一组，item 集合天然干净；且天然满足「默认完全看不到留存区」|

**（3）正解：tab 是「过滤器」，不是「多视图容器」**

与 §2.5「除 5 处外逻辑完全一致」自洽——**实现上它本来就是同一个列表**：

```
┌ 历史浮层 ─────────────────────────┐
│ [ 会话记录 ]  [ 留存区 (3) ]       │ ← role="tablist"，两个 .tab-btn（视觉）
├───────────────────────────────────┤
│ 条目：标题 · 时间 · [动作] [删除]   │ ← 单一容器 .treedd__menu 内的
│ 条目：…                            │    .treedd__item，结构上与今天逐字一致
└───────────────────────────────────┘
```

- `session_list_data` 全量下发 + `archivedIds: string[]`（**单一数据源，不拆成 sessions/archived 两个数组** ⇒ 无双份真相源）；
- 切 tab = 改一个过滤条件 + 重渲染**同一容器**（`renderHistoryMenu(list, view)`），**零 host 往返**、不需要 settings 那套 `_pendingTab` 缓存；
- 默认 tab = 「会话记录」，浮层每次打开重置为该 tab（不记忆上次，避免跨会话隐藏状态）；
- 未来若加 FD-3 会话搜索，只是**第三个过滤条件**，形态天然扩展——这是选 tab 而非折叠的真正价值（不只是好看）。

**（4）两条硬约束（违反即功能性 bug，必须写进设计与单测）**

1. **tab 按钮绝不能带 `.treedd__item` 类**：`dropdown.ts:197-206` 的 click 委托命中 `.treedd__item` 后立即 `close()` ⇒ 带了该类的结果是**点一下 tab 整个浮层就关了**。
2. **tablist 键盘导航不得依赖 Tab 键**：`dropdown.ts:190-193` 把菜单内 `Tab` 处理为「收起菜单」。tab 切换只用 **click + Enter/Space**（按钮原生语义），并把它们在 DOM 中置于 `.treedd__item` 集合之外。

**（5）为什么不采纳「对话面板顶部常驻 tab」**

历史操作是低频的：常驻会占用对话顶部横向空间，与标题条 / 任务进度条（planBar）拥挤，收益不配。浮层内顶部已足够。

### 2.5 「其他逻辑完全一致」——准确说法是：**除以下 5 处外一致**

这 5 处必须显式登记，否则实现时必翻车：

| # | 分叉点 | 为什么不可能完全一致 | 处理办法 |
|---|---|---|---|

| 4 | 新建会话归属 | 天然不属于留存（`new_session` 产出的 id 不在 `archivedIds`）| 无需代码，但要在 `createSession` 附近写注释固化，防后人误以为要初始化 |

**完全一致的部分**（不用改一行）：排序（`updatedAt` 降序）、标题派生（`getSessionDisplayName`）、相对时间（`fmtRelativeTime`）、空态、回放链路、`listSessions` 排除当前会话的规则。

### 4.2 为什么「行数大就该拆」是误区

1. **规则里没有行数判据**：`progressive-refactor-rules.md §1` 定的是「行数 > 1000 = **软观察信号**，功能内聚 → 保留监控，不强制拆分」，并明令禁止「阈值已达但理由是『看着乱』」。
2. **HOST-S15 已裁决**（2026-09-20）：不新增行数阈值、不加行数守卫；真判据是硬阈值三选一 —— 字段数 ≥15 / 职责数 ≥5 / **修改成本 = 单次改动需触碰 ≥10 处无关代码**。
3. **行数是会漂的数字判据**：每多改一次即过期，引用前必须重算（如同 `project-rules.md §7.6` 的 IPC 通道计数纪律）。
4. **HOST-S15 的签发理由今天仍然成立**：当时既无具体修改成本取证，也无「新加 UI 无处安放」的证据 —— **要先拿出新证据才能翻旧裁决，不能凭「现在更大了」**。

### 4.4 什么情况下才该拆（触发条件，写死免纠结）

- 任一新需求出现「**单次改动触碰 ≥10 处无关代码**」的具体证据 → 对该次涉及的**那一块**做局部抽离（**顺手在功能同批做**），而非全局重构；
- 连续 ≥3 个批次的新 UI 都要往同一个大文件里塞（候选：`chatView.ts` 的会话/历史区块）→ 届时把该**区块**抽成独立模块；
- HOST-S15 到期复查日 **2026-11-19**（四选一：复现 / 收敛 / 降级回 docs / 回退）。

### 6.1 命名候选逐词否决（2026-10-01，全库实锤）

**可用性判据**：① 全库无既有语义占用；② 不与「删除」混淆；③ 不暗示数据状态（它不是封存/冻结，仍能继续聊）；④ **不能暗示"移出了列表"**——它仍在列表里（第二个 tab），叫「已移出/不显示」是撒谎。

| 候选 | 否决理由（证据）|
|---|---|
| **归档 / 存档 / 档案** | 「归档」四处占用（`SessionArchiver` / `archiveMode` / 记忆回收站 / `protocol.ts:127` 注释）；「存档」近亲同义且已用于历史快照（`docs/architecture/host-plugin-alignment.md:4`）⇒ 会让人误以为数据搬走了，而实际 Round **原地不动** |
| **归忆 / 忆 / 记忆** | 语义错位：会话原文是记忆的**出处与证据**，不是记忆本身；且与产品口号「万物皆记忆」撞义 |
| ❗ **收纳区** | **直觉上的最佳候选，但被实锤否决**：项目语汇里「收纳」= **内容收进某个容器/聚合体** —— `docs/architecture/process-event-log-replay-design.md:346`「运行时即**收纳**进大容器」、`memory-as-summary.md:138`「历史保细节、记忆不**收纳**残缺」。用它表达"挪出列表" = 语义漂移 |
| **封存区** | 「封存」= 测试守卫的暂时挂起（`CHANGELOG.md:86`「封存期 `it.fails` 守卫」），且带"冻结"味，与本设计「仍能继续对话」冲突 |
| **搁置区** | 「搁置」= 推迟不做（`docs/方案-文件改动diff可视化-20260926.md:169`「部分搁置」），带拖延负面暗示 |
| **休眠区** | 「休眠」= 能力存在未接线（`docs/评估-memora设计质量-20260910.md:103`「休眠扩展点」、台账 DRIFT-PAUSE-1「休眠能力」）|
| **暂存区** | 暗示临时、可被清理 ⇒ 与「永久保留 Round 原文」的立项目**直接相反** |
| **抽屉 / 箱 / 库** | 「库」撞数据库/genealogy 语境；「抽屉」拟物，与 Trae/VS Code 中性正式的语言不合 |

**为什么最终维持「留存区」**：

1. 它是唯一**零占用 + 中性 + 不撒谎**的词（"留存"只承诺"保留"，而我们的机制恰恰就是"不删"）；
2. **带「区」字是关键**——与「会话记录」形成并列的两个位置，读起来对称。用户的直觉（"留存区比单叫留存好"）成立，理由正在于此：单字「留存」像动词/状态，加「区」才是一个地方；
3. **它不表达"挪开"的短板，由动词组补就够了**：

| 位置 | 按钮组 | 语义 |
|---|---|---|
| 会话记录 tab | `[移入留存] [删除]` | 「移入」= 位置变化，**不是**数据变化 |
| 留存区 tab | `[移回会话记录] [删除]` | 「移回」同理；不用「恢复」（不存在的损坏，何来恢复）|

⇒ **名字不需要承载全部语义，动词才是用户真正读到的地方。**
