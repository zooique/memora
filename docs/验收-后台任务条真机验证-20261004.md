# 后台任务条真机验收教程（CMD-1 刀 3）

> **为什么需要这份**：刀 3 的价值**全在视觉层**（看得见、点得掉），而 14 条单测只能验到
> 「消息通了、DOM 造了、判据对了」——**验不到「用户眼睛看到什么」**。本教程是把单测
> 覆盖不到的那部分变成可执行的手动步骤。
>
> **范围**：①-⑤刀 3 新增面（后台任务条 + 终止按钮 + 推送点 + ready 对齐）；
> ⑥⑦脱管定案 + 阶段二补漏（跨轮存活、自然终态上屏）；⑧宿主退出归宿（已真机定类为
> OS 层孤儿并补退出杀树，修复后复测见 §五之四）。
> 内核执行面的命令安全裁决 / 杀树正确性不在本教程内。

## 三、触发（先做自检，再做正题）

### 3.1 工具行自检（30 秒，验「模型到底会不会调工具」）

发一句：

> 读一下 package.json 的第一行

**判据**：对话流里出现一条**工具行**（中文名「读取文件」）。

- ✅ 出现 ⇒ 模型能发原生 function call，继续 §3.2。
- ❌ 只出现文字回答、没有任何工具行 ⇒ **模型不支持原生 function calling**。
  这不是本条 UI 的 bug，是前置能力缺失。此时刀 3 无法在真机上触发——
  **换一个支持 function calling 的模型**（或本地 Ollama）再回来。
  ⚠️ 别把这一条误判成「后台任务条没实现」。

### 3.2 起一个真正的后台命令

发这句（**显式点名 `background=true`**，别指望模型自己判断）：

> 用执行命令跑一条后台命令：`ping -n 90 127.0.0.1`，设 background=true

**为什么选这条命令**：

| 条件 | 说明 |
| --- | --- |
| `ping -n 90 127.0.0.1` | 约 **89 秒**，足够你从容看完整个验收；Windows `cmd` 语法（内核 win32 恒 `cmd /c`） |
| 不在 deny 黑名单 | 内核 deny 的是：`rm -rf /`、`Remove-Item -Recurse -Force`、`format`、`mkfs`、`dd if=`、fork bomb |
| 不在 always-ask 清单 | 那 7 条是 `git commit/push/reset/rebase/merge/checkout --`、`npm publish`。若你**开了**设置里的「执行二次确认」，会弹审批卡——**点确认即可**，这本身也是正常路径 |

**期望**：模型先发一条工具行「执行命令」，返回一个 `taskId`，然后继续回话；命令在后台继续跑。

## 四、五个观察点（逐条打勾）

### ① 刚启动就出现「后台任务」条 —— 验「刚启动推送点」

任务一起，**不等轮次结束**，底部就该出现一条：**「后台任务」+ 圆形徽章数字 1**。

- ❌ 只见工具行、底部空 ⇒ `step_boundary` 推送点没生效（这是刀 3 修的「刚启动不可见」缺口）
- 参考：轮次进行中时它可能被收进 `+N` chip（见 ②），点开 chip 就能看到

### ② 收纳 / 升主位 —— 验「优先级垫底」

| 阶段 | 期望形态 | 背后的判据 |
| --- | --- | --- |
| 轮次**进行中**（activity 活跃） | `activityBar` 占主位，后台条被收进 **`+1`** chip | 后台条优先级 0，不顶掉「正在思考」主状态 |
| 轮次**收尾后**（activity 归位） | 后台条**自动升为主位**，列表直接可见，「终止」按钮直接能点 | 它成了唯一活跃条 |

点 `+N` chip 应能展开/收起浮层。

### ③ 终止按钮 —— 验「用户侧 kill 入口」

后台条每一行 = **命令原文**（过长截断，悬停看全文）+ **状态标签**（运行中）+ **终止**按钮。

点「终止」后：

- 状态标签应立刻变 **「已终止」**，且该行的**终止按钮消失**（终态行不给按钮）
- **命令输出不会显示在界面上**——这是刻意设计（输出归模型消费，UI 不搬 KB~MB 级数据）

**硬判据（不信界面，信系统）**：开任务管理器，确认 `ping.exe` 进程**真没了**。
> Windows 走 `taskkill /T /F` 杀树。界面变「已终止」但进程还在 = 真缺陷。

### ④ 面板关掉再打开 —— 验「ready 全量对齐」（本轮刚修的那处）

**这是最容易漏的一格，也是本轮自审挖出来的真带伤。**

1. 让命令在后台跑着（再起一条即可）
2. 把侧边栏的 Memora 面板**折叠起来，再展开**（或直接关掉窗口重开）
3. 底部「后台任务」条**必须仍在**，列表与徽章数不变

- ❌ 进程还在跑、条却没了 ⇒ 就是 `postBackgroundTasks` 的 ready 补推缺失/被去重吞掉

### ⑤ 终态收尾 —— 验既有链路没被带坏

`ping` 自然跑完（或跑满你设的 `timeoutMs`）后：

- 轮次收尾时对话流出现 **「后台任务收尾」小节**（既有功能，回归检查点），
  内容应说明「已转为后台常驻（未被终止）」，**不应**出现「已全部终止」字样
- 后台条的行状态标签随之变为「已完成」/「超时被终止」，**且不再有终止按钮**

## 五之二、观察点 ⑥ · **本轮改动的主验收**（跨轮存活）

> 这是 2026-10-04 定案修订的**核心验收点**。前三轮验收的都是「turn 内可见」，
> 这一格验的是「turn **结束后**还活着」——也就是曾经骗你的那个场景。

1. 发一句 `用执行命令跑一条后台命令：ping -n 90 127.0.0.1，设 background=true`
2. 等模型回完话、**turn 结束**（底部 activity 条消失）
3. 底部「后台任务」条应**仍然是「运行中」**，**不应**变「已终止」
4. 开任务管理器确认 `ping.exe` **真的还在**

| 结果 | 判读 |
| --- | --- |
| ✅ turn 结束后仍「运行中」+ 进程在 | 脱管定案生效 |
| ❌ 变「已终止」+ 进程没了 | 回归：`reapAll` 那条杀逻辑还在（`grep -n "reapAll" src/` 应为 0 命中） |
| ⚠️ 变「已终止」但进程还在 | 另一处缺陷：进程没杀但状态被改 |

**第二段（跨轮吸收）**：

5. 等 `ping` 跑完那 90 秒
6. **随便问一句无关的**（例如「刚才那个跑完了吗」或「1+1 等于几」）
7. 模型应**自动**拿到 `bg-1` 的输出并提到它——因为结果留队，下一轮被自动吸收

- ❌ 模型完全不知道有过这个后台任务 ⇒ 跨 turn 留存没生效（检查 `finalizeBackgroundTasksOnTurnEnd` 里是否还有 `command-result` 丢弃行）
- ✅ 模型知道 ⇒ 闭环成立

**寿命边界（观察点 ⑧ 已闭环，2026-10-04）**：真机定类为 OS 层孤儿（父进程退出而
`ping.exe` 仍在），已补退出杀树——`Agent.close`（扩展正常停用）经 `killAllRunning`
真杀存活任务。故正常退出 VS Code 进程应终止；扩展崩溃 / 被强杀时 `close` 来不及执行，
该场景仍不保证。复测见 §五之四。

## 五之三、观察点 ⑦ · 终态 UI 准确 + 手动收起（阶段二补漏验收）

> 阶段一自查漏判：脱管改对了「不杀」，但没检查「状态变化怎么通知 UI」——
> 结果条会**一直写「运行中」而任务早已跑完**（假活跃，比原缺陷更坏）。
> 本组验的就是这条链补上没有。

### 7-1 终态自动更新（不用问任何问题）

1. 起一条短任务：`用执行命令跑一条后台命令：ping -n 20 127.0.0.1，设 background=true`
2. turn 结束，底部条显示**运行中**（这步和阶段一一致）
3. **什么都别做，等约 20 秒**
4. 底部条应**自行变成「已完成」** —— 不需要问任何问题、不需要点任何按钮

| 结果 | 判读 |
| --- | --- |
| ✅ 约 20 秒后自行变「已完成」 | 终态推送链通了 |
| ❌ 一直「运行中」 | 回归：`registry.notify` → loop 出口 → `agent.emit('backgroundTaskSettled')` → 宿主订阅 这条链断了。查 `src/agent/loop.ts` 的 `emitBackgroundTaskSettled?.(task)` 是否还在、`hosts/.../chatPanel.ts` 的 `a.on('backgroundTaskSettled', …)` 是否被删 |
| ❌ 变「已终止」 | 另一处问题：进程真被杀了（查 `detachAll` 是否被改回 `reapAll`） |

### 7-2 终态行手动收起

1. 承上，条上有一行「已完成」
2. 该行应有一个 **`×`** 按钮（**没有**「终止」——已结束的任务点了必然无反应）
3. 点 `×` → 该行消失
4. 进程**不该**被杀（任务管理器里没有残留的 `ping.exe`——其实它早跑完了，
   这里验的是**「×」不会误杀任何东西**）

### 7-3 收起后不复活

1. 承上，点过 `×` 之后
2. **把面板折叠再展开**（或关窗重开）
3. 那条**不该**回来

- ❌ 又冒出来 ⇒ 「记住了」放错地方了（应在宿主 `Set`，放 webview 则面板一重建即忘）

### 7-4 反例清单（出现即记 bug）

| 反例 | 判读 |
| --- | --- |
| running 行也有 `×` | 违反「进程在跑必须可见」不变量——用户能把在跑的任务藏起来，回到缺口原点 |
| `×` 的 hover 是**危险红** | 它不杀进程，视觉上必须与「终止」可区分，否则用户会以为点了会杀东西 |
| 收起后**内核记录也没了**（`kill_command` 取不回输出） | 违反「可逆 > 不可逆」——关掉的只是眼睛，不该连东西一起丢 |
| 一次终态**推两遍**相同快照 | 事件重复订阅（`on` 被写了两遍）——签名去重在处理器内部拦不住，那是两条独立调用 |

## 五之四、观察点 ⑧ · 宿主退出后的进程归宿（✅ 已闭环 2026-10-04 · 修复后需复测）

> **首次定类结果 = OS 层孤儿实锤**：完全退出 VS Code 约 10 秒后，`ping -n 300`
> （PID 15456）仍在运行，其父进程（扩展宿主 PID 15200）已不存在。Windows 不回收
> 脱离控制台的子进程，Job Object 兜底不成立。
> **处置**：已补退出杀树——`Agent.close` → `loop.shutdownBackgroundTasks` →
> 注册表 `killAllRunning`（taskkill 杀树），宿主 `deactivate` 零改动（本就 await close）。
> 残留缺口（如实）：扩展崩溃 / 被 OS 强杀时 `close` 来不及执行，该场景仍不承诺清理。

### 修复后复测（重建 dist 后必跑，验「承诺已成真」）

1. 承观察点 ⑥：起 `ping -n 300 127.0.0.1`（约 5 分钟，给观察留足窗口）、turn 已结束、
   任务管理器已确认 `ping.exe` 在
2. **完全退出 VS Code**（不是关聊天面板——关面板时扩展宿主没死，进程继续是预期）
3. 等约 10 秒，任务管理器找 `ping.exe`（含 `conhost.exe` 子进程）

| 结果 | 判读 |
| --- | --- |
| 进程没了 | ✅ 退出杀树生效，「正常退出终止」承诺成真 |
| 进程还在 | ❌ 收割链断：查 `Agent.close` 是否调了 `shutdownBackgroundTasks`、注册表 `killAllRunning` 是否真触达 `killNow` |
| 立刻在、30 秒后才没 | ⚠️ taskkill 异步延迟（可接受但需记录实际延迟，文案不得写「立即」） |

⚠️ 两个「关」必须分清：**关聊天窗口 ≠ 退 VS Code**。关面板只销毁 webview，条消失不消失
都不回答本观察点；只有扩展宿主真正退出才算数。
⚠️ 必须在 ping 的 5 分钟寿命内完成观察；超时看到的「没了」可能只是它正常跑完，结论作废。

## 六、**不该**出现的现象（反例清单，出现即记 bug）

1. **终态行仍有「终止」按钮** ⇒ 僵尸交互（点了必然无反应）
2. **界面显示「已终止」但 `ping.exe` 还在** ⇒ 杀树失败，最严重的一类
3. **无任务时底部常驻一条空的「后台任务」** ⇒ 空态没在懒创建**之前**返回，裸插入的空条永远可见
4. **面板重开后条消失**（进程还在） ⇒ ④
5. **状态文案与内核词表不一致**（如把「超时被终止」显示成别的） ⇒ 宿主自建了第二套词表
6. **一次改状态触发多次刷新 / 刷屏** ⇒ 签名去重失效
7. **命令输出整段糊在界面上** ⇒ 协议里混进了 `result` 字段

## 七、验完之后

发现问题请连同**下面三样**一起报，否则复现不了：

1. 你点的**原话**（是不是显式写了 `background=true`）
2. `dist/webview/scripts/chatView.js` 里 `background-tasks-bar` 的命中数（判代次用）
3. 宿主窗口的**输出面板**日志（`Memora` 相关行，尤其有无异常堆栈）

> 单测侧已锁的 14 条 + 7 组变异验证**只保证消息链路与判据**，不保证「你眼睛看到什么」。
> 上面这张表就是专门补这段的——**没跑完这张表，刀 3 不算验收通过**（台账里已如实标注
> 「真机未验」）。
