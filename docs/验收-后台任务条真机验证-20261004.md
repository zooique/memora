# 后台任务条真机验收教程（CMD-1 刀 3）

> **为什么需要这份**：刀 3 的价值**全在视觉层**（看得见、点得掉），而 14 条单测只能验到
> 「消息通了、DOM 造了、判据对了」——**验不到「用户眼睛看到什么」**。本教程是把单测
> 覆盖不到的那部分变成可执行的手动步骤。
>
> **范围**：仅刀 3 新增面（后台任务条 + 终止按钮 + 三个推送点 + ready 对齐）。
> 内核执行面（`run_command` 进程治理 / 杀树）不在本教程内。

## 〇、开跑前必须知道的三件事（否则你会误判成 bug）

| # | 事实 | 判据 |
| --- | --- | --- |
| 1 | **宿主 dist 必须重建**。当前 `hosts/memora-vscode/dist` 是上一次构建的产物，**不含后台条代码** ⇒ 不重建就 F5，看到的是旧版（表现为「什么都没有」） | `grep -c "background-tasks-bar" dist/webview/scripts/chatView.js` 期望 ≥1 |

## 三、触发（先做自检，再做正题）

### 3.1 工具行自检（30 秒，验「模型到底会不会调工具」）

发一句：

> 读一下 package.json 的第一行

**判据**：对话流里出现一条**工具行**（中文名「读取文件」）。

- ✅ 出现 ⇒ 模型能发原生 function call，继续 §3.2。
- ❌ 只出现文字回答、没有任何工具行 ⇒ **模型不支持原生 function calling**。
  这不是本条 UI 的 bug，是前置能力缺失。此时刀 3 无法在真机上触发——
  **换一个支持 function calling 的模型**（或本地 Ollama）再回来。
  ⚠️ 别把这一条误判成「后台任务条没实现」。

### 3.2 起一个真正的后台命令

发这句（**显式点名 `background=true`**，别指望模型自己判断）：

> 用执行命令跑一条后台命令：`ping -n 90 127.0.0.1`，设 background=true

**为什么选这条命令**：

| 条件 | 说明 |
| --- | --- |
| `ping -n 90 127.0.0.1` | 约 **89 秒**，足够你从容看完整个验收；Windows `cmd` 语法（内核 win32 恒 `cmd /c`） |
| 不在 deny 黑名单 | 内核 deny 的是：`rm -rf /`、`Remove-Item -Recurse -Force`、`format`、`mkfs`、`dd if=`、fork bomb |
| 不在 always-ask 清单 | 那 7 条是 `git commit/push/reset/rebase/merge/checkout --`、`npm publish`。若你**开了**设置里的「执行二次确认」，会弹审批卡——**点确认即可**，这本身也是正常路径 |

**期望**：模型先发一条工具行「执行命令」，返回一个 `taskId`，然后继续回话；命令在后台继续跑。

## 四、五个观察点（逐条打勾）

### ① 刚启动就出现「后台任务」条 —— 验「刚启动推送点」

任务一起，**不等轮次结束**，底部就该出现一条：**「后台任务」+ 圆形徽章数字 1**。

- ❌ 只见工具行、底部空 ⇒ `step_boundary` 推送点没生效（这是刀 3 修的「刚启动不可见」缺口）
- 参考：轮次进行中时它可能被收进 `+N` chip（见 ②），点开 chip 就能看到

### ② 收纳 / 升主位 —— 验「优先级垫底」

| 阶段 | 期望形态 | 背后的判据 |
| --- | --- | --- |
| 轮次**进行中**（activity 活跃） | `activityBar` 占主位，后台条被收进 **`+1`** chip | 后台条优先级 0，不顶掉「正在思考」主状态 |
| 轮次**收尾后**（activity 归位） | 后台条**自动升为主位**，列表直接可见，「终止」按钮直接能点 | 它成了唯一活跃条 |

点 `+N` chip 应能展开/收起浮层。

### ③ 终止按钮 —— 验「用户侧 kill 入口」

后台条每一行 = **命令原文**（过长截断，悬停看全文）+ **状态标签**（运行中）+ **终止**按钮。

点「终止」后：

- 状态标签应立刻变 **「已终止」**，且该行的**终止按钮消失**（终态行不给按钮）
- **命令输出不会显示在界面上**——这是刻意设计（输出归模型消费，UI 不搬 KB~MB 级数据）

**硬判据（不信界面，信系统）**：开任务管理器，确认 `ping.exe` 进程**真没了**。
> Windows 走 `taskkill /T /F` 杀树。界面变「已终止」但进程还在 = 真缺陷。

### ④ 面板关掉再打开 —— 验「ready 全量对齐」（本轮刚修的那处）

**这是最容易漏的一格，也是本轮自审挖出来的真带伤。**

1. 让命令在后台跑着（再起一条即可）
2. 把侧边栏的 Memora 面板**折叠起来，再展开**（或直接关掉窗口重开）
3. 底部「后台任务」条**必须仍在**，列表与徽章数不变

- ❌ 进程还在跑、条却没了 ⇒ 就是 `postBackgroundTasks` 的 ready 补推缺失/被去重吞掉

### ⑤ 终态收割 —— 验既有链路没被带坏

`ping` 自然跑完（或跑满你设的 `timeoutMs`）后：

- 轮次收尾时对话流出现 **「后台任务收割」小节**（既有功能，回归检查点）
- 后台条的行状态标签随之变为「已完成」/「超时被终止」，**且不再有终止按钮**

## 五、验收判据表（打印用）

| # | 观察点 | 通过 | 不通过 ⇒ 归因方向 |
| --- | --- | --- | --- |
| 0 | 工具行自检 | 出现工具行 | 模型不支持原生 function call（**先换模型，不是 UI bug**） |
| 0b | 编译自查 | `background-tasks-bar` 命中 ≥1 | 宿主 dist 没重建（**验的是旧代码**） |
| ① | 刚启动即出现条 | 底部出现「后台任务 N」 | `step_boundary` 推送点未生效 |
| ② | 优先级形态 | 进行中收进 `+1`；收尾后升主位 | 优先级数值被改 / activity 收时机异常 |
| ③ | 终止 | 标签转「已终止」+ 按钮消失 + **进程真死** | 路由未达 / 杀树失败（界面变但进程在 = 真缺陷） |
| ④ | 面板重开 | 条仍在 | ready 补推缺失或被签名去重吞掉 |
| ⑤ | 终态收割 | 「后台任务收割」小节出现 | 既有收割链路回归 |

## 六、**不该**出现的现象（反例清单，出现即记 bug）

1. **终态行仍有「终止」按钮** ⇒ 僵尸交互（点了必然无反应）
2. **界面显示「已终止」但 `ping.exe` 还在** ⇒ 杀树失败，最严重的一类
3. **无任务时底部常驻一条空的「后台任务」** ⇒ 空态没在懒创建**之前**返回，裸插入的空条永远可见
4. **面板重开后条消失**（进程还在） ⇒ ④
5. **状态文案与内核词表不一致**（如把「超时被终止」显示成别的） ⇒ 宿主自建了第二套词表
6. **一次改状态触发多次刷新 / 刷屏** ⇒ 签名去重失效
7. **命令输出整段糊在界面上** ⇒ 协议里混进了 `result` 字段

## 七、验完之后

发现问题请连同**下面三样**一起报，否则复现不了：

1. 你点的**原话**（是不是显式写了 `background=true`）
2. `dist/webview/scripts/chatView.js` 里 `background-tasks-bar` 的命中数（判代次用）
3. 宿主窗口的**输出面板**日志（`Memora` 相关行，尤其有无异常堆栈）
