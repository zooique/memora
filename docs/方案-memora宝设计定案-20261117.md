## 〇、执行前钉死的前提（三原则各自的判据真源）

本文所有设计判断**必须**满足三原则的具体判据，而非凭印象"大概符合"。先把每条原则的**可执行判据**钉出来，后文逐条过：

### SSOT（单一真理源）——来自 `single-truth-source-mindset.md`

| # | 判据 | 本文用法 |
|---|---|---|
| S1 | **最小单元 = turn**：新机制不能造第二个执行引擎，复杂度必须向外生长 | Worker = 普通 turn 载体，不造新 Agent 类/新 Loop |
| S2 | **自然生长五步**：① 立或找真理源 → ② 首个入口是普通消费者 → ③ 差异段 = 我与真理源的连接方式 → ④ 接管则退役旧形态 → ⑤ 契约扩张走最小面（加字段不新 op） | Worker 扩 SessionMeta 字段；Router 新建 role pack；全部是"差异段"写法 |
| S3 | **能力位与裁决归下游**：入口层只做采集与投递，禁止在入口预判能力位/做语义裁决 | 宝（Router）派发时只给 Mandate 边界，不写技术方向 |
| S4 | **身份时序**：对象身份在创建那一刻确定并落真源，不得由首个事件反向派生 | Worker 的两个新字段（workOrder/workStatus）必须在会话创建时同批写入；身份标记沿用既有 origin（见 §八 B1 的字段口径裁决） |
| S5 | **预留键 vs 僵尸键**：schema 未消费字段须区分 | SessionMeta 的两个新字段设计为预留键——当前宿主写入但 Worker loop 不直接读，消费时机由宿主事件钩子触发；`subscribed` 不在本期设字段（见 B10） |

### 自然生长——SSOT 的生长面（同文件）

| # | 判据 | 本文用法 |
|---|---|---|
| G1 | **复用同一份数据前四问**（谁写怎么写 / 能力还是数据 / 要不要造新词 / 删除测试） | SessionMeta 扩字段四问全部过，见 §三.1 |
| G2 | **措辞折叠纪律**：断言"共用/统一"前 grep 全部调用点核对 | 本文断言"Worker 复用普通 turn 执行面"前回源确认 AgentLoop 接口零改动 |
| G3 | **设计陷阱·新入口复制执行循环**：禁止在入口层复制判据/真源表 | Router 的状态投影从 SessionMeta.workStatus 读，不自己维护状态 |

| # | 判据 | 本文用法 |
|---|---|---|
| H1 | **托管只允许动两处**：① 代理工具定义 ② 代理会话与其他会话不一样的那层接线 | 本文所有改动落在这两处，见 §三.3 |

| H3 | **来源标记是记录，不是权限** | origin='hosted' 只做岔子路由判据，不做门禁 |

## 一、memora宝 定盘星

### 1.1 是什么

> **memora宝 = 一个独立的 Router 型 agent + 一条自己的微信式会话窗口 + 两级来源标记 + 给工作会话扩两个可选字段让它同时是 Worker + Ticket。** 自助模式一个字不改；它是**加在自助之上的一层操作人**。
>
> **命名注**：本文称 memora宝，与术语锚点定义的「Trae 宝」（托管模式的操作人）是同一角色在 memora 项目内的具体实例——Trae 宝是概念名，memora宝是实现名。

架构逻辑直接借自 DSH Superagent 的 Router/Worker 分层，但用 memora 自己的 turn/会话模型表达：

| memora宝 角色 | DSH 对应 | 做什么 | 工具面 |
|---|---|---|---|
| **memora宝**（Router） | DSH Router | 理解用户意图 → 建工作会话 → **写 Mandate 边界**（不是技术方向）→ 派发 → 收岔子 → 给用户汇报 | **只有会话管理工具**（建/停/查/发消息）；**不配**读文件/跑命令/改代码 |
| **工作会话**（Worker） | DSH Worker | 拿到 Mandate 边界后，独立跑完整 turn，自己判断技术方向、改代码、跑命令、提结论 | 完整自助能力（和今天的自助会话**一字不差**） |

### 1.2 不是什么（四条红线）

| 不是 | 为什么 | 依据 |
|---|---|---|
| ❌ 不是 TRAE 宝的"全局助理" | TRAE 宝两级是**跨项目记忆层 / 当前项目执行层**的分工。Memora 是**单项目 agent**（一个宿主 = 一个项目），跨项目记忆前提不存在。且 TRAE 全局助理做技术判断（"梳理相关方案、约束与偏好"），和 memora宝"不碰技术决策"的定位冲突 | DSH 吸收总推荐 §二 + TRAE 宝观察稿取舍表 |
| ❌ 不是多 agent 层级树 | 只有一层。不做"宝派宝"，不造父子树 | 白话设计文档 §八 |
| ❌ 不是一个新的"任务"实体 | **不造平行 Ticket 实体**。给现有工作会话加字段就行——会话本身就是 Worker + Ticket | SSOT 原则（复用同一份数据前四问） |
| ❌ 不是常驻后台服务 | 关掉编辑器宝就下班，重启后上下文断。被动的，只活在当前 turn 里 | 白话设计文档 §九 |

## 二、SSOT 原则排雷结论

### 2.1 命中 SSOT 的部分

**2.1.1 "工作会话就是 Worker，不造平行 Ticket 实体"——完全命中**

- 最小单元 = turn，Worker 就是完整 turn 载体，没引入新引擎（S1）
- SessionMeta 是既有真源，扩字段 = 在既有真源上生长（S2）
- 写入通道是 `ISessionStore.updateSessionMeta(Partial<SessionMeta>)`，天然单点写入

**2.1.2 可选字段设计——命中预留键 vs 僵尸键**

三个新字段全部 optional，自助会话字段为空、读侧如实降级。预留键（设计空间、不承诺当前消费）不是僵尸键（技术债、应清理）——区分清楚（S5）。

**2.1.3 会话就是真源，扩字段而非平行实体——命中复用前四问**

四问逐条过（G1）：
1. **谁写、怎么写**：宿主建会话时一次性写入 `workOrder` + `workStatus='working'`，后续 Worker 终态时宿主更新 `workStatus='completed'/'failed'`——是**增量改**（Partial 语义），不是整文件重写 ✅
2. **共用的是能力还是数据**：扩字段是扩展同一份数据（SessionMeta 的语义），不是焊死两条生命周期 ✅
3. **要不要造新词解释差异**：要（`workOrder` vs `declaredPaths`），但两者是**同一实体的两个侧面**——`declaredPaths` 是技术范围（动哪些文件），`workOrder` 是语义边界（解决什么问题、不解决什么问题）。同一会话实体，不是两个实体挤进同一载体 ✅
4. **删除测试**：删掉托管的消费逻辑后，自助会话的代码不会静默出错（自助会话字段为空，工作台 fallback 跳过）✅

### 2.2 未充分命中需钉纪律的部分

**2.2.1 Worker 身份诞生时序（S4）——两个新字段必须在 createSession 时同批写入**

SSOT 身份时序判据：对象身份必须在创建时落真源。Worker 的两个新字段（`workOrder`、`workStatus='working'`）**必须**在 `SessionMeta` 创建那一刻一起写入，不允许"先建会话后补字段"；来源身份沿用既有 `origin='hosted'`（不是新字段，见 §八 B1 裁决）。`subscribed` 本期不设字段、未启动（见 B10），不进入身份时序判据。Worker 会话创建后马上就要执行，没有"排队中"的实际语义——初始值直接是 `working`，不保留 `queued` 中间态。否则"会话已存在但 Worker 身份未确定"的窗口期会导致：
- 工作台读到一个 Worker 会话但 `workStatus` 尚未写入 → fallback 到"从既有事实推"，状态不准
- 岔子通知可能误判该会话是 hosted 但 `workOrder` 为空

**钉法**：JSDoc 注释里写"创建时一次性写入，不后补"，加一条守卫测试：hosted 会话创建后 assert 两个新字段全部非空（`workStatus` 至少有值），且 `origin='hosted'` 在。

### 2.3 命中设计陷阱需补防的部分

**2.3.1 Hand back 用 `enqueueCommandResult` 纯文本通道——边界，需钉格式**

SSOT 禁止"为新场景新开 op/消息类型（字段可表达时）"。当前用纯文本能跑通 Hand back 事件（Worker 超界 → 宿主正则解析 → 转发给宝），但有边界：
- Hand back 语义 ≠ 命令输出，纯文本格式必须**固定**，不能 Worker 随便写
- 将来 Hand back 需要结构化字段（比如"超界内容 + 建议 Ticket 类型"）时，纯文本不够——扩张路径要提前写

**钉法**：Hand back 消息固定格式 `[HAND_BACK] reason: <一句话> | suggestion: <可选建议>`，宿主用正则 `^\[HAND_BACK\]` 判定，其余当普通后台命令输出处理。结构化扩张路径 = 给 Hand back 消息加 JSON payload，宿主正则 + JSON.parse 兼容两种格式。

**2.3.2 派发时"不写技术方向"——必须钉工具 schema，不是靠 Prompt**

SSOT 能力位判据（S3）：入口层禁止做语义裁决。宝派发时只给 Mandate 边界，不给技术方案。但 LLM 天然倾向于夹带技术方向（比如"先加 PermissionManager 类"），只靠系统提示词约束是弱保证。

**钉法**：给托管派发工具（宿主自定义工具，走 `customTools` 通道）的 `inputSchema` 钉死只有：
```
mandate: string  // 只写"要解决什么问题"，≤200字
title?: string   // 可选，会话标题
paths?: string[] // 复用既有 declaredPaths，语义等同"动哪些文件"
```
**不提供** `technical_direction` / `solution_approach` 这类参数位——schema 层面就限制不能传。

## 三、自然生长原则排雷结论

### 3.1 命中自然生长的部分

**3.1.1 会话真源已存在，扩字段是差异段——五步范式全命中**

| 步骤 | 落地 |
|---|---|
| ① 立或找 | SessionMeta + ISessionStore 已存在，找到它 |
| ② 首个入口是普通消费者 | Worker = 普通 Agent 实例（同一个类），带了额外字段，是既有 turn 真源的普通消费者 |
| ③ 新入口只写差异段 | 差异段 = `workOrder` + `workStatus`（两个可选字段；`subscribed` 本期不设，见 B10） |
| ④ 接管则退役 | 托管不接管自助会话的任何行为——自助零改动（H2） |
| ⑤ 契约扩张走最小面 | 加两个可选字段，不是新增 op/新消息类型 |

**3.1.2 不新建 Agent 类/Engine/Executor——命中 S1**

Router = 普通 Agent（role pack 工具面收窄），Worker = 普通 Agent。**没有第二个执行引擎**——命中"turn 的重复 = 闭环的重复，非独立引擎"。

### 3.2 边界探索（方案当前没覆盖、必须钉死）

**3.2.1 Worker 被用户手动消息打断时的状态**

设想：
1. 宝派发 Worker 会话，`workOrder="加权限管理"`，`workStatus='working'`
2. 用户在侧栏看到这个会话，**自己发了一条新问题**（轮打用户级戳，不是 hosted 轮级戳）
3. Worker 实际在做用户新指令，而不是 `workOrder` 说的事；工作台状态仍显示 `working`

**钉法**：宿主 loop 入口判定——如果 hosted Worker 会话的**最近一条用户发起轮**（round 无 hosted 级戳）正在执行，`workOrder` **暂停生效**（Worker 身份临时失效），等该轮跑完后自动恢复。状态字段本身不暂停，只是宿主消费时加一层判定。

**3.2.2 workStatus 更新通道——宿主事件钩子对齐，Worker loop 不直接写**

Worker 跑 turn 时在**内核 AgentLoop**里，它**没有直接写入 SessionMeta 的能力**（SessionMeta 在宿主侧）。所有 `workStatus` 的更新必须通过**宿主接收到 Worker 的事件**触发：

| 状态转换 | 触发点 | 写入方 |
|---|---|---|
| `queued → working` | 会话创建后、Worker 首轮 turn 开始前 | 宿主建会话时**直接写 `working`**（不需要中间态） |
| `working → blocked` | Worker 发出 `ask_user`（决策层提问） | 宿主收到 Worker 的 `ask_user` 事件钩子时写 |
| `working → completed` | Worker 正常完成（`done` 收场） | 宿主收到 Worker 终态通知（已有的托管中断通知通道扩展）时写 |
| `working → failed` | Worker 异常终止（`error`/`aborted`） | 同上 |

**钉法**：P1 必须把这条"宿主事件钩子对齐"写进技术设计，不能等 P2。`ask_user` 事件钩子**已存在**（`assembler.ts` 主动提问检出时发射 `questionPending` 事件，宿主渲染提问 UI），宿主需新增消费逻辑来更新 `workStatus`；终态通知走既有托管中断通知通道扩展。

**3.2.3 declaredPaths vs workOrder——语义边界钉死**

| 字段 | 维度 | 用途 |
|---|---|---|
| `declaredPaths` | 技术范围 | "动哪些仓库相对路径"——宿主既有，供主控范围门禁判重叠 |
| `workOrder` | 语义边界 | "要解决什么问题、不解决什么问题"——P1 新增，供 Worker 理解任务、Hand back 时做边界比对 |

**两者不可互相替代**：Worker 拿到 `declaredPaths=['src/agent']` 知道不能动 `ui/`，但不知道"能不能重构 src/agent 的结构"——这两个不同维度。文档里必须显式钉死这条边界。

## 四、不带伤原则排雷结论

### 4.1 命中不带伤的部分

| # | 判据 | 方案落地 |
|---|---|---|
| H1 | 托管只允许动两处 | ① 新建 memora宝 role pack（封闭工具面）= 代理工具定义；② SessionMeta 扩字段 = 代理会话接线。全部在允许范围内 |
| H2 | 自助模式保持原样 | AgentLoop / toolExecutor / confirmCoordinator 自助路径零改动 |
| H3 | 来源标记是记录不是权限 | `origin='hosted'` 只做岔子路由判据（带戳轮岔子叫宝），不做门禁 |
| H4 | 不凭空创造新能力 | 派发走 `customTools` 通道、Hand back 走 `enqueueCommandResult`、Worker 执行走普通 turn——全部从既有能力生长 |

**J 节自查两句全部过**：
1. 不用托管的人会不会觉得行为变了？→ SessionMeta 两个新字段可选、自助消费面不读 → 不会。✅
2. 改动落在允许范围内吗？→ 全落在"代理工具定义 + 代理会话接线"两处之内。✅

### 4.2 未充分命中需补充的部分

**P1 期间 Worker 不做不可逆操作**

Hand back 机制是 P2 才加的。P1 没有 Hand back 意味着 Worker 超界时无法自动停下来报告给宝。此时 Worker 如果**自己触发了不可逆操作**（`run_command("git push")`）而宝没来得及拦——会出事。

**钉法**：P1 期间软约束两条（不靠硬门禁，靠纪律）：
1. `workOrder` 里**必须显式声明**"本条不触发推送/发布/发版"（宝派发时工具 schema 的 mandate 参数天然会包含这条声明）
2. Worker 的 role pack 软约束里钉死"执行前检查是否涉及推送/发布，涉及则 hand back 给宝（用纯文本通道）"

Hand back 落地后（P2）再放开。

## 五、外部参照：吸收/拒枝清单

### 从 DSH Superagent 吸收

| DSH 设计 | 吸收方式 | SSOT/自然生长依据 |
|---|---|---|
| **Router 不配技术工具** | memora宝 role pack 只配会话管理工具，不配读文件/跑命令/改代码 | S1（最小单元）：Router 不配技术工具是架构硬约束，不是产品选择 |
| **Router 只派发不做技术决策** | 派发工具 schema 钉死只有 mandate + title + paths，不给技术方向参数 | S3（能力位与裁决归下游）：入口层不预判语义 |
| **Ticket Mandate 边界 + Hand back** | 给 SessionMeta 加 `workOrder` 字段；Hand back 用 `enqueueCommandResult` 纯文本通道 | S2（自然生长）：不新建实体、不新建通道 |
| **Worker 独立跑完一个完整 turn** | 工作会话就是 Worker，完整自助能力，跑完全程 | S1：没有第二个引擎 |

### 从 DSH Superagent 拒枝

| DSH 设计 | 拒枝理由 |
|---|---|
| 独立 Session + 独立目录 | memora 是单项目 agent，Worker 共享工作区、Round 天然隔离。DSH 是 GitHub 监听模式需要隔离 worker 目录防止污染——设计前提不同 |
| Policy Eval 闸门（主动发现问题） | memora宝 当前是**被动的**（用户找它才启动），Eval 闸门没那么迫切。远期锚点，P1 不做 |
| Subscription（跨事件源） | DSH Ticket 订阅 Thread 是因为主动式 agent 持续监听。memora宝 不常驻，`subscribed` 是 **P3 未启动的设计预留、本期不设字段**——设一个宿主不消费的字段即僵尸键（违反 S5）。若 P3 启动，按当时真实消费端再定义字段并走守卫 |
| Prompt 版本管理 | DSH 是多人协作、需要可追溯。memora宝 是单人使用、角色包切换已有基础 |

### 从 TRAE 宝拒枝（对比后追加，不是原观察稿的判断）

| TRAE 宝设计 | 拒枝理由（**比原观察稿的理由更准确**） |
|---|---|
| **全局助理 + 项目助理的两层** | 两者是**跨项目记忆层 / 当前项目执行层**的分工。前提是跨项目。Memora 是单项目 agent（一个宿主 = 一个项目），"跨项目记忆"不存在。**原观察稿的理由是"再分一层就是父子树"——方向对但维度错**，正确维度是"产品定位不同" |
| **全局助理做技术判断**（"梳理相关方案、约束与偏好"） | 和 memora宝"不碰技术决策"的定位直接冲突。DSH Router 是不配技术工具强制只路由，TRAE 全局助理是主动做技术判断——两种完全不同的哲学 |
| **常驻后台、IM 集成** | memora宝 明确定位"关掉编辑器就下班、被动只活在当前 turn"。常驻需要新架构 |

## 七、设计边界清单（P1/P2 必须钉死的边界）

本文三原则排雷发现的设计边界，必须在对应分期的技术设计里钉死。不是实现细节，是架构级约束。

### P1 必须钉死的边界（7 条）

| # | 边界 | 钉法 |
|---|---|---|
| B1 | Worker 身份诞生时序 | `workOrder` + `workStatus='working'` 两个新字段**必须在 createSession 时同批写入**，不后补；来源身份用既有 `origin='hosted'`（非新字段）。`subscribed` 本期不设字段、未启动（见 B10），不参与身份时序。Worker 会话创建后马上执行，无 `queued` 中间态。加守卫测试 assert hosted 会话创建后 workStatus 非空 |
| B2 | 派发工具 schema | 只有 `mandate: string(≤200字)` + `title?` + `paths?`，**不给技术方案参数位**。靠 schema 约束不靠 Prompt |
| B3 | workStatus 更新通道 | **宿主事件钩子对齐**，Worker loop 不直接写 SessionMeta。`ask_user` 钩子已存在（assembler.ts 发射 `questionPending` 事件），宿主需新增消费逻辑；`done`/`error`/`aborted` 走既有托管终态通知扩展。全部事件钩子 → 宿主 `updateSessionMeta` |
| B4 | 用户手动打断 hosted Worker | 宿主 `dispatchHostedInput`（派发托管输入）入口判定：目标会话是 hosted Worker、且最近一条用户发起轮正在执行 → `workOrder` 暂停，轮跑完自动恢复 |
| B5 | declaredPaths vs workOrder 语义边界 | 文档里显式钉死：前者是技术范围（动哪些文件），后者是语义边界（解决什么问题、不解决什么问题），两者都是必需的 |
| B6 | Hand back 通道预留 | `enqueueCommandResult` 纯文本通道，消息固定格式 `[HAND_BACK] reason: <一句话> | suggestion: <可选>` |
| B7 | P1 Worker 不做不可逆操作 | workOrder 里必须显式声明"不触发推送/发布"；role pack 软约束钉死 |

### P2 必须钉死的边界（3 条）

| # | 边界 | 钉法 |
|---|---|---|
| B8 | Hand back 消费者 | 宿主收到 `[HAND_BACK]` 正则匹配消息 → 转发给宝（Router） → 宝决定转新 Ticket（建会话）、合并到现有活、或转述给用户 |
| B9 | Hand back 结构化扩张 | 先钉死纯文本格式，加 JSON payload 兼容（`[HAND_BACK] reason: ... | payload: {"action": "new_ticket", "type": "docs"}`） |
| B10 | `subscribed` 消费实现（**P3 未启动**） | Worker 订阅事件源（git commit、CI、Issue 评论）自动注入上下文是 **P3 设计预留**；本期**不设 `subscribed` 字段**、宿主不消费。此前「P2 前字段存在但不消费」的承诺已按用户裁决撤回（2026-11-17，见台账 `HOSTED-SUBSCRIBED-COLUMN-1`）：先设不消费的字段即僵尸键，违反 S5。P3 启动时按真实消费端定义字段，再走 `publicMemberSurfaceGuard` + 内核发版 |

## 八、落地分期（摘要，分期表以既有技术文档为准）

本文只做模型层和边界层。技术分期的具体条目（接口定义、测试用例、文件清单）落进既有技术文档（`评估-子会话与目标模式路线-20261108.md` §10 分期表 + 本文 §七 边界清单作为补充）。

## 九、一句话收束

> **memora宝 = 一个不配技术工具、只做会话调度的 Router 型 agent + 一条微信式对话窗口 + 给 SessionMeta 扩两个可选字段（身份来源沿用既有 origin）让工作会话同时是 Worker + Ticket。自助模式零改动；托管是加的一层操作人。从 DSH Superagent 吸收"Router/Worker 分层"和"Mandate + Hand back"的架构逻辑，用 memora 自己的 turn/会话模型表达；不学 TRAE 宝的跨项目记忆层，因为产品定位不同。SSOT = 会话本身就是 Worker + Ticket；自然生长 = 所有扩展从既有机制出发（加字段、扩 tool schema、复用事件回流通道）；不带伤 = 自助模式零改动、内核零新执行模型、托管只动"代理工具定义 + 代理会话接线"两处。**
