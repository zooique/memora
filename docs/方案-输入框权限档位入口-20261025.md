# 方案-输入框权限档位入口-20261025（v2 · 排雷推演版）

> **性质**：对同日 v1 稿的 SSOT / 不带伤对抗复核。**v1 全部结论保留，以下只记「排掉的雷 + 定稿设计」**。
> **排雷原则**：改判据 = 造伤；改喂给判据的事实 = 止血。本稿只做后者。
> **目标**：落地「输入框权限入口」，且结构上不允许出现第二真相源、僵尸通道、静默失败。

## 一、排雷清单（12 条，每条 = 雷 / 判据 / 处置）

### R1 🔴 真源主客倒置（v1 最深的伤）
- **雷**：v1 写「档位 = 两键派生投影」，但「信任」档（always-ask 豁免）**无法从 `(confirmWrites, confirmScripts)` 派生**。二期一到，要么给档位单独存储（档位变真源、两键变投影——主客翻转，历史用户的混合设置被覆盖），要么永远做不出信任档。
- **判据**：真源只能有一个方向；派生关系不能随时间翻转。
- **处置**：**真源 = 三个独立事实**：`confirmWrites` / `confirmScripts` / `exemptAlwaysAsk`（二期）。档位名**永不存储**，只是显示层对三事实的派生读法。一期不建 `exemptAlwaysAsk` 键（无实现 = 不建，防僵尸）。

### R2 🔴 回推面不通（v1 把假设写成事实）
- **雷**：v1 写「回推复用 `security_status`」。**实测：chat webview 侧零配置状态下推消费面**——`security_status` 仅 settingsPanel 处理（`:458`）；chat 侧无 `config_status` / `settings_data` / `mcp_status` / `ready` 任何状态握手（grep 全空）。也就是说输入框改档后**没有任何既有通道把结果送回 chat webview**。
- **判据**：「只上报、等回推、不本地翻转」是本仓既有纪律（mcpView 注释）；无回推 ⇒ UI 只能乐观翻转 ⇒ 变成第二份「我以为生效了」的状态。
- **处置**：① 承认**必须新增一个 chat 侧 `security_status` 消费点**（协议零成本，行数有成本，见 §四）；② **跨面板不广播**——extension 无面板注册表（实测 `extension.ts` 只有两个 `registerWebviewViewProvider`，无统一引用），不为本需求新建广播机制（复杂度守恒）；登记边界：另一面板下次装载时按持久键追平，不假装同步。

### R3 「自定义」档是逃逸态
- **雷**：v1 的枚举里留了「自定义（两键混合）」，点它还要在下拉里展开两个子开关 ⇒ 枚举不封闭 + UI 复杂度外溢到 chatView（余 1 行）。
- **处置**：**取消「自定义」档**。下拉 = 「两个预设动作（全部询问 / 全部自动）」+「两个就地开关（写入 / 执行，显示当前实际值）」+「信任项（置灰）」。**预设是动作不是状态**：点一下写两键，之后高亮由两键实际值决定 ⇒ 无第二状态源，混合态自然表达。

### R4 always-ask 一刀切豁免 = 结构性带伤
- **雷**：v1 只说「信任档豁免 always-ask」，但 `ALWAYS_ASK_COMMAND_PREFIXES` 里 `git reset` 与 `git reset --hard`、`git push` 与 `git push --force` 同档 ⇒ 一刀切豁免会把真不可逆操作一起放掉。
- **处置**：清单拆两组，判据仍在 `classifyCommand` **单点产出**（不加第二套判据）：
  - `NON_EXEMPTIBLE`（恒弹，任何档位）：`git push --force`、`git reset --hard`、`git clean`、`npm publish`；
  - `EXEMPTIBLE`（信任档可豁免）：`git commit`、`git push`（普通）、`git reset`（非 hard）、`git merge`、`git rebase`、`git checkout --`。
  - 内核 verdict 由 `'always-ask'` 细化为 `'always-ask' | 'always-ask-hard'`，宿主注入的是**一个布尔**（「豁免 exemptible 这类吗」），不是规则集 ⇒ SSOT 守住。

### R5 档名说谎
- **雷**：叫「全自动 / 信任」但仍有弹窗（hard 类恒弹 + MCP 未勾项仍弹）= 文案与实现不符（本仓定性为带伤）。
- **处置**：档名与副标题必须写边界，如「自动 · 不可逆操作仍询问」。**文案进守卫测试**（断言副标题含「仍询问」），防日后改实现忘改文案。

### R6 脚本面内容裁决落点未定（v1 留了二选一）
- **处置**（定死；**实现优于本条原始描述，已订正**）：原写"落点 toolExecutor 的 script 分支调 classifyCommand、`confirmScriptRun` 语义不变"。实现时改为**把裁决收进 `confirmScriptRun` 的可选第 4 参 `content`**（toolExecutor 只负责把正文喂进去）——判据更集中：deny 恒拦、always-ask 恒弹、normal 回落档位，全部走**同一个** `classifyCommand`，且审计 `path` 仍是脚本路径（可读）而非整份正文。**整份裁决不截断**（截断 = 裁决盲区；正则 O(n)，无性能顾虑）。
  - ⚠️ **能力边界（诚实登记）**：正文超 `SCRIPT_READ_MAX_LEN`（20 万字符）的脚本**读不出来 ⇒ 拒绝执行**（fail-closed），不给"读不动就放行"的口子——否则写个超大脚本即可绕过裁决。

### R7 审计可回看落点未定
- **处置**：进**活动抽屉时间线**（既有决策记录载体 `_logDecision` 同面），不开新存储域、不新建文件。最近 3 条内存快照（现状）升级为可回看。

### R8 「急停常驻，验证即可」= 把验收写成假设
- **处置**：列为真机验收项（硬门槛，未过不算完成）：信任档下 ① 停止按钮可见可点；② 长命令执行中暂停按钮可见；③ 审批卡在信任档下对 hard 类仍弹出且可拒。

### R9 MCP allowlist 与档位的关系未定
- **处置**：**不并入档位**。`memora.mcpToolAllowlist` 是独立真源（不同语义面：外部能力 vs 本机执行），合并会让档位变成三源混合体。下拉只给导航「MCP：N 项免确认 · 管理」→ 跳 MCP 设置页。**server 级放行（`mcp__<server>__` 前缀）作为独立一笔**，复用既有 `mcp_write{op:'allow'}`，零协议成本。

### R10 热更对象缺失
- **雷**：无 agent 时切档 ⇒ 键写了、热更无对象 ⇒ UI 显示已生效、内核未生效（静默失败族）。
- **处置**：共享 handler 与 settingsPanel 现行为对齐（`ensureAgent()`），**缺失时只落键**（装配期 `extension.ts:168` 已读键，天然追平）；热更/持久化失败**必须 notice error**，禁静默。

### R11 协议预算：129/130，+1 即爆线
- **处置**：零新消息类型。**`security_toggle` 的 `target` 成员二期才加，且加即实现**（不留有声明无实现的僵尸通道）。`security_status` / `metrics` 加字段 = 0 成本。

### R12 行数：chatPanel 4516/4516 顶格
- **处置**：**先减后加**。chat 侧新增（`security_status` 消费 case + 下拉挂载 + 接线）必须同批找到 ≥ 净增量的减法对象（候选：composer 静态模板段外置、或相邻域迁移，实施前实测）。chatView 逻辑**全外置** `helpers/autonomyPicker.ts`。

## 二、定稿设计

### 2.1 真源（唯一）

| 事实 | 存储键 | 期 |
|---|---|---|
| 写入二次确认 | `memora.confirmWrites`（既有） | 一期 |
| 执行二次确认 | `memora.confirmScripts`（既有） | 一期 |
| 豁免可豁免类 git 操作 | `memora.exemptAlwaysAsk`（新增，二期随实现同批建立） | 二期 |

**档位名 = 三事实的派生读法，永不存储。** 两个入口（设置页细粒度开关 / 输入框下拉）同读同写这些键，不存在第三份。

### 2.2 输入框入口形态

挂在 `#inputFooter > .composer-left`（chatPanel composer 行，与 Skill / 模型选择器同位），复用 `buildDropdownHtml` capsule 变体；逻辑外置 `helpers/autonomyPicker.ts`。

菜单内容（自顶向下）：
1. 预设动作：**全部询问**（写 T,T）/ **全部自动**（写 F,F）
2. 就地开关：**写入审批**（当前值）/ **执行审批**（当前值）—— 与设置页两开关同源
3. 导航：**MCP：N 项免确认 · 管理**（跳设置页 MCP 选项卡）
4. 二期项：**自动 · 不可逆操作仍询问**（前置不齐时置灰，置灰本身是诚实表达）

### 2.3 分期

| 期 | 内容 | 内核改动 | 协议增量 |
|---|---|---|---|
| 一期 | 共享 `handleSecurityToggle` + `helpers/autonomyPicker.ts` + chat 侧 `security_status` 消费点 + 输入框胶囊 | 无 | 0（需 chatPanel 减法配合） |
| 前置债 | R6 脚本面内容裁决；R4 always-ask 两组拆分 | 有（同一文件、同一判据函数） | 0 |
| 二期 | 三事实真源第三项 + 信任档点亮 + 补偿三件套（git 打点 / 审计进时间线 / 急停验收） | 有（注入布尔，不加判据） | 0 |

**顺序不可换**：前置债不完成，信任档不得点亮（否则豁免一个仍在漏的墙）。

## 三、红线与诚实登记的边界

**红线**：deny 档任何档位不得放行；NON_EXEMPTIBLE 恒弹；沙箱不进内核（ADR-040）；档位不落第二存储键；无补偿不点亮信任档。

**登记的已知边界（不假装不存在）**：
1. **跨面板不广播**：settings 改档后 chat 输入框显示到下次装载才追平。不为此新建面板注册表。
2. **信任档为持久态**：风险 = 用户忘记自己在信任档。补偿 = 输入框胶囊**恒显当前档位名**（非默认档加色），架构哲学「自主等级显式化」在此落地；不做「每次会话重置」（会与持久键语义打架）。
3. **MCP 免确认不受档位管辖**：只给入口不给合并。

## 六、吸收主流设计后的增补（2026-10-25 外部核实）

> 来源：Claude Code 权限文档（2026-10 版）/ Codex CLI 0.147+ 官方控制 / 11 个 harness 的 YOLO 模式源码调研（2026-07）/ Cline 官方 Auto Approve 文档。以下每条 = 主流做法 → 对本方案的动作。

### B1 「越自动越要收紧边界」（Gemini CLI：yolo 反而启用沙箱）
- 主流：Gemini CLI 在 yolo 下**开启沙箱**；Codex 的 `workspace-write` 是 OS 强制边界，与审批正交。
- **动作（新增，重要）**：**信任档 = 审批豁免 + 边界收紧**。切到信任档时，`setAllowedPaths([])` 只留基准信任根（项目根 + memora 数据目录 + 配置/数据目录），用户额外白名单**在该档下不生效**；退出信任档恢复。零新机制（既有 `extraRoots`），把爆炸半径从"整台机器"压到"项目目录"。

### B2 「yolo 之下还剩什么」——地板必须无条件
- 主流实测：11 个 harness 里只有 5 个在最宽松模式下仍有无条件地板。**Cline 的 yolo = `autoApprove:["*"]`（无任何地板、无受保护路径）、Cursor 的 denylist 在 4 种绕过演示后废弃、文档直言"agent 与你的账号之间没有安全边界"、OpenHands headless 恒批准**——这些是被点名批评的那一类。Aider 反过来：`--yes-always` 下 shell 是**自动拒绝**而非自动批准。
- **动作**：① 本方案**不学 Cline/Cursor 的裸实现**；② 吸收 Aider：**`run_command(background:true)` 在信任档下仍逐次询问**（后台任务活过 turn、脱离视线，风险高于前台）；③ 地板清单（deny 档）在任何档位恒生效，且**脚本面补齐后**才谈信任档（否则"写脚本再跑脚本"就是 Cursor 被绕过的第四条路径）。

### B3 「禁字符串清单打不过编码/包装/间接」
- 主流血训：Base64、子 shell、写脚本再跑——禁串清单全部失守；Gemini 文档明说 blocklisting 不如 allowlisting。
- **动作（诚实标注，不许美化）**：memora 的 `classifyCommand` 是正则匹配、不做 shell 词法解析 ⇒ **在全自动档下它只是"防误操作"，不是安全边界**（对齐 Claude Code 官方对 auto 模式的定性："不是安全边界"）。真正的地板是**路径白名单（allowlist 形态）+ 写边界**，不是命令正则。文档与 UI 文案据此写，不许反过来宣称。

### B4 规则表 vs 档位（Claude Code：allow / ask / deny + `Tool(specifier)` glob，deny > ask > allow）
- 主流：规则优先级 **deny 恒赢**，且更具体的 allow 不能从更宽的 deny 里挖洞；MCP 规则形态 `mcp__puppeteer__*`（server 段字面量、工具段可 glob）。
- **动作**：① 本方案 v2 的「预设动作 + 就地开关」**与规则表同构**（预设 = 批量写规则），未来若要升级为真规则表，UI 不用推翻 ⇒ 现设计已预留；② deny > 一切 的优先级写进守卫测试；③ MCP server 级放行键建议直接采用主流同形 `mcp__<server>__*`（用户零学习成本），server 段不允许通配（与主流一致，防"一次放行所有 server"）。

### B5 「换审批人，不是扩权限」（Codex `--approve-for-me` / Claude Code auto 模式）
- 主流 2026 新形态：用**分类模型/审核 agent** 代替人回答审批，**沙箱与策略不动**；OpenAI 定性"reviewer swap, not a permission grant",并明示"不是确定性的安全保证"。
- **动作**：登记为**未来形态，本期不做**（宿主起第二个模型调用 = 成本 + 复杂度，违复杂度守恒）。但它验证了本方案 R5 的判断：**任何"自动"都不得替代 hard 类恒弹**。若将来做，结构必须是"每次仍判、只换判的人"，不得变成"不判"。

### B6 审计的诚实边界 + 回滚
- 主流：Claude Code 明示 transcript "不是防篡改的审计轨迹"；Cline 有 Checkpoint 快照（但仍说"不替代 Git"）。
- **动作**：① 文案禁止自称"安全审计轨迹"，只说"操作留痕（供回顾）"；② 信任档的"可逆"只做 **git 打点**（记 HEAD / remote sha，零副作用），**不做文件快照**（Cline 教训：快照救不了数据库、外部 API、已推送的提交）。

## 七、最终判断：能不能 SSOT 不带伤落地

| 范围 | 结论 | 条件 |
|---|---|---|
| **一期**（输入框入口 + 三事实真源 + 预设动作/就地开关） | ✅ 能，无伤 | 协议净增 0、chatPanel 先减后加、热更失败必 notice |
| **前置债**（脚本面内容裁决 + always-ask 分级） | ✅ 能，无伤，且不做全自动也该做 | 整份裁决不截断；hard 类清单只增不减 |
| **信任档（含 git 全自动）** | ⚠️ **带上三件才无伤** | ① B1 边界收紧；② git 打点；③ B3 诚实标注"命令地板不是安全边界"。**缺任一件 = 带伤** |
| **把 deny 说成安全边界 / 全自动命名成无边界** | ❌ 永不做 | 那是 Cline/Cursor 被批评的形态 |

**一句话**：主流承认的是"减少摩擦"这个需求，不是"裸全自动"这个实现——所有负责任的实现都是「**边界 + 可逆 + 留痕**」三件套换掉「人肉点确认」。memora 照这条走就能不带伤；只加一个"全自动开关"就是带伤。

**合计（前置债 + 一期）**：新增/迁移约 **400-550 行**（其中约一半是测试与 JSDoc），净增约 300 行量级；**无新依赖、无新协议类型、无新机制**。
**二期**：另计约 300-500 行 + 真机验收。

### 8.2 判断

- **体量：中等偏小**。参照系：chatPanel 一个文件 4516 行；本方案总量不到它的 1/8，且没有跨包新架构。
- **难度：低到中，且难度不在技术、在工序**：
  1. **chatPanel 顶格**是唯一"与本需求无关的负债"——必须同批找个 ≥15 行的可外置域做减法。参照 HOST-SPLIT-1 第 3 刀实测（净降仅 24 行，未达 40 行判据被否决）⇒ **减法不好找，这是本方案最烦的一步**，不是最难，但最容易卡住。
  2. **内核安全边界改动**要求全量回归 + 分诊（vitest 不查类型，改完必跑 `tsc --noEmit`；红要先分真假）。
  3. **两次真机验收**（输入框 UI、信任档行为）——本仓硬门槛，DOM 测试不查计算样式，绕不过。
- **风险点**：① chatView 是 if-else if 链且余 1 行，接线比预期贵；② settingsPanel 迁共享会动现有 249 行 toggle 测试的消费面；③ chatView.test.ts 已 12399 行，新测试应落独立文件而非堆进它。

### 8.3 建议实施顺序（对 §2.3 的修正）

**前置债可独立先行，且应该先行**：它零 UI 依赖、不受行数闸门约束、本身是净收益（不做全自动也该做）。修正后顺序：

1. **前置债**（内核：分组 + 脚本面裁决 + 测试 + build/install/契约闸门）
2. **一期**（共享 handler + helper + 输入框胶囊 + 同批减法）
3. **二期**（三件套齐了才点亮信任档）

## 九、客观判断：memora 现在需不需要这个功能（2026-10-25）

> 本节是对前八节的**自我对抗**：方案写得越完整，越容易自我合理化。以下按证据重新裁决。

### 9.1 拆开看：四块的结论不同

| 块 | 判断 | 理由 |
|---|---|---|
| **MCP server 级放行** | ✅ **需要**（若在用 MCP） | 唯一被证实的痛感来源：allowlist 默认空、逐工具勾选。约 30 行，改 `policy.ts` 一个函数 + UI 一个勾 |
| **前置债**（脚本面裁决 + force 分级） | ✅ **需要，但不属于本需求** | 这是**安全洞**，不是便利功能。不做全自动也该做，且与输入框无关 |
| **输入框权限档位入口** | ⏸ **暂缓** | 见 9.2 |
| **信任档（git 全自动）** | ❌ **当前形态不建议** | 见 9.3 |

### 9.2 为什么输入框档位入口现在不该做（四条证据）

1. **档位控件需要 ≥2 档才有意义，memora 现在实质只有 1 档。** 默认双关 = 全自动；"全部询问"只是把它关掉。也就是说这个下拉**等价于设置页已有的两个开关**，是同一个语义的第二个入口。**轴上只有一个点就先做切换器 = 空转 UI**——架构哲学里"自主等级徽章"至今连"显示当前等级"都没落地（UX 审查清单里它是建议项），谈切换是盖二楼。
2. **痛感没有被数据证实。** 本需求的论据是"主流都做了"+ 一张别人产品的截图——这是从众论据与功能攀比，不是自身痛感。**零成本实测方法**：`memora.showMetrics=true`，审计计数（`_securityAuditTotal` / `_recentSecurityAudits`）本就随 metrics 投影，看一周就知道弹了多少次、弹的是哪类。
3. **优先级错配。** 宿主仍 0.1.x，台账里 P4 提示 UI 收敛、记忆治理链、role-pack 收口、memora-mcp 对齐均未闭合；UI-CONFIRM-P15、SEC-READ-1 真机未验。在这些之上插一笔 400-550 行 + 卡 chatPanel 减法 + 两次真机验收的"便利功能"，是错配。
   > **2026-10-25 事实订正（审计发现，不改暂缓结论）**：「宿主仍 0.1.x」是陈事实——宿主 0.2.0 已于 2026-10-23 定版并打 tag `vscode@0.2.0`。论据方向不变（台账未闭合项仍在、UI-CONFIRM-P15 / SEC-READ-1 真机未验），但版本表述以 0.2.0 为准；§9.5 重启条件中的「宿主 0.1.0 已出包」同此订正。
4. **成本里最烦的那一段与本需求无关**（chatPanel 减法）。为第二个入口付这笔债，不划算。

### 9.3 为什么 git 全自动不建议（与用户自身血训冲突）

仓库记忆里的 git 事故链：Windows 下 git 写操作污染索引、含空格中文路径被通配符删光目录、`git push` 走双远端、每次推送都要 `env -u NODE_OPTIONS LEFTHOOK=0`。**这个项目的 git 工作流本身就是高风险、需要人盯的**。在此之上加"让 agent 自动 commit/push 且不再问"，与自身经验直接冲突。主流也站在反对面：Anthropic 把 push/publish 放进"每次都问"，OpenAI 把 `--yolo` 限定在"外部加固环境"，Aider 在全自动档下**反而自动拒绝 shell**。

### 9.4 更好的路径（重排）

1. **先量**：开 `memora.showMetrics`，用审计计数确认到底弹不弹、弹多少、弹的是 MCP 还是 git。（零代码）
2. **若痛在 MCP**：只做 server 级放行（~30 行，复用 `mcp_write{op:'allow'}`）。
3. **独立做前置债**：脚本面内容裁决 + `push --force`/`reset --hard` 分级——这是补洞，不绑定到本需求。
4. **等轴上有第二个点再拉线**：宿主 0.1.0 出包、核心能力收敛、且内核真的具备"可豁免档"之后，输入框入口一次到位，不必返工。**线留着，不急着拉。**

### 9.5 可验证的重启条件（满足任一再动工）

- 审计计数实测：审批卡日均 ≥ 5 次，且以 MCP/普通命令为主（不含 git）；
- 用户确实在让 agent 跑 git 写操作并每次被打断，且书面接受风险；
- 宿主 0.1.0 已出包 + 台账相关未闭合项清零（**2026-10-25 订正**：宿主 0.2.0 已于 2026-10-23 出包，版本条件已满足，剩「台账清零」）；
- 内核已具备豁免注入能力（此时 UI 才有第二档可切）。

> **本方案的真实资产是排雷过程中挖出的三个洞**（脚本面零内容裁决、`--force` 未分级、chat 侧无回推面），**不是那个档位下拉**。前八节保留作为"一旦重启条件成立"的施工图。
