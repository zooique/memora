## 第三部分 · 设计定案

### 3.1 一条总则

**UI 侧不持有状态。UI = f(rounds, turnState)。**
凡是"运行时才有的特判"都是 bug 信号 —— `narrate_withdraw`、`tool_pending` 这两条「运行时瞬态、不落盘」消息，
本质就是运行时与重放不同构的证据；收口后它们应当自然消失（不是删掉，是变得不需要）。

### 3.2 数据：`RoundView` = `Round` 的投影（禁止字段漂移）

```ts
// shared/protocol.ts —— 用类型约束保证投影不漂移（改 Round 字段即编译报错）
export type RoundView = Pick<
  Round,
  'id' | 'userMessage' | 'interactiveInputs' | 'assistantLog' | 'status' | 'createdAt' | 'completedAt'
> & {
  /** 末段回答：assistantMessage ?? undefined（pending 轮无） */
  assistantMessage?: RoundMessage;
  /** 过程事件（运行时逐条增长，收场后定型） */
  processEvents?: ProcessEvent[];
  /** 运行时标记：true = 本轮仍在流式生长（UI 显示骨架 + 停止/暂停按钮） */
  live?: boolean;
};
```

| 字段 | 来源 | UI 用途 |
|------|------|---------|
| `id` | `Round.id` | 同环续接判定（与 `chunk.roundId` 同源，见协议 v1.5 注释） |
| `userMessage` | 同 | 用户气泡 |
| `interactiveInputs` | 同（含 `kind` / `question` / `options`） | 折叠的「你答 / 你补充」行 |
| `assistantLog` + `assistantMessage` | 同 | 跨暂停-续跑的多段回答（末段恒为 `assistantMessage`） |
| `processEvents` | 同 | 过程折叠块（思考/工具/自审查），运行时与重放**同一渲染函数** |
| `status` | 同 | `isRoundSettled()` 判"是否计入"，`status === 'interrupted'` 判"怎么画" |
| `live` | **新增**，仅运行时为 true | 骨架/停止按钮。收场后置 false，**不落盘** |

> **`live` 是本方案唯一新增的语义字段**，且它是"运行时相位"而非"数据"——落盘侧恒缺省。

### 3.2.1 收编既有 `ReplayRound`（M2 落地修正，重要）

排雷时漏了一个更严重的伤口：**宿主侧本来就有一份轮投影 —— `chatPanel.ts` 的 `ReplayRound`**
（扁平形状 `{content,ts}` + 派生字段 `interrupted` + kind 短名归约 `qa/supp`）。
若按初版方案新增 `RoundView` 而不动它，等于**又造第五份真相**——正是本方案要消灭的病。

M2 已执行收编（行为等价，250 个回放/chatView 测试守卫通过）：

| 项 | 收编前 | 收编后 |
|----|--------|--------|
| 轮投影结构 | `ReplayRound`（宿主私有，扁平） | `RoundView`（协议，内核 Round 的 `Pick` 投影） |
| `interrupted` | 存字段 | 由 `status === 'interrupted'` 派生（不存派生量） |
| 交互输入 kind | 归约为 `qa`/`supp` 短名 | 直接透出内核 `InteractiveInputKind`（短名是第二套命名） |
| 正文挂载 | `assistant?: {content,ts}` | `status === 'complete' && assistantMessage?.content`（判据不变） |
| 消费方 | `sendRoundView` / `collectHistoryMessages` | 同上，字段路径改为 Round 形状 |

**纪律**：派生量（interrupted / 「仅 complete 挂正文」）一律在**发送侧**从 `status` 派生，
不再进 `RoundView` 字段——字段一多就会与 Round 漂移。

### 3.3 状态：`TurnState` 一个枚举（替代五条状态消息）

```ts
export type TurnState =
  | { phase: 'idle' }
  | { phase: 'running'; roundId: string }
  /** 等待外部输入：pause（用户申请/已生效）与 ask（LLM 提问）UI 形态同构，
   *  差别只在 reason 与是否带 questions —— 内核侧两者仍不同源（见 §边界）。 */
  | { phase: 'waiting'; reason: 'pause' | 'ask'; pausePending?: boolean; questions?: AskQuestion[] }
  | { phase: 'settled'; roundId: string; status: RoundStatus };
```

UI 控件全部由它派生（**禁止布尔碎片**）：

| `turnState` | 发送键 | 停止键 | 输入框 | 待发送区 | 提问卡 |
|-------------|--------|--------|--------|----------|--------|
| `idle` | 发送 | 隐藏 | 可用 | 隐藏 | 隐藏 |
| `running` | 禁用 | 显示 | 可用（输入即 interject） | 显示（队列） | 隐藏 |
| `waiting(pause)` | 续跑 ▶ | 显示 | 可用 | 隐藏 | 隐藏 |
| `waiting(ask)` | 提交回答 | 显示 | 专用卡 | 隐藏 | 显示 |
| `settled` | 发送 | 隐藏 | 可用 | 隐藏 | 隐藏 |

> `pausePending`（在途申请未到 step 边界）沿用既有「站台等车」语义：申请在了就是"在暂停"，
> UI 即时切"继续（可反悔）"形态 —— 行为不变，只是从独立消息变成枚举里的一个字段。

### 3.4 通道：一条 `turn_update`（patch 语义）

```ts
| { type: 'turn_update'; rounds: RoundView[]; state: TurnState }
```

替代：`chunk` / `user` / `assistant` / `process_event` / `replay_events` / `status` / `paused` /
`pause_pending` / `need_clarify` / `pending_queue_update` / `interrupted` 的**状态职责**
（正文流式仍走 `chunk` 的增量通道，见 §3.6 例外）。

**双轨期纪律**：M1–M4 旧消息保留但**禁止新增旧消息类型**；M5 统一删除。

### 3.5 输入：一个入口，宿主路由（内核入口不动）

```ts
| { type: 'input'; text?: string; kind?: InteractiveInputKind }
```

宿主 `handleInput(text, kind)` 按 `turnState.phase` 路由（**内核 `chat` / `interject` /
`answerQuestion` / `resumeExecution` 四个入口保持不变**）：

| 当前 `turnState` | 用户动作 | 路由到内核 |
|------------------|----------|-----------|
| `idle` | 发送 | `chat(text)` |
| `running` | 发送（插话） | `interject(text)` —— 注入型，**不暂停** |
| `waiting(ask)` | 提交回答 | `answerQuestion(answers)` + `resumeExecution(text, signal, 'question-answer')` |
| `waiting(pause)` | 带文本续跑 | `resumeExecution(text, signal, 'supplement')` |
| `waiting(pause)` | 空文本续跑 | `resumeExecution(undefined, signal)` |

> 内核 `resumeExecution(content?, signal?, kind?)` **已支持 kind**（`InteractiveInputKind`：
> `question-answer` / `supplement` / `timeout`）—— 收口是**对齐既有形状**，不是新造 API。

### 3.6 渲染：一个函数，一个例外

```
render(rounds: RoundView[], state: TurnState) → DOM
```

- **骨架**（按钮 / 输入框 / 占位 / 折叠块 / 待发送区）一律重渲染 —— 它们便宜且最易错。
- **例外**：`running` 轮的正文区保留增量 append（流式性能，避免每 token 重排）。
  这是**唯一允许**的局部优化，且必须写在代码注释里（防后人"优化"回来）。

### 3.7 收场：两个判据各司其职（修正初版）

| 问题 | 判据 | 出处 |
|------|------|------|
| 这一轮**是否计入**会话视图 / LLM 历史 / 可引用 | `isRoundSettled(status)` | `roundStore.ts:142` |
| 这一轮**怎么画**（中断轮独立平铺 + 中断标记） | `status === 'interrupted'` | `roundStore.ts:136` 明文 |
| turn **是否结束**（输入框放开、滚动、分叉可用） | `turnState.phase === 'settled'` | 本文新增（turn 级，≠ round 级） |

三者不得互替。**这是本次排雷最重要的一条修正。**

### M3b-1 · 宿主并行发送 turn_update（webview 不消费）—— ✅ 已落地 2026-09-23

宿主侧新增 `postTurnUpdate(liveRoundId?)`，在四个点**并行**发送（旧消息一条不动，webview 的

| 调用点 | state |
|--------|-------|
| `consumeFlow` 起始 | `running` |

| 流尾 `pausedOnPurpose` | `waiting(pause)` |
| 流尾 `done` | `settled`（status=complete） |

- **`rounds` 一律取落盘历史**（`loadRoundBasedHistory`），运行时未落盘的当前轮**不入列**——
  半残数据比不投更危险；当前轮等 M3b-2 补 `LiveRoundState` 后再含。

## 第六部分 · 顺带发现的执行层缺口（不在本方案范围）

### 6.1 已澄清的事实：step 原子落盘的覆盖范围依赖「任务表」

`docs/architecture/step-atomic-persistence.md`（档2 已落地）：宿主 `checkpointRound` 在
`plan_item_boundary` 时增量落盘 pending Round，流尾复用同一合并语义。**这是真的，已实现。**

但 §二把 `plan_item_boundary` 当作「step 边界信号」使用，而它的 `planItemId` 来自**任务表 plan 的
active step**（内核：无任务表或 planItemId 未变则不产）。后果：

| 场景 | 增量落盘（档2 原状） | 断电后果 |
|------|----------|----------|
| 有任务表（多步任务） | ✅ 每个 plan step 推进时落盘 | 只丢当前 step 的过程 |
| **无任务表（普通问答 / 长工具循环）** | ❌ 只有流尾一次 | **过程全丢**——恰恰是最需要保护的长时间运行 |

### 6.2 语义澄清：落盘保的是「过程明细」，不是「历史记录」

断电后**轮本身保得住**：`appendUser` 已建 pending Round（userMessage 落盘）→
`listInterruptedRecent` 打捞 → `upgradeInterruptedRounds` 升级为正常 stop turn
（§一·五 定案 + T1 已实现）。丢的是 `processEvents` 明细，不是历史记录。

### 6.3 ✅ 已落地（2026-09-23）：迭代边界信号 = `step_boundary`（档3）

原待决策项：要让所有 loop 迭代都有增量落盘，需内核提供**迭代边界信号**——现有
`plan_item_boundary` 是 plan step 信号，**不可复用**为迭代边界（复用即固化术语撞车）。

**已按此结论落地**（详见 [architecture/step-atomic-persistence.md](./architecture/step-atomic-persistence.md) §九）：

- 内核新增 `step_boundary` chunk：迭代完成**且将继续下一轮**时产（终态不产 → 流尾兜底，
  并保住「终态 chunk 是末条」的既有流契约）；顺序上 `plan_item_boundary` 先、本 chunk 后（落盘快照必含折叠边界）。
- 宿主把 `checkpointRound` 从 `plan_item_boundary` 分支**迁到** `step_boundary` 分支 → **落盘时机单一**。
- 覆盖：有/无任务表、有/无工具全覆盖；无 `Round` schema 改动。
- 验收：内核 7 例 + 宿主 2 例 + 5 组变异（全部按预期转红）；两侧质量门 + 宿主构建通过。

**✅ 术语正名已收官（2026-09-23）**：任务项标识符 `PlanStep` → `PlanItem`（含 `planStepId` / `getActiveStepMeta` / `updatePlanStepStatus` / `STEP_STATUS_LABEL` 等派生名）、宿主协议 `PlanStepDto` → `PlanItemDto`、CSS 类 `plan-step*` → `plan-item*` / `round-block__step*` → `round-block__plan-item*`；**事件三方对调**——`iteration_boundary` 归位为 `step_boundary`（迭代边界），原被任务项占用的 `step_boundary` 改名 `plan_item_boundary`。宿主 UI 折叠块标题 `step-N` 改为「任务项 N」。存量落盘数据读取迁移按用户裁定**免除**（测试阶段零外部用户，`.memora/` 为本地桌面数据，重新生成即可）。覆盖内核 / 宿主 / scripts / role-packs / prompts / tasks / 现行文档；历史档号与 CHANGELOG 旧版本条目按「历史保留原貌」不动。
