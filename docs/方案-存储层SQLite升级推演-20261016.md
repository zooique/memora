## 一、结论先给

**内核的「接口层」零改动——因为 `IMemoryStorage` 本来就是按 SQL 后端设计的**（证据见 §二）。内核的实质改动收敛为三件：

1. **新增一个实现类**（`NodeSqliteStorage`，~350 行，纯新增文件，不动任何现有生产逻辑）；
2. **两个兼容性决策**（**2026-10-16 已拍板**，见 §八）：导入方式 = **A2 系（同步工厂 + 延迟加载，`process.getBuiltinModule`）**；Node 版本门槛 = **单一判据「工厂加载成功」**、`engines.vscode` **不收紧**；新增导出 **2 个**走 ADR-039 准入（决策 B）；
3. **测试与文档**（对拍测试 + ADR-002 补记 + CHANGELOG）。

改动大头在**宿主**（装配切换 + 一次性迁移），但都是「换线头」级小改：vscode 侧装配点 3 行 + 迁移接线 ~80 行 + 测试更新。

**关键实证（本机探针，对照 JSON 覆盖实锤）**：

```
CROSS-CONN-VISIBLE (db1 写 -> db2 读): true     ← 双连接互写互见
REVERSE-VISIBLE (db2 写 -> db1 读): true
ALL-IDS (双写不丢): ["from-dsh","from-vscode",...]   ← 对照 JSON 版 PROBE-DSH-SURVIVES: false
LIKE-ESCAPED (期望仅 literal-pct): ["literal-pct"]   ← escapeLike + ESCAPE 语义正确
```

**动工前两个验证项**：① VS Code extension host 的 Node 版本——**已实锤（2026-10-16）：本机 VS Code 1.142.0 stable 内嵌 Node 24.21.0，`node:sqlite` 全操作可用（★ 见 §五 条 1）**；② 并发 `touch` 写路径的 busy 实测（写锁整库级，探针只测了交替写）——**仍未跑**。

## 三、内核改动清单（分层）

### 层 0：接口层——**零改动**（逐方法已有 SQL 形态）

| 接口方法 | SQL 形态 |
| --- | --- |
| `upsert(memory)` | `INSERT INTO memories(...) VALUES(...) ON CONFLICT(id) DO UPDATE SET ...`（整对象覆盖，与契约「无 CAS 乐观锁」一致） |
| `delete(id)` | `UPDATE ... SET deleted_at=? WHERE id=? AND deleted_at IS NULL`（对已删除 no-op ✓） |
| `restore(id)` | `UPDATE ... SET deleted_at=NULL WHERE id=?` |
| `purge(id)` | `DELETE FROM memories WHERE id=?` |
| `listDeleted(limit?)` | `WHERE deleted_at IS NOT NULL ORDER BY deleted_at DESC` + 可选 LIMIT |
| `getDeletedById(id)` | `WHERE id=? AND deleted_at IS NOT NULL` |
| `purgeExpired(before)` | `DELETE ... WHERE deleted_at < ?` + `changes` 计数 |
| `getById(id)` | `WHERE id=? AND deleted_at IS NULL` |
| `getBySource(source)` | `WHERE source=? AND deleted_at IS NULL` |
| `search(query, limit)` | JS 侧 `segmentLower` 分词 → 逐 token `(content LIKE ? ESCAPE '\' OR name LIKE ? ESCAPE '\')` OR 连接 → `ORDER BY accessed_at DESC LIMIT ?`；空 query/零 token → 纯 `ORDER BY accessed_at DESC` |
| `count()` / `countBySource()` / `getAllSources()` | `COUNT(*)` / `COUNT(*) WHERE` / `GROUP BY source`（注释原话） |
| `touch(id, now)` | `UPDATE ... SET accessed_at=? WHERE id=? AND deleted_at IS NULL` + `changes` 判 true/false |
| `close()` | `db.close()`（数据保留 ✓ 与接口注释一致） |

**消费面零改动**：**14 个**生产消费文件（另有定义 `storageInterface.ts` / 实现 `inMemoryStorage.ts` / 桶 `index.ts` 三处引用，合计 17 处——2026-10-16 核实订正，原「17 个生产文件消费」是引用总数口径夸大）——roundSummaryGenerator / memoryInspector / memoryAdvisor / dedupManager / keywordsTouch / gcService / contextPreparer / toolExecutor / builtinToolHandlers / supersedeResolve / types.ts / projectManager.ts / roundStore.ts / sessionStore.ts，全部只调接口方法——换实现即全链切换，**零感知**。内核 `src/` **生产代码**对 `memories.json` 零引用（已 grep 实锤；仅 `src/memory/__tests__/types.test.ts:121` 一条注释提及）——文件路径语义从来只在宿主侧。

### 层 1：新增文件（决策 A：实现放哪）

| 方案 | 内容 | 判定 |
| --- | --- | --- |
| **a. 内核内置 `NodeSqliteStorage`（推荐）** | 新增 `src/memory/nodeSqliteStorage.ts`，用 `node:sqlite`（`node:*` 内置模块，不破「零第三方运行时依赖」）；三宿主（vscode / memora-mcp / dsh）共享同一实现 | ✅ 一份实现零并列；代价 = 内核 Node 门槛问题（见下） |
| b. 各宿主自实现 | vscode 一份 + dsh 一份 + mcp 一份 | ❌ 直接否决——三份并列即语义漂移灾难（与 ADR-MCP-001 决策 2 同款判据） |
| c. 独立包 `@zooique/memora-sqlite` | 不碰内核导出面/engines，代价是多包发版联动 | **否决（2026-10-16 拍板）**——经 A2 核实后**无剩余价值**：A2 已解决 engines/导出面顾虑，c 只剩三轴发版成本 |

**选 a 时的兼容性细节（决策 A 的实质）**：内核 `engines` 现为 `node >=22.0.0`，而 `node:sqlite` 需 ≥22.5（引入）、≥22.13（免 flag）。**门槛来源辨析（防误读）**：Node 版本门槛的**来源**是「选用 node:sqlite」这一技术选型（事实门槛，与实现放哪 a/b/c 无关）；决策 a 决定的是门槛的**分布**——「内核内置 + 静态 import（A1）」使门槛全局化：`index.ts` 静态导出该实现后，**任何** `import '@zooique/memora'` 的进程在**加载期**即解析 `node:sqlite` 说明符（哪怕该进程只用 JSON/内存实现）；「动态 import（A2）」或「独立包（c）」可将门槛局部化到真正使用 SQLite 的一方。即 **a ≠ 限制 Node 版本；a + A1 = 全消费者声明面收窄至 ≥22.13**（这是被选择的简单性，非技术宿命）。

- **A1（静态形态，备选）**：收紧 `engines` 至 `>=22.13` + 顶层静态 import。**vsix 场景实锤（2026-10-16）**：VS Code 扩展不走 npm 安装、`engines.node` 拦不住安装、只表现为**加载期崩溃**（老环境连 JSON 模式都用不了）——「诚实声明」在 vsix 场景失效。**2026-10-16 拍板：不采用**（见 §八-2）；若未来 major 视「<1.101 覆盖率」决定再收紧，届时另议。
- **A2（延迟加载形态 · 2026-10-16 拍板采用）**：**同步工厂 + `process.getBuiltinModule` 延迟加载**——`createNodeSqliteStorage(dbPath, options?)`（非 async）：内部 `process.getBuiltinModule('node:sqlite')` 取内建模块，**返回 `undefined` 即「环境不支持」**⇒ 抛专属错误（**显式判据，非异常吞没**；`typeof process.getBuiltinModule !== 'function'` 的 Node ≤22.2 走同一条判据）；类型用 `import type { DatabaseSync } from 'node:sqlite'`（类型导入，编译后消失、零 any）**＋显式结构白名单**——⚠ 2026-10-16 落地订正：原拟的 `typeof import('node:sqlite')` **类型注解被 eslint `consistent-type-imports` 禁止**，且手写白名单恰好落实下条要求的「API 子集固化」。**⚠ 类型与运行时不对称（2026-10-16 核实新增）**：根 `@types/node` 为 26.x（含 Node 26 API 面）、宿主为 22.x、运行时门槛 22.13 ⇒ `tsc` 绿**不等于**运行时有该 API（实测 `typeof import('node:sqlite')` 在现有 tsconfig 下编译通过，EXIT=0）——实现须**只使用 ≥22.13 已存在的 API 子集**，并以显式白名单固化，**判据不得是「tsc 绿」**（防「因错误的原因通过」）。
  **为何优于 `createRequire(import.meta.url)`（同日核实升级，替换上轮形态）**：① **不依赖 `import.meta.url`**——该符号在本仓宿主 esbuild bundle 场景**有事故史**（`hosts/memora-vscode/src/extension/host/assemble.ts:148-149`、`extension/extension.ts:126-127` 注释：「esbuild bundle 后 `import.meta.url` 路径漂移」）；② `createRequire(undefined)` 实测抛 `TypeError ERR_INVALID_ARG_VALUE`，若 bundle 使其失效，该异常会被 catch-all **吞成「老 Node 环境不支持」= 真故障伪装成环境问题**（违背「不带伤」）；③ 本机实测（Node 22.22.2 / 24.12.0）`process.getBuiltinModule('node:nonexistent')` 返回 `undefined` **不抛** ⇒「不支持」与「真 bug」判据分离；④ 版本代价 ≥22.3 被 `node:sqlite` 的 ≥22.13 门槛**完全吸收**，不抬门槛。
  **优势**：① 与 `createLlmProvider` 等现有**同步**工厂风格一致——原「async 工厂」方案的最大代价（异步构造面）作废（另注：`safeExecuteCode`/`accumulateStream` 证明内核并非无 async 先例）；② 门槛局部化（仅调用工厂者需 ≥22.13）；③ 老环境「扩展不挂 + JSON 照常」。`canUseNodeSqlite` 探测函数**剔除**（工厂结果 + 专属错误码已足够，少一个导出面）。宿主 `assembleAgent`（assemble.ts:266）为 async 上下文，接入零成本。
  **只读变体（2026-10-16 拍板，进签名）**：工厂用**重载**——`{ readOnly: true }` 返回 `ReadOnlyMemoryStorage`（`Pick<IMemoryStorage, 读方法>`，**结构上拿不到写方法**），保住 `hosts/memora-mcp/src/readOnlyFileStore.ts:16-18` 既有契约「只读保证由结构表达……约定会腐化，结构性缺失不会」；同时避免 MCP 自写第二个 sqlite 实现（否则并列从 IO 装载层 ~40 行升级为**实现类 ~350 行语义并列**，与下表 b 项否决判据自相矛盾）。
- **A3**：子路径导出 `@zooique/memora/sqlite`。违 ADR-039 单一入口精神，否决。

### 层 2：导出与准入（决策 B · 2026-10-16 修正）

`src/index.ts` 新增 **2 个**公共符号：`createNodeSqliteStorage`（工厂）+ `ReadOnlyMemoryStorage`（只读视图类型；options 类型内联进签名不单独导出）。

- **不导出实现类** `NodeSqliteStorage`——纯内部实现不挂公共面（ADR-039 判据①：宿主只经工厂消费，类随签名结构可用）；
- **不导出** `MEMORY_DB_FILENAME` 常量——工厂收 **`dbPath` 全长路径**，**文件路径语义继续留在宿主侧**（守 §层0「内核生产代码对 `memories.json` 零引用」边界，不引入新耦合）。

准入机制 = ADR-039 的**两条判据（宿主真实 import ／ README·手册 §十六 明文承诺）+ 三向机器化守卫**——**无「登记表」这一动作**（原表述「准入记录」为措辞漂移，已订正）。

⚠ **硬依赖（2026-10-16 核实新增）**：`src/__tests__/publicApiSurfaceGuard.test.ts` **双向夹住**——向 A（`:191-199`：公开面 ⊆ 消费面 ∪ 承诺面）与向 C（`:212-220`：§十六 承诺 ⊆ 公开面）。现状实锤：宿主此刻**零 import**、`README.md` 与手册 grep `NodeSqliteStorage`/`node:sqlite` **零命中** ⇒ **只加导出必红、只写承诺不导出也必红**。⇒ **实现 + 导出 + `docs/memora-api-reference.md` §十六 承诺必须同一 commit**。

### 层 3：测试（对拍是核心质量门）

**契约对拍测试**：现有 `InMemoryStorage` 的用例集**参数化跑两遍**（同一套断言跑内存实现与 SQLite 实现）——两实现语义逐位一致是本次升级的硬不变量（否则「插件搜到的和 agent 搜到的不同」）。⚠ **实测前提（2026-10-16 核实）**：全仓 grep **零命中**可复用的 storage 契约共用套件（无 `describeMemoryStorageContract` / `runStorageSuite` 之类），`src/memory/__tests__/inMemoryStorage.test.ts` 硬绑 `new InMemoryStorage()` ⇒ 「参数化」实为**重构既有测试文件**（抽出契约套件 + 两个入口），**不属于「纯新增文件」**（§六 量级表已含此口径修正）。重点对拍项：search 的 token 命中语义、`accessedAt` 降序、软删过滤、`changes` 判定的 true/false、空 query 行为。**已知边缘差异**（登记）：SQLite `LIKE` 对 ASCII 大小写不敏感、对非 ASCII 大小写敏感；JS `.toLowerCase()` 全局小写——中英文测试集覆盖不到的重音字符边缘差异记入已知边界。

### 层 4：迁移——**零内核新增**（宿主组合现有出口）

迁移 = 「读 JSON → 逐条 `parseMemory` → `storage.upsert`」= 宿主用现有出口的组合调用（先例：vscode 宿主 `assemble.ts:304 migrateRetiredSettingSources()` 同位置、同模式）。容错沿用既有语义：单条坏数据跳过 + warn，不因一条脏数据清库；原 `memories.json` **改名保留**（`memories.json.migrated-<date>`），不删除。

### 层 5：文档

`memora-api-reference.md`（**§十六 明文承诺 2 个新符号——与实现同 commit，否则 `publicApiSurfaceGuard` 向 A/C 红**，见 §层2）｜`memora-接入指南.md`（宿主 SQLite 接入段）｜**ADR-002 补记**（「回顾触发已达成」：Node 内置 sqlite 稳定、实现已提供）｜`CHANGELOG.md` `[5.0.0]` 区（**区头「本区归属」须同步改**，见 §六 版本区归属）｜`README`（可选——向 A 的判据②「承诺面」= README 全文 ∪ 手册 §十六，**在 README 提名亦满足向 A**；但**向 C 只校验 §十六**，故正式承诺位置仍以 §十六 为准，README 仅作补充）。

**为什么换 SQLite 后「vscode 运行中看不到 dsh 写入」也一并解决**：`WorkspaceStorage` 的内存快照层被移除——SQLite 实现是无状态连接，「每次调用直查库」，天然读到另一进程的最新提交（WAL 下读写不互斥，探针已实证双连接互写互见）。

**已登记薄并列债务的消解路径（2026-10-16 拍板：不下沉装载层）**：台账 `MCP-SERVER-1`:705 登记「两宿主并列仅限 IO 装载层（~40 行），须把 JSON 文件存储下沉到内核统一导出（需改内核，应与某批发版同批做）」。**本次不采纳「下沉」**——理由三条：① 下沉要求内核获得**记忆文件路径/格式语义**，与 §层0 边界（「文件路径语义从来只在宿主侧」，内核生产代码对 `memories.json` 零引用）直接冲突，且需改 ADR-002 既定边界 = **造伤**；② 债务有**自然归零路径**：迁移完成后 vscode 与 mcp **都读 `.db`**，JSON 装载层仅 MCP 兼容模式独存并带明确退出条件（迁移完成即删）；③ 下沉属「为消除并列而引入新抽象」，违背复杂度守恒。⇒ **内核切片范围 = 新增实现 + 工厂 + 对拍，不含装载层下沉**；MCP 侧经 `{ readOnly: true }` 复用内核实现，**并列不新增**（这是本拍板的关键：§四 若让 MCP 直用 `DatabaseSync` 自建，会把 IO 层并列升级为实现类语义并列）。

## 五、隐藏坑与验证项（对抗式）

1. **★ VS Code extension host 的 Node 版本（第一验证项）——已实锤（2026-10-16）**：本机 VS Code `1.142.0`（stable，官方 shim 与 `code --version` 双口径一致）内嵌 `Electron 43.7.7 / Node 24.21.0`；以官方同款 `ELECTRON_RUN_AS_NODE` 模式（即 `code` CLI 的运行模式）实测：`require('node:sqlite')` 可用、`DatabaseSync/StatementSync/Session/constants/backup` 全导出、建表/插入/查询/关闭全过、内嵌 SQLite `3.53.4`、**无实验警告**。版本线：**VS Code ≥1.101.0（2025-06-11，Node 22.15.1 ≥22.13）即满足 LOAD 门槛**；1.100.x 及以前为 Node 20.19.0 不满足 ⇒ 若未来决定收紧，可行下限 = `^1.101.0`（**2026-10-16 拍板：本次不收紧**，理由见下方「门槛口径」）。残余边界：实测为「同一 Electron 二进制以 Node 模式运行」，与 extension host（utility process）同源同一 Node 运行时；若需进程内 100% 终极确认，可用临时扩展 printf（可选加深，非阻塞动工）。
   **门槛口径（2026-10-16 拍板，消 §二/§五 二手数字冲突）**：全文曾混用两档概念，现具名隔离——**LOAD 门槛**（能加载）= Node ≥22.13（免 flag），**判据 = 工厂调用成功返回**（唯一来源纪律见条 11）；**CLEAN 门槛**（无 `ExperimentalWarning`）= 实测区间 ∈ (24.12, 24.21]（Node 22.22.2 与 24.12.0 实测**均有警告**，VS Code 内嵌 24.21.0 实测**无警告**；「v25.7.0 / Node 24.15+ 达候选发布」两说为**无独立核实的二手数字**，不采信）。**裁决：CLEAN 不是本次门槛**——警告是 stderr 噪音、不影响功能，把它当门槛等于主动放弃存量用户 = **造伤**。⇒ `engines.vscode` **不收紧**（A2 下加载期不受影响，宿主按工厂结果降级 JSON，判据单一）。
2. **node:sqlite 未达 stable**：22 线为实验性（Stability 1.1，免 flag 但打印警告）；「达候选发布（1.2）」的版本线**二手数字冲突、未独立核实**（见条 1「门槛口径」）——API 变动风险由「跟随 Node 版本」承担；备选 better-sqlite3（API 相近、有 `db.transaction(fn)` 封装）切换面小——若 RC 期出现严重问题可切，接口不破。
3. **写锁整库级 + `SQLITE_BUSY`**：多进程同时写会排队（探针未测「同时写同一行」的 busy 路径）——需配 `busy_timeout`（探针用 3000ms）+ 验证高频 `touch` 场景（召回命中即写，两条进程同召一批时双写 touch）。**第二验证项**。
4. **`search` 语义逐位对齐**（对拍测试兜底）：`LIKE` 的 ASCII NOCASE vs JS `toLowerCase`；`ESCAPE` 子句缺省时的零召回陷阱（注释已警示）；空 `accessed_at` 的排序差异（现有实现 `?? ''` 兜底——SQL 用 `COALESCE` 或保证 NOT NULL）。
5. **`node:sqlite` 无 `transaction(fn)` 封装**：批量导入须手写 `BEGIN/COMMIT/ROLLBACK`（try/catch）；单条操作天然自动提交。
6. **`close()` 生命周期**：接口注释「不可当作可逆的暂停」——宿主重启/停用链的调用点要与现状对齐。
7. **`metadata` 字段**：JSON 列（TEXT）序列化往返测试；`isModified` boolean → INTEGER 0/1 映射。
8. **发版联动（ADR-033 双轴）**：内核（新增 2 个导出；**本次拍板不收紧 `engines`**，见 §六 版本区归属）与宿主切换须锁步；`file:../..` 链接刷新纪律照旧。
9. **范围边界**：本次只动 `memories.json`；同目录 `sessions.json` / `rounds/` 的同类并发问题**存在但不属本次**（dsh 不碰它们；将来同类升级可复用本次模式）。
10. **降级语义（SSOT：禁数据分叉，2026-10-16 核实新增）**：宿主接入后按「迁移状态」分档——**未迁移**（无 `.db`）：JSON 正常读写（现状不变）；**已迁移**（有 `.db`）：JSON 侧降级为**只读**（读快照/旧 JSON + 显式提示；**禁写入**——允许写将产生两个活跃写端 = 数据真源分叉；「二次迁移/增量合并」否决为复杂度爆炸）。
11. **探测判据唯一来源纪律（2026-10-16 核实新增）**：判断「能否用 SQLite」的唯一来源 = **调用工厂的结果/专属错误码**；禁止任何宿主自行解析 `process.versions.node` 推断（防判据散点；版本号推断与真实加载可能不一致）。
