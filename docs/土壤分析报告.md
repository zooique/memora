## 二、项目类型

| 项       | 决策                     | 对技术选型的影响                                          |
| -------- | ------------------------ | --------------------------------------------------------- |
| 项目类型 | **CLI 工具 + 守护进程**  | 需要：命令行解析、stdin/stdout 协议、配置文件加载、启动快 |
| 部署形态 | **本地单机（用户机器）** | 不需要云原生；不需要分布式；不需要 Docker                 |
| 启动方式 | **CLI 命令行 REPL**      | 类似 Claude Code / aider：单进程、单用户、交互式          |

## 三、业务领域

| 项         | 决策                                      | 对技术选型的影响                                                                        |
| ---------- | ----------------------------------------- | --------------------------------------------------------------------------------------- |
| 业务领域   | **通用 Agent（领域无关）**                | 业务逻辑通过"记忆配置"（personality.md / rules/ / skills/）注入，核心代码不耦合任何领域 |
| 典型场景   | 编程辅助 / 小说创作 / 知识管理 / 日程规划 | 需要支持：文件操作、Shell 命令、网络搜索（可选）、代码执行                              |
| 多领域支持 | **必须**——一个 Agent 引擎 + 多个领域配置  | 设计为可插拔：领域切换 = 加载不同 personality.md                                        |

## 四、团队与用户

| 项         | 决策               | 对技术选型的影响                                               |
| ---------- | ------------------ | -------------------------------------------------------------- |
| 团队规模   | **1 人（您本人）** | 不需要复杂的 code review 流程；不需要多人协作的模块边界设计    |
| 目标用户量 | **1（单用户）**    | 不需要考虑并发性能（单进程内即可）；不需要限流、缓存、负载均衡 |
| 用户能力   | **开发者**         | CLI 习惯良好；接受配置文件手动编辑；不惧怕看日志               |
| 隐私要求   | **极高**           | 所有数据本地存储；不向云端泄露任何对话/记忆/文件内容           |

## 五、技术环境

| 项       | 决策                                                  | 对技术选型的影响                                     |
| -------- | ----------------------------------------------------- | ---------------------------------------------------- |
| 操作系统 | **Windows（用户当前）/ 跨平台（macOS / Linux 兼容）** | 路径处理必须跨平台；Shell 命令不能硬编码 `/bin/bash` |
| 运行时   | **Node.js ≥ 20 LTS**                                  | 原生支持 ESM、fetch、Test Runner；npm 生态成熟       |
| 包管理器 | **npm**（与 Node.js 同源；避免 pnpm 链接问题）        | 简单优先                                             |
| 工作目录 | `f:\zooique\memora`（Windows）/ 等效 Unix 路径        | 跨平台路径处理使用 `path.join` / `path.resolve`      |
| 时区     | **Asia/Shanghai**（UTC+8）                            | 时间处理用本地时区；存数据库用 ISO 8601 UTC          |

## 六、LLM 集成

| 项            | 决策                                           | 对技术选型的影响                                               |
| ------------- | ---------------------------------------------- | -------------------------------------------------------------- |
| 首选提供方    | **国产模型 API**（豆包 / 通义千问 / DeepSeek） | 全部走 OpenAI 兼容接口（已有先例）→ 抽象为统一的 `LlmProvider` |
| 备用提供方    | OpenAI / Anthropic（可选适配）                 | 同一 `LlmProvider` 接口可切换                                  |
| 接口协议      | **OpenAI Chat Completions 兼容**               | 国产模型（豆包/通义/DeepSeek）均提供此接口；零额外适配         |
| 本地模型      | **阶段一不支持**（阶段三可选）                 | Ollama 等可走同一 OpenAI 兼容接口；预留扩展点                  |
| 流式响应      | **必须支持 SSE 流式输出**                      | 用户体验关键；CLI 必须能逐字打印                               |
| Function Call | **必须支持**                                   | Agent Loop 的核心依赖                                          |
| 上下文窗口    | **128K 起步**（国产模型主流规格）              | 检索召回必须严格控制预算                                       |

## 七、外部依赖

| 项       | 决策                                     | 对技术选型的影响                                                                                                         |
| -------- | ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 数据库   | **SQLite 3 + better-sqlite3**            | 单文件无服务；同步 API 简单；支持 FTS5 / JSON1 / sqlite-vec                                                              |
| 向量检索 | **sqlite-vec**（阶段三）                 | 与 SQLite 同库；零额外依赖；倾向性已在 [agent上下文组装协议.md §4.4.2](../docs/基础设计文档/agent上下文组装协议.md) 明确 |
| 中文分词 | **jieba**（阶段二）                      | Node.js 端成熟方案；离线可用                                                                                             |
| 测试框架 | **Vitest**                               | 与 Vite 生态同源；支持 TypeScript 原生；与 [测试策略.md](../docs/基础设计文档/测试策略.md) 已对齐                        |
| 类型系统 | **TypeScript ≥ 5.x**                     | 强类型；IDE 提示；与设计文档的"代码与模型分工"哲学一致                                                                   |
| 日志     | **pino**（轻量 + JSON 输出）             | 比 winston 简单；性能高；阶段一可选 console                                                                              |
| 命令行   | **commander.js**                         | 成熟稳定；比 yargs 轻                                                                                                    |
| 配置     | **cosmiconfig**                          | 自动发现 `.memora/config.json` / `package.json` 中的 `memora` 字段                                                       |
| 终端 UI  | **ink**（可选，阶段一先用基础 readline） | 用于复杂的 CLI 交互（阶段二考虑）                                                                                        |

## 八、部署与运维

| 项       | 决策                                                                                                                       |
| -------- | -------------------------------------------------------------------------------------------------------------------------- |
| 部署方式 | `npm install -g memora`（全局安装）+ `memora` 命令启动                                                                     |
| 数据目录 | `~/.memora/`（跨平台：Windows `%APPDATA%/memora`、macOS `~/Library/Application Support/memora`、Linux `~/.config/memora`） |
| 配置目录 | 同上 `~/.memora/config.json`                                                                                               |
| 日志目录 | 同上 `~/.memora/logs/`                                                                                                     |
| 升级方式 | `npm update -g memora`（npm 自带）                                                                                         |
| 卸载     | `npm uninstall -g memora` + 数据目录保留（用户决定是否删除）                                                               |

## 九、风险评估

| 风险                 | 等级 | 缓解策略                                                                                                                                  |
| -------------------- | ---- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| 国产 LLM API 不稳定  | P2   | 多家备份；自动 failover；缓存常见回答                                                                                                     |
| FTS5 中文分词精度低  | P3   | 阶段一用文件名匹配；阶段二上 jieba；阶段三上 Embedding（详见 [agent上下文组装协议.md §4.4](../docs/基础设计文档/agent上下文组装协议.md)） |
| 单机 SQLite 并发限制 | P3   | 单用户场景无并发问题；冥想机制用项目级锁                                                                                                  |
| 路径跨平台兼容       | P2   | 全程使用 `path.join` / `path.resolve`；CI 加 macOS / Linux 跑测                                                                           |
| Windows Shell 差异   | P2   | 不硬编码 shell 命令；优先用 Node.js API 替代 Shell                                                                                        |
| CLI 体验不好         | P2   | 阶段一用 readline 起步；阶段二换 ink                                                                                                      |

## 十、阶段一切分（推荐）

| 阶段              | 范围                                                                | 交付物                      |
| ----------------- | ------------------------------------------------------------------- | --------------------------- |
| **阶段一·极简版** | Node.js 骨架 + 永驻/话题记忆 + LLM 适配 + Agent Loop + CLI 基础交互 | 可对话的 CLI，能记 1 个话题 |
| **阶段二·增强版** | FTS5 + jieba + 冥想归档 + 工具白名单 + 5 种能力记忆                 | 多话题管理 + 文件操作能力   |
| **阶段三·完备版** | sqlite-vec 语义检索 + 多项目并发 + 领域切换 + 性能优化              | 完整通用 Agent              |
