01 · 设计哲学

万物皆记忆

Memora 的核心哲学：一切元素都是记忆，区别仅在于持久化层级和生命周期不同。

核心设计原则

用户实时输入是触发点。系统以用户输入为锚，从各层级召回相关资源，融合后生成响应。输入不再只是"发送消息"，而是携带结构化意图的增量事件（SessionEvent）。

一切皆接口。开发人员定义接口（AgentOptions）、记忆系统接口（IMemoryStorage/ISessionStore/IVectorStore）、用户实时输入接口（SessionEvent/chat()）、用户自定义内容接口（Persona/Skill/Rule）——四层接口各自独立，职责清晰。

不中断 = loop 任务内 + 申请暂停。一问一答保持核心交互；loop 长任务自然获得「用户申请暂停查看 / 注入补充 / 确认继续」——暂停 = 申请暂停（requestPause），进行中的问答回合结束后于 loop 迭代边界挂起（软暂停，messages 保留，可续跑），可继续（resumeExecution 原路径续跑）或注入新内容（自动恢复 + 融合继续）。

02 · 系统层级

五层架构设计

从用户输入到底层存储，每一层都有明确的职责边界和接口契约。

输入层 SessionEvent + chat() / processEvent()
用户实时输入（文本/意图分类/四元组增量 delta）。宿主项目通过 agent.chat() 或 agent.processEvent() 输入。
补全层 Composer
四级补全链（P1→P2→P3→P4）。将增量事件补全为完整四元组（角色×任务×标准×资源），缺省时有明确来源。
编排层 Agent 门面 + AgentLoop
Agent 门面是宿主唯一入口。职责：角色匹配 → 记忆召回 → 技能注入 → 历史追加 → LLM 流式调用 → 后处理归档。管理检查点、状态机、计划推进。
记忆层 recall() + MemoryGovernance + 各 Manager
双通道召回（语义+关键词）。L0 衰减 / L1 去重 / L2 时效性 / L3 冲突检测。用户画像、Insight、会话归档等专职 Manager。
存储层 IMemoryStorage / ISessionStore / IVectorStore
宿主注入的存储接口。Memora 内核不依赖具体实现，宿主可提供 SQLite/文件系统/内存等任意实现。
用户输入SessionEvent → 补全层Composer → 编排层Agent → 记忆层recall → LLMLlmProvider → 输出AgentChunk
03 · 输入接口体系

四层输入接口

用户实时输入、开发者 API、记忆系统、自定义内容——每层接口都有独立的设计目的和契约。

● 用户实时输入接口
文本 + 意图分类 + 四元组增量。支持 chat / command / correction / clarify 四种意图，独立路径防污染。
SessionEvent · chat() · processEvent()
● 开发者 API 接口
Agent 门面构造参数 + 生命周期方法。宿主一行代码接入，支持自定义 Provider、存储、安全策略。
AgentOptions · Agent 类 · init() · close()
● 记忆系统接口
存储抽象层。宿主注入任意实现（SQLite/文件系统/内存），Memora 不依赖具体后端。
IMemoryStorage · ISessionStore · IVectorStore
● 用户自定义内容接口
角色（Persona）、技能（Skill）、规则（Rule/RuleSet）的文件定义。通过配置文件目录热加载，无需重启。
PersonaManager · SkillManager · ConfigManager

用户实时输入 — SessionEvent

替代纯文本输入，升级为结构化增量事件。输入不再只是"发送消息"，而是携带意图分类和四元组增量的结构化事件包。

// 增量事件类型 — 用户实时输入的核心接口 interface SessionEvent { type: 'chat' | 'command' | 'correction' | 'clarify'; // 意图分类 content: string; // 原始文本 delta?: DeltaPayload; // 四元组增量（可选） } // 四元组增量 — 角色×任务×标准×资源 interface DeltaPayload { role?: Role | SlotRef; // 角色增量（支持引用当前值） task?: string | SlotRef; // 任务增量 standard?: Standard | SlotRef; // 标准增量 resource?: ResourceState | SlotRef; // 资源增量 }

意图分类防污染：command/correction/clarify 不写 chat 历史，避免控制信号污染对话流。

开发者 API — Agent 门面

一行代码接入。开发者只需提供 Provider 和项目路径，无需关心内部组件组装。

// 最简接入 const agent = new Agent({ projectPath: './my-project', provider: new OpenAIProvider({ apiKey: '...' }), dataDir: './agent-data', }); await agent.init(); // 流式对话 for await (const chunk of agent.chat('你好')) { if (chunk.type === 'text') process.stdout.write(chunk.content); } // 高级：结构化事件输入（不中断工作模型） const event: SessionEvent = { type: 'chat', content: '帮我写一个排序函数', delta: { task: '写排序函数' }, }; for await (const chunk of agent.processEvent(event)) { ... }

Agent 门面暴露 12 个专职 Manager 的访问器（agent.persona、agent.memory、agent.config 等），供宿主直接操作。

记忆系统接口 — 存储抽象层

宿主注入任意存储实现，Memora 内核零依赖具体后端。

// 宿主注入存储实现 interface IMemoryStorage { upsert(memory: Memory): Promise<void>; search(query: string, opts?: SearchOptions): Promise<Memory[]>; delete(id: string): Promise<void>; } // 会话存储 interface ISessionStore { listSessions(): string[]; loadMessages(date: string, session: string): SessionMessage[]; saveCheckpoint(sessionId: string, json: string): void; loadCheckpoint(sessionId: string): string | null; } // 向量存储（可选，开启语义搜索） interface IVectorStore { search(query: string, limit: number): Promise<ScoredMemory[]>; }

三层存储各自独立，按需注入。不注入时内核使用内存存储降级运行。

用户自定义内容 — 角色/技能/规则

通过配置文件目录定义，热加载无需重启。开发者只需按规范编写文件，Memora 自动加载。

// 角色定义（personas/ 目录） interface PersonaDefinition { name: string; // 角色名 systemPrompt: string; // 系统 prompt triggers?: string[]; // 关键词触发（自动匹配） } // 技能定义（skills/ 目录） interface SkillDefinition { name: string; // 技能名 triggers: RegExp[]; // 正则触发 systemPrompt: string; // 技能 prompt（当轮注入） } // 规则定义（rules/ 目录） interface RuleDefinition { name: string; // 规则名 content: string; // 规则内容（注入 bootstrap） }

角色自动匹配（关键词+LLM辅助）、技能当轮实时注入、规则由 bootstrap 机制自动注入 —— 所有自定义内容即写即用。

04 · 触发流程

用户输入 → 系统响应 完整链路

用户实时输入是触发点，系统沿五层架构逐级处理，最终输出响应。

① 输入接收
agent.chat() 或 agent.processEvent() 接收用户输入。校验输入长度、会话状态（暂停/异常中拒绝）。
② 四级补全
Composer 将 SessionEvent.delta 补全为完整四元组（角色×任务×标准×资源）。P1→P2→P3→P4 逐级填充，缺省时暂停询问。
③ 上下文准备
角色自动匹配 → 双通道记忆召回（语义+关键词）→ 技能当轮注入 → 最近对话注入 → 用户消息写入历史。
④ LLM 流式调用
AgentLoop 执行 LLM 调用。支持工具调用循环、护栏规则检查、上下文窗口截断、反思重试。输出 AgentChunk 流。
⑤ 后处理归档
助手消息写历史 → 用户画像归档 → Insight 提取 → AutoConfig 分析。所有操作为 fire-and-forget，不阻塞用户响应。
用户输入SessionEvent → 补全层Composer → 角色匹配Persona → 记忆召回recall → 技能注入Skill → LLMLoop → 后处理Archive
05 · 四级补全链

三源融合 · 逐级补全

四元组每个槽位独立走补全链，缺省时有明确来源和可追溯性。

P1 · 显式输入
用户通过 delta 明确提供值，或通过 SlotRef 引用当前值
↓
P2 · 记忆沉淀
从检查点历史值延续，保持上下文一致性
↓
P3 · 系统内置
代码内置默认值兜底（角色=assistant、标准=完成、资源=空）
↓
P4 · 暂停询问
以上都无法补全时，生成澄清问题暂停等待用户回答

增量合并规则

增量槽引用：用户说「继续」时，任务槽引用 currentGoal，不覆盖。

新值槽覆盖：用户提供新标准时，直接覆盖 standard 槽。

数组槽追加：资源槽的 documents/memories 数组自动追加，非覆盖。

未提供字段（undefined）：走 P2→P3→P4 补全链。

P4 防滥用机制

连续 2 次高风险暂停后强制降级 P3，不再生成 P4 问题。低风险问题（lowRisk=true）由 Agent 自动兜底，不计入连续暂停计数。

申请暂停模型（v2.2 最终定论）

定位：不中断对话思路是大厂（Trae/WorkBuddy 等）已实现的功能——loop 任务内，Agent 在问答回合间隙主动弹窗提问、用户直接输入内容即进入待输入形态，等 loop 最近一轮任务结束自然衔接。大厂未做的是显式暂停/继续按钮（为减用户心智负担而隐藏）。memora 在其上增加显式的「暂停（申请暂停）」与「继续」按钮。

暂停 = 申请暂停（requestPause）：用户点击暂停 = 提交申请，内核置 pauseRequested，进行中的问答回合自然结束后于 loop 迭代边界挂起（messages 保留，可续跑），发射 {type:'paused'} chunk。非霸道中止——硬停止（signal.abort）才是唯一霸道中止路径（杀生成器、不可续跑）。

暂停后可继续可注入：空输入 → resumeExecution() 直接续驱 loop 原路径；携带输入 → 自动恢复 + 补充注入融合继续。

可续跑信号（canContinueWithoutInput()）：暂停态优先返回 true，否则 isInAutonomousStep || hasPendingPlan。宿主据此决定按钮形态——简单轮（无续跑可能）只给停止，不给暂停。

检查点（SessionCheckpoint）

检查点是会话运行时的完整快照，包含：会话标识、三态状态、目标（mainGoal/currentGoal/goalVersion）、执行计划、角色、标准、资源、热记忆窗口、工具执行日志、心跳时间戳。

interface SessionCheckpoint { sessionId: string; // 会话唯一标识 status: 'running' | 'paused' | 'error'; // 三态 mainGoal: string; // 原始目标（防漂移锚点） currentGoal: string; // 当前迭代目标 goalVersion: number; // 目标版本（每次更新递增） plan: PlanStep[]; // 执行计划 hotMemory: ChatMessage[]; // 热记忆窗口（截断后） completedToolCalls?: ToolExecutionRecord[]; // 工具执行日志 lastHeartbeat: number; // 心跳（防僵尸会话） }

恢复协议（5 步恢复）

① 快照反序列化 → ② 热窗口载入（恢复最近对话到 AgentLoop）→ ③ 温记忆按需召回（以 mainGoal 为查询条件，从温记忆召回早期上下文）→ ④ 契约重注入（角色+技能重新注入）→ ⑤ 恢复校验（ERROR 状态时校验 recovered 条件）。

工具幂等性 + 补偿机制

工具分三级幂等性：idempotent（天然幂等）、idempotent-key（依赖唯一键）、non-idempotent（需补偿）。恢复时对非幂等工具执行补偿操作，确保状态一致性。

08 · 记忆系统体系

记忆层级与治理

万物皆记忆——不同持久化层级的记忆，各有不同的生命周期和治理策略。

热记忆 AgentLoop 工作记忆中的最近对话。FIFO 截断（默认 20 轮），单条内容截断（500 字符）。存储在内存中，随检查点序列化。
温记忆 通过 recall() 双通道召回（语义+关键词）的归档记忆。存储在 IMemoryStorage 中，L0 衰减 / L1 去重 / L2 时效性 / L3 冲突检测治理。
冷记忆 用户画像（UserProfile）、Insight（关键洞察）、会话归档（SessionArchive）。由专职 Manager 在 postProcess 阶段异步归档。
配置记忆 角色（Persona）、技能（Skill）、规则（Rule）——通过配置文件目录加载，热重载无需重启。由 bootstrap 机制自动注入到 LLM 上下文。

记忆治理四层模型

L0 衰减：按时间衰减记忆分数，久未命中的记忆逐渐降权。

L1 去重：LLM 驱动的语义去重，相似记忆合并或降级。

L2 时效性：评估记忆是否过时，过时记忆标记或降级。

L3 冲突：检测互为矛盾的记忆（如"用户偏好 Python" vs "用户偏好 Rust"），标记冲突供用户确认。
