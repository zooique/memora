## 0. 一句话结论

**能做到**：粘贴 / 拖拽采字节、写盘、永久显示。
**做不到**：把 `File` 对象本身送过通道；也没办法在不改协议的前提下做「先落盘、再回执」的二次握手。
**必须先解决**：协议面只剩 1 条余量 ⇒ 采集链**不许新增消息类型**；`.memora` 目录名有 3 处各自拼接 ⇒ 加第四处前先抽单点。

## 2. VS Code 硬边界（决定形态的墙）

### B1 · `File` / `Blob` / `ImageData` **不能**被送进 Extension Host【A】

> Webview content can post strings or json serializable objects back to an extension. **They cannot post Blob, File, ImageData and other DOM specific objects** since the extension that receives the message does not run in a browser environment.

**这就是整条采集链的总约束**：字节在 webview 侧以 `File` 的形态出现，而 host 侧永远看不到这个对象。唯一能过通道的是字节的**字符串编码**（base64）。

### B2 · 通道是「JSON 可序列化」的，且二进制优化是**单向**的【A】

官方指南对 host → webview 方向写着：

> This method sends any JSON serializable data to the webview.

同一份 typedef 对 `ArrayBuffer` 的承诺是**有条件且单向**的：

> ...if your extension **targets vscode 1.57+** in the engines field of its package.json, any ArrayBuffer values that appear in message will be more efficiently transferred **to the webview** and will also be correctly recreated inside the webview.

⇒ **反向（webview → host）没有任何类似承诺。** 不要指望 `Uint8Array` 能保真到达：它不是 JSON 可序列化对象，`JSON.stringify` 会把它降级成索引字典。**结论＝只发 base64 字符串。**

### B3 · VS Code 自己会吞掉 drop 事件【B】

`microsoft/vscode-discussions` 的 1663 号案例（提问者自验确认）：

- 从 **操作系统文件管理器** 拖文件进 webview：不按住 **Shift** 时，VS Code 会用默认编辑器把该文件打开，webview 收不到 drop；
- 从 **VS Code 资源管理器** 拖进来：`dataTransfer.files` **为空**，绝对路径只在 `dataTransfer.getData('text/uri-list')` 里。

⇒ **两条推论**：
1. 拖拽的接收必须在 `dragover` 阶段 `preventDefault()`，并让用户看得见「这里可以放」；
2. 「从资源管理器拖」是**唯一零膨胀路径**——它给的是字符串 URI，可以直接当普通 JSON 发给 host，由 host 用 `fs` 读盘，字节**完全不过 postMessage**。这是 B1 之下最便宜的一条路，值得优先实现。

> 有待真机验证的线索【C】：社区 gist 称在 window 层拦截 `dragover` 可免除 Shift 要求。**不作为设计前提**，列入第 7 节真机清单。

> ⚠️ **本条的适用范围必须卡死**：上述实证与社区 gist **全部来自 `WebviewPanel`（编辑器 tab 里的 webview）**。而本项目的对话面板是 **`WebviewView`（侧边栏 view）**——两者是 VS Code 里两个不同的容器，drop 事件由谁先接管**没有任何理由保证一致**（侧边栏自己还有一套视图容器拖放逻辑）。⇒ 本节结论对侧边栏只能当作**待验证的假设**，不是判据。这一条不写清，就会拿 panel 的经验去给侧边栏下结论，正是本项目反复禁止的「把二手结论当契约」。

### B4 · CSP 与 `localResourceRoots`：本项目是**主动收紧**，不是先天不足【A + 仓】

官方默认其实放行两处：

> By default, webviews can only access resources in the following locations: Within your extension's install directory. Within the user's currently active workspace.

而本宿主的 `localResourceRoots` 被**显式收窄**到 `dist/webview`（chatPanel / settingsPanel 两处创建点一致）。所以对 VS Code 的官方默认而言，把 `.memora/attachments` 加回去是**放宽**——它是改了安全面，**必须显式记录为何值得**，不能当成「顺手加上」。

同时注意 `webview.cspSource` 的官方用途原文：

> This is the origin that should be used in a content security policy rule: `img-src https: ${webview.cspSource} ...;`

### B5 · `FileReader` 可用 —— **这是推断，不是契约**【A（仅证明未禁止）+ 推断】

官方指南**没有**任何条款禁止 `FileReader` / `ArrayBuffer`；`fetch` 在「加载 Worker 代码」场景还有官方示例（`result.blob()`）。

**但必须把话说到位**：「官方没写禁止」只证明**没有被明文限制**，**不证明**我们这块 webview 里它真能跑通（CSP 未声明 `connect-src`、webview 的 `<input type=file>` 友好度、`FileReader` 在挂起/恢复后的行为，都可能另有实际情况）。Cline / Roo 一类成熟插件普遍走「`FileReader` → base64 → `postMessage`」，这是**社区普遍实践（B 级以下）**，用作线索可以，用作设计前提不行。

⇒ **本文对它的处置**：作为「首版实现的首选路径」出手，但**必须配套一个失败兜底**（读不出来就给可见提示，绝不静默无反应），并把「能不能真读出来」放进第 7 节真机清单第 1 条。**不得**在测试里用 jsdom 的 `FileReader` 竖片就当它已被证实。

**落地形态（2026-10-28 已按此实现）**：`helpers/imageCapture.ts` 的读字节入口是「`Blob.arrayBuffer()` 优先 → `FileReader` 兜底」，两条都不成时产出一条**可见的拒收 chip** 而不是静默失败。选 `arrayBuffer()` 打头是因为它比 `FileReader` 少一层回调、少一个 `Promise` 包装；保留 `FileReader` 是因为两者在官方文档里**同样**只有「未禁止」这一条依据（本节的定级原因），单押一条等于把整个功能押在一个未获承诺的 API 上。两条路径都通过依赖注入暴露（`readBytes` / `sha256`），测试用假实现，不赌 jsdom 的实现细节。

## 3. 宿主（插件自身）的现状边界

### B6 · 输入区是 `<textarea>`，不是富文本【仓】

`chatPanel` 的输入区骨架里，输入框是**原生 `<textarea id="input">`**。后果：

- **不可能内联 `<img>`** —— textarea 只能装纯文本。这与方案 D17（附件条放在输入框上方）是一致的，且托盘上的 `#skillChips` / `#refChips` 已经是同构的「选择态行」范式，**不需要新造一个容器概念**。
- 副作用正好：粘贴图片时**不会**把图片的富文本语义塞进正文，`content: string` 一个字节都不用改（方案 D2 的前提成立）。

### B7 · 协议面余量只剩 **1** —— 采集链不许新增消息类型【仓 · 实测】

`shared/__tests__/protocolGuard.test.ts` 的门槛是 `IPC_CHANNEL_GOVERNANCE_THRESHOLD = 130`，本次实测去重消息类型 = **129**。

⇒ **任何一侧新增一条 `type: '...'` 都会当场把本体打红**（`toBeLessThan(130)`）。

好在同一个守卫的统计口径只认 `type: '...'` 字面量，**加字段是零增量**（既往已实测：加 op / 加字段 / 加 state 值均为 0 差值）。而 `input` 消息本来就是「本轮输入的总入口」，已经带 `text` / `answers` / `skillName` / `refs` / `injections`。

⇒ **结论：附件走 `input` 消息的字段扩展，禁止新开 `image_*` 通道。**
这条约束直接否决了「采集时先发一条 `image_ingest` 让 host 落盘、再等一条回执告诉 webview 保存好了」的常见设计——**那条设计今天就编译不过去（服务端：守卫红）**。

> **拍板订正（2026-10-28）**：本节「禁止新开 `image_*` 通道」结论**已被用户拍板部分推翻**——落盘链走**治理评估扩位 +2**（`image_ingest` 上行 + 落盘回执下行，`IPC_CHANNEL_GOVERNANCE_THRESHOLD` 130→132）。依据：130 本是用户口径的**治理评估触发线**（`protocolGuard.test.ts` L23 注释原文），评估扩位是它的预期用法而非破坏守卫；且已核全 129 条清单**无现成图片载体**可嫁接（「零新增全嫁接」因语义折叠高危被否）。本节「加字段是零增量」的事实继续有效——`input.attachments` 的发送时交付不受影响。拍板记录 = 台账 IMG-2 第 6 子块。

### B8 · CSP 目前是 `img-src data:`，且全仓零 `<img>`【仓】

`webview/helpers/htmlShell.ts` 的 CSP 为 `default-src 'none'; img-src data:; ...`，其注释明写「全库零 `<img>` 标签，不授任何外部源」。

⇒ **形态分岔**（两者互斥，必须二选一并写进理由）：

| 方案 | CSP 改动 | roots 改动 | webview 是否长期持有字节 |
|---|---|---|---|
| **P-a 内存预览**：悬停时把 base64 拼成 `data:` URI | 免改（已放行 `data:`） | 免改 | **要**（每条 chip 拖着一份 base64） |
| **P-b 磁盘预览**：悬停时用 `asWebviewUri` 指向 `.memora/attachments/<sha>.<ext>` | 加 `${cspSource}` 到 `img-src` | 加 attachments 目录 | 不要 |

**推荐 P-b**：它是 B4 里「数据只有一份（磁盘）」的形态，webview 不留字节 ⇒ 重启、重建 webview、面板隐藏销毁后都不会出现「UI 有 chip 但预览是空白」的半死状态。代价是改安全面，**理由必须写进 `htmlShell` 的注释**（现在那句「全库零 `<img>`」在加图后即成为谎话，必须同批改）。

### B9 · `.memora` 目录名有 **3 处**各自拼接，且其中一处自称唯一【仓 · 现存伤】

| 位置 | 形态 |
|---|---|
| `host/memoryStorage.ts` 的 `DATA_DIR_NAME` 常量 | 有常量，**注释自称「跨宿主路径契约的唯一计算点」** |
| `host/sessionStore.ts` 的 `filePath` 赋值 | 直接 `join(workspacePath, '.memora', 'sessions.json')` 字面量 |
| `host/assemble.ts` 的 `dataDir` 字段 | 直接 `join(projectPath, '.memora')` 字面量 |

`crossHostLayout` 那份契约测试只守护「记忆库这条路径两宿主一致」，**管不住** session 与 dataDir 两处 ⇒ 那份「唯一计算点」的注释是一句**未被机器守护的声明**（典型失守护卫：声明在、判据没绑上）。

⇒ **加 attachments 目录前，先把这三处收成一个 `resolveProjectDataDir(projectPath)` 单点并让测试钉住**，否则我们就是第四份拷贝的作者。这与既往教训「重构/搬家时豁免表与登记必须同步」同源：**先补无盲区，再加能力**。

## 4. 三条采集路径的成本对比

| 路径 | 能拿到什么 | 是否要 Shift | 字节过通道？ | 体积代价 | 备注 |
|---|---|---|---|---|---|
| **① 剪贴板粘贴**（截图 / 复制图片） | `paste` 事件里的 file item ⇒ `File` | 无关 | **必须**（B1 无解） | 5 MiB → base64 ≈ 6.7 MiB 字符串 | 唯一无法绕开膨胀的路径 |
| **② 从 OS 文件管理器拖入** | `dataTransfer.files` 的 `File` | **要**（否则 VS Code 拿去开编辑器，B3） | 必须 | 同 ① | 建议在 `dragover` 阶段抢下来 |
| **③ 从 VS Code 资源管理器拖入** | **只有 `text/uri-list` 字符串**（`files` 为空，B3） | 要 | **不需要** —— 发 URI 让 host 读盘 | 零 | **最便宜**，应优先实现 |
| ④ 备选：命令 + 原生文件选择框 | 由 host 直接读盘 | 无关 | 不需要 | 零 | 不是「粘贴/拖拽」，但可作①③之外的确定性兜底 |

**① 与 ③ 的 bytes 差距是 6.7 MiB vs 0** —— 这不是优化问题，是**要不要付 base64 这一份钱**的问题。界面提示也要跟着分：路径 ③ 可以即时落成 chip；路径 ①② 大图会有一瞬的读取/编码时间，**必须有明确反馈**（而不是看起来没反应）。

## 5. 由边界倒推的分层归属（SSOT）

```
webview  ── 只在 DOM 里见过 File；负责取字节、取出的唯一用途是把它交出去
   │
   │  base64 字符串（唯一可过通道的形态，B1/B2）
   ▼
extension ── 写盘 .memora/attachments/<sha>.<ext>，算 sha256（真相源）
   │
   │  ImageRef{sha256,mime,width,height,bytes,name}  ← 内核早已定义
   ▼
内核 ── 只认 ref，零 IO（维持既有分工，内核不需要为本条目改一行）
```

| 事项 | 归属 | 不许越界做什么 |
|---|---|---|
| 六步校验（已在 `shared/imageValidation.ts`） | webview 侧即时跑 | 不要在 extension 侧再跑一遍充当「复核」——同一公式的第二份实现必然漂移 |
| **sha256 生产点** | **extension（真源）** | webview 侧若为了 chip 展示算值，只能叫**提案**，不得自称真相 |
| 宽高 / mime | **magic bytes 嗅探产出**（同一份 `shared/` 实现） | 不许用 `file.type` 声明值（方案 D18） |
| 去重（G4 同 sha256 只留一条） | chip 层按**提案键**粗筛；host 侧按真相复核 | 不许把 webview 的提案值写进落盘文件名当最终答案 |
| 预览 | **P-b 磁盘预览**（推荐） | 不许把 base64 长期挂在 chip 上（B8 半死状态） |
| 回执 / ack | **不需要**（见 B7：新通道今天就红） | — |

**提案值与真值不一致时会怎样？** —— 不会错图。host 侧 `ImageResolver` 的既有契约是「输入三值交叉校验（sha256 / mime / bytes），不符按未命中处理」（方案 D20），走的是二级降级占位，**不是静默错图**。所以在「不许新增 ack 通道」这条硬约束下，这是唯一一致的解。

## 7. CI 不可验证项清单（必须真机验收）

以下任何一条**都做不到**靠 vitest / tsc / eslint 证明，把它们写成伪造全绿的测试是自欺：

1. **粘贴是否真能拿到 `File`**：Windows / macOS 各主流截图工具 + 浏览器「复制图片」三种来源分别验；最后一类常见只有 `text/html`、无 file item，需明确提示而非静默无反应。
2. **拖入是否必须 Shift**（B3），以及【C】级线索「window 层拦截可免 Shift」是否真成立。
3. **资源管理器拖入的 `text/uri-list` 形态**：不同版本 / 不同平台 URI 可能是 `file:` 也可能被包一层，需在 host 侧按 URI 解析而非正则假设。
4. **26.7 MiB 级 postMessage 的实际体感**（K4）：5 张 5 MiB 一次性发出的耗时与是否卡 UI。
5. **asWebviewUri 能否正常显示**（P-b）：放开 roots + CSP 后，Windows 盘符路径 / 中文路径是否被正确编码——这类中文+空格的路径在本项目有过血的教训。
6. **生成中贴图**：面板存在排队语义，贴图在生成中落到哪里、要不要提示，只有真机看得出。
7. **贴图后切走再切回，chip 还在不在**：该面板**不设** `retainContextWhenHidden`，webview 上下文可能被挂起/重建。这一条直接决定 Q1 能不能选「发送时才交付」——若 chip 会没，则要么改选采集即写盘，要么接受「未发送即丢弃」并写进 UI 提示。**实测回填（2026-10-28 真机）**：切走切回 chip **存活**，但 Ctrl+Alt+B 隐藏侧栏再唤回 ⇒ **chip 全丢** ⇒ `retainContextWhenHidden=false` 坐实 ⇒ Q1 已据此**反转定案「采集即写盘」**（见 §8 Q1）。
8. **侧边栏 `WebviewView` 的拖放是否与 `WebviewPanel` 一致**（B3 适用范围）：资源管理器拖入、OS 拖入、以及不按 Shift 时的行为，**必须分别在侧边栏里验一次**，不得沿用 panel 的结论。
