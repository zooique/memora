## 1. 结论先行

### 1.1 可行性判断：**有条件可行**

| 能做 | 不能做（且不要试） |
|---|---|
| 手机看**会话列表 + 轮次 + 工具步骤 + 运行状态**（含 PC 当前没在看的后台会话） | 把 VS Code / memora 界面"投屏"到手机（那需要远程桌面，不是本方案） |
| 手机向**指定会话**发一句话、插话、暂停/停止 | 让手机成为"第二个写 `.memora` 的写者"（与跨进程写锁冲突，见 §3.2-B1） |
| 手机答**执行类审批**（命令执行 / 脚本与代码执行 / guest 模式写入，见 §2-F13）/ 答 **ask 提问**（默认关闭，需单独授权） | 手机改设置/记忆/技能/角色（与"遥控输入区"目标无关，且各有独立落盘校验） |
| 跨网可用（**默认路径**）：PC 只出站，不买域名、不动路由器、手机不常开 VPN；**Mode D 是例外档**——要有公网 IP + 域名 + 端口映射，见 §4.5 | 多人协作、多 PC 聚合、云历史（明确不在产品边界） |

### 1.2 三个必须记住的不等式

1. **"手机版" ≠ "远程桌面"**。目标用户要的是"看着任务跑、能补一句话"，不是操作 IDE。
2. **"能看到" ≠ "另开一个客户端读文件"**。所有状态活在一个 extension host 进程的内存里；外部进程只能是**该进程的远程终端**。
3. **"能连上" ≠ "改个 baseUrl"**。memora 现在**没有任何服务端形态**，也没有为外部客户端准备的接口。

### 1.3 一句话选型

> **协议先定（传输无关），默认走产品自带 Relay，兜底走 Cloudflare Tunnel，客户端最后选。**

### 1.4 口径订正（2026-11-12 · 读本文前先看这一段）

1. **`T3` 是客户端底座，不是传输方案。** 它是 §10.5 选定的移动端代码底座，计划 vendored 到 `clients/mobile`（§10.4 第 8/9 条）。传输与客户端是**两个正交决策**——换底座不改传输，换传输不改底座。
2. **传输是三档 `Mode R`（中继会合）/ `Mode T`（隧道回环）/ `Mode D`（公网直连），三档都还没拍板。** 本文 §4.1 的「默认 Relay」、§9.1 的「验收一律按 Mode R」是**当时的推荐与验证口径**，不是已决方案；最终选哪档见 §17「产品取舍（待用户拍板）」。
3. **行号核对范围（如实声明）**：本次只逐行核对**新增 / 修改**的引用（§2 F3 / F4 / F5a、§7.1、§8、§15-§17）。全文其余历史行号**未重审**；引用前请按「待查实」口径自行复核。

### 3.2 三条硬边界（越界 = 方案作废）

**B1｜桥必须住在 extension host 内，不得旁挂外部进程。**
理由：`sessionLock` 保证一个会话只有一个写者（见 §2-F7），外部进程抢锁会与 VS Code 窗口互斥；而 Agent 实例、ask/confirm 队列、`pendingInterjections` 全在宿主内存（`chatPanel.ts#L384` 的 `_sessionAgents`、§2-F6 的两个协调器、`agent.ts#L1013` 的 `interject` 队列）。旁挂进程只能做"第二个写者"，直接违反架构前提。

**B2｜桥不得复用 `post()` 作为出口。**
`post()` 对后台流一律丢弃、且 `_turnState` 单份只描述当前会话（两条事实的真身与行号见 **§7.1 B1/B2**，此处不复述）。桥必须自己持有 per-session 投影，**否则手机永远只能看到 PC 正在看的那个会话**，且切到后台会话立刻失明。

**B3｜桥不得改变 PC 的 UI 焦点。**
`_currentSessionId` 是 PC 侧栏的焦点状态，不是全局状态。手机按 `sessionId` 定址订阅，**不调用 `switch_session`**（否则手机一点，PC 界面跟着跳，多端体验立刻崩）。

### 3.3 Transport 契约（约束，不含实现）

L0 只暴露下面这组能力，L1 以上全部不感知实现：

```ts
type ChannelName = 'ctl' | 'events' | 'cmd' | 'blob';

interface TransportChannel {
  /** 发送一帧；resolve = 已进入发送窗口（背压语义，不表示对端已收到） */
  send(frame: Uint8Array): Promise<void>;
  onFrame(cb: (frame: Uint8Array) => void): () => void;
  close(code: number, reason: string): void;
}

interface Transport {
  readonly kind: 'relay-ws' | 'p2p-datachannel' | 'vendor-tunnel' | 'direct-listen';
  /** 出站型（relay-ws / p2p-datachannel）：PC 主动发起；不得要求用户做任何入站开放 */
  connect(identity: TransportIdentity): Promise<void>;
  /** 入站型（vendor-tunnel / direct-listen）：宿主监听一个端口。vendor-tunnel 只绑 127.0.0.1（出站由 cloudflared/frp 承担）；direct-listen 绑任意地址（Mode D）。宿主进程内本就有监听先例：会话锁命名管道，sessionLock.ts#L157 */
  listen?(opts: { port: number; bind?: 'loopback' | 'any'; ipv6First?: boolean }): Promise<void>;
  /** 入站型通用（vendor-tunnel / direct-listen）：每次连入产生一个 Transport 实例，交由 L1 跑同一套握手 */
  onAccept?(cb: (conn: Transport, peer: { addr: string; deviceId?: string }) => void): () => void;
  readonly state: 'idle' | 'connecting' | 'ready' | 'degraded' | 'closed';
  onState(cb: (s: Transport['state'], info?: { rttMs?: number; cause?: string }) => void): () => void;
  openChannel(name: ChannelName): TransportChannel;
  /** 应用层保活；必须由本层负责，不得依赖 TCP keepalive */
  ping(): Promise<number>;
}
```

四种 `kind` 按两件事分：**谁发起**、**绑在哪**。`relay-ws` / `p2p-datachannel` 是**出站客户端**（R1、R10 适用）；`vendor-tunnel` 是**回环入站**——桥只绑 `127.0.0.1`，对外的出站由 cloudflared / frp 自己承担（**R1 不破例**：本机没有对外端口）；`direct-listen` 是**公网入站**（R1 / R10 显式例外，口径见 §4.5）。L1 以上只看到"四级状态 + 四个通道 + `ping`"，不区分谁拨号、也不区分绑在哪——这是 §4.5 与 §4.6 能复用同一套握手的前提。

**必须满足的约束清单（R1–R11）**

| # | 约束 | 判据 |
|---|---|---|
| R1 | **PC 全程主动出站**，不监听任何 TCP/UDP 入站端口 | 用户零配置；P2P 打洞属例外，见 §3.4。**Mode D（§4.5）也是显式例外**：宿主监听单个高位端口。**Mode T / 自接穿透（§4.6）不算例外**——桥只绑 `127.0.0.1`，对外出站由隧道进程负责 |
| R2 | 双向帧，二进制或文本皆可（建议二进制封套 + JSON 载荷） | — |
| R3 | 单连接多路复用 ≥ 4 路（ctl/events/cmd/blob），同路严格有序、跨路无序 | 大快照不得阻塞审批帧 |
| R4 | 可靠有序（TCP-like），不丢帧；不做 UDP 语义 | 命令不可丢 |
| R5 | 断线检测 ≤ 30s（手机锁屏/切网/进电梯都要快速发现） | 应用层 `ping` **10s** 间隔、连续 3 次未回即 `degraded→closed`（10×3 = 30s，与判据一致） |
| R6 | 可恢复：重连后按水位补齐，**服务端不保存任何业务状态** | `resume { upSeq, recvSeq }`（水位定义见 §6.7） |
| R7 | 背压可观测：发送方必须能拿到"窗口满"信号，允许阻塞 `send()` | 防手机弱网把 PC 内存打爆 |
| R8 | 单帧上限（建议 256KB）+ 超限分片与重组 | 大 diff / 图片走 blob 通道分片 |
| R9 | 不要求中继解析业务载荷（E2EE 必须成立） | 中继只见密文与路由头 |
| R10 | 一个 PC 只维护 **1 条**出站连接，承载多台手机多路 | 家用路由 NAT 表友好。**Mode T 的桥没有出站**（出站由 cloudflared/frp 承担，桥只做回环入站）；**Mode D 也没有出站**：改为 N 条入站（每台设备一条），不反向拨号 |
| R11 | 冷启动可用：从 `connect()` 到 `ready` 目标 ≤ 3s（中继）/ 不设上限（P2P） | 手机点开即用 |

### 3.4 不同传输下"设计上要变的东西"

| 传输 | 契约是否变 | 必须额外设计的内容 | 主要风险 |
|---|---|---|---|
| **Relay（出站 WSS）**（默认） | 不变 | ① 房间模型 `pcId → room`，手机按 `pcId` 加入；② PC 上线/掉线 presence 广播；③ 重连后 `re-announce`（服务端连接态与设备表解耦）；④ 带宽成本与限流 | 中继可见元数据（谁连谁、帧大小时序）；中继可拒绝服务 |
| **Cloudflare Tunnel**（兜底，Mode T） | **变**：`kind: 'vendor-tunnel'` + `listen({ bind: 'loopback' })`——桥只绑 `127.0.0.1`，出站由 cloudflared 承担；**R9 被削弱** | ① 回环监听端口与本地对接（§3.3 `listen()`）；② TLS 在 CF 边缘终止 ⇒ **必须自建应用层 E2EE**（L1 不能省）；③ 域名/DNS 成为新配置面；④ `--protocol http2` 与 `quic` 必须可切换并带探活 | 域名过期、DNS 误改、边缘限速 → 手机"页面打不开" |
| **P2P 打洞**（可选加速） | 不变，但 **R1 破例** | ① 控制面（信令）仍出站，数据面需临时 UDP 监听 → 声明为"临时套接字，不做用户配置"；② ICE 候选交换、5s 超时、失败降级 TURN；③ 必须能无感回落中继 | 对称 NAT / 双 NAT / 企业网封 UDP；手机进后台被挂起 |
| **Mode D 直连**（家宽公网 IP，可选档，§4.5） | **变**：`kind` 增 `'direct-listen'`，补 `listen()` / `onAccept()`（`bind: 'any'`）；**R1 / R10 例外** | ① 宿主监听单个高位端口（默认 8443，IPv6 优先）；② DDNS 维护 `A`/`AAAA`（10–15 分钟轮询、TTL 60–120s）；③ 自签证书 + L1 指纹信任；④ 公网暴露安全档（限速/封禁、只开单端口）；⑤ IP 变更即连接失效 → 重解析重连 | 宿主直接暴露公网；依赖该机 VS Code 常驻；IP 变更后的不可用窗口 |

> **自接穿透（frp / 厂商中继，§4.6）** 走的是 Cloudflare 那一行的**同一组参数**：`kind: 'vendor-tunnel'` + `listen({ bind: 'loopback' })`，只是把 cloudflared 换成别的隧道客户端、域名换成自己的。**绑定地址是安全定位的分界线**：Mode T / 自接穿透 = 回环（R1 不破例）；Mode D = 公网（R1 显式例外 + 安全档 §4.5.5）。

> **设计取向（最重要的一条）**：L0 之上的一切（配对、协议、仲裁、投影）**不因传输变化而改**。传输差异被压缩进 `connect()` / `listen()` / `reconnect()` / `identity()` 四个方法内部。这正是"先定协议、后换传输"能执行的前提。

## 4. 传输选型（默认 / 兜底 / 排除）

> 本节价格、额度、外部限制均为 **2026-11-10** 调研值，**使用前需复核**（复核触发条件见 §12）。

### 4.1 默认：产品自带云端 Relay（面向普通用户）

```
手机 App ──WSS(443)──► Relay（香港 / 境内合规机房） ◄──WSS(443)── PC 扩展宿主
     └──────────── 应用层 Noise E2EE（端到端）────────────┘
```

**为什么是它**（按重要性排序）

1. **与 NAT 类型完全无关**：CGNAT、对称 NAT、双 NAT 都不影响，因为两端都只做出站 443 `[文档]`。
2. **普通用户唯一走得完的流程**：装 App → 登录 → 扫码。不买域名、不改路由器、不常开 VPN。
3. **隐私话术可控**：E2EE 后 Relay 是哑管道；相比 Cloudflare/ngrok 的"边缘终止 TLS、可见明文"，这是产品级差异。
4. **有同模式先例**：dsh-Go 桌面侧就是"Relay + 二维码 + E2EE"（其 Host 插件 `ds-harness-remote` + 自建账号/中继服务）：账号登录、公钥固定与 Noise IK 见 `app/lib/remote/relay/dsh_remote_backend.dart#L13-L21`；二维码登录入口见 `app/lib/remote/relay/relay_backend.dart#L128`，**扫码配对 + 8 位配对码**见同文件 `#L466-L513` `[码]`；国内 to C 远控（向日葵/ToDesk）是"账号 + 云端撮合 + 中继兜底" `[文档]`。
5. **协议一旦按 Relay 设计**（设备令牌、可切换传输、水位恢复），后续换/加传输不需要改业务层。

**代价**：把"网络可达性"变成"你要运营一个服务"。真实负担是 **7×24 可用性 + 合规**，不是机器钱。

**失败模式**

| 故障 | 用户看到 | 必须有的应对 |
|---|---|---|
| Relay 单节点宕机 | 所有手机"电脑离线"，PC 本地任务不受影响 | 第二节点；或 PC 侧切到 Mode T **并让手机重新配对**（§4.4）——已按 Mode R 绑定的手机手里没有隧道域名，**不能无感热切** |
| 香港节点晚高峰跨境抖动 | 延迟由闲时 50–100ms 升到晚高峰 100–300ms `[社区]`，出现"转圈" | 前端超时提示；不影响正确性 |
| 令牌泄露 / 撞库 | 陌生设备尝试连接 | 设备级撤销 + 短期票据 + 速率限制 |
| 合规（境外节点数据出境 / 境内备案） | — | 上线前法务确认 `[推断]` |

### 4.2 兜底：Cloudflare Tunnel（命名隧道）+ Access

- **形态**：`cloudflared` 作为 Windows 服务常驻，命名隧道指向 `127.0.0.1:PORT`，**纯出站 443**，无入站端口 `[文档]`；Access 邮箱 OTP 限制只有车主本人能进 `[文档]`。
- **成本**：Tunnel 免费；Access 免费版 50 用户 `[文档]`；唯一硬成本是域名（Cloudflare Registrar 成本价约 $7.85/年起 ≈ ¥56/年）`[文档]`。`trycloudflare` 随机域名官方明确"仅供测试" `[文档]`。
- **链路**：能穿透 CGNAT；但**免费套餐无大陆边缘节点**，流量走香港/新加坡/日本 `[文档]`；社区实测闲时 50–100ms、晚高峰 100–300ms `[社区]`。
- **必须注意的经验**：`cloudflared` 默认 QUIC/UDP，在家宽/NAS 上存在"连上又反复断线"，改 `--protocol http2` 后稳定；也有环境反过来只有 QUIC 可用 `[社区]` ⇒ **协议必须可切换 + 带连通性探活**。
- **安全**：TLS 在 CF 边缘终止，CF 可见明文 ⇒ **若要求"中继不可见内容"，必须叠加应用层 E2EE**（与 Relay 共用 L1）。
- **配对语义的局限**：Access 的邮箱验证码证明的是"你是这个邮箱"，**不是"这台 PC 是你的"**；设备级撤销能力弱（撤的是人，不是设备）。所以 Access **不能替代** §5 的设备配对，只能当外层门禁。
- **为什么只能是兜底而不是默认**：**"买域名"这一步对普通用户太重**，且与 Relay 故障域不同（Relay 挂了它还能顶，反之亦然）。

### 4.3 明确排除（含排除理由，便于半年后不再重开讨论）

| 路径 | 排除理由 |
|---|---|
| `code tunnel` 作为产品传输 | 微软标注 **dev-only**、每账号 **10 条隧道**（超出随机删旧）、带宽受限、可能断连需重启 `[文档]`；手机端只有 vscode.dev 桌面版 Web IDE，**没有自有 UI**；强依赖 GitHub 登录（国内不稳定 `[社区]`）。可保留为"开发者自救通道" |
| ngrok 免费版 | 3 端点 / **1 GB/月** / 20k 请求/月 / 域名不可定制 / 国内链路差 `[文档]`+`[社区]` |
| 纯 WebRTC 作为唯一路径 | 对称 NAT 必落 TURN ⇒ **并不能省掉服务器**，只是把中继换成 TURN；手机进后台 WebRTC 被挂起。仅适合同 LAN/打洞成功时的加速 |
| Tailscale / ZeroTier 作为普通用户默认 | 要装 App + 账号 + **常开 VPN**；iOS 中国区获取有障碍（需美区账号）`[社区]`；ZeroTier 免费仅 10 设备/1 网络 `[文档]`。可作"高级模式：我自己有 tailnet" |
| frp 作为产品中继 | 端口映射模型不适合多租户多设备；HTTP 模式下 frps 见明文；xtcp 打洞成功率官方明示"无法保证" `[文档]` |
| 公网 IPv4 + 端口映射（**作为产品默认**） | 移动宽带基本不可得；电信/联通需申请且 80/443 被封 `[社区]`；**不能当默认**——需域名 + 端口映射，违背"用户不动路由器"。用户自持公网 IP 时降级为可选档，见 §4.5 |
| 纯 IPv6 | 家宽前缀会变、路由器 IPv6 防火墙默认拦入站、蜂窝侧策略不可控 `[社区]`；只能做直连优化，不能当唯一路径 |

> 上两行排除的是**"作为产品默认传输"**。§4.5 的 **Mode D** 是"用户自己已有公网 IP、愿意自备域名与端口映射"时的**可选档**，前提与代价写在 §4.5，不改变"默认 Relay"的结论。

### 4.4 成本与规模拐点（**整表需复核**）

> 成本列均为 `[文档]` 定价页口径（2026-11-10）；"真正负担"列为人天/运维判断，属 `[推断]`。

| 阶段 | 建议 | 月成本 | 真正负担 |
|---|---|---|---|
| 内测 / 日活 <100 | **不自建**。Cloudflare Tunnel + Access；技术用户可选 Tailscale | 域名 ≈¥5/月 `[文档]` | 只需盯域名与隧道 |
| 日活 100–1,000 | 单台香港轻量（约 ¥25/月，免备案）+ Cloudflare 兜底 | ¥25–45 `[文档]` | 健康检查、日志、证书续期、一条降级开关 |
| 日活 1,000–10,000 | 双节点（香港 + 境内备案）+ 就近接入 + 监控/告警/限流 | ¥100–500 `[推断]` | 需值班与容量规划；开始有滥用处置 |
| 日活 >10,000 | 多地域 + 独立账号服务 + 合规审计 | ¥数千起 `[推断]` | 专职 SRE + 法务 |

**口径（全篇唯一说法，取代任何"先只用某种传输"的表述）**

| 场景 | 传输 | 配对方式 | 代价 |
|---|---|---|---|
| **产品默认** | Relay（§4.1） | **Mode R**：`pid` 会合（§5.2） | 需运营一个中继服务 |
| **用户自托管 Relay** | 自建 Relay（形态同 §4.1） | **Mode R**（协议不变） | 自建运维；对用户要求最高，仅高级模式 |
| **Relay 不可用 / 最小部署（技术预览）** | Cloudflare Tunnel（§4.2） | **Mode T**：隧道直连（§5.3） | 要有域名；**配对的双方必须同时在线**；换域名需重配 |
| **家宽有公网 IP（联通等，端口不限）** | **Mode D**：宿主直接监听（§4.5） | **Mode D**：域名直拨 + 一次性口令（§5.3） | 要有域名 + DDNS；**VS Code 必须常驻**；见 §4.5 安全档 |
| **用户自接穿透（frp / 厂商中继 / 自建隧道）** | 视为 **Mode T 的地址变体**：`url` 换成自己的隧道域名（§4.6） | **Mode T**：一次性口令（§5.3） | **监听能力实现一次后**，接新隧道只需填 `url`、不再改插件（首次接入隧道的契约改动见 §3.4）；须满足 §4.6.1 五条（透传、E2EE 在隧道之上、承载 WS、域名稳定、只监听回环） |

- 首发若坚持"零服务器"，只能用 Mode T：二维码里直接写 `wss://<你的域名>`，手机**拨隧道**完成首次信任。代价是**丢掉"不同时在线也能配对"**（§5.5-1）与跨网漫游体验。
- 因此**推荐首发即上 Relay 单节点**（¥25–45/月，见上表），CF Tunnel 作为降级开关；若接受上述降级，也可以 CF-only 起步。
- 无论哪种：**协议都按 Relay 架构设计**（设备令牌、E2EE、可切换传输、水位恢复）——换传输不改 L2/L3。

> 反例提醒：不要因为"现在量小"就把传输写死进业务层（例如把业务接口设计成 HTTP 端点 + 域名路径）。那样等要上 Relay 时，L2/L3 全部要重写。

### 4.5 Mode D：家宽自托管直连（公网 IP）

**定位**：PC 自己持有公网 IP，手机直接连它，**中继与隧道都不需要**。与 Mode T **协议层与 L1 握手完全复用**，差异是并列三条：① **地址来源**——DDNS 域名 + 端口映射，而非隧道分配的域名；② **方向**——宿主真开一个入站端口（R1/R10 的唯一例外，`kind:'direct-listen'`，§3.3），而 T 仍是出站客户端；③ **信任面扩大**——暴露在公网的是扩展宿主本身，不是只转发密文的中继（§4.5.5）。成本除域名外近乎零。

> 本节依据用户实测事实写入：其联通宽带**有公网 IP 且端口不限**（长期用 5890 等端口映射远程桌面，一直可用）。这**不是**普遍情况，因此 Mode D 是**可选路径**，不改变 §4.4 的默认口径。

#### 4.5.1 地址来源与动态 IP

**先分清两类量**（"IP 很少变，所以一天查一次够了"缺的就是这一步换算）：

| | 决定什么 | 该定多少 |
|---|---|---|
| **轮询（刷新）周期** | **最坏不可用时长**——IP 恰好在两次检查之间变了，就要等下一次检查才发现 | **10–15 分钟** |
| **TTL** | 变更**被发现之后**，多久传到手机 | **60–120s**，不因"IP 很少变"调大 |

检查成本极低（读一次 WAN 地址 + 比对一次 DNS 记录），所以按"天"计没有收益。换算：

> **最坏不可用 ≈ 轮询周期 + DDNS 更新延迟（秒级）+ TTL + 一台设备的一次退避（≤30s）**
> 10 分钟轮询 ⇒ 约 **12 分钟**；24 小时轮询 ⇒ 约 **24 小时**。

| 项 | 结论 |
|---|---|
| PC 侧 | DDNS 客户端每 **10–15 分钟**检查一次，**仅在变化时才更新**；记录 TTL **60–120s** |
| 变更检测优先看本地 WAN | 先读路由器 API / UPnP `GetExternalIPAddress` / 光猫状态页拿 WAN 地址，**与 DNS 现有记录比对**，不一致才调 DNS 服务商 API——避免高频打外部"查我的 IP"服务（限流/被墙/隐私） |
| 兜底检测 | 本地拿不到 WAN 地址时（路由器不开放 API），退回外部回显服务，频率同上 |
| 手机侧 | **只认域名，不认 IP**；每次重连前重新解析 |
| IP 变更后 | 现有连接必然断（对端地址失效）→ 手机重解析 → 按既有退避（1s/2s/4s…上限 30s）重连 |
| 为什么不"主动推送新地址" | 推送需要一条不依赖地址的通道——那就是中继。为省一个 DDNS 客户端而重新引入中继依赖，得不偿失 |

**手机侧 DNS 缓存坑（必须实现，不能只依赖 TTL）**：运营商/中间 DNS 不一定尊重 60s TTL，可能缓存更久（甚至按小时）。因此：

1. **首次连接失败立即强制重新解析一次**，再按既有退避重试。
2. **是否绕过本地缓存，分两段**：先做一次普通解析（便宜）；若结果与上次相同、但连接仍失败，再走一次**绕过缓存**的查询（DoH 或直连权威 NS，取决于客户端能力）——避免每次失败都打穿 DNS。
3. 连接成功即记录本次解析结果，供下次"结果没变但连不上 ⇒ 走第 2 步"判断。

**不做**：不让手机"记住旧 IP 兜底"——那会引入证书/指纹之外的第二个身份源，且家用 IP 常被运营商回收给他人。

#### 4.5.2 端口策略

- 用户实测**端口不限**（5890 这类端口长期可用），但仍**默认高位端口（如 8443）**：低位端口在部分企业网/校园网出口被拦。
- **80/443 是否被封属运营商策略**，不作为假设；不依赖 443 落地。
- 端口号**只降低扫描噪音**，安全措施不在这里（见 §4.5.5）。

#### 4.5.3 IPv6 优先

| 项 | 结论 |
|---|---|
| 现状 | 联通家宽通常分配 **/64 公网 IPv6**，**不封端口、无需映射** `[社区]` |
| 前缀变化 | 随拨号变化 → 由 DDNS 的 `AAAA` 记录解决（与 `A` 分开更新） |
| 可用性判断 | ① 能解析出 `AAAA`；② 该地址 TCP 可达 → 走 IPv6 |
| IPv4 回退 | `AAAA` 不可达 → 退回 `A` 记录（需端口映射已生效） |
| 手机在纯 IPv4 网络 | 直接用 `A`；若没做端口映射 → 判定"此网络下不可用"，提示换网络或改 Mode R |

**实现口径**：**串行回退**（不是 Happy Eyeballs 竞速）——先试 `AAAA`，2s 内未建连即切换 `A`；不做并行竞速（省电、少日志噪音）。

#### 4.5.4 证书与信任

| 项 | 结论 |
|---|---|
| 证书 | **默认自签**（签发对象是域名，不是 IP；换 IP 不影响证书生效） |
| 信任来源 | **不是 CA**，而是 Noise 指纹固定 + 首次配对核对（§5.4、§5.6） |
| TLS 的地位 | **只是外壳**（防被动嗅探/中间盒干扰），机密性与身份都在 L1 |
| `域名 + DNS-01`（可选） | 已有域名，就可以用 DNS-01 签**正规 CA 证书**；唯一收益是浏览器/PWA 不告警，**不是安全前提**（信任仍来自 L1 指纹） |
| 未知证书 | 客户端**不因此报错**、只记录；真正校验在 L1 指纹 |

#### 4.5.5 公网暴露安全档（与 R/T 的实质差异之一：信任面）

暴露在公网的是**扩展宿主本身**，不是只转发密文的中继。

| 措施 | 要求 |
|---|---|
| 只认已配对设备 | Noise IK 按**已登记公钥**发起；未配对设备握手**直接断连**（不回业务错误，避免探测） |
| 握手限速与封禁 | 同源 5 分钟内失败 ≥5 次 → 封 30 分钟；失败响应加 100–300ms 随机延迟 `[推断]` |
| 不额外开监听 | 宿主进程**只允许这一个 TCP/UDP 监听端口**（会话锁命名管道不计，它不是网络端口）；不得顺带开 HTTP 管理页/健康检查页 |
| 单端口策略 | 业务、ctl、blob 复用同一端口（L0 多路复用已保证） |
| 端口号的定位 | **仅降低扫描噪音**，安全不依赖端口保密 |
| 握手前不回敏感信息 | 响应不得含版本号、主机名、`pcId` |

> 对用户现状的一句提示：长期把**远程桌面端口**直接映射到公网，风险高于本方案（RDP 是高频爆破目标且无应用层 E2EE）。至少换高位端口 + 强口令/来源白名单；Mode D 自身还有"公钥白名单 + E2EE"两层。

#### 4.5.6 可用性硬前提

桥必须活在 **extension host 进程内**（§3.2-B1，跨进程写锁约束），而 extension host **随 VS Code 窗口关闭而停止**。所以 Mode D 的真实前提是：

> **那台机器的 VS Code 常驻运行。**

| 影响 | 说明 |
|---|---|
| 系统重启/更新/崩溃 | **不自恢复**；手机侧表现为"电脑离线" |
| 无守护 | 没有 supervisor 拉起，也没有自愈 |
| 内核运行时在进程内 | Agent 实例、ask/confirm 队列、`pendingInterjections` 全在宿主内存（§3.2-B1）——外置进程拿不到这些，没有可跑的任务 |
| 写锁是**跨进程**的 | `sessionLock` 是跨进程互斥（命名管道，见 §2-F7、§7.4）：外置进程即使愿意当写者，也会与 VS Code 窗口抢同一把锁，二者只能活一个 |

**应对选项**（按推荐度）：① **保持窗口常驻**（关闭即失联）；② **开机自启 + 自动恢复上次窗口** `[文档]`；③ **崩溃后手动恢复**（手机显示离线，回 PC 重开）；④ ~~改成独立守护进程~~——**不可行，两条独立理由**：① **拿不到内核运行时**（上表第 3 行），外置进程没有任务可跑，不是权限问题而是能力问题；② **争锁**（上表第 4 行），跨进程写锁不会因为"多一个进程"多出一个入口，只会让两个进程互斥。

> 适用人群是"有一台常开的机器、且愿意维护它"的用户；这与"产品默认 Relay"不冲突。

#### 4.5.7 用户侧自检清单（照做即可）

| # | 步骤 | 判定方式 |
|---|---|---|
| 1 | 确认 WAN IP 与出口 IP 一致 | 路由器 WAN 页显示的 IP == 在外部网络访问"查我的 IP"服务看到的 IP；一致 = 有公网 IP，不一致 = CGNAT |
| 2 | 端口映射生效 | 外部网络 `curl -v telnet://<域名>:8443` 能建立 TCP（能连上即可，不看 HTTP 状态） |
| 3 | 外部网络拨测通 | 手机关 Wi-Fi 用蜂窝连一次；能连上并完成握手 = 通过 |
| 4 | DDNS 解析正确 | `nslookup <域名>` 的 `A`/`AAAA` == 当前 WAN IP / IPv6 地址 |
| 5 | IP 变更后多久能恢复 | 手动重播号换 IP → 计时到手机重连成功；判定 **≤ 轮询周期 + DDNS 更新延迟 + TTL + 30s**（10min 轮询、≤30s 更新延迟、60s TTL ⇒ ≈12 分钟）。明显超时 = 轮询没生效或 TTL 被调大 |
| 6 | DNS 缓存不挡路 | 换 IP 很久后仍解析到旧地址 → 中间 DNS 缓存过久；确认"失败即强解析 + 必要时绕过缓存"两段已实现 |

### 4.6 第三方穿透 / 自建中继的接入要求（**任意传输都能接，插件不为每种工具写适配**）

> **结论先行**：§3.3 的 L0 契约（`connect` / `reconnect` / `identity`；**入站型另加 `listen`**——Mode T 与自接穿透绑回环、Mode D 绑公网，见 §3.3）本身就是"传输可替换"的抽象。插件**不关心**对面是隧道、中继还是直连——只要有一条能收发帧的连接到达本机端口，就走同一套握手（§5.6）与业务协议（§6）。**因此接入一种新传输不需要改插件，只需要填一个地址**（二维码里的 `url`）。

本节回答一个具体问题：**没有公网 IP 的用户，能不能自己外挂一个内网穿透工具（Cloudflare Tunnel / frp + VPS / 厂商中继）跟插件对接？**——能，不必等产品支持；成立条件是下面五条。

#### 4.6.1 接入条件（缺一不可）

| # | 条件 | 为什么 | 不满足的具体后果 |
|---|---|---|---|
| 1 | **透明透传**：只搬字节，不解密、不改帧、不做协议改写 | L1 帧端到端，中间任何改写都会让 `nonce` / `seq` 校验失败 | 隧道既卸 TLS **又解应用层**（要求装它的根证书、或当 HTTP 反代改写请求）→ E2EE 被绕过，**机密性归零**（与 §4.2 同一条） |
| 2 | **承载 WebSocket**（二进制帧、长连接、保活） | L0 跑在 WS 之上，`ping` 10s × 3 判死（§3.3-R5） | 只支持 HTTP、不支持 WS 升级 → 握手阶段就失败，且错误信息通常很误导（表现为"连不上"，而不是"不支持升级"） |
| 3 | **端到端加密在隧道之上** | Noise 握手与密钥只在 PC 与手机两端（§5.6）；隧道方即便终止 TLS 也只看到密文 | 把加密交给隧道（例如只信隧道给的 TLS）→ 隧道提供方成为新的可信第三方，§5.8"服务端不可信"的结论作废 |
| 4 | **地址稳定**：二维码下发隧道域名，域名可复用 | 手机只认二维码里的 `url`（§5.3） | 临时域名（每次重启变）→ 手机每次都得重新配对，实际不可用 |
| 5 | **目标只监听本机回环**：隧道模式下桥 `listen({ bind: 'loopback' })`，只绑 `127.0.0.1`，本机不对外开端口（§3.3；**R1 不破例**） | 对外由隧道守护进程负责，宿主不暴露 | 图省事让桥绑 `0.0.0.0`（等于 `bind: 'any'`）→ 顺手做了个没有安全档的 Mode D（§4.5.5） |

第 1、3 条成立即"**换任何穿透都安全**"——隧道只搬运密文；受隧道影响的只有可用性（第 2、4 条）与本机暴露面（第 5 条）。

#### 4.6.2 验收清单（可执行）

| # | 步骤 | 判定方式 |
|---|---|---|
| 1 | 本机回环直连 | 先用本机 WS 客户端连 `ws://127.0.0.1:<port>`，能完成 `hello` / `hello_ok` = 桥本身没问题，问题在隧道 |
| 2 | 隧道透出后从外部网络连 | 手机关 Wi-Fi 走蜂窝连 `wss://<域名>`，能完成握手 = 透传与 WS 升级均成立 |
| 3 | **连续 30 分钟空闲不掉线** | 不发业务帧挂 30min，期间 `ping`/`pong` 正常且无重连 = 隧道没把长连接当短请求（专门测"能连上、几分钟后莫名掉线"，比 §3.3-R5 的 30s 判死长得多） |
| 4 | 断网重连自动恢复 | 关蜂窝 30s 再开 → 自动 `resume` 补齐（§6.7），用户无需操作 |
| 5 | 隧道重启（域名不变）后无需重新配对 | 重启隧道进程 → 手机重连即可、**不弹配对页** = 地址稳定，且身份来自指纹而非域名 |
| 6 | 确认看不到明文业务帧 | 抓包或隧道日志里只有 TLS 密文；能读出可辨认的用户文本 / 路径 = 第 1 或第 3 条没做到 |

#### 4.6.3 安全结论（为什么不需要审计隧道实现）

信任**不来自隧道提供方**，而来自 Noise 指纹固定 + 首次配对核对（§5.4、§5.8）。所以**不必审计隧道代码**，只需确认它**不试图解密或改写**（§4.6.1 第 1 条）——这条用 §4.6.2 第 6 步就能直接验证。

#### 4.6.4 定位：相对 Mode D，隧道类是更合适的形态

| | 隧道 / 中继类（Mode R、Mode T、用户自接穿透） | Mode D（§4.5） |
|---|---|---|
| 本机监听 | **零**（宿主只出站；或只监听 `127.0.0.1` 给隧道进程） | 对公网开一个端口 |
| 谁先发起 | 宿主 / 手机主动出站 | 任何人可先来敲端口 |
| 前提 | 一个域名（走产品 Relay 时连域名都不要） | 公网 IP + 域名 + DDNS + **该机常驻** |
| 暴露面 | 只有隧道边缘 | 扩展宿主本身（§4.5.5） |

一句话：**Mode D 是在公网开一个端口等人来敲，隧道模式是本机零监听、只往外走**——前者省掉第三方，代价是把暴露面挪到自己机器上。因此：**相对 Mode D 而言**，隧道 / 中继（含 Mode R、Mode T 与本节的自接穿透）是更合适的形态；但**产品内默认仍是自带 Relay（§4.1、§4.4）**——隧道类解决的是"没有 Relay / 想自建"的场景，不是替代默认。Mode D 只适合自持公网 IP 的自用场景。

**接入方只需三件事**：起隧道并指向 `127.0.0.1:<port>` → 把域名填进二维码的 `url`（`mode:"tunnel"`，§5.3）→ 照 §4.6.2 验收。**不需要**改插件，也**不需要**为某个工具写适配层。

## 5. 配对与鉴权

### 5.1 核心模型：**按会合码 `pid`（即 `pairId`，8 位数字）会合，不按地址连接**（**仅 Mode R**）

**本节只描述 Mode R**（产品默认，走 Relay，§4.1）。它解决的是"配对时双方不在同一网络也不该失败"：配对阶段**没有任何一方需要知道对方 IP**，双方各自出站到中继，在临时房间会合。

**Mode T / Mode D 是另一条路径**（§5.3；没有 Relay 时）：手机**按域名直连**——Mode T 拨隧道分配的域名，Mode D 拨 DDNS 域名（§4.5）；不存在任何房间会合；`pid` 退化为"一次性口令"，且**要求两端同时在线**。三条路径共用同一套 L1 握手与指纹核对（§5.6），差别只在"怎么找到对方"——所以 §3 的分层与 §6 的协议都不需要分叉。

> 下称 `pid`，与 `pairId` 同义。

```
PC                                   中继                        手机
 │ ① 生成 pairId + pairSecret        │                           │
 │ ② 出站连接 + register(pairId) ───► │ ◄── ③ 扫码得 pairId+secret │
 │                                   │     出站连接 + join(pairId)│
 │ ◄──────── ④ 房间内互转密文帧 ──────► │ ────────────────────────► │
 │ ⑤ Noise IK 握手（双向身份）        │     ⑤ 同左                 │
 │ ⑥ PC 弹窗确认手机指纹 ────────────► │ ◄── ⑦ 手机显示 PC 指纹确认   │
 │ ⑧ 设备表落盘（globalState）        │     ⑧ PC 身份落盘          │
```

### 5.2 主流程（二维码 · **Mode R**，需中继）

1. PC 端命令"memora: 配对新手机"，宿主生成：`pid`（8 位数字）、`pairSecret`（32B 随机）、`pk_pc`（PC 长期身份公钥）、`pcName`（`工作区名 @ 主机名`）。
2. 向中继注册 `pid`，TTL 5 分钟（过期自动释放，防长期占用）。
3. 二维码内容 **只含会合信息**——不含 PC 或手机的地址；`relay` 只是中继入口，不是任何一端的地址：

```json
{ "v": 1, "pid": "48213905", "secret": "b64...", "relay": "wss://...", "pcFp": "AB12-CD34", "pc": "memora@DESKTOP-7K" }
```

4. 手机扫码 → 出站 `join(pid)` → 双方在房间内跑 Noise IK（`pairSecret` 作为 PSK 增强，防中继伪造房间）。
5. **双向指纹核对** → PC 端弹模态框"允许该设备？"，手机端同时显示 PC 名称与指纹。
6. 双方交换并保存对方长期公钥；PC 写 `context.secrets` + `globalState` 设备表，手机写本地 Keychain。

### 5.3 兜底流程（无二维码 / 无 Relay）

**Mode R 的手动输入**：手机选"手动输入" → 输 **8 位 `pid`** → 会合 → 双方各自显示 **4 位配对指纹**（`H(pk_pc || pk_phone)` 派生，短、仅供人工比对）→ 用户目视比对 → PC 点"允许"。

**Mode T（没有 Relay，只有 Cloudflare Tunnel，§4.4）**：

1. PC 先起隧道并**保持在线**（`cloudflared` 常驻）。
2. 二维码内容改为 `{ "v":1, "mode":"tunnel", "url":"wss://memora.example.com", "pid":"48213905", "pcFp":"AB12-CD34" }`。
3. 手机**直连**该 `wss://` → 首帧 `hello` 带 `mode:"tunnel"` + `pid`（**字段定义见 §6.2，不新增封套**）→ 双方跑同一套 Noise IK 与指纹核对 → PC 确认。
4. 与 Mode R 的差别只有两点：① `pid` 不再承担"会合"职责，而是**一次性口令**（PC 内存校验，5 分钟过期、一次即废；失败回 `err{ code:'bad_passcode', ch:'ctl' }`）；② **两端必须同时在线**，且手机必须能解析该域名。

> **短码只承担寻址职责，不承担安全职责**（Mode R 是"会合码"，Mode T / D 是一次性"口令"）。即使 `pid` 被猜到，攻击者也过不了指纹确认 + PC 侧人工批准。

**Mode D（家宽公网 IP，§4.5）**：

1. PC 监听 `8443`（IPv6 优先），DDNS 维护 `A`/`AAAA`。
2. 二维码内容与 Mode T 同构，只是 `mode` 不同、`url` 换成 DDNS 域名：`{ "v":1, "mode":"direct", "url":"wss://home.example.com:8443", "pid":"48213905", "pcFp":"AB12-CD34" }`。
3. 手机直连 → 首帧 `hello` 带 `mode:"direct"` + `pid`，握手与指纹核对**与 Mode T 完全一致**。
4. 差别只在传输侧：没有边缘节点、TLS 直落宿主（自签）、且**宿主本身在公网**（安全档见 §4.5.5）。

> 因此 `hello.mode` 取值是 **`relay`（缺省）/ `tunnel` / `direct`**——同一个字段三个值，**不新增封套、不改 17 条计数**。

### 5.4 身份与指纹（两种派生，别混用）

- `pcFp` = `SHA-256(pk_pc)` 前 8 hex，分 2 组展示（`AB12-CD34`）；`phoneFp` 同理。这是**设备指纹**：长、稳定，用于长期识别与"密钥已变化"判定。
- §5.3 的 4 位数字是**配对指纹**（`H(pk_pc || pk_phone)` 派生）：短、随配对会话变化，只用于配对当次的人工比对。两者不可互相替代。
- **首次信任即固定（SSH-like）**：后续连接只校验公钥是否与设备表一致，**不再弹窗**。
- 公钥变化（重装 App / 换机）→ PC 端要求重新配对，并提示"设备密钥已变化"。

### 5.5 三个容易被忽略的语义（本设计的关键差别）

1. **配对 ≠ 建立长连接**。配对产物是"双方公钥"，落盘即完成；**不要求当次连接成功**。这才是"不同时在线也能配对"（**仅 Mode R**；Mode T / Mode D 要求两端同时在线，见 §5.3）。
2. **（Mode R）配对后靠 `pcId` 找机器，不靠地址**。PC 每次上线向中继 `announce(pcId, roomToken)`（`pcId` 存 `globalState`，非机器指纹）；手机持有 `(pcId, pk_pc)`，冷启动查 `presence(pcId)`：在线直连，离线显示"PC 未运行"并允许订阅上线通知（中继只做 presence，不存业务数据）。
   **Mode T / Mode D 下没有 presence**：手机直接持有域名（Mode T 是隧道域名，Mode D 是 DDNS 域名）——二维码里给，`pcId` 只作设备表索引与日志标识，**不承担发现职责**；"PC 未运行"由连接失败 / 隧道 502 / 端口不通判定。
3. **（Mode R）服务端只做撮合**。中继不保存业务状态、不保存设备表；设备表在 PC 本地。
   **Mode T 下没有业务服务端**：Cloudflare 只做字节转发且 **TLS 在边缘终止**；**Mode D 连边缘都没有**，TLS 直落宿主。两者都要求 L1 E2EE 是唯一机密性来源（§3.4、§4.2、§4.5.4），这条不能省。

### 5.6 鉴权与加密边界（三层）

| 层 | 位置 | 负责 | **不负责** |
|---|---|---|---|
| 传输层 | L0（中继/隧道） | 路由、房间、连接存活 | 不解析业务内容；不做设备授权决策 |
| 加密层 | L1（宿主内实现，跑在 L0 之上） | 身份认证、E2E 机密性/完整性、防重放、会话密钥轮换 | 不判断"这台设备能否审批" |
| 业务授权层 | L3 `RemoteBridge` | 设备 ACL、权限档位、按会话授权、in-flight 仲裁、审计留痕 | 不碰密钥材料 |

### 5.7 密钥存放

| 材料 | 位置 | 理由 |
|---|---|---|
| PC 长期私钥 | **`context.secrets`（VS Code SecretStorage）** | 绝不落 `.memora` 工作区目录——否则随仓库/快照外泄 |
| 手机长期私钥 | 系统 Keychain / Keystore | — |
| 会话密钥 | 仅内存，进程退出即销毁 | 短期、可重建 |
| 设备表（`deviceId → phonePub, 权限档, 最近活跃`） | `globalState` | 可跨窗口共享；不含密钥 |
| `pcId` | `globalState` | 稳定身份，**不随会话/工作区变化**（VS Code 重装或换机时可能丢失，丢失后需重新配对） |

> 明确禁止：把任何私钥写进 `WorkspaceSessionStore` / Round 落盘路径 / 日志。

### 5.8 "服务端不可信"时还能保住什么

**保得住**
- 消息机密性与完整性（E2E：中继只见密文帧；密钥协商不经过中继明文）。
- 身份不可冒充（指纹核对 + 首次信任固定；**Mode R** 下中继伪造房间还会被 PSK 识破）。
- 重放防护（每帧 `nonce` + 单调 `seq`；L3 校验 `nonce` 单调且未使用过）。
- 授权不被绕过（ACL 与权限档只在 PC 侧判定，手机无法自授权）。

**保不住（必须写进产品文案与威胁模型）**
- **元数据**：谁连谁、连接时长、帧大小与时序、活跃时段。
- **可用性**：中继可断连、限速、拒绝服务；P2P 下运营商可干扰。
- **发现阶段的引导**：中继可把手机导向错误房间 → 靠指纹核对兜底，但用户必须真的看一眼指纹。（Mode T 下对应风险换成：域名或 DNS 被劫持、隧道域名过期 → 同样只靠指纹核对兜底。）
- **首次配对的一次性秘密**：**仅 Mode R** 存在 `pairSecret`（放在二维码里、当 Noise IK 的 PSK）→ 二维码被拍照截取时攻击者可参与会合，但**仍需 PC 侧人工确认**才能完成配对。
  **Mode T / Mode D 的二维码不含 `secret`**（§5.3），首次信任由两件事共同保证：① `pid` 作为**一次性口令**，PC 内存校验、5 分钟过期、一次即废；② 双向指纹核对 + PC 侧人工批准。缺任何一项都不能完成配对。
  > **结论（不留"可选"）**：**Mode D 复用一次性口令 + 指纹核对 + PC 人工批准**，与 Mode T 完全同构；**不采用"仅指纹核对"**——Mode D 的握手端点直接暴露在公网，任何人可触发，没有口令就等于把"能否发起握手"交给扫描器（配合 §4.5.5 的限速，才谈得上可控）。

### 5.9 权限档位（默认最小）

| 档位 | 能做什么 | 默认 |
|---|---|---|
| `observe` | 看会话列表、看轮次/过程/状态 | 配对后默认 |
| `send` | 发消息、插话、暂停/停止 | 需 PC 端勾选 |
| `approve` | 答复**执行类审批**（命令执行 / 脚本与代码执行 / guest 模式写入，见 F13）、答复 ask 提问 | **默认关闭**，单独开关 |

审批默认关闭的理由：`confirmCoordinator` 是 fail-closed 设计（**30 分钟超时自动拒绝**，`confirmCoordinator.ts#L5-L20`），说明审批是安全边界，不应因"手机方便"默认放开。

> ⚠️ **ask 与 confirm 的超时语义相反**：`askCoordinator` 30 分钟超时是**自动继续**（LLM 代选，无副作用，`hosts/memora-vscode/src/extension/host/askCoordinator.ts#L11-L19`），`confirmCoordinator` 30 分钟超时是**自动拒绝**。两者时长相同但**是两个独立常量、两种相反终态**——实现方不得合并处理（合并 = 把审批变成 fail-open，安全模型反转）。

**撤销**：设备表删条目 → 立即断该 device 的 channel + 拒绝其 nonce。手机侧密钥不删，但会被永久拒绝。

## 6. 业务协议（L2）

### 6.1 帧封套

```jsonc
// ctl 握手 · Mode R（产品默认）：不带 mode / pid
{ "t": "hello", "ch": "ctl", "v": 1, "deviceId": "...", "nonce": "...", "phoneFp": "AB12-CD34" }

// ctl 握手 · Mode T（§5.3）：多带 mode + 一次性口令 pid
{ "t": "hello", "ch": "ctl", "v": 1, "deviceId": "...", "nonce": "...", "phoneFp": "AB12-CD34",
  "mode": "tunnel", "pid": "48213905" }

// ctl 握手 · Mode D（§4.5）：形态与上一帧完全同构，只有 mode 取值不同
{ "t": "hello", "ch": "ctl", "v": 1, "deviceId": "...", "nonce": "...", "phoneFp": "AB12-CD34",
  "mode": "direct", "pid": "48213905" }

{ "t": "evt", "ch": "events", "seq": 41, "sid": "20261110-abc", "kind": "delta", "p": { /* 载荷 */ } }
{ "t": "cmd", "ch": "cmd",    "rid": "u-7",  "sid": "20261110-abc", "kind": "send",  "p": { "text": "..." } }
{ "t": "attention", "ch": "events", "sid": "20261110-abc", "kind": "confirm" }
{ "t": "ack", "ch": "events", "seq": 41 }          // ↑ 手机确认 PC 的下行
{ "t": "err", "ch": "cmd", "rid": "u-7", "code": "stale_phase", "msg": "回答已失效" }  // ↓，ch 必带
```

- `seq`：**每会话单调递增**，`seq=0` 表示快照。用于补洞。
- `rid`：上行请求 id，回执与错误按 `rid` 关联。
- `sid`：会话定址，**所有业务帧必须带**。
- `ch`：`ctl` 帧可省；`ack` / `err` **必带 `ch`**，标明"针对哪条通道的 seq / rid"，并走该通道回发（§6.5）。
- `hello.mode` / `hello.pid`：**直连型传输专用**字段。`mode` **三取值：`relay`（缺省）/ `tunnel` / `direct`**——Mode R 两个字段都省略（等价 `relay`），Mode T 带 `tunnel`，Mode D 带 `direct`；`pid` 在两种直连下都是一次性口令。属**字段扩展，不新增封套类型**，故 §6.5 计数不受影响。

### 6.2 ctl 通道

| 方向 | `t` | 消息 | 说明 |
|---|---|---|---|
| ↑ | `hello` | `hello { v, deviceId, nonce, phoneFp, mode?, pid? }` | 连接后第一帧；`mode` 三取值：省略 = Mode R，`"tunnel"` = Mode T（§5.3），`"direct"` = Mode D（§4.5）；后两者必须带一次性口令 `pid` |
| ↓ | `hello_ok` | `hello_ok { serverTime, pcId, caps[], limits{ maxFrame, credit } }` | `caps` 用于能力协商（判定规则见 §6.8）；`pid` 校验失败回 `err{ code:'bad_passcode', ch:'ctl' }` |
| ↓ | `reset_required` | `reset_required { sid }` | 水位不可补（判定见 §6.7 第 2 分支）→ 手机重拉 `snapshot` |
| ↑ / ↓ | `ping` / `pong` | 无载荷 | 应用层保活（10s 间隔，3 次未回判死，见 §3.3-R5） |
| ↓ | `host_state` | `host_state { online, windows[] }` | 多窗口时告知有几台"主机"（§8-P1-8） |
| ↑ | `resume` | `resume { upSeq, recvSeq }` | 重连后按水位补齐（命名见 §6.7） |
| ↓ | `resume_ok` | `resume_ok { fromSeq, headSeq }` | 可回放：`fromSeq = sentSeq + 1`，回放到 `headSeq` 为止（§6.7） |
| ↑ | `sub` / `unsub` | `sub { sid }` / `unsub { sid }` | 按会话订阅（**仅上行**，下行用 `err` 或 `snapshot` 回应） |
| ↑ | `ack` | `ack { seq, ch }` | **手机确认 PC 的下行**（背压 credit 回收），故为上行 |

> 其余 `t`（`evt` / `cmd` / `attention` / `blob_get` / `blob_data`）见 §6.5 的分组表；`err` 也见 §6.5（**它必带 `ch`，随 `ch` 走**），本节只列控制面。

**错误码（`err.code`）——`err` 的唯一枚举来源**

| `code` | 含义 | 触发条件 | 带 `ch` | 手机端处理 |
|---|---|---|---|---|
| `bad_passcode` | Mode T / Mode D 一次性口令无效 | `hello.pid` 过期 / 已用过 / 与 PC 内存不符 | `ctl` | 回到配对页，重新扫码或索取新口令 |
| `no_session` | 会话不存在或未装配 Agent | `sid` 不在 `_sessionAgents`，或是草稿态（§6.6 断路器） | `cmd` | 刷新 `session_list`，关闭该详情页 |
| `stale_phase` | 相位已变，本次输入失效 | `answer` / `resume` 到达时相位已不是其期望值（§7.2） | `cmd` | 立即重拉该会话 `snapshot`，提示"状态已更新" |
| `already_resumed` | 重复解暂停 | 会话已不在 `waiting(pause)` | `cmd` | **当成功处理**（幂等），不提示错误 |
| `busy` | 会话正在跑，不接受新 turn | `send` 到达时 `_turnState` 为 `running` / `waiting`（**相位层面**拒绝，与设备无关） | `cmd` | 置灰输入或转 `interject`；提示"正在运行" |
| `in_flight` | 同一会话的发送窗口被占 | 该 `sid` 已有在途 `send`（`sendInFlight`，§7.3），**即使相位 idle**（**仲裁层面**拒绝，含 PC 占用） | `cmd` | 显示 `holder`："PC 正在发送 / 另一台手机正在发送"；可重试 |

> `busy` 与 `in_flight` 的边界：**`busy` 看相位（这台机器能不能接新 turn），`in_flight` 看仲裁（谁先拿到这个 turn）**。前者重试也没用（要等本轮结束），后者等窗口释放即可重试。两者可以同时成立，此时**先回 `in_flight`**（更具体的持有者信息优先）。

### 6.5 封套类型（`t`，共 17 条）

按职责分三组（`snapshot`/`delta` **不在本表**，它们是 `t:"evt"` 的 `kind`）：

| 组 | `t` 取值 | 数量 | 走哪条通道 |
|---|---|---|---|
| 控制帧 | `hello` `hello_ok` `resume` `resume_ok` `reset_required` `host_state` | 6 | `ctl` |
| 通道/生命周期 | `ping` `pong` `ack` `err` `sub` `unsub` | 6 | `ctl`；**`ack` / `err` 必带 `ch`，随 `ch` 通道回发** |
| 业务载荷 | `evt` `cmd` `attention` `blob_get` `blob_data` | 5 | `events`（`evt` / `attention`）/ `cmd` / `blob` |

- `evt.kind` ∈ `snapshot` `delta`；`delta.p.kind` ∈ `append_text` `process_event` `tool_pending` `plan` `status` `settled`
- `cmd.kind` ∈ `send` `interject` `answer` `resume` `pause` `stop` `confirm_answer` `remove_pending_item` `clear_pending_queue`

**计数口径**：17 = 6 + 6 + 5。**不含** `evt.kind` / `cmd.kind` 的业务取值（那是封套内的第二层分派），也不含复用现有 DTO 的字段级结构。Mode T 的 `hello.mode`/`hello.pid`、Mode D 的 `mode:"direct"` 都是**字段扩展**、不新增封套，故三条路径共用同一组 17 条。原 `resume_required` 已删除——它与 `reset_required` 是同一个动作的两种叫法（都只能重拉快照），保留会让实现方以为存在"半恢复"路径。

> ⚠️ 一处同名不同层：`t:"resume"`（ctl 帧，重连水位恢复）≠ `t:"cmd", kind:"resume"`（业务命令，解暂停）。同理 `t:"ack"` 与 `cmd` 的回执靠 `rid` 关联、不是一个东西。

其中 **`attention { sid, kind: 'ask' | 'confirm' | 'settled' | 'error' }` 是真实语义缺口**：webview 只在打开时可见，没有"提醒"概念（现有仅 `onConfirmShown` 的本地通知钩子，`confirmCoordinator.ts#L38-L45`）。**MVP 只用它做前台/应用内提醒**；系统级推送（APNs/FCM）列为后续阶段（§11.1）。

### 6.7 增量 vs 快照，与断线补洞

- **快照**：`sub` 成功后立刻发一次 `snapshot`，`seq` 归零重建（等价现有 `replay:true` 语义，`protocol.ts#L1824-L1825`）。
- **增量**：之后只发 `delta`；文本流按 200–300ms 合并（避免每个 token 一帧）。
- **三处水位命名（先对齐名字，再谈补洞）**

  | 名字 | 谁维护 | 含义 |
  |---|---|---|
  | `recvSeq` | 手机 | 手机**已收到**的最后一个下行 `seq` |
  | `upSeq` | 手机 | 手机**已发出**的上行序号（对应 `rid` 递增） |
  | `sentSeq` | PC（每设备一份，§6.8） | PC **已发给该设备**的最后一个 `seq` |

- **补洞责任在 PC**（R6：中继不存业务状态）：L3 每会话保留最近 **500 条 delta 或 2MB**（先到为准）。手机重连后发 `resume { upSeq, recvSeq }`；PC 用自己那份 `sentSeq` 判定，**`recvSeq` 只作参考、不被信任**：
  1. **窗口内（成功）**：回 `resume_ok { fromSeq, headSeq }`，其中 **`fromSeq = sentSeq + 1`**（PC 侧该设备水位 +1），`headSeq` = PC 当前 head。随后从 `fromSeq` 顺序回放到 **`headSeq`**（**这是终止条件**），再转为常规 delta 推送。手机收到 `resume_ok` **不得重置 `seq`**，按回放帧递增，收到 `headSeq` 即视为对齐。
  2. **不可补（失败）**：满足任一即回 `reset_required { sid }` —— ① `recvSeq > sentSeq`（手机水位超前，必然错乱）；② `sentSeq - recvSeq > 500`；③ 缺失段已出 2MB 窗口；④ 该 `sid` 已被回收/重建（`seq` 谱系变了）。手机收到后重拉 `snapshot`（`seq` 归零重建）。
  3. **超时无应答**（手机侧 5s 内未收到 `resume_ok` 也未收到 `reset_required`）：手机按失败处理，直接重拉 `snapshot`。
  
  > 注意 `downSeq` 这个名字**已废弃**：它在旧稿里同时指"手机接收水位"和"PC 侧每设备水位"，是歧义源。现在手机侧叫 `recvSeq`，PC 侧叫 `sentSeq`，回放区间是 `[fromSeq, headSeq]`。
- **不可丢帧**：`confirm` / `confirm_closed` / `settled` / `error` 提升为"重要帧"，不进降采样与丢弃策略。

### 6.8 多设备订阅同一会话

- `RemoteBridge.subscribers: Map<sid, Map<deviceId, { sentSeq, credit }>>`（`sentSeq` = PC 已发给该设备的最后 `seq`，§6.7）。
- 事件 → 广播给该 `sid` 的所有订阅者；**每个设备独立水位与独立 `reset_required` 判定**。
- 能力协商：`hello_ok.caps` 决定是否下发 `process_event` 明细（低端机可只收 `status` + 文本）。
- 背压：每设备每会话独立 credit；窗口满时**先合并/降采样 `process_event`，绝不丢 `confirm`/`settled`**；持续满 → 发 `degraded` 提示并断开该设备（保护 PC 内存）。

### 6.9 大载荷（blob 通道）

- 触发：审批 diff 全文、图片附件。**diff 只可能出现在 `guest 模式写入` 类审批**——命令执行 / 脚本与代码执行恒 `hasDiff=false`（`protocol.ts#L1773-L1777`：判据归内核 `hasDiff` 单点，"命令/代码/脚本执行三类恒 false"）。owner 模式写文件已不触发审批（§2-F13）。
- 流程：下行只给 `{ hasDiff: true, diffRef }`（`hasDiff` 已是内核单点判据，`protocol.ts#L1774-L1778`）→ 手机 `blob_get { ref }` → 宿主从本地读、按 64KB 分片回 `blob_data`。

### 7.2 规则表

| 相位 | PC | 手机 | 冲突解法 |
|---|---|---|---|
| `idle` | 可发 | 可发（`send` 权限） | 先到先得；后到者回 `err{ in_flight, holder }`（§7.3），绝不并发起两个 turn。注意这里**不是 `busy`**——相位允许发送，只是发送窗口被占 |
| `running` | 可插话 / 暂停 / 停止 | 同 | 插话共享内核队列（SSOT `loop.pendingInterjections`，见 §2-F11），两端看到同一份 `pendingQueue`。此处 `send` 一律回 `err{ busy }`——新任务要等本轮结束，插话必须走 `interject` |
| `waiting(ask)` | 可答 | 可答（`approve` 权限） | 第一个合法 `answer` 生效；后到者回 `err{ stale_phase }`，并把最新相位推回 |
| `waiting(pause)` | 可 resume | 可 resume | 幂等：第二个 `resume` 回 `already_resumed` |
| 审批 pending | 可批 | 视 `approve` | 第一个决定生效；另一侧立即收到 `confirm_closed`（复用 `#L1792`） |
| 未 `sub` 的会话（手机端"列表页"状态） | — | 只能看 `session_list_data` 摘要，不能收发 | 订阅（`sub { sid }`）= 手机进入该会话详情页；不订阅就没有 `events` 流，因此也发不出去（§6.6 断路器要求 `sid` 已装配） |

### 7.3 发送 in-flight 令牌（防双发包）

```
sendInFlight: Map<sid, { deviceId, rid, ts }>
```

- 进入 `handleInput` 前置位，settle / 报错 / 超时（30s）后释放。
- 冲突时回 `err{ code:'in_flight', holder:'pc'|'phone' }`，手机端 UI 直接显示"PC 正在发送"。
- 这不是新的一致性机制，只是把内核已有的"一会话一写者"在**进程内**再表达一次，避免两个入口抢同一 turn。

### 7.4 写锁的角色（为什么多端一致性没变成灾难）

`sessionLock` 是**跨进程**互斥（见 §2-F7），保证"多窗口/多 VS Code 实例不会同时写同一会话"。手机端**不参与锁**，因为它不是写者——它只是把命令投递给持有锁的那个宿主进程（§3.2-B1）。这是本设计能绕开"多端并发写"最脏部分的原因。

#### 风险与坑（结合本仓实际，不是通用建议）

- **guard 的 filter 是按包名写死的**（`esbuild.config.mjs#L189` 只匹配 `^@zooique/memora$`）：包名一改，守卫对旧包名仍生效、对新包名完全不管。协议包本身零依赖、允许值导入，所以**不能**简单把新包也塞进 filter——要么在 filter 旁写清"新包为何不拦"，要么改成"拦内核 + 显式放行协议包"两条规则。
- **`max-lines` 的 glob 是 `src/**/*.ts`**：包建在 `packages/` 下就**不受任何闸约束**（`chatPanel.ts` 那种 4242 行的逐文件阈值同理不覆盖）。必须显式加 override，否则等于悄悄取消了这条门禁。
- **`dist/shared/protocol.js` 是 tsc 直出、不打包**（`esbuild.config.mjs#L12`）：包化后这个产物消失，任何按该路径引用的调试/加载习惯会断，需在提交说明里点出。
- **`module: Node16` + `exports`**：包的 `exports` 必须同时给 `types` / `import`；源码内的相对导入必须带 `.js` 扩展名（本仓已在用 `./settingsTabs.js` 这种写法，照抄即可）。
- **"类型只 import 不 export"的摇树陷阱**：34 个类型名会被 esbuild 整段擦除；但 `PRESET_SEARCH_ENGINES` / `MCP_TRANSPORTS` 是**值**，若被误写成 `import type`，运行时拿到 `undefined`——**不报编译错**，只会表现为下拉框空掉。
- **循环依赖**：协议包 `import type` 内核是单向的今天；必须把方向写死为"**内核永不 import 协议**"，否则 tsc 可能过、esbuild 会报循环，且 `dist` 中出现顺序依赖。
- **`watch` 不重建包**：`npm run watch` 只跑 `tsc -watch -p ./`，不构建 `packages/protocol`；改协议字段后 webview 侧会用到旧 `d.ts`。开发期需额外开一条包的 watch。

### 硬约束：宿主生命周期边界与 headless 演进路径

> **一句话结论**：桥活在 extension host 进程内（§3.2-B1），**进程生命周期 = VS Code 窗口生命周期**。所以"打开 VS Code 就能一直远程控制"**不成立**；成立的版本是"**窗口开着（可最小化）就能远程控制**"。这不是已知限制，是硬约束——写在这里是为了避免半年后有人按文档做完才发现"电脑重启后就连不上"。

#### 六条边界（每条给"为什么"与"手机侧表现"）

| # | 边界 | 为什么 | 手机侧表现 / 对策 |
|---|---|---|---|
| 1 | **懒激活** | 扩展按 `activationEvents` 启动；侧栏从没被点开时 `activate()` 根本没跑，桥不存在 | 手机连不连得上取决于"用户有没有点过侧栏"。**对策**：必须申请 `onStartupFinished`（或等价事件），否则不能宣称"打开即监听" |
| 2 | **窗口即进程** | extension host 随窗口生死；Windows 上关掉最后一个窗口 = VS Code 退出，**没有"最小化到托盘继续服务"** | 关窗口即离线。可用形态只有"窗口开着、可以最小化" |
| 3 | **宿主会被重启** | 扩展更新、宿主未捕获异常、VS Code 自身更新，都会重启 extension host：端口释放、连接断开、需重新握手 | 表现为"突然掉线"，而且**原因不可自证**（用户无法区分是断网、宿主重启还是插件崩了）。**对策**：手机端必须有明确的"主机离线"态，不能一直转圈 |
| 4 | **系统休眠 / 锁屏** | 网络栈挂起 → TCP 静默失效；若重连依赖定时器，休眠期间定时器不推进 | 唤醒后可能长时间显示"在线"但发不出帧。**对策**：唤醒后**立即探测一次**，不等 §3.3-R5 的 30s 判死周期 |
| 5 | **工作区信任（Workspace Trust）** | 未受信任的文件夹限制扩展能力，桥可能不启动或只读 | 不是 bug，是平台策略。**对策**：UI 明确告知"该工作区未受信任"，不允许静默失败 |
| 6 | **多窗口 = 多宿主** | 每个 VS Code 窗口一个独立 extension host，各有 Agent 注册表与会话集合；同一个端口只能被一个进程占用 | 手机连到哪个窗口，就**只看到该工作区的会话**——这是设计后果，不是缺陷（另见 §9.2 多窗口聚合不做）。**对策**：定义选举规则，见下表第 4 条 |

#### 四条"必做"（把"可能"变成"事实"）

| # | 必做 | 不做会怎样 | 是否属 MVP |
|---|---|---|---|
| 1 | **开机即激活**（`onStartupFinished`） | 手机能否连上取决于用户点没点侧栏——"有时能连有时不能" | **是**（自用可用的最低要求） |
| 2 | **开机自启 VS Code + 自动打开固定工作区** | 系统重启后桥压根不存在；表现为"重启后再也连不上" | **是**（同上；没有它，第 1 条也无意义） |
| 3 | **崩溃 / 更新后的自恢复**（系统计划任务检查并拉起；或至少手机明确显示"主机离线"） | 手机一直转圈，用户误判为"插件坏了" | **自恢复不进 MVP**；但"离线态可见、不假装在线"**必须进 MVP** |
| 4 | **多窗口唯一服务端规则**（建议：首个持锁窗口当服务端，其余不启桥；或在配置里显式指定某个工作区） | 端口冲突 / 两个宿主都自认该服务，手机连到哪个看运气 | MVP 只需"单窗口假设"；多窗口选举列入 P1（与 P1-8 `hostId` 一起做） |

> 与 §4.5.6 的关系：那里讲的是 Mode D 的"该机必须常驻"，本节讲的是**所有模式共有的**生命周期天花板；两者共同的结论是"不能简单改成一个独立守护进程"，推导见 §4.5.6，本节不重复。

#### headless 演进路径（长期答案，但不是本方案的增量改造）

**事实依据（`[码]`）**：内核 `src/` 是**纯 Node 库**——`src/index.ts#L1-L3` 自述"通用 Agent 纯逻辑库（Node.js，零 native 依赖）… 宿主项目通过本入口 import 接入；持久化/搜索/会话等宿主能力均经接口注入"；`src/index.ts` 导出面共 **79 条**（`#L11` 的 `Agent` 只是第一条，也是**唯一运行时入口类**；另有 `AGENT_CONSTANTS` `#L24`、`createNodeSqliteStorage` `#L134`、`RolePackManager` 等少量运行时值，其余是类型与端口接口）；其中"宿主实现、注入进来"的端口类型 10 个：`ISessionStore`（`#L199-L205`）、`IRoundStore`（`#L211`）、`IMemoryStorage`（`#L129`）、`ISessionViewLoader`（`#L231`）、`IWebSearchProvider`（`#L141`）、`IFetchProvider`（`#L158`）、`ICodeExecutionProvider`（`#L165-L169`）、`IProjectSearchProvider`（`#L179-L187`）、`IEnvironmentProvider`（`#L175`）、`ILogger`（`#L265`）。**VS Code 只是第一个宿主**，所以"第三个宿主"（headless 常驻进程 + 同一套内核 + 同一个 L0/L1/L2/L3 桥）在概念上已经成立，且不受窗口生命周期约束。

**但三条障碍是真实的，别写成"包一层 CLI"**：

| # | 障碍 | 具体含义 |
|---|---|---|
| ① | **端口要自己实现** | headless 宿主得把上表那批注入端口全部实现（会话/轮次存储、搜索、抓取、代码执行、项目搜索、环境上报、日志）。VS Code 侧的这些实现就在 `hosts/memora-vscode/src/extension/host/`，但只有纯逻辑能搬，落盘路径/权限/进程模型都得重做。**工作量在"实现端口"，不在"加个 main"** |
| ② | **写锁互斥** | 写锁是**跨进程**的（§7.4、§2-F7）：headless 与 VS Code 宿主同时开，必然互斥。只能"二选一"，或"**headless 为主、VS Code 降为客户端**"——后者等于重排现有 UI 的地位 |
| ③ | **UI 资产要重做** | webview 与审批相位机在 headless 下不存在，得重新提供前端——等于把 §10 的客户端选型提前，且不再是"可选" |

**结论**：**当前方案的天花板是"窗口得开着"**。自用场景（电脑常开 + VS Code 常开）完全够；要以"面向他人的产品"交付，必须走 headless 宿主，而那是**新增一个宿主形态**，不是本方案的增量改造。

**补一条既有文档没写死的边界（2026-11-12）**：**跨进程写锁使"旁挂一个 headless 桥、同时服务 VS Code"不可行。** 写锁是跨进程的（`sessionLock.ts#L38` 的 `CrossProcessSessionLock`，互斥落点是 `#L182` 的 `server.listen(address)`，见 §7.4），headless 进程一旦要往某个会话写（发消息 / 答审批 / 插话），就会与 VS Code 宿主对这个会话的写锁互斥；而"只读旁挂"又满足不了上行的三条命令。可行的只有两种：① 桥活在 VS Code 进程内（本方案，天花板 = 窗口必须开着）；② headless 成为**唯一写者**、VS Code 降级为客户端（换宿主形态，不是增量）。不存在"两个进程都能写、只是分工不同"的第三种。

## 9. MVP 验收口径

### 9.1 验收集合（"能看到 + 能发一句话 + 能答审批"）

> **验收一律按 Mode R（产品默认，走 Relay）**。Mode T 只做设计有效性确认（§5.3 的四步），**不纳入本轮 MVP 验收**；否则"两端必须同时在线"会把验收变成一项额外的人为约束。
>
> **Mode D 也不纳入 MVP 验收**：它依赖用户侧网络（公网 IP / IPv6、端口未被封）与"该机 VS Code 常驻"（§4.5.6），两者都不可复现。Mode D 的验收单列在 §4.5.7 自检清单，由用户在自己的网络上照做。

1. PC 打开 VS Code + memora，「手机」入口显示 `未连接 / 已连接 N 台`。
2. 点"配对新手机" → 二维码 + 8 位短码；**手机输短码可配对成功**（不要求同网）。
3. 手机看到会话列表：标题、是否在跑、待审批数。
4. 进入会话 → 看到轮次（用户消息 / 助手文本 / 工具步骤折叠 / 状态条），**PC 没在看的后台会话也能看**。
5. 发送一句话 → **若该会话正是 PC 当前显示的会话**，PC 侧栏同步出现该轮（同走 `handleInput` → 同一 webview 投递路径）；若该会话在 PC 侧是后台会话，则 **PC 侧栏不跟随**（§3.2-B3：桥不改 PC 焦点），只在手机侧 `events` 流可见。
6. 后端触发**命令执行类审批**（例如让助手跑一条 shell 命令）→ 手机弹审批卡（工具名 + 命令/路径摘要 + 允许/拒绝，**不含 diff 全文**）→ 手机批准 → PC 侧卡片同步消失。**注意**：写文件（owner 模式）按现码**不触发审批**（§2-F13），拿它做验收会一直等不到卡片。
7. 断网 30s 后重连 → 自动 `resume` 补齐窗口内 delta；超窗自动重拉快照，状态不错乱。
8. PC 关闭窗口 → 手机显示"主机离线"，可订阅上线通知。

### 9.2 明确不做（MVP）

草稿同步、引用/技能/图片上传、设置与记忆面板、多 PC 同时在线、后台推送（只做前台 + 应用内提醒）、语音输入、多窗口聚合、多人协作、**headless 常驻宿主**（第三个宿主形态，见 §8「headless 演进路径」——它是长期解法，不属于本轮增量）。

### 9.3 分期

> **已归档口径**：本节 M0–M4 的分期已被 §9.4 的 S0–S5 **取代**（排序以 §9.4 为准）。此表保留，只为记录当时的切分理由与验收点（尤其「M1 是架构风险验收点」这条判断仍成立）。**不要再按 M 阶段排期**——两套并行排序会让"现在做到哪"无法回答。

| 阶段 | 内容 | 独立可验证 |
|---|---|---|
| M0 | Transport + 配对 + echo bridge | 跨网配对成功、断线重连、背压不崩 |
| M1 | 只读订阅（`snapshot`+`delta`+`attention`） | 手机能看到**后台会话**在跑 |
| M2 | 上行（`send`/`interject`/`pause`/`stop`） | 手机发一句，PC 同步 |
| M3 | 审批（双投递 + `confirm_answer` + ACL） | 手机上批一个**命令执行类**审批（写文件不触发，见 §2-F13） |
| M4 | 仲裁与多设备（in-flight 令牌、多设备水位、错误码） | 两台手机 + PC 同时操作不出错 |

> **M1 是架构风险的验收点**：如果 P0-1/P0-3 没做，M1 必然只能看到 PC 当前会话——这时要停下来补 P0，不要用"手机自动跟随 PC 会话"糊过去。

### 9.4 阶段划分 S0→S5（2026-11-12 · 取代 M0-M4 作为**排序**口径，验收集合仍用 §9.1）

> **两条线共享同一批前置，不要重复立项**：手机遥控与「路由主助手」（[评估-子会话](./评估-子会话与目标模式路线-20261108.md) §13）都只依赖三件事——**① 会话定址**（任意 sid 可寻址）、**② 后台会话可投影**（§7.1 B1/B2）、**③ 审批可跨会话答复**（§7.1 B3）。三件事各自只做一次；两个消费者各自消费。因此 `REMOTE-R0-1` 落地的两件（投影纯函数 / 按会话应答）同时是路由线的 S0/S1 前置。

| 阶段 | 内容 | 独立可验证 | 依赖 |
|---|---|---|---|
| **S0** | **多会话可见**：任意 sid 的投影可算（`deriveSessionProjection`）+ 会话列表亮「在跑 / 待审批 / 待答」 | PC 侧不切会话也能看到后台会话状态 | 无传输（纯宿主内） |
| **S1** | **会话可寻址**：按 sid 发消息 / 插话 / 暂停 / 恢复 / 答提问（`answerFor` + ask 桥层路由） | 脚本或面板对指定 sid 发一条命令，落到该会话 | S0 |
| **S2** | **路由闭环**：主助手派发 → 子会话完成 → 主助手新 turn 自动汇报 | 一句话 → 建会话 → 派任务 → 自动汇总，不靠用户追问 | S1 + 路由工具面 |
| **S3** | **手机只读回环 / 局域网**：手机看会话与轮次（`listen` 仅回环 / 局域网档，绑定地址可配） | 同机或同网手机看到实时轮次 | S0 + 宿主监听能力 |
| **S4** | **跨网**：Mode R / T / D 任一档打通（**具体档位待 §17 拍板**） | 不同网络下配对 + 断线重连 | S3 + 配对/鉴权 |
| **S5** | **手机上行为主场景**：审批、作答、派发在手机完成 | 一天不用 PC 也能推进任务 | S2 + S4 |

**与既有文档排序的两处差异（都带理由，不是口味）**：

1. **既有 §9.3 把整条线押在 Relay 上**（M0 = Transport + 配对 + echo bridge，§9.1 又要求「验收一律按 Mode R」）。问题：**自用场景不该把运营云服务前置**——配对与中继是成本最高、最不容易自测的一段，而 S0/S1/S2 完全不需要它。S 阶段把「宿主内可见 / 可寻址 / 路由闭环」放到传输之前，跑通后再决定传输档位。
2. **S1 阶段不得对外宣称「路由可用」**。S1 只做到「有工具、能派活」，**没有汇报闭环**——主助手只能派、不会说，用户不问就永远不知道子会话结束了。路由这个词对外只属于 S2；S1 的对外说法是「会话可寻址」。

## 10. 客户端选型：决策规则（不是结论）

### 10.1 三条候选

> 本节是**历史候选清单**（不是架构约束）。其中 **A / B 已否决**——AGPL-3.0 的传染性与 memora 的 MIT 不兼容，**不需要看其他理由**（§10.5 决策记录）；保留在表里只为说明"曾经评估过什么、为什么出局"。真正参与 spike 的只有 **C 系路线**（自建窄原生/PWA，或复用 MIT 底座如 T3 移动端）。

| 候选 | 复用度 | 代价 |
|---|---|---|
| **A. 改造 dsh-Go**（**已否决，见 §10.5**：AGPL-3.0 传染性） | 传输/加密层可照搬（`DshCarrier` = **3 个核心方法** `call`/`openLink`/`close` + **6 个成员** `kind`/`hostVersion`/`tracer`/`supportsUplink`/`allowsEndpoint`/`peerCapabilities`，`packages/dsh_client/lib/src/carrier.dart#L34-L75` `[码]`）；聊天 UI 可复用；**语义需重写**（端点白名单**实测 99 条**，其中 `terminal/*` **10 条**，`packages/dsh_remote/lib/src/carrier/tunnel_carrier.dart#L22-L123` `[码]`；DSH 事件词表 `models.dart#L1344-L1468`） | 大量 DSH 面板会因端点缺失而空转；改造成本与"DshClient 能力面被裁剪"长期共存 |
| **B. fork dsh-Go 界面，只保留聊天屏**（**已否决，见 §10.5**：同上） | UI 骨架/滚动/输入可留；把所有 DSH 端点调用替换为 memora 的 `cmd`/`events` | 要删掉半套应用；但对齐成本低于 A |
| **C. 从零写窄原生端（或极简 PWA，或复用 MIT 底座）** | 复用度最低（若复用底座则为中） | 只实现"列表 + 聊天 + 审批"三屏，最容易验收、最容易长期维护 |

### 10.2 决策规则：**1–2 天 spike，6 个端点能否在不改 UI 的前提下对接**

> **适用范围**：本节只用于 **C 系路线**。**A / B 已出局**（AGPL，§10.5），不再参与判据；spike 主体是 **T3 移动端**（§10.5），失败则退窄壳或换底座。

| 步骤 | 判据 |
|---|---|
| ① **先定协议（§6），再选客户端** | 协议未定就选客户端 = 被客户端框架牵着走 |
| ② 在候选客户端（当前是 T3 移动端）里加一层适配，只实现 6 个端点：`session/list`、`session/prompt`、`session/follow`、`session/cancel`、`userQuestions/answer`、`$events` 握手；其余回 `METHOD_NOT_ALLOWED` | 能否**编译通过**，且**不修改它的传输层与状态层** |
| ③ 连上 Relay，跑通"列会话 → 发一句 → 看到回复" | 能否**转起来**（不要求 UI 全绿） |
| ④ 记录 UI 断裂面（哪些屏/按钮不可用、要改多少个文件） | 断裂面 ≤ 聊天屏且 UI 改动 ≤ 15 文件 → 底座可用（T3）；跨多个主导航 → 退窄壳（C）；> 一半功能不可用 → 换底座或从零写 |

**时间盒**：spike 超过 2 天仍未"转起来"→ 判失败，不要在底座上继续投入。
**为什么这条规则能判**：候选底座的耦合点集中在"端点语义 + 传输/状态抽象"；只要能降级、且不用改它的传输层，剩下的就是删屏与换数据源，成本可线性预估。反过来，一旦必须改它的传输层（如 Effect 的 stream 语义），成本就是不可估的——这正是 §10.5 的第一条推翻判据。

### 10.3 一个已排掉的选项（防止重开）

**不要把 memora 做成 DSH 插件来白拿手机端。** memora 内部已评估并缓行（见 `docs/方案-dsh-Cordis原生插件-20261016.md` 的"当前不投"结论），且已有"与 VS Code 宿主双开时静默覆盖丢失"的实证风险。那是"另一个产品形态"，不是"手机版"。

### 10.4 仓库结构与协议边界（手机端是否独立仓、两个仓库怎么连）

> **结论**：现阶段**不拆仓**。手机端作为 `clients/mobile` 进主仓，与内核、VS Code 宿主并列；真正需要"共享"的不是代码，而是**协议**——把协议提成 `packages/protocol`，两端都依赖它，这就是唯一的连接点。

**现状对照（`[码]`，2026-11-12 核对——与下面的目标结构有偏差，先摆出来）**

| 项 | 现状 | 与目标结构的差 |
|---|---|---|
| 仓库形态 | 单包 `@zooique/memora` v6.0.0（`package.json`），**没有** `pnpm-workspace.yaml` | 目标需要 workspace，`packages/protocol` 才能被三方同时引用 |
| 内核 | `src/`（纯 Node）。`src/index.ts` 导出面 **79 条**：`#L11` 的 `Agent` 是**唯一运行时入口类**，另有点少量运行时值（`AGENT_CONSTANTS` `#L24`、`createNodeSqliteStorage` `#L134`、`RolePackManager`）+ 大量类型与 **10 个注入端口接口** | 不需要动 |
| 宿主 | `hosts/memora-vscode`、`hosts/memora-mcp`；两者对内核的写法是 `"@zooique/memora": "file:../.."`（`hosts/memora-vscode/package.json#L433`、`hosts/memora-mcp/package.json#L45`） | 这是现成的"同仓互引"先例，`packages/protocol` 可照抄 `file:` 写法 |
| 协议定义 | 目前位于 `hosts/memora-vscode/src/shared/protocol.ts`（扩展与 webview 共用） | 需**上提**为 `packages/protocol`；不上提，手机端只能复制一份 |
| `packages/`、`clients/` | **两者都不存在** | 均为新增目录 |

**1｜判断标准先行**：两端真正需要共享的只有**协议**（17 条封套 + DTO，§6.5），不是代码。内核 `src/` 是纯 Node（`src/index.ts#L1-L3`），React Native 跑不了；宿主 webview 是 DOM，手机也用不上；`vscode` 模块更是只有 VS Code 宿主能 import。所以"连接两个仓库"的实质是**让两端引用同一份协议定义**。

**2｜推荐结构（现阶段不拆仓）**

```
memora/
├─ packages/protocol/        # 纯类型 + schema + 版本常量，零运行时依赖
├─ src/                      # 内核（Node）
├─ hosts/memora-vscode/      # VS Code 宿主
├─ hosts/memora-mcp/         # MCP 宿主（已存在）
└─ clients/mobile/           # 手机端（Expo RN）
```

`packages/protocol` 是唯一被三方依赖的包，硬约束：**不 import 内核的值、不 import RN、不 import `vscode`**（只允许 zod 这类零运行时依赖的校验库）。

> **实测例外（`[码]`）**：允许对内核 `import type`——`protocol.ts` 现在就有 9 个内核 DTO 的类型引用（`@zooique/memora`：`ArchiveMode` / `BackgroundTask` / `ImageRef` / `InteractiveInputKind` / `ProcessEvent` / `Round` / `RoundMessage` / `RoundStatus` / `StrategyKeyFace`），编译期擦除、不进 bundle。**禁止的是值导入**。若把类型也切断，只能把这 9 个 DTO 在协议包里重造——那才是真正的漂移源。

**3｜现在不拆的理由**：协议还在动——同仓里改一个字段，两端当场编译报红；拆仓后用任何工具都换不回这个反馈速度。拆仓的唯一收益是"发布节奏解耦"，当前没有该需求。

**4｜三条纪律（比目录结构更重要）**

- **绝不复制 `protocol.ts`**：出现第二份拷贝必然静默漂移——编译能过，运行时字段对不上；
- **schema 与类型同源**：用 zod 等定义一次并推导类型，两端共用同一份校验器（而不是"一边手写 interface、一边手写 validator"）；
- **契约测试用同一批 golden fixture**：至少三个——正常 turn、带 diff 的审批、超时后状态；宿主侧断言"产出 == fixture"，手机侧断言"fixture 能解析"。**这是将来拆仓后唯一还能拦住漂移的东西**，所以现在就要有。

**5｜什么时候才拆（出现任一即可）**

| 信号 | 具体判据 |
|---|---|
| 手机端需单独发版 / 灰度 | App Store 审核周期 vs 插件周更，两边节奏开始互卡 |
| 客户端 CI 拖慢主仓 | Expo/EAS 与 vsix 是两套工具链，主仓 CI 时长明显上升 |
| 出现维护者分工 | 有人只负责手机端，主仓 review 成为瓶颈 |

**6｜拆了之后怎么连（三选一，明确推荐一种，不要混用）**

| 方式 | 写法 | 评价 |
|---|---|---|
| **协议发包（推荐）** | 发 npm（或私有 registry），双方 `^1.x` | 改协议 = 发版 + 两端各升一次；有版本记录、有兼容回归 |
| git 依赖 | `github:you/memora#protocol-v1.2.0` | 省去维护包，但装依赖慢，且无法表达 peer 兼容范围 |
| submodule（**不推荐**） | — | 常见事故：在 submodule 内改完提交、忘了更新主仓指针，两边指向不同 commit |

**7｜版本协商**：`hello` 已有 `v`（§6.2）。建议补 `minSupported`（对端最低可接受版本），并采用"**服务端支持 N-1**"策略，目标是"手机没升级也能连，只是看不到新功能"，而不是硬失败。这是 `hello` 的**字段扩展**（§6.5 计数不变）；现在加几乎零成本，拆仓后再加要改两端 + 发版。

**8｜反例（要写清"为什么错"）**

- **不要把手机端放进 `hosts/memora-vscode/`**：`hosts/` 的语义是"内核的宿主实现"，而手机端是同一内核的**远程客户端**，自己不跑内核；塞进去会让人以为它要嵌 Node 运行时。
- **不要让手机端依赖 `src/`（Node 内核）**：RN 里没有 `node:fs` / `node:net`，连 `import` 都过不了。
- **底座 fork 的摆放**：若采用 T3 Code 作为底（MIT `[社区]`，动工前复核许可证），**只 vendored 三个目录到 `clients/mobile`**——`apps/mobile`、`contracts`、`client-runtime`（与 §10.5 一致），并记录**上游仓库 + commit SHA + 已改文件清单**；不要整仓 fork——那会陷入它的 monorepo / Effect-TS 日更，最后变成养 fork 债；vendored 单目录在升级时可定向 diff。

**9｜命名理由**：`clients/mobile` 优于 `apps/mobile`——将来若做 headless 宿主（§8），那个才是第三个"宿主"，而手机始终是"客户端"。名字定对，后面能少一轮讨论。

**10｜许可证前提**：memora 是 MIT（`LICENSE` 首行 `MIT License`、`package.json` 的 `"license": "MIT"`），因此 **AGPL / GPL 底座不可用**；MIT / Apache-2.0 底座可安全 vendored。这条与 §10.1 的候选评估同时适用——候选若带 AGPL 传染性，直接出局，不再做 spike。

> 与既有章节的分工：`hello.v` 的字段语义在 §6.2，本节不重复；"手机端不是宿主、不跑内核"与 §8 的宿主生命周期无关（手机端**没有**宿主生命周期问题，它只是客户端）。

### 10.5 决策记录：为什么放弃 dsh-Go、为什么选 T3 移动端

> 这是**决策记录**，不是优缺点清单。写下"当时为什么这么选、什么情况下应该推翻"，目的是半年后不要重开同一场讨论。
>
> 本节出现的 `T3 移动端` / `Happy` / `assistant-ui` 是 §10.1 三候选**之外**的具体底座与备选分支（即在 §10.2 spike 之后的去处），**不是第四/第五候选**——§10.1 是"形态"层面的历史清单，本节是"具体底座"层面的决策。

#### 放弃 dsh-Go 的真实原因（按权重排序）

| 权重 | 原因 | 依据 |
|---|---|---|
| ① | **许可证不可用**：memora 是 MIT，dsh-Go 是 **AGPL-3.0** | `[码]` `E:\zooique\dsh-Go\LICENSE` 首行即 AGPL-3.0；memora `package.json#license: MIT`。AGPL 的传染性会直接污染插件分发，这一条足以单独否决，不需要再看其他 |
| ② | **语义层是 DSH 专有**：改造成 memora 的 session/turn/round 等于重写数据层 | `[码]` 端点白名单 **99** 条、`terminal/*` 占 10（§10.1）；事件词表是 `turn/step/tool/approval`（`models.dart#L1344-L1468`）。memora 的边界是 `session/turn/round` + 审批相位机（§6.3）——两张表没有交集，映射层会变成"第二个协议" |
| ③ | **它的核心价值我们不需要**：价值在 proot 运行时与 DSH 桌面桥 | 本方案的手机端不跑内核、只需要"连到 PC 那一端"（§3.2-B1）；proot 与桌面桥在这里是纯负债（体积、权限模型、崩溃面） |

**但它是我们最好的"形态参考"**：界面组织（会话列表 → 流式消息 → 工具卡折叠）、审批卡的三态（待批 / 已批 / 已拒）、以及扫码配对的双向握手流程，都值得直接抄交互。**可以参考，不能当底座**——这两件事必须分开说，否则下一个人会重新论证一遍"AGPL 能不能用"。

#### 选 T3 移动端的理由

- **数据模型同构**：它的 `thread / turn / tool-call` 与我们的 `session / turn / round` 是同一套形状，映射是字段级而非语义级；
- **需求覆盖**：对照 §9.1 的 8 条验收口径，约 5 条已有产品级实现（会话列表、流式会话流、工具调用折叠展示、审批卡交互、断线重连 UI）；余下需自建的集中在 PC 侧语义（焦点不跟随、主机关闭后的"离线"态）`[推断，需 spike 逐条核对]`；
- **许可证干净**：MIT，可 vendored（§10.4 第 10 条）；
- **仍在维护**：2026-11-11 仍日更 `[社区]`——这既是理由也是风险（见下）；
- **一套代码覆盖两端**：iOS + Android 单代码库，符合"自用优先、不做两套原生"的取舍。

#### 代价与不确定项（诚实写）

| 项 | 说明 |
|---|---|
| **monorepo + Effect-TS 日更** | 上游迭代快 = 我们的 diff 会快速变大。**因此只 vendored 三个目录**：`apps/mobile`、`contracts`、`client-runtime`（§10.4 第 8 条），绝不整仓 fork |
| **diff 展示与附件的完成度** | 是否逐屏做了"带 diff 的审批卡"、附件上传流是否完整——**未核实**，`[推断]` 阶段。这是它能否覆盖 §9.1 第 2 条的关键 |
| **补洞语义要读代码** | 我们的 `resume` 是水位补齐（§6.7），它的重连是"拉最新"。两者能否在不改 UI 的前提下对齐，必须读它的同步代码才能判断 |
| **Effect-TS 学习成本** | 改动越深越受它的抽象约束；"只改 UI 层"这个前提一旦破了，成本会跳变 |

#### 决策何时应被推翻（判据，不是"视情况"）

| 触发条件 | 结论 |
|---|---|
| spike 发现**它的传输层与我们的帧模型无法在不改 UI 的前提下对接**（例如它把重连写死在 Effect 层的 stream 语义里，无法插入 `resume` 水位） | 放弃它，回到"自建 RN 壳 + 只复用协议"（协议已独立成包，成本可控） |
| 对接需要改动 **UI 层超过 15 个文件、或跨 3 个以上主导航屏** | 说明"同构"是假象，`vendored` 会变成"改写上游"，直接止损 |
| 产品决定**只要 iOS/Android 原生体验**（不要跨端一致、不接受 RN 的一致性折中） | 转 **Happy** 原生路线 |
| 产品决定**做 WebView / PWA 壳**（PC 侧直接复用现有 webview 资产） | 转 **assistant-ui**（Web 形态更顺，且 §10.4 的协议包可直接复用） |

> 三条判据都在 spike 阶段可判定，不需要等到开发中期。**15 个文件 / 3 个主导航屏**是建议阈值，团队可按实际规模调整，但必须是一个数字，不能是"改动较大"。

## 11. 风险与未决问题

### 11.1 风险登记

| 风险 | 等级 | 缓解 |
|---|---|---|
| 中继成为单点（可用性/隐私） | 高 | E2EE 必选；支持自建 Relay（仍 Mode R）；Relay 挂时 PC 侧切 Mode T **需手机重新配对**（不能热切，§4.1） |
| 宿主生命周期天花板（窗口必须开着） | 高 | **所有模式共有**：六条边界 + 四条必做见 §8「硬约束」；Mode D 语境下更严重（无守护可退），其应对见 §4.5.6。长期解法是 headless 宿主（§8），但属新增宿主形态、不进 MVP（§9.2） |
| 宿主直接暴露公网（Mode D） | 高 | 缓解见 §4.5.5（公钥白名单 / 握手限速封禁 / 只开单端口）与 §5.8（一次性口令 + 指纹 + PC 人工批准）；暴露面高于中继，故不纳入 MVP 验收（§9.1） |
| 手机端触发 draft flush 抢焦点 | 高 | L3 强制 `sid` 校验 + 禁止 `isDraft` 路径 |
| 后台会话看不到（复用 `post()`） | 高 | P0-1/P0-3 必须先落地 |
| 全量快照打爆手机流量 | 中 | 裁剪 + delta + 合并窗口 |
| 双端同时发送产生两个 turn | 中 | in-flight 令牌 + 内核 `isBusy` 守卫 |
| 审批误触 | 中 | `approve` 默认关；只暴露执行类审批（写文件不触发，§2-F13）；不含 diff 全文；confirm 30 分钟超时**自动拒绝**（ask 则是自动继续，§5.9） |
| 中继可见元数据 | 中 | 文案披露；支持自建；可选帧长填充 |
| 多窗口连错主机 | 低 | `hostId` + 主机列表（P1-8） |
| 手机后台被系统挂起（长连接不可常驻） | 中 | **MVP 只保证前台**：回到前台立即重连 + 应用内提醒（`attention` 帧，§6.5）；系统级推送（APNs/FCM）**列为后续阶段**，不进 MVP（iOS 挂起、FCM 国内受限 `[文档]`，见 §9.2） |

### 11.2 未决问题（接手人需要先回答）

1. **账号体系要不要做？** Relay 需要"你是谁"，但 memora 目前没有账号。最小可行是"设备令牌 + 配对码"（无账号），代价是换手机要重新配对。
2. **Relay 归属**：产品方自建 / 用户自托管 / 两者都支持？影响协议里"服务端地址是否可配置"。
3. **审批在手机上怎么呈现**：只给"允许/拒绝"够不够？要不要 diff 摘要？（P1-6 的边界）
4. **多 PC 何时支持**：MVP 不做，但协议里 `pcId` 已预留——需确认沙盒/工作区维度是否进列表。
5. **端到端加密选型**：Noise IK（成熟参考实现：Rust `snow`、C `noise-c`、JS `noise-handshake`，`[文档]`）还是自研 X25519+AEAD？前者省事但引入依赖。
6. **合规**：面向公众商业运营时，境内节点 ICP 备案、境外节点数据出境需法务确认 `[推断]`。

## 13. 一页速查

- **可行性**：有条件可行；边界 = 看任务 + 发一句 + 答审批。
- **三条硬边界**：桥在宿主内、桥不复用 `post()`、桥不改 PC 焦点。
- **传输**：默认自带 Relay（WSS 出站 + E2EE）；兜底 Cloudflare Tunnel（+自建 E2EE）；**Mode D** 家宽有公网 IP 时宿主直接监听单端口（+同一套 E2EE）；P2P 仅加速。
- **传输可替换**：L0 只要求"一条能收发帧的连接"——**任意传输都能接**（自接隧道如 frp / 自建中继，就是 `mode:"tunnel"` 的 `url` 变体；**监听能力实现一次后**接新隧道只需填 `url`，不再改插件，首次接入的契约改动见 §3.4；桥只 `listen({ bind:'loopback' })`，§3.3），前提是**透传 + E2EE 在隧道之上**；临时域名、只支持 HTTP、要求装根证书的都不满足（§4.6）。
- **为什么不能"用户自己搞"**：普通用户不买域名、不动路由器、不常开 VPN。**Mode D 是这条的例外**——用户自备域名与端口映射，故只作为可选档而非默认（§4.5）。
- **配对**：三种模式共用同一套 L1 握手与指纹核对。**Mode R**（默认）`pid`（= `pairId`）会合、跨网、**可不同时在线**；**Mode T**（兜底）手机按域名直拨隧道、`pid` 为一次性口令、**两端必须同时在线**；**Mode D** 手机按 DDNS 域名直拨宿主、二维码 `mode:"direct"`、握手与 Mode T 同构（§5.3）。
- **Mode D 三前提（缺一不可）**：① 有公网 IP（IPv6 /64 或 IPv4，端口未被封）；② 一个域名 + DDNS **10–15 分钟**轮询、TTL 60–120s（最坏不可用 ≈ 轮询 + 更新延迟 + TTL + ≤30s 退避 ≈ 12 分钟）；③ 该机 **VS Code 常驻**（桥在扩展宿主进程内，无守护进程，§4.5.6）。
- **协议**：上行复用现有 `kind`，下行复用现有 DTO；封套新增 **17 条 `t`**（ctl 6 + 通道 6 + 载荷 5；`snapshot`/`delta` 是 `evt.kind`，**不计入**这 17 条）；`turn_update` 必须裁剪，`attachmentUris` 必须换 blob。
- **补洞**：中继不存状态 ⇒ 补洞责任在 PC，500 条/2MB 窗口；`recvSeq`（手机）/ `sentSeq`（PC 每设备）两个名字不要混用，回放区间 `[fromSeq, headSeq]`。
- **先改什么**：**P0-0 + P0 五条**（协议上提为前置，§8）；P0 = per-session 状态、`handleInput` 定址、投影可复用、审批双投递、附件解耦。
- **客户端**：协议先定；1–2 天 spike 判 **C 系底座可用性**（**A/B 已否决**：AGPL，§10.5），判据是"6 端点能否在不改 UI 的前提下对接"（§10.2）。
- **路由（2026-11-11 探索，见 §14）**：路由主助手只带会话管理工具；手机端不新增封套、不新增确认步。**决策与端无关，呈现按端裁剪**。会话层方案子会话可单独停；只有 v1 `delegate_task` 才是「只能停整轮」。
- **别做**：投屏、第二写者、DSH 插件换手机端、草稿同步、设置面板。

## 14. 路由回执与取消（手机作为消费方的约束，2026-11-11 探索 · 第二版）

> **定位**：本节只写手机端作为「派发结果」的消费方受什么约束。路由契约真源 = [评估-子会话与目标模式路线-20261108.md](./评估-子会话与目标模式路线-20261108.md) §13。本节自成结论，不需要先读那份。
> **第二版（同日）**：路由形态改为「主助手只带会话管理工具，执行全部下放给独立会话」（会话层方案）。本版订正两条：①「不做设备感知」→ 决策不分端、**呈现分端**；②「只能停整轮」→ 只适用于 v1 `delegate_task`，会话层方案子会话可单独停。
> **结论先行**：不新增封套、不新增确认步；回执复用 `attention`；**决策不分端，呈现按端裁剪**。

### 14.1 决策与呈现的二分（本版最重要）

- **决策与端无关**：同一句话、同样的上下文与会话列表状态 → 同一个路由结果。路由决策**不读设备信息**，否则同一句话在 PC 和手机上结果不同，不可解释、不可复现。
- **呈现按端裁剪**：同一份结果，桌面给完整卡片，手机给一句话 + 可展开。裁剪只作用在呈现层，**不回流契约、不写回存储、不产生第二份数据**（投影函数带 detail 参数，同一数据源）。
- 一句话：**分端的是像素，不是逻辑。**

手机必须保留 / 可以省的字段：

| 字段 | 手机 | 理由 |
| --- | --- | --- |
| 结论首句（完整一句话） | **必须保留** | 用户在地铁上只看这一句；截断要截在句末，不能截成半句 |
| 四态（完成 / 未完成 / 中断 / 失败） | **必须保留** | 决定用户下一步：继续等、重派、还是放弃 |
| 是否还能追问 / 会话是否还活着 | **必须保留** | 决定「能不能再发一句」；死会话上发消息是假操作 |
| 待审批数 | **必须保留** | 可操作项，不能折叠掉 |
| 摘录全文（800 字） | 可省 | 展开时按 `caps` 拉，不默认下发 |
| 执行耗时 | 可省 | 诊断信息，手机不需要 |
| 任务全文 | 可省，留标题/摘要 | 派发内容在子会话里能看 |
| capabilities 明细 | 可折叠 | 安全信息，需要时可查 |

### 14.2 手机看到的是「会话列表」，不是「路由结果」

会话层方案下主助手与子会话都是普通会话，手机的控制面就是会话列表：

- 列表按父子归组：主助手 → 子会话（可折叠）。
- 每项显示状态（running / waiting / settled / failed）与待审批数。
- 进入任一子会话可读它的历史（同一份投影，P0-3）。
- 手机不需要知道「路由」这个概念；它只知道有哪些会话、各自什么状态。这是会话层方案相对 v1 的最大简化。

### 14.3 回执形态（不新增帧）

| 场景 | 复用 | 说明 |
| --- | --- | --- |
| 一句话结论 | `attention { kind:'settled' }`（§6.5）+ 正文首段 | `settled` 已有，不新增 `kind` |
| 可展开明细 | `evt.delta.process_event` | 是否下发由 `hello_ok.caps`（§6.8）决定 |
| 失败 | `attention { kind:'error' }` + `LlmErrorCategory` | 分类已有，不新造错误词表 |

- **不新增 `attention.kind = 'dispatch'`**：派发不是新语义，只是 `settled` 的一个原因。
- **不在封套加「派发了几个」字段**：计数由宿主生成文案时算，不动协议面。
- **低端机看不到派发明细是有意降级**：`caps` 不允许时只收 `status`；用户看到「本轮完成」，看不到「派了 2 个子会话」。这是能力协商结果，不是缺陷。

### 14.4 人工确认（会话层方案下这条变硬了）

- v1 子 agent 只读，所以「不因用了子 agent 而确认」成立。**会话层方案子会话是普通会话，能写盘、能跑命令，确认必须真的能上屏。**
- 后台子会话的确认卡当前只推前台 ⇒ 不上屏 ⇒ 永不计时 ⇒ 子会话永久阻塞。**这是会话层方案的硬前置（P0-4），不是可选优化。**
- 审批卡必须显示**来源会话**（哪个子会话、要批什么），否则用户不知道批给谁；不允许只显示「某个任务需要确认」。
- 手机端的审批入口放在会话列表（待审批数）+ 会话详情（具体卡片），不新增「路由审批」帧。
- 不设「长任务确认阈值」：没有可靠耗时度量，设了就是拍脑袋。

### 14.5 取消（订正：会话层方案可单停子会话）

| 操作 | 效果 | 手机文案 |
| --- | --- | --- |
| 停某个子会话 | 只停该会话的当前 turn，其它会话不受影响 | 「停止这个子会话」 |
| 停主助手 | **只停主助手自己的 turn；子会话继续跑** | 「停止主助手本轮（子会话继续运行）」 |
| 停止全部 | 当前没有这个命令 | 不显示；若要做，单独立项 |

- **订正**：v1 `delegate_task` 的「stop 杀整轮、pause 无效」只适用于同步递归。会话层方案每会话是独立 Agent、有独立控制器，所以「单独停一个子会话」成立。
- **反直觉点必须写进 UI**：用户点主助手的「停止」，直觉是「全停了」，实际子会话还在跑。这是会话层方案最容易出事的地方——必须在按钮文案或二次提示里说清「只停主助手」。
- **不做级联停止**，两条理由：① 停止语义会变模糊——用户点停止，是想停当前这一个、停这一批、还是全停？按钮只有一个，级联停止把明确的「停当前」变成需要猜的「停到哪一层」；② 级联停止要求主助手在线才能执行，而「按住停止」必须是本地立刻生效的动作，不能依赖某个 agent 恰好还活着。
- `interject` 只对目标会话有效；对子会话插话不会影响主助手，反之亦然。

### 14.6 通知粒度（会话变多后，通知必须收敛）

- **子会话需要审批** → 推（可操作、且它在阻塞）。
- **子会话失败** → 推（可操作：重派或放弃）。
- **主助手汇总完成** → 推（一句话结论）。
- **子会话正常完成** → **不推**。否则 N 个子会话就是 N 条通知，主助手随后那条汇总反而被淹没。
- **不推步骤**：`process_event` 明细按 `caps` 降采样（§6.8），不是通知内容。
- 依据：§6.5 已写明 `attention` 是真实语义缺口，MVP 只做前台/应用内；§11.1 系统级推送列后续。

### 14.7 明确不做

| 项 | 原因 |
| --- | --- |
| 路由选择器 / 执行体下拉 | 决策不分端；纠正靠主助手一句话 |
| `attention.kind = 'dispatch'` | 与 `settled` 重复，造成两个完成出口 |
| 封套加「派发了 N 个」字段 | 文案生成侧可算，不必动协议面 |
| 手机端确认「要不要用子 agent」 | 实现细节，不是用户决策 |
| 级联停止（一个按钮停全部） | 新批量语义，无真实需求 |
| 手机推送每个子会话的完成 | 通知风暴，且主助手会汇总 |

### 14.8 与契约文档的关系

- 契约（形态 / A-B-C / 工具面 / 最小改动集）真源 = [评估-子会话与目标模式路线-20261108.md](./评估-子会话与目标模式路线-20261108.md) §13。
- 若两份文字冲突：**契约看 §13，手机端表现看本节**；不设第三个真相源。

## 15. PC 侧 UI 结论（2026-11-12 · **判断，不是取证**）

**一句话**：PC 侧能做的所有形式都是**管理台**，不是**使用界面**；真正的使用界面在手机上。

| 形态 | 定性 | 理由 |
|---|---|---|
| 侧边栏常驻面板 | 管理台 | 挤占聊天区；手机在用时 PC 用户通常不在电脑前 |
| 独立 `WebviewPanel` | 管理台 | 适合低频高信息量（配对 / 设备 / 权限 / 审计），不适合日常"看一眼任务跑哪了" |
| 状态栏一行 | 管理台 | 信息密度低但**常驻可见**，是"PC 端还开着"的唯一低成本提示 |
| 树视图（新 `TreeDataProvider`） | **不做** | 会构成**第二套会话列表**：同一份会话在 chat 面板与树视图各渲染一次，任何"先改哪边"都是 SSOT 违例 |

**推荐组合（一个都不多）**：
1. **状态栏一行常驻状态**：`已连接 N 台 / 待审批 K`，点击 = 打开命令面板动作项；
2. **命令面板承载全部动作**（配对、断开、复制配对码、切换权限档、打开管理面板）——不新增视图容器；
3. **独立 `WebviewPanel` 承载低频配置**：配对 / 设备列表 / 权限档 / 审计流水；
4. **会话总览并入 chat 面板**（列表项后缀 + 活动标识），**不新增第二个列表**；
5. **通知只用于三类一次性事件**：① 配对成功 / 失败；② 主机离线 → 恢复在线；③ 审批超时被 fail-closed 拒绝（通知里给"去哪里看"）。**周期性状态一律走状态栏**，不发通知。

> 为什么这五条是"判断"：仓库里没有手机端的任何 UI 取证，本节来自"PC 端不应与手机抢主界面"的取舍。待真机迭代后回填实测。

## 16. 网络入站端口开放（B 组 · 2026-11-12）

### 16.1 结论

1. **socket 留在宿主，内核零改动。** 内核现有公开方法已足够承载全部远端动作：`Agent#chat`（`src/agent/agent.ts#L550`）、`#interject`（`#L1013`）、`#requestPause`（`#L903`）、`#resumeExecution`（`#L701`）、`#answerQuestion`（`#L1136`）。内核事件流也已具备（宿主侧已在消费 `roundSummaryGenerated` / `memoryAdded` 等，见 `chatPanel.ts#L3069`、`#L3551`）。
2. **入站端口是现有设计里风险最高、也必须最后做的一条。** 现有默认形态是 **PC 全出站、不监听**（§3.3-R1；现状佐证 §2-F2：全仓唯一 `listen` 是会话锁命名管道，无任何本地 HTTP/WS 服务）。
3. **仓库既有取向可引**：`hosts/memora-mcp/src/server.ts#L4-L8` 明确写「stdio 而不是 HTTP……不需要额外端口、不需要鉴权隧道」——同一取向：**能不加端口就不加**。

### 16.2 安全缺口（逐条，缺一条就不能开）

| # | 缺口 | 现状 | 补齐要求 |
|---|---|---|---|
| G1 | 无绑定地址配置 | 无任何监听能力 | 默认 `127.0.0.1`；局域网档必须显式开启并显示当前绑定地址 |
| G2 | 无设备身份与配对 | 无设备表、无公钥固定 | 配对白名单（设备公钥 + 指纹），首次信任**必须 PC 侧人工批准** |
| G3 | 无 TLS | — | 直连档必须 TLS（或等价 E2EE）；回环档可豁免但不得对外宣称"安全" |
| G4 | 无失败限流 | — | 按来源 IP + 设备维度失败计数、指数退避、临时封禁与 TTL |
| G5 | 无可回溯审计 | — | **追加式**审计（只 append，不就地改写），落 `globalStorage`，**不写 `.memora`**（避免污染用户数据目录与 git 仓库） |

**另两条硬前置**：① 工作区未受信任 → **拒绝入站**或只读（不得静默降级）；② 监听失败（端口占用 / 权限）→ **显式报错并保持未监听态**，禁止"失败了但 UI 显示已连接"。

### 16.3 宿主改动分级

> **命名说明（2026-11-12）**：本表**不用** `P0/P1/P2` —— 那套符号属于 §8 的「客户端/宿主前提」分级，两套同名不同义会让"§8 P0-1"与本节 P0 无法区分。本节改用**纯文字档位**（必做档 / 可后补档 / 不做档），不引入新前缀，读者无需额外记忆映射。

| 档位 | 项 | 说明 |
|---|---|---|
| **必做档（不改就做不了）** | ① 绑定地址配置；② 配对白名单与设备表；③ 权限三档（只读 / 可答 / 可发）；④ 失败限流与 TTL；⑤ 追加式审计（`globalStorage`）；⑥ 监听失败显式报错 | 六项缺一不可 |
| **可后补档（但要在首发前登记）** | ① 多设备并发上限；② 审计导出；③ 设备撤销与重配；④ 主机离线通知订阅 | 不影响第一条命令跑通 |
| **不做档（明确不做）** | ① 远端改设置 / 记忆 / 技能；② 远端新建 / 删除 / fork 会话；③ 草稿同步 | 与"遥控输入区"目标无关，且各有独立落盘校验面 |

### 16.4 契约三层与三条硬约束

**三层**：`L0 transport`（socket / TLS / 配对）→ `L1 帧`（`ctl` 握手 + 业务封套，见 §6）→ `L2 路由`（`cmd.kind` → 宿主既入口）。三层各自可单测，**不跨层直接调**。

**三条硬约束（越界 = 方案作废）**：

1. **桥不调 webview 专用输入入口与 `post()`**：`chatPanel.post()` 是"当前显示会话"的渲染出口（`#L2368`），桥调用它会污染前台；`handleInput` 的 webview 分支同理。桥只调**会话 API**（按 sid）。
2. **桥不 `switch_session`**：切会话是用户意图，不是远程命令的副作用。桥要么按 sid 直接寻址，要么拒绝——不得"先切过去再发"。
3. **桥不得绕过相位裁决直调内核**：仍走 §7.2 规则表与 `remoteCommandPolicy` 真值表；错误码只用固定集合（`REMOTE_COMMAND_CODES`，禁自造字符串）。

## 17. 产品取舍（**待用户拍板** · 2026-11-12）

> 以下每一条都**没有**默认答案。写成"待拍板"而不是"建议"，是为了避免半年后有人把某一行当成已定方案。

| # | 取舍项 | 选项 | 影响 |
|---|---|---|---|
| D1 | **远程能力默认开不开、默认权限档** | 默认关 / 默认只读 / 默认可答；三档权限默认值 | 默认关 = 最安全但用户要手动开；默认可答 = 开箱可用但审批面扩大 |
| D2 | **鉴权形态** | 一次性口令 + 指纹 / 仅指纹 / 设备证书 | 前两者无 TLS 依赖；证书形态最稳但配对成本最高 |
| D3 | **是否为自用功能运营云服务（Relay）** | 不运营（只做 LAN / 自建隧道）/ 运营自用 Relay | 运营 = 有成本与隐私责任；不运营 = 跨网依赖用户自备隧道或公网 IP |
| D4 | **是否开局域网直连档** | 不做 / 做（默认回环 + 可选 LAN 绑定） | 做 = 首次可用门槛最低；不做 = 必须走隧道/中继才能用 |
| D5 | **并发上限** | 单设备 / 多设备 N / 不限（受 §6.8 水位约束） | 影响仲裁与审计复杂度 |
| D6 | **手机端做到什么程度** | 只读 + 答审批 / 加发消息 / 加派发路由（S2 工具面） | 决定 §10 客户端底座是否够用 |
| D7 | **是否接受「窗口必须开着」** | 接受（本方案天花板）/ 不接受（需 headless 宿主，§8） | 不接受 = 工期与范围量级变化，不是增量 |
| D8 | **路由形态下谁宣布「整体完成」** | 主助手（汇总子会话结果）/ 用户 / 宿主聚合 | 决定 S2 的验收口径，也决定 §13.8 三条判据怎么落 |
