## 0. 一句话结论

大文本行为（读文件 / 联网搜索 / 读记忆原文 / 读技能正文……）**一律走同一条通道**：

```
带问题取件 → 一次一份 → 提炼 → 原文落盘 → 只积攒情报 + 留引用
```

**并行不靠在主上下文同时铺开多份**，而靠**派发独立上下文的子 agent**，各自提炼、只回传结论。

## 1. 问题：不是压缩参数错了，是前提错了

### 1.1 症状（CTX-1 实锤）

`互动叙事平台方案` 项目「方案设计师」角色包实测：

- turn 开头已成功读取 3 份文档（seq 12-17）；
- 上下文压缩很快把已读内容清空；
- 后续 `search_project` 搜「核心/愿景」返回"未找到"——**词明明在文档里**；
- LLM 陷入「内容被清 → 以为没读过 → 重读 → 撞 `[ALREADY_READ]` / `FILE_NOT_FOUND`」死循环；
- 开始**凭文件名猜**不存在的文件（`大厂方案对标分析报告` / `UI设计语言方案` / `MVP规划`）。

### 1.2 原方向错在哪

原定方向是「压缩时给工具结果设最小保留窗口」或「压缩后强提示路径清单」——**这是在"全量加载"这个前提下做补救**。

前提本身就错了：**这些东西从一开始就不该整个进上下文**。一旦进来，无论保留窗口怎么调，都是在跟稀缺窗口抢空间：压缩必然发生，丢失必然发生，死循环只是时间问题。

**所以 CTX-1 的性质变了：不是压缩参数问题，是"内容该不该进来"的架构问题。**

### 1.3 第一性原理

| 事实 | 推论 |
|---|---|
| 上下文是**稀缺**资源，且存在性能墙（业界实测 ~1M token 后一致衰减，与窗口上限无关） | "尽量多放"是负收益，不是正收益 |
| LLM 真正需要的是「回答当前问题所需的那几句」 | 需要的是**情报**，不是**原文** |
| 原文可随时从磁盘重取 | 无必要常驻内存 |

结论：**有价值的是提炼结果，原文只是提炼的输入。**

## 3. 方案：三道关

### 3.1 第一关 · 入口关（Select）—— 大文本不进门

**做法**：读文件、联网搜索、读记忆原文，一律不再把全文塞进对话。

原文**落盘存好**（复用现有 `offloadDir`），主上下文只带三样：

| 带进来 | 说明 |
|---|---|
| **答案** | 针对本次"问题"的提炼结果 |
| **路径** | 原文落盘位置（= 引用，可再取） |
| **元信息** | 尺寸、时间、来源类型 |

要细节？**带着问题再取一次**（取片段，不是整本）。

### 3.2 第二关 · 单行道 —— 一次一份

主对话里同时只处理**一份**大文本。

这**不靠喊口号约束**，而是入口关的**自然结果**：全文根本没进来，"同时铺开三份"就无从发生。

### 3.3 第三关 · 分身术（Isolate）—— 并行靠开新房间

真要同时查五份？**开五个干净的独立上下文**，各给一个明确任务，各自查完、各自提炼，**只把结论交回来**。

**memora 的硬约束**（不可违背）：

| 约束 | 含义 |
|---|---|
| 单 Agent（ADR） | 子 agent **不能**是"第二个 orchestrator"——那是已被砍掉的老路（`目标模式生长探索-分层阶段化.md` §4.1 的教训：换壳不换质、违反最小单元哲学） |
| 最小单元 | 子 agent = 同一套 `turn ⊃ loop ⊃ step` 的 **fresh 实例**（对应 §6.2「spawn 一个 fresh `runChat` 当阶段」） |
| 契约优先 | 派发必须带 **input/output 契约**；否则隔离退化为"各自为政" |

## 4. 三个待决点的暂定结论

> 这三条是**暂定**（可讨论、可推翻），但都有调研支撑，不是拍脑袋。

### 4.1 「带问题去看」= 先读完再提炼，还是检索即问答？

**暂定：分三层，不做二选一。**

| 层 | 机制 | 适用 |
|---|---|---|
| 默认 | **先落地，只回提炼结果 + 引用**（业界 Tier-1 offload） | 绝大多数场景 |
| 深挖 | 需要细节时**带 `question` 再取**，只返回相关片段 | 提炼不足时 |
| 彻底 | **派子 agent** 去看，只回结论 | 需并行 / 需彻底隔离 |

**理由**：
- 单独用「检索即问答」的风险是**问题问偏就漏信息**——对"我还不确定要找什么"的探索型任务是致命的；
- 单独用「先读后提炼」的风险是**峰值仍在**——原文短暂进过上下文；
- 而 Tier-1 offload（落盘 + 引用）恰好同时压制两者：**不进上下文**且**信息不丢**（随时可再取）。

### 4.2 情报区自己会不会撑爆？

**暂定：会。所以情报区必须有预算 + 淘汰。**

- 情报积攒 = 业界的 **structured note-taking**（Anthropic 三方法之一），**不是随便攒**；
- 必须有 **token 预算**，超预算时按价值/时序淘汰；
- 位置在上下文**尾部**——遵守「稳定前缀 + 增长尾部」，避免破坏 KV-cache；
- 若不设预算，只是把爆点从"原文"挪到"情报"，问题原样搬家。

### 4.3 丢了原文，需要时怎么办？

**暂定：丢原文 ≠ 断链。留引用 + 允许再取（仍带问题）。**

- 落盘路径**本身就是引用**；
- `[ALREADY_READ]` 语义升级为：**「已读过 → 情报在第 N 条 → 原文在 <路径>」**，而不是生硬拒绝；
- 这同时**消解 CTX-1 的根因②**：`[ALREADY_READ]` 与 `FILE_NOT_FOUND` 不再打架——统一成一句话：「读过的看引用与情报，没读过的才去读」。

## 8. 拍板结构（2026-09-13 对抗式审查后）

> 复核依据：[legacy-contract-audit-rules.md](../.trae/rules/legacy-contract-audit-rules.md)（先读码再定类）+ [single-truth-source-mindset.md](../.trae/rules/single-truth-source-mindset.md)（最小单元）+ [ADR-017](../.trae/decisions/ADR-017-natural-growth-redefinition.md)（架构层先行）。
> **结论：方向接受，整包不接受。** 按「1 个拆项 → 3 个架构锚点 → 2 条验收」逐层拍，不整包拍。

### 8.1 先拆项：CTX-1 是三个根因的合集

| 症状 | 真根因 | 归属 |
|---|---|---|
| 死循环：`[ALREADY_READ]` 与 `FILE_NOT_FOUND` 打架 | 缓存断言「你已读过」，而内容已被压缩清空——文案与事实不符 | **本方案** |
| 凭文件名猜不存在的文件 | 路径清单随压缩一起消失 | **本方案** |
| `search_project` 搜不到文档里明明存在的词 | **③a 多词整串字面量匹配**（独立缺陷，实锤）／**③b 读的是项目根外路径**（与通道耦合，当前几乎不可达） | **③a 另立子项；③b 归本方案** |

**压缩只改内存消息数组，不可能让磁盘检索失败。** 第三条实测根因：

- `search_project mode=content` 走 `escapeRegExp(pattern)`——**整串字面量**匹配（`hosts/memora-vscode/src/extension/host/projectSearchProvider.ts:78` + `:263-265`）。LLM 传「核心/愿景」这类多词带分隔符 query → 正则即 `/核心\/愿景/i` → 全文无此连续子串 → **必然零命中**；
- 零命中时「截断诚实化」失效：`src/agent/toolExecutor.ts:981-983` 在算 `truncated` 之前就 return，`counter.truncated` 与宿主 `MAX_FILES_SCANNED=500` 上限信息全部丢失 → LLM 被告知「不存在」，实为「只扫了前 500 个文件就停了」。

**实证（2026-09-13，执行宿主编译产物内的 `escapeRegExp` 源码）**：单关键词 `核心` / `愿景` 均 `命中=true`；多词 `核心/愿景` → 正则 `/核心\/愿景/i` → **`命中=false`**；`核心 愿景` 同样 `false`。→ **带分隔符的多词 query 必然零命中**，且失败信息与「真不存在」无法区分。

**不拆项则 Step 1 的验收标准是假的**：通道跑通后原文不再进上下文，LLM 只能靠 `search_project` 找回信息——这条缺陷**会被本方案放大**。

### 8.2 三个架构锚点（架构层 · 必须现在拍，先文档化再动代码）

| 锚点 | 待定 | 建议 | 理由 |
|---|---|---|---|
| **A · 收口点** | 通道是「新入口关」还是「压缩链提升」 | 机制**收口为单一原语**（落盘 + 引用替换）；触发点允许两个但须显式声明差异 | 压缩链现已有 3 策略（`src/agent/loop.ts:308-323`）+ `compress_context` 工具 + `truncateMessages` 硬闸；再加一个 offload = 同语义多实现（带伤 §3「重复实现」） |
| **B · 情报区生命周期** | 内存 / 进 checkpoint / 落盘 | **不进 checkpoint**（会话内可重建）；丢失可接受——原文在盘、引用可再取 | 进 checkpoint = 触碰**持久化数据面**，按版本契约分面须留迁移；收益不匹配（原文本就未丢） |
| **C · 预算来源** | 情报区预算从哪来 | **复用装配预算 / 占用模型**，不新增第 5 个预算维度 | 对齐既有裁决「预算/占用模型无记忆维度」；否则爆点只是从「原文」搬到「情报」 |

**A 的前置 —— 已实证，结论：当前断链（2026-09-13）**。offload 目标目录用 `process.env.HOME ?? process.cwd()`（`src/agent/compaction.ts:232`）——全库**唯一**的第二套 home 解析（SSOT 应为 `src/utils/path.ts::expandHome()`），且 `loop.ts:322` 无参构造 → `~/.memora/outputs` 即生产取值。**但宿主把 `dataDir` 注入为项目级 `<工作区>/.memora`（`hosts/memora-vscode/src/extension/host/assemble.ts:258`），信任根 = projectPath / memoraDir / configDir / agentDataDir 四项全在项目侧，不含用户级 `~/.memora`。**

**实证**：用真实 `dist` 的 `SecurityGuard` + 真实信任根断言 `read_file <offload 路径>` → **「路径越界」拦截**；仅「未打开工作区」兜底场景（`resolveWorkspacePath()` 回退 `~/.memora`，此时 `~/.memora` 恰是 projectPath）放行。→ **offload 文案「如需完整内容请使用 read_file 工具读取上述路径」在常态下不可执行。**

**⇒ 落点结论（锚点 A 的一部分）· ✅ 已落地（2026-09-13，OFFLOAD-1）**：offloadDir 收敛到 **`<工作区>/.memora/outputs/`**，且 `offloadDir` 改必传、未注入则**不注册**该策略（内核不再派生落点）。一步同时满足两条约束：① 在信任根内 → `read_file` 可读；② `.memora` 在 `IGNORED_DIR_NAMES`（`src/agent/builtinToolHandlers.ts:73-80`）内 → 天然被 `search_project` / `list_dir` 忽略，不污染项目检索、不触发「伪建表」类自我强化。**零新增白名单配置。**

**🔴 风险升级：Step 1 会把偶发缺陷变成系统缺陷。** 当前 offload 是事后兜底，只有 >20K token 的巨型结果才触发 → 缺陷偶发；Step 1 把它提升为**默认入口通道**后，每次大文本读取都走此路径 → 稳定产出「读了文件 → 原文没进上下文 → 路径也读不回来」的**最坏情形（比现状更糟）**。故该修复是 Step 1 的**硬前置**，不是并行项。

**🔴 前提复核：offload 从未通电（2026-09-13 实证）。** 触发条件是 `estimateTokens(content) > thresholdTokens`，而 `estimateTokens = ceil(text.length / 4)`（字符数，非真实分词，`src/agent/compaction.ts:365-367`）。对全部内置工具结果：

| 工具结果 | 上限（chars） | `estimateTokens` | > 20,000？ |
|---|---|---|---|
| read_file | 50,000 | 12,500 | ❌ |
| web_fetch 正文 | 50,000 | 12,500 | ❌ |
| skill / resource 正文 | 50,000 | 12,500 | ❌ |
| run_code / run_script stdout | 20,000 | 5,000 | ❌ |
| 自定义工具（`customTools`） | **无上限** | 无上限 | ✅ 唯一可达 |

→ **内置工具全部结构性不可达**（上限 ≤50,000 chars = 12,500 tokens < 阈值）；仅宿主注册的返回超大结果的自定义工具能触发。**即 `OffloadCompactionStrategy` 在当前内核中近似死代码，只在单测（自定义小阈值）里活。** 证据链自洽：**正因从未触发，落点越界缺陷才可能长期无人发现。**

**对方案的意义**：§5 说的「三块砖都已存在，只差接成一条通道」需要修正为 —— **这一块砖从未通电，且插头插错位置**（结构同构是纸面的，运行上从未生效）。故 Step 1 不是「接线」，而是**让机制首次真正生效**：首次生效 = 首次暴露全部未验证行为，风险显著高于文档原预期 → 必须先修落点与可达性、并补测试，再谈「提升为入口通道」。

**C 的附带**：offload 阈值 `20_000` 是构造器字面量（`src/agent/compaction.ts:233`，`loop.ts:322` 无参调用），不在 `src/agent/constants.ts` 预算 SSOT 内。它一旦成为默认入口通道的承重旋钮，必须与 `CONTEXT_TOKENS_BUFFER_RATIO` / `SUMMARY_LAYER_TOKEN_RATIO` 同家。

### 8.3 两条可判定验收（替代软标准「死循环消失」）

1. **引用链可回取** ✅ **已达成（2026-09-13）**：offload 落点收敛到 `<工作区>/.memora/outputs/` 后，`read_file` 直接读回（真实信任根断言 ALLOW；有工作区常态下实测通过），且 `search_project` 不因此产生伪命中（`.memora` 属 `IGNORED_DIR_NAMES`）；守卫测试：产物与引用**同落**注入目录（loop + compaction 各 1 例），变异验证 `opts.offloadDir ?` → `true ?` 即红；
2. **真实场景复跑**：CTX-1 原场景重跑，`[ALREADY_READ]` 文案不再与 `FILE_NOT_FOUND` 打架——即文案与事实同批更新，不再属「撒谎注释」类。
