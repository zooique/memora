## 0. 一句话结论

大文本行为（读文件 / 联网搜索 / 读记忆原文 / 读技能正文……）**一律走同一条通道**：

```
带问题取件 → 一次一份 → 提炼 → 原文落盘 → 只积攒情报 + 留引用
```

**并行不靠在主上下文同时铺开多份**，而靠**派发独立上下文的子 agent**，各自提炼、只回传结论。

## 1. 问题：不是压缩参数错了，是前提错了

### 1.1 症状（CTX-1 实锤）

`互动叙事平台方案` 项目「方案设计师」角色包实测：

- turn 开头已成功读取 3 份文档（seq 12-17）；
- 上下文压缩很快把已读内容清空；
- 后续 `search_project` 搜「核心/愿景」返回"未找到"——**词明明在文档里**；
- LLM 陷入「内容被清 → 以为没读过 → 重读 → 撞 `[ALREADY_READ]` / `FILE_NOT_FOUND`」死循环；
- 开始**凭文件名猜**不存在的文件（`大厂方案对标分析报告` / `UI设计语言方案` / `MVP规划`）。

### 1.2 原方向错在哪

原定方向是「压缩时给工具结果设最小保留窗口」或「压缩后强提示路径清单」——**这是在"全量加载"这个前提下做补救**。

前提本身就错了：**这些东西从一开始就不该整个进上下文**。一旦进来，无论保留窗口怎么调，都是在跟稀缺窗口抢空间：压缩必然发生，丢失必然发生，死循环只是时间问题。

**所以 CTX-1 的性质变了：不是压缩参数问题，是"内容该不该进来"的架构问题。**

### 1.3 第一性原理

| 事实 | 推论 |
|---|---|
| 上下文是**稀缺**资源，且存在性能墙（业界实测 ~1M token 后一致衰减，与窗口上限无关） | "尽量多放"是负收益，不是正收益 |
| LLM 真正需要的是「回答当前问题所需的那几句」 | 需要的是**情报**，不是**原文** |
| 原文可随时从磁盘重取 | 无必要常驻内存 |

结论：**有价值的是提炼结果，原文只是提炼的输入。**

## 3. 方案：三道关

### 3.1 第一关 · 入口关（Select）—— 大文本不进门

**做法**：读文件、联网搜索、读记忆原文，一律不再把全文塞进对话。

原文**落盘存好**（复用现有 `offloadDir`），主上下文只带三样：

| 带进来 | 说明 |
|---|---|
| **答案** | 针对本次"问题"的提炼结果 |
| **路径** | 原文落盘位置（= 引用，可再取） |
| **元信息** | 尺寸、时间、来源类型 |

要细节？**带着问题再取一次**（取片段，不是整本）。

### 3.2 第二关 · 单行道 —— 一次一份

主对话里同时只处理**一份**大文本。

这**不靠喊口号约束**，而是入口关的**自然结果**：全文根本没进来，"同时铺开三份"就无从发生。

### 3.3 第三关 · 分身术（Isolate）—— 并行靠开新房间

真要同时查五份？**开五个干净的独立上下文**，各给一个明确任务，各自查完、各自提炼，**只把结论交回来**。

**memora 的硬约束**（不可违背）：

| 约束 | 含义 |
|---|---|
| 单 Agent（ADR） | 子 agent **不能**是"第二个 orchestrator"——那是已被砍掉的老路（`目标模式生长探索-分层阶段化.md` §4.1 的教训：换壳不换质、违反最小单元哲学） |
| 最小单元 | 子 agent = 同一套 `turn ⊃ loop ⊃ step` 的 **fresh 实例**（对应 §6.2「spawn 一个 fresh `runChat` 当阶段」） |
| 契约优先 | 派发必须带 **input/output 契约**；否则隔离退化为"各自为政" |

## 4. 三个待决点的暂定结论

> 这三条是**暂定**（可讨论、可推翻），但都有调研支撑，不是拍脑袋。

### 4.1 「带问题去看」= 先读完再提炼，还是检索即问答？

**暂定：分三层，不做二选一。**

| 层 | 机制 | 适用 |
|---|---|---|
| 默认 | **先落地，只回提炼结果 + 引用**（业界 Tier-1 offload） | 绝大多数场景 |
| 深挖 | 需要细节时**带 `question` 再取**，只返回相关片段 | 提炼不足时 |
| 彻底 | **派子 agent** 去看，只回结论 | 需并行 / 需彻底隔离 |

**理由**：
- 单独用「检索即问答」的风险是**问题问偏就漏信息**——对"我还不确定要找什么"的探索型任务是致命的；
- 单独用「先读后提炼」的风险是**峰值仍在**——原文短暂进过上下文；
- 而 Tier-1 offload（落盘 + 引用）恰好同时压制两者：**不进上下文**且**信息不丢**（随时可再取）。

### 4.2 情报区自己会不会撑爆？

**暂定：会。所以情报区必须有预算 + 淘汰。**

- 情报积攒 = 业界的 **structured note-taking**（Anthropic 三方法之一），**不是随便攒**；
- 必须有 **token 预算**，超预算时按价值/时序淘汰；
- 位置在上下文**尾部**——遵守「稳定前缀 + 增长尾部」，避免破坏 KV-cache；
- 若不设预算，只是把爆点从"原文"挪到"情报"，问题原样搬家。

### 4.3 丢了原文，需要时怎么办？

**暂定：丢原文 ≠ 断链。留引用 + 允许再取（仍带问题）。**

- 落盘路径**本身就是引用**；
- `[ALREADY_READ]` 语义升级为：**「已读过 → 情报在第 N 条 → 原文在 <路径>」**，而不是生硬拒绝；
- 这同时**消解 CTX-1 的根因②**：`[ALREADY_READ]` 与 `FILE_NOT_FOUND` 不再打架——统一成一句话：「读过的看引用与情报，没读过的才去读」。

### 6.1 Step 1 展开 —— 动手前读码（2026-09-13）：**前提不成立，须先补 1a**

**两处读码实锤（Step 1 硬阻塞）**：

| # | 实锤 | 位置 |
|---|---|---|
| **F-a** | `read_file` **无分段能力**：schema 只有 `path`；handler 签名 `readFile(relativePath: string)` | `src/agent/builtinTools.ts:347-357`、`builtinToolHandlers.ts:202` |
| **F-b** | `read_file` 超长**静默截断**：`sanitizeExternalText` 只追加 `…`，不告知「被截断 / 共多少 / 如何续读」 | `src/agent/toolExecutor.ts:158`（上限 `FILE_READ_MAX_LEN = 50_000`，`builtinToolHandlers.ts:57`） |

**为什么这是硬阻塞 —— 一个二难（逻辑决定论，由代码结构推出，非经验推断）**

Step 1 的形态是「结果超阈 → 落盘 → 回『预览 + 路径 + 尺寸』」，而 LLM 回取原文的唯一路径是 `read_file <路径>`。于是阈值只有两档命运：

- **阈值 < 12,500 tokens**（= 内置工具结果上限 50,000 chars ÷ 4）→ 入口关生效，但**LLM 读回产物时产物本身同样超阈 → 再次落盘 → 得到新路径 → 再读 → …**。`ToolResultCache` 拦不住：offload 文件名含时间戳与随机串，每次路径都不同 → 去重 key 必 miss。**无限嵌套落盘** —— CTX-1 的重读死循环机制性再版，且这次是内核自己制造的。
- **阈值 ≥ 12,500 tokens** → 对全部内置工具**结构性不可达**（与 §8.2 发现的「offload 从未通电」完全同构）→ 入口关成为**第二块死砖**。

**⇒ 逃逸只有一条：让 `read_file` 具备分段读取能力。** 有了分段，「路径即引用」才是一条真通道（读到产物 → 分段续读 → 每次只取一份）；这同时消解 F-b —— 截断必须诚实告知「共 N 行 / 已显示第 X–Y 行 / 续读用 offset」。**注意 F-b 与 SEARCH-1 的「零命中丢失截断标记」同属一个缺陷族：静默截断 = 假阴性**。

**⇒ Step 1 拆为三步，顺序不可交换**

| 子步 | 做什么 | 为何必须在这一序位 |
|---|---|---|
| **1a**（新 · 硬前置）✅ **已落地 2026-09-13** | `read_file` 加 `offset`/`limit`（**按 token 预算分段**）+ 截断诚实化；**统一 token 估算器**（删 `compaction` 孤儿 `÷4`） | 无它则 1b 不是「提升为入口通道」，而是**亲手造一个死循环**；估算器不唯一则「同源」是假的 |
| **1b** | 入口关：抽单一原语（落盘 + 引用替换），触发点前移到工具结果回填；压缩链那级删除 | 依赖 1a |
| **1c** | `[ALREADY_READ]` 文案与事实对齐（CTX-1 根因②） | 依赖 1b 产生的落盘事实 |

**1b 的收口点（锚点 A 的兑现方式）**

- 现状 `OffloadCompactionStrategy` 把**四件事揉在一个类里**（遍历 messages → 找超阈 → 落盘 → 替换），且挂压缩链（事后）。
- 抽原语后：原语只做「落盘 + 生成替换文本」；入口关调用它。
- 原文既然不再进上下文，压缩链那级就在压缩链上**恒不触发** → 按「读者先亡、写者后死」纪律应**整级删除**，而非留作兜底。留下 = 同语义两处实现（带伤设计 §3「重复实现」）。
- 阈值落 `src/agent/constants.ts`，与 `CONTEXT_TOKENS_BUFFER_RATIO` / `SUMMARY_LAYER_TOKEN_RATIO` 同家（锚点 C 兑现）。

**已拍板（2026-09-13，用户定）**

1. **参数形态**：走**行号** `offset`/`limit`（Claude Code 同款；按 `\n` 切分，行号语义稳定 → 续读不重不漏）。
2. **单次上限**：`SINGLE_TOOL_RESULT_MAX_TOKENS = 6_000`（≈ 窗口 5%），落 `src/agent/constants.ts` 的 `LOOP_CONSTANTS` 内，与 `CONTEXT_TOKENS_BUFFER_RATIO` / `SUMMARY_LAYER_TOKEN_RATIO` **同家**（锚点 C 兑现）。
3. **同源**：**一个键两处引用**。

**🔴 第三个硬前置：估算器必须唯一（又一处动手前读码才发现的前置）**

拍板第 2 点原写作「24,000 chars（≈6,000 tokens）」——**这个等价关系不成立**。全库并存两个 token 估算器：

| 估算器 | 比例 | 使用者 |
|---|---|---|
| `contextManager.estimateTokensText` / `estimateTokensMessages` | CJK `1.5` 字符/token、其他 `3`（**CJK 感知**） | 上下文占用、截断线、装配预算——**正式口径，且是唯一公开出口**（`src/index.ts` 导出） |
| `compaction.ts::estimateTokens` | 一律 `4` 字符/token | **仅 compaction 内部**两处调用，无任何其他模块导入 → 孤儿 |

⇒ 同样 24,000 字符：按正式口径，中文 ≈ 16,000 tokens、英文 ≈ 8,000 tokens，**都不等于 6,000**。故「24,000 chars 上限」既守不住窗口 5%，也守不住同源不变量。**正解：限额表达为 token 量（本键），两侧一律按 token 判定**——字符只是估算的输入，不是限额本身。

**对 §8.2 那张家用表的修正说明**：该表按 `÷4` 算得「内置工具结果 ≤12,500 tokens < 阈值 20,000 → 结构性不可达」。此结论**在 offload 现有代码路径上仍然成立**（它确实调那个孤儿 `÷4` 估算器）；但它同时暴露另一件事：**offload 的触发判据与上下文占用报出的数字不同源**，中文场景下同一段文本两处相差近 2.7 倍。1a 一并收口（删孤儿估算器，`OffloadCompactionStrategy` 改调正式估算器）。

**那个孤儿估算器的守卫本身就是假闸门**：它三个用例中的第一个名为「准确估算中文 Token 数」、注释写「4 个汉字 ≈ 6-8 tokens」，断言却是 `toBe(1)`（`ceil(4/4)`）——**用例名、注释、断言三者互相矛盾**，等于把错误固化成预期。1a 同批删除。

**1a 收口摘要（2026-09-13，已落地）**

| 项 | 落地内容 | 文件 |
|---|---|---|
| 分段参数 | `read_file(path, offset?, limit?)`，1-based 行号；按 token 预算**二分**最大可容纳行数（token 随行数单调增 → 二分成立）；脚注预留按最坏位数估算 | `builtinToolHandlers.ts`、`builtinTools.ts`、`toolExecutor.ts` |

## 7. 风险与对抗式自检

| # | 风险 | 应对 |
|---|---|---|
| R1 | **隔离 ≠ 对齐**：子 agent 各看一份，可能给出互相冲突的结论 | 派发必须带 input/output 契约；产出落**产物文件**作对齐锚（§6.2 已述） |
| R2 | **token 成本上升**：业界多 agent 系统总 token 可达单 agent 的 15 倍 | 只在「需并行 / 需彻底隔离」时用；简单任务不派发 |
| R3 | **提炼丢信息**：提炼质量取决于"问题"提得准不准 | 保留可再取引用；提炼结果标注来源，便于回溯 |
| R4 | **情报区膨胀** | 见 4.2：预算 + 淘汰，不是无限攒 |
| R5 | **破坏 prompt cache**：情报区位置若动摇前缀 | 情报区固定在尾部；前缀（系统提示 / 工具定义 / 项目指令）保持稳定 |
| R6 | **过度设计**：Step 1 未验证就上 Step 3 | 分步验证，每步单独可回滚 |

**对抗式自问**（偏离即回到正常设计）：

1. 这套逻辑从零设计会这样写吗？——会，业界主流正是如此。
2. 去掉"兼容现有工具契约"这一层，核心是否仍完整？——核心是"原文不进上下文"，与工具形态无关。
3. 是否在 SSOT 边界之外另开了一条手写通道？——**目标：不**。但代码层当前是 5 处空间回收点（压缩链 3 策略 + `compress_context` 工具 + `truncateMessages` 硬闸）外加一套独立 offload 落点常量；收敛到单一原语前，此问答**暂不成立**（见 §8.2-A）。

## 8. 拍板结构（2026-09-13 对抗式审查后）

> 复核依据：[legacy-contract-audit-rules.md](../.trae/rules/legacy-contract-audit-rules.md)（先读码再定类）+ [single-truth-source-mindset.md](../.trae/rules/single-truth-source-mindset.md)（最小单元）+ [ADR-017](../.trae/decisions/ADR-017-natural-growth-redefinition.md)（架构层先行）。
> **结论：方向接受，整包不接受。** 按「1 个拆项 → 3 个架构锚点 → 2 条验收」逐层拍，不整包拍。

### 8.1 先拆项：CTX-1 是三个根因的合集

| 症状 | 真根因 | 归属 |
|---|---|---|
| 死循环：`[ALREADY_READ]` 与 `FILE_NOT_FOUND` 打架 | 缓存断言「你已读过」，而内容已被压缩清空——文案与事实不符 | **本方案** |
| 凭文件名猜不存在的文件 | 路径清单随压缩一起消失 | **本方案** |
| `search_project` 搜不到文档里明明存在的词 | **③a 多词整串字面量匹配**（独立缺陷，实锤）／**③b 读的是项目根外路径**（与通道耦合，当前几乎不可达） | **③a 另立子项；③b 归本方案** |

**压缩只改内存消息数组，不可能让磁盘检索失败。** 第三条实测根因：

- `search_project mode=content` 走 `escapeRegExp(pattern)`——**整串字面量**匹配（`hosts/memora-vscode/src/extension/host/projectSearchProvider.ts:78` + `:263-265`）。LLM 传「核心/愿景」这类多词带分隔符 query → 正则即 `/核心\/愿景/i` → 全文无此连续子串 → **必然零命中**；
- 零命中时「截断诚实化」失效：`src/agent/toolExecutor.ts:981-983` 在算 `truncated` 之前就 return，`counter.truncated` 与宿主 `MAX_FILES_SCANNED=500` 上限信息全部丢失 → LLM 被告知「不存在」，实为「只扫了前 500 个文件就停了」。

**实证（2026-09-13，执行宿主编译产物内的 `escapeRegExp` 源码）**：单关键词 `核心` / `愿景` 均 `命中=true`；多词 `核心/愿景` → 正则 `/核心\/愿景/i` → **`命中=false`**；`核心 愿景` 同样 `false`。→ **带分隔符的多词 query 必然零命中**，且失败信息与「真不存在」无法区分。

**不拆项则 Step 1 的验收标准是假的**：通道跑通后原文不再进上下文，LLM 只能靠 `search_project` 找回信息——这条缺陷**会被本方案放大**。

### 8.2 三个架构锚点（架构层 · 必须现在拍，先文档化再动代码）

| 锚点 | 待定 | 建议 | 理由 |
|---|---|---|---|
| **A · 收口点** | 通道是「新入口关」还是「压缩链提升」 | 机制**收口为单一原语**（落盘 + 引用替换）；触发点允许两个但须显式声明差异 | 压缩链现已有 3 策略（`src/agent/loop.ts:308-323`）+ `compress_context` 工具 + `truncateMessages` 硬闸；再加一个 offload = 同语义多实现（带伤 §3「重复实现」） |
| **B · 情报区生命周期** | 内存 / 进 checkpoint / 落盘 | **不进 checkpoint**（会话内可重建）；丢失可接受——原文在盘、引用可再取 | 进 checkpoint = 触碰**持久化数据面**，按版本契约分面须留迁移；收益不匹配（原文本就未丢） |
| **C · 预算来源** | 情报区预算从哪来 | **复用装配预算 / 占用模型**，不新增第 5 个预算维度 | 对齐既有裁决「预算/占用模型无记忆维度」；否则爆点只是从「原文」搬到「情报」 |

**A 的前置 —— 已实证，结论：当前断链（2026-09-13）**。offload 目标目录用 `process.env.HOME ?? process.cwd()`（`src/agent/compaction.ts:232`）——全库**唯一**的第二套 home 解析（SSOT 应为 `src/utils/path.ts::expandHome()`），且 `loop.ts:322` 无参构造 → `~/.memora/outputs` 即生产取值。**但宿主把 `dataDir` 注入为项目级 `<工作区>/.memora`（`hosts/memora-vscode/src/extension/host/assemble.ts:258`），信任根 = projectPath / memoraDir / configDir / agentDataDir 四项全在项目侧，不含用户级 `~/.memora`。**

**实证**：用真实 `dist` 的 `SecurityGuard` + 真实信任根断言 `read_file <offload 路径>` → **「路径越界」拦截**；仅「未打开工作区」兜底场景（`resolveWorkspacePath()` 回退 `~/.memora`，此时 `~/.memora` 恰是 projectPath）放行。→ **offload 文案「如需完整内容请使用 read_file 工具读取上述路径」在常态下不可执行。**

**⇒ 落点结论（锚点 A 的一部分）· ✅ 已落地（2026-09-13，OFFLOAD-1）**：offloadDir 收敛到 **`<工作区>/.memora/outputs/`**，且 `offloadDir` 改必传、未注入则**不注册**该策略（内核不再派生落点）。一步同时满足两条约束：① 在信任根内 → `read_file` 可读；② `.memora` 在 `IGNORED_DIR_NAMES`（`src/agent/builtinToolHandlers.ts:73-80`）内 → 天然被 `search_project` / `list_dir` 忽略，不污染项目检索、不触发「伪建表」类自我强化。**零新增白名单配置。**

**🔴 风险升级：Step 1 会把偶发缺陷变成系统缺陷。** 当前 offload 是事后兜底，只有 >20K token 的巨型结果才触发 → 缺陷偶发；Step 1 把它提升为**默认入口通道**后，每次大文本读取都走此路径 → 稳定产出「读了文件 → 原文没进上下文 → 路径也读不回来」的**最坏情形（比现状更糟）**。故该修复是 Step 1 的**硬前置**，不是并行项。

**🔴 前提复核：offload 从未通电（2026-09-13 实证）。** 触发条件是 `estimateTokens(content) > thresholdTokens`，而当时的 `estimateTokens = ceil(text.length / 4)`（字符数，非真实分词，即 §6.1 所述孤儿估算器，1a 已删除；其断言 `toBe(1)` 的守卫同批删除）。对全部内置工具结果：

| 工具结果 | 上限（chars） | `estimateTokens` | > 20,000？ |
|---|---|---|---|
| read_file | 50,000 | 12,500 | ❌ |
| web_fetch 正文 | 50,000 | 12,500 | ❌ |
| skill / resource 正文 | 50,000 | 12,500 | ❌ |
| run_code / run_script stdout | 20,000 | 5,000 | ❌ |
| 自定义工具（`customTools`） | **无上限** | 无上限 | ✅ 唯一可达 |

→ **内置工具全部结构性不可达**（上限 ≤50,000 chars = 12,500 tokens < 阈值）；仅宿主注册的返回超大结果的自定义工具能触发。**即 `OffloadCompactionStrategy` 在当前内核中近似死代码，只在单测（自定义小阈值）里活。** 证据链自洽：**正因从未触发，落点越界缺陷才可能长期无人发现。**

**⚠️ 口径变化（2026-09-13 补记 · 1a 落地后重算）**：上表结论**只在孤儿 `÷4` 口径下成立**，不是「内置工具天然不可达」。1a 已把 `OffloadCompactionStrategy` 改调正式 CJK 感知估算器（`estimateTokensText`，CJK `1.5`、其他 `3` 字符/token），同表重算：

| 工具结果 | 上限 | 全中文 tokens | 全英文 tokens | > 20,000？ |
|---|---|---|---|---|
| read_file | **≤6,000 tokens（按预算分段，不再是字符上限）** | ≤6,000 | ≤6,000 | ❌ **结构性不可能**（同源不变量的直接后果） |
| web_fetch 正文 | 50,000 chars | ≈33,333 | ≈16,667 | ✅ **中文可达** |
| skill / resource 正文 | 50,000 chars | ≈33,333 | ≈16,667 | ✅ **中文可达** |
| list_dir | 50,000 chars | ≈33,333 | ≈16,667 | ✅ **中文可达** |
| run_code / run_script stdout | 20,000 chars | ≈13,333 | ≈6,667 | ❌ |
| 自定义工具 | 无上限 | 无上限 | 无上限 | ✅ |

⇒ **三件事同时发生**：① offload 在中文场景**首次真正通电** —— Step 0 的落点修复由此从「未雨绸缪」变成「正在承重」；② `read_file` 因分段上限（6,000 < 20,000）**结构性不可能**触发 offload，回取产物时单次输出恒 ≤6,000 → 不再落盘 → **嵌套不可能**（§8.3-2 的判据由此可判）；③ 但阈值 `20_000` 仍是构造器字面量（`compaction.ts` 构造器 + `loop.ts` 无参构造），与 `SINGLE_TOOL_RESULT_MAX_TOKENS` **分居两处、无编译期关联**，不变量只靠 3.3× 边际维持 —— **1b 须把阈值搬进 `LOOP_CONSTANTS`，让「阈值 > 单次上限」成为可读的常量关系**。

**守卫（1a 同批补 · 变异实证）**：`compaction.test.ts` 新增三条 —— CJK 口径判别用例（含「两口径判别方向相反」的前提自检，防退化为无判别力用例）、边界精确对齐用例（`> 阈值` 而非 `≥`）、`compact` 侧同源落盘用例。双向验证：把判据改回 `Math.ceil(len/4)` → **3 条全红**（未补守卫前同一变异 **23 条全绿**，即「估算器唯一」当时是纸面声明）。

**对方案的意义**：§5 说的「三块砖都已存在，只差接成一条通道」需要修正为 —— **这一块砖从未通电，且插头插错位置**（结构同构是纸面的，运行上从未生效）。故 Step 1 不是「接线」，而是**让机制首次真正生效**：首次生效 = 首次暴露全部未验证行为，风险显著高于文档原预期 → 必须先修落点与可达性、并补测试，再谈「提升为入口通道」。

**C 的附带**：offload 阈值 `20_000` 是构造器字面量（`src/agent/compaction.ts:233`，`loop.ts:322` 无参调用），不在 `src/agent/constants.ts` 预算 SSOT 内。它一旦成为默认入口通道的承重旋钮，必须与 `CONTEXT_TOKENS_BUFFER_RATIO` / `SUMMARY_LAYER_TOKEN_RATIO` 同家。

### 8.3 两条可判定验收（替代软标准「死循环消失」）

1. **引用链可回取** ✅ **已达成（2026-09-13）**：offload 落点收敛到 `<工作区>/.memora/outputs/` 后，`read_file` 直接读回（真实信任根断言 ALLOW；有工作区常态下实测通过），且 `search_project` 不因此产生伪命中（`.memora` 属 `IGNORED_DIR_NAMES`）；守卫测试：产物与引用**同落**注入目录（loop + compaction 各 1 例），变异验证 `opts.offloadDir ?` → `true ?` 即红；
2. **回取不嵌套**（2026-09-13 读码补，§6.1 发现原验收不完备）：`read_file` 读回 offload 产物时**不得再次落盘**（若再落盘 → 新路径 → 无限嵌套）。判据：一次 `read_file <产物路径>` 后，`outputs/` 目录**文件数不增**。**1a ✅ 已落地 → 结构性成立**：`read_file` 单次输出恒 ≤6,000 tokens < 阈值 20,000 → 读回不可能再触发落盘（同源不变量，见 §8.2 口径变化表）。**端到端实测待 1b 落地（入口关真实生效）后补做。**
3. **真实场景复跑**：CTX-1 原场景重跑，`[ALREADY_READ]` 文案不再与 `FILE_NOT_FOUND` 打架——即文案与事实同批更新，不再属「撒谎注释」类。

### 8.4 不吸收（本次不拍）

- **Step 3 子 agent**：涉单 Agent ADR 边界，**单独拍板**，不随本方案默许落地；
- **待讨论清单前三条**（提炼由谁执行 / 淘汰规则 / 子 agent 用不用便宜模型）：属**枝叶层**，按 ADR-017「枝叶按需自然长」先不拍——尤其「提炼由谁执行」若两条路并存，本身就是 8.2-A 的同语义多实现；
