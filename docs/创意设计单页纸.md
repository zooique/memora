## 1. 项目一句话

Memora 是一个"专注模式"的 AI Agent 记忆内核 + 桌面精灵宿主，让 LLM 在无状态推理基础上获得连续演化的任务能力。

---

## 2. 核心矛盾

### 无状态推理 ←→ 连续演化任务

- **左侧（无状态推理）**：LLM 本质是无状态函数 `f(prompt) → response`，每次调用独立，无内在记忆
- **右侧（连续演化任务）**：用户真实任务跨会话/跨天/跨项目，需要记忆累积、衰减、召回、关系网络
- **Memora 的根本职责**：在无状态推理之上构建连续演化能力，同时不破坏推理的纯粹性

> 此矛盾不可消除，只能通过架构层隔离 + 记忆生命周期管理持续演化。所有 ADR 决策都直接或间接服务于此矛盾。

---

## 3. 矛盾识别三步法

> 三步法层层深入：表面矛盾（易识别）→ 深层矛盾（需架构思考）→ 演化矛盾（项目演进中暴露）

### 3.1 表面矛盾（项目启动时识别，已收敛 ✅）

**内核纯逻辑 ←→ 宿主 native 能力**

- 内核需保持零依赖（可嵌入任意宿主）
- 宿主需要 native 能力（better-sqlite3 持久化 / electron GUI / commander CLI）
- **解决**：ADR-002 IMemoryStorage 接口 + 零 native 依赖内核，宿主注入持久化实现

### 3.2 深层矛盾（架构设计时识别，已收敛 ✅）

**配置驱动组合根 ←→ 运行时状态驱动组合根**

- assembler.ts 是配置驱动组合根：从 AssembleInput 配置创建 12 个无状态组件
- agent.ts 是运行时状态驱动组合根：创建 3 个有状态 Manager（ArchiveCoordinator / MemoryDecayScheduler / SessionManager），需要 Agent 的 `emit`/`_chatBusy` 等运行时回调
- **解决**：双组合根并存，不强求一致。强行合并会让 AssembleInput 从配置型退化为混合型

### 3.3 演化矛盾（HC-18/19/20 三连跳过暴露，接受 🟡）

**门面类体积膨胀 ←→ 单一职责原则**

- agent.ts 1395 行（HC-18 评估跳过）
- ui.ts 1933 行（HC-19 仅拆 PerceptionPanelController，其他评估跳过）
- sprite.ts 1533 行（HC-20 评估跳过）
- **本质**：门面类（Facade）是 ADR-SP-015 组合模式的合理产物，体积是组合的代价
- **接受**：不通过拆分薄委托降行数，需通过 Controller 合并（架构层 ADR）才能本质减行

## 4. 主要任务（≤5 个，直接服务核心矛盾）

> 主要任务必须 ≤5 个，每个直接服务 §2 核心矛盾。所有 ADR 决策应能映射到这 5 个任务之一。

### 任务 1：统一记忆模型

- **服务矛盾**：让"连续演化"有统一的记忆载体
- **核心实现**：source 开放字符串基元驱动，不引入"规则/技能/历史"等独立子系统
- **关键 ADR**：ADR-004（source 开放字符串）、ADR-014（IMemoryRelationStore 侧车）、ADR-015（archiveMode 三态）

### 任务 2：三层架构落地

- **服务矛盾**：让"无状态推理"与"连续演化"在不同层级各司其职
- **核心实现**：Agent 级配置（configDir）→ 用户记忆（dataDir）→ 项目级配置（projectPath/.memora/）
- **关键约束**：memora.db 是 Agent 级共享资源，不随子项目切换重建

### 任务 3：专注模式 + 记忆衰减

- **服务矛盾**：防止"连续演化"退化为"无限堆积"
- **核心实现**：应无所住而生其心——记忆有生命周期，decayScores 定时衰减，archiveMode 三态控制归档
- **关键 ADR**：ADR-009（专注模式与衰减机制）

### 任务 4：双组合根架构

- **服务矛盾**：让"无状态组件"与"有状态 Manager"在各自合理的组合根装配
- **核心实现**：assembler.ts（配置驱动，12 个无状态组件）+ agent.ts（运行时状态驱动，3 个有状态 Manager）
- **关键决策**：不强求合并两个组合根

### 任务 5：门面类合理体积

- **服务矛盾**：接受组合模式的体积代价，避免强行拆分引入的拼凑
- **核心实现**：Facade 类（agent.ts / ui.ts / sprite.ts）持有多个子 Manager，薄委托方法是 Facade 契约的合理产物
- **关键决策**：HC-18/19/20 三连跳过，28 个委托方法不可拆

## 5. 不做清单（≥3 条）

> 不做清单明确边界，避免过度工程。每条对应一个"反模式"。

### 不做 1：多 Agent 并发

- **理由**：单 Agent 模型，memora.db 跨项目共享，避免并发引入的状态混乱
- **违反则**：破坏 §1 硬约束 4（单 Agent 模型 + 三层架构）

### 不做 2：在 SQLite 存原始工作内容

- **理由**：仅存投影/摘要，原始内容（如小说章节、代码文件）通过宿主工具访问
- **违反则**：导致索引膨胀（违反 §9.3 DON'T）

### 不做 3：拆门面类薄委托

- **理由**：HC-18/19/20 三连跳过评估证明，28 个委托方法是 Facade 契约的合理产物
- **违反则**：引入跨 Manager 依赖传递，违反"自包含"原则和"避免过度工程"原则

### 不做 4：混合技能定义与内存存储

- **理由**：技能通过 skills/ 文件夹管理（agent 级 + 项目级），用关键词匹配
- **违反则**：导致检索低效，违反 §9.3 DON'T

### 不做 5：引入 web 框架依赖

- **理由**：内核零 UI 依赖，UI 由宿主处理
- **违反则**：破坏零依赖内核原则（§1 硬约束 6 + §9.2 DON'T）

### 6.1 演化矛盾详记（HC-18/19/20 三连跳过）

> 三连跳过是项目演化中的重要架构决策，单独记录以避免后续重复评估。

#### HC-18：agent.ts 拆分评估跳过（2026-07-04）

- **评估对象**：`src/agent/agent.ts`（1395 行）
- **候选拆分**：ArchiveCoordinator / MemoryDecayScheduler / SessionManager 迁入 assembler.ts
- **跳过理由**：3 个 Manager 都需要 Agent 的 `emit`/`_chatBusy` 等运行时回调，迁入会让 AssembleInput 从配置型退化为混合型。MemoryDecayScheduler 还有定时器 + 累积指标的生命周期问题
- **架构决策**：双组合根合理性确认——assembler.ts（配置驱动）vs agent.ts（运行时状态驱动）是合理分工，不是缺陷

#### HC-19：ui.ts 拆分评估部分跳过（2026-07-04）

- **评估对象**：`hosts/memora-sprite/src/electron/renderer/ui.ts`（1933 行）
- **已拆分**：PerceptionPanelController（218 行，commit `34dd42c`），ui.ts 1933→1649
- **评估撤销 3 个**：
  - globalKeyboardController（~80 行）：紧耦合 state.currentPanel/state.isStreaming/switchPanel/emitStopMessage/showModal/hideModal，需大而全 Host 接口
  - windowControlsController（~50 行）：仅 4 个 1 行方法 + 1 个 SVG 切换，收益低
  - unreadBadgeController（~50 行）：3 个方法都是简单 DOM 操作，收益低
- **架构决策**：800+ 行薄委托不拆，只拆有实质逻辑的 600 行中的独立部分

#### HC-20：sprite.ts 拆分评估跳过（2026-07-04）

- **评估对象**：`hosts/memora-sprite/src/sprite/sprite.ts`（1533 行）
- **路径校正**：实际在 `src/sprite/sprite.ts`（非 `src/electron/sprite.ts`），是纯逻辑 Facade，零 Electron 依赖
- **候选拆分**：5 个候选全部 ROI 不足
  - RecycleBinCleanupController：59 行收益太小
  - ConfigManager：5+ 依赖，编排逻辑不减少
  - AgentEventBridge：即便拆出 sprite.ts 仍 1398 行
  - DailyMessageCounter：63 行不抵参数传递成本
  - SpriteEventMap 类型：40 行收益不抵 4 处 import 修改
- **架构决策**：门面类体积是 ADR-SP-015 组合模式的合理产物，同 HC-18/HC-19

## 8. 后续演化方向

> 当 §6 表中某项从 🟡 接受 转为 ❌ 未解决 时，启动对应演化方向。

### 8.1 门面类体积本质减行（需架构层 ADR）

- **触发条件**：agent.ts 超 1500 行 / ui.ts 超 2000 行 / sprite.ts 超 1600 行
- **方向**：不通过拆薄委托，而通过 Controller 合并
  - affectController + rapportController + contextAwareness + patternDetector → 单一 PerceptionController
  - 需先走 ADR 评估合并的合理性
- **预期效果**：sprite.ts 减约 200-300 行（4 个 Controller 合并为 1 个）

### 8.2 IMemoryStorage 拆分（可选）

- **触发条件**：IMemoryStorage 方法数超 16
- **方向**：拆为 IMemoryStorage（核心 CRUD）+ IMemoryRecycleBin（回收站）
- **当前状态**：14 方法，暂不触发

### 8.3 Phase 4 生态准备（持续推进）

- 存储独立包发布到 npm（@memora/storage）
- 技能拖入安装体验打磨（skillDropManager）
