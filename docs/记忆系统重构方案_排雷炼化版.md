## 一、重构目标

```
当前：6 种类型 × 4 级永久性 × 6 管理器 × 3 归档模式 × 4 归档原因
目标：1 种记忆 × 1 个存储 × 1 条召回管线 × 1 种归档时机
```

核心转变：**从"概念驱动"到"基元驱动"**。

## 二、新记忆模型

### 2.1 基元定义

```typescript
interface Memory {
  id: string;           // 唯一标识（source:name，如 'rule:core'、'insight:1718083200000'）
  content: string;      // 记忆内容（Markdown 文本）
  source: string;       // 来源标签（开放字符串，非枚举）
  name: string;         // 可读名称（文件名或摘要标题）
  created_at: string;   // 创建时间（ISO 8601）
  accessed_at: string;  // 最后访问时间（每次召回时刷新）
  score: number;        // 权重（0-1，召回时用于排序）
}
```

**与当前 Memora 的对比：**

| 字段 | 当前 Memora | 新模型 |
|------|-------------|--------|
| id | `{type}:{name}` | `{source}:{name}`（语义不变，type → source） |
| type | 枚举：personality/rule/skill/tool/topic/work-projection | **移除**，合并到 source |
| permanence | 枚举：always/domain/topic/on-demand | **移除**，召回策略由查询时决定 |
| content | Markdown 文本 | 不变 |
| name | 文件名 | 不变 |
| tags | JSON 数组 | **移除**，source 标签足够 |
| weight | 0-1 | 改名为 score，语义不变 |
| created_at | ISO 8601 | 不变 |
| updated_at | ISO 8601 | **移除**，用 accessed_at 替代 |
| file_path | 文件路径 | **移除**，id 中已包含来源信息 |

### 2.2 source 标签体系（开放式）

source 是**开放字符串**，不是枚举。以下仅为泊文当前使用的约定标签：

| source | 含义 | 来源 | 注入策略 |
|--------|------|------|---------|
| `persona` | 角色人格 | agent-config/personas/*.md | 每次注入（活跃角色） |
| `rule` | 创作规则 | agent-config/rules/*.md + .memora/rules/*.md | 每次注入 |
| `skill` | 技能定义 | agent-config/skills/*.md | 按需注入 |
| `insight` | 对话洞察 | 每轮问答结束后 LLM 提取 | 按相关性召回 |
| `profile` | 用户画像 | 每轮问答中 LLM 实时提取 | 每次注入（已确认项） |

**新增来源无需改代码**——只需在存储时指定 source 字符串即可。

### 2.3 移除的概念

| 移除 | 理由 |
|------|------|
| MemoryType 枚举 | 被 source 字符串替代，开放式 > 封闭式 |
| Permanence 4 级 | 召回策略由查询时决定，不是记忆的固有属性 |
| TopicMount 话题漂移检测 | 被简单关键词搜索替代 |
| ArchiveManager 封存重试 | 归档改为同步执行，不需要重试队列 |
| MessageHistory 独立概念 | 会话消息归 AgentLoop 管理，摘要归 MemoryStore |
| TopicStore 话题文件 | 改为会话文件（sessions/*.md，仅 UI 回溯） |
| archive/ 目录 | 不再需要封存区 |
| ArchiveMode 3 种模式 | 每轮提取，不再需要归档模式 |
| ArchiveReason 4 种原因 | 每轮提取，不再需要归档原因 |

## 三、新存储架构

### 3.1 目录结构

```
{dataDir}/
├── memora.db              ← SQLite（唯一的记忆存储 + 会话索引）
└── sessions/              ← 会话记录（原始消息，仅供回溯）
    ├── 2026-06-11-001.md
    ├── 2026-06-11-002.md
    └── 2026-06-10-001.md
```

配置文件（`agent-config/` + `.memora/`）不在此目录中——它们是**源**，启动时加载到 SQLite。

### 3.2 SQLite Schema

```sql
CREATE TABLE IF NOT EXISTS memories (
    id          TEXT PRIMARY KEY,
    content     TEXT NOT NULL,
    source      TEXT NOT NULL,
    name        TEXT NOT NULL,
    created_at  TEXT NOT NULL,
    accessed_at TEXT NOT NULL,
    score       REAL NOT NULL DEFAULT 0.5
);

CREATE INDEX IF NOT EXISTS idx_memories_source ON memories(source);
CREATE INDEX IF NOT EXISTS idx_memories_score ON memories(score);
```

**与当前 Memora 的对比：**

| 当前 | 新 | 变化 |
|------|-----|------|
| type TEXT NOT NULL | source TEXT NOT NULL | 枚举 → 开放字符串 |
| permanence TEXT NOT NULL | **删除列** | 召回策略不再固化 |
| tags TEXT DEFAULT '[]' | **删除列** | source 标签足够 |
| weight REAL DEFAULT 0.5 | score REAL DEFAULT 0.5 | 改名 |
| updated_at TEXT | **删除列** | 用 accessed_at 替代 |
| file_path TEXT | **删除列** | id 中已包含来源 |

### 3.3 FTS5 全文索引（可选增强）

```sql
CREATE VIRTUAL TABLE IF NOT EXISTS memories_fts USING fts5(
    id, content, name, source,
    content='memories',
    content_rowid='rowid'
);
```

FTS5 提供中文全文搜索能力，召回时比 LIKE 查询更精准。如果不需要全文搜索，用 LIKE + 关键词匹配即可（见召回逻辑）。

### 3.4 文件系统 → SQLite 同步

**原则：文件系统是源，SQLite 是索引。单向同步，启动时增量 upsert。绝非全量重建。**

```
Agent 启动 → 扫描 agent-config/ + .memora/ 所有 .md 文件
  → 对每个文件 upsert 到 SQLite（id 匹配则更新，不匹配则插入）
  → 只 upsert source=['persona','rule','skill'] 的记录（配置文件来源）
  → 绝不触碰 source='insight' 或 source='profile' 的记录（对话提取来源，无对应文件）
```

> **⚡ 排雷修正 R-01 [P1]：** 原方案曾写"启动时全量重建"——会丢失之前提取的 insight 和 profile（它们仅有 SQLite 中存，无对应文件）。修正为增量 upsert，只操作配置来源的记录。

**配置来源 vs 提取来源：**

| 来源 | source | 有对应文件？ | 启动时行为 |
|------|--------|------------|-----------|
| agent-config/personas/*.md | persona | 是 | upsert |
| agent-config/rules/*.md | rule | 是 | upsert |
| agent-config/skills/*.md | skill | 是 | upsert |
| .memora/rules/*.md | rule | 是 | upsert |
| .memora/skills/*.md | skill | 是 | upsert |
| 对话中 LLM 提取 | insight | **否** | **不动（保留）** |
| 用户画像提取 | profile | **否** | **不动（保留）** |

**source 赋值规则（文件加载时）：**

```typescript
// 从文件路径自动推断 source（目录映射 + frontmatter 覆盖）
function inferSource(filePath: string, frontmatterSource?: string): string {
  // 优先：frontmatter 中显式声明的 source
  if (frontmatterSource) return frontmatterSource;

  // 回退：目录路径映射
  if (filePath.includes('personas/')) return 'persona';
  if (filePath.includes('/rules/')) return 'rule';
  if (filePath.includes('/skills/')) return 'skill';

  // 默认
  return 'unknown';
}
```

> **⚡ 排雷修正 R-02 [P2]：** 补充 inferSource() 机制。agent-config/ 下的 `.md` 文件是设计文档而非代码，要求每个文件都写 `frontmatter source:` 不现实。目录结构本身就是最自然的分类——放在 `rules/` 下的就是规则，不需要再声明一遍。frontmatter 覆盖作为"显式声明优先"的逃生门即可。

与当前 `MemoryLoader.loadAllToIndex()` 的区别：
- **不再全量重建**，改为按 source 增量 upsert
- 不再区分 4 种 STARTUP_SCAN_TYPES——扫描所有 `.md` 文件，source 由 frontmatter 或目录映射决定
- 不再检查 permanence——所有配置文件都加载
- 保留 `isPlaceholderContent()` 跳过空壳模板
- 保留工具不进记忆（`tools/` 由 `registerTool` 注册）

## 四、召回逻辑

### 4.1 设计原则

**每次用户发消息，从所有记忆中搜索最相关的几条注入上下文。**

不需要话题概念，不需要漂移检测，不需要管理器。

### 4.2 召回流程

```
用户发消息
    │
    ▼
┌───────────────────────────────────────┐
│ Step 1: 提取查询关键词                  │
│   从用户输入中提取关键词                 │
│   （Intl.Segmenter 中文分词 + 停用词过滤） │
└──────────────┬────────────────────────┘
               │
               ▼
┌───────────────────────────────────────┐
│ Step 2: 搜索记忆                        │
│   方案 A: FTS5 全文搜索                 │
│   方案 B: LIKE 关键词匹配               │
│   查询条件:                              │
│     - content 包含关键词                │
│     - OR name 包含关键词                │
│     - ORDER BY score DESC              │
│     - LIMIT 10                         │
└──────────────┬────────────────────────┘
               │
               ▼
┌───────────────────────────────────────┐
│ Step 3: 过滤与排序                       │
│   - 排除 source='persona' + 'rule'     │
│     （已单独注入 system prompt，避免重复） │
│   - 按 score 降序排列                   │
│   - 取 top N（默认 5）                  │
└──────────────┬────────────────────────┘
               │
               ▼
┌───────────────────────────────────────┐
│ Step 4: 注入上下文                       │
│   拼接到 system prompt 末尾              │
│   格式:                                 │
│   [相关记忆]                            │
│   - {source}: {name}                   │
│     {content 摘要}                      │
└───────────────────────────────────────┘
```

> **⚡ 排雷修正 R-09 [P1]：** Step 3 排除清单原只写了 `persona`，但 `rule` 也在 Layer 2 单独注入。若不排除，规则会在"相关记忆"中重复出现，浪费 token。修正为排除 `source NOT IN ('persona', 'rule')`。

### 4.3 关键词提取

**方案：优先使用 Intl.Segmenter（浏览器/Node.js 内置），回退 2-gram。**

```typescript
function extractKeywords(input: string): string[] {
  const words: string[] = [];

  // 优先使用 Intl.Segmenter 做中文分词（比 2-gram 精准）
  try {
    const segmenter = new Intl.Segmenter('zh-CN', { granularity: 'word' });
    for (const { segment, isWordLike } of segmenter.segment(input)) {
      if (isWordLike && segment.trim().length >= 2) {
        words.push(segment.trim());
      }
    }
  } catch {
    // 回退：2-gram
    // 注意：必须过滤停用词，否则 "角色设定" → "色设" 无意义
    const cleaned = input.replace(/[^\u4e00-\u9fff]/g, '');
    for (let i = 0; i < cleaned.length - 1; i++) {
      words.push(cleaned[i] + cleaned[i + 1]);
    }
  }

  // 英文词提取
  const englishWords = input.match(/[a-z]{2,}/gi) || [];
  words.push(...englishWords.map(w => w.toLowerCase()));

  // 去重 + 停用词过滤
  const stopwords = new Set([
    '的', '了', '是', '在', '我', '有', '和', '就', '不', '人', '都',
    '一', '一个', '上', '也', '很', '到', '说', '要', '去', '你', '会',
    '着', '没有', '看', '好', '自己', '这', '那', '什么', '怎么', '可以',
    '这个', '那个', '他们', '我们', '因为', '所以', '但是', '如果', '虽然',
    '能', '把', '被', '让', '给', '对', '从', '为', '比', '与', '或',
    '吗', '呢', '吧', '啊', '哦', '嗯', '呀', '哈',
  ]);

  return [...new Set(words)].filter(w => w.length >= 2 && !stopwords.has(w));
}
```

> **⚡ 排雷修正 R-06 [P2]：** 原方案默认 2-gram 分词会产生无意义 token（"角色设定"→"色设"）。已改为 Intl.Segmenter 优先，2-gram 仅作回退。

**关键词提取后的 SQL 构建（参数化查询 + IN 子句，避免 OR 爆炸）：**

```typescript
function buildRecallQuery(keywords: string[]): string {
  if (keywords.length === 0) return null;

  const conditions = keywords.map(k =>
    `(content LIKE '%${escapeLike(k)}%' OR name LIKE '%${escapeLike(k)}%')`
  ).join(' OR ');

  return `
    SELECT id, source, name, content, score
    FROM memories
    WHERE source NOT IN ('persona', 'rule')
      AND (${conditions})
    ORDER BY score DESC
    LIMIT 5
  `;
}

// 转义 LIKE 通配符，防止注入
function escapeLike(str: string): string {
  return str.replace(/[%_]/g, '\\$&');
}
```

> **⚡ 排雷修正 R-08 [P2]：** 关键词 > 5 个时 OR 条件过多会影响性能。此时降级为只搜索前 5 个关键词，或切换到 FTS5 全文索引。

**与 TopicMount 的 Jaccard 对比：**

| 维度 | TopicMount（当前） | 朴素关键词（新） |
|------|-------------------|-----------------|
| 代码量 | 200+ 行 | ~20 行 |
| 分词方式 | Intl.Segmenter | 2-gram + 空格分词 |
| 相似度算法 | Jaccard 集合相似度 | 不需要——直接搜索 |
| 话题漂移检测 | 需要（阈值 0.35/0.25） | 不需要——每次都搜索 |
| 召回时机 | 仅在"漂移"时召回 | **每次用户发消息都召回** |
| 复杂度 | 高（状态机 + 阈值调优） | 低（无状态） |

### 4.4 召回 SQL

**方案 A：LIKE 关键词匹配（简单，无 FTS5 依赖）**

```sql
SELECT id, source, name, content, score
FROM memories
WHERE source NOT IN ('persona', 'rule')
  AND (content LIKE '%关键词1%' OR content LIKE '%关键词2%' OR name LIKE '%关键词1%')
ORDER BY score DESC
LIMIT 5
```

**方案 B：FTS5 全文搜索（更精准，需要 FTS5 编译支持）**

```sql
SELECT m.id, m.source, m.name, m.content, m.score
FROM memories_fts f
JOIN memories m ON f.rowid = m.rowid
WHERE memories_fts MATCH '角色 OR 设定'
  AND m.source NOT IN ('persona', 'rule')
ORDER BY rank, m.score DESC
LIMIT 5
```

### 4.5 注入格式

最终注入上下文包含两个区块：

**① `[相关记忆]`** — 从 SQLite 按关键词召回，注入完整 content（不截断），默认 top 5。

**② `[最近对话]`** — 从 AgentLoop 获取最近 3 轮对话（user + assistant 原文），固定注入。不引入话题检测——3 轮噪声的 token 成本可接受，且 LLM 有能力忽略不相关的上下文。

```markdown
[系统指令：你是小说创作助手]

[相关记忆]
- [rule] 核心规则：每 500 字必须有一件事发生
- [insight] 主角偏好暗黑风格，性格冷峻但内心善良
- [insight] 用户偏好：不喜欢话痨型配角，喜欢沉默型角色
- [profile] 用户信息：在写一本玄幻小说，目标平台起点中文网

[最近对话]
用户：你觉得主角叫什么名字好？
助手：看你想要什么风格，冷峻型还是热血型？
用户：冷峻型，叫林默吧
助手：好的，记下了。

[用户消息]
帮我写一段主角遇到反派的场景
```

**注入位置：** system prompt 末尾，用户消息之前。`[相关记忆]` 和 `[最近对话]` 顺序不固定——最近对话放在前面更容易让 LLM 感知当前语境。

> **设计取舍：** 不用动态话题过滤。3 轮固定注入的成本约 500-800 tokens，占总窗口 < 2%。如果后续实测发现 token 浪费严重，可用轻量关键词重叠法过滤（~20 行代码，插拔式）。

## 五、归档与提取逻辑

### 5.1 设计原则

**每轮问答结束后异步提取记忆，一轮一提，原子级粒度。**

人的思维是散的——刚在说天气，下一句就聊明星，再下一句讨论哲学。会话级摘要会把不相关的话题混为一谈。只有**一轮问答**才是语义连贯的最小单元。

不需要 4 种归档原因，不需要 3 种归档模式，不需要会话边界检测。

### 5.2 触发时机

**用户输入时判断，回答后提取。决策点在提问时，不在回答后。**

```typescript
// Agent.chat() 核心流程
async chat(input: string): Promise<string> {
  // Step 1: 输入分类（提问时，零成本）
  const shouldExtract = await this.classifyInput(input);

  // Step 2: 正常对话
  const assistantContent = await this.agentLoop.processUserInput(input);

  // Step 3: 如果分类为 extract，异步提取 insight
  if (shouldExtract === 'extract') {
    const promise = this.extractAndStore(input, assistantContent);
    promise.catch(() => null); // 失败不影响对话
  }

  return assistantContent;
}
```

| 场景 | 行为 |
|------|------|
| 通用知识 / 问候 / 确认 | 输入时判定 skip → LLM 回复 → 结束（零开销） |
| 用户专属 / 创作相关 | 输入时判定 extract → LLM 回复 → 异步提取 insight |
| 用户切换项目 | 切换前等待当前提取完成（awaitPendingExtractions） |
| 用户关闭应用 | 关闭前等待当前提取完成 |

### 5.3 输入分类：三层架构

**宿主提供领域关键词，Memora 内置 LLM 精判。各司其职。**

```
用户输入
    │
    ▼
┌──────────────────────────────────────┐
│ Layer 1: 通用规则（Memora 内置）       │
│   短输入 / 问候 / 确认 → skip         │
│   命中 → 直接返回                     │
│   未命中 → 进入 Layer 2               │
└──────────────┬───────────────────────┘
               │
               ▼
┌──────────────────────────────────────┐
│ Layer 2: 宿主关键词（宿主提供）        │
│   命中创作关键词 → extract             │
│   命中用户专属关键词 → extract         │
│   命中 → 直接返回                      │
│   未命中 → 进入 Layer 3                │
└──────────────┬───────────────────────┘
               │
               ▼
┌──────────────────────────────────────┐
│ Layer 3: LLM 精判（后台异步优化）      │
│   不阻塞主对话 → 默认 extract          │
│   LLM 返回 skip → 异步回滚            │
└──────────────────────────────────────┘
```

**Layer 1 — 通用规则（Memora 内置，零成本）：**

```typescript
function classifyByRules(input: string): 'skip' | null {
  const trimmed = input.trim();
  if (trimmed.length < 5) return 'skip';
  const trivialPatterns = /^(你好|hi|hello|ok|好的|嗯|知道了|谢谢|thanks|对|不是|是的)/i;
  if (trivialPatterns.test(trimmed)) return 'skip';
  return null; // 未命中，交给下一层
}
```

**Layer 2 — 宿主关键词（宿主提供，零成本）：**

```typescript
// 宿主注册关键词（Memora 开放接口）
agent.setMemoryKeywords({
  domain: ['主角', '角色', '情节', '设定', '世界观', '伏笔', '章节', '写作', '创作', '小说', '故事', '人物', '反派', '配角', '大纲'],
  personal: ['我', '我的', '我觉得', '我喜欢', '我不喜欢', '帮我', '记住', '之前', '上次'],
});

function classifyByHostKeywords(input: string, keywords: MemoryKeywords): 'skip' | 'extract' | null {
  if (keywords.domain.some(k => input.includes(k))) return 'extract';
  if (keywords.personal.some(k => input.includes(k))) return 'extract';
  return null; // 未命中，交给下一层
}
```

**Layer 3 — LLM 精判（后台异步优化，不阻塞主对话）：**

```typescript
async function classifyByLLM(input: string): Promise<'skip' | 'extract'> {
  const result = await llm.chat(`
    判断以下用户输入是否包含值得长期记忆的信息。
    值得记忆：用户偏好、决策、设定、创作内容、个人经历、明确要求记住的内容。
    不值得记忆：问候、确认、闲聊、通用知识科普、与创作无关的通用问题。
    只回答 "skip" 或 "extract"。
    用户输入：${input}
  `);
  return result.trim().toLowerCase().includes('extract') ? 'extract' : 'skip';
}
```

> **⚡ 排雷修正 R-10 [P2]：** 原方案在 Layer 3 `await classifyByLLM()`，用户发消息后要等两次 LLM 调用（分类 + 对话），延迟翻倍。修正为：Layer 1+2 未命中时直接返回 `'extract'`（宁可多提，不可漏提），LLM 精判作为后台异步优化——如果判为 skip，异步删除刚提取的 insight。影响：首次模糊输入会多提取一条（很快被后台删除），不影响对话体验。

**三层串联：**

```typescript
async function classifyInput(input: string): Promise<'skip' | 'extract'> {
  // Layer 1: 通用规则
  const ruleResult = classifyByRules(input);
  if (ruleResult) return ruleResult;

  // Layer 2: 宿主关键词
  const keywordResult = classifyByHostKeywords(input, this.hostKeywords);
  if (keywordResult) return keywordResult;

  // Layer 3: 默认 extract + 后台异步精判修正
  return 'extract';
}
```

| 调用 | 使用的模型 | 说明 |
|------|----------|------|
| 主对话 | 用户配置的模型 | 正常聊天 |
| LLM 精判（classifyByLLM） | 复用的 provider 实例 | 轻量调用（~20 tokens 输入，1 token 输出） |
| 提取 insight（extractAndStore） | 复用的 provider 实例 | 中等调用（~500 tokens 输入，~50 tokens 输出） |

> **⚡ 排雷修正 R-13 [P2]：** 补充模型使用策略。分类和提取都复用用户配置的同一个 provider 实例，不引入额外模型依赖。调用量很小（分类 1 token 输出，提取 ~50 tokens 输出），对用户配额影响可忽略。

**Score 衰减机制：**

```typescript
// 每次召回时，被召回的记忆 score 略微提升（上限 1.0）
function boostScore(memory: Memory): void {
  memory.score = Math.min(1.0, memory.score + 0.05);
  memory.accessed_at = new Date().toISOString();
}

// 定期衰减：长时间未访问的记忆 score 逐渐降低（下限 0.1）
function decayScores(memories: Memory[], now: Date): void {
  const ONE_DAY = 24 * 60 * 60 * 1000;
  for (const m of memories) {
    const daysSinceAccess = (now.getTime() - new Date(m.accessed_at).getTime()) / ONE_DAY;
    if (daysSinceAccess > 7) {
      m.score = Math.max(0.1, m.score - 0.02 * Math.floor(daysSinceAccess / 7));
    }
  }
}
```

> **⚡ 排雷修正 R-04 [P2]：** 原方案未定义 score 的更新/衰减机制，导致新旧记忆权重相同，召回结果不体现新鲜度。补充 boostScore（召回时提升）+ decayScores（7 天衰减）。

### 6.2 注入代码（伪代码）

```typescript
function buildSystemPrompt(query: string): string {
  const parts: string[] = [];

  // Layer 1: 角色人格
  const persona = memoryStore.getActivePersona();
  if (persona) parts.push(persona.content);

  // Layer 2: 创作规则
  const rules = memoryStore.getBySource('rule');
  parts.push(rules.map(r => r.content).join('\n\n'));

  // Layer 3: 用户画像
  const profile = memoryStore.getBySource('profile');
  if (profile.length > 0) {
    parts.push('[用户画像]\n' + profile.map(p => `- ${p.content}`).join('\n'));
  }

  // Layer 4: 相关记忆（召回）
  const recalled = memoryStore.search(query, { exclude: ['persona', 'rule', 'profile'], limit: 5 });
  if (recalled.length > 0) {
    parts.push('[相关记忆]\n' + recalled.map(m =>
      `- [${m.source}] ${m.name}: ${m.content}`  // 完整注入，不截断
    ).join('\n'));
  }

  // Layer 5: 最近对话（最近 3 轮，固定注入）
  const recentHistory = agentLoop.getRecentHistory(3);
  if (recentHistory.length > 0) {
    parts.push('[最近对话]\n' + recentHistory.map(m =>
      `${m.role}：${m.content}`
    ).join('\n'));
  }

  // Layer 6: 工具描述（由 AgentLoop 自动处理，此处不展开）

  return parts.join('\n\n');
}
```

> **⚡ 排雷归档 R-14 [P2]（已知限制）：** `getBySource('rule')` 返回全部规则文件一起注入。泊文当前仅 2 个规则文件（agent-config + .memora 各约 2 个），总量 < 2000 tokens，可接受。规则增长到 10+ 时再引入"关键规则"标签区分。
