道生万物 · 通用交互输入框架

道 → 一（统一接口）→ 二（资源/动作）→ 三（角色/任务/标准）→ 万物 → 复归于道
沉淀日期：2026-08-07 · 方法：第一性原理 + 对抗式审查 · 版本：v2.6（提纯：保留最终核心思想） · 来源：基于 memora 项目（自家实例）+ 提示工程 / Web 语义 / 编程范式等独立惯例的通用化推演（详见附录）
借喻声明：本文借道家「道生一，一生二，二生三，三生万物」之生成论形态，行工程建模之实。道家原义中「二」为阴阳、「三」为阴阳和合（冲气），本文的「二」为动静二分、「三」为三个并列维度，属借喻性重构，非严格义理对应——取「层层生成」之形，不取「阴阳和合」之义。同理，四元组 = 三元坐标 + 资源基底——资源是生成的物质条件而非第四坐标，故称「三生万物」而非「四生万物」。
定位（叙事校准）：本文是《落地体验输入系统梳理》（体验入口）所推导机制的结构命名与哲学收束——体验篇先确立六个用户场景与机制族，本文再用「道 → 一 → 二 → 三 → 万物 → 复归于道」为同一套结构命名。本文不是设计源头，是命名容器；设计决策的检验标准在体验篇（「机制服务谁 / 体验靠什么实现」两条链闭合）。阅读顺序：先读体验篇，需要结构命名时再进本文。适用范围：任意 Agent / LLM 应用的输入设计——请求协议定义、提示词结构、工具调用约定、交互状态建模。本框架与具体项目解耦，不依赖任何特定实现；项目实例仅作验证参照（见附录）。

道 · 交互之本

框架的起点：交互本身

道 = 一次交互本身（信息流转）：输入 → 处理 → 输出。它是不可名状的本源，一切皆从这一次交互展开。对 LLM 应用而言，模型天然无状态——每一次交互都是从「道」重新开始，这正是框架闭环（复归于道）存在的原因。

一 · 统一输入接口

第一原则：一切请求走同一协议（输入侧）
  • 含义：所有输入（任何来源、任何形式）经同一接口进入系统，结构同构。
  • 边界：此处指输入侧协议（请求如何进入系统），不是存储/输出侧契约。实例：tool_call JSON、chat() 签名、ChatCompletion 消息结构、HTTP 请求语义。
  • 层面说明（协议族收敛 v2.3）：本文的「一」是协议族而非单个协议——按交互模式分两个成员：Request 协议（一问一答：完整自包含请求）与 SessionEvent 协议（不中断模型：增量事件，见《不中断工作模型演进》）。二者共享同一输入侧位置（请求如何进入系统）、同一结构基底（四元组），差别在「完整 vs 增量」语义。工程落地时的 parse / renderer 是协议族的实现组件（输入解析器 + 排版器），不再是「一」本身——「一」= 协议形状约束，parse/renderer = 协议执行者。
  • 为什么必须存在：自然语言天然不完整（缺省普遍），接口的职责是「缺省补全」。没有统一接口，缺省无处补，万物无法生成（见「三生万物 · 机制②」）。

二 · 资源与动作

一生二：所有输入二分
维度资源动作
本性静止 · 被动动态 · 主动
内容背景信息、数据、上下文、记忆、历史指令、意图、对资源的操作
计算机类比数据（操作数）代码（操作符）

收拢规则：所有非指令的内容都归为资源——一刀切断分类爆炸。

资源的三层构成

资源不是单一类型，按来源与生命周期分三层，全部落在「资源」槽内（不另立维度）：

层内容说明
静态资源用户文档、背景资料、参考库、知识库低频变动；按确定性分级走注入/检索（见落地篇 §04）
对话记录（原始历史）完整交互历史（用户消息/Agent 消息/工具调用）原始对话记录本身就是资源——它是「记忆」的未提炼形态；会话内常驻于热窗口
会话状态（检查点）目标、计划、角色/标准、检查点、热窗口不中断模型下新增成员；是「继续」类增量的引用对象（见「三源融合」补全链）

「记忆即资源」的准确含义：记忆 = 对话记录（原始）+ 提炼记忆（归档摘要）双层；二者都是资源的供给者——原始记录直接承载上下文，提炼记忆承载跨会话知识。

核心洞察（书的比喻）：资源本身是静止的，没有动作它就是死数据；同一资源在不同「角色」下产出完全不同——这正是 LLM 的本质（同一上下文，不同角色设定产生不同输出）。

资源 ⇄ 动作的递归性

资源和动作不是绝对的，是视角问题：一段文本在解析前是资源，解析后是动作；任务的产出可成为下一轮的资源；「分析一段指令」本身就是把动作当作资源（LISP 的 code-as-data）。这个递归性让二分无需新增类别就能覆盖无限场景，也是「三生万物」生成侧的真正引擎。

三 · 角色 / 任务 / 标准

二生三：动作的三个近似正交维度
要素本质示例（书）
角色（定位/视角）以什么身份解读资源农民 → 当柴火烧；科学家 → 分析内容；作者 → 审校结构
任务（行为 + 对象）对资源做什么读（默认）/ 背诵 / 只看片段 / 撕毁 / 引用第 3 章
标准（目标/约束）做到什么程度背诵全书前 3 章 / 准确率 95% / 10 分钟内完成

对象绑定：动作需显式绑定「作用于哪个资源」——对象选择归入任务的参数（行为 = 动词 + 对象），标准负责范围/时限。

「近似正交」而非「正交」：三要素大体独立，但存在耦合——角色约束任务的可选集（农民不会「审校」），标准受任务类型约束（背诵的标准 ≠ 焚烧的标准）。
跨领域一致性：此三分与提示工程「Role + Task + Constraint」三段式、自然语言理解的三问（谁 · 做什么 · 做到怎样）一致——多个独立领域收敛到同一结构，是框架通用性的佐证。

三生万物 · 三个层次

「生万物」拆分为三个层次：生成机制 / 运行闭环 / 边界条件

A · 生成机制（如何从三到万物）

  1. 坐标组合（最浅层）：三要素近似正交坐标轴，资源是物质。任意具体请求 = 四元组 (角色, 任务, 标准, 资源)。取值域叉乘，即生万物。
  2. 缺省补全（接口的职责）：自然语言天然不完整——角色缺省补「通用助手」，标准缺省补「尽力而为」，资源缺省补「无」。万物 = 补全后的完整四元组。
  3. 资源 ⇄ 动作递归（深层引擎）：见「二」节——递归性让二分覆盖无限场景，无需新增类别。

B · 运行闭环（不属于「生」，属于「归」）

  1. 记忆回流：交互的万物沉淀为记忆，记忆成为下一轮请求的资源——万物复归于道。模型无状态，记忆让系统连续演化。此条是时间维度的循环，与「生成」不同层次。

C · 边界条件（框架外依赖）

  1. 涌现：三坐标齐备时，模型组合能力产生超越输入的新信息。此属模型侧能力，框架只保证输入完整，不承诺涌现本身。

三源融合 · 统一接口的落地

缺省补全的值从哪来：来源维度与结构维度分离

「一 · 统一输入接口」的职责是缺省补全——但补全的值从哪里来？答案是三个输入来源。核心原则：来源是元信息，结构是本质——三个来源不是从「二/三」层延伸出来的，而是「一」的三个供给者；「二/三」描述融合后四元组的结构，与值来自何处无关。若把来源塞进结构（如「资源分内置/记忆/用户三类」），四元组会爆炸为 81 种组合而本质不变——这正是「非指令皆资源」收拢规则要防止的分类爆炸。

优先级来源供给的槽位
P1 显式（现在）用户输入实时任务 + 实时标准 + 附带资源
P2 推断（过去）记忆沉淀（对话记录原始历史 + 提炼记忆）历史角色偏好（角色）、历史目标（任务要素）、历史偏好（标准）、历史内容（资源）、对话记录（上下文）——目标/计划语义上属「任务」维度；其被存储于会话状态/检查点（见《不中断工作模型演进》）属存储位置问题，不改变语义归类
P3 兜底（设计）系统内置角色默认、约束默认、能力模板（skill）
用户文档（用户主动撰写的固定内容）不是第四源——它按确定性等级跨 P2/P3 两个渠道分流：高确定性（用户声明「每轮必须遵守」）归 P3 系统内置侧（同 rule 确定性注入）；低确定性 / 长文（背景资料、参考库）归 P2 记忆侧（语义召回）。「三源」指供给渠道（现在/过去/设计），用户文档是「用户撰写的设定」，沿渠道分流而非新增渠道——否则四元组会再次分类爆炸。

记忆全覆盖四元组

记忆沉淀的是「历史完整四元组」——既是资源供给者（内容），也是动作要素供给者（历史目标、历史标准、历史角色偏好）。记忆不是只覆盖资源侧，它覆盖四元组全集——这正是「万物复归于道」的准确含义：万物（完整请求）归档为记忆，下次补全时从记忆中抽取填空。载体说明：角色偏好落 persona 设定文件、目标/计划落会话状态/检查点、内容/洞察落召回记忆——存储载体分属，语义同归四元组，不改变「记忆覆盖全集」的归类。

融合器形态

接口 = 一个入口 + 四槽位填充。补全链的核心规则（v2.3 修正）：P1 显式优先，但分「完整覆盖」与「增量引用」两种输入形态——

  • 完整覆盖（特例）：输入是自包含请求（含完整角色/任务/标准/资源），P1 直接覆盖对应槽位，P2/P3 仅作缺省。
  • 增量引用（主路径）：输入是增量/指代（如「继续」「把那个也加进来」），P1 是对资源层会话状态的引用——「继续」= 任务槽增量（动作=continue，对象=currentGoal），直接引用常驻的对话记录/会话状态推进，无需召回解析。增量槽引用状态、新值槽覆盖，槽位级混合。
v2.3 关键修正：原「每槽独立走 P1→P2→P3 优先级链，互不干扰」的覆盖模型仅适用于完整自包含输入（特例）。真实交互以增量为主——用户输入常是相对既有状态的引用，「继续」类输入在会话状态常驻时直接引用资源层推进；仅当状态不在场（冷恢复/跨会话）才退回 P2 记忆召回解析（依赖式降级路径）。覆盖、增量、依赖三模型由此收敛为「增量为主、覆盖/依赖为特例」。
落地对应（通用）：现有 Agent 架构的「启动加载（内置）→ 按需召回（记忆）→ 实时输入（用户）」三机制即此结构的实例——理论命名先于实现，落地即确认。三源命名统一按优先级表述：P1 用户输入（显式·现在）> P2 记忆沉淀（推断·过去）> P3 系统内置（兜底·设计）。
