01 · 第一性：用户到底在做什么

所有机制都从这六个体验场景长出来——它们是用户对 Agent 不可妥协的诉求

抛开一切抽象，用户与 Agent 交互时只有六个不可妥协的体验诉求。每个诉求都必然推导出至少一个机制；没有对应体验诉求的机制，就是过度设计。

体验场景用户诉求（第一性）推导出的机制违背时用户感受
① 发起说一句话就开始干活，别让我配置统一输入接口 + 缺省补全链（P1 显式 → P2 记忆 → P3 内置）「为什么还要填这么多设置」
② 继续说「继续」就能接着上次干，不失忆对话记录 ∈ 资源层常驻 + 增量引用（任务槽引用 currentGoal）「你怎么忘了刚才的事」
③ 纠正中途说「不对，改成那样」能改向且不跑偏增量事件（correction）+ 目标版本控制（goalVersion 防漂移）「越改越离谱 / 改了没用」
④ 追问系统不懂时问我，但少问、问到点子上P4 暂停询问（可选·终极补全）+ 滥用抑制（连续 2 次后必须给方案）「一直在问我，烦死了」
⑤ 恢复关掉重开还能接着干，不重复劳动检查点 + 恢复协议（快照→热窗→温召回→契约重注入→校验）「重启就要重新来一遍」
⑥ 信任能看见它在干什么、改了什么、为什么状态机三态可见（RUNNING/PAUSED/ERROR）+ 事件意图分类 + 契约分级路径「黑盒，不敢让它干」
一句话：用户不关心你的四元组、不关心你的触发链——他关心的是「我说的话你能懂、你能记住、你能改对、你能问我、你能续上、我能看懂」。所有机制都只是这六个诉求的实现手段。

02 · 机制推导：从体验长出来的设计

六大机制族 —— 每个都对应至少一个体验场景

机制族 A：输入理解（服务体验 ① 发起 + ② 继续）

  • 统一输入接口：一切输入走同一入口（协议族：Request 完整请求 / SessionEvent 增量事件）。体验含义：用户不需要知道系统内部怎么分类输入，怎么说都行。
  • 缺省补全链 P1→P2→P3：用户没说全（缺角色/缺标准/缺资源），系统用「显式 → 记忆 → 内置」补全。体验含义：用户说半句话也能干活。
  • 增量引用（主路径）：「继续」「把那个也加进来」这类输入是相对既有状态的增量，直接引用资源层会话状态推进，无需召回解析。体验含义：用户可以用最短的话表达最复杂的延续。

机制族 B：状态承载（服务体验 ② 继续 + ⑤ 恢复）

  • 资源三层：静态资源（文档/资料）+ 对话记录（原始历史）+ 会话状态（目标/计划/检查点）——全部在「资源」槽。体验含义：系统记得你说过的每句话，且知道当前干到哪。
  • 检查点 + 恢复协议：快照反序列化 → 热窗口载入 → 温记忆按需召回 → 契约重注入 → 恢复校验。体验含义：重启不失忆、不重复。

机制族 C：方向控制（服务体验 ③ 纠正）

  • 增量事件 + 意图分类：correction 类输入只更新变动的槽位，注入执行上下文。体验含义：用户一句话就能改向。
  • 目标版本控制（goalVersion）：每次重规划锚定原始目标，确定性校验偏差（约束哈希 + 相似度阈值），超阈值提示新会话。体验含义：改了不跑偏，跑偏能发现。

机制族 D：澄清协议（服务体验 ④ 追问）

  • P4 暂停询问：前三层补全都不够时，Agent 主动暂停问一句。体验含义：问比猜好——猜错更烦。
  • 滥用抑制：信息缺失到无法推进才问；高风险操作才问；连续 2 次后必须给可执行方案。体验含义：少问、问到点子上。

机制族 E：可见性（服务体验 ⑥ 信任）

  • 状态机三态：RUNNING / PAUSED / ERROR，UI 可展示，ERROR 保留原因。体验含义：用户知道它活着、停了、还是出错了。
  • 契约分级路径：rule 等确定性契约 100% 在场（注入），persona/skill 输入驱动匹配后注入，经验内容按需召回。体验含义：安全规则永不丢——用户敢把重要约束交给你。

机制族 F：表达引擎（服务体验 ①-⑥ 共用的输出侧）

  • 渲染器（排版）+ 上下文管理器（窗口/预算/恢复）：把四层输入稳定排版为 Prompt，动态层后置高注意力。体验含义：用户输入永远是「最后说的话」，模型注意力最强处。
  • 输出格式路由：根据任务类型和上下文决定输出格式（纯文本回答 / 结构化报告 / 工具调用 / 确认提问）。体验含义：输出自动适配场景，不用用户规定"请用列表回答"。
  • 结果展示策略：工具调用结果按类型分级展示——成功→摘要+关键数据；失败→原因+可操作建议；长结果→分页/折叠。体验含义：用户看到的是"结论"，不是原始 JSON。
  • 错误信息分级：运行时错误按严重程度分级呈献给用户——提示级（可忽略）、确认级（需用户决策）、告警级（需干预）。体验含义：错误不打断流程，只在需要用户时出现。
对抗式检查：机制族 A-F 与体验场景 ①-⑥ 一一对应，无孤儿机制、无覆盖不到的体验。若未来要新增机制，先问「它服务哪个体验场景」——答不上来就不加（复杂度守恒）。

03 · 抽象收敛：13 → 7 核心 + 6 可选

落地标准的第二刀：不是所有想清楚的抽象都要平铺，核心最小集 + 可选按需启用。13 = 机制族 A-F 推导抽象总数（增量事件与意图分类拆计）：统一输入接口 / 缺省补全链 / 增量引用 / 资源三层 / 检查点+恢复协议 / 增量事件 / 意图分类 / 目标版本控制 / P4 暂停询问 / 滥用抑制 / 状态机三态 / 契约分级路径 / 渲染器+上下文管理
层级抽象说明
核心 7 项
（任何落地必须有）		① 统一输入接口（协议族）一切输入入口同构
② 缺省补全链 P1→P3（+P4 可选）残缺输入可执行
③ 资源层（静态/对话/会话三层）系统有记忆、有状态
④ 分级路径（契约注入/经验召回）确定性契约不概率化
⑤ 增量引用 + 增量事件最短表达延续，改向不漂移
⑥ 检查点 + 恢复协议可恢复：快照→热窗→温召回→契约重注入→校验
⑦ 渲染器 + 上下文管理排版真理源 + 窗口/预算/恢复
可选 6 项
（按需启用）		触发链（粗召回→解析→精召回）仅会话开启/冷恢复需要
目标版本控制（goalVersion）长任务防漂移需要；短任务可省
事件意图分类（command/correction/clarify/chat）上下文污染风险高时启用
状态机三态（RUNNING/PAUSED/ERROR）不中断模型/长时运行时启用；ERROR 保留原因
tiebreaker 同档仲裁同优先级冲突时启用（服务 ③ 纠正/⑥ 信任：冲突仲裁结果可见）
热记忆窗口截断策略长会话防膨胀时启用（服务 ② 继续：持续会话不失控）
落地铁律：最小可落地版本 = 核心 7 项，基线模型 = 一问一答 + 会话持久化（检查点）——不做触发链、不做目标版本、不做意图分类、不做状态机三态也能跑通 ①-⑥ 全部体验（用最朴素的实现）。可选项只有在对应体验场景真正出现压力时才启用——抽象是贷款，体验是抵押，别提前透支。

04 · 用户旅程（体验视角的端到端）

一次完整交互的六个体验节点，标注每个节点动用了哪些机制
每个节点都有对应的机制服务，每个机制都能回溯到它服务的体验节点——这是「体验优先」的检验标准：从上往下问「这个机制服务谁」，从下往上问「这个体验靠什么实现」，两条链都要闭合。

05 · 哲学收束（最后一步：用道生万物语言命名）

设计已经完成——现在才轮到哲学。收束 = 命名容器，不是推导来源

以上全部机制，最后用《道生万物输入框架》的语言收束为一个可记忆的整体：

哲学层本文推导出的机制（先有）哲学命名（后有）
一 · 统一输入接口协议族（Request / SessionEvent）+ 缺省补全链 + 增量引用一切输入同构，从「一」进入
二 · 资源与动作资源三层（静态/对话/会话）系统只有「背景」与「指令」两类东西
三 · 角色/任务/标准四元组结构（角色 × 任务 × 标准 × 资源）每个请求的三个维度 + 物质基底
三生万物缺省补全 + 组合生成 + 增量演化从简单输入生成完整执行
复归于道对话记录/会话状态回流资源层万物沉淀为下一轮的资源
道一次交互本身（信息流转）体验的起点与终点
先有用户体验，后有机制；先有机制，后有哲学。
哲学是记忆术，不是设计原理——用「道生万物」记住这套结构，但永远从体验出发设计
