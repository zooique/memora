01 · 四层输入与稳定性谱系

三源的工程扩展：用户来源按处理路径细分为「用户文档 + 实时输入」（非三源本身的第四源）
层稳定性变化频率不可靠类型（影响设计）
程序设定（persona/rule/skill）最稳定几乎不变几乎无 —— 可缓存、编译期类型化。skill 归 P3 系统内置（能力模板），按 B 篇三源融合结论采纳
用户文档（固定内容）稳定低频（用户主动改）陈旧 —— 需变更检测（watcher）。按确定性分级：契约→P3 注入 / 资料→P2 检索（见 §04）
记忆层不可预测高频语义扭曲型：归档提炼+召回可能带偏方向且难察觉 —— 需降级 + 可解释。对应 D 篇「温记忆（recall）」
实时输入易变但方向可信每次信息缺失型：残缺/碎片但意图真实 —— 需补全 + 澄清
关键区分：记忆的不可靠是「语义扭曲型」，实时输入的不可靠是「信息缺失型」——前者需要降级与可解释，后者需要补全与澄清，二者驱动不同的接口策略。注：这里的「澄清」是《不中断工作模型演进》（D 篇）P4「暂停询问」的概念萌芽——本文件按一问一答模型仅声明澄清方向，不展开 P4（P4 需要 Agent 主动暂停能力，见 D 篇）。

02 · 核心决策：管道 vs 排版文档

答案不是二选一：工程侧管道，交付侧渲染
方案优点致命缺陷
纯管道（分层传）逐层控制/降级/预算LLM 对碎片消息注意力稀释；角色消息互相污染
纯文档（扁平拼）模型理解好无法逐层降级；任何层变化全量重排；来源不可追溯
管道 + 渲染两者兼得：工程能力 + 模型理解多一个渲染器抽象（复杂度守恒：收益覆盖故障面，成立）

对抗式提醒：顺序 ≠ 优先级

  • 「用户层最高优先级」用 priority 字段表达冲突仲裁（文档说 A、用户说 B → 取高优先），不要用「放最前面」表达——否则缓存全废。
  • 实时输入靠近生成端有副作用：模型可能顺着残缺硬编——渲染器应在实时输入区显式标注补全状态，把不确定性暴露给模型。
  • 「本质是文本」是底层事实，但排版决定解读：同一句话放在「设定区」与「输入区」，模型行为完全不同。

03 · 触发链：用户输入第一性

用户输入提供本次交互的方向 —— 它是所有后续检索的查询条件

第一性（查询条件来源）≠ P1（冲突仲裁优先级）：前者指所有召回/检索以用户输入为查询条件（见本节的触发语义）；后者指 B 篇三源仲裁中用户输入优先级最高（P1 显式 > P2 记忆 > P3 内置）。二者勿混——「放最前面」是排版位置，「取高优先」是冲突仲裁，见 §02 对抗式提醒。

第一性原理：记忆召回、角色匹配、文档检索都需要查询条件，而查询条件只能来自用户输入——因此用户输入是第一性触发条件。但「先解析、再抽取」是线性简化：解析本身需要上下文（「继续上次那个」没有记忆就无法解析），真实链路是两阶段互动：

设计要点：粗召回先行是因为它是无 LLM 的（零推理成本），让贵的 LLM 解析吃上粗召回的上下文——这是成本与质量的平衡点。精召回用解析出的角色/任务/标准作更精确的查询条件，是第二级增强。

v1.2 修正：会话内增量短路（主路径）

上图是会话开启 / 冷恢复 / 全新请求时的全量触发链。但真实交互以会话内增量为主——此时触发链短路：

场景触发路径说明
会话内增量（「继续」「把那个也加进来」）用户输入 → 直接引用资源层会话状态（对话记录/检查点/计划/目标）→ 槽位级 delta 合并 → 执行上一轮已规划（planList/currentGoal 在场），「继续」= 任务槽增量（动作=continue，对象=currentGoal），无需召回、无需 LLM 解析——增量槽引用状态、新值槽覆盖，混合输入同理
会话开启 / 冷恢复（新会话 / 窗口外继续）全量触发链：粗召回 → 输入解析 → 精召回 + 设定匹配状态不在场，「继续」退回指代解析——依赖式降级路径（即上图）；恢复协议见《不中断工作模型演进》
完整新请求（自包含）粗召回 → 输入解析 → 精召回（或直接覆盖）B 篇「完整覆盖」特例
收敛结论：增量为主路径、全量触发链为开启/恢复路径、覆盖为完整请求特例——三模型在 B 篇补全链中已统一（增量引用 / 完整覆盖 / 依赖降级），本文件触发链与之对齐：「解析需要上下文」仅对会话外场景成立，会话内无需解析。

对抗式修正：设定层不是全部「被输入驱动」

设定内容驱动方式为什么
rule（安全规则等）无条件静态基线（每轮全量注入）契约必须 100% 在场——规则丢失 = 安全漏洞
persona / skill输入驱动匹配角色选择、技能触发本质是查询

04 · 分级路径：契约注入 vs 经验召回

统一召回路径是错误方向 —— 它把确定性契约概率化

现状澄清：memora 不是统一召回，而是分级——persona/skill 不参与 recall（纯文件+内存缓存），rule 走 bootstrap（100% 确定性加载），content/insight/profile 走 recall（语义召回）。

统一召回为什么不合理：① 召回是概率性的（相关度排序、阈值过滤），契约走召回可能这轮丢失角色/规则——安全规则不能靠召回碰运气；② 设定是「定义存在」（骨骼，必须在场），对话记忆是「累积经验」（血肉，按需浮现）——访问模型本就不同；③ token 成本倒挂：设定小可全量，记忆大必须按需。

用户固定文本的正确分流（按确定性等级）

文档性质路径判据
高确定性（用户声明「每轮必须遵守」）确定性注入（同 rule）契约语义
低确定性 / 长文（背景资料、参考库）语义召回（同 content）资料语义
契约走注入，资料走召回 —— 分级而非统一，是永久性分级思想对用户文档层的延伸

05 · 接口草案

工程侧管道 + 唯一渲染器 + 分级取数
// 四层输入，每层独立（对应稳定性谱系）
export interface InputLayers {
  system: LayerBlock;      // P3 程序设定：rule 基线 + persona/skill（skill 归 P3，按 B 篇三源融合结论采纳）
  documents: LayerBlock;   // 用户固定文档：高确定性（契约）→ P3 档同 rule 注入；低确定性/长文（资料）→ P2 档同记忆检索
  memory: LayerBlock;      // P2 记忆召回（动态，可降级）——对应 D 篇「温记忆（归档 recall）」；D 篇「热记忆」= 会话窗口，由渲染器窗口管理承担
  live: LayerBlock;        // P1 实时输入（残缺，需补全 + 澄清）
}

// 每个管道块自带工程属性 —— 「管道 vs 文档」的胜负手
export interface LayerBlock {
  content: string;
  priority: 1 | 2 | 3;        // 冲突仲裁档：1 实时输入 > 2 记忆 > 3 设定
  tiebreaker: number;         // 同档仲裁序号（v1.3 新增）：同 priority 内按序号取高优先（如设定档：系统内置=1 < 用户文档=2）
  budgetTokens: number;       // 该层 token 上限（ContextManager 裁剪）
  cacheable: boolean;         // 可命中 prompt 缓存（稳定层置前置）
  degraded: boolean;          // 记忆失败时跳过，不阻塞
}

// 触发链（v1.2 分层）：会话内增量短路 / 会话开启与冷恢复走全量
export interface TriggerChain {
  // 会话内增量（主路径）：直接引用资源层会话状态，跳过召回与解析
  applyDelta(input: string, session: SessionState): FourTuple;
  //   「继续」→ 任务槽增量（动作=continue，对象=currentGoal）；混合输入 → 增量槽引用 + 新值槽覆盖
  // 会话开启 / 冷恢复（降级路径）：全量触发链
  coarseRecall(rawInput: string): RecallResult;        // 无 LLM
  parse(input: string, ctx: RecallResult): FourTuple;  // 输入解析/意图解析（LLM）：用户输入 → 四元组骨架；与 A 篇「动作解析」（Agent 解析 tool_call）区分
  refine(tuple: FourTuple): ResolvedLayers;            // 精召回 + 设定匹配
}

// 排版器（v1.3 拆分）：仅负责分层 → 排版文档（B 篇「一」协议族的实现组件之输出侧）
export interface PromptRenderer {
  render(layers: ResolvedLayers): RenderedPrompt;
}

// 上下文管理器（v1.3 拆分）：窗口管理 / 预算裁剪 / 状态恢复（原渲染器过载职责迁出）
export interface ContextManager {
  fitBudget(layers: ResolvedLayers, window: TokenBudget): ResolvedLayers;  // 层预算裁剪
  manageWindow(hot: HotMemory, strategy: TruncateStrategy): HotMemory;     // 热记忆截断（单一真理源，对齐 D 篇）
  restore(snapshot: CheckpointSnapshot): ResolvedLayers;                   // 状态恢复（重启/恢复后重建上下文）
}

来自《道生万物输入框架》的核心术语速查
  • 四元组 = 角色 × 任务 × 标准 × 资源（任意具体请求的结构；任务 = 行为 + 对象）
  • 三源 = 用户输入（P1 显式·现在）/ 记忆沉淀（P2 推断·过去）/ 系统内置（P3 兜底·设计）——「一」的供给渠道

  • 资源⇄动作递归 = 文本解析前是资源、解析后是动作；code-as-data（LISP）
  • 复归于道 = 交互产物沉淀为记忆 → 记忆成为下一轮请求的资源
