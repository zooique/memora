01 · 核心转变：能力分级而非模式切换

一切改动的根源在于一个前提变化 + 一个范式修正（v2.0）+ 一个定位收敛（v2.1）+ 一个最终定论（v2.2）
最终定论（v2.2）· 申请暂停模型：不中断对话思路是大厂（Trae/WorkBuddy 等）已实现的功能——loop 任务内，Agent 在问答回合间隙收集问题主动弹窗提问，用户直接输入内容即进入待输入形态，等 loop 最近一轮任务结束自然衔接。大厂未做的是显式暂停/继续按钮（为减用户心智负担而隐藏）。memora 的定位 = 在既有 loop 能力之上，增加显式的「暂停（申请暂停）」与「继续」按钮：暂停 = 申请暂停（requestPause），申请之后等进行中的问答回合结束才于 loop 迭代边界挂起（messages 保留，可续跑）；暂停后可直接继续任务（resumeExecution 续驱 loop），也可注入新的内容（补充输入，自动恢复 + 融合继续）。硬停止（signal.abort）仍是唯一霸道中止路径，行为不变。
定位收敛（v2.1）：不中断工作模型不是与一问一答并列的独立模式，而是一问一答核心交互之上的 loop 长任务升级。实测体验（2026-08-08）揭示两个事实：① 用户输入长任务若 Agent 单轮就完成——暂停/注入是伪需求（没有持续工作可暂停）；② 主流 Agent（Claude/OpenAI）的长任务形态 = 持续 loop 执行 + Agent 单向暂停提问（用户终止→澄清→继续），缺的只是「用户实时暂停查看 + 主动注入」。故收敛为：一问一答保持核心交互；loop 长任务自然进入「用户可暂停查看 / 注入补充 / 确认继续」——能力随任务复杂度分级，无模式开关。
范式修正（v2.0）：v1.x 把「暂停」实现为会话级冻结——PAUSED 状态下新消息被拒、输入通道与工作通道一起锁死。实测证明这是错的：用户期望「暂停」只让大模型停手，输入通道永远开放。修正为双通道解耦：
输入通道（Input Channel）——永不冻结：用户任何时刻可输入，输入 = 最新指令注入。暂停/恢复/工作中都不拦截输入；未暂停时输入 = 普通对话或增量，暂停中输入 = 补充注入（自动恢复工作通道并融合继续）。
工作通道（Work Channel）——可暂停：Agent 的执行循环（LLM 生成 + 工具调用）可被暂停（中断当前生成，保留已生成文本）、可恢复、可被 Agent 主动暂停（P4 抛问题）。
二者解耦：暂停 ≠ 冻结对话，暂停 = 停下手头的工作等待下一步指令。
维度一问一答模型不中断工作模型（v2.1）
能力分级短任务：一次请求-响应完成，无需状态长任务：loop 持续执行，自然升级为可暂停/可注入/可查看（非模式切换，能力随复杂度分级；单轮完成时暂停无意义）
暂停语义无暂停（停止即终止）申请暂停（v2.2）：暂停 = 提交申请（requestPause），进行中的问答回合结束后于 loop 边界挂起（软暂停，messages 保留，发射 {paused} chunk）；可继续（空输入 resumeExecution 原路径续跑）或注入（补充输入自动恢复 + 融合继续）
通道模型单通道：请求-响应，输入即触发一次工作双通道解耦：输入通道永不冻结 + 工作通道可暂停（v2.0 范式修正核心）
会话生命周期单次请求-响应，结束即销毁上下文开启后常驻，RUNNING / PAUSED / ERROR 三态（v1.3）；PAUSED 只停工作通道，输入通道照常开放；用户开启/关闭（关闭即销毁，非状态迁移）
输入语义完整请求（自包含）增量事件（相对当前运行状态的增量）——任何时刻可注入，暂停时注入 = 自动恢复 + 融合继续
任务模型单次动作目标 + 计划 + 版本（持续演进，防漂移）
缺省补全一次性猜测（接口补全）暂停询问（Agent 主动暂停澄清，终极补全形态）
上下文每轮重新组装基线常驻 + 热记忆持续 + 窗口截断
状态无状态（每轮从道开始）检查点贯穿（断点续跑）
一句话：一问一答是短任务的形态，不中断是长任务的自然升级——输入是永不干涸的泉（输入通道），Agent 工作是可暂停的泵（工作通道）；泵停了泉还在流，注入新水后泵继续转。

03 · 三个质变详解

必须重设计的部分，不是修补

质变一：接口语义 —— Request → SessionEvent（+ 输入通道永不冻结）

一问一答的输入是「完整请求」；工作模式下用户持续注入的是增量——新指令、修正、澄清、闲聊。每个输入必须解释为「相对当前运行状态的增量」，而非独立的四元组。这与《探索未来.md》的「暂停态注入澄清信息、修正目标、新增约束」对应。

输入通道永不冻结（v2.0 修正）：v1.x 实现中 PAUSED 状态拒绝所有新消息（会话级冻结），实测体验证明这是错的——用户暂停 Agent 后仍要能随时输入补充。修正：输入是持续开放的注入通道，与工作通道解耦——暂停中收到用户消息 = 自动恢复工作通道 + 把消息作为补充注入（Agent 融合后继续原任务）；未暂停时输入 = 普通对话/增量。输入内容不做「补充/纠正/新指令」的代码级分类——语义判断归 LLM（架构哲学 §4：代码做确定性规则，模型做语义理解），LLM 结合上下文自行决定「这是补充、继续、还是改向」。

增量默认分辨率（v1.2）：「继续」类增量的语义确定性来自上一轮已规划——默认 = 执行 planList 中最近一个未完成步骤（动作=continue，对象=currentGoal）。分辨率规则：① 有未完成步骤 → 推进最近步骤；② 计划已停滞/无下一步 → 降级 P4 暂停澄清；③ 混合输入（增量 + 新内容）→ 增量槽引用 + 新值槽覆盖（槽位级 delta，见 §04 合并规则）。

质变二：任务模型 —— 行为 → 目标 + 计划 + 版本

一问一答的任务 = 本次做什么；工作模式的任务 = 长期目标（mainGoal）+ 当前目标（currentGoal）+ 计划（planList）+ 目标版本（goalVersion）。目标版本控制是防漂移的锚：每次重规划必须与原始目标一致性校验，偏差超阈值提示「建议新会话」（探索未来.md 风险6）。

一致性校验判定者（v1.6）：不依赖 LLM 自评（自评漂移检测不可靠），采用确定性校验 + LLM 解释结合——① 确定性层：mainGoal 关键约束哈希对比（关键约束为用户显式声明或通过确定性规则提取，不依赖 LLM 提取，防自我引用；新增约束/删除约束触发 warning）+ 目标文本相似度阈值（如 >0.7 视为同目标、0.4-0.7 提示确认、<0.4 判定漂移）；② LLM 层：仅对确定性层判定"需确认"的场景生成解释供用户决策。二者结合，杜绝"LLM 自评自己的规划是否漂移"的自我确认偏差。另：goalVersion++ 时强制触发检查点快照（版本变更即状态变更，须可回溯）。

质变三：缺省补全 —— 猜 → 问（+ 暂停 = 停工作不停输入）

这是最深刻的哲学转变。一问一答里信息缺失只能靠接口猜测（P1>P2>P3 补全链）；工作模式下 Agent 可以主动暂停并询问（探索未来.md 核心规则 2：信息缺失/高风险/任务完成时主动暂停）。「暂停询问」是缺省补全机制的终极形态——补全从概率性猜测升级为确定性澄清。补全链变为：P1 显式 → P2 记忆推断 → P3 内置 → P4 暂停询问（前三层都不够时）。注：P4 的「澄清」概念萌芽于《输入管道与触发链架构》§01（信息缺失型输入需补全 + 澄清，v1.3 已标注），此处将其升级为补全链的终极形态。P4 暂停期间会话落入检查点持久化（休眠零算力），用户返回后经恢复协议续接——暂停不是终止。

暂停语义统一（v2.2 · 申请暂停模型）：用户暂停与 Agent 主动暂停（P4）走同一个双通道语义——
  • 暂停（Pause）= 申请暂停（requestPause）：用户点击暂停 = 提交申请，内核置 pauseRequested，进行中的问答回合自然结束后于 loop 迭代边界挂起（messages 保留，可续跑）——软暂停，非霸道中止。硬停止（signal.abort）才是唯一霸道中止路径（杀生成器、不可续跑）。
  • 恢复（Resume）= resumeExecution：重启工作通道续驱 loop——空输入直接继续原路径（热窗口在内存）；携带输入则自动恢复 + 融合继续（补充注入）。
  • 暂停中注入 = 用户暂停后输入补充内容发送 = 自动恢复 + 融合继续；不输入内容直接点继续 = 原样继续。
  • Agent 主动暂停（P4） = Agent 在关键节点（信息缺失/高风险/计划完成）停工作通道并抛问题，输入通道开放，用户回答即恢复。
  • 可续跑信号（canContinueWithoutInput）：暂停态优先 true，否则 isInAutonomousStep || hasPendingPlan——宿主据此决定暂停按钮显隐；简单轮（无续跑可能）只给停止。
对比 v1.x：不再有「PAUSED 拒绝新消息」的会话冻结——暂停只针对大模型的工作，不针对用户输入。
对抗式平衡：P4 不能滥用——频繁暂停反而增加用户负担（探索未来.md 风险7）。约束：仅当信息缺失导致下一步完全无法推进、或涉及高风险操作时才允许暂停；连续 2 次暂停后必须输出可执行方案。低风险决策由 Agent 兜底并在日志标注。

异步 I/O 承接（探索未来.md 硬约束第 4 项）：探索未来.md L34 的「全程异步 I/O vs IMemoryStorage 同步语义（ADR-002 补充）」在本设计中的承接——会话状态/检查点走内核事件系统（异步事件循环）；记忆统一模型 IMemoryStorage 维持同步语义（单线程内存访问）；SQLite/文件持久化封装为异步适配层，事件处理与存储读写解耦，避免同步 I/O 阻塞事件循环。

检查点恢复协议（v1.2 补充，回应「断点续跑失真」）

断点续跑 ≠ 仅反序列化快照——热窗口是截断的，早期上下文不在场内，直接恢复会让 Agent「失忆」。恢复须走完整协议：

  1. 快照反序列化：载入 SessionCheckpoint（mainGoal/currentGoal/plan/role/standard/resource/hotMemory）
  2. 热窗口载入：hotMemory 作为对话记录（资源层常驻成员）载入上下文
  3. 温记忆按需召回：以 mainGoal/currentGoal 为查询条件，从温记忆（归档 recall）召回窗口外的早期上下文，合并进资源槽
  4. 契约重注入：rule 等确定性契约重新注入；persona/skill 按输入驱动匹配后重新注入（分级路径不变）
  5. 恢复校验：校验资源/目标/计划齐备（状态机 ERROR 转 RUNNING 前强制）；增量事件从最后已提交检查点起重放

delta 合并规则（v1.2 补充）：SessionEvent.delta 与四元组基线合并采用槽位级规则——增量槽引用（如「继续」= 任务槽引用 currentGoal，不覆盖）、新值槽覆盖（如用户给出新标准）、数组槽追加（如补充资源列表）；会话基线 = 检查点恢复后的四元组。增量主路径（会话内）与全量路径（开启/恢复）均由此规则统一。

05 · 接口草案（升级版）

增量事件 + 会话检查点 + 四级补全
// 增量事件（替代完整请求 —— 质变一的接口形态）
export interface SessionEvent {
  type: 'command' | 'correction' | 'clarify' | 'chat'; // 意图分类防污染
  content: string;
  delta?: Partial<FourTuple>;   // 槽位级增量：增量槽引用基线（如「继续」→ 任务槽引用 currentGoal）、新值槽覆盖、数组槽追加
}

// 会话检查点（核心状态 —— 质变二与新增维度的载体）
export interface SessionCheckpoint {
  sessionId: string;
  status: 'running' | 'paused' | 'error';  // 三态（v1.6）：ERROR 独立可见，不自动转 PAUSED；PAUSED 区分 idle/error 原因
  error?: { cause: string; at: number; recovered: boolean };  // 异常原因（恢复前校验 recovered）
  mainGoal: string;          // 原始目标（防漂移锚点）
  currentGoal: string;
  goalVersion: number;
  plan: PlanStep[];
  role: Role;                // 会话级，可中途变更
  standard: Standard;        // 会话级，可更新
  resource: ResourceState;   // 会话资源快照（四元组资源维度：当前引用的文档/记忆/上下文——断点续跑可还原；与 B 篇「记忆覆盖四元组全集」对齐）
  hotMemory: ChatMessage[];  // 热记忆（截断窗口，防膨胀）
  lastHeartbeat: number;     // 心跳防僵尸
}

// 四级补全（质变三：加 P4 暂停询问）
export interface ComposerV2 {
  compose(event: SessionEvent, cp: SessionCheckpoint):
    { resolved: ResolvedDelta; needClarify?: ClarifyQuestion[] };
  // P1 显式 → P2 记忆推断 → P3 内置 → P4 暂停询问
}

// 状态机（双向暂停 + 三态）—— v2.0：三态描述工作通道，输入通道不受约束
export interface SessionStateMachine {
  onEvent(e: SessionEvent, cp: SessionCheckpoint): StatusTransition;
  // v2.0：PAUSED 态收到 chat 事件 = 自动恢复（auto-resume）+ 补充注入，不拒绝；
  // 仅 command（如显式暂停）在 PAUSED 态保持状态。ERROR 态仍拒绝 chat（须先 recover）。
  recover(cp: SessionCheckpoint): boolean;  // 恢复校验（v1.3）：ERROR→RUNNING 前须 error.recovered===true 且 cause 已解除
}

// 工作循环（v2.0 新增：执行循环的自主推进语义；v2.2 对齐已落地 API）
export interface WorkLoop {
  // 收到需求后自主连续执行：计划非空时循环推进步骤，流式输出过程 chunk
  // 停下条件：① 计划完成 ② P4 需澄清（needClarify）③ 高风险确认 ④ 用户申请暂停（requestPause）
  run(goal: string, cp: SessionCheckpoint, signal: AbortSignal):
    AsyncGenerator<WorkChunk, void, unknown>;
  // v2.2 申请暂停（软）：置 pauseRequested，进行中的问答回合结束后在迭代边界挂起 + return + {paused} chunk（messages 保留，可续跑）
  requestPause(reason?: string, by?: 'user' | 'agent' | 'system'): void;
  // v2.2 续跑（软）：驱动 loop.continueAfterPause 继续推进；input 可选（补充注入 → 自动恢复 + 融合）
  resumeExecution(input?: string, signal?: AbortSignal): AsyncGenerator<AgentChunk, void, unknown>;
  // v2.2 可续跑信号：paused 优先 true；否则 isInAutonomousStep || hasPendingPlan —— 宿主据此决定暂停按钮显隐
  canContinueWithoutInput(): boolean;
}

// 触发链分层（会话开启全量 / 进行中增量）
export interface TriggerChainV2 {
  boot(sessionGoal: string): SessionCheckpoint;  // 开启：全量触发链 + 基线注入
  step(event: SessionEvent, cp: SessionCheckpoint): Delta; // 进行中：增量解析
}
