# Memora 设计质量评估（2026-09-10）

> 方法：**第一性原理 + 对抗式审查**。所有论断标注证据来源与类型（`实锤` = grep/wc/实测；`推断` = 由实锤推导）。

## 0. 结论先行

| 维度 | 评级 | 一句话 |
|---|---|---|
| 架构骨架（turn⊃loop⊃step） | 🟢 业界第一梯队 | 与 2026「单 Agent + 深优化工具集」主流回退方向**同向且更彻底** |
| 记忆层（memory-as-summary + 工具现查） | 🟢 领先 | 独立踩中 2026 全年最强共识：**tool-based memory 优于 pipeline RAG** |
| 上下文空间管理（替换→压缩→裁掉） | 🟡 优秀但有真实缺口 | 三级分层优于业界默认单级压缩，但缺 token 效率的**量化自证** |
| 恢复模型（放弃跨重启） | 🟢 教科书级减法 | 主动放弃业界最重的 durable execution，符合「不预支复杂度」 |
| 工程纪律（零依赖 / SSOT / 测试比） | 🟢 罕见 | 零运行时三方依赖 + 测试代码 > 生产代码 |
| 复杂度集中度（agent 模块体量） | 🔴 **最大真实风险** | `src/agent/` 40,396 行 = 内核 57%，`loop.ts` 单文件 2635 行 / 89 个 private |
| 评估设施（客观度量） | 🔴 **第二真实风险** | 无 eval harness；有 A/B benchmark 脚本但非持续回归门 |

**总裁决**：Memora 的**设计决策质量高于其代码组织质量**。它的「形而上」（该做什么、不该做什么）几乎每一处都踩在 2026 业界最优解上，且多数是**先于业界共识独立到达**的；它的「形而下」（模块切分、单文件体量、量化验证）则落后于设计本身约一到两个身位。用萧然的话说：**解构问题这一步做得极好，最简逻辑这一步做了八成，剩下两成变成了 `loop.ts` 的 2635 行。**

## 1. 逐项对位审查（Memora vs 2026 业界）

### 1.1 架构骨架：单 Agent 单循环 —— 🟢 领先

**Memora 的形**：`turn ⊃ loop ⊃ step`（`docs/architecture/agent-design-philosophy.md`）。一个 agent、一个 loop、一次 LLM call 即一个 step。**实锤**：内核 `src/agent/seed/`（所谓「编排器」）总计仅 **567 行**（`orchestrator.ts` 296 + `prepare.ts` 142 + `types.ts` 118）—— 编排层薄到几乎不存在。

**业界 2026 的形**（三条独立证据指向同一结论）：
- Anthropic《Building Effective Agents》："find the simplest solution possible, and only increasing complexity when needed"；
- Cognition《Don't Build Multi-Agents》："failure generally boils down to missing context within the system"；等算力基准（Tran & Kiela 2026, arXiv:2604.02460）证明单 Agent 在多跳推理上**持续追平或超越**多 Agent；
- 2026 上半年一线团队出现**主动回退潮**：从 Multi-Agent 退回「Single Agent + Skill」（magicliang 2026-05 综述）。

**对位裁决**：Memora **无需回退，因为它从未前进到多 Agent**。它的「单 Agent」不是妥协，而是 ADR 级硬约束（单 Agent 架构 / 零依赖 / 统一记忆）。在这个维度上 Memora 与 2026 最优解**完全重合**，且编排层比 Anthropic 自家 research 系统（15× token 成本）轻得多。

**但要注意反证**：业界判断「单 Agent 何时不够」有**四条明确信号**（agentpatterns.ai）——① 工具数 >15-20；② 任务需要根本不同的 system prompt；③ 需要真并行；④ 需要信任边界隔离。

**Memora 已踩中信号 ①**：**实锤** 内置工具 **23 个**（`grep -oP "name: '\K[a-z_]+" src/agent/builtinTools.ts` → 23），已越过「15-20 个工具后 LLM 选择准确率下降」的经验阈值。**这不是缺陷，是已登记的边界**——但业界给出的标准解法是「拆分工具到 specialist 子 Agent」，而 Memora 的答案是**角色包手动切换 + 工具白名单（`act.toolMode` / `act.toolReadonly`）**。这是一个**有意的不同赌注**：赌模型能力迭代会消化工具选择压力，而不是增加编排。**这个赌注与 Anthropic「Skill 优于 Agent」立场一致，方向可信；但没有本地实测数据支撑「23 个工具下模型选择率仍可接受」。**（→ 归入 §3 风险 R4）

### 1.2 记忆层：memory-as-summary + 工具现查 —— 🟢 领先（最强项）

**Memora 的形**：
- 记忆单元**只有一个**：round-summary（`docs/architecture/memory-as-summary.md`）；
- `Memory` 原语 = 6 个基础字段（id/content/source/name/createdAt/accessedAt）+ 软删除 `deletedAt`；
- **无自动注入**：检索唯一入口 = `search_memories` 工具，由 LLM 主动调用；
- **无记忆层 cap**、无 `memoryTokens`/`memoryCount` 占用段（2026-09-10 减法定案，`ea76435d`）；
- 记忆治理 = supersede（写时取代）+ boost（越用越重要），**衰减已移除**。

**业界 2026 的形**（这是本报告中最强的一组证据）：
- Mem0 April 2026 报告：**tool-based memory 比 full-context 少 90% token、少 91% 延迟**，代价仅 6 个百分点准确率（66.9% vs 72.9%，LoCoMo）；
- usewire.io 2026 综述标题直陈："**Agents that get to call their memory beat agents that get fed by it**"；"RAG chooses on behalf of the agent. Tool-based memory lets the agent choose for itself"；
- ICLR 2026 MemoryAgentBench 把该模式**形式化为评估标准**；
- Atlan 五模式分类中，Pattern 3（tiered memory, agent-managed）正是 MemGPT/Letta 路线，Memora 亦在此外。

**对位裁决（这是全报告最重要的判断）**：

Memora 的记忆设计与 2026 最强共识**逐条重合**，且有三处**独立超越**：

| 维度 | 业界 2026 主流 | Memora 实锤 | 裁决 |
|---|---|---|---|
| 检索范式 | 工具现查优于 pipeline RAG | `search_memories` 唯一入口，自动注入已退役 | 🟢 完全同向 |
| 记忆单元 | 多类型（episodic/semantic/procedural/working）分层 | **只有 round-summary 一种**，`SummaryType` 5 值是标签非类型 | 🟢 **更简**——业界正在为类型爆炸头疼 |
| 遗忘机制 | TTL / intelligent forgetting / 冷热分层 | **衰减已移除**，只保留 supersede + boost | 🟡 **不同赌注**，见下 |
| 冲突消解 | recency / confidence / merge / escalate | supersede（写时取代）+ 保留被取代项供追溯 | 🟢 同向且更省（不引入置信度评分） |

**独立超越之一：拒绝「记忆类型学爆炸」。** 2026 业界（CoALA / Atlan）花大量篇幅区分 episodic/semantic/procedural/working，Memora 直接一句「记忆即摘要」把类型学砍成零。这符合萧然「解构复杂问题」——因为对**单 Agent + 工具现查**而言，类型在检索时由 LLM 自己判断，无需系统预先分类。**实锤**：`SummaryType` 只是 content 上的一个标签（`preference|fact|decision|intent|general`），**没有任何按类型分派的检索路径**（grep 无类型路由消费者）。

**独立超越之二：把「记忆占用」概念物理删除。** 业界 tiered memory 普遍在预算里为记忆留 cap；Memora 删掉了 `memoryLayerCapTokens` 全链。**这更正确**——因为「工具现查」意味着记忆不占常驻预算，它是**按需拉取的 token**，给它在预算里留位反而是「结构性幻觉」（一个恒 0 的字段在宣称一个已被取消的类别）。这条判断是 MEMORY.md 里「反复病灶模式 §11」的原型，Memora 自己识别并修正了。

**独立超越之三：无跨会话身份问题的部分免疫。** 业界 2026 三大未解难题之一是「cross-session identity」；Memora 用**按日切分会话 + round-summary 提升为顶层持久字段**（`summaryType`/`sessionName`/`roundId` 从 metadata 提升到顶层，因为宿主 SQLite 不持久化 metadata）部分绕开了它。**实锤**：`src/memory/types.ts` 中这些字段为 memory 顶层字段而非 metadata 子对象。

**唯一存疑项（🟡）**：**衰减移除 vs 业界 TTL/forgetting**。业界（Mem0、Atlan、多篇 2026 综述）普遍认为 intelligent forgetting 是必要能力，理由是 **memory staleness** 是三未解难题之一。Memora 的理由是「supersede 已经解决了『旧信息被新信息取代』，无需独立衰减」。**这个论证成立但有边界**：supersede 处理的是**显式矛盾**（新事实推翻旧事实），TTL 处理的是**隐式过期**（没有任何新事实，但旧事实自然失效，如「我下周要去上海」过了那一周）。**Memora 目前对隐式过期无机制。**（→ 归入 §3 风险 R3，属真实缺口而非错误）

### 1.3 上下文空间管理：替换 → 压缩 → 裁掉 —— 🟡 优秀但缺量化自证

**Memora 的形**（`src/agent/compaction.ts` + `contextManager.ts` + `budget.ts`，三文件共 **777 行**）：
- **三级递进**：① 替换（`ReplaceRoundsStrategy`，LRU，`DEFAULT_REPLACE_KEEP_RECENT_ROUNDS=5`）→ ② 压缩（`OffloadCompactionStrategy`，LLM 生成，临时）→ ③ 裁掉（`truncateMessages` 硬闸）；
- 预算公式：`可用 = 窗口×0.85 − 固定开销` → `锚点 = 输入×2` → `完整对话层 = 剩余×0.9`；
- 硬截断闸：`token > 窗口 && 消息>3` → 压到 `窗口×0.9 − system`；
- 两处「响应预留」口径已注明差异（15% 减法 vs 10% 乘法），**明确标注「纯属巧合，勿统一」**。

**业界 2026 的形**：
- 业界主流是**单级压缩**：到阈值就 summarize 或 truncate；
- Atlan 五模式里的 structured compression 接近 Memora 的第二级；
- **context rot / lost-in-the-middle** 是公认问题，业界的答案是「分层预算 + 渐进披露」。

**对位裁决**：

Memora 的**三级递进本身优于业界默认的单级压缩**，关键优势在**第一级「替换」的边际成本为零**——它复用**已落盘的 round-summary**（step 原子落盘时已生成），不重新调 LLM。这意味着：**在压力未到压缩线之前，Memora 用「换指针」而不是「烧 token」来腾空间**。**实锤**：`compaction.ts` 的 `ReplaceRoundsStrategy` 的输入是既有 summary，非新生成。

这在业界是一个非常干净的最优解——业界讨论「summarize on threshold」时默认每次压缩都要付出 LLM 调用成本，Memora 把这个成本**前移到 step 落盘时**（本来就要写），于是第一级压缩变成纯内存操作。

**但有两个真实缺口：**

1. **🔴 缺 token 效率量化自证。** 业界 2026 的核心考核指标是**每查询 token 数**（Mem0: 6,956 tokens/query @ 92.5 分 vs full-context 26,000）。Memora **有** A/B benchmark 基础设施（`scripts/benchmark-seeds.ts`、`scripts/test-memory-tool-recall-benchmark.ts`、`docs/architecture/memory-tool-recall-ab-benchmark.md`），但这是**一次性脚本，不是持续回归门**。**实锤**：无 `eval/` 目录，无 CI 中的 benchmark 门。这意味着「三级空间管理比单级好多少」「工具现查比自动注入省多少 token」这两个最关键的效率主张，**Memora 至今没有自己的数字**，只有设计推演。

2. **🟡 `dialogueFillRatio` 休眠扩展点。** `computeContextBudget` 有该可选入参（默认 0.9），但 `contextPreparer` 调用**未传** → 零供给。MEMORY.md 已登记为 G40 触发驱动暂缓。这是**正确的克制**（不预支复杂度），但也意味着这个参数目前是「看起来可调的假旋钮」——**符合萧然「不预支复杂度」纪律，但应确认注释是否已说明「当前无供给方」**，否则未来读代码者会误以为它生效。

**统一性加分**：Memora 主动在注释里声明「15% 减法预留 vs 10% 乘法保留**基准不同、语法不同，恰好互余纯属巧合，勿统一**」。这是**极高水平的自我审查**——绝大多数代码库会让后来者「顺手统一」这两个数字，制造一个静默的语义错误。Memora 用注释把陷阱封死了。这个细节的质量高于业界平均水准一个量级。

### 1.4 恢复模型：放弃跨重启 —— 🟢 教科书级减法

**Memora 的形**（2026-09-10 减法定案）：
- `SessionCheckpoint` = **同进程内存态，不落盘**；
- 崩溃 → `appendInterrupted` 补全为完整 turn 身份 → 下次按普通 Round 历史加载；
- **不存在跨重启恢复 / 断点续跑 / 宿主续跑提示**；整链已退役；
- 判据：**自愿介入（暂停/插话/ask）要求内存态连续；进程死亡即降级为非自愿中断（收场重开）**。

**业界 2026 的形**：
- durable execution（Temporal / LangGraph）是热门方向，主打 checkpointing；
- 业界列举 checkpoint 防住的四种失败：重复副作用 / 丢失审批 / 过期计划 / 重试风暴；
- 但也有一句关键限定（来自该方向最佳实践）：**"context helps a model remember what was said, durable execution tells the system what actually happened — different categories of truth."**

**对位裁决**：

这是全报告里**最体现萧然原则**的一处设计。

业界 durable execution 的价值主张，**前提是「系统有必须与外部世界保持一致的状态」**——支付、审批、运维操作、任何有副作用的动作。Memora 是**本地优先的对话内核**，其 step 落盘已经在**同一 Round 文件**内原子记录了所有过程事件（`processEvents`），副作用边界清晰。

于是 Memora 做了一个极漂亮的推理：**既然崩溃后的正确行为就是「把这轮当作被打断的普通轮重新加载」，那么持久化 checkpoint 就没有任何消费者。** 它保留的是**同进程内**的 `pendingPause` / `loop.requestPause()` step 边界 yield / `resumeExecution` / `appendInterrupted`——这些服务于**自愿介入**（用户按暂停、插话、ask_user），而自愿介入天然要求进程还活着。

**这个减法的正确性有界**（Memora 自己也标明了边界）：它成立的前提是「非自愿中断 = 收场重开可接受」。对本地优先对话 Agent **成立**；对长时任务 Agent **不成立**。Memora **没有假装普适**，它把这个约束写进了设计判据。

**业界对照**：这正是业界反复警告却少有团队敢做的——2026 有大量文章说「premature optimization of memory management adds complexity without measurable benefit」，但**真正把一个已建成的恢复链整条砍掉的团队极少**。Memora 做到了，且保留了所有**真正有消费者**的部分。**这是「解构复杂问题」的正面范例。**

### 1.5 角色包：只带数据不带代码 —— 🟢 更严格的信任模型

**Memora 的形**：
- 文件夹形态：`manifest.json` + `persona.md` + `rules.md` + `skills/`（**实锤**：`role-packs/` 下 4 个角色包——1 兜底契约包 `memora助手` + 3 示例包，结构一致）；
- 三层：L1 内容（md）/ L2 策略枚举（**实锤**：`STRATEGY_KEY_RULES` 共 **20 个键** —— prepare 2 / act 9 / reflect 4 / global 5；其中 `reflect.loopContinue` 为 v0.13 兼容别名，故**活性键 19 + 别名 1**）/ L3 代码（远期，沙箱，未设计）；
- **角色包只「选择」不「定义」**：枚举外取值是 error（`KeyRule` 注释明示）；
- 所有数值键上下限集中在 `strategyKeys.ts`（SSOT），validator 与 resolver 共用；
- 切换**仅手动**（ADR-028），无自动匹配。

**业界 2026 的形**：
- Claude Skills 打包 scripts + 支持 `context: fork` 子 Agent 隔离；
- 业界的角色/Role 通常是**带能力的**（能调工具、能跑代码）。

**对位裁决**：

Memora 的角色包是**更严格的声明式模型**：只带数据（md + 枚举选择），不带代码。这带来两个业界稀缺的性质：

1. **角色包无法越权**。因为 L2 键是**枚举封闭集**，validator 校验未知键并报 warning（`strategyKeys.ts` 头注释明示），角色作者**在能力面上只能选不能造**。业界 Role prompt 常见风险是「role prompt shapes behavior; it does not constrain capability」（qubitool 2026 原文），Memora 用枚举把 capability 也约束住了。
2. **数值键全部有区间**（`intRange` / `range`），**下限防语义错误、上限防资源失控**。**实锤**：`MIN_STEP_BUDGET=10 / MAX_STEP_BUDGET=500 / MAX_OUTPUT_LIMIT=65536 / MAX_CONTEXT_LIMIT=1_000_000`。业界罕见的防呆密度。

**明确标注的未定义边界**（Memora 自己承认，值得肯定）：**权限信任模型 + 版本契约**。即：第三方角色包如何被信任、角色包升版如何兼容，这两个问题**在文档里被明确标为未定**，而不是被含糊带过。这是健康的。

**一处与业界共识的张力（🟡）**：业界 2026 反复强调「工具数 >15-20 应拆分」，而 Memora 用角色包手动切换来管理工具面。**手动切换意味着用户必须知道该切哪个包**——业界会说这缺少「router」模式（一个 orchestrator 自动分派）。**Memora 的立场（ADR-028）是「自动重开 = 伪需求，重开走 LLM 显式 `task_table_write(overwrite)`」**。这个立场**符合「不预支复杂度」**，但代价是**用户认知负担**。这是一个**尚未被真实用户反馈验证的赌注**，不是错误。

## 2. 工程纪律评估 —— 🟢 罕见水准

| 指标 | 实锤数据 | 业界对照 |
|---|---|---|
| 运行时三方依赖 | **`dependencies: undefined`**，仅 `peerDependencies: {pino}` | 业界 Agent 内核普遍拖 10-40 个包 |
| 测试:生产 代码比 | **40,574 : 28,491 ≈ 1.42 : 1** | 业界优秀线约 1:1 |
| 测试文件数 | 101（内核）+ 25（宿主） | — |
| 测试结果 | 内核 2749 passed / 4 skipped | — |
| 向量检索 | 纯 JS `JsonVectorStore`（cosine），`IVectorStore` 供宿主注入 | 业界默认拖 SQLite/LanceDB |
| ADR 文档 | 30 篇（ADR-001..030） | 罕见 |
| 设计文档 | `docs/*.md` 共 **10,344 行** | 罕见 |
| 规则文件 | `.trae/rules/` **17 篇**心智规则 | 极罕见 |

**对位裁决**：

**零运行时依赖**是最值得单独说的。业界 2026 的记忆层文章几乎都在教你怎么选向量库（"21 frameworks and 20 vector stores integrated"）。Memora 的答案是：**接口留出（`IVectorStore`），内核自带纯 JS 实现，宿主想接 SQLite 自己接**。这带来三个直接收益：① 内核可以在任何 Node ≥22 环境跑；② 测试无需 native 编译；③ **架构边界物理化**——宿主想下沉 provider 策略都无处可插。这与 ADR-002 零依赖 / kernel/host 边界铁律是同一件事的两面。

**测试比 > 生产**在 Agent 内核这个类别里非常罕见。业界的 Agent 框架（LangChain 等）测试比通常远低于 1。

**但要注意：测试比高 ≠ 测试有效。** MEMORY.md 的「反复病灶模式 §3」明确记载「突变后测试仍绿 ≠ 测试有效」。**实锤风险**：`loop.ts` 2635 行（89 个 private 方法）由 `loop.test.ts` 4094 行覆盖——**单文件近乎 1:1.55 的覆盖密度**，这既说明覆盖扎实，也说明**测试与实现高度耦合**：任何对 loop 的拆分都会引发大规模测试重写。**这是体量风险的第二重形态**（→ R1 的一部分）。

## 3. 真实风险清单（对抗式审查的核心部分）

> 以下每一条都是**经实锤确认的真实缺口**，不是「可能有用」的对称性增强。按严重度排序。

### 🔴 R1｜`src/agent/` 体量失衡 —— 全项目最大风险

**实锤**：
- `src/agent/` = 78 文件 / **40,396 行** = 内核 69,065 行的 **58.5%**；
- `loop.ts` **2,635 行**、**89 个 private 成员**；
- `agent.ts` **1,890 行**、51 个方法；
- 对照：`src/memory/` 8,567 行、`src/role-pack/` 5,565 行、`src/utils/` 4,531 行。

**判定**：`loop.ts` 已越过「God Object」的经验阈值（业界普遍认为单文件 >1500 行、单类 >30 个方法即需审视）。MEMORY.md 自己也登记了「`ui.ts` 行数阈值 1500」的观察，但 `loop.ts` 是它的 1.76 倍且**已在阈值之上仍未拆分**。

**根因分析（第一性原理）**：`loop.ts` 的 89 个 private 分成几族——**上下文装配**（`_prepareContext` / `buildSystemPrompt` / `rebuildSystemMessage` / `refreshOccupancyDialogue`）、**LLM 调用与重试**（`_callAndRoute` / `callLlmWithRetry` / `determineTaskType` / `resolveProvider`）、**工具执行**（`handleToolCalls` / `executeToolCalls`）、**空间管理**（`compressContext` / `findEarliestRound` / `findLargestToolResult` / `summarizeForCompression`）、**消息维护**（7 个 append/replace 方法）。**这五族之间的耦合度远低于它们各自的内聚度**——即：这是一个**可拆但未拆**的状态。

**对照已有进展**：`managers/` 目录已抽出 14 个 manager（共 3,775 行），`contextManager` 已作为独立类被 loop 持有（**实锤**：`loop.ts` 中 `private readonly contextManager: ContextManager`）。所以**拆分范式已经建立且验证过了**——`contextManager` 就是成功先例。问题在于**其余四族尚未按同一范式迁出**。

**与萧然原则的关系**：这是「解构复杂问题」**执行不彻底**的典型案例——设计层解构得极干净（turn/loop/step、三阶段、三级空间管理），但**代码层没有把同一次解构贯彻到底**。这不是设计缺陷，是**收敛未完成**。

**建议（触发驱动，不预支）**：等一个真实触发点（下一次 `loop.ts` 出现合并冲突、或某族需要独立测试、或体量再增长），按 `contextManager` 的成功范式**逐族迁出**到 `managers/`。**不建议现在大重构**——萧然纪律 D6 明确「触发驱动 > 观察驱动」。

---

### 🔴 R2｜无 eval harness —— 设计主张无法自证

**实锤**：
- 无 `eval/` 目录；`find -iname "*eval*"` 仅命中 ADR-022 与两个一次性脚本；
- `scripts/benchmark-seeds.ts` + `scripts/test-memory-tool-recall-benchmark.ts` 存在，但**非 CI 持续门**；
- ADR-022 标题含 "agent-evals"，说明**问题已被识别**；
- `docs/architecture/module-inventory.md` 中评估视角标注为**远期**。

**判定**：业界 2026 的评分标准已完全量化（LoCoMo / LongMemEval / BEAM；五个维度：BLEU / F1 / LLM score / token / latency）。**Memora 没有任何一项自己的数字。**

**这是 R2 的关键论证**：Memora 有两类核心主张需要数字支撑：
1. **效率主张**：「三级空间管理省 token」——缺对照实验；
2. **质量主张**：「工具现查优于自动注入」——这正是业界争议最激烈的点（Mem0 显示工具式牺牲 6 个百分点准确率换 90% token）。**Memora 单方面选择了工具现查，但没有测过自己在这个 trade-off 上的位置。**

**注意这不是说 Memora 选错了**——业界证据（usewire 2026："Agents that get to call their memory beat agents that get fed by it"）强烈支持 Memora 的选择。问题是：**Memora 采纳了业界结论，却没有验证该结论在自己的架构上成立**。这在工程上意味着：如果某个实现细节让 Memora 的工具现查退化（例如 summary 质量不足、reranker 失效），**没有任何机制会发现**。

**与萧然原则的关系**：萧然要求「任何修复与结论必须经显式验证」。设计层做到了（每个决策都有 ADR + 判据）；**量效层没做到**——因为没有度量工具。这是**纪律在执行面上的一个已知空洞**。

**建议**：不需要建全量 eval 平台。**最小可用方案**：把已有的 `test-memory-tool-recall-benchmark.ts` 固化成一个**可重复运行、输出固定指标快照**的命令（token/query + 命中率），纳入「改动记忆层时手动跑一次」的检查表。这符合「不预支复杂度」——不建平台，只把已有脚本变成可复现证据。

---

### 🟡 R3｜隐式过期的记忆无机制（衰减移除的边界）

**实锤**：治理只有 supersede + boost；衰减链已移除；`listFading` 度量的是「冷度」而非「即将消失」。

**判定**：supersede 处理**显式矛盾**（新事实推翻旧事实）。**隐式过期**（无新事实但旧事实自然失效：时间性事实、一次性的临时状态）**无任何机制**。

**业界对照**：memory staleness 被列为 2026 三大未解难题之一，主流用 TTL / temporal validity 处理。

**为什么这是 🟡 不是 🔴**：Memora 的 `SummaryType` 里有 `intent` 类型（意图），而 round-summary 天然带 `roundId` / `sessionName` / `createdAt`；**LLM 在检索时能自己看到时间戳并判断时效**。所以隐式过期**可以由 LLM 在读取时处理**，而非系统提前剪枝——这与「记忆即工具现查」的哲学一致。**这是一个可行的替代方案，只是没有被显式论证过。** 建议在 `memory-as-summary.md` 里补一段「为何 supersede 足够、隐式过期交给 LLM 判读」，把这条隐含论证显式化（当前是「用文档迁就实现」的潜在违反——实现移除了衰减，文档若未论证会显得像缺失）。

---

### 🟡 R4｜23 个工具越过业界阈值，但用角色包手动切换应对（赌注未验证）

**实锤**：23 个内置工具；角色包切换仅手动（ADR-028）；无 router 自动分派。

**判定**：业界阈值 15-20 已被越过，标准解法是 specialist 拆分。Memora 的手动切换是**有意的不同赌注**。**未见本地实测数据支撑「手动切换工具面 = 可接受的选择准确率」。**

**为什么 🟡 而非 🔴**：这与 Anthropic「Skill 优于 Agent」立场一致（skill 是给模型做加法，编排是乘法——加法投资不因模型升级作废）。**方向可信**。且 Memora 的工具不是全部同时暴露——`act.toolMode: allow|block` + `act.toolReadonly` 机制说明**工具面是可控的**。问题只是「没有测过」。

## 4. 综合裁决：Memora 设计质量处在什么位置

### 4.1 与业界 2026 最优解的逐维对位

| 业界 2026 共识 | Memora | 判定 |
|---|---|---|
| 单 Agent 优于过早多 Agent | 单 Agent 硬约束，编排层 567 行 | ✅ 同向且更彻底 |
| Tool-based memory > pipeline RAG | `search_memories` 唯一入口 | ✅ 独立到达同一结论 |
| 上下文是 RAM 不是 storage | 三级空间管理 + 硬截断闸 | ✅ 同向且更细 |
| 分层预算 / progressive disclosure | 固定开销 → 锚点 → 对话层 | ✅ 同向 |
| Durable execution / checkpointing | **主动放弃**（有界且论证完备） | ✅ 符合「不预支复杂度」 |
| 维护成本 / 错误归因 | 单 Agent，无跨 Agent 归因问题 | ✅ 结构性免疫 |
| 需要 eval 量化 | **缺** | 🔴 R2 |
| 需要控制单文件体量 | **缺**（loop.ts 2635 行） | 🔴 R1 |
| 需要 intelligent forgetting | **无**（有 LLM 判读替代方案但未论证） | 🟡 R3 |

**9 维中 6 维达标或超越，2 维真实缺口，1 维部分。**

### 4.2 用萧然的话回答

> **「解构复杂问题，用最简单的逻辑实现复杂功能。」**

**解构（做得极好）**：Memora 把「一个 AI Agent 内核」这个大问题解构成了四层正交结构——
`turn ⊃ loop ⊃ step`（时间轴）+ 三阶段（Prepare/Act/Reflect，执行轴）+ 三级空间管理（内存轴）+ 角色包 L1/L2/L3（配置轴）。
**四轴正交、互不交叉、每轴单一真理源**。2026 业界文章里，能与之比肩的解构清晰度不多见。

**最简逻辑（做了八成）**：
- ✅ 记忆砍到只有 round-summary 一种单元；
- ✅ 恢复链整条砍掉（保留有消费者的部分）；
- ✅ 零运行时依赖，向量库只留接口；
- ✅ 记忆占用段物理删除（拒绝结构性幻觉）；
- ⚠️ **但 `loop.ts` 的 2635 行说明：时间轴的「最简」没有落到代码上**。

**一句话总评**：

> **Memora 的架构设计质量是「业界第一梯队」，其设计纪律（减法、SSOT、边界）甚至高于多数公开的 Agent 框架。它最大的问题不是想错，而是「想得比写得的更简」——设计层已完成九成的减法，代码层只落到了六成。** `loop.ts` 的 2635 行与缺失的 eval harness，是这份优秀设计上最明显的两道未收口。

### 4.3 优先级建议（按萧然纪律：触发驱动）

| 优先级 | 项 | 触发条件 |
|---|---|---|
| **P1** | R2 eval 最小化：把已有 benchmark 脚本固化为可复现指标快照 | **现在可做**（低成本、提升后续所有主张的可验证性） |
| **P1** | R5 修 `module-inventory.md` 陈旧条目 | 现在可做（单点） |
| **P2** | R3 显式论证「supersede 足够 / 隐式过期交给 LLM」 | 下次改 `memory-as-summary.md` 时顺手补 |
| **P3** | R1 `loop.ts` 逐族拆分 | **等真实触发点**（合并冲突 / 某族需独立测试 / 体量再涨） |
| **P3** | R4 工具选择准确率实测 | **等真实用户反馈**（工具选错的实际案例） |
