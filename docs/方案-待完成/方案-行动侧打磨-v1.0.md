### 2.2 数据流

```
ToolExecutor.writeFile(path, content)
  ↓
  ① 读取旧文件（如果存在）
  ↓
  ② 生成 unified diff（Differ.diff(oldLines, newLines)）
  ↓
  ③ 渲染 diff 为 ANSI 彩色字符串（DiffRenderer.render(hunks)）
  ↓
  ④ 终端展示 + 用户交互（readline）
  ↓ [Enter] → 继续写入                    [n] → return false → toolError
  ↓ [v]   → 显示全文（less-like 分页）   → 回到确认提示
  ↓
  ⑤ 写入文件 + 返回结果
```

### 2.3 Diff 算法设计

采用**简化 Myers 算法**——针对代码文件的实际情况做特化（不需要处理所有极端情况）：

```
输入：oldLines: string[], newLines: string[]
输出：Hunk[] = [{ oldStart, oldCount, newStart, newCount, lines: DiffLine[] }]
      其中 DiffLine = { type: 'same' | 'add' | 'remove', content: string }

算法：
  1. LCS（Longest Common Subsequence）预处理
     → 快速跳过相同前缀/后缀
     → 中间不同部分做逐行比较

  2. 上下文窗口 = 3 行（diff 块周围保留 3 行相同内容作为锚点）

  3. 相邻 hunk 合并（间距 < 6 行时合并为一个 hunk）

  4. 多 hunk 截断（超过 5 个 hunk 时显示前 3 个 + "…其余 X 处变更" 摘要）
```

**为什么不用外部 diff 库**：

- 现有依赖（picocolors, better-sqlite3）都不提供 diff
- `diff` npm 包虽然成熟但增加依赖 → 不符合"零新依赖"目标
- 简化 Myers 实现约 80 行，足够覆盖代码变更的常见场景
- 如果未来需求增长，切换到 `diff` 库的成本 = 换 import + 改 5 行类型适配

### 2.4 渲染器设计

```
DiffRenderer.render(hunks: Hunk[], oldPath: string, newPath: string): string

输出：
  ┌─ 📝 {相对路径} ──────────────────────────────────────┐
  │  共 N 处变更: +{adds} −{removes}                     │
  │  〔空行〕                                              │
  │  {每个 hunk 的内容}                                    │
  │  ──────────────────────────────────────────────────── │
  │  [交互提示行]                                          │
  └───────────────────────────────────────────────────────┘

每个 hunk 的内部格式：
  pc.cyan(`  第 ${oldStart} 行`)                         ← 青色行号锚点
  pc.red(`  - ${trimContent(line)}`)                     ← 红色删除行
  pc.green(`  + ${trimContent(line)}`)                   ← 绿色新增行
  pc.dim(`    ${trimContent(line)}`)                     ← 灰色上下文行

特殊情况：
  - 新文件（无旧内容）：不生成 diff → 显示 "新建文件：{路径} ({N} 行)"
  - 空文件（content 为空）：不生成 diff → 显示 "清空文件：{路径}（确认删除所有内容？）"
  - 完全不变：不触发确认 → 直接返回 "文件未变更"
```

### 2.5 交互设计

使用 `node:readline/promises`（已在 `path-guard.ts` 中使用）：

```
确认写入？[Enter=确认] [n=拒绝] [v=查看全文]

| 按键            | 行为                                                         |

| Enter / y / yes | 确认写入 → 继续                                              |

function wrapToolExecutor(toolExec: ToolExecutor, config: Config) {

  const onBeforeWrite =
    config.confirmWrites !== false

            oldContent?.split('\n') ?? [],
            newContent.split('\n'),

          const diffDisplay = DiffRenderer.render(hunks, path);
          const ok = await promptUser(diffDisplay);
          return ok;

      : undefined;

  return async (name: string, args: string): Promise<string> => {
    // ... 现有 start/end 格式化不变 ...
    const result = await toolExec.execute(name, args, { onBeforeWrite });
    // ...
  };
}

```typescript
function formatActionSummary(records: ToolCallRecord[]): string {
  if (records.length === 0) return '';

  const lines = [
    '',
    pc.dim('─'.repeat(50)),
    pc.bold('📋 本轮摘要'),
    '',
    ...records.map((r) => {
      switch (r.tool) {
        case 'read_file':
          return pc.dim(`  🔍 read_file  ${r.path}  ${r.newLength ?? '?'} 行`);
        case 'write_file':
          return pc.yellow(
            `  ✏️  write_file ${r.path}  +${r.newLength ?? '?'} −${r.oldLength ?? '?'}`,
          );
        case 'search_memories':
          return pc.dim(
            `  🔍 search_memories  "${r.query}"  ${r.results ?? 0} 条`,
          );
        case 'list_dir':
          return pc.dim(`  📁 list_dir  ${r.path}`);
        default:
          return pc.dim(`  🔧 ${r.tool}`);
      }
    }),
    pc.dim('─'.repeat(50)),
  ];
  return lines.join('\n');
}
```

## 四、A-103：流式 Markdown 渲染

### 4.1 设计约束

**核心约束：流式**。LLM 输出是逐字符到达的，你不知道下一个字符是什么。这意味着不能做完整的 Markdown
AST 解析——只能做**状态机模式**的增量渲染。

### 4.2 状态机设计

````
状态定义：
  NORMAL        → 普通文本
  HEADING       → 检测到行首 # 后的状态
  CODE_FENCE    → 检测到 ``` 后的状态（代码块内）
  INLINE_CODE   → 检测到 ` 后的状态（行内代码）
  LIST_ITEM     → 检测到行首 - /* 后的状态

转换规则（每个字符驱动状态切换）：

  NORMAL + '\n' + '#'    → 缓冲行首 # → 等待确认是否为 heading
    → 下一个 ' ' 或 '#'  → 确认 heading → 输出 pc.bold(pc.cyan(...))
    → 下一个普通字符      → 不是 heading → 还原缓冲 + 继续 NORMAL

  NORMAL + '\n' + '``'   → 累积 ```
    → 第三个 '`'          → CODE_FENCE 开始/结束切换
    → 后面跟语言标签     → 记录语言，输出 pc.dim(`\`\`\`${lang}`)

  INLINE_CODE + '`'      → INLINE_CODE 结束（输出 pc.dim(缓冲内容)）

  NORMAL + '\n' + '-'    → LIST_ITEM（输出 pc.cyan('•') + 缩进）
    → '\n' + '-'          → 继续 LIST_ITEM
    → '\n' + 空行         → 回到 NORMAL
````

### 4.3 输出效果

```
NORMAL：                            → stdout.write(chunk)  （不变）
HEADING（# + 空格后）：              → pc.bold(pc.cyan(chunk))
CODE_FENCE 内：                     → pc.dim(chunk)  （灰色代码）
INLINE_CODE：                       → pc.dim(chunk)  （灰色内联代码）
LIST_ITEM：                         → pc.cyan('• ') + chunk
```

### 4.4 实现约束

- **不做行缓冲**：能逐字渲染就不等换行。唯一的例外是 heading（需要确认 `#`
  后面是空格还是普通文本）
- **HEADING 确认**：`#` 出现在行首时，缓冲 `#`，等待下一字符。如果是空格 →
  heading 确认，输出 bold cyan。如果是普通字符 → 还原 `#` + 继续 NORMAL
- **代码块语言标签**：不解析，直接显示 ``pc.dim(`\`\`\`${lang}`)``

### 4.5 代码位置

**新增文件**：

```
src/cli/markdown-renderer.ts    → MarkdownRenderer 类，~150 行
```

**修改文件**：

```
src/cli/repl.ts                 → 流式输出时用 MarkdownRenderer 包裹
```

**集成方式**（repl.ts 中原有 flow 对比）：

```typescript
// 当前：
for await (const chunk of loop.processUserInput(input)) {
  process.stdout.write(chunk); // ← 直接写
  assistantContent += chunk;
}

// 优化后：
const md = new MarkdownRenderer();
for await (const chunk of loop.processUserInput(input)) {
  process.stdout.write(md.feed(chunk)); // ← 经渲染器处理
  assistantContent += chunk;
}
process.stdout.write(md.flush()); // ← 清理残留状态
```

**对 `assistantContent` 不再要求原始文本**：`assistantContent`
仍用原始文本（`chunk`），写入 topic-\*.md 时不受影响。

接口由 SecurityGuard 实现时走安全确认，由 DiffRenderer 实现时走 diff 展示，不同模式激活不同实现。
