## 四、P1 详情：diskWrite 契约覆盖自定义工具（已落地 2026-11-01）

- **缺口真源**：`ToolDefinition.diskWrite` 宿主可声明，但写盘派生索引（`PATH_WRITE_TOOL_NAMES`/`OPAQUE_WRITE_TOOL_NAMES`）只从 `ALL_BUILTIN_TOOL_DEFS` **静态**派生 ⇒ 宿主经 `registerTool` 注册的写工具**绕过写串行闸**（正踩 `loop.ts` 写串行闸防的「insert+append 同 step 并行 → 静默丢内容」）+ **无改盘追踪**（`fileChangeTracker` 不报）。
- **正解（生长非堆砌）**：让 `diskWrite` 声明对**所有**工具生效（声明即判据），延伸既有契约链；**不新建注册表**。
- **落地形态（三消费面同源，缺一即半个补丁）**：
  1. **写串行闸 + opaque 屏障**：`AgentLoop.resolveWriteIntent` 按工具定义声明判定（查找序 = 当前定义快照（含自定义工具）→ 内置全量兜底），`'path'` 走 `args.path` 同目标链、`'opaque'`/提取失败走屏障；
  2. **写后 read_file 缓存与覆盖度台账失效**：同走 `resolveWriteIntent`（原按 `WRITE_PATH_EXTRACTORS` 静态表只覆盖内置，自定义写工具落盘后模型会继续读到陈旧缓存）；
  3. **宿主改盘追踪**：`tool_start` 事件新增**可选** `diskWrite` 字段（最小契约扩张），`fileChangeTracker.noteToolStart` 消费上报声明；`chatPanel` 的 opaque 分支**一次判定、双向对称**——写前按声明判定并落 `scriptSnapshots`，写后按**写前登记**（`scriptSnapshots.has`）做快照 diff，不重判工具名。静态名集仅作旧事件兜底。
- **静态派生索引的去留（2026-11-02 订正）**：`PATH_WRITE_TOOL_NAMES` / `WRITE_PATH_EXTRACTORS` **保留**——内置工具契约钉 + 宿主 `DISK_WRITE_TOOLS` 仍派生自后者，但**不再是唯一判据来源**；`OPAQUE_WRITE_TOOL_NAMES` 随宿主 `chatPanel` 消费退役而**标废弃、6.0.0 移除**（本版保留导出并标 `@deprecated`，移除清单真源 = `tasks/待完成任务.md` · `DEPRECATE-1`；符号本体仍在 `builtinTools.ts` 供 `CONFIRM_ENTRY_BY_TOOL` 键集核对与守卫测试）。
- **四条不带伤约束（已验证全绿）**：① `confirmEntry.test.ts` 登记表键集 ≡ `OPAQUE_WRITE_TOOL_NAMES` 双向相等（未动）；② `publicMemberSurfaceGuard` 钉死 `ToolDefinition` 成员（未加成员，仅注释订正）；③ `builtinTools.test.ts` 契约钉 path 集 / opaque 集（未动）；④ 派生索引静态 vs 运行时注册的张力 → 取「按声明动态判据」。
- **完成判据（订正版）**：注册一个声明 `diskWrite:'path'` 的自定义写工具后，同 step 并行两写**不静默覆盖**、**写后 read_file 缓存失效**、**宿主改盘追踪上报**；三处守卫同步后全量门禁绿。
- **原判据与实施遗留三处（2026-11-01 排雷订正，防未来照旧稿复述）**：
  1. 「`confirmEntry` 登记生效」**不适用于自定义工具**——`CONFIRM_ENTRY_BY_TOOL` 是**内置执行面**的审批路由表，自定义工具走 `confirmPolicy`（`always`/`audit`/缺省，见 `ToolDefinition.confirmPolicy`）；声明 `diskWrite` 不会把自定义工具塞进该表，也不该塞（两件事不折叠）。
  2. 原判据漏列**第三消费面**「写后缓存/覆盖度失效」——只改串行闸会留下「自定义写工具落盘后模型仍读到陈旧 `read_file` 缓存」的半个补丁。
  3. **实施遗留（同日第二刀）**：宿主 `chatPanel` 的 opaque 分支原只改了 `tool_start` 侧（按声明判定），`tool_result` 侧仍按 `SCRIPT_WRITE_TOOLS` 静态名集 ⇒ 自定义 opaque 工具「写前扫了快照、写后不 diff」，且 `scriptSnapshots` 条目泄漏。已改为消费**写前登记**，一处判定双向对称。
- **未覆盖面（如实登记，不承诺全覆盖）**：`guardRail.write_loop` 护栏仍只 `matches('write_file')` ⇒ 自定义写工具不受「整文件覆盖连写止损 / 同路径连续失败止损」。**刻意不扩**：该护栏判据依赖 `mode=overwrite` 语义，自定义工具无 `mode` 约定，硬扩会把「无 mode」误当整文件覆盖而误拦；**静默丢内容**风险已由写串行闸（本刀已覆盖）挡住，护栏属第二层止损、非安全底线。触发条件 = 出现自定义工具的连写 / 连失败实例再评估。
- **验证（实测）**：内核 3091 例 + 宿主 2340 例全绿；双侧 tsc / eslint `--max-warnings 0` 绿；`verify:dist-contract` 内核 dist ↔ src 一一对应、宿主 bundle 同代（hash `040c00f69277`，2026-11-01 实测）；新增测试 4 组（自定义 `'path'` 同路径两写串行 / `tool_start` 上报与未声明缺省 / 宿主自定义声明进追踪 / 声明 `opaque` 不进按路径追踪）。
- **不重叠**：与 `TOOLSIG-1` 正交（那条管参数形状，本条管写盘声明是否生效）。

## 五、P2 详情：失败升级窄版（R1 · 已落地 2026-11-01）

- **缺口真源**：后台通道（`SessionArchiver` / `TextPolishManager` / `RoundSummaryGenerator`）原按 `backgroundProvider ?? provider` **裸回退**——后台这次失败，本次摘要 / 归档直接失败（前台明明可用却无兜底）。
- **正解（生长非堆砌）**：把「后台 Provider 选谁 + 失败升级」收敛为**唯一判定点** `resolveBackgroundProvider(background, foreground)`（`src/llm/backgroundProvider.ts`）；装配期 `assembler.ts` 三个消费者共用一份解析结果，热切换 `agent.setBackgroundProvider` 复用同一函数，**不在各消费者内部复制升级判据**。未配置后台 Provider 时原样返回前台实例（零包装开销 = 「缺省回退前台」契约的实现点）。
- **升级判据（两条硬边界）**：
  1. **只在后台通道**——主对话 `AgentLoop` 完全不经过本模块（主对话换档 = 动态分档 `autotier`，§二已拒枝）；
  2. **只在「未产出任何增量」时用前台重试一次**——已流出内容的失败不重试（重发 = 正文重复，**脏数据比失败更坏**）；`signal.aborted`（用户已取消）不重试。
- **口径拍板（2026-11-01，用户选定「单次失败即升级」）**：原稿写的「连败 N 次 + TTL」**被否**——后台调用彼此独立、无天然次数语义，凑出「N 次」必须在 Provider 外维护「计数 + 定时复位」状态机 = 在最小单元外新造状态。**代价如实登记**：后台通道持续故障时，每次仍先失败一次（多一次请求延迟）。
- **能力位镜像**：装饰器把 `supportsToolCalling` / `supportsVision` 镜像自 primary（装饰器只加「失败升级」，不得改变能力语义，否则调用方判据与实际执行面不符 = 谎报）。上报名为 `后台名(→前台名)`。
- **验证（实测）**：`src/llm/__tests__/backgroundProvider.test.ts` 6 例（未配置→原样返回前台 / 后台正常时前台零调用 / 产出前失败→升级一次 / 产出后失败→不重试且异常抛出 / 取消→不重试 / 能力位镜像）；内核 `npx tsc --noEmit` 退出 0。
- **热切换覆盖面（2026-11-01 第二刀已收口）**：`TextPolishManager` 补 `setBackgroundProvider`（形态与归档 / 摘要同构），**三个消费者热切换全覆盖**——此前润色沿用装配期实例（用户改后台模型后点「润色」仍走旧模型，另外两个跟随、一个不跟随的可见不一致）。验证 = 走公开面 `agent.polish.polish()` 断言后台实例被真实调用（2 例）+ 变异验证（移除注入 → 恰好这 2 例转红）。同批删除宿主「语义去重」退役名 5 处（`DedupManager` 已于 `GOVERNANCE-SRC-1`（2026-10-18）整链退役，现存 `read_dedup` 为纯本地护栏、不调 LLM）。
- **为何只做窄版（对抗式）**：全量 per-request escalation 两条硬伤——① 同请求跨档重发 token 翻倍；② 升档后仍失败形成死循环。窄版只碰后台任务：不影响主对话体验，纯收益。

## 九、扩展轴实测澄清（2026-11-01 会话后补 · 三轴地图与 MCP 定位）

> 触发：用户提出「在 VS Code 插件里仿照 skill 增加一个插件模块（明确插件目录 + 手动选择，含角色包内置插件）」。回源码逐条实测后收敛如下；全部符号引用。

### 三轴分工（memora 的「插件系统」实为三条受控轴，共用同一内核地基）

| 轴 | 定位 | 实测真身（符号引用） |
| --- | --- | --- |
| MCP 服务器 | 接外部工具（**窄插件**） | `memora.mcpServers` → `startMcpServers` → `registerTool`；跨进程协议、零信任、只交换工具，调用过裁决链 |
| 技能 skill | 全局能力包（说明书 + 资源 + 脚本） | 用户目录 `SkillManager.loadExtraDir`；启停全链已在生产：设置面板 `toggleSkillDisabled` → `memora.disabledSkills`（ConfigurationTarget.Global）→ `assemble` 注入内核 `disabledNames` 真源 → 对模型 = 不存在 |
| 角色包 role-pack | 完整「插件包」：人格 + 规则 + 内嵌技能 + 能力白名单 + 策略 | `manifest.skills`（`RolePackManifestSkill`，L3 脚本）+ `manifest.capabilities`（中立命名空间 `file:write` 等 → `CAPABILITY_TO_TOOLS` 闭表映射工具白名单）；消费链实测全通：`read_skill` 渐进披露 L2 优先查激活包内嵌技能（`toolExecutor`），脚本走同一沙箱 + 裁决链（`scanPackSkills` layer3） |

### 对用户思路的逐条裁决

1. 「内核 agent 边界 vs 宿主功能边界」——**即现状架构**（内核机制 / 宿主策略与注入），以本表钉死，不另拆。
2. 「插件目录放代码」——**拒枝复确认**：= 运行时动态装载器（§二 已拒）。skill 脚本之所以可放目录，因其**按次执行**过沙箱 + 裁决链；「注册即常驻」的插件代码是另一信任级别，同进程加载外部代码破坏零依赖宪法与 §13 信任设计。
3. 「角色包内置插件」与「和 skill 一样手动选择」——**均已存在**（上表 role-pack 行 + skill 启停链），无需新建。
4. **MCP 与 dsh 插件不是同一思路**（同为「可插拔扩展」，三个对立选择）：dsh = 同进程（node_modules import）+ 全接缝（模型 `ctx.llm` / 工具 / 事件 / UI 投影 / pre-step）+ 插件与宿主**同信任**；memora MCP = 跨进程 + 单接缝（仅工具）+ **零信任**（外部只按声明交换能力）。memora 刻意选窄：表达力换信任边界（零依赖 + §13 + 拒枝记录三重护栏），是设计决策非能力差距。
