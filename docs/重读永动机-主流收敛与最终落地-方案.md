# 重读永动机 · 主流收敛与最终落地方案

## 0. 一句话

把「压缩后模型反复重读同一文件、token 疯狂烧」从根上拆掉：**被逐出的读结果要留下「带覆盖度的已读摘要」，而不是空占位**——模型拿到要点就不必重读整文件；配合一个**按「已读判据解耦」的结构化台账**，让防重确定性触发。这是把 CTX-1b 已定稿的 B1–B3 方案，用主流证据 + 198 万 token 真机复发重新佐证、收敛成可落地形态。

## 1. 实证（本次真机复发，2026-09-15）

`round-1789441792151.json`（一次 turn）：
- **182 次 `read_file`**，循环重读同一批文件（宪法 / 产品构思 / 作者端 / 读者端 / 缺口分析 / 评估报告 / 白话总结 / Spike 任务表，各重读 ~14 次）；
- 工具 186 次、1:1 配对、`toolFailureCount: 0`、`status=complete`；
- **`tokenIn 1,982,332`（≈198 万）**、`tokenOut` 仅 802、耗时 406s。

> 与 CTX-1 首次 148 次重读、171 万 token 同根。性质：**合法但冗余的读**（配对完好，故 TOOLPAIR-2 成形守卫正确不拦——这不是成形问题，是**读取防重与压缩协同**缺口，CTX-1b 的 B1–B3 未落地所致）。

**主流共识一句话**：模型重读是因为「它需要的要点被逐出上下文后拿不到了」；解法不是**禁止重读**（那是和模型对抗），而是**让被逐出的读留下一份可用的摘要 / 让重读廉价** + **把提取的关键事实写进跨重置的记忆**。这正是 CTX-1b 定案的形态，本方案只是把它对准主流证据再夯实。

## 3. 根因归位与关键洞察

### 3.1 结构性失效（为何 198 万）
防重前置 `isCachedResultStillInContext` 要求「结果**仍在**上下文」；而压缩链 `ResultReplacementStrategy` 的**唯一职责就是把结果移走** → 前提恒假 → 防重结构性失效 → 每次压缩后模型以为「没读过 / 忘了内容」→ 重读 → 又占满 → 永动机。

### 3.2 关键洞察（主流 + 实证共同指向）
- **禁止重读必然失败**：模型需要内容，空 `[ALREADY_READ]` 会逼它换参重读（换 offset 绕过）——`toolResultCache` 去重主体含 offset/limit 就是放大器。
- **正确姿势 = 让步式防重**：不空拒，而是「**已读 + 覆盖度摘要 + 续读指针**」——模型拿到要点就不再整读；确实要细节才用 `offset` 定向续读（`read_file` 已有 offset/limit + 分段脚注，CTX-1 Step 1a 已具备）。

## 4. 最终不带伤设计（承重序 B1→B3）

### B0 · 结构化工具台账（把「已读」判据从"在上下文"解耦出来）· P0
- **现状缺口**：`toolResultCache` 判据 =「结果是否还在上下文」→ 被压缩抵消。台账则只记「**发生过**」不判「在不在」。
- **落法**：读/工具调用入台账（同 `resetTurnState` 生命周期），判据与占用解耦；`remember_intel` 情报区已能累积「已提炼要点」，台账与情报区分工：台账记"读过没"，情报区提供"读出了什么"。
- **不带伤**：非新引擎，是把已存在的 `remember_intel` 语义提为「已读记账」的确定性护栏；不新增后台任务（turn 内同步）。

### B1 · read_file 压缩 → 带覆盖度的摘要替代（非空占位）· P1 【关键、先止烧】
- **落点**：压缩链**第二级** `ResultReplacementStrategy`——这正是逐出发生处。
- **形态**：对 `read_file` 结果，**不**清空为占位，而替换为**带覆盖度的已读摘要**：
  `[已读 <path> 第 X–Y 行（覆盖 M%）] <要点>。需细节请用 read_file(path, offset=Y+1, limit=?)。`
  - 覆盖度元信息（防 unknown unknowns / 虚报"已读完"）；
  - 续读指针复用既有 `read_file` offset/limit + 脚注（CTX-1 Step 1a），零新机制；
  - 触发锚点 =「返回分段脚注时」（offload 对 read_file 结构性不触发，故摘要在此生成）。
- **不带伤**：替换的是**即将被逐出**的位置，不改变健康态；模型拿到「已读+覆盖度」后**不再需要重读整文件**——这正是主流的 editing→memory 分工（清结果省 29%、供要点再省 39%）。

### B2 · 拦截三分支 + 升级拦截器 · P0-1 + P0-2
- **拦截三分支（P0-1，以 B0 台账为真源）**：同 `(path,offset,limit)` 再触发时——① 内容仍可用 → 拦（返已读）；② 已被 B1 摘要化 → **返摘要 + 续读指引**；③ 文件已改 → 放行重读。
- **升级 `DuplicateCallInterceptor`（P0-2，顺带修 N1/N2/N3）**：同参判据（N2）+ 判定前移执行前（N1 真 block）+ threshold SSOT（N3）。**不新建计数器**。

### B3 · 失败即给证据 · P2（后置）
失败读（如幻觉路径）返回「目录清单 / 存在性证据」，让模型自纠正，不再对不存在文件反复试读。

### 明确不做的部分（防泄漏）
- ❌ 不做「禁止重读的硬拦截」：与模型对抗会诱发换参绕过（3.2）。
- ❌ 不做服务端 prompt-cache 依赖：mimo 无可信缓存，靠内核可控（B1 摘要），不赌外部。
- ❌ 不新增后台/定时任务：台账与摘要都在 turn 内同步（SSOT「摘要+归档=turn 后处理」）。

## 6. 落地序（先止烧，后完善）

- **B1 先行（本批目标）**：摘要替代非空占位——一次改动直接打破「逐出→重读」循环，预估可复现 30–50% token 下降（对齐主流 29%–39% 量级）。
- **B0 紧随**：台账解耦判据，让 B2 拦截有确定性真源。
- **B2 → B3 后置**：三分支 + 拦截器升级 + 失败证据。

## 7. 可判定验收

- **重读率**：同一 turn 内同 `(path,offset,limit)` 的 `read_file`，第二次起应返「已读摘要+覆盖度」，不再整读（对全量测试 + 真机复测）。
- **token 降幅**：真机短测（多次读同一文件）tokenIn 应显著下降（≥30% 量级）。
- **无新后台/状态**：改动全在既有 loop 同步路径。
- **守卫不受扰**：TOOLPAIR-2 `llmPairingGuardFires` 仍应 0（B1–B3 不产生畸形批次）。
