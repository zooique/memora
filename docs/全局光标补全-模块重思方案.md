# 全局光标补全 · 模块重思方案

> **来源**：新枝破土（输入补全深化）→ 问诊门控 → 模块重思
> **日期**：2026-07-14
> **状态**：📋 方案待评审（模块重思产物，未实装）

## 1. 问题陈述

### 1.1 战略定位

用户明确指出：**输入补全是桌面精灵的差异化打法**。

| 维度 | 分析 |
|------|------|
| 竞争劣势 | memora 的对话/记忆/角色功能被大厂碾压，无差异化壁垒 |
| 核心优势 | 桌面精灵常驻后台，可在日常使用中全局生效 |
| 差异化路径 | 全局光标补全——任何应用输入时都能调用个人记忆库 |
| 目标体验 | 用户激活光标输入时，静默启动补全，无需切窗 |

### 1.2 现状

当前输入补全（[quickInputCompletion.ts](../hosts/memora-sprite/src/electron/renderer/quick-input/quickInputCompletion.ts)）已实现：

- 浮窗模式：`Ctrl+Shift+I` 触发，独立窗口，屏幕居中靠上 1/4 定位
- 数据源：`searchMemories` + `searchSessionMessages` 双源并行
- 补全能力：防抖触发 / 候选合并去重 / ↓↑ 键盘导航 / Tab 回填
- 反馈回路：采纳 boost（单次会话内）+ score 量纲统一

### 1.3 痛点

| 痛点 | 说明 |
|------|------|
| 触发割裂 | 需要主动呼出独立浮窗，打断当前工作流 |
| 定位不跟随 | 屏幕居中而非光标位置，视线和鼠标需要长途迁移 |
| 回填需手动 | 选中后写入剪贴板，用户还需手动 Ctrl+V 粘贴 |
| 场景局限 | 仅在 memora 内有效，未发挥"常驻后台 + 全局生效"优势 |

### 1.4 设计约束

| 约束 | 说明 |
|------|------|
| 不违反内核零依赖 | native 依赖只放在宿主项目（hosts/memora-sprite） |
| 不新增 IPC 治理压力 | 当前 IPC 通道数 105，接近 150 治理阈值，优先复用现有通道 |
| 隐私边界 | 不监听全局键盘输入，不读取其他应用窗口内容 |
| 跨平台 | Windows 优先，macOS/Linux 后续（native 依赖需跨平台构建） |

## 2. 技术可行性分析

### 2.1 "静默启动"的技术边界

用户期望"光标激活输入时静默启动"，但技术上存在两层"光标"概念混淆：

| 光标类型 | 获取方式 | 跨应用可行性 |
|---------|---------|------------|
| 鼠标光标（mouse cursor） | `screen.getCursorScreenPoint()` | ✅ 已有先例（[quickInputWindow.ts:156](../hosts/memora-sprite/src/electron/windows/quickInputWindow.ts)） |
| 文本输入光标（caret） | UI Automation API / MSAA | ❌ 需 native addon 调用系统 API |

**结论**：完全静默启动（监听其他应用的 caret 焦点变化）在 Electron 原生能力下不可行。可行折中：

- **保留快捷键触发**（不静默），但窗口跟随鼠标光标位置弹出
- 这是正确的隐私边界——不监听全局输入，只在用户主动触发时工作

### 2.2 现有基础设施复用率

研究子代理探索结果显示，`quickInputWindow` 已具备全局光标补全的 80% 基础设施：

| 能力 | 现状 | 复用度 |
|------|------|-------|
| 全局快捷键触发 | `Ctrl+Shift+I` 已绑定，ShortcutManager 支持热更新 | 100% |
| 光标屏幕定位 | `screen.getCursorScreenPoint()` 已使用 | 100%（改定位公式即可） |
| 候选数据源 | `searchMemories` / `searchSessionMessages` 已暴露到渲染进程 | 100% |
| 剪贴板写入 + 三重保护 | `confirmQuickInput` + `suppressNextChange` 链路完整 | 100% |
| 失焦延迟关闭 | 200ms blur 延迟，给 Alt+Tab 切换留余量 | 100% |
| 动态高度调整 | `resizeQuickInput(80-400px)` 已预留 | 100% |
| 候选列表 UI + 键盘导航 | `quickInputCompletion.ts` 已完整实现 | 100% |

**关键发现**：无需新建窗口类型，复用 `quickInputWindow` 改造即可。

### 2.3 回填机制的技术路径

补全结果回填到当前焦点窗口是核心难点，有三条路径：

| 方案 | 机制 | 依赖 | 体验 | 可行性 |
|------|------|------|------|-------|
| A. 剪贴板 + 手动粘贴 | 选中 → 写剪贴板 → 浮窗关闭 → 用户 Ctrl+V | 零新依赖 | 多一步操作 | ✅ MVP |
| B. 剪贴板 + 自动粘贴 | 选中 → 写剪贴板 → 模拟 Ctrl+V → 浮窗关闭 | `@nut-tree-fork/nut-js`（native） | 无缝 | ✅ 进阶 |
| C. 直接键盘事件注入 | 选中 → 模拟逐字符键盘事件 | native 模块 | 中文 IME 支持差 | ❌ 不推荐 |

**方案 B 的 native 依赖评估**：
- `@nut-tree-fork/nut-js`：活跃维护，跨平台（Win/Mac/Linux），支持键盘模拟
- 宿主项目已有 `better-sqlite3` native 依赖，打包流程已支持 native 二进制
- 体积增加约 5-10MB，对桌面应用可接受
- 与 Electron Node.js 24 LTS 兼容（需验证）

**推荐**：MVP 用方案 A（零依赖快速验证），验证后升级方案 B（体验质变）。

## 3. 设计方案

### 3.1 核心理念：光标跟随快捷补全

不做"静默启动"（技术不可行 + 隐私风险），改为**"一键触发的光标跟随补全"**：

```
用户在任何应用输入时
  → 按 Ctrl+Shift+I（或自定义快捷键）
  → 补全浮窗在当前鼠标位置附近弹出（贴着光标，非屏幕居中）
  → 用户输入查询 / 直接查看基于剪贴板内容的候选
  → 实时显示候选列表（记忆 + 对话双源）
  → Tab/Click 选中
  → 自动写入剪贴板 +（进阶）自动粘贴回当前焦点窗口
  → 浮窗关闭，继续原工作流
```

### 3.2 交互模型设计

#### 3.2.1 触发方式

| 触发 | 说明 |
|------|------|
| 快捷键（主） | `Ctrl+Shift+I`（可配置），全局触发，跟随鼠标位置弹出 |
| 剪贴板感知（辅） | 触发时检测剪贴板是否有文本，若有则作为初始查询预填（用户可修改） |

**剪贴板感知的创新点**：用户复制一段文本后直接按快捷键，浮窗已基于复制内容拉取候选——减少输入步骤。需遵守 `suppressNextChange` 保护，避免读取触发自身剪贴板事件。

#### 3.2.2 定位策略

改造 [quickInputWindow.ts:156-162](../hosts/memora-sprite/src/electron/windows/quickInputWindow.ts) 的定位公式：

```typescript
// 现状：屏幕居中靠上 1/4
const display = screen.getDisplayNearestPoint(screen.getCursorScreenPoint());
const workArea = display.workArea;
win.setPosition(
  Math.round(workArea.x + (workArea.width - width) / 2),
  Math.round(workArea.y + workArea.height * 0.25 - height / 2),
);

// 改造：光标位置 + 偏移，含屏幕边缘溢出回弹
const cursor = screen.getCursorScreenPoint();
const display = screen.getDisplayNearestPoint(cursor);
const workArea = display.workArea;
let x = cursor.x + 16;  // 鼠标右侧 16px
let y = cursor.y + 16;  // 鼠标下方 16px
// 边缘溢出回弹
if (x + width > workArea.x + workArea.width) {
  x = cursor.x - width - 16;  // 改为鼠标左侧
}
if (y + height > workArea.y + workArea.height) {
  y = workArea.y + workArea.height - height - 16;  // 贴底部
}
win.setPosition(Math.round(x), Math.round(y));
```

#### 3.2.3 候选展示

复用现有 `quickInputCompletion.ts` 的候选列表渲染，零改动：
- ↓↑ 键盘导航 / Tab 确认 / Click 选择
- 来源标签（记忆/对话）+ score 排序 + Top-5 截断
- 采纳反馈回路（单次会话内 boost）

#### 3.2.4 回填机制（分阶段）

**MVP（方案 A）**：
1. 选中 → `confirmQuickInput(text)` → 主进程写剪贴板 + `suppressNextChange()`
2. 浮窗关闭
3. 在光标附近显示微小 Toast"已复制，Ctrl+V 粘贴"（1.5 秒自动消失）
4. 用户 Ctrl+V 粘贴到当前焦点窗口

**进阶（方案 B）**：
1. 选中 → `confirmQuickInput(text)` → 主进程写剪贴板 + `suppressNextChange()`
2. 主进程调用 `nut-js.keyboard.type(Key.V, ...)` 模拟 Ctrl+V
3. 浮窗关闭
4. 文本自动粘贴到当前焦点窗口

### 3.3 架构改动清单

| 改动点 | 文件 | 层级 | 依赖 |
|--------|------|------|------|
| 定位公式改造 | `quickInputWindow.ts` show() | 主进程 | 零新依赖 |
| 剪贴板感知预填 | `quickInput.ts` initQuickInput() | 渲染进程 | 零新依赖 |
| Toast 提示 | 新增 `completionToast.ts` 或复用 quickInputWindow | 渲染进程 | 零新依赖 |
| 自动粘贴（进阶） | 新增 `inputInjector.ts` 主进程模块 | 主进程 | `@nut-tree-fork/nut-js` |
| 快捷键配置 | `shortcutDefaults.ts` 新增 action | 共享 | 零新依赖 |

### 3.4 IPC 通道影响

**零新增 IPC 通道**。所有改造复用现有通道：
- `QUICK_INPUT_CONFIRM` / `QUICK_INPUT_CLOSE` / `QUICK_INPUT_RESIZE` / `QUICK_INPUT_SHOW`
- `MEMORIES_SEARCH` / `SESSION_SEARCH`

进阶方案的自动粘贴在主进程内完成，不经过 IPC。

## 4. 分阶段实施计划

### 4.1 Phase 1：光标跟随定位（MVP-1）

**范围**：改造定位公式，浮窗跟随鼠标光标位置弹出。

**改动**：
- `quickInputWindow.ts` show() 内定位逻辑（约 10 行改动）
- 边缘溢出回弹处理

**验证**：
- 多显示器场景（光标在副屏时浮窗在副屏弹出）
- 屏幕边缘（右侧/底部溢出时回弹到左侧/顶部）

### 4.2 Phase 2：剪贴板感知预填（MVP-2）

**范围**：触发时检测剪贴板内容，作为初始查询预填输入框。

**改动**：
- `quickInput.ts` initQuickInput() 内，`onQuickInputShow` 回调中读取剪贴板
- 若剪贴板有非敏感文本（复用 `clipboardHandler.isSensitive` 检测），预填输入框并触发补全
- 输入框全选状态，用户可直接覆盖或修改

**隐私保护**：
- 复用 `clipboardHandler.isSensitive` 的 5 种正则检测（token / 信用卡 / 密码 / 私钥 / AWS key）
- 敏感内容跳过预填，保持空输入框

### 4.3 Phase 3：回填 Toast 提示（MVP-3）

**范围**：选中后显示"已复制，Ctrl+V 粘贴"Toast。

**改动**：
- 复用 quickInputWindow 的 resize 能力，或新建极小 Toast 窗口（120x40px）
- 1.5 秒自动消失，不抢焦点

### 4.4 Phase 4：自动粘贴（进阶）

**范围**：引入 `@nut-tree-fork/nut-js`，选中后自动模拟 Ctrl+V。

**改动**：
- 新增 `inputInjector.ts` 主进程模块（封装 nut-js 键盘模拟）
- `quickInputWindow.ts` 的 `QUICK_INPUT_CONFIRM` handler 内，写剪贴板后调用 `inputInjector.paste()`
- 用户配置开关（默认开启，可关闭回退到手动粘贴）

**风险**：
- native 依赖跨平台构建（Windows 优先，macOS/Linux 后续）
- 杀毒软件可能拦截键盘模拟（需代码签名 + 用户白名单）
- 部分应用可能拒绝模拟输入（如管理员权限窗口）

### 4.5 Phase 5：上下文感知补全（远期）

**范围**：基于当前工作文件 / 对话主题过滤候选。

**改动**：
- 需要新增 IPC 通道暴露当前上下文（工作文件路径 / 最近对话主题）
- 补全查询时携带上下文，主进程侧过滤候选

**暂不实装**，待 Phase 1-4 验证后评估。

## 5. 隐私与安全边界

| 边界 | 说明 |
|------|------|
| 不监听全局键盘输入 | 补全只在用户主动按快捷键时触发，不后台监听键盘事件 |
| 不读取其他应用窗口内容 | 不使用 UI Automation 读取其他应用文本，只处理用户在浮窗输入的查询 + 剪贴板内容 |
| 剪贴板敏感内容过滤 | 预填前检测 5 种敏感模式（token / 信用卡 / 密码 / 私钥 / AWS key），命中则跳过 |
| 自动粘贴可选 | Phase 4 的自动粘贴默认开启但可关闭，用户有完全控制权 |
| 查询不持久化 | 补全查询本身不写入记忆库，只有用户确认选中的文本才走 `onAfterConfirm` 记忆沉淀 |

## 6. 风险与替代方案

### 6.1 风险矩阵

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| nut-js 与 Electron 兼容性问题 | 中 | Phase 4 阻塞 | MVP（Phase 1-3）不依赖 native，先验证核心价值 |
| 杀毒软件拦截键盘模拟 | 中 | Phase 4 降级 | 代码签名 + 文档说明 + 自动降级到手动粘贴 |
| 光标定位在多显示器/DPI 缩放下偏移 | 低 | Phase 1 体验 | `getCursorScreenPoint()` 返回 DIP 点，需测试 125%/150% 缩放 |
| 剪贴板预填读取触发敏感内容泄露 | 低 | Phase 2 隐私 | 复用 `isSensitive` 检测，命中则跳过 |

### 6.2 替代方案（已驳回）

| 方案 | 驳回理由 |
|------|---------|
| 新建 `cursorCompleteWindow` 窗口类型 | 与 quickInputWindow 功能重叠 80%，浪费基础设施 |
| 在主窗口内做补全 | 无法跨应用生效，丢失"全局"核心价值 |
| 监听全局键盘事件做静默补全 | 隐私风险极高 + 技术不可行（Electron 无全局键盘钩子） |
| 使用 `webContents.sendInputEvent` 回填 | 只能发送到自家窗口，不跨应用 |

## 附录 B：nut-js 自动粘贴伪代码

```typescript
// hosts/memora-sprite/src/electron/inputInjector.ts（Phase 4 新增）
import { keyboard, Key } from '@nut-tree-fork/nut-js';

/**
 * 输入注入器 —— 模拟键盘事件将补全结果粘贴到当前焦点窗口
 *
 * 流程：写剪贴板 → 模拟 Ctrl+V → 系统粘贴到焦点窗口
 * 依赖 nut-js 的跨平台键盘模拟能力。
 */
export class InputInjector {
  /**
   * 模拟 Ctrl+V 粘贴剪贴板内容到当前焦点窗口
   *
   * 前置条件：调用前已完成 clipboard.writeText + suppressNextChange
   */
  async paste(): Promise<void> {
    await keyboard.pressKey(Key.LeftControl, Key.V);
    await keyboard.releaseKey(Key.LeftControl, Key.V);
  }
}
```
