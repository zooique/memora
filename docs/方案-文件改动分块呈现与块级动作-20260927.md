## 0. 一句话结论

**分块算法本身是对的**——真机数据复现实锤：本次改动算法输出的就是 **2 个独立块**，中间未改动的那行不高亮。用户看到「整个文件一起」，根因在**呈现层**（两块只隔 1 行、按钮在文件顶/底而不在改动处），不在算法。
命题 1（文件内去掉「全部」按钮）**已落地**，且与 Qoder / Trae 官方形态一致。命题 2（块级独立入口）需拍板三方案之一。

## 1. 真机实证（本次测试）

### 1.1 测的是什么

从 `.memora/rounds/round-1790457474083.json` 读出，**这不是普通的「改一个文档」**，而是刻意复现 DIFF-3 的场景：

| 序 | 工具 | 参数 | 结果 |
|---|---|---|---|
| 1 | `write_file` | `mode=insert`, `insert_line=28` | 28 行 → 31 行 |
| 2 | `write_file` | `mode=append` | 31 行 → 37 行 |

任务项原文即写「同一 step 内并行 insert（中段）+ append（文末）改同一文件，复现 DIFF-3 触发场景」。

### 1.2 算法输出（实锤，非推断）

用磁盘上的 37 行文件反推改动前的 28 行，喂给真实 `computeFileDiff`：

```
BEFORE_LINES 28  AFTER_LINES 37
DEGRADED false
HUNKS [{"s":28,"e":30,"removed":0},{"s":32,"e":37,"removed":0}]
```

即：

- **块 1 = 第 28–30 行**（中段插入，3 行）
- **第 31 行 = 未改动**（`**遗留标注**…`）——**不高亮**
- **块 2 = 第 32–37 行**（文末追加，6 行）
- `degraded=false`（未触发 1200 行降级）

⇒ **算法已经做到了用户要的「被旧内容分隔就分开」**。§「只有相邻才合并」的规则也已在 `lcsHunks` 里：walk 期间遇到相同行即 flush 当前块。

### 1.3 为什么看起来还是「一起」

三个叠加原因，全在呈现层：

| # | 原因 | 实证 |
|---|---|---|
| ① | **两块只隔 1 行**。第 28–30 行绿、第 31 行白、第 32–37 行绿——在 37 行的小文件里，尾部 10 行有 9 行是绿的，视觉上几乎连成一片 | §1.2 hunk 数据 |
| ② | **按钮在文件顶/底，不在改动处旁边**。`revealRange` 把视口滚到首个改动块（第 28 行），此时顶部那组（第 0 行）已滚出视野，只剩底部那组（末行）在视野里 ⇒ 用户看到的就是「只有底部一排按钮」 | `renderInline` 的 `revealRange(InCenter)` + `provideCodeLenses` 顶/底两组 |
| ③ | **改动块自身没有序号/边界标记**，用户无法从 UI 上读出「这是第几处、共几处」 | `buildDecorationItems` 只铺底色，块首行行尾仅挂 `⟵ 原: …` |

### 2.3 关于 per-hunk CodeLens 的位置

QCoder（另一同名产品文档 <https://www.qcoderai.com/docs/chat-editing>）写明「CodeLens actions appear **above each hunk**」。

**本方案的关键改进**：挂在 hunk **末行的下一行**（`endLine + 1`）。CodeLens 显示在行上方 ⇒ 视觉上紧跟该 hunk **之后**，归属明确，绕开 §11.8 的位置歧义。这是本方案与旧形态的**唯一但决定性**差异。

## 4. 命题 2：三方案与代价

| 方案 | 做什么 | 解决①视觉连片 | 解决②按钮不在改动处 | 改动面 | 代价 |
|---|---|---|---|---|---|
| **A. 只增强可辨识度** | 每块加序号/边界标记（块首行行尾追加 `改动 1/2` 类标记 + 块间更明显的边界） | ✅ | ❌ | 仅渲染层 | 低 |
| **B. per-hunk 按钮 + 真块级动作（推荐）** | 每个 hunk 后（`endLine+1`）放「接受此处 / 拒绝此处」；记录模型支持块级存活 | ✅ | ✅ | 渲染层 + 记录模型 + 回退逻辑 | 中 |
| **C. 维持现状**（只做命题 1） | — | ❌ | ❌ | 无 | 零 |

### 4.1 推荐 B 的理由

1. **用户要的就是它**：原话「没有按照块级独立显示按钮」。A 只解决「看不出几处」，不解决「按钮不在改动处」。
2. **数据结构已就位**：`DiffHunk` 同时携带「新文件中的行范围」+「被移除的旧行」⇒ 块级回退 = 行数组区间替换，**不需要新的 diff 机制**。
3. **与主流一致**：Qoder / Trae / QCoder 三层粒度全有「变更级」这一层；我们缺的正是它。

### 4.2 B 的实装要点（待拍板后细化）

- **块级回退**：`revertHunk(afterContent, hunk)` = 行数组把 `[startLine..endLine]` 换成 `hunk.removed`，写回后 **重算 diff**（其余块坐标自动更新），不维护块索引 ⇒ 无坐标漂移面。
- **块级接受**：该块从「待确认集」移除（不再高亮、不再出现在块按钮里）。存**内容指纹**而非行号（行号会随其他块回退而漂移）。
- **与文件级动作的关系**：文件级「确认/回退」作用于**剩余的全部块**；跨文件「全部确认/全部回退」不变。
- **计数口径**：状态栏与会话区常驻条目前按「文件数」计。B 引入块级后是否改按「改动处数」计，需一并拍板（建议**仍按文件数**——用户心智是「几个文件没确认」，块级是文件内的细分操作）。

### 4.3 B 的风险（如实记）

- 记录模型从「两全文」升级为「两全文 + 块存活集」，`FileChangeRecord` 属**持久化无关**（不落盘）⇒ 无迁移成本，但 `discardRecord` / `reconcile` / `hunkCache` 都要跟着走一遍。
- §11.8 残留风险「长文件中段看不到按钮」**顺带解决**（块按钮跟着改动走，不再只有顶/底）。

## 5. 五类不带伤扫描（预判）

| 带伤类型 | 判定 |
|---|---|
| **命名** | 块级动作文案必须是「接受此处 / 拒绝此处」（真块级）；**不得**沿用「确认本文件」措辞挂在每个块上——那是 §11.3 已判过的粒度混淆真伤 |

## 8. 落地记录（2026-09-27）

### 8.1 纯逻辑层（fileChangeDiff.ts，可单测）

只加**两个导出**，不加 `DiffHunk` 字段、不加块存活集：

| 导出 | 作用 |
|---|---|
| `applyHunkReverts(afterText, hunks)` | 行数组的**区间替换**：`[startLine..endLine]` → `hunk.removed`。多块按 `startLine` **降序**处理 |
| `hunkKey(hunk, afterText)` | 块寻址指纹 = 位置 + 内容（FNV-1a），用于「渲染 → 点击」的寻址，对不上即 fail-closed |

**关键推导（一个原语撑两个动作，与 git 的 index 模型同构）**：

- 拒绝一块 = `applyHunkReverts(after, [该块])` → **写盘**；
- 接受一块 = 基线改成 `applyHunkReverts(after, 其余块)` → **不动盘**，该块在新 diff 中自然消失。

⇒ 不维护「已接受块集」、不做坐标迁移、不做指纹持久化。

**降序是硬要求**（不是风格）：插入块还原会**改变行数**，升序处理会让后一块的行号整体前移、`splice` 打空。变异验证：把 `sort((a,b) => b.startLine - a.startLine)` 改成升序 → **恰 1 红**（真机形态「中段插入 + 末尾追加」例，残留内容正是预测的两行）。

⚠️ 变异验证的**自我排雷**：最初写的「多块一次性还原 = 写前内容」用的是等长替换（count == removed.length，行数不变）⇒ 升序降序结果一样 ⇒ 变异**不变红**。补上真机那组（两块都是插入）后才真正咬住。教训：**变异不变红要先怀疑断言没咬住判据，而不是断言代码有问题。**

### 8.6 第十二轮 · 真机验收后的两处修复（2026-09-27 · 用户即时反馈）

用户结论：§8.5 四点**全部通过**；另报一 BUG + 一提案。

**BUG-1「点了一个按钮后，底部修改的按钮跑到上面去了」**

> 定性用硬证据，不靠推断（真机文件实测，非推测）。

- 真机文件：`一束买不起的光/02-概念/创意杠杆候选.md`——`endsWithNewline = false`、`lineCount = 28`，被改的那行 = 第 28 行（0-based 索引 27），**正好是文件最后一行**。
- `hunk.endLine + 1 = 28` 越界 ⇒ `safeLineRange` clamp 回 27 ⇒ CodeLens 渲染在**所挂行的上方** ⇒ 末块按钮**必然落在该块之上**。
- VS Code 扩展 API **没有**「渲染在行下方的 CodeLens」⇒ 这是**结构性约束**，位置不可解。**不是行号算错**——同一次计算出的 `[startLine, endLine]` 与装饰高亮完全一致（§8.4 已钉「高亮位置 = 按钮位置」同源）。
- 为何「点一下才跑上去」：点掉前一块后只剩末块 ⇒ 场上唯一的按钮就是那颗被 clamp 的 ⇒ 观感上「跑到上面」。**位置从头到尾没变，变的是「还有没有别的按钮作参照」。**

处置（位置解不了 ⇒ 让**归属不依赖位置**）：

| 动作 | 说明 |
|---|---|
| 块按钮标题**恒带序号** | `$(check) 接受此处（N/M）` / `$(discard) 拒绝此处（N/M）`；单块也显 `（1/1）`，**不搞时有时无** |
| 顺带补旧根因 | 「看不出共几处」——序号一次解决 |

守卫 2 条（末行 clamp 形态 + 序号恒显）；变异 `const suffix = ''` → **恰 2 红**（两条序号断言），确认补偿真被钉住。

**诉求 2「对比内容改上下排列（左右看不清原文）」**

- 定性：`vscode.diff` 是**左右并排**，窄编辑器里长行被挤成两个半栏 ⇒ 原文难读。
- 为什么不能「把 diff 设成 inline 再打开」：扩展 API 拿不到该入口——`vscode.diff` 第 4 参数（`TextDocumentShowOptions`）**不含布局**；布局只受用户全局 `diffEditor.renderSideBySide` 或**切换型**命令（Toggle 类，盲调 = 改用户设置）影响 ⇒ **自渲染统一视图是唯一确定性路线**。
- 落地：
  - 纯逻辑 `formatUnifiedDiff(before, after, title)`（`fileChangeDiff.ts`）——单列 `- `/`+ ` 文本，每块一条分隔头 `──────── 改动 N/M · 新文件第 X 行 ────────`，首行标题 + `共 N 处改动`。
  - 呈现层改用**只读虚拟文档 + `showTextDocument`**：零落盘、天然只读（用户在对照页上误编辑不可能），旧的 `leftUri/rightUri + executeCommand('vscode.diff')` 路径与 `existsSync`/`rightSeed` 一并删除。
