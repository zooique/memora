## 一、锚点：迭代的底层方法论

任何未来迭代都建立在同一条铁律上：**回到最小单元**（一次输入 → 一次执行 → 一次交接判断，见 `single-truth-source-mindset.md`）。

本项目的最小单元是 **turn（问答闭环）⊃ loop（step 编排）⊃ step（LLM 原子调用）**。未来的迭代不该是"再加一个 orchestrator / 再加一个子系统"，而是**在最小单元上按需打开能力口径**。三个方向由此展开：

1. **连接能力**——让外部工具/生态进得来，却不破坏内核零依赖。
2. **观测能力**——把内核"可观察"固有属性伸出去喂给评测，却不引入运行时依赖。
3. **协同能力**——在角色包视角轮播之上，按需长出真实多 agent，却守住"单 agent 最小单元"ADR。

> 三个方向都以**现有代码**为生长点，不新建引擎。

## 二、对照基线（2026-09-18 实测主流）

### 三大能力缺口

| # | 缺口 | 主流做法 | 本项目现状 | 性质 |
|---|---|---|---|---|
| D1 | 工具/连接生态 | 全面落 **MCP**（四家框架均已支持），工具声明式接入 | 内置工具箱 + 宿主白名单自定义，**缺 MCP 标准声明** | 接入成本被生态甩开 |
| D2 | 可观测/评测 | LangSmith / Langfuse 是生产标配；支持 trace / eval / replay | 内核纯逻辑 + 宿主自绘 UI，**metrics 存在但未接评测基准** | 拿不到生态回放/评测/流量分析 |
| D3 | 多 agent 协同 | 主流做真实多 agent / handoff / 专才拆分 | 压成 `run_team_meeting` 单次 LLM 调用（视角轮播） | 能力维度缺失，但方向与"多 agent 可能 overkill"主流一致 |

### 次级短板（另记）

- **文本 tool_call**：为兼容本地无原生 FC 的 provider 保留文本通道，但那是自己 P0 翻车过的地方（见 [文本工具调用静默失败-专项处理提示词.md](../prompts/文本工具调用静默失败-专项处理提示词.md)）。是诚实但"不合群"的成本，需持续守卫。

## 三、自然生长原则（每条落地的硬约束）

遇复杂问题先回到最小单元：

- **不在闭环外再造引擎**：任何能力都从 turn ⊃ loop ⊃ step 生长，不做第二个 orchestrator。
- **内核零依赖是宪法**：连接/观测均以**接口注入（I…Provider）**形态走宿主侧，内核不 import 三方运行时依赖。
- **SSOT 三件套**：单真源（内核单一设计原点）+ 不带伤（声明/文档/协议/测试同批收敛）+ 探索先落 docs 再固化 ADR。
- **每次只推进一档**：验证稳定被真实场景复现消费后才推进下一档（S2 固化触发）。

## 四、三个迭代方向的收敛路径（生长，不是堆砌）

### 方向 1 · 连接生态（MCP）

**现状杠杆**：已有 `IWebSearchProvider` 接口注入范式 + `registerTool` 去重守卫 + 内置工具箱。
**生长点**：抽一层 **tool descriptor 归一接口**（复用现有 toolExecutor），内核声明"工具长什么样"，宿主侧把 MCP 客户端映射成本内核认知的工具壳。

```
宿主注入 MCP tool → 经接口打包成 {name, description, parameters, execute}
   → 内核 loop 只认这套壳，不关心背后是 MCP / 本地 / 白名单。
```

- [ ] 探索：MCP 工具协议采样 JSON-RPC + tool_call 归一（业界调研，不照搬）。
- [ ] 试点：宿主侧接一个 MCP server（如 filesystem / fetch），证明工具壳可透传。
- [ ] 内核**零改动天花板**校验：壳足够薄时，loop 无需感知 MCP 存在。
- **守**：内核 import 白名单仍为空；MCP 客户端全在宿主。

### 方向 2 · 可观测/评测

**现状杠杆**：`AgentMetrics`（五维：llm/recall/tools/context/tasks）+ `LoopMetrics` + `getMetrics()` 只读出口 + processEvents 事件流。
**生长点**：把 metrics + 事件流**以接口暴露给宿主**，宿主侧翻译成评测基准可消费的 trace。**内核零观测依赖**保持。

- [ ] 探索：OpenTelemetry trace 语义 vs 现有 metrics 五维的映射（要 OTel 还是 keep 轻量 JSON trace）。
- [ ] 试点：宿主侧产出一个"对一次真实多步任务的回放/评测"页面或导出。
- [ ] 不做：内核 import provider；评测工具若接回放，只在宿主。
- **守**：不破坏 `getMetrics()` 只读影子出口语义；metrics 仍单一真源。

### 方向 3 · 协同（真实多 agent 边界）

**现状杠杆**：角色包（persona/rules）手动切换 ADR + `run_team_meeting` 单调用 + assembleRolePack。
**生长点**：把"多角色评估同一问题"从**单次调用**逐步提升为**同一闭环的新实例**（对应 `目标模式生长探索-分层阶段化.md` §6.2 spawn fresh `runChat` 当阶段），但**必须在单 agent ADR 边界内单独拍板**（该 ADR 硬约束先决）。

- [ ] 探索：spawn fresh runChat 作为"工具"形态，带 input/output 契约（并列解耦）。
- [ ] 试点：run_team_meeting 之上，让子视角独立上下文跑一回合，只回提炼结论。
- **守**：子实例不是第二个 orchestrator；必须有 input/output 契约（否则隔离退化为各自为政）。

## 五、落地顺序（建议，可调）

> 纪律：前一步没跑稳，不进下一步（同大文本通道-探索方案 Step N 顺序不可换）。

| 相 | 方向 | 验证标准 |
|---|---|---|
| **1 先做** | 连接生态 | 真实 MCP server 工具可经壳被 loop 调用，内核 import 白名单不破 |
| **2 再做** | 可观测/评测 | 一次多步任务可导出/回放 trace，metrics 五维与 trace 对齐 |
| **3 最后** | 协同 | 真多视角独立上下文完成一回合评估，主上下文保持轻量 |

理由：**先解决"接不进生态"（D1）→ 再解决"看不透自己在干嘛"（D2）→ 最后才碰"要不要上真实多 agent"（D3，副作用最大）。**

## 八、开源与竞争定位观察（2026-09-19 横评延伸）

> **触发**：承接 §0 横评（2026-09-18）——复盘「若开源到 GitHub 会有人用吗 / 存在核心竞争力吗」。结论 = 三条观察 + 一条突围路径，全部为**探索期可逆**判断，不预设实施。

### 8.1 按现状开源 ≈ 无人生产使用（四道门槛）

| # | 门槛 | 现状 | 后果 |
|---|---|---|---|
| G1 | 需自建宿主 | 是内核，hosts/ 为自己 VS Code 宿主 | 陌生人无宿主跑不起来，连 demo 都没有 |
| G2 | 记忆质量无证明 | 无语义检索、无 LoCoMo/LongMemEval 类基准分 | 记忆是招牌但无数字，对比 Mem0（92.5/94.4）被劝退 |
| G3 | 生态零接入 | 无 MCP（同 §二 D1） | 2026 年 agent 不能插 MCP = 无外设接口 |
| G4 | 卖点不可描述 | "turn 为种子/摘要单轨/零依赖"是设计哲学 | 是给维护者看的，不是给用户看的 |

> fork/star 学习可能有，生产使用基本为零。**内核品质不会自动变成采用理由。**

### 8.2 核心竞争力真实存在，但在技术层（市场不感知）

- **真有**：上下文工程（工具台账/预算链/压缩链，与 Claude 平台 tool result clearing 同构且更早）；**零 token 成本记忆**（每查询 0 token，Mem0 约 7K/query）；架构自律（单闭环/零依赖/3052 单测）。
- **市场不买单**：上述全是维护者视角。用户感知不到"零依赖"，只感知到"没有语义检索"。"摘要单轨"是有争议的取舍，不是卖点。

### 8.3 唯一现实突围路径：记忆包化（可插拔，Mem0 模式）

> 不把「内核 + VS Code 宿主」整个开源（= 把个人实验当产品卖）。成立形态只有一个：

**把「零成本记忆 + 上下文工程」抽成可插拔记忆包，主打 Mem0 × MemPalace 之间的空位。**

| 方案 | 检索 | 成本 | 定位 |
|---|---|---|---|
| Mem0 | 向量+关键词+实体 | ~7K tokens/query（贵） | 准，但贵 |
| MemPalace | verbatim + 空间检索 | 0（纯本地） | 全量，但糙 |
| **本项目（潜在空位）** | 摘要单轨 + 关键词（**+语义召回可注入**） | **0，无需 embedding，全本地** | 便宜 + 本地 + 可解释 |

- **前置硬条件（缺一票否决）**：
  1. **语义召回回归且真接线**——B0 收编因果诚实（写端从未接线、生产从未生效），但作为记忆包，"零成本"会被"不准"一票否决；回归形态应为**可注入能力（I…Provider 式）**，默认不强制，守住零依赖宪法；
  2. **打出基准分**——LoCoMo/LongMemEval 子集，把"架构好"翻译成"数字好"（呼应 §四方向 2 可观测/评测，评测基准是记忆包成立的前提之一）。
- **VS Code 宿主**降级为参考宿主/demo，主角必须是可插进任意 agent 循环的记忆包（**只有能插进别人 agent 的东西才有人用**）。

### 8.4 与既有三方向的关系（增量，非替代）

- §二 D1/D2/D3 覆盖「连接/观测/协同」；本节新增第 4 缺口 = **D4 记忆语义召回缺失**（G2 根因，B0 收编后为纯关键词单通道）。
- 突围路径的优先序：**D4（语义召回可注入）→ D2（基准分）→ D1（MCP）** 是「记忆包化」的成立顺序；§五原落地序（D1→D2→D3）是「内核生态化」的顺序，两者**并行不冲突**——记忆包化可在宿主侧先行试点，内核零改动天花板不变。
- **待拍板（不预设结论）**：语义召回以何种形态回归（可注入 Provider？嵌入仍留宿主？）；是否把记忆包作为独立 npm 包发布（vs 随内核整包发布）。
