## 一、锚点：迭代的底层方法论

任何未来迭代都建立在同一条铁律上：**回到最小单元**（一次输入 → 一次执行 → 一次交接判断，见 `single-truth-source-mindset.md`）。

本项目的最小单元是 **turn（问答闭环）⊃ loop（step 编排）⊃ step（LLM 原子调用）**。未来的迭代不该是"再加一个 orchestrator / 再加一个子系统"，而是**在最小单元上按需打开能力口径**。三个方向由此展开：

1. **连接能力**——让外部工具/生态进得来，却不破坏内核零依赖。
2. **观测能力**——把内核"可观察"固有属性伸出去喂给评测，却不引入运行时依赖。
3. **协同能力**——在角色包视角轮播之上，按需长出真实多 agent，却守住"单 agent 最小单元"ADR。

> 三个方向都以**现有代码**为生长点，不新建引擎。

### 三大能力缺口

## 三、自然生长原则（每条落地的硬约束）

遇复杂问题先回到最小单元：

- **不在闭环外再造引擎**：任何能力都从 turn ⊃ loop ⊃ step 生长，不做第二个 orchestrator。
- **内核零依赖是宪法**：连接/观测均以**接口注入（I…Provider）**形态走宿主侧，内核不 import 三方运行时依赖。
- **SSOT 三件套**：单真源（内核单一设计原点）+ 不带伤（声明/文档/协议/测试同批收敛）+ 探索先落 docs 再固化 ADR。
- **每次只推进一档**：验证稳定被真实场景复现消费后才推进下一档（S2 固化触发）。

## 四、三个迭代方向的收敛路径（生长，不是堆砌）

### 方向 1 · 连接生态（MCP）

**现状杠杆**：已有 `IWebSearchProvider` 接口注入范式 + `registerTool` 去重守卫 + 内置工具箱。
**生长点**：抽一层 **tool descriptor 归一接口**（复用现有 toolExecutor），内核声明"工具长什么样"，宿主侧把 MCP 客户端映射成本内核认知的工具壳。

```
宿主注入 MCP tool → 经接口打包成 {name, description, parameters, execute}
   → 内核 loop 只认这套壳，不关心背后是 MCP / 本地 / 白名单。
```

- [ ] 探索：MCP 工具协议采样 JSON-RPC + tool_call 归一（业界调研，不照搬）。
- [ ] 试点：宿主侧接一个 MCP server（如 filesystem / fetch），证明工具壳可透传。
- [ ] 内核**零改动天花板**校验：壳足够薄时，loop 无需感知 MCP 存在。
- **守**：内核 import 白名单仍为空；MCP 客户端全在宿主。

### 方向 2 · 可观测/评测

**现状杠杆**：`AgentMetrics`（五维：llm/recall/tools/context/tasks）+ `LoopMetrics` + `getMetrics()` 只读出口 + processEvents 事件流。
**生长点**：把 metrics + 事件流**以接口暴露给宿主**，宿主侧翻译成评测基准可消费的 trace。**内核零观测依赖**保持。

- [ ] 探索：OpenTelemetry trace 语义 vs 现有 metrics 五维的映射（要 OTel 还是 keep 轻量 JSON trace）。
- [ ] 试点：宿主侧产出一个"对一次真实多步任务的回放/评测"页面或导出。
- [ ] 不做：内核 import provider；评测工具若接回放，只在宿主。
- **守**：不破坏 `getMetrics()` 只读影子出口语义；metrics 仍单一真源。

### 方向 3 · 协同（真实多 agent 边界）

**现状杠杆**：角色包（persona/rules）手动切换 ADR + `run_team_meeting` 单调用 + assembleRolePack。
**生长点**：把"多角色评估同一问题"从**单次调用**逐步提升为**同一闭环的新实例**（对应 `目标模式生长探索-分层阶段化.md` §6.2 spawn fresh `runChat` 当阶段），但**必须在单 agent ADR 边界内单独拍板**（该 ADR 硬约束先决）。

- [ ] 探索：spawn fresh runChat 作为"工具"形态，带 input/output 契约（并列解耦）。
- [ ] 试点：run_team_meeting 之上，让子视角独立上下文跑一回合，只回提炼结论。
- **守**：子实例不是第二个 orchestrator；必须有 input/output 契约（否则隔离退化为各自为政）。

## 五、落地顺序（建议，可调）

> 纪律：前一步没跑稳，不进下一步（同大文本通道-探索方案 Step N 顺序不可换）。

| 相 | 方向 | 验证标准 |
|---|---|---|
| **1 先做** | 连接生态 | 真实 MCP server 工具可经壳被 loop 调用，内核 import 白名单不破 |
| **2 再做** | 可观测/评测 | 一次多步任务可导出/回放 trace，metrics 五维与 trace 对齐 |
| **3 最后** | 协同 | 真多视角独立上下文完成一回合评估，主上下文保持轻量 |

理由：**先解决"接不进生态"（D1）→ 再解决"看不透自己在干嘛"（D2）→ 最后才碰"要不要上真实多 agent"（D3，副作用最大）。**

## 八、开源与竞争定位观察（2026-09-19 横评延伸）

> **触发**：承接 §0 横评（2026-09-18）——复盘「若开源到 GitHub 会有人用吗 / 存在核心竞争力吗」。结论 = 三条观察 + 一条突围路径，全部为**探索期可逆**判断，不预设实施。

### 8.1 按现状开源 ≈ 无人生产使用（四道门槛）

| # | 门槛 | 现状 | 后果 |
|---|---|---|---|
| G1 | 需自建宿主 | 是内核，hosts/ 为自己 VS Code 宿主 | 陌生人无宿主跑不起来，连 demo 都没有 |
| G2 | 记忆质量无证明 | 无语义检索、无 LoCoMo/LongMemEval 类基准分 | 记忆是招牌但无数字，对比 Mem0（92.5/94.4）被劝退 |
| G3 | 生态零接入 | 无 MCP（同 §二 D1） | 2026 年 agent 不能插 MCP = 无外设接口 |
| G4 | 卖点不可描述 | "turn 为种子/摘要单轨/零依赖"是设计哲学 | 是给维护者看的，不是给用户看的 |

> fork/star 学习可能有，生产使用基本为零。**内核品质不会自动变成采用理由。**

### 8.2 核心竞争力真实存在，但在技术层（市场不感知）

- **真有**：上下文工程（工具台账/预算链/压缩链，与 Claude 平台 tool result clearing 同构且更早）；**零 token 成本记忆**（每查询 0 token，Mem0 约 7K/query）；架构自律（单闭环/零依赖/3052 单测）。
- **市场不买单**：上述全是维护者视角。用户感知不到"零依赖"，只感知到"没有语义检索"。"摘要单轨"是有争议的取舍，不是卖点。

### 8.3 唯一现实突围路径：记忆包化（可插拔，Mem0 模式）

> 不把「内核 + VS Code 宿主」整个开源（= 把个人实验当产品卖）。成立形态只有一个：

**把「零成本记忆 + 上下文工程」抽成可插拔记忆包，主打 Mem0 × MemPalace 之间的空位。**

| 方案 | 检索 | 成本 | 定位 |
|---|---|---|---|
| Mem0 | 向量+关键词+实体 | ~7K tokens/query（贵） | 准，但贵 |
| MemPalace | verbatim + 空间检索 | 0（纯本地） | 全量，但糙 |
| **本项目（潜在空位）** | 摘要单轨 + 关键词（**+语义召回可注入**） | **0，无需 embedding，全本地** | 便宜 + 本地 + 可解释 |

- **前置硬条件（缺一票否决）**：
  1. **语义召回回归且真接线**——B0 收编因果诚实（写端从未接线、生产从未生效），但作为记忆包，"零成本"会被"不准"一票否决；回归形态应为**可注入能力（I…Provider 式）**，默认不强制，守住零依赖宪法；
  2. **打出基准分**——LoCoMo/LongMemEval 子集，把"架构好"翻译成"数字好"（呼应 §四方向 2 可观测/评测，评测基准是记忆包成立的前提之一）。
- **VS Code 宿主**降级为参考宿主/demo，主角必须是可插进任意 agent 循环的记忆包（**只有能插进别人 agent 的东西才有人用**）。

### 8.4 与既有三方向的关系（增量，非替代）

- §二 D1/D2/D3 覆盖「连接/观测/协同」；本节新增第 4 缺口 = **D4 记忆语义召回缺失**（G2 根因，B0 收编后为纯关键词单通道）。
- 突围路径的优先序：**D4（语义召回可注入）→ D2（基准分）→ D1（MCP）** 是「记忆包化」的成立顺序；§五原落地序（D1→D2→D3）是「内核生态化」的顺序，两者**并行不冲突**——记忆包化可在宿主侧先行试点，内核零改动天花板不变。
- **待拍板（不预设结论）**：语义召回以何种形态回归（可注入 Provider？嵌入仍留宿主？）；是否把记忆包作为独立 npm 包发布（vs 随内核整包发布）。

## 九、以成熟编码 agent 实测工作方式为参照的能力缺口（2026-09-29 延伸）

> **触发**：2026-09-29 用户提问「用成熟 agent 的功能能力找 memora 的生长点」——参照系从 §二的**供给侧横评**（主流框架对框架，2026-09-18）换成**消费侧实证**：一个真实编码 agent（WorkBuddy）在 memora 仓库内执行真实任务（深审 / 类型收敛 / 18 分钟全量测试）的同时，逐项对照其能力面与 memora 工具面。两类证据互补：横评看「业界长什么样」，实证看「agent 日常到底在用什么」。
> **性质**：探索期可逆，同 §八；缺口编号接续为 **D5**。

### 9.1 对照结果（全部经源码实测，非印象）

| 能力面（参照 agent） | memora 现状（实测） | 判定 |
|---|---|---|
| **后台任务 + 完成通知**（长测试/构建期间照常工作） | `run_project_script` 同步阻塞，默认 60s / 硬上限 600s；同 step 工具虽已 Promise.all 并发（`loop.ts` 保持顺序并发 + prior 依赖链），但**单脚本执行无异步形态** | 🔴 **D5 新缺口** |
| 任务清单**跨回合持久** | `checkpoint.plan`/`planItemLog` 存在但跨 turn 兜底丢弃（`agent.ts` 清空逻辑 + 单测注释「宏任务一个 turn 完不成则兜底丢弃」），进度退化为概率性记忆检索 | 🟡 设计题 → 待拍板（9.3） |
| 文件名搜索（最高频动作，按修改时间排序 + 分页） | `search_project` name 模式裸词/猜名放宽已落地（2026-09-29，原 `SEARCH-name-glob` 观察项销项，根因与收据见 `tasks/archive/completed-history.md`） | ✅ 已落地，从本清单移出 |
| 多模态读取（截图/PDF 直接看） | `read_file` 纯文本 | 🟡 **D7 登记**（触发 = 宿主接入多模态模型；按「预支复杂度 = 负收益」原则：模型链路不支持时实现即死代码） |
| **直接运行命令**（不落盘即可执行 `git status` / `npm test -- --grep x` 等任意命令） | 现状 =「能跑命令但必须先落文件」：`write_file 写 sh → run_project_script → delete_file` 多两轮往返；`run_command` 已有闭合方案定档 3.1.0 | 🟡 **D6 登记**（方案 SSOT 见 [方案-命令执行能力-run_command-20260922.md](./方案-命令执行能力-run_command-20260922.md)，2026-09-22 拍板在案） |
| 同 step 并行工具调用 | `loop.ts` 已 Promise.all 保持顺序并发 | ✅ 已有，非缺口（证伪一条直觉） |

### 9.2 D5 · 执行的时间维度：后台长任务

**缺口本质**：大项目编码的高频动作（全量测试 / 构建 / 依赖安装 / 数据迁移）在 600s 上限边缘或之上；同步阻塞的 step 里「等待时间 = 上下文里除了等什么都不能干」，超上限则整类任务被拒。实证：memora 自身内核全量测试在本机实测 18m42s。

**生长形态（候选，未定案）**：
1. `run_project_script` 增 `background` 参数 → 立即返回任务句柄；
2. 新增 `check_task` 句柄查询工具（取 stdout / 退出码 / 运行态）；
3. 内核消息面增 task_completed 事件，loop 在 step 边界自然收结果。

**设计难点（动手前必须文档化）**：异步结果回流 × turn 生命周期的咬合——turn 已结束而任务未完，结果归属谁？跨 turn 后台任务是**会话状态**还是**工具结果**？不先答这两问直接实现，会成为第二个 DIFF-3 级并发缺陷。

### 9.3 跨 turn 任务的确定性进度（待拍板）

现状哲学 = 「宏任务 = turn 粒度，丢弃后下 turn 重新规划 + 记忆兜底」，单 turn 场景成立。缺口场景：跨几十 turn 的大重构，其进度是**确定性状态**，退化为概率性记忆检索有丢失风险——任务表与记忆的本质区别即「确定性 vs 概率性」。候选形态：项目级 plan 挂 `registerProject`，而非新持久化面。**与记忆子系统的边界先文档化，勿直接实现。**

### 9.4 评估后否决（防未来纠结，同批次拍板记录）

| 候选 | 否决理由 |
|---|---|
| 工具 schema 按需加载（ToolSearch 式） | 14 个内置工具全量描述成本可控，触发驱动：工具面翻倍再议 |
| write_file replace_all | 不做有充分理由（改错毁代码 > 多补上下文重试）；参照 agent 自身亦极少使用 replace_all |
| 定时/自动化任务 | 非编码 agent 核心场景 |
| MCP 接入内核层 | 与 §四方向 1 **不矛盾**：MCP 客户端本就归宿主，内核只认工具 descriptor 壳——本条否决的仅是「内核 import MCP 依赖」，方向 1 设计维持 |

### 9.5 D6 / D7 登记细目（2026-09-29 用户点名收编）

- **D6 · 直接命令执行（run_command）**：设计已于 2026-09-22 闭合并定档 3.1.0（不进 3.0.0 的三条硬理由、主流对照、确认/黑名单/超时设计均见方案文档，此处不复述）。本节只补一条**参照 agent 实证**：成熟编码 agent 的高频动作里「直接跑一条命令验证/查状态」远多于「写脚本→跑→删」闭环，两轮额外往返 × 大项目高频调用 = 可观的时间与轮次成本。
- **D7 · 多模态读取**：`read_file` 纯文本，无法消费截图/PDF/设计图。**触发条件 = 宿主接入多模态模型**（模型链路是硬前提，内核消息面预留属预支复杂度，触发前不动）。

### 9.6 与既有方向的关系

- D5（时间维度）/ D6（命令面）/ D7（多模态）与 D1-D4（连接/观测/协同/记忆召回）**无重叠**：D5/D6 解决「单步等待浪费 + 命令往返开销 + 任务时长上限」，是 loop 执行模型与工具面的生长；D7 取决于模型链路。
- 排期**不推翻** §五 / §8.4 既有顺序：D5/D6/D7 可独立立项，但按「每次只推进一档」纪律，当前 3.0.0 发包期**不启动**，仅登记。D6 已有 2026-09-22 拍板「定档 3.1.0」，与本项目排期自然衔接。

### 10.2 品味评价：对照后的「押得好」与「直说的差距」

**押得好的（对照确认为差异化，非落后）**：

1. **记忆路线**：主流做「压缩丢弃」，本项目做「结构化留存 + 召回」——事实上的分歧点、2026-10-11 检索未查到公开同款（呼应 §8.3 记忆包化的空位判断）。
2. **气口级事中协作**（暂停 / 插话 / 审批卡 / 权限裁决链）vs 主流 auto-approve + 事后回滚——对自主度的**信任假设不同**，对敏感操作场景更贴实际。
3. **内核/宿主分层**与 Cline SDK 化、Copilot harness 分层同向——架构经得起横向对照。
4. **设计纪律**（SSOT / 不带伤 / 诚实降级）是独立产品的护城河来源——Roo 教训（事实 6）：没有护城河的独立 agent 必被生态碾压，护城河只可能来自设计质量 + 记忆深度。

**直说的差距（对照新发现）**：

1. **形态单一（仅 VS Code 宿主）**——最大结构性风险；但短期**刻意不追**（见 10.4 拒枝）。
2. **D8 · 自动文件快照回滚缺失（本节新增缺口编号）**：事实 2 的三家（Claude Code / Cline / Cursor）全有 turn 级文件快照一键回滚，本项目只有**显式审查流**（`fileChanges` confirm/revert = 半成品前身，「改完再审查」而非「自动存底」）——用户手滑改坏文件时，后悔药比主流少。**触发 = 用户真实要求「改回去 / 恢复到刚才」**；触发未现，按 §七 口径**仅本文档登记、不进台账**。
3. **召回式记忆的软肋要认清**：检索靠 LLM 主动调 `search_memories`，**不调 = 记忆等于不存在**，而启动注入保证出现——这条路线把宝押在模型调用意愿上。已在册 `HOST-S3-1`（记忆命中可视化）是第一步补法（让调没调可见）；**长期观察方向 = 混合形态**（高价值记忆常驻注入 + 海量按需召回），但等 S3-1 上线看清真实调用率再拍板，**现在不设计**（数据替我们拍板）。

### 10.3 自然生长方向（三层收敛）

**第一层 · 种子决定的长势（不变的方向）**

主流的种子是「任务执行器」→ 长出 cloud agent / 并行 / 更快——**拼执行力**（算力优势，不可争）；本项目的种子是「turn 问答闭环 + 摘要即记忆」→ 该长成**越用越懂你的长期协作体**——**拼关系深度**。由此得出一条硬判据：
