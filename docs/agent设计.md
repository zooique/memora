## 一、文档概述

### 1.1 设计目的

本项目旨在打造一款**自研可控、本地私有化、领域无关的通用 AI Agent 系统**。区别于通用对话机器人，本 Agent 具备以下核心差异化能力：

- **长期记忆沉淀**：跨会话、跨话题的记忆持久化与智能召回
- **记忆永久性分级约束**：通过永久性标记（always / domain / on-demand）控制不同记忆的召回确定性和约束强度，替代传统的"规则+ Skill 分系统"模式
- **自主记忆召回**：Agent 自主从记忆中召回所需内容，而非依赖静态模板
- **领域可插拔**：同一套架构，加载不同记忆配置即可适配不同领域

### 1.2 设计核心理念

**万物皆是记忆。**

除了用户当前直接输入的提示词内容，Agent 的一切都是记忆——人格是"我记得我是谁"，规则是"我记得该怎么做事"，技能是"我记得怎么做某类事"，对话历史是"我记得之前聊过什么"。

这意味着：
- **没有独立的"规则系统"和"能力系统"**——规则和技能都是记忆，只是永久性不同
- **统一的记忆召回管线**——所有内容走同一套检索/召回逻辑，区别仅在于召回的确定性程度
- **Agent 只做一件事**：从记忆中召回与当前任务相关的一切，然后响应

借鉴成熟产品所长，自主重构通用 Agent 行为逻辑：

- **借鉴 Trae**：三级分层规则体系的工程化管理思想——映射为记忆的永久性分级
- **借鉴 OpenClaw**：分层记忆、人格本体设定（SOUL.md → personality.md）、文件+数据库双存储模式
- **自主重构**：将规则/技能/历史统一为记忆体系，以话题为记忆组织维度，通过永久性标记控制召回确定性

### 1.3 核心底层认知

本 Agent 所有能力基于正规第三方商用 API 开发，不逆向破解任何软件私有接口，合规稳定。

整体架构为：**本地记忆引擎（记忆存储与召回）+ 大模型 API（推理与决策）**

- **记忆引擎**：负责记忆存储、索引维护、上下文组装、文件读写、数据库操作（记忆基础设施）
- **大模型 API**：负责意图识别、内容生成、工具调度、记忆萃取、质量自检（推理与决策中枢）

大模型是决策者，记忆引擎是服务者。记忆引擎不"指挥"任何事——它提供记忆召回能力，由模型决定何时需要什么记忆（通过工具调用或在 Loop 中自主判断）。

## 二、整体架构总纲

### 2.1 运行闭环

```
用户需求 → 基础记忆召回（永驻 + 领域）→ [Agent Loop: 模型推理 → 工具调用/增量记忆召回 → 结果回填 → 循环] → 后置处理 → 记忆写入与沉淀
```

**记忆召回不是一次性事件**。启动时只加载永驻记忆和领域记忆（这两者确定性 100%，无需模型判断）。话题记忆和能力记忆在 Loop 中按需召回——模型可以调用"检索记忆"工具来获取更多上下文，也可以在任务类型切换时由系统自动补充对应能力记忆。

**Agent Loop** 是本架构的核心执行引擎，解决"一次性对话"无法自主完成多步任务的问题：

```
while (模型输出包含 tool_call) {
    执行工具/召回记忆 → 结果回填上下文 → 模型基于新上下文再次推理
}
// 模型输出纯文本时，循环结束，返回最终结果
```

- **纯文本输出**：模型直接返回答案，循环结束，用户看到结果
- **工具调用输出**：模型返回 tool_call——可以是业务工具（读文件、写代码），也可以是记忆工具（检索更多话题上下文、激活其他技能）。代码执行后将结果回填到上下文，模型再次推理——循环往复直到模型认为任务完成
- **增量记忆召回**：当模型判断当前上下文不足以完成任务时，可主动调用记忆检索工具获取更多历史话题或激活新技能。这避免了"预加载全部记忆"造成的上下浪费

**关键设计决策**：不设固定规划阶段（借鉴 Trae 2.0 的经验），模型自主决定何时推理、何时调用工具。固定规划阶段在通用场景下会限制模型灵活性——不同领域的任务类型差异太大，刚性规划反而让模型"走上错误的路径"。

### 2.2 存储架构（冷热分离）

摒弃文件/数据库二选一模式，采用**文件承载本体，数据库承载索引**的冷热分离架构：

#### 2.2.1 本地文本文件（前台操作台，高频读写）

所有记忆内容以 MD/JSON 格式存储，按记忆类型组织：

- **人格记忆**：Agent 人格本体文件（personality.md）
- **规则记忆**：全局/项目级规则文件（rules/*.md）
- **话题记忆**：实时会话上下文、当日原始对话流水、话题文件、长期精华记忆（topics/*.md）
- **能力记忆**：技能文案文件（skills/*.md）、工具定义文件（tools/*.json）

**优势**：可读、可手动编辑、备份迁移零成本。

#### 2.2.2 SQLite 数据库（后台记忆中枢，低频检索）

单文件无服务数据库，仅存储索引与结构化数据，不存储完整原文：

- 文档索引：绑定 MD 文件路径、段落分片、时间、记忆标签
- 检索数据：FTS5 全文分词索引、Embedding 向量相似度索引
- 结构化数据：会话 ID、话题 ID、记忆类型、记忆权重

## 三、记忆体系

### 3.1 核心原则

**万物皆是记忆。** 除了用户当前直接输入的提示词内容，Agent 的一切都是记忆。

人格是记忆，规则是记忆，技能是记忆，对话历史是记忆，工具执行结果也是记忆——只是生命周期不同。它们之间没有本质区别——只有**永久性**和**召回确定性**的区别。

- 人格记忆每轮必召回（确定性 100%），因为 Agent 必须知道自己是谁
- 核心规则每轮必召回（确定性 100%），因为 Agent 必须遵守底线约束
- 领域规则按领域匹配召回（确定性高），因为不同领域需要不同的行为约束
- 话题记忆按相似度召回（确定性中），因为 Agent 需要相关的历史上下文
- 能力记忆按任务类型召回（确定性中），因为 Agent 需要匹配当前任务的能力

### 3.2 记忆分类（按永久性分级）

| 记忆类型 | 永久性 | 召回策略 | 存储形式 |
|---------|--------|---------|---------|
| **人格记忆** | 永驻 | 不检索，每轮直接加载 | personality.md |
| **规则记忆** | 永驻/领域级 | 核心规则永驻，领域规则按领域匹配召回 | rules/*.md |
| **话题记忆** | 话题级 | 按话题相似度召回（FTS5 + 向量） | topics/*.md + 话题报告 |
| **能力记忆** | 按需级 | 按任务类型召回 | skills/*.md + tools/*.json |
| **工作记忆** | 瞬时（当前 Loop） | 不检索，Loop 内自动生成并持有 | 仅存在于上下文，Loop 结束后写入话题文件 |

> **工作记忆**是 Agent Loop 执行过程中产生的记忆：模型回复、工具调用结果、增量召回的上下文。它们生命周期最短——Loop 内存在于上下文，Loop 结束后转为话题记忆（写入话题文件）。工作记忆不是独立存储的记忆类型，而是话题记忆的"瞬时态"。

**永久性标记**：每条记忆在 SQLite 索引中有一个 `permanence` 字段，取值及含义：

| permanence 值 | 含义 | 召回行为 |
|---------------|------|---------|
| `always` | 每轮必召回 | 不走检索，直接加载到上下文。适用于人格、核心安全规则 |
| `domain` | 领域匹配时召回 | 当前项目的领域标签匹配时加载。适用于领域规则 |
| `topic` | 话题相似时召回 | 按话题相似度检索召回。适用于对话历史、话题报告 |
| `on-demand` | 任务需要时召回 | 按任务类型匹配召回。适用于技能、工具 |

**为什么用"永久性"而非"优先级"**：优先级暗示"高优先级先加载、低优先级后加载"——这是加载顺序的概念。永久性暗示"这条记忆是否总是需要"——这是召回确定性的概念。人格记忆不是"优先级最高"，而是"永远需要"。

### 3.3 记忆分层（按新鲜度 + 存储形式）

话题记忆内部按新鲜度进一步分层：

| 层级 | 时间范围 | 存储形式 | 召回方式 | 上下文组装协议对应 |
|------|---------|---------|---------|-------------------|
| **工作记忆** | 当前对话窗口 | 原文全量（话题文件） | 全部加载 | 话题记忆填充优先级 1-2 |
| **短期记忆** | 1-2 天内 | 同话题原文（话题文件） | 全文加载 | 话题记忆填充优先级 2 |
| **中期记忆** | 本周 | LLM 炼化的话题报告 + 关键引用 | 话题报告 + 原文索引 | 话题记忆填充优先级 3 |
| **长期记忆** | 本月/本年 | 关键词索引 + 一句话摘要 | 按需召回 | 话题记忆填充优先级 4 |
| **归档记忆** | 跨年 | 标签 + 索引 | 检索触发 | 话题记忆填充优先级 5 |

### 3.4 记忆组织维度

**以话题为组织维度，以对话轮次为记录单元。**

详细设计见 [agent上下文组装协议.md](./agent上下文组装协议.md) 第三章"记忆系统"。

剪枝策略和归档文件生命周期管理见协议文档 7.4 节。故障容错与降级策略见协议文档第九章。

### 3.5 记忆归档（冥想机制）

借鉴 OpenClaw 心跳机制的定时触发思想，但定位不同——OpenClaw 心跳是对外主动执行任务，本方案的冥想是对内维护记忆（归档对话、炼化话题报告、更新索引）。实现「日间对话，夜间沉淀」：

**日间运行模式**：所有交互仅操作本地文件，实时写入话题文件；SQLite 仅静默更新索引，不参与 Prompt 拼装，最大化响应速度。

**触发归档时机**：
- 定时触发：每日凌晨固定时间自动执行
- 手动触发：会话关闭后，用户主动执行记忆归档
- 启动补执：宿主启动时检查上次归档时间，超过 24 小时自动补执

**归档执行步骤**：
1. 代码读取当日全部话题文件
2. 调用大模型 API，剥离无效闲聊，萃取关键信息，炼化为结构化话题报告
3. 更新长期精华记忆文件和话题报告
4. 同步更新 SQLite 全文索引与向量索引（包括规则记忆和能力记忆的索引更新）
5. 可选：打包备份原始对话，封存话题文件

## 四、规则记忆与能力记忆

规则和技能不是独立于记忆的"系统"，而是记忆的两种类型。它们的特殊性在于永久性高于话题记忆，但本质仍然是"Agent 记住了什么"。

### 4.1 规则记忆

规则是 Agent 的"行为记忆"——它记得自己应该怎么做事。规则记忆按永久性分为两级：

**永驻规则**（`permanence: 'always'`）：
- **存储位置**：全局公共目录（`~/.memora/global/rules/`）+ 项目配置目录（`<configDir>/rules/`）中标记为 `always` 的规则
- **核心内容**：通用行为约束、输出格式、底线禁忌
- **召回行为**：每轮必召回，不走检索。相当于 Agent 的"本能"
- **优先级**：兜底基线。当领域规则未覆盖时生效；当领域规则与全局规则冲突时，领域规则优先

**领域规则**（`permanence: 'domain'`）：
- **存储位置**：项目配置目录（`<configDir>/rules/`）中标记为 `domain` 的规则
- **核心内容**：领域专属约束、专业规范、行业标准
- **召回行为**：当前项目的领域标签匹配时召回。相当于 Agent 的"专业知识"
- **优先级**：高于全局规则。冲突处覆盖全局配置——因为领域规则更贴近具体场景

**Agent 人格设定**不属于规则记忆，而是人格记忆（`permanence: 'always'`）——它定义了 Agent 是谁、遵循什么原则，是所有记忆生效的前提。

### 4.2 能力记忆

能力记忆是 Agent 的"程序性记忆"——它记得自己能做什么、怎么做。能力记忆按永久性分为两类：

**技能记忆**（`permanence: 'on-demand'`）：
- **存储位置**：项目配置目录（`<configDir>/skills/`）
- **核心内容**：封装的能力文案（prompt 级别），改变 Agent 的"思考方式"
- **召回逻辑**：技能选择本质上是记忆检索——Agent 从能力记忆中找到与当前任务匹配的技能。演进路径分两个阶段：
  - **初期**：系统辅助检索——关键词匹配，低成本高确定性。系统根据用户输入关键词从能力记忆索引中匹配技能
  - **后期**：模型自主检索——将所有可用技能的简短描述作为工具 schema 注入上下文，让模型通过 tool_call 自主决定激活哪个技能。用 LLM 的判断力替代关键词匹配
- **关键区分**：技能选择 ≠ 工具调用。前者是从记忆中检索"怎么想"的能力（技能记忆），后者是执行"怎么做"的动作（工具记忆）

**工具记忆**（`permanence: 'on-demand'`）：
- **存储位置**：项目配置目录（`<configDir>/tools/`）
- **核心内容**：可调用的函数定义（函数级别），提供 Agent 的"执行能力"
- **召回逻辑**：与技能记忆同步召回，通过 Function Calling 执行

**技能记忆与工具记忆的本质区别**：

| 维度 | 技能记忆 | 工具记忆 |
|------|---------|---------|
| 层级 | Prompt 级别 | 函数级别 |
| 作用 | 改变"思考方式" | 提供"执行能力" |
| 调用通道 | 通过 prompt 引导 | 通过 Function Calling |

### 4.3 统一索引

规则记忆和能力记忆与话题记忆共享同一个 SQLite 索引。所有记忆在索引中的结构统一：

```
记忆索引表（memories）：
- id: 记忆唯一标识
- type: 'personality' | 'rule' | 'skill' | 'tool' | 'topic' | 'topic-report'
- permanence: 'always' | 'domain' | 'topic' | 'on-demand'
- domain: 领域标签（仅 domain 级记忆需要）
- file_path: 对应的 MD/JSON 文件路径
- keywords: 关键词（FTS5 索引）
- embedding: 向量嵌入（向量索引）
- updated_at: 最后更新时间
- metadata: JSON 扩展字段
```

**统一索引的好处**：
- 一套检索逻辑服务所有记忆类型
- 跨类型检索成为可能（如"找到所有关于'数据库'的记忆"，包括规则、技能、对话历史）
- 索引维护只需一套管道

## 五、核心运行模块

### 5.1 记忆召回模块（核心模块）

**万物皆是记忆，万物走同一套召回管线。** 本模块是 Agent 最核心的基础功能，负责从记忆系统中召回与当前任务相关的一切内容。

**记忆召回不是一次性事件，而是分阶段进行**：

**阶段一：启动时强制召回**（不可跳过，确定性 100%）
```
1. 召回永驻记忆 → 人格 + 核心规则（permanence: 'always'，不走检索，直接加载）
2. 召回领域记忆 → 领域规则（permanence: 'domain'，按领域标签匹配）
3. 召回初始话题记忆 → 最近 N 轮对话（permanence: 'topic'，快速上下文预热）
```

**阶段二：Agent Loop 中按需增量召回**（模型自主触发）
```
当模型判断当前上下文不足以完成任务时，可调用记忆检索工具：
- search_topics("关键词") → 返回相关话题报告和对话原文
- activate_skill("技能名") → 加载对应能力记忆到上下文
- recall_context("话题ID") → 加载指定话题的完整历史
```

**为什么不是全量预加载**：
- 预加载所有话题记忆浪费上下文窗口，模型可能不需要 80% 的内容
- 预加载所有技能描述干扰模型判断——它不需要知道所有技能，只需要知道"有技能可查"
- 让模型自主决定何时检索记忆，更符合"万物皆是记忆"——模型像人一样主动回忆，而非被动接收

**Token 预算管理**：
- 阶段一占上下文窗口的 15-30%（永驻+领域+初始话题）
- 阶段二的每次增量召回受单次预算限制（不超过窗口的 10%）
- Agent Loop 的工具结果预算独立计算（不超过窗口的 20%）
- 超过预算时触发上下文压缩（详见协议文档 7.6 节）

**代码与模型的分工**：
- **代码负责**：记忆索引查询、话题文件读写、上下文裁切、Token 计算
- **大模型负责**：话题报告炼化、记忆权重打分、决定何时检索更多记忆、能力记忆的智能选择（后期）

话题记忆的详细召回逻辑见 [agent上下文组装协议.md](./agent上下文组装协议.md) 第四章"话题记忆动态填充逻辑"。

### 5.2 Agent Loop 模块（核心执行引擎）

**Agent Loop 是模型驱动的**——模型自主决定何时推理、何时调用工具、何时检索更多记忆。代码只做三件事：执行模型请求的工具、将结果回填到上下文、管理 Token 预算。

```
while (模型输出包含 tool_call) {
    // 代码执行模型请求的工具或记忆检索，将结果回填到上下文
    执行工具/检索记忆(tool_call) → 结果回填上下文 → 模型基于新上下文再次推理
}
// 模型输出纯文本 → 循环结束 → 进入后置处理
```

**关键设计决策**：
- **模型驱动，代码执行**：模型是循环的控制者——它决定调用什么工具、何时停止、何时需要更多记忆。代码是被动的执行者
- **不设固定规划阶段**（借鉴 Trae 2.0 经验）。固定规划在通用场景下会限制灵活性——模型自主决定何时推理、何时调用工具，而非被锁定在预先制定的计划中
- **循环终止条件**：模型输出纯文本（无 tool_call）时循环自然结束。模型自己判断任务是否完成
- **最大循环次数**：设置上限（如 20 轮），防止无限循环或 API 成本失控
- **循环内记忆写入**：每轮工具调用结果和模型回复实时追加到话题文件的工作记忆区，确保即使循环中断也不丢失上下文

### 5.3 上下文组装模块

纯代码执行。将记忆召回模块的输出组装为标准 OpenAI 格式 messages 数组，提交给 API。

**messages 数组结构**：

```
[
  // ========== 指令层（system role）==========
  // 人格、规则、技能——告诉模型"你是谁、该怎么想"
  { role: "system",  content: "人格记忆（personality.md）" },
  { role: "system",  content: "规则记忆（永驻规则 + 领域规则）" },
  { role: "system",  content: "能力记忆（当前激活的技能文案 + 可用工具 Schema）" },

  // ========== 上下文层（user/assistant role）==========
  // 对话历史——告诉模型"之前发生了什么"
  { role: "user",    content: "话题记忆注入：以下是当前话题的历史上下文" },
  { role: "user",    content: "历史对话第1轮 - 用户输入" },
  { role: "assistant", content: "历史对话第1轮 - 模型回复" },
  { role: "user",    content: "历史对话第2轮 - 用户输入" },
  { role: "assistant", content: "历史对话第2轮 - 模型回复" },
  // ... 更多历史对话轮次 ...

  // ========== 当前输入层（user role）==========
  { role: "user",    content: "用户当前主动输入" },

  // ========== Agent Loop 中追加的工作记忆 ==========
  { role: "assistant", content: "模型本轮回复 / tool_call" },
  { role: "tool",    content: "工具执行结果或记忆检索结果" },
  { role: "assistant", content: "模型基于工具结果的再次回复 / tool_call" },
  // ... 循环直到模型输出纯文本 ...
]
```

**为什么对话历史用 user/assistant 而非 system**：
- LLM 的训练数据中，对话上下文以 user/assistant 交替格式呈现。将历史上下文放入 system 角色会破坏模型对"这是过去的对话"的认知模式
- System 消息在多数 API 中有独立的 Token 限制（如 32K），而 user/assistant 消息使用完整的上下文窗口
- 行业实践一致：Claude Code 将 CLAUDE.md 作为 user 消息注入，Cline 将对话历史作为 user/assistant 交替传递。只有指令/规则/身份定义放在 system 中

**关键设计**：
- 指令层内容（人格、规则、技能）在对话期间不变，阶段一只加载一次
- 上下文层内容（话题记忆、对话历史）随对话推进动态追加
- 工作记忆（工具结果、模型回复）在 Agent Loop 中动态生成并追加，Loop 结束后写入话题文件

详细设计见 [agent上下文组装协议.md](./agent上下文组装协议.md) 第二章"Agent 记忆召回文档"。

### 5.4 后置处理模块

双重能力：

- **代码层面**：排版清洗、内容保存、日志追加、话题文件写入
- **模型层面**：内容校验、质量自检、不合格内容自动重写

## 六、领域适配

### 6.1 设计原则

Agent 核心架构是**领域无关的**。本架构的记忆体系、Agent Loop、存储架构——不依赖任何特定领域。

领域特性通过**不同永久性级别的记忆**注入：人格记忆定义"是谁"，规则记忆定义"怎么做事"，能力记忆定义"能做什么"。换一套记忆 = 换一个领域的 Agent。

### 6.2 适配方式

| 适配项 | 记忆类型 | 永久性 | 配置位置 |
|--------|---------|--------|---------|
| Agent 人格 | 人格记忆 | `always` | personality.md |
| 领域规则 | 规则记忆 | `domain` | rules/*.md |
| 技能库 | 能力记忆 | `on-demand` | skills/*.md |
| 工具集 | 能力记忆 | `on-demand` | tools/*.json |
| 可归档内容分类 | — | — | schema.json |

### 6.3 领域切换示例

同一套 Agent 架构，加载不同永久性的记忆即可适配不同领域：

| 领域 | 人格记忆 | 规则记忆 | 能力记忆 |
|------|---------|---------|---------|
| 小说创作 | "你是一个小说创作助手" | 叙事规范、标点约束 | 去 AI 味、审视角、读章节、归档设定 |
| 代码开发 | "你是一个代码助手" | 代码规范、安全约束 | 代码审查、重构、读文件、运行测试 |
| 学术写作 | "你是一个学术写作助手" | 引用格式、学术规范 | 文献整理、查重、检索文献、格式化 |

## 七、技术选型明细

| 选型 | 方案 | 理由 |
|------|------|------|
| 编程语言 | JavaScript（ES Module） | 模块化接入方案选择 npm 嵌入式（9.2 节），JavaScript 是唯一选择；Node.js 对文件 IO、SQLite、定时任务支持完善 |
| 模块系统 | ES Module | `@memora/core` 作为 npm 包使用 ESM，与宿主项目的 import 语法一致 |
| API 接口 | 正规第三方 API，兼容 OpenAI 标准格式 | 合规稳定 |
| 短时存储 | 话题文件（MD 格式） | 可读、可手动编辑 |
| 长期本体存储 | Markdown 文件 | 备份迁移零成本 |
| 检索数据库 | SQLite（FTS5 全文检索 + Embedding 向量索引） | 单文件无服务 |
| Token 统计 | tiktoken 或等效库 | 上下文裁切 |
| 定时任务 | node-cron | 嵌入式模式下冥想机制的定时触发（9.8 节） |

## 八、分阶段迭代开发路线

### 阶段一：极简版

实现永驻/领域记忆加载 + 话题文件上下文管理 + 基础 API 调用 + 基础对话模式（单轮问答，无工具调用循环）。无自动记忆归档、无数据库。

### 阶段二：轻量实用版

新增每日归档、长期精华记忆、关键词路由能力记忆、工具调用循环（Agent Loop 完整实现）。接入 SQLite 基础索引，实现手动归档记忆。

### 阶段三：完整版

新增自动冥想归档、向量相似度召回、模型自主能力记忆选择、内容自检、Function Calling 工具调用、MCP 工具集成、安全权限系统，成型完整通用 Agent。

## 九、模块化接入方案

### 9.1 设计目标

Agent 核心架构是**领域无关的**，天然可抽离为独立模块。目标是：

- Agent 核心代码作为独立 npm 包（`@memora/core`），不绑定任何宿主项目
- 宿主项目（bowen-reader 或其他项目）通过 `npm install` 接入，仅持有配置文件
- 同一套 Agent 核心代码，加载不同配置文件 = 不同领域的 Agent
- 不同项目的数据（记忆、话题、归档）完全隔离

### 9.2 运行形态

| 方案 | 描述 | 适用场景 |
|------|------|---------|
| **A. npm 嵌入式**（推荐） | Agent 作为 npm 包，宿主 `import` 后直接调用。冥想机制用 `node-cron` 在宿主进程内定时执行 | Node.js/Electron 项目 |
| **B. 独立进程** | Agent 作为独立进程运行，暴露 HTTP/WebSocket 接口。冥想机制独立运行，不依赖宿主进程存活 | 多语言项目、需要独立进程管理的场景 |
| **C. 混合模式** | 核心是 npm 包，可选启动独立进程模式 | 灵活但维护成本高 |

**当前选择：方案 A（npm 嵌入式）**。理由：
- 宿主项目 bowen-reader 是 Electron（Node.js），天然支持 npm 包
- 零额外进程开销，调用延迟最低
- 冥想机制依赖宿主存活的问题，通过"宿主启动时检查上次归档时间，超过 24 小时自动补执"解决

### 9.3 目录结构约定

**Agent 核心包**（独立仓库）：

```

│   ├── core/

│   │   ├── topicReport.js      # 话题报告炼化

│   │   └── retrieval.js        # FTS5 + 向量检索（统一召回管道）
│   ├── storage/

│   │   └── dbStore.js          # SQLite 数据库操作
```

### 9.4 存储隔离

不同项目的数据完全隔离，每个项目有独立的存储根路径：

```
~/.memora/
├── projects/
│   ├── bowen-reader/               # 小说项目的 Agent 数据
│   │   ├── topics/                 # 话题文件
│   │   ├── archive/                # 归档文件
│   │   ├── agent.db                # SQLite 数据库
│   │   └── session.json            # 会话元信息
│   └── another-project/            # 另一个项目的数据
│       ├── topics/
│       ├── archive/
│       └── agent.db
└── global/
    ├── personality.md              # 全局人格（可选，项目级可覆盖）
    └── rules/                      # 全局规则（所有项目生效）
        └── universal.md
```

**隔离原则**：
- 每个项目有独立的 SQLite 数据库文件，话题文件和归档目录
- 全局规则对所有项目生效，但项目级规则优先
- 跨项目记忆不共享（除非用户显式配置共享话题）

### 9.5 API 设计

Agent 核心对外暴露最小可用 API：

```javascript
import { Agent } from '@memora/core';

// 初始化
const agent = new Agent({
  projectId: 'bowen-reader',           // 项目标识 → 决定存储路径
  storageRoot: '~/.memora',        // 存储根目录
  configDir: './agent-config',         // 配置文件目录（相对宿主项目根目录）
  llm: {
    provider: 'openai',                // 模型提供商
    apiKey: process.env.OPENAI_API_KEY,
    model: 'gpt-4o'
  }
});

await agent.init();

// 发送消息 → 返回完整响应
const response = await agent.chat('帮我写一段对话');
// response: { content: '...', toolCalls: [...], sessionId: '...' }

// 流式响应
for await (const chunk of agent.chatStream('继续写')) {
  // chunk: { type: 'text' | 'tool_call' | 'done', content: '...' }
}

// 关闭（触发待归档数据的写入）
await agent.close();
```

**关键设计**：
- 构造函数参数最小化——只有 `projectId`、`storageRoot`、`configDir`、`llm` 四个必填参数
- 配置文件按目录约定自动发现，不需要显式列出每个文件路径
- Agent 内部的所有复杂度（记忆管理、上下文裁切、工具循环）对宿主完全透明

### 9.6 配置文件约定

遵循"约定优于配置"原则。宿主项目只需按约定目录结构放置配置文件，Agent 自动加载：

| 配置项 | 记忆类型 | 永久性 | 约定路径（相对于 configDir） | 说明 |
|--------|---------|--------|---------------------------|------|
| 人格设定 | 人格记忆 | `always` | `personality.md` | 项目级人格，可选。缺失时使用全局人格 |
| 规则 | 规则记忆 | `always`/`domain` | `rules/*.md` | 所有 `.md` 文件自动加载 |
| 技能 | 能力记忆 | `on-demand` | `skills/*.md` | 每个 `.md` 文件是一个技能 |
| 工具 | 能力记忆 | `on-demand` | `tools/*.json` | 每个 `.json` 文件是一个工具定义 |
| 领域 Schema | — | — | `schema.json` | 领域可归档内容类型定义 |

Agent 核心包提供 `templates/` 目录，包含各领域的配置模板，宿主项目可复制后修改。

### 9.7 宿主项目接入流程

**首次接入**（以 bowen-reader 为例）：

```
1. npm install @memora/core
2. 复制模板：cp -r node_modules/@memora/core/templates ./agent-config
3. 编辑 ./agent-config/personality.md → 设定人格记忆
4. 编辑 ./agent-config/rules/ → 放置规则记忆
5. 编辑 ./agent-config/skills/ → 放置能力记忆
6. 在宿主代码中创建桥接层：
   - Electron 项目：渲染进程 ↔ preload IPC ↔ 主进程 ↔ Agent
   - 普通 Node.js 项目：直接 import Agent
7. 启动对话
```

**接入第二个项目**：

```
1. npm install @memora/core
2. cp -r templates ./agent-config
3. 换一套记忆配置文件（人格、规则、技能）
4. projectId 设为新项目名称
→ 同一套代码，不同的 Agent
```

### 9.8 冥想机制在嵌入式模式下的调整

原设计是"每日凌晨固定时间自动执行"，在嵌入式模式下依赖宿主进程存活。调整如下：

- **正常运行**：宿主进程存活时，`node-cron` 按每日凌晨执行归档
- **宿主关闭**：超过 24 小时未执行归档时，下次 `agent.init()` 自动补执。补执时合并所有未归档日期的对话原文
- **手动触发**：宿主可随时调用 `agent.archive()` 手动执行归档

### 9.9 多项目并发安全

当同一台机器上多个项目同时运行 Agent 时：

- 每个项目有独立的 SQLite 数据库文件（`agent.db`），不存在锁竞争
- 跨会话记忆共享的锁是**项目级别**的，不会误锁其他项目的话题文件
- 全局规则目录（`~/.memora/global/`）只读加载，无并发写入

## 十、方案优势总结

- **合规安全**：全部使用正规付费 API，无账号封禁风险
- **领域无关**：同一套架构适配多种领域，通过配置切换
- **冷热分离**：文件管高速实时交互，数据库管精准记忆召回
- **渐进迭代**：无需一步到位，可分阶段开发
- **完全可控**：所有记忆数据全部私有化存储，100% 自主掌控
