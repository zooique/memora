## 0. 本版三项裁决

### 0.1 术语正名（不改术语锚点）

本文此前把最上层写作「L3 目标模式」。**现正名为「目标聚焦编排（单 turn）」**。

**显式声明**：这不是 `terminology-anchor-rules.md` §5 定义的「目标模式」（那指**对多个 turn 的编排、只给目标文档、全自动至达成**，未实现）。本文讨论的是它的**前置阶段**：单 turn 内聚焦一个目标、由主助手操作独立子会话完成、需人工触发。

不改术语锚点的理由：锚点里的定义是远期锚，本文如果改写它，等于用一个未落地的方案定义覆盖既定术语；两个定义并存在参考文献里，未来必错一份。因此**本文不引入第二个「目标模式」定义，只用一个新名字指代自己的射程**。

### 0.3 口径三（同步 / 异步）移出待拍

本文 §2.1 与 §8.4 已按**同步**写完，即已决，不再是待拍项。改写为「已定 v1 同步 + 代价登记」（§2.5）。待拍只保留 §7 的一、二、四。

### 0.4 v1 载体形态定案（2026-11-11）：父 turn 内的同步递归，不是会话实体

**定案**：v1 = 父那一 turn 内的同步递归。**不落 Round、不进会话列表、内存 messages 用完即弃**；结果从递归返回值经父的工具返回值通道回传。

**保留**（不随载体重订的结论）：

- **deny 轴**：§7.4 依据一已重写——`toolReadonly='readonly'` 能挡写盘和命令，但 deny 仍不可替代（可见面隐藏 / `ask_user` / 有副作用但不写盘的常驻工具）。
- **同步执行**（§2.5）：父在同一 turn 内等齐子结果，§2.1 的单裁决者前提才成立。
- **深度 1 + 同一步最多 2 个**：子会话不注入派发端口（结构性），端口信号量硬限并发。

**替换**（原 P1④「独立子会话 + 落 Round + 宿主派发端口」作废）：

- **不建会话实体**：不进 `AgentRegistry`、不写 `SessionMeta`、不建假 Round。
- **不碰确认队列**：子会话非前台，若还能写盘就会触发「不上屏 ⇒ 不计时 ⇒ 父永久阻塞」（§7.2 的硬耦合）；v1 用 deny 轴从根上不给写工具。
- **不写父状态**：不复用父 loop 的 `onToolExecuted` / `onPendingQuestion` 回调；子 loop 用独立 `ToolExecutor`。
- **结果形态**：子递归返回值（最终回答原文，截断上限 20,000 字），首行由内核按流标志生成 `[SUBAGENT:completed]` / `[SUBAGENT:interrupted]` / `[SUBAGENT:failed]` 确定性头部。

**形态细节与六条夹紧规则**的唯一落点是 [loop-design.md](./architecture/loop-design.md) §5.3；本节只记裁决与理由，不复制定义。

## 1. 结论先行

| 层 | 形态 | 一句话结论 | 依赖 |
| --- | --- | --- | --- |
| **L1 单会话助手** | 现状：一会话一 Agent，处理用户分散需求 | 已落地，是唯一有成体系支撑的一层 | — |
| **L2 主助手 + 独立子会话** | 主助手派生独立会话执行，结果回传 | 有「实例地基」但**没有语义**：缺派生、回传、配额、子轮归处，也缺「比默认更窄」的工具面 | L1 实例面 + §3.2 所列新增件 |
| **L3 目标聚焦编排（单 turn）** | 聚焦一个目标，先产出指导文档，再由主助手派子会话完成 | 是 L2 的**消费者**，不是兄弟；不加第二套完成判据 | **L2 全部** + 指导文档 + 跨 turn 状态 |

一句话版本：**L3 不能绕过 L2 生长；L2 必须同步做，否则 L3 的单裁决者前提不成立。**

> **载体口径订正（2026-11-11）**：上表 L2 的「独立子会话」是路线名，**不等于 v1 实现形态**。v1 不建会话实体、不落 Round（§0.4），因此表内「子轮归处」与 §7.2 的「列表可见性」不是 v1 的前置缺口，而是将来「独立子会话」形态的议题。v1 的可见性 = 父工具结果里的 `[SUBAGENT:*]` 头部。

## 2. 硬结论（连成立条件、代价与天花板一起写）

### 2.1 「一范围一裁决者」成立，但只在「父同一 turn 内等齐子结果」这个窗口内成立

- 取证：`done` 由**纯文本收场**产生——`src/agent/loop.ts:2008-2064`（`handleTextResponse` 在文本交付后 `yield done`）；由 `handleIterationResult` **消费**——`src/agent/loop.ts:1207-1239`。另有步数上限收场 `src/agent/loop.ts:1116`、用户硬中止 `src/agent/loop.ts:1210-1213`。
- 取证：任务表**无裁决权**，只是注入文本 `src/agent/assembler.ts:468-494`；turn 结束清空 plan，**暂停态例外**——`src/agent/agent.ts:1207-1224`（`:1214` 明写 `if (cp.pauseMeta) return;`）。
- 成立：子会话判自己那块（各自 turn），父在同一 turn 内判整体 —— 两个射程、各自一个裁决点，**不改现有判据**。
- 不成立：父跨 turn 推进 —— 父的 `done` 会在子还没回来时宣布整体完成；要补就得加第二判据或复活多 turn 编排。
- **推论（判断）**：异步派发让父先收场 ⇒ **异步必然破坏本结论**。

### 2.2 主助手不得复核子会话已交付的切片

同一切片若「子会话 `done`」+「父复核」两处都判，就是同一块两个裁决者。正确读法：**子会话判切片，主助手只判「整体锚点 + 切片齐备」**。

### 2.3 目标聚焦编排不加第二套完成判据

- 并列加一层「达成判定」⇒ 两个「算不算完」且无裁决顺序。
- 唯一站得住：父的**单 turn `done` 本身就是整体判定**，判据来自指导文档（文档进上下文，不另立裁决器）。
- 成立条件：父单 turn 长跑（§2.1）且不复核切片（§2.2）。任一破坏即失效。

### 2.4 父单 turn 的预算天花板（本版新增，原缺）

- 取证：默认迭代上限 **50**——`src/role-pack/strategyKeys.ts:41`；角色包最高可声明 **500**——同文件 `:86`；下限 10——`:79`。抬预算的唯一旋钮是**角色包配置**，没有「目标级预算」接口。
- 因此 P3 的真实形态是：**目标必须装进父会话当前角色包的 `stepBudget`**。默认 50 步装不下的目标，会撞上限收场，此时**根本没有整体判定**（父是被预算结束的，不是判定达成的）。
- 本文**明确不做**目标级独立预算（与 §10 一致）。代价：目标规模受角色包配置硬约束；P3 必须有一条「撞上限」失败路径用例，不得只验小目标。

### 2.5 v1 同步：已决 + 代价登记

- 已定：v1 用**同步工具**（一次调用阻塞到子会话收场），同一步多调用天然并行。
- 代价登记（不再作为待拍）：
  1. 拿不到「随时查进度」——同步调用期间父没有观察点。
  2. 父的 step 时间被拉长，用户可感知延迟（量级无样本，见 §11）。
  3. 子会话一挂起（`ask_user`）就会拖死父——因此 v1 必须禁子会话提问（§7.4）。
  4. 父 abort 后子不一定立刻停（协作式），存在「父收场、子仍在写」窗口——必须靠端口信号合并 + 验收用例兜（§10 P1）。

## 4. 「指导文档」的落点

内容与指针分两层，这是分工不是双写：

| 层 | 落点 | 谁写 | 谁读 |
| --- | --- | --- | --- |
| **正文（内容真源）** | 工作区产物文件（如 `docs/目标/<slug>.md`） | 一次收敛动作由主助手写入；后续只有主助手在有据可依时改 | **新增的 Prepare 注入段**（见 §4.1）每轮读入；子会话只收派发时传的切片段 |
| **指针（当前目标真源）** | 项目级固定路径 **或** `SessionMeta` 一个字段（作用域见 §7.1） | 收敛动作写、换目标时改 | 注入段与 UI 状态面 |

### 4.1 注入载体（本版补上，原缺）

- 现有唯一的「工作区文件 → 每轮固定注入」通道是 `resident` 项目规则段（`src/agent/managers/residentRules.ts:1-15`），而该段已被 §4.2 否掉（语义不同、共享预算、撞在途的常驻层收缩）。
- 因此 v1 定：**新增一个 Prepare 注入段「当前目标」**，只读指针指向的那一个文件；读盘判据、路径守卫、字符上限**复用同一套现成实现**（不另写第二份），fail-closed 同源（工作区未信任整段不注入）。
- 段内必须写明未注入原因：读取失败 / 文件缺失 → **段内一行「本次未注入（原因），下轮重试」**，落点是段内文案，**不新增 notice 通道**。
- 字符预算：单段上限**与项目规则段同量级但独立计数**（判断：先取 5,000 起，超限按序截断并标注），不与项目规则段共享预算——否则两段互相挤占，边界上会得出两个结论（同 `residentRules.ts:23-37` 的教训）。
- **「不能只是提示词」的准确含义**：不能靠模型自己想起来 `read_file`；必须有注入段。原 §4.1 那句话在本版按此收窄。

### 4.2 它不能是什么（逐条带证据）

- ❌ **不能是 checkpoint 字段**：goal 三字段曾存在于检查点，因零读取被作为**僵尸字段**删除——`src/agent/managers/sessionManager.ts:273-277`、`src/__tests__/publicMemberSurfaceGuard.test.ts:4-7`（GOAL-DRIFT-1）。
- ❌ **不能是记忆条目**：记忆是 round 摘要，参与衰减与 GC。
- ❌ **不能是任务表**：turn 级、结束即清空（暂停态例外，`src/agent/agent.ts:1214`）；任务项单 active 不变量的真源在 `src/agent/managers/sessionManager.ts:609-626`（写点契约 + `ensureActivePlanItem`），不是在消费侧。
- ❌ **不塞进项目规则段**：`resident === true` 的条目并入「项目规则」固定段，共享单条 5,000 / 合计 10,000 字符预算，且 fail-closed 于工作区信任——`src/agent/managers/residentRules.ts:23-37`、`:67-70`。目标是**临时且唯一**，项目规则是**稳定且多条**。
- ❌ **不能只是提示词**：见 §4.1 的收窄定义。

### 4.3 与 checkpoint 的分野（判断）

checkpoint 存「这一轮执行到哪了」（执行态，含 plan 快照）；指导文档存「要达成什么」（意图）。互不替代，不共享字段。

### 4.4 「同一时间只推进一个目标」的落点与纪律冲突

- 若选项目级（固定路径 + 归档目录）：文件在＝目标在，换目标＝旧文件归档 + 写新文件。
  - **必须补显式可见面**：仓库既有定案是「隐式切换：重配置对象只被显式调用」（`single-truth-source-mindset.md` 设计陷阱）。「文件在即激活」如果不是隐式状态，就必须有一处**显式呈现**（状态条 / 会话头一行「当前目标：X」）让人与模型都能看见。没有呈现面，它就是隐式切换，违反既有纪律。
  - **git 处置必须回答**：内容可能含个人计划 ⇒ 默认 `.gitignore` 排除工作区侧目录（判断，非取证）；归档目录同理。若用户要版本化目标，则改为显式提交策略——这是产品口径，见 §7.1。
  - **多根**：宿主的项目根口径是「一个宿主 = 一个项目」——`hosts/memora-vscode/src/extension/extension.ts:316-324`；多根工作区下「项目级」实际只覆盖首根，其余根无法表达。
- 若选会话级：只保证「一个会话一个目标」，多会话可多目标；**且不是「改动小」**——`SessionMeta` 是导出接口且有冻结成员面守卫（`src/__tests__/publicMemberSurfaceGuard.test.ts:915-928`），加字段即红，须改守卫基线。
- 多个目标文档可以存在，但**当前**只能有一个指针；不允许两个激活。
- 换目标处置：旧文档移入归档 + 指针切换（一步确定性动作）；**不做**「暂停目标」字段（那是第二个状态机）。

## 5. 切片规则必须进文档 + 一条弱保证

- 若切片与验收锚点由主助手临场决定，「整体按文档判」就退化为模型直觉，文档只是参考材料。
- 文档最少两节：**切片表**（id / 范围 / 验收锚点 / 依赖顺序）与**整体锚点**（切片齐备 + 集成项）。
- **主助手不得改写切片验收锚点**；派发时原样传递该切片段。
- **弱保证（必须写进边界）**：锚点是同一个模型在 P2 收敛时写的，§5 的「不得改写」只有**约定**、没有执行机制——模型仍可能在编排时重写锚点。**单裁决者 ≠ 裁判独立**。这是有意接受的弱保证；要变成强保证，需要「锚点哈希锁定 + 派发时比对」这类新机制，本文不做。

## 6. UI 形态（**本节为判断，不是取证**）

- **语义与 UI 解耦是纪律**：先定「谁判、判什么、状态放哪」，形态后议。
- 技术上：现有 VS Code webview **能承载**最小可见面（会话列表、目标卡片、子会话在跑/成败），不是硬阻塞。
- 真正受限的是**注意力与屏幕**：一个主助手 + 多个子会话要同时呈现「待办、在跑、卡住、待决策」，插件边栏装不下，也不该装。
- 结论（判断）：**将来可能需要独立客户端**——不是「现在不能在插件里做」。
- 推进顺序：**先语义 → UI 只做最小可见面（能看见子会话在不在、成没成、当前目标是哪一个）→ 真实使用后再定形态**。形态未定时，禁止把「专属 UI」当立项前提。

## 7. 待拍口径（只剩一、二、四；三已决）

### 7.1 口径一：目标状态的作用域

| 选项 | 次生后果 |
| --- | --- |
| 会话级（`SessionMeta` 字段） | 与会话即单位一致、天然跨重启；但命中冻结成员面守卫需改基线，且只保证单会话单目标；fork 不继承该字段（`SessionMeta` 现有语义以身份/命名/角色名为主，`src/memory/sessionStore.ts:110-128`），子会话需另定继承规则 |
| 项目级（固定路径文件） | 全局只可能一个目标、跨会话共享、无需新字段；但需回答 git 处置、多根只覆盖首根（`extension.ts:316-324`）、写入冲突（用户手改 vs 分叉写入）、可发现性（不加显式呈现面即违反「隐式切换只被显式调用」） |

**成本披露（不预选）**：两条都有硬成本，没有「更省」的一条。选哪条取决于「目标该属于项目还是属于一次对话」，这是产品定义，不是工程优劣。

### 7.2 口径二：子会话可见性（**已升为 P1 前置**）

> **v1 不适用（2026-11-11）**：v1 不建会话实体、不落 Round，因此「子会话是否进列表」在 v1 路径上不存在。本节口径保留给将来的「独立子会话」形态；v1 的可见性 = 父工具结果里的 `[SUBAGENT:*]` 头部。下文的写确认硬耦合仍是 v1 必须 deny 写工具的原因。

| 选项 | 次生后果 |
| --- | --- |
| 进用户会话列表 | 实现最省（子会话就是普通会话）；但用户列表被派生会话淹没，「子」与「普通」不可区分；用户点进去只能看历史，看不到「进度」 |
| 隐藏子会话 | 需要新的存储归属与列表过滤规则（现有形态不存在）；且确认卡无人可见 → 见下 |
| **进列表但归组/折叠**（第三选项） | 保留可发现性又避免淹没；仍需一个「父子归属」字段与列表分组规则，成本介于两者之间 |

**与写确认的硬耦合（取证）**：确认队列只在**前台会话**推送（`confirmCoordinator.ts:206-210`），且计时只在首次上屏开始（`:262-264`）。**非前台请求永不上屏则永不计时，也就永不超时** ⇒ 若选「隐藏」且子会话还能写，父会**永久阻塞**。因此无论选哪个，v1 都必须让子会话**没有写工具**（§7.4）。

### 7.3 口径四：既有「≥3 次真实案例」纪律

既有结论要求子 agent 累计 ≥3 次真实案例才重启评估，至今 0 次；用户本次把它抬成硬前置。**本文不裁决是否破。**

- **什么算一例**（本版补）：一次真实使用（**失败的一次也算**）；同一场景连续重复只算 1 例；纯测试/纯演示不算。
- **记在哪**（本版补）：台账观察区一条累计（`tasks/待完成任务.md`），逐例记「场景 / 切片数 / 回传长度 / 是否人工纠偏 / 成败」，**不新建文件、不凭印象**。

| 选项 | 次生后果 |
| --- | --- |
| 破（直接进 P1） | 快速拿到第一条真实链路；但切片粒度、回传形态、并发与成本模型全靠推演，无数据校准；旧文 §7/§8 的否决与缺陷仍需逐条重新裁决，不因「前置提升」自动失效 |
| 不破（累计 3 例再进） | L2 只能以最小实验形态存在（单工具、深度 1、无组队）；L3 推迟 |
| 挪门槛（3 例守在 L3 入口，L2 期间逐例记账） | L2 在零案例下事实获准；门禁移到更难执行的位置（要等真实使用才凑得满）；「一例」判据刚立、尚无实践检验 |

**它不是免检**：3 仍是硬门槛，只是守在 L3 入口而非 L2 入口；L2 期间必须逐例记账，不足 3 例不进 L3。

### 7.4 已决项：v1 子会话「只读 + 禁提问」（附依据与代价）

- **依据一（工具面，2026-11-11 重写）**：**原说法已订正**——旧文写「只有 deny 能实现只读」，不准确。`src/agent/toolRunner.ts:189-201` 的 `toolReadonly = 'readonly'` 已能按 `readonly` 标记挡下写盘与命令；`capabilities` 白名单确实只能加特权、不能减常驻（`src/agent/toolExecutor.ts:558-564`、`:988-997`），但它不是唯一的收窄手段。deny 轴**不可替代**的理由只剩三条：
  1. **从模型可见面隐藏**：`toolReadonly` 只在执行时拒绝，工具仍留在 `list` 里，模型会看见并反复尝试，白烧 step；deny 在 `isToolExposed`（`toolExecutor.ts:988-997`）第一行就把工具从可见面移除。
  2. **`ask_user` 管不到**：它是 `readonly: true` 的常驻工具（`toolExecutor.ts:521`），只读闸按 `readonly` 标记放行；真正的挂起发生在 loop 层（`src/agent/loop.ts:1726` `willSuspendForAsk` → `:1897` `handleAskUser`），只能靠 deny 挡。
  3. **有副作用但不写盘的常驻工具**：`remember_intel` / `task_table_write` / `task_table_update` / `register_work`（`toolExecutor.ts:517-522`）不经过 `write_file`，只读闸的「写盘」语义也不覆盖它们；按「副作用」枚举比按「是否写盘」更可靠。
- **deny 的取法（按副作用枚举，不按工具名直觉）**：写盘 / 删文件 / 跑命令 / 杀命令 / 跑项目脚本 / 跑技能脚本 / `ask_user`，再加 `remember_intel` / `task_table_write` / `task_table_update` / `register_work`。工具名真源 = `DEFAULT_EXPOSED_TOOLS`（`toolExecutor.ts:503-537`）。**代价**：子会话不能贡献情报和任务项，得队长自己汇总——这是有意选择，不是遗漏。
- **实现位置（硬约束）**：deny 判定必须放在 `isToolExposed` 第一行、**在 `customTools.has(name)` 之前**（`toolExecutor.ts:990`）——否则 MCP / 自定义工具会先命中「恒暴露」分支，直接绕过 deny。
- **依据二（写确认）**：子会话非前台 ⇒ 确认卡不上屏 ⇒ 不计时 ⇒ 永不超时 ⇒ 父永久阻塞（`confirmCoordinator.ts:206-210`、`:262-264`）。
- **依据三（提问）**：`ask_user` 命中即 `paused`（`loop.ts:1726` / `:1897`），同步调用里没人替它答 ⇒ 父卡死。
- **结论**：v1 必须引入一条**工具拒绝名单**（deny 优先于常驻豁免集与自定义工具），清单见上方「deny 的取法」。这是**新增不变量**，必须独立立项与独立验收（§9、§10 P1），不能当 P1 的小功能顺带。
- **代价**：P1 的子会话**只能看不能改**；「子会话负责改代码」要等到这条 deny 轴被接受并放开白名单子集之后。**这是有意的收窄，不是遗漏**。

## 8. 被推翻的判断（过程记录，不美化）

1. **子 agent 排在最后 → 改为 L2 硬前置**
   - 原来怎么想：先图片工具、再目标模式，子 agent 最后评估（依据旧文「半生长、不落地」）。
   - 为什么推翻：用户定义里 L3 的执行载体就是独立子会话；载体语义不存在时，L3 只能退化成单会话长任务。
2. **「你提前实现了会话层再生长一层」→ 其实只有实例面**
   - 原来怎么想：一会话一 Agent、独立执行，似乎就是子 agent。
   - 为什么推翻：实例隔离 ≠ 派生语义。父子、回传、配额、子轮归处四项全缺（§3.2/§3.3）。
3. **目标聚焦编排按「软档：文档常驻」理解 → 改为 L2 之上的编排层**
   - 原来怎么想：不加判定、只让文档常驻，靠模型自觉。
   - 为什么推翻：用户定义含「由助手操作独立子会话完成」——这是编排，不是常驻提示；软档解决不了「谁去干、干完怎么回流」。
4. **异步优先 → v1 同步**
   - 原来怎么想：Trae 形态是异步派发、随时查进度，理应照搬。
   - 为什么推翻：异步要求父持续在线等待，而现有 loop 没有等待态；父一收场，整体判定无人持有（§2.1）。
5. **（本版新增）「用能力白名单把子会话收窄成只读」→ 不成立**
   - 原来怎么想：按审查倾向，白名单一次性绕开写确认与提问两个洞。
   - 为什么推翻：白名单只能**加**特权工具，不能**减**常驻工具（`toolExecutor.ts:558-564`、`:963-980`）；常驻集已含写盘/命令/提问（`:502-533`）。只能新增 deny 轴。
6. **（2026-11-11 新增）独立子会话载体 → 父 turn 内同步递归**
   - 原来怎么想：P1 = 宿主派发端口 + 新建子会话 + 显式继承父角色包 + 落 Round。
   - 为什么推翻：v1 只需要「父 turn 内多一份隔离上下文」，不需要会话身份；建会话实体反而带出 Round 归属、列表可见性、确认队列三条副作用（§0.4）。角色包继承也随之失去理由——权限不再从角色包来。

## 9. 边界与新增不变量（集中一条边界）

**边界声明**：引入新不变式 = **必须单独立项**，本文只做路线与口径，不预支实现。

本路线触及的新增不变量（各自独立验收，不得塞进功能清单）：

1. **工具拒绝名单（deny）**：优先级 deny > 常驻豁免集 > 白名单；唯一判据点在 `isToolExposed` 层，三态语义不变（§7.4）。
2. **「当前目标」注入段**：新增 Prepare 段 + 独立字符预算 + fail-closed 同源（§4.1）。
3. **目标指针状态**：作用域一旦选项目级即新增「隐式状态」，必须配显式呈现面（§4.4）。
4. **派生深度 = 1**：**不需要新计数**——子会话装配时**不注入派发端口**，`delegate` 工具在子会话里根本不存在。这是端口层的结构性保证，不是新不变式，但必须有「孙派发被拒」用例。

## 13. 路由：执行体选择（探索，2026-11-11）

> **状态**：探索章。不并入 §0 三项裁决，不改 §10 分期表；§0.4 的载体口径仍是实现形态的唯一真源。
> **射程**：只回答「主助手凭什么决定派 / 不派 / 派给谁」以及它在宿主 UI、手机控制两面的后果。不重新定义子 agent 形态（形态见 [loop-design.md](./architecture/loop-design.md) §5.3）。
> **为什么放在本文**：路由是 §0.4 载体（`delegate_task`）的**上一层决策**。同一对象（派发）若另开一份文档，会造出两份「谁决定派」的真源。
> **证据纪律**同文首：取证写 `文件:行`，判断标「判断」。

### 13.1 我的判断：路由不是新 agent，是主 agent 内的一层

先把结论钉死：**「路由 agent」不是一个独立 agent。它是主 agent 在同一次 LLM 调用里选择「这一步交给谁」的一层判断；v1 里这一层的全部实现，就是 `delegate_task` 这一次工具调用。**

四条理由：

1. **独立 router 会变成「turn 之上再包一个 turn」**。仓库最小单元是 turn ⊃ loop ⊃ step；[目标模式生长探索-分层阶段化.md](./目标模式生长探索-分层阶段化.md) §4.1 已判过这个形态——外层 orchestrator 是第二个单元，内部每个子会话翻开仍是 turn/loop/step。独立 router 只是把「会话」换成「一次只做选择的 turn」，换壳不换质。
2. **独立 router 拿不到选择所需的上下文**。选执行体要看历史、记忆召回、任务表、工作区状态，这些全是装配层的产出（`src/agent/assembler.ts`）。独立 agent 要再注入一遍，等于把装配层实现两份。
3. **仓库里已有的三个「路由」都不是 agent**：`determineTaskType` 是纯函数规则路由（`src/agent/managers/llmCaller.ts:139`，选 provider）；`TURN_START_STRATEGY_PROMPT` 是 prompt 层行为边界（`src/agent/assembler.ts`）；`delegate_task` 是工具层派发（`src/agent/builtinTools.ts:520-557`）。没有任何一个是独立执行体，也没有一个需要独立上下文。
4. **与既有裁决同向**。[turn-intent-reasoning-design.md](./architecture/turn-intent-reasoning-design.md) D2 已裁定「意图理解是 LLM 天然能力，不给步骤脚本、不做分类机」。独立 router 等于把这条判断外置成第二次 LLM 调用——方向正相反，且第二次调用的裁决者与第一次不是同一个。

这条定义直接决定后面四件事（不是「视情况而定」，是推论）：

| 设计面 | 因为「路由是同一次调用内的工具选择」，所以 |
| --- | --- |
| 协议 | 不需要「路由消息 / 路由会话 / 路由上下文」；输入是主 agent 已有的装配结果，输出是工具调用 + 参数 |
| 成本 | LLM 调用次数不增加；没有第二次上下文装配，也没有第二次计费 |
| 可解释 | 只能靠「派发参数 + 回执」呈现；要求模型自证「为什么选这一路」= 让它事后编理由 |
| 可纠正 | 纠正发生在**下一句话**，不发生在 UI 控件上；UI 改派需要重放入参与撤销已执行步骤，那是另一个机制 |

顺带说一句不讨好的：Trae 那种「判断意图 → 分派执行体 → 汇总」的观感，本质是「一个 agent + 一组工具 + 一套系统提示」，界面上看到的「分派」是工具调用行的投影。把观感当架构实现成独立 router，会买到双倍延迟和双倍成本，换不到任何能力。

**与 §2.1 的一致性**：路由发生在父的同一 turn 内，父仍是唯一裁决者——§2.1 的前提没有被这一层破坏，反而要求它必须留在父内。

### 13.2 已定案（取证，不是本文判断）

这五条是后续设计的硬约束，不要再论证：

1. **派发的 observable 形态 = 一次工具调用**。`tool_start` 带 `args`、`tool_result` 带 `delegate`，都进 `Round.processEvents` 落盘（`src/memory/roundStore.ts:289-318`），重放可见。
2. **回执已经存在，且是结构化的**。`DelegateTaskReceipt = { terminal, excerpt, durationMs, queuedMs }`（`src/agent/types.ts:29-41`）；`terminal` 四态由内核按流终态标志生成，不是模型写的。
3. **宿主已经渲染了路由结果**。过程流里的 delegate 行 = 「派发」段（`args.task` 全文 + capabilities 列表）+ 「回执」段（结论摘录 + 排队/执行两段耗时 + 截断标注）+ 四态色调 class（`hosts/memora-vscode/src/webview/scripts/processFlowCells.ts:229-305`）；宿主透传点 `hosts/memora-vscode/src/webview/panels/chatPanel.ts:3246-3255`。老数据无 `delegate` 字段时回退两态，不补假徽标（同文件测试）。
4. **v1 的执行体能力边界**：子 agent 只读、深度 1、同一步最多 2 个、不继承父角色包、`capabilities` 只能点名 `web:search` / `web:fetch`（[loop-design.md](./architecture/loop-design.md) §5.3）。路由不能越过这四条。
5. **队伍不是执行体池**：`setRolePackTeams` 注释明写「组员仅会议参与，不用于日常」（`src/role-pack/rolePackManager.ts:446-451`）；`run_team_meeting` 是一次内嵌 `provider.chat()`，单轮、无工具循环（`src/agent/builtinTools.ts:559-580`）。把队伍当路由池就是推翻这条定案。

### 13.3 我建议这样定，待复核

#### 13.3.1 路由契约

**输入**：不新增输入通道。主 agent 已有的装配结果就是输入（用户消息 + 召回 + 项目规则 + 任务表 + 当前角色包 persona）。

- **不做设备感知路由**（判断）：手机来的 `cmd.kind:send` 与桌面 `handleInput` 走同一条路（[手机方案](./方案-手机远程控制-20261110.md) §6.6），协议里没有「来自手机」这个信号。若为路由新增该字段，同一句话在 PC 和手机上会得到不同结果——不可解释、不可复现，是最坏的一类分叉。设备差异应该由「用户怎么说话」体现。
- **不做模式感知路由**：当前没有「模式」这个运行时状态；角色包是用户显式选择并写回会话文件的（`hosts/memora-vscode/src/shared/protocol.ts:533-535`），不是路由可读的模式位。

**输出**：不是「执行体选择对象 + 参数」，而是**具体工具调用**。理由：显式路由对象会造出第二裁决点（谁执行这个对象？主 agent 还得再调一次）；工具调用天然有参数、有结果、有过程流、有幂等契约（`delegate_task: 'non-idempotent'`，`src/agent/builtinTools.ts:167-169`）。

**允许「先问一句再决定」**：已有机制，不新造。父层用 `ask_user`（`pause/ask/resume`）澄清后再派；**子层不行**——`ask_user` 在子会话被 deny（§7.4），子递归里提问会把父挂死。所以「先问再做」只能发生在派发之前，不能发生在子任务内部。

**可解释（三级，只保留前两级）**：

| 级 | 内容 | 评价 |
| --- | --- | --- |
| L0（已有，必做） | 过程流 delegate 行：派发段 task 全文 + capabilities + 回执段摘录/耗时/四态 | 已经是「这次派了什么、结果如何」的最低可解释面 |
| L1（建议，尽力而为） | 派发前一句 `narrate`（「这个适合让子会话去查」） | 复用现有 narrate 通道，不进正文、不落独立存储。模型不一定说；说错比不说更糟，所以它是补充不是契约 |
| L2（不建议） | 结构化「路由理由」字段（为什么选 A 不选 B） | 没有机制校验真伪，等于要求模型自证；且独立 router 才需要它 |

**可纠正（两层，只做第一层）**：

- **这一次**：用户下一句话说「你自己做 / 换个思路」。零新机制——下一次工具选择自然会变。
- **以后的默认**：只能落在项目规则或记忆条目，**不能落在路由 UI 的本地状态**（否则第二真相源）。
- **不做就地改派**：在过程流里点下拉换执行体，需要重放工具入参、撤销已执行步骤、处理幂等与非幂等混排。没有这套机制时做控件，就是「有 UI 改不动」的半截。

**落盘**：**不单独落盘**。路由决策就是 `tool_start` + `tool_result`，已在 `Round.processEvents` 里。**不新增 `route_decision` 事件类型**——那会让同一事实有两个载体（tool_start 与 route_decision），并让内核 loop 多一个产出点。

#### 13.3.2 宿主 UI

**落点：过程流，不新增容器。** 判据来自 13.1：路由是一次工具调用，过程流的定义就是「运行时过程事件（tool_start/tool_result/narrate/thought/…）」（`docs/architecture/process-event-log-replay-design.md`）。它天然是过程流里的一行，而且宿主已经这么做了（13.2 第 3 条）。

**不新增「路由模式徽标」**（判断）：徽标表达的是「策略」（自动/手动），delegate 行表达的是「这一次走了哪路」。两者不是一个东西。如果将来确实要一个「允许自动派发」的开关，它属于**输入区权限档位那一层**（同一类「这次我允许它做什么」的语义，见 [方案-输入框权限档位入口-20261025.md](./方案-输入框权限档位入口-20261025.md)），不是新造一个路由面板。

**一个真实缺口（取证）**：派发段只渲染 `args.task` 与 `args.capabilities`，**不渲染 `rolePack`**（`processFlowCells.ts:246-262`）。而 `rolePack` 恰恰是「派给谁」的那一半——现在 UI 只回答了「给了什么权限」，没回答「用了谁的人格」。建议补一行 `Role pack: <name> / none`（待复核：需确认 `args` 解析对老数据缺键的降级，以及文案是否进 l10n）。

**「路由错了」的操作路径**（建议）：

1. **就地重说**（主路径）：零机制。
2. **停止本轮**（已有）：`stop` → abort 传导到子递归（见 §14.4 的链路）。
3. **事后回看**（已有）：delegate 行折叠看参数与回执。
4. **不做**：过程流内下拉改派、单条子任务撤销。

**与「过程流」的边界**：路由决策**算一次工具调用**。自洽理由有两条：① observable 形态就是 tool_start/tool_result，另立容器会与它重复；② 另立容器需要内核新增事件产出点，而现有设计里新增 ProcessEvent 成员要同时改 union、回放、宿主渲染三处（`process-event-log-replay-design.md`），收益为零。

#### 13.3.3 手机控制（结论 + 指针）

完整约束见 [手机方案 §14](./方案-手机远程控制-20261110.md)。这里只给三条结论：

1. **回执不新增帧**：复用 `attention { kind:'settled' | 'error' }`；明细走 `evt.delta.process_event`，是否下发由 `hello_ok.caps` 决定。
2. **不因「用了子 agent」而要求人工确认**：v1 子 agent 只读，没有需要确认的副作用；将来放开写子集时，确认必须走同一个 `confirm_answer`。
3. **取消必须诚实**：v1 没有 per-dispatch 取消，`stop` 杀掉整个 turn（含子递归），`pause` 在子递归期间无效。

### 13.4 只是选项，不建议现在做

| 选项 | 为什么现在不做 | 什么条件下才值得重开 |
| --- | --- | --- |
| 独立 router agent | 13.1 四条理由；双倍成本换不到能力 | 出现「必须用另一个模型做路由」的实证需求（如路由模型与执行模型不同且成本更低） |
| 自动切换角色包 | 角色包是用户显式选择并写回会话文件；自动换会与 `rolePackSwitched` 事件链冲突 | 用户明确提出「让助手自己决定用哪个人格」，且能回答「换包后旧包规则残留怎么办」 |
| 把队伍当执行体池 | 与 `setRolePackTeams` 注释直接冲突；且要重新回答权限（存档 §7 已否决「能力继承队长」）与回传（会议无工具循环） | 用户明确要「组员日常干活」，并接受重新设计权限与回传 |
| 设备感知路由 | 协议无来源字段；同一句话在两端行为不同，不可解释 | 协议里出现语义化的「来源」概念（不只是传输层） |
| per-dispatch abort（只杀一个子任务） | 新不变量，需独立立项；父 stop 仍要杀全部 | 手机端出现「想停一个子任务但不想杀整轮」的真实案例 ≥3 次 |
| 路由 UI 面板 / 模式徽标 | 13.3.2：策略与结果混在一层 | 输入区档位那一层确实需要「派发开关」时，挂在档位上而非新面板 |
| 结构化路由理由字段 | 模型自证，无校验 | 出现「用户需要审计为什么这么派」的合规需求 |
| 路由结果单独落盘 | 与 tool_start/tool_result 双载 | 不重开：现有载体已足够 |

### 13.5 三条判据收口

**SSOT**：路由决策的唯一真源 = 主 agent 的工具调用记录（`Round.processEvents` 的 tool_start/tool_result）。UI 不攒「当前路由模式」，手机不攒「这次派了谁」，都从同一份投影读。禁止新增 `route_decision` 字段 / 表 / 事件。

**自然生长**：

- 挂「目标模式」？不。目标模式是跨 turn 编排（未实现），路由是单 turn 内的工具选择。
- 挂「角色包」？不。角色包是换装，不是分派；自动换装还会破坏用户显式选择契约。
- 挂「队伍」？不（现在）。注释已钉死「组员仅会议参与」。
- 挂「过程流」？是。过程流已是工具调用的容器，delegate 行已经长在里面。

**不带伤（会做出「一半」的做法，逐条排）**：

| 半截形态 | 为什么是半截 | 本文处置 |
| --- | --- | --- |
| 有路由 UI、没有纠正路径 | 能点但改不动 | 不做 UI，纠正靠下一句话 |
| 有手机入口、取消不了 | 用户以为能停一个子任务，实际杀整轮 | 文案如实写「停止本轮（含派发中的子任务）」 |
| 有解释、但解释是事后编的 | 模型自证无校验 | 不做结构化理由字段；narrate 只做补充 |
| 自动换角色包、但没有回推面 | 用户不知道现在是谁 | 不做 |
| 设备感知路由、但没有协议字段 | 两端行为不同且不可复现 | 不做 |
| 路由结果落第二处 | 双载 | 不做 |

| 批 | 做什么 | 边界 | 为什么这样切不带伤 |
