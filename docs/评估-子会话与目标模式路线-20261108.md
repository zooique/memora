## 0. 本版三项裁决

### 0.1 术语正名（不改术语锚点）

本文此前把最上层写作「L3 目标模式」。**现正名为「目标聚焦编排（单 turn）」**。

**显式声明**：这不是 `terminology-anchor-rules.md` §5 定义的「目标模式」（那指**对多个 turn 的编排、只给目标文档、全自动至达成**，未实现）。本文讨论的是它的**前置阶段**：单 turn 内聚焦一个目标、由主助手操作独立子会话完成、需人工触发。

不改术语锚点的理由：锚点里的定义是远期锚，本文如果改写它，等于用一个未落地的方案定义覆盖既定术语；两个定义并存在参考文献里，未来必错一份。因此**本文不引入第二个「目标模式」定义，只用一个新名字指代自己的射程**。

### 0.4 v1 载体形态定案（2026-11-11）：父 turn 内的同步递归，不是会话实体

**定案**：v1 = 父那一 turn 内的同步递归。**不落 Round、不进会话列表、内存 messages 用完即弃**；结果从递归返回值经父的工具返回值通道回传。

**保留**（不随载体重订的结论）：

- **deny 轴**：§7.4 依据一已重写——`toolReadonly='readonly'` 能挡写盘和命令，但 deny 仍不可替代（可见面隐藏 / `ask_user` / 有副作用但不写盘的常驻工具）。
- **同步执行**（§2.5）：父在同一 turn 内等齐子结果，§2.1 的单裁决者前提才成立。
- **深度 1 + 同一步并发硬限**：子 agent 不注入派发端口（结构性），端口按角色包策略 `act.subagentConcurrency` 硬限并发（`0` = 不注入端口；省略 = 内核缺省值，真源见 `src/role-pack/strategyResolver.ts`，文档不复述数字）。

**替换**（原 P1④「独立子会话 + 落 Round + 宿主派发端口」作废）：

- **不建会话实体**：不进 `AgentRegistry`、不写 `SessionMeta`、不建假 Round。
- **不碰确认队列**：子 agent 非前台，若还能写盘就会触发「不上屏 ⇒ 不计时 ⇒ 父永久阻塞」（§7.2 的硬耦合）；v1 用 deny 轴从根上不给写工具。
- **不写父状态**：不复用父 loop 的 `onToolExecuted` / `onPendingQuestion` 回调；子 loop 用独立 `ToolExecutor`。
- **结果形态**：子递归返回值（最终回答原文，截断上限 20,000 字），首行由内核按流标志生成确定性终态头部（四态成员与判据见 [loop-design.md](./architecture/loop-design.md) §5.3，本节不复制成员名）。

**形态细节与六条夹紧规则**的唯一落点是 [loop-design.md](./architecture/loop-design.md) §5.3；本节只记裁决与理由，不复制定义。

| 层 | 形态 | 一句话结论 | 依赖 |
| --- | --- | --- | --- |
| **L1 单会话助手** | 现状：一会话一 Agent，处理用户分散需求 | 已落地，是唯一有成体系支撑的一层 | — |

## 2. 硬结论（连成立条件、代价与天花板一起写）

### 2.1 「一范围一裁决者」成立，但只在「父同一 turn 内等齐子结果」这个窗口内成立

- 取证：`done` 由**纯文本收场**产生——`src/agent/loop.ts:2008-2064`（`handleTextResponse` 在文本交付后 `yield done`）；由 `handleIterationResult` **消费**——`src/agent/loop.ts:1207-1239`。另有步数上限收场 `src/agent/loop.ts:1116`、用户硬中止 `src/agent/loop.ts:1210-1213`。
- 取证：任务表**无裁决权**，只是注入文本 `src/agent/assembler.ts:468-494`；turn 结束清空 plan，**暂停态例外**——`src/agent/agent.ts:1207-1224`（`:1214` 明写 `if (cp.pauseMeta) return;`）。
- 成立：子 agent 判自己那块（各自 turn），父在同一 turn 内判整体 —— 两个射程、各自一个裁决点，**不改现有判据**。
- 不成立：父跨 turn 推进 —— 父的 `done` 会在子还没回来时宣布整体完成；要补就得加第二判据或复活多 turn 编排。
- **推论（判断）**：异步派发让父先收场 ⇒ **异步必然破坏本结论**。

### 2.2 主助手不得复核子 agent 已交付的切片

同一切片若「子 agent `done`」+「父复核」两处都判，就是同一块两个裁决者。正确读法：**子 agent 判切片，主助手只判「整体锚点 + 切片齐备」**。

### 2.3 目标聚焦编排不加第二套完成判据

- 并列加一层「达成判定」⇒ 两个「算不算完」且无裁决顺序。
- 唯一站得住：父的**单 turn `done` 本身就是整体判定**，判据来自指导文档（文档进上下文，不另立裁决器）。
- 成立条件：父单 turn 长跑（§2.1）且不复核切片（§2.2）。任一破坏即失效。

### 2.4 父单 turn 的预算天花板（本版新增，原缺）

- 取证：默认迭代上限 **50**——`src/role-pack/strategyKeys.ts:41`；角色包最高可声明 **500**——同文件 `:86`；下限 10——`:79`。抬预算的唯一旋钮是**角色包配置**，没有「目标级预算」接口。
- 因此 P3 的真实形态是：**目标必须装进父会话当前角色包的 `stepBudget`**。默认 50 步装不下的目标，会撞上限收场，此时**根本没有整体判定**（父是被预算结束的，不是判定达成的）。
- 本文**明确不做**目标级独立预算（与 §10 一致）。代价：目标规模受角色包配置硬约束；P3 必须有一条「撞上限」失败路径用例，不得只验小目标。

### 2.5 v1 同步：已决 + 代价登记

- 已定：v1 用**同步工具**（一次调用阻塞到子 agent 收场），同一步多调用天然并行。
- 代价登记（不再作为待拍）：
  1. 拿不到「随时查进度」——同步调用期间父没有观察点。
  2. 父的 step 时间被拉长，用户可感知延迟（量级无样本，见 §11）。
  3. 子 agent 一挂起（`ask_user`）就会拖死父——因此 v1 必须禁子 agent 提问（§7.4）。
  4. 父 abort 后子不一定立刻停（协作式），存在「父收场、子仍在写」窗口——必须靠端口信号合并 + 验收用例兜（§10 P1）。

## 4. 「指导文档」的落点

内容与指针分两层，这是分工不是双写：

| 层 | 落点 | 谁写 | 谁读 |
| --- | --- | --- | --- |
| **正文（内容真源）** | 工作区产物文件（如 `docs/目标/<slug>.md`） | 一次收敛动作由主助手写入；后续只有主助手在有据可依时改 | **新增的 Prepare 注入段**（见 §4.1）每轮读入；子 agent 只收派发时传的切片段 |
| **指针（当前目标真源）** | 项目级固定路径 **或** `SessionMeta` 一个字段（作用域见 §7.1） | 收敛动作写、换目标时改 | 注入段与 UI 状态面 |

### 4.1 注入载体（本版补上，原缺）

- 现有唯一的「工作区文件 → 每轮固定注入」通道是 `resident` 项目规则段（`src/agent/managers/residentRules.ts:1-15`），而该段已被 §4.2 否掉（语义不同、共享预算、撞在途的常驻层收缩）。
- 因此 v1 定：**新增一个 Prepare 注入段「当前目标」**，只读指针指向的那一个文件；读盘判据、路径守卫、字符上限**复用同一套现成实现**（不另写第二份），fail-closed 同源（工作区未信任整段不注入）。
- 段内必须写明未注入原因：读取失败 / 文件缺失 → **段内一行「本次未注入（原因），下轮重试」**，落点是段内文案，**不新增 notice 通道**。
- 字符预算：单段上限**与项目规则段同量级但独立计数**（判断：先取 5,000 起，超限按序截断并标注），不与项目规则段共享预算——否则两段互相挤占，边界上会得出两个结论（同 `residentRules.ts:23-37` 的教训）。
- **「不能只是提示词」的准确含义**：不能靠模型自己想起来 `read_file`；必须有注入段。原 §4.1 那句话在本版按此收窄。

### 4.2 它不能是什么（逐条带证据）

- ❌ **不能是 checkpoint 字段**：goal 三字段曾存在于检查点，因零读取被作为**僵尸字段**删除——`src/agent/managers/sessionManager.ts:273-277`、`src/__tests__/publicMemberSurfaceGuard.test.ts:4-7`（GOAL-DRIFT-1）。
- ❌ **不能是记忆条目**：记忆是 round 摘要，参与衰减与 GC。
- ❌ **不能是任务表**：turn 级、结束即清空（暂停态例外，`src/agent/agent.ts:1214`）；任务项单 active 不变量的真源在 `src/agent/managers/sessionManager.ts:609-626`（写点契约 + `ensureActivePlanItem`），不是在消费侧。
- ❌ **不塞进项目规则段**：`resident === true` 的条目并入「项目规则」固定段，共享单条 5,000 / 合计 10,000 字符预算，且 fail-closed 于工作区信任——`src/agent/managers/residentRules.ts:23-37`、`:67-70`。目标是**临时且唯一**，项目规则是**稳定且多条**。
- ❌ **不能只是提示词**：见 §4.1 的收窄定义。

### 4.3 与 checkpoint 的分野（判断）

checkpoint 存「这一轮执行到哪了」（执行态，含 plan 快照）；指导文档存「要达成什么」（意图）。互不替代，不共享字段。

### 4.4 「同一时间只推进一个目标」的落点与纪律冲突

- 若选项目级（固定路径 + 归档目录）：文件在＝目标在，换目标＝旧文件归档 + 写新文件。
  - **必须补显式可见面**：仓库既有定案是「隐式切换：重配置对象只被显式调用」（`single-truth-source-mindset.md` 设计陷阱）。「文件在即激活」如果不是隐式状态，就必须有一处**显式呈现**（状态条 / 会话头一行「当前目标：X」）让人与模型都能看见。没有呈现面，它就是隐式切换，违反既有纪律。
  - **git 处置必须回答**：内容可能含个人计划 ⇒ 默认 `.gitignore` 排除工作区侧目录（判断，非取证）；归档目录同理。若用户要版本化目标，则改为显式提交策略——这是产品口径，见 §7.1。
  - **多根**：宿主的项目根口径是「一个宿主 = 一个项目」——`hosts/memora-vscode/src/extension/extension.ts:316-324`；多根工作区下「项目级」实际只覆盖首根，其余根无法表达。
- 若选会话级：只保证「一个会话一个目标」，多会话可多目标；**且不是「改动小」**——`SessionMeta` 是导出接口且有冻结成员面守卫（`src/__tests__/publicMemberSurfaceGuard.test.ts:915-928`），加字段即红，须改守卫基线。
- 多个目标文档可以存在，但**当前**只能有一个指针；不允许两个激活。
- 换目标处置：旧文档移入归档 + 指针切换（一步确定性动作）；**不做**「暂停目标」字段（那是第二个状态机）。

## 5. 切片规则必须进文档 + 一条弱保证

- 若切片与验收锚点由主助手临场决定，「整体按文档判」就退化为模型直觉，文档只是参考材料。
- 文档最少两节：**切片表**（id / 范围 / 验收锚点 / 依赖顺序）与**整体锚点**（切片齐备 + 集成项）。
- **主助手不得改写切片验收锚点**；派发时原样传递该切片段。
- **弱保证（必须写进边界）**：锚点是同一个模型在 P2 收敛时写的，§5 的「不得改写」只有**约定**、没有执行机制——模型仍可能在编排时重写锚点。**单裁决者 ≠ 裁判独立**。这是有意接受的弱保证；要变成强保证，需要「锚点哈希锁定 + 派发时比对」这类新机制，本文不做。

## 6. UI 形态（**本节为判断，不是取证**）

- **语义与 UI 解耦是纪律**：先定「谁判、判什么、状态放哪」，形态后议。
- 技术上：现有 VS Code webview **能承载**最小可见面（会话列表、目标卡片、子会话在跑/成败），不是硬阻塞。
- 真正受限的是**注意力与屏幕**：一个主助手 + 多个子会话要同时呈现「待办、在跑、卡住、待决策」，插件边栏装不下，也不该装。
- 结论（判断）：**将来可能需要独立客户端**——不是「现在不能在插件里做」。
- 推进顺序：**先语义 → UI 只做最小可见面（能看见子会话在不在、成没成、当前目标是哪一个）→ 真实使用后再定形态**。形态未定时，禁止把「专属 UI」当立项前提。

## 7. 待拍口径（只剩一、二、四；三已决）

### 7.1 口径一：目标状态的作用域

| 选项 | 次生后果 |
| --- | --- |
| 会话级（`SessionMeta` 字段） | 与会话即单位一致、天然跨重启；但命中冻结成员面守卫需改基线，且只保证单会话单目标；fork 不继承该字段（`SessionMeta` 现有语义以身份/命名/角色名为主，`src/memory/sessionStore.ts:110-128`），子会话需另定继承规则 |
| 项目级（固定路径文件） | 全局只可能一个目标、跨会话共享、无需新字段；但需回答 git 处置、多根只覆盖首根（`extension.ts:316-324`）、写入冲突（用户手改 vs 分叉写入）、可发现性（不加显式呈现面即违反「隐式切换只被显式调用」） |

**成本披露（不预选）**：两条都有硬成本，没有「更省」的一条。选哪条取决于「目标该属于项目还是属于一次对话」，这是产品定义，不是工程优劣。

### 7.2 口径二：子会话可见性（**已升为 P1 前置**）

> **v1 不适用（2026-11-11）**：v1 不建会话实体、不落 Round，因此「子会话是否进列表」在 v1 路径上不存在。本节口径保留给将来的「独立子会话」形态；v1 的可见性 = 父工具结果里的 `[SUBAGENT:*]` 头部。下文的写确认硬耦合仍是 v1 必须 deny 写工具的原因。

| 选项 | 次生后果 |
| --- | --- |
| 进用户会话列表 | 实现最省（子会话就是普通会话）；但用户列表被派生会话淹没，「子」与「普通」不可区分；用户点进去只能看历史，看不到「进度」 |
| 隐藏子会话 | 需要新的存储归属与列表过滤规则（现有形态不存在）；且确认卡无人可见 → 见下 |
| **进列表但归组/折叠**（第三选项） | 保留可发现性又避免淹没；仍需一个「父子归属」字段与列表分组规则，成本介于两者之间 |

**与写确认的硬耦合（取证）**：确认队列只在**前台会话**推送（`confirmCoordinator.ts:206-210`），且计时只在首次上屏开始（`:262-264`）。**非前台请求永不上屏则永不计时，也就永不超时** ⇒ 若选「隐藏」且子会话还能写，父会**永久阻塞**。因此无论选哪个，v1 都必须让子 agent**没有写工具**（§7.4）。

### 7.3 口径四：既有「≥3 次真实案例」纪律

既有结论要求子 agent 累计 ≥3 次真实案例才重启评估，至今 0 次；用户本次把它抬成硬前置。**本文不裁决是否破。**

- **什么算一例**（本版补）：一次真实使用（**失败的一次也算**）；同一场景连续重复只算 1 例；纯测试/纯演示不算。
- **记在哪**（本版补）：台账观察区一条累计（`tasks/待完成任务.md`），逐例记「场景 / 切片数 / 回传长度 / 是否人工纠偏 / 成败」，**不新建文件、不凭印象**。

| 选项 | 次生后果 |
| --- | --- |
| 破（直接进 P1） | 快速拿到第一条真实链路；但切片粒度、回传形态、并发与成本模型全靠推演，无数据校准；旧文 §7/§8 的否决与缺陷仍需逐条重新裁决，不因「前置提升」自动失效 |
| 不破（累计 3 例再进） | L2 只能以最小实验形态存在（单工具、深度 1、无组队）；L3 推迟 |
| 挪门槛（3 例守在 L3 入口，L2 期间逐例记账） | L2 在零案例下事实获准；门禁移到更难执行的位置（要等真实使用才凑得满）；「一例」判据刚立、尚无实践检验 |

**它不是免检**：3 仍是硬门槛，只是守在 L3 入口而非 L2 入口；L2 期间必须逐例记账，不足 3 例不进 L3。

### 7.4 已决项：v1 子 agent「只读 + 禁提问」（附依据与代价）

- **依据一（工具面，2026-11-11 重写）**：**原说法已订正**——旧文写「只有 deny 能实现只读」，不准确。`src/agent/toolRunner.ts:189-201` 的 `toolReadonly = 'readonly'` 已能按 `readonly` 标记挡下写盘与命令；`capabilities` 白名单确实只能加特权、不能减常驻（`src/agent/toolExecutor.ts:558-564`、`:988-997`），但它不是唯一的收窄手段。deny 轴**不可替代**的理由只剩三条：
  1. **从模型可见面隐藏**：`toolReadonly` 只在执行时拒绝，工具仍留在 `list` 里，模型会看见并反复尝试，白烧 step；deny 在 `isToolExposed`（`toolExecutor.ts:988-997`）第一行就把工具从可见面移除。
  2. **`ask_user` 管不到**：它是 `readonly: true` 的常驻工具（`toolExecutor.ts:521`），只读闸按 `readonly` 标记放行；真正的挂起发生在 loop 层（`src/agent/loop.ts:1726` `willSuspendForAsk` → `:1897` `handleAskUser`），只能靠 deny 挡。
  3. **有副作用但不写盘的常驻工具**：`remember_intel` / `task_table_write` / `task_table_update` / `register_work`（`toolExecutor.ts:517-522`）不经过 `write_file`，只读闸的「写盘」语义也不覆盖它们；按「副作用」枚举比按「是否写盘」更可靠。
- **deny 的取法（按副作用枚举，不按工具名直觉）**：写盘 / 删文件 / 跑命令 / 杀命令 / 跑项目脚本 / 跑技能脚本 / `ask_user`，再加 `remember_intel` / `task_table_write` / `task_table_update` / `register_work`。工具名真源 = `DEFAULT_EXPOSED_TOOLS`（`toolExecutor.ts:503-537`）。**代价**：子 agent 不能贡献情报和任务项，得队长自己汇总——这是有意选择，不是遗漏。
- **实现位置（硬约束）**：deny 判定必须放在 `isToolExposed` 第一行、**在 `customTools.has(name)` 之前**（`toolExecutor.ts:990`）——否则 MCP / 自定义工具会先命中「恒暴露」分支，直接绕过 deny。
- **依据二（写确认）**：子 agent 非前台 ⇒ 确认卡不上屏 ⇒ 不计时 ⇒ 永不超时 ⇒ 父永久阻塞（`confirmCoordinator.ts:206-210`、`:262-264`）。
- **依据三（提问）**：`ask_user` 命中即 `paused`（`loop.ts:1726` / `:1897`），同步调用里没人替它答 ⇒ 父卡死。
- **结论**：v1 必须引入一条**工具拒绝名单**（deny 优先于常驻豁免集与自定义工具），清单见上方「deny 的取法」。这是**新增不变量**，必须独立立项与独立验收（§9、§10 P1），不能当 P1 的小功能顺带。
- **代价**：P1 的子 agent**只能看不能改**；「子 agent 负责改代码」要等到这条 deny 轴被接受并放开白名单子集之后。**这是有意的收窄，不是遗漏**。

## 8. 被推翻的判断（过程记录，不美化）

1. **子 agent 排在最后 → 改为 L2 硬前置**
   - 原来怎么想：先图片工具、再目标模式，子 agent 最后评估（依据旧文「半生长、不落地」）。
   - 为什么推翻：用户定义里 L3 的执行载体就是独立子会话；载体语义不存在时，L3 只能退化成单会话长任务。
2. **「你提前实现了会话层再生长一层」→ 其实只有实例面**
   - 原来怎么想：一会话一 Agent、独立执行，似乎就是子 agent。
   - 为什么推翻：实例隔离 ≠ 派生语义。父子、回传、配额、子轮归处四项全缺（§3.2/§3.3）。
3. **目标聚焦编排按「软档：文档常驻」理解 → 改为 L2 之上的编排层**
   - 原来怎么想：不加判定、只让文档常驻，靠模型自觉。
   - 为什么推翻：用户定义含「由助手操作独立子会话完成」——这是编排，不是常驻提示；软档解决不了「谁去干、干完怎么回流」。
4. **异步优先 → v1 同步**
   - 原来怎么想：Trae 形态是异步派发、随时查进度，理应照搬。
   - 为什么推翻：异步要求父持续在线等待，而现有 loop 没有等待态；父一收场，整体判定无人持有（§2.1）。
5. **（本版新增）「用能力白名单把子 agent 收窄成只读」→ 不成立**
   - 原来怎么想：按审查倾向，白名单一次性绕开写确认与提问两个洞。
   - 为什么推翻：白名单只能**加**特权工具，不能**减**常驻工具（`toolExecutor.ts:558-564`、`:963-980`）；常驻集已含写盘/命令/提问（`:502-533`）。只能新增 deny 轴。
6. **（2026-11-11 新增）独立子会话载体 → 父 turn 内同步递归**
   - 原来怎么想：P1 = 宿主派发端口 + 新建子会话 + 显式继承父角色包 + 落 Round。
   - 为什么推翻：v1 只需要「父 turn 内多一份隔离上下文」，不需要会话身份；建会话实体反而带出 Round 归属、列表可见性、确认队列三条副作用（§0.4）。角色包继承也随之失去理由——权限不再从角色包来。

## 9. 边界与新增不变量（集中一条边界）

**边界声明**：引入新不变式 = **必须单独立项**，本文只做路线与口径，不预支实现。

本路线触及的新增不变量（各自独立验收，不得塞进功能清单）：

1. **工具拒绝名单（deny）**：优先级 deny > 常驻豁免集 > 白名单；唯一判据点在 `isToolExposed` 层，三态语义不变（§7.4）。
2. **「当前目标」注入段**：新增 Prepare 段 + 独立字符预算 + fail-closed 同源（§4.1）。
3. **目标指针状态**：作用域一旦选项目级即新增「隐式状态」，必须配显式呈现面（§4.4）。
4. **派生深度 = 1**：**不需要新计数**——子 agent 装配时**不注入派发端口**，`delegate` 工具在子 agent 里根本不存在。这是端口层的结构性保证，不是新不变式，但必须有「孙派发被拒」用例。

### 13.1 概念（第三版）：不是新 agent，是把主会话装配成「只带会话管理工具」的主助手

先把结论钉死：**不新增一个「路由 agent」实体。路由 = 主会话本身，被宿主装配成只带会话管理工具的主助手；它不读文件、不跑命令，所有实际工作派给独立会话。**

两条边界要分清：

- **不是「每次 turn 之外再加一个路由大脑」**。那会多一次 LLM 调用、多一次上下文装配，且第二次调用的裁决者与第一次不是同一个。[目标模式生长探索-分层阶段化.md](./目标模式生长探索-分层阶段化.md) §4.1 已判过「在 turn 之上再包一层 turn」这个结构。
- **是「主助手这个会话的工具面被收窄到会话管理」**。它仍是同一个 `Agent` 类、同一套 loop；区别只在装配时给它的工具清单与系统提示（判断，落点见 §13.9）。

这个形态的四个直接后果（不是视情况而定）：

| 设计面 | 后果 |
| --- | --- |
| 协议 | 不需要「路由消息 / 路由会话」；主助手的工具是宿主注入的会话管理工具，子会话是宿主已有的普通会话 |
| 成本 | 路由本身便宜（一次工具调用），但**每件需要看工作区的事都要起一个完整会话**——这是硬价格，见 §13.4 |
| 可解释 | 一次派发 = 主助手过程流里的一行工具调用（目标会话 + 任务 + 回执）；不需要新的解释通道 |
| 可纠正 | 子会话可寻址 ⇒ 「停掉这个、换一个再派」在机制上可行（第一版说不可行，已订正） |

**与 §2.1 的关系（重要，登记为冲突）**：§2.1 的「一范围一裁决者」成立条件是「父在同一 turn 内等齐子结果」。路由形态是**异步**的：主助手派发后本轮可以结束，子会话各自 `done`，主助手在收到完成事件后的**新 turn** 里汇总。因此 §2.1 与 §2.4（父单 turn 预算天花板）**不再直接适用于路由形态**，P3 的分期前提需要另行裁决。本文只登记冲突，不替它调和。

### 13.2 两层结构与会话层落点

路由 agent 与会话内子 agent 是两层，不是一层：

| 层 | 谁在这里 | 管什么 | 实体 |
| --- | --- | --- | --- |
| **会话层** | 路由 agent = 主助手 | 创建会话、派活、查状态、读结果、停止、归档；不干活 | 宿主里一个个真实会话 |
| **会话内层** | 内核 loop + `delegate_task` | 一个会话自己干活时，用子 agent 隔离上下文 | 不是会话，也不需要是会话 |

因此「工具面只留会话管理」与「v1 子 agent 不是会话实体」**不冲突**：前者说的是会话层，后者说的是会话内层。路由 agent 与 `delegate_task` 没有直接联系，也不需要在两者之间做形态迁移。

**落点：会话层在宿主。**

- 宿主已经有：每会话一个 `Agent` 实例（`agentRegistry`）、会话存储、fork、rename、跨进程写锁、每个 Agent 独立的停止/暂停控制器。这些就是路由主助手需要的「会话实体」。
- 与手机方案共享同一批前置：per-session 视图状态、`handleInput` 定址、投影可复用、确认双投递（[手机方案](./方案-手机远程控制-20261110.md) §8 P0-1..P0-5）。**一套基础设施，两个消费者。**
- 内核零新增执行模型：主助手的每个工具都是宿主自定义工具，走现有 `customTools` 通道；子会话就是普通会话。

**会话层的硬边界与前置（必须写清）**：

1. **定位：一个项目、多个并行会话**。工作区根恒取 `workspaceFolders[0]`，无工作区兜底 `~/.memora`（`hosts/memora-vscode/src/extension/extension.ts:81-95`）。这是产品定位，不是缺陷：跨项目 = 多个窗口，每个窗口一个路由 agent。
2. **并发写策略：同一时刻只允许一个写会话**（硬约束，详见 §13.9）。读会话不限量；v1 不做 worktree、不做目录隔离、不做并行写。理由：多个会话同时写同一个项目，冲突在 git 层无法自动裁决；独立目录只是把冲突藏起来，不是消掉。
3. **后台子会话的确认卡不上屏**。确认队列只推前台会话（`confirmCoordinator.ts`），非前台永不上屏 ⇒ 永不计时 ⇒ 子会话第一次写盘就永久阻塞。**P0-4 是硬前置。**
4. **子会话完成 → 主助手自动汇总，没有现成触发**。内核跨 turn 自动续跑（Handoff）已于 2026-09-05 废弃。要么主助手在 turn 内轮询（白烧 step），要么宿主在子会话 settle 时投系统消息并起新 turn（可接后台任务回流 / Step 3 的 registry `kind='agent'` 设想）。**这是整个模式成立的前提，已提级为 H4（§13.9 第一位；防环/预算/去重见「H4 机制」）。**
5. **后台流不可见**。`post()` 对非当前会话的后台流一律丢弃，`_turnState` 只有单份。P0-1/P0-3 不做，主助手读不到子会话进展，手机也看不到。
6. **「工具面只留会话管理」在现有暴露模型里表达不出来**。`list` = 常驻 ∪ 白名单 ∪ 自定义 − deny，没有「只允许这些」的模式；`toolWhitelist=[]` 仍带常驻写工具。靠 deny 枚举全部内置工具是「点名必漏」。安全故事要成立，需要新增「封闭面」档位（§13.9 K1）。
7. **成本 N×**。每个子会话是完整 turn；主助手不带读文件工具 ⇒ 连「这个项目用什么框架」都要起会话。这是真实价格，不是缺陷，必须写进产品预期。

### 13.3 已定案（取证，不是本文判断）

这八条是后续设计的硬约束，不要再论证：

1. **内核/宿主边界**：会话、持久化、搜索均经注入端口，内核不含会话实现（`src/index.ts` 的 `ISessionStore` / `IRoundStore` / `ISessionViewLoader` 段）。“会话是实体”在 memora 里天然是**宿主概念**。
2. **宿主会话基建齐全**：每会话一个 `Agent` 实例（`hosts/memora-vscode/src/extension/host/agentRegistry.ts`）、会话存储、fork、rename、跨进程写锁、每个 Agent 独立的停止/暂停控制器（`src/agent/agent.ts` 的 `requestPause` / 中止入口）。
3. **v1 子 agent 在会话内层，不是会话实体**：父 turn 内同步递归，不落 Round、不进列表、无 id、不可单独读、不可单独停（[loop-design.md](./architecture/loop-design.md) §5.3）。这不影响路由——路由在会话层，不需要子 agent 变成会话。
4. **后台流不可见**：`post()` 对非当前会话的后台流一律丢弃，`_turnState` 只有单份（[手机方案](./方案-手机远程控制-20261110.md) §2 F3/F4）。
5. **一个宿主 = 一个项目**：工作区根恒取 `workspaceFolders[0]`，无工作区兜底 `~/.memora`（`hosts/memora-vscode/src/extension/extension.ts:81-95`）。
6. **暴露模型只能加/减，不能「只允许」**：`list` = 常驻 ∪ 白名单 ∪ 自定义 − deny（`src/agent/toolExecutor.ts` 的 `list` 语义）；`toolWhitelist=[]` 仍带常驻写工具。
7. **手机 MVP 边界**：无系统推送、无语音、只保证前台（[手机方案](./方案-手机远程控制-20261110.md) §9.2 / §11.1）。
8. **队伍不是执行体池**：`setRolePackTeams` 注释明写「组员仅会议参与，不用于日常」（`src/role-pack/rolePackManager.ts:446-451`）；`run_team_meeting` 是一次内嵌 `provider.chat()`，单轮、无工具循环（`src/agent/builtinTools.ts:559-580`）。原判断保留，不订正。

> **v1 的既有呈现仍有效**：`delegate_task` 的派发/回执行已经落在过程流里（`tool_start` 的 `args` + `tool_result.delegate`，`src/memory/roundStore.ts:289-318`；宿主渲染 `hosts/memora-vscode/src/webview/scripts/processFlowCells.ts:229-305`）。会话层方案的派发行是**宿主自定义工具**，不是 `delegate_task`，但「派发=过程流一行」这条形态可复用。

### 13.4 我建议这样定，待复核

#### 13.4.1 工具面清单（什么算「会话管理」）

判据：**只改「有哪些会话、会话在干什么」，不改工作区内容。**「读一个文件」不算——那是子会话的事（与用户判断一致）。

| 能力 | 算会话管理 | memora 对应 | 现状 |
| --- | --- | --- | --- |
| 创建会话 | 是 | `createSession`（chatPanel）/ `newSessionFromCommand` | 有，但由 webview 驱动；需可编程入口且不抢 PC 焦点 |
| 派发消息 | 是 | `handleInput` | 有，需 `sid` 定址（手机方案 P0-2） |
| 列会话 | 是 | 会话列表 + `refreshSessionActivity` | 有，需补状态与待审批数 |
| 读历史 | 是 | `RoundStore` + 投影 | 有数据，需可复用的 `project(sid)`（P0-3） |
| fork | 是 | `agent.forkSession()` | 有 |
| 改标题 | 是 | `sessionManager.renameSession` | 有 |
| 停/暂停单个会话 | 是 | 每 Agent 的 controller / `requestPause` | 有 |
| 回复用户 | 是 | 主助手自己的最终回答 | 有 |
| 定时任务 | 是（Trae 有） | 无用户级调度器（现有 `setInterval` 只服务 GC 与 UI 计时） | **缺口**；v1 不做，不假装有 |
| `ask_user` | 否 | 正文直接问，结束本轮即可 | 不需要 |
| 读文件 / 跑命令 / 搜索项目 | 否 | 子会话的工具面 | 由子会话承担 |
| 记忆召回 / 技能 / 任务表 | 否 | 子会话 | 主助手不碰 |

**代价必须写明**：主助手不能自己回答任何需要工作区事实的问题——它只能从当前对话与子会话标题里答，其余一律派发。这是这条硬约束的价格，不是缺陷。

#### 13.4.2 输入 / 输出

- **输入**：主助手自己的对话上下文 + **会话列表（工作记忆）**。不读设备信息、不读「模式」位。
- **输出**：具体工具调用 + 参数，不是抽象的「路由决策对象」。建议参数形状：
  - `create_session { title?, rolePack? } → { sid }`
  - `send_message { sid, text } → { accepted }`
  - `list_work_sessions { filter? } → [{ sid, title, state, pendingApprovals }]`
  - `read_session_history { sid, lastN } → [{ roundId, user, assistant, tools }]`
  - v1 不提供 `stop_session` / `pause_session` / `rename_session`（停止必须本地立刻生效；见 §13.11.1）
- **派发内容纪律**（Trae 的三条，落到参数）：传目标、上下文、约束；不重复子会话已有的内容；不在子会话里塞执行纪律（纪律归角色包 / 项目规则）。
- **先问一句**：直接用正文提问并结束本轮，不需要 `ask_user`——用户下一句就是答案。这样「只留会话管理」不被打破。

#### 13.4.3 可解释，以及「决策与呈现」的二分（订正第一条）

**决策与端无关**：同一句话、同样的上下文与会话列表状态，必须得到同一个路由结果。禁止在决策里读设备信息——否则同一句话在两端结果不同，不可解释、不可复现。

**呈现按端裁剪**：同一份结果，桌面给完整卡片，手机给一句话 + 可展开。裁剪**只作用在呈现层**，不回流契约、不写回存储、不产生第二份数据（投影函数参数化，见 §13.5）。

> **原说法已订正**：第一版写「不做设备感知路由」时把「决策」和「呈现」混成了一件，砍掉呈现适配会得到「手机上给你一段 800 字摘录」。现在按二分执行。

可解释的三级（保留前两级）：

| 级 | 内容 | 评价 |
| --- | --- | --- |
| L0（必做） | 主助手过程流里的派发行：目标会话 + 任务摘要 + 状态/回执 | 一次派发的最低可见面 |
| L1（建议） | 派发前一句 `narrate` | 复用现有通道；模型不一定说，说错比不说更糟，所以是补充不是契约 |
| L2（不建议） | 结构化「路由理由」字段 | 模型自证无校验 |

#### 13.4.4 可纠正（订正第二条）

- **这一次**：可纠正 = `create_session` + `send_message` 改派到新会话；旧会话由用户停（v1 主助手无 `stop_session`，见 §13.11.1）。机制上可行（第一版说「不做就地改派」是按 v1 同步递归写的，已订正为「机制可行、UI 暂不做」）。
- **以后的默认**：落项目规则 / 角色包 persona，不落 UI 本地状态。
- **不做**：过程流内下拉改派。不是机制缺失，是 UI 成本与收益不匹配；先让用户用一句话完成同样的事。

#### 13.4.5 落盘

- 主助手的每次派发 = 它自己 Round 里的一条 `tool_start` / `tool_result`（宿主自定义工具同样走过程流）。
- 子会话自己的 Round 落在自己的会话里，不复制进父会话。
- **父子关系**是宿主级元数据（内核 `SessionMeta` 有冻结成员面守卫，不加字段）：唯一落点是宿主侧一张 `parentSessionId` 关系表；UI / 手机都从这一份读，不各存一份。
- 不新增 `route_decision` 事件类型：派发已经是工具调用，双载没有收益。

### 13.5 宿主 UI

- **主助手就是一个普通会话**。它的过程流里，派发是一行自定义工具调用（目标会话 + 任务 + 状态）；点这一行应能跳到目标会话（建议，待复核）。
- **历史会话列表按父子归组**：主助手 → 子会话（可折叠）。这正是 [sub-session-visibility-and-goal-scope.md](./architecture/sub-session-visibility-and-goal-scope.md) §1 当年为「独立子会话」保留的口径，现在由会话层方案让它重新适用。
- **不新增路由面板 / 模式徽标**：策略开关若将来需要，挂输入区权限档位那一层；「这次派了谁」挂在过程流那一行。
- **补两个现状缺口**：① 后台会话流当前被丢弃（P0-1/P0-3），不补主助手看不到子会话进展；② 子会话的待审批数要进列表（复用 `refreshSessionActivity`，手机方案 P1-7）。
- **停止语义要写清**：停主助手 ≠ 停子会话（它们是独立会话）。UI 必须明确「停止主助手本轮」与「停止该子会话」，不能一个按钮两种含义。**不做级联停止**，两条理由：① 停止语义会变模糊——用户点停止，是想停当前这一个、停这一批、还是全停？按钮只有一个，级联停止把明确的「停当前」变成需要猜的「停到哪一层」；② 级联停止要求主助手在线才能执行，而「按住停止」必须是本地立刻生效的动作，不能依赖某个 agent 恰好还活着。

### 13.6 手机控制（结论 + 指针）

完整约束见 [手机方案 §14](./方案-手机远程控制-20261110.md)。三条结论：

1. **决策不分端，呈现分端**：手机拿结论 + 四态 + 可追问入口；摘录全文与执行耗时（诊断信息）可省。
2. **子会话可单独停**（订正）：会话层方案下每个子会话是独立 Agent，有独立控制器；v1 `delegate_task` 的「只能停整轮」不适用于路由形态。
3. **子会话的审批必须在手机上可见可答**：否则后台子会话永久阻塞（P0-4）。审批卡必须显示来源会话。

**共享前置与阶段对齐（2026-11-12 补）**：手机遥控与本文的路由主助手**共享同一批前置，只有三件**——① 会话定址（任意 sid 可寻址）；② 后台会话可投影；③ 审批可跨会话答复。三件不重复立项，两个消费者各取所需；`REMOTE-R0-1` 已落地其中的投影纯函数与按会话应答，即本文 §13.10 的 P1 基础设施。阶段排序改按 [手机方案 §9.4](./方案-手机远程控制-20261110.md) 的 S0→S5：**S0 多会话可见 → S1 会话可寻址 → S2 路由闭环**（与本文 §13.10 的 P1/P2 对应，S2 ≈ P2）。

两条纪律（同为 2026-11-12 口径订正）：
- **S1 不得对外宣称「路由可用」**：S1 只是「有工具、能派活」，**没有汇报闭环**——主助手能派不会说，用户不问就不知道子会话结束。路由对外只属于 S2。
- **`T3` 是客户端底座，不是传输方案**（[手机方案 §1.4](./方案-手机远程控制-20261110.md)）；传输三档 R/T/D 均未拍板。本文不因传输未定而阻塞 S0-S2 —— 这三阶段全在宿主内，不依赖任何传输。

### 13.7 只是选项，不建议现在做

| 选项 | 为什么现在不做 | 什么条件下才值得重开 |
| --- | --- | --- |
| 独立 router agent（每次 turn 外多一次调用） | 13.1：多一次调用、多一次装配，且两个裁决者 | 出现「必须用另一个模型做路由」的实证需求（路由模型与执行模型不同且成本更低） |

| 过程流下拉改派 | 机制已可行（停旧 + 建新 + 再派），UI 收益不抵成本 | 用户一天内多次用一句话改派，且明确嫌慢 |
| 结构化路由理由字段 | 模型自证，无校验 | 出现「用户需要审计为什么这么派」的合规需求 |

| 定时任务工具 | 调度器一进内核，就要处理「触发时无人到场」「失败谁重试」「多个定时任务撞同一工作区」三件新状态机，会把会话层复杂度提前拉进来；不是不急，是不该现在拉 | 用户提出「每天几点自动跑一次」的真实需求，且上面三件事有答案 |
| 每子会话独立工作目录 / 并行写 | 不做，而且不是做不到：同一项目并行写会在 git 层打架，独立目录只是把冲突藏起来；v1 串行写（§13.9 并发写策略） | 真出现并行写需求时，按 worktree 立项，不是加配置 |
| 主助手带只读工作区工具 | 与「只留会话管理」的硬约束冲突 | 成本 N× 被实测证明不可接受，且用户愿意放宽约束 |

### 13.8 三条判据收口

**SSOT**：

- **会话关系一份**：宿主侧 `parentSessionId` 表，UI / 手机 / 主助手都从它读。
- **会话状态一份**：`refreshSessionActivity` / 投影（P0-3），主助手与手机共用同一投影函数。
- **决策记录一份**：主助手自己 Round 里的 `tool_start` / `tool_result`。
- **主助手不维护任务表**：会话列表就是它的工作记忆（用户第 1 点）。多一份 plan 就是第二真相源。
- 禁止新增 `route_decision` 字段 / 表 / 事件。

**自然生长**：

- 挂「目标模式」？不。目标是跨 turn 自动推进（未实现），会话层方案是异步会话管理；两者可以叠，但不是一回事。
- 挂「角色包」？不。换装 ≠ 分派；自动换装还会破坏用户显式选择契约。
- 挂「队伍」？不（现在）。注释已钉死「组员仅会议参与」。
- 挂「过程流」？是。派发就是工具调用一行，`delegate_task` 已经证明这个形态成立。
- 挂「手机桥」？是。同一份会话 API / 投影，两个消费者（人与主助手）。

**不带伤（会做出「一半」的做法，逐条排）**：

| 半截形态 | 为什么是半截 | 本文处置 |
| --- | --- | --- |
| 有会话工具、读不到历史 | 主助手只能瞎派，无法判断进展 | 读历史是 P2 的硬入口，不满足不宣称「路由可用」 |
| 能建会话、不能单独停 | 跑飞的任务只能杀整轮 | 每会话控制器已有；必须接到工具上 |
| 后台子会话审批不上屏 | 第一次写盘就永久阻塞 | P0-4 硬前置 |
| 派发没有完成触发 | 主助手永远不汇报，用户以为它忘了 | H4 先定，再宣称「自动汇总」 |
| 用 deny 枚举实现「只留会话管理」 | 新增内置工具会静默泄漏进主助手 | K1 封闭面档位；枚举只作临时兜底 |
| 手机只给 800 字摘录 | 屏幕上不可用 | 呈现分端：结论 + 四态 + 可追问 |
| 手机只给一句话、不能展开 | 用户无法核验，只能盲信 | 保留可展开入口 |
| 允许多个写会话并行 | 同一文件互相覆盖，冲突在 git 层无法裁决 | 串行写（§13.9 并发写策略） |
| 把「跨项目并行」当默认能力 | 一个宿主 = 一个项目；跨项目是多窗口 | 定位为「一个项目、多个并行会话」 |

### 13.9 会话层方案的最小改动集

**内核（只一项）**

- **K1 封闭工具面档位**（allow-only / profile）：`list` 从「常驻 ∪ 白名单 ∪ 自定义 − deny」增加一条「只允许显式清单」的装配档。理由：主助手的安全故事是「它只能管会话」，而现有模型只能加/减；`toolWhitelist=[]` 仍带常驻写工具，deny 枚举必漏。**这是新增不变量，必须单独立项、独立验收**（含公开面登记）。
- 其余零改动：会话实体在宿主，内核不需要认识父子关系；子会话就是普通 `Agent`。

**宿主（七项，按依赖排序）**

| # | 改动 | 说明 |
| --- | --- | --- |
| **H4（提级，第一位）** | **子会话 settle → 主助手新 turn** | 整个路由模式成立的前提；触发源、防环、预算、去重见下方「H4 机制（v1 定稿）」 |
| H1 | 会话管理 API | 可编程、`sid` 定址、不抢 PC 焦点、不走 draft 分支；**手机与主助手共用** |
| — | P0-1..P0-5 | 手机方案 §8 的五条硬前置（per-session 状态 / handleInput 定址 / 投影 / 审批双投递 / 附件解耦） |
| H2 | 主助手装配 | 会话工具 + 封闭面（K1）+ 不注册 MCP / 自定义写工具；角色包只给 persona |
| H3 | 父子关系表 + 列表归组 | 宿主级 `{ childSid, parentSid, parentRequestId, dispatchedRoundId }`；历史列表可折叠分组；H4 的分组与去重都读这一份 |
| H5 | 停止语义分档 | 「停主助手本轮」≠「停该子会话」；两个入口，两个文案 |
| H6 | 并发与成本上限 + **并发写策略** | 同一宿主窗口共享工作区；**同一时刻只允许一个写会话**，读会话不限量；v1 不做 worktree / 目录隔离 / 并行写。深度 1 结构性：只有主助手装配会话工具。 |
| H7 | 派发行渲染 + 跳转 | 过程流一行；点击跳到目标会话（可选） |

**H4 机制（v1 定稿）**

1. **触发源：宿主监听子会话的 turn 终态，不靠模型自报。** 会话从 running 落到 settled / failed / interrupted 时，宿主生成完成事件；会话列表用的 `refreshSessionActivity` 读同一份状态，不另造一套。派发时在 H3 关系表里写入 `parentRequestId`，完成事件带着它回来。

2. **环怎么断：汇报轮禁止派发。** 完成事件触发的主助手 turn 打标记 `origin = 'child-settled'`；该轮里 `create_session` / `send_message` 直接返回错误「汇报轮不可派发」。代价：汇报轮不能自动重派、不能自动追问；子会话失败时主助手只能汇报，用户再说一句才重派。**被否方案**：① 只靠提示词「汇报轮不要派发」——模型可能不听，环就断不了；② 「只有用户发起的 turn 才允许派发」——太宽，把「用户说完后同一 turn 连派」也禁了，等于砍掉主流程。

3. **批量与预算：一次用户请求最多 1 次汇报轮，且只在「该 `parentRequestId` 名下没有在跑的子会话」时触发。** 3 个子会话完成不会出 3 条碎片汇报；代价是最慢的那个会拖住整批，卡死的子会话会一直拖（会话列表仍显示 running，用户能看见并手动停）。**超了怎么办：不静默截断**——超出的完成事件只更新列表状态和未读标记，不再起 turn；用户下次说话时，宿主把这期间完成的会话作为一条系统消息注入（复用 `appendSystem`），列表保留未读。**被否方案**：每个完成事件各起一个 turn——N 个子会话就是 N 条碎片汇报，且每条都可能再派，环的概率和噪音都翻倍。

4. **去重：`(sessionId, roundId)` 内存集合，一个回合的终态只通知一次。** 宿主重启会杀掉全部子会话（它们就在扩展宿主进程里），不会留下「人死了事件还在」的情况，所以 v1 不持久化去重集合；内存集合按会话保留最近 N 条，防无限增长。**被否方案**：① 只用 `sessionId`——一个会话可以完成多轮，会吞掉合法的第二次完成；② 事件自带全局 id——当前链路没有稳定的跨重启事件 id，为一个宿主生命周期内的问题加协议字段不划算。

**并发写策略（硬约束）**：同一宿主窗口内多会话共享工作区；同一时刻只允许**一个写会话**在跑，读会话不限量。v1 不做 worktree、不做目录隔离、不做并行写。为什么这样切：多个会话同时写同一个项目，冲突在 git 层无法自动裁决；独立目录只是把冲突藏起来，不是消掉。先串行是「不带伤」的选择；等真有并行写需求，再谈 worktree 隔离——那时是立项，不是配置。

**现在就能做**：H1 + P0 + H3 + H7（H1/P0 同时解锁手机 M1，不白做）。
**必须先定才能承诺**：H4（自动汇总）+ K1（安全故事）。没有 H4，「我干完会跟你说」就是假的。
**必须等新形态**：系统级推送；并行写（worktree）作为独立立项。

### 13.10 分期（边界与「为什么这样切不带伤」）

| 期 | 内容 | 独立可验收 | 明确不做 |
| --- | --- | --- | --- |
| **P1 基础设施** | P0-1..P0-5 + H1 会话 API | 手机能看到**后台**会话；主助手能列会话、按 `sid` 发一句 | 任何主助手工具面、任何父子归组 |
| **P2 路由闭环** | K1 + H2/H3/H5 + **H4** | 一句话 → 建会话 → 派任务 → 子会话完成 → 主助手新 turn 自动汇总 | 手机端回执、系统推送 |
| **P3 手机与体验** | 手机 `attention` + H7 跳转 + 归组 | 手机收到一条结论；点派发行能跳到子会话 | 多级父子、级联停止 |
| **P4 调优** | H6 并发/成本 + 串行写压测 | 3 个读会话并行 + 1 个写会话不打架；成本可观测 | worktree、定时任务 |

**为什么这样切不带伤**：P1 与手机共享，不做白工；P2 把 H4 纳入闭环——「主助手会汇报」不再依赖用户追问，这是路由模式和「一个能派活的聊天框」的分界线；P3 才做手机回执；P4 才压并发。每一期都有可演示的闭环，不靠「以后会好」。

### 13.11 路由 agent v1 实现规格（未实现，2026-11-12）

> **同批三件，缺一不成立**：① 会话管理工具面（4 个）；② 落定汇报 H4；③ 汇报轮禁止再派发。咬合点是一条数据链：工具写关系表 → 落定事件读关系表 → 汇报轮带 `origin='child-settled'` 被闸①读。拆开做会得到三种废形态：有工具无汇报＝只能派不会说；有汇报无闸＝无限套娃；有闸无工具＝死代码。
> **状态**：规格，未实现。总开关 `memora.routingAgent.enabled` 默认 `false`。

#### 13.11.1 工具集：四个，签名与边界

**边界判据（结构性，不靠提示词）**：四个工具的参数类型都是封闭对象，没有 `path` / `cwd` / `glob` / `command` 字段；handler 只调用宿主会话存储与投影（`RoundStore` / 投影 / `refreshSessionActivity`），不碰工作区文件系统；未知参数键直接拒绝（`E_ARGS`）。因此「读会话历史」读到的是**子会话写进回答里的内容**，不是文件系统——路由 agent 没有读项目的权力。

```ts
// 1) 建会话（mode='review' 时宿主装配只读工具：Read/Grep/Glob + submit_review）
create_session(input: { title?: string; rolePack?: string; mode?: 'work' | 'review' }): Promise<
  | { ok: true; sid: string }
  | { ok: false; code: 'E_DENIED' | 'E_LIMIT' | 'E_HOST' | 'E_ARGS'; message: string }
>

// 2) 派发（子会话已在跑时拒绝，不排队）
send_to_session(input: { sid: string; text: string }): Promise<
  | { ok: true; accepted: true }
  | { ok: false; code: 'E_DENIED' | 'E_NOT_FOUND' | 'E_BUSY' | 'E_LIMIT'; message: string }
>

// 3) 读状态 / 读历史
read_session(input: { sid: string; mode: 'status' | 'history'; lastN?: number }): Promise<
  | { ok: true; status: SessionStatus }
  | { ok: true; rounds: RoundDigest[] }
  | { ok: false; code: 'E_NOT_FOUND' | 'E_ARGS'; message: string }
>

// 4) 列会话（默认只列自己名下的）
list_work_sessions(input?: { scope?: 'children' | 'all' }): Promise<
  | { ok: true; workspaceRoot: string; sessions: SessionBrief[] }
  | { ok: false; code: 'E_ARGS'; message: string }
>
```

- `SessionStatus = { state: 'running' | 'waiting' | 'settled' | 'failed' | 'interrupted'; roundId?: string; pendingApprovals: number }`
- `RoundDigest = { roundId: string; userText: string; assistantExcerpt: string; toolNames: string[]; status: string }`
- `SessionBrief = { sid: string; title: string; state: SessionStatus['state']; pendingApprovals: number; parentSid?: string }`
- `assistantExcerpt` ≤ 800 字（沿用 `DelegateTaskReceipt.excerpt` 口径）；`lastN` 默认 3、上限 20，超限 `E_ARGS`；`scope` 默认 `'children'`，`'all'` 只返回元数据，不返回别人历史。
- 业务失败一律返回 `{ ok: false }`，不 throw；throw 只留给程序错误。每个 `parentRequestId` 最多 4 个在册子会话（`E_LIMIT`）。

**明确不提供（v1）**：`stop_session` / `pause_session` / `rename_session`（列表页已有停/改名入口）、`list_projects`、`copy_history`、`schedule_task`、`set_display_name`、文件/命令、工具检索、委派执行。逐项判据见 §13.11.2 的对照表。**v1 无 `stop_session`；可纠正 = 建新 + 用户停旧；理由 = 停止必须本地立刻生效。** 主助手发现派错了，只能新建会话改派，并明确告诉用户「旧的那个还在跑，要你去停」；它不能自己停——停止语义（停这一个 / 这一批 / 全停）会因主助手参与而变模糊，而且它可能把正在出结果的会话停掉，与 §13.5「不做级联停止」的两条理由同源。

#### 13.11.2 工具面判定与闸①：约束在工具上，不在提示词里

**样本对照（只用于发现遗漏，不作为规范来源）**：

| 真实样本里的能力 | 规格判断 | 判据 |
| --- | --- | --- |
| 可见输出 | **不新增工具**；助手正文就是唯一出口 | 一个出口，避免两套消息通道 |
| 建会话 | 提供 `create_session` | 路由必需 |
| 发消息 | 提供 `send_to_session` | 路由必需 |
| 读某会话可见历史 | 提供 `read_session(mode:'history')` | 判断进展必需 |
| 列会话与状态 | 提供 `list_work_sessions` | 工作记忆必需 |
| 列项目 | **不加工具**；`list_work_sessions` 返回 `workspaceRoot` | memora 一个宿主窗口 = 一个工作区（§13.2 第 1 条）；跨项目 = 多窗口，各有一个路由。`list_projects` 只会返回一个永远只有一项的列表 |
| 复制历史 | **不提供** | 派活不需要 fork 语义；复制是列表页的 UI 入口 |
| 改标题 | **不提供** | 建会话时 `title` 可选、宿主自动命名；用户可在列表改 |
| 定时任务 | **v2** | 见 §13.11.10 三条理由 |
| 改自己的显示名 | **不提供** | 会话层设置，不是路由决策 |
| 文件 / 命令（Read/Write/Edit/Shell） | **不提供** | 结构性边界：有工具就一定会被模型尝试，提示词拦不住 |
| 工具检索 / 委派执行 | **不提供** | 工具检索会绕过封闭面，等于把文件/命令重新放回手里；委派执行是执行能力，归子会话 |
| 读技能 / 记忆召回 | **不提供** | 执行能力，归子会话；给路由就等于给它一条读项目的侧门 |
| 任务表 | **不提供** | 待办靠会话列表与关系表承载（§13.11.10），不新造实体 |
| 停止会话 / 取消别人任务 | **不提供** | 停止必须本地立刻生效（§13.11.1） |

**硬约束（判据）**：两套集合各自独立断言，不共用常量、不互相推导：

```ts
const ROUTER_TOOLS = ['create_session', 'send_to_session', 'read_session', 'list_work_sessions'] as const;
const REVIEW_TOOLS_V1 = ['Read', 'Grep', 'Glob', 'submit_review'] as const;
const REVIEW_TOOLS_V15 = ['Read', 'Grep', 'Glob', 'submit_review', 'run_check'] as const;

expect(effectiveToolNames(masterAgent).sort()).toEqual([...ROUTER_TOOLS].sort());
expect(effectiveToolNames(reviewAgent).sort()).toEqual(
  [...(RUN_CHECK_ENABLED ? REVIEW_TOOLS_V15 : REVIEW_TOOLS_V1)].sort(),
);
```

- 主助手 4 个；review v1 4 个、v1.5 5 个。`run_check` 只在 review 集合里，主助手集合出现即红（等号已覆盖）。
- 多一个红，少一个也红；`not.toContain('Shell')` 只是补充负例，主判据是等号。
- review 也走**封闭面装配**：`REVIEW_TOOLS` 是它的全部生效工具，不是「在默认工具上再减几个」。

**为什么不是提示词**：提示词能被忽略；工具不在注册表里，模型连调用入口都没有。前者是纪律，后者是能力边界。

**「enabled 只能在全绿后置 true」由谁执行**：

1. **运行时启动检查（权威）**：宿主 `activate()` 读 `memora.routingAgent.enabled`；为 `true` 时先算主助手与 review 的 `effectiveToolNames`，任一集合不等于声明 → **拒绝启用**（记 error 日志、按 false 处理、给一次用户可见警告），fail closed。
2. **宿主单测（回归）**：上述两条 `toEqual` 放进宿主单测，防止改装配后绕过启动检查。
3. **构建期不做**：工具面是运行时装配结果，构建期拿不到 `effectiveToolNames`；硬塞一个构建期 grep 只会变成第二套近似判据。

所以这条约束的执行者是**运行时启动检查**，单测是第二道；文档只是规格，不是执行者。

**与「先做 H4、不先收紧工具面」的消解**：H4 代码可以先落，但开关置 `true` 必须过上面的启动检查，否则保持休眠。先落代码 ≠ 先开功能。若封闭面档位（K1）未实现，等号检查必然失败——这正是**开功能**的闸，不是 H4 代码的闸。

**闸①落点**：

- **唯一入口**：`createSessionTools({ masterSid, runtime, relations, limits })` 返回四个 handler；每个 handler 第一行调 `assertCanDispatch(masterSid, toolName)`。`create_session` / `send_to_session` 判；`read_session` / `list_work_sessions` 放行。
- **判据**：`runtimeFor(masterSid).origin === 'child-settled'` → 返回 `E_DENIED`。
- **字段**：`SessionRuntimeState.origin?: 'user' | 'child-settled'`（`sessionRuntime.ts:41-50`）。缺省视同 `'user'`。
- **谁写**：`handleInput` 开用户轮时置 `'user'`；`H4Coordinator.triggerReport()` 在 `runFlow` 前置 `'child-settled'`，finally 清回 `'user'`。
- **防绕过**（回答「明天有人加一个新派发工具，会不会绕过」）：
  1. 主助手的 customTools **只在一个装配点注册**，且来自这个工厂；
  2. 工厂给每个 handler 包 guard；新工具不走工厂就拿不到会话 API 句柄；
  3. 两条单测：① 主助手注册的自定义工具名集合 **等于** 工厂声明集合；② 最终生效工具名集合 **等于** `ROUTER_TOOLS`。绕过工厂或漏关内置工具，都会红。
- 只靠提示词被否：模型可能不听，环断不了。

#### 13.11.3 关系表：键、写入、删除、重启

| 项 | 规则 |
| --- | --- |
| 键 | `childSid`（v1 深度 1，一个子会话只有一个父） |
| 写入 | `create_session` 成功建会话后；`send_to_session` 仅当该 `sid` 尚无表项（首次派发） |
| 字段 | `{ childSid, parentSid, parentRequestId, dispatchedRoundId }`；v1 后两者都取主助手当前 `roundId` |
| 读取 | H4 `onFlowTerminal` 按 `childSid` 查；闸②按 `parentRequestId` 聚合 |
| 删除 | 汇报轮结束后删该 `parentRequestId` 全部表项；子会话删除/归档时删单条；主会话删除时删其全部子项 |
| 上限 | 每 `parentRequestId` ≤ 4 条 |
| 重启 | **纯内存、不持久化**。子会话就在扩展宿主进程里，重启即死，表随进程清空，不存在「等一个不会回来的结果」。代价：重启后关系丢失，原父子变成普通会话（v1 接受） |

**「会不会永远等」**：不会等 Promise——H4 只在落定事件里反应，表重启即空。真正会「永远等」的是**子会话卡在 running**：表项还在、落定事件不来、汇报不触发。v1 不设会话超时，靠会话列表的 running 让用户手动停（见 §13.11.7 第 3 条）。

#### 13.11.4 失败 / 中断也汇报（采纳补落定点）

结论：**补**。理由：用户关窗后失败没人报，正是这个模式最该起作用的时候；成本是三个分支各一处，且都在现有 catch / finally 内。

- 新增 `onFlowTerminal({ sessionId, roundId, terminal: 'done' | 'failed' | 'interrupted', byUser?: boolean })`，落点：
  1. 正常分支（`chatPanel.ts:3518-3527`）→ `done`；
  2. `aborted` 分支（`chatPanel.ts:3510-3513`）→ `interrupted`；
  3. `consumeFlow` 的 catch（`chatPanel.ts:3408-3412`）与 `runFlow` 的同步 throw（`chatPanel.ts:2932-2939`）→ `failed`；`roundId` 为空则跳过。
- `pausedOnPurpose` 分支（`chatPanel.ts:3514-3517`）**不算落定**：暂停可恢复，不是终态。
- 幂等：每个 flow 一个本地 `terminalEmitted` 标记，配合 coordinator 的 `notifiedRounds` 去重；catch 与 finally 双触发只算一次。
- 汇报内容：terminal + 摘录 + 待审批数。失败时主助手**不得自动重派**（闸①），只能汇报并问用户。
- 用户手动停子会话 → `interrupted`，尽量带 `byUser`。该标记今天不存在；**推断**需要在 `handleStop` 置一个 runtime 标记（`stoppedByUser?: boolean`），否则只能报 terminal、不区分是谁停的。

#### 13.11.7 风险清单（六条保留 + 两条新增）

| # | 风险 | 判据 | 处置 |
| --- | --- | --- | --- |
| 1 | 无限套娃 | 工具派发 → 落定 → 汇报轮 → 再派发 | 闸① 结构性拦；H4 单独上线且无会话工具时不会发生 |

| 4 | 宿主重启丢去重集合 | 子会话同进程，重启即死 | 无新事件，丢集合无害；正在汇报的那轮丢，用户再问 |

| 8 | **用户手动停子会话** | `aborted` 分支 | 算落定，报 `interrupted`，不当失败；无 `roundId` 则跳过；不阻断同批其它子会话的 quiescence 判定 |

#### 13.11.8 内核 origin 的公开面与基线

- `chat(input, signal?, attachments?, opts?: { origin?: 'user' | 'system' })`：可选第 4 参，旧调用不变。
- `Round.origin?: 'user' | 'system'`：可选字段，老 round 缺省 `'user'`，无迁移。
- **两个独立命名类型，不是同一个字段的两种用途**：`type SessionRuntimeOrigin = 'user' | 'child-settled'`（只判闸①，落在 `SessionRuntimeState.origin`）；`type RoundOrigin = 'user' | 'system'`（只判历史与渲染，落在 `Round.origin`）。两者禁止复用同一个类型别名。汇报轮同时置：runtime = `child-settled`，kernel = `system`；渲染层永远看不到 `'child-settled'`。
- 透传链路：`chat` → flow seed → round 创建点。**具体创建函数未核实**（推断为 `RoundStore` 的建轮入口）；落地前先定位这个单点，避免在多条建轮路径各写一次。
- 公开面守卫：`src/__tests__/publicMemberSurfaceGuard.test.ts` 的冻结成员表；登记 `chat` 的新可选参数与 `Round.origin`。基线更新按守卫失败提示操作（**具体命令名未核实**）。
- 宿主渲染：`Round.origin === 'system'` 不渲染用户气泡，渲染为系统行；否则历史里会出现一条假用户消息，正是裁决 2 禁止的。

#### 13.11.9 校验结构：写盘方不得自证

- **判据**：任何「完成 / 已改好 / 可宣称不带伤」的结论只有两种状态：`relayed`（仅转述）与 `verified`（已复核）。默认 `relayed`；升级 `verified` 的唯一路径是一条 `mode='review'` 的子会话给出 `pass`。
- **落点**：`H4Coordinator` 的关系表条目加 `claim: { state: 'relayed' } | { state: 'verified'; reviewSid: string; reviewRoundId: string }`。这是宿主状态，不进模型上下文，也不由路由 agent 写。
- **谁置位**：
  - 子会话终态到达时，coordinator 先置 `relayed`；
  - 复核会话调用 `submit_review({ targetSid, targetRoundId, verdict, evidence, anchors })`，且 `verdict='pass'`、`targetRoundId` 等于被复核子会话已落定的 `roundId`、`anchors` 非空且可核（§13.11.11 的四种锚点）时，coordinator 置 `verified`；
  - 目标不匹配、复核会话不是 `mode='review'`、或 `verdict='fail'` → 保持/降回 `relayed`。
- **工具**：`submit_review` 只装配在 `mode='review'` 的子会话上，不在 `ROUTER_TOOLS` 里；工作子会话也没有它。所以写盘方无法自证，路由 agent 也无法替它盖章。
- **复核会话的工具面（v1 / v1.5 两档）**：
  - v1：`Read` / `Grep` / `Glob` + `submit_review`（4 个，封闭面装配）；没有 `Write` / `Edit` / `Shell` / `run_check`。**限制**：跑不了测试，需要「跑测试才算验证」的声明只能是 `relayed`；「不带伤」在 v1 无法由路由独立确认。
  - v1.5：加 `run_check`（§13.11.13），5 个；仍无 `Write` / `Edit` / `Shell`。
  - 两档各自有独立的等号断言（§13.11.2），不共用一套集合。
- **汇报措辞（硬要求）**：
  - `relayed`：「X 声称已完成，**我没有复核（仅转述）**。原文：…。要我派一条只读线复核吗？」
  - `verified`：「X 已完成，并经只读复核（复核会话 Y）：…。」
  - `relayed` 时禁用词：`已改好`、`已验证`、`不带伤`、`确认无误`。
- **宿主注入**：汇报轮由宿主先注入一行系统状态「已验证 N / 仅转述 M」，模型正文不能改变这一行；模型正文必须按上面两种措辞写。
- **为什么不是软建议**：`verified` 不是模型自报的字符串，而是 coordinator 根据「复核会话 + 目标 roundId + pass」三要素算出来的状态；模型说自己验证过不算。

#### 13.11.10 秘书职责 v1：只做会话层

- **v1 做**：派活、收结果、记待办、按纪律推进（不重复已有内容、不塞执行纪律）。
- **待办承载**：不新造任务表。待办 = 关系表里未结算的 `parentRequestId` + `list_work_sessions` 里 `running` / `waiting` 的会话。会话列表就是工作记忆。
  - 没有会话承载的待办（例如「以后再问用户」）在 v1 没有持久载体：要么建一个会话，要么在正文里说、下一轮靠上下文。重启后关系表清空，但会话列表持久，路由可用 `list_work_sessions` 重新发现 running 会话——这是恢复路径。
  - 为什么不需要新实体：待办要跨重启、要独立生命周期、要多人可见，才需要任务表；v1 的待办都挂在会话上，会话已有生命周期，再加一张表就是第二套真相。
- **cron 明确 v2**，三条理由：
  1. **到点无人到场**：确认、审批、失败处置都没有人，需要一套「无人值守策略」，这是新状态机；
  2. **失败谁重试**：重试次数、退避、终止条件、谁收尸，都要定；
  3. **多个定时任务撞同一工作区**：与写串行闸冲突，需要排队或租约。
  三条都不是加一个 `cron` 字段能解决的，所以 v1 不做；用户提出真实需求且三条有答案时再立项。

**一个命名冲突**：内核已有 `list_sessions`（历史路标），路由工具叫 `list_work_sessions`，避免同名两义。

**二、三条外化去处**

| 类别 | 谁写 | 写在哪 | 谁读 |
| --- | --- | --- | --- |
| 待办 | 承接该任务的子会话（或用户） | `tasks/待完成任务.md` | 用户；下一次路由经子会话/复核转述，不直接读文件 |
| 契约 | 改契约的子会话（需用户批准） | `docs/` 对应文档 | 未来的子会话、人 |
| 证据 | 执行子会话写回执；复核子会话确认 | commit hash / `file:line` / log path / `sid:roundId` | 复核会话、用户；路由只携带锚点字符串 |

- 路由自己**不写**这三处（没有写工具）；它只在汇报里点名「已外化到哪」。
- 这与 §13.11.10 不冲突：会话列表是路由的工作记忆，台账是待办的持久化副本；写台账的是承接任务的子会话，不是路由。
- 没有会话承载的待办：建会话，或只在正文说，不落台账（v1）。

**三、别让记忆当证据**

- `verified` 的必要条件 = **可复核锚点**（`commit:<sha>` / `file:<path>:<line>` / `log:<path>#<marker>` / `round:<sid>:<roundId>`）+ `mode='review'` 会话确认；缺任一 → `relayed`。
- 锚点只是必要条件：有锚点、没复核，仍是转述。
- 带不出锚点的结论，汇报强制降级：「X 声称…（仅转述，无可复核锚点）」。
- 与 §13.11.9 同一套：`verified` 只由 coordinator 在「review pass + 锚点匹配」时置位。

**四、读不到文件 vs 要知道进度**

- **最终判断：路由 agent 不能读任何项目文件，一份也不行。**
- 进度来自三处：`read_session(mode:'status')` 的 live 状态；`read_session(mode:'history')` 的子会话可见历史（含它自己写的结论/锚点）；H4 的 terminal 事件。
- 要看项目内容 → 派 `mode='review'` 的只读子会话去看，让它带回结论 + 锚点；路由只读会话。
- 为什么不给「几份授权文件」：任何文件白名单都会把边界从「工具面事实」降成「配置/提示词」；`read_file(path)` 的路径参数就是全项目，且文件含密钥/隐私。复核会话是可控替代：它有读工具、没有写/命令，产出必须带锚点。

**五、压缩落在哪一层**

- `compress_context` 解决**当前轮溢出**（收尾即弃），不解决跨轮。
- 跨轮由 `roundSummaryGenerator` 接管（每轮 1-3 句、≤500 字，进记忆库；细节用 `search_memories` / `trace_summary`）。
- 路由的过程天然不在它上下文里——过程在子会话历史里，路由只持有派发与汇报。所以**不新增压缩器、不新增压缩时机**。
- 裁决与待办的保留：靠汇报轮输出格式（先结论、再待办、再锚点）+ 轮摘要 1-3 句。
- 唯一要补的是 live 工作列表（`list_work_sessions`），不是压缩。

#### 13.11.12 发现派错、旧会话还在烧 token 时说什么

- **前置事实**：路由 agent 没有 `stop_session`，也没有取消别人任务的能力；旧会话会继续跑、继续消耗。
- **必须说清六件事**（模板级要求，不要求逐字）：
  1. 承认派错；
  2. 点名旧会话（标题 + sid 短号）和当前状态；
  3. 明说「它还在跑，会继续消耗 token，我没有停它的权限」；
  4. 给出用户动作：「请到会话列表停掉它」；
  5. 说明替代：已经建了哪个新会话、派了什么；
  6. 给可选下一步：「要不要我先把旧会话的进展读给你，再决定停不停」。
- **禁说**：「已停止」「已取消」「不会再消耗」——它没有这个能力。
- **示例（要求级，不是文案定稿）**：「我派错了：旧会话『改鉴权』（sid a1b2）还在跑，会继续消耗 token，我没有停它的权限。请到会话列表停掉它；我已建了『鉴权-只读复核』（sid c3d4）重新派。要不要我先读一下旧会话的进展？」

#### 13.11.13 `run_check`：受限验证器（v1.5，v1 不提供）

**判断：v1.5，不进 v1。** 按「一个 handler + 一张常量表 + 一处注册」的阈值逐项看，四项都超：

1. **进程生命周期**：spawn、超时、杀进程树、孤儿回收、输出截断——这不是一个 handler，是一层 runner；
2. **副作用收口**：typecheck/lint 会写 `.tsbuildinfo`/`.eslintcache`，还要写日志；必须逐项声明并限制，不能靠「它只读」；
3. **嵌套闸**：`gate:fast` 在 review 会话里跑，会和宿主提交钩子的 gate 抢同一工作区与锁，需要检测外层 gate 并 fail fast，这又是新状态；
4. **白名单维护**：`test:<已登记路径>` 要随测试文件增删同步，漏登记就是假验证。

四项里任何一项单独都能塞进 v1，四项一起就是完整 runner。按你的判据降 v1.5。**v1 明写**：测试类结论只能 `relayed`，「不带伤」这类判断在 v1 无法由路由 agent 独立确认。

**工具形状**

```ts
// 只在 mode='review' 的会话装配；不是 Shell 的受限模式，名字和参数都要让人一眼看出区别
run_check(input: { check: ReviewCheckId }): Promise<
  | { ok: true; check: ReviewCheckId; verdict: 'pass' | 'fail'; exitCode: number;
      durationMs: number; logTail: string; logPath?: string }
  | { ok: false; code: 'E_CHECK_UNKNOWN' | 'E_ARGS' | 'E_TIMEOUT' | 'E_SPAWN' | 'E_DECL'; message: string }
>
```

- `ReviewCheckId` 是**代码常量表的字面量联合**，不是 `string`：

```ts
// 白名单唯一来源：host 源码常量。不是设置、不是提示词、不是项目文件。
const REVIEW_CHECKS = [
  { id: 'kernel:typecheck', cmd: 'npm', args: ['run', 'typecheck'], timeoutMs: 180_000, writes: ['*.tsbuildinfo'] },
  { id: 'host:typecheck',   cmd: 'npm', args: ['--prefix', 'hosts/memora-vscode', 'run', 'typecheck'], timeoutMs: 180_000, writes: ['*.tsbuildinfo'] },
  { id: 'kernel:lint',      cmd: 'npm', args: ['run', 'lint'], timeoutMs: 120_000, writes: ['.eslintcache'] },
  { id: 'host:lint',        cmd: 'npm', args: ['--prefix', 'hosts/memora-vscode', 'run', 'lint'], timeoutMs: 120_000, writes: ['.eslintcache'] },
  { id: 'test:chatPanel',   cmd: 'npm', args: ['run', 'test', '--', '<登记的文件路径>'], timeoutMs: 180_000, writes: ['.workbuddy/tmp/**'] },
] as const;
type ReviewCheckId = (typeof REVIEW_CHECKS)[number]['id'];
```

（args 以仓库脚本为准，示例只表达形状；`test:*` 的 id 与固定文件路径一一登记，不接受运行时拼接。）

- **参数校验**：`check` 必须是 `REVIEW_CHECKS` 里的 `id`，否则 `E_CHECK_UNKNOWN`；没有 `command` / `path` / `args` / `shell` 字段，未知键 `E_ARGS`。
- **执行**：`spawn(entry.cmd, entry.args, { shell: false, cwd: 固定工作区 })`；固定 `env`，不继承模型可控变量；超时杀进程树；`logTail` 截到 4000 字，完整日志写 `.workbuddy/tmp/review-check-<id>-<ts>.log`。
- **不含 `gate:fast`**：v1.5 的白名单明确排除；嵌套 gate 会与提交钩子抢同一工作区/锁。要跑全量由人在终端跑，不由 review 会话跑。
- **只装配在 review**：主助手与工作子会话都没有 `run_check`；主助手集合里出现即红（§13.11.2 的等号）。

**副作用（诚实写）**

- typecheck/lint 会写 `*.tsbuildinfo` / `.eslintcache`，runner 会写 `.workbuddy/tmp/` 日志；每条 `REVIEW_CHECKS` 用 `writes` 逐项声明。
- 因此 **review 不是「结构上零写盘」**：它是「不写源码，只写声明的构建/缓存/日志路径」。汇报里不能说「review 没有写任何东西」。
- runner 在 spawn 前校验 `cwd` 与写入声明；某检查的写入路径不在声明里 → `E_DECL`，拒绝执行，不赌。
- 失败保留 `logPath` 日志尾供查；成功日志按 `.workbuddy/tmp` 现有 TTL 清理。

**`verified` 的升级条件**（与 §13.11.9 合并）：

- review 跑 `run_check` 得到 `pass`，并把 `checkId + logPath + exitCode` 放进 `submit_review` 的 `anchors` → 才允许 `verified`；
- `run_check` 只提供锚点，仍要 `submit_review(pass)`；缺一回到 `relayed`。

### 14.2 缺口：五样机制 + 一张表

判据：从「同 loop 子 agent」到「独立会话编排」，缺的是**让另一个执行体独立存在且可被寻址的宿主件**，不是「把 `delegate_task` 挪进另一个循环」。

| # | 缺什么 | 为什么现有机制替代不了 | 现状 |
|---|---|---|---|
| A | **会话寻址原语**（按 sid 建 / 发 / 读 / 列） | `handleInput` 隐式取 `_currentSessionId`，没有 sid 入参；内核 `list_sessions` 只读历史路标；宿主建会话由 webview 驱动 | 半截：`SessionRuntimeStates`、`deriveSessionProjection`、`answerFor(sid, …)` 已有；**sid 定址发送未落**（`chatPanel.handleInput` 无 sid 形参） |

| C | **封闭工具面**（allow-only） | 暴露模型只能加/减；`toolWhitelist=[]` 仍带常驻写工具；deny 枚举「点名必漏」 | 缺（§13.9 K1） |
| D | **后台会话可见 / 可答** | `post()` 丢非当前会话的后台流；确认卡只在前台**上屏**，计时只在首次上屏启动 | 半截：队列已按会话隔离、`answerFor` 已存在；**后台卡不上屏 ⇒ 后台首次写盘永久阻塞** |
| E | **工作区写租约（一仓一线）** | 只有 per-session 跨进程锁（`CrossProcessSessionLock`，锁名 = dataDir + sessionId）与 per-Agent `ChatLockManager`；**没有 workspace 级锁** | 缺；「一仓一线」目前只是 `.trae/rules` 纪律 |
| F | **父子关系表** | 内核 `SessionMeta` 冻结、无 parent 字段；`forkSession` 明写「分出的是平等普通会话」 | 缺；唯一落点是宿主侧表 |

**不是「其实不缺、只是没接线」**：A / D 是半截（读侧有、写侧没有），B / C / E / F 是真缺。已齐的是**实例面**——每会话一个 `Agent`、会话存储、per-session 控制器——这也是路由形态可以生长而不是重造的原因。

### 14.3 角色包：地基还是障碍

**判断：「角色包卡住了这件事」不成立。** 角色包今天已经在承担「一次派发的能力信封」：`subagentConcurrency` 决定能不能派、派几个；`rolePack` 名字决定子 agent 拿哪份 L1；`capabilities` 决定点名开哪两档只读能力。它不承担的，是**会话实体**本身——而会话实体已经在宿主里。

**但它也只到「派发信封」这一层，不能直接当「长期占会话的角色」的地基。** 差三样：

1. **封闭工具面**：主控的安全故事是「只能管会话」，而角色包只能给工具做加法。这是 §13.9 K1，属装配档。
2. **能力提示**：角色包没有「我要会话管理能力」的声明位；四个会话工具是宿主 customTools，内核 `capabilityMap` 映射不到。
3. **运行态**：角色包是只读内容，不能承载待办、租约、claim——这些必须落在宿主（关系表 + 租约）；写进 manifest 就是把状态塞进内容。

**建议的切点（判断，待拍）——合并而非并存：**

- **不新增 agent 实体**：主控 = 一个**普通会话**，其 active role pack 是「主控」包；它跨 turn 存活靠会话，不靠新生命周期。
- **角色包只加一个声明位**：在 `capabilityMap` 登记 `session:manage`（空映射，语义同 `llm:summarize`：声明不解锁内核工具，只免 warning）。宿主读到该声明 + 总开关才注册四个会话工具。这样「主控能管会话」是**能力声明**，不是提示词。
- **封闭面留在装配档**，不写进 manifest。理由：安全边界不能是用户可编辑的配置文件；manifest 是用户资产，装配档是宿主安全断言。与 §13.9「K1 单独立项」的既有裁决一致。

于是「长期占用一个会话的角色」= 会话 + 角色包（内容 / 能力声明）+ 宿主装配档（工具面 / 租约 / 关系表），三者各归各位，没有第二套角色系统。

### 14.4 生长路径（四阶段，各自可跑通、可回退）

> 不新增分期符号：阶段一 / 二对应既有 S0 / S1 / S2-a，阶段三对应 S2-b，阶段四对应 §13.10 P4 的并发写。每阶段都有总开关，关掉回到今天的行为。

| 阶段 | 复用 | 只新增一样东西 | 验通现象 | 回退 |
|---|---|---|---|---|
| **一 · 会话可寻址（S0 + S1）** | `SessionRuntimeStates`、`deriveSessionProjection`、`answerFor`、`CrossProcessSessionLock` | sid 定址的 `send / read / list` 宿主 API（先给脚本 / 面板用，不挂 AI） | 对**非当前** sid 发一条消息，它真的跑；PC 不切会话也能看到 live 状态与待审批数 | 删 API；无 schema 变更 |
| **二 · 只读派发原型（S2-a）** | 角色包会话绑定、customTools、过程流、`delegate_task` 已证明的「派发 = 一行工具调用」形态 | 四个会话工具 + **封闭面装配档** + 主控角色包（声明 `session:manage`）；**只允许派 `mode='review'` 的会话** | 主控生效工具名集合**等于** `{create_session, send_to_session, read_session, list_work_sessions}`；能派只读会话，过程流出现派发行；**不宣称自动汇报** | 总开关 false ⇒ 不注册工具，行为与今天一致 |
| **三 · 落定汇报闭环（S2-b）** | 阶段一 / 二的 sid API 与关系表 | `onFlowTerminal` + 汇报轮闸（`origin='child-settled'` 禁止再派发）+ 批量去重 | 子会话落定 → 主控**新 turn** 自动汇总；汇报轮派发返回 `E_DENIED`；同批只出一次汇报 | 关开关 ⇒ 不落定、不起 turn |
| **四 · 写租约与审计（P4）** | 阶段一~三全部；`relayed / verified` 口径（§13.11.9） | **工作区写租约**（派发期准入）+ 工作会话（`mode='work'`） | 第二个写会话在派发期被拒 / 排队；审计能追到「谁派了谁、结果来自哪个 sid:roundId、是否复核」 | 关开关 ⇒ 退回只读派发 |

阶段二刻意只派只读会话：这样在写租约落地前，**路由模式不会破坏一仓一线**。工作会话必须等阶段四——这不是保守，是让「会不会坏」可以被单独观察。

### 14.5 不变量与风险

**写锁那条：方向对，机制描述要修正。**

- 取证：`CrossProcessSessionLock` 的锁名 = dataDir + sessionId，**per 会话**；`ChatLockManager` 也是 **per Agent**；宿主内**没有 workspace 级锁**。
- 取证：`index.lock` 只在两个 git **写操作**重叠时出现；两个会话各写各的源码**不碰 index**，不会报 `index.lock`。
- 结论（判断）：写线确实最危险，但危险形态不是 `index.lock` 报错，而是**无锁 + 无感知的静默覆盖**（同文件后写者赢，任何一方都收不到错误）。`index.lock` 只是两个会话都去提交时的**偶发可见症状**。
- 更关键：「一仓一线」今天**不是运行时机制，是 `.trae/rules` 里的纪律**（`delegation-discipline-rules.md` B1 / B3）。子会话看不到别的会话在写，主控也没有「谁在写」的信号。所以修法不能停在 git 层，必须是**派发期写租约**：主控派写会话前向宿主申请，宿主串行化；租约要可审计，也要在子会话卡住时过期（否则重演 §13.11.7 风险 3 的「永不落定」）。

其余三条：

| 不变量 | 现状落点 | 风险 |
|---|---|---|
| 并发额度 | `act.subagentConcurrency` 只罩 `delegate_task`；路由工具是宿主 customTools，**不经过这个端口** | 主控派会话没有额度 ⇒ 要新增派发期配额（§13.11.1 的 `E_LIMIT`） |
| ask / confirm 归属 | 每会话独立队列（`ConfirmCoordinator`）；但卡只推前台，计时只在首次上屏启动 | 后台写会话第一次要确认就**永久阻塞**（`_enqueue` 不 pump、`_show` 不调用 ⇒ 计时器不启动） |
| 审计可追溯 | 子 agent 回执在父 Round 的 `tool_result`；内核无父子字段 | 会话层必须补关系表；`verified` 只能由 coordinator 按「复核会话 + 目标 roundId + 锚点」置位，不能听模型自报 |

**最可能被破坏的一条：写线。** 理由不是它最重要，而是它是四条里**唯一没有机制载体**的——其余三条至少已有单会话级实现（配额、队列、Round），只有「一仓一线」完全靠人 / agent 自觉。

### 14.6 边界：哪些不动

| 对象 | 本章结论 |
|---|---|
| **memory** | **不动**。轮摘要仍按会话写进同一记忆索引（`agent.ts` 注释：fork 共享记忆索引）；主控不召回子会话细节，细节由子会话带结论与锚点回来。 |
| **定时调度** | **不做**（v2）。三条理由见 §13.11.10：到点无人、失败谁重试、多任务撞同一工作区。 |
| **技能 / 插件** | **不动**。技能工具留在子会话；给主控装配 `read_skill` 等于给它一条读项目的侧门。插件不属于 memora 运行时。 |
| **MCP** | **不动**。子会话照旧使用自己的 `customTools`（MCP 桥接）；主控封闭面**不注册** MCP。 |

| **角色包** | **只加一处**：登记 `session:manage` 空能力声明（判断，待拍）。不改 schema 现有键、不改三态语义。 |

| **队伍（teams）** | **不动**。组员仅会议参与，不变成执行体池（`setRolePackTeams` 注释）。 |

### 14.7 判断不了 / 待拍

1. **主控用真实角色包还是宿主硬编码 profile**：真实包可让用户换 persona，但也让「主控」变成用户可改的东西；硬编码 profile 更安全但多一个概念。判断倾向前者（复用现有会话角色包绑定），需产品拍板。
2. **写租约粒度**：workspace 级（简单、粗）还是文件 / 路径声明级（精细、要新协议）？v1 建议 workspace 级 + 拒绝（不排队），与 §13.9「串行写」一致。
3. **后台确认是否必须上屏**：若阶段二 / 三只派只读会话，这个前置可以晚到阶段四再解；若提前开放写，P0-4 必须先落。
4. **核实不到**：`handleInput` 改成 sid 定址后对草稿（`isDraft` / `flush`）、插话相位、附件分支的影响面——只读了 `handleInput` 主路径，未通读全部分支。
5. **核实不到**：宿主是否存在我未找到的 workspace 级写锁；目前只核实到 `CrossProcessSessionLock`（per session）与 `ChatLockManager`（per Agent）。

### 14.8 候选方案评估：用「工具域互斥」承载主控（2026-11-13 追加）

**方案转述（不是结论）**：把工具分成「会话管理」与「其他动手」两类，二者互斥、只能选一类，由角色包承载——角色包启用会话管理工具后就没有任何动手能力，所有任务交给会话；主控是派活的领导，动手的是工作人员。

**总裁决：部分成立。** 方向（主控不应有动手能力）成立；三个实现细节不成立。

| 方案主张 | 裁决 | 依据 |
|---|---|---|
| 主控与动手工具互斥 | **成立** | 这是两层结构里「主控不干活」的最小表达，与 §13.2 的会话层 / 会话内层分工一致 |
| 用「只读 / 可写」当互斥轴 | **不成立** | 该轴已存在（`ToolDefinition.readonly` + `diskWrite` + `ToolRunner.applyPrechecks`），但它管「改不改盘」，不管「动不动手」；`read_file` / `delegate_task` / `run_team_meeting` 在只读轴下全部放行，却都是「动手」 |
| 用工具注册的 `mutating` 标记强制 | **不成立** | 会变成第四套真源（已有 `readonly`、`diskWrite`、`DEFAULT_EXPOSED_TOOLS` 三套），且仍无法表达「会话管理」这个正向集合 |
| 用角色包单独承载安全边界 | **部分成立** | 角色包可承载「领导」的 persona / 规则；但 manifest 是用户可编辑资产，不能当安全断言 |
| 所有任务都建会话 | **不成立（作为 v1 默认）** | 与「阶段二只派只读会话」的安全序位冲突；纯对话不需要会话；成本 N× |
| 复核归主控层 | **部分成立** | 复核应由主控**派出**的只读子会话承担，不是主控自己的能力；必须结构隔离 |
| 子会话失败只能重派 | **成立（v1）** | 汇报轮禁派 ⇒ 自动重试结构性不可能；重派只能由用户发起 |

#### 14.8.1 互斥轴：选 A，不选 B；A 只能用正向白名单强制

**取证（两条既有轴）**

- `readonly`：`ToolDefinition.readonly`（`src/agent/builtinTools.ts`），由 `ToolRunner.applyPrechecks` 在 `toolReadonly='readonly'` 时拦截非只读工具（`[ERR:TOOL:READONLY_DENIED]`）。
- `diskWrite`：`'none' | 'path' | 'opaque'`（同 `ToolDefinition`），管「写与写怎么排序」，与 `readonly` 正交。
- 暴露面：`ToolExecutor.isToolExposed` = deny → customTools → `search_project` → `DEFAULT_EXPOSED_TOOLS` → 白名单；`DEFAULT_EXPOSED_TOOLS` 里既有 `read_file`，也有 `write_file` / `run_command` / `task_table_write` / `delegate_task`。

**判断**：A（会话管理 vs 其他动手）与 B（只读 vs 可写）是两根不同的轴，A 才是方案要表达的东西。B 已经在代码里，但它回答的是「能不能改项目盘」，不是「这个会话是不是只负责派活」。用 B 代替 A 会得到「一个能读遍全项目、能派子 agent、能开会，但只是不能写盘」的主控——这不是领导，是带只读权限的工程师。

**强制方式**：A 只能用**正向 allow-only 装配档**（§13.9 K1），且判定必须排在 `isToolExposed` 的 `denyTools` 之后、`customTools` 与 `DEFAULT_EXPOSED_TOOLS` **之前**（否则常驻工具与 MCP 自定义工具会先命中「恒暴露」而漏出）。不能用 `mutating` 布尔（第四套真源），不能用 deny 枚举（新增内置工具会静默泄漏，§13.9 已判过）。

**两套轴归属不同的工具（点名）**

| 归属 | 工具 |
|---|---|
| B 放行、A 必须禁（最容易被「只读就安全」误判） | `read_file`、`read_image`、`list_dir`、`search_project`、`search_memories`、`trace_summary`、`read_skill`、`read_resource`、`list_resources`、`list_skills`、`web_search`、`web_fetch`、`compress_context`、`remember_intel`、`ask_user`、`run_team_meeting`、`delegate_task` |
| 两轴同禁 | `write_file`、`delete_file`、`run_command`、`kill_command`、`run_project_script`、`run_skill_script`、`run_code`、`task_table_write`、`task_table_update`、`register_work` |
| 两轴同放（尚未实现） | 四个会话工具（`create_session` / `send_to_session` / `read_session` / `list_work_sessions`） |

三个特别点名的：

- **`delegate_task`**：`readonly=true`，B 轴放行；但它是一条**绕过父子关系表与审计**的第二派发通道（它不产生 session id，也不进 `list_work_sessions`）。主控若持有它，会出现「同一次派活有时在关系表里、有时不在」。A 轴必须禁。
- **`run_team_meeting`**：声明只读，但会发一次 `provider.chat()`；B 轴放行、A 轴禁止。它是「只读 ≠ 不动手」的现成证据。
- **`list_sessions`**：只读，但它是内核的**历史路标**，不是 live 会话列表；A 轴下也不该给主控，否则同一件事会有两套列表语义（§13.11.11 已登记命名冲突，路由侧应叫 `list_work_sessions`）。

补充一条反例：`search_memories` 声明 `readonly: true`，命中即 `UPDATE accessedAt`（真 SQLite 写）。这再次说明 B 轴的「只读」承诺是「不改项目文件」，不是「零副作用」——拿它当「主控不动手」的判据不成立。

#### 14.8.2 主控不写，怎么验证结果

**需要的三样东西**

| 需要 | 现在有没有 | 取证 / 缺口 |
|---|---|---|
| 读会话状态 / 历史 | **没有模型工具**；数据源齐 | `RoundStore` 落盘轮；`deriveSessionProjection`（`{ state, rounds }`）；`SessionRuntimeStates`。§13.11.1 的 `read_session` 仍是规格，未实现 |
| 看子会话改了什么 | **没有模型工具**；宿主有数据与纯函数 | `gitCollector` 的 `diffUnstaged` / `diffStaged`、`computeFileDiff(before, after)`、`fileChangeTracker` 都在宿主 UI 侧；没有面向模型的 diff 工具 |
| 结论的可复核锚点 | 有口径，无载体 | §13.11.9 的 `commit:` / `file:line` / `log:` / `round:sid:roundId`；需要 reviewer 或子会话正文携带 |

**判断（v1 建议）**：主控只拿 `read_session`，**不拿 diff 工具**。验证链条是「子会话交结论 + 锚点 → 主控转述为 `relayed` → 需要盖章时派一个 `mode='review'` 的只读子会话去读代码 / 跑受限检查 → `verified`」。理由：diff 工具一旦接受路径参数，就等于把 `read_file` 从侧门放回主控；不给路径参数、只按「该会话时间窗 + 该会话 `diskWrite` 目标」取 diff，又是一套新的边界与截断规则，应单独立项，不能混进 v1。

**如实写**：`read_session` 与 diff 工具都**不存在**，不是「已有只是没接线」。宿主侧的数据源存在，工具面不存在。

#### 14.8.3 小任务是否值得建会话

**判据不是「任务大小」，是「要不要工作区事实」。**

- 纯对话 / 已有上下文能答（解释概念、改写、基于用户给的材料）→ 主控直接答。
- 需要读或改工作区（哪怕一行）→ 派会话。主控没有读工具，它无法自己确认任何工作区事实；硬答就是编。
- 判定者是**主控**（它是派发者），用户可用一句话覆盖（「这个直接答」/「派下去」）。判定依据写进主控角色包的 persona / 规则，属提示词层，**没有代码强制**——这是已知代价，不要假装有结构保证。

**轻量通道**：复用同一个会话实体 + 小 `stepBudget` + `mode='review'`，**不要**启用 `delegate_task` 当轻量通道（绕过关系表、审计、停止语义）。也就是说，「轻」体现在预算与模式，不体现在新实体。

**代价写明**：主控不带读工具 ⇒ 连「这项目用什么框架」都要派一个只读会话。这是 §13.2 第 7 条已登记的价格，不是缺陷；若实测不可接受，再讨论放宽，而不是现在就偷偷给它 `read_file`。

#### 14.8.4 复核会话：结构上必须与写会话不同

「换个角色继续」不成立，必须同时有三道结构约束：

1. **`mode` 在创建时固定**，是宿主会话运行时属性，**不由 active role pack 推导**。同一 sid 换角色包不改变 mode。
2. **复核面封闭**：`Read` / `Grep` / `Glob` + `submit_review`，没有 `Write` / `Edit` / `Shell` / `run_check`（v1）。这走的是与主控同一套 allow-only 装配档，不是 deny 枚举。
3. **`verified` 由 coordinator 计算**：`reviewSid !== targetSid`、`targetRoundId` 等于被复核会话已落定的轮、锚点非空，三者同时成立才置位；模型自报不算。

再加一条时序约束：**复核只能发生在目标落定之后**，否则读的是移动靶，diff 与结论对不上。

**层次纠正**：复核会话不是「主控层的能力」，它是主控派出的**子会话**，与工作会话同层。主控自己不读代码——它没有读工具。把复核说成「主控复核」会让后来人以为主控有读权限。

#### 14.8.5 角色包 schema：不加「工具域」键；与 `session:manage` 合并为一处

**合并结论：二者是同一个扩展点的两面，合并后只保留宿主装配档。**

- 上一轮的 `session:manage` 是**正向声明**（「我要会话管理工具」）；本方案的「互斥」是**负向封闭**（「我不要动手工具」）。只做正向，常驻动手工具仍在；只做负向，主控没有会话工具。两半必须成对。
- 成对之后的落点只能是**一个宿主的 `sessionMode` 装配档**（`master` / `review` / `work`）：它同时决定「有哪些工具」与「只能有哪些工具」。
- **不写进 manifest**：manifest 是用户资产，用户能改的配置不能当安全边界；也不新增 `strategy.act.toolDomains` 之类的键——那会与 `capabilities` 三态、`readonly`、`diskWrite` 形成第四套判据。
- **订正上一轮**：§14.3 曾建议在 `capabilityMap` 登记 `session:manage` 空映射。本轮评估后**撤回**——两把钥匙（包声明 + 宿主开关）会让「包声明了但宿主没开 / 宿主开了但包没声明」产生两种二义，而安全判定只需要宿主一处。角色包仍承载「领导」的 persona 与规则，但不承载工具面。

一句话：**角色包管「我是谁」，装配档管「我能碰什么」。** 方案原文想用前者承担后者，这是唯一必须改的地方。

#### 14.8.6 失败模式：重试上限与死循环落在哪一层

- **v1 自动重试结构性不可能**：汇报轮 `origin='child-settled'` 禁止派发（§13.11.2 闸①）。子会话失败 → 主控在汇报轮只能报告并问用户，不能自动重派。这是设计内代价，不是遗漏。
- 若要做自动重试，必须新增受控状态机：coordinator 持 `attempts`（按 `parentRequestId`）、上限 N、独立 origin（不能用 `user` / `child-settled` 混用）、全局派发预算、超限转人工。**不建议进 v1**——它是第二套"谁能派"的判据。
- **手动打断**：用户可停主控本轮；可停任一子会话（每会话独立控制器）。主控**没有** `stop_session`，不能自己停跑飞的子会话（§13.11.1 的停止语义裁决）。这个不对称必须在 UI 文案里说清。
- **防护顺序**：结构性闸（汇报轮禁派）> 配额计数 > 提示词。任何只靠提示词「不要重复派」的方案都无效。

#### 14.8.7 与写租约、并发额度的关系：不同约束，共用强制层

| 约束 | 管谁 | 现状 | 能否互相替代 |
|---|---|---|---|
| 工具域互斥（本方案） | **主控**能不能自己干活 | 缺（封闭面未实现） | 不能：只读主控照样能派一个写会话 |
| 阶段二只派只读会话 | **子会话**能不能写 | 缺（`mode` 未实现） | 不能：只派只读子会话，主控照样可能自己写 |
| 工作区写租约 | 同一时刻**几个写者** | 缺（无 workspace 锁） | 不能：前两者都不限制两个子会话并行写 |

所以它们**不是同一件事的两面**，是三条独立约束；可以共用的只是**同一套 allow-only 装配档机制**，不能合并成一条语义。

**与四阶段路径的冲突（必须点明）**：方案原文「所有任务交给会话」要求阶段二就能派动手活，而阶段二的序位是「只派只读会话」，动手活等阶段四的写租约。**以阶段路径为准更安全**：在写租约落地前开放写会话，等于跳过 §14.5 里唯一没有机制载体的不变量。若用户接受「阶段二只派只读活」，方案可以立刻落；若不接受，就必须把写租约一起提前——那是另一个立项，不是配置项。

**并发额度**：主控的派发走宿主 customTools，不经过 `act.subagentConcurrency`（那个端口只罩 `delegate_task`）。所以派发期配额要单独加（§13.11.1 的 `E_LIMIT`，每 `parentRequestId` 上限）。这与工具域互斥无关，不能拿额度当互斥的替代。

#### 14.8.8 对上一轮建议的订正留痕

| 原说法（§14.3） | 订正 | 原因 |
|---|---|---|
| 在 `capabilityMap` 登记 `session:manage` 空映射，宿主据此注册会话工具 | **撤回**；只保留宿主 `sessionMode` 装配档 | 包声明 + 宿主开关是两把钥匙，会产生「声明了没开 / 开了没声明」两种二义；安全判定只该有一处 |
| 「主控 = 普通会话 + 角色包 + 宿主装配档」 | **保留**，但角色包只承担 persona / 规则，不承担工具面 | 用户可编辑资产不能当安全边界 |

### 14.10 UI 配套：双模式、三块结构与两条非 UI 约束（2026-11-13 追加）

> 本节只做 UI 与模式边界的盘点，**不替用户选命名**；命名一律「待拍」。取证写「文件 + 符号」，推断标「判断」，查不到标「核实不到」。

#### 14.10.1 两模式命名候选（待拍）

先说两个不能用的：

- **`托管` 不能用**。取证：`.trae/rules/generic/delegation-discipline-rules.md` 标题即「托管执行纪律（Delegation & Receipt Discipline）」，`project-rules.md` L164 也把它登记为「派发 / 并发 / 自证 / 汇报 / 边界」。它指的是「把活派给别的 agent 并收执」的**纪律**，不是会话编排；复用会让两件事永远混淆。
- **「用户管理模式」不建议**。「管理」只在编排模式下成立；直连模式下用户是**直接做**，不是管理会话。用「管理」会把两种模式都包进去，区分度归零。
- **「trae 宝模式」是口语别名**，不进代码、不进 UI 文案。

候选与代价（待拍）：

| 候选 | 指代 | 代价 |
|---|---|---|
| **直连** | 用户直接对会话下指令，自己汇总 | 无新机制、上下文隔离天然；代价是用户承担协调与汇总，没有单一出口 |
| **编排** | 主控管理会话创建 / 追问 / 推进，用户只对接主控 | 单一出口；代价是 §14.2 的五样机制 + §14.10 的 UI + §14.5 的写租约，缺一不可 |

判断：两词只描述「谁在协调」，**不描述「谁在写」**，所以不能替代写租约（见 14.10.4）。本文一律用「直连 / 编排」作占位，不当作定名。

#### 14.10.2 UI 三块结构

| 块 | 职责 | 现有可复用件（取证） | 要新增 |
|---|---|---|---|
| 中部主控对话 | 唯一出口；来自子会话的内容必须挂会话名标识 | `chatView` 的 process-flow 平铺容器、round 底栏 | 「来源会话」标识；主控窗口不聚合子流（14.10.3） |
| 侧边会话面板 | 列出会话、点进看历史 | 会话列表 + `switchToSession` 重放历史（`chatPanelHistory` 用例：切换会话 → 按会话取实例 + 重放历史 + 推标题） | 运行态 / 模式归属标识 |
| 卡片层 | 产物、建议芯片、打开会话；派发与进度用**原地更新卡片** | `planBarView`（任务看板）、`writeConfirmCardView`（确认卡）、后台任务条（`BGTASK-SWITCH-REPUSH-1`） | 「派发卡」新卡种（已派出 / 运行中 / 已完成），不刷气泡 |

判断：卡片层是本节里**唯一纯 UI** 的部分，可独立做；它不依赖写租约，也不改变工具面。

#### 14.10.3 硬约束：主控对话不得展示子会话原始流

取证：现状每个会话有自己的流与投影（`deriveSessionProjection`），`ChatPanel` 只把 `_currentSessionId` 的流上屏；切到子会话才看到它的完整历史。所以「主控窗口不混子流」在**分会话**结构下天然成立。

但要写死三条：

1. 主控窗口只显示**结论 + 状态**，不显示子会话的 tool_call / 思考流；
2. 需要细节时，用户点「打开会话」进子会话看，主控窗口不复制一份；
3. 卡片数据是**用户可见产物**，不得回灌主控上下文；否则等于给主控开一条读子会话原始内容的侧门（与 §14.8.2「主控不拿 diff / `read_file`」冲突）。

#### 14.10.4 两条不是 UI 能解决的问题

**（1）模式是并发治理边界，不是视图开关。**

判断：方向成立，但「同一 workspace 同一时刻只允许一个模式持有写权」这句话**不能靠模式标签实现**。取证：宿主只有 per-session 锁（`CrossProcessSessionLock`，锁名 = dataDir + sessionId）与 per-Agent `ChatLockManager`；**没有 workspace 级锁**；`git index.lock` 只挡 git 写操作。即使只开一个模式，**同一模式内两个会话仍可并行写**（后台流本来就支持并发）。

正确落点：模式决定「谁有权申请写准入」（直连 = 用户会话直接申请；编排 = 只由主控的派发器申请），**写租约**决定「同时几个写者」（= 1）。没有写租约，模式只是 UI 状态。这与 §14.5 的「E 工作区写租约」同一条，不新增机制。

**（2）「可查看」默认只读旁听；接管要显式，且主控必须收到通知。**

取证：

- 「可查看」已有：切会话 + 重放历史（`switchToSession` / history replay）。
- **没有**「接管」语义：全仓无 `takeover` / `takeOver` / 会话级「接管」符号；`confirmCoordinator.setForeground` 只是前台焦点，不是接管。
- 更糟：用户切进子会话后**可以直接发消息或插话**（`Agent.interject` 是执行中唯一写入口，step 边界注入），这不是只读旁听；且主控没有任何通知通道（子会话的 `interject` 不产生主控可订阅的事件）。
- 主控**感知不到外部改动**：宿主只有 `ActiveFileTracker`（`workspace.onDidChangeTextDocument` / `onDidSaveTextDocument`）用于更新活动文件上下文；没有面向 agent 的「文件被外部修改」通知，也没有 `createFileSystemWatcher` 推给主控。

结论：**「接管」与「接管通知」都缺**。这是 §14.2 的 D（后台可见可答）+ F（关系表）之外的新增缺口，必须单列，不能假装 UI 能解。

#### 14.10.5 切换安全

要求：切模式前必须显式告知「在跑的会话数量 + 切过去之后没有人替你收结果」。

取证：**没有**模式概念，所以也没有切换前置提示。可复用的只有通用确认通道 `showWarningMessage`（现有用法：删除会话确认、图片超限拒收），以及每会话 `isChatBusy`（`agent.internals.chatLockManager?.isBusy`）能算单会话是否在跑；**没有**「在跑会话数」的聚合查询。

判断：这是「有材料、缺装配」——可复用确认通道与 `isChatBusy`，但要新增聚合计数与前置提示；不能只弹一句「确定切换吗」。

#### 14.10.6 与 §14.8 / §14.9 的对齐与冲突

- **不冲突**：模式是宿主 `sessionMode` 装配档的选择器（§14.8.5），不是角色包字段；UI 只切模式，不直接授予 / 回收工具。安全边界仍在装配档。
- **冲突点 1**：§14.9 的「单一出口」与侧边面板并存。判断：面板是**观察面**，不是第二出口——凡能改状态的操作（发消息、接管）都必须回到主控或显式接管，不能在面板里静默发生。
- **冲突点 2**：§14.9 E5 / E6 否掉了「主控读 diff / 主控复核」。UI 的「打开会话」「产物卡」只能给**用户**看，不能作为主控输入；否则等于绕过封闭面。
- **冲突点 3**：§14.9 E3 否掉了「轻量通道」。UI 不要加「快速任务」按钮直接起一个不登记的会话；所有派发仍走会话工具与关系表。

#### 14.10.7 核实不到 / 缺

| 项 | 结论 |
|---|---|
| 会话级「接管」语义 | **缺**（全仓无符号） |
| 接管后通知主控 | **缺**（无事件通道） |
| 主控感知外部文件改动 | **缺**（只有 `ActiveFileTracker`，不推 agent） |
| 模式切换前置提示 | **缺**（有 `showWarningMessage`，无聚合计数与前置逻辑） |
| 在跑会话数的聚合 API | **核实不到**（只核实到 per-Agent `isChatBusy`） |
| 「产物 / 建议芯片」实体 | **缺**（chat 侧无 artifact 实体；chip 仅存在于 settings / roles 样式） |

### 14.11 主控模式的主窗口 UI 形态（2026-11-13 追加）

> 本节接 §14.10.7 的缺项，只补「主窗口长什么样」；不改 §14.10 的三块结构，不新增编号体系。三类标注：**取证**（带来源）/ **判断** / **待拍**。

#### 14.11.1 参照系拆两层：排版可抄，消息模型不可抄

| 层 | 能否照抄微信 | 理由 |
|---|---|---|
| **排版层** | **可抄** | 气泡、左右分侧、文字 / 图片 / 文件同列混排、时间分隔、引用块——这些是「阅读节奏」的容器，不携带状态语义 |
| **消息模型** | **不可抄** | 微信消息是**不可变、无状态、一次落定**的；它没有「一件还在进行中的事」这个对象 |

**判断**：硬把状态塞进消息模型，只会得到两种坏结果——(a) 同一条任务冒多个气泡（每变一次状态发一条）；(b) 历史滚上去后状态变了却看不到在变（状态挂在已滚出视口的消息上）。

所以「运行任务气泡」**不是一条消息，是一个有状态对象**：借气泡的外观，不借消息的生命周期。

#### 14.11.2 运行任务气泡：三条承载规则

1. **锚点不可变、中间可原地变**：派发落一条固定气泡，落定落一条固定气泡；中间状态只挂在最新一条上原地刷新：排队 → 运行中 → 等待确认 → 落定。理由：锚点稳定才能被引用和回看；中间原地变才能避免气泡洪水。
2. **状态要能漏出侧边栏**：活动栏角标 / 状态栏 / 需要拍板时一条可跳转的通知。理由：插件的心智是「打断与返回」，不是「进入后专注」；用户不会一直盯着主窗口。
3. **落定后收束成一行**：任务名 + 成败 + 一句话结论，点开看细节。理由：对话流要能读；落定后的任务是「历史」，不是「当前」。

**与 §14.10.7 缺项的对接**（只映射，不新增概念）：

- §14.10.2 的「派发卡」新卡种 = 本节说的运行任务气泡，不是第二种东西；
- §14.10.7 的「接管通知」可以复用规则 ② 的通知通道，但**语义不同**：② 是任务状态，接管是外部干预，文案必须分开；
- §14.10.7 的「产物 / 建议芯片」落在规则 ③ 的展开层，不单独占一条消息。

#### 14.11.3 「把插件 UI 当手机」：两半判定 + 一个待拍岔口

先取证主窗口载体（这一步决定「宽度」前提是否成立）：

| 说法 | 取证结果 |
|---|---|
| 聊天面板现在是侧栏 view | **取证成立**：`extension.ts` 的 `registerWebviewViewProvider(MemoraChatViewProvider.viewType, chatProvider)` |
| 仓库里有编辑器标签页形态 | **仅设置面板**：`settingsPanel.ts` 的 `createWebviewPanel(..., ViewColumn.Active)`；聊天 / 工作台没有对应注册 |
| 用户截图里的「TRACE 宝的工作台」 | **核实不到**：仓库内 `tracer.ts` 是遥测采集，不是工作台；没有同名面板 |
| 侧边栏 300–500px | **核实不到仓库证据**：仓库不定义侧栏宽度（VS Code 客户端行为，用户可拖拽）；只能作为用户观察 / 外部事实 |

**待拍岔口（本轮不替你选）**：主控窗口到底落在「侧栏 view」还是「编辑器标签页」？

- 落侧栏：宽度与手机同量级，「当手机」的宽度半边成立；代价是看子会话 / 看产物更挤。
- 落标签页：宽度足够、可全屏，宽度半边的前提**不成立**；代价是用户要离开代码去一个独立标签，违背「干活时能瞄到」。
- 第三种候选：**侧栏做主控对话 + 标签页做会话详情**。这是候选，不是裁决。

**两半判定**：

- **宽度半边：形态相关。** 在侧栏形态下成立（300–500px 与手机 375–430pt 同量级；外部观察，仓库核实不到）；在编辑器标签页形态下不成立（宽度足够）。注意「侧栏 300–500」与「标签页宽度足够」是两条不同观察，不能混成一句事实。
- **注意力半边：不成立。** 微信是专一注意力（全屏、一次一件事、手势返回）；插件是打断与返回（用户开着代码、被打断看一眼、再切回）。

**结论**：不是二选一，而是**借窄列排版 + 借打断式交互**。若为了像微信而牺牲「干活时能瞄到」，是拿形式换功能。

#### 14.11.4 更根本的定性

**判断**：用户要的不是「微信界面」，而是「一个能替他跑会话、并且让他知道在干什么的同事」；微信只是这个同事的说话样子。

因此验收标准不是「像不像微信」，而是两条：**不离开代码也能知道主控在干什么**；**需要拍板时一句话就能拍**。

#### 14.11.5 与 §14.10 的衔接（只引用，不复述）

| §14.10 的既有结论 | 本节的处理 |
|---|---|
| 三块结构（14.10.2） | 中部主控对话 = 气泡流 + 运行任务气泡；侧边面板 = 会话列表 + 运行态；卡片层 = 落定收束 + 产物 / 建议 / 打开会话 |
| 主控不展示子流（14.10.3） | **不变**：任务气泡只给结论 + 状态；点「打开会话」进子会话看细节 |
| 模式是写权准入、不是视图开关（14.10.4） | **不变**：气泡只呈现状态，不改变写权；写租约仍缺 |
| 切换前置提示（14.10.5） | **不变**：仍需在跑会话数聚合 + 显式告知 |
| 「接管 / 通知」缺项（14.10.7） | **不变**：本节只借用通知通道，不声称已有接管语义 |

#### 14.11.6 取证 / 判断 / 待拍清单

- **取证**：聊天面板是侧栏 view（`registerWebviewViewProvider`）；编辑器标签页仅用于设置面板；仓库无侧栏宽度常量；仓库无「TRACE 宝工作台」实现；无会话级接管语义与外部改动通知（§14.10.7）。
- **判断**：排版可抄、消息模型不可抄；运行任务气泡是有状态对象；三条承载规则；「当手机」两半判定；「同事」而非「微信」的验收标准。
- **待拍**：两模式命名（直连 / 编排 仍待拍）；主窗口载体（侧栏 / 标签页 / 侧栏 + 标签页）；运行任务气泡的状态字段与转移（排队 / 运行中 / 等待确认 / 落定 / 失败 / 中断）；落定行的默认折叠；状态漏出选角标还是状态栏还是通知（可多选）；「打开会话」是切前台还是新开标签页。
