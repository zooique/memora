## 0. 本版三项裁决

### 0.1 术语正名（不改术语锚点）

本文此前把最上层写作「L3 目标模式」。**现正名为「目标聚焦编排（单 turn）」**。

## 1. 结论先行

| 层 | 形态 | 一句话结论 | 依赖 |
| --- | --- | --- | --- |
| **L1 单会话助手** | 现状：一会话一 Agent，处理用户分散需求 | 已落地，是唯一有成体系支撑的一层 | — |

## 2. 硬结论（连成立条件、代价与天花板一起写）

### 2.1 「一范围一裁决者」成立，但只在「父同一 turn 内等齐子结果」这个窗口内成立

- 取证：`done` 由**纯文本收场**产生——`src/agent/loop.ts:2008-2064`（`handleTextResponse` 在文本交付后 `yield done`）；由 `handleIterationResult` **消费**——`src/agent/loop.ts:1207-1239`。另有步数上限收场 `src/agent/loop.ts:1116`、用户硬中止 `src/agent/loop.ts:1210-1213`。
- 取证：任务表**无裁决权**，只是注入文本 `src/agent/assembler.ts:468-494`；turn 结束清空 plan，**暂停态例外**——`src/agent/agent.ts:1207-1224`（`:1214` 明写 `if (cp.pauseMeta) return;`）。
- 成立：子会话判自己那块（各自 turn），父在同一 turn 内判整体 —— 两个射程、各自一个裁决点，**不改现有判据**。
- 不成立：父跨 turn 推进 —— 父的 `done` 会在子还没回来时宣布整体完成；要补就得加第二判据或复活多 turn 编排。
- **推论（判断）**：异步派发让父先收场 ⇒ **异步必然破坏本结论**。

### 2.2 主助手不得复核子会话已交付的切片

同一切片若「子会话 `done`」+「父复核」两处都判，就是同一块两个裁决者。正确读法：**子会话判切片，主助手只判「整体锚点 + 切片齐备」**。

### 2.3 目标聚焦编排不加第二套完成判据

- 并列加一层「达成判定」⇒ 两个「算不算完」且无裁决顺序。
- 唯一站得住：父的**单 turn `done` 本身就是整体判定**，判据来自指导文档（文档进上下文，不另立裁决器）。
- 成立条件：父单 turn 长跑（§2.1）且不复核切片（§2.2）。任一破坏即失效。

### 2.4 父单 turn 的预算天花板（本版新增，原缺）

- 取证：默认迭代上限 **50**——`src/role-pack/strategyKeys.ts:41`；角色包最高可声明 **500**——同文件 `:86`；下限 10——`:79`。抬预算的唯一旋钮是**角色包配置**，没有「目标级预算」接口。
- 因此 P3 的真实形态是：**目标必须装进父会话当前角色包的 `stepBudget`**。默认 50 步装不下的目标，会撞上限收场，此时**根本没有整体判定**（父是被预算结束的，不是判定达成的）。
- 本文**明确不做**目标级独立预算（与 §10 一致）。代价：目标规模受角色包配置硬约束；P3 必须有一条「撞上限」失败路径用例，不得只验小目标。

### 2.5 v1 同步：已决 + 代价登记

- 已定：v1 用**同步工具**（一次调用阻塞到子会话收场），同一步多调用天然并行。
- 代价登记（不再作为待拍）：
  1. 拿不到「随时查进度」——同步调用期间父没有观察点。
  2. 父的 step 时间被拉长，用户可感知延迟（量级无样本，见 §11）。
  3. 子会话一挂起（`ask_user`）就会拖死父——因此 v1 必须禁子会话提问（§7.4）。
  4. 父 abort 后子不一定立刻停（协作式），存在「父收场、子仍在写」窗口——必须靠端口信号合并 + 验收用例兜（§10 P1）。

## 4. 「指导文档」的落点

内容与指针分两层，这是分工不是双写：

| 层 | 落点 | 谁写 | 谁读 |
| --- | --- | --- | --- |
| **正文（内容真源）** | 工作区产物文件（如 `docs/目标/<slug>.md`） | 一次收敛动作由主助手写入；后续只有主助手在有据可依时改 | **新增的 Prepare 注入段**（见 §4.1）每轮读入；子会话只收派发时传的切片段 |
| **指针（当前目标真源）** | 项目级固定路径 **或** `SessionMeta` 一个字段（作用域见 §7.1） | 收敛动作写、换目标时改 | 注入段与 UI 状态面 |

### 4.1 注入载体（本版补上，原缺）

- 现有唯一的「工作区文件 → 每轮固定注入」通道是 `resident` 项目规则段（`src/agent/managers/residentRules.ts:1-15`），而该段已被 §4.2 否掉（语义不同、共享预算、撞在途的常驻层收缩）。
- 因此 v1 定：**新增一个 Prepare 注入段「当前目标」**，只读指针指向的那一个文件；读盘判据、路径守卫、字符上限**复用同一套现成实现**（不另写第二份），fail-closed 同源（工作区未信任整段不注入）。
- 段内必须写明未注入原因：读取失败 / 文件缺失 → **段内一行「本次未注入（原因），下轮重试」**，落点是段内文案，**不新增 notice 通道**。
- 字符预算：单段上限**与项目规则段同量级但独立计数**（判断：先取 5,000 起，超限按序截断并标注），不与项目规则段共享预算——否则两段互相挤占，边界上会得出两个结论（同 `residentRules.ts:23-37` 的教训）。
- **「不能只是提示词」的准确含义**：不能靠模型自己想起来 `read_file`；必须有注入段。原 §4.1 那句话在本版按此收窄。

### 4.2 它不能是什么（逐条带证据）

- ❌ **不能是 checkpoint 字段**：goal 三字段曾存在于检查点，因零读取被作为**僵尸字段**删除——`src/agent/managers/sessionManager.ts:273-277`、`src/__tests__/publicMemberSurfaceGuard.test.ts:4-7`（GOAL-DRIFT-1）。
- ❌ **不能是记忆条目**：记忆是 round 摘要，参与衰减与 GC。
- ❌ **不能是任务表**：turn 级、结束即清空（暂停态例外，`src/agent/agent.ts:1214`）；任务项单 active 不变量的真源在 `src/agent/managers/sessionManager.ts:609-626`（写点契约 + `ensureActivePlanItem`），不是在消费侧。
- ❌ **不塞进项目规则段**：`resident === true` 的条目并入「项目规则」固定段，共享单条 5,000 / 合计 10,000 字符预算，且 fail-closed 于工作区信任——`src/agent/managers/residentRules.ts:23-37`、`:67-70`。目标是**临时且唯一**，项目规则是**稳定且多条**。
- ❌ **不能只是提示词**：见 §4.1 的收窄定义。

### 4.3 与 checkpoint 的分野（判断）

checkpoint 存「这一轮执行到哪了」（执行态，含 plan 快照）；指导文档存「要达成什么」（意图）。互不替代，不共享字段。

### 4.4 「同一时间只推进一个目标」的落点与纪律冲突

- 若选项目级（固定路径 + 归档目录）：文件在＝目标在，换目标＝旧文件归档 + 写新文件。
  - **必须补显式可见面**：仓库既有定案是「隐式切换：重配置对象只被显式调用」（`single-truth-source-mindset.md` 设计陷阱）。「文件在即激活」如果不是隐式状态，就必须有一处**显式呈现**（状态条 / 会话头一行「当前目标：X」）让人与模型都能看见。没有呈现面，它就是隐式切换，违反既有纪律。
  - **git 处置必须回答**：内容可能含个人计划 ⇒ 默认 `.gitignore` 排除工作区侧目录（判断，非取证）；归档目录同理。若用户要版本化目标，则改为显式提交策略——这是产品口径，见 §7.1。
  - **多根**：宿主的项目根口径是「一个宿主 = 一个项目」——`hosts/memora-vscode/src/extension/extension.ts:316-324`；多根工作区下「项目级」实际只覆盖首根，其余根无法表达。
- 若选会话级：只保证「一个会话一个目标」，多会话可多目标；**且不是「改动小」**——`SessionMeta` 是导出接口且有冻结成员面守卫（`src/__tests__/publicMemberSurfaceGuard.test.ts:915-928`），加字段即红，须改守卫基线。
- 多个目标文档可以存在，但**当前**只能有一个指针；不允许两个激活。
- 换目标处置：旧文档移入归档 + 指针切换（一步确定性动作）；**不做**「暂停目标」字段（那是第二个状态机）。

## 5. 切片规则必须进文档 + 一条弱保证

- 若切片与验收锚点由主助手临场决定，「整体按文档判」就退化为模型直觉，文档只是参考材料。
- 文档最少两节：**切片表**（id / 范围 / 验收锚点 / 依赖顺序）与**整体锚点**（切片齐备 + 集成项）。
- **主助手不得改写切片验收锚点**；派发时原样传递该切片段。
- **弱保证（必须写进边界）**：锚点是同一个模型在 P2 收敛时写的，§5 的「不得改写」只有**约定**、没有执行机制——模型仍可能在编排时重写锚点。**单裁决者 ≠ 裁判独立**。这是有意接受的弱保证；要变成强保证，需要「锚点哈希锁定 + 派发时比对」这类新机制，本文不做。

## 6. UI 形态（**本节为判断，不是取证**）

- **语义与 UI 解耦是纪律**：先定「谁判、判什么、状态放哪」，形态后议。
- 技术上：现有 VS Code webview **能承载**最小可见面（会话列表、目标卡片、子会话在跑/成败），不是硬阻塞。
- 真正受限的是**注意力与屏幕**：一个主助手 + 多个子会话要同时呈现「待办、在跑、卡住、待决策」，插件边栏装不下，也不该装。
- 结论（判断）：**将来可能需要独立客户端**——不是「现在不能在插件里做」。
- 推进顺序：**先语义 → UI 只做最小可见面（能看见子会话在不在、成没成、当前目标是哪一个）→ 真实使用后再定形态**。形态未定时，禁止把「专属 UI」当立项前提。

| --- | --- |
| 会话级（`SessionMeta` 字段） | 与会话即单位一致、天然跨重启；但命中冻结成员面守卫需改基线，且只保证单会话单目标；fork 不继承该字段（`SessionMeta` 现有语义以身份/命名/角色名为主，`src/memory/sessionStore.ts:110-128`），子会话需另定继承规则 |
| 项目级（固定路径文件） | 全局只可能一个目标、跨会话共享、无需新字段；但需回答 git 处置、多根只覆盖首根（`extension.ts:316-324`）、写入冲突（用户手改 vs 分叉写入）、可发现性（不加显式呈现面即违反「隐式切换只被显式调用」） |

**成本披露（不预选）**：两条都有硬成本，没有「更省」的一条。选哪条取决于「目标该属于项目还是属于一次对话」，这是产品定义，不是工程优劣。

### 7.2 口径二：子会话可见性（**已升为 P1 前置**）

| 选项 | 次生后果 |
| --- | --- |
| 进用户会话列表 | 实现最省（子会话就是普通会话）；但用户列表被派生会话淹没，「子」与「普通」不可区分；用户点进去只能看历史，看不到「进度」 |
| 隐藏子会话 | 需要新的存储归属与列表过滤规则（现有形态不存在）；且确认卡无人可见 → 见下 |
| **进列表但归组/折叠**（第三选项） | 保留可发现性又避免淹没；仍需一个「父子归属」字段与列表分组规则，成本介于两者之间 |

**与写确认的硬耦合（取证）**：确认队列只在**前台会话**推送（`confirmCoordinator.ts:206-210`），且计时只在首次上屏开始（`:262-264`）。**非前台请求永不上屏则永不计时，也就永不超时** ⇒ 若选「隐藏」且子会话还能写，父会**永久阻塞**。因此无论选哪个，v1 都必须让子会话**没有写工具**（§7.4）。

### 7.3 口径四：既有「≥3 次真实案例」纪律

既有结论要求子 agent 累计 ≥3 次真实案例才重启评估，至今 0 次；用户本次把它抬成硬前置。**本文不裁决是否破。**

- **什么算一例**（本版补）：一次真实使用（**失败的一次也算**）；同一场景连续重复只算 1 例；纯测试/纯演示不算。
- **记在哪**（本版补）：台账观察区一条累计（`tasks/待完成任务.md`），逐例记「场景 / 切片数 / 回传长度 / 是否人工纠偏 / 成败」，**不新建文件、不凭印象**。

| 选项 | 次生后果 |
| --- | --- |
| 破（直接进 P1） | 快速拿到第一条真实链路；但切片粒度、回传形态、并发与成本模型全靠推演，无数据校准；旧文 §7/§8 的否决与缺陷仍需逐条重新裁决，不因「前置提升」自动失效 |
| 不破（累计 3 例再进） | L2 只能以最小实验形态存在（单工具、深度 1、无组队）；L3 推迟 |
| 挪门槛（3 例守在 L3 入口，L2 期间逐例记账） | L2 在零案例下事实获准；门禁移到更难执行的位置（要等真实使用才凑得满）；「一例」判据刚立、尚无实践检验 |

**它不是免检**：3 仍是硬门槛，只是守在 L3 入口而非 L2 入口；L2 期间必须逐例记账，不足 3 例不进 L3。

### 7.4 已决项：v1 子会话「只读 + 禁提问」（附依据与代价）

- **依据一（工具面）**：`capabilities` 只能加特权、不能减常驻（`toolExecutor.ts:558-564`、`:963-980`）；常驻集含 `write_file` / `delete_file` / `run_command` / `ask_user`（`:502-533`）。**因此「用能力白名单做只读」不成立**——这是对审查建议中用代码证据的推翻。
- **依据二（写确认）**：子会话非前台 ⇒ 确认卡不上屏 ⇒ 不计时 ⇒ 永不超时 ⇒ 父永久阻塞（`confirmCoordinator.ts:206-210`、`:262-264`）。
- **依据三（提问）**：`ask_user` 命中即 `paused`（`src/agent/loop.ts:1692-1699`），同步调用里没人替它答 ⇒ 父卡死。
- **结论**：v1 必须引入一条**工具拒绝名单**（deny 优先于常驻豁免集），子会话注入 deny = 写/删/命令/脚本/`ask_user`。这是**新增不变量**，必须独立立项与独立验收（§9、§10 P1），不能当 P1 的小功能顺带。
- **代价**：P1 的子会话**只能看不能改**；「子会话负责改代码」要等到这条 deny 轴被接受并放开白名单子集之后。**这是有意的收窄，不是遗漏**。

## 8. 被推翻的判断（过程记录，不美化）

1. **子 agent 排在最后 → 改为 L2 硬前置**
   - 原来怎么想：先图片工具、再目标模式，子 agent 最后评估（依据旧文「半生长、不落地」）。
   - 为什么推翻：用户定义里 L3 的执行载体就是独立子会话；载体语义不存在时，L3 只能退化成单会话长任务。
2. **「你提前实现了会话层再生长一层」→ 其实只有实例面**
   - 原来怎么想：一会话一 Agent、独立执行，似乎就是子 agent。
   - 为什么推翻：实例隔离 ≠ 派生语义。父子、回传、配额、子轮归处四项全缺（§3.2/§3.3）。
3. **目标聚焦编排按「软档：文档常驻」理解 → 改为 L2 之上的编排层**
   - 原来怎么想：不加判定、只让文档常驻，靠模型自觉。
   - 为什么推翻：用户定义含「由助手操作独立子会话完成」——这是编排，不是常驻提示；软档解决不了「谁去干、干完怎么回流」。
4. **异步优先 → v1 同步**
   - 原来怎么想：Trae 形态是异步派发、随时查进度，理应照搬。
   - 为什么推翻：异步要求父持续在线等待，而现有 loop 没有等待态；父一收场，整体判定无人持有（§2.1）。
5. **（本版新增）「用能力白名单把子会话收窄成只读」→ 不成立**
   - 原来怎么想：按审查倾向，白名单一次性绕开写确认与提问两个洞。
   - 为什么推翻：白名单只能**加**特权工具，不能**减**常驻工具（`toolExecutor.ts:558-564`、`:963-980`）；常驻集已含写盘/命令/提问（`:502-533`）。只能新增 deny 轴。

## 9. 边界与新增不变量（集中一条边界）

**边界声明**：引入新不变式 = **必须单独立项**，本文只做路线与口径，不预支实现。

本路线触及的新增不变量（各自独立验收，不得塞进功能清单）：

1. **工具拒绝名单（deny）**：优先级 deny > 常驻豁免集 > 白名单；唯一判据点在 `isToolExposed` 层，三态语义不变（§7.4）。
2. **「当前目标」注入段**：新增 Prepare 段 + 独立字符预算 + fail-closed 同源（§4.1）。
3. **目标指针状态**：作用域一旦选项目级即新增「隐式状态」，必须配显式呈现面（§4.4）。
4. **派生深度 = 1**：**不需要新计数**——子会话装配时**不注入派发端口**，`delegate` 工具在子会话里根本不存在。这是端口层的结构性保证，不是新不变式，但必须有「孙派发被拒」用例。
