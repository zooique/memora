## 0. 本版三项裁决

### 0.1 术语正名（不改术语锚点）

本文此前把最上层写作「L3 目标模式」。**现正名为「目标聚焦编排（单 turn）」**。

**显式声明**：这不是 `terminology-anchor-rules.md` §5 定义的「目标模式」（那指**对多个 turn 的编排、只给目标文档、全自动至达成**，未实现）。本文讨论的是它的**前置阶段**：单 turn 内聚焦一个目标、由主助手操作独立子会话完成、需人工触发。

不改术语锚点的理由：锚点里的定义是远期锚，本文如果改写它，等于用一个未落地的方案定义覆盖既定术语；两个定义并存在参考文献里，未来必错一份。因此**本文不引入第二个「目标模式」定义，只用一个新名字指代自己的射程**。

### 0.4 v1 载体形态定案（2026-11-11）：父 turn 内的同步递归，不是会话实体

**定案**：v1 = 父那一 turn 内的同步递归。**不落 Round、不进会话列表、内存 messages 用完即弃**；结果从递归返回值经父的工具返回值通道回传。

**保留**（不随载体重订的结论）：

- **deny 轴**：§7.4 依据一已重写——`toolReadonly='readonly'` 能挡写盘和命令，但 deny 仍不可替代（可见面隐藏 / `ask_user` / 有副作用但不写盘的常驻工具）。
- **同步执行**（§2.5）：父在同一 turn 内等齐子结果，§2.1 的单裁决者前提才成立。
- **深度 1 + 同一步并发硬限**：子会话不注入派发端口（结构性），端口以 `SUBAGENT_MAX_CONCURRENT` 信号量硬限并发（取值见 `src/agent/assembler.ts`，文档不复述数字）。

**替换**（原 P1④「独立子会话 + 落 Round + 宿主派发端口」作废）：

- **不建会话实体**：不进 `AgentRegistry`、不写 `SessionMeta`、不建假 Round。
- **不碰确认队列**：子会话非前台，若还能写盘就会触发「不上屏 ⇒ 不计时 ⇒ 父永久阻塞」（§7.2 的硬耦合）；v1 用 deny 轴从根上不给写工具。
- **不写父状态**：不复用父 loop 的 `onToolExecuted` / `onPendingQuestion` 回调；子 loop 用独立 `ToolExecutor`。
- **结果形态**：子递归返回值（最终回答原文，截断上限 20,000 字），首行由内核按流标志生成确定性终态头部（四态成员与判据见 [loop-design.md](./architecture/loop-design.md) §5.3，本节不复制成员名）。

**形态细节与六条夹紧规则**的唯一落点是 [loop-design.md](./architecture/loop-design.md) §5.3；本节只记裁决与理由，不复制定义。

## 1. 结论先行

| 层 | 形态 | 一句话结论 | 依赖 |
| --- | --- | --- | --- |
| **L1 单会话助手** | 现状：一会话一 Agent，处理用户分散需求 | 已落地，是唯一有成体系支撑的一层 | — |
| **L2 主助手 + 独立子会话** | 主助手派生独立会话执行，结果回传 | 有「实例地基」但**没有语义**：缺派生、回传、配额、子轮归处，也缺「比默认更窄」的工具面 | L1 实例面 + §3.2 所列新增件 |
| **L3 目标聚焦编排（单 turn）** | 聚焦一个目标，先产出指导文档，再由主助手派子会话完成 | 是 L2 的**消费者**，不是兄弟；不加第二套完成判据 | **L2 全部** + 指导文档 + 跨 turn 状态 |

一句话版本：**L3 不能绕过 L2 生长；L2 必须同步做，否则 L3 的单裁决者前提不成立。**

> **载体口径订正（2026-11-11）**：上表 L2 的「独立子会话」是路线名，**不等于 v1 实现形态**。v1 不建会话实体、不落 Round（§0.4），因此表内「子轮归处」与 §7.2 的「列表可见性」不是 v1 的前置缺口，而是将来「独立子会话」形态的议题。v1 的可见性 = 父工具结果里的 `[SUBAGENT:*]` 头部。

## 2. 硬结论（连成立条件、代价与天花板一起写）

### 2.1 「一范围一裁决者」成立，但只在「父同一 turn 内等齐子结果」这个窗口内成立

- 取证：`done` 由**纯文本收场**产生——`src/agent/loop.ts:2008-2064`（`handleTextResponse` 在文本交付后 `yield done`）；由 `handleIterationResult` **消费**——`src/agent/loop.ts:1207-1239`。另有步数上限收场 `src/agent/loop.ts:1116`、用户硬中止 `src/agent/loop.ts:1210-1213`。
- 取证：任务表**无裁决权**，只是注入文本 `src/agent/assembler.ts:468-494`；turn 结束清空 plan，**暂停态例外**——`src/agent/agent.ts:1207-1224`（`:1214` 明写 `if (cp.pauseMeta) return;`）。
- 成立：子会话判自己那块（各自 turn），父在同一 turn 内判整体 —— 两个射程、各自一个裁决点，**不改现有判据**。
- 不成立：父跨 turn 推进 —— 父的 `done` 会在子还没回来时宣布整体完成；要补就得加第二判据或复活多 turn 编排。
- **推论（判断）**：异步派发让父先收场 ⇒ **异步必然破坏本结论**。

### 2.2 主助手不得复核子会话已交付的切片

同一切片若「子会话 `done`」+「父复核」两处都判，就是同一块两个裁决者。正确读法：**子会话判切片，主助手只判「整体锚点 + 切片齐备」**。

### 2.3 目标聚焦编排不加第二套完成判据

- 并列加一层「达成判定」⇒ 两个「算不算完」且无裁决顺序。
- 唯一站得住：父的**单 turn `done` 本身就是整体判定**，判据来自指导文档（文档进上下文，不另立裁决器）。
- 成立条件：父单 turn 长跑（§2.1）且不复核切片（§2.2）。任一破坏即失效。

### 2.4 父单 turn 的预算天花板（本版新增，原缺）

- 取证：默认迭代上限 **50**——`src/role-pack/strategyKeys.ts:41`；角色包最高可声明 **500**——同文件 `:86`；下限 10——`:79`。抬预算的唯一旋钮是**角色包配置**，没有「目标级预算」接口。
- 因此 P3 的真实形态是：**目标必须装进父会话当前角色包的 `stepBudget`**。默认 50 步装不下的目标，会撞上限收场，此时**根本没有整体判定**（父是被预算结束的，不是判定达成的）。
- 本文**明确不做**目标级独立预算（与 §10 一致）。代价：目标规模受角色包配置硬约束；P3 必须有一条「撞上限」失败路径用例，不得只验小目标。

### 2.5 v1 同步：已决 + 代价登记

- 已定：v1 用**同步工具**（一次调用阻塞到子会话收场），同一步多调用天然并行。
- 代价登记（不再作为待拍）：
  1. 拿不到「随时查进度」——同步调用期间父没有观察点。
  2. 父的 step 时间被拉长，用户可感知延迟（量级无样本，见 §11）。
  3. 子会话一挂起（`ask_user`）就会拖死父——因此 v1 必须禁子会话提问（§7.4）。
  4. 父 abort 后子不一定立刻停（协作式），存在「父收场、子仍在写」窗口——必须靠端口信号合并 + 验收用例兜（§10 P1）。

## 4. 「指导文档」的落点

内容与指针分两层，这是分工不是双写：

| 层 | 落点 | 谁写 | 谁读 |
| --- | --- | --- | --- |
| **正文（内容真源）** | 工作区产物文件（如 `docs/目标/<slug>.md`） | 一次收敛动作由主助手写入；后续只有主助手在有据可依时改 | **新增的 Prepare 注入段**（见 §4.1）每轮读入；子会话只收派发时传的切片段 |
| **指针（当前目标真源）** | 项目级固定路径 **或** `SessionMeta` 一个字段（作用域见 §7.1） | 收敛动作写、换目标时改 | 注入段与 UI 状态面 |

### 4.1 注入载体（本版补上，原缺）

- 现有唯一的「工作区文件 → 每轮固定注入」通道是 `resident` 项目规则段（`src/agent/managers/residentRules.ts:1-15`），而该段已被 §4.2 否掉（语义不同、共享预算、撞在途的常驻层收缩）。
- 因此 v1 定：**新增一个 Prepare 注入段「当前目标」**，只读指针指向的那一个文件；读盘判据、路径守卫、字符上限**复用同一套现成实现**（不另写第二份），fail-closed 同源（工作区未信任整段不注入）。
- 段内必须写明未注入原因：读取失败 / 文件缺失 → **段内一行「本次未注入（原因），下轮重试」**，落点是段内文案，**不新增 notice 通道**。
- 字符预算：单段上限**与项目规则段同量级但独立计数**（判断：先取 5,000 起，超限按序截断并标注），不与项目规则段共享预算——否则两段互相挤占，边界上会得出两个结论（同 `residentRules.ts:23-37` 的教训）。
- **「不能只是提示词」的准确含义**：不能靠模型自己想起来 `read_file`；必须有注入段。原 §4.1 那句话在本版按此收窄。

### 4.2 它不能是什么（逐条带证据）

- ❌ **不能是 checkpoint 字段**：goal 三字段曾存在于检查点，因零读取被作为**僵尸字段**删除——`src/agent/managers/sessionManager.ts:273-277`、`src/__tests__/publicMemberSurfaceGuard.test.ts:4-7`（GOAL-DRIFT-1）。
- ❌ **不能是记忆条目**：记忆是 round 摘要，参与衰减与 GC。
- ❌ **不能是任务表**：turn 级、结束即清空（暂停态例外，`src/agent/agent.ts:1214`）；任务项单 active 不变量的真源在 `src/agent/managers/sessionManager.ts:609-626`（写点契约 + `ensureActivePlanItem`），不是在消费侧。
- ❌ **不塞进项目规则段**：`resident === true` 的条目并入「项目规则」固定段，共享单条 5,000 / 合计 10,000 字符预算，且 fail-closed 于工作区信任——`src/agent/managers/residentRules.ts:23-37`、`:67-70`。目标是**临时且唯一**，项目规则是**稳定且多条**。
- ❌ **不能只是提示词**：见 §4.1 的收窄定义。

### 4.3 与 checkpoint 的分野（判断）

checkpoint 存「这一轮执行到哪了」（执行态，含 plan 快照）；指导文档存「要达成什么」（意图）。互不替代，不共享字段。

### 4.4 「同一时间只推进一个目标」的落点与纪律冲突

- 若选项目级（固定路径 + 归档目录）：文件在＝目标在，换目标＝旧文件归档 + 写新文件。
  - **必须补显式可见面**：仓库既有定案是「隐式切换：重配置对象只被显式调用」（`single-truth-source-mindset.md` 设计陷阱）。「文件在即激活」如果不是隐式状态，就必须有一处**显式呈现**（状态条 / 会话头一行「当前目标：X」）让人与模型都能看见。没有呈现面，它就是隐式切换，违反既有纪律。
  - **git 处置必须回答**：内容可能含个人计划 ⇒ 默认 `.gitignore` 排除工作区侧目录（判断，非取证）；归档目录同理。若用户要版本化目标，则改为显式提交策略——这是产品口径，见 §7.1。
  - **多根**：宿主的项目根口径是「一个宿主 = 一个项目」——`hosts/memora-vscode/src/extension/extension.ts:316-324`；多根工作区下「项目级」实际只覆盖首根，其余根无法表达。
- 若选会话级：只保证「一个会话一个目标」，多会话可多目标；**且不是「改动小」**——`SessionMeta` 是导出接口且有冻结成员面守卫（`src/__tests__/publicMemberSurfaceGuard.test.ts:915-928`），加字段即红，须改守卫基线。
- 多个目标文档可以存在，但**当前**只能有一个指针；不允许两个激活。
- 换目标处置：旧文档移入归档 + 指针切换（一步确定性动作）；**不做**「暂停目标」字段（那是第二个状态机）。

## 5. 切片规则必须进文档 + 一条弱保证

- 若切片与验收锚点由主助手临场决定，「整体按文档判」就退化为模型直觉，文档只是参考材料。
- 文档最少两节：**切片表**（id / 范围 / 验收锚点 / 依赖顺序）与**整体锚点**（切片齐备 + 集成项）。
- **主助手不得改写切片验收锚点**；派发时原样传递该切片段。
- **弱保证（必须写进边界）**：锚点是同一个模型在 P2 收敛时写的，§5 的「不得改写」只有**约定**、没有执行机制——模型仍可能在编排时重写锚点。**单裁决者 ≠ 裁判独立**。这是有意接受的弱保证；要变成强保证，需要「锚点哈希锁定 + 派发时比对」这类新机制，本文不做。

## 6. UI 形态（**本节为判断，不是取证**）

- **语义与 UI 解耦是纪律**：先定「谁判、判什么、状态放哪」，形态后议。
- 技术上：现有 VS Code webview **能承载**最小可见面（会话列表、目标卡片、子会话在跑/成败），不是硬阻塞。
- 真正受限的是**注意力与屏幕**：一个主助手 + 多个子会话要同时呈现「待办、在跑、卡住、待决策」，插件边栏装不下，也不该装。
- 结论（判断）：**将来可能需要独立客户端**——不是「现在不能在插件里做」。
- 推进顺序：**先语义 → UI 只做最小可见面（能看见子会话在不在、成没成、当前目标是哪一个）→ 真实使用后再定形态**。形态未定时，禁止把「专属 UI」当立项前提。

## 7. 待拍口径（只剩一、二、四；三已决）

### 7.1 口径一：目标状态的作用域

| 选项 | 次生后果 |
| --- | --- |
| 会话级（`SessionMeta` 字段） | 与会话即单位一致、天然跨重启；但命中冻结成员面守卫需改基线，且只保证单会话单目标；fork 不继承该字段（`SessionMeta` 现有语义以身份/命名/角色名为主，`src/memory/sessionStore.ts:110-128`），子会话需另定继承规则 |
| 项目级（固定路径文件） | 全局只可能一个目标、跨会话共享、无需新字段；但需回答 git 处置、多根只覆盖首根（`extension.ts:316-324`）、写入冲突（用户手改 vs 分叉写入）、可发现性（不加显式呈现面即违反「隐式切换只被显式调用」） |

**成本披露（不预选）**：两条都有硬成本，没有「更省」的一条。选哪条取决于「目标该属于项目还是属于一次对话」，这是产品定义，不是工程优劣。

### 7.2 口径二：子会话可见性（**已升为 P1 前置**）

> **v1 不适用（2026-11-11）**：v1 不建会话实体、不落 Round，因此「子会话是否进列表」在 v1 路径上不存在。本节口径保留给将来的「独立子会话」形态；v1 的可见性 = 父工具结果里的 `[SUBAGENT:*]` 头部。下文的写确认硬耦合仍是 v1 必须 deny 写工具的原因。

| 选项 | 次生后果 |
| --- | --- |
| 进用户会话列表 | 实现最省（子会话就是普通会话）；但用户列表被派生会话淹没，「子」与「普通」不可区分；用户点进去只能看历史，看不到「进度」 |
| 隐藏子会话 | 需要新的存储归属与列表过滤规则（现有形态不存在）；且确认卡无人可见 → 见下 |
| **进列表但归组/折叠**（第三选项） | 保留可发现性又避免淹没；仍需一个「父子归属」字段与列表分组规则，成本介于两者之间 |

**与写确认的硬耦合（取证）**：确认队列只在**前台会话**推送（`confirmCoordinator.ts:206-210`），且计时只在首次上屏开始（`:262-264`）。**非前台请求永不上屏则永不计时，也就永不超时** ⇒ 若选「隐藏」且子会话还能写，父会**永久阻塞**。因此无论选哪个，v1 都必须让子会话**没有写工具**（§7.4）。

### 7.3 口径四：既有「≥3 次真实案例」纪律

既有结论要求子 agent 累计 ≥3 次真实案例才重启评估，至今 0 次；用户本次把它抬成硬前置。**本文不裁决是否破。**

- **什么算一例**（本版补）：一次真实使用（**失败的一次也算**）；同一场景连续重复只算 1 例；纯测试/纯演示不算。
- **记在哪**（本版补）：台账观察区一条累计（`tasks/待完成任务.md`），逐例记「场景 / 切片数 / 回传长度 / 是否人工纠偏 / 成败」，**不新建文件、不凭印象**。

| 选项 | 次生后果 |
| --- | --- |
| 破（直接进 P1） | 快速拿到第一条真实链路；但切片粒度、回传形态、并发与成本模型全靠推演，无数据校准；旧文 §7/§8 的否决与缺陷仍需逐条重新裁决，不因「前置提升」自动失效 |
| 不破（累计 3 例再进） | L2 只能以最小实验形态存在（单工具、深度 1、无组队）；L3 推迟 |
| 挪门槛（3 例守在 L3 入口，L2 期间逐例记账） | L2 在零案例下事实获准；门禁移到更难执行的位置（要等真实使用才凑得满）；「一例」判据刚立、尚无实践检验 |

**它不是免检**：3 仍是硬门槛，只是守在 L3 入口而非 L2 入口；L2 期间必须逐例记账，不足 3 例不进 L3。

### 7.4 已决项：v1 子会话「只读 + 禁提问」（附依据与代价）

- **依据一（工具面，2026-11-11 重写）**：**原说法已订正**——旧文写「只有 deny 能实现只读」，不准确。`src/agent/toolRunner.ts:189-201` 的 `toolReadonly = 'readonly'` 已能按 `readonly` 标记挡下写盘与命令；`capabilities` 白名单确实只能加特权、不能减常驻（`src/agent/toolExecutor.ts:558-564`、`:988-997`），但它不是唯一的收窄手段。deny 轴**不可替代**的理由只剩三条：
  1. **从模型可见面隐藏**：`toolReadonly` 只在执行时拒绝，工具仍留在 `list` 里，模型会看见并反复尝试，白烧 step；deny 在 `isToolExposed`（`toolExecutor.ts:988-997`）第一行就把工具从可见面移除。
  2. **`ask_user` 管不到**：它是 `readonly: true` 的常驻工具（`toolExecutor.ts:521`），只读闸按 `readonly` 标记放行；真正的挂起发生在 loop 层（`src/agent/loop.ts:1726` `willSuspendForAsk` → `:1897` `handleAskUser`），只能靠 deny 挡。
  3. **有副作用但不写盘的常驻工具**：`remember_intel` / `task_table_write` / `task_table_update` / `register_work`（`toolExecutor.ts:517-522`）不经过 `write_file`，只读闸的「写盘」语义也不覆盖它们；按「副作用」枚举比按「是否写盘」更可靠。
- **deny 的取法（按副作用枚举，不按工具名直觉）**：写盘 / 删文件 / 跑命令 / 杀命令 / 跑项目脚本 / 跑技能脚本 / `ask_user`，再加 `remember_intel` / `task_table_write` / `task_table_update` / `register_work`。工具名真源 = `DEFAULT_EXPOSED_TOOLS`（`toolExecutor.ts:503-537`）。**代价**：子会话不能贡献情报和任务项，得队长自己汇总——这是有意选择，不是遗漏。
- **实现位置（硬约束）**：deny 判定必须放在 `isToolExposed` 第一行、**在 `customTools.has(name)` 之前**（`toolExecutor.ts:990`）——否则 MCP / 自定义工具会先命中「恒暴露」分支，直接绕过 deny。
- **依据二（写确认）**：子会话非前台 ⇒ 确认卡不上屏 ⇒ 不计时 ⇒ 永不超时 ⇒ 父永久阻塞（`confirmCoordinator.ts:206-210`、`:262-264`）。
- **依据三（提问）**：`ask_user` 命中即 `paused`（`loop.ts:1726` / `:1897`），同步调用里没人替它答 ⇒ 父卡死。
- **结论**：v1 必须引入一条**工具拒绝名单**（deny 优先于常驻豁免集与自定义工具），清单见上方「deny 的取法」。这是**新增不变量**，必须独立立项与独立验收（§9、§10 P1），不能当 P1 的小功能顺带。
- **代价**：P1 的子会话**只能看不能改**；「子会话负责改代码」要等到这条 deny 轴被接受并放开白名单子集之后。**这是有意的收窄，不是遗漏**。

## 8. 被推翻的判断（过程记录，不美化）

1. **子 agent 排在最后 → 改为 L2 硬前置**
   - 原来怎么想：先图片工具、再目标模式，子 agent 最后评估（依据旧文「半生长、不落地」）。
   - 为什么推翻：用户定义里 L3 的执行载体就是独立子会话；载体语义不存在时，L3 只能退化成单会话长任务。
2. **「你提前实现了会话层再生长一层」→ 其实只有实例面**
   - 原来怎么想：一会话一 Agent、独立执行，似乎就是子 agent。
   - 为什么推翻：实例隔离 ≠ 派生语义。父子、回传、配额、子轮归处四项全缺（§3.2/§3.3）。
3. **目标聚焦编排按「软档：文档常驻」理解 → 改为 L2 之上的编排层**
   - 原来怎么想：不加判定、只让文档常驻，靠模型自觉。
   - 为什么推翻：用户定义含「由助手操作独立子会话完成」——这是编排，不是常驻提示；软档解决不了「谁去干、干完怎么回流」。
4. **异步优先 → v1 同步**
   - 原来怎么想：Trae 形态是异步派发、随时查进度，理应照搬。
   - 为什么推翻：异步要求父持续在线等待，而现有 loop 没有等待态；父一收场，整体判定无人持有（§2.1）。
5. **（本版新增）「用能力白名单把子会话收窄成只读」→ 不成立**
   - 原来怎么想：按审查倾向，白名单一次性绕开写确认与提问两个洞。
   - 为什么推翻：白名单只能**加**特权工具，不能**减**常驻工具（`toolExecutor.ts:558-564`、`:963-980`）；常驻集已含写盘/命令/提问（`:502-533`）。只能新增 deny 轴。
6. **（2026-11-11 新增）独立子会话载体 → 父 turn 内同步递归**
   - 原来怎么想：P1 = 宿主派发端口 + 新建子会话 + 显式继承父角色包 + 落 Round。
   - 为什么推翻：v1 只需要「父 turn 内多一份隔离上下文」，不需要会话身份；建会话实体反而带出 Round 归属、列表可见性、确认队列三条副作用（§0.4）。角色包继承也随之失去理由——权限不再从角色包来。

## 9. 边界与新增不变量（集中一条边界）

**边界声明**：引入新不变式 = **必须单独立项**，本文只做路线与口径，不预支实现。

本路线触及的新增不变量（各自独立验收，不得塞进功能清单）：

1. **工具拒绝名单（deny）**：优先级 deny > 常驻豁免集 > 白名单；唯一判据点在 `isToolExposed` 层，三态语义不变（§7.4）。
2. **「当前目标」注入段**：新增 Prepare 段 + 独立字符预算 + fail-closed 同源（§4.1）。
3. **目标指针状态**：作用域一旦选项目级即新增「隐式状态」，必须配显式呈现面（§4.4）。
4. **派生深度 = 1**：**不需要新计数**——子会话装配时**不注入派发端口**，`delegate` 工具在子会话里根本不存在。这是端口层的结构性保证，不是新不变式，但必须有「孙派发被拒」用例。

### 13.1 概念（第三版）：不是新 agent，是把主会话装配成「只带会话管理工具」的主助手

先把结论钉死：**不新增一个「路由 agent」实体。路由 = 主会话本身，被宿主装配成只带会话管理工具的主助手；它不读文件、不跑命令，所有实际工作派给独立会话。**

两条边界要分清：

- **不是「每次 turn 之外再加一个路由大脑」**。那会多一次 LLM 调用、多一次上下文装配，且第二次调用的裁决者与第一次不是同一个。[目标模式生长探索-分层阶段化.md](./目标模式生长探索-分层阶段化.md) §4.1 已判过「在 turn 之上再包一层 turn」这个结构。
- **是「主助手这个会话的工具面被收窄到会话管理」**。它仍是同一个 `Agent` 类、同一套 loop；区别只在装配时给它的工具清单与系统提示（判断，落点见 §13.9）。

这个形态的四个直接后果（不是视情况而定）：

| 设计面 | 后果 |
| --- | --- |
| 协议 | 不需要「路由消息 / 路由会话」；主助手的工具是宿主注入的会话管理工具，子会话是宿主已有的普通会话 |
| 成本 | 路由本身便宜（一次工具调用），但**每件需要看工作区的事都要起一个完整会话**——这是硬价格，见 §13.4 |
| 可解释 | 一次派发 = 主助手过程流里的一行工具调用（目标会话 + 任务 + 回执）；不需要新的解释通道 |
| 可纠正 | 子会话可寻址 ⇒ 「停掉这个、换一个再派」在机制上可行（第一版说不可行，已订正） |

**与 §2.1 的关系（重要，登记为冲突）**：§2.1 的「一范围一裁决者」成立条件是「父在同一 turn 内等齐子结果」。路由形态是**异步**的：主助手派发后本轮可以结束，子会话各自 `done`，主助手在收到完成事件后的**新 turn** 里汇总。因此 §2.1 与 §2.4（父单 turn 预算天花板）**不再直接适用于路由形态**，P3 的分期前提需要另行裁决。本文只登记冲突，不替它调和。

### 13.2 两层结构与会话层落点

路由 agent 与会话内子 agent 是两层，不是一层：

| 层 | 谁在这里 | 管什么 | 实体 |
| --- | --- | --- | --- |
| **会话层** | 路由 agent = 主助手 | 创建会话、派活、查状态、读结果、停止、归档；不干活 | 宿主里一个个真实会话 |
| **会话内层** | 内核 loop + `delegate_task` | 一个会话自己干活时，用子 agent 隔离上下文 | 不是会话，也不需要是会话 |

因此「工具面只留会话管理」与「v1 子 agent 不是会话实体」**不冲突**：前者说的是会话层，后者说的是会话内层。路由 agent 与 `delegate_task` 没有直接联系，也不需要在两者之间做形态迁移。

**落点：会话层在宿主。**

- 宿主已经有：每会话一个 `Agent` 实例（`agentRegistry`）、会话存储、fork、rename、跨进程写锁、每个 Agent 独立的停止/暂停控制器。这些就是路由主助手需要的「会话实体」。
- 与手机方案共享同一批前置：per-session 视图状态、`handleInput` 定址、投影可复用、确认双投递（[手机方案](./方案-手机远程控制-20261110.md) §8 P0-1..P0-5）。**一套基础设施，两个消费者。**
- 内核零新增执行模型：主助手的每个工具都是宿主自定义工具，走现有 `customTools` 通道；子会话就是普通会话。

**会话层的硬边界与前置（必须写清）**：

1. **定位：一个项目、多个并行会话**。工作区根恒取 `workspaceFolders[0]`，无工作区兜底 `~/.memora`（`hosts/memora-vscode/src/extension/extension.ts:81-95`）。这是产品定位，不是缺陷：跨项目 = 多个窗口，每个窗口一个路由 agent。
2. **并发写策略：同一时刻只允许一个写会话**（硬约束，详见 §13.9）。读会话不限量；v1 不做 worktree、不做目录隔离、不做并行写。理由：多个会话同时写同一个项目，冲突在 git 层无法自动裁决；独立目录只是把冲突藏起来，不是消掉。
3. **后台子会话的确认卡不上屏**。确认队列只推前台会话（`confirmCoordinator.ts`），非前台永不上屏 ⇒ 永不计时 ⇒ 子会话第一次写盘就永久阻塞。**P0-4 是硬前置。**
4. **子会话完成 → 主助手自动汇总，没有现成触发**。内核跨 turn 自动续跑（Handoff）已于 2026-09-05 废弃。要么主助手在 turn 内轮询（白烧 step），要么宿主在子会话 settle 时投系统消息并起新 turn（可接后台任务回流 / Step 3 的 registry `kind='agent'` 设想）。**这是整个模式成立的前提，已提级为 H4（§13.9 第一位；防环/预算/去重见「H4 机制」）。**
5. **后台流不可见**。`post()` 对非当前会话的后台流一律丢弃，`_turnState` 只有单份。P0-1/P0-3 不做，主助手读不到子会话进展，手机也看不到。
6. **「工具面只留会话管理」在现有暴露模型里表达不出来**。`list` = 常驻 ∪ 白名单 ∪ 自定义 − deny，没有「只允许这些」的模式；`toolWhitelist=[]` 仍带常驻写工具。靠 deny 枚举全部内置工具是「点名必漏」。安全故事要成立，需要新增「封闭面」档位（§13.9 K1）。
7. **成本 N×**。每个子会话是完整 turn；主助手不带读文件工具 ⇒ 连「这个项目用什么框架」都要起会话。这是真实价格，不是缺陷，必须写进产品预期。

### 13.3 已定案（取证，不是本文判断）

这八条是后续设计的硬约束，不要再论证：

1. **内核/宿主边界**：会话、持久化、搜索均经注入端口，内核不含会话实现（`src/index.ts` 的 `ISessionStore` / `IRoundStore` / `ISessionViewLoader` 段）。“会话是实体”在 memora 里天然是**宿主概念**。
2. **宿主会话基建齐全**：每会话一个 `Agent` 实例（`hosts/memora-vscode/src/extension/host/agentRegistry.ts`）、会话存储、fork、rename、跨进程写锁、每个 Agent 独立的停止/暂停控制器（`src/agent/agent.ts` 的 `requestPause` / 中止入口）。
3. **v1 子 agent 在会话内层，不是会话实体**：父 turn 内同步递归，不落 Round、不进列表、无 id、不可单独读、不可单独停（[loop-design.md](./architecture/loop-design.md) §5.3）。这不影响路由——路由在会话层，不需要子 agent 变成会话。
4. **后台流不可见**：`post()` 对非当前会话的后台流一律丢弃，`_turnState` 只有单份（[手机方案](./方案-手机远程控制-20261110.md) §2 F3/F4）。
5. **一个宿主 = 一个项目**：工作区根恒取 `workspaceFolders[0]`，无工作区兜底 `~/.memora`（`hosts/memora-vscode/src/extension/extension.ts:81-95`）。
6. **暴露模型只能加/减，不能「只允许」**：`list` = 常驻 ∪ 白名单 ∪ 自定义 − deny（`src/agent/toolExecutor.ts` 的 `list` 语义）；`toolWhitelist=[]` 仍带常驻写工具。
7. **手机 MVP 边界**：无系统推送、无语音、只保证前台（[手机方案](./方案-手机远程控制-20261110.md) §9.2 / §11.1）。
8. **队伍不是执行体池**：`setRolePackTeams` 注释明写「组员仅会议参与，不用于日常」（`src/role-pack/rolePackManager.ts:446-451`）；`run_team_meeting` 是一次内嵌 `provider.chat()`，单轮、无工具循环（`src/agent/builtinTools.ts:559-580`）。原判断保留，不订正。

> **v1 的既有呈现仍有效**：`delegate_task` 的派发/回执行已经落在过程流里（`tool_start` 的 `args` + `tool_result.delegate`，`src/memory/roundStore.ts:289-318`；宿主渲染 `hosts/memora-vscode/src/webview/scripts/processFlowCells.ts:229-305`）。会话层方案的派发行是**宿主自定义工具**，不是 `delegate_task`，但「派发=过程流一行」这条形态可复用。

### 13.4 我建议这样定，待复核

#### 13.4.1 工具面清单（什么算「会话管理」）

判据：**只改「有哪些会话、会话在干什么」，不改工作区内容。**「读一个文件」不算——那是子会话的事（与用户判断一致）。

| 能力 | 算会话管理 | memora 对应 | 现状 |
| --- | --- | --- | --- |
| 创建会话 | 是 | `createSession`（chatPanel）/ `newSessionFromCommand` | 有，但由 webview 驱动；需可编程入口且不抢 PC 焦点 |
| 派发消息 | 是 | `handleInput` | 有，需 `sid` 定址（手机方案 P0-2） |
| 列会话 | 是 | 会话列表 + `refreshSessionActivity` | 有，需补状态与待审批数 |
| 读历史 | 是 | `RoundStore` + 投影 | 有数据，需可复用的 `project(sid)`（P0-3） |
| fork | 是 | `agent.forkSession()` | 有 |
| 改标题 | 是 | `sessionManager.renameSession` | 有 |
| 停/暂停单个会话 | 是 | 每 Agent 的 controller / `requestPause` | 有 |
| 回复用户 | 是 | 主助手自己的最终回答 | 有 |
| 定时任务 | 是（Trae 有） | 无用户级调度器（现有 `setInterval` 只服务 GC 与 UI 计时） | **缺口**；v1 不做，不假装有 |
| `ask_user` | 否 | 正文直接问，结束本轮即可 | 不需要 |
| 读文件 / 跑命令 / 搜索项目 | 否 | 子会话的工具面 | 由子会话承担 |
| 记忆召回 / 技能 / 任务表 | 否 | 子会话 | 主助手不碰 |

**代价必须写明**：主助手不能自己回答任何需要工作区事实的问题——它只能从当前对话与子会话标题里答，其余一律派发。这是这条硬约束的价格，不是缺陷。

#### 13.4.2 输入 / 输出

- **输入**：主助手自己的对话上下文 + **会话列表（工作记忆）**。不读设备信息、不读「模式」位。
- **输出**：具体工具调用 + 参数，不是抽象的「路由决策对象」。建议参数形状：
  - `create_session { title?, rolePack? } → { sid }`
  - `send_message { sid, text } → { accepted }`
  - `list_sessions { filter? } → [{ sid, title, state, pendingApprovals }]`
  - `read_session_history { sid, lastN } → [{ roundId, user, assistant, tools }]`
  - `stop_session { sid }` / `pause_session { sid }` / `rename_session { sid, title }`
- **派发内容纪律**（Trae 的三条，落到参数）：传目标、上下文、约束；不重复子会话已有的内容；不在子会话里塞执行纪律（纪律归角色包 / 项目规则）。
- **先问一句**：直接用正文提问并结束本轮，不需要 `ask_user`——用户下一句就是答案。这样「只留会话管理」不被打破。

#### 13.4.3 可解释，以及「决策与呈现」的二分（订正第一条）

**决策与端无关**：同一句话、同样的上下文与会话列表状态，必须得到同一个路由结果。禁止在决策里读设备信息——否则同一句话在两端结果不同，不可解释、不可复现。

**呈现按端裁剪**：同一份结果，桌面给完整卡片，手机给一句话 + 可展开。裁剪**只作用在呈现层**，不回流契约、不写回存储、不产生第二份数据（投影函数参数化，见 §13.5）。

> **原说法已订正**：第一版写「不做设备感知路由」时把「决策」和「呈现」混成了一件，砍掉呈现适配会得到「手机上给你一段 800 字摘录」。现在按二分执行。

可解释的三级（保留前两级）：

| 级 | 内容 | 评价 |
| --- | --- | --- |
| L0（必做） | 主助手过程流里的派发行：目标会话 + 任务摘要 + 状态/回执 | 一次派发的最低可见面 |
| L1（建议） | 派发前一句 `narrate` | 复用现有通道；模型不一定说，说错比不说更糟，所以是补充不是契约 |
| L2（不建议） | 结构化「路由理由」字段 | 模型自证无校验 |

#### 13.4.4 可纠正（订正第二条）

- **这一次**：会话层方案下会话可寻址 ⇒ `stop_session(sid)` + `create_session` + `send_message` 就是一次真改派。机制上可行（第一版说「不做就地改派」是按 v1 同步递归写的，已订正为「机制可行、UI 暂不做」）。
- **以后的默认**：落项目规则 / 角色包 persona，不落 UI 本地状态。
- **不做**：过程流内下拉改派。不是机制缺失，是 UI 成本与收益不匹配；先让用户用一句话完成同样的事。

#### 13.4.5 落盘

- 主助手的每次派发 = 它自己 Round 里的一条 `tool_start` / `tool_result`（宿主自定义工具同样走过程流）。
- 子会话自己的 Round 落在自己的会话里，不复制进父会话。
- **父子关系**是宿主级元数据（内核 `SessionMeta` 有冻结成员面守卫，不加字段）：唯一落点是宿主侧一张 `parentSessionId` 关系表；UI / 手机都从这一份读，不各存一份。
- 不新增 `route_decision` 事件类型：派发已经是工具调用，双载没有收益。

### 13.5 宿主 UI

- **主助手就是一个普通会话**。它的过程流里，派发是一行自定义工具调用（目标会话 + 任务 + 状态）；点这一行应能跳到目标会话（建议，待复核）。
- **历史会话列表按父子归组**：主助手 → 子会话（可折叠）。这正是 [sub-session-visibility-and-goal-scope.md](./architecture/sub-session-visibility-and-goal-scope.md) §1 当年为「独立子会话」保留的口径，现在由会话层方案让它重新适用。
- **不新增路由面板 / 模式徽标**：策略开关若将来需要，挂输入区权限档位那一层；「这次派了谁」挂在过程流那一行。
- **补两个现状缺口**：① 后台会话流当前被丢弃（P0-1/P0-3），不补主助手看不到子会话进展；② 子会话的待审批数要进列表（复用 `refreshSessionActivity`，手机方案 P1-7）。
- **停止语义要写清**：停主助手 ≠ 停子会话（它们是独立会话）。UI 必须明确「停止主助手本轮」与「停止该子会话」，不能一个按钮两种含义。**不做级联停止**，两条理由：① 停止语义会变模糊——用户点停止，是想停当前这一个、停这一批、还是全停？按钮只有一个，级联停止把明确的「停当前」变成需要猜的「停到哪一层」；② 级联停止要求主助手在线才能执行，而「按住停止」必须是本地立刻生效的动作，不能依赖某个 agent 恰好还活着。

### 13.6 手机控制（结论 + 指针）

完整约束见 [手机方案 §14](./方案-手机远程控制-20261110.md)。三条结论：

1. **决策不分端，呈现分端**：手机拿结论 + 四态 + 可追问入口；摘录全文与执行耗时（诊断信息）可省。
2. **子会话可单独停**（订正）：会话层方案下每个子会话是独立 Agent，有独立控制器；v1 `delegate_task` 的「只能停整轮」不适用于路由形态。
3. **子会话的审批必须在手机上可见可答**：否则后台子会话永久阻塞（P0-4）。审批卡必须显示来源会话。

### 13.7 只是选项，不建议现在做

| 选项 | 为什么现在不做 | 什么条件下才值得重开 |
| --- | --- | --- |
| 独立 router agent（每次 turn 外多一次调用） | 13.1：多一次调用、多一次装配，且两个裁决者 | 出现「必须用另一个模型做路由」的实证需求（路由模型与执行模型不同且成本更低） |
| 自动切换角色包 | 角色包是用户显式选择并写回会话文件；自动换会与 `rolePackSwitched` 事件链冲突 | 用户明确提出「让助手自己决定用哪个人格」，且能回答「换包后旧包规则残留怎么办」 |
| 把队伍当执行体池 | 与 `setRolePackTeams` 注释直接冲突；且要重新回答权限（存档 §7 已否决「能力继承队长」）与回传（会议无工具循环） | 用户明确要「组员日常干活」，并接受重新设计权限与回传 |
| **设备感知的路由决策** | 决策必须与端无关；呈现分端已采纳（§13.4.3） | 不重开：决策层永远不读设备 |

| 过程流下拉改派 | 机制已可行（停旧 + 建新 + 再派），UI 收益不抵成本 | 用户一天内多次用一句话改派，且明确嫌慢 |
| 结构化路由理由字段 | 模型自证，无校验 | 出现「用户需要审计为什么这么派」的合规需求 |

| 定时任务工具 | 调度器一进内核，就要处理「触发时无人到场」「失败谁重试」「多个定时任务撞同一工作区」三件新状态机，会把会话层复杂度提前拉进来；不是不急，是不该现在拉 | 用户提出「每天几点自动跑一次」的真实需求，且上面三件事有答案 |
| 每子会话独立工作目录 / 并行写 | 不做，而且不是做不到：同一项目并行写会在 git 层打架，独立目录只是把冲突藏起来；v1 串行写（§13.9 并发写策略） | 真出现并行写需求时，按 worktree 立项，不是加配置 |
| 主助手带只读工作区工具 | 与「只留会话管理」的硬约束冲突 | 成本 N× 被实测证明不可接受，且用户愿意放宽约束 |

### 13.8 三条判据收口

**SSOT**：

- **会话关系一份**：宿主侧 `parentSessionId` 表，UI / 手机 / 主助手都从它读。
- **会话状态一份**：`refreshSessionActivity` / 投影（P0-3），主助手与手机共用同一投影函数。
- **决策记录一份**：主助手自己 Round 里的 `tool_start` / `tool_result`。
- **主助手不维护任务表**：会话列表就是它的工作记忆（用户第 1 点）。多一份 plan 就是第二真相源。
- 禁止新增 `route_decision` 字段 / 表 / 事件。

**自然生长**：

- 挂「目标模式」？不。目标是跨 turn 自动推进（未实现），会话层方案是异步会话管理；两者可以叠，但不是一回事。
- 挂「角色包」？不。换装 ≠ 分派；自动换装还会破坏用户显式选择契约。
- 挂「队伍」？不（现在）。注释已钉死「组员仅会议参与」。
- 挂「过程流」？是。派发就是工具调用一行，`delegate_task` 已经证明这个形态成立。
- 挂「手机桥」？是。同一份会话 API / 投影，两个消费者（人与主助手）。

**不带伤（会做出「一半」的做法，逐条排）**：

| 半截形态 | 为什么是半截 | 本文处置 |
| --- | --- | --- |
| 有会话工具、读不到历史 | 主助手只能瞎派，无法判断进展 | 读历史是 P2 的硬入口，不满足不宣称「路由可用」 |
| 能建会话、不能单独停 | 跑飞的任务只能杀整轮 | 每会话控制器已有；必须接到工具上 |
| 后台子会话审批不上屏 | 第一次写盘就永久阻塞 | P0-4 硬前置 |
| 派发没有完成触发 | 主助手永远不汇报，用户以为它忘了 | H4 先定，再宣称「自动汇总」 |
| 用 deny 枚举实现「只留会话管理」 | 新增内置工具会静默泄漏进主助手 | K1 封闭面档位；枚举只作临时兜底 |
| 手机只给 800 字摘录 | 屏幕上不可用 | 呈现分端：结论 + 四态 + 可追问 |
| 手机只给一句话、不能展开 | 用户无法核验，只能盲信 | 保留可展开入口 |
| 允许多个写会话并行 | 同一文件互相覆盖，冲突在 git 层无法裁决 | 串行写（§13.9 并发写策略） |
| 把「跨项目并行」当默认能力 | 一个宿主 = 一个项目；跨项目是多窗口 | 定位为「一个项目、多个并行会话」 |

### 13.9 会话层方案的最小改动集

**内核（只一项）**

- **K1 封闭工具面档位**（allow-only / profile）：`list` 从「常驻 ∪ 白名单 ∪ 自定义 − deny」增加一条「只允许显式清单」的装配档。理由：主助手的安全故事是「它只能管会话」，而现有模型只能加/减；`toolWhitelist=[]` 仍带常驻写工具，deny 枚举必漏。**这是新增不变量，必须单独立项、独立验收**（含公开面登记）。
- 其余零改动：会话实体在宿主，内核不需要认识父子关系；子会话就是普通 `Agent`。

**宿主（七项，按依赖排序）**

| # | 改动 | 说明 |
| --- | --- | --- |
| **H4（提级，第一位）** | **子会话 settle → 主助手新 turn** | 整个路由模式成立的前提；触发源、防环、预算、去重见下方「H4 机制（v1 定稿）」 |
| H1 | 会话管理 API | 可编程、`sid` 定址、不抢 PC 焦点、不走 draft 分支；**手机与主助手共用** |
| — | P0-1..P0-5 | 手机方案 §8 的五条硬前置（per-session 状态 / handleInput 定址 / 投影 / 审批双投递 / 附件解耦） |
| H2 | 主助手装配 | 会话工具 + 封闭面（K1）+ 不注册 MCP / 自定义写工具；角色包只给 persona |
| H3 | 父子关系表 + 列表归组 | 宿主级 `{ childSid, parentSid, parentRequestId, dispatchedRoundId }`；历史列表可折叠分组；H4 的分组与去重都读这一份 |
| H5 | 停止语义分档 | 「停主助手本轮」≠「停该子会话」；两个入口，两个文案 |
| H6 | 并发与成本上限 + **并发写策略** | 同一宿主窗口共享工作区；**同一时刻只允许一个写会话**，读会话不限量；v1 不做 worktree / 目录隔离 / 并行写。深度 1 结构性：只有主助手装配会话工具。 |
| H7 | 派发行渲染 + 跳转 | 过程流一行；点击跳到目标会话（可选） |

**H4 机制（v1 定稿）**

1. **触发源：宿主监听子会话的 turn 终态，不靠模型自报。** 会话从 running 落到 settled / failed / interrupted 时，宿主生成完成事件；会话列表用的 `refreshSessionActivity` 读同一份状态，不另造一套。派发时在 H3 关系表里写入 `parentRequestId`，完成事件带着它回来。

2. **环怎么断：汇报轮禁止派发。** 完成事件触发的主助手 turn 打标记 `origin = 'child-settled'`；该轮里 `create_session` / `send_message` 直接返回错误「汇报轮不可派发」。代价：汇报轮不能自动重派、不能自动追问；子会话失败时主助手只能汇报，用户再说一句才重派。**被否方案**：① 只靠提示词「汇报轮不要派发」——模型可能不听，环就断不了；② 「只有用户发起的 turn 才允许派发」——太宽，把「用户说完后同一 turn 连派」也禁了，等于砍掉主流程。

3. **批量与预算：一次用户请求最多 1 次汇报轮，且只在「该 `parentRequestId` 名下没有在跑的子会话」时触发。** 3 个子会话完成不会出 3 条碎片汇报；代价是最慢的那个会拖住整批，卡死的子会话会一直拖（会话列表仍显示 running，用户能看见并手动停）。**超了怎么办：不静默截断**——超出的完成事件只更新列表状态和未读标记，不再起 turn；用户下次说话时，宿主把这期间完成的会话作为一条系统消息注入（复用 `appendSystem`），列表保留未读。**被否方案**：每个完成事件各起一个 turn——N 个子会话就是 N 条碎片汇报，且每条都可能再派，环的概率和噪音都翻倍。

4. **去重：`(sessionId, roundId)` 内存集合，一个回合的终态只通知一次。** 宿主重启会杀掉全部子会话（它们就在扩展宿主进程里），不会留下「人死了事件还在」的情况，所以 v1 不持久化去重集合；内存集合按会话保留最近 N 条，防无限增长。**被否方案**：① 只用 `sessionId`——一个会话可以完成多轮，会吞掉合法的第二次完成；② 事件自带全局 id——当前链路没有稳定的跨重启事件 id，为一个宿主生命周期内的问题加协议字段不划算。

**并发写策略（硬约束）**：同一宿主窗口内多会话共享工作区；同一时刻只允许**一个写会话**在跑，读会话不限量。v1 不做 worktree、不做目录隔离、不做并行写。为什么这样切：多个会话同时写同一个项目，冲突在 git 层无法自动裁决；独立目录只是把冲突藏起来，不是消掉。先串行是「不带伤」的选择；等真有并行写需求，再谈 worktree 隔离——那时是立项，不是配置。

**现在就能做**：H1 + P0 + H3 + H7（H1/P0 同时解锁手机 M1，不白做）。
**必须先定才能承诺**：H4（自动汇总）+ K1（安全故事）。没有 H4，「我干完会跟你说」就是假的。
**必须等新形态**：系统级推送；并行写（worktree）作为独立立项。

### 13.10 分期（边界与「为什么这样切不带伤」）

| 期 | 内容 | 独立可验收 | 明确不做 |
| --- | --- | --- | --- |
| **P1 基础设施** | P0-1..P0-5 + H1 会话 API | 手机能看到**后台**会话；主助手能列会话、按 `sid` 发一句 | 任何主助手工具面、任何父子归组 |
| **P2 路由闭环** | K1 + H2/H3/H5 + **H4** | 一句话 → 建会话 → 派任务 → 子会话完成 → 主助手新 turn 自动汇总 | 手机端回执、系统推送 |
| **P3 手机与体验** | 手机 `attention` + H7 跳转 + 归组 | 手机收到一条结论；点派发行能跳到子会话 | 多级父子、级联停止 |
| **P4 调优** | H6 并发/成本 + 串行写压测 | 3 个读会话并行 + 1 个写会话不打架；成本可观测 | worktree、定时任务 |

**为什么这样切不带伤**：P1 与手机共享，不做白工；P2 把 H4 纳入闭环——「主助手会汇报」不再依赖用户追问，这是路由模式和「一个能派活的聊天框」的分界线；P3 才做手机回执；P4 才压并发。每一期都有可演示的闭环，不靠「以后会好」。
