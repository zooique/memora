# 后台任务跨轮存活（CMD-1 阶段 3 · 「后台」名副其实）

> **来源**：2026-10-04 用户真机反馈——起后台命令后 turn 结束，UI 底部条从「运行中」变「已终止」，
> 而用户**从未点过终止**。助手正文还说「后台运行中，完成后结果会自动回到上下文」。
> **纪律**：设计决策先文档化为闭合闭环，再开始代码实现。本文是实施规格真源。

---

## 一、缺口实锤（真机记录，非推断）

证据文件：`F:\用户目录\Desktop\小说项目\.memora\rounds\round-1791074929352.json`

| 时刻 | 事件 |
| --- | --- |
| 00:48:52 | `run_command` 返回 `[BACKGROUND_STARTED] taskId=bg-1` |
| 00:48:53 | 助手正文：「**状态：后台运行中，完成后结果会自动回到上下文**」 |
| 00:48:55 | `background_report`：「本轮仍有 1 个后台命令在运行，**已全部终止**（其输出不再回流）」 |
| 00:48:55 | 本轮结束，**全程 6.286 秒**（命令需 90 秒） |

⇒ **按钮可见的 3 秒里进程已被杀**；用户未点击。`killed` 由 turn 终态收割产生，非用户操作。

### 三个根因（逐条 grep 定位）

| # | 根因 | 位置 | 性质 |
| --- | --- | --- | --- |
| 1 | 回执文案承诺「完成后结果会自动进入你的上下文」「期间可继续其它工作」，**只字未提 turn 结束会终止** | `src/agent/toolExecutor.ts:1500` | **内核对用户说谎**——模型只是照抄 |
| 2 | turn 终态 `reapAll()` 无条件杀光存活后台任务 | `src/agent/loop.ts`（`finalizeBackgroundTasksOnTurnEnd`） | **`background` 名不副实**：实为「本轮内异步」 |
| 3 | `killed` **混装**「用户主动杀」与「turn 收割杀」，UI 一律显示「已终止」 | `src/agent/backgroundTasks.ts`（`kill()` / `reapAll()` 皆置 `killed`，无原因字段） | **UI 不可解释** |

## 二、主流对标（外部实锤，2026-10-04 查证）

| 产品 | 进程活过 turn | 结果取回 | 主动唤醒 |
| --- | --- | --- | --- |
| **Claude Code** | ✅ 活到进程退出 | ✅ 输出重定向到文件 + Read 按需取 | ❌ |
| **Trae** | ✅ | ✅ 新问一句 | ❌（**官方承认**） |
| **memora 现状** | ❌ **turn 结束即杀** | ❌ | ❌ |

- **Claude Code**：输出写文件（不占上下文）、任务 ID 跟踪、清理规则 = 退出时清 / 输出 >5GB 终止 /
  macOS-Linux 内存压力空闲 30min 回收。可后台化的典型场景明确包含 **dev server、watch**（即永不结束的任务）。
- **Trae**：用户原话「它经常说在后台执行，执行结束后我会怎样，但我根本没有途径获取怎么样了，
  **有时候早就执行完了还得我新问一句**」。官方答复：「Agent 将长任务挂到后台执行后，当前轮次的对话就
  结束了。目前它**无法在后台进程结束时主动发消息唤醒你**并报告结果」。

**结论**：三家都不主动唤醒（这是行业共性缺口）；**memora 更差一档——唯一在 turn 边界杀人的**。
本方案补的正是「杀进程」这一档，**不碰「主动唤醒」**（见 §五）。

## 三、设计定案：**两句话**

> **一、别杀它。二、别扔它的结果。**

`finalizeBackgroundTasksOnTurnEnd` 现有两个动作，**拆开处理、一动一留**：

| 动作 | 现状 | 改后 | 理由 |
| --- | --- | --- | --- |
| 丢弃 `command-result` 队列 | `filter(r => r.kind !== 'command-result')` | **删除此行** | 见 §3.1 判据对齐 |
| 处理存活后台任务 | `reapAll()`（杀光） | **改为脱管不杀**（`detachAll()`） | turn 不是进程的容器 |

### 3.1 为什么删那一行是对的（SSOT 论证，非「放宽限制」）

「回流不跨 turn」这条旧定案，**只封杀了 `command-result`，却放行了 `interject`**：

| 跨 turn 注入的数据 | 旧定案态度 | 性质 |
| --- | --- | --- |
| 用户插话 `interject` | ✅ 放行（`clearPendingInterjections` 明确只清 `interject`） | 外部产生的事实、显式一条消息、`appendUser` |
| 后台结果 `command-result` | ❌ 封杀 | 外部产生的事实、显式一条消息、`appendSystem` |

**两者性质完全相同，却用两套标准** ⇒ 违反 SSOT。且 turn 内部跑的 `command-result` 走的就是同一条
通路（`_handleInterrupt` → `appendSystem`），**机制在 turn 边界突然失效，是不一致而非保护**。

⇒ 本次**不是推翻一条定案，是补齐一条没贯彻到底的判据**。

### 3.2 为什么成本能压到「删一行」（实现事实）

| 事实 | 位置 | 推论 |
| --- | --- | --- |
| `loop` 是 **Agent 级单例**（装配时创建一次，close 时置 null） | `agent.ts:1350` / `:1907` | `interruptQueue` **天然跨 turn 存活** ⇒ 无需新存储 |
| `clearPendingInterjections()` **只清 `kind==='interject'`** | `loop.ts` | 两个清理点**设计时已分流**，删掉的那行不与它冲突 |
| 队列消费通路 `_handleInterrupt` → `appendSystem` | 已有 | **零新工具 / 零新队列 / 零新状态机** |

### 3.3 用户视角的两种情形（**同一机制的两个时刻**，非两套机制）

| 情形 | 队列状态 | 用户动作 | 结果 |
| --- | --- | --- | --- |
| 后台跑完，用户**还没开新 turn** | 条目躺在 `interruptQueue` | 下一条消息发出去 | 新 turn 首 step 边界吸收 ⇒ 结果进入本轮上下文 |
| 后台跑完，**用户已开新 turn** | 同上，被吸收 | 无需额外动作 | 排队中，当前轮迭代即拿到 |

⚠️ **诚实边界**：若用户开了新 turn 且该轮**立刻收尾**，队列条目会留到**下一个** turn。
这是「排队」而非「丢失」，不丢数据。

## 四、诚实口径（必做，否则本方案只做了一半）

进程**活过 turn，但活不过 extension 进程**——窗口关闭即终止。这与 Claude Code 同源
（官方：tasks are automatically cleaned up when Claude Code exits），**不是缺陷**，
但**必须写进工具描述与回执文案**，否则又是一轮「说了不算」。

文案改法（刀 2 执行）：

| 位置 | 现状 | 改后口径 |
| --- | --- | --- |
| 回执 `[BACKGROUND_STARTED]` | 「完成后结果会自动进入你的上下文」 | 「命令已在本轮之外继续运行；**结果不会自动进入当前上下文**，你可以在后续任意一轮用 `kill_command` 传入该 taskId 取回截至当时的输出」 |
| 工具描述 `background` 参数 | 「true = 后台执行：立即返回 taskId，结果完成后自动回到上下文」 | 删去「自动回到上下文」承诺，补「活过本轮、活不过宿主进程」 |

**校验点**：改后文案里**不得出现**「自动回到上下文」「完成后你就会看到」类承诺。

## 五、刻意不做（含触发条件，不写「已做」）

| 不做项 | 理由 | 触发条件（何时重启） |
| --- | --- | --- |
| **A · turn 挂起等后台跑完**（用户原始提议） | `pause` 走 `interruptQueue` 的 `kind:'pause'`，**由 step 边界消费**（非立即生效），且唤醒依赖**用户手动 `resumeExecution`**。让后台完成自动唤醒 = **新开一条唤醒通路**（新机制），另需处理「dev server 永不结束 ⇒ turn 永久挂起」与 pause 态语义分叉 | 真机出现「模型在同一 turn 内必须等后台结果才能回答」 |
| **C · 无新 turn 时自主起新 round 汇报**（用户「诈尸复活」） | `externalTaskLoop`（自主多轮编排）已于 **2026-09-04 整体删除 1181 行**，设计定案「复杂度在单 turn 内自然生长」。复活 = 新能力面 + 一串未定边界：用户输入中如何打断 / 自主轮 `userMessage` 写什么 / 落盘与归档归属 / 多任务完成合并成几轮 / 自主轮再起后台任务是否防死循环 / 重启是否恢复 | 真机出现「用户反复抱怨要再问一句」（Trae 社区同款） |
| **主动唤醒推送**（三家都缺，memora 的差异化机会） | 需新建「任务终态迁移 → 宿主 notice」事件通路；刀 3 的后台任务条已具备 UI 底座 | 本方案落地后真机验证 |
| **保质期**（陈旧结果防突兀） | `MAX_PENDING_COMMAND_RESULTS` 限量 + Agent close / 切会话队列自然清空 = 天然有界 | 真机出现「结果隔夜突现且模型误当相关」 |
| **终止原因字段**（区分手动杀 / 超时强杀） | detach 落地后，「turn 收割」这个**最误导的原因消失**，剩余两种（手动 kill / 30min 超时强杀）语义接近 | 真机出现「用户以为是自己杀的，其实是超时」 |
| 跨 Agent / 跨会话的后台任务管理 | 注册表按实例隔离是硬不变量 | 不做（永久） |
