# 后台任务跨轮存活（CMD-1 阶段 3 · 「后台」名副其实）

> **来源**：2026-10-04 用户真机反馈——起后台命令后 turn 结束，UI 底部条从「运行中」变「已终止」，
> 而用户**从未点过终止**。助手正文还说「后台运行中，完成后结果会自动回到上下文」。
> **纪律**：设计决策先文档化为闭合闭环，再开始代码实现。本文是实施规格真源。

## 一、缺口实锤（真机记录，非推断）

证据文件：`F:\用户目录\Desktop\小说项目\.memora\rounds\round-1791074929352.json`

| 时刻 | 事件 |
| --- | --- |
| 00:48:52 | `run_command` 返回 `[BACKGROUND_STARTED] taskId=bg-1` |
| 00:48:53 | 助手正文：「**状态：后台运行中，完成后结果会自动回到上下文**」 |
| 00:48:55 | `background_report`：「本轮仍有 1 个后台命令在运行，**已全部终止**（其输出不再回流）」 |
| 00:48:55 | 本轮结束，**全程 6.286 秒**（命令需 90 秒） |

⇒ **按钮可见的 3 秒里进程已被杀**；用户未点击。`killed` 由 turn 终态收割产生，非用户操作。

### 三个根因（逐条 grep 定位）

| # | 根因 | 位置 | 性质 |
| --- | --- | --- | --- |
| 1 | 回执文案承诺「完成后结果会自动进入你的上下文」「期间可继续其它工作」，**只字未提 turn 结束会终止** | `src/agent/toolExecutor.ts:1500` | **内核对用户说谎**——模型只是照抄 |
| 2 | turn 终态 `reapAll()` 无条件杀光存活后台任务 | `src/agent/loop.ts`（`finalizeBackgroundTasksOnTurnEnd`） | **`background` 名不副实**：实为「本轮内异步」 |
| 3 | `killed` **混装**「用户主动杀」与「turn 收割杀」，UI 一律显示「已终止」 | `src/agent/backgroundTasks.ts`（`kill()` / `reapAll()` 皆置 `killed`，无原因字段） | **UI 不可解释** |

## 二、主流对标（外部实锤，2026-10-04 查证）

| 产品 | 进程活过 turn | 结果取回 | 主动唤醒 |
| --- | --- | --- | --- |
| **Claude Code** | ✅ 活到进程退出 | ✅ 输出重定向到文件 + Read 按需取 | ❌ |
| **Trae** | ✅ | ✅ 新问一句 | ❌（**官方承认**） |
| **memora 现状** | ❌ **turn 结束即杀** | ❌ | ❌ |

- **Claude Code**：输出写文件（不占上下文）、任务 ID 跟踪、清理规则 = 退出时清 / 输出 >5GB 终止 /
  macOS-Linux 内存压力空闲 30min 回收。可后台化的典型场景明确包含 **dev server、watch**（即永不结束的任务）。
- **Trae**：用户原话「它经常说在后台执行，执行结束后我会怎样，但我根本没有途径获取怎么样了，
  **有时候早就执行完了还得我新问一句**」。官方答复：「Agent 将长任务挂到后台执行后，当前轮次的对话就
  结束了。目前它**无法在后台进程结束时主动发消息唤醒你**并报告结果」。

**结论**：三家都不主动唤醒（这是行业共性缺口）；**memora 更差一档——唯一在 turn 边界杀人的**。
本方案补的正是「杀进程」这一档，**不碰「主动唤醒」**（见 §五）。

## 三、设计定案：**两句话**

> **一、别杀它。二、别扔它的结果。**

`finalizeBackgroundTasksOnTurnEnd` 现有两个动作，**拆开处理、一动一留**：

| 动作 | 现状 | 改后 | 理由 |
| --- | --- | --- | --- |
| 丢弃 `command-result` 队列 | `filter(r => r.kind !== 'command-result')` | **删除此行** | 见 §3.1 判据对齐 |
| 处理存活后台任务 | `reapAll()`（杀光） | **改为脱管不杀**（`detachAll()`） | turn 不是进程的容器 |

### 3.1 为什么删那一行是对的（SSOT 论证，非「放宽限制」）

「回流不跨 turn」这条旧定案，**只封杀了 `command-result`，却放行了 `interject`**：

| 跨 turn 注入的数据 | 旧定案态度 | 性质 |
| --- | --- | --- |
| 用户插话 `interject` | ✅ 放行（`clearPendingInterjections` 明确只清 `interject`） | 外部产生的事实、显式一条消息、`appendUser` |
| 后台结果 `command-result` | ❌ 封杀 | 外部产生的事实、显式一条消息、`appendSystem` |

**两者性质完全相同，却用两套标准** ⇒ 违反 SSOT。且 turn 内部跑的 `command-result` 走的就是同一条
通路（`_handleInterrupt` → `appendSystem`），**机制在 turn 边界突然失效，是不一致而非保护**。

⇒ 本次**不是推翻一条定案，是补齐一条没贯彻到底的判据**。

### 3.2 为什么成本能压到「删一行」（实现事实）

| 事实 | 位置 | 推论 |
| --- | --- | --- |
| `loop` 是 **Agent 级单例**（装配时创建一次，close 时置 null） | `agent.ts:1350` / `:1907` | `interruptQueue` **天然跨 turn 存活** ⇒ 无需新存储 |
| `clearPendingInterjections()` **只清 `kind==='interject'`** | `loop.ts` | 两个清理点**设计时已分流**，删掉的那行不与它冲突 |
| 队列消费通路 `_handleInterrupt` → `appendSystem` | 已有 | **零新工具 / 零新队列 / 零新状态机** |

### 3.3 用户视角的两种情形（**同一机制的两个时刻**，非两套机制）

| 情形 | 队列状态 | 用户动作 | 结果 |
| --- | --- | --- | --- |
| 后台跑完，用户**还没开新 turn** | 条目躺在 `interruptQueue` | 下一条消息发出去 | 新 turn 首 step 边界吸收 ⇒ 结果进入本轮上下文 |
| 后台跑完，**用户已开新 turn** | 同上，被吸收 | 无需额外动作 | 排队中，当前轮迭代即拿到 |

⚠️ **诚实边界**：若用户开了新 turn 且该轮**立刻收尾**，队列条目会留到**下一个** turn。
这是「排队」而非「丢失」，不丢数据。

## 四、诚实口径（必做，否则本方案只做了一半）

进程**活过 turn**。宿主退出时是否被清理，**当前无代码保证**：`Agent.close` 不杀注册表存活
进程，OS 是否随扩展退出回收子进程未经真机证实（验收教程观察点 ⑧ 真机定类）；Claude Code
的退出清理是它自己的实现，属对标目标，**不得写成本仓现状**。超时边界同理：30min
（`BACKGROUND_MAX_TIMEOUT_MS`）只是**显式传 timeoutMs 时的钳制上限**，缺省不传 = 永不超时。
**结论：文案先写「不保证随宿主退出被清理」，真机定类后再决定是补退出杀树（让承诺成真）
还是维持「可能残留」口径**——未验证就承诺「活不过宿主」是谎报。

文案改法（刀 2 执行）：

| 位置 | 现状 | 改后口径 |
| --- | --- | --- |
| 回执 `[BACKGROUND_STARTED]` | 「完成后结果会自动进入你的上下文」 | 「命令已在本轮之外继续运行；**结果不会自动进入当前上下文**，你可以在后续任意一轮用 `kill_command` 传入该 taskId 取回截至当时的输出；未传 timeoutMs 时没有超时上限」 |
| 工具描述 `background` 参数 | 「true = 后台执行：立即返回 taskId，结果完成后自动回到上下文」 | 删去「自动回到上下文」承诺，补「宿主扩展退出时不保证清理它，别起永不结束的命令后遗弃」（刀 2 当时口径，**已被 §4.1 取代**：退出杀树落地后改为「正常退出终止，崩溃/被强杀不保证」） |

**校验点**：改后文案里**不得出现**「自动回到上下文」「完成后你就会看到」「活不过宿主进程」
「窗口关闭即终止」类承诺。

### 4.1 真机定类结果（2026-10-04 · 观察点 ⑧ 闭环）

**定类 = OS 层孤儿实锤**：完全退出 VS Code 约 10 秒后，任务管理器中 `ping -n 300`
（PID 15456）仍在运行，其父进程（扩展宿主 PID 15200）已不存在——Windows 不回收脱离
控制台的子进程，Job Object 兜底在此环境不成立。

**处置 = 补退出杀树（让承诺成真）**：

| 落点 | 内容 |
| --- | --- |
| `BackgroundTaskRegistry.killAllRunning()` | 实例终态真杀全部 running（主动终止单点 `terminate` 与 `kill` 共用；不回调 listener） |
| `AgentLoop.shutdownBackgroundTasks()` | 纯透传，返回收割数；未装配返 0 |
| `Agent.close()` | null 化 loop **之前**调用；宿主 `deactivate` 本就 await close ⇒ 宿主侧零行为改动 |
| 文案 | 工具描述 / `[BACKGROUND_STARTED]` 回执 / turn 收尾报告统一为「正常退出 VS Code（扩展停用）时终止；崩溃 / 被强杀不保证」 |
| 定案锚 | ADR-036（双生命周期边界 + 回流留存；S2 固化触发 1：src 引用 ≥1） |

**两个生命周期终点从此分开**（勿再折叠成一句「后台任务退出时处理」）：turn 终态 =
`detachAll` 不杀（跨轮存活，本文 §三）；Agent 实例终态 = `killAllRunning` 真杀
（注册表实例隔离，实例销毁后任务不可寻址，不杀即孤儿）。

**新承诺不违反上方校验点**：允许的措辞是**有条件**的「正常退出 VS Code 时终止」；
仍禁止无条件的「活不过宿主进程」「窗口关闭即终止」——① 关聊天面板销毁 webview ≠
退 VS Code；② 扩展崩溃 / 被 OS 强杀时 `close` 来不及执行，该场景依旧不承诺清理。

### 4.2 观察点 ⑧ 第二轮复测实锤 + exit 钩子兜底（2026-10-04 追加，梯度 A 定案）

**缺口实锤（真机日志，非推断）**：新 dist（16:01 构建，含 `killAllRunning`）下重测——
16:15:02 起 `ping -n 300`，16:15:28.817 renderer 发 terminate，**16:15:28.848 扩展宿主
即退出（exit 0）**——从 terminate 到进程消失仅 **31ms**；Memora 日志无任何「收割存活
后台命令任务」痕迹；ping 成为孤儿（父进程已死）继续跑至自然结束。

**根因定性**：杀树代码本身正确（`deactivate` → `agent.close()` → `killAllRunning` →
taskkill /T /F），但它埋在 async `close()` 深处（前面隔着两个 5 秒预算的 await）。
**Windows 正常关窗给扩展宿主的清理窗口实测只有 31ms**——异步清理链根本跑不到杀树行。
§4.1 的「正常退出 VS Code 时终止」承诺因此当前是**谎**：正常关窗路径同样不保证。

**定案（梯度 A，零新依赖）**：给「Agent 实例终态」补**第二触发通路**——进程退出事件兜底：

| 落点 | 内容 |
| --- | --- |
| `skillScriptRunner.killProcessTreeSync` | **同步**杀树原语：Windows `execFileSync('taskkill', ['/pid', pid, '/T', '/F'])`；POSIX `process.kill(-pid, 'SIGKILL')`（本就同步）。与异步版 `killProcessTree` 共享 taskkill 参数构造（同源，防双真理源）。**为什么必须同步**：`process.on('exit')` 钩子返回后 Node 即退出，异步 `spawn` 的 fork 由 libuv 线程池派发，可能来不及完成——杀树静默失败（「静默失败 = 假阴性」同族） |
| `BackgroundTaskRegistry` 构造 | 注册 `process.on('exit')` 钩子：遍历 running 条目 → 输出快照 → `killNowSync` → 置 `killed`（**不回调 listener**，与 terminate 单点同约定） |
| `BackgroundTaskRegistry.shutdown()` | `killAllRunning()` + 注销 exit 钩子（注册/注销**配对**——钩子是进程级、注册表是实例级，不配对 = 多实例钩子堆积 + 闭包泄漏） |
| `loop.shutdownBackgroundTasks` | 透传改指 `shutdown()`（返回收割数不变，`Agent.close` 调用方零改动） |
| 幂等 | `deactivate` 赶得上 → close 杀光 + dispose → exit 钩子 `disposed` 空转；赶不上 → exit 钩子同步收割。两条通路共用 terminate 单点语义，非两套机制 |

**诚实边界更新**（本轮落地后口径）：① 正常退出 VS Code（含 31ms 窗口）→ exit 钩子
**同步**兜底，承诺成真；② 扩展崩溃 / 被 OS 强杀 / 断电 → `exit` 钩子同样来不及执行，
**依旧不承诺清理**（该边界不变）；③ 真机复测观察点 ⑧ 第三轮（重测退出后 ping 是否残留）
为验收锚点——**✅ 已通过（2026-10-04 16:58）**：26ms 关窗窗口下零 ping 残留（ping 自然
寿命未到即被收割），通路归因存灰区（杀树日志未及 flush 落盘），结果层锚达成，收据见
CHANGELOG 同日第三轮条目。

## 五、刻意不做（含触发条件，不写「已做」）

| 不做项 | 理由 | 触发条件（何时重启） |
| --- | --- | --- |
| **A · turn 挂起等后台跑完**（用户原始提议） | `pause` 走 `interruptQueue` 的 `kind:'pause'`，**由 step 边界消费**（非立即生效），且唤醒依赖**用户手动 `resumeExecution`**。让后台完成自动唤醒 = **新开一条唤醒通路**（新机制），另需处理「dev server 永不结束 ⇒ turn 永久挂起」与 pause 态语义分叉 | 真机出现「模型在同一 turn 内必须等后台结果才能回答」 |
| **C · 无新 turn 时自主起新 round 汇报**（用户「诈尸复活」） | `externalTaskLoop`（自主多轮编排）已于 **2026-09-04 整体删除 1181 行**，设计定案「复杂度在单 turn 内自然生长」。复活 = 新能力面 + 一串未定边界：用户输入中如何打断 / 自主轮 `userMessage` 写什么 / 落盘与归档归属 / 多任务完成合并成几轮 / 自主轮再起后台任务是否防死循环 / 重启是否恢复 | 真机出现「用户反复抱怨要再问一句」（Trae 社区同款） |
| **主动唤醒推送**（三家都缺，memora 的差异化机会） | 需新建「任务终态迁移 → 宿主 notice」事件通路；刀 3 的后台任务条已具备 UI 底座 | 本方案落地后真机验证 |
| **保质期**（陈旧结果防突兀） | `MAX_PENDING_COMMAND_RESULTS=3` 只限**每步注入条数**（不限队列总量）；Agent close 队列随实例销毁。注册表终态条目与队列条数目前**都无 GC**，不是「天然有界」 | 真机出现「结果隔夜突现且模型误当相关」 |
| **终止原因字段**（区分手动杀 / 超时强杀） | detach 落地后，「turn 收割」这个**最误导的原因消失**；但超时仅在显式传 timeoutMs 时存在（缺省永不超时），高频死因其实只剩手动 kill | 真机出现「用户以为是自己杀的，其实是超时」 |
| 跨 Agent / 跨会话的后台任务管理 | 注册表按实例隔离是硬不变量 | 不做（永久） |

## 五之二、阶段二补漏：终态 UI 不准 + 用户无法清理（2026-10-04 追加）

### 5.2.1 缺口实锤：脱管引入了一个**比原 bug 更坏**的谎

脱管落地后复查通知链，发现**任务自然跑完时宿主完全收不到通知**：

```
任务跑完 → settle() → notify() → setCompletionListener 回调
                              → 只做 enqueueCommandResult（入队给模型）
                              → ❌ 无任何出宿主的通路
```

而宿主推 UI 快照只有三个时机：`step_boundary`（turn 内）/ `background_report`（turn 终态时，
此时任务还在跑）/ `background_kill` 处理后。**脱管后 turn 已结束，三个时机全不覆盖
「任务自然跑完」** ⇒ 条上一���写「运行中」，实际早已跑完。

> **对比原 bug**：原 bug 是「进程死了却显示已终止」（假终态）；本漏是「进程活着却显示运行中」
> （假活跃）。**假活跃更坏**——它让用户以为还有事在跑，而真相是结果早已躺在队列里。
> ⚠️ 这是**阶段一自查漏判**（改了「不杀」却没检查「状态变化怎么通知 UI」这条链），
> 真机验收前必须补完，否则验出来的每条结论都会被假状态污染。

### 5.2.2 补法一：接既有注入面，零新机制

顺着装配区**既有的宿主回调注入模式**（`toolExec.setOnToolsChanged` / `setBudgetProvider`
/ `IProjectSearchProvider`），**不加第二个 `setCompletionListener`**（该 setter 已被 loop
占用，加第二个即第二真理源）：

```
registry 自然终态（settle：进程完成 / 超时；主动 kill 刻意不走 notify——
  输出已直接返回，再回调会双份消费）
  → setCompletionListener（单点，loop 持有）
  → loop 除 enqueueCommandResult 外，触发一个「后台任务变化」出口
  → 宿主接上 → 转成已有的 background_tasks 快照下发
  → webview 走现成内容签名去重（变了才推，零噪音）
主动 kill 的 UI 路径：宿主 kill RPC 返回后自行回拉一次快照（不依赖本事件）
```

**不新增协议通道**（107 不变）、**不新增状态**、**不加定时器**。

### 5.2.3 补法二：终态行可手动收起（不自动消失）

⚠️ **自我订正**：讨论中我曾说「不让用户手动关」，**错**——我反驳的是「自动消失」，
用户诉求是「手动关闭」，两者不同。手动关闭必须做。

| 进程状态 | 按钮 | 显示 | 点它发生什么 |
| --- | --- | --- | --- |
| **还在跑** | 「终止」 | 运行中 | 真杀进程（现状不变） |
| 已完成 / 已终止 / 超时被终止 | `×` | 对应终态 | **仅从视图收起** |

**running 行不给 `×`**：它只有「终止」（真杀）。若 running 也能藏起来，就回到缺口原点
——「派了人出去办事，不让他在工位上待着」；进程在跑就必须看得见，这是不变量。

**关掉的是「眼睛」不是「东西」**：任务条目与输出仍在内核，`kill_command` 随时取回。
**不真删**——可逆 > 不可逆（反悔还能捞回来）。

**「记住了」放宿主侧不放 webview**：放 webview 则面板一折叠即忘，刚关掉的条又冒出来
（与刀 3 的 ready 补推同源问题）。

### 5.2.4 通道：复用 `background_kill` + `reason`，**不新增**

```
{ type: 'background_kill'; taskId: string; reason: 'terminate' | 'dismiss' }
```

| reason | 宿主行为 | 进程 | 数据 |
| --- | --- | --- | --- |
| `terminate`（缺省，兼容旧 webview） | 真终止 | 杀 | 保留 |
| `dismiss` | 记入「已收起」集合并过滤快照 | **留着** | 保留 |

**一个通道两个明确动作**优于开第二条通道 ⇒ 治理阈值不受影响。

### 5.2.5 一致性自检（不带伤）

| 检查 | 结论 |

| 第二份真相源？ | 无。真相源恒为内核注册表；宿主只存「哪条被收起」= **用户偏好**，非数据副本 |
| 僵尸分支？ | 无。`dismiss` / `terminate` 各有真实用例，各钉一条测试 |
| 预支复杂度？ | 无。不做主动唤醒、不做保质期、不做结果摘要预览（**要内容就问一句**，同 Claude Code） |
| 破坏通道治理？ | 无。107 → 107（阈值 130） |
| 又说谎？ | 无（**UI 按钮路径**）。自然终态 settle→事件、宿主 kill→处理后回拉，两条路径状态变化必有一次快照推送，UI 拿真值。**已知边界（LLM 路径）**：模型调 `kill_command` 后靠下一个 step_boundary 推送；若 turn 当场结束（kill step 之后无下一 step 边界）则无推送点，条停留旧状态直至下个 turn / 面板重开（ready force 补齐）——登记于此，不加定时器（真机出现误读再立项） |
