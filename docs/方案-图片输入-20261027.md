# 方案 · 图片输入（多模态用户输入）

> 状态：**定稿（P0 待施工）**。日期：2026-10-27。

## 1. 已否决结论与修正依据（勿按旧结论施工）

### R1 —— 否决「改 `Message.content` 类型」

曾主张 `content: string | ContentPart[]`。实测：`src/` 内 `.content` 直接消费 **88 处**、`role: '...'` 构造点 **47 处**；更致命的是两处摘要拼装已写成 `typeof m.content === 'string' ? m.content : '[tool]'` —— 改类型后**用户消息会被静默标成 `[tool]`**，无编译错、无测试红。

⇒ 改为**新增正交可选字段**。`content` 的类型与语义一个字节不变。

### R2 —— 路由风险的方向

曾称「带图请求走 `ProviderRouter` 会被派到纯文本模型」。**该事实陈述已被 R8-1 推翻**（主对话必然经过路由函数）。

保留的结论只有一条：**正交字段方案天然隔离**——摘要路径只消费 `content`，拿不到 `attachments`。

### R3 —— 图片挂 `RoundMessage` 而非 `Round`

`Round` 只有一个 `userMessage`，但还有 `interactiveInputs[]`（中途补充 / 回答提问，各自是 `RoundMessage`）。一轮可有多条用户输入，各带各的图。

### R4 —— 图片显示链路的因果（`localResourceRoots` 的真实用途）

曾误判「`localResourceRoots` 不含工作区 ⇒ webview 显示不了工作区文件」，并据此把缩略图推到 P2「因为动安全面不可行」。

**VS Code 官方文档原文**：webview **默认**可访问「扩展安装目录 + 用户当前活动工作区」；`localResourceRoots` 的用途是**额外放开**。

⇒ 真实因果是：**是我们自己显式写死了 `localResourceRoots: [dist/webview]`，主动把工作区的默认权限关掉了**。所以解法不是"改架构"，而是把这条白名单加回一个子目录 + CSP 放行 `cspSource`。

结论修正：缩略图从「因安全面不可行」变为「**P1 可做，方案已定（D11）**」。P0 仍不做——复杂度该排期，不该恐惧。

### R5 —— GC 不用 `Round.refCount`

`refCount` 是**轮级**计数，图片是**文件级**引用。轮级计数器反推文件级引用，在分叉 / 异常中断下必然漂移。改幂等扫孤儿。

### R6 —— 补齐「图片到底从哪个接口进」

只设计 `Message.attachments` 字段、却不说图片如何进入 `Agent.chat(input: string)`，等于方案缺了入口 ⇒ 补 D8 / D7。

### R7 —— 对照一个厂商级完整实现后的五处修正

**参照对象与取证边界**：对照 WorkBuddy 自身宿主（Electron + JS 明文打包）的多模态实现。可证部分 = 工具 schema、明文 skill、`cli/dist/*.mjs` 与 `renderer/assets/*.js` 中的 `ImageUtils` / `imageBlobService` / `prepareForModel`；不可证部分 = Electron 主进程（在 `app.asar` 内）、云服务后端、模型侧视觉编码器。**下文只引用可证部分，不外推。**

**R7-1 · 五条缺口（补为 D18–D22）**

| 缺口 | 对方的做法 | 本文原状 |
|---|---|---|
| mime 判据 | magic bytes 嗅探，再按白名单分「直接支持（jpeg/png/webp）」与「需转码（bmp/tiff/gif）」 | `ImageRef.mime` 来源未定义 |
| base64 校验 | 估算字节 = 解码字节，且重编码须与原文一致 | 只写了「入口限额」 |
| 读取校验 | `read(blob_id, mime, size)` 三值交叉校验；identity 非法则 warn + 返回 `undefined`（fail-safe 不抛） | `ImageResolver(sha256)` 单参 |
| 占位文案 | `[Image from {name} ({mime}, {size}) - stored at: {path}]` —— 带路径 | `[用户发送了 N 张图片]` —— 只有计数 |
| 历史衰减 | `processHistoryForApi(input, retainRounds)`：只复水最近 N 轮，更早降级占位 | 完全没设计（§5.11-2 只承认「全量重传」，未给衰减手段） |

**R7-2 · 默认值相反，但维持我们的（对抗式审查的正面结论）**

对方：`getCurrentModel()?.supportsImages !== false` ⇒ **默认 true**；解析异常时明确 `keeping images`。
本文：默认 **false**。

**不因别人这么做就改。** 差异根因是代价模型不同：对方是自有云服务，判错 ≈ 一次报错重试；memora 是用户自带 key，判错 = 真花钱 + 消息丢失。
另有一条独立判据：`supportsToolCalling` 默认 true 是因为「多传一个 tools 字段」无害；图片不是这样——**图片进了请求体就是要计费的**。风险不对称 ⇒ 默认值必须不对称。

**R7-3 · 门禁从一级改两级（D7 修正）**

对方是「不支持就 `strip` 掉图 + 占位 + 对话继续」，从不阻断。本文原为「入口抛错阻断」。
复审后的判断：**两者各对一半。**

- 入口（用户**未声明**支持）⇒ 必须**阻断**。理由不是"安全"，是**错误可见性**：阻断时用户 5 秒内知道该勾哪个开关；而 strip 会返回一个看似正常、实则答非所问的回答，用户可能几分钟甚至永远不发现。**能自我纠正的错 > 不可发现的错。**
- 序列化（用户**已声明**支持，但字节取不到 / 文件损坏 / resolver 未命中）⇒ 必须**降级不阻断**。此时再阻断毫无用处——用户已经做了他能做的（勾了），阻断只会让一条老会话彻底打不开。这一层吸收对方的做法。

⇒ D7 拆成两级，`supportsVision` 的**唯一消费点仍是入口**（防僵尸字段的那条判据不变），降级只是表现层兜底，不构成第二个能力位判据。

**R7-4 · P2 论据降权（重要：我此前把「不做」论证过头了）**

曾写「工具化读图这条路在主流开源项目里是残缺的」，依据是 Roo Code 把那段代码注释掉了。
**事实**：WorkBuddy **实现了**这条路——`function_call_result` / `function_call_output` 里的图片照样做 dehydrate / rehydrate / 能力过滤。所以「残缺」不成立，Roo 的注释约束是 **OpenRouter prompt cache 只允许一个 user 消息**，那是渠道特性，不是协议硬限。

本项目的真实硬障碍在别处，且更硬：**`read_file` 是 `readFile(path, 'utf-8')`，工具结果协议是字符串**（F18 / F19）——图片在进入模型之前就已经被解码损坏了。
⇒ D14 结论不变（P2 不做），但**理由换掉**：不是「不可行」，是「要同时改 `read_file` 的二进制支持 + 工具结果的内容协议，且与单条 tool 结果 token 上限冲突」。**结论对、论据错，比结论错更危险——因为它会挡住后续重启这条路。**

**R7-5 · 占位符带路径 ≠ 模型能自己读回（防空头承诺）**

D21 让占位文案带 `blob_path`。这**不等于**「模型可以自己把图读回来」——本项目 `read_file` 只读 `utf-8`（F18），模型读到的是损坏的文本。
⇒ 占位带路径的真实收益只有两条：① 人类可定位（用户自己去看/去报障）；② 为 P2 预留稳定坐标。**任何注释、文案、设计说明都不得声称"模型能自愈"**，那是我们目前给不起的承诺。

**R8 —— 排雷：逐条回核全文的事实基线（附证据）**

> 排雷方法：对本方案所有「事实基线 / 落地可施工性」主张，回到仓库源码逐个符号核对。**结论分三类：成立 / 修正 / 新增**。本节结论与 §5–§7 正文一一对应，**正文即最终口径**。

**R8-1 · 「主对话不走路由」是错的（结论对、论据错）**

曾写「`providerRouter` 全仓 2 个消费点，且都是 `'summary'`；主对话根本不走路由」。

实测：**主对话必然经过路由函数**——`LlmCaller.resolveProvider` 无条件调用 `determineTaskType(safeMessages)`，再 `router(taskType)`，taskType 取 `simple / reasoning / code`（`src/agent/managers/llmCaller.ts` · `resolveProvider` / `determineTaskType`）；且 `providerRouting` 默认值是 `'auto'`（`src/role-pack/strategyResolver.ts` · `resolveProviderRouting`）。

今天不炸的**唯一原因**：宿主注入的 router 是恒等函数（`hosts/memora-vscode/src/extension/host/assemble.ts` · `createProviderRouter`，`return (_taskType) => provider`），且注释明写「为未来按任务类型自动选择不同 Provider 预留」。

⇒ 真实风险方向不是「摘要模型收到图」，而是：**入口判的 `supportsVision` 可能不是实际被调用的那个 provider 的能力**。今天两者恒等，结构上不等。同日型伤已存在于 `supportsToolCalling`（`src/agent/loop.ts` · `toolCallingEnabled` 读 `this.opts.provider`）。

处置（不扩大到改既有架构，只做两件事）：
1. §5.6 门禁改为「判在**本轮实际被调用的 provider**」——实现上即取 `resolveProvider` 的结果，而不是 `opts.provider` 快照；
2. 在 §6 不带伤清单登记：**一旦启用多模型路由，图片能力位必须跟着路由后的 provider 走**，否则重演 `supportsToolCalling` 的同型伤。

**R8-2 · 「`Message` 里没有轮次信息」不成立，但结论不变**

曾据此论证「窗口判断不能放 `formatMessages`」。类型上 `Message.roundId?` 与 `SessionMessage.roundId?` **都存在**（`src/llm/provider.ts` · `Message`；`src/memory/sessionStore.ts` · `SessionMessage`），所以「没有轮次信息」的说法不成立。

**但结论仍然正确，真正的依据是另一条**：`applySessionToLoop` 投影时只取 `role / content`，**`roundId` 在这一跳被丢掉**（`src/agent/managers/sessionManager.ts` · `applySessionToLoop`）。所以到达 `formatMessages` 的消息里 roundId 时有时无（turn 内 push 的有、会话加载重建的没有），**不构成可用判据**。

⇒ 结论「窗口判断放装配层」不变；论据改为「装配层是唯一持有会话序号的地方，且 `applySessionToLoop` 已经丢掉了 roundId」。**伪代码里的 `round.seq` 不存在**——`Round` 只有 `id / createdAt / refCount`，真源是「会话 `roundIds` 数组的索引差」（§5.12 已改）。

**R8-3 · 契约面漏 `SessionMessage` / `EstimableMessage`，装配链是两跳（最易踩死的落地缺口）**

只定义 `Message.attachments` 与 `RoundMessage.attachments` 是不够的。实际链路是 **5 类载体、3 跳投影**：

| 载体 | 是否对象展开 | 方案覆盖 |
|---|---|---|
| `Message`（`src/llm/provider.ts`） | — | ✅ |
| `RoundMessage`（`src/memory/roundStore.ts`） | — | ✅ |
| `RoundInteractiveInput`（extends `RoundMessage`） | 继承 | 未说明（D13 首版不带图，仍应显式声明） |
| **`SessionMessage`**（`src/memory/sessionStore.ts`） | — | ❌ **漏** |
| webview 投影对象（`chatPanel` turn 投影） | ✅ 对象展开 | 自动透传 |

两跳装配（**都是显式字段白名单，不是对象展开**）：
1. `MessageHistory.loadRoundBasedMessages`：`Round → SessionMessage[]`，只抄 `role / content / roundId / timestamp`；
2. `SessionManager.applySessionToLoop`：`SessionMessage[] → Message[]`，只抄 `role / content`。

第 2 跳的既有注释本身就是血训：「整体重建≈隐式字段白名单，任何未显式列出的字段每次 pause 被静默丢弃」。**漏任一跳的后果：图片在切会话 / 分叉 / 重启后静默消失，编译不报错、无测试红。**

⇒ D3 补 `SessionMessage.attachments`；D26 把「三跳全改」列为落地硬项；§6.3 公开面清单补 `SessionMessage` / `EstimableMessage`（token 估算入参类型也是公开导出面）。

**R8-4 · 「无附件即早退」放最前会打回现有三分支（按图施工即回归）**

现有 `formatMessages` 有三个分支：`tool`（带 `tool_call_id`）、`assistant + toolCalls`（带 `tool_calls`、content 空串转 null）、普通。若按下面这种写法：

```ts
if (!m.attachments?.length) return { role: m.role, content: m.content };
```

这一行会把前两个分支的 `tool_call_id` / `tool_calls` **全部吞掉**，直接违反 §6.4 承诺的「无附件路径字节级一致」。文字说「既有分支原样保留在最前」，代码没写。

⇒ §5.3 伪代码定为「先走既有三分支，仅在普通分支内展开 parts」，并用快照测试钉住存量请求字节级不变。

**R8-5 · D10 的 `1100` 不是上界，是"中位数"（与"宁可高估"的旗号相反）**

外部核实（2026-10-27）：
- Claude 官方口径：视觉 token = `⌈width/28⌉ × ⌈height/28⌉`，标准档单图上限 **1568**、高清档 4784；
- OpenAI high detail：`85 + 170 × tiles`（每 tile 512×512），一张 4K 图 resize 后约 12 tiles ≈ **2125**。

⇒ 固定 `1100` 对小图高估（浪费预算、早截断）、对 OpenAI high 的大图**低估近一半**（真会爆窗）。而 `ImageRef` **已经收了 `width/height` 却不用于唯一的计量点**——收尺寸不用尺寸，是设计内部不一致。

⇒ 改为按尺寸计算，仍落在同一函数、不新增模块：
`imageTokens = min(⌈w/28⌉×⌈h/28⌉, 1568)`，并按 provider 档位留一个可配置上限（默认 1568，OpenAI high 场景可上调）。

**R8-6 · 新增硬缺口：D5「同步查内存表」与验收「重启后仍能追问」自相矛盾**

D5 规定 resolver 同步查宿主内存表；验收第 ③ 条要求「重启 VS Code 从历史恢复 → 图片仍在且能继续追问」。

**重启后进程内存必为空** ⇒ resolver 全部未命中 ⇒ 全部降级占位 ⇒ 模型看不到任何历史图 ⇒ 验收③ **不可能通过**。这是设计与验收的直接冲突（§5.11 的"诚实登记"没有覆盖它）。

⇒ 新增 D24 / D25 补齐，不改变同步签名：
- **预读时机**：会话加载（`loadRoundBasedMessages` / `switchToSession` / `forkSession`）把 `SessionMessage.attachments` 交给 loop 之前，宿主**同步读盘**把**窗口内**附件字节填入 resolver 缓存；
- **封顶**：条目 ≤ 32、总字节 ≤ 128 MiB，LRU 淘汰（无上限 = 内存随历史线性涨）；
- **窗口复用**：D22 的 `retainRounds=4` 在这里承担第二个职责——**预读量的上限**。窗口外的不预读，自然也不复水；
- **未命中仍降级**：预读失败 / 超限 / 文件被删，走 D7 二级，不阻断。

**R8-7 · 与 MCP 方案的真相源裂缝（两份文档各说各话）**

`docs/方案-MCP工具接入-20261023.md` 的 S6 / D7 已把「工具返回图片」登记为触发证据，明确「本期不做（内核 `Message.content: string`）」——这与本文 P2 的「模型自主读图」是**同一个能力的两个入口**，但两份文档互不引用。

⇒ §4 边界表加一行划界：**MCP 工具返图 / 工具化读图不在本方案承载，见 MCP 方案 D7**；P2 重启时必须先做两文档合流，否则会各做一半、长出两套「模型怎么看到工具图片」。

**R8-8 · GC 扫描面写宽了、时机写窄了（实现最易窄化）**

- §6.10 写「所有 Round 内全部 `RoundMessage.attachments`」是对的，但实现最容易只扫 `userMessage`。`assistantLog` / `interactiveInputs` / `evidence` 里的引用会被当孤儿删掉。须**显式枚举四处**。
- 「会话删除后跑一次」不等于「Round 物理删除时跑」：`Round` 被多会话共享，删会话通常**不产生孤儿**；真孤儿来自 `Round` 被 GC 物理删除。启动时扫描能兜住全部，会话删除时扫描是空跑（保留无妨，但别当主力）。

**R8-9 · 宿主契约面整个漏列（清单只写了内核一半）**

§6.3 若只列内核公开成员（`Message` / `LlmProvider` / `OpenAICompatibleConfig` 等），就把「能力位」当成了内核单点。实测（2026-10-27）宿主侧另有三跳：`shared/protocol.ts` · `LlmProviderConfig`（DTO 真源）→ `providerStore`（透传）→ `host/llmConfig.ts`（**前台 + background 两处构造**）。

⇒ §6.3 补宿主三跳；§7 P0-5 明确落点四跳。漏 background 那处的症状是「主对话能发图、后台任务模型拿不到能力位」——**两处构造 = 第二次谎报位点**（同族伤，见 `single-truth-source-mindset.md`）。

**R8-10 · `ImageRef.width/height` 没有任何产出方（必填字段无生产者）**

D10 用 `width/height` 算 token，§6.12 校验链却**没有一步解析尺寸**、也没写 P0 派工。等于把两个必填字段写在类型里、却无人赋值 ⇒ 序列化侧拿到 `undefined`：`Math.ceil(undefined/28)` 得 `NaN`，`Math.min(NaN, 1568)` 仍 `NaN`，累加后整个估算值污染成 `NaN`——**且不会有任何现有测试红**（无附件路径根本不走这条分支）。

⇒ §6.12 补第 6 步（四种格式头手写解析，全部只读前几十字节、不解码整图），§7 P0-3 的校验链共六步。

memora 的差异点仍只有一处——**图片不内联进消息体，而是引用 + 序列化时物化**，这是为了适配「每轮整文件重写落盘」（F3）这一本项目独有约束。另一处差异是**不转码**（D16）：对方在渲染层用 canvas 压缩改写字节，本项目坚持原字节入库 + 入口限额，代价是体积、收益是可审计（sha256 恒等于用户给的那张图）。

**外部核实（2026-10-27）**：单图 token 口径以官方公式为准——Claude 视觉 token = `⌈width/28⌉ × ⌈height/28⌉`（标准档单图上限 **1568**，高清档 4784）；OpenAI high detail = `85 + 170 × tiles`（每 tile 512×512，4K 图约 2125）。固定常数 `1100` 两头都不对：对小图高估、对 OpenAI high 的大图低估近一半。D10 因此按 `ImageRef` 的 width/height 计算（R8-5）。

## 4. 职责边界（内核 vs 宿主）

判据只有一条：**「知道文件在哪」归宿主，「知道 HTTP 长什么样」归内核；内核零外部 IO。**

| 事项 | 内核 | 宿主 | 理由 |
|---|---|---|---|
| `ImageRef` 结构、`attachments?` 字段 | ✅ | ❌ | 协议结构是对外契约 |
| `supportsVision` 字段 + **默认值** | ✅ | ❌ | 与 `supportsToolCalling` 同构；灰度语义归内核 |
| 能力位**取值**（勾选） | ❌ | ✅ | 用户级配置 |
| 拼 `image_url` part | ✅ `formatMessages` | ❌ | OpenAI 协议适配 |
| **字节读取**（sha256 → data URL） | ❌ | ✅ 注入 `ImageResolver` | 内核不做文件 IO |
| 落盘 / 哈希 / 去重 / 孤儿扫描 | ❌ | ✅ `.memora/attachments/` | `.memora` 由宿主分配 |
| 粘贴 / 拖拽 / 选文件 | ❌ | ✅ webview DOM | DOM 只在 webview |
| 入口限额（张数 / 字节 / 格式） | 只防形态 | ✅ **唯一裁决点** | 同 `contextWindow` 护栏原则 |
| token 计量（含图） | ✅ 单点 | ❌ | 预算系统在内核 |
| 缩略图 / 打开原图 | ❌ | ✅ | UI + URI 转换 |
| **MCP 工具返图 / 工具化读图** | ❌ | ❌ | **不在本方案承载**：入口不是用户粘贴而是工具结果，见 `docs/方案-MCP工具接入-20261023.md` D7（R8-7）。两文档 P2 重启前必须先合流 |

一句话：**内核拿到「这里有一张图，sha256=abc，png，1920×1080」；宿主拿到「它在磁盘哪、多大、能不能删」。两者用 sha256 对齐，互不越界。**

### 4.1 边界缺口审查（2026-10-27，逐条核过代码）

判据：**同一个用户动作，换一条相邻通道就会落到另一个入口**——凡是「换通道后图无处可去 / 语义变了 / 限额失效」的，都是边界缺口。

## 5. 核心设计

### 5.1 单一表达式

```ts
/** 图片引用：内存 / 落盘 / 装载 / 请求 —— 同一个表达式（载体与三跳推导见 §5.1.1） */
interface ImageRef {
  sha256: string;   // 内容哈希 = 身份 + 去重键 + 物理文件名
  mime: 'image/png' | 'image/jpeg' | 'image/webp' | 'image/gif';
  width: number;
  height: number;
  bytes: number;
  /** 展示名（附件行 chip 的文字）：**必填**，唯一生产点 = 宿主采集（`file.name`，无名则 `粘贴图片-{sha256 前 6}`） */
  name: string;
  /** 替代文本（无障碍 / 模型侧占位文案可用），与 name 分开：一个是「人认哪个文件」，一个是「图是什么」 */
  alt?: string;
}
```

三个落点（均为**新增可选**，`undefined` = 无图 ⇒ 存量行为零变化）：

```ts
interface Message        { /* 既有字段全不动 */ attachments?: readonly ImageRef[]; }
interface RoundMessage   { /* 既有字段全不动 */ attachments?: readonly ImageRef[]; }
interface SessionMessage { /* 既有字段全不动 */ attachments?: readonly ImageRef[]; }
```

> ⚠️ 载体不是「四处同一个表达式」，而是 **5 类载体 / 3 跳投影**。`SessionMessage` 是最易漏的那一类（R8-3 / §5.1.1）。`RoundInteractiveInput` 继承 `RoundMessage`，字段自动具备，但 D13 首版**不写入**（插话不带图）。

**为什么这是生长而不是移植**：`content` 的语义是「这条消息的文字」，88 处消费点全建立在这上面。加正交字段后 `.content` 一个字节没变，所有既有逻辑（摘要 / 截断 / 记忆 / CoT / 去重 / 注入装配）看到的仍是它熟悉的字符串。图片是**新增的正交维度**，只有序列化和计量两处需要读它。

白送的三个保证（靠**结构**而非**约定**）：摘要看不到图 ⇒ 不会把图喂给轻量模型；截断只切文本 ⇒ 结构上不可能切碎图片；记忆只存文本 ⇒ 天然符合「图片不进记忆」。

### 5.1.1 装配三跳：漏一跳图片就静默消失（R8-3）

这是本方案**最容易踩死且最难发现**的地方：三个投影点都是**显式字段白名单**，不是对象展开。漏改任一跳，编译不报错、测试不红、图片就是不出现。

| # | 投影 | 位置 | 现状 | 本方案要做的 |
|---|---|---|---|---|
| 1 | `Round → SessionMessage` | `MessageHistory.loadRoundBasedMessages` | 只抄 `role / content / roundId / timestamp` | 补 `attachments: msg.attachments` |
| 2 | `SessionMessage → Message` | `SessionManager.applySessionToLoop` | 只抄 `role / content`（**连 roundId 都丢**） | 补 `attachments: tm.attachments` |
| 3 | `Message → 请求体` | `OpenAICompatibleProvider.formatMessages` | 三条分支（tool / assistant+toolCalls / 普通） | 仅**普通分支**展开 parts（§5.3） |

**为什么不能靠"对象展开自动透传"**：webview 轴（`chatPanel` 的 `{...round.userMessage}`）确实是对象展开，白送；但**内核轴（1、2 两跳）全是白名单**，必须逐跳显式补。

**第 2 跳的既有注释就是血训**（原文）：「整体重建≈隐式字段白名单，任何未显式列出的字段每次 pause 被静默丢弃」。图片若只补第 1 跳，症状是：当前 turn 能发图、切会话 / 分叉 / 重启后全丢。

**为什么 `EstimableMessage` 也要补**：`estimateTokensMessages` 的入参类型是 `EstimableMessage{ content, toolCalls? }`，不补 `attachments?` 就只能在调用点 `as any`，那是把类型欺骗埋进计量点。

### 5.2 为什么内核禁 base64（四条独立爆点）

| 爆点 | 后果 |
|---|---|
| 落盘 | `workspaceRoundStore` 每轮整对象 JSON 原子重写（F3）；5 张 2MB 图 × 20 轮 ≈ 200MB 反复搬运 |
| token 估算 | `estimateTokensText` 按字符算 ⇒ 1MB 图虚报 ≈ 26 万 token，实际 85~1600（F6）⇒ 预算误判爆窗 ⇒ 触发截断 ⇒ **把 data URL 从中间切断** ⇒ 请求 400 |
| 摘要 | 若 base64 在 `content` 里，摘要会把它当文本喂给轻量模型（F7）⇒ 花钱让模型读乱码 |
| 重放 | 每轮全量重传，撞 provider 请求体上限（DeepSeek 48 MiB / OpenAI 20 MB per image） |

### 5.3 base64 的唯一生成点

`formatMessages` 是全仓唯一序列化出口（F2），也是唯一生成 base64 的地方。**无附件路径产出与今天字节级一致**（存量请求零回归，用快照测试钉住）。

```ts
private formatMessages(messages: Message[]): unknown[] {
  return messages.map((m) => {
    // ① 既有三分支必须先走完，且**字节级不变**（tool 的 tool_call_id、
    //    assistant+toolCalls 的 tool_calls / content 空串转 null 都在这里）
    if (m.role === 'tool') {
      return { role: 'tool', tool_call_id: m.toolCallId, content: m.content };
    }
    if (m.role === 'assistant' && m.toolCalls) {
      return {
        role: 'assistant',
        content: m.content && m.content.length > 0 ? m.content : null,
        tool_calls: m.toolCalls,
      };
    }
    // ② 只有**普通分支**才可能带附件；无附件时产出与现状完全一致
    if (!m.attachments?.length) return { role: m.role, content: m.content };
    const parts: unknown[] = [];
    if (m.content) parts.push({ type: 'text', text: m.content });
    for (const a of m.attachments) {
      // 入参是整个 ref（三值校验需要 mime/bytes）；返回 URL 或降级文案，见 §5.4
      const r = this.config.imageResolver?.(a);
      parts.push(r && 'url' in r
        ? { type: 'image_url', image_url: { url: r.url } }
        : { type: 'text', text: r && 'text' in r ? r.text : `[图片不可用 ${a.sha256.slice(0, 8)}]` });
    }
    return { role: m.role, content: parts };
  });
}
```

> ⚠️ R8-4：**不要把「无附件即早退」放在最前**——`if (!m.attachments?.length) return { role, content }` 会吞掉 tool / assistant+toolCalls 两个分支的 `tool_call_id` / `tool_calls`，按图施工即回归。三分支必须显式写全。

### 5.4 ImageResolver：端口在内核，实现在宿主

```ts
// 内核：端口（无实现、无 IO、无路径知识）
// 入参是整个 ref（D20 三值交叉校验需要 mime/bytes，不能只给 sha256）
type ResolvedImage = { url: string } | { text: string };
type ImageResolver = (ref: ImageRef) => ResolvedImage | undefined;

// 宿主：缓存条目只存**原始字节**（不常驻 base64，省 33% 内存），dataUrl 按需生成
interface CachedImage { bytes: Buffer; mime: string }
const cache = new Map<string, CachedImage>();   // 由 §5.4.1 预读填充，LRU 封顶

const imageResolver: ImageResolver = (ref) => {
  const hit = cache.get(ref.sha256);
  if (!hit || hit.mime !== ref.mime || hit.bytes !== ref.bytes) return undefined;
  return { url: `data:${hit.mime};base64,${hit.bytes.toString('base64')}` };
};
```

### 5.4.1 缓存怎么被填满：会话加载期预读（补 R8-6 的硬缺口）

**问题**：D5 要求 resolver 同步查内存表、且「同步签名足够」；但验收第 ③ 条要求「重启 VS Code 后图片仍在且能继续追问」。重启后内存必空 ⇒ resolver 全未命中 ⇒ 全降级占位 ⇒ **验收③不可能通过**。这是设计与验收的直接冲突。

**解法（不改同步签名）**：把「填缓存」这件事挪到**会话加载期**，那里本来就是同步语义。

```
会话加载（loadRoundBasedMessages / switchToSession / forkSession）
  → 拿到 SessionMessage.attachments（窗口内）
  → 宿主同步 readFileSync 读 .memora/attachments/{sha256}.{ext}
  → 三值校验（D20）通过后写入 cache
  → applySessionToLoop（第 2 跳，§5.1.1）
  → 后续每次 formatMessages 都能同步命中
```

四条判据：

1. **只预读窗口内的**：`retainRounds = 4` 在这里承担**第二个职责**——预读量上限。窗口外的不预读、也不复水（D22），两处口径同源，不分叉。
2. **封顶**：条目 ≤ 32、总字节 ≤ 128 MiB，LRU 淘汰（D25）。无上限 = 内存随历史会话线性涨。
3. **预读失败不阻断**：文件被删 / 损坏 / 超限 ⇒ 跳过该条，序列化期走 D7 二级降级占位，对话继续。
4. **不改变内核契约**：预读是纯宿主侧行为，`ImageResolver` 仍是同步纯查表；内核不知道"预读"这个概念存在。

**为什么不改成异步 resolver**：异步化要连带 `formatMessages` → `chat()` 整条时序下游扩散一层（本轮 §5.4 既有结论），而预读已经用同步语义解决了同一问题——**能用同步解决的，不引入异步**（同「能用重算表达的，不引入状态」）。

**剩余风险（诚实登记）**：首次打开的会话若附件目录巨大，预读会有一次同步 IO 抖动。缓解：只读窗口内 + LRU 封顶，最坏 32 × 5 MiB ≈ 160 MiB 读盘（多见于极端历史）；实测超 50ms 再考虑分帧预读。

`formatMessages` 侧映射：

```ts
const r = this.config.imageResolver?.(a);
parts.push(r && 'url' in r
  ? { type: 'image_url', image_url: { url: r.url } }
  : { type: 'text', text: r && 'text' in r ? r.text : `[图片不可用 ${a.sha256.slice(0, 8)}]` });
```

**为什么返回值是「URL 或文案」二选一，而不是只返回 URL**：
降级文案需要**路径**（D21），而路径只有宿主知道。若让内核拼路径，内核就有了文件系统知识；让宿主返回文案，内核只做不透明透传 —— 这与 provider 注入 `{baseUrl}` 完全同构。**降级文案的生产权归宿主，这是本方案的一条边界判据。**

- 未命中 ⇒ 序列化成**可见占位**，**不静默丢**（静默丢 = 模型困惑 + 用户零线索）。
- 未命中**不阻断**（D7 二级）：这是"已声明支持但字节取不到"的场景，阻断只会让老会话打不开。
- **为什么不在宿主 chat 前把 ref 物化成 dataUrl 塞进 content**：那会让内存有 base64、磁盘只有 ref ⇒ 同一事实两套表达、两处转换点，未来每个新入口都要记得转。resolver 只有 `formatMessages` 一个出口，漏不掉。
- **为什么不把 `formatMessages` 改 async**：同步查内存表足够；异步化会把 `chat()` 的时序往下游扩散一层，收益为零。

### 5.5 三层真相（回答「复选框够不够」）

| 层 | 内容 | 缺了会怎样 |
|---|---|---|
| ① 用户声明 | 配置面板 `supportsVision` 复选框，走 `supportsToolCalling` 同一条链（⚠️ **仅链路相同，显隐口径不同**：既有的 `supportsToolCalling` 只在 `provider === 'local'` 时显示、云端恒回落 `undefined`；图片能力位对云端也必须可见可勾，见 §7 P0-5） | 内核不知道能不能发 |
| ② 发送门（入口，fail-closed） | 有图 ∧ 未声明 ⇒ **拒绝发送 + 说明原因** | 勾了但模型不支持 ⇒ 裸 400，用户不知道改哪个开关 |
| ③ 错误回指 | 400 分支 suggestion 加「确认模型是否支持图片 / 检查『支持图片输入』是否与实际模型相符」 | 复选框变成不可证伪的摆设 |

**第②层为什么必须「拒绝」而不是「降级继续」**：降级路径（strip 图 + 占位 + 照常回答）确实存在且成熟，但它制造的是**不可发现的错误**——用户看到一个正常回答，却不知道自己的图根本没发出去。而阻断是**5 秒内可自我纠正**的错误。**能纠正的错 > 纠正不了的错**，这是一级判据，不因业界做法而改（详见 R7-3）。

**降级只保留给另一种失败**：用户已勾选、字节却在读取时拿不到（文件被删 / 损坏 / mime 不符）⇒ 序列化期降级占位，**不阻断**（D7 二级 / §5.4）。此时阻断毫无用处——用户已经做了他能做的。

**默认 `false`（与 `supportsToolCalling` 默认 `true` 相反，刻意）**：前者错了只是"少个能力"，后者错了是"请求失败 + 花钱"。风险不对称必须默认值不对称。OpenCode 的「能力标志缺失按纯文本注册」是独立佐证（§3）。

### 5.6 能力门禁：唯一消费点

`processUserInput` 入口判一次（这是 `supportsVision` 的**唯一消费点**，防僵尸字段）：

```ts
// 入参需新增第三参（与 Agent.chat 同源，§5.7）
if (attachments.length > 0 && !this.resolveTurnProvider().supportsVision) {
  throw configError('当前模型未声明支持图片输入', …, [
    '在设置面板「大模型」页确认该模型支持图片',
    '勾选「支持图片输入」后再试',
    '或移除图片仅发送文字',
  ]);
}
```

- **能力位读谁（R8-1）**：能力位读的是 **`resolveTurnProvider()` 的返回值**（即 `LlmCaller.resolveProvider` 按 `taskType` 选出的那个），**不是 `this.opts.provider` 快照**。今天宿主 router 是恒等函数、两者相同；一旦启用多模型路由，读快照就会判错 provider。
- 需要同步登记：`supportsToolCalling` 今天犯的是同一个错（`toolCallingEnabled` 读 `opts.provider`）。本方案**不顺手改它**（超出范围），但 §6 不带伤清单必须写明「图片能力位已按路由后 provider 判；工具能力位仍是旧口径」——分两层写，不折叠。
- 判在入口而非 `formatMessages`：错误发生在**用户可理解的时刻**（发送前），而不是流式失败后。
- 判在入口而非 `setProvider`：provider 可热切换，入口**每 turn** 判一次即覆盖本 turn 的 provider 状态（"本轮"= "本 turn"，术语见 §5.6 下方）。**边界（IMG-5，2026-10-28 补）**：「每 turn 判」只覆盖「换到另一个 provider 实例」，覆盖不到「同一 provider 的配置被改」——能力位是内核实例的**只读构造快照**（`openaiCompatible._setCapabilities`），配置改了必须**换实例**才生效。故宿主在 `onDidChangeConfiguration` 的已装配分支里重建实例（busy 时置 stale，于下一个 `send` 前补做）；只改入口判据不动实例，会得到「勾了 supportsVision 仍被拦、必须 Reload」的假象。
- **降级不构成第二判据**：`formatMessages` 里的降级（§5.4）**不读 `supportsVision`** —— 它只看「resolver 给没给 URL」。所以降级不构成第二个能力位判据，「唯一消费点」这条判据仍然成立；否则它就成了两个消费者，僵尸字段防线自动失效。

### 5.7 接口入口

```ts
// Agent 层：既有两参不动；新增第三可选参 —— 零破坏，且不新开并列入口
async *chat(input: string, signal?: AbortSignal, attachments?: readonly ImageRef[]): AsyncGenerator<AgentChunk>;

// AgentLoop 层：同源加第三可选参（真正落 attachments 的是这一跳，不能只改 Agent 层）
async *processUserInput(
  userInput: string,
  signal?: AbortSignal,
  roundId?: string,
  attachments?: readonly ImageRef[],
): AsyncGenerator<AgentChunk, void, unknown>;
```

- **为什么不加 `chatWithAttachments`**：两个入口 = 两条路径的状态机要各自维护（pause / resume / interject 全都要覆盖），并列即腐化。
- **为什么不用 options 对象替换第二参**：那是对既有调用方的破坏性变更，收益为零。
- **为什么 `attachments` 挂在 `processUserInput` 的第 4 位而不是第 2 位**：第 3 位 `roundId` 是既有调用方（宿主预分配轮次）在用的，插队会改全部调用点；追加到末尾才是零破坏。
- `chatSync` 同源加第三参，保持两个出口签名一致。
- `appendUserMessage` 也要同源加 attachments，但**只有 `processUserInput` 这一处传图**；`continueAfterPause`（续跑补充输入）与 `interject` 注入两处恒传 `undefined`（D13 插话不带图）。写错这里会把插话通道变成第二条图片入口。

### 5.8 正文恒非空（关键不变式）

**任何带图消息，`content` 必须是非空文本。** 纯图输入时正文写 `[用户发送了 2 张图片]`。

每一条都有既有代码作为依据：
- `messageHistory.appendAssistant` 有 `if (!content.trim()) return;`（F10）——空正文不落盘。
- `chatPanel` 装配「最近对话」注入有 `if (r.userMessage?.content)`（F17）——空正文整条被跳过。
- `<user_input>` 包裹需要有东西可包（F9）。
- 模型看到「一张图 + 一句文字锚点」比「纯图」更不容易跑偏。

这条不变式把「空消息」这个边界**整体消灭**，而不是在 88 处逐一加判空。

### 5.9 token 计量

`estimateTokensMessages` 是全仓单点，**同函数内**加一条分支（按尺寸计算，R8-5）：

```ts
// 单图 token 上界：按 Claude 官方 patch 公式 ⌈w/28⌉×⌈h/28⌉ 推算，clamp 到标准档 1568
const IMAGE_TOKEN_UPPER_BOUND = 1568;

function imageTokens(ref: ImageRef): number {
  return Math.min(
    Math.ceil(ref.width / 28) * Math.ceil(ref.height / 28),
    IMAGE_TOKEN_UPPER_BOUND,
  );
}

// estimateTokensMessages 内
if (m.attachments?.length) {
  let imgTokens = 0;
  for (const a of m.attachments) imgTokens += imageTokens(a);
  // 折回等价 CJK 字符数，复用同一套 ceil 公式（不引入第二套 token 数学）
  cjkChars += imgTokens * CJK_CHARS_PER_TOKEN;
}
```

- **为什么不再用固定 1100**（R8-5 订正）：外部核实（2026-10-27）——Claude 标准档单图上界 **1568**（`⌈w/28⌉×⌈h/28⌉`，高清档 4784）；OpenAI high detail = `85 + 170×tiles`，4K 图 resize 后约 12 tiles ≈ **2125**。固定 1100 对小图高估、对 OpenAI high 的大图**低估近一半**，与「宁可高估」的旗号相反。`ImageRef` 已有 `width/height`，白收不用是内部不一致。
- **`IMAGE_TOKEN_UPPER_BOUND` 必须可配**：默认 1568 覆盖 Claude / 常规 OpenAI；实测后端为 OpenAI high 时上调到 2048+。配置项进与 `supportsVision` 同一 DTO（§5.5），避免第二个配置面。
- **这不是精度问题，是方向问题**：宁可高估（早截断、可解释）不可低估（爆窗、神秘 400）。
- 图片**不进** `estimateTokensText`（那是「单段文本」入口）。
- **`EstimableMessage` 必须补 `attachments?: readonly ImageRef[]`**（公开导出类型，§6.3），否则调用点只能 `as any`。

> ⚠️ **估算器单点 ≠ 显示单点（2026-10-27 复核补的真缺口）**：内核 `estimateTokensMessages` 是**唯一**计量函数没错，
> 但「谁喂数据给它」决定环准不准。宿主对话占用环（`chatPanel.postHistoryOccupancy` → `collectHistoryMessages`）
> 当前只取 `{ role, content }`，**会剥掉 `attachments`** 再喂估算器 ⇒ 环只按文本计、图片被漏算，
> 显示「还剩 8k」实则已溢出而用户无感知。这是 P0 级别的**真缺口**（非设计取舍），完成判据见 §7 P0-11 与台账 `IMG-1`。
> 修复点：宿主侧**必须**把带 `attachments` 的 history 喂给同一 `estimateTokensMessages`（不另写估算），且**复用同一
> `RETAIN_IMAGE_ROUNDS` 窗口衰减**——否则衰减轮图片在环上仍被计入、与模型侧实际挂载错位。

### 5.10 图片显示链路（**2026-10-27 前移至 P0**，方案已定）

**拍板：`localResourceRoots` 加一格 + CSP 加一项。**

```ts
// 面板创建处：把自家收紧的白名单加回一个子目录（不放开整个工作区）
localResourceRoots: [
  vscode.Uri.joinPath(this.extensionUri, 'dist', 'webview'),
  vscode.Uri.joinPath(workspaceRoot, '.memora', 'attachments'),
]
// htmlShell CSP
img-src data: ${cspSource};
```

缩略图 URL = `webview.asWebviewUri(Uri.joinPath(attachmentsRoot, `${sha256}.${ext}`))`。

- **为什么不走 blob**：还要改 CSP 加 `blob:`，还要管 `revokeObjectURL` 生命周期，且重放时要把全部图片字节传一遍。方案 A 由浏览器自己按 URL 缓存、按需加载、零内存管理。
- **缓存的代价（IMG-6，2026-10-28 补）**：内容寻址 ⇒ 同一文件的 URL 恒定 ⇒ 缓存是**正确**的（同内容同地址）。但文件被手删后再悬停会命中缓存而**不发请求**，`img.onerror` 因此不触发 ⇒ **`onerror` 只是「这次请求失败」信号，不能当存在性判据**。悬停文案已相应改为「预览加载失败（sha 前 8）」，不再断言「图片不可用」。真判存在性须由宿主 `stat`（IMG-6 二级，未做）。
- **风险面**：白名单只到 `.memora/attachments` 单目录，其中只有本扩展写入的文件；CSP 只放行 `cspSource`（与既有 `script-src` 同源），不引入新的网络源。
- **两个消费面（勿折叠）**：① **输入框附件行 chip 的悬停预览**——P0（安全面随之前移，因为悬停预览就是这个面）；② **聊天记录里已发送图片的渲染**——仍属 P1。两个面共用同一条 URL 与同一份白名单。

**消费面②（聊天记录）为何不继承 D28 的「文件名 + 悬停」**（2026-10-27 用户提问后定案）：

| 判据 | 输入框附件行（P0） | 聊天记录（P1） |
|---|---|---|
| 这个面的角色 | **选择清单**——「我选了哪几张」，文字可扫、省高度 | **对话内容**——「图长什么样」本身就是上下文 |
| D28 的原始约束 | 位图撑高 chip、破坏单轨等高 | **不成立**：正文是纵向流，图有自然位置 |
| 悬停可用性 | 行静止，悬停安全 | **长会话滚动时指针划过一串图 ⇒ 弹窗乱闪**，且「要看图还得悬停」割裂阅读 |
| 数量级 | ≤5 张（单轮上限） | 可达上百张 ⇒ **必须 `loading="lazy"`**（视口外不加载），P0 不需要 |

⇒ **继承组件与数据，不继承形态**：P1 聊天记录里**直接显示缩略图**（高 ≤160 / 宽 ≤240 上限），`ImageRef.name` 退到 `alt` 与 `title`，点击 / 悬停放大复用**同一个预览 tip 组件**，缺陷态仍是「图片不可用（sha256 前 8）」。把 D28 机械外推到正文 = 用 chip 行的约束去约束正文（判据作用域外溢）。

- **两个数据源（勿折叠，P1 施工前必读）**：聊天记录的图片**取自存储层 `RoundMessage.attachments`**（webview 投影是对象展开，自动透传，F4），**不是**取自装配层的窗口衰减结果（§5.12 / `RETAIN_IMAGE_ROUNDS`）。两者服务不同目的——窗口衰减只为**省 token**，**不得**被当成 UI 渲染开关；否则第 5 轮之前的图在聊天记录里会凭空消失（而模型侧本就只看到占位）。

- **验证方法**：必须实测「悬停 chip 出预览 → 移走附件文件 → 预览显示『图片不可用』」三步，不能只看门禁绿。

**输入框附件行（D28 / D29 · 2026-10-27 用户拍板）**：

| 项 | 定案 | 依据 |
|---|---|---|
| 落点 | **第三条同构行 `#imageChips`**（兄弟 = `#skillChips` / `#refChips`） | 图片与文件引用的清理语义、URL 源都不同；塞进 `#refChips` 要引入 kind 联合类型 |
| 行绑定 | 复用既有 `bindSingleTrackRow(row)` + `syncRowEdges(row)` | HOST-CTX-10 单轨判据（不换行 / 溢出横滚 / 边缘渐隐）是**一套**，不许第三条行自带第二套 |
| chip 内容 | **与 `#refChips` 同构的文字 chip**：`span.skill-chip__name` = `ImageRef.name`（文件名）+ × 移除；`title` = 「图像 MIME / 像素尺寸 / 体积；悬停预览」 | **不放缩略图**（D28）：位图会撑高行高、破坏 chip 等高；文字 chip 与既有两行视觉一致 |
| 文字截断 | `max-width` + `text-overflow: ellipsis`（同 `.skill-chip__name` 既有规则） | 长文件名不许换行撑破单轨 |
| 悬停预览 | **单例 tip 元素**（`#imgPreviewTip`，挂在 body 内的 `position: absolute` 层），`mouseenter` 时才 `img.src = asWebviewUri(...)`，`mouseleave` 清 `src`；上方空间不足时翻到下方 | 复用 `#occTip` 的单例 tip 范式，不新建组件体系；**不挂在一点即开的 Popover**（附件行里点击已被 × / 打开占用） |
| 预览尺寸 | 固定上限约 320×320，`object-fit: contain`；点击放大 / 打开原图归 P1 | 悬停预览是「确认是不是这张」，不是看图工具 |
| 钉住语义 | 不提供 🔒（发送即清，同 `#refChips`） | 图钉住 = 每轮重发同一张，撞窗口衰减（D22）与 body 上限 |

- **诚实登记的残余风险**：悬停预览让 `<img>` 在悬停时才 decode，**常规使用不再有「粘 5 张 4K 图」的内存峰值**；但悬停一张 4K 图仍要 decode 整图（`<img>` 尺寸只影响绘制不影响解码），单次峰值与图片本身等量级。缓解只到「单例 + 离开即清 `src`」，**不做转码**（D16 是硬约束）。
- **P0 前移的代价**：webview 安全面两处（CSP `img-src` + `localResourceRoots` 加 `.memora/attachments`）必须在 P0 一次改对，且要跑真机三步：悬停出预览 → 移走附件文件 → 预览显示「图片不可用」。
- **缺陷态**：文件已被删 / 被移走时，悬停预览显示「图片不可用（{sha256 前 8}）」，**chip 本身仍在**（它与请求侧的降级占位是同一条判断，§5.5 第②层）。

### 5.11 已知限制（诚实登记，不假装已解决）

1. **「最近对话」注入只带占位文本**：注入装配只拼 `content`（F17），带图轮在注入里显示为占位。模型知道"用户发过图"但看不到图 ⇒ **可能追问或复述错误**。缓解：占位文案中性化（不承诺可见），P1 观察是否真出现复述错误。**不通过"注入里补图"解决**——那会把注入通道变成第二条图片通道。
   ⚠️ 诚实条款：D21 让占位带路径，但**不构成"模型能自己读回"的保证**——`read_file` 只读 utf-8（F18），模型拿到的是损坏文本。占位路径的收益仅限「人类可定位 + 为 P2 预留坐标」（R7-5）。
2. **历史图片每轮全量重传**：无状态 API 的必然，与 Cline / Roo 一致，非设计缺陷。**衰减手段**：按 `retainRounds` 窗口只复水最近 4 轮（D22 / D23），窗口外降级为占位（§5.12）。剩余代价 = 窗口内仍全量传，由入口限额（单轮 ≤5 张、≤20 MiB）兜底。
3. **中途插话不带图（D13）**：`interject(content: string)` 签名不变，`RoundInteractiveInput` 不带 `attachments`。
4. **不做内联缩略图（D17）**：输入框上方附件条，不嵌进文字流；语义弱化为「附属于本段文字」。
5. **首次加载会话有一次同步预读 IO**（§5.4.1）：窗口内附件同步读盘，最坏 32 × 5 MiB ≈ 160 MiB。实测超 50 ms 再考虑分帧预读；当前判断为可接受（只在打开会话时发生一次）。

### 5.12 历史图片的窗口衰减

**判据**：装配投影时，只有最近 `RETAIN_IMAGE_ROUNDS = 4` 轮内的 `RoundMessage.attachments` 被带上；更早轮次**不带**（`content` 不变，仍是那句占位）。

```ts
// 装配层（loadRoundBasedMessages，Round → SessionMessage 投影处），不是 formatMessages
// 真源 = 会话 roundIds 的**索引差**（Round 无 seq 字段，见 F23）
const idx = session.roundIds.indexOf(round.id);   // 该轮在会话中的位置
const currentIdx = session.roundIds.length - 1;   // 当前轮位置
const withImages = currentIdx - idx < RETAIN_IMAGE_ROUNDS;
attachments: withImages ? msg.attachments : undefined,   // 同一行还要在第 2 跳透传（§5.1.1）
```

五条设计理由：

- **为什么在装配层而不是 `formatMessages`**：`formatMessages` 拿到的消息是**扁平的、且已丢掉轮次归属**——`applySessionToLoop` 投影只取 `role / content`，`roundId` 在这一跳就被丢了（R8-2）。所以它结构上无法判断"这是第几轮"。装配层本来就在做 Round → SessionMessage 投影，**是唯一同时持有「会话 `roundIds` 数组」和「当前轮位置」的地方**，窗口判断是它天然持有的上下文。**放错层会逼着往投影里加 seq 字段——那是为了一条优化去污染持久化结构。**
- **为什么按轮次而不是按字节预算**：字节预算需要先算出所有图的大小再排序淘汰，必然产生「这一轮的图被淘汰掉一半」的怪异中间态，而用户看到的是"我明明发了 3 张，模型只提了 1 张"。轮次是整数、可解释、可预期。
- **为什么零状态**：窗口 = `当前索引 − 消息索引`，纯计算。**不需要任何持久计数器**——与 D12「GC 用幂等扫孤儿」同一条思路：能用重算表达的，就绝不引入状态。
- **与上下文截断正交**：截断切的是文本（§6.6），窗口切的是图片挂载。两者互不依赖，任一方生效另一方仍然正确。
- **窗口的第二个职责**：同一个 `RETAIN_IMAGE_ROUNDS` 同时是**预读量上限**（§5.4.1）。两处共用同一常量，不分叉；改一处即两处同步。

**窗口内整轮进退**：`interactiveInputs` 与 `userMessage` 同属一个 `Round`，因此不存在"半轮的图在、半轮不在"的状态。

**诚实登记的残余风险**：窗口外的轮次若被追问「刚才那张图」，模型会失忆并可能编造。**这是有意的取舍**——全量复水的代价（body 上限 + 费用）在长会话里必然先撞墙，而"最近 4 轮"覆盖了绝大多数真实追问场景。P1 需实测：长会话追问第 6 轮前的图，观察模型是明确说"看不到"还是编造；若普遍编造，再考虑提高窗口或改注入文案。

## 6. 不带伤清单

### 6.1 协议计数（最容易踩死）

- 现状余量见 `shared/__tests__/protocolGuard.test.ts` 的阈值与实时差值（**不落计数快照**：该数字每次增删通道即过期）。
- **订正（2026-10-28）**：本节原判「本设计**零新增消息类型**，图片随已有 `send` 输入走（判别词是 `kind`）」——**已被平台边界与真机推翻**。实际新增 **4 条**专用消息（`IPC_CHANNEL_GOVERNANCE_THRESHOLD` 132→134）：`image_ingest`（W→E，粘贴/拖入的字节上行）、`image_ingest_result`（E→W，落盘三态回执）、`image_pick_request`（W→E，请求宿主开原生文件框）、`image_picked`（E→W，拾取三态回执）。推翻依据：① **字节不能随 `send` 走**——`send` 是对话输入载荷，图片字节必须走「宿主复算 sha256 → 落盘 → 三态回执」的独立时序（§5.3 的 base64 单点 + D20 三值校验），塞进 `send` 等于让未复算的提案值进模型上下文；② **资源管理器拖入被平台判死**（外部拖入事件止于 workbench 层，webview iframe 零事件），而 `showOpenDialog` 只有扩展宿主拿得到 ⇒ 必须有一条 W→E 拾取请求 + 一条 E→W 回执，这是拖入失效后唯一不依赖 Drag&Drop 的入口。拍板过程见台账 `IMG-2` 第 5 / 6 子块。
- ⚠️ **禁止**在 `shared/protocol.ts` 出现 `type: 'image'` / `type: 'attachment'` 字面量——`extractMessageTypes` 正则会无条件累加，一条即判红（F12）。
- 宿主 DTO 字段：`{ sha256, mime, width, height, bytes, name }`，**不用 `type`**（`name` 见 D29：必填，无声明名时宿主按 `粘贴图片-{sha 前 6}` 兜底——粘贴入口恒走兜底，见 `IMG-4`）。

顺序**保序**（「这张和这张对比」依赖顺序），采集层按输入顺序编号，不许「文字前置、图片后置」。

### 6.6 截断与摘要

- 截断只作用于 `content` ⇒ 图片结构上不可能被切碎。

### 6.7 入口限额（宿主唯一裁决点）

| 项 | 上限 | 依据 |
|---|---|---|
| 单图字节 | 5 MiB | 主流单图上限 20MB；5MB 是 Claude / OpenAI 安全交集 |
| 单轮张数 | 5 | 超 5 张实用价值趋零，成本线性涨 |
| 单轮总字节 | 20 MiB | base64 膨胀 33% 后不撞 48 MiB body 上限 |
| **单轮图片 token** | **≤ 该模型 `contextWindow` 的 25%** | 字节无限额、token 无限额 ⇒ 小窗口模型（8k）收到 5 张 4K（≈10.6k token）必爆。**这是唯一「真机上真会爆」的缺口**（§4.1 G3） |
| 格式 | PNG / JPEG / WebP / GIF | **拒 SVG**（脚本注入面 + 多数 vision 不支持） |

超限在**入口**拒绝并给可见提示，不靠服务端 400 兜。第四条的数字要**给出来**（「本轮图片约 10.6k token，超过该模型窗口 25%（2k）」），只说「太多了」用户无法自我纠正。

**同轮去重（§4.1 G4）**：同轮同 `sha256` 只留一条 chip，再粘同一张提示「已添加」。sha256 本来只保证**物理文件**去重，数组去重必须显式做——否则同一张图发两遍 = 双倍 token + 无意义视觉重复。

**富文本粘贴（§4.1 G5）**：只认 `clipboardData.files` / `items` 里的 `image/*`，**不解析 `text/html`**。从网页 / Word / 微信复制常带 `<img src="data:image/png;base64,…">` 而 `files` 为空——此时给一条提示「检测到内嵌图片，请截图后单独粘贴」，**不假装接住了**。

**落盘失败（§4.1 G6）**：`fail-closed`——入口拒绝 + 可读原因（`.memora/attachments` 不可写）。**不降级为内存态**：内存态重启必失，等于承诺了做不到的事（R8-6 同族）。

**格式判定只看字节，不看扩展名、不看用户声明的 mime**（D18）：`%PNG` / `FFD8FF` / `RIFF….WEBP` / `GIF8` 四种 magic bytes 手写嗅探（F20：内核零依赖、无 `file-type` 类库，这段 ≤20 行）。SVG 天然被拒——它不是这四种之一，**不需要单独写一条"拒 SVG"规则**（规则少了，漏判面也就少了）。

### 6.8 不转码

不引 sharp / canvas：内核零三方运行时依赖是硬约束，宿主也不该为可选功能扛原生依赖。靠入口限额解决。

### 6.9 记忆与 CoT 隔离

图片不进记忆（`Memory` 是文本资产）、不进 CoT（`thought` 是文本增量轨）、不进「最近对话」注入的图片通道（只留占位文本）。零额外逻辑——这些链路全都只读 `content`。

### 6.10 孤儿扫描（不用引用计数）

```
orphans = attachments/ 现存文件名集
        − ⋃(每个 Round 的 userMessage.attachments)
        − ⋃(每个 Round 的 interactiveInputs[*].attachments)
        − ⋃(每个 Round 的 assistantMessage.attachments)
        − ⋃(每个 Round 的 assistantLog[*].attachments)
```

- 幂等、可重复跑、无需持久计数器；**启动时扫一次为主力**（能兜住全部孤儿）。
- R8-8：**扫描面必须显式枚举四处**，不能只扫 `userMessage`——`assistantLog` / `interactiveInputs` / `assistantMessage` 里的引用若被漏算，会被当孤儿删掉，症状是「历史里的图突然变灰」且无测试红。
- **时机**：会话删除后跑一次是空跑（`Round` 被多会话共享，删会话通常不产生孤儿）；真孤儿来自 `Round` 被 GC 物理删除。启动扫描是真正兜底，别把「会话删除时扫」当主力。
- 单测覆盖三态：只有孤儿 / 只有活引用 / 混合；另加一条「引用只存在于 `interactiveInputs`」的用例，钉住扫描面不漏。
- 越界防护：只删 `.memora/attachments` 下、文件名匹配 `^[0-9a-f]{64}\.(png|jpg|jpeg|webp|gif)$` 的文件——**永不递归、永不删目录**。
- **未发送即落盘（§4.1 G9）**：采集时就写盘（校验需要字节），所以「粘了但没发送」「粘完切了会话」都会留下孤儿文件。**接受**这个孤儿窗口——靠启动扫描兜底，**不做**「输入框卸载即删」（会与 `History` 撤销、切会话、草稿恢复打架）。⚠️ 与 G8 合起来意味着：孤儿能被回收，但**活引用的图无容量上限**。

### 6.11 隐私

图片落 `.memora/attachments/`（本地工作区），不上传第三方。首次粘贴时 UI 明示「图片会随请求发送给模型提供商」。

### 6.12 入口校验链（D18 / D19）

宿主采集图片时按此顺序校验，任一步失败即拒绝并给可见原因（**不静默丢弃、不带病入库**）：

| # | 校验 | 防的是什么 |
|---|---|---|
| 1 | 字节非空 | 空文件 |
| 2 | 字节数 ≤ 5 MiB | 内存与请求体膨胀 |
| 3 | magic bytes 嗅探出 mime ∈ {png,jpeg,webp,gif} | 扩展名伪装、SVG、非图片 |
| 4 | 嗅探结果与声明的 mime 一致（若声明存在） | 前端声明与实际不符 |
| 5 | 解码后字节数 == 原字节数（往返一致） | 传输/拼接截断 |
| 6 | **解析像素尺寸窄高（width/height）** | `ImageRef` 必填字段无人产出 ⇒ token 计量与 UI 显示全错（见下） |

**为什么第 5 步要往返校验**：只校验长度挡不住非法 base64；只校验字符挡不住截断。**两个都做才算闭合**——这一条是厂商实现里最容易被跳过的判据，跳过后的症状是「偶尔发出的图在服务端变成半张」，极难复现。

> **落地形态（2026-10-28）**：第 5 步刻意实现为**不解回字节**——base64 是固定比率编码，
> 「去掉 padding 后的字符数 × 3 ÷ 4 取整」恒等于原始字节数，故「长度一致」这件事用纯算术
> 即可判定，既不依赖 `Buffer` 也不依赖 `atob` ⇒ 浏览器侧（webview 采集）与 node 侧
> （extension 落盘）能共用同一份代码，不必为环境差异准备两套。此为该步的实际依赖面最小化。

**为什么第 6 步必须手写解析、且必须在这一步就做**：`ImageRef.width/height` 是 §5.9 token 计量与 `alt` 显示的唯一来源，但**没有任何现成 API 能白给**——`sharp`（原生二进制）、`image-size`（三方包）都违背零依赖约束（§6.8）。所以只能读文件头取固定偏移，四种格式各一小段：PNG 取 IHDR（第 16–23 字节、大端 uint32 宽高）、JPEG 遍历 `SOF0–SOF15` 段（跳过 `C4/C8/CC`，段内偏移 5 起两字节高再两字节宽）、WebP 按签名分 `VP8 ` / `VP8L` / `VP8X` 三型（`VP8X` 是扩展区宽高各减一）、GIF 头第 6–9 字节小端 uint16。**全部只读前几十字节、不解码整图**。⚠️ 若把这一步挪到发送时或省掉，`width/height` 就是 `ImageRef` 里的两个死字段：token 估算退化成 `0`（低估 ⇒ 爆窗）或 `NaN`（比较恒 false ⇒ 静默失效），且**没有任何现有测试会红**。

> **订正（2026-10-28 落地复核）**：本节原文写「内核只在 `formatMessages` 侧做 `ref` 三值比对（D20）——那是二次防线」，该说法**不可实施**，已订正。**D20 三值校验的唯一落点是宿主 resolver 内部**（§5.4 示例代码的判据行 `hit.mime !== ref.mime || hit.bytes !== ref.bytes`），理由有三：
> ① 三值要比的其中一值是**原图字节**，而 `ImageResolver` 的返回值只是 `{url}` / `{text}` / `null`，**不含字节** —— 内核手里根本没有可比对的那一半；
> ② 真要在内核侧校验 `sha256`，就得引入哈希实现（`node:crypto` / Web Crypto），破「零三方依赖」（§6.8）且讓内核不再是纯端口；
> ③ 即便能做，代价是**每轮每条带图消息都重算一次全图哈希** ——`formatMessages` 是每次请求都走的熱路径，这条成本没有收益。
> ⇒ 宿主核验不符 ⇒ 直接返回 `{text}` 占位或 `null`（宿主缓存条目里已有三值，比对是常数开销），内核只负责把它转成**可见占位**（D7 / §5.4）。内核侧**不存在**三值校验这道防线。

**为什么校验在宿主而不在内核**：内核零 IO（§4），拿不到原始字节。

### 6.13 占位文案规范（D21）

- **生产权归宿主**：`ImageResolver` 返回 `{text}` 决定文案，内核只做不透明透传（§5.4）。
- **内核 fallback 只给最短信息**：`[图片不可用 {sha256 前 8 位}]` —— 内核不知道路径，也不该知道。
- 宿主文案格式：`[图片 {文件名} {mime} {人类可读大小} 存于 {相对路径}]`。
- **禁止**在文案里写「已发送」「模型可见」这类断言——降级路径的语义恰好相反（§5.11-1 / R7-5）。
- 文案里出现的路径**必须是工作区相对路径**，不出现绝对路径（避免泄露用户名/盘符到模型上下文）。

## 8. 反对方案（对抗式审查）

| 方案 | 否决理由 |
|---|---|
| base64 进 `Message.content` | 四连爆（§5.2）。 |
| `content` 改联合类型 | 88 处消费点 + 两处摘要兜底把用户消息静默标 `[tool]`，无编译错无测试红（R1）。 |
| 加 `image_upload` 协议消息 | 直接顶到协议计数阈值（F11），且不携带新语义。**与落地形态的分野**：此处否决的是「**一条** `image_upload` 把字节与对话输入混装」；实际落地是 **4 条各司其职的专用消息 + 宿主落盘回执**（`image_ingest` / `image_ingest_result` / `image_pick_request` / `image_picked`，2026-10-28 扩位，见 §6.1 订正）——两者不是同一条路线。 |
| 新增 `chatWithAttachments` | 两个入口 = 两套状态机（pause / resume / interject 各要覆盖），并列即腐化（D8）。 |
| 用 `Round.refCount` 做图片 GC | 轮级计数反推文件级引用，分叉 / 中断必漂移（R5）。 |
| 内建模型能力表 | 违背内核零解析；表会腐。复选框 + fail-closed 覆盖多数场景（D15）。 |
| 探针探测 | 每次配置真花钱，400 与额度 / 违规难区分。 |
| 缩略图走 blob URL | 仍要改 CSP，还要管 revoke 生命周期 + 重放全量传字节（§5.10）。 |
| 自动压缩 / 缩放 | 引原生依赖，违背零依赖约束（D16）。厂商实现确实在渲染层用 canvas 压缩，本项目不跟——原字节入库才能保证 sha256 恒等于用户给的那张图（可审计）。 |
| `supportsVision` 默认 true | 把"能力缺失"和"请求失败花钱"当同类风险（D6）。**即使厂商级实现这么做也不改**——对方是自有云服务，判错只是重试（R7-2）。 |
| 入口失败也走 strip 降级 | 制造**不可发现的错误**：用户看到正常回答，却不知道图根本没发出去（§5.5 / R7-3）。 |
| 历史图片全量复水 | 长会话必然先撞 body 上限；窗口衰减是零状态纯计算（§5.12）。 |
| 内核里拼降级文案的路径 | 内核因此获得文件系统知识，破坏零 IO 边界；文案生产权归宿主（§5.4 / §6.13）。 |
| 给 `Message` 加轮次字段以支持窗口判断 | `applySessionToLoop` 已经把 `roundId` 丢了（R8-2）；补回它等于为一条优化污染投影结构，且历史消息仍无序号。窗口判断天然属于持有 `roundIds` 数组的装配层（§5.12）。 |
| 把 `formatMessages` / resolver 改异步 | 一条异步要扩散到 `chat()` 整条时序下游；而「会话加载期同步预读」已用同步语义解决同一问题（§5.4.1）。能用同步解决的不引入异步。 |
| **只发路径 / 链接，让模型调工具看图**（2026-10-27 用户提问，**否决**，D31） | 三条硬理由：① **协议层挡死**——`Message.content: string`（`src/llm/provider.ts`），工具结果只能回字符串，OpenAI Chat Completions 的 `role:'tool'` 也不收内容数组 ⇒ 工具**没法把图还给模型**；Anthropic 的 `tool_result` / OpenAI Responses 的 `function_call_output` 才支持图片，那是**换协议**不是加工具。② **支持面收窄**——`image_url` data URL 是跨厂商唯一一致形态（兼容端点 + 本地运行时都认），工具返图只有少数协议支持、Ollama 基本没有。③ **token 不省**——图最终仍要进上下文，一分不少，还多一次 LLM 往返（延迟 + 成本），且模型**可能不调**（小模型尤其）⇒ 「图没被看」而用户不知道，正是本方案判为「不可发现的错误」的那一类。**若真实动机是「图不该每轮重发」**（A 的真实痛点），最小解是把窗口衰减从 4 轮收紧（§5.12），不必换协议。真要做 = P2 + MCP D7 合流，且必须先改工具结果协议为内容块（波及全部工具 / 摘要 / token 估算 / 落盘），属 major 级，**不在 P0 塞半个**。 |
| 只在粘贴时填 resolver 缓存、不做预读 | 重启 / 切会话后缓存必空 ⇒ 全部降级占位 ⇒ 验收③不可能通过（R8-6）。预读不是优化项，是验收前提。 |
| 注入通道里补图 | 会把「最近对话」注入变成第二条图片通道，双真相源（§5.11-1）。 |

## 9. 与既有 SSOT 的嫁接关系（零并列真相）

| 既有单点 | 如何嫁接 |
|---|---|
| 能力位链（DTO → store → llmConfig → 构造器 → loop） | `supportsVision` 走**同一条链**，不新开通道 |
| `formatMessages` | **唯一** base64 生成点，无附件路径字节级不变 |
| `estimateTokensMessages` | 分支加在**同函数内**，不另立估算模块 |
| `Round` / `RoundMessage` 落盘 | 新增可选字段，整对象 JSON 天然带上，零 IO 改造 |
| provider 由宿主注入 | `ImageResolver` 同构注入，内核只定端口 |
| 输入边界裁决归宿主 | 图片限额与 `contextWindow` 护栏同类 |
| 装配投影层（**两跳**：`loadRoundBasedMessages` → `applySessionToLoop`） | `retainRounds` 窗口判断落在**第 1 跳**，**第 2 跳**只做透传；都不往 `Message` 加轮次字段（§5.12 / R8-2 / R8-3） |
| 对话 token 占用环（`chatPanel.postHistoryOccupancy`） | **必须**把带 `attachments` 的 history 喂给内核 `estimateTokensMessages`，**不得**自行剥 `attachments` 重算；窗口衰减复用同一 `RETAIN_IMAGE_ROUNDS`（P0-11） |
| 会话加载入口（切换 / 分叉 / 重启） | 预读挂在这里，不新开加载通道（§5.4.1） |
| MCP 工具链 | 工具返图**不并入本方案**，走 MCP 方案 D7（R8-7）——避免两套「模型怎么看到图片」 |
| provider 注入的「宿主给值、内核透传」范式 | resolver 返回的降级文案同构：宿主生产、内核不解释（§5.4 / §6.13） |
| `showToast` | 超限 / 拒绝提示复用，不新建通道 |
| `Agent.chat` 现有两参 | 第三参追加，不替换、不并列 |

**新增的并列真相 = 零。** 这是本方案唯一值得称为"设计"的地方。
