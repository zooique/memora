## 2. 不可砍的安全底线（引用，不复制）

方案 §16.2 的 G1–G5 原文写的是「缺一条就不能开」，§16.3 六项必做档写的是「缺一不可」。这不是清单，是开端口的准入条件：

- **绑定地址配置**：默认 `127.0.0.1`，LAN 档显式开启并显示当前绑定地址。
- **设备身份与配对白名单**：公钥 + 指纹，首次信任必须 PC 侧人工批准。
- **权限三档**：只读 / 可答 / 可发，按档裁决，不靠「谁能连上就算授权」。
- **失败限流与 TTL**：来源 IP + 设备维度计数、退避、临时封禁。
- **追加式审计**：落 `globalStorage`，只 append，不写 `.memora`。
- **监听失败显式报错**：端口占用 / 权限不足时必须报错并保持未监听态，禁止「失败但 UI 显示已连接」。

三条硬约束（§16.4）照旧：**桥不调 webview 输入入口与 `post()`**、**桥不 `switch_session`**、**桥不绕过相位裁决直调内核**（仍走 §7.2 规则表与 `remoteCommandPolicy` 真值表，错误码只从 `REMOTE_COMMAND_CODES` 取）。

> **E2EE 机制定案（2026-11-26）**：L1 从「Noise IK」订正为 **TLS 1.3 + 双向自签证书 + 证书指纹固定**（D2 的安全目标不变：一次性口令 + 双向指纹 + PC 人工批准 + 信任不来自 CA）。spike 实测与否决理由见方案 §19.9；本节六项不复制其细节。

**大白话**：端口 + IP 只是门牌号，不是锁。R0 的命令面已经能发审批、作答、发消息，裸端口等于把 Agent 的遥控器挂到网线上。

## 3. 阶段顺序与切口

严格按方案 §9.4 的 S0→S5 排序，本单只推进前两段加 LAN 桥，不跳级：

| 顺序 | 阶段 | 本轮做不做 | 为什么 |
|---|---|---|---|
| 1 | **S0 多会话可见** | ✅ 第一刀 | 零传输、零端口、零产品取舍 |
| 2 | **S1 会话可寻址** | ✅ 第一刀 | 依赖 S0，仍然不碰端口 |
| 3 | **LAN 档桥**（S3 的局域网半边） | ⏭ S0/S1 通了再做 | 必须带齐第 2 节六项，不能先开端口后补锁 |
| 4 | **外网 Mode T** | ⏭ 后置 | 用户自接隧道，插件只提供 URL 配置面，约束见 §4.6.1 五条 |
| 5 | S2 路由闭环 / S5 手机主场景 | ❌ 本轮不开 | D6 已拍为不做路由派发；手机端底座虽已选（第 9 节），但 §18.5 判定闸门未过且 S0/S1 未通 |

**形态订正（2026-11-26）**：回环档与 LAN 档是**同一个桥**的两个 profile（绑定地址 + 权限档 + 传输适配器的组合），不是两套实现；安全闸与监听同批落地。四个 profile 的交付口径与销项证据见方案 §19.3。

**交付顺序（2026-11-26 定案，判据见方案 §19.8）**：先宿主后手机。宿主内**先做手机端依赖的底座**（S0/S1 按 sid 服务多会话），其余 PC 功能可并行、不阻塞手机端闸门；手机仓开工须三条全过——S0/S1 销项、LAN 桥通过、§18.5 闸门全过。内核零网络不变，手机端永远只接宿主桥。

**明确不做**：手机 App 开工（底座已选但 §18.5 判定闸门未过，且 S0/S1 未通；见第 9 节）、Relay 运营（D3 已拍不运营）、Mode D 公网直连（安全档最高，最后做）。

**回环档的边界**：只绑 `127.0.0.1` 能最快跑通桥协议，但**手机连不上**，只能当开发验证，不能当交付。第一刀的可交付形态必须是带配对 + 等价 E2EE 的 LAN 档。

## 4. 第一刀（S0/S1）规格

**消费面 = A：PC 侧侧栏/面板**（用户 2026-11-24 已按推荐认可）。理由：肉眼可验，避免再造一个零消费方的前置件——这正是 `REMOTE-R0-1` 现在的病。

- **S0**：任意 sid 的投影可算（复用 `deriveSessionProjection`）+ 会话列表亮「在跑 / 待审批 / 待答」。验收 = PC 不切会话也能看到后台会话状态（§9.4）。
- **S1**：按 sid 发消息 / 插话 / 暂停 / 恢复 / 答提问，复用 `routeInput`（已按 sid 路由）+ `answerFor`，不新造动词、不新造错误码；`remoteAnswerRouter` 属桥层件，不在此接入。验收 = 面板对指定 sid 发一条命令，落到该会话（§9.4）。
- **不得宣称「路由可用」**：S1 只有工具、没有汇报闭环，对外说法只能是「会话可寻址」（§9.4 差异 2）。
- **共享前置不重复立项**：S0/S1 同时是路由主助手线的前置，做一次两条线消费（§9.4 头部注记）。

**开工时按台账治理纪律立项**，不挂在 `REMOTE-R0-1` 下面（该条只记已落地的 R0 前置件，桥本体另起）。

## 7. 已拒绝的路线（防复活）

| 路线 | 否决理由 |
|---|---|
| 「填个端口 + IP 就能连，具体怎么连接不管」 | 砍掉配对、E2EE、限流、审计，裸入口；同网段任何人可驱动审批。端口 + IP 不是锁 |
| 手机 App 先行 | 底座已选（第 9 节）不等于开工：§18.5 判定闸门未过，且 S0/S1 未通时做 App = 造零消费方 |
| 把手机端做成「两个对等对话」/ 给助手会话做列表 | 助手是一条固定会话（工作区指针认定），工作会话是 N 条；照「两个对话」实现会造第二助手或第二列表真源。判据在方案 §19.6 |
| 手机端直接新建 / 删除 / fork 会话（含借 tabbar 夹带） | 撞 §8 P2-12 / §16.3 不做档与 §6.6 断路器；要开先走第 6 节重开条件，判据在方案 §19.6 第 4 条 |
| 整仓 fork 某候选当双 tab 壳 / 拿 agent 选择页改叫宝卡 | 没有候选原生长着「宝卡 + 工作列表」双 tab：ccpocket 是覆盖式多 pane、PinkCollab 是顶部 pager；壳须自建，候选只供叶子；agent / provider 选择入口撞 D6。判据在方案 §19.7 |
| Relay 先行 | §9.4 差异 1：自用场景不该把运营云服务前置 |
| 回环档当交付 | 手机连不上，只能开发验证 |

## 8. 插件改动面（引用判据，不复制）

插件侧要动的不是「开个端口」，而是把宿主从「只服务当前显示会话」改成「按 sid 服务多个会话」。判据全集在方案，下面只列改动面与引用：

| 改动面 | 要改成什么 | 判据出处 |
|---|---|---|
| per-session 视图状态表 | 单份 `_turnState` → `SessionViewState`（state / rounds / pendingQueue / activity），webview 与 bridge 各自订阅（**2026-11-26 现状订正**：宿主已是 `_turnStates: Map<string, TurnState>`，分片本身完成；剩余是按 sid 的投影消费面与真机验收） | §9 P0-1（现状事实见 §7.1 B1 与本表订正；现行调用链判据见方案 §19.2） |
| `handleInput` 会话定址化 | 显式传 `sid`，旁路 draft 分支 | §9 P0-2 |
| 投影函数宿主入口 | 复用 `deriveSessionProjection`，补「按 sid 取素材」的宿主入口 | §9 P0-3（R0-b 已落纯函数） |
| 审批 / 提问双投递 | `ConfirmDeps.post` 扩为 `post` + `onRemote`，答复仍归一到 `answer()`（谁先答谁生效） | §9 P0-4 |
| 附件 URL 与远端解耦 | 远端走 blob 通道，否则图片全 404 | §9 P0-5 |
| 协议包上提 | `protocol.ts` 上提 `packages/protocol`；只共享协议不共享代码；禁复制 `protocol.ts`，schema 与类型同源。手机端独立仓不 import 该包，靠 golden fixture 双向断言对接 | §10.4 + 仓库形态订正（2026-11-24） |

**三条硬约束**（§16.4，越界 = 方案作废）：桥不调 webview 输入入口与 `post()`；桥不 `switch_session`；桥不绕过相位裁决直调内核（仍走 §7.2 规则表 + `remoteCommandPolicy` 真值表，错误码只从 `REMOTE_COMMAND_CODES` 取）。

### 9.1 选型结论（判据在方案 §18）

- **首选 `K9i-0/ccpocket`**：§18.7 A 类第一；MIT、Flutter 一套出 Android、QR / Tailscale 配对无账号。它的 Codex / Claude 语义已渗进 `ChatSessionState`，**必须删模块，不是加个 provider**（§18.2）。
- **备选 `slopus/happy` 的 `packages/happy-android`**：质量最高，但须先证明能只取 Android 包、切断 relay / E2EE（§18.7）。
- **其余三个出局**：`happier` 约 1GB 且重模块多、`ovis` 绑 `herdr`、`opencode-mobile` 只支持 OpenCode（§18.2）。
- **交互借 `assistant-ui`**：只借会话列表 / 流式消息 / 工具卡 / 内联审批 / 附件，不借 runtime / cloud / 品牌资产（§18.7 B 类）。
- **T3 路线已推翻**：§10.2 的 6 端点适配前提对 T3 不成立（§18.3），不再作为默认答案。
- **数据时点**：以上排序基于方案 §18 的 2026-11-13 查询基线，本单未重新查询；要重排先回方案 §18 改判据。

### 9.2 开工闸门（判据在方案 §18.5）

选型通过 ≠ 可以 fork。进入 fork 与 P0-0 之前，两道闸门必须都过：

1. **§18.5.1 半天判定**（四步）：跑起来 → 塞假会话 → 流式与审批卡 → 改一个字段看报错扩散面。全过 = 可 fork；②③不过 = 它不是通用壳，转「只借 UI」；④不过 = 止损。
2. **§18.5.2 两条人工项**：V1 审批卡能否映射 memora 的「本次任务都允许 / 中断」与 ask / confirm 分开；V2 客户端重连会不会绕过 memora 的增量水位。这两条 `dart analyze` 与编译通过都替代不了。

**顺序不变**：S0/S1 → LAN 桥 → 外网 Mode T（第 3 节）。§18.5 判定与 V1/V2 可与 S0/S1 并行做，但它们**不能让手机 App 提前开工**——S0/S1 未通时做 App = 造零消费方（第 7 节）。
