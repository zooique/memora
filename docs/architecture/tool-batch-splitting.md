# 方案 · 工具批按 step 断段（toolBatch）

- **日期**：2026-09-26
- **状态**：**已实施**（2026-09-26；用户确认反转 + 澄清「无可见分隔的 step 可合并」）——宿主侧落地，验证全绿（见 §六）。**2026-09-27 扩展**：纳入「外部可见条目（问答卡）断面」（BATCH-SPLIT-1）——判据表见 §4.1 第三行、伪码见 §4.2、实测见 §六。
- **性质**：**纯宿主渲染**（`groupToolBatches` 切段判据扩展）。内核生产代码零改动、落盘结构零变更。
- **输入**：用户真机反馈（本轮：连续思考之间无文字分隔 → 整轮工具被合入第一个折叠块）；09-27 追加输入：重放复现「问答卡被推到批块之后、答后工具跑到卡片之前」（BATCH-SPLIT-1）。关联台账 `TOOL-RUN-1·视觉`（§164）/ `stepIndex 预留消费方`（§62）/ `THOUGHT-STEP-1`（§87）；术语锚点 §1（step = 一次 LLM 调用 + 可选工具执行）。
- **前置文档**：[方案-工具批折叠合并-20260925.md](../方案-工具批折叠合并-20260925.md)

## 一、问题（真机现象）

一轮内模型连做 9 步（「思考 · 第 1 步」…「第 9 步」），每步思考后都调工具；因步骤之间无 `narrate`（也无其它可见分隔物），前后相邻工具之间**无任何打断物** → 被 `groupToolBatches` 判为一大段连续工具 → 合并成**一个「工具×23」大块**，且锚定在第 1 步首个工具处。用户看不到「哪几个工具属于哪一步」。

**根因链**：切段判据的打断物 = `{narrate, text_self_review, plan_item_boundary}`（今唯一声明 = `chatView.ts` `BATCH_SPLITTER_TYPES`），而 `thought` 明确「穿插不断段」。当模型不吐叙述（① 未满足）时，跨 step 的工具之间**没有任何判据可打断** → 糊成一块。

**用户诉求**：恢复「一步 = 思考 → 一句内容 → 该步工具块」的三段式节奏；**每步工具单独成块**。本轮**无任务表**（不产 `plan_item_boundary`），结构全凭 step。

**用户补充裁定（2026-09-26，修正初稿）**：断段应跟随**可见分隔物**——有思考块的步 → 其工具单独成块；**没有可见分隔（模型不产 reasoning）的连续 step 工具 → 允许合并为一块**（无可见断面即不切）。故断段由「**新 step 的思考**」触发（见 §四），而非「`tool_start.stepIndex` 单独变化」。

## 二、与 2026-09-25 决议的冲突（必须显式）

前置方案 §一 曾**明确否决「按 step 分组」**（方案 A），改「按事件相邻性切段」（方案 B），理由原文：

> 🔴 **反直觉点**：「连续 3 次 `read_file`」有两种成因——①一次 LLM 调用并发吐 3 个（同 step）②分 3 次各吐一个（跨 3 个 step；mimo 中转属此类）→ 按 step 合并盖不住 ②。故不采用「按 step 分组」。

**本方案反转该决议。** 反转依据（非「当时的判断错了」，是「前提变了」）：

1. **用户心智变了**：旧决议做出时「一步 = 思考 + 工具」尚未成为真机预期；思考分桶（`THOUGHT-STEP-1`，同日）落地后，**每步一个思考块**已成主结构，工具块不按步对齐即与它错位。
2. **旧决议的目标已由另一手段达成**：旧决议怕「切碎」，手段是「跨 step 合并」。现「思考折叠块」为每次步切换提供结构兜底 → 不再是「满屏无结构小卡」。
3. **信息保真更高**：跨 step 合并把**不同步**的工具糊在一起，丢失「哪几个工具属于哪一步」——新方案消除该损失。

→ 这是一次**判据取舍的反转**，不是 bug 修复。**必须显式记录、必须用户确认**。

## 三、不带伤评估

### 3.1 §7 定性：改判据（高风险动作）→ 须带 ②③

本方案改的是**切段判据**（打断物集合新增「步切换」），属 `legacy-contract-audit-rules.md` §7 的「**改判据**」。故必须满足三条件：

| 条件 | 本方案兑现 |
| --- | --- |
| ① **可追溯** | 对应真机现象（本轮截图）+ 台账 `TOOL-RUN-1·视觉` 触发命中（§164） |
| ② **可观测** | 批结构直接可见 + 新增切段矩阵用例；**顺带解除** §62「stepIndex 预留消费方」僵尸键疑云——`tool_start.stepIndex` 首次获得真实消费方 |
| ③ **可退出** | 改动限于 `groupToolBatches` 单函数（约 3 行）；回退 = 删除步切换判据，无 schema / 协议 / 落盘变更 |

### 3.2 五类带伤预检

| 类 | 判定 | 依据 |
| --- | --- | --- |
| 双轨镜像 | 无 | 判据仍单点（`groupToolBatches`，白名单 `BATCH_SPLITTER_TYPES`）；`stepIndex` 事实单源（内核 loop 打标），思考分桶与工具分块是**同一事实的两个渲染**，非镜像。内核 `stepBoundary.test.ts` 的不变量守卫是按 chunk 层**保守并集**断言的**上位前提守护**，非判据镜像，且与宿主集合**非严格同构**（见该用例注释） |
| 降级兜底残留 | 无死分支 | `stepIndex` 缺省（旧数据）→ 回落纯相邻性（现行为），该回落**真可达**（旧 round） |
| 类型 hack | 无 | 无 `as` |
| 重复实现 | 无 | 三渲染上下文共用 `groupToolBatches`（既有约束） |
| 僵尸声明 | **反向解除** | `tool_start.stepIndex` 由「零消费」转为「有消费」→ 台账 §62 二元判据命中「**保留**」 |

### 3.3 不变量

- 不变量「批 = 相邻工具的**最大连续序列**（中间无打断物）」**保持**；本方案**只扩打断物集合**（新增「步切换」），不重构不变量本身。
- 段 id（= 段内首个 `tool_start` 的 `seq`）契约不变 → 批容器 DOM key（`data-tool-batch`）不变 → 无迁移、无僵尸 key。

## 四、设计

### 4.1 切段判据（在前置方案 §3.1 基础上扩展）

| 条目 | 角色 |
| --- | --- |
| `narrate` / `text_self_review`（自审查输出）/ `plan_item_boundary` | 打断物（**不变**） |
| **`thought` 归属新 step（其 `stepIndex` ≠ 当前批所属 step）** | **新增打断物（可见分隔物）** |
| **外部可见条目（问答卡 `interactiveInputs` 行）落在相邻两工具 ts 之间** | **新增打断物（外部条目断面 · 2026-09-27 扩展）** |
| `thought` 归属**同 step**（`stepIndex` 相同） | **不断段**（step 内伴随物） |
| `tool_start` / `tool_result` | 段内容（按 `toolCallId` 配对，不变） |

**外部条目断面（2026-09-27 扩展 · BATCH-SPLIT-1）**：问答卡（`.round-block__input`）来自 `interactiveInputs` / 运行时缓存——**无 seq、不在 `events` 里** ⇒ 对按 seq 扫描的切段判据天然不可见，会把「工具 → 问答卡 → 工具」并成一批、卡片推到批块之后。故由**渲染层**抽「同容器实际可见的问答卡 ts」（`chatView.ts` `visibleInputTs`：取数处与判据分列，判据不认 DOM）作**虚拟断面**注入；判据 = 「桶号」（小于该工具 ts 的边界数）变化即断段——**与落位（`insertPlanItemInOrder`）同用 ts 键**（呈现在哪、断面就在哪），不引入第三套键；`boundaryTs` 为空即回落旧行为（无外部条目即无断面）。

### 4.2 实现（`groupToolBatches` 单函数，约 5 行）

```text
开批时记 currentStep = 该 tool_start 的 stepIndex
遇 tool_start：桶号 = 小于本工具 ts 的外部条目数（boundaryTs 空 → 恒 0 = 旧行为）；
  无 current 则开新批并记 currentStep/桶号；桶号变化 → 断段（先关批再开新批）；
  否则并入当前批（**不在 tool_start 处断段**）
遇打断物（narrate / text_self_review / plan_item_boundary）：current = null
遇 thought：
  if (current 已开 && currentStep !== undefined && thought.stepIndex !== undefined
      && thought.stepIndex !== currentStep) → 断段（current = null）
```

**判据 = 新 step 的思考**：只有「新 step 的思考」（可见分隔物）出现时断段；同 step 的思考碎片不断段。`currentStep` 取自**开批那条 `tool_start` 的 `stepIndex`**——故 `tool_start.stepIndex` 由「零消费」转为真实消费方（§3.2 僵尸解除）。

**回落**：任一侧 `stepIndex` 为 `undefined`（旧数据）→ 不断段（回落相邻性 = 现行为）。因内核对新 round 全量打标、旧 round 全量无标，回落**按轮整体成立**，不会半新半旧。

### 4.3 边界

- **单工具 step** → 单工具批（行即批，现状形态，零回归）。
- **无任务表**（本轮场景）→ 不产 `plan_item_boundary`，结构全凭 step 判据。
- **有任务表** → `plan_item_boundary` 仍打断（叠加，两者不冲突：任务项 ⊃ 步）。
- **步内多工具并发**（同 stepIndex）→ 仍合一块（守住旧决议「同 step 并发工具合并」的收益）。
- **无思考分隔的跨 step 工具**（模型不产 reasoning）→ 不切段、维持相邻合并（用户裁定：无可见分隔即可合并）。

## 五、取舍（诚实记）

1. **有思考分隔的跨 step 工具序列不再合并**：每一步有思考块时，工具按步分块（每步一块）。**用户已确认接受**。**无思考分隔**的连续 step 工具仍合并（§4.3）——此边界由「可见分隔物」统一，不依赖 `tool_start.stepIndex` 单独变化。
2. **长循环块数上升**：20–30 step → 最多 N 个工具块 + N 个思考块。与 `THOUGHT-STEP-1`（§87）已登记的「步级形态回归风险」**同源**，属用户已知接受项。
3. **收益**：消除「不同步工具糊成一块」的信息损失；工具块与思考块同号对齐（可读性 + 可定位）。
4. **不加中间态**：不做「跨 step 有条件合并」（避免猜测性复杂度，D6）。真机若再现「块太多」，按 `THOUGHT-STEP-1` 的既定路径（收起态合并摘要）评估，**不在本方案预支**。

## 七、明确不做（边界）

- **不加「第 N 批」编号**（前置方案 §3.4 纪律：批号与「思考 · 第 N 步」互不对齐）。
- **不改内核**（判据只读宿主已可见的数据：`ProcessEvent` 的 `stepIndex` + 渲染层可见的问答卡 `ts`；不新增内核产出、不改落盘）。
- **不做「跨 step 有条件合并」的中间态**（D6 防预支）。
- **诉求 ①（模型每步吐一句叙述）不在本方案**：① 是**交互体验增强**（内核提示词层，鼓励模型吐 `narrate`），非分组判据；① 不入 `narrate` 也不影响本方案的确定性断段（本方案正是为「① 不保证」而设计的确定性兜底）。
