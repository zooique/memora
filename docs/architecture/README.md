# Memora 系统架构说明书

> **基于单一真理源思维模型构建的 Agent 内核架构**
>
> 核心公理：**单轮问答闭环是 Agent 的最小完整单元。一切复杂行为（Loop、记忆、召回、摘要）都是这个单元的自然生长，而非独立的新系统。**
>
> 本文档是架构参考手册，不是设计推导。完整的推导过程见 [docs/agent-design/README.md](../agent-design/README.md)，思维模型见 [.trae/rules/single-truth-source-mindset.md](../../.trae/rules/single-truth-source-mindset.md)，运行时架构见 [docs/architecture/runtime-architecture.md](runtime-architecture.md)。

## 一、设计哲学

### 1.1 单一真理源（SSOT）

**单一真理源不是"只有一个文件/一个模块"，而是"只有一个设计原点"**：

- 一套最小单元，承载所有复杂行为。
- 同一套逻辑，在多种场景下复用，不做场景特化。
- 复杂度向外生长，核心保持简单。

| 错误做法 | 正确做法 |
|---------|---------|
| Loop 需要独立引擎 | Loop 是最小单元的重复，用 Handoff 策略区分 |
| 新场景需要新机制 | 新场景是已有机制的参数化配置 |
| 在复杂场景上叠加补丁 | 回到最小单元，看能否在单元层面解决 |

### 1.2 最小单元的定义

一个系统无论多复杂，最终都以"**一次触发，一次回答**"为基本单元。这个单元必须满足三个条件：

- **自足**：一次触发，一次回答，内部完整。
- **可重复**：同一单元可被反复调用，且每次独立。
- **可观察**：单元的执行过程对外可见，可被记录、可被测试。

### 1.3 复杂度生长法则

所有复杂行为都是最小单元的组合与重复，而非另起炉灶：

| 复杂行为 | 在最小单元中的位置 |
|---------|----------------|
| 多轮对话 | 闭环的序列（Handoff 选 wait） |
| 自动执行 | 闭环的自主衔接（Handoff 选 loop） |
| 长期记忆 | 闭环的后处理（Reflect 阶段） |
| 上下文压缩 | 闭环的截断策略（迭代边界触发） |
| 可插拔角色 | 闭环的换装（角色包匹配） |
| 行为策略 | 闭环的调校（L2 枚举） |

## 二、系统总览

### 2.1 架构分层

```
宿主层（Host）
  ├── memora-sprite（Electron 桌面应用）
  ├── CLI 工具
  └── 自定义宿主
        │
        ▼ 通过 Agent 门面类接入
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
内核层（memora 核心库）
  ├── Agent 门面（组装编排）
  │   ├── AgentLoop（执行引擎）
  │   ├── ContextManager（上下文窗口）
  │   ├── Composer（不中断工作模型）
  │   └── SessionManager（会话管理）
  │
  ├── 记忆系统
  │   ├── recall（双通道召回）
  │   ├── InsightExtractor（洞察提炼）
  │   └── IMemoryStorage（存储接口）
  │
  ├── 角色系统
  │   ├── RolePackManager（角色包管理）
  │   ├── PersonaManager（单角色管理）
  │   └── SkillManager（技能管理）
  │
  ├── LLM 适配层
  │   ├── LlmProvider（模型调用）
  │   └── ProviderRouter（模型路由）
  │
  └── 安全与工具
      ├── SecurityGuard（安全护栏，整合 rule 段规则）
      └── ToolExecutor（工具执行）
```

### 2.2 核心概念

| 概念 | 定义 |
|------|------|
| **闭环（Round）** | Agent 的最小完整单元：一次触发，一次回答，三阶段闭环 |
| **Trigger（触发）** | 外部驱动，拉起一轮闭环的入口。来源：用户、系统、其他 Agent |
| **Handoff（衔接决策）** | 回答后决定下一轮由谁触发的出口。三选一：wait / loop / end |
| **回答前（Prepare）** | 理解触发、匹配角色包、召回知识、装配上下文 |
| **回答中（Act）** | 生成回答、执行工具、多步行动的内循环 |
| **回答后（Reflect）** | 生成摘要、提炼记忆、衔接决策 |
| **角色包（Role Pack）** | 以角色为单位的固定范式：L1 内容 + L2 策略 + 远期 L3 代码 |
| **行为策略（Behavior Strategy）** | L2 策略层的枚举项：角色的行为开关 |
| **内循环** | 回答中阶段工具调用的循环（决定"一轮有多深"） |
| **外循环** | 回答间阶段多轮闭环的串联（决定"一次任务有多长"） |

### 2.3 数据流总图

```
                      ┌──────────┐
                      │ 外部输入  │  ← 用户/系统/其他 Agent
                      └────┬─────┘
                           │
                           ▼
                  ┌──────────────────┐
                  │  ① 角色包匹配     │  ← 只在外部输入时触发

                  │  prompt          │     再检索知识
                  └──────┬───────────┘
                         │
                         ▼
                  ┌──────────────┐
                  │  ② recall()  │  ← 只在外部输入时触发

                 ┌───────────────┐
                 │  ③ 执行循环   │  ← Loop 自循环不触发 ①②
```

## 三、核心闭环：单轮问答

### 3.1 闭环的三阶段结构

```
     ┌──────────────────────────────────────────┐
     │            单轮问答闭环                     │
     │                                          │
     │  回答前 → 回答中 → 回答后                  │
     │     │                    │               │
     │     └──── 气口（衔接）───┘               │
     └──────────────────────────────────────────┘
```

- **回答前（Prepare）**：认知阶段——先想清楚自己拥有什么、需要什么。
- **回答中（Act）**：行动阶段——输出回答，并在需要时调用工具。
- **回答后（Reflect）**：沉淀阶段——把本轮变成记忆，并决定下一轮由谁触发。

### 3.2 两个开口

| 开口 | 职责 | 变化 |
|------|------|------|
| **Trigger（入口）** | 拉起一轮闭环的外部驱动 | 来源可变（用户/系统/Agent），闭环本身不变 |
| **Handoff（出口）** | 回答后衔接决策 | 三选一：wait / loop / end，策略可变，引擎不变 |

### 3.3 触发源决定召回行为（核心设计）

这是单一真理源的核心证明——闭环的召回行为由"触发源"决定，而非"是否在 Loop 中"：

| 触发源 | 角色包匹配 | recall() | 上下文组装 |
|--------|-----------|----------|-----------|
| **外部输入**（用户/系统/其他 Agent） | 触发 | 触发 | system prompt + 召回结果 + 全量消息 + 截断摘要 |
| **Loop 自循环**（工具调用/自动续跑） | 不触发（角色包已固定） | 不触发 | 已有上下文 + 追加本轮结果 |

## 四、回答前（Prepare）

### 4.1 理解输入（两阶段设计）

理解输入与角色包匹配存在循环依赖：理解输入需要角色包，角色包匹配需要输入。**解决方式：拆为两个阶段，中间插入确定性匹配。**

```
第一阶段：原始理解（不依赖角色包）
  - 输入预处理：分词、去噪、提取触发词
  └→ 角色包匹配（基于触发词确定性匹配，见 4.2）
      ↓
第二阶段：深度理解（在角色包视角下）
  - 意图识别、任务分类、资源预估
```

第一阶段使用**确定性匹配**（触发词精确匹配或正则匹配），不依赖语义理解。第二阶段在角色包固定后，用角色包的视角做深度理解。

### 4.2 角色包匹配（含粘性机制）

角色包匹配是**前置筛**——它不参与后续的 token 配额竞争，而是直接修改 system prompt 的结构。

**匹配规则**：基于输入触发词（确定性匹配），从角色池中匹配最合适的角色包。匹配成功后，角色包的 persona（身份设定）、rule（安全契约）、skill（技能清单）被装载进 system prompt。

**粘性机制**：同一会话中，角色包匹配有粘性——首次匹配成功后，角色包在当前会话中保持固定，不会因后续输入而频繁切换。

| 触发场景 | 匹配行为 | 说明 |
|---------|---------|------|
| 首次外部输入 | 全量匹配：从角色池中匹配最合适的角色包 | 匹配成功后，角色包在当前会话中"锁定" |
| 后续外部输入 | 不重新匹配，沿用已锁定的角色包 | 除非输入显式命中触发词，触发切换 |
| 显式切换角色包 | 用户主动请求切换，替换当前角色包 | 替换后新角色包锁定 |
| 触发词命中切换 | 输入命中其他角色包的触发词，且互斥 | 新旧角色包互斥时自动切换，非互斥时合并 |

**粘性纪律**：
- 切换的触发条件：输入显式命中其他角色包的触发词，且新旧角色包的触发词被声明为互斥（在 frontmatter 中声明 `exclusiveWith` 字段）。
- 触发词互斥时自动切换，非互斥时合并（多角色包共存，冲突裁决机制见 §9.4）。
- 角色包切换后，当前会话中已装载的 L1 内容被替换，但已生成的对话记录和摘要保持不变。

**粘性漂移处理**：在长会话中，用户意图可能逐渐偏离最初锁定的角色包，而因未命中触发词，角色包一直锁定在原位。系统通过以下机制应对：
  - 连续 N 轮未命中当前角色包触发词时（N 默认 5，可通过 L2 策略 `driftThreshold` 配置），在 system prompt 中注入"当前角色包可能已不适用，如需要可建议切换角色"的提示，允许 LLM 主动建议切换
  - 用户接受建议后，触发重新匹配（走首次匹配流程）
  - 用户拒绝建议，则保持当前角色包锁定，N 轮计数重置

### 4.3 召回相关（三个通道）

知识来自三个通道，按顺序执行：

| 通道 | 匹配方式 | 职责 | 先于 |
|------|---------|------|------|
| 角色包匹配 | 触发词确定性匹配 | 确定视角框架 | 所有召回 |
| 记忆召回 | 语义+关键词双通道 | 检索长期记忆 | 摘要召回（并行） |
| 摘要召回 | 语义+关键词双通道 | 检索历史摘要 | 记忆召回（并行） |

角色包匹配**先于**记忆/摘要召回执行——先确定"用什么角色"，再做"用什么知识"。记忆与摘要两个通道并行触发，互不阻塞。

### 4.4 装配上下文

装配分两步：先装载角色包（确定视角框架），再装配知识与历史（填充内容）。

```
第一步：装载角色包 → 生成 system prompt
  system prompt = persona（身份设定）
                + rule（安全契约，全量注入，不可丢失）
                + skill（技能清单，运行时激活匹配）

第二步：装配上下文
  上下文 = system prompt（角色包提供的视角框架）
         + 最近 N 轮完整对话（固定加载，保证连续性）
         + 记忆召回结果（事实知识）
         + 摘要召回结果（历史对话片段）
```

## 五、回答中（Act）

### 5.1 生成

Agent 基于装配好的上下文，调用 LLM 生成回答。生成过程的纪律：

- **流式输出**：回答逐字产出，用户可以实时看到思考过程。
- **路由选择**：根据任务分类（简单/推理/代码/摘要），路由到最合适的模型。
- **可中断**：任何时刻可被软暂停（挂起）或硬中止（放弃）。

### 5.2 工具调用

Agent 通过工具调用扩展行动能力：

- **工具声明**：Agent 感知可用的工具清单及其能力。
- **决策与调用**：在生成过程中，Agent 判断"是否需要工具"并调用。
- **结果回填**：工具执行结果回到上下文，供后续生成使用。

### 5.3 内循环与外循环的配比

| 循环类型 | 位置 | 决定 | 示例 |
|---------|------|------|------|
| **内循环** | 回答中内部 | 一轮有多深 | 多次工具调用 |
| **外循环** | 回答间串联 | 一次任务有多长 | 多轮闭环串联 |

两者是**可配比的资源**，而非固定结构。角色通过 L2 策略选择深与长的配比（工具步数上限、Loop 续跑开关）。

## 六、回答后（Reflect）

### 6.1 摘要生成

每轮闭环完成后，**后台异步**生成本轮摘要（1-2 句话，50-100 token），存储在对话记录中。

**设计目标**：摘要从"运行时补救"变成"结构化数据"——截断时直接取用已存在的摘要，无需等 LLM 即时生成。

#### 6.1.1 摘要生成失败降级

摘要生成是后台异步的，不阻塞主流程，但可能失败（LLM 超时、返回空、异常等）。需定义失败时的降级行为：

| 失败场景 | 降级策略 | 说明 |
|---------|---------|------|
| 异步生成超时/失败 | 跳过本轮摘要，标记为"未生成" | 截断时直接丢弃被裁轮次，不注入摘要 |
| 摘要内容为空 | 标记为"空摘要"，不创建占位符 | 与"未生成"同等处理 |
| 连续多轮失败 | 累计失败计数，触发会话级摘要抑制 | 超过阈值时自动关闭当前会话的摘要生成，改为仅持久化原始对话 |

**核心原则：摘要对截断是"锦上添花"，而非"雪中送炭"。**

- **fail-open**：摘要不存在时，截断依然工作——只是被裁轮次没有摘要替补，内容直接丢失。
- **异步重试**：失败的摘要生成在下一轮闭环的 Reflect 阶段重试，不独占资源。
- **同步回退（仅限关键场景）**：如果宿主强制要求摘要完整性（如归档场景），可在 Handoff 前调用同步摘要生成，但延迟由宿主承担。
- **阈值保护**：连续 N 轮失败后，**会话级运行时标志**抑制摘要生成（非修改 L2 策略），避免资源浪费。新会话重置该标志。

### 6.2 记忆提炼

从摘要中提炼长期记忆，而非原始对话。提炼路径：

```
原始对话（完整，但每轮可能很长）
        │
        ▼ 异步提炼
    轮次摘要（精简，1-2 句话）
        │
        ▼ 价值判断
    长期记忆（洞察、用户画像）
```

**收益**：去噪（摘要已过滤冗余）、高效（摘要比原始对话短得多）、一致（同一份摘要，结果可复现）。

### 6.3 衔接决策（Handoff）

提炼完成后，闭环来到出口——Handoff 决定三件事：

1. **是否有下一轮**（继续 or 结束）。
2. **下一轮由谁触发**（用户 or 系统）。
3. **以什么姿态触发**（等待输入 or 自动续跑）。

| 模式 | Trigger 来源 | Handoff 策略 | 终止 |
|------|-------------|--------------|------|
| 对话 | 用户 | 等待用户 | 用户结束 |
| Loop | 系统自动 | 自动续跑 | 目标/上限/中断 |
| 目标（远期） | 对齐差距分析 | 自动续跑直至对齐 | 验收清单完成 |

## 七、数据模型

### 7.1 三元数据：对话记录·摘要·记忆

| 类型 | 载体 | 生成时机 | 用途 | 生命周期 |
|------|------|---------|------|---------|
| 对话记录 | `AgentLoop.messages[]` | 运行时实时累积 | 当前上下文全量拼接 | 单次会话，截断时部分丢弃 |
| 轮次摘要 | 对话记录元数据 | 每轮闭环完成后异步生成 | 截断替补 + 历史检索 | 随对话记录持久化 |
| 长期记忆 | 记忆系统（`source: insight/profile`） | 从摘要中异步提炼 | 跨会话召回 | 长期保留，权重衰减 |

### 7.2 数据流转路径

```
对话记录 ──异步提炼──▶ 轮次摘要 ──价值判断──▶ 长期记忆
                               │
                               └── 被截断时注入上下文
```

### 7.3 上下文装配策略

装配上下文的策略，取决于**本轮由谁触发**，而非是否在同一会话：

```
外部输入触发（角色包匹配 + recall）：
  1. 角色包匹配 → 装载 persona/rule/skill 到 system prompt
  2. recall() → 记忆 + 摘要召回（在角色包视角下检索）
  3. 注入召回结果
  4. 进入执行循环

执行循环（不触发角色包匹配，不触发 recall）：
  1. 拼接已有上下文（system prompt + 召回结果 + 历史消息 + 当前输入）
  2. 调 LLM
  3. 如果 LLM 返回 tool_calls → 执行工具 → 回到步骤 1
  4. 如果 LLM 返回文本 → done

截断（任一迭代边界触发）：
  1. 检查 token 是否超阈值
  2. 超了 → 执行截断选择算法（见下文）
  3. 不超 → 继续

截断选择算法：
  1. 保留最近 N 轮（L1 固定轮次），不受截断影响（第一优先级保护）
  2. 从最旧轮次开始，按时间顺序尽量保留（第二优先级保护，保证对话有起始上下文）
  3. 中间剩余轮次被裁掉，注入其已存在的摘要
  4. 如果预算仍然超限，从最旧轮次开始降级保护（即裁减最早的非 L1 轮次），直到预算满足
  5. 极端情况（预算极低）：仅保留会话起始轮次（第一轮对话） + L1 最近轮次 + 当前输入

后处理（响应流结束后触发）：
  1. 持久化对话记录
  2. 异步生成摘要
  3. 异步从摘要提炼记忆
```

### 7.4 设计纪律

1. **摘要先行，记忆后生**：记忆从摘要中提炼，而非原始对话。
2. **摘要保真**：摘要是对该轮对话的忠实记录，不预判记忆价值。
3. **截断时摘要注入**：被裁轮次的摘要按时间顺序注入，不合并、不压缩。
4. **召回不分源**：`recall()` 对记忆和摘要一视同仁，都按语义相关度排序返回。
5. **摘要与洞察共存**：摘要（对话级，保真）和洞察（事实级，去噪）是两条独立的数据流。
6. **角色包匹配先于召回**：角色包匹配（视角框架确定）先于记忆/摘要召回执行。

## 八、上下文预算模型

### 8.1 设计理念

**资源有限，必须取舍。** 在无限对话场景中，若没有硬性预算约束，摘要和记忆可能填满整个上下文窗口，导致系统不可用。

**核心原则**：
- **内核提供机制，角色包提供策略**——预算计算逻辑归内核，数值由角色包 L2 策略层配置
- **百分比是界面，token 是执行单位**——用户在角色包中配置百分比，内核按总预算换算为 token 硬上限
- **按优先级填充，超出即淘汰**——每个类型有硬性上限，超过时按规则丢弃

### 8.2 接口定义

```typescript
/**
 * 上下文预算配置
 * 属于角色包 L2 策略层的一部分
 * 内核提供机制，角色包提供数值
 */
interface ContextBudgetConfig {
  /** 可用输入上下文总 token 数（模型窗口 - 系统提示 - 输出预留之后） */
  totalBudget: number;

  /** 各类型配额 */
  allocations: {
    /** 最近完整轮次（按轮数固定，不参与 token 配额竞争） */
    recentRounds: number;      // 默认 10

    /** 历史摘要占剩余预算的百分比（0-100） */
    summariesPercent: number;  // 默认 25

    /** 跨会话记忆占剩余预算的百分比（0-100） */
    memoriesPercent: number;   // 默认 16
  };
}
```

### 8.3 预算执行流程

装配上下文的优先级分层：

| 层级 | 内容 | 预算 | 淘汰规则 |
|------|------|------|---------|
| **L1 最近轮次** | 最近 recentRounds 轮完整对话 | 硬性固定，不参与配额竞争 | 超过 N 轮时，最旧被裁（进入 L2 摘要系统） |
| **L2 摘要召回** | 历史轮次摘要，按语义相关度排序 | 剩余预算 × summariesPercent ÷ 100 | 超过上限时，丢弃最旧摘要（LRU） |
| **L3 记忆召回** | 跨会话记忆，按置信度排序 | 剩余预算 × memoriesPercent ÷ 100 | 超过上限时，丢弃最低置信度记忆 |
| **L4 当前轮输入** | 本轮用户输入 + 工具结果 | 剩余全部 | 超预算时截断输入末尾，system prompt 标注"上下文紧张" |

执行步骤：

```
装配流程：
  1. 装载 L1：最近 recentRounds 轮完整对话
     → 消耗 token_recent
     → 剩余 = totalBudget - token_recent

  2. 计算 L2/L3 配额
     → 摘要预算 = 剩余 × summariesPercent ÷ 100
     → 记忆预算 = 剩余 × memoriesPercent ÷ 100
     → 当前轮预算 = 剩余 - 摘要预算 - 记忆预算

  3. 装载 L3：召回记忆，按置信度从高到低填充
     → 超过记忆预算时，丢弃最低置信度的

  4. 装载 L2：召回摘要，按时间从新到旧填充
     → 超过摘要预算时，丢弃最旧的

  5. 剩余给当前轮输入 + 工具结果
     → 如果当前轮输入超预算，从输入末尾截断，并在 system prompt 中标注"上下文紧张，优先处理最新信息"
```

### 8.4 与角色包的集成

在 L2 行为策略表中新增一组策略维度：

| 策略维度 | 类型 | 默认值 | 说明 |
|---------|------|--------|------|
| `contextBudget.totalBudget` | token 数 | 122K (128K 模型) | 可用输入预算 |
| `contextBudget.recentRounds` | 轮数 | 10 | 最近完整轮次 |
| `contextBudget.summariesPercent` | 百分比 | 25 | 摘要占剩余预算 |
| `contextBudget.memoriesPercent` | 百分比 | 16 | 记忆占剩余预算 |

角色包只声明它想改变的部分——未声明则使用全局默认值。未声明时，从宿主配置中读取全局默认值。

### 8.5 典型配置场景

| 场景 | recentRounds | summariesPercent | memoriesPercent | 效果 |
|------|-------------|-----------------|----------------|------|
| 默认通用 | 10 | 25% | 16% | 历史 vs 当前 ≈ 40:60 |
| 长对话助手 | 5 | 30% | 20% | 减少完整轮次，给历史信息更多空间 |
| 简短问答 | 20 | 10% | 5% | 保留更多完整对话，少做摘要 |
| 隐私敏感 | 0 | 0% | 0% | 无状态，不保留任何历史 |
| 翻译角色 | 1 | 0% | 0% | 每轮独立，翻译不依赖上下文 |

### 8.6 设计纪律

1. **百分比之和不超过 100%**：超过时显式报错，避免静默归一化导致意外行为
2. **L1 最近轮次不参与配额竞争**：它是连续性保证，优先级高于所有召回内容
3. **淘汰窗口的摘要不丢失**：摘要仅在上下文窗口中淘汰，持久化存储不受影响
4. **totalBudget 由宿主传入**：内核只负责"按预算执行"，不负责"预算从哪里来"
5. **百分比是配置界面，token 是执行单位**：避免在多模型场景下行为不一致

### 8.7 成本追踪与预算执行

#### 8.7.1 设计理念

成本预算与 Token 预算（§8）是不同维度的资源约束：

| 维度 | 约束对象 | 单位 | 用途 |
|------|---------|------|------|
| Token 预算 | 单轮上下文窗口 | token | 控制内容装配范围 |
| 成本预算 | 跨轮次累计 | 货币（元/美元） | 控制单任务总花费 |

**两者独立但正交**：Token 预算保证内容可装配，成本预算保证花费可控。一个任务可能 Token 预算充裕但成本预算吃紧。

#### 8.7.2 成本模型

成本追踪依赖宿主提供的计价模型：

```typescript
/**
 * LLM 调用计价模型
 * 由宿主注入，内核只读使用
 */
interface CostModel {
  /** 模型名称 → 计价规则 */
  [modelName: string]: {
    /** 输入 token 单价（每千 token） */
    inputPricePer1K: number;
    /** 输出 token 单价（每千 token） */
    outputPricePer1K: number;
    /** 计价货币单位（如 "CNY"、"USD"） */
    currency: string;
  };
}
```

#### 8.7.3 跨轮次累计

成本在 Reflect 阶段累计，作为会话级元数据：

```
每轮闭环完成后（Reflect 阶段）：
  1. 统计本轮所有 LLM 调用的 token 消耗（输入 + 输出）
  2. 按 CostModel 计算本轮成本 = ∑(inputTokens × inputPrice + outputTokens × outputPrice)
  3. 将本轮成本累加到会话级累计成本
  4. 检查累计成本是否超过成本预算
```

**累计成本**与会话绑定，在会话元数据中持久化：

| 字段 | 类型 | 说明 |
|------|------|------|
| `totalCost` | number | 当前会话累计成本 |
| `costBreakdown` | Record<string, number> | 按模型维度的成本明细 |
| `costBudget` | number | 成本预算上限（来自 L2 策略） |
| `costCurrency` | string | 货币单位 |

#### 8.7.4 预算执行

成本预算在 **Handoff 前** 检查，而非回答中执行时：

```
Handoff 前检查：
  0. 成本预算未设置（undefined）→ 跳过检查，正常继续
  1. 累计成本 ≥ 成本预算 → 强制 Handoff 选 end（终止任务）
  2. 累计成本 ≥ 成本预算 × 80% → 切换回 cheapest 模型（预警降级）
  3. 累计成本 < 成本预算 × 80% → 正常继续
```

**cheapest 模型定义**：从 CostModel 中按 `inputPricePer1K + outputPricePer1K` 总价最低选出的模型。若 CostModel 中无可用模型，则跳过降级步骤，保持当前模型。

**不中断当前轮**：成本检查只在轮次边界触发，不中断正在执行的回答。模型切换也发生在下一轮边界，不影响当前轮的执行。这与 Token 预算的执行时机对齐——都是"阶段边界检查，非运行时中断"。

#### 8.7.5 与角色包的集成

在 L2 全局策略中完善成本相关维度（参见 §9.2 跨阶段策略表）：

| 策略维度 | 类型 | 默认值 | 说明 |
|---------|------|--------|------|
| `costBudget` | 金额 | 无（不限） | 单任务总成本上限 |
| `costCurrency` | 枚举 | "CNY" | 计价货币 |
| `costAlarmPercent` | 百分比 | 80 | 预警阈值，超过时降级模型 |
| `costOnExceeded` | 枚举 | stop / degrade | 超预算时的行为 |

#### 8.7.6 设计纪律

1. **成本是估算，不是精确计费**：token 计价是预估值，实际计费可能因缓存、折扣等不同。内核不承诺精确计费。
2. **成本检查不中断当前轮**：只在轮次边界检查，避免在回答中阶段突然打断 LLM 调用。
3. **成本模型由宿主提供**：内核只负责按公式计算，不负责计价规则的来源。
4. **成本明细可追踪**：每轮成本明细记录在会话元数据中，供宿主审计和展示。
5. **成本预算与 Token 预算不互相推导**：不能从 Token 预算推导出成本预算，反之亦然。

## 九、角色包体系

### 9.1 三层结构

```
角色包三层结构
├── L1 内容层（文本）：persona / rule / skill / 知识引用
├── L2 策略层（枚举）：行为开关，角色只"选择"不"定义"
└── L3 代码层（扩展）：自定义钩子（远期，沙箱隔离）
```

**L1 内容层**：角色的知识资产。人设、规则、技能、知识引用。

**L2 策略层**：角色的行为偏好——枚举全部候选维度，角色只做"选择"，不做"定义"。这是"触及程序运行而不触及代码"的边界。

**L3 代码层**：远期设想，需沙箱隔离防恶意代码，当前不设计。

### 9.2 L2 行为策略全景

#### 回答前（Prepare）：认知策略

| 策略维度 | 可选值 | 含义 |
|---------|--------|------|

| 最近轮次数 | 1 / 2 / 3 / N | 固定加载的轮数（参见 §8.4 `contextBudget.recentRounds`） |
| 记忆召回 | full / limited / none | 是否召回长期记忆 |
| 记忆召回配额 | token 数 | 记忆占用上限（参见 §8.4 `contextBudget.memoriesPercent`） |
| 摘要召回 | on / off | 是否召回历史轮次摘要 |
| 召回置信度 | 0.0~1.0 | 召回结果的相似度阈值 |
| 任务分类 | keyword / semantic / llm | 判断任务复杂度的方式 |

### 9.3 粘性匹配机制（参见 §4.2）

参见 4.2 节"角色包匹配（含粘性机制）"。角色包粘性是基于会话的——首次匹配成功后锁定，保留显式切换通道。

### 9.4 多角色包冲突裁决

#### 9.4.1 问题定义

当用户同时装载多个角色包（非互斥合并，参见 §4.2），每个角色包携带自己的 L1 内容（persona/rule/skill）和 L2 策略，可能产生冲突：

| 冲突类型 | 示例 | 冲突对象 |
|---------|------|---------|
| 规则冲突 | 工程师 say "仅允许只读工具" / 项目总监 say "允许全部工具" | `rule` 段 |
| 人设冲突 | 两个角色包对同一问题给出不同风格的 persona | `persona` 段 |
| 策略冲突 | 两个角色包设置不同的 `toolApproval` 策略 | L2 策略维度 |

#### 9.4.2 裁决原则

**单一真理源思维**：冲突裁决不是引入新系统，而是让规则自身携带优先级属性。

**优先级金字塔**（从高到低）：

| 层级 | 来源 | 说明 |
|------|------|------|
| P0 全局安全规则 | 宿主全局配置 | 不可被任何角色包覆盖（如"禁止删除文件"） |
| P1 角色包显式优先级 | 角色包声明的 `priority` 字段 | 加载时显式声明，优先级高的角色包胜出 |
| P2 加载顺序 | 角色包被装载的先后顺序 | 后加载的优先级高于先加载的 |
| P3 冲突解决策略 | 规则自身的 `conflictStrategy` 属性 | 见 §9.4.3 |

#### 9.4.3 冲突解决策略

每条规则（或 L2 策略条目）可携带 `conflictStrategy` 属性，定义与同级规则冲突时的合并方式：

| 策略 | 含义 | 适用场景 |
|------|------|---------|
| **strictest** | 取最严格的版本 | 安全规则、权限规则 —— 默认策略 |
| **specific** | 取最具体的版本（规则范围更窄的胜出） | skill 清单、工具白名单 |
| **latest** | 后加载的覆盖先加载的 | 非关键性偏好（如生成温度、流式开关） |
| **merge** | 合并（取并集） | 工具白名单、技能清单——双方能力合并 |
| **reject** | 冲突时报错，阻止装载 | 互斥配置（如两个角色包都声明了 `exclusiveWith` 同组） |

**默认策略**：安全相关规则（rule 段）默认 `strictest`，非安全规则默认 `latest`。

**覆盖链**：规则自身显式声明的 `conflictStrategy` > 角色包 frontmatter 中声明的默认 `conflictStrategy` > 段级别默认值（见 §9.4.4 表格）。角色包级默认值只对该角色包内部未显式声明 `conflictStrategy` 的规则生效。

#### 9.4.4 合并规则

| 角色包段 | 合并方式 | 冲突策略默认值 |
|---------|---------|--------------|
| `persona` | 串联拼接，用分隔线区分 | latest（后加载的 persona 追加在后） |
| `rule` | 优先级金字塔裁决 | strictest |
| `skill` | 合并（取并集） | merge |
| L2 策略 | 按策略维度逐项裁决 | 见 §9.4.3 表格 |

**示例**：角色包 A（工程师）和角色包 B（项目总监）同时装载：

```
persona -> 串联拼接："你是一名工程师。\n---\n你是一名项目总监。"
rule    -> strictest：A 说"只读工具"，B 说"全部工具" → 取"只读工具"
skill   -> merge：A 的 {代码审查, 文件编辑} + B 的 {项目计划, 报告生成} → 全部可用
L2 策略 -> 逐项裁决：
  - toolReadonly: A=readonly, B=full → strictest → readonly
  - temperature: A=0.2, B=0.7 → latest → 0.7（后加载的生效）
```

#### 9.4.5 角色包优先级声明

角色包在 frontmatter 中声明以下字段：

```yaml
---
name: 工程师
priority: 10          # 数值越大优先级越高（默认 0）
conflictStrategy: strictest  # 该角色包内所有规则的默认冲突策略
exclusiveWith:         # 互斥角色包列表
  - 翻译
  - 设计师
---
```

**优先级规则**：
- 未声明 `priority` 的角色包默认优先级为 0
- 优先级仅在角色包显式设置时参与裁决，不参与粘性匹配的首次选择
- 同一优先级时，按加载顺序裁决（后加载的优先）

**exclusiveWith 验证规则**：
- 互斥是双向的：角色包 A 声明 `exclusiveWith: [B]` 意味着 A 和 B 互斥，不要求 B 也声明
- 多级互斥不传递：A 互斥 B，B 互斥 C，A 和 C 不自动互斥——互斥关系是二元关系，非传递闭包
- 互斥角色包同时装载时：后装载的替换先装载的（自动卸载先装载的，装载新角色包），并通知用户角色包已切换。这与 §9.4.2 P2"后加载的优先"以及 §4.2"触发词互斥时自动切换"的行为一致
- 格式要求：`exclusiveWith` 值为角色包名称数组，每个名称匹配 frontmatter 中的 `name` 字段

#### 9.4.6 设计纪律

1. **全局安全规则不可被覆盖**：P0 优先级高于所有角色包，角色包不能通过 `priority` 覆盖全局安全规则。
2. **冲突显式化**：合并后的冲突裁决结果应在会话初始化时记录，供宿主审计。
3. **默认安全优先**：`strictest` 是 rule 段的默认策略，确保安全规则不因合并而松动。
4. **多角色包不是"同时说话"**：多角色包合并后，persona 是串联拼接的，Agent 在同一轮中只有一个 persona 视角——拼接的 persona 可能出现矛盾，由 LLM 自行调和。

## 十、常见设计陷阱

### 10.1 循环依赖陷阱

**场景**：A 依赖 B，B 依赖 A——理解输入需要角色包，角色包匹配需要输入。

**解**：拆为两个阶段，中间插入确定性匹配。第一阶段只做原始理解（提取触发词），第二阶段在角色包固定后做深度理解。**确定性匹配打破循环依赖**。

### 10.2 粘性缺失陷阱

**场景**：每次触发都重新匹配，导致角色频繁切换，体验不稳定。

**解**：粘性匹配——首次匹配成功后锁定，但保留切换通道。**粘性不是"永不切换"，而是"不因无关输入而切换"**。

### 10.3 补丁思维陷阱

**场景**：为 Loop 设计独立的"跳过召回"逻辑，或为多模式设计多套上下文组装逻辑。

**解**：回到最小单元。在闭环内部用参数化解决（如触发源参数），不在闭环外部加分支。

### 10.4 粘性漂移陷阱

**场景**：长会话中，用户意图逐渐偏离最初锁定的角色包，但角色包一直锁定在原位，导致视角始终不匹配。

**解**：粘性不是永久的。连续 N 轮未命中触发词时，通过 system prompt 允许 LLM 主动建议切换角色。**粘性漂移的应对不是"定期重新匹配"，而是"让 LLM 自己知道它可能不合适"**。

### 10.5 截断模糊陷阱

**场景**：上下文超预算时，只说"裁掉中间段"但不定义选择标准，导致不同实现产生不同截断行为。

**解**：截断选择算法必须确定——保留两端（第一轮 + 最近 N 轮），裁掉中间，若仍超限则从最旧开始裁减。**截断是确定性操作，不依赖语义判断**。

## 十二、远期锚点与已知缺口

> 本节收集已确认但**不执行**的架构缺口。它们被记录在此，以约束接口形状、防止设计遗憾，并明确当前架构的边界。标记为"不执行（长期目标）"的条目，在架构稳定前不会进入实现。

### 12.1 状态机：IDLE 与 INITIALIZING 状态（不执行，长期目标）

**缺口**：当前状态机（参见 [agent-design §9](../agent-design/README.md#第九章-状态闭环运行的骨架)）定义为 `RUNNING → PAUSED → ERROR → RUNNING`，缺少 IDLE 和 INITIALIZING 状态。

**设计方向**：

```
IDLE ──trigger──▶ RUNNING ──pause──▶ PAUSED ──resume──▶ RUNNING
  ▲                  │                                      │
  └── end ───────────┘               └──error──▶ ERROR ──recover──▶ RUNNING
                                                                    │
                                                                    └── fail──▶ IDLE
```

- **IDLE**：无闭环运行时的基线状态。系统就绪但空闲，等待 Trigger。
- **INITIALIZING**：系统启动阶段，在首次 Trigger 前自动转换到 RUNNING。

**不执行的原因**：内核的会话生命周期由宿主管理——IDLE 的职责（等待输入、展示状态）在宿主层，INITIALIZING 的职责（配置加载、资源初始化）也在宿主层。内核只管理闭环运行中的状态（RUNNING/PAUSED/ERROR），这是单一真理源的体现——**内核只管理"最小单元运行中"的状态，不管理"单元未运行"的状态**。

### 12.2 错误处理：降级策略的具体行为（不执行，长期目标）

**缺口**：L2 策略（§9.2 跨阶段策略表）中 `错误处理` 维度有 retry / degrade / stop 三个选项，但"degrade"（降级）的具体行为未定义。

**设计方向**：降级意味着在保持运行的前提下降低服务质量。可能的降级维度包括：

| 降级维度 | 行为 | 恢复方式 |
|---------|------|---------|
| 模型降级 | 切换到更便宜的模型 | 下一轮恢复 |
| 工具降级 | 禁止调用非只读工具 | 异常恢复后恢复 |
| 记忆降级 | 关闭跨会话召回 | 下一轮恢复 |
| 摘要降级 | 关闭摘要生成 | 下一轮恢复 |

**不执行的原因**：降级策略是宿主级决策，不同宿主对"降级"的定义不同——CLI 工具可能直接 stop，GUI 应用可能弹窗让用户选择。内核只提供 retry（重试）和 stop（终止）两种确定性行为，degrade 由宿主实现，**内核不替宿主做"降级"的权衡**。

### 12.3 子 Agent：超时与结果收集（不执行，长期目标）

**缺口**：子 Agent 的异步 fork 机制（参见 [agent-design §14.1](../agent-design/README.md#141-子-agent单轮闭环的递归)）未定义超时处理、结果收集和错误传播行为。

**设计方向**：

- **超时**：子 Agent 执行超时（默认 30s）后，主流程收到超时错误，可选择重试或跳过
- **结果收集**：子 Agent 完成后，通过回调或 Promise 将结果返回主流程
- **错误传播**：子 Agent 的异常应被捕获并作为错误结果返回，而非抛出到主流程

**不执行的原因**：子 Agent 是远期锚点，当前不实现。超时和结果收集的逻辑在实现时自然定义——它们是 fork 机制的自然组成部分，与 fork 同步实现，无需提前设计行为规范。
