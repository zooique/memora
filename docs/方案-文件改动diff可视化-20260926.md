# 方案：文件改动 diff 可视化（无 git 依赖 · host-only）

> 状态：评审修订完成 + 决策闭环（2026-09-26，13 条见 §9；P0-4=A、多文件=全部打开 已拍板）
> 日期：2026-09-26
> 范围：VS Code 宿主（hosts/memora-vscode），零内核改动

---

## 0. 一句话结论

**纯宿主（extension 侧）实现，零内核改动。** 宿主借内核 `process_event` 的 `tool_start`（写前、`args` 可用）/ `tool_result`（写后）时序，自取改动前后内容，用 VS Code 原生 `TextEditorDecorationType` + `vscode.diff` 实现"打开真实文件 + 块级高亮 + 旧内容对比 + 一键恢复"。历史回溯不碰，归 git。

---

## 1. 背景与问题

默认 `confirmWrites=false`（`extension.ts:126` 的 `?? false`）→ 自动批准模式：

- 内核写文件后只回一句文本摘要（行数），用户**不知道具体改了什么**。
- 用户没开 git 或不想依赖 git 时，没有"改动可见性"机制。
- 主流 agent 工具（Cursor / Cline）都有"不依赖 git 的改动对比"，这是基础体验缺口。

### 用户给定的三点需求（本方案的范围边界）

1. **改后文件直接打开进 VS Code 工作区**（用户能立刻看到文件）。
2. **内容保存生效** + **块级高亮**对比改前/改后；旧内容**仅展示**，真实文件里已不含旧内容；支持**「确认对比」/「取消对比」**两动作，**取消直接恢复旧数据**。
3. **只需"本次改动可见性"**，不需要回溯历史修改——历史归 git。

## 2. 决策：为什么是 host-only（含推翻"动内核"的实证）

### 2.1 曾被推翻的错误结论

早期曾判断"需动内核，让内核把 before/after 经 `tool_result` 事件透出"。该结论被以下实证推翻：

- `loop.ts:1669-1675`：每个工具**执行前**先 `yield tool_start`（含 `args`），`loop.ts:1750-1761` 之后才真正写盘。
- → 宿主在 `tool_start` 时刻读磁盘 = **写前旧内容**；`tool_result` 时刻再读 = **写后新内容**；`toolCallId` 仅作**写前/写后配对的临时键**，记录最终**按文件路径合并**（§3.2），**非**按 `toolCallId` 逐条记录。
- 内核方案带 🔴 必修带伤：**越内核边界**——diff 展示是 UI 关注点，内核只该纯逻辑。
- ~~② 把 before/after 全量塞进会被 `roundStore` 持久化的 `tool_result` 事件 → 会话存储爆炸~~ → **此论据已实证推翻，删去**：`tool_start` 载荷本就含 `write_file` 全量 `content`（`chatPanel.ts:2601`），且已随 `eventsByRound` → `checkpointRound` 落盘（`chatPanel.ts:2422-2433`）——不动内核也是这个行为，不构成"内核方案新增的代价"。推翻理由只剩 ① 一条。

### 2.2 本方案借用的内核现有实现（实证）

| 内核事实 | 位置 | 本方案用途 |
|---|---|---|
| `tool_start` 在工具执行前发出，载荷含 `args`（**JSON 字符串，非对象**） | `chatPanel.ts:2601`（`args: chunk.args`）；类型 `args?: string`（`types.ts:37` / `roundStore.ts:226`），源头 `loop.ts:1673` 的 `tc.function.arguments` | 宿主须 `JSON.parse(args)` 后取 `path`（并处理 `undefined` / 解析失败）；此刻读磁盘 = `beforeContent` |
| `tool_result` 在工具执行后发出，含 `ok`/`blocked` | `chatPanel.ts:2608-2617` | 过滤 `ok && !blocked` 后配对 = 有效改动 |
| 内核落盘文件工具仅 `write_file` / `delete_file` | `builtinTools.ts:454`（write_file，mode=overwrite/append/insert）、`builtinTools.ts:476`（delete_file） | 触发集合；`args.path` 为相对项目根路径 |
| `confirmWrites` 默认 false | `extension.ts:126` | 本方案不依赖内核 confirm 模式的 before/after 透传（那条通道默认关） |

> 注意：`edit_file` / `create_file` **不存在**为独立工具——新建文件走 `write_file` 的 overwrite（此时 `beforeContent=null`），追加走 `write_file` 的 append/insert。

### 2.3 已评估并拒绝的替代方案：消费内核 `WriteExtensions.onBeforeWrite`

内核**确已存在**一个为「diff 展示 + 用户确认」准备的钩子：`WriteExtensions.onBeforeWrite(path, beforeContent, afterContent)`（`toolExecutor.ts:291-304`，已进公开导出面 `src/index.ts:46`），由 `write_file` 处理器在写前**无条件**调用——处理器自己读旧内容并算出 `finalContent`（append/insert 也正确），精度不亚于宿主二次读盘。

**仍然拒绝它**，实证两条：

1. **不可达**：LLM 循环路径 `ToolRunner.runOne → raceToolWithSignal` 只调 `execute(name, args)`，**不透传 `extensions`**（`toolRunner.ts:170-179`）→ 该分支在生产路径恒为 `undefined`；要用它必须先动内核补 threading。
2. **覆盖不全**：`delete_file` 不走该回调（`builtinToolHandlers.ts:507-553` 无 `extensions` 参数）→ 删除场景仍得宿主侧读盘，机制被迫裂成两套。

> **精确界定「内核持有的 diff」（2026-09-26 复核）**：内核**不含任何 diff 算法**。所谓"diff"仅指 `WriteConfirmationRequest`（`pathGuard.ts:110-126`）携带的两段**全文**：`beforeContent`（写前读盘）+ `afterContent`（= 处理器自算的 `finalContent`），二者经 `truncateForDiff` **截断到 `MAX_DIFF_CONTENT_LENGTH`=10KB**（`pathGuard.ts:128-140`，唯一调用点 `pathGuard.ts:331-332`）——**有损，不可用于恢复**。真正的行级/并排对比由**渲染方**做：webview 确认卡用文本拼接（`chatView.ts`），本方案用 `vscode.diff`。且该通道默认**不可用**（`confirmWrites=false` 不触发；`onBeforeWrite` 分支在 LLM 路径不可达）。⇒ 本方案**不消费**内核这份数据，而是宿主自取**未截断**全文（恢复需要完整内容）。

结论：**宿主在 `tool_start`/`tool_result` 读盘，是覆盖「write + delete」的唯一 host-only 统一路径**。代价是它与确认卡的 before/after 构成**两个产生点**（勘误见 §5 收敛点行）——须显式声明各自关注域，**不得声称同源**。

## 3. 契约设计

### 3.1 触发工具集合

```
DISK_WRITE_TOOLS = ['write_file', 'delete_file']
```

**内核落盘工具**仅这两个（`builtinTools.ts:454` / `476`）。`task_table_*` 是内核数据不落盘，排除。

> **范围声明（防超范围断言）**：本条只界定**内核落盘工具**。带外改动不在覆盖内——`run_code` / `run_project_script` 执行任意代码可写盘、用户可在编辑器手改文件；二者都不产生 `tool_start`/`tool_result` 写事件，本文档不覆盖。

### 3.2 `FileChangeTracker`（extension 侧新 manager）

**接入点（唯一，禁另起订阅层）**：现**无事件总线**，`emitEvent` 是 `consumeFlow` 内的局部闭包（`chatPanel.ts:2513-2525`）；`tool_start` / `tool_result` 的唯一消费点是 `consumeFlow` 的两个 `chunk.type` 分支（`chatPanel.ts:2599-2607` / `2608-2623`）。实现须在这两处调 tracker（或抽出单一 hook），**不得新增订阅/总线**——否则同一事件出现第二条通道，正是 §5 收敛点要防的漂移。

```
/** 未确认改动（按文件归属：一个文件一条，不按工具调用） */
interface ChangeRecord {
  path: string;                 // 记录键 = 文件绝对路径（展示用相对项目根）
  beforeContent: string | null; // 该文件**首次**未确认改动前的快照；新文件 = null
  afterContent: string | null;  // **最近一次**写入后的内容；已删除 = null
  mode?: 'overwrite' | 'append' | 'insert'; // 最近一次 write_file 的 mode
  writeCount: number;           // 累积写入次数（展示用）
  updatedAt: number;            // 最近改动时刻（展示/淘汰用）
}
```

> **最小单元 = 「一个文件的一次未确认改动」，不是「一次工具调用」。** 同一文件反复被写只**合并**为一条（保留最早的 `beforeContent`）——这样「恢复旧版」才能回到 agent 介入**之前**的状态，而不是回到上一次中间态。字段名与确认卡/安全层**同概念同名**（`protocol.ts:877-878`、`pathGuard.ts:123-125`）；旧稿的 `before`/`after` 与以 `toolCallId` 为主键的记录均已废（见 §9 P0-2 / P0-6）。

数据流：

1. **tool_start**（`name ∈ DISK_WRITE_TOOLS`）：
   - `JSON.parse(args)` → `path`。`args` 是 JSON 字符串且类型可选：`undefined` / 解析失败 / 无 `path` → **跳过本条，不追踪不抛错**。
   - 解析为绝对路径；读磁盘快照（`ENOENT` → `null`）。
   - 存入**临时配对表** `pending: Map<toolCallId, {path, snapshot, mode}>`（仅本次调用生命周期，用完即删）。
2. **tool_result**（`ok && !blocked` 且 `name ∈ DISK_WRITE_TOOLS`）：
   - 取 `pending`；读盘得 `afterContent`。
   - **合并进 `records: Map<绝对路径, ChangeRecord>`**：该路径已有未确认记录 → **保留旧 `beforeContent`**，只更新 `afterContent` / `mode` / `writeCount++` / `updatedAt`；否则新建一条。
   - 推入渲染管线，删除 `pending` 条目。
3. **tool_result**（`blocked` 或 `!ok`）：丢弃 `pending`（写入未发生）。

> **归属与生命周期（本节核心口径）**：`records` 注册表属 **extension 激活期（工作区级）单例**，由 `extension.ts` 装配后注入面板（与 `skills/`、`role-packs/` 同款，`extension.ts:192-206`），**不在面板/会话内 `new`**。→ 记录**独立于聊天会话存在**：切会话、开新会话、关面板、跨 turn 都不丢。清除**仅三条**：① 用户点「确认」；② 用户「恢复旧版」（恢复后注销）；③ **extension host 重启 / 窗口 reload** → 全清（内存方案的自然边界，用户已接受）。
> 这**不是**"历史回溯"（历史归 git，见 §6）——它是**未确认改动的存活期**，与"这个文件被改过且还没被接受"这一事实同寿命。
> 记录条目数上限 100（超出淘汰最旧未确认条目并提示——**被淘汰 = 该条 `beforeContent` 释放 ⇒ 不可再「恢复」，仅从列表消失**，O5 已决）；单条内容受 §4.1 阈值约束；`records` **不进 `roundStore`、不落盘**。

### 3.3 渲染契约（满足用户三点）

| 需求 | 实现 | VS Code API |
|---|---|---|
| ① 打开进工作区 | **逐个打开本次改动的全部文件**（O3 已决：全部打开，方便逐个查看确认） | `vscode.window.showTextDocument(vscode.Uri.file(absPath))`（对每条 `ChangeRecord` 调一次） |
| ② 块级高亮 | 真实文件编辑器加 decoration 标出变更行块（**不改内容**）；基线 = 记录的 `beforeContent` | `TextEditorDecorationType` + `editor.setDecorations` |
| ② 旧内容仅展示 | `beforeContent` 走内存虚拟文档（不落盘），与真实文件做对比 | `vscode.diff(virtualOldUri, realUri, title)`，见 §3.5 |
| ② 确认/取消 | 「确认」= 关 diff + 清 decoration + **注销该文件记录**（接受改动）；「取消/恢复旧版」= 写回 `beforeContent` + 注销 | 见 §3.4 |
| ③ 仅本次可见性 | 记录不落盘、不进 `roundStore`；**跨会话存活**，仅重启/确认/恢复清除；历史回溯归 git | — |

**双呈现分工（必守）**：审批卡已有一份**文本 diff**（`chatView.ts:4358-4370`，注释自称「webview 侧唯一实现点」）。`confirmWrites=true`（含 guest）时同一改动会出现两种形态的 diff（卡内文本 + 原生 `vscode.diff`）。规则：**审批阶段只看确认卡**；tracker 的自动打开在 confirm 模式下**抑制或延后**至审批通过之后。

### 3.4 两动作语义

- **确认对比（保留改动 + 注销）**：关闭 diff 编辑器 + 清除 decoration + **从 `records` 注销该文件条目**（= 用户已接受这次改动，之后对同文件的写入将以新基线开始）。真实文件保持新内容。无写操作。
- **取消对比 / 恢复旧版（撤销本次改动 + 注销）**：把 `beforeContent` 写回真实文件；**写回成功后注销该文件条目**。
  - **安全约束（硬）**：回退写回前**必须经内核 `SecurityGuard` 路径校验**——调 `agent.security.assertPathAllowed(绝对路径, 'write_file')`（`pathGuard.ts:259`），拒绝越界/黑名单路径。
  - **实现通道（已实证定案）**：宿主与内核**均不存在可调的工具执行入口**（`src/index.ts` 无相关导出；宿主仅有 `agent.security.*` 与自身 `atomicWriteFileSync`）→ **不"复用内核 `write_file` 处理器"**，而是**宿主侧最小写**：`assertPathAllowed` 校验通过后，用 `atomicWriteFileSync`（`atomicWriteSync.ts:27`，已存在）写回。**显式声明**：这是宿主对 overwrite/delete 的**最小重复实现**（非内核 handler）——跨层各管各的写入通道（宿主直写、不经内核工具），受控灰区（「项目认可」查无规则出处），须注释对齐来源；删除场景用等价 `fs.unlink`（同样先 `assertPathAllowed`）。
  - ⚠️ 旧稿曾写"必须经由内核 `write_file` 工具路径" + 误引 `setAllowedPaths`（那是**设置器** `pathGuard.ts:230`，非检查方法）——两者均已勘误（见 §9 P0-8）。
  - ~~**回退写禁入追踪（re-entrancy，硬）**：回退自身走 `write_file` 会再产出 `tool_start`/`tool_result`…~~ → **实现期判定：不需要**（2026-09-26 落地）。回退通道最终定为**宿主直写**（`atomicWriteFileSync` / `rmSync`，见上条）——它**不经过内核工具**、**不产生任何 `tool_start`/`tool_result`** ⇒ tracker 无自追踪回路，guard 属多余复杂度（复杂度守恒：不预提）。若未来改为经内核工具回退，再补 guard。
  - `beforeContent=null`（新建文件被恢复）→ 实际是**删除**该文件（`unlink`，但同样需经内核 `delete_file` 或 SecurityGuard 校验）。
  - `afterContent=null`（删除被恢复）→ 实际是**重建**文件（写回 `beforeContent`）。
- **动作呈现位置（O4 已决）**：状态栏单项 `Memora: N 个未确认改动`（`window.createStatusBarItem`）；点击弹 `QuickPick`，每行 = 一个文件、行内动作 = 「打开对比 / 恢复旧版 / 确认」。理由：多文件时不刷屏、贴合 VS Code 惯例（类 SCM 状态条）；不新造 webview 面板（复杂度守恒）。

### 3.5 旧内容载体：虚拟文档（零临时文件，P0-4 推荐 A）

- **载体**：`workspace.registerTextDocumentContentProvider('memora-diff', provider)`（VS Code 官方 Virtual Documents 指南），旧内容由 provider 从本方案已有的内存 `Map` 返回；`vscode.diff(Uri.parse('memora-diff:/<路径 hash>/<原文件名>'), realUri, title)`。**键 = 文件路径（非 `toolCallId`）**——记录已按文件合并（§3.2），一个文件只有一条记录、只有一个稳定键；`toolCallId` 是瞬态的、不能用作 URI 键。**全程不落盘**。
- **语言高亮**：虚拟 URI 尾部保留原文件名与扩展名 → VS Code 自动推断语言 ID。
- **生命周期**：**关闭 diff Tab 只关视图、不释放记录**——记录（含 `beforeContent`）存活到「确认 / 恢复 / 扩展重启」（§3.2）；否则关 Tab 后就无法再打开对比、也无法「恢复旧版」（功能自毁）。**仅「确认」或「恢复」注销该条时**才从内存 `Map` 释放其内容（无磁盘残留、无清理任务）。
- **delete_file 场景**：`afterContent=null` 且真实文件已不存在 → diff 右侧给一个**空虚拟文档**（另一 scheme 或同 scheme 的空内容 URI），对比即「旧内容 vs 空」，语义正确。
- **write_file overwrite 新文件**：`beforeContent=null` → 左侧空虚拟文档，对比即「空 vs 新内容」（等同新建预览）。
- 备选（若拍板改 B）：落 `context.globalStorageUri` 真文件 + 用后删除——**仅在需要跨会话持久化时才有意义**，而 §6 已明确不做历史。

## 4. 边界与阈值（不带伤护栏）

### 4.1 大文件阈值

before/after 全量进内存 + 对比视图渲染会撑爆（虚拟文档方案下已无落盘成本，剩下的是内存与渲染）。

- ❌ ~~复用 `SINGLE_TOOL_RESULT_MAX_TOKENS = 6000` 并按 `.length` 判~~ → **已废**。该键语义域 = 「进入 LLM 上下文的单条工具结果 token 数」，且 `constants.ts:146-148` **明文禁止**「改写成字符数限额——同一字符数在中英文下 token 数相差近 2 倍，按字符限额必然让其中一侧越界」。拿它做 `.length` 比较 = 借错真源 + 违规。
- ✅ **定案（O2 已决）**：宿主定义 `DIFF_PREVIEW_MAX_CHARS = 10240`，**值取自**内核 `MAX_DIFF_CONTENT_LENGTH`（`pathGuard.ts:129`，注释「防大文件撑爆 IPC 传输和 UI 渲染」——与宿主 UI 场景同因）。该内核常量为**模块私有、未导出**，宿主无法直接 `import`；为守住"零内核改动"，此处**并列定义同值常量 + 对齐注释**（受控灰区——「项目认可」查无规则出处，勿引以为据）。**2026-09-26 乙批次已收编**：内核导出该常量、宿主改 `import`，并列副本删除（DIFF-2 闭合，见 §11.9）；⚠️ 两侧超限行为不同（内核 = 截断后照常展示 / 宿主 = 跳过对比只提示），**只统一数值、不统一行为**。
- 判定：若 `max(beforeContent ?? '', afterContent ?? '')` 超上述阈值：
  - 仍打开真实文件 + 加**整文档级** decoration 标记（不计算精确行块）。
  - **跳过**虚拟文档 diff（避免大文本进渲染 + 内存翻倍）。
  - 仍提供「恢复旧版」按钮（恢复只写回 `beforeContent`，不依赖已丢弃的 diff 侧）。

### 4.2 隐私（密钥）·P0-4 已拍板 A（见 §10）

- ⚠️ **旧稿前提不成立（勘误）**：曾写「临时旧文件落 `.memora/tmp/diff/`，而 `.memora/` 已被 `.gitignore:47` 忽略 → 不会进 git」。实测：`.gitignore:46-47` 是**本开发仓自己**的忽略规则；宿主代码全库**零处**写用户的 `.gitignore` → **用户项目里 `.memora/` 完全可能被 git 跟踪**，落在那里的旧密钥文件会进 git。隐私声明的前提不成立。
- **处置（推荐 A）**：旧内容**只在内存**，经 `TextDocumentContentProvider` 以虚拟文档交给 `vscode.diff` → **零落盘 ⇒ 无泄露面、无 git 风险、无清理负担**（见 §10.2）。旧稿的「用户工作区内落盘」（候选 C）**否决**。
- 若最终改选 B（`context.globalStorageUri` 落真文件）：须断言落点在用户工作区之外 + 用后删除（Hygiene，防磁盘长期明文留存）。
- decoration / diff 展示均在本地 UI，绝不回传 LLM（内核侧无感知，天然满足）。

### 4.3 快照时序的精度边界（🟡 记录 + 部分搁置）

**实证时序（决定快照窗口）**：同 step 内所有 `tool_start` **先于任何执行**逐一 yield（`loop.ts:1663-1675` 只 push promise，执行统一在 `1761` 的 `Promise.all`）；`tool_result` 亦**统一在批次完成后**才 yield（`loop.ts:1761-1766`）。→ 宿主的 `beforeContent` = **整批执行前**，`afterContent` = **整批结束后**；窗口是整个批次，而非「单个工具前后」。

据此需覆盖的场景：

1. ~~同批次写同一 `path`~~ / ~~同批次 `delete_file(A)` + `write_file(A)`~~ → **已被 §3.2 的「按文件合并」策略治愈**：一个文件只保留一条记录、`beforeContent` 取最早快照，故批次内多次写盘 / 删写交叉不再产生错配（旧稿按 `toolCallId` 逐条记录才会错配，见 §9 P0-6）。
2. **带外改动**（`run_code` / `run_project_script` 执行代码写盘、用户手改）：无 `tool_*` 事件，**结构上不可见**，非本机制职责（见 §3.1 范围声明）。若发生，该文件的对比会失真（`afterContent` 只是宿主快照时看到的内容）。

### 4.4 回退安全（硬约束，重复强调）

任何"恢复旧版"写回 → 必须经内核 `write_file` / `delete_file` 工具路径或同源 `SecurityGuard` 校验。**宿主 `fs` 直写绕过安全模型属禁止项**；且该写必须**禁入 tracker 追踪**（§3.4 re-entrancy）。

三分类：**原"动内核"方案=必修推翻**；本 host-only 设计**修后**无必修带伤，仅 §4 的建议级护栏项。⚠️ 旧稿"全绿"结论不可信——它建立在三处失实前提上（见 §9）。

## 6. 不做什么（scope 收窄，防过度设计）

- ❌ 不实现"改动历史回溯"（跨会话回看旧版本）——那是 git 的职责。**但"未确认改动"不是历史**：它跨会话存活，直到用户确认/恢复或扩展重启（§3.2）。
- ❌ 不落盘持久化（重启即清空）——**不等于**把记录绑在会话上（旧稿误述已废，见 §9 P0-6）。
- ❌ 不引入 git 依赖（不调用 `git diff`）。
- ❌ 不改动内核 `src/` 任何文件。
- ❌ 不在 webview 内做 diff 渲染（webview 无磁盘/编辑器权限，必须在 extension 侧）。
- ❌ 不消费内核 `WriteExtensions.onBeforeWrite`（理由见 §2.3：不可达 + 覆盖不全）。

## 7. 验证计划（实现后必跑，证明不带伤）

1. **内核零改动实证**：`git diff --stat src/` 应为空（仅 docs/ 新增）。
2. **触发正确性**：写测试模拟 `tool_start(write_file, path=A)` → 改盘 → `tool_result(ok)` → 断言 `records` 中 A 有 1 条记录且 `beforeContent≠afterContent`。
3. **新文件**：`write_file` 到不存在路径 → `beforeContent=null`，diff 左侧空。
4. **删除**：`delete_file` → `afterContent=null`，「恢复」重建文件且内容 == beforeContent。
5. **大文件**：注入超 §4.1 阈值内容 → 断言**不打开**对比视图（仅整文档 decoration）、仍可调「恢复」。
6. **回退安全**：mock `SecurityGuard`，断言「恢复旧版」走内核写路径（而非 `fs` 直写）。
7. **存储不膨胀**：断言 `ChangeRecord` 不入 `roundStore`（对比 `round.processEvents` 长度不变）。
8. **隐私 / 零落盘**：断言方案 A 下全程无新增临时文件（工作区与 `globalStorage` 均无写入）、`git status` 不受影响、**不依赖用户 `.gitignore`**。若拍板 B/C，改为断言落点在用户工作区之外。
9. **`args` 解析**：注入 `args=undefined` / 非法 JSON / 无 `path` → 断言跳过且不抛错。
10. **回退无自追踪**：断言「恢复旧版」走**宿主直写**、**不产生** `tool_start`/`tool_result` 事件（故天然不新增 `ChangeRecord`；无 re-entrancy 面，无需 guard）。
11. **阈值口径**：断言判定走 §4.1 新口径，且代码中**不出现** `.length` 与 token 常量比较。
12. **对比视图生命周期**：关闭 diff Tab → 断言**记录仍存活**（可再次打开对比、可「恢复」）；仅「确认」/「恢复」注销时 → 断言虚拟文档内容从内存释放（无泄漏、无残留 URI）。
13. **跨会话存活（P0-6 核心）**：切换 / 新建 chat 会话（面板重建）后 → 断言 A 的未确认记录**仍在**、仍可打开 diff 与「恢复」；模拟 extension host 重启 → 断言**只有这一条途径**会全清。
14. **按文件合并**：对 A 连续两次 `write_file` → 断言仍只有 1 条记录、`beforeContent` 为最早快照、`writeCount=2`、`afterContent` 为最新。
15. **确认即注销**：点「确认」后 → 断言 A 条目被注销、decoration 清除；随后的新写入以新基线建新记录。
16. **多文件全部打开（O3）**：一次 turn 改动 A/B/C → 断言三条记录各自触发 `showTextDocument`、三文件均打开；状态栏计数 = 3；QuickPick 列出三条。

## 10. 外部养分吸收与 P0-4 拍板（2026-09-26 联网调研 → 已拍板 A）

> 依据 network-soil-mindset：设计前先搜索、结论进设计、来源可追溯。

### 10.1 同行怎么做（来源见文末）

| 做法 | 谁在用 | 对我们的启示 |
|---|---|---|
| **内存虚拟文档承载 diff 左侧**（自定义 scheme + `TextDocumentContentProvider`，全程不落盘，合入或关 Tab 即清） | VS Code 官方《Virtual Documents》指南；AI Diff merge 扩展（`ai-diff://` 内存文件系统，原文「No temp files for the diff view itself… leaves nothing on disk」） | **P0-4 最优解：根本不写临时文件** |
| **影子宫仓库落 extension 全局存储**（`globalStorage` + workspace 路径 hash 分组） | Cline `CheckpointTracker`；Roo Code 同款 shadow repo（均与用户主 git 隔离） | 若确需落盘，落点共识 = **extension 全局存储**，而非用户工作区 |
| 只读对比用虚拟文档，确需真文件才落 extension storage 目录 | Editor Text Toolkit（read-only virtual document vs 落到 extension storage 的 copy 文件） | 印证取舍顺序：能虚拟就不落盘 |
| **对比基准分区**：本次会话改动 / 全部未提交 / 自分支点 | Claude Code `/diff` 面板（v2.1.260，`Ctrl+X B` 切换） | 印证我们「仅改动可见性（不做历史）」的范围选对了；注：我们的存活期更宽——**跨会话存活、重启清空**（§3.2） |
| **带外改动（手改 / 其他工具）不纳入快照** | Roo Code 文档明确列为 limitation | 印证 §3.1 范围声明 |

### 10.2 P0-4 三候选与推荐

| 候选 | 隐私（旧密钥） | git 风险 | 清理负担 | 实现成本 |
|---|---|---|---|---|
| **A. 虚拟文档（推荐）**：`registerTextDocumentContentProvider('memora-diff', …)` + `vscode.diff(虚拟 URI, 真实 URI)` | **无**（内容只在内存） | **零** | **零**（关闭 diff Tab 不释放记录；仅确认/恢复注销时释放） | 低：一个 provider，复用既有内存 `Map` |
| B. `context.globalStorageUri` 落真文件 | 磁盘明文留存（需用后删） | 零（工作区之外） | 有 | 低-中 |
| C. 用户工作区 `.memora/tmp/`（旧稿） | 磁盘明文 + **可能进 git** | **有** | 有 | 低 |

**推荐 A**（2026-09-26 已拍板），理由：① 直接消灭 P0-4 的隐私前提问题——不存在文件就不存在泄露面；② 与 VS Code 内置 git 扩展同路数（虚拟 scheme 展示旧内容），属生态既定做法；③ 复用已有内存 `Map`，不新增落盘与清理逻辑；④ 语言高亮靠虚拟 URI 尾部保留原扩展名即可。
**A 的已知限制**：对比视图仍受内存/渲染约束 → 由 §4.1 阈值 gate（超限只做整文档 decoration + 保留「恢复」）。
**B 的适用条件只有一个：连扩展重启后也要保留**（真正的跨**进程**）。旧稿把它误写成"跨会话持久化"，混淆了两件事（勘误见 §9 P0-6）：**跨会话**（切 chat 会话 / 跨面板 / 跨 turn）由内存方案的**归属上移**（§3.2：记录属 extension 级单例，非会话级）即可满足，**不需要落盘**；你已明确接受"重启即丢"，故 **B 仍不需要**。**C 否决**（git 风险）。

### 11.2 内联呈现重构（第三轮，2026-09-26 · 用户命题）

**命题原话**：「能不能直接打开文件处直接显示？不用专门打开 diff 对比？参考 traecode 和 qoder 的方案。」

**参考对象实证（检索 Trae 文档 / 社区）**：Trae 的交互是「悬停改动处出现 `Y (Accept) / N (Reject)`」+ 顶部「全部接受 / 全部拒绝」。Trae 是 VS Code fork，Qoder 同类；其行内 Accept/Reject 在**纯扩展**层面的等价物即 **CodeLens**——`CodeLens.command` 只支持单命令 ⇒「多按钮并排」= 同一 range 上放多个 CodeLens（VS Code 会并排渲染）。

**API 实证（读 `@types/vscode` 而非凭记忆）**：

| 能力 | 判据 |
|---|---|
| 行内虚拟文本 | `ThemableDecorationRenderOptions.before/after` ✅（`ThemableDecorationAttachmentRenderOptions`：`contentText`/`textDecoration`/`color`/`fontStyle`/`margin`） |
| 实例级附件 | `DecorationOptions.renderOptions`（`DecorationInstanceRenderOptions`）同样含 `before`/`after` ✅ |
| 行内按钮 | `CodeLensProvider` + `onDidChangeCodeLenses` ✅ |

**落地形态（内联；diff 窗口降级为按需）**：

| 层次 | 实现 |
|---|---|
| 高亮 | `HIGHLIGHT_OPTIONS`：整行绿底 + 左侧 3px 竖条 + 概览标尺（字面色，不依赖主题） |
| 旧内容（行尾） | hunk **首行** 的 `renderOptions.after.contentText` = `⟵ 原: <单行摘要> (+N 行)`，删除线 + 灰红斜体 |
| 旧内容（全文） | hunk 首行 `hoverMessage`（Markdown 代码块，最多 30 行，超出省略） |
| 操作按钮 | 每个 hunk 上方 2 个 CodeLens：`确认本文件` / `回退本文件`；首个 hunk 追加 `全部确认` |
| 视口 | `revealRange(首个 hunk 锚点, InCenter)` |
| diff 窗口 | `vscode.diff` 仅由「改动通知 / 状态栏 QuickPick」按需触发，**不再自动弹出** |

**新增纯逻辑模块**：`hosts/memora-vscode/src/extension/host/fileChangeDiff.ts`

- 算法 = **前缀/后缀裁剪 + 行级 LCS**（`Uint32Array` 后缀型 DP + 正向回溯）。
- 「删 N 增 M」在 walk 期间不 flush ⇒ 天然合并为同一块（不会拆成「删除块 + 新增块」）。
- `MAX_LCS_LINES = 1200`，超限降级为「中间整体一块」并置 `degraded`（渲染层写日志）。
- 空串按 **0 行** 处理（`'' → []`）：否则 `''.split('\n')` 的 `['']` 会把「清空文件」误算成「保留 1 个空行」。

**SSOT 收口**：装饰与 CodeLens 共用同一份 `hunkCache`（`hunksFor` / `hunksOfPath`）——两处各算一遍 diff 会漂移，属 SSOT 违例。

**文案诚实性修正**：CodeLens 挂在每个 hunk 上，但确认/回退动作作用于**整个文件**（记录粒度 = 文件），故文案定为「确认本文件 / 回退本文件」，**不写**「确认此处」。

**按钮语义**：CodeLens 内部命令（`memora.fileChange.confirmInline` / `restoreInline`）**不进** `package.json#contributes.commands`——它们需要文件绝对路径参数，暴露到命令面板会得到无参调用而静默失败。

**质量门**：`fileChangeDiff` **19 项**（含降级 / 裁剪后回精确模式 / 清空 / 新建 / 多处改动 / 锚点 clamp）；三文件合计 **33 passed**；宿主 `tsc --noEmit` = 0、`eslint --max-warnings 0` = 0。

**变异验证（实锤）**：注释掉 `lcsHunks` 中的 `cur.removed.push(midBefore[i])` → **6 项精确变红**（单行替换 / 删增相邻合并 / 首行改动 / 末行改动 / 多处不连续 / 裁剪后精确模式），恢复后 19/19 绿 ⇒ 断言确实咬住判据，非「因错误的原因通过」。

### 11.4 对话区常驻条 + 全量回退（2026-09-26 · 用户拍板）

**命题**：把「全部确认」从文件内（易与「本文件」粒度混淆，见 §11.3 伤 1）上移到**对话区**常驻条，并**补齐「全部回退」**（带二次确认）。

**核心设计决策 = 两个动作的「安全等级」不同级**：

| 动作 | 写盘？ | 可撤销？ | 二次确认 | 依据 |
|---|---|---|---|---|
| **全部确认** | ❌ 纯内存清理 | — | **不需要** | 只清装饰 / 虚拟文档 / 缓存 / 记录，改动早已落盘生效 ⇒ 幂等零风险（对齐 Trae「全部接受」直接执行） |
| **全部回退** | ✅ 覆盖写回；**原为新建的文件会被删除** | ❌ 不可撤销（无 git 时无法找回） | **必须**（模态 + 明细） | 会连用户在改动之后的**手动编辑一并覆盖**；破坏性操作走双重保险（项目契约） |

**多入口同一实现（SSOT）**：`memora.confirmAllFileChanges` 是「全部确认」的**唯一实现**，被 ① 对话区常驻条 ② 状态栏 QuickPick 首项 ③ 命令面板（`package.json` 贡献） ④ 改动通知按钮 共用；`memora.revertAllFileChanges` 同理（对话区 + 命令面板）。**webview 侧不实现任何清理 / 写盘逻辑**，只 `postMessage` → host `executeCommand`。

**分层与改动**：

| 层 | 文件 | 改动 |
|---|---|---|
| 协议 SSOT | `src/shared/protocol.ts` | +2 W→E（`confirm_all_file_changes` / `revert_all_file_changes`）、+1 E→W（`file_changes`） |
| 渲染/动作 | `extension/host/fileChangeView.ts` | `revertAll()`（模态确认 + 逐个执行 + 汇总成败）、`applyRestore()`（**无 UI 版**，供批量复用）、`onDidChange` 事件、`snapshotFiles()`、`notifyChanged()` |
| 宿主接线 | `extension/extension.ts` | `setFileChangesProvider` + 订阅 `onDidChange → pushFileChanges` |
| 面板 | `webview/panels/chatPanel.ts` | 两条消息 → `executeCommand`；`pushFileChanges()`；**`handleWebviewReady` 补推一次** |
| webview | `webview/scripts/chatView.ts` | `updateFileChangesBar()`（懒创建、`insertBefore(inputBar)`）；`file_changes` 分支 |
| 样式 | `webview/styles/chatStyles.ts` | `.file-changes-bar` 系列（注意色左条；令牌**核实后**使用 `--warn`/`--danger`/`--border`/`--text-muted`） |

**关键设计点**：

1. **「时间面」漏面防护**：常驻条状态**两个时机推送缺一即漏** —— 改动集变化时 + **webview ready 回放时补推**。只推前者 ⇒「关掉面板再打开，常驻条凭空消失」（项目里踩过四次的同类漏面）。故新增 `snapshotFiles()` 并在 `handleWebviewReady` 补推。
2. **批量广播收口成一次**：`confirmChange(rec, notify = false)` 供 `confirmAll` 循环使用，循环后统一 `notifyChanged()` 一次 —— 避免 N 次 `postMessage` 触发 webview N 次重渲染。

4. **拦截逻辑落 host**：webview 只 `postMessage`，不做前置判定、不做本地乐观更新（真源 = 宿主 tracker；webview **不自维护计数副本**）。

### 11.7 文档-现实一致性补漏（2026-09-26）

**发现**：§11.4 声称「全部回退」有「对话区 + 命令面板」两个入口，但 `package.json#contributes.commands` **只贡献了 `memora.confirmAllFileChanges`**——`memora.revertAllFileChanges` 虽已 `registerCommand`（webview `executeCommand` 可用），**却未贡献** ⇒ 命令面板里根本没有它。**文档声称 ≠ 现实**。

**裁决**：**补齐 `package.json` 贡献项**（而非删文档条目）——两个批量动作的入口应当对称；且该命令无参调用时自身弹模态确认、无记录时零动作，放进命令面板**安全**。同步更新 `REVERT_ALL_FILE_CHANGES_COMMAND` 的注释（原写「对话区常驻条入口」，补为「对话区常驻条 / 命令面板入口」）。

**复核**：`package.json` JSON 解析通过（`contributes.commands` 共 11 条，文件改动族 3 条齐全）；`tsc` = 0、`eslint` = 0、`commentHygiene` 守卫 1 passed。

### 11.8 第六～八轮：命令 id 守卫 / 形态收紧 / 装饰存活（2026-09-26）· **本节终值取代 §11.6**

**第六轮（命令 id 双源守卫 + 路径归一）**

- `package.json` 侧「补一行」只是**数据修补、不是守卫** —— 命令 id 一旦两处漂移，仍会静默失效。新增 `__tests__/fileChangeCommands.test.ts` 做**双向**机检：3 个对外命令**必须**在 `contributes.commands` 里；2 个 CodeLens 内部命令**必须不在**（它们要文件绝对路径参数，暴露到命令面板会无参静默失败）。用例不硬编码 id 字面量（从模块 import 常量）、包根用 `import.meta.url` 定位（不用 `process.cwd()`）。
- `relPath` 归一：模型偶发把 `path` 写成**绝对路径**，内核 `assertPathAllowed` 接受绝对路径不拦 ⇒ 原样透传会把用户目录结构经 `file_changes` 泄给 webview。`toRelPath()` 折回相对路径（反斜杠统一正斜杠）。变异验证：去掉归一 → 1 red，报错文本里直接出现 `F:\proj\sub\x.md`。
- `isRemovedOnly` 原在 `fileChangeView` 内**内联重复**一遍 → 改为从 `fileChangeDiff` import（该函数当时**生产侧零消费者**，只被测试引用，重复处是真 SSOT 违例）。
- `confirmAll` **半收敛**（N 次 refreshStatusBar + N 次 lensProvider.refresh）→ 抽 `discardRecord()`，循环内不刷新、结束统一一次。

**第七轮（形态收紧 + 渲染竞态）**

- **删 per-hunk CodeLens**。CodeLens 渲染在**所在行的上方**，挂 hunk 首行时按钮紧贴在**上一个 hunk 末尾**之下 ⇒ 真机被误读成「回退上一段」「新增的内容没有回退」；而动作粒度本就是**整个文件**，逐 hunk 摆按钮只会放大该错觉。改为**文件顶部（第 0 行）+ 底部（末行）各一组四按钮**：确认本文件改动 / 回退本文件改动 / 全部确认（N 个文件）/ 全部回退（N 个文件）。
- **渲染竞态**：一个 step 内模型可能**并行多次写同一文件**（真机实测 `insert` + `append` 同 step 发出），`noteToolResult` 会连着触发多次渲染；`openTextDocument` 是异步的 ⇒ 先发起的渲染可能**后完成**并覆盖最新装饰。三道守卫：①`renderSeq`（每文件只让最新一次渲染落地）②await 之后**重取最新记录**（tracker 是唯一真源，不用发起时的旧快照）③`hunkCache` 值改带**写后内容指纹**（原仅按 path 命中会拿旧 hunk 渲染）。
- **坐标对齐**：内核直写盘不经编辑器 ⇒ VS Code 文档缓存可能仍是旧内容，按旧行数算出的 range 会把高亮画到**错误的行**（真机截图实证：中段插入行没高亮、相邻行被高亮）。文档与写后快照不符且 `!doc.isDirty` 时 `workbench.action.files.revert` 重载后再渲染。

**第八轮（装饰存活 —— 真机「切走再切回，高亮全没、只剩按钮」）**

- **根因**：**装饰项绑定在编辑器实例上**，VS Code 在编辑器重新可见时**不会**替扩展恢复；而 CodeLens 走 **provider 模式**（`provideCodeLenses` 由 VS Code 主动回调）⇒ 现场表现恰好是「高亮丢了、按钮还在」，与用户逐字描述吻合。
- **修复**：`renderInline` 改为对**所有显示该文档的可见编辑器**逐个 `setDecorations`（装饰是 per-editor 的，只设一个 ⇒ 分屏另一侧无高亮）；新增 `reapplyDecorations()`（按 `uri.fsPath` 去重后逐文件补齐，`reveal=false` 不抢视口）；`register()` 挂 `vscode.window.onDidChangeVisibleTextEditors`。
- **守卫**：`__tests__/fileChangeView.test.ts`（`vi.hoisted` mock vscode · node 环境）4 例 —— ①`register()` 必须注册可见性监听 ②可见变化 → 重设装饰 ③分屏同一文档 → 每编辑器各设一次 ④未追踪文件零装饰。**变异验证**：删监听 → 3 red（④不动）；`visibleTextEditors.slice(0,1)` 退化单编辑器 → 1 red（仅③，零误伤）。
- **踩坑**：用例假文档的 `fsPath` 必须与 tracker 记录键**同源**——tracker 用 `resolve(root, 'a.md')`，Windows 下得 `\proj\a.md`（反斜杠）；手写 `/proj/a.md` 对不上 ⇒ `tracker.get()` 返 undefined，守卫先假红。修法：`const FILE = resolve(ROOT, REL)`。

**全量终值（取代 §11.6 的 40 文件 / 724 用例）**：宿主 `vitest run --no-file-parallelism` → `Test Files 1 failed | 41 passed (42)`、`Tests 1 failed | 728 passed | 2 skipped (731)`；`tsc --noEmit -p ./` + `-p ./tsconfig.scripts.json` = 0；`eslint . --max-warnings 0`（宿主自己的 `eslint.config.mjs`）= 0。唯一 failed 仍是 `projectSearchProvider` 501 文件扫描 30s 超时（**AssertionError = 0** ⇒ 本环境容器文件系统删除路径慢导致的已知假红，非逻辑失败）。

**残留风险（本机无法验证，须真机判定）**：①`revealChange` 里 `workbench.action.files.revert`（带 uri 参数）是否**同步**更新 extension host 侧 `doc.getText()` —— 若滞后仍会按旧坐标画（代码对该情况已留痕 `文档已被改动或重载失败（高亮范围可能错位）`）；②回退「原为新建」的文件会 `rmSync` 删除它，但**已打开的编辑器标签页会留下僵尸态**（VS Code 标记文件已删除、仍显示旧内容）——本轮未处理。③顶/底两组按钮在**长文件中段**不可见（按钮只在首行/末行），若真机反馈「滚到改动处没按钮」再评估是否加挂首处改动锚点。

### 11.9 第九轮 · 乙批次：W2 未保存编辑守卫 + 内核导出面收编（2026-09-26 · 用户拍板）

**命题（用户拍板范围「乙 · 宿主 DIFF 收口」）**：W2 静默覆盖修复 + 内核导出面补齐（DIFF-2 与清单双枚举一次闭合）+ 新缺口登记台账。全部基于已实证问题，不新增能力、不碰安全面。

**W2（数据丢失类 · 回退静默覆盖用户未保存编辑）**：`applyRestore` 原完全不看 `doc.isDirty`——文件有未保存编辑时点「回退本文件改动 / 全部回退」，写回 `beforeContent` 会把缓冲区编辑**静默吞掉**（第七轮的 `!doc.isDirty` 守卫只管渲染重载、不管回退；`revertAll` 模态文案也只提「已保存的手动编辑」）。**修法（用户拍板「弹模态确认」）**：① `applyRestore` 加 **fail-closed 闸**（返回改 `RestoreOutcome` 三态：`ok` / `dirty` / `failed`，`dirty` 单列、不混进失败原因），任何调用方漏问即被拦；② 单文件回退遇 dirty → **模态确认**（明细写明「未保存的编辑将一并丢弃，可先取消并保存」），取消 = 不动文件、记录保留；③ 批量回退**先扫全部 dirty、一个模态一次列出**（明细标「（含未保存编辑）」+ 计数），`overwriteDirty` **只放行清单内文件**——确认之后才变 dirty 的仍被闸拦下、如实报失败。**守卫**：`fileChangeView.test.ts` +4 例，**全走真实命令路径**（`registerCommand` 捕获处理器，不私调内部方法）：干净直写不弹模态（含「文档打开但未修改 ≠ dirty」）/ dirty 取消不写盘、记录保留 / dirty 确认写回注销 / 批量一次模态列全量。**变异验证**：删 fail-closed 闸 → 恰 2 红（dirty 两条）；删 `isDirty` 判据 → 恰 1 红（「打开但干净不该弹」）；零误伤、MUTATION 残留 0。

**内核导出面（DIFF-2 闭合 + 跨包清单收编）**：① `pathGuard.ts` 导出 `MAX_DIFF_CONTENT_LENGTH`、`src/index.ts` 安全层收录 → 宿主 `fileChangeView` 改 `import`、**删并列副本**（消费点直用内核常量）；⚠️ **只统一数值、不统一行为**（内核 = 截断后加「已截断」标记照常展示 / 宿主 = 跳过对比只提示），两侧注释均已写明。② `WRITE_PATH_EXTRACTORS`（按 `args.path` 改盘工具清单）过 `src/index.ts` 导出 → 宿主 `fileChangeTracker` 的 `DISK_WRITE_TOOLS` 改为 **`Object.keys` 派生**——跨包双枚举收编为单源，内核新增按 path 写工具时宿主自动跟随；宿主测试字面量断言升格为**跨包契约钉**（内核清单变动即红）。③ 内核 `npm run build` 重建 dist（宿主解析的是 dist 的 .d.ts；`dist/index.d.ts` 两导出实读在位）。

**措辞订正（F1 自封认可）**：原文多处写「属**项目认可**的『同模式重复』」——全库无任何规则定义该豁免类，唯一相关口径 ADR-017「相同模式重复 2 次即应提取」反而是反向的 ⇒ 授权链自证闭环，实为**受控灰区**。§3.4 / §4.1 / §11.3 三处已订正，勿再引「项目认可」为据。

**新缺口登记（不修，登记即消费）**：**DIFF-4**（无 `path` 的改盘工具双盲：`run_code` / `run_*_script` 两侧同盲——串行闸不防 + 可视化少报）、**DIFF-5**（内核 builtinTools 工具表 ↔ `WRITE_PATH_EXTRACTORS` 两处枚举无对拍守卫：忘加提取器 = 串行不防 + 追踪不报 + 契约钉不红的三重静默）。
