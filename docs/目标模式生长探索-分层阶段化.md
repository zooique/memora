> **探索中（2026-09-11）**：本稿是可逆探索决策，先落 `docs/` 验证，不占 ADR 编号、不进索引。

> 结论摘要：**把"目标模式"的分层状态从"会话上下文内存"搬到"产物文件 + 记忆库"，每阶段开一张干净上下文、按需召回、阶段完结对需求文档验收回写。不新增编排单元。**

---

## 0. 一句话结论

**目标模式不该靠"外部 agent 管会话、自动建多个会话"生长，而该靠"目标产物文件当跨阶段状态的唯一载体 + 每阶段一个干净上下文 + 阶段完结对需求文档验收"生长。** 前者是把刚砍掉的多 turn 编排换壳成多会话编排；后者是复用现有 turn 闭环 + 记忆召回 + 产物落盘，不新增最小单元。

---

## 1. 背景与问题

当前内核最小单元：**turn ⊃ loop ⊃ step**。step 平铺、以 turn 打包、封闭在单个会话/对话框内。

核心矛盾：**单会话内 step 无限 loop，上下文必然腐坏（context rot）**。

- 一次回答内部反复"想一步 → 调工具 → 看结果"，历史工具输出、中间推理、废弃分支全部堆进同一个窗口；
- LLM 注意力是稀缺资源（attention budget），上下文越长，对早期关键信息与最终目标的可见度越低；
- "目标模式 = 多阶段、跨时长、逐步对齐需求文档"的任务，无法在一个持续膨胀的会话里可靠跑完。

---

## 2. 曾走过的路（为什么此路不通）

| 尝试 | 结果 | 问题 |
|---|---|---|
| 多 turn 任务编排（自动编排 turn 实现目标） | 已砍（2026-09-04） | 复杂度转移：跨 turn 状态传递/对齐/校验难维护 |
| 全程打磨单对话内的上下文装配 | 已打磨 | 只是把污染往后推，不消除源头 |
| step 一直 loop 到底 | 探索中放弃 | 仍在同一个会话，污染依旧，注意力稀释不变 |

**共同点**：三个方案都在"会话上下文内存"这一层打转，没有动"状态该存在哪"这个根本问题。

## 3. 本次假设（提出时）

> 目标模式能否凌驾于会话管理之上——用一个外部 agent 控制程序，自动创建会话，每个会话聚焦一个阶段/模块，逐步对齐最终需求文档，最后用会话记录所有过程？

## 4. 评估

### 4.1 直接评估版（诊断对，药方容器错）

- **诊断正确**：上下文腐坏是真瓶颈，不是错觉。
- **药方错在容器**：用"会话"当编排单元，本质是"多会话编排"，与砍掉的"多 turn 编排"同源，只把粒度从 turn 放大到 conversation，复杂度原样更大。
- **三点结构性问题**：
  1. 换壳不换质：从"注意力稀释"换到"跨会话状态同步"。
  2. 违反最小单元哲学：外层 orchestrator 是第二个单元，其内部每个子会话翻开仍是 turn/loop/step——在 turn 之上再包一层 turn。
  3. 核心矛盾没解：污染根因是"不该进上下文的被放进了上下文"，分窗只是拆小，另增对齐债。
- **被抓住的真东西**：跨会话需要"产物沉淀 + 按需召回"。

### 4.2 吸收养分后的修正版（外围印证）

- 上下文腐坏是 2026 首要工程瓶颈（Anthropic 上下文工程四支柱 Write/Select/Compress/**Isolate**；Context Rot 是结构性衰减）。
- 业界主流收敛形式是 **sub-agent context isolation / delegation**：主 agent 分解任务 → 派发到 fresh context 子任务 → 只回传压缩摘要 → 主窗口不堆 scratch work（Anthropic 多智能体系统 Beat 单 agent 90.2%；MS CORPGEN 三层时间尺度；LangChain Deep Agents supervisor+task）。
- 这些系统管理的是 **fresh context 与任务/阶段产物，不是新建 UI 会话**。"会话"是持久化/界面概念，硬当编排单元会与应用层耦合死。
- **反面教训**：隔离 ≠ 对齐。子代理彼此无 trace 会冲突决策，隔离须配 input-output 契约。"对需求文档对齐/验收"不是可选补充，而是隔离能 work 的充分条件。

## 5. 提议的分层结构（探索目标）

把同一套最小单元按时间/焦点尺度分成三层，状态载体逐层外置：

```
目标层  需求文档（单一真理源，顶层产物——"最终要实现什么"）
  │        每阶段开始：从产物/记忆召回该阶段 spec
会话层  阶段产物（每个阶段一个干净上下文 + 阶段完结回写差异）
  │        round/task：操作层，per-turn 执行
操作层  turn ⊃ loop ⊃ step（现有最小单元，不变）
```

**关键机制**（各层间的"对齐校验"）：
- 阶段开始：从目标产物召回本阶段 spec → 装配进干净上下文。
- 阶段执行：在 turn 闭环内跑本阶段（复用现有 loop/工具/记忆召回）。
- 阶段完结：**对需求文档跑验收/回归，差异回写产物**——隔离与校验成对出现。
- 状态载体 = 产物文件 + 记忆库；**不是会话上下文内存**。旧的污染永远不进新窗口。

---

## 6. 落地路径（不新增单元）

1. **先不造第二个 orchestrator**。用现有 turn 闭环 + "目标需求文档作顶层真理源"验证：
   - 阶段开始时从产物/记忆召回该阶段 spec；
   - 阶段完结回写差异做验收；
   - `task_table` 是操作层、产物文档是阶段层、需求文档是目标层，三层各管一段。
2. **仅在需要"并行"或"彻底隔离的专注上下文"时**，才 spawn 一个 fresh 的 `runChat` 当"阶段"——该 fresh turn 即阶段，产物文件即对齐锚。
3. 决策口：若"忘记主动检索/目标漂移"等真实场景复现，说明召回/验收机制不牢，再评估是否升级机制。
