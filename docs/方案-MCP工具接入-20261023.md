## 0. 两条不可让渡的红线（本方案的判定基准）

1. **内核零第三方运行时依赖**：MCP SDK **只在宿主**依赖里，内核不得引 SDK、不得引用任何 MCP 类型。
2. **落地不带伤**：不接受「第二条审批路径」「消费方私有绕过」「测试专用 API 挪用」这类要长期记账的形态。**做不到则本方案不落地**。

> 这两条由用户 2026-10-23 明示确立；本方案所有取舍都以它们为界。

## 1. 定案基线

### 1.1 为什么必须动内核（推翻初版「纯宿主版」）

初版让宿主自建确认层，试图零内核改动。实测结论：**审批语义只能有一个实现**，而它的所有者已经是内核：

- `SecurityGuard.confirmGate()`（`src/security/pathGuard.ts`，private）注释明写「SSOT：**全部四类**确认——写入 / 命令 / 代码 / 脚本执行——的**唯一执行路径**」。
- 但 `ToolExecutor.execute()` 的 custom 分支（`src/agent/toolExecutor.ts`）**直接调 `custom.handler(args, ctx)`**，`ToolContext` 只有 `guardPath` ⇒ 自定义工具**既不审批、也不产生工具调用级审计**（仅当 handler 主动调 `ctx.guardPath` 时有路径审计 `path-allow`/`path-deny`）。
- ⇒ 宿主侧自建确认层 = **第二条路径** = 违反红线 2。**没有第三条中间路**（初版试过的「类型断言」已因零容忍打回；在宿主框架内绕，只会再犯一次）。

### 1.2 定案

- **形态**：内核出 **minor**（新增可选能力，不破坏既有调用），宿主实现 MCP 客户端。
- **内核变更 = 2 项 + 1 项明确拒绝**：K1 审批统一（**代码面**）、K2 注销生产化（**注释面 + 测试**）；K3 不是改动，是**有判据的拒绝决定**（本期不放宽 schema 类型，§5.3）。
- **SDK 依赖位置不变**：`@modelcontextprotocol/sdk` 只在 `hosts/memora-vscode`，内核 `package.json` 的零依赖 description 不被触碰。
- **发版顺序**：内核 minor 先行发布 → 宿主版 `^新minor` 依赖之。**宿主不得用 peer/dep 之外的私有途径调用内核内部方法。**

**既有壳的实证（读码，非假设）**：`ToolDefinition` / `ToolHandler` 由 `src/index.ts` 公开导出；`registerTool()` 有 5 道防覆盖校验并触发 `onToolsChanged`（刷 `toolDefinitions` + system prompt）；`removeTool()` 已存在且同样触发刷新；`setToolWhitelist()` 可按来源裁剪。宿主向内核注入能力的既有先例 = `ICodeExecutionProvider` / `webSearchProvider` / `fetchProvider` → MCP 走同一注入范式。

## 3. 拍板 A（豁口 1 · schema）：**映射 + 约束搬 description；明确不放宽内核类型**

### 3.1 结论

宿主 `toToolDefinition()` 把 MCP `inputSchema` **逐层映射**成内核窄类型；映射不进去的结构约束（嵌套 object / enum / 数值范围 / `$ref`）**转述进该参数的 `description`**；顶层 `anyOf`/`oneOf` → **剔除该工具 + 宿主告警**。**全程零 `as` / 零 `@ts-ignore`。**

### 3.2 为什么不在这次内核 minor 里放宽 `parameters` 类型（新证据）

原以为「放宽类型」是纯类型层改动。读码否定了这个判断：

- [loop.ts#L2700-L2702](../src/agent/loop.ts#L2700-L2702)：system prompt 的工具清单渲染器写作
  `Object.entries(t.parameters.properties).map(([name, schema]) => \`- ${name} (${schema.type}): ${schema.description}\`)`
  —— **只读顶层 `type` 与 `description`**。一旦允许嵌套 schema，模型可见的这段文案只剩顶层 `object: <顶层描述>`，**嵌套字段的 type/description 全部从模型可见事实中消失**，**等于把「放宽类型」变成「改模型可见事实」**。
- ⇒ 放宽类型 = 类型改动 **+** 模型可见的 prompt 渲染改动 **+** 全套内置工具文案回归验证。**收益（保住结构化约束）不抵风险**，且 S8 已提供官方替代口径。
- **故 K3 = 明确「本期不放宽」，并把触发条件写死**（§5.3）。这不是搁置，是**有判据的拒绝**。

### 3.3 具体形态

- `toToolDefinition(inputSchema, name, description)` 逐层**构造**出符合内核类型的对象：
  - 支持形态（`string` / `number` / `boolean` / `array` + `items`）→ 原样映射；
  - 不支持形态 → 把约束转述进该参数 `description`（如「取值必须为 a / b / c 之一」）；
  - `required: inputSchema.required ?? []` —— **必填兜底**（`validateAndCoerceArgs` 直接 `for (const req of required)`，MCP 的 `required` 可选，缺了抛 TypeError）；
  - 顶层 `anyOf`/`oneOf` → 剔除 + 告警。
- **代价诚实登记**：约束由结构降为自然语言，模型可能忽略；**无 benchmark 支撑**（调研未找到）⇒ 必须可观测（§10 登记表）。

## 4. 拍板 B（豁口 5 · 审批落点）：**单一路径——自定义工具也走 `confirmGate`**

### 4.1 结论

**内核给 `ToolDefinition` 增可选字段 `confirmPolicy?: 'always' | 'audit'`（缺省 = 字段不存在 = 不过闸 = 现状不变）；`ToolExecutor` 的 custom 分支按该字段先经 `SecurityGuard.requestToolCallConfirmation()` → 复用私有 `confirmGate` → 宿主确认 UI。**
**⇒ 全仓仍只有一条确认执行路径，不存在第二条。**

### 4.2 为什么这是干净的（与初版的关键差别）

| 关注点 | 初版（纯宿主） | 本版（内核接口） |
| --- | --- | --- |
| 确认执行路径 | 内核一条 + 宿主一条 = **两条** | **只有一个 `confirmGate`** |
| `pathGuard` 的 SSOT 注释 | 必须改成限定句（变弱） | **扩写为「全部确认（含自定义/外部工具）」——更真，不是更弱** |
| 策略来源 | 宿主自建静态表 | `ToolDefinition.confirmPolicy`（**工具自身属性，不是外部名表**） |
| 判据语义 | 与内核四类并列，易误读 | 只回答「这个工具要不要问」，**不参与命令/脚本裁决** |
| 审计 | 宿主另起一套 | 同一 `emitAudit` 通道 |

**关键：`CONFIRM_ENTRY_BY_TOOL` 静态表不动。** 该表承载「命令 / 脚本 / 写入」的**执行语义裁决**；动态工具不参与该裁决，只声明「要不要问」——两件事不折叠，故不塞同一张表。

### 4.3 三档如何映射到 `confirmPolicy`

| 档 | 宿主行为（注册时计算） | 内核看到的 |
| --- | --- | --- |
| 逐次确认（默认） | `confirmPolicy: 'always'` | 每次过 `confirmGate`（`needConfirm = true`，弹确认） |
| allowlist 免确认 | `confirmPolicy: 'audit'` | 过闸但自动放行（`needConfirm = false`）→ 落 `write-auto`，**仍有审计** |
| server 停用 | 不注册（或注销） | 工具不存在 |

- **反「自动化默认」**：首版**不提供「全部放行」**配置项（auto-approve 是拒枝）；allowlist 必须逐条显式书写。
  - ⚠️ **本句已被实现生长订正（2026-10-25）**：「逐条」的粒度是**服务器**而非工具——实现在工具级键 `mcp__<server>__<tool>` 之外补了整台级键 `mcp__<server>__*`，一条即放行该 server 的全部工具（`policy.serverAllowlistKey`，与工具级共用同一张 allowlist、同一个 `has` 判据）。仍然成立的是：server 位**不通配**（`serverAllowlistKey('*')` 只等于「名为 `*` 的那台」），故不存在「一次放行所有 server」，放行几台仍要显式写几条键。宿主侧四处文案沿用本句旧表述、与实现相反，已按本订正同步（H2）。
- **失败语义**：**只承诺超时 fail-closed**（`CONFIRM_TIMEOUT_MS`）。**不承诺**「面板不可达即拒」——宿主已明确该分支从未实现且刻意不补（切走会误伤）。**「面板切走不误伤」是未验证断言，已从验收判据删除**；真实后果 = 卡无法作答 → 超时拒绝 ⇒ **登记为 UX 缺口**（§10）。
- **审计：零新增类型，复用既有词汇**（2026-10-23 终稿，纠正前一版「新增 `tool-allow`/`tool-decline`」的错判）：
  - [pathGuard.ts#L529-L537](../src/security/pathGuard.ts#L529-L537)、[#L559-L567](../src/security/pathGuard.ts#L559-L567)、[#L585-L591](../src/security/pathGuard.ts#L585-L591) 实证：`confirmGate` 的三个出口**恒落既有三值**——自动放行 `write-auto` / 用户确认 `write-confirm` / 拒绝 `write-decline`（**不是两个值**：前一稿写「恒发 write-auto / write-decline」漏了批准时的 `write-confirm`，已订正）；
  - [pathGuard.ts#L505-L510](../src/security/pathGuard.ts#L505-L510) 实证：`run_command` 把**命令字面量直接塞进 `targetPath`** ⇒ `path` 字段**早就是「被裁决对象标识」**，不只装路径；
  - ⇒ 工具调用沿同一口径：`type` 用 `write-auto` / `write-confirm` / `write-decline`、`tool` = `mcp__<server>__<tool>`、`source` = `'custom'`、`path` = **调用摘要**。
  - **⚠️ 落地约束（读码发现）**：`confirmGate` 现有三个 `emitAudit` **都不带 `source` 字段** ⇒ 若入口只照原签名透传，`source:'custom'` 根本落不了地。K1 的入口必须带可选 `source` 参数并一路透传（`confirmGate` 加可选末参即可，写入类调用不传 = 维持 `undefined`，既有行为不变）。
  - **为什么这样最符合 SSOT**：决策词汇只有一套，主体由 `tool` / `source` / `path` 三个专用字段承载。若新增 `tool-*` 值，同一条决策轴会出现**两套词汇**（`write-*` 管 4 类、`tool-*` 管第 5 类）= 同语义多实现在命名层复发。
  - **代价照实说**：`write-` 前缀对工具调用不精确，但这是**既成决策**（同 [pathGuard.ts#L218-L220](../src/security/pathGuard.ts#L218-L220) 对 `WriteConfirmationRequest` 的处理：改名 = 破坏性公共面、收益仅命名纯度）。处理 = **同批把 [pathGuard.ts#L195](../src/security/pathGuard.ts#L195) 的注释从「写入确认/拒绝/自动」扩写为「确认决策（写入 / 命令 / 代码 / 脚本 / 自定义工具）」**，一句注释、零类型改动。
  - **消费面**：`chatPanel.ts` 的 denied 计数**不用改**（已在计 `write-decline`，工具拒绝自动计入）。

### 4.4 配置来源与授权边界（2026-10-25）

> **状态：三条全部定案（2026-10-25）**——第 1 条由用户直接拍板（「角色包不管 MCP」）；第 2、3 条同日以「**都这么定**」原话确认。授权原文与收据见 `tasks/待完成任务.md` ㉖。三条**均为用户授权，不是 AI 自推自批**（此前的「建议定案」分级标注已在用户确认后撤销，避免留下「AI 建议＝用户已同意」的假授权记录）。重开须先改判据再重推，不得只改结论。

三条结论互为一体（一条主判据 + 两条推论），任何一条被单独放宽都会破坏另两条：

| 问题 | 拍板 | 判据 |
| --- | --- | --- |
| 角色包能否声明所需 MCP server | **不能**（已拍板）。`capabilities` 与 `manifest` 均不得出现 MCP server 引用（名字 / 路径 / 配置片段） | 角色包管「你是谁、怎么做事」（persona / rules / skills = **内容面**）；MCP server = **在本机拉起的任意进程**（写一条配置 = 授权某条命令在你机器上执行 = **用户授权面**）。两件事不同源，塞进同一容器就是双轨。**结构守护已存在**（读码实证）：`capabilityMap.ts` 的 `CAPABILITY_TO_TOOLS` 是闭表、未知能力静默跳过，而 MCP 派生名是运行时动态的、静态表装不下 ⇒ 此条**零代码即成立**；要守的只是「有人给该表加通配」 |
| 工作区级 `.mcp.json` 是否支持 | **不支持**：不读任何仓库内 MCP 配置文件（现状即此；2026-10-25 定为**定案**） | 上一条的直接推论——「项目自带能力」的唯一架构落点是角色包；角色包不管 MCP ⇒ 项目级配置**失去语义出口**（不是「暂缓」，是「无落点」）。剩下唯一动机「少粘一次」不值四笔代价：首次同意持久化 / Workspace Trust 联动 / 与 VS Code 原生 MCP 双启动同一 server / allowlist 来源隔离 |
| allowlist 与 server 配置的作用域 | **都只允许用户级**（`scope: machine`，2026-10-25 拍板），工作区级同名键不读 | 授权单源：能免确认执行的人只能是**本机用户**，不能是仓库作者。若 allowlist 可来自工作区，「克隆仓库 = 免确认执行任意命令」。**补充判据（2026-10-25）**：批准是「本机用户对本机进程」的同意，跨机同步批准 = 把 A 机的同意带进 B 机 ⇒ 作用域取值本身也是授权面，故取 `machine`（不参与 Settings Sync）而非 `application`；代价 = 每机各配一次。断言见 `mcpConfig.test.ts`，判据见远程方案 §6 R7 |

**主流对照（2026-10-25 网检，只取与本拍板相关的判据）**：

| 客户端 | 项目级配置 | 信任形态 | 结论取用 |
| --- | --- | --- | --- |
| Cline | **无**（只有 `~/.cline/data/settings/cline_mcp_settings.json`） | 不涉及 | 最保守端，与本方案同侧 |
| Claude Code | 有（仓内 `.mcp.json`，local/project/user 三档，优先级 local → project → user，**整体取用不合并字段**） | project server **首次逐条批准**，`claude mcp reset-project-choices` 可重置；**其自身已知洞** = 非交互（`claude -p` / SDK）下 project server **无提示加载**，只能靠 `disabledMcpjsonServers` 兜 | 批准形态可借鉴；但它允许仓库在 `.claude/settings.json` 里自批准 server ⇒ **配置与授权同源**，本方案不取 |

**代价照实说**：团队共享一台 server 需每人粘一次配置。已有缓解 = 导入通道接受 `mcpServers`（Claude Desktop / Cursor）与 `servers`（VS Code）双外壳，成本 ≈ 一次粘贴；不做的是「自动跟随仓库」。

**连带结论 · `diskWrite` 对自定义工具恒不生效（否决，非暂缓 · 已定案，授权见 §4.4 状态行）**：

- 判据 = **内核无法履行该承诺**。MCP 写盘发生在 server 子进程，内核的写串行闸与 `fileChanges` 追踪**结构上触不到**；让 custom 声明 `diskWrite` = 让内核获得一个它管不到的能力标示 = **谎报能力**，比不声明更坏（读者会以为它被追踪了）。
- 可见性只能来自**事后观测**，而事后观测的单一手段已经存在（宿主只读 git 采集器，`@git-changes` 的既有路径）⇒ **不为此新造第二个快照器**（`scriptSnapshots` 已是第一个债，勿复制同型伤）。
- 现状（注册时不填字段）+ **代价声明放在授权点**：allowlist 开关旁写明「该工具由外部进程执行，写盘未经内核追踪」。放授权点能影响决定；放执行点只是事后唠叨，且每次多一条噪音。
- 升级条件（方案 §10 保留）：出现「必须追踪 MCP 写盘」的真需求 ⇒ 用**已有** git 采集器取调用前后差集，仍不进内核。

## 5. 内核变更清单（代码 1 项 + 注释 1 项；K3 是不改动的决定）

### K1 · 审批统一（必需）

- `ToolDefinition` 增可选字段 `confirmPolicy?: 'always' | 'audit'`（**缺省 = 字段不存在 = 不过闸 = 现状**；`'never'` 不作为取值，因为宿主永不需要"关掉审计"，仅"关掉弹窗"）。
- `SecurityGuard` 增方法 `requestToolCallConfirmation(toolName: string, summary: string, needConfirm: boolean): Promise<boolean>` → 内部调私有 `confirmGate(summary, toolName, summary, needConfirm, undefined, 'custom')`。**单一入口，两种模式**：`needConfirm=true`（`'always'`）/ `false`（`'audit'`）。
  - **配套**：`confirmGate` 增可选末参 `source?: AuditEvent['source']`（实现取类型面而非窄字面量，未来写入类也能显式标注来源），透传进**全部四个审计出口**（自动放行 / 未注入 handler 拒绝 / 确认与拒绝 / 回调异常拒绝；现状四个都不带 `source`）；写入类既有调用不传 = `undefined`，零行为变化。
  - **可达性（2026-10-23 实测定案，勿再写"非公开面"）**：`SecurityGuard` **类类型**未从 `src/index.ts` 导出，但 `Agent.security` getter 在公开成员面（`publicMemberSurfaceGuard` 钉死）⇒ **宿主运行时可拿到实例、该方法可被调用**。判 **minor** 的依据是「纯新增方法、不破坏既有消费方」，**不是**「宿主碰不到」——后者为假。
  - **消费约束（切片 2 必须遵守）**：宿主**只经 `ToolDefinition.confirmPolicy` 表达审批意图**，**不得**直接调 `requestToolCallConfirmation` 自行拼判据——那会造出第二套判据实现，违反 §1.1「审批语义只有一个实现」。

- 同批注释扩写：[pathGuard.ts#L195](../src/security/pathGuard.ts#L195)「事件类型：路径允许/拒绝、写入确认/拒绝/自动」→「**确认决策**（写入 / 命令 / 代码 / 脚本 / 自定义工具）」（一句注释，零类型改动）。

## 11. 风险

1. **内核改动落在安全层**：K1 触碰 `SecurityGuard` 与 `ToolExecutor` 两个最敏感位置，属**安全回归风险**。缓解：切片 0 必须有「拒绝时 handler 未调用」的断言测试，且不改变既有四类的任何判据。
2. **`confirmPolicy` 缺省 = 不过闸**：默认不弹窗 = 保持现状，但也意味着**忘记设置就静默不审批、不审计**。缓解：宿主侧对 MCP 工具**强制显式设置**（`'always'` 或 `'audit'`，无缺省路径），并在注册处断言。
3. **schema 约束文字化被忽略**：无 benchmark，靠埋点判定（§10 首行）。
4. **`required` 兜底遗漏 = TypeError**：切片 1 必须覆盖「无 `required`」用例。
5. **依赖打包**：`vsce --no-dependencies` ⇒ SDK 必须 esbuild 内联；体积与 ESM 兼容是切片 1 实测项。
   **已实测（2026-10-23，切片 1）**：`pnpm run compile` 通过，`dist/extension/extension.js` 单文件 2.31MB 内含 `StdioClientTransport` / `LATEST_PROTOCOL_VERSION` ⇒ SDK 已被 esbuild 内联，ESM 无兼容问题。体积判据留给切片 4 复核（若接近包体上限再按需拆分）。
   **切片 4 已复核（2026-10-23）**：`dist/extension/extension.js` = 2,438,135 字节（2.33MB，`env -u NODE_OPTIONS pnpm run compile` 实测）——较切片 1 基线 +0.02MB，增量 = 切片 2/3a/3b/4 的宿主业务逻辑（policy / resultNormalizer / runtime 热更），SDK 早在切片 1 内联故无二次膨胀；`StdioClientTransport` / `LATEST_PROTOCOL_VERSION` 仍在包内（复验），热更逻辑（`applyMcpConfigChange`）在包内。**结论：单文件 2.33MB 不接近包体上限，不触发拆分**（拆分判据 = 接近上限，未达）。
6. **审计主体字段过载**：工具调用把**调用摘要**塞进 `path`（与 `run_command` 把命令字面量塞 `path` 同构）。若有消费面把 `path` 当**文件路径**处理（拼链接 / 去重 / 展示），会出现误用。缓解：实施前全库 grep `AuditEvent` 的 `path` 消费面一次，按 `source` 分流，不只看已发现的那处。
   **已核验（2026-10-23 读码）**：① `AuditEvent.path` 的宿主消费面只有 denied 计数（`chatPanel.ts` 按 `type` 判断，不读 `path`）；② 确认卡只把 `WriteConfirmationInfo.targetPath` 当**纯文本**渲染（`chatView.ts` 的 `writeConfirmPath.textContent = msg.targetPath`），不拼链接、不取 basename ⇒ **当前无同型误用**。若后续新增「点击打开文件」，须按 `source` 分流后再放开。
