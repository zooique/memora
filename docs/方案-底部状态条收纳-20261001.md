## 三、设计契约（SSOT）

- **显隐裁决单点**：新增 `resolveDock()`——三条的 `hidden` 与 DOM 归位**只由它裁决**；各条自己的更新函数（updateFileChangesBar / updatePendingQueueBar / showActivity）只上报 `setDockActive(id, active)` 与 `setDockFixed('activity', level==='error')`，**不再直接写 hidden / insertBefore**。
  **（2026-10-05 定案·follower 双单点契约，P10C 已落地）** `follower` 节点（`#activityDetail`）走**位置/显隐分离**：
  `resolveDock` **只搬 DOM 位置**（进浮层 / 退主位），三个搬运点**一律不写 follower `hidden`**；
  随从显隐由条目注册时传入的 `reconcileFollower` 回调自决（activity 传
  `reconcileActivityDetailVisibility`，也是 `is-unread` 类的唯一写入点）：
  ①在浮层 panel 内 ⇒ 随抽屉展开态（`hidden = !_dockExpanded`）；
  ②在主位区 ⇒ `open || 活动未读 || metrics 诊断信号未读` 才显形。
  旧实现三个搬运点无条件写 `follower.hidden = true`，条 2500ms 自动撤就连用户正在看/未读的
  详情一起陪葬（真机「活动详情动不动就消失」）；且 open=true 时若 hidden=true 会撞全局
  `[hidden]{display:none!important}` = 真机「点开即消失」（jsdom 不渲染样式，单测曾把
  bug 锁成契约，见 `方案-提示UI两分收敛-20261005.md` §九教训 12）。变异锁见
  `chatView.test.ts`「P4 补审 B」4 条。
- **条 DOM 单实例**：主位 = 条在浮层 panel 之前（insertBefore inputBar）；被收纳 = 条 appendChild 进 panel。节点移动保留事件监听（DOM 规范保证），无双份渲染。
- **chip 独立 DOM**：`+N` 计数 chip 是独立按钮（不塞进条内）——activityBar 渲染会 `textContent=''` 整体重置，塞条内会被抹掉。
- **空态**：无活跃条 → 无 chip 无浮层；单条 → 主位直显无 chip（N=0 不显示）。
- **error 豁免**：`fixed` 标记恒主位，裁决优先于 priority 排序（**让位于 confirm**——确认卡恒主位，见 `chatView.ts` 的 `pickDockHead` 三层：confirm > fixed > priority）；error 消失（**当前实现 = 定时器到期，非用户点清除**——见 §一 谎报订正；「用户点清除」是尚未落地的目标形态，见 §6.3 宪法②）→ fixed 撤销 → 正常排序接管。

### 6.1 根因诊断：四个病共享一个根

2026-10-05 对抗式审查审出四个用户可见缺陷，逐条追溯后发现**同源**：

| 病 | 用户现象 | 根因 |
| --- | --- | --- |
| 详情被拖死 | 「活动详情动不动就消失，我都没法看了」 | 详情是 `#activityBar` 的随从节点，而条是**瞬态**（2500ms 自动撤）⇒ 条撤带走随从 |
| 谎报清除 | 方案写「带清除」，实际没有 | 表格写了「已具备」⇒ 无人核实（谎报位点复发） |
| error 无出口 | 错误只能等 8 秒 | 瞬态载体被用来承载**非瞬态内容**（错误是需要用户知晓的状态） |
| 收敛与展开对撞 | 「读完要收起」vs「正在看别撤」无解 | 自动显形+ 自动消失两个机制叠加，**无第三个区分维度**（`details.toggle` 不区分触发源） |

**一根因**：**瞬态载体（会自己消失的条）承载了非瞬态内容（状态、历史、用户正在看的东西）**。

### 6.2 外部形态调研（2026-10-05 实查官方文档，非记忆）

| 产品 | 输入区上方放什么 | 关键机制 |
| --- | --- | --- |
| **Cline**（docs.cline.bot/usage/ide） | **空的** —— diff 审批、命令审批**全在消息流里** | 接受「滚动查看」；上方区域不承载信息 ⇒ 无需治理 |
| **Roo Code**（docs.roocode.com/basic-usage/the-chat-interface） | **Action Buttons**（批准/拒绝）——仅此一层 | 常驻的是「**自动批准**」下拉，**是开关不是通知**；错误直接显示在消息里 |
| **Claude Code**（code.claude.com/docs/interactive-mode） | **Tab 式权限对话框** | footer 选中态「Esc 取消选中而**非**中断」⇒「看」与「做」分离；`esc to interrupt` 把「进行中」当**状态**不当**消息** |
| **Trae（TraeCode v3.5.x，2026-10-05 二轮实查，来源见本节末）** | 无通知位；审批是**对话流内动作节点上的内联卡**（跳过 / 运行 / 加白名单） | ①常驻的是**设置里的模式开关**（命令四档：始终手动/白名单/黑名单/始终运行；MCP 独立开关；**按 IDE / SOLO 环境分档**）②**沙箱优先于询问**：默认沙箱内自动执行、节点标「沙箱中」，越权才问；危险命令 shell 拦截直接拒 ③**瞬态错误自动重试并撤回工具卡片**，失败属于动作节点，不另立错误条 ④待办节点**完成即自动总结折叠**，展开看详情；Subagent/工具卡片皆可折叠 ⑤删除类操作灰度自动执行、文件进**回收站**兜底——方向是「让执行默认安全」而非「多问」 |

**共性（四家一致）**：**都不做「通知收纳」，也都没有「常驻状态仪表」**。每一类内容各归其位（动作节点在流里、模式开关在设置里、完成态折叠），而不是塞进一个会消失的条里再想办法收好。

⚠️ **载体差异（不可照搬处）**：Claude Code 是 TUI（字符网格，可纯键盘选中态交互）；Roo/Cline/Trae 是 VS Code 系 webview，**与 memora 同载体**。但 Trae/Cline 的内联审批有一个 memora **当前没有的载体前提**：消息流里存在「工具动作节点」（命令/工具调用本身是流内一个节点，审批是该节点的一个状态）；memora 的工具动作不进消息流（见 P13 红线），硬把审批卡塞进 `#messages` = 漂在流里的孤儿卡，是造伤不是借鉴。
⚠️ **memora 的额外约束**：`#planBar` 任务表是用户明确拍板「永不让位」的，四家均无对应物（Trae 的待办在流内、完成折叠，与 memora 顶部常驻任务表不同位——该形态仅供 planBar 远期评估，本方案不动）。

> **Trae 来源（2026-10-05 实查）**：`docs.trae.ai/ide/auto-run-and-security`、`/sandbox`、`/ide-settings-overview`（自动运行四档/MCP 开关/环境分档/沙箱三选项）、`www.trae.ai/blog/engineering_thought_0108`（2026-01，沙箱+shell 拦截+回收站）、`docs.trae.ai/ide/changelog`（2026-06-17 可重试错误自动重试并撤回未执行卡片；2026-06-10 删除进回收站；待办节点完成自动总结折叠；Subagent 卡片可折叠）。

### 6.3 形态宪法（二轮调研修订版 · ✅ 2026-10-05 用户拍板定案）

> **拍板记录（2026-10-05）**：四条宪法照此定案；「不自动弹」取向定为**终态行为**（error 通知条本身仍按
> 现状自动显 8s，不自动弹的只是详情面板）；C1 排在**止血版真机验收通过之后**。
> 定案时 C1 尚未实施，本结论暂存本过程稿；待 C1 落地、被 `src/` 消费后按沉淀机制评估升 ADR。
>
> **2026-10-05 二轮（Trae）调研对初稿的两处修正**：
> ①草案的「输入框上方常驻状态仪表」**撤销**——四家无一家有此物，是设计者自造形态；
> Trae 证据表明**状态附着在已有载体上**（动作节点上的沙箱标记、设置里的模式开关），不另立面。
> ②草案「需要点头的一律进消息流」**收窄**——Trae/Cline 的内联审批以「流内动作节点」为载体前提，
> memora 没有该载体（P13 红线）；且审批卡是**阻塞 turn** 的，最新动作节点视觉上就在输入框正上方，
> 「输入框上方恒主位」与「流底动作节点」**视觉同位**，真正的缺口不是位置而是**决策无历史**。

| # | 宪法 | 依据 |
| --- | --- | --- |
| ① | **阻塞决策贴输入区，决策完留痕**：A 类确认卡维持输入框上方恒主位（A1 不动）；决策**结果**（批准/拒绝/超时 + 工具面）写入活动时间线——补的是「无处回顾刚才批了什么」，不是搬家 | Trae 审批卡在流底动作节点（视觉同位）；Trae/Roo 决策后节点留在时间线；P13 红线无流内载体 |
| ② | **状态不自己消失，瞬态进度不占状态位**：error/info 条作为**瞬态通知**可自动撤，但其事件**必先落时间线**（现状已如此：`showActivity` 先 push 历史）；错过通知 ⇒ 入口有未读徽章，信息不丢 | Trae 瞬态错误自动重试、卡片撤回但失败归动作节点；Roo 错误显在消息里 |
| ③ | **常驻的是入口与开关，不是通知，也不是仪表**：唯一常驻面 = **抽屉入口**（徽章表达未读/计数，label 可选表达进行中数）；会变成历史的东西一律进抽屉体，不占固定空间。模式开关（memora 的 guest/三档）远期对齐 Trae/Roo，**不在本方案做** | Roo 常驻自动批准开关；Trae 常驻自动运行档位；四家均无状态仪表 |
| ④ | **抽屉不自动弹**：未读只亮入口徽章；时间线**只在用户主动拉开抽屉时可见**。完成态折叠、按需展开 | Trae 待办完成自动总结折叠、展开看详情；意图闩方案已被 6 条红证死（见台账 P15） |

**目标形态（动/静分离 · 修订版）**：

```
顶部    #planBar 任务表                —— 不动（已拍板）
消息流  ask 提问内联（A4 不动）         —— 提问类刻意贴上下文；确认类不入流（P13）
输入框上方
        A 类确认卡（阻塞时恒主位）      —— 不动（A1）；决策结果落时间线（宪法①）
        B 类活跃控件条（现有收纳机制）   —— 文件改动/待发送队列/后台任务，带动作按钮
        抽屉入口（常驻·唯一状态面）      —— 徽章=未读/收纳计数；不自动弹（宪法③④）
         └ 抽屉体
            ├ 控件段：被收纳的活跃条     —— 现状机制，按钮可达
            └ 时间段：活动历史 + 诊断指标 + 决策记录 —— 有界（现状 20 条）
```

**与草案的差异（如实登记）**：①没有「常驻仪表条」——状态压缩进入口徽章/label；
②确认卡不迁消息流，改为「卡不动 + 决策入线」；③抽屉体明确分**控件段/时间段**两段，
时间线段就是现有 `#activityDetail`（历史列表+metrics）摘掉「瞬态条随从」身份后的归处。

**一次性解决四个病**：详情在抽屉体时间段里（条死了它不死，现状止血契约转正后拆除）·
谎报出口真实存在（入口常驻可达，不再靠条自动弹）· error 有出口（事件已落线 + 未读徽章，
条 8s 撤也不丢）·「收起 vs 别撤」不再对撞（**压根不自动弹**，open 轴从「详情的折叠态」

### 6.5 为何不逐个修（带伤论证）

四个病同根（6.1）。逐个修= 每轮只处理一个症状，下一个症状再冒出来，且每轮都要重新对抗式审查一轮。
**先立宪法再改代码**的收益：一次裁决换掉后续所有同类讨论的返工。
**代价**：形态改动 ≈ 3 个节点的位置逻辑重写 + `follower` 机制拆除，**必须分阶段独立提交 + 真机验证**（jsdom 证不了「眼睛看到的」）。

> **紧迫性更新（2026-10-05 止血后，如实登记）**：四病中①②④已由 P10B/P10C 在现架构内消除症状
> （条撤不陪葬、open 轴保活、文档谎报订正），本方案已从「修致命 bug」**降级为形态升级**，可以等。
> 仍由本方案闭合的只剩：③的另一半（error 靠 8s 瞬态条，入口不常驻时仍可能错过）与
> ④的体验取向（详情未读仍会**自动弹**，宪法④要求不弹）。**不自动弹是取向不是缺陷，拍板前不得当 bug 修。**
