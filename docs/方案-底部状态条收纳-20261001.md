# 方案 · 底部状态条收纳（StatusDock）

> 2026-10-01 晚 · 用户命题「显示内容形态太多了……同时出现的时候变成点击按钮切换？」
> 拍板：底部三条收纳 / 浮层面板交互 / 错误直显豁免 / 优先级 错误>文件>待发送>通知指标。

## 一、现状实锤（真源盘点）

会话过程状态面 4 个，同屏最多 4 条：

| 条 | 位置 | 语义 | 动作 |
| --- | --- | --- | --- |
| `#planBar` | 顶部 | 任务进度（≥3 任务项常驻，可展开浮层） | 无（纯观测） |
| `#activityBar` | 消息区下 | 错误/通知/指标三类合一（错误常驻保护：info 不覆盖 error，chatView.ts showActivity） | 错误态带清除按钮 |
| `.file-changes-bar` | 输入栏前 | N 个文件未确认改动 | **全部确认 / 全部回退** |
| `.pending-queue-bar` | 输入栏前 | 待发送队列（打断时） | **清空 / 逐条删除** |

痛点：错误 + 文件待确认 + 待发送队列同屏时，底部堆 3 条 + 顶部 1 条。

## 二、定案（用户三拍板）

1. **收纳范围 = 底部三条**（fileChanges / pendingQueue / activityBar 的非错误态）；**错误态直显豁免**（fail-visible 不让位）；**顶部 planBar 不动**（不与底部抢空间）。
2. **交互 = 浮层面板**：主位条尾部「+N」chip，点击展开浮层（同 planBar head→panel 纵向展开形态，**零 absolute 零锚定计算**），被收纳条 DOM **单实例移入**浮层（事件监听随节点保留），浮层内动作按钮直接可用。
3. **主位优先级**：错误（豁免）> 文件改动 > 待发送 > 通知/指标。

## 三、设计契约（SSOT）

- **显隐裁决单点**：新增 `resolveDock()`——三条的 `hidden` 与 DOM 归位**只由它裁决**；各条自己的更新函数（updateFileChangesBar / updatePendingQueueBar / showActivity）只上报 `setDockActive(id, active)` 与 `setDockFixed('activity', level==='error')`，**不再直接写 hidden / insertBefore**。
- **条 DOM 单实例**：主位 = 条在浮层 panel 之前（insertBefore inputBar）；被收纳 = 条 appendChild 进 panel。节点移动保留事件监听（DOM 规范保证），无双份渲染。
- **chip 独立 DOM**：`+N` 计数 chip 是独立按钮（不塞进条内）——activityBar 渲染会 `textContent=''` 整体重置，塞条内会被抹掉。
- **空态**：无活跃条 → 无 chip 无浮层；单条 → 主位直显无 chip（N=0 不显示）。
- **error 豁免**：`fixed` 标记恒主位，裁决优先于 priority 排序；error 消失（用户点清除）→ fixed 撤销 → 正常排序接管。

## 四、scope 边界（防蔓延）

- `#activityDetail`（指标/历史详情折叠）**不动**——独立形态，真机反馈再评估。
- `#planBar` 顶部形态不动。
- 三条的**内容渲染、按钮事件、数据流**全部不动——只改「显隐与归位」的裁决归口。

## 五、验证计划

- 优先级裁决：fileChanges + pendingQueue 同活 → fileChanges 主位（变异：裁决去掉 priority 排序 → 红）。
- error 豁免：error + fileChanges 同活 → activityBar 主位在浮层外（变异：去掉 fixed 豁免 → 红）。
- 收纳形态：双条同活 → chip=+1、浮层展开含次位条、**浮层内动作按钮可达**（确认按钮存在且可点击）；再点收起。
- 单条空态：单条活跃无 chip；全部清空 → chip/浮层消失。
- 全量回归 + tsc + eslint + tokensClosure。
