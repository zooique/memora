# 结论沉淀：工具分类、代理人构想与多会话拓扑

> 本文只沉淀**已得出的结论**，不新做论证。所有事实以源码为准，本文不复制源码细节，只给指针与一句结论。
> 定位与分工：本文是**结论册**（判断 + 判错记录 + 方法论），不是探索稿。方向探索归 `docs/未来迭代方案-探索.md`（多 agent 协同见其 §四方向 3、三层收敛见其 §10.3）；该文**未覆盖**本文的工具分类结论、多会话拓扑 / 存储并发判据与「四样缺」，这些段落为本文件独有，与其不重复。

## §1 三件事的结论

**1）工具分类动议：方向留，形态否。**
把 26 个内置工具按「只读类 / 修改类」切开，用作权限边界——**不成立**。分类只能作为给人看的认知标签，不能当执行面判据，因为工具的能力归属本身混杂（既读又写占相当比例），且执行入口不受暴露面名单约束。结论：分类可以作为长期方向（若未来要做能力画像），但**不作为本版机制**。

**2）代理人 agent 构想：方向成立，条件不具备。**
「一个代理人 agent 替我编排多个会话」在体验上是自然诉求，但它落地依赖四样原语：会话增删改查工具、会话完成事件、第二条可并发的执行流、「只读 + 编排」权限档。当前**四样全缺**，因此它是路线图条目，不是待办。

**3）架构拓扑选择：乙更像自然生长，但堵点在存储层。**
甲（一项目一 Agent、多进程多实例、靠拆 `dataDir` 隔离）与乙（单 Agent 持多个可并发会话）之间，**乙更符合单 Agent 模型与最小单元复用**；但真正的阻塞不是 Agent 结构，而是**同一 `dataDir` 下的存储层并发无锁**。所以第一块砖是存储并发——**不记内核 6.0.0 账**，由同波次发布的宿主 `vscode@0.8.0` 承载（分层口径真源 = `tasks/archive/6.0.0-kernel.md` 的 `KERNEL-6.0.0-BATCH-1` 条目「宿主轴 = `vscode@0.8.0`，定位 = 存储升级 + 多会话呈现」段）。

## §2 关键事实（直接采用，标注来源）

- **26 个内置工具的真实分布**：16 严格只读 / 5 严格写 / 4 既读又写 / 1 控制面。
  按 `src/agent/builtinTools.ts` 的 `BUILTIN_TOOLS`（22 条）+ `ALL_BUILTIN_TOOL_DEFS` 追加的 4 条条件工具（`web_search` / `web_fetch` / `run_code` / `search_project`）**逐条枚举**所得；`readonly` 取定义行声明，副作用按 `src/agent/toolExecutor.ts` 对应分支与 `diskWrite` 声明判。

  | 工具 | readonly | 实际副作用（判据） | 归属 |
  |---|---|---|---|
  | `read_file` | true | 只读文件内容 | 严格只读 |
  | `write_file` | — | 按 `args.path` 落盘写（`diskWrite: path`） | 严格写 |
  | `delete_file` | — | 按 `args.path` 删文件（`diskWrite: path`） | 严格写 |
  | `list_dir` | true | 只列目录 | 严格只读 |
  | `search_memories` | true | 只读记忆索引 | 严格只读 |
  | `trace_summary` | true | 只读摘要 / 原始对话 | 严格只读 |
  | `list_sessions` | true | 只读会话路标 | 严格只读 |
  | `compress_context` | true | 只改上下文内存，不落盘 | 严格只读 |
  | `ask_user` | true | 挂起提问，不改外部状态 | 严格只读 |
  | `remember_intel` | true | 写会话内私有情报区，不落项目盘 | 严格只读 |
  | `task_table_write` | — | 写任务表（会话状态，非项目盘） | 严格写 |
  | `task_table_update` | — | 改任务项状态（会话状态，非项目盘） | 严格写 |
  | `read_skill` | true | 只读技能正文 | 严格只读 |
  | `read_resource` | true | 只读技能资源文件 | 严格只读 |
  | `run_skill_script` | — | 执行任意脚本，可任读任写（`diskWrite: opaque`） | 既读又写 |
  | `run_project_script` | — | 执行项目脚本，可任读任写（`diskWrite: opaque`） | 既读又写 |
  | `run_command` | — | 执行任意 shell，可任读任写（`diskWrite: opaque`） | 既读又写 |
  | `kill_command` | — | 终止后台任务并取输出快照，不直接改盘 | 控制面 |
  | `list_resources` | true | 只列资源清单 | 严格只读 |
  | `list_skills` | true | 只列技能清单 | 严格只读 |
  | `register_work` | — | 追加写 `work-projections.json`（`diskWrite: opaque`） | 严格写 |
  | `run_team_meeting` | true | 内嵌一次 LLM 调用，不改项目状态 | 严格只读 |
  | `web_search`（条件） | true | 只读网络检索 | 严格只读 |
  | `web_fetch`（条件） | true | 只读网页正文 | 严格只读 |
  | `run_code`（条件） | — | 执行任意代码，可任读任写（`diskWrite: opaque`） | 既读又写 |
  | `search_project`（条件） | true | 只读项目内搜索 | 严格只读 |

  口径：**严格只读** = 不改项目文件（按 `readonly` 声明；仍可能有会话状态 / 内存态副作用，见下方「`readonly` 的边界」）；**严格写** = 只产生写、不承担读取回答；**既读又写** = 执行面可任读任写；**控制面** = 只操作会话内后台任务注册表。合计 16 + 5 + 4 + 1 = 26，与枚举一致。
- **暴露面 ≠ 执行面**：`DEFAULT_EXPOSED_TOOLS`（21 条）与 `toolWhitelist` 只影响 `list()`（即 LLM 可见清单），`execute()` **不查白名单**。来源：`src/agent/toolExecutor.ts`（`DEFAULT_EXPOSED_TOOLS`、白名单过滤分支、`execute` 主入口）。
- **只读唯一拦截点**：`toolRunner.applyPrechecks` 中 `toolReadonly === 'readonly' && !toolDef.readonly` ⇒ `[ERR:TOOL:READONLY_DENIED]`（`reason: readonly_denied`），且判据查「全部工具定义」而非暴露面。来源：`src/agent/toolRunner.ts`。
- **`readonly` 的边界**：定义真源 = `src/agent/builtinTools.ts` 的 `ToolDefinition.readonly` JSDoc（原文「true：只读操作（读文件/搜索/查询）… false：写操作（写文件/删除/修改）」）——它承诺的是**不改项目文件**，不是**零副作用**。已核实：`ask_user` 挂起经 `SessionManager.pause()` 写检查点 `pauseMeta` 并发 `sessionPaused` 事件；`remember_intel` 只改 loop 内存态 `intelNote`（不落盘）；`compress_context` 只改内存上下文；`run_team_meeting` 仅一次 LLM 调用、无落盘。⇒ 「只读 agent」挡不住**会话状态写入**与内存态变更。
- **权限三层取更严**：`PERMISSION_FIELD_LENIENCE` 是**单轴秩表**——`toolReadonly` 中 readonly(0) 严于 full(1)、`toolMode` 中 block(0) 严于 allow(1)；**没有正交双轴表达力**。来源：`src/role-pack/strategyResolver.ts`。
- **事件面无「会话完成」**：`AGENT_EVENTS` 共 25 项，无 `sessionCompleted` / `turnDone` / `sessionEnded`。来源：`src/utils/eventEmitter.ts`。
- **会话工具只有「读」**：`listSessions` 只给 sessionId/displayName/主题/summary；`loadRawRoundMessages` 可下钻 ≤5 条；**没有任何 create / send / cancel 会话的工具**。来源：`src/agent/builtinToolHandlers.ts`。
- **单锁单实例**：`Agent.chat()` 持锁；`assertSessionReplaceable` 遇 busy 抛 `chatBusyError`；多实例必须不同 `dataDir`（否则记忆互相污染）。来源：`src/agent/agent.ts`、`src/agent/managers/sessionManager.ts`。
- **宿主没有程序级事件出口**：`activate()` 返回 void，全宿主无 `vscode.EventEmitter`；「结束提醒」现阶段只有一条路径——`attentionNotice` 提示音，且窗口聚焦时不发。来源：`hosts/memora-vscode/src/extension.ts`、`hosts/memora-vscode/src/host/attentionNotice.ts`。
- **「Agent Inbox / 跨会话通信」不在本仓**：`src/` 与 `hosts/` 中 `inbox` 零命中；`send_message_to_session` 属 Trae 平台工具，**不是 Memora 能力**。不得写成 Memora 已有能力。

## §3 判错记录

**1）「把工具分成只读类 / 修改类，就能做权限边界」**
当时判断：两类标签就是边界，贴上即可拦。
为什么错：26 个工具里归「手」（能改外部状态）的 10 个中有 4 个**既读又写**（`run_command` / `run_code` / `run_skill_script` / `run_project_script`），标签天然二义；更关键的是 `execute()` 不查白名单 ⇒ 标签 ≠ 边界。
正确结论：分类是认知工具，边界只能由执行面判据（`readonly` 闸 + 权限档）承担。

**2）「给写工具补 `readonly: true` 标记就能分类」**
当时判断：把标记补齐，分类就自动准确。
为什么错：被 `src/agent/__tests__/builtinTools.test.ts` 的 `NON_READONLY_WHITELIST` 元测试直接推翻——白名单工具**不得**标只读，这是既有契约。
正确结论：`readonly` 是**安全语义声明**，不是分类标签；不能为了分类去污染它。

**3）「关掉感知类工具会把模型逼向编造」**
当时判断：去掉读类工具，模型只能瞎猜。
为什么错：这是行为推断，**不可静态证**。可证的替代论点更强：`run_command` / `run_code` 属「手」且无 `readonly`，关掉读类只是把读取诉求赶进**不受只读闸约束的执行面**。
正确结论：评估「关掉」要看**诉求的迁移路径**，而不是猜模型心理。

**4）「有 16 个公开面成员需要收紧」**
当时判断：数出 16 个，准备一并收紧。
为什么错：实测为 14 个，且其中已有成员存在宿主生产调用；「B 层一并收紧」本身是**三处文字叠加造出的幻觉任务**。
正确结论：该动议已拍板关闭，不再执行。

**5）「为省版本号，在公开类型上另加『是否显式声明』布尔字段」**
当时判断：加个派生布尔即可区分默认值与显式声明，省一次 breaking change。
为什么错：违反 SSOT §2.2——同一事实拆成两个字段，**落笔即漂移**，还会再长出一个守卫来对齐它们。
正确结论：判定出口**只读派生**，不并列镜像。

## §4 方法论（可复用）

- **标签 ≠ 边界**：分类是给人看的认知工具，不是执行面的判据。凡「按类别拦/放」的设计，先问拦在哪一层、判据在哪一行。
- **藏 ≠ 禁**：从暴露面去掉不等于执行不了。评估收紧效果必须查执行入口，而不是可见清单。
- **能验收 ≠ 有用**：一个能力若工具体系里没有对应原语，验收再绿也只是摆设——先验原语，再验流程。
- **关掉 ≠ 关得好**：关掉一类能力，要看被关的诉求会不会改走另一条**不受闸约束**的路径。

## §5 架构方向（不进本版）

- 两条拓扑：**甲**「一个项目一个 Agent、多实例」（靠拆 `dataDir` 隔离）vs **乙**「单 Agent 多执行位」（一个 Agent 持多个可并发会话）。
- 结论：**乙更像自然生长**——复用最小单元、不复制 Agent 内核；甲只是用进程边界绕开并发问题。
- 真正的堵点**不是 Agent 结构**，而是**存储层同 `dataDir` 并发无锁**。
- 第一块砖 = **存储并发**；**不记内核 6.0.0 账**（宿主 `vscode@0.8.0` 承载，与 6.0.0 同波次发布）。
- 代理人 agent 的「四样缺」：① 缺工具（无会话增删改查原语）；② 缺事件（无「会话完成」事件）；③ 缺第二执行流（单锁单活跃会话）；④ 缺「只读 + 编排」权限档（现有秩表无正交双轴）。
  **这四条是路线图，不是待办。**

## §6 明确不做

1. **工具分类**：方向留（认知层可用），形态否（不作为权限机制落地）。
2. **公开面收紧**：已结案关闭，**明确不删**任何现有公开成员。
3. **跨会话通信与 Agent Inbox**：非本仓能力，不设计、不实现、不作为既有能力表述。
4. **存储层并发改造**：确认为第一块砖，但**不在内核 6.0.0 的改动范围**——由宿主 `vscode@0.8.0` 承载，与 6.0.0 同波次发布。
