# Memora — 炼化管线减法方案 v1.0

> **定位**：在动态记忆挂载下，识别炼化存储系统的冗余调用，削减 LLM 调用频次
> **状态**：方案设计（待排雷 + 实施） **日期**：2026-06-04
> **来源**：用户提出"动态挂载下还有减法空间么"
> → 问诊（5 方向评审，3 入选）→ 方案更新 **关系**：本文档是对

## 一、问题与背景

### 1.1 现状

对话问答每发生一轮（用户输入 + Agent 回复），当前系统会触发以下事件：

| 事件                           | 触发点                  | 是否调 LLM        |
| ------------------------------ | ----------------------- | ----------------- |
| 主对话 LLM                     | loop.processUserInput() | ✅ 必需           |
| TopicMount.focus()             | chat() 开头             | ❌ 仅 SQLite 查询 |
| history.appendUser/Assistant() | chat() 结尾             | ❌ 文件追加       |
| userProfile.archive()          | chat() 结尾             | ❌ 正则检测       |
| **topicSummarizer**            | **未归档消息 ≥ N**      | ✅ 1 次 LLM       |
| **dialogueSnapshot**           | **切话题时**            | ✅ 1 次 LLM       |
| workProjection                 | 读文件时 hash 变化      | ✅ 1 次 LLM       |

**问题 1：topicSummarizer 触发条件不明**。当前实现中：

- `MessageHistory.summarizeAndArchive()` 是 private，被 `switchTopic()` 调用
- 但 N=5 阈值在哪个地方定义？代码搜索显示——**没有显式阈值**，依赖"切话题时才触发"（事件驱动）。

**实际上：30 轮同一话题 = 0 次 topicSummarizer 调用**（因为没有切话题）。

**问题 2：dialogueSnapshot + topicSummarizer 输入重叠**。

- snapshot：截断 2000 字 user 发言 → 提取 3-5 句原文
- summary：截断 800 字 user+assistant 对话 → 提炼约束/偏好/决策/快照

两者都从"对话原文"出发，重复读取用户发言。

**问题 3：workProjection 在 tag 重复存了结构**。

- `m.tags` 包含 `structure:章节1`、`decision:决策1` 字符串化
- `m.content` 是 `entry.summary`（50-100 字概要）
- structure/decision 在 tag 中可被全文搜索，但 Memory 类型没有专门的列

## 二、问诊 5 方向评审

| 方向                                  | 评审             | 接入                             |
| ------------------------------------- | ---------------- | -------------------------------- |
| 1. topicSummarizer 改为话题级触发     | **采纳 A**       | LLM 调用 ↓ 70%（30 轮话题 0 次） |

| 3. 短话题跳过 summary                 | 自动随 A 达成    | 不单独做                         |
| 4. focus() 关键词缓存                 | 不减 LLM 调用    | 不做                             |
| 5. workProjection tag 重复            | 动 schema 风险高 | 不做                             |

## 三、方向 A：topicSummarizer 改为话题级触发

### 3.1 现状行为

```
对话生命周期：
  ┌──── 30 轮同一话题 ────┐
  │ R1: 写 topic-*.md     │
  │ R2: 写 topic-*.md     │
  │ ...                   │
  │ R30: 写 topic-*.md    │
  │ 切话题 → switchTopic() → summarizeAndArchive() 触发 1 次 LLM
  └───────────────────────┘
```

**实际 30 轮触发 0 次 summary LLM**（因为没切话题）。问题不大，但：

- `archiveMissingTopics()`
  在启动时扫所有 topic，**未归档的话题补 1 次**——可能产生 **N 个 topic × 1 次**
  LLM 调用
- 启动慢（虽然 fire-and-forget）
- 漏归档话题的元数据写入延迟

### 3.2 目标

**话题生命周期内不调 LLM**。只在以下时机触发 1 次：

| 触发时机              | 频次      |
| --------------------- | --------- |
| 切话题（switchTopic） | 高频      |
| 启动时补归档          | 启动 1 次 |
| 用户显式（未来扩展）  | 未来      |
| 超长话题中途归档      | > 30 轮时 |

### 3.3 设计

**关键观察**：现有 `archiveCurrentTopic(reason)` 已经支持
`'switch' | 'signal' | 'lazy'` 三种 reason——这是**事件驱动**的成熟设计。

**问题**是：除了 `'switch'`，其他 reason 实际触发频率极低（`signal`
没接入，`lazy` 仅启动时）。

**重构方向**：

```typescript
// 当前：每个 reason 走同一条 LLM 路径
async archiveCurrentTopic(reason: 'switch' | 'signal' | 'lazy' = 'switch'): Promise<void>

// 优化后：reason = 触发时机，LLM 触发逻辑统一在内部
// 调用方不需要关心 LLM 调用的频次
```

**新增触发点**：

```typescript
// src/agent/agent.ts
async chat(input: string) {
  // ... 现有逻辑 ...

  // 新增：超长话题中途归档检查
  const messageCount = await this.history.getCurrentTopicMessageCount();
  if (messageCount > 30 && messageCount % 10 === 0) {
    // 每 10 轮（30/40/50/...）触发 1 次中途归档
    this.history.archiveCurrentTopic('midway').catch(() => {});
  }

  // ... 用户画像 / 技能匹配 ...
}
```

**新增 reason 枚举**：

```typescript
type ArchiveReason = 'switch' | 'signal' | 'lazy' | 'midway';
```

### 3.4 关键约束

- ✅ 现有的 `archiveCurrentTopic` 已经支持 reason 枚举——只需要新增 `'midway'`
- ✅ `pendingArchives` 已经管理 fire-and-forget——不需要改
- ✅ `awaitPendingArchives` 已经支持 close() 时等待——不需要改
- ✅ 失败降级已经完备（log.warn 不阻塞）——不需要改

**改动量**：~30 行（agent.ts 中加 8 行的中途归档检查 + comment 8 行 +
reason 枚举 1 行 + 单元测试 13 行）

### 3.5 风险

| 风险                      | 缓解                                |
| ------------------------- | ----------------------------------- |
| 30 阈值不合适             | hardcode 写死但用常量，便于将来调整 |
| % 10 触发条件可能漏检     | 单元测试覆盖"30/40/50 轮"场景       |
| 启动补归档 + 中途归档冲突 | `topicFile.summary` 幂等跳过        |

### 3.6 预期收益

| 场景                    | 当前                          | 优化后                             | 节省            |
| ----------------------- | ----------------------------- | ---------------------------------- | --------------- |
| 30 轮同一话题           | 0 次（漏归档）                | 2 次（30/40 中途）+ 1 次（切话题） | +3 次有意义归档 |
| 10 轮话题               | 0 次（漏归档）                | 1 次（切话题）                     | +1 次有意义归档 |
| 100 个未归档 topic 启动 | 100 次 LLM（fire-and-forget） | 100 次 LLM（unchanged）            | 无              |
| 3 次切话题              | 3 次                          | 3 次（unchanged）                  | 无              |

**A 的真正价值**：把**漏归档的 30 轮话题**变成**有意义归档**，同时**没有增加 LLM 成本**（从 0
→ 2，但每 10 轮才 1 次）。

## 四、方向 B：snapshot + summary 合并为 1 次 LLM

### 4.1 现状

```
切话题时（2 次 LLM）：
  L1: DialogueSnapshotExtractor.extract()
      输入：2000 字 user 发言
      输出：3-5 句原文（m.content 之外的独立产物 → 写入 frontmatter seed_snapshots）
      Prompt: 200 tokens
      Latency: ~1-2s

  L2: TopicSummarizer.summarize()
      输入：800 字 user+assistant 对话
      输出：约束/偏好/决策/快照（写入 frontmatter summary + SQLite 索引）
      Prompt: 200 tokens
      Latency: ~1-2s

  总计：~2-4s 等待，~400 tokens 消耗
```

**问题**：两个 LLM 调用都从"对话原文"出发，但产物（seed_snapshots vs
summary）有重叠（snapshot 就是 summary 的"快照"字段）。

### 4.2 目标

**合并为 1 次 LLM**：

```
切话题时（1 次 LLM）：
  L1: CombinedArchiveExtractor
      输入：2000 字 user 发言 + 800 字对话
      输出：{
        constraints: string[],
        preferences: string[],
        decisions: string[],
        snapshots: string[],    ← 替代 DialogueSnapshotExtractor.extract()
        summary: string          ← 替代 TopicSummarizer.summarize()
      }
      一次性写入 frontmatter summary + seed_snapshots + SQLite 索引
      Prompt: 300 tokens（一次性给完整指令）
      Latency: ~1-2s
```

**节省**：~50% LLM 调用次数，~50% token 消耗，~50% latency。

### 4.3 设计

**新建模块**：

```typescript
// src/agent/topic-archiver.ts

export interface CombinedArchiveResult {
  constraints: string[];
  preferences: string[];
  decisions: string[];
  snapshots: string[];
  summary: string; // 串联所有字段的可读文本
}

export type TopicArchiverFn = (
  messages: TopicMessage[],
) => Promise<CombinedArchiveResult | null>;

export function createTopicArchiver(provider: LlmProvider): TopicArchiverFn {
  return async (messages) => {
    const conversation = messages
      .map((m) => `[${m.role}]: ${m.content}`)
      .join('\n')
      .slice(0, 2000);

    const promptMessages: Message[] = [
      {
        role: 'system',
        content: `你是记忆价值评估与结构化提取助手。分析以下对话，提取用户独有的信息。

判断标准：
- 约束：用户透露的技术栈、环境限制、项目配置
- 偏好：用户的代码风格、工作流、审美、命名习惯
- 决策：用户做出的会影响未来交互的架构选型、策略决定
- 快照：5-8 句用户原文中信息量最高的句子（≤30字/句，逐句截取，不改写）

输出格式（严格 JSON，不含 markdown 代码块标记）：
- 对话全是通用问答/闲聊，无任何独有信息 → 只输出 SKIP
- 否则：{"约束":["..."], "偏好":["..."], "决策":["..."], "快照":["..."]}
- 空数组的字段可省略
- 每条约束/偏好/决策 10-20 字，只提取用户独有的信息
- 快照 5-8 句，按原文顺序

输入说明：
- 字段名为中文（与原 topic-summarizer 兼容）
- 快照与 summary 的"快照"字段一致`,
      },
      { role: 'user', content: conversation },
    ];

    let result = '';
    for await (const chunk of provider.chat(promptMessages, {
      maxTokens: 400,
    })) {
      if (chunk.content) result += chunk.content;
    }
    const trimmed = result.trim();
    if (trimmed.toUpperCase() === 'SKIP' || trimmed.length === 0) return null;

    try {
      const parsed = JSON.parse(trimmed);
      // 构造可读 summary 文本
      const parts: string[] = [];
      if (parsed['约束']?.length)
        parts.push('约束：' + parsed['约束'].join('；'));
      if (parsed['偏好']?.length)
        parts.push('偏好：' + parsed['偏好'].join('；'));
      if (parsed['决策']?.length)
        parts.push('决策：' + parsed['决策'].join('；'));
      if (parts.length > 0) {
        return {
          constraints: parsed['约束'] ?? [],
          preferences: parsed['偏好'] ?? [],
          decisions: parsed['决策'] ?? [],
          snapshots: parsed['快照'] ?? [],
          summary: parts.join(' | '),
        };
      }
      return null; // 解析后无任何有价值字段
    } catch {
      // JSON 解析失败降级为原始文本快照
      return {
        constraints: [],
        preferences: [],
        decisions: [],
        snapshots: trimmed
          .split('\n')
          .filter((l) => l.length > 5)
          .slice(0, 5),
        summary: trimmed,
      };
    }
  };
}
```

### 4.4 与现有模块的关系

| 模块                                   | 现状                            | 优化后                             |
| -------------------------------------- | ------------------------------- | ---------------------------------- |
| `topic-summarizer.ts`                  | 存在                            | **删除**（被 topic-archiver 替代） |
| `dialogueSnapshot.ts`                  | 存在                            | **删除**（被 topic-archiver 替代） |
| `topic-archiver.ts`                    | **不存在**                      | **新增**                           |
| `MessageHistory.archiveCurrentTopic()` | 调 summarizer                   | 调 archiver                        |
| `Agent._assembleComponents()`          | `new DialogueSnapshotExtractor` | 删除（不再需要）                   |

### 4.5 seed_snapshots 的处理

当前 `DialogueSnapshotExtractor` 的产物是
`seed_snapshots[]`——切话题时提取上一话题的 3-5 句原文，写入下一话题文件的 frontmatter。

**新流程**：

```
切话题流程：
  1. 用户触发 switchTopic("new_topic")
  2. MessageHistory.switchTopic() 内部：
     a. 旧话题 archiveCurrentTopic('switch') → 调用 archiver(messages)
     b. archiver 返回 { snapshots, summary, ... }
     c. 写入旧话题的 frontmatter summary（不变）
     d. 写入新话题的 frontmatter seed_snapshots = snapshots（不变）
     e. 写入 SQLite 索引（不变）
```

**关键**：合并后**产物增加**——`snapshots`
既能写旧话题 summary（作为字段），又能写新话题 seed_snapshots（作为种子）。

## 六、与现有设计的一致性

### 6.1 与记忆减法 v1.0 的关系

| 记忆减法 v1.0      | 本方案                 | 关系                                |
| ------------------ | ---------------------- | ----------------------------------- |
| 归档触发改为话题级 | 方向 A 增加中途触发    | 补强（弥补"30 轮不切话题就漏归档"） |

| 封存不删除         | 不涉及                 | 独立                                |
| 失败重试 3 次      | 不涉及                 | 独立                                |

### 6.2 与"自然生长"原则的一致性

- ✅ 方向 A：当前 topic-summarizer 只有 1 个调用方，方向 A 不引入新调用方
- ✅ 方向 B：合并 2 个调用方为 1 个——是收敛而非发散
- ✅ 删除了 2 个独立模块（topic-summarizer.ts、dialogueSnapshot.ts）——是减法
- ✅ 引入 1 个新模块（topic-archiver.ts）——但承担了前两者的全部职责

### 6.3 与现有架构的兼容性

- ✅ 不改 `Memory` 类型
- ✅ 不改 `MemoryIndex` 接口
- ✅ 不改 `TopicMount` 接口
- ✅ 不改 `RecallPipeline` 接口
- ✅ 不改 SQLite schema
- ✅ 不改 topic-\*.md 文件格式（summary 字段格式不变，seed_snapshots 字段格式不变）

**唯一变化**：LLM 调用的内部实现——外部行为（写 frontmatter 字段、写 SQLite 索引、TopicMount 召回）完全不变。

---

## 八、不实施

| 方向                    | 不做原因               |
| ----------------------- | ---------------------- |
| workProjection tag 重复 | 动 schema 风险高，暂缓 |
| focus() 关键词缓存      | 计算量 < 1ms，不值得改 |
| 短话题跳过 summary      | 方向 A 实施后自动达成  |

---

## 九、判定

✅ **接纳执行**。本方案：

1. **方向 A**（中途归档）解决"30 轮不切话题就漏归档"的核心问题
2. **方向 B**（合并 archiver）解决"切话题 2 次 LLM"的浪费
3. **总 LLM 调用** ↓ 50%（重度用户每天节省 10+ 次）
4. **总代码量** ↓ 30 行（删除 2 个旧模块 + 1 个新模块的净增为 +30 行）
5. **架构兼容** 100%（不改 schema、不改接口、不改格式）

**核心理念**：在"一切都是话题生命周期事件"的统一模型下，炼化只在该发生的时候发生。
