# Memora — 炼化管线减法方案 v1.0

> **定位**：在动态记忆挂载下，识别炼化存储系统的冗余调用，削减 LLM 调用频次
> **状态**：排雷修正完成，待实施 **日期**：2026-06-04（排雷修正）
> **来源**：用户提出"动态挂载下还有减法空间么"
> → 问诊（5 方向评审，3 入选）→ 排雷（5 风险修正）→ 方案更新
> **核心修正**：不新建 topic-archiver，改为扩展 topic-summarizer（发现其已在请求快照但丢弃）
> **关系**：本文档是对
> [方案-记忆减法-v1.0.md §4.3 归档管线](./方案-记忆减法-v1.0.md)
> 的**炼化触发重构** + 答案**终结**记忆减法方案的最后一里路

## 一、问题与背景

### 1.1 现状

对话问答每发生一轮（用户输入 + Agent 回复），当前系统会触发以下事件：

| 事件                           | 触发点                  | 是否调 LLM        |
| ------------------------------ | ----------------------- | ----------------- |
| 主对话 LLM                     | loop.processUserInput() | ✅ 必需           |
| TopicMount.focus()             | chat() 开头             | ❌ 仅 SQLite 查询 |
| history.appendUser/Assistant() | chat() 结尾             | ❌ 文件追加       |
| userProfile.archive()          | chat() 结尾             | ❌ 正则检测       |
| **topicSummarizer**            | **未归档消息 ≥ N**      | ✅ 1 次 LLM       |
| **dialogueSnapshot**           | **切话题时**            | ✅ 1 次 LLM       |
| workProjection                 | 读文件时 hash 变化      | ✅ 1 次 LLM       |

**问题 1：topicSummarizer 触发条件不明**。当前实现中：

- `MessageHistory.summarizeAndArchive()` 是 private，被 `switchTopic()` 调用
- 但 N=5 阈值在哪个地方定义？代码搜索显示——**没有显式阈值**，依赖"切话题时才触发"（事件驱动）。

**实际上：30 轮同一话题 = 0 次 topicSummarizer 调用**（因为没有切话题）。

**问题 2：dialogueSnapshot + topicSummarizer 输入重叠**。

- snapshot：截断 2000 字 user 发言 → 提取 3-5 句原文
- summary：截断 800 字 user+assistant 对话 → 提炼约束/偏好/决策/快照

两者都从"对话原文"出发，重复读取用户发言。

**问题 3：workProjection 在 tag 重复存了结构**。

- `m.tags` 包含 `structure:章节1`、`decision:决策1` 字符串化
- `m.content` 是 `entry.summary`（50-100 字概要）
- structure/decision 在 tag 中可被全文搜索，但 Memory 类型没有专门的列

## 三、方向 A：topicSummarizer 改为话题级触发

### 3.1 现状行为

```
对话生命周期：
  ┌──── 30 轮同一话题 ────┐
  │ R1: 写 topic-*.md     │
  │ R2: 写 topic-*.md     │
  │ ...                   │
  │ R30: 写 topic-*.md    │
  │ 切话题 → switchTopic() → summarizeAndArchive() 触发 1 次 LLM
  └───────────────────────┘
```

**实际 30 轮触发 0 次 summary LLM**（因为没切话题）。问题不大，但：

- `archiveMissingTopics()`
  在启动时扫所有 topic，**未归档的话题补 1 次**——可能产生 **N 个 topic × 1 次**
  LLM 调用
- 启动慢（虽然 fire-and-forget）
- 漏归档话题的元数据写入延迟

### 3.2 目标

**话题生命周期内不调 LLM**。只在以下时机触发 1 次：

| 触发时机              | 频次      |
| --------------------- | --------- |
| 切话题（switchTopic） | 高频      |
| 启动时补归档          | 启动 1 次 |
| 用户显式（未来扩展）  | 未来      |
| 超长话题中途归档      | > 30 轮时 |

### 3.3 设计

**关键观察**：现有 `archiveCurrentTopic(reason)` 已经支持
`'switch' | 'signal' | 'lazy'` 三种 reason——这是**事件驱动**的成熟设计。

**问题**是：除了 `'switch'`，其他 reason 实际触发频率极低（`signal`
没接入，`lazy` 仅启动时）。

**重构方向**：

```typescript
// 当前：每个 reason 走同一条 LLM 路径
async archiveCurrentTopic(reason: 'switch' | 'signal' | 'lazy' = 'switch'): Promise<void>

// 优化后：reason = 触发时机，LLM 触发逻辑统一在内部
// 调用方不需要关心 LLM 调用的频次
```

**新增触发点**：

```typescript
// src/agent/agent.ts — chat() 末尾新增中途归档检查
async chat(input: string) {
  // ... 现有逻辑（主对话 LLM、用户画像等）...

  // 新增：超长话题中途归档检查
  // 复用已有的 this.roundCount 计数器，无需新增方法
  if (this.roundCount >= 30 && this.roundCount % 10 === 0) {
    // 每 10 轮（30/40/50/...）触发 1 次中途归档（fire-and-forget）
    this.history.archiveCurrentTopic('midway').catch(() => {});
  }

  return result;
}
```

**新增 reason `'midway'`**：

```typescript
// src/agent/message-history.ts — archiveCurrentTopic 签名扩展
async archiveCurrentTopic(
  reason: 'switch' | 'signal' | 'lazy' | 'midway' = 'switch',
): Promise<TopicSummarizerResult | null> {
  // ... 现有逻辑 ...

  // 'midway' 行为：与 'signal' 一致——已有 summary 时仍重新调用（追加覆盖）
  // 幂等保护：topicFile 写 summary 时覆盖而非追加
  const shouldCallLLM =
    reason !== 'switch' || !currentSummary;
  // → reason='midway' 时 shouldCallLLM = true（强制重新归档）
}
```

**关键设计**：

- `'midway'`：已有 summary 时仍重新调用 LLM（追加覆盖），确保后 10 轮的新信息被纳入
- `'switch'`：已有 summary 时跳过（幂等），因为切话题前的 summary 已经是最新的
- `'signal'`：已有 summary 时仍重新调用（用户显式触发，优先级最高）

### 3.4 关键约束

- ✅ `roundCount` 已在 `agent.ts` 中维护——无需新增
  `getCurrentTopicMessageCount()`
- ✅ 复用 `pendingArchives` 的 fire-and-forget 管理——不需要改
- ✅ `awaitPendingArchives` 已经支持 close() 时等待——不需要改
- ✅ 失败降级已经完备（log.warn 不阻塞）——不需要改

**改动量**：~10 行（agent.ts 中 +5 行中途归档检查 + 注释 3 行 +
reason 枚举 2 行）

### 3.5 风险

| 风险                      | 缓解                                            |
| ------------------------- | ----------------------------------------------- |
| 30 阈值不合适             | hardcode 写死但用常量 `MIDWAY_ARCHIVE_INTERVAL` |
| `>= 30` 首次触发即 `30`   | 单元测试覆盖 29/30/31/40/50 轮场景              |
| 启动补归档 + 中途归档冲突 | `topicFile.summary` 覆盖而非追加，后写者覆盖    |
| 中途归档 LLM 失败不阻塞   | fire-and-forget + catch(() => {})，无感知降级   |

### 3.6 预期收益

| 场景                    | 当前                          | 优化后                             | 节省            |
| ----------------------- | ----------------------------- | ---------------------------------- | --------------- |
| 30 轮同一话题           | 0 次（漏归档）                | 2 次（30/40 中途）+ 1 次（切话题） | +3 次有意义归档 |
| 10 轮话题               | 0 次（漏归档）                | 1 次（切话题）                     | +1 次有意义归档 |
| 100 个未归档 topic 启动 | 100 次 LLM（fire-and-forget） | 100 次 LLM（unchanged）            | 无              |
| 3 次切话题              | 3 次                          | 3 次（unchanged）                  | 无              |

**A 的真正价值**：把**漏归档的 30 轮话题**变成**有意义归档**，同时**没有增加 LLM 成本**（从 0
→ 2，但每 10 轮才 1 次）。

## 四、方向 B：snapshot + summary 合并为 1 次 LLM

### 4.1 关键发现（排雷 P0-L3）

**当前 `topic-summarizer.ts` 的 system
prompt 已经在请求「快照」字段**（[topic-summarizer.ts §L62](file:///f:/zooique/memora/src/agent/topic-summarizer.ts#L62)）：

```
"快照：提取 5-8 句用户原文中信息量最高的句子，逐句截取（≤30 字/句）"
```

但 `TopicSummarizerFn` 返回类型是
`Promise<string | null>`，快照数据在格式化为文本后被**丢弃**。然后
`DialogueSnapshotExtractor` 又做了一次独立的 LLM 调用专门提取快照。

**真正的浪费**：summarizer 消耗 tokens 请求快照 → 丢弃；Extractor 再消耗 tokens 请求快照 → 使用。两次 LLM 调用做了重复工作。

### 4.2 修正方案：扩展 topic-summarizer 而非新建 archiver

**不新建 `topic-archiver.ts`**，直接**扩展 `topic-summarizer.ts`**
的返回类型，保留结构化字段。

```typescript
// src/agent/topic-summarizer.ts — 扩展返回类型

/** 话题摘要结构化输出（扩展原 string 返回） */
export interface TopicSummarizerResult {
  constraints: string[];
  preferences: string[];
  decisions: string[];
  snapshots: string[]; // 不再丢弃！
  summary: string; // 格式化文本（写 SQLite 索引 + frontmatter）
}

/** 保持向后兼容：原 TopicSummarizerFn 现返回结构化结果 */
export type TopicSummarizerFn = (
  messages: TopicMessage[],
) => Promise<TopicSummarizerResult | null>;
```

**LLM 调用不变**（prompt 不变、maxTokens 从 150 →
250 保护快照不被截断）。只是在解析 JSON 后**不丢弃 snapshots**。

### 4.3 与现有模块的关系

| 模块                                   | 现状          | 优化后                          |
| -------------------------------------- | ------------- | ------------------------------- |
| `topic-summarizer.ts`                  | 存在          | **扩展返回类型**（+30 行）      |
| `dialogueSnapshot.ts`                  | 存在          | **删除**（-110 行）             |
| `MessageHistory.archiveCurrentTopic()` | 调 summarizer | 调 summarizer（用 R 的类型）    |
| `Agent.switchTopic()`                  | 并列调 2 个   | 删 extractor，从 R 取 snapshots |

### 4.4 switchTopic() 时序修正（排雷 P1-L4）

**当前问题**：`dialogueSnapshot.extract()` 是 fire-and-forget，`.then()` 在
`this.currentTopic` 被 `switchTopic()`
修改后才执行，导致 seed_snapshots 写入错误话题文件。

**修正后流程**（顺序化）：

```
切话题流程：
  1. 用户触发 switchTopic("new_topic")
  2. Agent.switchTopic() 内部：
     a. await archiveCurrentTopic('switch') → 返回 { snapshots, summary, ... }
     b. 从 R.snapshots 设置旧话题的 seed_snapshots（此时 currentTopic 仍为旧值）
     c. topicMount.unmount(); roundCount = 0
     d. history.switchTopic(newTopic) → 修改 currentTopic
  3. 一次性写入：旧话题 frontmatter seed_snapshots + summary + SQLite 索引
```

### 4.5 改动量

| 文件                                           | 操作     | 行数                                      |
| ---------------------------------------------- | -------- | ----------------------------------------- |
| `src/agent/topic-summarizer.ts`                | **扩展** | +30（返回类型 + maxTokens + 类型导出）    |
| `src/agent/dialogueSnapshot.ts`                | **删除** | -110                                      |
| `src/agent/message-history.ts`                 | 修改     | +15（R type + midway reason）             |
| `src/agent/agent.ts`                           | 修改     | +25（switchTopic 重构 + 方向 A 中途归档） |
| `src/agent/__tests__/dialogueSnapshot.test.ts` | **删除** | -185                                      |
| `src/agent/__tests__/topic-summarizer.test.ts` | 修改     | +30                                       |

**总计**：1 删除 + 2 修改 + 1 删除测试 + 1 修改测试，约 **-10 行净减**。

### 4.6 风险

| 风险                                        | 缓解                                       |
| ------------------------------------------- | ------------------------------------------ |
| 删除 DialogueSnapshotExtractor 破坏现有对话 | 唯一调用点在 Agent.switchTopic()，单点替换 |
| summarizer maxTokens 从 150 提至 250        | 原 150 已在请求快照但可能截断，250 正好够  |
| switchTopic 从 fire-and-forget 改为 await   | 切话题增加 ~2s 等待，但消除了时序 bug      |
| 中途归档 + 切话题归档可能冲突               | topicFile.summary 幂等覆盖                 |

### 4.7 预期收益

| 场景                  | 当前             | 优化后       | 节省 |
| --------------------- | ---------------- | ------------ | ---- |
| 切话题 1 次           | 2 次 LLM         | 1 次 LLM     | 50%  |
| 切话题 1 次 token     | ~600 (150+450)   | ~250         | 58%  |
| 切话题 1 次 latency   | ~3s (并行)       | ~2s (单次)   | 33%  |
| 短话题（< 2 消息）    | 0 次（< 2 跳过） | 0 次（不变） | —    |
| 启动补归档 N 个 topic | 2N 次 LLM        | N 次 LLM     | 50%  |

## 九、判定

✅ **接纳执行（排雷修正版）**。本方案：

1. **方向 A**（中途归档）解决"30 轮不切话题就漏归档"的核心问题
2. **方向 B**（扩展 summarizer）发现 summarizer 已在请求快照 → 只改返回类型，不改 prompt
3. **总 LLM 调用** ↓ 50%（重度用户每天节省 10+ 次）
4. **代码净增** **~5 行**（1 删除 + 2 修改 + 1 删除测试 + 1 修改测试）
5. **架构兼容** 100%（不改 schema、不改接口、不改格式）
6. **排雷发现**：5 个风险（L1-L5）全部修入方案，无遗留

**核心理念**：在"一切都是话题生命周期事件"的统一模型下，炼化只在该发生的时候发生。
