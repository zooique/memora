# memora 白话设计文档 · 模块篇

> **这份文档怎么读**：先用「一、整体运作逻辑」把整个机器跑一遍（讲清它是怎么转起来的），再按模块逐个深入（每个模块独立成节，可以跳着看）。
>
> **读者不需要懂代码。** 出现的代码名只是"路标"——方便你对着源码找，不影响理解。
>
> **术语钉死（2026-09-04 收敛定案）**：
> - **step（一步）** = 一次"想 + 可选行动"。LLM 推理一次，必要时调一个工具。
> - **loop（步循环）** = 在一次回答内部，把多个 step 串起来的编排。
> - **turn（问答闭环）** = 一次「用户输入 → 最终回答」的最小完整单元，对应一个 `roundId`。
> - **嵌入关系**：`turn ⊃ loop ⊃ step`。turn 是最大的完整单元，loop 在 turn 内部转，step 是 loop 转一圈的最小动作。
> - ~~多 turn 任务编排~~（已废弃）：复杂任务不拆成多个 turn，全部在**一个 turn 内部的 step 循环**里生长。

# 一、整体运作逻辑

## 1. 一句话：这是什么机器

**memora 是一台"插卡机"。**

内核（memora 本身）是一块**通用的 agent 底座**——它会想一步做一步、会管上下文、会查记忆、会调工具，但它**不认识任何具体专业**。专业能力全靠**插卡**：插一张"文档设计师"卡，它就是文档助手；插一张"小说助手"卡，它就是写小说的。**同一个内核，换卡换人。**

## 2. 四层结构（一张图看懂）

```
┌─────────────────────────────────────────────┐
│  卡片层（角色包）                             │
│  = 可独立制作、可流通的文件夹                  │
│  persona.md / rules.md / skills/ + 策略旋钮   │
│  ⚠ 只带"内容 + 旋钮"，不带代码                 │
└───────────────────┬─────────────────────────┘
                    │ 插入（放进 role-packs/ 目录）
                    ↓
┌─────────────────────────────────────────────┐
│  宿主层（比如 VS Code 插件）                  │
│  = 负责"落地"：读写磁盘、渲染界面、连 LLM      │
│  提供角色包目录、工作区存储、白名单、执行前把关  │
└───────────────────┬─────────────────────────┘
                    │ 组装 + 委托
                    ↓
┌─────────────────────────────────────────────┐
│  内核层（memora · 通用 agent 底座）           │
│  turn ⊃ loop ⊃ step · 预算 · 记忆 · 工具注册表 │
│  = 纯逻辑，不碰磁盘、不认界面                  │
└───────────────────┬─────────────────────────┘
                    │ 落到磁盘
                    ↓
┌─────────────────────────────────────────────┐
│  物理层（工作区里的 .memora/ 文件夹）          │
│  rounds/ · sessions.json · memories.json     │
└─────────────────────────────────────────────┘
```

**四层各管一段，边界清晰**：卡片给"人设与旋钮"，宿主管"落地与界面"，内核管"怎么想怎么做"，物理层管"存在哪"。

## 3. 一次对话怎么转起来（时间轴）

```
你敲下一句话
    │
    ▼
① 装配台子 ── 角色包填入常驻设定 + 你的输入 + 最近对话
    │            （记忆不再预装，改成需要时 LLM 自己查）
    ▼
② 一次回答内部 loop 转起来
    ├─ step 1：LLM 想一步 → 可能要调工具 → 落盘
    ├─ step 2：LLM 想一步 → 可能要调工具 → 落盘
    ├─ step 3：……
    └─ 直到该收尾（软上限 / 步数到顶 / 干完）
    │        （空间满了走三级：替换 → 压缩 → 裁掉）
    ▼
③ 收尾沉淀 ── 这一轮结束，产出一条记忆摘要
    │
    ▼
④ 物理落盘 ── 写进 .memora/（一轮一文件）
```

## 4. 三条贯穿始终的"铁律"

这三条不属于任何单个模块，但**每个模块都受它们约束**，先记住：

1. **完整对话永远优先装**：从最近往回装，装到预算满为止，**第一条问答必然在场**（会话起点背景）。
2. **触发输入是顶级锚点**：你这句输入本身，从预算最上游独立划块，**永不压缩**。（首个回答预留为多 turn 编排遗留，已退役收敛——锚点只保当前输入。）
3. **记忆是可查询资源，不是背景板**：不再每轮硬塞，由 LLM 按需调 `search_memories` 去查；**桌上已摊着的东西，召回时不会再装第二遍**（互斥）。

# 二、模块：step（最小动作 · 真理源）

## 1. 它是什么

**step = 一次"想 + 可选行动"。** LLM 推理一次；如果有必要，调一个工具；拿到结果，交给下一步。

这是整个系统**最小的、不可再分的动作单元**。

## 2. 为什么说它是"真理源"

因为**"发生过什么"最终是由 step 记录的**。一次回答内部可能有十几个 step，每个 step 干完，系统就把"这一步干完了什么"记下来。

**step 的产物 = 运行记录的原子**。上面所有东西（turn 的完整记录、记忆摘要、上下文里的对话）都是从这些原子往上堆出来的。

## 3. 一个 step 完成 → 落一次盘（关键机制）

这是保住运行记录的核心手法：

> **每推进到一个新 step，就把当前已经产出的过程落盘一次。**

具体怎么做的（观察到一个"步边界"信号时）：

1. 把"这一步之前已产出的过程事件"合并进这一轮的记录；
2. 立刻写盘（这一轮此时还是"进行中"状态）；
3. 于是**崩溃最多只丢"当前这一步"**——之前完成的 step 都已在库里。

> **为什么敢这么设计？** 因为"每步落盘"的成本可控、收益极大：一边跑一边存，不用等整个回答结束。这样即使断电，也不是"整轮全丢"，而是"只丢最后一步"。
>
> **幂等保证**：落盘用的是"事件序列号单调 + 合并语义单一"——同一个事件不会存两遍，重复触发也安全。

## 4. 它和 loop 的关系

```
loop（编排者）
  └─ 拉起 step 1 → 落盘
     拉起 step 2 → 落盘
     拉起 step 3 → 落盘
     ……
```

**step 只负责"我自己这一步"，落盘不落盘由它在完成时触发**；loop 只负责"要不要再来一步"。职责不混。

# 三、模块：loop（步循环 · 编排者）

## 1. 它是什么

**loop = 在一次回答内部，反复拉起 step 的那个循环。**

"想一步 → 调工具 → 看结果 → 再想一步"，串起来就是 loop。

## 2. 边界（最容易搞混的一点）

> **loop 只存在于一次回答内部。它不是"一轮接一轮地做多个任务"。**

一次回答（一个 turn）进来，loop 在里面转；转完了，这个 turn 就结束了。**不存在"loop 跨越多个 turn"这回事。**（历史上曾有"多 turn 任务编排"，已于 2026-09-04 废弃——所有复杂度改在单个 turn 内部的 step 循环里生长。）

## 3. 循环里"只追加、不重装配"

这是 loop 的一个重要性质：

- **进入 loop 之前**：台子已经搭好（装配过一次）。
- **loop 每转一圈**：**不再重新装配台子**，只在已拼好的上下文物件后面**追加"这一步刚干完的事"**。

> 为什么？因为重装配 = 重新算预算、重新拼提示词，既慢又会让上下文"抖"。**一次装配、多步追加**，稳且省。

## 4. 循环里 LLM 有权随时"想起"

同一次回答内部，LLM 想到需要旧背景时，**随时可以调 `search_memories` 去查**——查什么、查几次，由它自己按需决定，系统不预先替它装一批。

> **为什么记忆改成"工具现查"？** 因为"每轮自动塞一批"塞不准——该想起的没想起、想起的又太多。改成工具后，LLM 自己知道"我现在缺什么"，去查比系统瞎猜准。代价是多花一次工具调用，换来的是记忆不再无脑占上下文。

## 5. loop 里的"目标锚定"

触发这次问答的那句输入本身，是整件事的**根**——**永不压缩**。因为 loop 里每个 step 都在朝它定义的目标推进，**目标不能被吃掉**。（首个回答预留已随多 turn 编排退役——锚点只保这句输入。）

# 四、模块：turn（问答闭环 · 最大完整单元）

## 1. 它是什么

**turn = 一次「用户输入 → 最终回答」。** 它有明确的开头（你的输入进来）和结尾（回答交付并收尾）。

**一个 turn 对应一个 `roundId`**——这是它在这套系统里的"身份证号"。

## 2. turn 内部有四个阶段

| 阶段 | 干什么 | 谁来做 |
|---|---|---|
| **回答前（Prepare）** | 装配台子：角色包 → 策略 → 上下文 | 种子编排器 |
| **回答中（Act）** | loop 反复拉 step，边想边做 | loop |
| **回答后（Reflect）** | 沉淀：生成记忆摘要、归档 | 后处理 |
| **收尾** | 交付最终结论，落盘 | 门面 |

## 3. turn 是一切的"生长点"

> **系统里几乎所有模块，都是 turn 三阶段的自然生长，而不是独立系统。**

- 要"看懂输入、装上下文" → 长出**角色包 / 技能 / 记忆召回**（回答前）；
- 要"多步行动" → 长出 **loop / 工具 / 任务表**（回答中）；
- 要"记住这次干了啥" → 长出**记忆摘要 / 归档**（回答后）。

这个视角很重要：**不是因为"我们要做记忆系统"才有记忆，而是"turn 干完需要沉淀"才自然长出记忆。**

## 4. 什么时候停

一次回答看几个信号，**哪个先到按哪个**：

1. **软上限**——空间一路替换/压缩，压到最后除了顶级锚点基本都变摘要了、摘要层也满了 → 系统主动注入"收尾信号"，让 LLM 收敛交付。
2. **循环迭代上限**（默认 **50**；**不是**旋钮表里那个 20，见 §九·4 的辨析）——一次回答内部不能无限地想一步调一次工具，到顶就收尾（防死循环烧钱）。角色包可用 `stepBudget` 覆盖；不声明或填 `0`，就走这个 50 的兜底（这条键**没有"不限"路径**，防死循环是有意为之）。
3. **自然结束**——任务干完了，LLM 交付就停。

**还有一个"还没开始就拦下"的判负**：你贴了一大段超长内容 → 系统装配前先算一遍，发现连"至少跑一段"都不够 → 直接提示"内容太大，建议放进文件读"，不硬跑（免得误报成"摘要满了"）。

## 5. 中途被打断怎么收场（两种，完全不同）

**第一种 · 运行时暂停（自愿，原地续跑）**
- 你点暂停、插句话、或 LLM 主动提问 → 这些是**"申请"**，不是硬切。
- 系统**等当前这一步做完，在 step 边界上介入**，不当场砍掉正在跑的 step。
- 介入后**还是同一个问答闭环**，内存里的一切都还在。你补句话或点继续，它**在原来的地方接着跑**。
- **这是唯一需要"续跑"的场景。**

**第二种 · 中止 / 断电（非自愿，补全收场）**
- 崩溃、断电、关程序 → **内存里的一切都没了**，"原地续跑"从物理上不成立。
- 所以系统**不试图恢复**。它做的事简单：**把这个没跑完的闭环，补全成一个完整的闭环身份**（标上"已中断"，有半截输出就一并附上），登记进会话历史。
- 于是它成了一段**普通历史**——下次打开接着聊，它和其他历史一样被装进上下文。

> **两种的唯一差别**：中止/断电的那一轮**没有记忆摘要**（它没走完收尾）。空间紧张时想把它换成摘要，换不了——跳过去交给现场压缩，或者干脆被裁掉。**不会因为"缺摘要"就卡住。**
>
> **为什么不做"跨程序恢复暂停态"？** 因为代码分不清"你是优雅暂停后关的程序"还是"断电时恰好停在暂停态"。既然分不清，就一律按最坏情况（断电）处理。这样模型最简单，也不会出现"程序偷偷帮你恢复了一个你不想要的暂停"这种意外。

# 五、模块：工具系统（内核出厂的能力库）

## 1. 它是什么

**工具 = 内核出厂带着的一套"本领"。** step 里那句"想一步 → 调工具 → 看结果"，那个"工具"就是在这里注册、在这里执行的。

第二层结构图里那一句"**工具注册表**"指的就是这一整节。工具的清单是一张**数组**（代码里叫 `BUILTIN_TOOLS`），增删工具只改这一处。它有个反直觉但很实用的规矩——**别在别处再抄一份清单**：抄的那份迟早跟真身对不上（代码注释里就栽过，写死"当初有 8 个"，实际早涨到十几个）。所以**下面的清单只是举例，完整名目以这张数组为准**。

## 2. 工具分三类

| 类型 | 有哪些（**举例，不是全集**） | 什么时候可见 |
|---|---|---|
| **始终可用** | 读写删文件（`read_file`/`write_file`/`delete_file`）、列目录 `list_dir`、搜记忆 `search_memories`、追溯摘要 `trace_summary`、问用户 `ask_user`、跑脚本 `run_project_script`…… | 永远在 |
| **条件性** | `web_search`、`web_fetch`、`run_code`、`search_project` | 宿主注入了对应 Provider 才出现（联网 / 代码执行 / 项目搜索） |
| **自定义** | 宿主用 `registerTool` 自己造的领域工具 | 宿主注册后 |

> **别拿上面这张表数数。** 工具数量会随版本增减，**抄一份名字到文档里必然腐化**——这个坑已经栽过两次：代码注释写死"当初有 8 个"（实际早涨到十几个），本文档也曾漏列 `list_resources` / `list_skills` / `register_work` 三个。所以这里只做**举例**帮读者建立直觉：**完整名目的唯一真身是 `BUILTIN_TOOLS` 数组**（`src/agent/builtinTools.ts`），增删工具只改那一处。
>
> 顺带一提：`compress_context`（压上下文）和 `ask_user`（问用户）虽然独立定义成常量，但它们**也在 `BUILTIN_TOOLS` 数组里被引用**，所以同样"永远在"。

## 3. 声明和执行分家

工具的定义和干活分开成两个文件：

- `builtinTools.ts`——只写**声明**：名字、描述、收什么参数。**这段"说明书"就是给 LLM 看的，也是这个工具的对外契约。**
- `toolExecutor.ts` / `builtinToolHandlers.ts`——写**执行**：真去读写文件、搜记忆、跑搜索。

分离的好处：LLM 只看到说明书，看不到实现；换实现不用换说明书。

## 4. 卡片不能添工具（呼应角色包那节）

再钉一次认知：**工具是内核的，不是卡片的。** 角色包只能"选用/声明"（卡里写"我要联网"），不能"创造"（卡不能自己发明一个新工具）。**自定义工具只有宿主（写插件的人）才有资格加**，入口就是 `registerTool`。所以"插卡"换的是行为方式 + 知识范围，本领清单是内核统一的——这跟角色包那章"卡不能带代码、不能造新工具"是同一条铁律的两面。

## 5. 一次工具调用走四步

LLM 说完"我要用某工具、参数是…"，系统按下面走：

1. **校验**：路径在白名单里吗？只读模式下这是写操作吗？——不规矩的先拦下。
2. **幂等检查**：同样的活是不是刚成功干过？干的又是"结果固定"那类 → 直接回喂上次结果，不白跑（也防重复写文件、重复提问）。读操作、副作用不可预知的，**永不跳过**。
3. **执行**：真去干活。**外部来的结果**（网页、脚本输出）先"净化"再给 LLM——剥掉控制字符和终端转义序列，超长截断。防的是一个坏网页把一堆垃圾或偷偷的指令塞进上下文。
4. **回喂**：结果放进上下文；前后几轮的工具结果只留最近几条，旧的被占位符顶替，防止工具结果把窗口堆爆。

> 审批（要不要弹"允许"）不在这一步——那是**宿主执行前检查**的事（见宿主 / 安全章）。内核只管"校验 + 幂等 + 净化 + 执行"。

## 6. 两道"节约"

- **预算联动**：项目搜索这类结果多的工具，**剩余对话预算越紧、单次返回条数越少**——从硬上限一路下探到兜底几条，防"查一大堆把窗口撑爆"。
- **单条长度上限**：读文件、读技能、读资源、注入的脚本输出，各有单条上限，超了就截掉加省略号。

## 7. 一句话

**工具 = 内核出厂的本领清单（声明 / 执行分家，三类来源），每次调用走"校验 → 幂等 → 净化执行 → 回喂"四步，靠预算联动和长度上限防爆窗口；角色包只能选用，宿主才能添。**

# 六、模块：上下文组装（装配台子）

## 1. 它是什么

**上下文组装 = 每次真正发给 LLM 之前，把"该给它看的东西"拼成一份完整的输入。**

## 2. 装哪三样

1. **常驻设定**——角色包填进来的东西（persona / rules / 技能 / 工具说明）。
2. **本轮你的输入**——就是这句话，**顶级锚点，独立划块，永不压缩**。
3. **完整对话记录**——从最近往回装，能装几轮装几轮；**第一条问答必然在场**。

## 3. 预算不是"固定几轮"，是"现算的"

桌子大小 = **模型自己的上下文上限**（你在 LLM 配置里填的数，不填按 120K 兜底）。系统**不数轮**，而是用公式现算：

```
1. 先扣掉给模型回答留的一份（不然它没地方写答案）
2. 再扣掉常驻设定的固定开销（persona / rules / 技能 / 工具说明）
3. 再划走"你这句输入本身"（顶级锚点，永不压缩）
4. 剩下的九成，才是"最近对话"能装的空间 —— 能装几轮算几轮
```

> **所以轮数是算出来的结果，不是规定。** 窗口大装得多，窗口小装得少。这就是"不能拿固定轮数（比如'最近 20 轮'）当限制"的根本原因。

## 4. 撑爆了怎么办（三级空间管理）

空间不够时，按**严格先后顺序**自我维护：

**第一级 · 替换（系统自动，几乎零成本）**
- 每个走完收尾的闭环都存了一条摘要。
- 空间不够时，系统自己**按"最早的先换"**，把最旧的一轮对话正文，换成它自己那条已存好的摘要。
- **这是系统机械动作，不用 LLM 出手。** 注：若上下文被硬截断过（中间被剪掉重排），替换会**暂时歇手**——因为这时"哪轮对哪份摘要"的账目容易对乱，宁可不换。

**第二级 · 压缩（没现成摘要可换时，LLM 才上）**
- 作用对象：**还没有摘要可换的东西**——一次回答中途还没收尾的 step 现场、超大号工具结果、**以及被中止/断电打断的那一轮**。
- 先把超长工具结果悄悄换成一句话占位（**微压缩**）。
- 还不够，LLM 主动调**压缩工具**现场压成一条**临时摘要**——**这次回答一结束就扔掉**，进不了记忆库。

**第三级 · 裁掉（压不动就丢）**
- 连现场压都不划算 → 由**预算裁切**直接丢，从上往下裁，只保最近的一批。
- **第一轮问答永远不被裁。**

> **一句话分清楚**：能换的用现成摘要**替换**；没得换的（含中断轮）LLM 现场**压缩**；都压不动了直接**裁掉**。
>
> **⚠ 别混淆两种"摘要"**：这里说的**压缩摘要**是**临时产物**（本轮用完就扔）；**真正的记忆摘要**是闭环收尾后系统沉淀的那一条（见记忆模块）。**两者不是一回事。**

## 5. 互斥：不在上下文里出现两遍

工具召回记忆时，会先把**"已经在场的东西"**剔掉。所谓"已经在场"包含三类：

- **正文还在桌上的那几轮**（你眼前看得到）；
- **已被换成摘要的那些轮**（正文撤了，但摘要摊在桌上）；
- **正在进行的这一轮**（话刚进库、还没摆上桌那一瞬）。

> **（2026-09-10 已收口）**：早期实现拿的是"**最近 20 轮**"这个**近似值**——窗口大会漏剔、窗口小会多剔。现改成**精确名单**：直接问"桌上此刻实际摊着哪几轮"。**意图没变，是代码从"近似"回到了"精确"。**

## 6. 会不会撑爆？不会（硬闸）

每次真正发给模型之前还有一道**硬闸**：只要总量超过窗口，就从最近往回装、把中间剪掉，硬压到窗口的九成（留一成给回答）。

**唯一的例外**：你把上下文上限填得比模型真实上限还大。系统按你填的数算，**不替你兜底**（有意为之：你对自己填的参数负责）。

# 七、模块：记忆系统（可查询的资源）

## 1. 它是什么

**记忆 = 沉淀下来的"这次干了啥"，跨会话可查。** 它是 **turn 收尾的自然产物**，不是独立系统。

## 2. 怎么沉淀

- 一次问答闭环结束 → 进入收尾 → **产出记忆摘要**（一两句这个任务干了啥）。
- **一个闭环一条**；一次回答内部的每个 step **不单产记忆**（避免历史垃圾）。
- **中止/断电收场的那一轮不产摘要**（没走完收尾）——这就是"唯一差别"。
- 摘要有**取代机制**：同一会话里新摘要和旧摘要高度重合 → 旧摘要被标"已取代"（**打标记，不是删除**）。

## 3. 怎么取用：工具现查（不是自动注入）

这是记忆模块 2026-09 的**范式切换**：

- **旧做法**：每轮自动塞一批记忆进来 → 塞不准（该想起的没想起，想起的又太多）。
- **新做法**：记忆变成**可查询的资源**，LLM 需要时自己调 `search_memories` 去查。

> **为什么不预装？** 因为"现在需不需要记忆、需要哪条"，只有 LLM 在处理这个具体问题时才知道。系统替它猜，只会猜错。

## 4. 检索之后会做什么

- **命中即刷新"最近使用时间"**：被查到 = 被想起 = 强化（对齐人类记忆隐喻）。查询是低频的，不会造成"越查越热"的自强化。
- **互斥过滤**：已经在上下文的轮次，其摘要不会被重复查回（见上下文组装模块 §5）。

## 5. 记忆治理：取代 + 越用越重要

- **取代（supersede）**：写新记忆时，若与旧的重合，旧的被标记取代。
- **强化（boost）**：越常被召回，越重要。
- **衰减已移除**：不做"记忆随时间变淡"——因为"多久没被想起"度量的是"冷度"，不是"即将消失"。

# 八、模块：记忆检索（怎么查得到）

## 1. 一句话：检索是"工具现查"，不是"自动塞"

记忆系统讲了"存"和"取代"，这一节讲另一半——"**查**"。前面说过范式切了：**不再每轮自动塞一批记忆，而是 LLM 需要时自己调 `search_memories` 去查。** 这一节回答"它到底靠什么查得到"。

## 2. 两条通道，各查各的

为了不"该想起的想不起"，检索走**两条并行的通道**，再合起来：

- **语义通道**（向量库）：把记忆和你的问题都变成"高维坐标"，找空间上离得近的。好处是**能理解意思**——你问"上次那个性能 bug"，它能顺带捞起"响应慢"那条。它依赖两样东西：向量存储（`vectorStore`）+ 把文字变成向量的嵌入能力。
- **关键词通道**（索引全文）：按字面词条命中。好处是**不含糊**——你要精确到某个词，它一定在。

> 文字匹配马大哈（同义不同字），向量匹配不精确（意思像但词根本不同）。**两条互相补。** 语义通道没配好 / 跑失败，**自动退化成只剩关键词**——功能不瘫，只是"贴心度"下降。

## 3. 怎么合成一份结果（融合排序）

两通道分别先捞**多一点**（按最终条数 ×2），合并去重后，按这个顺序筛一遍：

1. **先扔"已被取代"的**：同会话里被新摘要顶掉（superseded）的旧摘要，不作为当前事实返回（旧料还能手动追溯原文，见第 5 条）。
2. **再扔"已经在眼前"的**：正文还在桌上、或摘要已摆上桌的那些轮，它们的摘要不再重复查回来（互斥，跟上下文组装章 §5 是同一件事）。
3. **最后按"语义贴合度"从高到低排序**，取前 N 条。

> **排序只认语义贴合度**。每条命中带着"最近什么时候被用过"（accessedAt）——这是**提示字段，不是排序依据**。因为"多久没被想起"量的是冷热度，不是重要性；时间只提示，主次由 LLM 结合手头任务判断。

## 4. 两条路子：宽搜 vs 严搜

`search_memories` 带个 `mode` 参数：

- **match**（默认）：几个关键词，**任一个**命中就算。
- **near**：几个词**必须都在**才算（要在同一条件里组合时用）。

## 5. 查到了干嘛：先粗筛，再精取（别一把全拉）

检索返回的是**预览**（每条截到 ~120 字符 + 相似度 + 最近使用时间）——这是"粗筛"，让 LLM 先看对不对味。真正要看完整，再调 **`trace_summary`** 用命中项附带的"会话 + 轮次"坐标，去取那段原文。

> **为什么两步走？** 一次拉太多会爆窗口。先看预览确定要不要深挖，才精取那几条。round-summary 命中时，工具会直接附上它的会话/轮次坐标，`trace_summary` 拿过去就能用，不用 LLM 自己解析。

## 6. 命中即"被想起"

任何查询命中一条，就把它的"最近使用时间"刷新成此刻——模拟"被想起 = 被强化"。这是低频操作，不会变成"越查越热"的死循环。

## 7. 一句话

**记忆检索靠"语义向量 + 关键词"双通道并跑、按语义贴合度融合排序（先扔被取代的和已在眼前的），只回预览让 LLM 粗筛，要看完整再经 trace_summary 精取；命中即刷新最近使用时间。配不上向量就自动退化成纯关键词——能用，只是不那么贴心。**

# 九、模块：角色包（插卡）

## 1. 它是什么

**角色包 = 一张可以插的卡。** 它就是**一个文件夹**（放在 `role-packs/` 目录下），可以独立制作、拷贝、流通——你把文件夹发给别人，别人放进目录，就装上了一张新卡。

## 2. 卡里装什么（三样，全是"数据"不是"代码"）

1. **描述性内容（最重要、唯一必需）**——这个角色是谁（`persona.md`）、守什么规矩（`rules.md`）、会哪些技能（`skills/`）。**纯文字**，是你写给它的人设与知识。
2. **行为策略键（可选，一整套现成旋钮）**——调它的"脾气"：工具能不能写文件、一次回答最多想几步、回答多大、温度多高、要不要自审查……**这些键内核都预先定义好了，有参考范围，都有兜底值**。
3. **能力声明（可选，只是"声明"）**——比如"我需要联网搜索"。**只是告诉系统"我想用这个能力"，不是自带一个新能力。**

> **关键澄清（别误会成"插卡 = 装新工具"）**：**角色包不能带代码，也不能自己造新工具。** 它能做的只有两件事——**①换内容**（人设/规矩/技能文档）；**②调旋钮**（在内核已提供的键里选）。工具本身（读文件、搜网页、跑脚本……）都是**内核出厂就带的**，卡片只能"选用/声明"，不能"增添"。
>
> 所以插卡的准确意思是：**同一个内核，换一种"行为方式 + 知识范围"**，而不是换一套新本领。

## 3. 最省事的卡：啥都不设置也能用

**一张卡可以什么都不设置**——不写任何策略键，只写描述性内容（甚至只有 persona），照样能插、能用。因为：

- 每个策略键都有**兜底值**：不设 `temperature` 就自动用默认 0.7；不设步数上限就用默认值。**缺什么补什么，不会因为没设置就报错。**
- 唯一的"必填"只有卡的**名字**（`name`）——身份证，不能没有。

> **舒服的制作体验**：想做个新角色，**先只写一段人设文字就够了**，插上去马上能用；等发现它"话太多 / 太快下结论 / 老爱问问题"，再回头调对应旋钮。**从最简的卡开始，按需要慢慢加旋钮。**

## 4. 旋钮一览（都有范围 + 兜底值）

| 什么时候管 | 管什么 | 例子（默认值） |
|---|---|---|
| 回答前 | 要不要先跟你确认理解、摘要记什么角度 | 理解确认默认**关** |
| 回答中 | 能不能动工具、**单轮工具调用**步数上限、回答多大、温度、路由 | 单轮工具调用步数上限默认 **20**、温度默认 **0.7**、回答上限默认 **4096** |
| 回答后 | 要不要自审查、要不要沉淀摘要、要不要追问 | 自审查默认**关**、摘要默认**开** |
| 全局 | 整轮 token 上限、**循环迭代上限**（`stepBudget`，就是 §四·4 那个 50）、出错怎么办、什么时候主动问你 | 出错默认**重试**、主动提问默认**最多 3 次** |

> 每个键都是**在预定义选项里"选一个"或"填一个范围内数值"**——角色包做的是"选择"，不是"定义"。
>
> **⚠ 别把两个"步数"搞混**（名字像，但是两个键、两个值）：
> - **单轮工具调用步数上限**（本表，默认 **20**）= 一次工具调用批次里最多调几次工具；
> - **循环迭代上限**（见 §四·4 停止信号，默认 **50**）= 一次回答内部 loop 最多转多少步，角色包不声明时走这个兜底。
>
> 「全局」那行的**整轮 token 上限**默认值为 `0`，语义是**不设限**（不是 0 个 token）；它是软上限，只有声明值小于模型上下文窗口时才会触发。

## 5. 插卡的具体链

```
你把文件夹放进 role-packs/ 目录
        ↓
宿主启动时扫这个目录（内置卡 + 用户卡，两处都扫）
        ↓
内核读取 manifest.json + persona.md + rules.md + skills/
        ↓
"常驻设定"就被这张卡填好了
        ↓
这次对话里，它就是这张卡定义的那个角色
```

> **两张来源**：**内置卡**（跟着程序一起来的）+ **用户卡**（你自己放进用户目录的）。两者平级，都能用。

## 6. 组队（小组会议）—— 诚实定界

多张卡可以组成一个"小组"，指定一个组长 + 若干组员。发起"小组会议：主题"时，系统预置一个流程骨架（组长开场 → 每个组员各说一步 → 汇总），**每一步切换到对应组员的视角**（相当于临时插上那张卡）。

> **但要说清楚**：目前"组队"**就只做了这一件事**——让不同角色的文字视角轮流上场分析问题。没有更复杂的编排、没有投票、没有交叉质询，就是"轮流以各自的文字规范发言 + 组长收尾"。**别把它想成一套多智能体协作引擎，它只是"文字视角轮播"。**

## 7. 尚未定义、先记录在案

插卡这条链还有两个边界没画，**目前按"先不做、先记下"处理**：

1. **卡的权限信任模型**：卡片可以"声明"要什么能力（如联网），但"声明 ≠ 授予"——谁批准、什么时候批准，还没定。
2. **卡的版本契约**：卡片是独立制作的，将来内核的键若变动，老卡怎么办（兼容 / 报错 / 自动迁移）——还没定。

> 这两条都是**卡片生态变大之后才会真正咬人**的问题。现在系统尚未正式发布，**先记录，不提前设计**（避免为想象中的问题预支复杂度）。

# 十、模块：物理记录（东西存在哪）

## 1. 它是什么

前面说了那么多"存下摘要""补全成历史"，**这些到底落在磁盘哪里？** 说清楚，不然"断电不续跑"会显得悬空。

程序在**工作区**里建了一个隐藏文件夹 `.memora/`，所有持久化的东西都在这里：

```
.memora/
  rounds/
    index.json          轮次索引（id → 状态 + 引用计数）
    {roundId}.json      一个"问答闭环"一个文件，装它的完整数据
  sessions.json         会话清单：每个会话的标题 + 它包含哪些轮（只存"指针"）
  memories.json         记忆库：沉淀下来的记忆摘要都在这
```

## 2. 关键点

- **一轮对话 = 一个文件**。每个走完的闭环最终落成 `rounds/{roundId}.json`；轮与轮互相独立，不靠一个大文件串起来。
- **会话只是"指针列表"**。`sessions.json` 里一个会话只记"标题 + 这轮属于哪个会话"，正文都在各自的轮文件里。**所以删会话、改标题都很轻，不会动到正文。**
- **记忆单独一处**。`memories.json` 是记忆库，沉淀的摘要进这里。

## 3. 落盘时机：一边跑一边存

物理记录**不是等整轮结束才写一次**，而是**分两级**：

| 时机 | 写什么 | 效果 |
|---|---|---|
| **每推进一个 step** | 把这一步之前已产的过程合并进当前轮，写盘 | **崩溃最多只丢当前这一步** |
| **整轮结束** | 写入完整轮数据 + 记忆摘要 | 这一轮正式归档 |

> 这就是"**step 是真理源**"的物理体现：**是 step 的完成在触发落盘**，运行记录因此被"一步一格"地保住。

## 4. 一堵重要的墙：内存态 vs 落盘态

- **落盘的**（写到磁盘、关机也在）：走完的轮、会话清单、记忆库。
- **只在内存的**（程序一关就没了）：**正在进行的这一轮**，包括"你点了暂停"这个状态本身。

> **暂停态为什么不在磁盘里？** 因为它压根没被存下来。暂停只是"这一轮在内存里停了一下"——**程序还活着，它就在；程序一死，它就不存在了**。所以"断电就当普通历史接着聊"，不是系统**选择**不恢复，而是**它物理上无处可恢复**。这也是为什么不需要"断点续跑"——没有可续的那个点。

# 十一、模块：宿主（落地者）

## 1. 它是什么

**宿主 = 把内核"接上真实世界"的那一层。** 典型例子是 VS Code 插件。

## 2. 它负责什么

| 职责 | 具体 |
|---|---|
| **读写磁盘** | `.memora/` 的轮文件、会话清单、记忆库 |
| **渲染界面** | 对话面板、过程轨迹、任务板、占用指示器 |
| **连模型** | 提供 LLM 配置（地址 / 模型 / 密钥 / 上下文窗口） |
| **提供卡片目录** | 内置角色包目录 + 用户角色包目录 |
| **安全把关** | 文件白名单、执行前检查（拒绝/放行） |
| **按需注入** | 网络搜索、代码执行等"外部世界能力" |

## 3. 边界铁律：内核不认识"具体世界"

> **内核只认三样东西**：模型地址、模型名、密钥。**provider 怎么解析、用云端还是本地、默认值怎么填——全部归宿主。**
>
> 内核**不碰磁盘、不认界面、不知道你用的是什么编辑器**。这样换一个宿主（VS Code / 桌面端 / 别的），内核一行不用改。

**这也是"本地优先/隐私闭环"的落点**：宿主可以只接本地 LLM（如 Ollama），全程零网络——内核不关心，也就不会破坏这个选择。

# 十二、横向模块：会话状态与安全

## 1. 会话状态机（三态）

一次会话有明确的三种状态，流转规则严格：

```
RUNNING（跑着）
   ↕  用户/Agent/系统 可双向暂停恢复
PAUSED（暂停）
```

- **RUNNING ⇄ PAUSED**：正常暂停与恢复。
- **PAUSED → ERROR、ERROR → PAUSED 都不允许**（非法转换被拦）。
- **ERROR 态的语义**是"崩溃残留 → 恢复前强制校验"——但**当前产品流中没有自动产生者**，它是个保留态。

## 2. 安全护栏

- **文件白名单**：只允许在指定路径内操作。
- **只读 / 写操作 / 脚本执行**分档控制——内核按"只读模式"拦写操作，宿主经执行前检查决定拒绝或放行（3.0.0 起内核不再提供"审批"旋钮，"需审批"标签与回调已删除；要真实审批的宿主在自己的执行前检查里做）。
- **角色包内容红线检查**：对卡片文本做合规检查。

# 十三、横向模块：强关联群落（改一处 · 验一片）

## 1. 为什么要有这一节

前面把机器拆成零件一个个讲。但零件之间是**互相咬合**的——很多"功能"其实是横跨好几个模块的一条链。这一节反过来，把**强关联的模块握成几个"群落"**。

它对两类人都有用：

- **看热闹的**：看懂"这功能其实是好几位合作干成的"，不再以为记忆是一件、上下文是另一件的两码事。
- **要动手改代码的**（重点）：**你改了一个小模块，不该只测它自己——要沿着它所在群落的咬合方向，把关联点都验一遍。** 下面是每个群落的"改动→要验什么"清单。

> 群落图上两个方向要分清：**实线箭头** = 数据/调用流过；**虚线** = 契约/约束咬合（改了它，别处可能悄悄坏）。箭头写的是"谁在依赖谁"。

## 2. 群落一：问答种子链（step · loop · turn）

**成员**：step（§二）、loop（§三）、turn（§四）。这是用户点题里说的"种子"。

**它们怎么咬合**：
- **step 是原子**：一次"想 + 可选行动"，它干完就触发一次落盘——**运行记录的原子**。
- **loop 编排 step**：一次回答里反复拉 step，"只追加、不重装配"。
- **turn 装下 loop**：turn 的三阶段（Prepare/Act/Reflect）是所有其它模块生长的骨架，loop 只在 Act 阶段转。

**改动联动检查点**（改了其中一个，另外两个通常要一起回归）：

| 你改了 | 要连带验 |
|---|---|
| **step 的落盘时机/幂等键** | loop 是否仍"每步落盘"、turn 收尾归档是否重复写、断电恢复是否仍"只丢一步" |
| **loop 的编排/暂停/插话** | step 边界的气口——暂停、排队插话、`ask_user` 挂起是否还在边界上正确介入；预算触顶/步数到顶时插话会不会被静默丢弃 |
| **turn 的阶段划分** | Prepare 装配的东西是否喂进了 Act、Reflect 收尾是否吞掉 Act 产出的摘要——三阶段是挂在 turn 上的"生长点"，动它等于动所有挂件 |

## 3. 群落二：记忆生态（写·查·防重·落盘）

**成员**：记忆系统（§七，写/取代）、记忆检索（§八，查）、工具系统（§五，`search_memories`/`trace_summary` 入口）、上下文组装（§六，互斥与替换）、物理记录（§十，落盘）。

**它们怎么咬合**（这是用户点题的核心例子，一条完整的数据环）：
- **写**：turn 收尾（Reflect）沉淀记忆摘要 → 落进记忆库（物理记录）。
- **查**：LLM 调 `search_memories` 工具 → 记忆检索双通道 → 命中即刷新最近时间。
- **防重**：上下文组装在装配期会记录"哪几轮已在眼前"（互斥名单）→ 检索时用这个名单把已在眼前的摘要剔掉；同理，**空间管理把某轮正文替换成摘要后**，也会把它记进互斥名单，防它被二次召回。
- **回溯**：摘要命中/替换后，还能用 `trace_summary` 按 roundId 取回原文。

**改动联动检查点**：记忆是横跨五六个模块的链，最容易"改一头、断一头"：

| 你改了 | 要连带验 |
|---|---|
| **记忆的字段/schema**（比如改摘要的溯源字段） | search_memories 返回、trace_summary 追溯参数、装配期互斥名单、收尾沉淀——四处都要对齐 |
| **取代机制（superseded）** | 检索前置过滤是否把被取代摘要挡在 top-N 外；替换压实时是否仍取"当前未被取代"的摘要 |
| **物理落盘/归档/GC** | 记忆库查询、搜索命中、回收站联动"删除摘要即脱钩溯源"是否同步 |
| **search_memories 工具本身** | 语义通道是否还通、向量失败是否仍能降级到关键词、互斥名单是否正确吞掉眼前轮 |

## 4. 群落三：上下文空间生命线（装配 · 预算 · 压缩 · 工具结果）

**成员**：上下文组装（§六，装配）、工具系统（§五，结果回收）、预算（藏在装配章 §3）。

**它们怎么咬合**：
- 装配按**预算公式**现算"能装几轮"，预算决定窗口物理多大。
- 空间紧张时走**三级**：替换（拿已存摘要顶正文）→ 压缩（现场压临时摘要，收尾即弃）→ 裁掉。
- 工具结果的**占位**（`ResultReplacement`，压缩链二级）仍在这条线上——与装配共用"上下文视图"的一致性；**超长结果卸载已不挂本线**（2026-09-13 · 1b 起移至入口关 `appendToolMessage`，门前换鞋：原文从不进上下文，只留路径 + 预览 + 续读）。
- **LLM 私有工作笔记（情报区，Step 2）是一个额外注入块**：走尾部 system 消息、复用截断线淘汰，**不占装配预算**（对齐「预算/占用模型无记忆维度」锚点，不新增第 5 个预算维度）。

**改动联动检查点**：

| 你改了 | 要连带验 |
|---|---|
| **预算公式/窗口大小** | 装配能装几轮、搜索/列文件的"预算下探"档位、硬闸裁剪——窗口变化牵动所有"灌进上下文"的工具 |
| **压缩工具/三级空间管理** | "临时摘要收尾即弃"与"真记忆摘要进库"**不能混**（文档里反复强调的两张表）；被替换轮的正文本体、替换后摘要、残留占位符三者视图是否一致 |
| **工具结果回收策略** | 占位符是否只顶掉旧结果、最近几条是否都还在；入口关卸载（1b 起）：原文落盘 `.memora/outputs`、上下文只留「路径 + 预览 + 续读」，发送视图恒定不含原文，且 `read_file` 读回产物不再次落盘（不嵌套） |

## 5. 怎么用这张图

改代码前先问自己：**我动的这个模块，在哪个群落的哪条箭头上？** 顺着箭头的实线（数据流）验证数据还通不通，顺着虚线（约束）验证契约有没有被打破。三个群落之间有交叉（比如"上下文空间"用到"记忆生态"的摘要做替换），交叉点就是**首测对象**。

# 十四、一句话合起来

> **插一张卡（角色包：只有内容 + 旋钮，不带代码；最省事的卡只写人设也能用）→ 一句话进来 → 搭好台（常驻设定 + 你的输入[顶级锚点] + 尽量多塞的最近对话，首轮必在场；记忆不预装，需要时 LLM 自己查）→ 一次回答内部由 loop 反复拉 step（想一步→做一步→再看一步，只追加不重装配），每个 step 完成就落一次盘 → 空间满了三级走：替换 → 压缩 → 裁掉（首轮永在场）→ 该停时停（软上限 / 步数到顶 / 干完，输入太大则预先拦下）→ 中途被打断分两种：主动暂停就原地续跑（同一闭环，只在内存），崩溃断电就补全成完整闭环、下次当普通历史接着聊 → 每个走完的闭环沉淀一条真记忆 → 落盘进工作区的 `.memora/`（一轮一文件、会话存指针、记忆单独一处；暂停态只在内存，所以断电无处可续）。长会话反复用装配 + 替换自然运转，体验从"全原文"平滑退化成"摘要对话"。**
