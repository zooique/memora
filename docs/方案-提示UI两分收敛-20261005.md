## 二、对抗式审查：拍板②「超时自动确认」必须驳回

### 事实

| 链 | 超时 | 无响应结果 | 语义 |
| --- | --- | --- | --- |
| 确认 confirm（chatPanel.ts:1441-1453） | 30s | **拒绝**（fail-closed） | 不执行 |
| 提问 ask（chatPanel.ts:231 `ASK_TIMEOUT_MS = 120_000`） | 120s | **自动继续**（fail-open） | agent 自行往前走 |

两条链语义**不是不一致，是风险分级**：

- **ask 超时继续是安全的**——不回答，就什么都不执行，agent 空转继续。
- **confirm 超时若改成批准，就是把「执行副作用」的默认从「不做」翻成「做」**。

### 驳回理由

1. **安全模型反转**：命令确认的 `deny` 档是命令字面量护栏（`classifyCommand`）。超时自动批准 = 用户离开 90 分钟后，agent 自动执行任意命令（`rm -rf`、`git push --force`、装包）。
2. **失败静默**：自动批准后用户不知道批准了什么，也不知何时批准的。fail-closed 至少留一条 error notice。
3. **因果错配**：你要解决的真问题是「用户看不见卡 → 被自动拒绝 → 功能像坏了」。根因是 **S1（卡错装在滚动容器内）**，不是超时太短。修 S1 后 30s 极少触发。**用放宽安全门去掩盖 UI bug，是把病灶包起来。**
4. **「完全阻塞不好」是伪命题**：Claude Code / Cline / Roo 的命令确认**就是不超时**，agent 挂起等。挂起成本 = loop 暂停、不烧 token、不占资源，用户随时可停止。这是安全闸门的正常语义。

### 定案：采纳 A，时长 **30 分钟**（用户 2026-10-05 重拍）

| 项 | 取值 |
| --- | --- |
| 语义 | **维持 fail-closed**（超时 = 拒绝，不反转） |
| 时长 | 30s → **30 分钟** |
| 倒计时 | 最后 60 秒进入倒计时显示「还有 N 秒将自动拒绝」 |
| **前置条件** | **必须同批补 S8**（面板不可达立即拒绝），否则见下 |

**为什么 30 分钟可以**：fail-closed 下，超时长度**不带来任何安全风险**——风险来自「超时后自动做什么」，不是「等多久」。拉长时长只增加「loop 挂起更久」这一项低代价。

**为什么 30 分钟必须配 S8**：当前 `onDidDispose`（chatPanel.ts:833-835）只清 `_editorSub`，**不清 `_pendingWriteConfirmations`**。30 秒时不显眼；换成 30 分钟 = 用户关掉面板后 agent 卡满 30 分钟才释放。补上 S8 后，僵尸等待从「30 分钟」砍到「0」，**安全与可用性同时变强**。

**为什么不统一 ask 的 120 秒**：不统一是对的（风险分级不同，见上表）。差距拉大后更需在文档登记为有意设计——已登记为 S6。

## 三、形态评估：占位式 vs 遮罩式（基于现有设计）

| 约束（现有设计事实） | 占位式 | 遮罩式 |
| --- | --- | --- |
| 面板三层结构（chatPanel.ts:3715「消息区 → 活动区 → 输入区」） | 落在既有「活动区」层，**零新增层级** | 需打破三层模型 |
| z-index 分层（消息区 1 / 输入区 20，chatStyles.ts:32-34） | 不动 | 需 21+ 层，与 treedd 下拉菜单层级冲突风险 |
| 已验证的锚定先例（`scrollToBottomBtn` 锚 `#inputBar` 顶边，chatPanel.ts:3821-3826，有守卫测试） | 同款锚定，可直接复用 | 无关 |
| 单点裁决机制（StatusDock `resolveDock`，chatView.ts:2499） | 可复用同一套裁决 | 需另起浮层 + 焦点管理 |
| 决策时回看上下文（命令是什么、目标路径对不对） | 消息区照常可读可滚 | 自断一臂 |
| 无障碍成本 | 近零 | 手写焦点陷阱 + Escape 逃生 + `aria-modal` |
| 已存在的同形态资产（`#clarifyBar` 就是输入区上方占位） | 现成 | 无 |

**结论：占位式。** 不是审美偏好，是改动面小、不引入新层级与新竞态。

> 需澄清：「覆盖输入区」在主流里是两种实现——Claude Code CLI（终端无分层）用**遮罩**；Cline / Roo（VS Code 侧栏，与 memora 同载体）用**输入区上方动作区 + composer 禁用**。memora 属后者，取占位式。

## 五、设计契约（SSOT）

> 🔴 **本段已按 A1 修正重写（2026-10-05）**。原契约基于「新增 `resolvePromptSlot()` 独立裁决器」，
> 该裁决器在 A1 审查时被否决（与 `resolveDock()` 争同一插入锚点 = 双源）⇒ 下列机制名**均不存在于代码**。

- **裁决单点（现行）**：**不新增裁决器**。A 类作为最高优先级 entry（`confirm`，priority 10）注册进既有 `resolveDock()`，复用其 `active` / `fixed` / 主位 / 收纳机制。各载体只上报 `setDockActive(id, active)`，**禁直写 `hidden` / `insertBefore`**（散写即回到堆叠现状，StatusDock 之前就是这么烂的）。
- **队列真源归 host（现行）**：pending 确认队列真源是宿主的 `_confirmQueue` + `_pendingWriteConfirmations`（Map）与 `_pumpConfirmQueue`（唯一推送点）。**webview 不自持队列**，只投影 host 逐条推的 `write_confirm_request`，裁决回传 `write_confirm_answer`。webview 自持 = 双源漂移。**（原契约的 `write_confirm_queue` 快照消息未做——FIFO 串行下 webview 只需知道「当前有卡」，不需要队列全貌。）**
- **输入锁单点（现行）**：**`setComposerReplaced(boolean)`**（唯一写入点，作用于 `#inputWrap`），由 `resolveDock()` 调用。**（原写的 `setInputLocked` 不存在。）** 触发条件 = 存在 `priority === CONFIRM_PRIORITY` 的活跃 entry。
  ⚠️ **已知欠账（2026-10-05 登记）**：`#inputBar` 的 `hidden` 另有三处裸写（超时清理 / clarifyBar 兜底进入 / 兜底退出），与本单点**并存**。二者粒度不同（`inputBar` 整体 vs `inputWrap` 内层），当前未撞车（ask 态与confirm 态实际互斥），但**互斥性无代码保证**——详见 `tasks/待完成任务.md` 对应条目。
- **ask 收口（现行）**：**#3 ask 不进 A 类槽**。A4 定案「ask 维持内联」（`renderAskInline` 挂消息流提问块下方，问题紧挨上下文才有意义）；`#clarifyBar` **保留为无 assistant 锚点时的异常兜底**（P3 已取消注销，见下表）。**「二者互斥」是拍板时的期望，非代码保证。**

### 方法论教训（本轮血训，应沉淀进 `.trae/rules`）

1. **「修复后仍复现」时，先写探针观测，再改代码。** 本轮连续两次靠推理定位（"我以为是同步关卡" → "我以为是 chip 挤卡"），两次都改在真问题之外。探针（`MutationObserver` + 关键节点相邻性断言）10 分钟定位第二源头，胜过三轮推理。
2. **探针的边界要写在结论里**：jsdom 无布局引擎、无重排、无重绘 ⇒ 探针只能证「DOM 位置没变」，**证不了「眼睛看到的没变」**。因此「探针全绿」≠「用户看到的是对的」，不可据此宣称修复完成。
3. **真机现象描述要先核对可行性再采信**：本轮 round 记录里三条 `tool_result` 间隔仅 8ms（物理上不可能是三次点击），初判「用户逐张点了三张」被数据否证 —— 真实机制是内核三工具并发等 `Promise.all`，卡审完后结果一次性广播。**先问「这组数据支持这个结论吗」，再往下走。**
4. **相邻性判据写完必须用真实 DOM 验证方向**：`head.previousElementSibling !== anchor` 与 `anchor.previousElementSibling !== head.el` 在有隐藏条夹入时**同时成立**，写反则恒假、修复静默失效。写这类判据前先 `dump` 一次真实 DOM。
5. **验证方法本身也要怀疑**：查bundle 是否含新代码时，正则漏配成员表达式（`head.el` 的 `.`）导致误判「产物没更新」，差点错手。**验证方法有缺陷时先怀疑方法，别急着下结论。**
6. **「静态断言全绿」不等于「行为正确」**（P4 血训）：`insertBefore` 搬一个**已在位**的节点，最终 DOM 完全相同 ⇒ 任何终态断言都抓不到「有没有搬」。本轮实测：把免重排判据退化成「无条件重排」，静态位置断言**全绿**。必须另写**行为观测**（拦截 `insertBefore` 数调用次数）才锁得住。
7. **「读源码推演」超过三轮就该上探针**（P4 血训）：P4 落地时我对着探针输出连续改了 3 次断言方向（`nextElementSibling` ↔ `previousElementSibling`）全改错——因为探针是从 `inputBar` 往回打印的，箭头方向天然反直觉。**判据方向不能靠推理确认，必须用探针的 `prev`/`next` 双向值一次打全。**
8. **HTML 模板注释里写代码会炸模板**：注释里出现 `textContent = ''` 时，`''` 里的内容让 `<!--` 注释**提前闭合**，TS 直接报 `TS1005`。写模板内注释时避开 `--` 序列。
9. **否决一个决策后必须回扫所有引用它的地方**（2026-10-05 补审血训，本仓最贵的一类伤的第四发）：A1 否决了「新增 `resolvePromptSlot()` 独立裁决器」并改为「A 类注册进 `resolveDock`」，但**只改了提出处（A1 表格），没改引用处（§四定案 1/2/3 + §五整段契约）** ⇒ 方案文档里长期描述着 `setInputLocked` / `write_confirm_queue` / `setPromptActive` 三个**代码中零存在**的机制，后人按图施工必然找不到。**第三处更隐蔽**：A1 表格末句「dock 插入锚点由 `inputBar` 改为 A 类槽」同样未落地——A 类槽就是 `resolveDock` 里的一个 entry，**不存在独立锚点**，真源仍是 `const anchor = inputBar`。
    **纪律**：①决策被否决/改名/降级后，`grep` 该决策的**全部出现**（正文 + 表格 + 契约段 + 阶段表 + 台账 + 代码注释），**一次改齐**；②**「已落地」的说法要回核引用它的每一处**，提出处改了而引用处没改 = 制造第二个真相源；③这是 `single-truth-source-mindset.md`「措辞折叠」纪律的**结构版**——措辞折叠是读者信了测试不拦，结构残留是**后人照着文档施工会直接做错**。
10. **「渲染结果」不能当「事实」喂给判据；累计读数不能当「新闻」**（2026-10-05 P10B 血训，**连续三版才修对**）：
    ① v1 判据 `!activityUnread && activityMetrics.hidden` 把**渲染结果**（`hidden` 只置 false 从不复位）当事实 ⇒ 首次 metrics 后详情区恒显形，「读完即收起」在 metrics 路径失效；
    ② v2 改喂「渲染全文快照 diff」**仍然错**——宿主 `postMetrics` **每轮都推**，而 `llmCallCount`/token 是**累计计数、每轮必涨** ⇒ 全文每轮不同 ⇒ 退化成「每轮弹一次」，换壳不换病；
    ③ v3 改诊断信号量，却误收**安全审计总数 total**——当日下午沿真机触发链复核再实锤：内核对白名单**正常放行也发 `path-allow`**，宿主 total 无条件累加 ⇒ AI 每轮读文件 total 必涨，与 llmCallCount **同病**，变异测试因构造数据没让审计逐轮涨而漏网；
    ④ **定案（v3.1 · 诊断信号量）**：未读事实 = `metricsSignalOf(msg)`——只收「出了事 / 配置变了」的量（系统提示指纹、工具失败数、截断数、未解析工具意图数、安全审计**拒绝数 denied**）；累计计数、token、budget、trace、**审计 total** **不入信号**；展开中到达的新信号当场消费（seen=latest），收起后不反标未读。
    **🔴 判据的长期正确形式**：未读只由**诊断信号变化**驱动——渲染结果（`hidden`）、推送事件（「推过」）、仪表盘读数（累计计数）三类**永不入信号**。一个量能不能入信号，判据是「**正常轮次它会不会变**」（fail/denied 只在异常时涨，可入；total/计数每轮必涨，不可入），不是「累计 vs 瞬时」的字面归类——v3 就死在按字面把 total 当「安全事件量」。读数回答「现在是多少」，新闻回答「出了什么事」，两个维度不许折叠。**改这段代码前先看这条。**
11. **「改完 347 用例全绿」不等于覆盖到了**：P4 补审时既有 metrics 用例（6+ 条）**全绿**，但它们只断言 `metrics.hidden === false` 与 `textContent` 内容，**无一条断言 `activityDetail.hidden` 在 metrics 路径上的行为** ⇒ 全绿是**覆盖缺口**而非「无问题」的证据。**纪律**：修「某条路径的显隐/行为」时，grep 现有用例里**有没有断言那个路径上的那个属性**；只有断言了别的属性 ⇒ 该路径根本没被测。
12. **jsdom 不渲染样式表：CSS 互斥类缺陷它天生瞎，旧用例还可能把 bug 锁成契约**（2026-10-05 P10C 血训）：details 展开（`open=true`）时判据仍写 `hidden=true`，真机全局 `[hidden]{display:none!important}` ⇒ 「点开即消失」；jsdom 不加载样式 ⇒ 全绿，且既有用例在 expand 后**断言 `hidden=true`**——把真机 bug 当正确行为锁死。**纪律**：①涉显隐（`hidden`/`display`/类互斥）的修复，验收必须含真机或浏览器探针的**计算样式**断言，jsdom 绿只证明 DOM 属性被写过；②改判据时先 grep 旧用例的**断言方向**——它可能正锁在旧错误行为上，「全绿」也可能是错误被固化，不是保护。

  转 `console.error`，不新增错误通道。

### 已知取舍（如实登记，非隐瞒）

- **T1 切换微闪** →✅ **已解决（P7）**。真机复现后定位根因为「webview 同步关卡 + 宿主异步推下一条」的
  两帧时序差，非「多张卡」本身。改为点击不收卡、等待宿主指令（同 DOM 覆盖渲染）⇒ 结构上
  不存在空档。**附带修复 F1**：原实现下队列无下一条时卡片会带已裁决内容滞留，用户再点一下
  ⇒ 宿主 `pending` 已 delete ⇒ 第二个 answer 静默丢弃（用户视角「点了没反应」）；等待态的
  `disabled` + `writeConfirmAwaitingNext` 双重early-return 消解。
- **T1'曾考虑但否决的方案：复合选项卡**（用户提议「做成可切换 tab，点第一个自动切第二个 +
  按钮可点上一个重新选择」）。**三条否决理由**：①**治不了病根** —— 选项卡同样要「关旧的、
  开新的」，闪烁照旧；②**安全倒退** —— 画 tab 头必须同时渲染三条命令文本 ⇒ 用户审第1 条时
  第 2、3 条内容已摊在屏幕上，违背 fail-closed「未审内容不该可见」；③**假撤销** —— 上一条
  已执行（真机实测 tool_result 在点第三条前就回了），「切回重选」物理上不可能实现，只能做
  成假动作；要真做对须引入「整批裁决后统一执行」的批量事务（新高危新功能，非本轮范围）。
- **T2 中止入口**：A 类替换 composer 后，停止/暂停键随 `#inputWrap` 一并让位。逃生链是
  面板恒带的「拒绝」（拒绝即脱身，随后 composer 恢复、停止键回归）。若真机出现「想直接
  中止整轮却只能逐个拒绝」的阻塞，再在面板内加三级动作，不为假想需求预支协议。
- **T3夹具双源未治**：测试夹具 `dispatch(msg: unknown)` 签名无类型约束，14 处
  `write_confirm_request` 用例中 7 处不补 `timeoutMs`（编译期抓不到）。治它要给 dispatch
  加协议类型约束，**波及 683 处调用**，与 P6 同批立项，本轮不冒进。
- **T4 假绿防线只覆盖 CSS 文本层**：新增守卫读的是生产 `chatStyles.ts` **源码文本**，
  可抓住「兜底规则被删/改名」。但若有人改的是**别处**引入的样式（内联 style、其他
  样式文件、webview 内 `<style>`），守卫**抓不到**。彻底解法是让测试环境真加载样式表
  （如引入 `getComputedStyle` 实测），代价大且 jsdom 对 cascade 支持不全 —— 登记为
  已知防线边界，不假装覆盖完整。
