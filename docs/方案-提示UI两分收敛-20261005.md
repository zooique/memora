## 二、对抗式审查：拍板②「超时自动确认」必须驳回

### 事实

| 链 | 超时 | 无响应结果 | 语义 |
| --- | --- | --- | --- |
| 确认 confirm（chatPanel.ts:1441-1453） | 30s | **拒绝**（fail-closed） | 不执行 |
| 提问 ask（chatPanel.ts:231 `ASK_TIMEOUT_MS = 120_000`） | 120s | **自动继续**（fail-open） | agent 自行往前走 |

两条链语义**不是不一致，是风险分级**：

- **ask 超时继续是安全的**——不回答，就什么都不执行，agent 空转继续。
- **confirm 超时若改成批准，就是把「执行副作用」的默认从「不做」翻成「做」**。

### 驳回理由

1. **安全模型反转**：命令确认的 `deny` 档是命令字面量护栏（`classifyCommand`）。超时自动批准 = 用户离开 90 分钟后，agent 自动执行任意命令（`rm -rf`、`git push --force`、装包）。
2. **失败静默**：自动批准后用户不知道批准了什么，也不知何时批准的。fail-closed 至少留一条 error notice。
3. **因果错配**：你要解决的真问题是「用户看不见卡 → 被自动拒绝 → 功能像坏了」。根因是 **S1（卡错装在滚动容器内）**，不是超时太短。修 S1 后 30s 极少触发。**用放宽安全门去掩盖 UI bug，是把病灶包起来。**
4. **「完全阻塞不好」是伪命题**：Claude Code / Cline / Roo 的命令确认**就是不超时**，agent 挂起等。挂起成本 = loop 暂停、不烧 token、不占资源，用户随时可停止。这是安全闸门的正常语义。

### 定案：采纳 A，时长 **30 分钟**（用户 2026-10-05 重拍）

| 项 | 取值 |
| --- | --- |
| 语义 | **维持 fail-closed**（超时 = 拒绝，不反转） |
| 时长 | 30s → **30 分钟** |
| 倒计时 | 最后 60 秒进入倒计时显示「还有 N 秒将自动拒绝」 |
| **前置条件** | **必须同批补 S8**（面板不可达立即拒绝），否则见下 |

**为什么 30 分钟可以**：fail-closed 下，超时长度**不带来任何安全风险**——风险来自「超时后自动做什么」，不是「等多久」。拉长时长只增加「loop 挂起更久」这一项低代价。

**为什么 30 分钟必须配 S8**：当前 `onDidDispose`（chatPanel.ts:833-835）只清 `_editorSub`，**不清 `_pendingWriteConfirmations`**。30 秒时不显眼；换成 30 分钟 = 用户关掉面板后 agent 卡满 30 分钟才释放。补上 S8 后，僵尸等待从「30 分钟」砍到「0」，**安全与可用性同时变强**。

**为什么不统一 ask 的 120 秒**：不统一是对的（风险分级不同，见上表）。差距拉大后更需在文档登记为有意设计——已登记为 S6。

## 三、形态评估：占位式 vs 遮罩式（基于现有设计）

| 约束（现有设计事实） | 占位式 | 遮罩式 |
| --- | --- | --- |
| 面板三层结构（chatPanel.ts:3715「消息区 → 活动区 → 输入区」） | 落在既有「活动区」层，**零新增层级** | 需打破三层模型 |
| z-index 分层（消息区 1 / 输入区 20，chatStyles.ts:32-34） | 不动 | 需 21+ 层，与 treedd 下拉菜单层级冲突风险 |
| 已验证的锚定先例（`scrollToBottomBtn` 锚 `#inputBar` 顶边，chatPanel.ts:3821-3826，有守卫测试） | 同款锚定，可直接复用 | 无关 |
| 单点裁决机制（StatusDock `resolveDock`，chatView.ts:2499） | 可复用同一套裁决 | 需另起浮层 + 焦点管理 |
| 决策时回看上下文（命令是什么、目标路径对不对） | 消息区照常可读可滚 | 自断一臂 |
| 无障碍成本 | 近零 | 手写焦点陷阱 + Escape 逃生 + `aria-modal` |
| 已存在的同形态资产（`#clarifyBar` 就是输入区上方占位） | 现成 | 无 |

**结论：占位式。** 不是审美偏好，是改动面小、不引入新层级与新竞态。

> 需澄清：「覆盖输入区」在主流里是两种实现——Claude Code CLI（终端无分层）用**遮罩**；Cline / Roo（VS Code 侧栏，与 memora 同载体）用**输入区上方动作区 + composer 禁用**。memora 属后者，取占位式。

## 四、定案

1. **A 类 · 决策面板**：位于 `#inputBar` 之前（既有的「活动区」层），**占位式**非遮罩；出现时 composer 禁用 + placeholder 改「等待你确认……」+ 发送键禁用；承载 #2 四类确认与 #3 主动提问，二者互斥（确认优先于提问）。
2. **B 类 · 状态条**：维持 StatusDock 既有裁决（主位 + 仲裁），#4–#9 全部注册进 dock；多并存时「+N」chip 升级为**图标条**。
3. **队列**：多确认改为队列展示（计数器 N/M + 逐个导航 + 全部批准/拒绝）。
4. **#1 任务表维持顶部不动**；#10 #11 输入区常驻元件不动。

## 五、设计契约（SSOT）

- **裁决单点**：新增 `resolvePromptSlot()`，对齐 `resolveDock()` 范式——A 类各载体只上报 `setPromptActive(id, active)`，**禁直写 `hidden` / `insertBefore`**（散写即回到堆叠现状，StatusDock 之前就是这么烂的）。
- **队列真源归 host**：pending 确认队列的真源是 host 的 `_pendingWriteConfirmations`（Map）。**webview 不自持队列**，只投影 host 推的快照（新增 `write_confirm_queue` 消息或复用 `turn_update` 投影）。webview 自持 = 双源漂移。
- **输入锁单点**：`setInputLocked(boolean)` 唯一写入点，由 `resolvePromptSlot()` 调用；解锁时机 = 队列清空 / 全部裁决完毕 / 超时。
- **ask 收口**：A 类槽落地后，`#clarifyBar` 双轨**注销**（正常走 ask-inline，异常兜底改走 A 类槽），消除两套渲染路径。

| **E3** | 积压 | S2 未修：宿主并发确认仍是「各自独立 30 分钟计时 + 只展示最新」 | P2 修 |

### 落地后复审（2026-10-05 第三轮，**真机实锤 1 条**）

前两轮都是**读代码复审**，第三轮由用户真机截图暴露——**结构性假绿，336 用例全绿却功能失效**：

| ID | 类型 | 问题 | 处置 |
| --- | --- | --- | --- |
| **E4** | 假绿（真机） | A 类激活时确认卡显示在输入框**上方**而非替换之。根因：`chatStyles.ts` 里 `#inputWrap { display: flex }` 覆盖了 HTML `hidden` 属性的 UA `display:none`（CSS 规范行为，非 bug）。`setComposerReplaced` 写的 `inputWrap.hidden = true` **确实为 true** ⇒ 断言恒真，视觉纹丝不动。**P1b 的输入锁设计完全失效**，用户仍可边审边打字 | 全局 `[hidden] { display: none !important; }` + `#inputWrap[hidden]` 双保险；新增源码级守卫（读生产 CSS 文本） |

**为什么两轮复审都没抓到**：jsdom 不加载 `<style>`、测试夹具不含样式表、`hidden` 是属性
而非计算样式 —— 三重巧合使「属性断言」与「用户能否看见」彻底脱钩。同类坑本仓已逐个补过
**18 处** `.xxx[hidden]` 兜底（`.activity-bar` 注释里写着同一句警告），**全是打补丁**。

**可复用的排他性推理**：`resolveDock` 同一函数同时裁决「卡可见」与「composer 让位」，
故「A 生效 B 未生效」只可能是「JS 属性写对、CSS 盖掉」—— 直接锁定根因层。

**同批附带修复**：
- E1 续：`startConfirmCountdown` 对非法 `timeoutMs` **静默 return** ⇒ 真源漂移时倒计时
  无声消失且无痕可查（与 E2 同款病）。改为显式抛错，由 `onMessage` 既有兜底 catch
  转 `console.error`，不新增错误通道。
- 注释撒谎 5 处：4 处「30s」过期 + 1 处**机制性描述失效**（用例组头「旧 requestId 由
  host 超时独立兜底」—— 串行化后旧请求根本没被推出去，描述的机制已不存在）。
  ⚠️ 后者比前者更伤：过期数字靠 grep 能抓到，**因果错误只能靠理解语义抓到**。

### 已知取舍（如实登记，非隐瞒）

- **T1 切换微闪**：连续确认时，webview 点击后本地关卡、宿主随即推下一条 ⇒ 理论上有一帧「关→开」。
  两 postMessage 同进程、间隔远小于一帧，实测不可见；真机若观察到闪烁，再改为「宿主驱动关闭 +
  提交后禁用按钮」的加状态方案（当前不预支该复杂度）。
- **T2 中止入口**：A 类替换 composer 后，停止/暂停键随 `#inputWrap` 一并让位。逃生链是
  面板恒带的「拒绝」（拒绝即脱身，随后 composer 恢复、停止键回归）。若真机出现「想直接
  中止整轮却只能逐个拒绝」的阻塞，再在面板内加三级动作，不为假想需求预支协议。
- **T3夹具双源未治**：测试夹具 `dispatch(msg: unknown)` 签名无类型约束，14 处
  `write_confirm_request` 用例中 7 处不补 `timeoutMs`（编译期抓不到）。治它要给 dispatch
  加协议类型约束，**波及 683 处调用**，与 P6 同批立项，本轮不冒进。
- **T4 假绿防线只覆盖 CSS 文本层**：新增守卫读的是生产 `chatStyles.ts` **源码文本**，
  可抓住「兜底规则被删/改名」。但若有人改的是**别处**引入的样式（内联 style、其他
  样式文件、webview 内 `<style>`），守卫**抓不到**。彻底解法是让测试环境真加载样式表
  （如引入 `getComputedStyle` 实测），代价大且 jsdom 对 cascade 支持不全 —— 登记为
  已知防线边界，不假装覆盖完整。

## 八、scope 边界（防蔓延）

- `#planBar` 顶部形态与锚定逻辑**不动**（用户拍板）。
- `#contextOccupancy` / `#currentCapabilityBadge` 输入区 Row2 常驻元件**不动**。
- A/B 两类载体的**内容渲染、按钮事件、数据流**不动——只改「归位、显隐、队列、输入锁」的裁决归口（对齐 StatusDock 既有范式）。
- 内核**零改动**：确认语义、超时、队列全部在宿主层裁决。
