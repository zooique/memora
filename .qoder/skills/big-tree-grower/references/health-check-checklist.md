# 大树健康度检查清单

> 用于 grower 手动入口 9"健康度诊断"和自动入口 21"自动体检"，对项目三层（根系/躯干/枝叶）进行全面健康度诊断

---

## 诊断前置准备

在执行诊断前：

1. 加载 `.trae/rules/project-rules.md` 了解项目画像和技术栈
2. 浏览 `.trae/rules/` 目录，识别所有规则文件及其 `alwaysApply` 标记
3. 浏览 `decisions/` 了解已有的 ADR 记录
4. **识别项目类型**（决定躯干/枝叶层的检查方式）：

| 判断条件                                   | 项目类型 | 说明                                                   |
| ------------------------------------------ | -------- | ------------------------------------------------------ |
| 项目包含源代码文件（.js/.py/.ts/.java 等） | 代码项目 | 躯干层检查基类/工具函数，枝叶层检查分层规范            |
| 项目仅包含文档文件（.md/.yaml 等）         | 文档项目 | 躯干层检查 SKILL/references 一致性，枝叶层检查文档质量 |
| 混合                                       | 混合项目 | 两种检查方式都执行                                     |

> **判断方式**：读取 `project-rules.md`
> 中的技术栈描述，或浏览项目根目录结构。如果技术栈中包含编程语言/框架，则为代码项目；如果仅有"运行时：无"或类似声明，则为文档项目。

---

## 根系健康度检查

> 根系层检查对所有项目类型通用——无论代码项目还是文档项目，都需要规则文件和 ADR。

### R1：规则文件完整性

| 检查项                   | 方式                       | 标准                                                                                     |
| ------------------------ | -------------------------- | ---------------------------------------------------------------------------------------- |
| 规则文件是否齐全         | LS `.trae/rules/`          | 对照 `project-rules.md` 中的规则文件索引，所有列出的文件都存在                           |
| alwaysApply 文件是否存在 | 检查各规则文件 frontmatter | `project-rules.md` 必须为 `alwaysApply: true`；其他 alwaysApply 文件根据项目实际情况确认 |
| 规则文件索引是否准确     | 对照实际文件               | 索引中列出的文件与实际文件一致                                                           |

### R2：规则之间一致性

| 检查项               | 方式                                                   | 标准                                     |
| -------------------- | ------------------------------------------------------ | ---------------------------------------- |
| 技术栈描述一致       | 对比 `project-rules.md` 与其他包含技术栈信息的规则文件 | 各文件中的技术栈清单一致                 |
| 分层策略一致         | 对比分层相关规则文件（如存在）                         | 层数、层名、职责描述一致                 |
| 命名约定一致         | 对比 `project-rules.md` 与命名相关规则文件             | 命名规则不矛盾                           |
| 约定速查表与实际一致 | 对照架构速查文件（如存在）的速查表与各专项规则         | 速查表中的实现名称与专项规则中的描述一致 |
| 无冲突定义           | 通读各规则文件的"禁止"部分                             | 不同文件中的"禁止"规则不互相矛盾         |

### R3：ADR 覆盖度

| 检查项             | 方式                                     | 标准                      |
| ------------------ | ---------------------------------------- | ------------------------- |
| 关键决策有对应 ADR | 对照 `project-rules.md` 中的核心架构决策 | 每个核心决策有对应 ADR    |
| ADR 与实际一致     | 对比 ADR 决策与项目实际状态              | ADR 中的选择与实际一致    |
| ADR 数量是否合理   | LS `decisions/`                          | 至少 3-5 个核心决策的 ADR |

### R4：规则可执行性

| 检查项                 | 方式                         | 标准                                |
| ---------------------- | ---------------------------- | ----------------------------------- |
| 规则是否可被 AI 理解   | 通读 `project-rules.md`      | AI 角色定义清晰，DO/DON'T 明确      |
| 规则是否有可操作的示例 | 检查新模块指南文件（如存在） | 包含可复制粘贴的模式或步骤          |
| 规则是否过于复杂       | 评估各规则文件的长度和密度   | 单文件不超过 300 行（排除代码示例） |

### R5：矛盾演化验证

> 对照 seeder 创意设计单页纸中的"矛盾演化预判"，验证当前阶段的实际矛盾是否与预判一致。

| 检查项             | 方式                                           | 标准                                       |
| ------------------ | ---------------------------------------------- | ------------------------------------------ |
| 当前阶段识别       | 对比当前项目状态与演化预判各阶段的触发条件     | 明确判定当前处于预判的哪个阶段             |
| 矛盾浮现准确性     | 对比当前实际浮现的问题与预判的矛盾             | 预判矛盾与实际矛盾一致 / 部分一致 / 不一致 |
| 矛盾的主要方面验证 | 判断预判的"矛盾的主要方面"是否正确             | 如果预判有误，更新主要方面判断             |
| 架构影响回溯       | 检查预判的"对架构的影响"是否需要修正           | 如果预留的扩展点未使用或不足，标记为需修正 |
| 预判是否需要更新   | 基于当前验证结果判断是否需要更新创意设计单页纸 | 如有重大偏差，建议回退到 seeder 矛盾分析   |

**验证结果处理**：

| 验证结果    | 处理方式                                            |
| ----------- | --------------------------------------------------- |
| ✅ 预判准确 | 记录验证结论，继续使用当前预判                      |
| ⚠️ 部分偏差 | 更新创意设计单页纸的演化预判，补写 ADR 记录偏差原因 |
| ❌ 严重偏差 | 归档待办，建议执行矛盾分析重新审视核心矛盾          |

## 躯干健康度检查

> 躯干层检查按项目类型分叉。代码项目检查代码抽象的复用和扩展性；文档项目检查 Skill 模板的一致性和复用性。

### 代码项目

#### T1-C：抽象工具复用率

| 检查项                 | 方式              | 标准                                        |
| ---------------------- | ----------------- | ------------------------------------------- |
| 基类被多少模块继承     | Grep 搜索基类名   | 如果基类只有 1-2 个继承者，考虑是否过度抽象 |
| 工具函数被多少文件调用 | Grep 搜索函数名   | 如果工具函数只有 1 个调用者，考虑内联       |
| 通用组件被多少页面使用 | Grep 搜索组件导入 | 如果组件只有 1-2 个使用者，考虑是否值得     |

#### T2-C：重复造轮子

| 检查项                          | 方式                    | 标准                              |
| ------------------------------- | ----------------------- | --------------------------------- |
| 是否存在功能相同的工具函数      | Grep 搜索相似函数名模式 | 发现多个同名模式的函数 → 徒长枝   |
| 是否存在功能相同的组件          | Grep 搜索相似组件名模式 | 发现多个同名模式的组件 → 徒长枝   |
| 是否存在功能相同的 Service 方法 | Grep 搜索相似方法名模式 | 发现多个同名模式的方法 → 考虑提取 |

#### T3-C：基类扩展性

| 检查项                           | 方式         | 标准                               |
| -------------------------------- | ------------ | ---------------------------------- |
| 添加新模块是否需要修改基类       | 阅读基类代码 | 如果需要修改基类，说明扩展性有问题 |
| 基类是否有过大的方法             | 阅读基类代码 | 单个方法超过 50 行可能职责不单一   |
| 基类是否有未被子类覆盖的抽象方法 | 阅读基类代码 | 所有抽象方法都有子类覆盖           |

### 文档项目

#### T1-D：模板复用率

| 检查项                              | 方式                                   | 标准                                        |
| ----------------------------------- | -------------------------------------- | ------------------------------------------- |
| references/ 文档被多少处引用        | Grep 搜索 references 文件名            | 如果参考文档只有 1 处引用，考虑是否值得独立 |
| SKILL.md 中的流程模板是否被实际执行 | 对比 SKILL.md 定义的入口与实际使用记录 | 定义了但从未触发的入口 → 考虑是否需要       |
| 共享概念是否提取到 references       | 检查 SKILL.md 中是否有重复描述的流程   | 3 次以上重复应提取到 references/            |

#### T2-D：内容重复

| 检查项                                 | 方式                                      | 标准                                              |
| -------------------------------------- | ----------------------------------------- | ------------------------------------------------- |
| 是否存在功能相同的参考文档             | 对比 references/ 下各文档的职责           | 发现职责重叠的文档 → 考虑合并                     |
| SKILL.md 与 references/ 是否有冗余描述 | 对比 SKILL.md 概述与 references/ 详细内容 | SKILL.md 只保留入口和路由，详细逻辑在 references/ |
| 不同 Skill 之间是否有重复内容          | 对比 seeder 和 grower 的 references/      | 通用内容应提取到共享位置或明确交叉引用            |

#### T3-D：模板扩展性

| 检查项                                 | 方式                   | 标准                                         |
| -------------------------------------- | ---------------------- | -------------------------------------------- |
| 新增入口是否需要修改 SKILL.md 核心结构 | 阅读 SKILL.md 的入口表 | 如果新增入口需要改核心结构，说明扩展性有问题 |
| references/ 文档是否职责单一           | 阅读各参考文档         | 单文档覆盖多个不相关主题 → 考虑拆分          |
| 触发词是否易于新增                     | 检查触发词管理流程     | 新增触发词只需在固定位置添加，不需改动多处   |

## 枝叶健康度检查

> 枝叶层检查按项目类型分叉。代码项目检查代码分层规范和重复模式；文档项目检查文档质量和一致性。

### 代码项目

#### L1-C：分层规范遵守

| 检查项                      | 方式                        | 标准                                                 |
| --------------------------- | --------------------------- | ---------------------------------------------------- |
| Controller/Handler 是否薄层 | 抽样 2-3 个 Controller 文件 | 不含业务逻辑，只做参数提取和调用转发                 |
| Service 是否持业务逻辑      | 抽样 2-3 个 Service 文件    | 包含完整的业务逻辑和错误处理                         |
| 是否存在越权调用            | Grep 搜索跨层级导入         | 如 Controller 直接调用 Model、Route 直接调用 Service |

#### L2-C：代码量合理性

| 检查项                 | 方式                   | 标准                                                 |
| ---------------------- | ---------------------- | ---------------------------------------------------- |
| 新增 CRUD 模块的代码量 | 统计最近添加的模块文件 | 如果比新模块指南描述的步骤多很多，可能存在模式未提取 |
| 单个文件是否过长       | 检查文件行数           | 超过 500 行建议拆分                                  |

#### L3-C：重复模式识别

| 检查项                                | 方式                  | 标准                              |
| ------------------------------------- | --------------------- | --------------------------------- |
| 同一逻辑是否在 3+ 个文件出现          | Grep 搜索相似代码片段 | 达到 3 次应提取为工具函数         |
| 同一组件模式是否在 3+ 个页面出现      | Grep 搜索相似组件结构 | 达到 3 次应提取为通用组件         |
| 同一校验模式是否在 5+ 个 Service 出现 | Grep 搜索相似校验逻辑 | 达到 5 次应提取到基类或共享工具中 |

### 文档项目

#### L1-D：文档结构规范

| 检查项                    | 方式                             | 标准                                   |
| ------------------------- | -------------------------------- | -------------------------------------- |
| 文档标题层级是否正确      | 检查 Markdown 标题结构           | 不跳跃（# → ## → ###），一级标题唯一   |
| YAML frontmatter 是否完整 | 检查 SKILL.md 入口文件           | 包含 `name` 和 `description`，格式正确 |
| 文件命名是否符合约定      | 对照 `project-rules.md` 命名约定 | 连字符命名法/固定名称等符合规范        |

#### L2-D：文档量合理性

| 检查项                      | 方式                          | 标准                               |
| --------------------------- | ----------------------------- | ---------------------------------- |
| 单个参考文档是否过长        | 检查 references/ 下各文件行数 | 超过 400 行建议拆分                |
| SKILL.md 入口表是否过于庞大 | 检查入口数量                  | 超过 25 个入口考虑分组或拆分 Skill |

#### L3-D：内容重复模式

| 检查项                       | 方式                       | 标准                           |
| ---------------------------- | -------------------------- | ------------------------------ |
| 同一流程描述是否在 3+ 处出现 | Grep 搜索相似描述段落      | 达到 3 次应提取到 references/  |
| 同一触发词是否在多处定义     | 对比真理源和速查的触发词表 | 触发词只在真理源定义，速查引用 |
| 交叉引用是否断链             | 逐条检查 Markdown 链接     | 所有链接目标可达               |

#### L4-D：时间线一致性扫描

> 用于写作项目，检查故事节点的时间线逻辑是否自洽。

| 编号 | 校验内容                             | 检查方式                                       | 标准                                         |
| ---- | ------------------------------------ | ---------------------------------------------- | -------------------------------------------- |
| T1   | 同一角色是否同时出现在两个地点？     | 对比各故事节点的时间点和角色参与               | 同一时间点，一个角色只能出现在一个地点       |
| T2   | 暗线事件是否早于公开揭示？           | 对比暗线故事节点和公开揭示节点的时间顺序       | 暗线事件的时间点必须早于公开揭示             |
| T3   | 故事节点时间是否超出故事线起止范围？ | 对比节点时间点与所属故事线的时间范围           | 节点时间必须在故事线起止范围内               |
| T4   | 大事件是否影响了相关故事线？         | 检查大事件节点后，相关故事线是否有对应反应节点 | 大事件应在其影响的故事线中有体现             |
| T5   | 章节装配是否打乱了因果顺序？         | 对比写作时的节点组装顺序与节点的因果依赖关系   | 因果上在前的节点不能排在因果上在后的节点之后 |

## 诊断后的行动建议

根据诊断结果，推荐以下后续动作：

| 诊断结果                     | 推荐动作                                                             | 归档方式                                                          |
| ---------------------------- | -------------------------------------------------------------------- | ----------------------------------------------------------------- |
| 根系有问题                   | → 建议执行规则对齐或年轮审判来修正规则                               | 规则问题不写入待完成任务，在退出声明中建议规则对齐                |
| 躯干有问题                   | → 代码项目：执行"剪枝"或"架构评审"；文档项目：执行"规则对齐"或"速修" | 可行动问题写入 `tasks\待完成任务.md`，标注来源"grower 健康度诊断" |
| 枝叶有未提取的重复模式（L3） | → 执行"剪枝"（躯干升级判断）                                         | 同上                                                              |
| 枝叶有已重复的抽象（徒长枝） | → 执行"剪枝"                                                         | 同上                                                              |
| 枝叶有越权调用 / 结构违规    | → 代码项目：执行"提交前审查"；文档项目：执行"速修"                   | 同上                                                              |
| 发现安全漏洞                 | → 执行"安全审计"                                                     | 同上                                                              |
| 全部通过                     | → 记录健康度快照，下次迭代末再检查                                   | 无需归档                                                          |

### 归档到待完成任务.md 的格式

每条问题按以下格式写入 `tasks\待完成任务.md`：

```markdown
| ID   | 问题       | 影响范围   | 建议方案   | 来源                     |
| ---- | ---------- | ---------- | ---------- | ------------------------ |
| T-xx | {问题描述} | {影响范围} | {建议方案} | grower 健康度诊断 {日期} |
```

- 优先级根据问题的严重程度分配 P1-P5
- 暂缓/需人工决策的问题标注为"暂缓"，单独列在暂缓区
- 归档后不删除原诊断报告的内容（报告保留完整的诊断上下文）

## 历史对比（动态健康度追踪）

> 树是**活的**，健康度应该是**动态的**。单次诊断只能看到横截面，多次诊断的对比才能看到趋势。此步骤在每次诊断完成后执行。

### 对比方式

1. 检查 `tasks/健康度快照/` 目录下是否存在上一次诊断快照
2. 如果存在，对比本次与上次的各项评分：

| 对比维度 | 上升/下降/持平 | 说明                    |
