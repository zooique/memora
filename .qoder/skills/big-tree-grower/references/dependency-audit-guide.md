# 依赖审计指南

养树不只看枝叶，也要看土壤。过期的依赖是腐土，漏洞的依赖是虫害。本指南规范依赖审计的流程——定期扫描、分类处理、归档跟踪。

---

## 触发场景

- 手动：`依赖检查` `依赖审计`
- 自动：全自动循环完成后、版本发布前
- 被动：用户提到"依赖安全""过期依赖""升级依赖"时主动建议

---

## 核心流程

```
运行依赖扫描 → 分类结果 → 安全漏洞自动修 → 过期依赖评估 → 归档待办
```

### 第一步：运行依赖扫描

执行项目包管理器的安全审计和过期检查命令（具体命令从 `.trae/rules/` 中读取）：

- 安全审计：获取已知漏洞列表
- 过期检查：获取过期依赖列表

### 第二步：分类结果

| 类别                       | 判断标准                   | 处理方式                             |
| -------------------------- | -------------------------- | ------------------------------------ |
| 🔴 安全漏洞（高危）        | 审计报告显示 critical/high | 尝试自动修复命令，失败则评估手动升级 |
| 🟡 安全漏洞（中危）        | 审计报告显示 moderate      | 记录到待完成任务，择机修复           |
| 🟢 安全漏洞（低危）        | 审计报告显示 low           | 记录，不强制修复                     |
| 🟡 过期依赖（major）       | breaking changes           | 逐项评估影响，归档待任务             |
| 🟢 过期依赖（minor/patch） | 向后兼容                   | 执行批量更新命令                     |
| ⚪ 废弃包                  | 官方标记为 deprecated      | 查找替代方案，归档迁移任务           |

### 第三步：安全漏洞修复

- **可自动修复**：自动修复命令能处理 → 执行并验证测试
- **需手动修复**：自动修复命令失败 → 逐包升级并验证
- **无法修复**：上游未提供修补 → 归档到待完成任务，标注风险

### 第四步：过期依赖评估

对每个 major 版本过期的包：

1. 读取 CHANGELOG 了解 breaking changes
2. 搜索项目代码确认使用方式
3. 评估升级影响范围
4. 归档升级任务到待完成任务

### 第五步：报废依赖处理

对标记为 deprecated 的包：

1. 确认废弃原因和推荐替代
2. 搜索项目中使用该包的代码
3. 评估迁移成本
4. 归档迁移任务到待完成任务

---

## 输出内容

- 扫描统计：依赖总数 / 过时数 / 漏洞数
- 已修复：自动修复的漏洞列表
- 待处理：归档到待完成任务的任务数
- 建议：最紧急处理的 3 项

---

## 安全原则

- 高危漏洞立即修复，不可暂缓
- 修复后必须运行项目测试命令验证回归
- 不自动升级有 breaking changes 的依赖
- 锁文件必须纳入版本管理
