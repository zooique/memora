### 🔴 F4 — 判据搬家无法纯宿主落地（2026-11-19 落地尝试实锤，新增）

| 项 | 内容 |
| --- | --- |
| **背景** | 用户拍板按推荐三步走推进落地，第一步 = 把停止/暂停/恢复、通知的归属判据从 `agentDriven` 搬到按轮 `Round.origin`，再删补丁。落地前探查可行性。 |
| **探查事实** | ① 确认层 `confirmCoordinator.bindSession` 能按轮读，因闭包持有**当前会话 agent**，`agent.currentRoundId()` 现取轮 id → `getRoundOrigin(roundId)`（`chatPanel._eventLogRoundStore`，webview 侧）。② 停止/暂停/恢复 `workSessionTools.ts` 的门禁 `deps.isAgentDriven?.(sid)`、通知 `hostedSessionNotice.resolveTarget` 的 `isAgentDriven(sessionId)`，判的都是**目标工作会话**（另一条 sid）；台账明示「不为了停而去装配新实例」，故目标无活实例时拿不到 `currentRoundId()`，确认层模式不可复用。③ host 侧 `sessionStatus.isWorkerIdentitySuspended` 是「按 sid 读**最近一轮** origin」（`readRoundIds(sid).at(-1)`），若拿它做停止门禁会误伤：hosted 会话里用户中途亲手发一轮（origin=user）仍在跑时，最近轮是 user，判据翻 false ⇒ 助手停不了自己派的活。 |
| **根因（第一性原理）** | `agentDriven` 承载的是**会话级、进程内的当前驱动权**；`Round.origin` 是**轮级、落盘的出生事实**。两者不是同一事实，不能用「最近一轮 origin」冒充「当前驱动权」——那正是 SSOT 反对的「同一事实两处登记且口径不同」。真正治本需 origin 进内核执行上下文，让停止门禁读到「当前这一轮」的 origin，即台账 `HOSTED-ROUND-ORIGIN-1` 的内核 A 形态。 |
| **落地判定** | ⛔ 第一、二步（判据搬家 + 补丁作废）**阻塞**，不强推。理由：无活实例拿不到当前轮 id（硬断）；最近轮替代会误伤（带伤）。这是「不带伤」原则明确禁止的场景，与用户质量优先取向一致。 |
| **可无伤落地的** | F1 文档注记（如实标目标态 vs 当前态，零判据）、F2 已自清（假阳性）。判据搬家待内核 A 形态发版窗口，与 F1 收回方向合并拍板。 |
