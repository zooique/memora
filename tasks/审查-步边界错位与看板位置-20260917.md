## TL;DR

**问题 B（标题错位）一句话根因**：`step_boundary` 事件由 **"active step 推进检测"** 产出（`loop.ts:1040-1052` 读 `getActiveStepMeta`），其语义是"**推进到**的那一步"，且**在每次迭代的 LLM 调用之后、工具执行之前**产出。而 `writePlan` 写入新计划、把 **step1 置为 active** 发生在**该次迭代的工具阶段**（晚于边界产出）。于是：**任何计划的第一步都拿不到自己的边界**；同时本轮的**会议骨架**（prepare 期预置）的第 2 步被迭代 1 的 `onStepBoundary` 自动完成并推进 → 产出一条**携带骨架标题的边界**，占了本轮的「boundary[0]」槽位 → UI 按边界顺序编号（`chatView.ts:959`）把 step-1 的标题显示成骨架第 2 步（共鸣小说家），而 step-1 的**内容**（组长开场）恰好落在这个槽位下 → 用户看到的正是「**内容对、标题错**」。

**问题 A（看板位置）一句话根因**：运行时**两条轨都渲染了**（`renderPlanBoard` 非空时无条件调 global + inline，`chatView.ts:424-427`），但 **global 轨被 prepend 进滚动容器 `#messages`**（`chatView.ts:190-196, 340`；`chatStyles.ts:34-35` `overflow-y:auto`）→ 流式期间**自动滚到底部，global 直接滚出视野**；用户唯一可见的只剩 **inline 轨**，而 inline 是**单行、无任何事件监听、只显示当前 active 步**（`chatView.ts:300-330`）→ 于是「底部 / 点击无反应 / 只看到当前步骤」三条同时成立。**F1 锚点修复没覆盖运行时，是因为运行时 inline 落到底部根本不是锚点退化造成的**（退化路径已修复，见 `chatView.ts:264-276` + 用例 `chatView.test.ts:1705-1724`），而是"**宿主 = 最新消息块（在会话最底部）**" + "**process-flow 先于 inline 挂进同一锚点**"两个独立机制叠加。

### 1.2 d3523035 到底是谁？—— 不是"上一轮残留的旧 plan"，而是**本轮的会议骨架第 2 步** `[实锤]`

- `d3523035` 的 `title = "共鸣小说家 发言：给出下一个步任务建议"`。
- `tryBuildMeetingPlan`（`rolePackManager.ts:549-567`）的骨架模板是 `` `${m} 发言${suffix}` ``，其中 `suffix = "：" + topic`，`topic` = 输入中「小组会议」之后的部分。本轮输入 = `"小组会议：给出下一个步任务建议"`（见 round 文件 `userMessage`）。
  → 令 `m = 共鸣小说家`，模板产出 **`"共鸣小说家 发言：给出下一个步任务建议"`，与 d3523035 逐字相同（含空格）**。
- 骨架预置发生在 **prepare 期**（`prepare.ts:74-81`，`writePlan('overwrite', meetingSteps)`），**不经过工具调用、不落 processEvents**，故它不会出现在任何 round 文件的 `task_table_*` 里——这解释了"为什么它不在本轮写入的 4 个 id 中"。
- 旁证：`d3523035` 在**全仓 4 个 round 文件里只出现在本轮**（前 3 轮 grep 均 false）；且唯一带「小组会议」输入的轮就是本轮。

**为什么本轮会重开骨架（而非续会）**：骨架预置的守卫是 `hasInflightPlan`（`prepare.ts:74-77`）。上一轮 `round-1789539624589`（status=`interrupted`）**所有** `task_table_write` 的返回都是 `"…当前共 0 个步骤"` `[实锤]` → 该轮 plan 始终为空 → `autoClearPlanIfAllDone`（`agent.ts:960-969`）读到 `plan.length===0` 直接 return → 落盘计划保持空 → 本轮 `hasInflightPlan()===false` → **预置新骨架**。

> ⚠️ 这里同时暴露一个**独立疑点**（非 A/B）：interrupted 轮为何每次 `task_table_write` 都得到 0 步？见「待验证项 V3」。

### 1.3 机制钉死（代码行 + 时序）

**产出点**：`loop.ts:1031-1052`
```
1031  if (this.onStepBoundary && !this.willSuspendForAsk(...)) {   // 每次迭代完成都进
1032    this.onStepBoundary({ summary: ... });                       // ← 先：自动完成当前 active 步
1035  }
1040  const activeStepMeta = this.getActiveStepMeta?.();             // ← 后：读【已推进】的新 active
1042  if (activeStepMeta && activeStepId && activeStepId !== this.lastBoundaryStepId) {
1047    yield { type:'step_boundary', stepId: activeStepId, title: ... }; // 语义 = "推进到 X"
```
- `onStepBoundary` 的实现（`assembler.ts:348-356`）：取当前 active 步 → `sessionManager.completeStep({planStepId})`。
- `completeStep`（`sessionManager.ts:864-902`）：`updatePlanStepStatus(planStepId,'done')` → 内部 `ensureActiveStep()`（`sessionManager.ts:809-817, 829-846`）**把下一个 pending 置为 active**。
- `getActiveStepMeta`（`assembler.ts:361-367`）：`plan.find(s => s.status==='active')` → 返回**推进后**的那一步。

于是每次迭代的**净效果**：
1. 把「迭代开始时 active 的那一步」标 done 并推进；
2. 产出一条**指向"推进到的那一步"**的 `step_boundary`；
3 这一切发生在**本迭代的工具执行之前**。

**逐迭代代入本轮**：
- 迭代 1 开始：`checkpoint.plan` = 骨架 `[S1=组长主持开场(active), S2=共鸣小说家(d3523035), …]`。
  - 迭代 1 末：完成 S1 → 推进到 S2 → `boundary(d3523035)`。**→ seq 167**。
  - 迭代 1 工具：`task_table_write(overwrite)` **整体覆盖骨架** → 新 step1 `9b25df6d` active。
- 迭代 2 末：完成 `9b25df6d` → 推进到 `209cde71` → `boundary(209cde71)`。**新 step1 的"进入"边界的唯一机会，被这次"离开 step1"的事件吃掉了**。
- 迭代 3/4 同理；迭代 5 完成最后一步后无 pending → 无边界。

**三个硬事实全部对上**：
1. `seq167 边界早于 seq168 task_table_write` —— 边界在**本迭代工具之前**产出（`loop.ts:1031→1072` 的先后），而 task_table_write 是**该迭代的工具**。`[实锤]`
2. `stepId 来自另一个 plan` —— 来自 **prepare 期预置的会议骨架**（`prepare.ts:78-81`），非本轮工具写入的 4 步。`[实锤]`
3. `新 plan step1 无边界` —— step1 的"置为 active"发生在 `writePlan`（工具内），**晚于**该迭代的边界产出；下一次边界检测（迭代 2 末）读到的 active 已经跳到 step2。`[实锤]`

### 1.4 逐条回答子问题

| 子问题 | 定论 |
|---|---|
| 进入本轮时 checkpoint.plan 为何有残留 active？何时清理？ | **本轮无残留**（空 → 重开骨架）。通用机制：`autoClearPlanIfAllDone`（`agent.ts:960-969`）在 `chat()`/`continueAfterPause` 的 `finally`（`agent.ts:470/613`）执行，**仅当 plan 全 done 且非暂停**才 `clearPlan`（`sessionManager.ts:905-911`，清 plan+stepLog）。→ 任何以「非全 done / 暂停 / interrupted」结束的 turn，其 plan **会残留到下一轮**。`[实锤]` |
| `writePlan('overwrite')` 后 `ensureActiveStep` 激活谁？是否按索引继承旧步状态？ | **不继承**。`writePlan`（`sessionManager.ts:765-800`）：`overwrite` 先 `cp.plan=[]`，再对每个新步 `appendPlanStep`（新 UUID、`status:'pending'`、`order=当前长度`，`sessionManager.ts:745-753`），最后 `ensureActiveStep()` → **第一个 pending 置 active = step1**。旧步状态被整体丢弃，不存在索引继承。→ **team-lead 的"按索引继承旧步状态"假设不成立；"第 2 步先 active"另有其因。**`[实锤]` |
| `lastBoundaryStepId` 在 `writePlan` 时是否重置？ | **从不重置**。全仓 grep：仅 `loop.ts:320`（声明）、`:1042`（比较）、`:1043`（赋值）三处，**无任何 reset**，跨 turn 亦不清。但它**不是本例的因**：即便重置，迭代 2 末仍只会产出 `209cde71`（因为读的是"推进到"的值）。真正漏掉 step1 的是**检查时机**（迭代完成时、且晚于 `onStepBoundary` 的自动推进），不是去噪缓存。`[实锤]` |
| "第 2 步变 active 早于第 1 步被标记 done"如何解释？ | **dual-writer（双写）**：内核的 `onStepBoundary`→`completeStep`（`loop.ts:1031` / `assembler.ts:348-356`）在**迭代 2 的边界处**（seq246）就已把 step1 标 done 并推进到 step2；LLM 随后在**自己的工具阶段**才发 `task_table_update(step_id:"1", done)`（seq247-248）。→ 观察到的"第 2 步先 active、第 1 步后 done"= **内核自动推进抢在 LLM 显式推进之前**，且 LLM 的 update 是**冗余 no-op**（该步已是 done）。`[实锤]` |

> **对抗式追问：这个"每次迭代自动完成 active 步"的设计是缺陷还是取舍？**
> 它是**为了让边界机制能工作**才存在的：边界检测发生在"本迭代工具之前"，若内核不抢先推进，就只能等 LLM 的 `task_table_update`（在工具里、更晚），本迭代永远检测不到推进 → 一条边界都不会有。所以**自动推进是边界的必要前提**，但它同时**与 `assembler.ts:346` 的文档契约自相矛盾**——注释写"写 stepLog…避免双写 / plan 仍是任务状态真理源"，而实现调用的 `completeStep` **恰恰写了 plan 状态（done + 推进）**，构成对 plan 的第二次写。这是本问题的**结构性支点**。

### 1.5 Q1 结论（可钉死）

> **真缺陷根因**：`step_boundary` 的**语义锚点**（"推进到 X"）与**产出时机**（迭代末、工具前）的组合，使**计划的第一步永远缺失进入边界**；叠加**prepare 期预置骨架**的第 2 步被迭代 1 边界自动推进，产出一条**属于骨架的边界**并占据 boundary[0]。UI 以"边界序号"编号（`chatView.ts:959` `bounds.indexOf(bound)+1`），于是编号与标题整体错位一格。

## Q2 定论：位置 / 无交互 / 只显示当前步

### 2.1 运行时到底渲染了哪条轨？—— 两条都渲染 `[实锤]`

调用链（运行时）：

```
内核 yield step_boundary / tool_start(task_table_*) 
  └─ chatPanel 收到 chunk
       ├─ tool_start && name∈{task_table_write,task_table_update} → this.postPlanUpdate()   chatPanel.ts:2472-2474
       └─ 流尾 → this.postPlanUpdate()                                                       chatPanel.ts:2618
            └─ postPlanUpdate(): 从 agent.getCheckpoint().plan 取快照
                 ├─ plan 空 → post({type:'plan_update', steps:[]})                           chatPanel.ts:2676-2684
                 └─ plan 非空 → post({type:'plan_update', steps})                            chatPanel.ts:2694-2697
                      └─ webview onMessage: plan_update → renderPlanBoard(msg.steps)         chatView.ts:3710-3712
                           └─ renderPlanBoard(): plan 非空 → renderGlobalPlanBoard(steps)  ← 顶部轨   chatView.ts:424-425
                                                 + mountInlinePlanBoard(steps)          ← 内联轨   chatView.ts:426-427
```

→ **运行时 global 与 inline 都被创建**（不是"没渲染 global"）。空计划分支才两轨一起收（`chatView.ts:417-422`）。

### 2.2 为什么用户"只看到 inline"？

- **global 轨**：`renderGlobalPlanBoard` 用 `prependStatusBlock(globalPlanBoard)`（`chatView.ts:340`）→ `messages.prepend(el)`（`chatView.ts:190-196`）。而 `#messages { flex:1; overflow-y:auto }`（`chatStyles.ts:34-35`）**本身就是滚动容器**，`.plan-board` **无 `position:sticky/fixed`**（`chatStyles.ts:1232-1240`）。
  → 流式期间每个 chunk 都 `scrollToBottom(messages)`（如 `chatView.ts:2515/2294`）→ **global 恒在滚动区顶部、随内容滚出视野**。`[实锤]`
- **inline 轨**：`mountInlinePlanBoard` 挂到 `activeAssistantEl`（= **最新**的 assistant 块，在会话最底部），锚点 `insertBeforeBody` → 插到 `.msg-body` 之前（`chatView.ts:264-276, 293`）。
  → 用户视野（自动贴底）里唯一稳定可见的进度 UI 就是这条 inline。`[实锤/推断]`

判定：**"global 没渲染"= 假；真相是"渲染了但被滚动容器卷走、运行时不可达"** + "用户实际看到的可交互面是 inline（它本来就不交互）"。

### 2.3 为什么"运行时仍在底部"？—— 与 F1 无关（F1 修的是另一回事）`[实锤]`

- F1 的 bug 是 `insertBefore(el, null)` 按 DOM 规范退化为 `appendChild`（落到块最末）。**该退化已被修复**：现 `insertBeforeBody` 三段式降级终点是 **`host.prepend(el)`（顶部）**，**不是 appendChild**（`chatView.ts:264-276`）。`chatView.ts:257-259` 那段注释描述的是**被修复的旧行为**。用例 `chatView.test.ts:1705-1724` 已把"inline 在 `.msg-body` 之后"这条旧断言删除，并正向断言"inline 在 `.msg-body` 之前（F1 修复后转绿）"。
- 运行时"仍在底部"的真实成因（**两个与锚点降级无关的机制**）：
  1. **宿主块本身在最底部**：inline 挂在 `activeAssistantEl`（最新消息），该块位于会话末尾——锚点再"靠上"，块也在底部。`[实锤]`
  2. **process-flow 抢在 inline 之前占同一锚点**：`meta` 到达即 `prepareFlowShell` → `renderProcessFlow` → `ensureProcessFlow`（`chatView.ts:763-790`）已把 `.process-flow` 插到 `.msg-body` 之前；随后 `plan_update` 才把 `.plan-inline` 也插到 `.msg-body` 之前。两次都是"插在 body 前"，**后插者更靠下** → 运行时 DOM 顺序 = `[label][process-flow][plan-inline][msg-body][footer]`。`[实锤]`
     - 佐证最终态：`finalizeRound` 时 `enableRoundBlock`→`insertBeforeBody(rb)` 再把 round-block 插到 body 前、并移除 process-flow → 得 `[label][plan-inline][round-block][msg-body]`，即 inline 落在 **"角色名与折叠块之间"**——**正是用户说"任务完成后位置合理"的那个位置**。`[实锤]`
  → 结论：**运行时 inline 排在平铺过程之下（近底部），完成后因 process-flow 被折叠块替换而"上浮"到角色名与折叠块之间**。两个现象同一机制。`[推断，高置信]`

### 2.4 "点击无反应" 与 "只显示当前步骤"

- **inline**：`renderInlinePlanBoard`（`chatView.ts:300-330`）只 `createElement` + `textContent`，**零事件监听、无 `<details>`** → **设计上不可交互**；文案恒为 `N/M + 🔵 + active 描述前 28 字`（`chatView.ts:319-327`）→ **设计上只显示当前步**。`[实锤]`
- **global**：每步是 `<details>`（`chatView.ts:368-408`），**本可展开**（`summary` 有 `cursor:pointer`，`chatStyles.ts:1268-1271`），但因 2.2 被滚出视野 → 运行时点不到。`[实锤]`

### 2.5 Q2 结论

> **技术事实**：运行时两条轨皆渲染；global 因在滚动容器内被卷走、运行时不可达；用户可见的 inline 是**设计上的弱交互轨**（单行 / 无监听 / 只显示当前步）。"底部"由"宿主块在末尾 + process-flow 抢锚点"共同决定，**与 F1 锚点降级无关**。
> **产品定位（是否该合并为单轨 / 放顶部常驻 / 加交互）→ 交产品经理**（已有 `tasks/方案-任务进度UI定位重梳理-20260917.md`）。

## 最小修复建议（只给方案，不改代码）

### 方案一（首选，治 B1/B2/B4 同源）：把 `step_boundary` 的检出对齐到"本迭代工具执行之后的 plan 状态"
