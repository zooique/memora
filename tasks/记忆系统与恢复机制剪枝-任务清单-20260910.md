### 目标
`RecalledMemorySummary`（AgentChunk 载荷）、`ProcessRecallItem`（过程事件）、`metrics.recallCount`（指标）三者构成一条**自动召回展示链**。自动注入退役后（`recallAndInject` 返回恒空数组），该链**零生产**——chunk 永不 emit、过程事件永不产生、`recallCount` 恒为 0。

工具化后「召回了什么」已由 `memory_search` 的 `tool_start` / `tool_result` 过程事件天然展示，本链属**冗余僵尸**。

## P0-B 🔴 SessionCheckpoint 跨重启恢复退役

### 目标
按「断电优先」裁决，**跨重启不再恢复暂停态**：进程死亡即视为非自愿中断，走「中断轮收场 → 重开」。`SessionCheckpoint` 持久化降级为**同进程内存态**（仅支撑暂停/超时判定），跨进程上下文一律靠 Round 记录（唯一物理真理源）。

### 冲突实锤
`src/agent/agent.ts:253-257`：
```ts
const persistedCheckpoint = this._sessionManager?.loadPersistedCheckpoint();
if (persistedCheckpoint && persistedCheckpoint.status === 'paused') {
  await this.restoreFromCheckpoint(persistedCheckpoint);   // ← 恢复暂停态，违反裁决
}
```
代码无法区分「优雅暂停后关闭」与「断电前恰好暂停」，按「以断电为标准」应一律不恢复。

### 职责归属判定（评估结论）
| 职责 | 新范式下归属 | 判定 |
| --- | --- | --- |
| `hotMemory` | step 原子落盘 + `appendInterrupted` 打捞已覆盖 | 🔴 重叠，退役 |
| `plan`/`stepLog`/`completedToolCalls` | 收场重开后进度不再「续」，靠记录让 AI 自接 | 🟡 降级 |
| `pauseMeta` | 注释自承「仅含展示信息」(`sessionManager.ts:878`)、「供重启恢复展示」(`assembler.ts:322`) | 🟡 持久化退役 |
| `pausedAt`/`lastHeartbeat` | 同进程暂停超时（`PAUSE_TIMEOUT_MS = 30min`）仍需 | 🟢 留内存态，退持久化 |

### 执行步骤（三步，风险递增，逐步验证）
1. ✅ **删内核自动恢复**（`agent.ts:255` paused 分支）——**已落地（2026-09-10）**。~~改为：加载 checkpoint 仅用于状态机对齐/事件发射，不 restoreFromCheckpoint。~~
   > ⚠ **计划缺陷修正（执行时发现，已按验收口径处理）**：原文字写「保留状态机对齐」，但 `loadPersistedCheckpoint` 自身的对齐分支会 `stateMachine.pause()` + 启暂停超时定时器——即**仍会把重启后的会话置回 paused**，与本节验收口径「断电/重启后不再自动进入 paused」直接矛盾（原文与验收口径自相矛盾）。实测亦证实：只删自动恢复会留下**不自洽中间态**（状态机 paused 但 loop 无热记忆/闭环节点锚点 → `resumeExecution` 半途续跑并把补充输入**分裂成新轮**，TS-9 重启用例 1 轮 → 2 轮）。故同批**去掉 paused 回填**。
2. ✅ **宿主提示降级**（`chatPanel.maybeOfferCheckpointRestore` / `isRestorableCheckpoint`）——**已落地（2026-09-10）**。~~保留「有未完成 plan 的任务」提示（任务原地续做仍有价值），去掉「paused/error 一律提示」。当前实现 `cp.status !== 'running' → true` 需收紧为「仅 plan 有 pending/active」。~~
3. ⏳ **`SessionCheckpoint` 持久化降级为内存态**——跨进程不再落盘恢复；`pauseMeta` 持久化随之下线（同进程内存态足够）。

### 验收口径
- 断电/重启后**不再自动进入 paused**；中断轮走 `appendInterrupted` 收场为正常 turn。
- 有未完成 plan 的任务仍提示续跑（保留价值路径）。
- 暂停超时归档（30min）在同进程仍生效。
- 全量测试绿（注意：涉及 checkpoint 的测试需同步调整，预计改动面较大）。

### 风险
- **高**。涉及内核状态机 + 宿主恢复协议 + 暂停超时 + 既有测试群。
- **体验取舍（用户已确认接受）**：「暂停 → 关程序 → 重开」不再恢复暂停态，变为收场重开。
- 建议**第 1 步独立提交**（删自动恢复），观察后再推进 2、3 步。

## P1-B 🟡 minFallback 显式化 + 温召回短路

### 背景
`checkpointRestoreCoordinator.warmRecall()` 是 `recall()` 唯一生产消费者（断点恢复的温记忆召回）。两处待改进：

1. **`minFallback` 隐式吃默认值**：`recall(...)` 未显式传 `minFallback` → 隐式取 `DEFAULT_MIN_FALLBACK = 2`（`recallDefaults.ts:7`）。违背「显式优于隐式」，且读者无法判断是「有意兜底」还是「忘了关」。
2. **缺短路**：只要 `mainGoal/currentGoal` 非空就召回一遍记忆库 + touch 写盘。但会话 ≤ `HOT_MEMORY_MAX_ROUNDS`(20) 轮时，热窗口已覆盖全部历史，温召回纯属多余。

### 执行步骤
1. 恢复路径**显式传参** `minFallback`，并注释说明「恢复场景为何保留兜底」（恢复时 LLM 无工具机会，零记忆会丢失任务连续性）。
2. 加**短路判断**：历史轮次 ≤ `HOT_MEMORY_MAX_ROUNDS` 时直接跳过温召回（省一次存储查询 + 写盘）。

### 验收
- 恢复路径显式传参可见；≤20 轮场景温召回被跳过（补测试断言）。
- `minFallback` 取值（0 纯语义 vs 2 宁滥勿缺）**待用户拍板**——本任务先做显式化，值可后续调整。

### 风险
- **低**。短路为纯收益；显式化不改行为（同值）。

## P0-B 第 3 步评估：SessionCheckpoint 持久化降级为内存态（2026-09-10，**不建议按原文执行**）

**备选方案**：
- **A（推荐）**：**保留** `SessionCheckpoint` 持久化（它是「未完成 plan 续跑」这一保留路径的载体），仅**清理 `pauseMeta` 持久化**（展示字段，同进程内存态足够）+ 同步注释。改动面小、零功能损失。
- **B**：完整评估「checkpoint 持久化到底还服务哪些路径」后，若确认「未完成 plan 续跑」也应退役，则第 2 步应与第 3 步**合并重做**（先删提示路径，再降级持久化），而非分步——**当前分步顺序本身有缺陷**。
- **C**：暂缓，维持现状（第 1、2 步已达成「断电优先」主要目标，第 3 步属边界清理）。

**待萧然拍板**：选 A（小改清理 pauseMeta）还是 B（重新评估续跑路径去留）。
