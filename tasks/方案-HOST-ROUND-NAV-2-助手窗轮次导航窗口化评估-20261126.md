# 助手窗轮次导航窗口化评估（HOST-ROUND-NAV-2）

> **状态**：⏳ 观察 · **暂不实施**（2026-11-26 用户拍板：现状够用）。
> **台账条目** → [待完成任务.md](./待完成任务.md) 的 `ROUND-NAV-WINDOW-1`。
> **关联真源**：`hosts/memora-vscode/src/webview/helpers/roundNav.ts`（导航逻辑单点）、
> `hosts/memora-vscode/src/webview/styles/chatStyles.ts`（`#roundNav` 样式与形态隐藏）。

## 1. 背景

- **工作会话（self）**：右侧 `#roundNav` 是「全量条 + 压密」——每轮用户输入一根横条，轮数多时先压间隙、再压条高。几十轮的日常场景够用。
- **memora宝（assistant）**：一个会话理论上会累积**上百轮**。同一套压密逻辑在上百轮会把条压到 3px 高 / 1px 间隙，既看不清也点不准，所以 2026-11-20 拍板**整条隐藏**。
- **用户诉求**：偶尔想翻阅宝会话的历史记录，隐藏后体验不友好，故一度想翻案（在宝形态也显示）。

## 2. 现状事实（代码层）

`#roundNav` 实际是**两层**，不是单一「小点」：

1. **条列** `.round-nav__track`：右缘一列横条，全量渲染 + 压密。压密真源 = `computeDensity()`（先压 `gap`、再压 `barH`，极端兜底为轨道自身滚动且滚动条隐藏）。
2. **hover 预览** `.round-nav__list`：鼠标悬停展开的文字预览列表，**全量渲染**每轮一条、可滚动、当前项高亮。

其它真源点：

- **采集**：`collect()` 每帧全量 `querySelectorAll('.msg.user')`。
- **重建判据**：`sync()` 仅在「全量预览文本签名」变化（`signatureOf()`）时才 `rebuild()`。
- **高亮映射**：`refresh()` 依赖 `bars[i] ↔ cachedWrappers[i]` **同序对应**。
- **形态隐藏**：`chatStyles.ts` 中 assistant 形态下 `.round-nav` 整条 `display:none`（2026-11-20 拍板）。

## 3. 需求本质

要的是**低频「按需翻阅」**，不是高频「常驻导航」。这决定了「把常驻条列修好搬过去」是过度设计的方向。

## 4. 两档方案

- **第一档（最小、不带伤）**：`computeDensity` 改为「装得下就逐字不变 / 装不下就固定条高 + 固定间隙 + 轨道滚动」；轨道略加宽以容纳细滚动条；滚轮仅在指针悬停轨道时接管滚动（不逐轮跳转、不抢页面滚动）。
- **第二档（窗口化）**：条列只渲染**当前轮附近 N 根**，滚轮移动窗口，全量由窗口滑动覆盖。

## 5. 三原则评估

- **SSOT**：改造**公用的** `#roundNav` 优于另造第二套轮次列表——后者等于让「找轮次 / 预览文本 / 定位」多出一份实现，必漂移。两档都只动 `roundNav.ts` 一处策略。
- **自然生长**：复用既有 `collect()` / `refresh()` / `applyMetrics()` / 点击委托，不新增协议字段、不新增组件。
- **不带伤**：`count ≤ N` 时行为**逐字等于旧实现**，工作会话常见轮数零变化；宝形态从「整条隐藏」变为「可用」。唯一需要显式改判的是 2026-11-20 的隐藏拍板（改判需连同断言一起改，见 §6.3）。

## 6. 第二档任务量（本次评估重点）

### 6.1 改动面（按文件）

| 文件 | 改什么 | 量级 |
|---|---|---|
| `helpers/roundNav.ts` | 新增窗口起点状态；`rebuild` 全量 → 窗口渲染；`refresh` 加「active 移出窗口 → 移窗」；`applyMetrics` 压密 → 固定尺寸算 N；新增 wheel 监听 | 核心·大 |
| `styles/chatStyles.ts` | 轨道宽度 / 滚动条策略；宝形态解隐藏（移除 assistant 隐藏项） | 小 |
| `helpers/__tests__/roundNav.test.ts` | 现有断言依赖「条数 = 轮数 / 压密常量」，窗口化后条数 = N 根、压密常量作废 → 大改 + 新增边界 | 大 |
| `__tests__/assistantFormView.test.ts` | 「整条收起」断言改判 | 小 |
| `__tests__/chatView.test.ts` | 端到端窗口跟随 / 点击跳对轮 | 中 |

### 6.2 三个「带伤级」隐藏坑

1. **重建判据不含窗口起点 → 滚轮移窗静默失效**：`sync()` 的签名只由全量预览文本组成，滚轮移动窗口时预览没变 → 签名不变 → 不重建，条列纹丝不动。必须把窗口起点纳入重建判据。
2. **`bars[i] ↔ cachedWrappers[i]` 同序假设被打破**：窗口化后条只有 N 根，映射须改为 `wrappers[windowStart + i]`。改错 = 高亮亮错轮、点击跳错轮，属直接用户可见伤害，须显式映射 + 测试钉死。
3. **hover 浮层与条列变成两套滚动**：浮层独立滚动容器、全量渲染。条列窗口化后若浮层不跟随，会出现「条在滚、浮层仍全量滚动」的割裂。要么浮层也窗口化（工作量再加），要么明确浮层保持全量并登记技术债。

### 6.3 测试影响

- 现有 `roundNav.test.ts` 的镜像守卫（条高 / 间隙上限与令牌同值）因「不再压密」而失效，需重写判据。
- 新增边界：active 在窗口首 / 尾、滚到最顶 / 最底、点击窗口内条目跳对轮、`count ≤ N` 时逐字等于旧行为（不带伤验收线）。
- 变异验证：拆掉「窗口起点纳入重建判据」→ 对应用例必须转红。
- 改判登记：`assistantFormView.test.ts` 的「整条收起」断言须显式改写为「显示」，不是删断言凑绿。

### 6.4 治标真相

窗口化只优化「渲染多少」，**不优化「采集多少」**：`collect()` 每帧仍全量扫 DOM，`signatureOf()` 仍全量拼签名，成本随轮数线性增长。真要根治须让宿主下发 round 列表（数据源化），属另一个更大的工程，不应并入本刀。

## 7. 结论与重启触发

- **暂时不做**：现状（工作会话够用、宝形态隐藏）在用户当前使用强度下可接受。
- **重启触发**（任一即升档）：
  1. 宝会话实际累积到一屏以上（约 ≥ 15 轮）且用户反馈「翻阅历史不便」；
  2. 第一档真机被判定不够用（上不了第二档时再评估）；
  3. 后续需要根治采集成本（届时连数据源化一并设计）。
- **重启时的顺序**：先做第一档并真机验收；第二档、浮层窗口化、collect 数据源化**各自单列、不合并成一刀**，避免出问题无法定位是哪一面带伤。
