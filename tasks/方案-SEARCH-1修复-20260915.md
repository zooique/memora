### 2.2 最锋利的一条（直接锁死 F2/F3/F5 的定性）

> **"The tool usually knows more than the harness passes on. Three states arrived, two survived, and the surviving pair could not represent the case that mattered."**

配 ripgrep 的既有事实：**exit 0 = 有匹配 / 1 = 无匹配 / 2 = 出错**（三态）。本仓对应：

| ripgrep 三态 | memora 现状承载物 | 结果 |
|---|---|---|
| 1 无匹配（**可信的零**） | `matches = []` | ✅ 可表达 |
| 有匹配但被截断 | `truncated: true`（逐条挂载） | 🟡 **零命中时与上者同形**（F2） |
| **2 出错 / 未完成检索** | `catch → return []` | ❌ **与"可信的零"逐字同形**（F3） |

→ **"三态到达，两态存活"** 就是 SEARCH-1 的完整定性。修复 = 补齐第三态 + 给截断加载体。

## 四、决策点拍板

### D1 · 多词语义 → 拍 **C：精确优先 + 零命中回退**

#### 候选与实测（真机语料 34 文件 + 真机 13 条 content query，复刻真实算法）

| 策略 | 语义 | 零命中 | 前缀一致性（零精度退化） | 回退面 | 路径型 query 噪声 |
|---|---|---|---|---|---|
| 现状 | 整串字面量 | **4** | — | — | 3 条（无误伤） |
| **A** 纯 OR | 任一分词命中 | 0 | **6/13 退化** | 全量 | **3 → 20（炸）** |
| **B** 两桶恒并轨 | 精确桶 + 放宽桶 | 0 | **8/13 退化** | 全量 | 20（炸） |
| **C** 精确优先 + 零命中回退 | 整串命中则原样；整串零命中才放宽 | **0** | **13/13 ✅** | **4（= 现状零命中数）** | **3（= 现状）✅** |

纯 OR 的精度退化实例（真机）：`一、这个项目到底要做什么` 1 → **20**；`技术栈选型` 4 → **20**；`§4.2` 2 → **16**。

#### 四条零命中的**真实成因**（实测，非推断）

| query | 成因 | 逐词存在性证据 |
|---|---|---|
| `技术栈 FastAPI Next.js PostgreSQL` | **F1 多词（空格）** | `技术栈`=8 文件 / `FastAPI`=5 / `Next.js`=3 / `PostgreSQL`=3，**四词各自都在** |
| `FastAPI PostgreSQL` | **F1 多词（空格）** | 两词各在（5 / 3 文件） |
| `四、读者会体验什么` | **近义措辞差（非多词）** | 语料写的是 `读者体验旅程图`；`读者`=16 / `体验`=14，但 `读者会体验` **连续串 = 0** |
| `读者会体验` | **近义措辞差（非多词）** | 同上 |

> **重要发现**：4 条里只有 **2 条**是 F1 本体（多词），另 **2 条**是「概念明明存在、措辞差一个字」的近义失配。**两者都被 C 的回退统一修复** → C 的收益面**大于**F1 本身，正对用户原始抱怨「搜不到明明存在的词」。

#### D1b · 回退词表必须用 **R5（显式片段优先）**

v3 初版直接复用 `extractKeywords`，实测暴露**新带伤**：

```
extractKeywords("技术栈 FastAPI Next.js PostgreSQL")
  → ["技术","fastapi","next.js","postgresql","next","js"]
                                        ^^^^^^ ^^^^  碎片！
```
根因：`recall.ts:19` 的英文补充 `input.match(/[a-z]{2,}/gi)` **在 `.` 处切断** `Next.js` → `next` + `js`；`js` 会匹配一切 `JSON/Node.js`。实测 **20 条回退命中里 10 条纯靠 `js` 命中**（`| 运行环境 | Windows + Node.js |`）——**假阴性换成了假阳性**，同样违反诚实化。

| 词表构造 | `技术栈 …PostgreSQL` 碎片词 | 纯碎片命中 |
|---|---|---|
| R0 `extractKeywords` | `["next","js"]` | **10 / 20** |
| **R5 显式片段优先** | **`[]`** | **0 / 20** ✅ |

**R5 不变量（供测试断言）**：
1. **空白分隔片段是一等公民**——纯 ASCII 片段**原样保留、不二次切分**（`Next.js` 保持 `Next.js`）；
2. 含 CJK 的片段走 `extractKeywords`（复用内核分词原语，不新造分词器）；
3. 词表内**不得出现原查询中不存在的 ASCII 碎片**（`js` / `next`）。

**落地细化（实现时新增的三条守卫，2026-09-15）**：
- 探针 R5 的第三条分支（多段时再对整串 `extractKeywords`）实测**恒冗余**，且会把 `/[a-z]{2,}/gi` 的碎片路径重新引进词表 → **实现中删除该分支**；
- ASCII 分支补 `length >= 2` 守卫（与 `extractKeywords` 自带守卫**同源**，不另立第二条标准）：否则 `"a b"` 会产出 `a|b` 级正则 → 命中几乎每一行（**假阳性**）。该守卫对所有已测词**中性**（实测词长均 ≥ 2）；
- 词表**大小写不敏感去重、保留首次写法**（`TODO todo` 不产出两条等价分支）。

#### 为什么不选 AND
`search_memories mode="near"` 用 AND（`keywords.every`），但项目内容搜索**不可照搬**：AND 结果集 ⊆ OR 结果集，**AND 只会更少召回** → 直接放大 F1 本体（只命中一个词的文件被丢弃）。用户原始场景正是被"全含语义"放大出来的。

#### 尾注 · regex 模式登记为候选（本次不做）
主流（N4）默认 regex + `literal` 开关，本仓是**逆向**（只 literal 且谎称 regex）。但**翻转为 regex 默认必须先有第四态**：LLM 生成的非法正则会 `new RegExp` 抛错，若此时仍是 `catch → []`（F3），就又把"查法错了"变成"不存在"——**制造新带伤**。故：**先修 S1（三态通道），regex 开关单独立项**（§七登记）。

### D2 · 接口形状 → **必须一次改完**（发版前零成本窗）

```ts
// src/project-search/types.ts —— searchText 返回对象化（破坏性变更，发版前）
export interface ProjectTextSearchResult {
  matches: ProjectTextMatch[];
  /** 扫描/结果被截断 → 零命中或少量命中都**不代表"不存在"**（给 F2 载体） */
  truncated: boolean;
  /** 截断主因 —— 内核据此分叉文案（修 F5） */
  truncatedBy?: 'results' | 'files';
  /** 已扫描文件数（宿主**上报数据**，非共享常量；见 D4） */
  scannedFiles?: number;
  /** 因超大文件被整文件跳过的数量（修 F4-lite） */
  oversizedSkipped?: number;
  /** 单文件命中曾被 3 条上限截断（修 F6） */
  perFileCapped?: boolean;
  /** 检索自身失败（超时/异常）≠ 真零命中（修 F3）——与 matches=[] 正交 */
  failed?: boolean;
  /** 整串未精确命中、已放宽为分词匹配（修 F1）——结果**非精确**命中 */
  relaxed?: boolean;
  /** 放宽时实际使用的词（供文案"已按 … 放宽"，也给 LLM 判断放宽是否合理） */
  termsUsed?: string[];
}

export interface ProjectTextSearchOptions extends ProjectFileSearchOptions {
  pattern: string;
  /** 内核分词 SSOT 产出的放宽词表；宿主**仅在整串零命中时**启用，未提供则不放宽 */
  terms?: string[];
}

export interface IProjectSearchProvider {
  searchFiles(options?: ProjectFileSearchOptions): Promise<ProjectFileMatch[]>;
  searchText(options: ProjectTextSearchOptions): Promise<ProjectTextSearchResult>;  // ← 形状变更
}
```

**为何"一次改完"**：`IProjectSearchProvider` 是 `src/index.ts:171-177` 的**公开导出**，而 v3.0.0 **尚未发 npm**。现在改 = 破坏性变更**零外部成本**；发版后改 = semver 破坏 + 宿主迁移 + 双形状并存期。F1（`terms`）与 F2/F3/F5/F6 应**合并为同一次接口变更**，否则要付**两次**破坏性变更。

**⚠️ 明令禁止的替代方案**：用「可变 options 回写」（provider 往 `options.truncated` 上写）代替返回形状。`walkText` 内部确用可变 `counter` 传计数，但那只在**单个实现内部**；提升为**跨宿主接口语义** = 未来宿主静默忽略 → **正是 F2 这一类的静默假阴性**。返回形状是自明的，忽略不掉。

**放宽的判定落在宿主**（只有宿主知道扫了多少）：内核**总是**下发 `terms`，宿主执行 `整串 → 0 → 用 terms 放宽` 并回报 `relaxed/termsUsed`。

**落地细化（防双轨，2026-09-15）**：内核文案里的「已按 … 放宽」**只**从 `result.termsUsed` 取值，**不得**回退到调用方自己下发的 `terms`（两份副本需保持一致 = 双轨镜像）。守卫 = 差分 mock：宿主回报 `['zebra']` 而内核下发 `['核心','愿景']`，断言文案含 `zebra` 且**不含** `核心`。
（同源论据：`truncated` 的判定也一直在宿主 —— `projectSearchProvider.ts` 的 `shouldStop`。**内核不自作主张猜"该不该放宽"**。）

### D3 · >64KB 文件 → **两档分步**

| 档位 | 内容 | 风险 | 收益 | 归入 |
|---|---|---|---|---|
| **F4-lite** | 只报数（`oversizedSkipped`），**IO 零改动** | 极低 | 消除"静默"：LLM 知道还有未检索的文件 | **S1（随接口批）** |
| **F4-full** | `size` 预检**挪到 `readFile` 之前**（`stat` 在 `:216` 已拿到）+ 部分读（`fs.open` + `read` 前 64KB） | 中（唯一动 IO） | 真正达成 `:33` 宣称的内存保护 + 大文件**可搜**（对齐 `:174` 声明的"只读前 N 字节"意图） | **S2（单列）** |

F4-full 必带 **UTF-8 字节切分边界收口**（按 `lastIndexOf('\n')` 回退，避免 `\uFFFD` 进 `preview`）。

**本仓实测背景（为何 F4 是真伤）**：600 文件中 **24 个（4.00%）> 64KB**，被挡住的恰是最该被搜的——宿主最大源文件 `chatPanel.ts`(159KB)、`docs/architecture/agent-design-philosophy.md`(87KB)、`role-pack-spec.md`(78KB)、**全部工作日志**（65–131KB）；`src/agent/toolExecutor.ts` = 62.6KB，距上限**只剩 1.4KB**。

### D4 · `MAX_FILES_SCANNED=500` → ⚠️ **推翻原建议，改为"数据上报"**

**原建议（审查文档 §四·D4）**：上收为内核导出常量（类比 `PROJECT_SEARCH_RESULT_MAX_LEN`）。

**对抗式审查结论：不成立。** 二者**性质不同**：

| 常量 | 内核是否亲自 enforce | 归属 |
|---|---|---|
| `PROJECT_SEARCH_RESULT_MAX_LEN = 100` | ✅ **是** —— `toolExecutor.ts:966` 亲自 clamp | 内核（导出合理） |
| `MAX_FILES_SCANNED = 500` | ❌ **否** —— 内核**从不扫描**；纯宿主内部预算 | **宿主** |

把它提升为内核常量 = 让内核持有一个**它无权决定**的宿主实现细节 = **跨层镜像**（带伤模式「双轨镜像」），且下游换来的是"两个宿主必须共享同一个魔法数"的耦合。

**正确解法（已并入 D2 形状）**：宿主把 `truncatedBy` + **`scannedFiles` 作为数据**回报；内核文案用**宿主上报的数字**，而非自己持有常量。

→ **派生出一条可复用的判定律（建议登记）**：
> **宿主内部预算量不得提升为内核常量；只能以"结果对象数据"形式上报。内核只持有"它自己要 clamp/enforce 的量"。**

| # | 改动 |
