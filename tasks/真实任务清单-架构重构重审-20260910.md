## 二、唯一真实候选：F3「LLM 调用」族（需进一步论证）

### 2.1 为什么 `callLlmWithRetry` 与上面 10 个不同

它的 7 个触点**全是「可注入的协作者」，没有一个是 loop 自己的可变状态**：

| 触点 | 次数 | 性质 | 可否显式注入 |
|---|---|---|---|
| `metrics` | 5 | 共享可变对象（计数） | ✅ 传入引用即可（本就共享） |
| `strategy` | 4 | **只读**策略快照 | ✅ 传入 |
| `contextManager` | 3 | 独立类实例 | ✅ 传入 |
| `tracer` | 2 | 独立接口 | ✅ 传入 |
| `toolExecutedThisTurn` | 1 | **只读**快照 | ✅ 传入 |
| `resolveProvider` | 1 | 同族私有方法 | ⚠️ 一并搬 |
| `_waitForRetryWithAbort` | 1 | 同族私有方法（32 行，触点 0） | ✅ 一并搬 |

**结论**：`callLlmWithRetry`(**196 行**) + `resolveProvider`(**19 行**) + `determineTaskType`(**30 行**) + `_waitForRetryWithAbort`(**32 行**) = **~277 行**，是**真正可搬的第二块**，且触点全为「传参可解」。

### 2.2 但要先答三个问题（否则不启动）

| # | 问题 | 判据 | **实测答案** |
|---|---|---|---|
| 1 | **`metrics` 是共享可变对象**——搬走后计数是否仍正确？ | 须确认是「引用共享」还是「值拷贝」 | ✅ **已实测**：`private metrics = new LoopMetrics()`（loop.ts:363）是**类实例字段**，`getMetrics()`（:2225）**逐字段读它** → **引用共享**。传入 `LlmCaller` 后计数仍写同一实例 → **安全**。⚠️ 但注意 `LoopMetrics` 类体**自身就在 loop.ts:162-211（49 行）**，且 `this.metrics` 全文件 **30 处**使用（跨 15+ 成员）→ 它是**跨成员共享的度量对象**，不是 F3 私有 |
| 2 | `strategy` / `toolExecutedThisTurn` 是**每轮热切换**——传快照还是传 getter？ | 传快照 = 重试循环内看不到最新策略（行为变化）→ 须传 getter | ✅ **已实测**：`this.strategy.errorHandling` 在**重试循环内被读 3 次**（相对行 33 循环外 / 140·148·165 循环内），循环结构为 `for (let attempt = 0; attempt <= MAX_LLM_RETRIES; attempt++)`（相对 57）。**→ 必须传 getter**（`() => this.strategy`），传快照会在重试中途 `setStrategy` 时读到旧值 = **行为变化**。⚠️ 结论：**传 getter 符合纪律**（触点性质变为「可注入读者」而非「持有状态」），使 F3 **技术上可搬** |
| 3 | 搬走后**收益是什么**？ | 196 行从 2,624 降到 ~2,350（**减 10%**）。**收益是否值这个风险窗口？** | 📊 **待裁**：减 10% ≠ 质变；且 F3 会与 `LoopMetrics`（30 处引用）、`strategy` 热切换产生新接口面 |

**结论**：Q1 已答（**安全**）；Q2 已答（**必须传 getter，技术上可搬**）；**Q3 是唯一未决项——ROI 判断**（搬出 ~277 行、2,624 → ~2,347，值不值一个重构窗口 + 新接口面）。
> **📌 建议**：**暂不启动 P3-2**。理由：① 减 10% 不改变「文件仍 2,300+ 行」的事实；② 会引入 `LlmCaller` 新类 + getter 接口面（复杂度守恒）；③ 按 D6「触发驱动」，当前无真实痛点逼它（无合并冲突、无独立测试需求）。**触发条件**：出现「`callLlmWithRetry` 相关合并冲突」或「需独立测试重试逻辑」时再启动。

### 2.3 附带发现：`LoopMetrics` 是独立候选（不同性质）

`class LoopMetrics`（**loop.ts:162-211，49 行**）是**自包含的度量值对象**——11 个计数字段 + 3 个派生 getter（`hitRate` / `taskSuccessRate` / `taskAvgDurationMs`），**零 loop 依赖**。

| 维度 | 评估 |
|---|---|
| 可搬性 | ✅ **可搬**（纯值对象，无 loop 状态依赖） |
| 收益 | 49 行迁出 + 让「度量定义」与「度量消费」分离 |
| **代价** | ⚠️ **30 处 `this.metrics` 引用点**分布在 15+ 成员——**搬走类定义不改引用点**（引用点写 `this.metrics.xxx`，与类定义位置无关）→ **实际改动面 = 1 处 import** |
| 裁决 | 🟡 **可做，但收益小**（49 行、零行为风险、1 处 import）——属「顺手级」，非「必要级」 |

## 五、本次重审的判据沉淀

1. **「可拆性」的唯一判据是 state 触点，不是行数、不是「族名听起来独立」。**
   ARCH-2 用「族行数 + 职责听起来封闭」判出 F2/F1/F6 三个「大块」，**实测后三个全错**——`executeToolCalls` 16 触点、`buildSystemPrompt` 4 触点、`compressContext` 6 触点。
2. **低耦合 ≠ 值得搬。** 40 个低耦合成员里，只有 6 个有体量；其余是 getter/setter——**搬它们会把「单文件 API 契约」拆成跨文件查找，是负收益**。
3. **真正的可搬对象有一个特征：触点全是「可注入的协作者」（metrics/strategy/logger/tracer），而非「loop 自己的可变状态」。** `callLlmWithRetry` 符合，`executeToolCalls` 不符合。
4. **「撤销一个候选」与「完成一个候选」同等有价值**——本清单 5 个候选里撤销 4 个，**省下的是 4 个高风险重构窗口**。

## 六、诚实边界

- **本文的行数/触点数据均由可复现脚本产出**（对 85 个成员逐一测量），方法学：以「方法声明行 → 下一成员声明行」为界，统计段内 `this.X` 去重数与写操作数。**已知偏差**：① 段边界含末尾注释；② `this.X` 去重会把「只读一次」与「读写五次」视为同一点数（故另有「写」列并列呈现）。**数据为量级判据，非精确计数**。
- **`metrics` 的共享语义（§2.2 问题 1）已由源码实读确认**：`metrics` 为类实例字段（`loop.ts:363`），`getMetrics()` 逐字段读同一实例 → 引用共享、搬走计数仍正确。**Q1 = 安全**；**Q2 = 必须传 getter**（`strategy.errorHandling` 在重试循环内被读 3 次）；**Q3（ROI）为唯一未决项，本文不给结论，交用户拍板**。
- 重申：**Q1/Q2 的「已实测」均指源码直读**（Read `loop.ts` 对应行），非运行期验证；若 F3 启动，仍须以「搬后全量测试零回归 + 变异验证」作最终判据。
- 本清单**不推翻** ARCH-2/ARCH-3 的设计法理（三段式、哲学判据），只**推翻它们对「哪些族可拆」的假设**。
