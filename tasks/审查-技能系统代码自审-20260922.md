#### P2-B 宿主 **UI 面**与**注入面**优先级相反（P1-A 的同源另一面）

宿主内部「解析」恰好 2 处、互为反向（已穷举 `agent.skills` / `agent.rolePackManager` 全部消费点）：

| 面 | 站点 | 顺序 |
|---|---|---|

#### P2-C 技能系统唯一设计文档与实现分叉

`docs/architecture/role-pack-skills-progressive-disclosure.md`：
- §2.3 要求「脚本必须声明 `runtime`」并给出 SKILL.md frontmatter `scripts:` 声明示例（含 `timeout`）——**内核没有任何代码读这段 frontmatter**（全仓 grep `scripts:` 只在该文档命中），真实 runtime 完全由扩展名推断，timeout 只经工具参数。照此文档写角色包 = 写出被静默忽略的声明。
- §2.2/§2.3 的工具参数写成 camelCase（`skillName` / `resourcePath`），实际协议是 `skill_name` / `resource_path`（`builtinTools.ts:615-643`）。

#### P1-D 全局技能池缺「引用契约」+ 缺一致性守卫（原判 P2，排雷后**升级**；2026-09-22 **已修复**）

原判「name 别名不对称，用户手滑打文件名会失败」——**低估了**。排雷后真身是**规范与实现系统性互斥**：

| 事实 | 证据 |
|---|---|
| 全局池 4 个技能 **frontmatter 真名全是中文**（代码审查 / 内容摘要 / 联网搜索 / 角色包制作器），文件名全是 kebab | 逐文件解析 frontmatter 实测 |
| 角色包设定文本的技能引用**唯一合法形式 = 反引号 kebab** | `SKILL_REFERENCE_RE = /`([a-z0-9]+(?:-[a-z0-9]+)*)`/g`（`builtinPackCoverage.test.ts:60`），非 kebab 反引号内容**不参与判定** |
| 全局技能：`read_skill` **只匹配真名**，不匹配文件名 | `skillManager.get:66-68`（`read_skill("code-review")` 实测 → `SKILL_NOT_FOUND`） |
| 内置包「name 与文件名一致」守卫**只扫仓库根 `role-packs/`**，不扫宿主全局技能池 | `ROLE_PACKS_DIR`（`builtinPackCoverage.test.ts:34`） |

⇒ 角色包若要引导「何时用全局技能」，**只能写显示名，且这条路无守卫保护**（2026-09-22 订正：原判「两种写法都不通」属过度断言）：
- 写 `` `code-review` ``（kebab，符合引用格式规范）→ **双重失败**：①反向守卫判**悬空引用 → 测试红** ②`read_skill` 也解析不到（真名是中文）；
- 写 `` `代码审查` ``（显示名）→ **功能可用**：`read_skill` 按 `name` 匹配能命中；但正则不匹配 → **静默不算引用**（不红、也不被任何守卫覆盖）。
- 实测确认：三个内置包的 persona/rules **反引号中文引用为零**，全局 4 技能在设定文本中零引用。

⇒ 后果：「两级技能同构」声明有个空洞——L1 清单同构、L3 链同构，但**设定文本引用契约只覆盖包内技能，全局池是空白**：全局技能可被引用，但只剩「显示名」这一**无守卫**形态（作者写错文件名或改名，无机器发现）。**当前无功能影响**（L1 清单仍能让模型用中文名 read_skill），但这是下一个写角色包的人/agent 必踩的坑。

根因：`name` 字段**一词两职**——既是 UI 显示名（用户看的中文），又是 LLM 引用键（须 kebab）。分离需动数据契约，`SKILL.md` 已定的「kebab = 引用格式」与「中文 displayName」在当前模型里无法共存。

**✅ 修复结论（2026-09-22，对齐主流规范后落地）**

先查证主流（agentskills.io/specification 原文 + 本地 `.trae/skills/` 吸收的 5 个主流技能）：

| 问题 | 主流答案 | 对本方案的后果 |
|---|---|---|
| `name` 只能英文吗？ | **是**。规范限定 `^[a-z0-9-]+$`（小写字母/数字/连字符），且**必须与父目录名一致** | 「中文 name」不合规，原计划保留中文 name 的路线作废 |
| 有没有 `displayName`？ | **没有**。可选字段仅 `license` / `compatibility` / `metadata` / `allowed-tools` | 「name + displayName 分离」方案**不成立**——主流只有一个 `name`，另立 displayName 即自造标准 |
| 中文怎么办？ | 放 `description`（本地主流技能实测：name 全英文 kebab、description 全中文） | 一行不用改 `name` 概念，`description` 已天然承担中文说明 |

⇒ **定案：不做「双职责分离」，直接把全局技能池的 `name` 对齐 kebab**（`code-review` / `summarize` / `web-search` / `role-pack-creator`，与文件名一致）。
理由：① `name` 一词两职是**自造伪问题**——主流里 `name` 职责唯一（机器引用键），中文说明归 `description`；② 分离方案要新增一个规范外字段，属「自造标准」，恰与研究结论相反；③ kebab 后**引用提取器无需放宽**（中文误报问题根本不出现），两类载体 `name` 语义自动统一，P1-A/P2-B 的「两级同构」空洞同时补齐；④ **零用户可见损失**——中文能力仍在 `description` 与 SKILL.md 正文标题（如 `# 角色包制作器`）里。

#### P2-E 空目录残留

`hosts/memora-vscode/src/extension/skills/role-pack-creator/` 下有**全空**目录树 `resources/templates/standard/skills/`（源与 dist 都有，递归 0 文件）。因为为空，L3 索引为空（实测 `listResources` 返回 `[]`），当前无影响；但它与 SKILL.md 第 169 行「`templates/` 是脚本私有资源，非 L3 `resources/` 索引」的声明相冲突，会诱导后人往里放文件（放进去就会被扫进 L3）。
**排雷补充（关键，决定处置成本）**：`git ls-files` 实测该路径**零追踪**（git 不追踪空目录）→ 删除是**纯 FS 操作、零 git 参与**，不触碰「本环境 git rm 不可靠」红线；删后 git status 无变化，须用 Glob/Read 复验。

#### P2-F `getSkillScriptInfo` 不做白名单校验（角色包侧）

实测：`getSkillScriptInfo("project-init","scripts/init-novel-project.mjs")` → `{runtime:'node'}`，而 `getSkillScriptPath` 对同一参数返回 `null`。因调用方（`assembler.ts:734-746`）先查 path 再查 info，该分支不可达；但独立调用者会拿到「看似存在」的信息。

#### 附：`read_skill` 错误文案过时

`toolExecutor.ts:1214` 仍写「角色包未声明该技能」，实际还会查全局池 → 会误导 LLM 放弃重试。

### 2.1 通但需注意（会影响实测判断）

1. ~~**P1-G 宿主无技能热重载入口（最可能干扰实测）**~~ **✅ 已补（2026-09-22）**

## 四、不带伤原则下的推进评估（分批裁决）

### 4.1 分批原则（一句话）

> **改「行为」的项不进实测窗口；不改「行为」的止血现在就做。**
> 依据：待实测的行为必须是**被审过的那个行为**，否则实测结果归因不纯（用户纪律：A-then-B 串行 / 完成一步验证再下一步；「改判据＝造伤，改喂判据的事实＝止血」）。

### 4.8 质量复检发现并修复：热重载命令在对话中会**静默丢弃**请求（2026-09-22）

> 触发：对批次 2/3 落地物做质量复检时，回内核核验自己写的注释断言（**注释不等于证据**），
> 发现断言本身是错的。

**缺陷（实锤，非推断）**：

| 事实 | 证据 |
|---|---|
| 内核在对话中**只暂存带 `source` 的请求**，`undefined`（全量）**不暂存** | `src/agent/agent.ts:1495-1500`：「暂存 source 待锁释放后补执行；**undefined（全量）不暂存——无具体来源，补执行语义不明**」；实证断言 `agent.test.ts:1848`「对话繁忙时 reloadConfig() 无参数不暂存（全量重载无具体来源）」**通过** |
| 带 `source` 的暂存**确实会被补执行** | `agent.test.ts:1833` 通过；运行日志实测 `[INFO] 对话进行中，配置重载已暂存，将在对话结束后补执行 {"source":"skill"}`；消费点 = `Agent.flushPendingConfigReload()`（`agent.ts:514-526`，turn 结束后 `for (const src of pending) await this.reloadConfig(src)`） |
| 初版命令调的正是**无参** `reloadConfig()` | 初版 `extension.ts` 用 `await agent.reloadConfig()` |

⇒ **后果**：用户在对话进行中点「重载技能与角色包」→ 内核在守门处直接抛 `chatBusyError`（**未做任何重载、也不入暂存队列**）→ 宿主 catch 后提示「技能重载失败」。请求**被静默丢弃**，且文案把「根本没尝试」说成「失败」。**用户以为点了、其实什么都不会发生。**

**修复**（宿主侧，判据同源）：

```ts
if (agent.isBusy) {                       // 判据同源：agent.isBusy 读的就是内核守门用的同一个 chatLockManager.isBusy
  await Promise.allSettled([              // 忙碌态两次调用都会以 chatBusyError 结束（守门在任何 IO 前），属预期路径
    agent.reloadConfig('skill'),
    agent.reloadConfig('rolePack'),       // 两条都进 pendingConfigReload → turn 结束后被补执行
  ]);
  vscode.window.showInformationMessage('技能重载请求已提交；若对话仍在进行，将在对话空闲时自动生效');
  return;
}
```
