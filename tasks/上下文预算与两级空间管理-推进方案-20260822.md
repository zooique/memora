## 0. 设计核心复述（一句话）

> 动态轮数替代固定 N 轮；角色包 3 键（`memoryRecallPercent` cap / `minFallback` 装配保底 / `taskLoopLimit` 硬上限）；锚点分级（触发输入独立划块永不压 + 第一条必然在场）+ 两级空间管理（替换 LRU 内核自动 / 压缩交 LLM 兜底）+ 装配时间线互斥（替换产物不被二次召回）+ 三终止（自然/硬上限续接/软上限饱和）+ 装配前判负（输入过大两防线）。

## 第 2 阶段 · 上下文装配：动态预算替代固定 N 轮

> **目标**：`contextPreparer.ts` 从「固定 N 轮」改为「按 Provider 窗口预算动态填充」。这是核心改造，风险集中在**容量来源**与**轮数派生**。

### 2.1 前置依赖：容量来源接续（必须先定）
- 现状：`llm/types.ts` 有 `contextWindow?: number`（静态配置声明）；`config/loader.ts` 读取。**缺的是 runtime 容量**。
- 落地动作：确认装配层能取的「当前 model 窗口」——优先用配置 `contextWindow`，缺失时降级为 `maxContextTokens`（ContextManager 现有硬上限），保证公式可算。
- 涉及：`contextPreparer.ts` + `agent/types.ts`（若需透传）。

### 2.2 预算公式落地（对齐 role-pack-spec §C）
```
可用预算 = 窗口 − 固定开销(system+persona+rules+技能L1+工具schema) − 输出预留(15~20%)
顶级锚点空间 = 本轮用户输入 + 首个回答预留（独立划块，暂以输入长度估算）
完整对话层 = 剩余预算，从最近往回塞
记忆摘要层 = 剩余预算 − 完整对话层占用（≤ × memoryRecallPercent cap）
动态轮数 = 完整对话层能装几轮（派生，无 recentRounds 键）
```

### 2.3 落地动作
1. 新增「预算计算」纯函数（可在 `compaction.ts` 或独立 `budget.ts`，SSOT）。
2. `contextPreparer.ts`：
   - `recallAndInject` 入参从 `recentRounds` 改为「预算上下文」；`getRecentHistory` / `getRecentRoundIds` 改为「按预算容量取轮次集合 + 第一条必在场」。
   - `excludeRoundIds` 改为「完整对话层实际注入轮次集合」（互斥时间线，见 §4）。
3. `loop.ts` `getRecentHistory(rounds)` 签名改「预算/轮次集合」。
4. **第一条必在场**：装配时若第一条超出窗口预算，显式补第一条 + 计入 exclude（文档已标，此处落地）。

### 2.4 验收
- 长/短输入下上下文 token 可控；`contextManager.truncateMessages` 触发率下降；装配不再依赖 `recentRounds`。
- 单测：预算计算边界（输入超大、记忆百分比极端）。

## 第 3 阶段 · 装配前判负（洞 3 落代码）

> **目标**：输入过大在装配前确定性拒绝/降级，不误报为软上限。

### 落地动作
1. `contextPreparer.recallAndInject` 装配入口前，调预算公式算「顶级锚点划走后剩余预算」。
2. 剩余 < 最小可运行阈值（如 ≤ 1 轮正文余量）→ 返回明确的「输入过大」信号（事件/错误码），宿主据此提示（放文件用 `read_file`）。
3. 不占用软上限统计。

### 验收
- 超大输入走独立降级路径；软上限计数不受其污染。

## 第 4 阶段 · 两级空间管理（替换 + 压缩）

> **目标**：落地「先替换（LRU 内核自动）、后压缩（LLM 兜底）」与装配时间线互斥。

### 4.1 替换（第一级，内核自动 LRU）
- 现状：无；需新增「问答闭环正文 → 已存记忆摘要」替换动作。
- 落地动作：
  - 扩展 `compaction.ts`：新增 `ReplaceRoundsStrategy implements ICompactionStrategy`——检测「对话层内轮次超限/越界」时，取该轮 `roundId` 对应已存 round-summary 替换正文；按 LRU（最早先换）；被替换轮计入 exclude。
  - **不暴露为 LLM 工具**（机械动作，内核自动）。
  - `loop.ts` 迭代前微压缩链上，把替换作为第一级、tool_result 占位压缩作为第二级（现有 `ResultReplacementStrategy` 保留为第二级一部分）。

### 4.2 压缩（第二级，LLM 触发 + 内核兜底）
- 现状：`compaction.ts` `ResultReplacementStrategy`（tool_result 占位）已存在；`OffloadCompactionStrategy`（卸载到文件）已存在未接入。
- 落地动作：
  - 新增**压缩摘要工具**（给 LLM 主动调）：对「无已存摘要的执行闭环/超大 tool_result」现场压成临时摘要替换；loop 收尾即弃。工具定义入 `builtinTools.ts`，handler 入 `builtinToolHandlers.ts`。
  - `OffloadCompactionStrategy` 作为超大结果兜底接入（可经策略注入）。

### 4.3 互斥（装配时间线闭合，无需额外机制）
- 现状已天然成立（§0 盘点）。本阶段只是**确保替换产物 roundId 在下一次装配被 exclude**——由 §2.3 的「exclude=注入轮次集合」自动保证，补一个单测锁定即可。

### 验收
- 长 loop：旧轮次先被替换成摘要、无摘要的才压缩；替换后再次装配不双写；loop 收尾压缩摘要丢弃、记忆摘要沉淀。

## 第 5 阶段 · 软上限终止 + 硬上限续接

> **目标**：「摘要层饱和注入收尾信号」+「硬上限触顶报告进度并续接」。

### 落地动作
1. **软上限**：新增确定性预算检测——「完整对话层除顶级锚点外全摘要化 + 摘要层 token 达容量上限」→ 注入收尾信号（system 消息），由现有 handoff 收敛逻辑承接。
2. **硬上限续接**：`taskLoopLimit`（seed/orchestrator）触顶时：报告完成进度 + 列未完成内容（已有进度汇报能力），不等话硬断；下次输入按记忆递归续接。

### 验收
- 软上限触发时 LLM 收敛产出最终交付；硬上限触顶不冷断。

## 关键风险与待确认决策

1. **容量来源**：`contextWindow` 静态配置够不够，还是要 Provider 运行时暴露？→ 阶段 2 前置，需确认。
2. **「第一条必在场」边界**：会话不足预算时自然在场；超预算时是否强制保第一条（牺牲更新轮次）需拍板。
3. **替换的存储来源**：替换取 round-summary 是查记忆索引（`getBySource(ROUND_SUMMARY)`），需确认与 `roundSummaryLoader` 同源的性能。
4. **压缩摘要工具给 LLM 的触发边界**：LLM 主动调 vs 内核自动检测强制，建议 LLM 触发 + 内核兜底双保险。
