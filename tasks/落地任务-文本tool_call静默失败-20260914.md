**SSOT 收敛核心（用户已拍板）**：

```

→ 内核入口 handleTextResponse 检出「文本工具意图」骨架（<tool_call / <function=）→
```

**养分吸收（同上版）**：工具调用=协议（CSDN）；原生 FC 静默降级是业界已知成本，标准做法 = 失败显式 fallback 而非补解析器（Together/MS/litellm）；幻觉工具名必须在注册表校验（TheNeuralBase）。

## 1. 批 1 · 宿主渲染出口纵深防线（`fix` · 独立可提交）

**目标**：`净化前有可读文本 && 净化后为空` → 回退转义显示原文，作为最后防线。

> **定位**：**纵深防线，非主修复**。主修复是批 2-4 的内核收敛；此处仅在批 3/4 修好后仍出现残留全标签时兜底。判据保留但标注为防御性。

### 变更

- **落点**：[renderMarkdown.ts](../hosts/memora-vscode/src/webview/helpers/renderMarkdown.ts) `renderMarkdown()` **内部唯一收口**（1 定义 / 3 调用全在 chatView）。

  - ⚠️ 不用「原文非空」：`---`/`**` 等合法无文本渲染会被误伤，必须用「净化前有可读文本」。
- **Node-safe 契约不变**：不引入 DOM，判据零依赖 markdown 解析结果（只比对前后空/非空）。

## 阶段0 · 本地 LLM 前置：互斥双能力位 + 回落接线（探索中）

> 本批把 `supportsStructuredOutput` 从「僵尸能力位」接到真实消费，作为本地 LLM（Ollama/LM Studio 等）能力的地基。
> 依据：本地运行时是否支持原生 `tools` 协议**无法从现有配置推断**（同是 OpenAI 兼容，有的支持原生 FC、有的只支持文本）。
> 无能力位声明 → 只能「能连但工具判定双轨」→ 复现本批批 3/批 4 收敛的旧伤。故能力位先行，阶段 1/2 才真正"零内核改"。
> 标注：🟡 探索中（可逆设计，验证稳定再定案，见 [探索期决策沉淀规则](../.trae/rules/exploration-decision-sedimentation-rules.md)）

### 目标

工具通道**确定性**选择，本地 LLM 无工具能力时**可观测回落**（不静默、不回文本双轨）：

```

  ├─ system prompt 列工具清单 + buildChatOptions 传 tools（现有原生 FC 路径）
  └─ provider.supportsStructuredOutput == true → buildChatOptions 传 response_format（JSON mode 回落）
     供应商完全不支持工具（两者皆 false）→ 收起工具清单，显式告知链不可用（接批 4 防静默语义）
```

### 变更

1. **能力位定义** [provider.ts](file:///f:/zooique/memora/src/llm/provider.ts)：
   - 新增 `readonly supportsToolCalling: boolean = false`（与 `response_format` 互斥语义对齐，默认 false）。
