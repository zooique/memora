# 真机观测 · 任务表去方框是否伤到 LLM 寻址（待执行）

## 一、为什么要观测（这不是可选项）

去方框的**全部理由**是「ASCII 方框对 LLM 零语义价值，却占 46.5% tokens」。

⚠️ **这是一个推断，不是证据。** 3010 个单测全绿**与它无关**——单测只验证"输出长什么样"，
不验证"LLM 读后怎么做"。而 `task_table_update` 是靠 **序号 `step_id="N"`** 寻址的：

- 原方框版：`│ 1  │ 描述 │ 执行中 │` —— 序号在**独立列**，与描述、状态三列对齐
- 现列表版：`1. 描述 [执行中]` —— 序号在**行首**，与描述同行

若列结构原本帮助 LLM 把「序号 ↔ 描述」绑定，去掉后可能抬高**寻址错位**概率。
**单测证伪不了这件事，只有真机能。**

## 二、待证伪的假设

| | 假设 | 若成立 |
|---|---|---|
| H0（本批依据） | 方框对 LLM 零语义价值 → 去掉只省 token，不掉质量 | 无需动作 |
| H1（反方） | 列结构帮助序号↔描述绑定 → 去掉抬高寻址错位 | 需补偿（见 §五） |

## 三、观测设计

**场景**（各 ≥1 次，越多越可信）：

| # | 场景 | 为什么选它 |
|---|---|---|
| S1 | 小组会议（≥4 步，含 rolePack 切换） | 骨架预置 + 序号寻址 + 角色切换三者叠加，最敏感 |
| S2 | 普通多步任务（≥5 步，无会议） | 对照：纯序号寻址 |
| S3 | 长任务（≥10 步） | 序号超过一位数（10、11…），考验序号解析 |

**观测项与判据**（每次运行记录）：

| 观测项 | 通过判据 | 失败信号 |
|---|---|---|
| **寻址正确率** | `task_table_update` 的 `step_id` **100% 命中目标步骤** | 更新到非目标步（错位） |
| **推进连续性** | active 每轮前移 1 步，无跳步/回退 | 跳步（如 1→3）、反复更新同一步 |
| **寻址形态** | 一律用**序号**寻址 | 出现用「描述文本」当 step_id（说明序号没读出来） |
| **勾选率**（ME-7） | 实际完成的步骤都被标 done | 完成但漏标 / 未完成却标 done |
| **重复建表** | 已有在途表时不再 `task_table_write` 覆盖 | 中途重建表（说明没看见当前任务表） |

## 四、现有观测通道（先认清能拿到什么）

| 通道 | 状态 | 说明 |
|---|---|---|
| `plan.taskTableWriteCount` | ✅ 有 | 内核 `loop.ts` 对 `task_table_write` 累加 |
| `task_table_update` 计数 | ❌ **无** | 2026-09-14 核实：`loop.ts` 只对 write 累加 → **勾选/寻址类只能人工核对对话记录** |
| 对话记录 | ✅ 有 | 最终判据来源：逐轮比对 `step_id` 与目标步骤 |

> 因此本观测**必须人工核对**，不要指望 metrics 自动出数。

## 五、失败时的补偿预案（预先拍定，避免临场摇摆）

| 方案 | 做法 | 代价 | 适用 |
|---|---|---|---|
| **P1（首选）** | 改 **Markdown 表格** `\| # \| 任务 \| 状态 \|` | 装饰字符比 ASCII 方框少约 60%，**保留列结构**，且 LLM 最熟悉 Markdown 表格 | H1 成立但结构确有价值 |
| P2 | 加显式寻址提示（如「更新第 N 步用 step_id="N"」） | 多几 token，不动排版 | 仅序号解析出错 |
| P3 | 回滚 `1affe112` | 恢复 46.5% token 开销 + 三套宽度缺陷回归 | H1 强烈成立且 P1 无效 |
