## 〇、一句话结论

> **设计架构已完成九成减法，代码架构只落到六成。** 本方案的目标不是「把大文件拆小」（那是症状），而是**把设计层已经做过的解构，在代码层做完**——让 `loop.ts` 的物理边界与「turn ⊃ loop ⊃ step」「三阶段」「三级空间管理」这三条设计轴的语义边界**逐一对应**。

### 1.4 调研结论：是否真的需要拆分？

**逐条对照 `.trae/rules/progressive-refactor-rules.md` 与 D6 触发驱动纪律**：

| 判据 | 结论 |
|---|---|
| 是否超阈值？ | ✅ 2,635 行 = 项目自设阈值 1500（`ui.ts` 观察项）的 1.76 倍；89 成员远超 30 经验线 |
| 是否有真实痛点？ | ⚠️ **部分**：合并冲突风险、单族独立测试困难、阅读成本高——但**尚无「因体量导致的实际事故」** |
| 是否预支复杂度？ | ❌ **不是**：拆分不新增抽象层，只做**同层职责归位**（把已存在的族移入同层文件） |
| 范式是否已验证？ | ✅ `contextManager` / `toolRunner` / 14 managers 均为成功先例 |
| 测试是否支撑？ | ✅ **测试全部经公开入口驱动，零私有访问** → 拆分不改测试 |

**裁决**：**需要拆分，但必须绑定触发条件**（见 §五）。理由：这不是「对称性增强」（D6 反对的那类），而是**一个明确超阈值、有已验证范式、且测试成本被实测证明极低的债务**。但**不应急于一次性大重构**——按族分阶段，每阶段独立提交、独立验证。

**同时诚实修正**：经本轮实测，拆分**不能**把 `loop.ts` 降到「~700 行」的想象值（那个数字此前基于虚高的族行数）。**现实目标 ≈ 1,200-1,400 行**——这仍是显著改善（减半），但**不等于「薄」**。真正把 loop 变薄，还需处理**字段声明区（~360 行）**，而那属独立且风险更高的动作，**本方案不含**。

## 二、目标类设计

### 2.1 统一范式（复用已验证的 `ContextManager` 模板）

**核心约束（来自 `contextManager.ts` 的设计注释，原话）**：

> 「ContextManager 不持有 messages 引用（避免与 AgentLoop 状态耦合），所有方法接收 messages 作为参数，是**无状态的纯计算 + 缓存**。」

即：**新抽出的类必须是「无状态纯计算 + 显式入参」**，不持有 loop 的可变状态引用。这是本方案最重要的设计纪律——**若新类持有 `loop.messages` 引用，就只是把耦合换了位置，没有真正解耦**。

### 2.2 P3-1 目标 → `ToolCallHandler` 类设计（首轮，示例）

```ts
/**
 * 工具调用处理器（从 AgentLoop 提取的独立职责）
 *
 * 职责（= 原 F2 族）：
 *   1. 工具调用解析（toolCalls → 可执行项，含 ask_user 识别）
 *   2. 执行编排（逐个/并行执行 + 结果收集 + 幂等判定）
 *   3. ask_user 挂起处理（暂停点识别 + 问题解析）
 *   4. 结果包装（wrapToolResult：错误/超长/隔离包装）
 *
 * 设计理由：AgentLoop 2,636 行超阈值，工具执行是最大的一块独立职责（~486 行，
 * 见 §1.3 实测），职责边界最清晰（输入 = toolCalls，输出 = toolResults）。
 *
 * 自然生长原则（对齐 ContextManager / ToolRunner）：不持有 loop 可变状态引用，
 * 状态经显式入参或只读 getter 传入 —— 便于独立单测。
 * 注：已存在 ToolRunner（单工具执行器）——本类是其**上层编排**（多工具/暂停/包装），
 * 不与之重复：ToolRunner 执行"一次工具"，ToolCallHandler 编排"一批工具"。
 */
export class ToolCallHandler {
  private readonly runner: ToolRunner;               // 复用既有单工具执行器
  private readonly getStrategy: () => L2RuntimeStrategy;  // 只读 getter（策略热切换）
  private readonly tracer: ITracer;

  /** 编排一批工具调用（纯编排：不读写 loop.messages） */
  async executeBatch(
    toolCalls: readonly Message['toolCalls'],
    ctx: ToolCallContext,
  ): Promise<ToolBatchResult> { ... }

  /** 识别是否含 ask_user（暂停点判定，只读） */
  detectSuspend(toolCalls: readonly Message['toolCalls']): boolean { ... }

  /** 解析 ask_user 入参为问题列表（纯函数） */
  parseAskCalls(...): AskQuestion[] { ... }

  /** 包装工具结果为 LLM 可读文本（纯函数） */
  wrapResult(toolName: string, result: string): string { ... }
}
```

> **关键设计点**：已存在 `ToolRunner`（loop 持有，`loop.ts:287`）是**单工具执行器**。本类是它的**上层批量编排**——**不是重复造轮子，而是补齐「多工具 + 暂停点 + 结果包装」这一层**。实施时必须确认边界：`ToolRunner` 保留「执行一个」，`ToolCallHandler` 负责「编排一批」。

### 2.3 决策点：F6 空间管理「并入 ContextManager」还是「新建」？

**这是一个必须用户拍板的架构分叉**：

| 方案 | 内容 | 优点 | 缺点 |
|---|---|---|---|
| **A. 并入** | `compressContext` 等迁入已有 `ContextManager` | 复用现有类，零新增文件；同域（都是上下文空间） | `ContextManager` 会从 ~500 → ~650 行，且它当前是「截断+摘要」，压缩是「主动 LLM 压缩」语义不同 |
| **B. 新建** | 独立 `ContextCompactor` | 语义纯净（「被动截断」vs「主动压缩」是两个动作） | 多一个类；两者都操作 `messages`，可能需要在 loop 里协调调用顺序 |

**第一性原理裁决**：`truncateMessages`（**被动、超限触发、无 LLM**）与 `compressContext`（**主动、LLM 触发、有成本**）的**触发条件、成本模型、失败模式全不同**→ 属**职责正交**，按 §2.3 模式选择标准应选 **B（职责拆分）**。但 `findEarliestRound`/`findLargestToolResult` 是**只读定位辅助**，可留在 loop 或随压缩器走。

**建议**：**B**，但**把 `summarizeForCompression`（调 LLM 生成压缩摘要）保留在 loop**——因为它是 LLM 调用，应与 F3 同族，不属纯空间管理。**此决策待用户确认**。

## 五、后续演进路径

```
本轮（P3-1..P3-4）      逐族迁出 → loop.ts ~1,200-1,400 行（减半，非「薄」）
        ↓
独立立项（本方案外）    分解字段声明区（~360 行）→ 才可能进一步压缩
        ↓
终态（不设时间表）      loop.ts = 纯 step 编排门面
                        agent/ 模块从 40k → 重组为「门面 + 编排 + 专职 managers」
        ↓

        ↓

```

**触发条件（D6 纪律）——满足任一即启动下一阶段**：
1. `loop.ts` 再次出现合并冲突（体量已造成实际摩擦）；

## 附录：本方案的三条硬纪律（防复发）
