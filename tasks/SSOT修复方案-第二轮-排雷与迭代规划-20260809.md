## §0 排雷方法

对第二轮报告的每条修复建议，验证三个问题：
1. **建议所依赖的事实是否成立**（复核报告断言）
2. **修法本身是否引入新风险**（特别是副作用与边界）
3. **修复的完整形态是什么**（避免修一半——尤其是 `void processEvent` 这种牵一发动全身的）

结论分级：✅ 成立可直接执行 / ⚠ 成立但需修正形态 / ❌ 不成立或应放弃。

## §1 逐条排雷

### R1 【P0】`void processEvent` 宿主修复

**复核：✅ 成立**。`chatHandlers.ts:346`（用户回答）与 `:384`（超时自动续跑）两处 `void agent.processEvent(event)`，而 `processEvent` 是 async generator（`agent.ts:818`），不迭代函数体不执行。

**排雷发现——修复形态必须比"加个 for await"更完整**：

宿主已有标准消费模式（`chatStreamHandler.ts:110-111`）：
```ts
const generator = agent.processEvent(event, abortController.signal);
await forwardStream(generator, ctx, messageId, abortController);
```

`forwardStream` 做三件事：迭代 chunk、IPC 转发渲染层、**finally 清理 AbortController**。澄清回答修复若只补迭代而不走这套，会引入两个新问题：

1. **并发闸门失效**：`handleUserInput:77` 的竞态保护判据是 `ctx.getAbortController()` 非空。`SESSION_CLARIFY_ANSWER` 若不占用 AbortController，用户可在澄清回答驱动的执行流进行中发新消息 → 内核 `acquireChatLock` 抛 `chatBusyError`（`agent.ts:470-472`）→ 静默失败。必须先占用、finally 释放，与 `handleUserInput:84-85` 对称。
2. **输出无处可去**：澄清回答后 Agent 会产出一轮完整回复（clarify→chat 转换 + 续跑），当前 handler 不转发 chunk → 用户看到"回答已提交"但看不到 Agent 的后续回复。必须走 `forwardStream` 推流。

**修正后的修法**：
- 抽 `handleClarifyAnswer(answers, ctx)`：占用 AbortController → 构造 `{type:'clarify'}` 事件 → `forwardStream(agent.processEvent(event, signal))` → finally 释放。`SESSION_CLARIFY_ANSWER` 与超时自动续跑两处共用。
- 超时路径注意：`autoResolveClarify` 里 `CLARIFY_AUTO_RESOLVED` 通知仍在 `forwardStream` 之前发出（用户先感知"自动继续"，再看到流），顺序合理，保留。
- **防回归测试**：断言回答后状态机离开 paused / `resetConsecutivePauseCount` 被调 / 回答文本进入对话流。**必须修复前能红**（当前 `void` 下这三个断言全部失败）。

### R2 【P0】`confirmConfigSuggestion` 补 `refreshBootstrapMemories`

**复核：✅ 成立**。`configManager.ts` 内 `deleteRule:346` / `updateRule:393` / `deleteSkill:430` 均调 `refreshBootstrapMemories`，唯独 `confirmConfigSuggestion`（`:138-204`）没有。且 `agent.reloadConfig('rule')` 是显式 no-op（`agent.ts:2393-2397`，"rule 类型由 ConfigManager CRUD 即时同步 bootstrap 段"）——**reloadConfig 这条备用路径对 rule 不存在，confirmConfigSuggestion 缺调用 = 该规则永进不了 bootstrap**。

**排雷确认无副作用**：`loop.refreshBootstrapMemories`（`loop.ts:1257-1260`）是**替换式重建**（`this.opts.bootstrapMemories = memories` + `rebuildSystemMessage()`），幂等。且 `confirmConfigSuggestion` 已先 `index.upsert`（`configManager.ts:199`），回调内 `getBootstrapMemories` 经 `getBySource(RULE)` 必然包含新规则 → 一次调用即同时完成"注入 + 去重"。

**微调**：`confirmConfigSuggestion` 中 `injectSystemMessage(rulePrompt)`（`:204`）在 bootstrap 重建后变成冗余注入（同一规则出现在 messages[0] 和独立 system 消息两处）。建议保留 `injectSystemMessage`（它是当前轮立即生效的兜底）但**不删**——两处来源由 LLM 去重，成本可忽略；删除反而在 bootstrap 刷新失败时无兜底。保持现状 + 补调用即可。

### R3 【P1】索引对账（有 add 无 evict）—— ⚠ 成立但必须限定范围

**复核：✅ 成立**。`loader.ts:63-100` 只 restore+upsert 无对账；`loadAllToIndex` 已返回 `loadedIds` 但无人消费。删除 `rules/*.md` 后 SQLite 行永生并继续注入 bootstrap。

**排雷发现——裸用 `loadedIds` 做差集有暗礁**：

| 事实 | 证据 |
|---|---|
| `Memory` 类型无文件源/运行时源区分字段 | `types.ts:29-39`（id/content/source/name/createdAt/accessedAt/score） |
| 运行时注入 rule 的入口 `addRule` 存在 | `configManager.ts:222-235`（只写 SQLite，不写文件） |
| 宿主生产代码对 `addRule/addSimpleRule` **零调用** | 全仓 grep 仅命中测试 mock |
| 项目文档声称 addRule 是合法运行时注入路径 | `architecture_philosophy_rules.md §10`（"config.addRule() 是运行时注入"） |

结论：**当前生产环境不存在"无文件但合法的 rule"**（addRule 零调用），裸差集今天不会误删。但 `addRule` 是文档化的合法 API，任何未来宿主接入都可能触发误删——对账若按"文件不存在即删"实现，会在未来静默吃掉运行时注入的规则。

**修正后的修法**（三选一，倾向方案 C）：

- **A. 裸差集**：`getBySource(RULE)` 中不在 `loadedIds` 的 → `index.delete(id)`。最简，但把「未来宿主用 addRule」变成地雷。
- **B. 白名单**：对账仅清理 `id` 以 `rule:` 开头且**文件确实不存在**的行，同时把 `addRule` 标记为 deprecated。改动面大。
- **C. 触发时机收窄（推荐）**：对账**只在启动扫描时执行一次**，且**只在 `closeProject`/`initProject` 边界**（项目切换时）用文件差集校正 `rule` 源。运行时注入（addRule）是会话级场景，不跨项目边界，天然避开。实现：`loadAllToIndex` 末尾加 `evictMissing(loadedIds, 'rule')`——注意**只对 rule**（persona/skill 的索引消费面不同，且 deletePersona 有独立修复 R6）。

### R4 【P1】统一 `blocked` 判据

**复核：✅ 成立**。`canContinueWithoutInput`（`agent.ts:1518` `some(s => s.status !== 'done')`）与 `isPlanStalled`（`sessionManager.ts:1056` `every(done||blocked)`）对 `blocked` 判据相反。全 blocked → 按钮可点 → 点击后早退 + 文案撒谎（`agent.ts:1016-1018`）。

**排雷补充——谁对谁错要想清楚再改**：

两个函数的语义其实不同，不能简单"统一成一个数"：
- `isPlanStalled`：**执行决策**——计划是否还有可推进性。blocked 步骤无法推进 → 停滞。**语义正确**。
- `canContinueWithoutInput`：**UI 信号**——是否值得展示"继续"按钮。blocked 步骤点了也白点 → 不该展示。**语义也正确**。

**错的是"继续"按钮的点击路径**：`resumeExecution:1016` 的早退分支在 `canContinueWithoutInput` 为 true 时被触发，说明两者之间存在第三种语义——**"可续跑"≠"续跑有意义"**。

**修正后的修法**：`canContinueWithoutInput` 增加第四个判据——`plan.some(s => s.status === 'pending' || s.status === 'in_progress')`（真正可推进），把 `blocked/done` 排除出按钮显隐。同时修 `:1017` 文案区分"已完成"与"全部阻塞"。`isPlanStalled` 不动（执行语义正确）。

### R5 【P1】`updateStep` 补 `touchCheckpoint`

**复核：✅ 成立**。`agent.ts:1979-1990` 直改 `step.status`（`:1985`）+ 手写 `cp!.lastHeartbeat`（`:1986`），不调 `touchCheckpoint()` → `checkpointDirty` 未置位（`sessionManager.ts:399-402`）→ 非 force 的 `flushCheckpoint`（`:416-418` 有 `if (!force && !checkpointDirty) return`）跳过写盘 → 计划状态变更可能永不落盘。

**排雷确认**：`sessionManager` 内其他所有 `plan` 变更路径均正确调用 `touchCheckpoint`（`updatePlan` 路径 `:1009-1010` 成对出现），唯 `updateStep` 这条漏了——**不是模式问题，是漏抄一行**。修法：`:1986` 改为 `sm.touchCheckpoint()`（它内部已含心跳语义？——需实现时确认 touchCheckpoint 是否更新 lastHeartbeat；若不更新，则 touchCheckpoint + 保留心跳行）。

### R6 【P1】`deletePersona` 只清内存

**复核：✅ 成立**。`personaManager.ts:273` → `configResourceManager.ts:109-118` 只 splice 内存数组。`MemoryLoader` 启动会把 persona upsert 进 SQLite（`loader.ts:21,86`）。

**排雷补充——比报告更深一层**：`deleteRule/deleteSkill` 走了 `configManager`（清 SQLite + 刷 bootstrap），而 `deletePersona` 走 `personaManager`（只清内存）。**两条删除链路结构不同**——persona 的 SQLite 行是 `MemoryLoader` 写入的，`personaManager` 无索引引用，所以"persona 的 SQLite 索引"是个**无消费者的镜像**（recall 排除 persona、bootstrap 不取 persona、仅 `memoryInspector.snapshot:268-269` 读它做展示）。

**修法二选一**：
- **A. 兑现注释**：`deletePersona` 同步 `agentIndex.delete('persona:<name>')`（需要 PersonaManager 持有索引引用——当前无）。
- **B. 收窄注释（推荐）**：persona 索引本就是展示镜像，把 `configFileSyncer.ts:83` / `sprite.ts:806` 的"SQLite 软删除"注释改成"内存缓存删除；SQLite 镜像由重启扫描校正"。**配合 R3 的启动对账，镜像在下次启动自动归位**。

### R7 【P1】`blocked` 文案 + `autoResumeIfPaused` 先于锁

- `agent.ts:829`（autoResume）先于 `:833`（acquireChatLock）→ 锁忙时状态机已翻 running 才抛错。**复核成立**。修法：先拿锁、再 auto-resume（注意：锁获取会绑定 AbortSignal，auto-resume 若在锁内执行需传入 combinedSignal）。
- `:1017` 文案"所有计划步骤已完成"对 blocked 撒谎。**复核成立**，随 R4 一并修。

### R8 【P2】`restoreFromCheckpoint` error 缺失分叉

**复核：✅ 成立**。`:544` 无条件 `resetToRunning()` + `:545` 复合条件 `status==='error' && checkpoint.error`——error 缺失时两分支都不进 → 状态机 running / 检查点 error 永久分叉。

**修法**（报告给的两选一，选后者）：
```ts
this.stateMachine.resetToRunning();
this.syncCheckpointStatus();   // checkpoint.status = stateMachine.status（强制两侧一致）
if (checkpoint.status === 'error') {
  const t = this.stateMachine.triggerError(checkpoint.error?.cause ?? 'unknown');
  ...
}
```
即：**先让检查点状态无条件跟随归零结果，再按实际字段重建**。这样任何字段缺失都不会产生"归零后的残留镜像"。

### R9 【P2】暂停超时定时器恢复路径缺席

**复核：✅ 成立**。`startPauseTimeoutTimer()` 唯一调用点 `sessionManager.ts:620`（`pause()` 内）；恢复路径 `:479`/`:551` 直接 `stateMachine.pause()` 绕过。

**排雷补充——"订阅状态转移"改动面评估**：SessionStateMachine 是纯转移函数式（无事件总线，转移表 4 条 + resetToRunning），给它加"状态变更回调"是**新机制**（构造参数 + 生命周期），复杂度守恒上不合算。更轻的修法：**在两条恢复路径的 `stateMachine.pause()` 之后补 `startPauseTimeoutTimer()`**——两行，与 `pause():620` 对称，不引入新抽象。

**对抗式审查**：恢复的 paused 会话距上次暂停可能已接近超时阈值，补启动定时器后 `checkPauseTimeout` 立即检查 `isPauseTimedOut`（`sessionManager.ts:1367-1371`）→ 已超时则自动清理 → 行为正确（该会话本来就不该恢复）。无副作用。

### R10 【P2】`restoreFromCheckpoint:564` 悬空 Promise

**复核：✅ 成立**。`loadSessionMessages` 是 async（`messageHistory.ts:264`），`restoreFromCheckpoint` 同步返回 `number`。

**排雷——改异步的影响面**：`restoreFromCheckpoint` 调用方：`agent.ts:1257`（init 流程，可 await）。改 `async` 是**破坏性签名变更**，需同步改调用方 + 返回值语义（现在返回恢复消息数）。折中：**保留同步签名，把 `loadSessionMessages` 的调用从 restore 中移除，改为由调用方在 await 后显式调用**，或内部 `void loadSessionMessages(...).catch(log)` 显式吞掉（接受切换竞态，因为 MessageHistory 的切换本质是"最后写入者胜"，restore 后到下一次 append 之间无其他写入者——竞态窗口实际极窄）。**倾向：显式 `.catch` + 注释说明竞态窗口**，不做签名破坏。

### R11 【P2】`goalVersion` 兑现或改名

**复核：✅ 成立**。全仓无两值比较，真实漂移判据是文本相似度（`goalConsistencyChecker.ts:130-142`）。

**排雷——"兑现"的成本审查**：真做版本校验需要引入"跨进程/跨恢复的目标一致性比对"，当前架构无该消费场景（单 Agent 单进程，goalVersion 的消费方就是事件 payload）。**兑现是臆测性需求，违反复杂度守恒**。**选改名**：`goalVersion` → `goalChangeSeq`（字段名 + 注释 + 事件 payload），一行成本，消除误导性命名。检查点序列化字段同步改名（无 schemaVersion 阶段，改名无迁移成本——**这恰是现在改名的窗口期**）。

### R12 【P2】roundLog 填 stepId

**复核：✅ 成立**。`completeRound`（`sessionManager.ts:973-1011`）不传 stepId；`loop.onRoundBoundary`（`agent.ts:1901-1908`）调用时未提供。`SessionCheckpoint.plan` 步骤有 `id`。

**修法**：`completeRound` 时取 `getActiveStep()?.id` 填入 roundLog 记录。需确认 `onRoundBoundary` 回调签名是否带 step 上下文——若无，`completeRound` 内部从检查点取 activeStep 即可。

### R13 【P3】MemoryRelation 级联清理 —— ⚠ 修法降级

**复核：✅ 问题成立**。`memory_relations` 无 FK（`sqliteRelationStore.ts:22-31`）；`ProjectManager.closeProject:340-344` 的 `agentIndex.delete` 不清关系边。

**排雷——CASCADE 不是银弹**：
- `memories` 主表删除语义是**软删除**（`storageInterface.ts:18`：delete 写 deletedAt，不物理移除）——`ON DELETE CASCADE` 只对**物理删除**触发，软删除不触发 → CASCADE 覆盖不了主场景
- 6 处显式清边（writeDelete/writePurge/deleteRule/deleteSkill/UserProfile）仍是必须的
- 引入 CASCADE 需确认 `PRAGMA foreign_keys=ON` 开启 + 主表外键定义 + 迁移，**复杂度收益比不合算**

**修正后的修法**：放弃 CASCADE。**只补 `closeProject` 的漏清**——`agentIndex.delete(id)` 前先 `relationStore` 按该 id 双向清边（sourceId=id OR targetId=id）。把「6 处清边」的遗漏点补上即可，不做结构性改造。

### R14 【P3】`consecutivePauseTimestamps` 入检查点

**排雷——建议降级为不做（或仅文档化）**：
- 防滥用机制被"重启绕过"的攻击面是本机用户自残，威胁模型极低
- 入检查点会破坏检查点字段的"纯净"（检查点是执行状态，计数是反滥用卫生状态，二者正交）
- 1h 窗口衰减已经自愈

**结论：放弃**，在代码注释里说明"计数为进程内状态，重启归零是设计而非缺陷"。

## §3 明确不做（防方案扩张）

| 项 | 理由 |
|---|---|
| CASCADE 级联删关系 | 软删除不触发 CASCADE；6 处显式清边仍是必须；复杂度收益比不合算（R13） |
| 暂停定时器改订阅状态转移 | SessionStateMachine 无事件总线，引入新机制违反复杂度守恒；两条恢复路径补两行即可（R9） |
| `goalVersion` 兑现为真校验 | 无消费场景，兑现是臆测性需求（R11） |
| `consecutivePauseTimestamps` 入检查点 | 重启归零是设计而非缺陷；计数是卫生状态不是执行状态（R14） |
| `restoreFromCheckpoint` 改 async | 破坏性签名变更，竞态窗口实际极窄，`.catch` + 注释足够（R10） |
