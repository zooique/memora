- **KILLTREE-ESRCH-1** — POSIX 上「进程组已消失」（`kill ESRCH`）被误报为终止失败｜📌 待发版归档（2026-11-12 内核代码 + 用例已落地；唯一剩余 = 内核下一版收据记录「ESRCH 已归类」）｜到期复查 2026-12-01
  **实锤**：宿主 `vscode@0.8.0` 首推 tag 后 ubuntu CI 红，`codeExecutor` 中断用例收到 `终止未确认`。表层修法是宿主补 POSIX `detached`（已做，见 `tasks/archive/0.8.0-host.md` §首推 tag 后的 CI 阻断与订正），但**内核 `killProcessTree` 的 POSIX 分支仍把一切 errno 一律记 `error`**：真实竞态（进程在终止指令到达前自行退出）时 `kill(-pid)` 抛 ESRCH，会被判成「终止失败」，与 Windows 侧已把 `taskkill 128` 单独归入 `alreadyExited` 的语义不对称。
  **目标形态**：POSIX 分支识别 `err.code === 'ESRCH'` → `{ ok: false, alreadyExited: true }` 且 `error` **带原因句**（对齐 Windows 128 分支写法；**仅 ESRCH**；`EPERM` 等表示目标可能仍存活，仍须记 error）；附一条「进程先退出再杀」的稳定用例（跨平台：Windows 走 taskkill 128 分支、POSIX 走 ESRCH 分支，各自断言 `alreadyExited === true`）。
  **2026-11-12 复核订正（error 不再留空）**：初版实现按「error 留空」落地，复核判定为技术对称性缺陷——留空使消费端 `terminationError = r.error ?? '进程树终止未确认'`（`skillScriptRunner.ts` `onAbort`）把同一个「已先行退出」语义写成「未确认」，并在中断路径继续打「中断时进程树终止失败」WARN（正是 128 分支刻意避免的噪音）。现改为 `'根进程已先行退出（kill ESRCH），无法确认进程树已清空'`；消费端模板不再产生重复病句，故未改文案模板。
  **2026-11-12 二次复核订正（WARN 按 `alreadyExited` 分档）**：复核指出只补文字不成立——`if (!r.ok)` 对 ESRCH 与 128 仍为真，WARN 照打。现将 `onAbort` 改为：`r.alreadyExited` ⇒ `logger.info(...'根进程已先行退出，进程树提前收场（非终止失败）')`；否则才 `logger.warn(...'中断时进程树终止失败')`。两平台一致（128 / ESRCH 同走 info），依据是二者都表示「目标在终止指令到达前自行结束」、不是终止失败；`terminationError` 仍如实写入原因句（`alreadyExited` 不蕴含树已清空）。调用方路径 `onAbort` 仅在外部 abort 时触发，超时路径不受影响。
  **为什么不在 0.8.0 夹带**：该判定在内核 `src/` 里，而内核 6.0.0 已发 npm——此刻改 `src/` 会让宿主内联代次与 npm 上 6.0.0 分叉（「随包内核代次 = 6.0.0」失真）。

  **落地记录（2026-11-12 · 写盘方自述，待独立复核）**：`src/skill/skillScriptRunner.ts` `killProcessTree` POSIX 分支 catch 首判 `err.code === 'ESRCH'` → `{ ok:false, alreadyExited:true }` 且带原因句（2026-11-12 复核后补齐，见上条订正），非 ESRCH 仍走原「记 error + 降级单杀」；`ProcessTreeKillResult.alreadyExited` JSDoc 补「Windows 128 / POSIX ESRCH 同源」。用例 3 条（`skillScriptRunner-exec.test.ts`）：① 跨平台「进程先退出再杀」；② 平台桩（临时改写 `process.platform='linux'` + `process.kill` 抛 ESRCH）在 Windows 本机验 ESRCH 判定；③ EPERM 守卫（不归 alreadyExited、仍记 error）。
