## 一、🔴 P1 · UI-TOKEN-PAIR-1（新）accent 底配错文字令牌 ⇒ 亮色主题对比度不达标

**现状**：`chatStyles.ts:886-887` 计数徽章 `background: var(--accent); color: var(--surface-inverse, #fff)`。

**证据链**：
1. `--surface-inverse` 定义 = `var(--vscode-foreground, #ffffff)`（tokens.ts:208），与 `--text-primary`（tokens.ts:68，同为 `--vscode-foreground`）是**同变量同语义的实质别名**，只是回退不同 ⇒ 第二个真理源。
2. 命名族错配：名字 `surface-*`（表面），实际用作 `color:`（文字）—— 全库唯一消费点即此处。
3. 全库 accent 底色 18 处，其中 17 处配 `--accent-foreground`；**唯独此处配了 `--surface-inverse`**。
4. 对比度推演（亮色主题 Light+：`--vscode-button-background≈#0078d4`、`--vscode-foreground≈#333333`）：
   `#333 on #0078d4` ⇒ **≈ 2.98:1**（WCAG AA 小字需 4.5:1）⇒ 不达标。
   改用 `--accent-foreground`（`--vscode-button-foreground`，亮色主题 ≈ #fff）⇒ **≈ 4.43:1**，与 VS Code 原生按钮标准一致。

**判定**：不是洁癖问题，是**跨主题无障碍缺陷**——暗色主题下侥幸可读（浅灰 on 蓝），亮色主题下徽章数字几乎看不见。这也正是「真机暗/亮走查」最该优先盯的点，现已从"全库走查"收敛到"1 处定点"。

**修法（不带伤 · 1 行 + 删 1 别名）**：`color: var(--accent-foreground, #ffffff)`；`--surface-inverse` 随之零消费 ⇒ 按 UI-TOKEN-DEF-1 同判据删定义。暗色主题视觉变化：#cccccc → #ffffff（徽章数字略更亮，属修复方向）。

## 二、🟡 P1 · UI-TOKEN-LAYER-1（新）分级令牌「主路径塌缩」——命名承诺层次，实现不分层次

**实锤**（脚本对账 tokens.ts 定义层，同一 `--vscode-*` 变量被多个令牌引用）：

| 变量 | 同族令牌（回退） | 后果 |
|---|---|---|
| `--vscode-toolbar-hoverBackground` ×4 | `--surface-hover`(.2) / `--surface-normal`(.16) / `--surface-inset`(.12) / `--surface-active`(.24) | 主路径四者**解析为同一颜色** |
| `--vscode-descriptionForeground` ×4 | `--text-secondary`(#9aa0a6) / `--text-tertiary`(#6e7681) / `--text-muted`(#9a9a9a) / `--feedback-warn-fg`(#d7ba7d) | 主路径前三者同色；且 `#9aa0a6` 与 `#9a9a9a` 几乎同值 ⇒ 令牌冗余 |
| `--vscode-panel-border` ×3 | `--border-panel`(.4) / `--border`(.25) / `--border-subtle`(.2) | 主路径三者同色 |

**契约分裂的硬证据**：同为 chip 的 hover 态，两处用了不同令牌——
`chatStyles.ts:85 .status-dock__chip:hover { background: var(--surface-active, .24) }` vs
`chatStyles.ts:294 .suggestion-chip:hover { background: var(--surface-hover, .2) }`
⇒ 代码表达「两者强度不同」，主路径渲染**完全相同** ⇒ 名字在撒谎。
消费规模：`--surface-hover` 32 处 / `--surface-active` 4 处 / `--text-secondary` 116 处 / `--text-muted` 14 处 / `--border` 87 处 / `--border-panel` 46 处。

**性质判定**：这不是 SSOT 漂移（守卫查不出来，因为消费层回退与令牌最内层自洽），是**表达力缺口 + 可用性损失**：hover 与 active 反馈在同一组件里视觉无差别，用户分不清「悬停」与「选中」。

**修法两路（待拍板，勿直接动手）**：
- **路 A（推荐 · 零视觉变化）**：定义层改链式 `--surface-normal/inset/active: var(--surface-hover)`（同族同理），保留名字不动消费侧，同时按 UI-TOKEN-COLOR-1 既有流程把消费层回退对齐新最内层色 ⇒ 消除假分级，代码更少，主路径视觉零变化（仅脱钩路径回退值统一）。
- **路 B（需真机验收 · 有视觉变化）**：引入 `color-mix()` / 相对颜色语法做真分层（hover / active 拉开 alpha 差）⇒ 层次真实存在，但依赖 Chromium 较新语法，需真机确认。

## 三、🟡 P2 · 设计系统维度缺失（z-index / opacity / line-height）+ 守卫盲区

**铁律对照**：tokens.ts:10「裸值只能出现在本文件」——以下三类**无令牌、全裸写、守卫不管**（守卫口径 = px + 颜色两类，本轮实测自报「裸值债 74 处冻结」）：

| 维度 | 实测（剥离 `var()` 回退后的真裸值） | 问题 |
|---|---|---|
| `z-index` | **17 处 / 9 个值**：1, 5, 10, 20, 25, 30, 100, 200, 1000 | 层级无刻度；100/200/1000 是典型「魔法大数」 |
| `opacity` | **41 处 / 11 档**：0, .35, .4, .5, .55, .6, .75, .85, .9, 1（且 `.5` 与 `0.5` 两种写法并存） | 透明度无刻度，随手调 |
| `line-height` | **36 处 / 6 档**：1, 1.4, 1.5, 1.6, 1.7, 1.75 | 排版核心维度无令牌；1.7 与 1.75 差 0.05 = 伪精度 |

**关联发现（守卫 74 债的主力）**：守卫自报属性分布 `width=20, height=17, max-width=10...` ⇒ 裸值债主力是**组件尺寸**，而已有 `--sq-*` 刻度（16/18/22/24/28/32）**覆盖不到实际用到的 11/12/13/15/20/26px**（如 `configStyles.ts:48` 26px、`dropdown.ts:20` 26px、`chatStyles.ts:223/269` 20px）⇒ 刻度下界过高 + 缺档，**刻度形同虚设**（定义了却被绕过）。另 `border: 1.5px` 5 处（非整数线宽，低 DPR 下渲染模糊）。

**修法**：① 先 1:1 建 `--z-*` / `--opacity-*` / `--lh-*` 三组刻度（值照现状映射 ⇒ **零视觉变化**），再择机合并伪精度档位；② 补 `--sq-2xs/3xs` 或把越界值就近归刻度（后者有微视觉变化，需拍板）；③ **守卫扩维**：把 z-index/opacity/line-height 纳入裸值冻结门，并新增「定义层同变量不同回退」守卫（防 §一/§二 复发）。

## 五、🟢 P3 · 反向结论：11 处 `prefers-reduced-motion` 逐元素规则**不是死代码**，勿按 UI-DOM-DEAD-1 判据清除

对抗式自审条目（防止把上一轮的判据错误推广）：
- UI-DOM-DEAD-1 的判据 =「全局 `!important` **压过同属性**的非 important 声明」。
- tokens.ts:272 全局兜底设的是 `animation-duration / transition-duration`（**长手属性**）；11 处逐元素设的是 `animation: none / transition: none`（**简写**，置 `animation-name` / `transition-property` 为 none）。**属性不同 ⇒ !important 不构成压制 ⇒ 逐元素规则仍生效。**
- 补充核验：`animationend/transitionend/animationstart` 全仓**零监听**、`forwards` **零用法** ⇒ 两者行为等价（均无事件依赖、无终态依赖）。

**结论**：属「功能冗余但非死代码」。建议**维持现状 + 补一行注记**（说明全局压时长 vs 局部禁动画是互补而非冗余），避免后人按 `[hidden]` 判据误删。
