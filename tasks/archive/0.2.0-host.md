  **触发（用户真机实测三条）**：① 卡片尺寸比输入框小；② 显示的对话记录像「弹到下面」；③ 回到底部按钮出现在底部、与确认框交叠。
  **🔴 根因分诊（三症状 = 两处真缺陷 + 一处固有代价，不是「粗糙」，也不该换形态）**：
  - **①② 同源**：卡片在 `resolveDock` 里**替换** `#inputWrap`（composer `hidden`、卡 `insertBefore(…, inputBar)`），但盒模型没跟输入框对齐 ⇒ 替换瞬间「盒子换了形状」：缺 `min-height`（矮约 38px）、`border-radius` 8 vs 14、底色 `surface-card` vs `surface-input`。而 `#messages` 是 `flex:1` ⇒ 高度突变直接表现为「对话记录整体弹一下」（无过渡，所以像「弹」）。**宽度其实一致**（`body` margin:0 的 flex column、无左右 padding，两者都吃满）——用户所说「小」是矮 + 圆角小 + 底色跳，不是窄。
  - **③ 独立真 bug**：`.scroll-to-bottom` 是 `bottom: calc(100% + sp-4)` 锚 `#inputBar` 顶边，而审批卡恰好插在 inputBar 正上方 ⇒ 按钮锚点落进卡片区域；更要紧的是 `#inputBar` 有 `z-index: var(--z-bar)=20` **创建了层叠上下文**、卡片无 z-index ⇒ 按钮不只视觉压住卡片的操作按钮，**还能抢走点击**（误触源）。且 `scrollToBottomBtn.hidden` 只由滚动位置决定（`chatView.ts:467/483/500`），与 confirm **零联动**。
  **定案（2026-10-22 用户拍板「ssot 不带伤原则推进落地」）：保留「替换」形态，不换弹窗。** 理由（第一性）：全覆盖弹窗（盖消息区+输入区）**遮挡上下文**，而审批恰恰要看 Agent 说要干什么；只盖输入区的浮层与现有「替换」占**同一块视觉空间**，净收益≈0，却要多开 z-index 层级 + 焦点陷阱（`setComposerReplaced` 原注释已论证不要），且卡片内容（命令 + diff）超过输入区高度后无解。**两处缺陷能精确定位，换形态是拿重构掩盖 bug。**
