## 二、目标类设计

### 2.1 新模块 `extension/host/activeFileTracker.ts`

```ts
import * as vscode from 'vscode';
import type { ActiveFileProjection, ExtensionToWebviewMessage } from '../../shared/protocol.js';

/** 显示/注入双路共用的快照（廉价事实，**不含正文**） */
export type DocContextSnapshot = { /* 原 chatPanel.ts:314 类型整体搬迁 */ };

/** tracker 唯一反向依赖：消息投递点（由 chatPanel 注入其 this.post） */
export interface ActiveFileDeps {
  post: (msg: ExtensionToWebviewMessage) => void;
}

export class ActiveFileTracker {
  private _attachActiveFile = true;
  private _lastActiveFileJson = '';
  private _activeFileSubs: vscode.Disposable[] = [];

  constructor(private readonly _deps: ActiveFileDeps) {}

  /** 方法名与语义**整体保留**（见 2.2） */

  postActiveFile(projection: ActiveFileProjection, force: boolean): void { /* this.post → this._deps.post */ }
  pushActiveFile(force = false): void { /* 原样 */ }
  ensureActiveFileTracking(): void { /* 原样 */ }
  disposeActiveFileTracking(): void { /* 原样 */ }
  setActiveFileAttach(enabled: boolean): void { /* 原样 */ }
}
```

模块级随迁：`snapshotDocContext` / `readDocBody` / `docInjectReason` / `mustInjectDocBody` /
`projectActiveFile` / `isAbsolutePathLike` + 常量 `MAX_DOC_CONTEXT_CHARS`（均为纯函数或
只依赖 `vscode.TextEditor`，无 chatPanel 类状态）。

### 2.2 设计原则：**方法名零改名**

调用点从 `this.resolveActiveFile(true)` → `this._activeFile.resolveActiveFile(true)`。
**纯路径变化，零语义变化**，diff 最小、最易审查、最不易引入第二套判据。

> **否决的替代方案**：把方法改名为 `resolve()` / `deliver()` / `start()`。
> 收益仅是"类名变更后读起来短一点"，成本是 6 个调用点 + 全部测试夹具 + JSDoc 交叉引用
> 一起改，且引入" tracker 方法名 ≠ 原语义名"的翻译层。违反「不顺便优化」。

### 2.3 与 chatPanel 的接口（单一挂载点）

```ts
// chatPanel.ts 构造处
this._activeFile = new ActiveFileTracker({ post: (m) => this.post(m) });
```

`post` 是 chatPanel 既有私有方法（消息投递单点），经闭包注入，**不引入新依赖方向**。

### 7.5 额外修复（实施中发现，非方案预设）

**① 一个静默失效（本刀最有价值的发现）**
`chatPanelHistory.test.ts` 原写法 `(provider as unknown as { _attachActiveFile: boolean })._attachActiveFile = attach;`
——字段搬走后，该赋值落到**野属性**上（TS 不报错、运行时不抛异常），而 `attach` 默认值 `true`
恰等于 tracker 初值 `true`，故**无一用例因此转红**。若不修，将来任何人加一个
`sendWithEditor(false, false)` 去测「开关关闭时不取快照」，都会**假通过**。
修法：三处路径随迁（写入、`pushActiveFile` 直调、字段断言读取），断言语义零变化。

**② 一处 tsc 类型错误**（vitest 不查类型，跑 `tsc` 才暴露）
`makeEditor` 返回类型标注为 `{ reads: { getText: number } }`，但用例访问了 `.document`
→ `error TS2339: Property 'document' does not exist`。已补进返回类型。
**教训复证**：vitest/esbuild 不查类型，改完必跑 `tsc --noEmit`（`npm test` 全绿 ≠ 类型干净）。

**③ 一处测试预期写错（如实记录，勿当 bug）**
「三事件全覆盖」用例首版期望 `docSubs` 触发后 `editorReads` 从 1 → 2，实测为 1 → 3。
根因：`onDidChangeTextDocument` 回调**先读一次** `activeTextEditor` 做「是不是当前文档」比较，
命中后才由 `pushActiveFile → resolveActiveFile` 读第二次。这是既有实现行为、非本次引入，
故按事实修正预期并在注释中写明原因（**不顺手优化**——那是"顺便优化"）。
