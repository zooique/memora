# 方案 · 会议步粒度硬切换（v0.13 S5 补强）

> 定案日期：2026-08-29
> 关联：角色包体系 v0.13（[role-pack-exclusivity-relocation.md](../docs/architecture/role-pack-exclusivity-relocation.md) §4.6 会议）
> 来源：第十五轮独立核实发现「硬切换只到轮粒度、不到步粒度」的集成缺口（orchestrator 层零测试守护）。
> **文档状态**：✅ 已并入权威设计文档（2026-08-29）——本方案为**决策追溯**（问题/边界/非目标），定案正文并入 [role-pack-exclusivity-relocation.md §4.3 装配驱动点 / §4.5 执行与护栏 / §6.2 新增清单 / §6.3 S5](../docs/architecture/role-pack-exclusivity-relocation.md)，两处不再分叉（本文件不回改设计）。

## 1. 问题（一句话）

v0.13 S5 会议机制已落地，但 `refreshRolePackPrefixForRound`（把成员 persona/rules/skills 真灌进系统前缀）只在**闭包入口（prepare.run）调一次**，而 `runStepSequence` 跑完全部 pending 步**不 re-prepare** → 一次自动会议里所有步共享入口 active 步的人格（或组长），成员的「真文档」进不了对应步的上下文。

结果：会议实际只靠 `buildTeamContextBlock` 给的**名字**让 LLM 软演，不是按真文档给意见。组的投资（指针集合 + 校验闸 + 逃生舱）没完全兑现。

## 2. 决策

**步入口硬切换**：`runStepSequence` 每跑一步前，按该步 `rolePack` 刷新表层装配（成员文档真进上下文）。

## 3. 边界（4 条，不可破）

| # | 边界 | 理由 |
|---|------|------|
| B1 | **工具面恒归组长** | members speak not execute（v0.13 §4.6 既定）。`refreshRolePackPrefixForRound`（agent.ts:1378）内部已按 `activePack` 策略构建 ChatOptions——键不切，工具白名单天然锁死组长，**无需额外代码**。这就是「真意见 + 组长工具」 |
| B2 | **只在步入口换前缀** | 一个步内部 LLM 要跑多轮（想→调工具→看结果→想），仅在步入口换一次，步内多轮不重复换（防抖动 + 省重建） |
| B3 | **装配源改读「正要跑的 pending 步」** | prepare.run 读 `plan.find(s=>s.status==='active')`；`runStepSequence` 跑的是 `pending` 步。直接读 `next.rolePack` 比查 active 步更直接、更准（避免「首轮无 active 步→硬切换不触发」的怪象） |
| B4 | **必须补 orchestrator 层集成测试** | `orchestrator.test.ts` 当前零会议覆盖（grep 无 rolePack/会议/meeting）。步粒度接缝无人看护，补一条「步2 以成员装配角色调 refreshRolePackPrefixForRound」端到端用例锁死契约 |

## 4. 实现落点（最小改动）

- 提取共享 helper `refreshAssemblyForRolePack(rolePack?: string): void`，收口 `prepare.run` 与 `runStepSequence` 两步装配逻辑（**SSOT**：resolveRoundAssemblyRole 范围校验 + setRoundAssemblyRole skills 跟随 + refreshRolePackPrefixForRound 前缀重建）。
- `prepare.run`：`this.refreshAssemblyForRolePack(activeStep?.rolePack)`（行为不变）。
- `runStepSequence`：步入口 `this.refreshAssemblyForRolePack(next.rolePack)`（新增）。
- `getNextPendingStep` 返回体补 `rolePack` 字段（供步入口装配读取）。
- **loop.ts 零改动**（会议不进执行闭环，守住 v0.13 边界）。
- `applyRolePackToolExposure()` 仍仅 prepare 调一次（工具面不动，B1）。
- skills 加载跟随装配视角（`resolveSkillTarget` = packName ?? roundAssemblyRole ?? activePackName）属「真意见」范畴，可接受（成员技能正文读得到）。

### 4.1 多路径装配关系（双装配点的语义分工）

`prepare.run`（闭包入口）与 `runStepSequence`（步入口）共用 `refreshAssemblyForRolePack`，但驱动点不同，存在一层「覆盖 + 冗余」关系，需明示：

| 路径 | 装配驱动 | 说明 |
|---|---|---|
| runChat 复杂任务 | **步入口**（权威） | `prepare.run` 读 active 步（规划前无）→ null，随后 `runStepSequence` 第一步刷新为 pending 步 rolePack，**覆盖**入口设置——入口的 active 步逻辑在此路径冗余（无害） |
| runChat 简单任务续跑 | prepare 期 active 步 | 无步序列，active 步存在（续跑现场）→ 读 active 步 rolePack 生效 |
| runEvent（增量事件） | prepare 期 active 步 | **无 runStepSequence**（event 路径不走上文步循环）→ 会议装配由入口 active 步驱动；语义一致（都读「当前执行步 rolePack」），仅驱动点不同 |

结论：步粒度补强只扩展「复杂任务步序列」这一条驱动链；prepare 期 active 步逻辑保留（服务续跑/event 路径），两者互不冲突（不同路径不同驱动）。

## 5. 不做的（防过度设计）

- 不把装配逻辑搬进 loop（那是 v0.13 否决的「往执行闭环开洞」）。
- 不每轮换前缀（B2）。
- 不切工具白名单（B1）。
- 不补「首轮无 active 步」特殊处理——步入口直接读 pending 步 rolePack，自然解决。
