## 三、另一候选：ask 提问域为何更该后做（附实证否决理由）

ask 域（`_pendingQuestions` / `_askTimeout` / `ASK_TIMEOUT_MS` / `ASK_TIMEOUT_NOTICE` +
`armAskTimeout` / `clearAskTimeout` / `handleAskTimeout`，~120 行）**净降潜力是安全审计域的 5 倍**，
却排在后面——理由不是偏好，是**撞红线**：

读 `handleAskTimeout`（chatPanel.ts:3252-3273）实测依赖：
- `this._turnState`（读 waiting.questions）
- `this.isAskWaiting()`（相位判据）
- `this._agent.cancelAsk()` + **`await this.runFlow(...)`**

`runFlow` 是 chatPanel 的**消费流主循环入口**（含 LiveFlowBuffer / 用户消息上屏 / 落盘收尾）。
把它作为依赖注入给 ask 域 = **让域反向持有宿主主循环**，与第 1 刀红线
（「不让 tracker 反向持有 provider 实例，否则域与宿主互相持有，销毁顺序成隐患」）同型。

⇒ **ask 域的前置条件是解耦 `runFlow`**，即第 4 刀 `consumeFlow` 阶段化的一部分，**不可单独一刀做**。

## 五、附：单测设计（若将来重做可直接用，现有覆盖为 0）

| 用例 | 断言要点 |
|---|---|
| 绑定 | `onAudit` 被调一次；**幂等**：连续两次绑定 ⇒ 前一次 unsub 被调（不累积订阅） |
| 无 agent | `getAgent()` 返回 undefined ⇒ 静默返回不抛 |
| 累计 total | 3 个事件 ⇒ `total === 3` |
| denied 判据 | `path-deny` / `write-decline` 计入；其余类型不计 |
| 最近 3 条上限 | 4 个事件 ⇒ `recent.length === 3` 且**保留最新 3 条** |
| 路径 basename | 事件 path 含目录 ⇒ 只余 basename（不泄露完整目录结构） |
| 快照拷贝隔离 | 改 `snapshot().recent` 元素**不影响** tracker 内部状态 |
| 空态 undefined | 无事件 ⇒ 返回 `undefined`（对应「有事件才携带」） |
| reason 透出 | 事件带 `reason`（如「命中黑名单」）⇒ 原样保留（丢弃则用户只知「拒绝」不知为何） |

配套变异电池（7 发）见实施记录：幂等首行删 / denied 判据删 / `length > 3` 改 `> 5` /
basename 改回原 path / spread 改直引 / `total > 0` 改恒真 / reason 透出删。

## 六、方法论教训（新增，写入台账与记忆）

**「小域搬迁」的隐藏成本 = chatPanel 侧 JSDoc 增量。** 三刀实测对比：

| 刀 | 域体量（迁出行） | chatPanel 侧新增 | 实测净降 | JSDoc 增量占比 |
|---|---|---|---|---|
| 第 1 刀（活动文件） | ~300 | ~16（字段 JSDoc 11 + re-export 5） | 233 | ~7% |
| 第 2 刀（确认队列） | ~172 | ~19（字段 8 + sugar 9 + import 2） | 155 | ~12% |
| **第 3 刀（安全审计）** | **54** | **27（字段 9 + 字段 3 + sugar 8 + 委托 3 + 投影 2 + import 2 + 注释）** | **24** | **~113%（超过净降本身）** |

⇒ **判据③的 40 行阈值对「小域」是假门槛**：域体量 <100 行时，搬迁侧的 JSDoc 增量会吃掉大部分收益。
**更诚实的判据形态**应是「净降 ≥ max(40, 迁出行数的 40%)」或直接「域体量 ≥100 行」。
⚠️ 但本轮**不擅自改判据**（红线：改判据 = 造伤）——只登记该阈值对小域失效的事实，
留待与台账同批拍板。
