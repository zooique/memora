## 一、任务 A · memora助手 = 兜底契约包（已随 S0 落地，不重复立任务）

### 1.1 身份裁定（必须先定，否则实施会做错）

memora助手**不是普通示例包**，它就是角色包体系方案 §4.6 / §八-8 定案的**兜底契约包**（名字由用户裁定，进内核常量 `BUILTIN_FALLBACK_PACK`）：

| 维度 | 普通示例包（小说助手/文档设计师/方案设计师） | 兜底契约包（memora助手） |
| --- | --- | --- |
| 物理位置 | `role-packs/<名>/` | 同目录（并列） |
| 语义 | 领域示例，可变 | 机制底线，名字由内核常量锁定 |
| 可否删除 | 可删 | **不可删**（宿主 UI 禁用删除入口） |
| 内容 | 领域 persona + 领域关键词 | **领域无关**，中性 persona + 最小通用 rules |
| 校验 | 无 | **构建期 existsSync**，缺即构建失败 |

**实施要点**：

* "不可删"**不给角色包加自指字段**——它是宿主 UI 的约束（角色包声明自己是内置的 = 自指字段被宿主解读，与插卡独立性冲突）。宿主只需按 `BUILTIN_FALLBACK_PACK` 常量名禁用删除入口。
* **`keywords` 留空或极泛**：兜底包若有领域触发词，会被组内/自动匹配抢占命中，把"没有领域人格"的包推到前台——与其定位相反。
* 名字进内核常量 `BUILTIN_FALLBACK_PACK`，**改名须走 ADR**（名字即契约：宿主持久化里存的是名字）。

### 1.2 验收（✅ 已随 S0 落地，2026-08-29）

```
role-packs/memora助手/
  ├─ manifest.json   （无 exclusiveWith、无领域 keywords、无领域 summaryFocus）
  ├─ persona.md      （中性助手：无领域身份，明确"不确定时追问而非编造"）
  └─ rules.md        （最小通用约束：安全 + 诚实 + 不越权，不含领域规则）
✅ 内核常量 BUILTIN_FALLBACK_PACK = 'memora助手'（src/role-pack/constants.ts）
✅ 宿主 copyRolePacks() 构建期 existsSync 校验（缺失即构建失败）
✅ 宿主角色管理视图：该包删除入口禁用（「兜底（禁删）」徽章）
```

### 1.3 归属

**并入角色包体系方案 S0**，不单独立任务（S0 已要求"内核新增兜底契约包 + 构建期校验"，本方案只是把它命名与内容规格化）。

## 二、任务 B · 角色包制作专家

### 2.1 待拍板：形态之争（角色包 vs 全局技能）

| 维度 | 做角色包 | 做全局技能 |
| --- | --- | --- |
| 使用方式 | **必须切换到该角色** → 打断当前工作（§9：切换是例外） | 任意角色下可用（L1 清单常驻、L2 按需读正文），**零切换** |
| 体积 | 目录（manifest + persona + rules + skills/） | **单 .md**（宿主全局技能池已有 code-review/summarize/web-search 三例） |
| 内容匹配 | "制作角色包"是**通用能力**，不专属任何人格 | 同上 → 按 §11.5，通用能力归**全局维度**（技能），不随角色变 |
| 长文档 | 全量进 context 或需 read_skill | 天然两级渐进披露（L1 指针 / L2 正文） |
| 流通共享 | ✅ 角色包是"卡"，可插拔分发 | 技能文件亦可分发（全局池 / 用户 skills 目录） |

**建议：先做全局技能** `role-pack-authoring.md`。理由：

1. 需求的本质是**能力**（快速制作），不是**形态**（角色包）——能力与形态应分离，形态按复杂度匹配选最轻的那个。
2. 角色包形态强制"切出当前角色才能做角色包"，与 §9 专注模式直接冲突；技能形态在任何角色下都能顺手做。
3. 若后续真出现"需要作为独立人格流通 / 分享给他人"的诉求，再从技能升级为角色包（自然生长阈值，§八-12）。

> **唯一支持做角色包的论据**是流通性（分享给其他 memora 用户直接当卡插）。若这条是你更看重的，告诉我，改走角色包形态。

### 2.2 SSOT 硬约束（无论哪种形态）

**❌ 禁止把 `role-pack-spec.md`（74KB）/ `role-pack-authoring-guide.md`（17KB）的正文复制进角色包或技能。** 规范一更新，副本即腐化——两份真理源，且副本会伪装成权威。

**✅ 正确做法**：

| 层 | 内容 | 来源 |
| --- | --- | --- |
| 内化（可复制） | **稳定硬约束**：必填字段表、目录与文件约定名、常见校验错误、最小可装载示例 | 规范中变化频率最低的部分 |
| 引用（不复制） | 完整字段语义、策略键取值、渐进披露细节 | 指向目标环境 `docs/architecture/role-pack-spec.md` + `role-pack-authoring-guide.md` |
| 标注 | 包/技能内注明"本内容为创作时快照，权威以目标环境规范为准" | — |
| **校验** | **用真实装载做校验，不用副本文档**：制作 → 装载 → 装载成功即合规 | 真理源是装载器与 validator，不是任何文档 |

最后一条是关键：**角色包是否合规的唯一裁判是装载器**。制作流程的收尾必须是"装载一次"，而不是"对照文档自查"。

### 2.3 硬前置（不做这两条，产物用不了）

1. **`userRolePacksDir` 当前为 `undefined`**——宿主 `assemble.ts:281-282` 注释明确"当前角色包不开放给用户，`loadExtraDir` 分支不会执行"。**用户自制的角色包目前无处装载**。任务 B 必须绑定「开放用户角色包目录」这一宿主改动，或明确产出落到 configDir（不推荐：那是程序目录，会随构建被覆盖）。

### 2.4 验收（写 → 验 → 用闭环，与 G22 同构）
