## 四、关键修复的最小 diff

### 问题 1（P1）— `_pendingToolExecutions` 双写 + 泄漏

**当前代码**（`agent.ts:1864-1869` 工具执行回调内）：
```ts
// 会话管理器可能尚未创建（assembler 中 loop 先于 sessionManager 创建）
// 暂存到队列，待 sessionManager 创建后统一写入
this._pendingToolExecutions.push(record);
// 若 sessionManager 已就绪，立即写入
this._sessionManager?.logToolExecution(record);
```

**建议代码**：
```ts
// 仅在会话管理器尚未就绪时暂存；就绪后直写真理源，避免缓冲无限增长 + 重建时重放双写
if (this._sessionManager) {
  this._sessionManager.logToolExecution(record);
} else {
  this._pendingToolExecutions.push(record);
}
```
> `_flushPendingToolExecutions()`（:2050-2062）保持不变：sm 就绪后一次性 drain 缓冲并清空（`this._pendingToolExecutions = []`，:2060），缓冲现为纯 transient outbox。

### 问题 2（P2）— `contextSummary` 跨会话失效

**当前代码**（`sessionManager.ts:226` 末尾）：
```ts
    return this.getHistory().switchSession(newSession);
```
**建议代码**：
```ts
    // SSOT-R3：消息集整体替换，作废上一段会话的上下文摘要（避免陈旧摘要注入新会话 system prompt）
    this.getLoop().contextManager.resetSummary();
    return this.getHistory().switchSession(newSession);
```
> 配套加固（可选）：`contextManager.getOrCreateSummary` 的缓存键由「消息数差」改为「会话标识 + 内容指纹」，从源头消除长度巧合导致的陈旧命中。

### 问题 3（P3）— 恢复路径重挂暂停计时器

**当前代码**（`sessionManager.ts:922-926` 附近，恢复 paused 分支）：
```ts
// 已知缺口：直接 stateMachine.pause 绕过 startPauseTimeoutTimer
this.stateMachine.pause(reason, source);
```
**建议代码**：
```ts
this.stateMachine.pause(reason, source);
// 恢复 paused 会话须重挂超时计时器，使挂载物生命周期与状态机一致
this.startPauseTimeoutTimer();
```
> 若 `startPauseTimeoutTimer` 已内含幂等/去重，直接补调用即可；否则先 `clearPauseTimeoutTimer()` 再挂。

### 问题 4/5（P3）— 资源层缓存收口（模式相同）

**建议模式**（以 `inMemoryStorage` 为例）：
```ts
// 消除 sourceCountCache 镜像：改为按需由 memories 派生，或所有写入口经统一 mutate 方法
private mutateMemory(id: string, fn: (m: Memory | undefined) => Memory | undefined) {
```

### 7.2 为何多轮审查仍有"问题"

1. **非回归，是新状态未纳入 SSOT 伞**：#1 属后续新增的"P3.3/P3.4 工具幂等 outbox"特性；#2 的 contextSummary 缓存 + restoreHistory 失效本身也是近期特性。前序 R1–R4 收敛的是 setPauseMeta/insight/loop.pauseRequested/runtimeNames 等**不同子域**。故"残留"实为"新增未审"，非"修复回退"。
2. **修复是 call-site 点修，未做结构层 pattern-fix**：#2 与 T9 是同一类病灶（派生缓存失效须在每个"会话替换"入口做）——T9 修了 restoreHistory，switchSession 漏了。根因是"会话替换"事件有多个入口（restoreHistory / switchSession / forkSession / rebuild），每个入口须各自记得失效所有派生缓存，无单一 chokepoint。点修永远追不上新入口/新缓存。
3. **测量噪声（假阳性膨胀）**：前序轮次 ~1/3 结论被证伪（T5/T11/T12 + #1/#6）；本轮 #5 亦误报。部分"问题"是"将来某路径若忘记 X 会漂移"的脆弱性提示，而非当前可复现缺陷。

### 7.3 根治方向（pattern-fix，非点修）

- **集中"会话替换"派生失效**：在 `SessionManager` 增设单一 `invalidateSessionDerivedState()`（或事件），reset `contextSummary` + 任何未来派生缓存；restoreHistory / switchSession / forkSession / rebuild 全部经此出口。新增缓存→必须订阅；新增入口→必须路由。从源头消除"对称的另一半没写完"。
- **工具执行 outbox 单路径**：仅 `sm` 缺失时入缓冲、存在即直写（见 §四 问题1 diff），缓冲为纯 transient，杜绝泄漏与重放双写。
- **提高判定门槛**：每条发现须给出"当前可复现的漂移/重复路径"，而非"将来可能漂移"；脆弱性提示单独归类，不计入"需修复"。
