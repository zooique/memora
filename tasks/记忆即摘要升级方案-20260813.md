## 一、排雷总览

### 1.1 7 个风险点评估

| # | 风险点 | 等级 | 影响范围 | 解读 |
|---|--------|------|---------|------|
| R1 | Memory 接口扩展（破坏性变更） | **P1** | types.ts + 29 个引用文件 + 公共 API | Memory 接口新增字段会破坏所有宿主项目 |
| R2 | InsightExtractor 行为变更（从"提取价值"到"每轮摘要"） | **P1** | insightExtractor.ts + prompt + 调用链 | 核心行为变更，需细分"价值洞察"和"轮次摘要" |
| R3 | SessionArchiver 冗余（轮次摘要已覆盖会话概要） | **P2** | sessionArchiver.ts + archiveMode 配置 | 轮次摘要粒度更细->会话级摘要失去独立价值 |
| R4 | 召回性能退化（摘要数量激增） | **P1** | recall.ts + memoryInspector.ts + token 预算 | 每轮 1 条摘要 vs 现有关键轮次才提取，数量差 10x+ |
| R5 | 存储层 Schema 迁移（SQLite 新增字段） | **P2** | SqliteStorage（宿主项目）+ InMemoryStorage | 需新增 sessionId/roundId/isTraceable/isModified 列 |
| R6 | traceSummary 工具实现（LLM 溯源工具） | **P2** | toolExecutor + loop.ts + 新工具 | 需接入 sessionStore，新增 roundId 追踪 |
| R7 | Profile 和 WorkProjection 对齐（非轮次记忆的迁移策略） | **P3** | userProfile.ts + workProjection.ts | 非轮次基的记忆，不强制纳入摘要模型 |

### 1.2 排雷详解

#### R1：Memory 接口扩展（P1 破坏性变更）

**现状**：`Memory` 接口（`src/memory/types.ts`）有 8+1 个字段，通过 `src/index.ts` 导出为公共 API。所有宿主项目依赖此类型。

**风险**：新增必填字段会破坏所有宿主项目的编译和运行时行为。

**排雷结论**：**所有新增字段（sessionId/roundId/isTraceable/isModified）必须为可选字段（`?`）**，保持向后兼容。

**影响文件**：
- `src/memory/types.ts`——Memory 接口 + parseMemory 验证函数
- `src/memory/storageInterface.ts`——IMemoryStorage 接口（无需修改，泛型存储）
- `src/agent/managers/insightExtractor.ts`——创建 Memory 时填充新字段
- `src/agent/managers/sessionArchiver.ts`——创建 Memory 时填充新字段（如保留）
- `src/memory/recall.ts`——召回时可能利用 sessionId 过滤
- `src/agent/managers/memoryInspector.ts`——搜索/快照可能利用新字段
- 所有测试文件中创建 Memory 的位置——需补充新字段（可选则不影响）

#### R2：InsightExtractor 行为变更（P1 核心变更）

**现状**：`InsightExtractor.extract()` 仅在有价值内容时产出 insight（LLM 判断为 null 则跳过）。每轮 postProcess 调用一次。

**目标**：每轮对话必须产出 1 条摘要（1-2 句话），且带 `SummaryType` 标签。

**排雷结论**：**不应修改 InsightExtractor 的行为**，而是新增一个独立的 `RoundSummaryGenerator`（轮次摘要生成器），与原 InsightExtractor 并行存在：

```
doPostProcess 中：
  ├── InsightExtractor（不变）：提取"有价值洞察"（source='insight'）
  └── RoundSummaryGenerator（新增）：每轮生成 1 条摘要（source='round-summary'）
```

**理由**：
- InsightExtractor 的 prompt 和分类逻辑已稳定，修改会破坏现有行为
- "价值洞察"和"轮次摘要"是两种不同粒度的信息，LLM 的 prompt 不同
- 并行存在方便对比效果，后续可逐步合并或淘汰

**影响文件**：
- 新建 `src/agent/managers/roundSummaryGenerator.ts`
- 修改 `src/agent/managers/archiveCoordinator.ts`——新增 roundSummary 阶段
- 修改 `src/agent/agent.ts`——doPostProcess 中调用 roundSummary
- 修改 `src/agent/assembler.ts`——组装 RoundSummaryGenerator

#### R3：SessionArchiver 冗余（P2 可优化）

**现状**：`SessionArchiver` 在会话切换时（或手动）生成会话级摘要，`source='content'`。

**分析**：如果每轮都有摘要，会话级摘要的信息密度被轮次摘要覆盖。但会话级摘要有"综合提炼"能力（keyDecisions/openQuestions），轮次摘要不具备。

**排雷结论**：**保留 SessionArchiver 但降级为"可选综合提炼"**，仅在 full 模式下触发。长期由 N 轮聚合摘要（`type='aggregated'`）替代。

#### R4：召回性能退化（P1 关键问题）

**现状**：当前 ~10-20% 的轮次产生 insight（LLM 过滤后）。每轮都产生摘要后，条目数增长 5-10x。

**影响**：
- 关键词搜索的性能下降（更多条目需要扫描）
- 上下文组装时 token 消耗增加（更多摘要需要注入）
- 向量存储的条目数膨胀

**排雷结论**：**必须在实施第 1 阶段时就引入 N 轮聚合机制**，否则内存和 token 消耗会线性增长不可控。

**解决方案**：
1. 召回时支持 `sessionId` 过滤（优先同窗口）
2. 召回时优先返回聚合摘要（`type='aggregated'`），降低原始摘要召回数量
3. 聚合阈值 N=50 轮（默认），可配置

#### R5：存储层 Schema 迁移（P2 宿主责任）

**现状**：`IMemoryStorage` 是接口，不关心具体字段。`InMemoryStorage` 直接存 `Memory` 对象。`SqliteStorage` 在宿主项目中实现。

**分析**：新增可选字段在 `InMemoryStorage` 中无需变更（对象已有字段直接存）。`SqliteStorage` 需要宿主项目做 schema 迁移（ALTER TABLE ADD COLUMN）。

**排雷结论**：新字段可选后，`InMemoryStorage` 零变更。`SqliteStorage` 的迁移由宿主项目负责，memora 内核只需输出迁移 SQL 模板。

#### R6：traceSummary 工具实现（P2 新功能）

**需求**：LLM 需要能通过 `traceSummary(sessionId, roundId)` 回溯到原始对话。

**实现依赖**：
1. `AgentLoop` 需要追踪当前 `roundId`（每轮分配唯一 ID）
2. `ToolExecutor` 需要注册新工具 `traceSummary`
3. 工具需要访问 `ISessionStore` 加载原始消息

**排雷结论**：roundId 追踪需要改动 loop.ts 的迭代逻辑。traceSummary 工具需要访问 sessionStore——当前 ToolExecutor 不持有 sessionStore 引用，需通过依赖注入提供。

**影响文件**：
- `src/agent/loop.ts`——新增 roundId 追踪
- `src/agent/toolExecutor.ts`——注册 traceSummary 工具
- `src/agent/types.ts`——新增工具定义

#### R7：Profile 和 WorkProjection 对齐（P3 远期）

**现状**：`UserProfile` 创建 `source='profile'` 记忆，`WorkProjectionManager` 创建 `source='work-projection'` 记忆。两者都不是轮次基的。

**排雷结论**：**首期不迁移 profile 和 work-projection**。它们有独立的创建逻辑和召回策略，不强制纳入"摘要即记忆"模型。短期只需在 Memory 接口中增加可选字段，profile 和 work-projection 不填即可。

## 三、RoundSummaryGenerator 详细设计

### 3.1 类定义

```typescript
/**
 * 轮次摘要生成器
 *
 * 职责：
 *   每轮对话完成后生成 1 条轮次摘要（1-2 句话），写入 memory storage。
 *   与 InsightExtractor 并行存在——InsightExtractor 提取"有价值洞察"，
 *   RoundSummaryGenerator 生成"本轮发生了什么"的客观记录。
 *
 * 设计原则：
 *   - 每轮必生成（不跳过——即使闲聊也生成"用户问候"等低价值摘要）
 *   - 轻量 LLM 调用：prompt 设计为 1-2 句话输出，低 token 消耗
 *   - 异步非阻塞：fire-and-forget，不阻塞主流程
 *   - 降级策略：LLM 不可用时跳过，不阻塞对话
 */
export class RoundSummaryGenerator {
  constructor(
    private readonly provider: LlmProvider,
    private readonly index: IMemoryStorage,
    private readonly sessionId: string,     // 当前会话 ID
    private readonly roundId: () => string,  // 获取当前轮次 ID 的回调
  ) {}

  /**
   * 生成轮次摘要
   *
   * @param userInput 本轮用户输入
   * @param assistantContent 本轮助手回复
   * @returns 写入的 Memory 对象，失败时返回 null
   */
  async generate(userInput: string, assistantContent: string): Promise<Memory | null> {
    // 1. 构造轻量摘要 prompt
    // 2. 调用 LLM（低 token 消耗）
    // 3. 解析摘要 + 判断 SummaryType
    // 4. 写入 memory storage（source='round-summary'）
    // 5. 返回 Memory 对象
  }
}
```

### 3.2 摘要 prompt

```
你是一个对话摘要助手。用 1-2 句话概括本轮对话的核心内容。

要求：
- 第三人称客观陈述
- 不超过 30 字
- 聚焦于"发生了什么"，而非"意味着什么"
- 如果纯闲聊，输出"用户进行了简短问候"

输出 JSON：
{
  "summary": "1-2 句话摘要",
  "type": "preference | fact | decision | intent | general"
}

type 判断规则：
- preference：用户表达了偏好（如"我喜欢简洁的 UI"）
- fact：用户陈述了事实（如"我用的 TypeScript"）
- decision：用户做了决策（如"我选方案 A"）
- intent：用户表达了意图（如"我打算下周发布"）
- general：以上都不符合（默认）

=== 对话内容 ===
用户：{userInput}
助手：{assistantContent}
```

### 3.3 Memory 对象

```typescript
const memory: Memory = {
  id: `round:${roundId}`,
  content: summary,           // 1-2 句话摘要
  source: 'round-summary',    // 新 source 标签
  name: `${type}-${roundId.slice(0, 8)}`,
  createdAt: now,
  accessedAt: now,
  score: 0.5,                 // 初始中等权重
  sessionId: currentSessionId, // 可选，当前会话 ID
  roundId: currentRoundId,    // 可选，当前轮次 ID
  isTraceable: true,          // 可选，初始可溯源
  isModified: false,          // 可选，初始未修改
  metadata: { type },         // 存储 SummaryType
};
```

## 四、存储模型变更

### 4.1 Memory 接口扩展

```typescript
export interface Memory {
  // 现有 8 个核心字段（不变）
  id: string;
  content: string;
  source: string;
  name: string;
  createdAt: string;
  accessedAt: string;
  score: number;
  deletedAt?: string;

  // 新增可选字段（溯源式记忆架构）
  /** 所属对话窗口 ID（可选，仅 round-summary/insight 记忆填写） */
  sessionId?: string;
  /** 所属对话轮次 ID（可选，仅 round-summary 记忆填写） */
  roundId?: string;
  /**
   * 可溯源标记（可选）
   * - true：可追溯到原始对话（sessionId + roundId 有效）
   * - false：不可溯源（原对话已删除）
   * - undefined：无需溯源（如 persona/rule 等配置类记忆）
   */
  isTraceable?: boolean;
  /**
   * 手动修改标记（可选）
   * - true：用户手动修改过摘要内容
   * - false：系统自动生成
   * - undefined：不需要此标记
   */
  isModified?: boolean;

  metadata?: Record<string, string>;
}
```

## 五、迁移策略

### 5.1 向后兼容

- 所有新字段为可选，现有代码无需修改
- 现有测试无需修改（测试中创建的 Memory 对象不填新字段）
- 宿主项目无需立即升级存储层

### 5.2 逐步铺开

```
Phase 1（基础设施）→ 不影响现有行为
  ↓
Phase 2（召回升级）→ 同窗口优先，提升体验
  ↓
Phase 3（聚合摘要）→ 性能保障，防止膨胀
  ↓
Phase 4（traceSummary 工具）→ LLM 新能力
  ↓
Phase 5（SessionArchiver 适配）→ 架构收敛
  ↓
Phase 6（存量数据迁移）→ 数据完整性
```

### 5.3 回滚策略

每个 Phase 都是独立的增量变更，无跨 Phase 耦合。回滚只需：
1. 恢复被修改的文件到上一个版本
2. 删除新增文件
3. 存储层：新字段为可选，不回滚 SQL 也不影响运行

## 六、实施顺序建议

### 推荐顺序：Phase 1 → Phase 2 → Phase 3 → Phase 4 → Phase 5 → Phase 6

**理由**：
- Phase 1 是基础，提供数据模型和生成能力
- Phase 2 和 Phase 3 是核心体验和性能保障，必须先做
- Phase 4 是 LLM 可用的新能力
- Phase 5 和 Phase 6 是架构收敛和清理，可延后

## 八、关键盲区分析

> 以下盲区是通过"场景推演"方式发现的，对应于 Phase 1-6 实施前必须解决的问题。

### 盲区 1：Round 边界定义不清（P0 — 必须先解决）

**场景**：用户说"帮我写一个排序函数，然后用测试用例验证"。LLM 先写代码 → 调用工具写入文件 → 读取结果 → 写测试用例 → 调用工具运行测试 → 返回结果。这是 1 次用户输入，但 loop 内部执行了 6 次 iteration。

**问题**：roundId 应该在哪个粒度分配？

| 方案 | 粒度 | 问题 |
|------|------|------|
| 每 iteration 分配 | 1 次 LLM 调用 | 一次用户输入产生 6 条摘要，信息冗余严重 |
| 每 processUserInput 分配 | 1 次用户输入 | 摘要粒度合理，但需要追踪"用户输入已完成"的边界 |

**结论**：**roundId 必须以 `processUserInput` 为粒度分配**，而非 `handleIteration`。

**当前方案验证**：`postProcess` 在 `executeChatLoop` 之后调用，而 `executeChatLoop` 内部调用 `loop.processUserInput`。所以 postProcess 的时机天然对应一次 `processUserInput` 的完整结束。**roundId 只需在 `processUserInput` 入口分配一次，传到 postProcess 即可。**

**增量改动**：
- loop.ts 新增 `currentRoundId` 字段，在 `processUserInput` 入口分配
- 新增 `getCurrentRoundId()` 方法供外部读取
- 不需要改动 iteration 循环

---

### 盲区 2：RoundSummaryGenerator 与 InsightExtractor 的摘要重复（P1）

**场景**：用户说"记住，我喜欢简洁的 UI"。InsightExtractor 产出 `source='insight'`，`content='用户偏好简洁UI'`，`score=0.8`。RoundSummaryGenerator 也产出 `source='round-summary'`，`content='用户表达了偏好简洁UI'`，`type='preference'`。

**问题**：同一轮对话，两个生成器各自产出一条高度相似的记忆。召回时两者都命中，信息冗余。

**分析**：

| 维度 | InsightExtractor | RoundSummaryGenerator |
|------|-----------------|---------------------|
| 触发条件 | 仅"有价值"内容 | 每轮必生成 |
| 信息密度 | 优先提炼可长期保留的 | 客观记录"发生了什么" |
| score 策略 | 质量分级 0.2/0.5/0.8 | 固定 0.5 |
| 内容示例 | "用户偏好简洁UI" | "用户表达了偏好简洁UI并请AI记住" |
| 冗余比例 | 大部分场景两者内容重叠 | — |

**结论**：**不应让 RoundSummaryGenerator 生成与 InsightExtractor 重叠的内容**。改为：

> **RoundSummaryGenerator 只生成"客观过程记录"**，不包含"提炼"。InsightExtractor 保留现有的"价值提炼"职责。

```
RoundSummaryGenerator 产出示例：
  "用户请求编写排序函数，AI 提供了快速排序实现并运行测试通过"

InsightExtractor 产出示例（当有价值时）：
  "用户偏好 TypeScript 和快速排序算法"
```

**增量改动**：
- RoundSummaryGenerator 的 prompt 中明确："只记录本轮发生了什么，不做价值判断"
- 无需额外去重逻辑——两种记忆的 content 天然不同

---

### 盲区 3：ISessionStore 接口变更（P1 破坏性变更）

**场景**：LLM 调用 `traceSummary('session-abc', 'round-5')`，工具需要从 sessionStore 中按 roundId 定位到原始消息。

**问题**：当前 `ISessionStore.appendMessage(date, session, message)` 和 `SessionMessage` 都不包含 `roundId`。

**影响**：
- 如果 `traceSummary` 只能按 sessionId 加载整个会话的消息，无法精确到具体轮次
- 宿主项目（如泊文）实现了 `ISessionStore`，接口变更需要宿主同步升级

**方案**：`SessionMessage` 新增可选 `roundId` 字段，`appendMessage` 新增可选 `roundId` 参数。

```typescript
export interface SessionMessage {
  role: MessageRole;
  content: string;
  timestamp: string;
  roundId?: string;  // 新增：可选，为空时不影响现有行为
}
```

**`traceSummary` 的降级策略**：
- 有 `roundId`：精确返回该轮次的消息（前后各 +1 轮做上下文）
- 无 `roundId`：返回整个会话的消息摘要（不如精确回溯，但至少可用）
- 对话已删除：返回"该摘要已不可追溯"

**增量改动**：
- `src/memory/sessionStore.ts`：SessionMessage 新增 `roundId?` 字段
- `src/agent/loop.ts`：`appendMessage` 时传入 `roundId`
- 现有宿主无需修改（`roundId` 可选，不传不影响）

### 盲区 4：跨会话 N 轮聚合失效（P2）

**场景**：用户开启了 3 个短会话，每个会话 10 轮。N=50 的聚合阈值永远不会触发。

**问题**：聚合机制只在单会话内生效，短会话的摘要永远得不到聚合。

**分析**：

| 模式 | 优点 | 缺点 |
|------|------|------|
| 单会话聚合（N=50） | 实现简单，边界清晰 | 短会话永远不聚合，跨会话冗余 |
| 全局聚合（按时间窗口） | 覆盖所有摘要 | 聚合边界模糊，跨会话语义断裂 |
| 混合模式 | 灵活 | 实现复杂 |

**结论**：**采用"全局时间窗口聚合"**，而非会话级聚合。

- 聚合阈值：累计 N 条摘要（跨会话累计）
- 时间窗口：最多跨 7 天（防止跨长时间段的摘要被错误聚合）
- 聚合触发：在 `postProcess` 中检查累计摘要数，达到 N 后触发聚合

**增量改动**：
- `RoundSummaryGenerator` 维护一个全局计数器（或从 storage 查询 `source='round-summary'` 的数量）
- 计数器达到 N 且最后一条摘要距当前 > 1 分钟（避免频繁聚合），触发聚合

### 盲区 5：traceSummary 返回内容的规模控制（P2）

**场景**：LLM 调用 `traceSummary('session-abc', 'round-5')`，该轮次包含 6 次 iteration（代码生成 + 工具调用 + 输出），原始消息总长度超过 5000 token。

**问题**：返回完整对话记录可能挤占 LLM 上下文窗口。

**结论**：**traceSummary 的返回内容应有上限**。

```
返回格式：
{
  "sessionId": "session-abc",
  "roundId": "round-5",
  "summary": "该轮对话的摘要内容（来自 round-summary 记忆）",
  "messages": [
    { "role": "user", "content": "..." },
    { "role": "assistant", "content": "..." },
    // 最多返回 5 条消息，超长截断到 2000 字符/条
  ],
  "isTruncated": true,  // 消息是否被截断
  "isTraceable": true
}
```

**限制策略**：
- 最多返回该轮次相关的 5 条消息（用户输入 + 主要回复 + 关键工具调用）
- 单条消息最多 2000 字符
- 超长时返回 `isTruncated: true`，让 LLM 知道内容不完整

### 盲区 6：存量数据迁移的真实成本（P3）

**场景**：项目升级到新版本后，现有 1000 条 `source='insight'` 记忆没有 `sessionId`/`roundId` 字段。

**问题**：这些存量 insight 无法被 `traceSummary` 回溯，也无法被同窗口优先召回利用。

**分析**：

| 迁移方式 | 成本 | 收益 |
|---------|------|------|
| 不迁移 | 零 | 存量 insight 降级为"不可溯源"，但内容仍可被召回 |
| 逐条回溯 | 需要 LLM 调用，成本高 | 可恢复部分溯源，但不精确 |
| 批量标记 | 零成本 | 全部标记 `isTraceable=false`，清晰声明不可溯源 |

**结论**：**存量 insight 不迁移，全量标记 `isTraceable=false`**。

```
升级后 behavior：
  - 存量 insight：isTraceable = false（清晰声明不可溯源）
  - 新产生的 round-summary：isTraceable = true（可溯源）

召回时：
  - 存量 insight 仍可被关键词/语义召回（内容不变）
  - 只是 LLM 知道"这条记忆不可追溯原始对话"
  - 这是合理的——以前的对话确实没有溯源能力
```

**增量改动**：
- 迁移脚本只需一条 SQL：`UPDATE memories SET is_traceable = 0 WHERE source = 'insight' AND is_traceable IS NULL`
- 不需要 LLM 调用，零成本

### 盲区 7：AutoConfigRefiner 与 RoundSummaryGenerator 的交互（P3）

**场景**：`postProcess` 中按顺序执行：InsightExtractor → RoundSummaryGenerator → AutoConfigRefiner。三者都访问 `index`（记忆存储）。

**问题**：AutoConfigRefiner 的 `analyze()` 方法可能也产生记忆（配置建议），这些记忆的 source 是什么？与 round-summary 的关系是什么？

**分析**：AutoConfigRefiner 目前不直接将结果写入 memory storage（它通过 `emit('configSuggested')` 事件通知宿主）。所以不会与 RoundSummaryGenerator 产生存储冲突。

**结论**：**无需特殊处理**。AutoConfigRefiner 和 RoundSummaryGenerator 各自独立，无交叉影响。

### 盲区 8：多轮 iteration 产生的工具调用消息是否应计入摘要（P3）

**场景**：用户说"查一下天气，然后告诉我"。LLM 调用 `getWeather` 工具 → 工具返回 JSON → LLM 生成回复。iteration 序列：

```
iter 1: LLM 输出 tool_call(getWeather)
iter 2: 工具执行结果注入 messages
iter 3: LLM 输出最终回复
```

**问题**：摘要应该基于"用户输入 + 最终回复"生成，还是基于"完整 iteration 序列"？

**结论**：**基于"用户输入 + 最终回复"生成**。工具调用过程是中间步骤，不应出现在摘要中。

- 摘要的输入 = `userInput` + 最终 `assistantContent`（即 `executeChatLoop` 返回的完整回复）
- 工具调用的中间结果不参与摘要生成
- 这与当前 `postProcess` 收到的参数一致（`input` 和 `assistantContent` 已在 `agent.ts` 中定义）

**当前方案已经正确**——不需要额外改动。
