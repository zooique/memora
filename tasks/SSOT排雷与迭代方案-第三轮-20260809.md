## 三、根因收敛

第三轮报告已指出 9/12 同源「方向性操作只写了一半」。本轮排雷进一步收敛为**三条可执行的工序级根因**：

1. **反序列化无单一收口原语**（F2-1）：JSON.parse 散落 + 校验只 warn 不填充 + 返回值被丢弃 → 缺 `parseCheckpoint` 真理源。
2. **「生产-消费」对缺消费者或判据错**（F3-1/F3-2/F2-2/F1-2/F4-2/F4-4）：写了标记没写读它的过滤器、写了回调没写注册、写了分支没写构造者、漏了 error 态守卫、漏了 lowRisk 透传。
3. **字段/状态双语义或双副本**（F1-1/F4-1/F4-3/F2-3）：一个字段承载相反语义、两份副本清理不对称、注释顺序与实际相反、唯一写点被旁路。

**工序级防御（建议进 `.trae/rules` 评审清单）**：任何增/删、生产/消费、读/写、置位/归零的改动，评审必须回答「反方向在哪？谁消费？失败走哪条降级路径？」答不出不许合入。此条能拦住上面 12 项里的 10 项。

### P0 —— 会静默丢失用户数据或崩进程

#### T0-1（F2-1）收口 `parseCheckpoint` + 字段补齐
- **根因**：反序列化散落且无降级填充，缺单一收口原语。
- **修复草图**：
  - 新增 `private static parseCheckpoint(json: string): SessionCheckpoint | null`
    - `JSON.parse` 包 try/catch，畸形 JSON 返回 null（不再抛 TypeError）。
    - 字段补齐：`hotMemory ??= []`、`plan ??= []`、`role ??= {name:'assistant'}`、`standard ??= []`、`resource ??= []`、`pauseMeta ??= undefined`、`goalChangeSeq ??= 0`、`lastHeartbeat ??= Date.now()`。
    - 调 `validateCheckpointIntegrity` 仅做 warn（不再假装填充），返回补齐后的对象。
  - `loadPersistedCheckpoint`（:445）与 `restoreFromCheckpoint`（hotMemory.map 处）共用 `parseCheckpoint`。
  - `loadPersistedCheckpoint` 的 catch(:493) 仍返回 null（降级内存模式），但路径前置已通过 parseCheckpoint 拿到带默认值的对象，不再整会话消失。
- **防回归测试**（uninterruptedWorkflow / sessionCheckpointLifecycle）：
  1. 缺 `hotMemory` 字段的磁盘 JSON → load 后 `cp.hotMemory` 为 `[]`（非 undefined，不崩）。
   - 变异：临时删补齐逻辑 → 测试转红。
  2. 缺 `plan` 字段 → `cp.plan` 为 `[]`。
  3. 畸形 JSON → load 返回 null（不抛）。
- **边界**：`parseCheckpoint` 只负责「补全到可用态」，不负责「丢弃旧版本检查点」；版本迁移交给 T1-4 的 `schemaVersion`。

#### T0-2（F3-1）对账判据改 `seenIds`
- **根因**：`loadedIds` 仅含「本次读成功」的规则，瞬时读失败（`EACCES`/文件占用）被 `skipped++` 排除 → 误判为孤儿软删。
- **修复草图**：
  - `loader.ts` `LoadResult` 增 `seenIds: string[]`；在 `fileStore.list` 后、对每个 name **只要尝试读取就 push 到 seenIds**（:68-95 区间内，无论读成功/占位/抛错都计入；占位模板本质文件在磁盘，应计入）。
  - `projectManager.ts:314` 的 `fileBackedIds` 由 `loadedIds` 改为 `seenIds`（合并 projectResult + configResult 的 seenIds）。
  - 保留 T6 的「仅 rule 源 / 仅启动边界」范围不变（避免误删运行时规则）。
- **防回归测试**（projectManager / loader）：
  1. 注入一个读取抛错的 rule 文件 → 重启后该规则**仍在索引**、仍注入 system prompt。
   - 变异：改回用 loadedIds → 测试转红。
  2. 真正删除的 rule 文件 → 仍被软删（seenIds 不含它）。
- **边界**：`seenIds` 不含运行时 `addRule` 注入的 id（addRule 不写文件）→ 不误删运行时规则，与 T6 结论一致。

#### T0-3（F2-2）补偿闭环兑现
- **根因**：`record.ok=false` 写了但无读取方、无标脏 → 重复补偿 + 重启后标记丢失。
- **修复草图**（选「兑现」而非「收窄」，为 MCP 重复副作用兜底）：
  - `ToolExecutionRecord` 增 `compensatedAt?: number`。
  - `getNonIdempotentExecutions`（:1287）过滤改为 `!r.compensatedAt`。
  - `compensateTool`（:1360 后）写 `record.compensatedAt = Date.now();` 并 `this.touchCheckpoint();`。
  - **注意**：`compensateTool` 在 `restoreFromCheckpoint` 循环(:1379) 中调用，标脏后需确认 `flushCheckpoint` 在 restore 上下文安全（落盘补偿态是期望行为，可行）。
- **防回归测试**（sessionManager）：
  1. 同一检查点 restore 两次 → 第二次 `getNonIdempotentExecutions` 为空（已补偿）。
   - 变异：删 `compensatedAt` 过滤 → 测试转红（重复补偿）。
  2. 补偿后 `checkpointDirty` 为真（标脏生效，重启不丢）。
- **边界**：若评估后认为「补偿本就是幂等告警、不该变状态」，则走「收窄」分支——删 `record.ok=false` 与注释，明确声明补偿是幂等告警。本方案默认「兑现」，但二选一，禁止维持现状。
