> 模块：`src/agent/`（内核 `@zooique/memora` v3.0.0）
> 重点：`src/agent/loop.ts`、`src/agent/guardRail.ts`
> 日期：2026-09-16
> 性质：**只诊断、不改码**。对"是否带伤"假说做证实/证伪。
> 判据来源（项目自带法律条文）：`legacy-contract-audit-rules.md`、`single-truth-source-mindset.md`、`architecture_philosophy_rules.md`、`programmer-mindset-rules.md`、`progressive-refactor-rules.md`、`ADR-017/023/031`、`.trae/documents/loop运行时护栏SSOT收敛方案.md`、`.trae/documents/任务表链路质量审查与双病根收敛.md`

## 0. TL;DR（结论先行）

**根因一句话：** loop.ts 的**「判定侧」与「事实/计数侧」没有单一收口**——护栏判定搬去了 `guardRail.ts`，但喂给判定的计数、以及判定产出的事实（blocked）仍散在 `loop.ts` 里由**平行数组 + 手写喂数**维护，于是"判据"和"喂给判据的事实"分居两文件、靠约定对齐而无可执行的不变量；任何一处口径漂移都静默失配。这不是单个 bug，是**收敛做到一半留下的结构性缺口**。

**四症状同源性判定：**

| 症状 | 与共同根因的关系 | 结论 |
| --- | --- | --- |
| ④ UI 显示异常 | **直接同源**（实锤） | 与 ①③ 同源 |
| ① 重复查看文件（防重没拦住） | **部分同源 + 一条独立缺口** | 部分同源 |
| ③ 循环调用工具（收敛不住） | **同源**（判据/计数/阈值分散） | 与 ①④ 同源 |
| ② 意外终止 | **不同源**（终止路径均为显式 return，无"意外"分支；最多经 ④ 次生） | **拆开** |

即：**①③④ 同源（判定/事实/计数未单一收口），② 不同源**。主理人"四类症状同源"的假说**不成立**——②必须单列。

**是否建议做结构性收敛：是。** 但**不是推翻重写，也不是再加一层补丁**——是把已开工的护栏收敛**做完**（写侧收口）+ 修一处陈年数组错位 + 按职责拆两块出 loop。理由：改动上千行、净增仍有 +377 行（见 §1.2），但 `guardRail.ts` 的写侧钩子 `onExec` **零消费**（§2.2），说明"新增护栏只注册不再动主循环"的目标**尚未达成**，现在停手 = 半成品带伤固化。

**收敛的 P0 项（两项）：**
- **P0-1** 把 `blockedFlags` 平行布尔数组收口为**单一返回值**（治④，补测试盲区）。
- **P0-2** 把 loop 的护栏**写侧喂数收口进 guardRail**（把 `onExec` 从死键变真消费，治①③）。

## 1. 复核与证伪（先推翻主理人给的前提）

> 主张"对抗式审查"：以下三条主理人前提经实证**不成立或需修正**。

### 1.1 证伪：「loop.ts ≈1500+ 行」——实际 **2660 行**

**【实锤】** 字节级统计（`[IO.File]::ReadAllBytes` 数 `\n`）：
- `src/agent/loop.ts` = **2660 行**（LF=2660, CR=0）
- `src/agent/guardRail.ts` = **353 行**（Read 工具可见末行 353）
- 对照：`agent.ts` = 1905 行、`toolExecutor.ts` ≈1215 行、`builtinToolHandlers.ts` ≈1132 行。

> 口径提醒：`Get-Content | Measure-Object -Line` 对同一文件给出偏小值（2219/2052），**不可用**；以 `ReadAllLines`/字节 LF 计数为准。主理人"约 1500+ 行"的旧印象已过时，loop.ts 比预估大 ~76%。

### 1.2 证伪：「改动上千行，几乎没长（净增 ≈26 行）」——实际 **净增 +377 行**

**【实锤】** 用 git 端点差分（编码无关，最可靠）：
- `git diff --shortstat 681978a6^ HEAD -- src/agent/loop.ts` → **674 insertions / 297 deletions** ⇒ **净 +377 行**。
- 窗口内逐提交 `--numstat` 求和：**812 增 / 435 删**（=1247 行被触碰），增删比 **1.87**。
- 最新提交 `b15220402`：**106 / 101**（净 +5）——与主理人"106 增 / 101 删"一致。
- 即 loop.ts 在本窗口 **从 2283 行长到 2660 行**。

**结论：** "几乎没长" **不成立**。真实形态是 **"改了 1247 行、净长 377 行"**——不是"冻住"，而是**净累积**。这更危险：说明每次改动**净留下**了 ~26 行/次的新结构（多为字段/分支），正是"上帝类继续膨胀"的形态。

> 主理人"717/338、净≈26"很可能是把 **目录级** numstat（`-- src/agent/`）与 **`guardRail.ts` 的 353 行**混算所致——方法论上把"目录净增"扣掉"新文件行数"当作"loop.ts 净增"是错的。请以本报告 §1.2 数字为准。

### 1.3 部分证伪：「防重/循环疑似四套机制并列」——实为 **2 套去重策略 + 1 套互补台账**

**【实锤】** 逐一定位：

| # | 机制 | 位置 | 粒度 / 判据 | 与其它重叠？ |
| --- | --- | --- | --- | --- |
| a | `DefaultDuplicateCallInterceptor` | `duplicateInterceptor.ts:56-75`；消费 `loop.ts:1251-1286` | **整批工具调用哈希**（跨迭代），返回 `ok/warn`（默认实现**从不返回 block**） | 与 b **策略不同**（批级 vs 主体级） |
| b | `read_dedup` 护栏 | `guardRail.ts:324-352`；数据源 `toolResultCache.ts:201-261` | **同工具+同主体**（闭环内），前提 `isCachedResultStillInContext` | — |
| c | `FileExposureLedger` 分支② | `toolLedger.ts:104-177`；消费 `loop.ts:1611-1628` | **按文件覆盖度**回显替身摘要 | 与 b **互补**（b 管"还在上下文"、c 管"已被压缩"） |

- **`guardRail.read_dedup` 不是第 4 套机制**——它是 b 的**判定搬迁**（把 loop 内联去重判定搬进 guardRail），数据仍来自同一个 `ToolResultCache`。
- c 与 b 的关系，`toolLedger.ts:4-5` **自己明文声明**"二者数据不同……故非 SSOT 并列"，且 ADR-031 明确这是"账本与占用解耦"的**有意互补**。

**结论：** "四套并列" **是误计**。真实为 **a（批级软去重）+ b（主体级硬去重）两套策略 + c（互补台账）**。真正值得收敛的是 **a/b 两套去重策略同时开启且语义边界靠注释维系**（见 §4-1），而非"四套并列"。

### 1.4 证实：「loop.ts 私有字段 ~20 个并列 flag」——成立，且**低估**

**【实锤】** 逐字段清点 `loop.ts:171-360`：**私有字段 52 个**，其中**运行态 flag/计数（布尔或整数）≥ 22 个**：

## 2. 证据（实锤）

### 2.1 【实锤·核心】`blockedFlags` 平行数组与 `results/toolCalls` **索引错位**

**位置：** `loop.ts:1523`（声明）→ 写点 `1583 / 1588 / 1590 / 1624` → 唯一读点 `1649`。

```ts
1523  const blockedFlags: boolean[] = [];
1570  if (guardHit?.guardId === 'search_limit') {      // 搜索分支
1583    blockedFlags.push(true);                        // 单写（对齐）
1585    continue;
1586  }
1588  blockedFlags.push(false);                         // 默认写（每个非 search 工具都会走）
1589  if (guardHit) {                                   // 其余护栏命中（ask_limit/write_loop/read_failed/read_dedup）
1590    blockedFlags.push(true);                        // ★ 二次写 → 同一工具产生 2 条 flag
1592    continue;
1593  }
1624    blockedFlags.push(true);                        // ★ 台账分支②：又在 1588 的 false 之后二次写
1649  const blocked = blockedFlags[i] === true;         // 读点：按 toolCalls 下标读 → 一旦错位，全批记反
```

**推理（确定性强，非猜测）：** `toolPromises`/`results` 每工具恰好 1 条（`1630-1636`、`1639`），与 `toolCalls` 对齐；但 `blockedFlags` 在"非 search 护栏命中"与"台账分支②命中"时**每工具多压 1 条**。于是 `blockedFlags.length = N + K`（N=工具数，K=命中数）。读点 `blockedFlags[i]` 从第一次命中起整体错位。

**后果链：**
- `1649-1650`：`blocked/ok` 记反 → 直接对应**症状④ UI 显示异常**（`tool_result` chunk 的 `ok/blocked` 见 `types.ts:31-43`，`1734-1741` 产出）。
- `1652`：`successfulWebSearchCount` 用错位的 `ok` 累加（web_search 同属 `DEDUP_SUBJECT_EXTRACTORS`，也会经 read_dedup 路径）。
- `1660-1666`：把**被拦截的** `[ALREADY_READ]` 文案当成功结果写进 `toolResultCache.set`（污染指纹）。
- `1669-1700`：对**被拦截替身**执行 `fileExposure.record`（"整读无脚注"分支 `1688-1699` 会对任意"ok 的 read_file"记覆盖度）→ **用替身文本污染台账**（`totalLines`=替身行数），可能反向触发分支②误拦（次生症状①）。【推断，与症状①的次生耦合】
- `1722-1729`：`invalidateFile/fileExposure.invalidate` 也据 `ok` 触发。

**归属（重要）：** git blame 显示 `1588 push(false)` 来自 `9e4b37b6`(2026-09-02)、`1590 push(true)` 来自 `fe33a0034`(2026-09-04)，且在 `b15220402^`（guardRail 迁移**之前**版本）里同构存在（父版本 `_arch_parent_loop` 读得 `1277 push(false)` + `1280 push(true)`）。
⇒ **这是陈年带伤，不是本轮 guardRail 迁移造成的。** 但它**恰好落在**本次收敛的"判定入口"上，且被 161 个测试**整体漏检**（见 2.3）——正是"改来改去没修到根"的典型。

### 2.2 【实锤】护栏"判定侧收了，写侧没收"——`onExec/notifyExec` 是死键

- `guardRail.ts:115` 定义 `onExec?:`；`guardRail.ts:221-225` 定义 `notifyExec()`。
- **全仓 grep `notifyExec|onExec`：仅出现在定义处与注释**（`guardRail.ts:47/92/115/221/223/268`），**零调用、零实现**。
- 计数**仍在 loop 手写喂数**：写侧 `loop.ts:1597-1610`、失败侧 `loop.ts:1704-1719`，写入 `guardState`（`loop.ts:235-243`）。
- `guardState` 只是把原三个散字段（`infoToolFailureBySubject`/`lastWritePath`/`samePathWriteStreak`）**合并进一个对象**，并未下沉到 guard 自身。

**判定：** 这是 `legacy-contract-audit-rules.md §3「僵尸声明」`——**"宣称却零消费的能力位"**（注释在 `guardRail.ts:8-9` 宣称"计数状态内聚到 guard 自身"，实现未做）。也是收敛方案 `.trae/documents/loop运行时护栏SSOT收敛方案.md §二/§四 S3/S5`的**未达成项**（原文："计数状态内聚到 guard 自身，从 loop.ts 删除单点字段"）。

### 2.3 【实锤】测试对 `blocked` 事实的盲区 —— 161 测试全绿却漏检 2.1

我实跑：`npx vitest run src/agent/__tests__/loop.test.ts src/agent/__tests__/guardRail.test.ts` → **2 文件 / 161 测试全绿**（17.45s）。

但 grep `loop.test.ts` 对 `blocked` 的断言**只有一处**（`loop.test.ts:3393-3403`，且**只覆盖 `web_search` 的 search_limit 分支**——恰是唯一"单写对齐"的路径）。对 dedup/read_failed/write_loop/ask_limit 命中的用例，测试只断言**消息内容含 `[ALREADY_READ]`**（`loop.test.ts:4559-4566`），**从不断言 chunk 的 `blocked/ok`**。

**结论：** `guardRail.test.ts` 只测 guard 的**纯函数判定**（`evaluateBlocked`/注册序/文案），`loop.test.ts` 只测**消息内容**——**"判定→事实→chunk"的接线无人守**。这正是 §1.2 的"改动上千行仍带伤"能存活 161 个绿灯的原因。**这是一个可执行的结构性证据，不是措辞。**

### 2.4 【实锤】其他并存/死分支

- **`DefaultDuplicateCallInterceptor.check` 永不返回 `'block'`**（`duplicateInterceptor.ts:61/65/70/74` 只返回 `ok/warn`），而 `loop.ts:1273-1283` 有完整 `block` 分支（且 `block` 直接 `return 'done'` 终止 turn）。⇒ 该分支只对**宿主注入型**拦截器可达（测试用 `always-block` 桩，见 2.3 日志）。属"能力位对默认实现恒 false"。
- **`buildPromptSection` 零生产消费**：`guardRail.ts:228-234` 定义，仅注释（`loop.ts:1980-1984`）与测试（`guardRail.test.ts:170-182`）引用。已**显式文档化**为"宿主可选能力"⇒ 属"已声明的通道零验收"，非隐性带伤（判**良性偏僵尸**）。
- **`guardRail.ts:17-19` 注释仍写"S1 阶段（shadow evaluate）"**，但 `evaluateBlocked` 已是**真拦截**（`loop.ts:1553` 起真用）⇒ 注释滞后于实现（`comment-doc-slimming` 范畴的残痕）。

## 3. 根因

### 3.1 共同根因（症状①③④）：**判定侧 / 事实侧 / 计数侧三权分立，无单一收口**

```
        ┌─────────────────────────── guardRail.ts（判据归此处）───────────────────────────┐
        │  matches / shouldBlock / promptId / 阈值真源 / life                            │
        │  onExec ✗（死键，零实现）                                                      │
        └───────────────────────────────────────────────────────────────────────────────┘
                     ▲ 读：counters（由 loop 组装后传入）
                     │ 写：loop 手写喂数（1597-1610 写侧 / 1704-1719 失败侧）
        ┌──────────────────────────── loop.ts（事实/计数归此处）───────────────────────────┐
        │  guardState（235-243）＋ 平行数组 blockedFlags（1523/1583/1588/1590/1624）        │
        │  → 读点唯一 1649 → 产出 tool_result.ok/blocked（1734-1741）                      │
        └───────────────────────────────────────────────────────────────────────────────┘
```

**一件事（"这个工具该不该拦、拦了没"）被拆成三份**：判据在 guardRail、计数在 loop、事实（blocked）用平行数组镜像——**三者之间没有任何编译期或运行期不变量**（既非同一对象、也非同一返回值），全靠人工约定。

对照判据：
- `single-truth-source-mindset.md` 核心公理："SSOT 不是只有一个文件，而是**只有一个设计原点**"。此处**有三个原点**。
- `legacy-contract-audit-rules.md §3「双轨镜像」`识别信号："两处存同一份状态，靠约定对齐"——`blockedFlags`（写 4 处/读 1 处）与 `guardState`（写 loop/读 guardRail）**双命中**。

### 3.2 症状① 的独立缺口（与共同根因并列，不混谈）：**read_dedup 的放行前提仍与"占用"耦合**

- `guardRail.ts:328-332`：`read_dedup.shouldBlock` 要求 `hit !== undefined && isCachedResultStillInContext(hit)`。
- 即：**内容一旦被压缩/裁掉/落盘改写 → 放行重读**（`loop.ts:2629-2634`）。
- 台账分支②（`toolLedger.ts:104-120` `shouldEchoLedgerStub`）本应兜住"已压缩"情形，但其覆盖度**只在 read_file 有分段脚注或整读成功时写入**（`loop.ts:1669-1700`）；**读失败（幻觉文件）不写台账**——读失败走 `read_failed`（阈值 3，`guardRail.ts:311`）。
- 叠加 2.1 的 `ok` 错位（命中分支② 时本工具 `ok` 记反），**"缝"进一步变大**。

⇒ 症状①（重复查看文件）**既是共同根因的表现，又有一条 ADR-031 遗留的结构性缺口**（判定前提与占用耦合，方案自认"保守：宁可多读"）。注意 ADR-031 §7 已把"补缝过度拦截"登记为**待验证候选**——说明这条缝**项目自己知道**，属"探索期允许的判据改动"（见 §5）。

### 3.3 症状②（意外终止）——**不同源，必须拆开**

loop 的所有终止都是**显式 return**，无"意外"路径：

| 终止点 | 行号 | 触发 | 是否"意外" |
| --- | --- | --- | --- |
| `'budget'` | `_callAndRoute 960-966` / `_prepareContext 1152-1160` | tokenBudget 触顶 | 有意 |
| `'done'`（LLM 收尾） | `handleIterationResult 816-841` | LLM 纯文本结束 | 有意 |
| `'aborted'` | `983-1009` / `1294-1308` | signal abort / timeout | 有意 |
| `'paused'` | `_handleInterrupt 925-929` / `handleAskUser 1380` | 暂停 / ask_user | 有意 |
| maxIterations | `runIterationLoop 808-810` | 撞迭代上限 | 有意兜底 |
| **骨架剔除即 done** | `handleTextResponse 1455-1465` | 正文含 `<tool_call>` 骨架 | ⚠️ 语义上"没交付即结束" |
| 空响应兜底即 done | `1466-1476` | 空响应 | ⚠️ 同上 |

**判定：** 症状②更可能的**独立**来源是——（a）`stripToolIntentSkeleton` 命中即 `done`（模型吐文本骨架时正文被清空 + 直接收尾，用户观感"没干完就停"）；（b）确定性护栏过早收敛（`search_limit` 停搜 `1570-1586` / `read_failed` 硬拦）后 LLM 给出兜底收尾；（c）宿主侧据 **2.1 错位的 `tool_result.ok`** 判定"本轮失败/已完成"而收尾【推断——宿主不在本次审查范围】。

⇒ **② 与 ①③④ 无共同代码根因**；最多经 2.1（④）**次生**。主理人"四症状同源"**不成立**。

## 5. 造伤 vs 止血 判定（用 `legacy-contract-audit-rules §7` 逐条判）

**§7 铁律：** **改「判据」＝造伤高风险；改「喂给判据的事实」＝止血。** 探索期也允许改判据，但必须带 ①可追溯 ②可观测 ③可退出。

| 改动 | 提交 | 属 | 判定 |
| --- | --- | --- | --- |
| 账本与占用解耦（判定只记"发生过"，不依赖"在不在上下文"） | `0e0c6124`（142/74） | **改事实** | **止血** ✓ 合规。§7 的教科书式正例。 |
| `web_fetch/trace_summary` 并入统一同参防重（主体扩展，判据零分叉） | `193e0a4d`（19/3） | **改事实** | **止血** ✓ 合规（§7 引言亲自点名此例"字面违规、意图合规"）。 |
| 分支②回显判定收敛为 `shouldEchoLedgerStub` 单一真理源、删死分支 | `3d271318`（6/12） | **改判据（收敛分歧）** | **止血/真收敛** ✓ 合规（带 `metrics.ledgerStubEchoCount` 观测、删死码）。 |
| 无区间整读"有覆盖即回显"（分支②放宽） | `142814c7`（11/8） | **改判据（加严拦截）** | ⚠️ 合规但**未定类**——正是 ADR-031 §7"补缝过度拦截候选"（登记 2026-09-15，带观测+待退出）。**这是探索期允许的判据改动**，非违规造伤。 |
| 覆盖区间判定收敛冗余重读（P0-1b） | `e81bec82`（15/8） | **改判据（加严）** | ⚠️ 同上，登记候选。 |
| GuardRail SSOT 收敛 + 阈值真源化（判定**搬迁** + `readFailed` 独立真源） | `b15220402`（106/101） | **判据搬迁 + 阈值真源化** | **意图＝止血**（语义不变，readFailed 值仍 3），**但执行＝半成品**：写侧未收口（§2.2）、死键 `onExec` 未清、且**在搬迁中保留了陈年 `blockedFlags` 错位**。 |

**总判定：** 最近的护栏/防重改动**主体是"止血/收敛"，不是"造伤"**。真正的问题**不是某次改了判据**，而是：
1. **收敛只做了一半**（判定搬了、写侧没搬）——留下 V2/V3/V9 的"双轨未收口"，这是**结构性、可复发的伤**（下一次改判据必再漂移）；
2. **陈年错位（V1）在搬迁时被原样搬走**——"改判据"的动作**没有顺手修掉它本可轻松修掉的接线 bug**，属"收敛动作未带验证闭环"。

这和 `programmer-mindset-rules.md §1.1「区分症状与根因」`、`§1.2「每次只修一个根因 + 修复后三步验证」`相冲突：本次收敛**缺"验证接线"的第三步**（161 绿灯掩盖了接线错误）。

## 6. 收敛方向（结构性，非补丁；P0/P1/P2）

> 总原则（`programmer-mindset-rules §2.2` + ADR-017）：**嫁接而非并列**——所有收口都落到**已有模块**（`guardRail.ts`/`contextPreparer.ts`/`messageHistory.ts`/`sessionStateMachine.ts`），**不新建引擎**；**每次只修一个根因**，各自可验证、可回滚。

### P0-1 · 把 `blockedFlags` 收口为**单一返回值**（治④，修 V1）
- **收敛点（单一收口文件）：** `loop.ts` `executeToolCalls`（1501-1751）。
- **做法：** 删除平行布尔数组，把每工具的判定结果并入 `toolPromises` 的返回结构（如 `Promise<{ content: string; blocked: boolean; guardId?: GuardRailId }>`），`_processToolResults` 与 `yield tool_result`（1734-1741）从同一结构取 `blocked/ok`。使"一行工具 = 一个结构体"，**结构上不可能错位**。
- **验收：** 新增断言——dedup / read_failed / write_loop / ask_limit **各自命中**时 `tool_result.blocked===true && ok===false`（补齐 §2.3 盲区）；161 现有 + 新断言全绿；`tsc --noEmit` 0 错。

### P0-2 · 护栏**写侧收口**：把 `onExec` 从死键变真消费（治①③，修 V2/V3/V9）
- **收敛点（单一收口文件）：** `guardRail.ts`（loop 只留"装载 + `notifyExec` 调用"）。
- **做法：** 每个 guard 实现 `onExec`（连写递增 / 失败+1 / 成功清零），计数状态**内聚进 guard 实例**；loop 在结果处理处仅调 `this.guardier.notifyExec(ctx)`；**从 loop 删除** `guardState:235-243`、写侧 `1605-1609`、失败侧 `1711-1717`。
- **验收：** grep 确认 `loop.ts` 不再含 `guardState`/`lastWritePath`/`readFailBySubject`/`samePathWriteStreak`；`guardRail.test.ts` 新增 `onExec` 递推用例（换路径复位 / 阈值命中 / 成功清零）；161 + 新用例全绿。

### P1-1 · 收敛"防重"双轨的语义边界（修 V4）
- 保留 a/b 两者（**粒度不同，不可合并**），但在 `guardRail.ts` 头部**显式登记两者正交**：a=整批同调用（叙事级软提示），b=同主体（事实级硬拦）；并把 a 的 `block` 分支（`loop.ts:1273-1283`）标注为"仅宿主注入型可达"。
- **验收：** 单一文档说清二者判据/阈值/生命周期，无同名歧义；默认拦截器不再暴露未达的 `block` 能力位（或显式注释其为扩展点）。

### P1-2 · loop.ts 职责拆分（`progressive-refactor-rules §2.2 模式 B`，先拆两块）
现状 loop.ts 承载 **约 20 类职责**（远超 §1 的"≥5 职责"阈值）：turn 入口、step 编排、中断/气口、上下文准备、LLM 调用、结果路由、工具执行编排、防重、护栏、自审查、任务表 nudge、ask 挂起、中断消费、观测埋点、消息写入口、systemPrompt 构建、轮次句柄、压缩实现、骨架剔除、provider 门控。
- **拆分点 1（优先，共享数据源少、职责封闭）：** `_prepareContext`（1070-1189，含 intel 注入 / 搜索收敛 / 软上限 / tokenBudget / 任务表注入 / nudge）→ **下沉到已存在的 `contextPreparer.ts`**（现 183 行，本就承接装配职责）。
- **拆分点 2：** `_handleInterrupt`/`_consumeInterjects`/`interruptQueue`/`pause`/`ask` 挂起（660-712、893-937、1343-1440）→ **下沉到 `sessionStateMachine.ts`**（现 167 行，本就管会话三态/续跑）。
- **验收：** loop.ts 从 2660 行下降 ~500+ 行；`tsc` 0 错；161 全绿；loop 只留"step 编排 + 结果路由"；**不改任何对外契约**（sugar 方法名保留、内部委托，`§6.2`）。

### P2-1 · 剥离观测埋点与消息写入口
- `getMetrics`/`recordBudget`/`recordOccupancy`/`refreshOccupancyDialogue`（2185-2244）→ 归 `LoopMetrics`/`tracer`（已存在）；
- `append*`/`clean*`（2444-2558）→ 归 `messageHistory.ts`（已存在，513 行）。

### P2-2 · 清僵尸声明
- P0-2 落地后 `onExec/notifyExec` 成为真消费（**必须在同一收敛里做完，否则删除**，不留"宣称零消费"）；
- `buildPromptSection`：已文档化为宿主可选，**保留但移出内核默认面**（或在导出注释标注为宿主生长缺口），不视为内核僵尸。

### 收敛顺序与红线
`P0-1 → P0-2 →（各自全绿）→ P1-1 → P1-2 → P2-*`。每步独立提交、独立全绿、可中途叫停。**红线：** `askCountThisTurn` 的 `perInput` 跨续跑累计不得并入 `perStep`（`loop.ts:757-758` 现有语义）；拦截不污染 metrics（`blocked≠失败`）；CTX-1 防死锁前提（"结果仍在上下文才拦"）不得动。
