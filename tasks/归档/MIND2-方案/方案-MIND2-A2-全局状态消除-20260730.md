# MIND2-A2 内核全局状态消除方案

## 一、现状分析

### 1.1 演进路径

ADR-SP-019 要求"所有模块级全局可变状态必须消除，使用显式依赖注入"。
审查发现 3 处模块级状态：

| 文件 | 变量 | 可变性 | 性质 |
|------|------|--------|------|
| logger.ts:298 | `export const logger: ILogger` | 初始化后不变（getter 懒升级） | 横切关注点单例 |
| loggerHolder.ts:35 | `let currentLogger: ILogger` | 初始化时变一次（setLogger 桥接） | holder 解耦模式 |
| tracer.ts:81 | `export const NOOP_TRACER` | 不可变常量 | 默认值常量 |

### 1.2 调研结论：不修（合理设计，非有害全局状态）

**关键区分**：ADR-SP-019 的意图是消除"运行时可变全局状态"（如 counter/状态机/运行时 flag），
不是消除"初始化后不变的单例"。logger 的可变性只在初始化时（setLogger），之后只读。

| 判定维度 | logger/loggerHolder | 有害全局状态（如 counter） |
|---------|---------------------|---------------------------|
| 可变时机 | 初始化时（一次性） | 运行时（持续可变） |
| 可测试性 | 已有 setLogger 注入 | 难 mock |
| 设计模式 | 横切关注点单例（pino/winston 标准实践） | 反模式 |
| 改动成本 | 20+ 文件改构造函数 | 低 |

### 1.3 与现有架构的对照

- **tracer 已注入**：Agent 通过 `opts.tracer ?? NOOP_TRACER` 接收——已是注入式
- **logger 是横切关注点**：20+ 模块需要日志，全局单例是标准实践
- **loggerHolder 是解耦设计**：utils 不依赖 logging，通过 holder 桥接——这是合理架构

### 1.4 改动成本评估

将 logger 改为构造函数注入：
- 20+ 文件需改构造函数签名（加 logger 参数）
- 引入大量样板代码（每个 Manager 都要存 this.logger）
- 收益：可测试性提升——但 setLogger 已提供 mock 能力，收益重复

**结论**：改动成本远超收益，判定**不修**。

## 二、不提取的归档

| 项 | 理由 |
|----|------|
| logger 改构造函数注入 | 20+ 文件改动，横切关注点单例是标准实践 |
| loggerHolder 改注入 | holder 是解耦设计，非有害全局状态 |
| NOOP_TRACER | 不可变常量，非可变状态 |
