# memora 内核 + 插件宿主组合 · 设计缺陷与功能缺口评估

> 评估对象：memora 内核（`src/`）+ 两宿主（memora-vscode / memora-sprite）的组合整体。
> 方法：第一性原理（向源头追溯）+ 对抗式审查（grep/实测，非记忆估算）。
> 范围：组合层面的系统性结论，单宿主接线缺口见 [宿主生长缺口扫描-memora-vscode-核实-20260823.md](./宿主生长缺口扫描-memora-vscode-核实-20260823.md)。
> 日期：2026-08-23。

---

## 〇、评估框架

- **设计缺陷**：架构决策本身导致的系统性脆弱点（即使当前能跑，也在埋雷）。
- **功能缺口**：内核能力存在、但宿主无法感知/消费，导致用户无感知的断点。
- 判定须有代码/文档证据；推测项标注「推测」。

## 一、设计缺陷（系统性，有证据）

### D1 · 内核门面收窄，内部 Manager 能力对宿主不可见（可观测性断点）
- **证据**：`agent.ts` 公开 getter 仅 `governance / skills / rolePacks / memory / security / works / sessionManager`（`agent.ts:1699-1788`）。`memoryAdvisor` **无 getter**（仅 internals 字段 `:128/155`）。`MemoryAdvisor` 独有方法 `sourceHealth()` / `detectConflicts()`（L3 冲突检测，`memoryAdvisor.ts:2`）经 `governance` 门面**只暴露 `suggest()`**，其余不可达。
- **后果**：宿主无法消费 MemoryAdvisor 的源健康诊断 / 冲突检测；能力被门面吞掉。
- **性质**：设计取舍（收敛暴露面），但造成"内核有、宿主永不可见"的隐性缺口。
- **修复方向**：若 sourceHealth/detectConflicts 有宿主消费场景，需在 `governance` 门面增转发或 Agent 增 getter。当前无消费者→按 ADR-017「无消费者暂缓」可暂不补。

### D2 · 持久化存储完全下放宿主，且无参考实现（DRY 违反 + 语义分叉风险）
- **证据**：内核 `index.ts` 仅导出 `InMemoryStorage`（`index.ts:80`），**不导出任何持久化实现**。两宿主各自从零实现 `IMemoryStorage`：vscode `WorkspaceStorage`（JSON 关键词，`workspaceStorage.ts`），sprite `SqliteStorage`（SQLite+向量）。
- **后果**：同一 `IMemoryStorage` 契约，两宿主 `search()` 实现能力不一致（vscode 仅关键词、sprite 有语义）→ **内核能力在两宿主表现不同**，违反"内核能力一致"的单一真理源直觉。
- **设计意图确认**：`host-plugin-alignment.md:413` 明确"宿主记忆存储实现要点"——持久化确为宿主责任，是**合理边界**，非缺陷。
- **真实雷区**：`memory-role-pack-boundary.md:81`——内核 `storageInterface.ts` 注释声明"实现侧在宿主"，宿主若写 `WHERE source='rule'` 类查询会**因后端差异静默失效**（vscode JSON 无 SQL、sprite SQLite 有 SQL）。这是**契约模糊导致的隐性功能缺口**。
- **修复方向**：`IMemoryStorage` 契约应明确"宿主不得假设特定查询语法"；或内核提供 `search` 语义的强制规范，让两宿主实现对齐。

### D3 · 两宿主获取内核的机制不一致（单一真理源裂痕）
- **证据**：vscode `package.json:108` 用 `@zooique/memora: file:../..`（symlink，内核变更实时生效）；sprite `package.json` 用 `from 'memora'`（裸包）+ `sync-memora.mjs` 脚本**编译→复制到 node_modules/memora**（最小化 dist）。
- **后果**：sprite 跑的是**内核编译快照**，改内核后须手动/构建时跑 `sync-memora`，否则 sprite 跑旧内核。两宿主"内核事实"可能分叉。
- **设计意图确认**：sprite 注释说明为避免 asar 打入全仓库、刻意复制最小化 dist——**合理妥协**（打包约束），非缺陷。
- **风险**：开发期易踩"改了内核 sprite 没生效"的坑；CI 必须保证 sync 先于 sprite 构建。
- **修复方向**：在 sprite 构建脚本/CI 中强制 sync 为前置步骤（已有 `sync-memora` 被 build:electron 调用，需确认 CI 也接）。

### D4 · loop 内部行为无用户可见事件出口（可观测性断点，跨层）
- **证据**：`loop.ts` 默认 `ResultReplacementStrategy` 压缩 + `DefaultDuplicateCallInterceptor` 去重在跑（实测 `loop.ts:231/234`），但 `types.ts`/`loop.ts` **无 compaction 完成 / duplicate 触发前的 emit 事件**（除已暴露的 `dedupCompleted`）。compaction 无 `compactionCompleted` 事件。
- **后果**：宿主无法告知用户"上下文已压缩"——用户无感知，与"可观测性边界"原则（architecture_philosophy_rules §12）存在张力（原则说可观测性由 ITracer 承载，但 tracer 是开发态，非用户态）。
- **修复方向**：内核 `AgentChunk` 增 `compactionCompleted` 事件（含压缩前后 token 数），宿主在对话面板提示。对应 tasks C1。

## 二、功能缺口（内核能力 ↔ 宿主消费断点）

| # | 缺口 | 类型 | 证据 | 状态 |
|---|------|------|------|------|
| F1 | compaction 用户提示 | 内核缺事件 | 见 D4 | tasks C1（P1） |
| F2 | MemoryAdvisor 源健康/冲突检测 | 门面未转发 | 见 D1 | 暂缓（无消费者） |

| F6 | vscode 无 SQLite | 规模阈值 | 见前轮 C3 | 暂缓（等规模拐点） |

## 三、对抗式审查结论

1. **组合整体健康度高**：内核能力契约清晰（Agent 门面 + AgentOptions 注入 + IMemoryStorage/ISessionStore 接口），两宿主均已基本对齐。无架构级致命缺陷。
2. **真正的系统性缺陷是 D1/D2/D4 的共性——"内核能力对宿主的出口收窄"**：
   - 持久化存储完全下放（D2）→ 两宿主实现分叉
   - 内部 Manager 经门面收窄（D1）→ 部分能力永不可见
   - loop 内部行为无事件（D4）→ 用户态无感知
   - 三者共同指向一个根因：**内核的"宿主消费面契约"未系统化定义**——哪些能力必须暴露、以何种形式（getter/事件/接口方法）、语义如何跨宿主对齐，缺乏单一真理源。
3. **D3 是打包约束下的合理裂痕**，不需修架构，只需 CI 纪律。
4. **两宿主不对称是最大实践风险**：vscode 对齐度高（assembler/checkpoint/向量），sprite 在 assembler/checkpoint 缺位。同一内核、两套宿主事实——这是"自然生长"过程中的必经阶段，但需一份"宿主对齐基线清单"防止漂移。

## 四、建议（按根因归类）

| 根因 | 建议 | 优先级 |
|------|------|--------|
| 宿主消费面契约缺位（D1/D2/D4 共性） | 定义"内核宿主消费面契约"：① IMemoryStorage.search 语义强制规范（防 F2 静默失效）；② 明确哪些 Manager 必须经 Agent getter 暴露；③ loop 关键行为必须 emit 用户态事件 | P1（架构基线） |
| 两宿主事实分叉（D3） | sprite CI 强制 `sync-memora` 前置；建立"宿主对齐基线清单"文档，每内核变更核对两宿主 | P2 |
| 存储语义分叉（D2） | 内核提供 `search` 语义参考实现/测试向量，两宿主实现需过同一测试套 | P2 |
| 门面收窄（D1） | 仅当有真实消费者时，在 governance 增 sourceHealth/detectConflicts 转发 | P3（待消费者） |

> 原则：不预增无消费者接口（ADR-017）；不复制内核逻辑到宿主（宿主只注入/转发/渲染）。
