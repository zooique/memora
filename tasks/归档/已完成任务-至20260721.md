### 提炼的根因模式

**BUG-6 同类模式：过度防御导致 IPC 静默阻断**

| 心智规则 | 本次应用 |
|---------|----------|
| 识别不可逆损失点 | 单向数据流 + 会话级内存态 = 阻断即永久丢失。剪贴板 `pendingItems`、`SUGGESTION_PUSH` 建议、`SPRITE_EVENT` 事件均属此类 |
| 怀疑前提 | "避免向隐藏窗口发送 IPC"听起来合理，但 Electron `webContents.send` 向隐藏窗口发送不抛异常。前提错了 |
| 绕过而非修补 | 不在守卫后加 pending 队列补偿（复杂度与问题本质不匹配），直接移除守卫，委托 `safeSendToWindow` 的 null/destroyed 检查 |
| 区分症状与根因 | "剪贴板丢失"是症状，"isVisible 守卫阻断单向推送"是根因。本次从 1 处扩展到 5 处审计，根因模式批量消除 |
| 方案复杂度匹配问题本质 | 单向推送 → `safeSendToWindow`；请求-响应 → `isFullWindowAccessible`。两套守卫各司其职，无额外抽象 |

### 守卫策略统一规范（沉淀到 windowUtils.ts JSDoc）

| 守卫函数 | 适用场景 | 行为 |
|---------|---------|------|
| `isFullWindowAccessible` | 请求-响应场景（需用户交互，如 WRITE_CONFIRMATION） | 检查 null + destroyed + isVisible + isMinimized，任一不满足返回 false |
| `safeSendToWindow` | 单向数据推送（剪贴板 IPC / 精灵事件 / 配置建议 / 快捷键触发） | 仅检查 null + destroyed，向隐藏窗口仍发送 IPC（渲染层缓存） |
