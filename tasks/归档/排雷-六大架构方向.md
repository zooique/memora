## 方向一：拆解 agent.ts

### 用户方案

将 Agent 类拆为 4 个独立模块：AgentBootstrap（组件组装 + 配置管理）/ AgentChat（对话编排 + 流式处理）/ AgentEvents（事件转发 + 生命周期）/ Agent（薄门面）。

### 雷区识别

#### 雷区 1.1【覆盖遗漏】已有 God Object 拆分成果被忽视

agent.ts 已完成多轮拆分，当前 1473 行，结构清晰：

- 组件组装：已委托给 [assembler.ts](file:///e:/zooique/memora/src/agent/assembler.ts)，Agent.assembleComponents() 仅是薄包装（40 行）
- 归档操作：已拆出 [archiveCoordinator.ts](file:///e:/zooique/memora/src/agent/managers/archiveCoordinator.ts)（152 行）
- 衰减调度：已拆出 [memoryDecayScheduler.ts](file:///e:/zooique/memora/src/agent/managers/memoryDecayScheduler.ts)
- 会话管理：已拆出 [sessionManager.ts](file:///e:/zooique/memora/src/agent/managers/sessionManager.ts)
- 12 个专职 Manager 已就位（Archive/AutoConfig/Config/Insight/MemoryAdvisor/MemoryDecay/MemoryInspector/MemoryMutator/RelationBuilder/Session/SessionArchiver/WorkProjection）

用户方案中的"AgentBootstrap"与现有 assembler.ts + Agent.init() 职责重叠。强行拆分会产生"第二个组装器"。

#### 雷区 1.2【重复定义】AgentEvents 与现有事件系统重叠

事件转发已分散到各 Manager，通过回调模式解耦：

- Agent 继承 TypedEventEmitter（直接 emit）
- SessionManager.forwardEvent 桥接（[agent.ts:928-932](file:///e:/zooique/memora/src/agent/agent.ts#L928-L932)）
- ArchiveCoordinator.emit 回调注入（[archiveCoordinator.ts:33-36](file:///e:/zooique/memora/src/agent/managers/archiveCoordinator.ts#L33-L36)）
- MemoryDecayScheduler.onDecayCompleted 回调注入

提取独立 AgentEvents 会引入"转发中转站"层级，违反自然生长原则（不足 3 次重复不提取）。

#### 雷区 1.3【边界盲区】chat() 状态字段与公开 API 耦合

chat() 专属状态字段：`_chatBusy` / `_chatLockToken` / `chatLockTimer` / `chatAbortController`。但 [forceReleaseChatLock()](file:///e:/zooique/memora/src/agent/agent.ts#L559-L575) 是宿主调用的公开 API，拆分到 AgentChat 后，Agent 门面必须暴露此方法 → AgentChat 实例必须暴露给 Agent → "薄门面"承诺破产。

#### 雷区 1.4【依赖顺序】postProcess 依赖多个私有字段

postProcessInner（[agent.ts:683-787](file:///e:/zooique/memora/src/agent/agent.ts#L683-L787)）依赖 `#config.archiveMode` + `#userProfile` + `insightExtractor` + `history` + `personaManager` + `skillManager` + `autoConfigRefiner`。拆分到 AgentChat 后需要 getter 回调注入（同 ArchiveCoordinator 模式），但 ArchiveCoordinator 已是 postProcess 的归档部分拆分结果。继续拆分会与 ArchiveCoordinator 职责重叠。

#### 雷区 1.5【遗漏】缺少量化依据

用户说"这不是重写，是机械拆分"，但未量化拆分后每个模块的行数。当前 agent.ts 1473 行的组成：

| 区块 | 行数估算 | 拆分后归属 |
|------|----------|-----------|
| 构造 + AgentConfig 类型 | ~120 | AgentBootstrap |
| init/close 生命周期 | ~150 | AgentEvents（生命周期） |
| chat() 核心编排 | ~150 | AgentChat |
| postProcess + postProcessInner | ~120 | AgentChat |
| recallAndInject + injectActiveSkill | ~70 | AgentChat |
| assembleComponents + rebuild | ~60 | AgentBootstrap |
| setProvider/setBackgroundProvider/setArchiveMode | ~60 | AgentBootstrap |
| 12 个 getter 访问器 | ~200 | Agent 门面 |
| 守卫方法 | ~50 | Agent 门面 |
| forceReleaseChatLock + 锁字段 | ~80 | AgentChat |
| getMetrics + 其他 | ~60 | Agent 门面 |

拆分后 Agent 门面仍需 ~600-800 行（getter + 守卫 + 生命周期委托 + 锁管理委托）。"薄门面"承诺缺乏数据支撑。

#### 雷区 1.6【覆盖遗漏】已有 ADR 评估记录

[已完成任务.md](file:///e:/zooique/memora/tasks/已完成任务.md) 中 QC-R2-09 评估："agent.ts postProcess() 拆为独立后处理器 — 2026-06-26 评估：postProcess 仅 80 行且已是薄编排层，提取后收益不抵成本"。postProcess 已通过 ArchiveCoordinator 拆出归档部分，剩余 120 行是角色匹配 + 技能匹配 + profile/insight 触发，是 chat() 的自然后处理。

### 优化方案

**否决"4 模块机械拆分"方案**。理由：违反自然生长原则（3 次阈值），忽视已有拆分成果，"薄门面"承诺缺乏量化依据。

**采纳"增量拆分"方案**，仅拆分内聚性最强、与对话编排耦合最深的部分：

| 任务 | 内容 | 理由 |
|------|------|------|
| AUDIT-1-1 | 提取 ChatLockManager（`_chatBusy` / `_chatLockToken` / `chatLockTimer` / `chatAbortController` + `forceReleaseChatLock` + 超时回调 + token 校验逻辑）到独立模块 `agent/chatLockManager.ts` | 4 个字段 + 1 个公开方法 + 超时回调是 chat() 中内聚性最强的单元；拆出后 chat() 主体逻辑更清晰；forceReleaseChatLock 通过委托暴露，门面契约不变 |
| AUDIT-1-2 | 评估 PostProcessPipeline 拆分可行性（postProcessInner 的角色匹配 + 技能匹配 + profile/insight 触发）| 与 ArchiveCoordinator 边界需先理清，评估而非直接执行 |

**不拆的部分**：init/close（与 Agent 实例强绑定）、assembleComponents（已委托 assembler.ts）、12 个 getter（门面自然职责）。

## 方向四：存储层异步化预研

### 用户方案

决策：IMemoryStorage 是否需要支持异步？如果是，新增 IAsyncMemoryStorage 兄弟接口；如果不是，文档声明"memora 是 Node.js 专用，不支持浏览器"。

### 雷区识别

#### 雷区 4.1【覆盖遗漏】接口注释已声明决策方向

[storageInterface.ts:30-32](file:///e:/zooique/memora/src/memory/storageInterface.ts#L30-L32) 已明确："所有方法均为同步（与 better-sqlite3 API 对齐），调用方已有的 `await` 调用仍然安全（await 同步值 = 立即返回）。未来如需支持异步存储后端（如 IndexedDB），可新增 IAsyncMemoryStorage 接口。"

这不是"未决策"，而是"已决策为同步优先 + 异步预留扩展点"。

#### 雷区 4.2【遗漏】better-sqlite3 同步性是核心优势

[ADR-002](file:///e:/zooique/memora/.trae/rules/decisions/ADR-002-storage-layer.md) 选择同步接口的理由是"与 better-sqlite3 API 对齐"。better-sqlite3 的同步性带来：(1) 无 callback hell (2) 事务原子性保证 (3) 性能优势（无 async 边界开销）。改为异步会丧失这些优势。

#### 雷区 4.3【边界盲区】"浏览器支持"需求从未是目标

当前架构中：

- 内核纯逻辑库（零 native 依赖）→ 理论上可在浏览器运行
- InMemoryStorage（测试用）→ 浏览器可用
- SqliteStorage（宿主）→ 依赖 better-sqlite3，浏览器不可用
- node:sqlite 适配器 → Node.js 22+ 专用
- 精灵宿主是 Electron 桌面应用，浏览器支持从未是 memora 的目标

#### 雷区 4.4【依赖顺序】异步化影响面巨大

IMemoryStorage 有 15 个方法。如果新增 IAsyncMemoryStorage，需要：

1. 定义异步接口（15 个方法签名改为 Promise 返回）
2. Agent 和所有 Manager 改为 await 所有 storage 调用
3. 召回管道（recall.ts）异步化
4. 衰减调度器异步化
5. 归档协调器异步化
6. InMemoryStorage 实现两套接口（同步 + 异步）

影响面远超"预研"范畴，且违反自然生长原则（不足 3 次重复需求不提取）。

#### 雷区 4.5【重复定义】VectorStore 已是异步接口

[IVectorStore](file:///e:/zooique/memora/src/memory/vectorStore.ts) 接口的 search 方法返回 `Promise<Memory[]>`。即语义搜索已是异步，关键词搜索是同步。这是"混合接口"设计，已满足实际需求（向量搜索涉及网络调用必须异步，SQLite 关键词搜索同步即可），无需强制统一为全异步。

### 优化方案

**采纳"保持同步 + 文档声明"方案**：

| 任务 | 内容 | 改动量 |
|------|------|--------|
| AUDIT-4-1 | 在 ADR-002 中补充"同步优先决策"的明确声明段落（已有注释，需提升到 ADR 级别） | ~20 行文档 |
| AUDIT-4-2 | 在 backend_layers_rules.md 的 IMemoryStorage 说明中补充"Node.js 专用，浏览器场景使用 InMemoryStorage" | ~5 行文档 |
| AUDIT-4-3 | 不新增 IAsyncMemoryStorage（未到 3 次重复需求阈值，违反自然生长原则） | 0 行 |

**未来触发时机**：出现真实浏览器使用需求 + IndexedDB 存储后端需求时，再启动异步化预研。

### 雷区识别

#### 雷区 6.1【覆盖遗漏】已按功能域拆分

宿主侧 IPC handler 已拆分为 7 个领域文件：

| Handler 文件 | 职责 |

另有 chatStreamHandler（流式核心）+ minimalHandlers（Agent 未就绪降级）。用户方案中的"按功能域分组"已实现。

#### 雷区 6.2【数据错误】通道总数与 STREAM_* 数量不准确

用户说"82 个通道"，实际 **105 个**（`IPC_CHANNELS` 渲染→主 78 个 + `MAIN_TO_RENDERER_CHANNELS` 主→渲染 27 个）。用户说"7 个 STREAM_*"，实际 **8 个**：

1. SPRITE_STREAM_START
2. SPRITE_STREAM_CHUNK
3. SPRITE_STREAM_END
4. SPRITE_STREAM_RECALL
5. SPRITE_STREAM_TOOL_START
6. SPRITE_STREAM_TOOL_RESULT
7. SPRITE_STREAM_THINKING
8. SPRITE_STREAM_ABORTED

#### 雷区 6.3【遗漏】已有 check-ipc-channels.ts 构建时校验

[check-ipc-channels.ts](file:///e:/zooique/memora/hosts/memora-sprite/scripts/check-ipc-channels.ts) 已实现 preload.ts 与 channels.ts 的通道常量双向一致性校验，lint 时运行。用户方案未提及此已有机制。

#### 雷区 6.4【重复定义】版本管理策略与当前命名规范冲突

当前命名规范：

- 字符串值：kebab-case（如 `'memories-list'`）
- 常量键名：大写下划线（如 `MEMORIES_LIST`）
- 前缀：主→渲染的精灵相关通道统一加 `SPRITE_` 前缀
- 无版本号

引入"v2 前缀"会破坏现有命名规范，且 IPC 通道变更需要 preload + channels + handler 三处同步，版本管理增加复杂度但收益不明（当前无通道需 v2 重构）。

#### 雷区 6.5【边界盲区】合并 STREAM_* 的兼容性成本

8 个 STREAM_* 通道合并为"一个带 type 字段的统一通道"：

- 优点：通道数减少 7 个
- 缺点：
  1. preload 暴露的 API 从 8 个方法变为 1 个方法 + type 参数
  2. 渲染层所有 STREAM_* 监听代码需重写
  3. TypeScript 类型安全降低（联合类型 vs 独立方法签名）
  4. 现有 2917 个测试中涉及 STREAM_* 的需更新
  5. Electron ipcMain 按通道名注册监听器，合并后需在 handler 内部按 type 分发，高频通道（STREAM_CHUNK）增加每次 chunk 的处理开销

成本远超收益。

#### 雷区 6.6【依赖顺序】通道合并需考虑 Electron ipcMain 限制

Electron 的 ipcMain.on/ipcMain.handle 是按通道名注册监听器。合并为统一通道后，需要在 handler 内部根据 type 字段分发，增加一层路由逻辑。对于高频通道（STREAM_CHUNK，每次对话产生数十到数百个 chunk），这会增加可观测的处理开销。

### 优化方案

**否决"通道合并"和"版本管理"方案**。理由：已按功能域拆分；合并成本远超收益；版本管理无实际需求驱动。

**采纳"文档化 + 分组优化"方案**：

| 任务 | 内容 | 改动量 |
|------|------|--------|
| AUDIT-6-1 | 在 channels.ts 中补充功能域分组注释（已有注释分块，补充域标识 `// ─── 对话域 ───` 等） | ~20 行注释 |
| AUDIT-6-2 | 在 directory-structure.md 中记录 IPC 通道治理现状（105 个通道 + 7 个领域 handler + 校验脚本 + 命名规范） | ~30 行文档 |
| AUDIT-6-3 | 新增通道时强制走"领域 handler 归属"检查（PR review checklist 或 lint 规则） | 流程文档 |

**未来触发时机**：通道数超过 150 个或出现跨领域 handler 时再启动合并评估。
