# 发包前文档 × 内核现实对账审查（2026-08-22）

> 审查范围：README.md / README.en.md / LICENSE / config.example.json / role-packs / docs/memora-api-reference.md / docs/memora-接入指南.md / docs/role-pack-开放键指南.md
> 方法：第一性原理 + 对抗式审查，所有结论经 grep / Read / 目录枚举实锤验证（非记忆估算）。
> 结论先行：**文档整体方向正确，但存在 3 个会直接让宿主接入者编译/运行失败的硬伤（🔴 P0），以及 2 处自相矛盾/事实失实（🟡 P1）。核心病灶是「公开 API 文档手抄、未与 `src/index.ts` 单一真理源对齐」这一流程缺陷。**

## 🔴 P0 — 释放即踩坑（文档误导宿主，破坏代码）

### P0-1：api-ref §16 大量「幻影类型导出」（`src/index.ts` 根本不存在）

- **证据**：对 `src/index.ts` 整体 grep 以下 token → **No matches found**：
  `SuggestOptions` `SuggestHit` `SourceHealthStatus` `SourceHealthEntry` `SourceHealthReport`
  `DedupPair` `DedupVerdict` `DedupVerdictSummary` `DedupReport`
  `TimelinessVerdict` `TimelinessReport` `ConflictVerdict` `ConflictReport` `ConflictInfo` `SessionArchiveResult`。
- 这些类型**内部确实定义**（如 `src/agent/managers/memoryAdvisor.ts` 定义 `SourceHealthReport/Entry/Status`、`src/agent/managers/dedupManager.ts` 定义 `DedupReport`），但**未被 `index.ts` 再导出**，不属于包对外边界。
- api-ref §16（line 963）明文宣称「**以下导出与 `src/index.ts` 完全对齐**」——**为假**。
- **宿主后果**：`import type { DedupReport } from '@zooique/memora'` 直接 TS2305 编译失败。
- **修复**：要么从 §16 删除这些内部类型；要么若应公开，则在 `index.ts` 补 `export type { ... }`（§12 / 接入指南已引用 `DedupReport` 等报告类型，倾向补导出）。并删掉「完全对齐」这句断言。

### P0-2：Eval 子系统**完全不存在**，却被写成公开 API

- **证据**：
  - `src/eval/` 目录**仅含 `__tests__/`，无任何实现 `.ts`**（`ls src/eval/` → `__tests__`）。
  - 对全 `src` grep `EvalRunner|collectAgentChunks|evaluateResult|EVAL_SCENARIOS` → **No files found**。
  - 然而 api-ref §16（lines 1108-1112）声明 `export type { EvalScenario, EvalExpectation, EvalResult }` / `export { collectAgentChunks, evaluateResult }` / `export { EVAL_SCENARIOS, EvalRunner }`；
  - 接入指南 §九（lines 571-617）整章「评估体系（Eval）」并给示例 `import { collectAgentChunks, evaluateResult } from '@zooique/memora'`。
  - **自相矛盾**：README.md (zh) line 17 边界声明「agent 级行为评估（eval）与独立验证**不在内核范畴**」，与 api-ref / 接入指南直接冲突。
- **宿主后果**：照接入指南 §九 写代码 → import 失败；且同一文档集内契约不闭合。
- **修复**：与 README 边界声明保持一致——**删除** api-ref §16 的 Eval 导出块与接入指南 §九；若要保留 Eval，须先实现并导出（当前 src/eval 为空壳）。

### P0-3：api-ref §0.2 配置示例是**扁平结构**，真实 `Config` 是**嵌套在 `llm` 下**

- **证据**：
  - api-ref §0.2（lines 63-71）示例：`{ "providers":{...}, "active":"deepseek", "background":{...}, "taskRouter":{...} }`（扁平）。
  - 真实 `Config` 类型 `src/config/loader.ts`（lines 84-97）：`llm: { providers, active, background, taskRouter }` 嵌套；`parseConfig` 读 `input.llm`（line 128）。
  - `config.example.json` **正确**：`llm.providers` / `llm.active` / `llm.background` 嵌套。
- **宿主后果**：照 api-ref §0.2 抄扁平 `providers` → `llm` 为 undefined → `createLlmProvider` 抛「LLM providers 未配置」。
- **修复**：§0.2 的 jsonc 示例改为与 `config.example.json` 一致的 `llm` 嵌套形态。

## 🟡 P1 — 自相矛盾 / 事实失实（误导但非硬崩）

### P1-1：中 / 英 README 对「宿主项目」说法冲突，且 sprite「独立仓库」失实

- **证据**：
  - README.md(zh) line 230：「[memora-vscode] — VS Code 插件宿主（**第一宿主**）」；line 232：「桌面精灵宿主（memora-sprite）**已独立仓库独立开发**」。
  - README.en.md line 221：「[memora-sprite](hosts/memora-sprite/) — An Electron-based desktop sprite host (v1.5.0)」（未提 vscode 为宿主）。
  - 事实：`ls hosts/` → `memora-sprite/` 与 `memora-vscode/` **两者皆在本仓库**；`cat .gitmodules` → **NO .gitmodules**（非子模块）。sprite 就在本仓库，zh line 232 陈述错误。
- **修复**：统一表述——两者均在 `hosts/` 下、非外部仓库；明确「参考宿主」是谁（或两者并列说明），删除「已独立仓库独立开发」。

### P1-2：接入指南 line 460 把配置文件名写成 `memora.json`

- **证据**：接入指南 §六 line 460「loadConfig(path?) | 加载 **memora.json** 配置文件」。真实 `src/config/loader.ts` line 392 读 `resolve(process.cwd(), '.memora/config.json')`（显式 path 另说）。文件名是 `config.json`，非 `memora.json`。api-ref §0.2 line 40 称 `config.json`（名字对、缺 `.memora/` 路径）。
- **修复**：「memora.json」→「config.json」，并补默认路径 `.memora/config.json`。

## 设计 / 流程缺陷（根因）

1. **公开 API 文档无 SSOT 约束**：项目自诩 SSOT-first，但 api-ref §16 是手抄清单，已与 `src/index.ts`（真 SSOT）漂移，出现 15+ 幻影导出 + 整个 Eval 子系统纪实。**建议**：CI 用脚本比对 `index.ts` 的 `export` 集合与 api-ref §16，或干脆由 `index.ts` 生成该章节，否则每次改导出都会悄悄腐烂。
2. **同一文档集内契约不闭合**：README 边界声明「eval 不在内核」与 api-ref / 接入指南「eval 是公开 API」自相矛盾；config 形状在 api-ref §0.2 与 config.example.json 之间不一致。文档间缺乏交叉引用的一致性闸门。
