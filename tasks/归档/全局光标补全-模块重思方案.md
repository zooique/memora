# 全局光标补全 · 模块重思方案

> **来源**：新枝破土（输入补全深化）→ 问诊门控 → 模块重思
> **日期**：2026-07-14
> **状态**：📋 方案待评审（模块重思产物，未实装）

## 1. 问题陈述

### 1.1 战略定位

用户明确指出：**输入补全是桌面精灵的差异化打法**。

| 维度 | 分析 |
|------|------|
| 竞争劣势 | memora 的对话/记忆/角色功能被大厂碾压，无差异化壁垒 |
| 核心优势 | 桌面精灵常驻后台，可在日常使用中全局生效 |
| 差异化路径 | 全局光标补全——任何应用输入时都能调用个人记忆库 |
| 目标体验 | 用户激活光标输入时，静默启动补全，无需切窗 |

### 1.2 现状

当前输入补全（[quickInputCompletion.ts](../hosts/memora-sprite/src/electron/renderer/quick-input/quickInputCompletion.ts)）已实现：

- 浮窗模式：`Ctrl+Shift+I` 触发，独立窗口，屏幕居中靠上 1/4 定位
- 数据源：`searchMemories` + `searchSessionMessages` 双源并行
- 补全能力：防抖触发 / 候选合并去重 / ↓↑ 键盘导航 / Tab 回填
- 反馈回路：采纳 boost（单次会话内）+ score 量纲统一

### 1.3 痛点

| 痛点 | 说明 |
|------|------|
| 触发割裂 | 需要主动呼出独立浮窗，打断当前工作流 |
| 定位不跟随 | 屏幕居中而非光标位置，视线和鼠标需要长途迁移 |
| 回填需手动 | 选中后写入剪贴板，用户还需手动 Ctrl+V 粘贴 |
| 场景局限 | 仅在 memora 内有效，未发挥"常驻后台 + 全局生效"优势 |

### 1.4 设计约束

| 约束 | 说明 |
|------|------|
| 不违反内核零依赖 | native 依赖只放在宿主项目（hosts/memora-sprite） |
| 不新增 IPC 治理压力 | 当前 IPC 通道数 105，接近 150 治理阈值，优先复用现有通道 |
| 隐私边界 | 不监听全局键盘输入，不读取其他应用窗口内容 |
| 跨平台 | Windows 优先，macOS/Linux 后续（native 依赖需跨平台构建） |

## 2. 技术可行性分析

### 2.1 "静默启动"的技术边界

用户期望"光标激活输入时静默启动"，但技术上存在两层"光标"概念混淆：

| 光标类型 | 获取方式 | 跨应用可行性 |
|---------|---------|------------|
| 鼠标光标（mouse cursor） | `screen.getCursorScreenPoint()` | ✅ 已有先例（[quickInputWindow.ts:156](../hosts/memora-sprite/src/electron/windows/quickInputWindow.ts)） |
| 文本输入光标（caret） | UI Automation API / MSAA | ❌ 需 native addon 调用系统 API |

**结论**：完全静默启动（监听其他应用的 caret 焦点变化）在 Electron 原生能力下不可行。可行折中：

- **保留快捷键触发**（不静默），但窗口跟随鼠标光标位置弹出
- 这是正确的隐私边界——不监听全局输入，只在用户主动触发时工作

### 2.2 现有基础设施复用率

研究子代理探索结果显示，`quickInputWindow` 已具备全局光标补全的 80% 基础设施：

| 能力 | 现状 | 复用度 |
|------|------|-------|
| 全局快捷键触发 | `Ctrl+Shift+I` 已绑定，ShortcutManager 支持热更新 | 100% |
| 光标屏幕定位 | `screen.getCursorScreenPoint()` 已使用 | 100%（改定位公式即可） |
| 候选数据源 | `searchMemories` / `searchSessionMessages` 已暴露到渲染进程 | 100% |
| 剪贴板写入 + 三重保护 | `confirmQuickInput` + `suppressNextChange` 链路完整 | 100% |
| 失焦延迟关闭 | 200ms blur 延迟，给 Alt+Tab 切换留余量 | 100% |
| 动态高度调整 | `resizeQuickInput(80-400px)` 已预留 | 100% |
| 候选列表 UI + 键盘导航 | `quickInputCompletion.ts` 已完整实现 | 100% |

**关键发现**：无需新建窗口类型，复用 `quickInputWindow` 改造即可。

### 2.3 回填机制的技术路径

补全结果回填到当前焦点窗口是核心难点，有三条路径：

| 方案 | 机制 | 依赖 | 体验 | 可行性 |
|------|------|------|------|-------|
| A. 剪贴板 + 手动粘贴 | 选中 → 写剪贴板 → 浮窗关闭 → 用户 Ctrl+V | 零新依赖 | 多一步操作 | ✅ MVP |
| B. 剪贴板 + 自动粘贴 | 选中 → 写剪贴板 → 恢复焦点 → 模拟 Ctrl+V → 恢复剪贴板 | `@nut-tree-fork/nut-js`（native） | 无缝 | ✅ 进阶 |
| C. 直接键盘事件注入 | 选中 → 模拟逐字符键盘事件 | native 模块 | 中文 IME 支持差 | ❌ 不推荐 |

**方案 B 的 native 依赖评估**：
- `@nut-tree-fork/nut-js`：活跃维护，跨平台（Win/Mac/Linux），支持键盘模拟
- 宿主项目已有 `better-sqlite3` native 依赖，打包流程已支持 native 二进制
- 体积增加约 5-10MB，对桌面应用可接受
- 与 Electron Node.js 24 LTS 兼容（需验证）

**业界共识验证**（2026-07-14 调研）：三个同类开源项目均采用方案 B 的"剪贴板 + 模拟粘贴"机制，无项目采用方案 C（逐字符注入）：
- [espanso](https://espanso.org/)（Rust 文本扩展）：Clipboard backend 为默认注入策略，Inject backend（逐字符）作为可选但 CJK 支持差
- [voice-input-src](https://github.com/yetone/voice-input-src)（macOS 语音输入）：clipboard + 模拟 Cmd+V，额外处理 CJK 输入法拦截
- [Beeftext](https://beeftext.org/)（Windows 文本扩展）：clipboard + 模拟 Ctrl+V

**推荐**：MVP 用方案 A（零依赖快速验证），验证后升级方案 B（体验质变）。

## 3. 设计方案

### 3.1 核心理念：光标跟随快捷补全

不做"静默启动"（技术不可行 + 隐私风险），改为**"一键触发的光标跟随补全"**：

```
用户在任何应用输入时
  → 按 Ctrl+Shift+I（或自定义快捷键）
  → 补全浮窗在当前鼠标位置附近弹出（贴着光标，非屏幕居中）
  → 用户输入查询 / 直接查看基于剪贴板内容的候选
  → 实时显示候选列表（记忆 + 对话双源）
  → Tab/Click 选中
  → 自动写入剪贴板 +（进阶）自动粘贴回当前焦点窗口
  → 浮窗关闭，继续原工作流
```

### 3.2 交互模型设计

#### 3.2.1 触发方式

| 触发 | 说明 |
|------|------|
| 快捷键（主） | `Ctrl+Shift+I`（可配置），全局触发，跟随鼠标位置弹出 |
| 剪贴板感知（辅） | 触发时检测剪贴板是否有文本，若有则作为初始查询预填（用户可修改） |

**剪贴板感知的创新点**：用户复制一段文本后直接按快捷键，浮窗已基于复制内容拉取候选——减少输入步骤。需遵守 `suppressNextChange` 保护，避免读取触发自身剪贴板事件。

#### 3.2.2 定位策略

改造 [quickInputWindow.ts:156-162](../hosts/memora-sprite/src/electron/windows/quickInputWindow.ts) 的定位公式：

```typescript
// 现状：屏幕居中靠上 1/4
const display = screen.getDisplayNearestPoint(screen.getCursorScreenPoint());
const workArea = display.workArea;
win.setPosition(
  Math.round(workArea.x + (workArea.width - width) / 2),
  Math.round(workArea.y + workArea.height * 0.25 - height / 2),
);

// 改造：光标位置 + 偏移，含屏幕边缘溢出回弹
const cursor = screen.getCursorScreenPoint();
const display = screen.getDisplayNearestPoint(cursor);
const workArea = display.workArea;
let x = cursor.x + 16;  // 鼠标右侧 16px
let y = cursor.y + 16;  // 鼠标下方 16px
// 边缘溢出回弹
if (x + width > workArea.x + workArea.width) {
  x = cursor.x - width - 16;  // 改为鼠标左侧
}
if (y + height > workArea.y + workArea.height) {
  y = workArea.y + workArea.height - height - 16;  // 贴底部
}
win.setPosition(Math.round(x), Math.round(y));
```

#### 3.2.3 候选展示

复用现有 `quickInputCompletion.ts` 的候选列表渲染，零改动：
- ↓↑ 键盘导航 / Tab 确认 / Click 选择
- 来源标签（记忆/对话）+ score 排序 + Top-5 截断
- 采纳反馈回路（单次会话内 boost）

#### 3.2.4 回填机制（分阶段）

**MVP（方案 A）**：
1. 选中 → `confirmQuickInput(text)` → 主进程写剪贴板 + `suppressNextChange()`
2. 浮窗关闭
3. 在光标附近显示微小 Toast"已复制，Ctrl+V 粘贴"（1.5 秒自动消失）
4. 用户 Ctrl+V 粘贴到当前焦点窗口

**进阶（方案 B）**：

基于 2026-07-14 开源项目调研修正，补充三个关键边界：焦点恢复、CJK 输入法处理、剪贴板内容恢复。

经 2026-07-14 排雷（沙盘推演）修正步骤顺序：焦点恢复必须在 Esc 之前（Esc 需发送给原窗口的 IME 而非浮窗），浮窗隐藏必须在焦点恢复之前（避免浮窗占用前台）。

```
1. 呼出浮窗前：记录前台窗口句柄（nut-js.getActiveWindow）
   → 必须在 create() 之前调用，否则浮窗自身会成为前台窗口
   → 用户在应用 A 输入框打字（caret 在 X 位置）
   → Ctrl+Shift+I 呼出浮窗（记录前台窗口 = 应用 A）

2. 选中 → confirmQuickInput(text)：
   2a. 检测原剪贴板格式（clipboard.availableFormats()）
       → 若非纯文本（图片/文件）→ 降级到复制+Toast（避免破坏非文本剪贴板）
   2b. 保存原剪贴板内容（clipboard.readText()）
   2c. 写入目标文本（clipboard.writeText(text)）
   2d. suppressNextChange()（抑制三重保护，一次性抑制）

3. 隐藏浮窗（this.hide()）
   → 必须在恢复焦点之前，否则浮窗占用前台导致焦点切换失败

4. 恢复焦点到原前台窗口（nut-js.focusWindow）
   → 应用 A 重新获得焦点，caret 仍在 X 位置（多数应用保留 caret）

5. CJK 输入法处理（借鉴 voice-input-src）：
   → 模拟 Esc 关闭原窗口可能激活的 IME 候选窗口
   → 必须在恢复焦点之后，否则 Esc 发送给浮窗而非 IME

6. 模拟 Ctrl+V（nut-js.keyboard.pressKey + releaseKey）
   → 系统将剪贴板内容粘贴到 caret X 位置

7. 延迟 100ms 等待粘贴完成

8. 恢复原剪贴板内容（clipboard.writeText(original)）
   → suppressNextChange()（再次调用，因为 suppressNextChange 是一次性抑制）

9. 调用 onAfterConfirm(text) 记忆沉淀
   → 只有粘贴成功后才记记忆，避免粘贴失败时误记

10. 浮窗显示"已粘贴到 [应用名]"Toast，800ms 后关闭
    → 粘贴成功和降级都用浮窗自身显示 Toast，不引入额外 UI
```

**排雷修正说明**（2026-07-14）：

| 原步骤 | 修正后 | 修正理由 |
|--------|--------|---------|
| 3. CJK 处理 → 4. 恢复焦点 | 3. 隐藏浮窗 → 4. 恢复焦点 → 5. CJK 处理 | Esc 需发送给原窗口的 IME，必须在焦点恢复之后 |
| 未说明浮窗隐藏时机 | 步骤 3 明确隐藏浮窗 | 焦点切换需浮窗先失活 |
| 未说明 onAfterConfirm 时机 | 步骤 9 粘贴成功后调用 | 避免粘贴失败时误记记忆 |
| 未说明 Toast 载体 | 步骤 10 复用浮窗自身 | 不引入额外 UI |
| 未说明非文本剪贴板处理 | 步骤 2a 检测格式并降级 | 避免破坏图片/文件剪贴板 |
| suppressNextChange 只调用一次 | 步骤 2d + 步骤 8 两次调用 | 一次性抑制，每次写入都需调用 |

**三个关键边界说明**：

| 边界 | 借鉴来源 | 不处理的后果 |
|------|---------|------------|
| 焦点恢复 | espanso + voice-input-src | 文本粘贴到浮窗自身而非原应用 |
| CJK 输入法处理 | voice-input-src | 中文用户偶发粘贴失败（Ctrl+V 被输入法拦截） |
| 剪贴板恢复 | 三项目共识 | 用户原剪贴板内容被覆盖，强烈反感 |

**降级策略**：上述任一步骤失败时，降级到 Phase 3 的"复制 + Toast 手动粘贴"模式，不阻断用户流程。降级时浮窗重新显示 Toast 提示"已复制，Ctrl+V 粘贴"。

### 3.3 架构改动清单

| 改动点 | 文件 | 层级 | 依赖 |
|--------|------|------|------|
| 定位公式改造 | `quickInputWindow.ts` show() | 主进程 | 零新依赖 |
| 剪贴板感知预填 | `quickInput.ts` initQuickInput() | 渲染进程 | 零新依赖 |
| Toast 提示 | 新增 `completionToast.ts` 或复用 quickInputWindow | 渲染进程 | 零新依赖 |
| 自动粘贴（进阶） | 新增 `inputInjector.ts` 主进程模块 | 主进程 | `@nut-tree-fork/nut-js` |
| 快捷键配置 | `shortcutDefaults.ts` 新增 action | 共享 | 零新依赖 |

### 3.4 IPC 通道影响

**零新增 IPC 通道**。所有改造复用现有通道：
- `QUICK_INPUT_CONFIRM` / `QUICK_INPUT_CLOSE` / `QUICK_INPUT_RESIZE` / `QUICK_INPUT_SHOW`
- `MEMORIES_SEARCH` / `SESSION_SEARCH`

进阶方案的自动粘贴在主进程内完成，不经过 IPC。

## 4. 分阶段实施计划

### 4.1 Phase 1：光标跟随定位（MVP-1）

**范围**：改造定位公式，浮窗跟随鼠标光标位置弹出。

**改动**：
- `quickInputWindow.ts` show() 内定位逻辑（约 10 行改动）
- 边缘溢出回弹处理

**验证**：
- 多显示器场景（光标在副屏时浮窗在副屏弹出）
- 屏幕边缘（右侧/底部溢出时回弹到左侧/顶部）

### 4.2 Phase 2：剪贴板感知预填（MVP-2）

**范围**：触发时检测剪贴板内容，作为初始查询预填输入框。

**改动**：
- `quickInput.ts` initQuickInput() 内，`onQuickInputShow` 回调中读取剪贴板
- 若剪贴板有非敏感文本（复用 `clipboardHandler.isSensitive` 检测），预填输入框并触发补全
- 输入框全选状态，用户可直接覆盖或修改

**隐私保护**：
- 复用 `clipboardHandler.isSensitive` 的 5 种正则检测（token / 信用卡 / 密码 / 私钥 / AWS key）
- 敏感内容跳过预填，保持空输入框

### 4.3 Phase 3：回填 Toast 提示（MVP-3）

**范围**：选中后显示"已复制，Ctrl+V 粘贴"Toast。

**改动**：
- 复用 quickInputWindow 的 resize 能力，或新建极小 Toast 窗口（120x40px）
- 1.5 秒自动消失，不抢焦点

### 4.4 Phase 4：自动粘贴（进阶）

**范围**：引入 `@nut-tree-fork/nut-js`，选中后自动恢复焦点 + 模拟 Ctrl+V + 恢复剪贴板。

**改动**：
- 新增 `inputInjector.ts` 主进程模块（封装 nut-js 窗口管理 + 键盘模拟 + CJK 处理）
- `quickInputWindow.ts` show() 前记录前台窗口句柄（`nut-js.getActiveWindow`，必须在 `create()` 之前）
- `quickInputWindow.ts` 的 `QUICK_INPUT_CONFIRM` handler 内，调用 `inputInjector.paste(text, originalWindow)`
- 用户配置开关（默认开启，可关闭回退到手动粘贴）

**排雷修正的三个关键实施细节**（完整伪代码见附录 B）：

#### 4.4.1 焦点恢复

- `show()` 第一行调用 `getActiveWindow()`，必须在 `create()` 之前
- 校验返回的窗口不是浮窗自身（通过窗口标题或进程名），若是则保持上一次的 `previousWindow`（处理快速连续呼出场景）
- `paste()` 时先 `this.hide()` 隐藏浮窗，再 `previousWindow.setFocus()` 恢复焦点

**风险点**：用户在浮窗期间切换了窗口（Alt+Tab），此时 previousWindow 已非前台。

**建议**：粘贴到原窗口（用户意图是补全原输入框），但 Toast 提示"已粘贴到 [应用名]"，让用户感知。

#### 4.4.2 CJK 输入法处理

**顺序要求**（排雷修正）：必须在焦点恢复之后执行 Esc，否则 Esc 发送给浮窗而非原窗口的 IME。

**Windows 实现路径**（需评估是否需 native addon）：
- 方案 1：`GetForegroundWindow` + `ImmGetIMEFileName` 检测输入法（需 native addon）
- 方案 2：直接模拟 Esc 再 Ctrl+V（无需检测，Esc 对非 IME 场景无副作用）

**建议**：先采用方案 2（简单粗暴但有效），若用户反馈误关其他候选再考虑方案 1。

#### 4.4.3 剪贴板恢复 + 非文本剪贴板保护

- 粘贴前检测 `clipboard.availableFormats()`，若非纯文本格式（图片/文件）→ 降级到复制+Toast
- 保存原剪贴板内容 → 写入目标文本 → `suppressNextChange()`（一次性抑制）
- 粘贴完成后恢复原剪贴板 → **再次** `suppressNextChange()`（每次写入都需调用，因为是一次性抑制）

**注意**：`suppressNextChange` 是一次性抑制（[clipboardHandler.ts:211-214](../hosts/memora-sprite/src/electron/clipboardHandler.ts)），每次 `clipboard.writeText` 都需配对调用，否则剪贴板三重保护会误判为"外部变化"触发通知。

#### 4.4.4 IPC 返回值扩展（排雷修正）

**问题**：现有 `QUICK_INPUT_CONFIRM` 返回 `{ success: boolean }`，渲染进程成功后显示"已复制"Toast。Phase 4 新增粘贴流程后，执行时间从 ~10ms 变为 ~300ms，且需要区分"已粘贴"和"已复制（降级）"两种成功状态。

**修正**：返回值扩展为 `{ success: boolean; mode: 'paste' | 'copy' }`：
- `mode: 'paste'` → 渲染进程显示"已粘贴到 [应用名]"Toast
- `mode: 'copy'` → 渲染进程显示"已复制，Ctrl+V 粘贴"Toast（降级或用户关闭自动粘贴）

渲染进程 `handleConfirm` 在等待期间（300ms）显示"粘贴中..."loading 状态，避免用户看到浮窗卡住无响应。

#### 4.4.5 onConfirm 回调职责调整（排雷修正）

**问题**：现有 `onConfirm` 回调负责"写剪贴板 + suppressNextChange"。Phase 4 的 `inputInjector.paste()` 也负责"写剪贴板 + suppressNextChange + 粘贴"。两者都执行会导致剪贴板被写两次。

**修正**：Phase 4 应拦截 `onConfirm` 的剪贴板写入，改为由 `inputInjector.paste()` 统一负责：
- `onConfirm` 只返回 `{ success: true }` 让 `paste()` 接管
- `paste()` 负责完整的"保存原剪贴板 → 写入目标 → 粘贴 → 恢复剪贴板"流程
- 降级时 `paste()` 返回 `{ success: true, mode: 'copy' }`，由 `onConfirm` 补写剪贴板

#### 4.4.6 降级策略

| 失败点 | 检测方式 | 降级动作 |
|--------|---------|---------|
| nut-js import 失败 | 模块加载 try/catch | 降级到复制 + Toast（mode: 'copy'） |
| `getActiveWindow` 返回 null | 返回值校验 | 降级到复制 + Toast |
| 原剪贴板非纯文本格式 | `availableFormats()` 检测 | 降级到复制 + Toast |
| `focusWindow` 失败 | try/catch | 降级到复制 + Toast |
| 粘贴后剪贴板未变化 | 粘贴后 `clipboard.readText()` 对比 | 降级到复制 + Toast |
| 用户配置关闭自动粘贴 | 配置项检查 | 直接走复制 + Toast |

**风险**：
- native 依赖跨平台构建（Windows 优先，macOS/Linux 后续）
- 杀毒软件可能拦截键盘模拟（需代码签名 + 用户白名单）
- 部分应用可能拒绝模拟输入（如管理员权限窗口）
- CJK 输入法候选窗口拦截 Ctrl+V（用前置 Esc 缓解）
- 焦点恢复后 caret 位置丢失（少数应用不保留 caret，降级到复制+Toast）

## 5. 隐私与安全边界

| 边界 | 说明 |
|------|------|
| 不监听全局键盘输入 | 补全只在用户主动按快捷键时触发，不后台监听键盘事件 |
| 不读取其他应用窗口内容 | 不使用 UI Automation 读取其他应用文本，只处理用户在浮窗输入的查询 + 剪贴板内容 |
| 剪贴板敏感内容过滤 | 预填前检测 5 种敏感模式（token / 信用卡 / 密码 / 私钥 / AWS key），命中则跳过 |
| 自动粘贴可选 | Phase 4 的自动粘贴默认开启但可关闭，用户有完全控制权 |
| 剪贴板内容恢复 | Phase 4 自动粘贴后恢复用户原剪贴板内容，不覆盖用户原复制内容（业界共识，三开源项目均做） |

// hosts/memora-sprite/src/electron/inputInjector.ts（Phase 4 新增）
import { keyboard, Key, getActiveWindow, Window } from '@nut-tree-fork/nut-js';
import { clipboard } from 'electron';

/** 粘贴结果（扩展 mode 字段，排雷修正雷 4.1） */
interface PasteResult {
  success: boolean;
  /** 成功模式：paste=自动粘贴成功，copy=降级到复制+Toast */
  mode: 'paste' | 'copy';
  reason?: 'no_previous_window' | 'non_text_clipboard' | 'focus_failed' | 'paste_failed';
  error?: unknown;
}

/**
 * 输入注入器 —— 模拟键盘事件将补全结果粘贴到原焦点窗口
 *
 * 流程（基于 espanso + voice-input-src 调研 + 排雷修正）：
 *   1. 检测原剪贴板格式（非纯文本则降级）
 *   2. 保存原剪贴板 → 写入目标文本 → suppressNextChange
 *   3. 隐藏浮窗（排雷修正：必须在恢复焦点之前）
 *   4. 恢复焦点到原窗口（排雷修正：必须在 Esc 之前）
 *   5. Esc 关闭 IME 候选窗口（排雷修正：必须在焦点恢复之后）
 *   6. 模拟 Ctrl+V → 延迟 100ms
 *   7. 恢复原剪贴板 → suppressNextChange（一次性抑制，每次写入都需调用）
 *
 * 三个关键边界：
 *   1. 焦点恢复：粘贴到原窗口而非浮窗自身
 *   2. CJK 处理：Esc 关闭可能激活的 IME 候选窗口
 *   3. 剪贴板恢复：不覆盖用户原剪贴板内容
 *
 * 任何步骤失败均降级到 Phase 3 的复制+Toast 模式（mode: 'copy'）。
 */
export class InputInjector {
  /** 粘贴后等待系统处理的时间（ms） */
  private static readonly PASTE_DELAY_MS = 100;
  /** Esc 后等待 IME 处理的时间（ms） */
  private static readonly ESC_DELAY_MS = 50;

  /**
   * 模拟 Ctrl+V 粘贴文本到指定窗口
   *
   * @param text 要粘贴的文本
   * @param previousWindow 呼出浮窗前的前台窗口（null 则降级）
   * @param hideFloat 隐藏浮窗的回调（排雷修正：调用方注入，避免 InputInjector 依赖 QuickInputWindow）
   * @param suppressNextChange 剪贴板三重保护抑制函数（由调用方注入）
   */
  async paste(
    text: string,
    previousWindow: Window | null,
    hideFloat: () => void,
    suppressNextChange: () => void,
  ): Promise<PasteResult> {
    // 边界 1：无原窗口句柄，降级
    if (!previousWindow) {
      return { success: false, mode: 'copy', reason: 'no_previous_window' };
    }

    // 边界 3 前置：检测原剪贴板格式，非纯文本则降级（排雷修正雷 6.2）
    const formats = clipboard.availableFormats();
    if (formats.length === 0 || !formats.includes('text/plain')) {
      return { success: false, mode: 'copy', reason: 'non_text_clipboard' };
    }

    // 保存原剪贴板内容
    const originalClipboard = clipboard.readText();

    try {
      // 写入目标文本 + suppressNextChange（第一次调用）
      clipboard.writeText(text);
      suppressNextChange();

      // 排雷修正雷 1.2：隐藏浮窗必须在恢复焦点之前
      hideFloat();

      // 边界 1：恢复焦点到原前台窗口
      try {
        await previousWindow.focus();  // Spike 验证：API 名为 focus() 非 setFocus()
      } catch (err) {
        return { success: false, mode: 'copy', reason: 'focus_failed', error: err };
      }

      // 边界 2：CJK 输入法处理——Esc 关闭可能激活的 IME 候选窗口
      // 排雷修正雷 5.1：必须在焦点恢复之后，否则 Esc 发送给浮窗而非 IME
      await keyboard.pressKey(Key.Escape);
      await keyboard.releaseKey(Key.Escape);
      await new Promise(resolve => setTimeout(resolve, InputInjector.ESC_DELAY_MS));

      // 模拟 Ctrl+V
      await keyboard.pressKey(Key.LeftControl, Key.V);
      await keyboard.releaseKey(Key.LeftControl, Key.V);

      // 等待系统完成粘贴
      await new Promise(resolve => setTimeout(resolve, InputInjector.PASTE_DELAY_MS));

      return { success: true, mode: 'paste' };
    } catch (err) {
      return { success: false, mode: 'copy', reason: 'paste_failed', error: err };
    } finally {
      // 边界 3：恢复原剪贴板内容（无论成功失败）
      // 排雷修正雷 1.1：suppressNextChange 是一次性抑制，恢复时需再次调用
      clipboard.writeText(originalClipboard);
      suppressNextChange();
    }
  }
}
