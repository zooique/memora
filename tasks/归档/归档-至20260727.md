## 评估归档（2026-07-27 第四轮）— HEAL-7 行为漂移修复

> 来源：HEAL-7「Web/Electron 路由镜像重复未抽 shared service 层」评估后修复归档。

### 评估结论

HEAL-7 原描述"平行实现 16+ 记忆操作，需抽取 shared service 层"经实地核查后判定为**行为漂移而非代码重复**：

1. **shared service 层已存在**：Web 路由与 IPC handler 均委托 `ctx.sprite.*` 门面方法，Sprite 即为共享调用链。薄路由处理模式是正确的传输适配层架构，不应再抽一层 service。
2. **唯一行为漂移在 batch-delete**：Web 用 `for` 循环调 `deleteMemory` + `isValidId`（500 字符上限）逐条校验，IPC 直接调 `deleteMemoriesBatch`（无上限，内核 `typeof === 'string' && length > 0` 校验）。校验策略不一致导致同一 API 在 Web/Electron 下行为不同。
3. **再抽 service 层违反提取原则**：路由层 16+ handler 均为 3-5 行薄委托，重复度未达"3 次以上才提取"阈值，强行提取增加抽象层无收益。

### 修复内容

- **HEAL-7**：`memoryRoutes.ts` 的 `POST /api/memories/batch-delete` 改为委托 `ctx.sprite.deleteMemoriesBatch(body.ids)`，与 IPC `MEMORIES_DELETE_BATCH` 共用同一调用链。校验逻辑统一收敛到 `MemoryController.deleteBatch` 内，消除 Web/IPC 校验策略漂移。

> 来源：HEAL-8「`sprite/tools.ts` setAgentRef / setMemorySearcher 模块级全局状态注入」。
> 核心目标：消除模块级 `let agentRef / memorySearcher` 全局状态，避免多 Agent 实例并行时互相覆盖；handler 内不再做 null 检查（防御式编程反模式）。

### 修复内容

- **HEAL-8**：`sprite/tools.ts` 引入 `createSpriteHandlers(deps)` 显式依赖注入工厂。
  - 新增 `AgentRef` / `MemorySearcher` / `SpriteHandlerDeps` 类型定义，仅暴露工具所需最小接口（`config.confirmConfigSuggestion` + `reloadConfig`），避免泄漏 Agent 全部 API
  - 4 个有状态 handler（memory_search + create_persona/skill/rule）改为闭包捕获 `deps`，handler 内直接使用 `memorySearcher(...)` / `agent.config.confirmConfigSuggestion(...)`，无 null 检查
  - `webSearchHandler` 因无状态依赖保持顶层导出，不进工厂
  - `index.ts` 移除 `setMemorySearcher` / `setAgentRef` 调用，改为构造 `memorySearcher` 闭包（封装 `agent.memory.search` + 字段映射）+ 最小 `AgentRef` 接口注入工厂
  - `tools.test.ts` 重构测试范式：新增 `createHandlersWithMocks` 辅助工厂，每个测试独立构造 handlers 实例（消除模块级状态泄漏）；新增「多实例并行：两次工厂调用产生独立 handlers 闭包」测试用例验证 ADR-SP-019 核心目标

### 设计决策

| 决策 | 理由 |
|------|------|
| 工厂返回闭包 handler 而非 class | handler 是函数式 API（`ToolHandler`），class 包装徒增抽象。闭包天然捕获依赖，与现有 `ToolExecutor.registerTool` 接口零摩擦 |

| `webSearchHandler` 不进工厂 | 无状态依赖，多 Agent 实例共享同一函数引用无副作用，强行入工厂徒增调用方负担 |
| 测试用 `createHandlersWithMocks` 工厂 | 与生产代码同构（同样走 `createSpriteHandlers`），保证测试覆盖真实路径，避免 mock 直接覆盖模块级状态的反模式 |

## 自动迭代第六轮（2026-07-27）— HEAL-9 sprite.ts 上帝类拆分

> 来源：HEAL-9「`sprite.ts` 上帝类（1355 行，承担 8 类职责）」。
> 核心目标：将 Sprite 从「门面 + 事件系统 + 生命周期 + personas 文件监听 + 欢迎回来召回 + 配置文件 CRUD + 50+ 委托方法」的上帝类，拆分为门面 + 3 个专职协作模块，使 Sprite 回归「门面 + 编排」单一职责。

### 评估结论

经实地核查，sprite.ts 承担 8 类职责：① 门面 ② 事件系统 ③ 生命周期编排 ④ personas 目录热重载 ⑤ 欢迎回来记忆召回 ⑥ 配置文件 CRUD 与内核联动 ⑦ 50+ 委托方法 ⑧ 仪表盘格式化。其中 ④/⑤/⑥ 三类职责与门面正交，可独立成模块；③/⑦ 已由前序 SPLIT 拆出 `spriteLifecycleManager.ts` / `spriteConfigManager.ts` 承接，本轮不再涉及。

### 修复内容

- **HEAL-9**：新增 3 个专职模块，sprite.ts 从 1355 行 → 971 行（-384 行 / -28%）。
  - `PersonaWatcher`：封装 `personas/` 目录的 `fs.watch` 递归监听 + 500ms 防抖 + `reloadConfig('persona')` 触发 + 错误降级通知。`Sprite.startWatchers()` / `Sprite.stopWatchers()` 委托本模块。
  - `WelcomeBackRecaller`：封装「用户离开时长 → 召回近 N 条新记忆 → 生成中文摘要 → 调用 `proactiveEngine.addNotice`」全流程。`Sprite.welcomeBackRecall(awayDurationMs)` 委托本模块。
  - `ConfigFileSyncer`：封装 persona/rule/skill 三类文件的 save/delete 与内核联动（`reloadConfig` / `updateRule` / `deleteRule` / `deleteSkill` / `skills.reload`）。`Sprite.syncConfigFile()` 委托本模块。
  - 三模块均采用「构造期注入 deps 对象 + getter 函数延迟访问内核 Manager」模式，避免 Sprite 构造时 Agent 内部 Manager 尚未初始化的时序问题。

### 设计决策

| 决策 | 理由 |
|------|------|
| deps 注入用 getter 函数而非直接属性 | `Sprite` 构造时 `agent.persona` / `agent.config` / `agent.skills` 可能为 null（Agent.init() 后才填充）。getter 函数 `() => this.agent.persona` 在调用时才求值，绕开构造期时序问题。直接传属性会导致 ConfigFileSyncer 持有 null 引用永远无法更新 |
| 三模块均不持有 Agent 实例 | 仅通过 deps 接口暴露所需最小方法（`reloadConfig` / `addNotice` / `listMemories` 等），符合最小依赖原则，便于单测 mock |
| 不为三模块新建独立单测文件 | 三模块逻辑通过现有 `sprite.test.ts`（26 个测试 / 897 用例）+ `spriteIntegration.test.ts` 端到端测试覆盖。模块均为薄委托，无独立业务分支，独立单测 ROI 低 |
| PersonaWatcher 用 500ms 防抖 | 沿用原 `sprite.ts` 内的 `PERSONA_RELOAD_DEBOUNCE_MS` 常量，保持原有热重载节奏，避免编辑器保存触发的连续事件导致多次 reload |
| 错误统一走 `proactiveEngine.addNotice('suggestion', reason, false, 'high')` | 与原 sprite.ts 错误降级路径一致，保持用户可见性 |
