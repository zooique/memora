## 三、「反复改同一处」是收敛还是 churn（重点）

**判定：收敛。** 三条硬证据：

1. **增删比近纯增**：`loop.test.ts` +719/−22（**36:1**）、`loop.ts` +417/−131（3.2:1）。反复重写的特征是增删比 ≈1:1，此处不符。
2. **判据下沉而非漂移**：`loop.ts` 内联 → `toolLedger.ts:104 shouldEchoLedgerStub`（`3d271318` 净负 −6）。
3. **新逃逸不再回主循环**：`aa8a79da` / `655de789` / `32880340` 三笔对 `loop.ts` **0 行**，全落 `toolLedger.ts` + 测试（主理人 `git show --stat` 复测属实）。

### 主理人复测发现的一处出入（已打回并获修订）

架构师原表述「判据下沉后 loop.ts 零改动＝收敛完成」**过强**：同族第四笔 `193e0a4d` 实改 `loop.ts` +22 行（架构师手中有 numstat 原文却只列支持结论的三笔，已自认选择性呈现）。主理人读 diff 后裁定：

- **`toolLedger.ts` 不在该笔文件清单内** → 判定侧零改动

### 修订后的准确表述（架构师）

> **收敛的可判别标志不是「loop.ts 零改动」，而是「判定侧零改动」。**
> 防重不变量分两半：**判定侧**（重读该不该拦）= `toolLedger.ts:104`，已单源；**写入侧**（什么算已覆盖）= `fileExposure.record`，仍在 `loop.ts`，**未收敛**。
> 故：判定侧自 `3d271318` 起零改动、零回迁；loop.ts 仍会变，但只因「写入侧 / 主体粒度 / 文案」而变，不再因「重读该不该拦」而变。

**衍生判别标准（本次最有价值产出）**：**改「判据」＝造伤；改「喂给判据的事实」＝止血。**
止血成立需三条件全中：①不变量不动 ②观测在位（`ledgerStubEchoCount` + §7 候选登记）③有退出条件（§7 写明「真机定类后收敛或降级」）。缺一即降级为带伤。

## 四、P0 硬伤（QA 发现，主理人逐条复核实锤）

### P0① 契约僵尸：用例名与断言反向，且新保证零守卫 🔴

`src/agent/__tests__/loop.test.ts:4595` 用例名：

```
D-2 · 结果已被压缩链替换为占位符 → 重读必须放行（死锁守卫，CTX-1 根因②）
```

而断言（`:4623-4624`）是**拦截**：`toHaveBeenCalledTimes(2)` + `[ALREADY_READ]` 为 `true`。

- **实锤**：用例名说「必须放行」，断言说「被拦」，完全反向（注释 `:4621-4622` 自陈契约已由「无信息必须放行」演进为「有信息拦＋回显」）。
- **真正的伤**：取代它的新保证是「替身摘要非空 → 不构成死锁」，但 D-2 **只断言 `[ALREADY_READ]` 出现**（空摘要也会出现），**未断言替身非空**。全仓 9 处 `ResultReplacementStrategy` 用例中已无任何一处断言「内容被清出上下文后必须真实执行」。
- **定性**：命中项目方法论「**用文档迁就实现 = 撒谎**」——不变量换血了，守卫没跟着换。
- **修法**：改真用例名 + 注释；或补一条断言锁定「替身摘要非空」。

### P0② CI 自动门禁不通电 🔴（主理人复核实锤）

- `.github/workflows/kernel-ci.yml:32` `# push:`、`:36` `# pull_request:` **已注释**，仅剩 `:40 workflow_dispatch:`
- `lefthook.yml:35-36` pre-push 的 `test:` / `run: npx vitest run` **已注释**；pre-commit 仅 eslint(staged) + tsc
- **后果**：60 笔提交无机器强制全量验证，「3099 绿」是自报的绿，非门禁的绿
