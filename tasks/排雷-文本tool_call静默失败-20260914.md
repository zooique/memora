## 一、逐条复验（只列本次真读了的）

### R1 · 文本协议宣告 vs 零解析器 🔴

```
src/agent/loop.ts:1749   prompt += `\n\n## 可用工具\n\n你可以通过 tool_call 调用以下工具：\n${toolDescs}`
src/agent/loop.ts:1803-1812  baseOptions.tools = [...{type:'function', function:{name,description,parameters}}]
```
全仓 grep `parseTextToolCalls|TOOL_CALL_RE|extractToolCalls|textToolCall|TextToolCallParser`
→ **生产代码 0 命中**（仅诊断/提示词文档与测试）。
→ 宣告与实现方向矛盾，成立。

**但结论要更狠一点**（本次排雷新增的表述）：这不只是「宣告了没实现」，而是
**同一轮同时宣告两条通道（原生 `tools` + prompt 文本指令），并把选择权交给模型**。
证据：`:1749` 的文本宣告是**无条件**的 —— 即使 provider 支持原生 FC 也会发。
→ 所以 mimo 那次「明明给了 tools 却吐 XML」不是模型单方面抽风，是**被我们教的**。
→ 这决定了修复的第一动作不是「加解析器」，而是「让宣告变成条件式」。见 §二。

### R3 · `messageCount` 真根因修正 🔴

现场原文（`sessions.json`，本次亲读）：
```json
"metas": { "2026-09-14-smu0mmsv2": { "autoName": "项目白话总结", "displayName": "项目白话总结",
                                      "updatedAt": "2026-09-14T02:32:14.331Z", "messageCount": 0 } },
"roundIdsStore": { "2026-09-14-smu0mmsv2": ["round-1789353127177"] }
```
- meta 内含 `autoName`/`displayName`、**不含 `createdAt`** → 该 meta 由 `updateSessionMeta` 建立
  （`sessionStore.ts:242-250` **不写 createdAt**；`createSession` 走 `{...meta}` 会带上入参的 createdAt）。
- 生产写序（内核 `messageHistory.ts:357 / 391 / 464` → 宿主 `appendRoundId`）：
  1. round 完成 → `appendRoundId` → `updateRoundBasedMessageCount(sessionId)`
  2. 该方法 `sessionStore.ts:359-361`：`const meta = this.metas.get(sessionId); if (!meta) return;` ← **meta 不存在则整段早退**

  4. 再无第二轮 → 永远停在 0

→ **真根因 = 写路径「顺序依赖 + 空窗期」（派生逻辑有条件执行）+ 建 meta 的路径不读真源。**
诊断的 `:220` 是 `getSessionMeta` 的**读时兜底返回值**（不是竞争写方）；`updateRoundBasedMessageCount` 才是被漏掉的另一半。
→ 且 `getSessionMeta:211-212` `if (meta) return meta;` **读到就返回、不与真源对账** → 读路径**不自愈**。

### R4 · `messageCount` 零生产消费者 🔴（推翻原假设的损害推断）

全仓 `getMessageCount`（排除 dist/coverage）：仅接口声明、内核实现、宿主 delegate 壳 + 测试。

### R8 · 畸形文本连 A 也解析不了 🔴（A 的最大陷阱）

→ 这是 A 方案最容易被误判为「已收口」的路径，必须在实现清单里当独立项列。

## 二、关键分歧拍板建议（A / B）

### 不变量（第一性原理）

1. **宣告的通道必须可解析**——不能告诉模型一条内核不认的协议。
2. **同一轮只宣告一条通道**——两条同发 = 把协议选择权交给模型 = 不确定性注入确定性系统。
3. **解析不出必须有信号**——不许把「想干活但没干成」记为成功。

现状同时违反 1、2、3。故 A 与 B **都不是完整解**：

| | 修 ① 通道可实现 | 修 ② 通道唯一 | 修 ③ 不静默 | 对本地 LLM（非原生 FC） |
|---|---|---|---|---|
| **B（撤宣告）** | ✖（放弃该通道） | 需配套「不发 tools」才成立 | ✖（模型自发吐 XML 时照旧静默） | **失去工具能力** |
| **A（补解析器）** | ✔ | ✖（宣告仍无条件） | ✖（畸形文本仍解析不出） | 保住工具能力 |

### 建议：**选 A，但 A 必须与「宣告收敛」+「告警兜底」同批落地**（否则 A 只是给静默失败换个姿势）

**理由**
- 项目明确要求「支持本地 LLM 的零网络隐私闭环」，而本地模型（Ollama 类）正是不支持原生 FC 的重灾区。
  选 B ⇒ 该场景**无工具能力** ⇒ 与产品承诺直接冲突。
- A 的**边际成本极低**：prompt 已经在付文本宣告的 token 成本与诱导代价，A 只是把它兑现成能力。
- 但只做 A 违反不变量 2、3 —— 这两条恰恰是本次故障的放大器。**A 的价值必须由 2、3 兜住才算数。**

### 反例风险（对抗式自审，逐条给缓解）

| # | 风险 | 严重度 | 缓解 |
|---|---|---|---|
| AR1 | **正文误判**：用户问「什么是 tool_call 格式」→ 模型的讲解被当调用执行 | 高 | **锚定全匹配**：`content.trim()` 必须**整体**是一个 tool_call 块（禁用 `includes`）+ **工具名白名单**（解析出的 name ∈ 本轮已注册工具名）+ **仅在本轮无原生 toolCalls 时**才尝试。三闸全过才执行。 |
| AR2 | **畸形文本解析不出**（本次现场） | 高 | 独立兜底项：解析失败/名字未知/参数非法 → **不执行 + 告警**（§三 第 3 步）。**A 不可替代它。** |
| AR3 | 文本通道是 best-effort（用文本猜结构），**永远达不到原生 FC 的确定性** | 中 | 定位为**降级通道**：有原生 FC 时不宣告文本（宣告收敛）。否则会在支持原生 FC 的 provider 上主动退化为文本。 |
| AR4 | 解析出来但参数非法（缺 path） | 低 | 走既有工具错误路径（`toolFailureCount`）即可；**但不得记为 success**。 |
| AR5 | AR1 的残余：整段恰好是合法调用文本的「教程式回复」被误执行 | 低 | 接受。代价不对称：误执行 = 用户当场可见可回退；误吞 = 静默空白（本次故障）。**宁误执行，勿静默。** |

### 判据设计（防"两条判据被统一"这一新坑）

- **执行判据（A）必须严格**：整段锚定匹配 + 工具名白名单。
- **告警判据（第 3 步）必须宽松**：`contains('<tool_call')` / `contains('<function=')` 即告警。
- 两者判据**不同源是正确的**，**禁止"统一口径"**：统一后会落进「要么漏报、要么误执行」二选一。
  （这是本项目「跨模块口径统一」类改动的一个**反例**，与 1a 估算器统一的方向相反，须在代码注释里写明理由，防未来被当作不一致而"修正"。）

### 若最终选 B，则 B 的诚实版必须包含

1. 不宣告文本通道 **且不发送 `tools` 参数**（否则模型仍被诱导）；
2. 对「无原生 FC 的 provider」**显式暴露"无工具能力"**（可观测，不能静默）；
3. 同样保留第 3 步的告警（模型自发吐 XML 的面永远存在）。

## 三、分层落地顺序（含精确落点）

### 第 0 步 · 拍板 + 入账（本轮，不改码）
- 拍板 A / B（见 §二）。
- **登记台账**：`tasks/待完成任务.md` 增 P0 条目。
  依据：本项目已实证「报告入库 ≠ 结论入账」（开源就绪度报告 5 P0 未进台账，导致两个真理源打架）。

### 第 1 步 · 止血（宿主，1 处，可独立提交）
- **落点**：`hosts/memora-vscode/src/webview/helpers/renderMarkdown.ts:57-62`（唯一收口）。
- **判据（精确）**：`pre = marked.parse(fixIncompleteMarkdown(text))`、`post = sanitize(pre)`；
  触发条件 = `textOf(pre).trim() !== ''` **且** `textOf(post).trim() === ''`
  → 返回 `一行提示 + escapeHtml(text)`（原文可见，不再空白）。
- **为何是「前后对比」而不是「原文非空」**：`---`（hr）、纯图片等输入「原文非空、合法渲染为无文本」，
  用「原文非空」会把这些**正常渲染**降级成乱码。前后对比只捕捉「净化**吃掉了**本来存在的文本」= 因果精确。
- **约束**：`textOf` 用正则剥标签（如 `replace(/<[^>]*>/g, '')` + 实体归一），**不得引入 DOM** →
  保住 `renderMarkdown` 的 Node-safe 纯函数性质（注释 :48-51 的契约）。
- **对称的另一半**：先 grep 是否已有 `escapeHtml` 工具函数再新增（避免再造一份）。
- **缺口（显式声明）**：真实 DOMPurify 行为在本环境不可单测（R5）；单测用注入 fake sanitize 覆盖判据。

### 第 2 步 · 治根（内核，按拍板）
**若 A**：
- 新增 `parseTextToolCalls` —— 建议 `src/llm/textToolCalls.ts`（纯函数、零依赖、Node-safe）。
- **唯一调用点**：拿到 `LlmCallResult` 后、路由（`loop.ts:964-988`）前统一过一遍；
  **禁止**在 `buildSystemPrompt` / `openaiCompatible.ts` 各写一份（否则又是"两侧各写一份正则"）。
- **宣告收敛**：`loop.ts:1749` 文本宣告改条件式（有原生 FC 时不发）。
  最小实现（在第 4 步能力位落地前）：宿主注入 `nativeToolCalling?: boolean`（默认 `true`，Ollama 类显式 `false`），内核据此决定「宣告哪条 + 是否发 tools」。
- 同批修正 `src/llm/provider.ts:37` 的谎言注释（R7）。

**若 B**：按 §二「B 的诚实版」三条落地 + 修正 `provider.ts:37` 措辞。

### 第 3 步 · 兜底（内核告警，独立于 A/B 都必须做）
- **落点**：`src/agent/loop.ts:1362 handleTextResponse`（纯文本结束的唯一收口）——或紧邻其上的路由判定处。
- **动作**：宽松判据命中 + 本轮无 toolCalls → `logger.warn` + 可观测计数/事件。
- **不得**把本轮记 `success: true`。（`metrics.success` 目前是聚合派生，具体口径需先定位派生点再定，见 §五 T2。）
- **可观测出口确认**（对称的另一半）：宿主有 `memora.showMetrics` 配置 → 指标面板存在，
  须确认新计数能进该面板；否则"写了没人看"，等于违反「不得静默」的初衷。

### 第 4 步 · 中期 · provider 能力位
- 新增 provider 能力元数据（**不复用 `supportsStructuredOutput`**，R6）；
- 内核据此**确定性选一条通道**（发 tools 就不宣告文本；不宣告即说明无工具能力）；
- 同时给 `supportsStructuredOutput` 定去留（删 / 正式启用），**不允许继续当僵尸键**。

### 第 5 步 · 次级（独立提交）
- 修 `messageCount` 写入正确性：`updateSessionMeta` **不得以 `?? 0` 造 meta**，
  须从真源 `roundIdsStore` 派生（或推迟到真源可用时再补），使「任意写序后 `messageCount === roundIds.length * 2`」恒成立。
- **不删该字段**：`SessionMeta` 属**持久化数据面**（宿主写 `sessions.json`），按本项目版本契约分面，
  删字段须留迁移；而它是零消费者（R4）→ 修写入的正确性 ROI 高、删除的 ROI 低。
- **同时**明确标注其当前无消费者（不假装有 UI 影响）；是否接入历史列表（用它展示条数）**另立任务** ——
  注意：「补一个没人读的字段的写入」若不同时定消费面，本身就是新的 SSOT 违例。
