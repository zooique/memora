## 一、问题分析

基于实际使用补全弹窗的体验，识别出以下 6 个迭代方向：

| # | 问题 | 核心矛盾 |
|---|------|----------|
| Q1 | 加锁模式缺失流式输入体验 | locked mode 的 `!pinnedMode → focus()` 守卫跳过了连续输入路径 |
| Q2 | 拖动手柄在 footer 中部，与交互按钮冲突 | 拖动区域（文本/按钮密集区）vs 心智模型（标题栏拖动） |
| Q3 | 浮窗单击打开完整窗口，无法快速呼出补全弹窗 | 浮窗入口单一（仅完整窗口）vs 高频场景（快速补全输入） |
| Q4 | 弹窗尺寸固定，无法手动调整 | 固定尺寸 vs 用户个性化需求（更宽/更高的输入区） |
| Q5 | 整体体验还有哪些可打磨细节 | 现有实现 vs 理想体验的差距 |
| Q6 | 弹窗形态与目标应用割裂感 | 独立弹窗 vs "融入目标应用输入流"的心理预期 |

## 二、方案设计

### Q1：流式输入路径统一 ✅ 已完成（Phase 1 · STEP-2）

<details>
<summary>点击展开详情</summary>

#### 2.1.1 现状

锁定模式在 Tab 提交后**跳过 `win.focus()`**，导致浮窗失去焦点后不自动回到输入框，打断连续输入流。

#### 2.1.2 方案

两种模式共用同一套"提交→粘贴→重聚焦"主路径，锁定模式仅叠加差异化行为（AlwaysOnTop + 跳过 blur 关闭）。

| 行为 | 基础模式 | 锁定模式 |
|------|---------|---------|
| 粘贴后重聚焦（流式输入） | ✅ | ✅（新增） |
| blur 关闭 | ✅（200ms 延迟） | ❌ 跳过 |
| AlwaysOnTop 恢复 | ❌ | ✅（paste 后强制恢复） |

#### 2.1.3 改动

| 文件 | 改动 | 行数 |
|------|------|------|
| `quickInputWindow.ts` | 移除 `if (!safePinnedMode)` 守卫，统一 refocus | -1 |
| `quickInputWindow.ts` | 提取 `handlePostPasteFocus(safePinnedMode)` 公共方法 | +8 |

**总净改动**：+7 行，删除 -1 行。

> **实现细节偏差（2026-07-23 核实）**：方案计划提取 `handlePostPasteFocus(safePinnedMode)` 公共方法，实际实现采用内联代码（`quickInputWindow.ts:560-569`），通过 `_pinnedMode?: boolean` 下划线参数 + 无守卫的 `this.win!.focus()` 达成"两种模式统一重聚焦"的核心目标。功能与方案等价，但未单独提取公共方法——实现者判断当前内联足够清晰，无需额外抽象层。

### Q4：手动拖拽调整弹窗尺寸 ✅ 已完成（Phase 2 · STEP-3）

<details>
<summary>点击展开详情</summary>

#### 2.4.1 现状（实现前）

`quickInputWindow.ts`：`resizable: false`，窗口尺寸固定（480×104~400）。

#### 2.4.2 已落地实现：原生 resize + CSS resize grip + userResized 保护

```typescript
const win = new BrowserWindow({
  width: QUICK_INPUT_WIDTH,       // 480
  height: QUICK_INPUT_HEIGHT,     // 104
  minWidth: 360,
  maxWidth: 720,
  minHeight: QUICK_INPUT_HEIGHT,  // 104
  maxHeight: QUICK_INPUT_MAX_HEIGHT * 1.5, // 600
  resizable: true,                // ← 关键变更
  frame: false,
});
```

配套实现：
- **CSS resize grip**：`.quick-input-container::after` 伪元素在右下角渲染 L 形 grip 图标（`cursor: nwse-resize`，≥16px 热区），解决 frameless 窗口原生 resize handle 仅 ~4px 难以抓取的问题
- **userResized 标志保护**：用户手动 resize 后置 `userResized = true`，自动高度调整逻辑（`resizeWindow()`）检测到此标志则跳过，防止补全列表显隐时的 IPC 调用覆盖用户设定尺寸；下次 `hide()`/`show()` 时重置回初始尺寸 480×104
- **skipResizeFlag**：程序化调整尺寸时置位，避免触发 resize 事件被误判为用户操作

#### 2.4.3 实际改动

| 文件 | 改动 | 证据 |
|------|------|------|
| `quickInputWindow.ts` | `resizable: true` + `minWidth/maxWidth/minHeight/maxHeight` + `userResized` 标志 + `skipResizeFlag` + resize 事件监听 | `:191 userResized`、`:197 skipResizeFlag`、`:220-225 配置`、`:278-284 监听`、`:616-618 保护` |
| `quick-input.css` | `.quick-input-container::after` CSS resize grip（L 形图标 + nwse-resize） | `:40-55` |
| `quickInput.ts` | 每次 `show()` 重置 `userResized` 与初始尺寸 | handleShow 路径 |

> 注：方案原列 `quick-input.html`（footer 右侧 grip 图标）为可选项，实际采用 CSS 伪元素实现，无需改 HTML。

#### 2.4.4 排雷回顾

| 风险项 | 等级 | 实际处理 |
|--------|------|----------|
| frameless 窗口 resize 边框极窄，难以抓取 | 🟡 中 | ✅ CSS resize grip（伪元素 L 形 grip + nwse-resize）解决 |
| resize 后补全列表高度计算不准确 | 🟡 中 | ✅ skipResizeFlag + resize 事件中重新计算解决 |
| 与现有动态高度调整冲突 | 🟡 中 | ✅ userResized 标志保护，hide/show 重置解决 |

**结论**：三项风险均已落地缓解措施，可行性验证通过。

### Q6：增强弹窗——融入目标应用输入流（远期探索方向）

> **状态**：方案排雷阶段，不进入执行。仅作为远期方向记录。

#### 2.6.1 构想

用户期望的不是"弹出一个独立窗口"，而是"赋能 Windows 本身输入能力"的感觉——弹窗更轻量、更融入目标应用上下文。

#### 2.6.2 技术路线对比

经过上一轮讨论，排除 TSF 输入法（投入产出比极不合理）和行内幽灵文本（通用场景不可行）后，确定**增强弹窗路线**：

| 增强项 | 技术手段 | 体验提升 |
|--------|----------|----------|
| 智能定位 | UIA（UI Automation）获取目标输入区域坐标，弹窗定位到输入框附近而非鼠标位置 | 减少"弹窗感"，视觉上靠近输入位置 |
| 材质降重 | Electron `acrylic` / `blurbehind` 材质，半透明背景 | 减少视觉重量，更像系统原生组件 |
| 降级策略 | UIA 不可用时 fallback 到鼠标光标定位 | 保证 100% 覆盖率 |

#### 2.6.3 排雷

| 风险项 | 等级 | 分析 | 缓解措施 |
|--------|------|------|----------|
| UIA 覆盖率不足 | 🔴 高 | 不同应用对 UIA 支持程度差异极大：Win32 原生控件可靠，Chromium 中等，Qt/Java 低，JetBrains 极低 | 100% 降级到鼠标定位，不做"全覆盖"承诺 |
| UIA 坐标不准 | 🟡 中 | 部分应用（如 WPF）UIA 返回的 bounding rect 可能偏移 | 加 10-20px 容差偏移，弹窗不遮挡输入区域 |
| acrylic 材质仅在 Windows 10+ 支持 | 🟢 低 | Windows 7 / 8 市场份额极低，且 Electron 已停止支持 | 降级到普通半透明背景 |
| 跨进程 UIA 调用性能 | 🟡 中 | 每次 show() 需 COM 跨进程查询，可能增加 50-200ms 延迟 | 异步获取 + 缓存（同一应用窗口切换时重用上次坐标） |
| 技术复杂度增加 | 🟡 中 | UIA 需要 native addon 或 nut-js 扩展，增加维护成本 | 封装为独立 `inputAreaLocator.ts` 模块，失败时零影响 |

#### 2.6.4 不做清单

| 不做事项 | 原因 |
|----------|------|
| TSF 输入法开发 | C++ COM 组件 + 数字签名 + 系统级维护，个人项目不可承受 |
| 行内幽灵文本（ghost text） | 绝大多数 Windows 应用不支持 inline completion API |
| 在目标窗口中嵌入子窗口 | Win10+ 跨进程子窗口嵌入受严格限制，UWP 完全禁止 |
| 光环/覆盖层渲染 | 美感与可靠性成反比，UIA 坐标不准时光环偏移比弹窗更难看 |

#### 2.6.5 触发条件

此方向满足以下条件时启动：
- Q4（手动 resize）完成且用户反馈弹窗尺寸仍不满意
- 用户明确反馈弹窗"割裂感"影响体验
- 开发者有充足时间研究 UIA 跨进程调用
