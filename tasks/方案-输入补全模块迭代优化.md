# 输入补全模块迭代优化方案

> **创建时间**：2026-07-20
> **状态**：方案设计完成，待审批
> **涉及模块**：`hosts/memora-sprite/src/electron/` 下 quickInputWindow、quickInput、float、pasteCoordinator

---

## 一、问题分析

基于实际使用补全弹窗的体验，识别出以下 5 个迭代方向：

| # | 问题 | 核心矛盾 |
|---|------|----------|
| Q1 | 加锁模式缺失流式输入体验 | locked mode 的 `!pinnedMode → focus()` 守卫跳过了连续输入路径 |
| Q2 | 拖动手柄在 footer 中部，与交互按钮冲突 | 拖动区域（文本/按钮密集区）vs 心智模型（标题栏拖动） |
| Q3 | 浮窗单击打开完整窗口，无法快速呼出补全弹窗 | 浮窗入口单一（仅完整窗口）vs 高频场景（快速补全输入） |
| Q4 | 弹窗尺寸固定，无法手动调整 | 固定尺寸 vs 用户个性化需求（更宽/更高的输入区） |
| Q5 | 整体体验还有哪些可打磨细节 | 现有实现 vs 理想体验的差距 |

## 二、方案设计

### Q1：流式输入路径统一（锁定模式 ← 基础模式）

#### 2.1.1 现状

锁定模式在 Tab 提交后**跳过 `win.focus()`**，导致浮窗失去焦点后不自动回到输入框，打断连续输入流。

核心代码在 [quickInputWindow.ts:434-444](file:///f:/zooique/memora/hosts/memora-sprite/src/electron/windows/quickInputWindow.ts#L434-L444)：

```typescript
// paste 完成：浮窗保持可见，按模式恢复焦点 + 置顶
if (this.isWinAlive()) {
  if (this.pinnedMode) {
    this.win!.setAlwaysOnTop(true);
  }
  // default 模式恢复焦点支持连续输入；pinned 模式不抢焦点（保持钉住语义）
  if (!safePinnedMode) {
    this.win!.focus();  // ← 锁定模式跳过这行
  }
}
```

#### 2.1.2 方案：锁定模式 = 流式输入的升级版

**核心思路**：两种模式共用同一套"提交→粘贴→重聚焦"主路径，锁定模式仅叠加差异化行为（AlwaysOnTop + 跳过 blur 关闭）。

```typescript
// after paste completes
if (this.isWinAlive()) {
  // 锁定模式：强制恢复置顶（paste 期间目标窗口可能改变 z-order）
  if (this.pinnedMode) {
    this.win!.setAlwaysOnTop(true);
  }
  // 两种模式统一：粘贴完成后重聚焦浮窗，支持连续输入
  this.win!.focus();
}
```

**模式差异化矩阵**（重构后）：

| 行为 | 基础模式 | 锁定模式 |
|------|---------|---------|
| 粘贴后重聚焦（流式输入） | ✅ | ✅（新增） |
| blur 关闭 | ✅（200ms 延迟） | ❌ 跳过 |
| AlwaysOnTop 恢复 | ❌（创建时已设置） | ✅（paste 后强制恢复） |
| 视觉标识 | 🔓 unlock 图标 | 🔒 lock 图标 |

#### 2.1.3 改动范围

| 文件 | 改动 | 行数 |
|------|------|------|
| `quickInputWindow.ts` | 移除 `if (!safePinnedMode)` 守卫，统一 refocus | -1 行 |
| `quickInputWindow.ts` | 提取 `handlePostPasteFocus(safePinnedMode)` 公共方法 | +8 行 |
| `quickInput.ts` | 无需改动（流式体验已由 `resetInputForNext()` 保证） | 0 |

**总净改动**：约 +7 行，删除 -1 行。

#### 2.1.4 排雷

| 风险项 | 等级 | 分析 | 缓解措施 |
|--------|------|------|----------|
| 锁定模式下 refocus 是否干扰用户目标窗口操作 | 🟡 中 | paste 后浮窗抢焦，用户正在目标窗口编辑时可能被打断 | 锁定模式本身就是"我要连续输入"的语义，抢焦符合预期。用户不需要连续输入时按 Esc 关闭即可 |
| 连续 paste 期间 focus 闪烁 | 🟢 低 | `pasteInProgress` 标志已保护 paste 期间不触发 blur 逻辑，refocus 在 paste 完成后执行，时序正确 | 现有防护机制已覆盖 |
| 竞态：paste 未完成时用户已切窗口 | 🟢 低 | `isWinAlive()` + `submitGeneration` 双重防护 | 现有防护机制已覆盖 |

**结论**：可行性高，风险可控。改动极小（1 行逻辑变更 + 方法提取），复用现有流式输入路径。

### Q2：拖动把手从 footer 迁移到 focus-bar 顶部

#### 2.2.1 现状

拖动区域绑定在 `#quick-input-footer`（[quickInput.ts:399-400](file:///f:/zooique/memora/hosts/memora-sprite/src/electron/renderer/quick-input/quickInput.ts#L399-L400)），即 footer 把手。该区域同时承载：快捷提示文本、润色按钮、展开按钮、常驻模式按钮、字数计数器——密集的交互元素与拖动手势冲突，需要通过 `closest('.expand-toggle, .pinned-toggle, .polish-toggle')` 排斥判断来避免误触发。

#### 2.2.2 方案：拖动迁移到 focus-bar

focus-bar 位于浮窗顶部，只含"聚焦：应用名"文本 + 关闭按钮，语义上等价于窗口标题栏。迁移后：
- 交互冲突减少（仅需排斥关闭按钮）
- 更符合用户心智模型（标题栏 = 拖动区域）
- footer 的 `cursor: move` 可移除，释放视觉空间

#### 2.2.3 改动范围

| 文件 | 改动 |
|------|------|
| `quick-input.html` | focus-bar 无需改动（已有 `id="focus-bar"`） |
| `quickInput.ts` | `bindDrag()` 中 `footerEl` → `focusBarEl`；添加 `focusBarEl` 到构造参数；排斥 `#close-btn` |
| `quick-input.css` | footer 移除 `cursor: move`；focus-bar 添加 `cursor: move`；close-btn 保留 `cursor: pointer` 覆盖 |

#### 2.2.4 排雷

| 风险项 | 等级 | 分析 | 缓解措施 |
|--------|------|------|----------|
| focus-bar 拖动面积较小（仅一行高度 28px） | 🟡 中 | 比 footer 宽度相同但高度更小，可能影响拖动可发现性 | 保留 footer 作为降级拖动区域（双区域拖动），或给 focus-bar 增加 `padding` 扩大热区 |
| 关闭按钮在 focus-bar 右侧，拖动时可能误触关闭 | 🟢 低 | 与现有 footer 按钮排斥逻辑一致，3px 拖动阈值已有防护 | 复用指针捕获 + 阈值判断模式 |

**结论**：可行性高。推荐**双区域拖动**方案——focus-bar 作为主拖动区域，footer 作为降级保留（移除 `cursor: move` 但保留拖动能力），兼顾心智模型和可发现性。

### Q3：浮窗单击呼出补全弹窗（重构浮窗入口交互）

#### 2.3.1 现状

浮窗单击触发 `expandToFull()`（[float.ts:294-297](file:///f:/zooique/memora/hosts/memora-sprite/src/electron/renderer/float/float.ts#L294-L297)）：

```typescript
// 非拖动 → 单击 → 展开为完整窗口
markDragHintSeen();
electronAPI.expandToFull(); // → windowStateManager.transition('full')
```

#### 2.3.2 方案：单击 → 补全弹窗，双击/右键 → 完整窗口

项目处于开发阶段，无用户习惯包袱，**直接切换**，不做渐进式过渡。

| 手势 | 当前行为 | 新行为 |
|------|---------|--------|
| 单击浮球 | 展开完整窗口 | **呼出补全弹窗**（在浮球附近弹出） |
| 双击浮球 | 无 | **展开完整窗口**（保留原入口） |
| 右键浮球 | 右键菜单（含"展开完整窗口"） | 不变 |

**补全弹窗定位**：不再跟随鼠标光标，改为在浮球下方偏移弹出（类似右键菜单定位）。

#### 2.3.3 关闭按钮保留聚焦数据 —— Windows 权限边界分析

**问题**：关闭弹窗后用户可能切换窗口，保存的 `savedCapture`（HWND + appName）可能指向旧窗口。

**Windows API 可行性分析**：

| 方案 | 依赖 | 可行性 | 理由 |
|------|------|--------|------|
| `GetForegroundWindow()` 轮询 | `user32.dll`（无权限限制） | ✅ 可行 | 关闭后启动 500ms 间隔轮询，检测前台窗口变化则失效 savedCapture。但轮询增加 CPU 开销 |
| `SetWinEventHook(EVENT_SYSTEM_FOREGROUND)` | `user32.dll`（需消息循环） | ✅ 可行 | 全局前台窗口切换事件钩子，零轮询开销。需要 Electron 主进程集成 native addon 或 PowerShell 事件监听 |
| `GetWindowThreadProcessId()` 校验 | `user32.dll`（无权限限制） | ✅ 可行 | 呼出时校验 savedCapture.hwnd 是否仍为当前前台窗口，若否则 fallback 到 capturePreviousWindow() |
| 时间戳过期（原方案） | 无外部依赖 | ✅ 可行 | 30 秒后自动失效，但无法感知窗口提前切换 |

**推荐方案**：**HWND 实时校验 + 时间戳兜底**（双重保护）

```
关闭时：savedCapture = { hwnd, appName, timestamp }
呼出时：
  1. 若 timestamp 超过 30 秒 → 失效，重新 capturePreviousWindow()
  2. 若未过期 → GetForegroundWindow() 与 savedCapture.hwnd 比较
     a. 相同 → 复用 savedCapture（用户未切换窗口）
     b. 不同 → 失效，capturePreviousWindow() 捕获当前前台窗口
```

此方案无需原生 addon，纯依赖现有的 `pasteCoordinator` 能力（已通过 nut-js 调用 `GetForegroundWindow`），零新增依赖。

#### 2.3.4 改动范围

| 文件 | 改动 |
|------|------|
| `float.ts` | 单击 handler 改为调用新 IPC `SHOW_QUICK_INPUT_FROM_FLOAT` |
| `floatWindow.ts` | 注册 `SHOW_QUICK_INPUT_FROM_FLOAT` IPC → 调用 `quickInputWindow.showAtPosition(x, y)` |
| `quickInputWindow.ts` | 新增 `showAtPosition(x, y)` 方法（跳过光标跟随，使用浮球下方定位）；关闭时保存 capture + 呼出时 HWND 校验 |
| `pasteCoordinator.ts` | 新增 `savedCapture` 字段 + `saveCapture()` / `getValidSavedCapture()`（含 HWND 校验 + 时间戳兜底） |
| `quickInput.ts` | 无需改动（渲染进程逻辑不变） |
| `ipc/channels.ts` | 新增 `SHOW_QUICK_INPUT_FROM_FLOAT` 通道 |

#### 2.3.5 排雷

| 风险项 | 等级 | 分析 | 缓解措施 |
|--------|------|------|----------|
| 关闭后保留的聚焦数据可能过期 | 🟡 中 | 用户关闭弹窗后切换了应用，savedCapture 指向旧窗口 | HWND 实时校验：呼出时比较 GetForegroundWindow()，不同则自动重新捕获；30 秒时间戳兜底 |
| 浮球下方弹出可能超出屏幕边缘 | 🟢 低 | 与光标跟随的 `clampPositionToWorkArea` 逻辑一致 | 复用现有 `keepWindowInWorkArea()` 夹紧逻辑 |
| 补全弹窗和浮球同时可见时视觉重叠 | 🟡 中 | 弹窗弹出位置可能与浮球重叠 | 定位偏移量足够（CURSOR_OFFSET_PX=16）将两者分开；必要时弹窗自动调整到浮球上方 |
| 双击检测的时机窗口 | 🟢 低 | 单击和双击需要区分，否则单击立即触发会覆盖双击 | 单击增加 300ms 延迟等待（`setTimeout`），若期间发生第二次 click（双击），则取消单击的 quick-input 呼出，改为展开完整窗口 |

**结论**：可行性高。项目开发阶段无习惯包袱，直接切换。聚焦数据用 HWND 校验 + 时间戳兜底，零新增依赖。

### Q4：手动拖拽调整弹窗尺寸

#### 2.4.1 现状

[quickInputWindow.ts:179](file:///f:/zooique/memora/hosts/memora-sprite/src/electron/windows/quickInputWindow.ts#L179)：`resizable: false`，窗口尺寸固定（480×104~400）。

#### 2.4.2 方案：启用原生 resize + CSS resize grip

```typescript
const win = new BrowserWindow({
  width: QUICK_INPUT_WIDTH,       // 480
  height: QUICK_INPUT_HEIGHT,     // 104
  minWidth: 360,                  // 最小宽度：保留基本输入体验
  maxWidth: 720,                  // 最大宽度：避免过度拉伸
  minHeight: QUICK_INPUT_HEIGHT,  // 104
  maxHeight: QUICK_INPUT_MAX_HEIGHT * 1.5, // 600
  resizable: true,                // ← 关键变更
  frame: false,                   // 保持无边框
  // ...
});
```

**配套 CSS**：在窗口右下角添加 resize grip 视觉提示：

```css
.quick-input-container::after {
  content: '';
  position: absolute;
  right: 0;
  bottom: 0;
  width: 16px;
  height: 16px;
  cursor: nwse-resize;
  /* 可选：右下角三角形 grip 图标 */
}
```

#### 2.4.3 改动范围

| 文件 | 改动 |
|------|------|
| `quickInputWindow.ts` | `resizable: true` + `minWidth/maxWidth/minHeight/maxHeight` |
| `quickInput.ts` | 监听 `resize` 事件，同步 resize 后补全列表高度计算 + textarea 自动高度 |
| `quick-input.css` | 添加 resize grip 视觉提示 |
| `quick-input.html` | 可选：在 footer 右侧添加 grip 图标 |

#### 2.4.4 排雷

| 风险项 | 等级 | 分析 | 缓解措施 |
|--------|------|------|----------|
| frameless 窗口 resize 边框极窄（~4px），难以抓取 | 🟡 中 | Windows 无边框窗口的原生 resize handle 非常细，用户体验差 | 必须加 CSS resize grip（≥16px 热区）；考虑在全窗口边缘增加 6px 透明热区用于 resize |
| resize 后补全列表高度计算不准确 | 🟡 中 | `resizeWindow()` 方法中高度计算基于固定常量，resize 后需要重新计算 | resize 事件中重新执行 `updateCompletionListHeight()` + `resizeWindow()` |
| resize 破坏窗口圆角/视觉一致性 | 🟢 低 | CSS 圆角通过 `border-radius` 控制，resize 后仍然生效 | 验证极端尺寸（360×104 / 720×600）下视觉效果 |
| 与现有动态高度调整冲突 | 🟡 中 | 补全列表显示/隐藏时渲染进程会调用 `resizeQuickInput(height)` IPC，手动 resize 后此逻辑可能覆盖用户设定 | 增加 `userResized` 标志：手动 resize 后锁定用户设定的高度，直到下次 hide/show 重置 |

**结论**：可行性中等。主要风险在 resize grip 的可用性和与动态高度调整的协调。建议 `userResized` 标志保护用户自主设定的尺寸。

### Q5：其他迭代优化方向

对补全模块进行系统性审视，识别以下额外优化方向：

#### A. 交互体验

| 方向 | 描述 | 优先级 |
|------|------|--------|
| **剪贴板智能预填** | 当前 show() 时无条件读取剪贴板预填。若剪贴板内容与上次提交的文本相同（用户刚粘贴过），跳过预填，避免重复 | P3 |
| **最近提交历史** | 在补全列表顶部或独立区域展示最近 3 次提交文本，支持快速复用（类似 terminal 的 ↑ 历史） | P3 |
| **Tab 提交前预览目标应用** | 在 footer 或 focus-bar 动态显示"将粘贴到：VSCode"，让用户在 Tab 前确认目标 | P2 |
| **模式切换快捷键** | `Ctrl+L` 切换锁定模式，不用鼠标点击图钉按钮 | P3 |

#### B. 补全质量

| 方向 | 描述 | 优先级 |
|------|------|------|
| **补全排序加权** | 当前双源搜索按分数合并。可增加"近期会话权重"和"采纳反馈权重"提升排序质量 | P3 |
| **上下文感知补全** | 基于当前聚焦应用名过滤候选（如在 VSCode 中优先展示代码相关记忆） | P4 |

#### C. 视觉打磨

| 方向 | 描述 | 优先级 |
|------|------|------|
| **粘贴动画** | Tab 提交后显示微动画（浮窗短暂缩小→恢复），提供操作反馈 | P4 |
| **聚焦应用图标** | focus-bar 中"聚焦：VSCode"旁显示应用图标（通过 exe 路径提取），提升识别速度 | P4 |
| **暗色主题适配** | 验证并优化暗色模式下浮窗的对比度和可读性 | P3 |

#### D. 健壮性

| 方向 | 描述 | 优先级 |
|------|------|------|
| **paste 超时保护** | 当前 `attemptPaste` 无超时，极端情况下可能永久阻塞。增加 5 秒超时 fallback 到 copy 模式 | P2 |
| **多显示器边缘处理** | 验证并修复多显示器边界（显示器间缝隙、不同 DPI）下的弹窗定位 | P3 |

## 三、排雷总览

### 3.1 风险矩阵

| 风险 | 影响 | 概率 | 等级 | 归属 |
|------|------|------|------|------|
| resize grip 在 frameless 窗口可用性差 | 中 | 高 | 🟡 | Q4 |

| paste 超时无保护 | 中 | 低 | 🟡 | Q5-D |

### 3.2 不做清单

| 不做事项 | 原因 |
|----------|------|
| 把浮窗单击改为补全弹窗后完全移除"展开完整窗口"入口 | 完整窗口是核心功能入口，必须保留（通过双击/右键菜单） |

| 在锁定模式下增加自动隐藏逻辑 | 与锁定模式"持续可见"的核心语义矛盾 |
