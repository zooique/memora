## §1 本版定位与总口径

**总口径（用户 2026-11-05 拍板）**：这一波把 6.0.0 从「废弃清账」升为**存储层架构升级 + 多会话并行**，工作量约为原计划的 **3~4 倍**；必须**分批提交、每批单独验收**，不许攒成一个一次性大补丁。

- **目标**：一个项目内多开会话同时运行（兑现台账 `MULTI-SESS-1` 的触发条件）。
- **分层**：存储层（批 1）→ 执行位（批 2）→ 项目文件（批 3）→ 事件与视图（批 4）→ 发版收口（批 5）。**前一层验收不过，后一层不开工**。
- **外部参照（2026-11-05 已核实，直接采用，不再论证）**：
  - 三家会话数据都是「每会话独立目录 + 单写者锁 + 原子写」，写入用 OS 级锁（POSIX flock / Windows 命名信号量），**进程死自动释放，不靠 TTL 抢锁**。
  - 工作目录并发写：默认全部是「共用 cwd 不管」；认真并行时全部改用 git worktree；全局排队与单写者策略零采用。
  - dsh 的 fs-local：进程内**按路径串行 + 版本守卫 + 临时文件 fsync → 原子替换**，不同文件不互相阻塞。
  - 三家都用**事件**而非轮询：落盘 `turn/end`（reason=completed）+ 内存 `idle/running`。
- **准入判据（沿用第一版，压缩为三行）**：A = 只有 breaking 窗口能结清；B = 不收进就没机会；C = 阻塞后续任务的前置。只是「顺手」的不入列（落 §4）。

### 3.2 批 1 · 存储层（2026-11-05 第二版方案）

**一句话**：**轮次池共享、会话清单一会话一文件、`index.json` 降为派生缓存、每会话一把 OS 锁、追加写 + torn tail 截断 + watchdog。**

1. **轮次池保持共享、轮次文件彻底只读**：`round-<id>.json` 不迁移、不拷贝；**任何引用动作不得改写轮次文件**（refCount 已移出，见 §3.2.1）。精确边界：轮次**归属进程在本轮执行期间**可增量落盘（status/消息），**收场后冻结、永不再写**；其他进程、其他会话的引用动作一律不碰它。分叉 = 新会话文件复制 `roundIds`，轮次文件零触碰。
2. **会话清单拆为一会话一文件**：`sessions/<sessionId>.json` = 会话元数据 + 该会话的 `roundIds`；分叉只复制 roundIds 清单，**轮次文件零拷贝**；列会话扫 `sessions/` 目录。
3. **`index.json` 降级为派生结果 + 内存缓存**（不是删除）：由扫描 `rounds/` 可随时重建。
4. **每会话一把 OS 级锁**（进程死自动释放）；第二写者直接回「已在别处运行」，不等待；写只追加 + 每批 fsync + 启动截断 torn tail。
5. **必配 watchdog**：外部三家都用「进程死自动释放」的锁——若进程**卡死但未退出**，锁不释放且无 TTL，该会话会**永久不可恢复**。watchdog 是必要补件，不是可选项。

**落地约束（方案成立的前提，写进实现，不是新结构）**：

- 派生索引**只在启动/显式重建时整体生成并原子覆盖**；**不得在每次 save 后增量写盘**——那不叫降级，是把刚拆掉的全局读改写文件又请回来。
- `getByIds` 必须改为「直接读文件 + ENOENT 视为缺失」，**不得以 `index.has(id)` 为门**（现状 `workspaceRoundStore.ts:182` 起先查缓存再查索引；跨进程时会静默漏掉别处新写的轮）。
- `rounds/{id}.json` 的 mtime **不能当 createdAt**（轮次执行期增量落盘本就刷新 mtime，旧档还被 refCount 回写污染过），时间真源 = `round.createdAt`。
- **一旦把「列轮次」改成扫 `rounds/` 目录派生（§3.2 第 3 条 / §3.2.1 第 3 条的方向），必须显式排除 `rounds/.trash/` 与任何临时文件**——`.trash` 是 7 天回收站（`{roundId}.{trashAtMs}.json`），被当成活轮会让索引、GC、崩溃打捞全部误判。**现状是「当前天然成立、但前提会变」**：列轮次全走 `index.json`、不 `readdirSync` ⇒ `.trash` 天然排除；改扫目录那一刻必须同时加上排除判据，不许留给后续。

#### 3.2.1 ✅ 引用计数（已裁定 2026-11-05 用户拍板 · 轮次文件彻底只读）

**终态要求**：`round-<id>.json` 写完一次之后**永远不会再被改写**。任何需要改它的动作，都是设计错误。

**1. 移出字段**：`round.refCount` 退出判断与写回（字段可暂留以兼容旧档，但**不参与任何判定、不参与写回**）；`index.json` 内的 refCount 副本同步作废（index 已降为派生缓存）。

**2. 真源迁到会话文件**：谁引用这一轮，只记在 `sessions/<sessionId>.json` 的 `roundIds` 里。分叉 = 新会话文件复制 `roundIds`，**不碰任何轮次文件**。

**3. GC 改为现场派生**：不再读 refCount，扫全部 `sessions/*.json` 统计每个 round 被引用次数，为 0 才进入回收。

⚠️ **措辞纠正（对「派生可重算 ⇒ 算错可修，不会造成不可逆删除」）**：派生保证的是**计数可复核、可修正**，**不保证删除可逆**——删除本身仍是不可逆动作。故回收必须保持两步：`listOrphaned` **只出候选（不删）** → `sweepOrphans` / 内核 GC **再删**，并保留 24h 存活保护（`DEFAULT_SWEEP_MIN_AGE_MS`）。一次扫描直接删 = 把「可重算的判据」用在不可逆动作上。

**5. 顺带修掉的病（本轮修复）**：现在「回写轮次」正是「**已完成轮次可能被回滚成未完成**」的根因——`incrementRef` / `decrementRef` 把内存里的**旧快照整轮写回**（`atomicWriteFileSync(filePath, JSON.stringify(cached, null, 2))`）；若该轮已被别处收场为 `complete`，旧快照（pending）会把状态倒回去。计数移出、引用动作不再写轮次文件后，**此病消失**。验收落点 = §2 批 1 ④「原 `complete` 仍 `complete`」。

**6. 已知缺陷（单独登记，不并入批 1 验收）**：`getByIds` 以 `index.has(id)` 为门（`workspaceRoundStore.ts:182` 起先查缓存再查索引）⇒ **跨进程持不同索引时会静默漏轮**。这是**既有缺陷，与本轮 refCount 改动无关**；是否随本批修由用户另行决定，先作为「已知缺陷」入表。
- 与 §3.2「落地约束」的关系必须说清：那里「`getByIds` 必须直读文件」是**派生缓存架构的结构性要求**（不直读则派生缓存不成立），照做；但**「修这条缺陷」的验收归属不并入批 1**——两件事，不许折叠成一件。

**7. 与「追加事件模型」（留 7.0.0，见 §4.5）的关系：同向、非替代。** 事件模型消掉的是「整文件重写」这个根因；refCount 移出 + 会话派生解决的是「引用真源放在哪」。即便将来迁到事件模型，「谁引用这一轮」仍只能记在会话文件，轮次文件仍不可写 ⇒ **本条照做，不会被事件模型吸收**；反过来，本条也不替代事件模型（闸 1–4 只是「在快照格式上守住不可变」）。

#### 3.2.4 代价与缓解（崩溃打捞）

- **代价**：崩溃打捞 `listInterruptedRecent` **性能不等价**。它现在靠 index 的 `status` 先判型、避免全量读盘（`workspaceRoundStore.ts:408-418`）；index 降为派生缓存后，扫描本身拿不到 status，必须读轮次文件解析（Round 是无头部分区的整 JSON）⇒ 无缓存时启动即 O(N) 全量解析。
- **缓解 = 扫描 + 缓存**：`rounds/` 目录扫描做「目录枚举 + 每文件 `stat`」，只对**变更过的文件**重新解析；解析结果按 `id → { status, createdAt, mtimeMs, size }` 缓存。
- **缓存失效判据（逐条写死，实现时照抄）**：
  1. **进程启动首载** → 无条件全量重建（不信任任何残留缓存文件）；
  2. **`rounds/` 目录条目集合变化**（新增 / 删除文件，按目录枚举结果比对）→ 全量重建；
  3. **单文件 `mtimeMs + size` 变化** → 只重新解析该文件；
  4. **缓存缺失 / JSON 解析失败 / 字段缺省** → 视为未命中，重新解析该文件；解析后仍失败 → 记警告并跳过该文件（不阻断整次扫描）；
  5. **`index.json` 版本号不符**（文件内写入 schema 版本；版本不同即弃用）→ 全量重建并原子覆盖。
- **缓存不做的事**：不用 mtime 当 `createdAt`（时间真源 = `round.createdAt`）；不把缓存当「轮总数」真源（要总数就扫目录）；不在每次 `save` 后增量写盘（见 §3.2 落地约束）。
- 执行期轮次文件 `mtime` 会抖动（增量落盘），这只影响**重新解析成本**，不影响正确性；收场冻结后该项自然稳定。

**闸 2 判据规格（适用范围：强判据仅对「已收场轮」）**

判定前提：`old.status` 已收场（判据 SSOT = `isRoundSettled`：`complete` / `interrupted`）才启用下方第 1、2 条**强判据**；未收场轮（`pending`）走**弱校验**。否则正常流程会被误杀——运行中 `processEvents` 的工具调用状态本就会从「运行中」变「完成」，同索引深度相等必然不成立。

1. **状态单调前进 + 标量恒等（仅已收场轮）**：已收场轮 `new.status` **必须恒等**旧值（`complete ↔ interrupted` 互跳同样拒绝）；`id` / `userMessage` / `assistantMessage` / `createdAt` / `completedAt` 同样必须恒等——否则「状态不变 + 列表不变」就能改写历史正文。
2. **列表字段同序前缀不变（仅已收场轮）**：`processEvents` / `evidence` / `interactiveInputs` / `assistantLog` 只允许追加——`new.length >= old.length` 且对每个 `i < old.length` 有 `new[i]` 与 `old[i]` 深度相等。**只比长度会漏掉「同长度换内容」**（改写历史正文 / 插队 / 重排都检测不到）。`pendingAsk` 不在此列：收场清空是生命周期定案（`appendAssistant` / `appendInterrupted` 的原子清）。
   - **pending 轮校验边界（弱）**：允许既有元素**就地更新**（工具调用状态推进）、**追加**新元素、`status` 前进到终态；拒绝列表**缩短**（删除既有事件）、既有元素的**身份字段**消失或乱序（`processEvents` 按 `seq`、`evidence` 按工具调用 ID）——否则历史被静默删除 / 重排而检测不到。
   - **比对基准固定为闸 1 直读磁盘的解析副本，不是缓存对象**——`checkpointRound` 会就地改缓存对象再 `save`，拿缓存比对会自我一致、恒真。
   - **比对位置**：`save()` 内（闸 1 重读之后、写盘之前）；`incrementRef` / `decrementRef` 在 `:241` / `:271` 直接 no-op（不进 `save`）；`checkpointRound` 对已收场轮丢弃 + debug 日志。
   - **失败返回**：`save()` 抛 `stale_round`（指纹 / 前缀不符）或 `settled_round_immutable`（状态回退或标量改写），**不写盘**；调用方既有 try/catch 记 warn（内核 append 路径）或 debug（宿主 checkpoint）。

**代价（2026-11-05 实测 + 估算）**：本机实测轮文件 3.4 KB → 读盘 0.07ms、解析 + 序列化 0.044ms；122.6 KB 大轮 → 解析 + 序列化 1.59ms（读盘约 0.5–0.7ms 为估算）。闸 1 的增量成本 = **一次读盘 + 一次反序列化**（整写原本就存在），即每 step 的 checkpoint 多 ≈0.1–2ms（轮越大越接近 2ms）。**优化选择：只对已收场轮做磁盘比对**——`pending` 轮是每 step 的 hot path，改走「内存基线 + `mtimeMs + size` 失效」（即闸 3），零新增读盘；已收场轮的写只发生在迟到的追加 / 引用动作，频率极低。结论：**范围收窄后代价可接受，不需要另建指纹缓存**（`mtime + size` 已是免费指纹）。

**错误码登记（2026-11-05 核查）**：全仓**无通用错误码登记处**——只有工具面 `ToolErrorCode`（`src/utils/errors.ts:25`）+ 守卫 `src/__tests__/toolFailurePrefixGuard.test.ts`，作用域是工具执行 `[ERR:TOOL:*]`，不覆盖宿主存储错误；宿主存储现有失败一律裸 `throw new Error(...)`。因此 `stale_round` / `settled_round_immutable` 是**两个裸字面量**，出现位置 = 本文 §3.2.5 + 实现时 `workspaceRoundStore.save()`，**不为此新造注册机制**；若将来收口，等存储层错误码达到 3 个以上再建表（不为 2 个码造第二真源）。

**现状核对（2026-11-05 只读）**：`RoundStatus` 四值中 `error` **零生产写点**（只出现在测试与打捞的读取条件 `pending || error`），`isRoundSettled` 只认 `complete` / `interrupted` ⇒ 机判按这两值判终态即可。

**状态逆跳写入点核查（2026-11-05 只读，全仓）**：写 `Round.status` 的生产点共 5 处——`roundStore.ts:820`（建轮即 complete，非回退）、`messageHistory.ts:539` / `:574`（`appendAssistant` → complete）、`:686`（`appendInterrupted` → interrupted，`:636` 已收场守卫）、`:363`（`appendUser` 非交互 → pending）。**可能回退的只有三条，且无「必须保留的例外」**：① `:363` 创建语义覆盖（已随 ID 修复结案，见前置依赖）；② `workspaceRoundStore.ts:241` / `:271` 用缓存旧快照整文件回写（§3.2.1 第 5 条「本轮修复」）；③ `chatPanel.ts:3370-3381` 的 `checkpointRound` 经 `save()` 写回缓存快照（跨进程时旧值为 pending）——即台账 `ROUND-CHECKPOINT-1` + `ROUND-CACHE-NOINVALIDATE-1`。恢复/打捞链（`interruptedSalvage.ts:49`）只调 `appendInterrupted`（受 `:636` 守卫），**无回退**。

**尺子两条，不是「是否已收场」**：闸 2「拒写」与闸 4「允许追加」共用同一判据组合——① 状态单向不回头；② 列表同序前缀增长。只按「是否已收场」一刀切会把续跑插话/证据/提问全部堵死（业务必需）。
