## §1 本版定位与总口径

**总口径（用户 2026-11-05 拍板）**：这一波把 6.0.0 从「废弃清账」升为**存储层架构升级 + 多会话并行**，工作量约为原计划的 **3~4 倍**；必须**分批提交、每批单独验收**，不许攒成一个一次性大补丁。

- **目标**：一个项目内多开会话同时运行（兑现台账 `MULTI-SESS-1` 的触发条件）。
- **分层**：存储层（批 1）→ 执行位（批 2）→ 项目文件（批 3）→ 事件与视图（批 4）→ 发版收口（批 5）。**前一层验收不过，后一层不开工**。
- **外部参照（2026-11-05 已核实，直接采用，不再论证）**：
  - 三家会话数据都是「每会话独立目录 + 单写者锁 + 原子写」，写入用 OS 级锁（POSIX flock / Windows 命名信号量），**进程死自动释放，不靠 TTL 抢锁**。
  - 工作目录并发写：默认全部是「共用 cwd 不管」；认真并行时全部改用 git worktree；全局排队与单写者策略零采用。
  - dsh 的 fs-local：进程内**按路径串行 + 版本守卫 + 临时文件 fsync → 原子替换**，不同文件不互相阻塞。
  - 三家都用**事件**而非轮询：落盘 `turn/end`（reason=completed）+ 内存 `idle/running`。
- **准入判据（沿用第一版，压缩为三行）**：A = 只有 breaking 窗口能结清；B = 不收进就没机会；C = 阻塞后续任务的前置。只是「顺手」的不入列（落 §4）。

### 3.2 批 1 · 存储层（2026-11-05 第二版方案）

**一句话**：**轮次池共享、会话清单一会话一文件、`index.json` 降为派生缓存、每会话一把 OS 锁、追加写 + torn tail 截断 + watchdog。**

1. **轮次池保持共享**：`round-<id>.json` 不迁移、不拷贝；`forkSession` + `incrementRef` 语义原样保留（但计数真源有阻塞，见 §3.2.1）。
2. **会话清单拆为一会话一文件**：`sessions/<sessionId>.json` = 会话元数据 + 该会话的 `roundIds`；分叉只复制 roundIds 清单，**轮次文件零拷贝**；列会话扫 `sessions/` 目录。
3. **`index.json` 降级为派生结果 + 内存缓存**（不是删除）：由扫描 `rounds/` 可随时重建。
4. **每会话一把 OS 级锁**（进程死自动释放）；第二写者直接回「已在别处运行」，不等待；写只追加 + 每批 fsync + 启动截断 torn tail。
5. **必配 watchdog**：外部三家都用「进程死自动释放」的锁——若进程**卡死但未退出**，锁不释放且无 TTL，该会话会**永久不可恢复**。watchdog 是必要补件，不是可选项。

**落地约束（方案成立的前提，写进实现，不是新结构）**：

- 派生索引**只在启动/显式重建时整体生成并原子覆盖**；**不得在每次 save 后增量写盘**——那不叫降级，是把刚拆掉的全局读改写文件又请回来。
- `getByIds` 必须改为「直接读文件 + ENOENT 视为缺失」，**不得以 `index.has(id)` 为门**（现状 `workspaceRoundStore.ts:182` 起先查缓存再查索引；跨进程时会静默漏掉别处新写的轮）。
- `rounds/{id}.json` 的 mtime **不能当 createdAt**（`incrementRef` 回写会刷新 mtime），时间真源 = `round.createdAt`。

#### 3.2.1 🔴 停住项：引用计数（命门，等裁定，本文不设计）

**结论：新方案的前提「Round 文件写一次后只读」在本仓不成立。**

- `incrementRef` / `decrementRef` 在缓存命中时**整文件重写 Round**（`workspaceRoundStore.ts:241-266` / `:271-298`，`atomicWriteFileSync(filePath, JSON.stringify(cached, null, 2))`）**并重写 index**（`saveIndex()`）；`forkSession` 对每个共享轮逐个 `incrementRef`（`src/agent/messageHistory.ts:183`、`:244`）。
- refCount 现存在**三处**：Round 文件 `round.refCount`、`index.json` 条目、内存缓存；源码注释明写不变量 `cache.refCount ≡ index.refCount ≡ 文件 refCount`（`workspaceRoundStore.ts:461-465`）。
- 拆成一会话一文件后，计数**仍写在那一个共享 Round 文件里** ⇒ 会话锁只锁会话，**锁不住共享轮**：
  - 两会话分叉引用同一轮 → 各自 `read-modify-write` 同一文件 → **lost increment** → GC 按 0 引用误删仍被引用的轮（数据丢失）；
  - 更重：写的是全量快照。若 A 载入时该轮 pending、B 随后把它收场为 complete，A 再 fork 触发 `incrementRef` 会把**旧快照整轮写回** ⇒ 状态回滚、已完成的轮被打捞重跑。这是代码路径的直接后果，不是推演。
- ⇒ **refCount 是「共享轮文件上的全局读改写点」。会话清单拆文件只解了会话这一处，轮次池这一处没解。** 所以 §2 批 1 的「20 次零丢失」**不能**当作轮次池安全的证据。

**两条既有方向（仅列供裁定，本文不选、不展开）**：

1. **计数改为派生**：refCount 不再落盘，由扫 `sessions/*.json` 的 roundIds 现场算出；`forkSession` 不再写轮文件（共享轮真正只读）。代价：GC/delete 判定每次多一次会话扫描。
2. **分叉复制轮**：`forkSession` 复制轮文件给新会话，放弃共享，refCount 生态退役。代价：磁盘与 fork 耗时随会话数线性增长。

**裁定前**：批 1 不开工；验收第 ④ 条标「未定（阻塞）」；不得先实现 1/2/3/5 再「顺手」补计数。

#### 3.2.2 五类消费方逐条结论（扫目录 + 派生缓存后）

| 消费方 | 现状依赖 | 改后是否等价 | 代价 / 差异 |
