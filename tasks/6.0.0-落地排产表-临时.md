## §1 本版定位与总口径

**总口径（用户 2026-11-05 拍板）**：这一波把 6.0.0 从「废弃清账」升为**存储层架构升级 + 多会话并行**，工作量约为原计划的 **3~4 倍**；必须**分批提交、每批单独验收**，不许攒成一个一次性大补丁。

- **目标**：一个项目内多开会话同时运行（兑现台账 `MULTI-SESS-1` 的触发条件）。
- **分层**：存储层（批 1）→ 执行位（批 2）→ 项目文件（批 3）→ 事件与视图（批 4）→ 发版收口（批 5）。**前一层验收不过，后一层不开工**。
- **外部参照（2026-11-05 已核实，直接采用，不再论证）**：
  - 三家会话数据都是「每会话独立目录 + 单写者锁 + 原子写」，写入用 OS 级锁（POSIX flock / Windows 命名信号量），**进程死自动释放，不靠 TTL 抢锁**。
  - 工作目录并发写：默认全部是「共用 cwd 不管」；认真并行时全部改用 git worktree；全局排队与单写者策略零采用。
  - dsh 的 fs-local：进程内**按路径串行 + 版本守卫 + 临时文件 fsync → 原子替换**，不同文件不互相阻塞。
  - 三家都用**事件**而非轮询：落盘 `turn/end`（reason=completed）+ 内存 `idle/running`。
- **准入判据（沿用第一版，压缩为三行）**：A = 只有 breaking 窗口能结清；B = 不收进就没机会；C = 阻塞后续任务的前置。只是「顺手」的不入列（落 §4）。

### 3.2 批 1 · 存储层

**目标形态**：会话数据按会话分目录；目录即索引；每会话一把 OS 级锁（进程死自动释放）；写只追加 + 每批 fsync + 启动截断 torn tail；watchdog 兜底卡死进程。

**为什么必须配 watchdog**：外部三家都用「进程死自动释放」的锁——若进程**卡死但未退出**，锁不释放且无 TTL，该会话会**永久不可恢复**。watchdog 是这个形态的必要补件，不是可选项。

**验收**：见 §2 批 1 行的三条（20 次零丢失 / 第二写者被拒 / 杀进程后锁自愈）。实验脚本沿用已有的临时双进程复现，只允许在临时目录跑，不入仓。

#### 3.2.1 🔴 冲突登记（**停在此，等用户裁定，本文不自行决定**）

1. **`index.json` 不在内核。** `grep index.json src/` 零命中；唯一实现是宿主 `hosts/memora-vscode/src/extension/host/workspaceRoundStore.ts`（实现内核 `IRoundStore`），`sessions.json` 同属宿主 `sessionStore.ts`。⇒ 批 1 按现状落刀改的是**宿主**，与「宿主轴不占内核 6.0.0 版本号」冲突。两条候选，均须裁定：
   - **(a)** 内核新增 round/session 落盘实现，宿主改为注入（占内核 major，工作量最大，但符合「内核不感知数据目录布局」的既有边界）；
   - **(b)** 本批归宿主 0.8.0（内核 6.0.0 只做批 2/3 的接口面）。
2. **`index.json` 有 5 类消费面，「移除」不等于删一个文件。** ① `listInterruptedRecent`（崩溃残留打捞，依赖 status+createdAt）；② `listOrphaned` / `sweepOrphans`（refCount）；③ `listAll` / `getByIds` / `listByStatus`（会话视图重放）；④ 归档两区索引（`hosts/memora-vscode/docs/session-archive-design.md`，归档区另有 `archived/rounds/index.json`）；⑤ `crossRestartRecovery.test.ts`。「目录即索引」= 重写这些读路径；保留兼容还是移除，**须先裁**。
3. **Round 跨会话共享与「每会话独立目录」冲突。** `forkSession` 把同一批 roundId 复制进新会话并 `incrementRef`（`src/agent/messageHistory.ts:183` / `:244`；接口 `src/memory/roundStore.ts:673` / `:680`）⇒ 一个 Round 可被 N 个会话引用，**不能只归属一个会话目录**。可解形态：(i) 会话目录只放 roundIds 清单、Round 仍全局存；(ii) Round 复制进各会话、放弃共享（refCount 生态退役）。**须裁定**。
4. **现状不是 SQLite。** 内核 `src/memory/nodeSqliteStorage.ts` 只实现 `IMemoryStorage`（记忆索引），**不含 rounds/sessions** ⇒ 「只追加 + fsync」要在 JSON 文件层自建，不能假设已有事务。
5. **`sessions.json` 是单文件全量读-改-写**（`hosts/memora-vscode/src/extension/host/sessionStore.ts`），与「每会话独立目录」同批必须一起改——否则会话清单仍是第二处 lost update 源。

## §6 删除机制

1. **谁删**：执行 6.0.0 发版的人。不是下一个读台账的人，也不是自动脚本。
2. **何时删**：`tasks/archive/6.0.0-kernel.md` 落盘后、发版收尾提交内。**发版前不得删**（否则批次与顺序失去唯一载体）。
3. **删前确认**：
   - 归档文件已存在，且 `KERNEL-6.0.0-BATCH-1` 已整区迁入；
   - §5 的动作 1–5 全部完成，或未完成项已逐条写回台账（不得只留口头说明）；
   - §4 各「不做」项的回顾时点仍挂在各自台账条目上，未随本文一起消失；
   - 全仓已无别的文档把本文当长期真源引用（`npm run scan:docs:refs:check` 除本文自身告警外无新增入边）。
4. **删除记录写在哪**：`tasks/archive/6.0.0-kernel.md` 的「本版收尾」段写一行：
   > 临时排产表 `tasks/6.0.0-落地排产表-临时.md` 已删除（<日期>）；批次与顺序以本归档与主台账为准。

   这行就是「该文档已删」的**唯一收据**。主台账**不新增副本**、不新增第二伞条目——`KERNEL-6.0.0-BATCH-1` 已在，再加一层只制造两份口径。
