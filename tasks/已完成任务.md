## 2026-09-24 · ask 态死键宣告切除（PAUSE-ASK-1 · 带伤收敛）

**来源**：TURN-PAUSE-1 审查未修项；2026-09-24 用户「真不带伤落地」拍板，从「观察」升格必修。SSOT × 带伤双维评估定性为**带伤「僵尸声明」模式**（宣告通道零验收、失败被静默）。

**根因（投影层抹掉路由层在意的区分）**：`deriveButtonSemantics` 只吃 `deriveSessionUiState` 折好的三值态，`waiting.reason`（ask/pause）在进矩阵前被抹掉；而 `handleInput` 的 `resume` 路由按 reason 判据（只收 pause）→ ask 态渲染出「继续生成」纯续跑键、点击被守卫静默丢弃。精确解剖：该键**带输入是活的**（走 `sendInput` 的 supplement 续跑 = 真能力），**只有空输入「纯续跑」是死键**——手术点因此是 `waiting(ask) + 空输入` 一格，非整个按钮。

**修法裁决（两方向取一，决定性依据留档）**：原登记「按钮矩阵加 reason 入参（ask 不显示 play）」vs「resume 路由收 ask」——取前者。依据 = `handleAskTimeout` 契约注释留档的产品定案「选项/自由输入仍是唯一主动通道，超时只是保底（**用户明确不要「跳过」按钮**）」：resume 收 ask 即造跳过按钮，违定案。落地 = `waiting(ask) + 空输入` 隐藏续跑键（null，不写 title/aria）；`waiting(ask) + 有输入`「发送补充并继续」保留（走 send 路由，真能力）。ask 等待期通道不变：提问卡作答 / 主输入补充 / 120s 超时自动续跑兜底。

**实现（webview 派生层收敛 + 注释订正，零内核改动）**：`turnUiState.ts` `ButtonSemanticsInput` 改吃完整 `SkeletonState`（含 reason；函数内部仍单一取数 `deriveSessionUiState`/`derivePausePending`），paused 分支加 `plainResume` 判据；`chatView.ts` `currentButtonSemantics` 同步传 `state`（`derivePausePending` 导入随消费点内移收回）；`chatPanel.ts` `handleInput` resume 分支注释**谎报订正**——原「实际不可达」在修复前不成立（ask 态 play 键正可达，HOST-S11 注释漂移同型），修复后改为精确表述「只兜跨消息竞态残留」。

**测试 + 变异验证（M9 锚点）**：`turnUiState.test` 新增 2 例（ask 空输入 → `pause:null` / ask 有输入 → play 保留），disabled 不变量重写为 `SkeletonState` 全分支遍历；`chatView.test` 新增按钮矩阵 DOM 2 例。变异：`plainResume` 恒 true 回退旧行为 → **两文件各红 1 例，精确命中 M9 两层哨兵** → 恢复 → 绿。

## 2026-09-24 · 提问卡被重放抹除修复（ASK-RENDER-1）

**现象（宿主真机 + 用户反馈）**：AI 触发 ask_user 提问暂停时，用户**全程看不到提问卡**，只面对一个无反应的「继续 ▶」按钮；超时（ASK_TIMEOUT_MS=120s）后自动续跑、记录里留下「未回答」。用户原以为「点继续触发了 ask 但无弹窗」。

**真机铁证**：`F:/用户目录/Desktop/小说项目/.memora/rounds/round-1790218628781.json` 单轮 74KB，`status=complete`，02:57:08→03:00:26。`interactiveInputs` 仅一条 `kind:"timeout"`，时间 **03:00:17.157Z**（精确 +120.000s = ASK_TIMEOUT_MS）；LLM 收尾首句「你没有选择处理方向，那我就先不动设定」。`processEvents` 无 `tool_start ask_user`；seq 417 thought「…Then ask_user.」→ 418 narrate 流式上屏 → ask 触发 ≈02:58:17 → 卡 120s → 421 thinking 超时后 3ms 自动续跑 → complete。**内核侧提问（原文+4 选项）完整产出，宿主侧未渲染。**

**根因（webview 渲染顺序契约违例，全落宿主）**：`replaySession()`（chatPanel.ts）走 `postTurnUpdate(undefined, true)` 发**单条** `turn_update` 同带 `replay:true` 与 `state(waiting/ask + questions)`。webview `handleMessage` 原顺序：先 `if (waiting/ask) renderAskPhase(...)` 渲染提问卡 → 紧接 `if (replay) renderReplayFromRounds(...)` 首行 `resetChatView()` 删掉 `.ask-inline`。因提问挂起轮非 complete，重放后无 assistant 锚点 → ask 卡无法内联重挂，且 `clarifyBar` 兜底也未启用（内联路径先走后被抹，留空）→ 用户只见无反应的「继续」按钮。即「继续 bug 与 ask 冲突」假说的真相：不是冲突，是**重放把刚渲染的提问卡抹掉了**。

**修复（零内核改动）**：`chatView.ts` `turn_update` 处理改为**重放先于提问卡渲染**（顺序契约）：`if (msg.replay === true) renderReplayFromRounds(...)` 必须排在 `if (waiting/ask) renderAskPhase(...)` 之前；并加「顺序契约」注释钉死（位置即契约，勿上移）。理由：重放 `resetChatView` 会清掉 `.ask-inline`；重放先跑后，提问卡在干净 DOM 上渲染（无锚点时降级 `clarifyBar` 兜底条，仍可见）。

**测试（不变量守护）**：`chatView.test.ts` 新增 `replay 与 waiting(ask) 同一条消息 → 提问 UI 不得被重放重建抹掉` 用例，断言改为**不变量**「提问未答 ⇒ 必存在可见提问 UI（`.ask-inline` 或 `#clarifyBar.visible`）」，不再窄断言内联形态（因 `rounds:[]` 重放无锚点会降级 clarifyBar）。覆盖「`replay:true` 与 `waiting(ask)` 同一条消息」此前从未覆盖的组合。

**变异验证（实锤）**：撤 revert 修复（回到 ask-first 顺序）→ 该不变量用例转红 `expected false to be true`（line 2867，提问 UI 被抹）→ 恢复修复 → 转绿。证明测试抓住顺序回归，非因错误的原因通过。

**质量门**：宿主全量 `vitest run`（38 文件）→ **665 passed · 1 failed · 2 skipped**；`tsc --noEmit` EXIT=0；`eslint --max-warnings 0` EXIT=0。唯一 failed = `projectSearchProvider.test.ts:475` I/O 超时（`Test timed out in 30000ms`）——与改动无关三重实锤：①该文件零 chatView 依赖；②`git diff --stat` 仅 `chatView.ts`（顺序重排）+ `chatView.test.ts`（新增不变量用例）；③本台账 TURN-PAUSE-1 行已登记其为已知 I/O flake（慢沙箱建 501 实文件扫描超 30s）。

**与 PAUSE-ASK-1 的关系（纠正旧判定）**：用户实测「无弹窗」的真因是**本项（渲染被抹）**，不是 PAUSE-ASK-1（resume 守卫只认 `reason==='pause'`）。两者不同层：① 本项修掉前，提问卡根本不出现 → 用户无从作答、也无从误触「继续」；② PAUSE-ASK-1 是「提问卡正确出现后，ask 态点继续被守卫静默丢弃」的次生窄路径——属设计意图内（ask 态正确操作=输入框作答），仍按原登记**观察、触发=真实误触反馈**再动。PAUSE-ASK-1 条目已补关系注记。

## 2026-09-24 · 暂停续跑投影刷新缺失修复（TURN-PAUSE-1）

**现象（宿主真机）**：暂停 → 点「继续」→ 提示已恢复，但按钮图标不变（仍「继续 ▶」）且续跑全程不切；续跑结束后再点「继续」无反应。

**根因（宿主侧投影刷新时机失控；内核暂停语义本身干净，D1/D2 回归守着）**：
- **主因**：`consumeFlow` 起始 `postTurnUpdate()`（`chatPanel.ts` L2480）执行于 `resumeExecution` body **之前**——async generator 惰性求值（`runFlow` 的 `factory(signal)` 只创建对象，首次 `next()` 才跑 body）。此刻 `sessionManager.status` 仍是 `paused` → `deriveTurnState` 第②条（`turnProjection.ts` L96-98）→ `waiting(pause)` → `deriveSessionUiState` 返回 `'paused'`（`turnUiState.ts` L79-80）→ 按钮恒为 play。
- **放大**：状态机翻转事件（`onSessionPaused` / `onSessionResumed`）只发 notice 不重投影；`onSessionResumed` 原走 `syncPendingQueue()`，其**长度守卫**在纯续跑（无 interject）下恒不触发 → 续跑全程无任何刷新点。
- **缺一**：`handlePause` 的 `requestPause` 成功分支漏 `postTurnUpdate()`，而上方注释已承诺补推（另两分支均有）。

**修复（全落宿主侧，零内核行为变更）**：
1. `onSessionPaused` / `onSessionResumed` 各补一次 `this.postTurnUpdate()`——**真源翻转事件 = 投影刷新点**（只读真源 + 幂等；chat 路径不 emit 这两个事件，故零影响）。
2. `onSessionResumed` 移除 `syncPendingQueue()`（长度守卫会吞掉纯续跑），改由 `postTurnUpdate` 自带 `pendingQueue` 载荷一次推完。
3. `handlePause` ok 分支补 `postTurnUpdate()`（三缺一补齐，与另两分支对称）。

**过程中撤回的一处（重要）**：曾在 `resumeInput` 加 `sessionManager.status !== 'paused'` 前置检查——被 `chatPanelInput.test.ts`「waiting(pause) 态 resume → 纯续跑」用例拦下（真回归）。判定为**给 `_turnState.phase` 单一判据装第二套判据 = SSOT 违例**，已撤回。根因修掉后用户不会在非暂停态看到「继续」按钮，无需二次判据。

**质量门**：新增 `chatPanelPauseProjection.test.ts` 2 例 → 宿主全量 **38 文件 / 664 passed · 2 skipped · 1 failed** → `tsc --noEmit` EXIT=0 → `eslint --max-warnings 0` EXIT=0。唯一 failed = `projectSearchProvider.test.ts:475` I/O 超时（该文件零 chatPanel 依赖；`git diff --stat` 实证改动仅 `chatPanel.ts`；本台账 09-23 行已登记其为已知 I/O flake）。

**变异验证**：撤掉两处 `postTurnUpdate()` → 两用例均转红（`expected [] to have a length of 1 but got +0`）→ 恢复转绿。

**未修（另行评估，勿顺手改）**：
- `waiting(ask)` 与 `waiting(pause)` 在 `deriveSessionUiState` 同映射 `'paused'`（UI 同形），而 `handleInput` 的 resume 路由只认 `reason==='pause'` → ask 态点「继续」被静默丢弃（改按钮矩阵需加 `reason` 入参）。
- `agent.ts` `resumeExecution` 对非 paused 态**静默 return**（对比 error 分支有 emit + yield error）。
- `sessionManager.updateGoal` 的 drift 自动暂停在生产路径**零调用**（仅测试），且直接 `pause()` 绕过 loop 队列——接线前不宜启用。
