## 2026-09-15 · 问题2「读一堆文件后卡住 5 分钟」根因定性 + 修复（SSE 停摆超时语义）

> **来源**：真机 `互动叙事平台方案` 会话，轮 `round-1789462982489`。
> **先说结论：初始判断「引擎无超时兜底」不成立**——兜底存在且按预期触发，真因是**超时语义被 `reader.cancel()` 抹掉**。

## 2026-09-13 · CTX-1 Step 1a · read_file 分段与 token 估算器统一

> **来源**：Step 1 动手前读码否决原形态（[大文本统一通道-探索方案.md](../docs/大文本统一通道-探索方案.md) §6.1）。Step 1 的形态是「结果超阈 → 落盘 → 回『预览 + 路径 + 尺寸』」，而 LLM 回取原文的唯一路径是 `read_file` —— 读码实证它 **① 无分段能力**、**② 超长静默截断**，于是阈值陷入二难（<12,500 tokens → 读回产物再超阈 → 再落盘 → 无限嵌套；≥12,500 → 对内置工具结构性不可达 = 第二块死砖）。**逃逸只有一条：让 `read_file` 能分段。** 1a 即此硬前置。

- **二难实锤**：`read_file` schema 只有 `path`（`builtinTools.ts:347-357`）+ handler `readFile(relativePath)`（`builtinToolHandlers.ts:202`）→ 无分段；`sanitizeExternalText` 超长只 `slice + '…'`（`toolExecutor.ts:158`）→ **静默截断 = 假阴性**（与 SEARCH-1「零命中丢失截断标记」同族）。
- **第三个硬前置（拍板时才发现）**：原拍板写「24,000 chars（≈6,000 tokens）」——**该等价关系不成立**。全库并存两个估算器：`contextManager.estimateTokensText`（CJK `1.5` / 其他 `3`，**唯一公开出口**）vs `compaction.ts::estimateTokens`（一律 `÷4`，**孤儿**，仅内部两处调用）。同样 24,000 字符：中文 ≈16,000、英文 ≈8,000 tokens，**都不等于 6,000**。⇒ 限额必须表达为 **token 量**并按 token 判定，字符只是估算输入。
- **孤儿估算器的守卫是假闸门**：其首个用例名「准确估算中文 Token 数」、注释「4 个汉字 ≈ 6-8 tokens」，断言却是 `toBe(1)`（`ceil(4/4)`）——**用例名 / 注释 / 断言三者互相矛盾**，把错误固化成预期。同批删除。
- **修复（内核 5 文件 + 测试 3 文件 + 出货文档 1 份）**：

  2. `readFile(path, offset?, limit?)`：1-based 行号，按 token 预算**二分**最大可容纳行数（token 随行数单调增 → 二分成立），脚注预留按最坏位数估算；
  3. **截断诚实化**：超预算输出 `[read_file 分段] 已显示第 X–Y 行（共 M 行）。继续读用 offset=Y+1。`；**读到末尾不追加脚注**（零噪音）；`offset` 越界如实告知而非返回空串；病态长行走 `clampCharsToTokenBudget` 并明示已截断；
  4. **估算器统一**：`compaction` 两处判据改调 `estimateTokensText`，删孤儿 `estimateTokens`；
  5. **净化拆分**：从 `sanitizeExternalText` 抽出 `stripControlChars`（去控制字符单一真理源，不限长）——`read_file` 改调它，不再传 `Number.MAX_SAFE_INTEGER` 这类假上限让调用方迁就接口（中途先写了两层包装，立即自我推翻为多余抽象）；

## 2026-08-28 · 中断轮保存修复（P1：半截回答不落盘 + F-1 分叉点错位同治）

> 来源：用户实测定回归——回答途中点击停止，该问答闭环**未保存**。排查定位为内核 consumeExecutionStream 中断路径返回值错误，与上轮审查归档的 F-1（interrupted 分叉点错位）**同源根因**。

- **根因**：真实 LLM 流式 abort 抛 `AbortError`（fetch stream 中断）→ `consumeExecutionStream` catch 分支返回 `{ aborted: false, failed: true }`（agent.ts catch 中 aborted 未置位）→ `act()` 首行 `if (streamResult.failed) return` 短路 → 专门为中断写的「半截内容 + \[已中断] 标记 appendAssistant」分支（orchestrator.ts L240-252）永不执行 → 轮次停在 pending 孤儿（refCount=0）不登记 → 会话无本轮。

- **修复**（agent.ts consumeExecutionStream）：AbortError 分支返回 `{ aborted: true, failed: false }`——中断是用户主动行为非失败，与类型注释语义对齐。修复后中断轮经 `act()` aborted 分支走 appendAssistant 落盘 + roundId 登记。

- **同治 F-1**：中断轮登记后，host 的 `latestRoundId`（sessionRoundIds 末尾）即本轮，interrupted 分叉点从「退到上一闭环」修正为「本轮」。

- **测试**：新增 `AbortThrowingProvider`（chunk 间检测 signal.aborted 抛 DOMException AbortError，模拟真实 fetch stream 中断，区别于既有 `AbortableMockProvider` 的 loop 边界路径）；新用例验证「已产出文本保留 + \[已中断] 标记」。修复前该用例必红（history 无 assistant 消息）。

- **宿主同源根因（二次实测回归后补齐）**：宿主 `consumeFlow` 收到 `aborted` chunk 后 **break**——for-await 中 break 触发 async iterator `return()`，沿 `yield*` 链提前终止 `chat → runChat → act → consumeExecutionStream`，`act()` 的中断保存（appendAssistant + roundId 登记）在委托 generator 之后永不执行。修复：`aborted` 分支改 `continue`（aborted 是末块，后续无 text），让流自然走完，中断通知仍按末尾 `controller.signal.aborted` 判断发出。

- **验证（补充）**：内核 vitest 全量 2485 绿（1 skip）；宿主 tsc 零错误 + vitest 232 绿。
