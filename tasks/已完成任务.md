### 体验断点清单

|----|--------|------|---------|
| B1 | P1 | SkillDropManager 在热重载失败时仍显示"技能安装成功"——用户误以为已生效，实际需重启 | F1 |

### 修复批次

#### F1 · SkillInstallResult 扩展热重载状态（B1 + B2）

- **skillInstaller.ts**：`SkillInstallResult` 接口新增 `hotReloaded?: boolean` + `hotReloadError?: string` 字段，JSDoc 明确三态语义（true=已生效 / false=需重启 / undefined=Agent 就绪后生效）
- **main.ts**：SKILL_INSTALL IPC handler 在 `appState.agent.reloadConfig('skill')` 成功时置 `hotReloaded=true`，失败（如 chatBusyError）时置 `hotReloaded=false` + `hotReloadError`，无 Agent 时留 undefined
- **preload.ts / preloadWeb.ts**：installSkill 返回类型同步扩展，保持 Electron / Web 双模式契约一致
- **skillDropManager.ts**：
  - `installSkillFile()` 返回 4 路分类：`'failed' | 'hot-reloaded' | 'hot-reload-failed' | 'no-agent'`
  - `handleSkillDrop()` 累计 4 个计数器（successCount/hotReloadedCount/hotReloadFailedCount/noAgentCount）
  - 按"最严重情况"优先级选择 toast：全热重载成功 → success toast "技能安装成功，已生效"；全无 Agent → info toast "Agent 就绪后生效"；部分热重载失败 → warning toast "重启后生效（当前对话进行中）"

#### F2 · SkillManager 最低激活阈值（B3 · 内核侧）

- **skillManager.ts**：新增 `SKILL_MATCH_MIN_SCORE = 0.3` 常量（模块私有，不导出避免跨包运行时依赖）
- `match()` 关键词评分循环过滤 `score >= SKILL_MATCH_MIN_SCORE`，替代原 `score > 0`
- 阈值取 0.3 的依据：3 关键词命中 1 个（0.333）激活，5 关键词命中 1 个（0.2）不激活；与 PersonaManager 的 KEYWORD_HIGH_CONFIDENCE_THRESHOLD (0.5) 形成梯度（persona 切换显式严格，skill 注入隐式宽松）

#### F3 · ipcListeners 阈值真理源对齐（B3 · renderer 侧）

- **ipcListeners.ts**：`handleSkillMatched` 删除 `score < 0.5` 二次过滤
- 设计理由：内核 `match()` 已用 `SKILL_MATCH_MIN_SCORE` 过滤低匹配度，凡到达 renderer 的 skillMatched 事件 score 均 ≥ 0.3（trigger 命中则 = 1.0）；renderer 二次过滤会造成"激活但不提示"的静默激活误导
- 符合用户偏好："opposes defensive programming"——kernel 是唯一真理源，renderer 不重复过滤
- 未导出 `SKILL_MATCH_MIN_SCORE` 常量到 renderer：避免跨包运行时依赖（Electron sandbox / 浏览器环境无法 import 'memora' 运行时值），renderer 不需要此值（不二次过滤）

#### F4 · Web 模式热重载对齐（B4）

- **systemRoutes.ts**：`POST /api/skill-install` 路由在 `result.success && ctx.isAgentReady()` 时调用 `ctx.agent.reloadConfig('skill')`
- 与 Electron IPC 行为完全一致：成功置 `hotReloaded=true`，失败置 `hotReloaded=false` + `hotReloadError`，Agent 未就绪时留 undefined
- 修复前：Web 模式安装技能后需重启 Agent 才生效；修复后：当前会话立即生效（对话繁忙等场景降级为"重启生效"）

### 测试覆盖

- **skillManager.test.ts**：新增 6 个 `SKILL_MATCH_MIN_SCORE 阈值边界` 测试（3/5/2/10 关键词命中场景 + 边界值 0.3 + 多技能取最高分）— 25/25 通过
- **skillDropManager.test.ts**：默认 mock 改为 `{ success: true, hotReloaded: true }`；新增 5 个热重载路径测试（单/多热重载失败、部分热重载失败、单/多无 Agent）— 26/26 通过
- **ipcListeners.test.ts**：原 `score<0.5 不弹 toast` 断言改为 `score=0.33 也弹 toast`（renderer 不二次过滤）— 97/97 通过

### 验证

- 内核 typecheck: 0 errors
- 精灵 typecheck: 0 errors
- 内核 vitest: 1538 passed + 1 skipped（+6 新测试）
- 精灵 vitest: 4482 passed（+5 新测试 + 1 改写）

### 设计决策

1. **不导出 SKILL_MATCH_MIN_SCORE 到 renderer**：ADR-017 枝叶层 2 次提取——renderer 不消费此值（不二次过滤），无需导出；避免跨包运行时依赖破坏 Electron sandbox
2. **删除二次过滤而非对齐到 0.3**：用户"反对防御式编程"偏好 + kernel 已是真理源——renderer 二次过滤是冗余防御层
3. **阈值取 0.3 而非 0.5**：3 关键词命中 1 个即激活（避免短关键词列表被误判为噪音），5 关键词命中 1 个不激活（避免长关键词列表误触）；与 persona 0.5 形成梯度
4. **Web 模式与 Electron 模式行为对齐**：F4 修复 B4 后，两条路径在热重载行为上完全一致——成功/失败/无 Agent 三态语义统一

## 2026-07-16 问诊关闭 · AUDIT-0716-1 native 模块隔离

> **来源**：AUDIT-0716 阶段 3 P0 历史遗留任务，2026-07-16 问诊评审后关闭
> **关闭类型**：❌ 原诊断错误（概念混淆 + 已被 ADR 澄清 + 推进属过度设计）

### 问题原描述

内核 10 个生产文件直接 import `node:fs` / `node:path` / `node:os`，原诊断认为违反"零依赖内核"原则，建议推进 IFileSystem 接口隔离。

### 关闭理由

1. **原诊断概念混淆**——将 Node.js 标准库（node:fs/node:path/node:os/node:crypto）误判为"native 模块"。ADR-002 [§关于"内核浏览器可 import"的定位澄清（2026-07-13 年轮补充）](../.trae/rules/decisions/ADR-002-storage-layer.md) 已明确：
   - "memora 内核是 Node.js 专用纯逻辑库（零 native 编译依赖，但依赖 Node.js 运行时 API）"
   - "'纯 JS 工具库'的范围明确为'Node.js 纯 JS'，不包括'浏览器纯 JS'"
   - "浏览器可 import 不是内核目标"

2. **推进 IFileSystem 接口属于过度设计**，违反两条原则：
   - 违反 [ADR-017](../.trae/rules/decisions/ADR-017-natural-growth-redefinition.md) §枝叶层 2 次提取原则——"不为未来可能的需求预留抽象"
   - 违反 ADR-002 §异步化触发条件——仅当"出现真实的浏览器直接运行 memora 内核需求"且"达到 2 次以上重复"时才启动 IAsyncMemoryStorage 预研，当前均不满足
   - project_memory.md 明确记录："Core kernel must explicitly定位为 'Node.js 专用'"，内核已明确定位 Node.js 专用

3. **零 native 依赖目标已守住**——better-sqlite3/electron/commander 已全部移出 src/（ADR-002 v0.7），10 个文件直接 import Node.js 标准库是核心功能依赖（pathGuard 符号链接解析、builtinToolHandlers 文件操作、projectRegistry 注册表读写等），无法懒初始化，也无必要隔离。

### ADR 评估

ADR-002 已包含 2026-07-13 年轮补充，定位澄清完整，**无需新增 ADR**。

### 规则状态

[project-rules.md §1.6](../.trae/rules/project-rules.md) 表述"不依赖任何 native 模块"存在轻度歧义（可被误读为包含 Node.js 标准库），但 ADR-002 年轮补充已给出权威解释。建议在未来"规则对齐"模式中将 §1.6 表述微调为"不依赖任何 native 编译模块"——当前不阻塞，不在本次问诊范围。

### 后续追踪

- AUDIT-0716-1 任务条目已从 [待完成任务.md](./待完成任务.md) 移除
- 若未来 ADR-002 §异步化触发条件满足（真实浏览器运行需求 + 2 次以上重复），重新启动 IFileSystem 评估

## 2026-07-14 UX-0714-1 · 搜索 loading 反馈

> **来源**：体验评审 UX-0714-1（🔴 严重）→ 问诊前置门控接纳 → 直接实现
> **范围**：纯渲染层改动，零内核改动、零新增 IPC

### 问题

`searchMemories` + `searchSessionMessages` 是 IPC 异步调用，记忆库较大或主进程繁忙时用户输入后看不到任何反馈。Phase 2 防抖 300ms + IPC 往返，可能 500ms+ 无反馈，用户不知道是否在搜索。

### 实现

- **`quickInputCompletion.ts`**：
  - 新增 `showLoading()` 私有方法：在候选列表容器中插入"搜索中..."占位项
  - `fetchCandidates` 在 IPC 发出前（`Promise.all` 之前）调用 `showLoading()`

  - loading 期间 `candidates` 数组为空，`handleKeyDown` 的 `length === 0` 检查让键盘导航天然失效
  - `aria-hidden="true"` 避免屏幕阅读器将占位项误报为可选项
  - IPC 返回后由 `renderCandidates` 或 `clearCandidates` 自然替换 loading
- **`quick-input.css`**：
  - 新增 `.completion-item.completion-loading` 样式（居中 + muted 色 + cursor: default）
  - 新增 `:hover` 排除规则（loading 占位不显示 hover 背景色）
- **`quickInputCompletion.test.ts`**：
  - 新增 4 个测试：IPC 发出后显示 loading / IPC 返回后 loading 被替换 / 双 IPC 失败时 loading 被清除 / loading 期间键盘导航失效

### 设计要点

- **防抖期间不显示 loading**：只在防抖结束、IPC 发出后才显示，避免输入时闪烁
- **复用类名而非新增高度计算逻辑**：loading 占位项用 `.completion-item.completion-loading` 双类名，让现有 `onListChange` 回调的 `querySelectorAll('.completion-item').length` 天然返回 1，高度计算为 80 + 1*38 = 118px，刚好容纳 loading 文本
- **乱序安全**：用户快速输入触发多次 `fetchCandidates` 时，旧请求的 loading 会被新请求的 `showLoading()` 覆盖（都是清空列表再插入），IPC 返回时 requestId 不匹配直接 return，loading 由最新请求接管

## 2026-07-14 AUDIT-0713-8 · 消除 requireNonNull 噪音（驳回 discriminated union，改用局部变量提取）

> **来源**：问诊：自动迭代 → 选择 AUDIT-0713-8 评估
> **决策**：驳回 discriminated union / InitializedAgent 方案，改用枝叶层手段（局部变量提取 + 非空断言 `!`）

### 驳回理由（4 项）

1. **`#private` 字段阻断 discriminated union**：Agent 有 3 个 `#private` 字段（#config/#provider/#backgroundProvider），TypeScript `#private` 在 conditional type / mapped type 中无法保留，类型变换后 `#private` 语义丢失。与 AUDIT-0713-5 驳回 ComponentRegistry、ARCH-0713-2 驳回 mixin 同源：`#private` 三次阻断架构层重构
2. **InitializedAgent 包装类违反门面契约（ADR-010）**：ADR-010 要求"宿主一行代码接入"，引入 InitializedAgent 会让 `agent.chat()` 在 init 前后返回不同类型，宿主代码需 `if (agent instanceof InitializedAgent)` 分支，破坏门面简洁性
3. **assertInitialized 已做运行时校验**：assertInitialized 在方法入口校验 `_initialized` + history + loop，后续 requireNonNull 是冗余的防御性编程（用户明确反对防御性编程——"掩盖 bug 而非解决 bug"）。根因是 TS 无法窄化 `T | null` 到 `T`，而非缺少校验
4. **13 处改为局部变量提取即可消除大部分噪音**：`this.requireNonNull(this.xxx, 'name').method()` 的噪音来自"内联调用 + 字段重复访问"，改为局部变量提取后 `const xxx = this.xxx!; xxx.method()`，噪音消除且更高效（避免重复属性访问）。这是枝叶层手段，无需架构层改动

### 执行内容

- 13 处 `this.requireNonNull(this.xxx, 'name').method()` 改为局部变量提取 + 非空断言 `!`
  - chat() 7 处（chatLockManager/loop/history）
  - recallAndInject() 2 处（pctx/loop）
  - postProcessInner() 3 处（history，统一提取到方法顶部）
  - forkSession() 1 处（_sessionManager）
  - switchProject() 1 处（projectManager）
  - createSessionManager() 2 处（history/loop，惰性 getter）
- 删除 `requireNonNull<T>` 私有方法（13 处调用已全部替换，方法无引用）
- 更新 getter 区域注释：`assertInitialized + requireNonNull 抛 MemoraError` → `assertInitialized 抛 MemoraError`

### 设计要点

- assertInitialized 仍是运行时校验的入口，保证"未 init 时抛 MemoraError"
- `!` 非空断言是编译期窄化工具，与 assertInitialized 配合：运行时校验 + 编译期窄化

## 2026-07-14 AUDIT-0713-5 · 评估引入 ComponentRegistry 模式（驳回）

> **来源**：问诊：自动迭代 → 选择 AUDIT-0713-5 评估
> **决策**：驳回。不引入 ComponentRegistry，改为提取 `nullifyAllComponents()` 私有方法 + 在 new-module-guide.md 补充"新增 Agent Manager 检查清单"（9 处修改点）

### 驳回理由（6 项）

1. **类型安全性是门面类核心价值（ADR-010）**：`agent.memory: MemoryInspector | null` 是编译期强类型，ComponentRegistry 变成 `registry.get<MemoryInspector>('memoryInspector')`——字符串 key + 显式泛型，拼写错误无法编译期发现
2. **`#private` 字段无法纳入**：Agent 有 3 个 `#private` 字段（#config/#provider/#backgroundProvider），ECMAScript `#private` 是类作用域的，ComponentRegistry 无法统一管理，导致"3 个字段在类、14 个在 registry"的分裂状态
3. **生命周期异构需适配层**：5 种生命周期模式（dispose/stop/close/仅 null 化/getter 回调注入），强行统一 `Lifecycle` 接口会引入 5 个适配器或 no-op 方法，增加的样板代码比减少的字段声明还多
4. **Assembler 已解决装配痛点**：真正的痛点（装配逻辑臃肿）已在 assembler.ts 拆出（4 阶段工厂函数），Agent 只负责"持有 + 暴露"
5. **依赖顺序需显式声明**：assembler.ts 有明确的 4 阶段创建顺序，ComponentRegistry 需要额外的依赖声明机制，当前显式顺序比隐式依赖图更清晰
6. **ADR-017 分层原则**：ComponentRegistry 是架构层改动，但痛点是枝叶层问题，应优先用枝叶层手段解决

### 替代方案（已执行）

- **建议 1**：提取 `nullifyAllComponents()` 私有方法——close() 的 17 字段 null 化集中到一个私有方法，close() 只调用 `this.nullifyAllComponents()`，新增 Manager 时只需在方法内加一行
- **建议 2**：在 [new-module-guide.md](../.trae/rules/new-module-guide.md) §7 补充"新增 Agent Manager 检查清单"——9 处修改点（跨 agent.ts + assembler.ts 2 文件）固化到规则文件，新增 Manager 时按清单检查
