## MIND-C2：config/loader.ts 类型守卫提取（2026-07-30）

> 来源：心智模型审计 P2 批次 2。loader.ts 中 9 处 `as Record<string, unknown>` 断言，提取语义一致的 4 处为类型守卫辅助函数。
> 方案文档 → [方案-MIND2-C2-loader类型守卫提取-20260730.md](./方案-MIND2-C2-loader类型守卫提取-20260730.md)

### 问题

`src/config/loader.ts` 中 9 处 `as Record<string, unknown>` 断言，存在守卫与断言的隐式耦合（守卫变更时编译器不报警）。其中 4 处属「默认值 {}」语义，3 处属「降级 undefined」语义，1 处属「throw」语义，1 处属「读字段」语义。

### 修复方案

仅提取语义一致的 4 处（parseConfig 顶层 input/llmInput/memoryInput/securityInput）为 `asRecordIfObject(value: unknown): Record<string, unknown>` 辅助函数：非空对象 → Record，否则 → 空对象 {}。

保留 5 处不提取：parseProviders/parseBackground/parseEmbedding 是「降级 undefined」语义（3 处）+ parseProviders 内层是「throw」语义（1 处）+ isEnoent 是「读字段」语义（1 处），强行合并需引入第二个辅助函数，3 处使用刚达阈值边际，保留原样更清晰。

### 修改文件清单

| 文件 | 变更类型 | 改动点 |
|------|---------|--------|
| `src/config/loader.ts` | 修改 | 新增 `asRecordIfObject` 辅助函数（14 行）+ parseConfig 顶层 4 处守卫+断言改为调用（-10 行重复模式） |

### 验证结果

- **内核 typecheck**：0 错误
- **内核全量测试**：1642 项全部通过（零回归）
- **宿主全量测试**：4604 项全部通过（零回归）

### 设计决策

- **避免过度工程**：不提取 asRecordOrUndefined 辅助函数（3 处使用刚达阈值边际），保留原样更清晰
- **语义一致性优先**：只提取语义完全一致的 4 处，不强行合并不同降级行为的断言

### 修复方案

**D3 核心**：ChatPanelHost 拆分为 4 个窄接口 + 删除死方法 `updateBadge`：

| 窄接口 | 方法数 | 职责 |

**D3 收窄依赖方接口**：

- `messageOperations.ts` 的 host 类型同步收窄为相同的 Pick 子集（4 方法精确对应 handleRegenerate/handleForget 实际调用集）

**D2 辅助**：提取 7 个 private DOM 字段为 CoreElements 容器（模式 A 纯状态容器）：
- 必需元素（缺失时抛出）：messagesEl / inputEl / btnSend / btnStop —— 用 `!:` definite assignment
- 可选元素（缺失时降级）：badge / btnMaximize / chatAgentStatusEl —— 用 `null` 初值

| 文件 | 变更类型 | 改动点 |

## MIND2-C3：归档失败 pending 队列——不再永久丢失（2026-07-30）

## MIND2-L5：lockManager.release 补 PID 校验双重保险（2026-07-30）

> 来源：心智模型审计 II P1。`release` 不校验 PID 归属可能删除他人锁（违反 §1.3「不可逆操作的双重保险」）。

### 问题

`acquire` 非阻塞（仅警告），两进程可同时持有「锁文件路径」。进程 A release 时直接 `unlink(currentLockPath)`——此时该路径可能已是进程 B 的锁。`release` 不读锁文件校验 PID，`safeUnlink` 还忽略所有删除错误。

注：FIX-P2-15「不强制阻止并发是有意设计」不覆盖此缺陷——并发策略与 release 误删是两件事。

### 修复方案

`release` 改为三段式校验：
1. 读取锁文件，校验 `pid === process.pid`
2. 匹配 → `safeUnlink` 删除（本进程持有的锁）
3. 不匹配 → 跳过删除并 warn（保护他人锁）；锁文件不存在/损坏 → 视为已释放

无论是否删除，都重置 `currentLockPath = null`（本进程不再持有引用）。

### 修改文件清单

- [lockManager.ts](file:///f:/zooique/memora/src/memory/lockManager.ts) — `release` 方法重写（137-174 行）
- [lockManager.test.ts](file:///f:/zooique/memora/src/memory/__tests__/lockManager.test.ts) — 新增 2 个测试用例：
  - 锁文件被其他进程覆盖时 release 不删除他人锁
  - 锁文件已被外部删除时 release 视为已释放不抛错

### 验证结果

- 内核 typecheck：0 错误
- 内核测试：1639 passed, 1 skipped（+2 新增测试）
- lockManager 专项测试：15 passed（含 2 个新用例），warn 日志正确触发

### 设计原则

- **双重保险**：release 前校验 PID，即使 acquire 设计允许并发，release 也不会误删他人锁
- **不破坏并发策略**：acquire 仍非阻塞仅警告（FIX-P2-15 有意设计），仅 release 增加保护
- **先重置后校验**：`currentLockPath = null` 在校验前执行，避免异常时残留引用

## MIND2-C1：写操作 IPC 改用 throwingHandle（2026-07-30）

> 来源：心智模型审计 II P0 第 2 项。`safeHandle` 系统级吞错——20+ 写操作 IPC 失败伪装成成功（违反 §1.1「区分症状与根因」）。

### 问题

写操作 IPC handler 全部使用 `safeHandle`，catch 后返回 fallback 降级值（如 `{ success: false, error: '未知错误' }`）。调用方无法区分"业务校验失败"（如 ID 不存在，预期分支）与"内核异常"（如 SQLite 挂了、Agent 未就绪，系统错误），错误反馈退化为通用文案。已建平行版本 `throwingHandle`（查询类专用 re-throw），但写操作仍用 safeHandle——根因（写操作缺失败可见性通道）未解决。

### 修复方案

**决策依据**（基于 search agent 完整调研）：渲染层已具备完整的 IPC 错误处理基础设施（`createIpcErrorHandler` + `formatErrorMessage` + `reportError` 三件套），90%+ 写操作调用方已有 try/catch + handleIpcError，改 throwingHandle 后零改动；仅 2 处裸调用需补 try/catch。

**改造模式**（统一模板替换）：
- 写操作 `safeHandle('context', fallback, fn)` → `throwingHandle('context', fn)`（去掉 fallback 参数）
- 业务校验失败（如 `isValidId` 不通过、`config`/`profile` 未就绪）保持返回 `success:false`（业务态，非异常）
- 内核异常（`requireAgent`/`requireSprite` 抛 SpriteError 或内核方法抛错）由 throwingHandle re-throw，渲染层 catch 显示真实错误

**L1-L3 LLM 治理类特殊处理**：
