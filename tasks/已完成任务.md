## 插件打断能力 —— 停止生成 + 插话（2026-08-14）

**依据**：memora MVP 闭环落地审查通过后，用户决策推进插件对齐；mvp-scope §二「打断能力（停止/插话）」为插件体验对齐的第一优先项。以插件（memora-doc-review）为北极星，memora 内核作为能力弹药库——**打断能力的实现内核已具备（chat/resumeExecution 均支持 AbortSignal），插件只做暴露，未改内核**。

### 实现
- **协议层**（protocol.ts）：`stop`（W→E，用户主动中断）+ `interrupted`（E→W，流被中断的应答，区分于正常 done）。集中联合类型定义，防两侧手写漂移
- **host**（chatPanel.ts）：
  - 新增 `_abortController` / `_currentFlow` / `_interrupted` 三态管理；
  - `handleStop()`：无进行中流时 no-op，abort 中断 chat()/resumeExecution() 流；
  - **插话队列**：生成中发送 = 置 `_interrupted` + abort 旧流 + `await _currentFlow` 待旧流彻底结束（chatLock 释放）再发新流，避免「发起新对话」busy 冲突；
  - `consumeFlow` 增加 controller 参数：检测 aborted chunk 提前退出，finally 按 controller 比对清理（防误清下一轮），结束区分 `interrupted`（发 interrupted）/ 正常 done
- **UI**（chatView.ts）：生成中**不禁用输入框**（支持插话，Enter 打断并重发）；发送按钮 loading 态切换为**停止方块**（点击=停止，title「停止生成」）；`interrupted` 消息渲染「已停止生成」提示条 + 兜底终结工具卡片
- **样式**（chatStyles.ts）：移除 send-spinner，新增 stop-icon 图标切换（loading 时隐藏发送箭头、显示停止方块；cursor 保持 pointer，不误导「不可点」）

### 设计（SSOT 自然生长）
- 复用内核已有 `AbortSignal` 能力（agent.ts chat/resumeExecution 签名 + consumeExecutionStream 的 aborted chunk 出口），**未在内核新增任何机制**——插件只是把「用户 stop/插话」接上信号
- 插话与停止共用同一 AbortController，单一中断语义；`_interrupted` 为「用户意图中断」权威标志
- 协议集中在 protocol.ts 联合类型，webview 停止/插话交互全走既有 postMessage 通道

## 修复会话记录无法加载 —— 跨天 key 丢失 + 双写 + 路径健壮（2026-08-14）

**依据**：用户「还是没有加载会话记录……需要底层优化，启用资深程序员心智模型，ssot 原则审查代码质量」；用户实测「昨天重启能拿到记录，今天没有了，是不是隔天」

### 根因（三处，第一性原则审查定位）
1. **跨天 key 丢失（核心，用户点名）**：内核按 `todayDate()-main` 归档（`YYYY-MM-DD-main`），昨天的记录落在 `2026-08-13-main`；UI 的 `loadHistory` 只读「当天」的 `2026-08-14-main` → 完全空白。昨天重启时 date 还是 8-13 所以能读到，今天跨天就丢失。
2. **UI 与内核双写**：内核 `chat()` 已通过 `appendUser/appendAssistant` 持久化（agent.ts L543/L583），UI 的 `handleSend`/`consumeFlow` 又各自 `persist` 一遍 → 同 key 双写导致历史重复；且 UI 存纯文本、内核存带文档前缀的 chatInput，内容不一致。
3. **sessionStore 路径健壮性**：extension.ts 用 `workspaceFolders[0] ?? ''` 构造，工作区未就绪时回退 `''` → `join('', '.memora', ...)` 生成相对路径 `.memora/...`，写到进程 cwd 下的错误位置（VS Code 宿主 cwd 不可控）→ 会话文件写丢。

### 修复（SSOT 单一真理源）
- **跨天合并加载**：`loadHistory` 遍历 `listSessions()` 全部 `*-main` 会话合并，按 timestamp 升序回放，杜绝隔天丢失；`handleClear` 遍历清空全部 main 会话。
- **user 消息剥离文档前缀**：新增 `stripDocContextPrefix`，仅当消息以 `[当前打磨文档内容]` 开头才剥离 `\n\n用户请求：` 后的用户原文（避免误伤普通对话中含「用户请求：」字样的消息）。
- **消除双写**：`handleSend`/`consumeFlow` 移除 UI 的 `persist`（持久化唯一真理源 = 内核 sessionStore）；`handleResume` 保留 UI 补写（resumeExecution 内核路径不写 user，宿主补丁防丢回答）。
- **路径健壮**：新增 `resolveWorkspacePath()`，工作区未就绪时回退用户主目录绝对路径，杜绝相对路径写丢。
- **不藏错**：`loadHistory` catch 由静默 `return []` 改为 `console.warn` 记录（SSOT 不吞因）。

### 纪律自查
- [x] 区分症状与根因：用户反馈「空白」是果，根因是跨天 key + 双写 + 路径
- [x] 单一真理源：持久化收敛到内核 sessionStore；会话路径收敛到 resolveWorkspacePath
- [x] 修复后三步验证：typecheck + 插件测试（7）+ compile 全通过

## 主动提问落地（内核 [ASK] 解析 + 插件 UI）（2026-08-13）

**依据**：`docs/architecture/mvp-scope.md` §三（Agent 主动提问 MVP 能力）+ philosophy §13.x（question_pending 事件契约）

### 背景：架构偏移修正
插件打磨场景原准备用 needClarify 承载主动提问，但排查发现 needClarify 是 **P4 目标槽位补全**（仅非 chat 事件/计划停滞触发），纯 `agent.chat()` 打磨场景永不触发。而 mvp-scope 定义的「主动提问」（askOn 驱动、`[ASK]` 结构化输出、question_pending 事件）内核未实现。经用户决策，**在内核实现完整主动提问**。

### 内核改动
- **AgentChunk** 新增 `question_pending`（questions: slot/question），types.ts
- **AGENT_EVENTS + AgentEventMap** 新增 `questionPending` 事件，eventEmitter.ts
- **AgentLoop**：`AgentLoopOptions.onPendingQuestion` 回调（loop 只解析不感知宿主）；`handleTextResponse` 检测行首 `[ASK] 问题`（`extractAskQuestions`，约定优于检测，可多条）→ 未命中走正常对话流；命中则回调 + yield question_pending + yield paused + return 'paused'
- **Agent**：装配 `loop.onPendingQuestion` → emit `questionPending` 事件 + `requestPause(reason, 'agent')` 触发暂停；用户回答经 resumeExecution → continueAfterPause 注入上下文续跑

### 插件改动
- chatPanel.ts：监听 `questionPending` 事件（替换 needClarify）→ 转发 need_clarify 消息渲染提问输入框；回答提交走 resumeExecution
- protocol.ts：need_clarify / clarify_answer 消息类型（先前已加）

### 实测验证（脚本 `scripts/verifyClarify.mts`）
- LLM 输出 `[ASK] 这个系统主要面向什么用户？` → question_pending 事件 ✅ + paused ✅
- 用户回答「目标用户是中小企业前端工程师」→ resumeExecution 续跑 → 生成完整模块划分 ✅
- 事件序列：question_pending → paused → (回答) → done，全链路跑通

### 现状说明（MVP 边界）
- 主动提问**触发指令注入**由角色包 `askOn`/`userFollowup=ask` 驱动（types.ts 已实现）；插件当前用 skill 而非角色包，实测靠 chat 输入引导输出 [ASK]。插件打磨场景要让提问自然触发，需在 skill 或装配层注入"可用 [ASK] 提问"引导——列入后续产品化增强，不在本次扩大改动。

### 纪律自查
- [x] 单一真理源：复用 needClarify 的 pause/resume 机制，不新建暂停引擎
- [x] 内核只产事件不渲染 UI，插件负责提问框渲染
- [x] 内核 typecheck + 56 测试通过（含 3 个 [ASK] 解析测试）；插件 typecheck 通过
- [x] 全链路真实 LLM 实测跑通
