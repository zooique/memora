## TL;DR

**是否为过度设计**：**是——过度在「实现层」，不是「需求层」。** 同一个 `PlanStepDto` 在 webview 上存在 **3 个投影点**（顶部看板 / 对话内联条 / 折叠块 📍 标签），其中前两个职责重叠、投影规则还不一致；而它要覆盖的增量信息（全局聚合）只占用户信息需求的少数。这一层抽象**已经产生了可观测缺陷**（inline 位置漂移到会话内容底部、点击无反馈），即故障面不是推演出来的，是已经兑现的。

**推荐定位（一句话）**：**砍成单轨，把现有的 `global` 看板升格为固定在对话区之上的「常驻进度条」**——默认一行（N/M + 进度条 + 当前步骤），点击展开锚定浮层看全部步骤；运行时不渲染 inline 轨，仅在完成后于本轮 assistant 块内（**紧随 `.msg-ai-label` 之后**，即架构师 A2 的目标位）留一条静态快照。**全程零新增协议字段。**

## 一、用户信息需求分析（第一性原理）

先不问「UI 该怎么画」，先问：**用户到底在什么时刻、需要知道什么？**

| 时刻 | 用户真正想知道 | 该信息是否必须由「专门的进度 UI」提供 |
|---|---|---|
| 任务刚开始（计划成型） | 它把我要的事拆成了哪几步？拆对了吗？ | 否——LLM 叙述 + 折叠块的 step 分组标题已交代 |
| 执行中（本例 190 秒、514 个过程事件） | 现在在第几步？卡住了没？还要多久？ | 否——流式过程行 + 折叠块顶部 `📍 执行 step-N` 已实时给出 |
| 任务刚完成 | 实际做成哪几步？对照我的要求齐了吗？ | **部分**——报告正文已分节，但「全量清单 + 哪些没做」需翻折叠块 |
| 隔天回看历史 | 同上 | **部分**——同上 |
| 多轮长任务中途插入新指令 | 计划被我/它改过吗？现在还剩几步？ | **是**——对话流里没有「当前全量计划」的快照 |

**一句话抽出真实需求**：用户要的不是「进度条」，而是**一个位置稳定、随时可见的「当前全量计划 + 完成度」入口**。这个需求的成立性来自上表最后两行：**对话流是追加式的、位置漂移的，它无法回答「此刻的全量状态」**。

**对抗式追问：如果这个需求成立，为什么用户观察到的两层 UI 都没解决问题？**
因为两层都犯了「位置不稳定」的错：
- `global` 轨虽然在顶部，但它是 `#messages` 的**子节点**，而 `#messages` 是滚动容器 → 一滚动就消失，等于没固定 `[实锤]`；
- `inline` 轨挂在**会话末尾那个 assistant 块**内；更关键的是，运行时 `.process-flow` 与 `.plan-inline` **共用同一个锚点**（都插到 `.msg-body` 之前），而 `insertBefore` 的**后插者更靠下** —— 于是运行时 DOM 序为 `[角色名][process-flow][inline][正文]`，**inline 被压在流式过程内容之下**；finalize 时 round-block 替换 process-flow → `[角色名][inline][折叠块][正文]`。**用户观察到的「运行时在底部」与「完成后在折叠块和角色名中间」是同一机制的两个相位** `[实锤]`（锚点实现 `chatView.ts:264-276` 与 `ensureProcessFlow` `chatView.ts:778-787` 逐行核对）。

所以用户的抱怨不是「不该有这个 UI」，而是「**这个 UI 没做到它唯一该做的事：位置稳定**」。

**反向检验：如果彻底删掉，用户会失去什么？**（要具体，不要泛泛）
1. 无法一眼回答「还剩几步」—— 只能展开折叠块逐个数。
2. 无法察觉 LLM **中途改写计划**（`task_table_write` append/overwrite）—— 折叠块只反映「发生过什么」，不反映「现在的计划是什么」。
3. 无法察觉 LLM **跳过某一步**就宣称完成 —— 折叠块会「自然地」不出现该步内容，缺口不可见（Claude Code 生态里的真实故障场景）。
4. 任务完成后，除了翻报告正文，没有「清单式」的完成对照物。

> 结论：**这 4 条里只有第 2、3 条是对话流真正覆盖不了的**（第 1、4 条折叠块能替）。也就是说，专用进度 UI 的**边际价值 = 计划漂移与遗漏的对照物**，而不是「看进度」。

- `step_boundary` 事件语义（`title`/`stepId` 含义、边界先于该步内容）= **不变**；B 修法改的是**边界集合与发出位置**（判定由架构师给出，本人核对 `loop.ts:1040-1052` 与 `chatView.ts:948-963` 后采信）

## 三、结论：是否过度设计

### 判定

> **是过度设计 —— 但过度在实现层，不在需求层。**

### 三条判据（不靠态度，靠可核对的量）

| 判据 | 内容 | 结果 |
|---|---|---|
| **A. 覆盖率** | 用户 5 类信息需求中，4 类已有现成来源（报告正文 / 折叠块 / 📍 标签 / 流式行），专用 UI 只补第 5 类（计划漂移对照） | **覆盖缺口 < 20%** |
| **B. 故障面 vs 收益** | 为覆盖这 <20%，引入了：**2 套渲染器** + **2 套 CSS 区块** + **3 个投影点** + **1 个 defer 状态机**（`pendingInlinePlan`）+ **1 套快照语义**。且故障**已经兑现**：运行时 inline 被压在流式过程之下（用户在会话底部看到它）、点击无反馈 —— 用户一次真机使用就撞到两个 | **收益未覆盖故障面** |
| **C. SSOT 一致性** | 两条轨渲染的是**同一份** `PlanStepDto`，却给出**两条不一致的投影**（global 全量可交互 / inline 单行不可交互）。用户必须在两个不同规则的同源视图间切换 | **违反单一真相源，制造认知负担** |

### 一句话

**需求为真（位置稳定的全局聚合入口是对话流覆盖不了的），实现为过度（用两条轨、三个投影点去做一件只需一个入口的事）。** 正确的动作不是「删掉」，而是**合并**。

## 四、推荐方案（单一推荐）

### 4.1 一句话

**单轨「顶部常驻进度条 + 点击展开锚定浮层」，运行时不渲染 inline 轨，完成后仅在对话流内留一条静态快照。**

### 4.2 规格

| 维度 | 推荐 | 理由（含否掉的替代） |
|---|---|---|
| **位置** | 在 `#messages` **之上**新增固定插槽（与滚动容器**同级**、非其子节点；`flex: 0 0 auto` 恒驻留，同既有 `.session-title-bar` `chatStyles.ts:61,66`） | `#messages` 是 `overflow-y:auto` 滚动容器 `[实锤]`，凡其子节点必滚走；新插槽让「固定」成为结构保证，而非样式补丁。**与架构师 A1 修法一致**（`审查-步边界错位与看板位置-20260917.md:167,195`，其标注「纯挂载位置改动，零协议」）。**层序无冲突**（已复核，v2.1 更正）：`chatView.ts:339` 提到的"检查点横幅"**顶部并不存在该元素** —— 全仓 `横幅\|banner` 命中仅 3 处且**全是注释**（`chatView.ts:339,3525`、`chatView.test.ts:1159`）；原顶部活动状态区已迁至**消息流下方、composer 上方**（`chatPanel.ts:2875-2878` 原文"从顶部迁到消息流下方…不再顶置挤占消息区"）；且 `prependStatusBlock`（`chatView.ts:190-196`）**全仓仅 1 个调用点**（`:340` `globalPlanBoard`）→ 该顺序协议今天是**单消费者空协议**。唯一前瞻残留：**若未来在顶部重建状态块，须重新规定其与该插槽的层序** —— 属未来约束，不是当前 A1 的边界条件 |
| **信息密度（收起，默认）** | 一行：`任务进度 2/4` + 4px 进度条 + `🔵 当前：<active step 描述前 N 字>` | 用户原话「默认显示当前的任务」；低噪是不常驻条的底线 |
| **信息密度（展开，点击）** | 锚定浮层：全量步骤（序号 + 描述 + 状态徽标）+ 每步 `stepLog`（相对时间） | 用户原话「点击展开所有任务」 |
| **交互** | **需要交互，且只保留 1 个**：点击条 ↔ 展开/收起浮层 | 见下「被否方案 ④⑤」 |
| **生命周期** | ① 计划非空 → 常驻条显示；② turn 结束 `autoClearPlan` → 常驻条隐藏（`postPlanUpdate` 推空 `steps` 已天然具备该语义 `[实锤]` `chatPanel.ts:2680-2684`）；③ 完成后 → 本轮 assistant 块内**紧随 `.msg-ai-label` 之后**留一条**静态快照**（复用 `plan-inline-done` 语义，但**仅完成时渲染**；落点与架构师 A2 的「过程簇最上」一致，只是不再有运行时相位）；④ 重启后消失（保持不变） | ③④ 是用户**明确认可**的既有行为，保留。注意 ③ 的落点即架构师 A2 的目标位——**本方案让 inline 只存在于该位置、且只以静态形态存在，故 A2 不再是一个需要修的缺陷** |
| **双轨取舍** | **合并为单轨**：运行时只留顶部常驻条；`inline` 降级为「仅完成后的静态快照」，删除其运行时实时刷新分支 | 见下「被否方案 ①②」 |
| **协议影响** | **零新增协议字段**。全部改动落在宿主 webview：复用 `plan_update` 消息 + 既有 `currentPlanSteps` 缓存，仅改挂载位置与渲染条件 | 见 §5 |

### 4.3 为什么是「顶部锚定浮层」而不是「真·modal 弹窗」

用户说的是「点击展开弹窗」。**建议采用锚定 popover，而非 modal**：modal 会遮住对话流，而用户查看进度的场景恰恰是「**一边看它做到哪一步，一边看它在写什么**」。锚在进度条下方的浮层不阻断对话阅读，同时满足「点击展开看全部」。

### 4.4 被否方案及理由

| # | 被否方案 | 否掉理由 |
|---|---|---|
| ① | **只留 inline 轨**（对话流内嵌） | 与核心诉求「固定」直接冲突：它挂在**会话末尾的 assistant 块**内，且位置由「谁先插到 `.msg-body` 之前」的插入顺序决定（运行时被 `.process-flow` 压在下面，finalize 后才上浮到折叠块之上）`[实锤 chatView.ts:264-276, 778-787]` —— 位置随流式状态变化，任何锚点微调都改不了"它在末尾那个块里"这一事实；且**设计上零交互 + 只显示当前步**（`chatView.ts:300-330`），无法满足「点击展开看全部」 |
| ② | **只留 global 轨，但仍在 `#messages` 内** | 等于没固定 —— `#messages` 是滚动容器，滚动即消失 |
| ③ | **底部状态条**（输入框上方 / VS Code 状态栏） | 视觉上离流式输出最近是优点，但：① 会与既有「待发送区 / 插话队列」争位；② VS Code 状态栏是宿主级全局位，多会话会串；③ 顶部是既有「状态栈」语义域（检查点横幅同域），放顶部语义一致 |
| ④ | **全删，连聚合视图也不要** | 失去唯一的「计划漂移/遗漏」对照物（§1 第 2、3 条）；且用户明确提出了诉求 |
| ⑤ | **复刻 Claude Code 的「流内 append 待办表」** | memora 的对话块结构是「过程在上 · 报告在下」（既有协议），流内 append 会与报告正文争夺底部，且历史沉淀里会堆 N 份重复表 —— 与「每多一层抽象多一个故障点」相悖 |
| ⑥ | **展开浮层里加「点击跳转到对话流对应步骤」** | 折叠块已能承担定位；跳转需要 DOM 定位耦合 + 步骤↔DOM 映射维护，收益低于成本 |
| ⑦ | **保留双轨、只做架构师 A2 最小修法**（把 `.plan-inline` 恒插到 `.msg-ai-label` 之后 = 过程簇最上，`审查-步边界错位与看板位置-20260917.md:168,196`） | **架构师明确将此项交产品拍板（`同文:197`「A3/A4 交产品经理，架构侧不预设结论」），我的判断是：不做。** 理由：① 它只治「位置」，不治「同一份 `PlanStepDto` 两个不一致投影」（§3 判据 C）与「零交互、只看得到当前步」（`chatView.ts:300-330`）—— 而后者恰是用户原话「点击没有反应，只能看到当前的运行步骤」的**两个抱怨中的另一个**，最小修法**只解决一半**；② 修完仍是 2 套渲染器 + 2 套 CSS + 3 个投影点 + 1 个 defer + 1 套快照语义，故障面**一分未减**，只是把 A2 这个症状按住了；③ 架构师自己也指出「**合并后 A2 自动消解**」（`同文:197`）—— 即我的方案不额外花成本就覆盖了 A2，而最小修法要多维护一条轨。**净结论：合并单轨是严格更优解**（同等覆盖运行时可见性，且少一层抽象） |

## 五、需要动协议 / 内核吗？（决策成本标注）

| 诉求 | 是否需改协议/内核 | 评估 |
|---|---|---|
| 顶部常驻条、展开浮层、单轨合并 | **否**。纯宿主 webview 改动（挂载插槽 + CSS + 渲染条件） | ✅ 推荐方案**不触碰**内核↔宿主契约 |
| **在 UI 上显示每步的执行角色（`【组长】`）** | **是**。需扩 `PlanStepDto` 增加 `rolePack`，并改 `postPlanUpdate` 映射（`protocol.ts:1038-1049` / `chatPanel.ts:2694-2696`） | **建议不扩。** 真机样本里步骤描述**本身就含角色名**（`"共鸣小说家发言：…"` / `"memora助手发言：…"` `[实锤]`），`rolePack` 在 UI 上是冗余字段；且它只在「会议模式（多角色）」下有语义，为单场景付「内核↔宿主契约变更」成本不划算 |

| 产品 | 形态 | 位置 | 可交互 | 默认密度 | 生命周期 |

**共同的取舍（跨家可实证）**：
1. **没有一家做「两个位置的同构进度」** —— 都不存在双轨。

4. **「可见」靠位置稳定实现**（终端常驻底部 / 顶部 header），**不是靠多渲染几份**。
5. `[实锤·最强论据]` Claude Code 官方文档：**对 Opus 4.8 / Sonnet 5 等强模型，默认不在会话里挂 task 工具**——"Claude tracks multi-step work without a written todo list"。即：当模型足够强时，**外部待办表被视为可选装饰，而非必需品**。这对 memora「任务表是给 LLM 的」这一内核设计是外部佐证，也支持「UI 层应更克制」的判断。

## 七、待用户确认的开放问题

1. **常驻的显示门槛**：任何非空计划（≥1 步）都占一条常驻条，还是只在 ≥3 步（对齐内核 `needsPlanning` 门槛）时出现？本样本是 4 步 / 190 秒的短任务，若每次都常驻，是否反而成了噪音？
