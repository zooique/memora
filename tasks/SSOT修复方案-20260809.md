## §1 根因收敛

7 条症状收敛为 4 个根因。**修根因，不修症状。**

## §2 修复方案

### 批次 1 —— P0 阻断性（必须整批上线）

#### 1.1 【战术止血】P0-1 + P0-2：补 paused 分支并把清理移入 finally

`agent.ts:1052-1069` 改为：

```ts
    try {
      for await (const chunk of loop.continueAfterPause(input, signal)) {
        // 与 processEvent:957-960 对称：内核事实驱动，loop 真正挂起时才翻状态机
        if (chunk.type === 'paused') {
          this.pause(this._pendingPauseReason ?? '用户主动暂停', this._pendingPauseSource);
        }
        yield chunk;
        if (chunk.type === 'text') {
          assistantContent += chunk.content;
        } else if (chunk.type === 'aborted') {
          wasAborted = true;
        }
      }
    } catch (err) {
      if (isAbortError(err)) {
        yield { type: 'aborted', reason: 'User cancelled the conversation' };
        return;
      }
      yield { type: 'error', message: err instanceof Error ? err.message : String(err) };
      return;
    } finally {
      // P0-2：无论正常结束 / abort / error，均释放幂等锁，
      // 否则 requestPause:1387 的 `!== undefined` 检查将永久拒绝后续暂停请求
      this._pendingPauseReason = undefined;
      this._pendingPauseSource = 'user';   // 新 P2：与 abandonPause:1425-1426 对称
    }
```

`agent.ts:953-976` 同步施加相同的 `finally`（删除 `:959` 的裸清除，由 `finally` 统一承担）。

**为什么 `finally` 而非在每个 return 前清**：清理是**退出该作用域的不变式**，而不是某条分支的动作。放 `finally` 使「新增 return 分支」不再有遗漏可能——把正确性从「记得写」变成「结构保证」。

#### 1.2 【战略根治】根因 A：抽取共用流消费器

在 `Agent` 内新增私有生成器，两条路径共用：

```ts
  /**
   * 消费执行流的单一真理源。
   *
   * chat 主路径（processEvent）与续跑路径（continueAfterPause）此前各持一份
   * 逐行同构的消费逻辑，已实证漂移（续跑路径漏了 paused 分支，致状态机不翻转）。
   * 收口于此，新增 chunk 类型只需改一处。
   *
   * @returns 消费结果；`failed` 为 true 时调用方应立即 return（错误已 yield）
   */
  async *#consumeExecutionStream(
    source: AsyncGenerator<AgentChunk, void, unknown>,
  ): AsyncGenerator<AgentChunk, { content: string; aborted: boolean; failed: boolean }, unknown> {
    let content = '';
    let aborted = false;
    try {
      for await (const chunk of source) {
        if (chunk.type === 'paused') {
          // 内核事实驱动：loop 在迭代边界真正挂起时状态机才翻 PAUSED
          this.pause(this._pendingPauseReason ?? '用户主动暂停', this._pendingPauseSource);
        }
        yield chunk;
        if (chunk.type === 'text') content += chunk.content;
        else if (chunk.type === 'aborted') aborted = true;
      }
    } catch (err) {
      if (isAbortError(err)) {
        yield { type: 'aborted', reason: 'User cancelled the conversation' };
      } else {
        yield { type: 'error', message: err instanceof Error ? err.message : String(err) };
      }
      return { content, aborted, failed: true };
    } finally {
      this._pendingPauseReason = undefined;
      this._pendingPauseSource = 'user';
    }
    return { content, aborted, failed: false };
  }
```

调用方（两处对称）：

```ts
// chat 主路径
const r = yield* this.#consumeExecutionStream(
  loop.processEvent(event, recalledMemories, combinedSignal),
);
if (r.failed) return;

// 续跑路径
const r = yield* this.#consumeExecutionStream(loop.continueAfterPause(input, signal));
if (r.failed) return;
```

**复杂度守恒审查（必须回答，否则不许抽）**：
- 消费者数量：2（非臆测的「以后可能」）
- 是否已实证漂移：**是**（P0-1 就是漂移产物）
- 抽象是否引入新故障面：`yield*` 的返回值传递是 TS/ES 原生语义，无额外运行时机制
- 净收益：删除约 40 行重复 → 新增约 30 行单一实现，且消除一整类复发

⇒ 通过。符合 MEMORY 中「2+ 处重复 + 已漂移 = 回溯补抽信号」。

**风险控制**：1.1 与 1.2 可分两个 commit。若 1.2 评审有异议，1.1 独立可上线并已闭合 P0。

### 批次 2 —— P1 SSOT 加固

#### 2.1 根因 C：`restoreFromCheckpoint` 状态恢复收口

`sessionManager.ts:539-545` 改为：

```ts
    // 恢复状态机：先强制归零再按检查点重建。
    // 原实现直接调 triggerError/pause，二者均仅允许从 running 出发
    // （sessionStateMachine.ts:154 / :256），跨会话恢复时若状态机残留 paused/error
    // 将静默失败（返回值未被检查）→ 检查点 status 与状态机分叉。
    this.stateMachine.resetToRunning();
    if (checkpoint.status === 'error' && checkpoint.error) {
      const t = this.stateMachine.triggerError(checkpoint.error.cause);
      if (!t.allowed) logger.error({ transition: t }, '检查点错误态恢复失败，状态机与检查点分叉');
    } else if (checkpoint.status === 'paused') {
      const t = this.stateMachine.pause('从检查点恢复', 'system');
      if (!t.allowed) logger.error({ transition: t }, '检查点暂停态恢复失败，状态机与检查点分叉');
    }
    // running 状态由 resetToRunning() 承担，无需额外操作
```

**要点**：
- `resetToRunning()`（`sessionStateMachine.ts:279`）已存在，设计定位就是「跳过校验的强制清理」——恢复场景正是其适用面，无需新增 API
- 返回值必须检查：静默失败是本类 Bug 的**传播机制**，不是附带问题

#### 2.2 根因 D：抽取原子写原语（**范围严格限定**）

新增 `src/utils/atomicWrite.ts`（单一真理源）：

```ts
/**
 * 原子写文件：先写同目录临时文件，再 rename 覆盖目标。
 *
 * 适用：内容为「唯一真理源」且损坏不可重建的文件（设定记忆、注册表、向量索引）。
 * 不适用：
 *   - 锁文件（需排他创建语义，rename 会覆盖他人的锁）
 *   - 面向用户的文件写工具（rename 更换 inode，破坏硬链接/软链目标/文件监视器）
 *
 * 临时文件与目标同目录，确保 rename 不跨设备（跨设备 rename 会 EXDEV 失败）。
 */
export async function atomicWriteFile(filePath: string, content: string): Promise<void> {
  const tmpPath = `${filePath}.tmp`;
  await writeFile(tmpPath, content, 'utf-8');
  await rename(tmpPath, filePath);
}
```

接入范围（**仅 3 处**）：

| 文件 | 改动 |
|---|---|
| `src/memory/vectorStore.ts:273-275` | 改为调用 `atomicWriteFile`（**先改它**——它是既有实现的来源，先让真理源落到公共原语上，避免"新原语 + 旧实现"并列） |
| `src/memory/store.ts:88` | `await atomicWriteFile(filePath, content)` |
| `src/memory/projectRegistry.ts:272` | 同步语境，需评估改异步或提供 `atomicWriteFileSync` 同名孪生（见下） |

**`projectRegistry` 的取舍**：`:272` 是 `writeFileSync`。两个选项——
- (a) 提供 `atomicWriteFileSync`：与异步版并列两份实现，违背单一真理源
- (b) 将调用点改异步：需追调用链，改动面不可控

⇒ **建议本批次只做 (a) 的替代方案：`projectRegistry` 暂不接入，单独立项**。理由：注册表损坏的后果（项目列表丢失）可通过重新扫描重建，**不满足「不可重建」判据**，未达到必须承担并列实现代价的门槛。避免为一致性而扩张。

### 批次 3 —— P2 契约收口

#### 3.1 `goalDriftDetected` 契约二选一（**禁止维持现状**）

现状：内核发事件、宿主零监听、注释承诺「宿主 UI 决定」。这是 MEMORY 已记录的「契约未兑现」类型，修法必须二选一：

- **选项 A（兑现）**：宿主 `chatHandlers.ts` 接线该事件 → IPC 转发 → 渲染层对 `minor` 级漂移展示非阻塞提示条（复用既有 `proactiveBanner`）。适合认为「用户应知晓目标偏移」。
- **选项 B（收窄）**：删除 `sessionManager.ts:788` 中"宿主 UI 决定是否暂停"的承诺，改为「内核对 `drift` 级自兜底暂停；`minor` 级仅记录日志」，并同步收窄事件文档。适合认为 `minor` 漂移不值得打扰用户。

**倾向 B**：`minor` 按定义即「轻微偏移」，为其新增一条 IPC + UI 通道，收益覆盖不了复杂度（复杂度守恒）。且内核对真正危险的 `drift` 级已有兜底。

若批次 1.2 落地，此项**自动消失**（清理收口于 `#consumeExecutionStream` 的 `finally`）。仅需补 `cancelPauseRequest:1408` 一处：
