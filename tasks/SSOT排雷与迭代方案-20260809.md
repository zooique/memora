### 1.1 雷C 的修正详情（初审误判）

初审判定 `pauseMeta` 整体为死代码，**这是错的**。实证：

- **消费方存在且在宿主关键路径上**：
  - `hosts/.../electron/main.ts:579-580` 读 `checkpoint.pauseMeta?.reason / ?.source`
  - `hosts/.../ipc/chatHandlers.ts:194-202` 读 `pauseMeta?.phase / ?.reason / ?.source` 下发渲染层
  - `hosts/.../panels/taskTablePanelManager.ts:307` 分支 `ctx.pausePhase === 'requesting'`
- **真正死的是相位取值**：全仓 `setPauseMeta` 唯一生产写入点为 `agent.ts:1783`，硬编码 `phase: 'suspended'`。`'requesting'` **从未被写入**。

由此推出两条**跨层死分支**：

1. `sessionManager.shouldPauseAtBoundary()`（:947-953）第二行 `phase !== 'requesting'` 恒真 → 函数恒返回 `false`，且自身零调用点 —— 双重死代码。
2. 宿主 `taskTablePanelManager.ts:307` 的 `'requesting'` UI 分支**永不可达**。

**结论修正**：`PauseMeta.phase` 的联合类型（`types.ts:303`）承诺了两阶段语义，实现只兑现了一半。这不是「死字段」，是**契约与实现不一致**——比死代码更危险，因为宿主按契约写了 UI。

## 二、P0 缺陷链（唯一必须立即修的项）

排雷过程中确认了一条完整、可复现、有真实副作用的缺陷链。这是本次审查最重的发现。

**时序**（`sessionManager.pause()` :540-565）：

1. `stateMachine.pause()` 翻状态为 PAUSED
2. `createCheckpoint()`（:544）→ 白名单重建 → `roundLog` / `completedToolCalls` / `pauseMeta` **被清空**
3. `persistCheckpoint()`（:356）→ **残缺快照落盘**
4. `loop.onPaused`（`agent.ts:1780-1789`）→ `setPauseMeta()` 补写 `pauseMeta`，但 `setPauseMeta`（:932-936）**只写内存不落盘**

**后果**：

| 字段 | 内存态 | 磁盘态 | 影响 |
|---|---|---|---|
| `pauseMeta` | 步骤 4 补回 | **永远缺失** | 宿主 `main.ts:579` 回落兜底文案「已暂停（重启恢复）」 |
| `completedToolCalls` | **永久丢失** | 永久丢失 | `hasToolExecuted`（`agent.ts:1734`）恒 false → **非幂等工具重复执行**；`compensateAllNonIdempotent`（:1167）过滤空数组 → **补偿空转** |
| `roundLog` | **永久丢失** | 永久丢失 | 宿主任务表历史归零 |

**为什么测试没抓到**（测试盲区，同属根因）：
- `uninterruptedWorkflow.test.ts:494-495` 在 `completeRound()` 后**直接**断言 `roundLog`，不经 pause 往返
- `:867` 的 `completedToolCalls` 是手工 fixture，`:1507` 只做查询

即：测试验证了「字段能写」，从未验证「字段能活过一次 pause」。**断言点与真实生命周期不对齐**。

## 三、迭代任务方案

### P0 — 检查点写入语义统一（阻塞级，必须先做）

**T0-1｜`createCheckpoint` 改为合并语义**
- 文件：`src/agent/managers/sessionManager.ts:332-353`
- 方案：废除字面量整体重建，改为 `this.checkpoint = { ...this.checkpoint, ...patch }` 形态；仅对确需重算的字段（`status` / `hotMemory` / `truncatedCount` / `lastHeartbeat`）显式覆写。
- 第一性原理：**重建即隐式白名单**——任何新增字段默认丢失，除非有人记得补。合并才是「快照」语义的正解。
- 验收：新增测试「pause → resume 往返后 `roundLog`、`completedToolCalls`、`pauseMeta` 全部保持」。

**T0-2｜落盘收口为单一入口 + 脏标记**
- 文件：`sessionManager.ts`（`persistCheckpoint` :367-375、`setPauseMeta` :932-936、`completeRound` :906-925、`recordToolCall` :1009-1012、`recover` :707-728）
- 方案：所有检查点内存写点统一置 `this.checkpointDirty = true`；在 pause / resume / recover / 回合边界四个语义边界 flush。禁止任何写点绕过。
- 验收：grep 断言——`this.checkpoint.X =` 形式的赋值全部落在标脏的方法内；`recover()` 后磁盘态 `error.recovered === true`。

**T0-3｜`recover()` 补落盘**
- 文件：`sessionManager.ts:707-728`
- 方案：`result.allowed` 分支内追加 flush。
- 理由：`stateMachine.recover()` 校验 `checkpoint.error.recovered === true`，而该标记只活在内存 → 崩溃重启后恢复链**永久断裂**。
- 验收：模拟「进入 ERROR → recover → 进程重启」，重启后会话可继续。

### P1 — 契约与实现对齐

**T1-1｜`PauseMeta.phase` 二选一：兑现或收窄**
- 文件：`types.ts:303`、`sessionManager.ts:947-953`、`agent.ts:1783`、`hosts/.../taskTablePanelManager.ts:307`
- 方案 A（推荐，复杂度守恒）：把 `phase` 收窄为 `'suspended'`，删除 `shouldPauseAtBoundary()`，同步删宿主死分支。
- 方案 B：在 `requestPause()`（`agent.ts:1308-1314`）写入 `phase: 'requesting'`，并把 `shouldPauseAtBoundary()` 接进 loop 边界判断，取代裸布尔 `loop.pauseRequested`。
- 判据：若近期无「定点步骤暂停」需求 → 选 A。**不允许维持现状**——契约悬空会持续误导宿主。
- 验收：`'requesting'` 在全仓要么有写入点+消费点，要么彻底消失。

**T1-2｜暂停超时归档路径合流**
- 文件：`sessionManager.ts:1238-1267`（运行时）与 `:399-421`（启动时）
- 方案：抽取 `markSessionTimedOut(sessionId)` 单一真理源，两条路径同时填 `_pauseTimedOutSession` 并 emit。
- 附带：清理 `:412` 的 `sessionId.split('-').length >= 4` 魔法判据——用显式标记字段替代字符串形状猜测。
- 验收：运行时超时后 `consumePauseTimedOutSession()` 能取到会话，归档被触发。

**T1-3｜关系侧车删除守门人**
- 文件：`src/memory/userProfile.ts:271-273`、`:385-388`
- 方案：所有 `index.delete(id)` 前置调用 `relationStore?.removeRelationsByMemoryId(id)`；或上收为 `deleteMemory(id)` 统一入口，禁止外部直接触碰 `index`。
- 验收：删除带关系的记忆后，关系库中该 id 的边数为 0。

### P2 — 悬空语义清理

**T2-1｜`goalVersion` 与漂移事件：闭环或删除**
- 文件：`sessionManager.ts:751/762`、`agent.ts:1595`、`eventEmitter.ts:41/175`
- 两个独立问题：
  1. `applyResolvedDelta`（`agent.ts:1585-1608`）对 **P2 记忆延续值**也调 `updateGoal` → `goalVersion` 每轮 chat 递增，退化为轮次计数器并每轮误报 drift。**修复：仅在目标真实变更时递增。**
  2. `goalDriftDetected` 零监听方 → 要么宿主接上（暂停+确认 UI），要么连同 `goalVersion` 一并删除。
- 验收：连续多轮 chat 不改目标时 `goalVersion` 保持不变。

**T2-2｜ERROR 态定性**（2026-08-09 已落地，定性=保留+标注）
- 文件：`sessionStateMachine.ts`、`agent.ts`
- 复核结论：`triggerError` 生产内部零运行时调用，但 **ERROR 态不可删**——检查点恢复回填是活路径（`loadPersistedCheckpoint` sessionManager.ts:481 / `restoreFromCheckpoint` :541，磁盘/外部 checkpoint status='error' → 翻 ERROR → recover() 强制校验），它是「崩溃残留 → 恢复前强制校验」语义的载体。
- 处置：**保留 API + 代码内标注触发面**（sessionStateMachine 类头 + agent.triggerError 注释），不做行为变更。运行时异常（LLM 超时/工具失败）走 `yield { type: 'error' }` 事件流（agent.ts:540/979/1057），不翻状态机；若未来要接线需产品决策。
- **修正方案文档原建议**：`resetToRunning()` **不删**——它是暂停超时清理的活调用（sessionManager.ts:1354，清理后状态机必须回 running），与 ERROR 态无关。
- 验收：ERROR 恢复链端到端测试已存在（uninterruptedWorkflow.test.ts triggerError/recover 段 + sessionCheckpointLifecycle）；触发面文档化。

**T2-3｜`autoConfigRefiner` 去重与 ID 生成**
- 文件：`src/agent/managers/autoConfigRefiner.ts:175`
- 方案：`analyze()` 生成建议前查已有 rule；ID 改为内容哈希，禁止 `captured.slice(0,10)` 直构。
- 验收：同一偏好重复触发不产生重复 rule。

### P3 — 防回归基础设施

**T3-1｜检查点字段生命周期测试套件**
- 新增 `sessionCheckpointLifecycle.test.ts`：对 `SessionCheckpoint` **每个字段**参数化断言 pause→persist→load→resume 全链保持。
- 价值：这是唯一能防止 T0-1 类缺陷复发的结构性手段。字段新增时测试自动要求补断言。

**T3-2｜内核 Rule 写 API 的旁路防护**（2026-08-09 已落地，定性=契约文档化）
- 对抗式审查否决两种原方案形态：
  - **显式警告**：宿主 `configFileSyncer` 是唯一消费者且已正确排序（先文件后 SQLite）——每次合法调用都会误报，有害。
  - **文件同步器注入**：无消费者需要注入（宿主已有自己的文件层）→ 死参数；且违背 ConfigManager「不直接操作文件」的类设计原则（configManager.ts:15），与宿主双写。
- 落地形态：**契约文档化**——configManager.ts 类头「文件层契约」总述（文件=真理源、SQLite=运行时索引、重启自愈、旁路写不持久）+
  `deleteRule/updateRule` JSDoc 补「文件层前置条件 + 重启复活风险」。当前旁路零生产调用者，防护价值=防未来踩坑，零行为变更。
- 验收：写 API 的 JSDoc 明确「先文件后本方法」，类头说明因果链。
