# 诊断：模型输出「文本形式 tool_call」→ 内核静默失败 + 宿主渲染为空白

> 诊断日期：2026-09-14 · 现场：`F:\用户目录\Desktop\互动叙事平台方案\.memora`（用户真实测试）
> 方法：**读原始落盘记录 + 读码 + 脚本复现渲染链路**，不采信推断

---

## 〇、现场（原始证据，未加工）

**用户消息**（唯一一条）：
```
理解项目然后，总结一个白话版文档
```

**LLM 实际输出**（`round-1789353127177.json` → `assistantMessage.content`）：
```xml
<tool_call>
<function=list_dir</parameter>
</function>
</tool_call>
```

**这一轮的账面状态**：
| 字段 | 值 | 问题 |
|---|---|---|
| `status` | `complete` | 记为**正常完成** |
| `metrics.success` | `true` | 记为**成功** |
| `metrics.toolFailureCount` | `0` | 记为**无工具失败** |
| `metrics.tokenIn / tokenOut` | 4721 / **23** | 只吐了 23 token |
| `metrics.durationMs` | 4683 | — |
| `processEvents` | meta / thinking / thought ×16 / thinking / metrics | **零 tool 事件** → 工具从未执行 |
| `sessions.json` → `messageCount` | **0** | 但 `roundIdsStore` 有 1 轮（应为 2） |

**用户体感**：「只思考，然后就结束了」——思考流有内容，正文区**空白**。

---

## 一、因果链（4 层，逐层实锤）

### 第 1 层 · 触发源：模型没走原生 function calling，改吐文本

模型 `mimo-v2.5-pro`（`api.xiaomimimo.com` 中转）**没有通过原生 `tool_calls` 字段**返回调用，而是**按 prompt 的文本指示**输出了一段 XML 文本；且格式**畸形**：

- 标签名未闭合：`<function=list_dir</parameter>`（`list_dir` 被当**属性名**消费，`=` 后才接 `</parameter>`）
- **完全没有参数**（`list_dir` 缺 `path`）
- 混入了本不该出现的 `</parameter>`

### 第 2 层 · 根因：内核**宣告了文本协议却没实现解析器**

内核**同时**做两件事，方向矛盾：

| 位置 | 内容 |
|---|---|
| `loop.ts:1749`（`buildSystemPrompt`） | `prompt += "\n\n## 可用工具\n\n你可以通过 tool_call 调用以下工具：\n" + toolDescs` ← **文本协议宣告** |
| `loop.ts:1803-1812`（`buildChatOptions`） | `baseOptions.tools = […{type:'function', function:{name, description, parameters}}]` ← **原生协议** |

- 对**支持原生 function calling** 的 provider：模型走 `delta.tool_calls` → `openaiCompatible.ts:397-414` 正常累积解析。
- 对**不支持 / 中转不透传 `tools`** 的 provider：模型只能**照 prompt 的文本指示**输出 → 而内核**没有文本解析器**。

**实锤**：全库 `grep` 文本 tool_call 相关实现，**仅 1 处注释、零实现**：
```
src/llm/provider.ts:37: /** 结构化输出约束：Provider 不支持时静默跳过，fallback 到纯文本 tool_call */
```
`src/` 内 `TOOL_CALL_RE` / `parseTextToolCalls` / `extractToolCalls` 等**全部零命中**；`openaiCompatible.ts` 只处理原生 `delta.tool_calls`。

→ **「文本 tool_call」这条路径被 prompt 宣告了，却从未实现** —— 这是根因。

### 第 3 层 · 放大器：静默失败（账面全绿）

解析不出工具调用 → 那段文本成为**普通 assistant 内容** → 内核判定「无工具调用」→ turn 正常收尾：
`success: true` + `toolFailureCount: 0` + `status: complete`，**零告警、零兜底、零重试**。

→ 一个「AI 想干活、但一步没干成」的轮次，被系统记录为**成功**。

### 第 4 层 · 显形器：宿主渲染把畸形标签吞成**空白**

渲染链路（`chatView.ts:2133`）：`body.innerHTML = renderMarkdown(text, sanitize)`
→ `renderMarkdown` = `marked.parse()` → `DOMPurify.sanitize()`（`helpers/renderMarkdown.ts:57-61`、`helpers/sanitizer.ts:25`）

**实锤（脚本复现，用真实 marked）**：
```
marked.parse('<tool_call>\n<function=list_dir</parameter>\n</function>\n</tool_call>')
  → "<tool_call>\n<function=list_dir</parameter>\n</function>\n</tool_call>"   // 原样透传为 HTML
剥离全部标签后的剩余文本 → ""                                              // 空
原文按标签切分后的文本片段 → []                                            // 零文本节点
```
- `marked` 不转义原始 HTML（`renderMarkdown.ts` 无任何 escape 调用）
- DOMPurify 用默认白名单，未知标签被移除而 `KEEP_CONTENT` 只保留**文本内容**
- 而这段输出**全部是标签、零文本节点** → **移除后什么都不剩** → 渲染为空白

**宿主侧另证**：`grep tool_call` 在 `hosts/memora-vscode/src` 的**生产代码零命中**（仅测试文件）→ 宿主对 `<tool_call>` 文本**无任何识别或特殊处理**。

## 二、分层归因

| 层 | 性质 | 是否缺陷 | 说明 |
|---|---|---|---|
| 1 模型/中转 | 触发源 | 半个 | 模型输出畸形 —— 但**内核的双重宣告把它从"可能"变成"必然"** |
| 2 内核 · 协议自相矛盾 | **根因** | ✅ **真缺陷** | 文本协议被宣告却未实现 → 该路径必然静默失败 |
| 3 内核 · 静默失败 | **放大器** | ✅ **真缺陷** | 账面无任何异常信号；「想干活但没干成」被记为成功 |
| 4 宿主 · 净化吃空 | 显形器 | ⚠️ 交互副作用 | DOMPurify 的职责是安全不是可用性；但**把不可理解的内容变成空白**比显示乱码更糟（乱码至少可诊断） |

**一句话**：**模型吐了一段"它以为的"工具调用，内核不认识、又不报警，宿主把它擦成空白** —— 三层都没兜住，于是「只思考然后结束」。

---

## 三、修复建议（分层，按 ROI）

### 立即（止血，成本低）
1. **宿主渲染兜底**（1 行判断）：渲染后若 `body` 无可见文本节点（或剥离标签后为空）但原文非空 → **回退显示转义后的原文** + 一行提示（如「模型输出无法解析」）。
   - 效果：**此类问题当场可见**，用户能直接反馈原始输出，而不是看到空白。
   - 定位：`chatView.ts:2133 / 2743 / 2821` 三处 `renderMarkdown` 注入位。

### 短期（治根，需设计）
2. **内核：工具调用意图识别 + 兜底**。当无原生 `toolCalls` 但正文疑似工具调用（含 `<tool_call` / `<function=` 等标记）时，**至少产出可观测信号**（warn / metrics 计数 / 事件），不要记为 `success: true`。
3. **内核：二选一，去掉协议自相矛盾**（关键决策）：
   - **A. 补文本解析器**：实现 `parseTextToolCalls(text)`（覆盖 `<function=NAME>...</function>` / 参数块），使其真正可用 → 对不支持原生 FC 的 provider 完整可用；
   - **B. 撤掉文本宣告**：prompt 不再说「你可以通过 tool_call 调用」，让不支持原生 FC 的 provider 明确「无工具能力」，而不是诱导它吐畸形文本。
   - **倾向 A**（本地模型/Ollama 场景正是「不支持原生 FC」的重灾区，而本项目明确要支持本地 LLM 零网络闭环）。

### 中期
4. **provider 能力探测**：宿主配置里标注该 provider/model 是否支持原生 function calling，内核据此在「原生 / 文本」两条通道间**确定性地**选一条，而不是两条都发。
5. **修 `messageCount` 派生不一致**（见 §四）。

## 四、次级发现（独立于主链）

**`messageCount` 派生缓存与真源不一致**：
- 真源 `roundIdsStore[会话]` = 1 轮；`messageCount = roundIds.length * 2` 应为 **2**，实际落盘 **0**。
- `sessions.json` 内部自相矛盾：同文件里 `metas[x].messageCount = 0` 而 `roundIdsStore[x].length = 1`。
- 落点：`hosts/memora-vscode/src/extension/host/sessionStore.ts` 存在**两条写 meta 的路径**——`:220` 正确计算（`roundIds.length * 2`）、`:249` 用 `existing?.messageCount ?? 0`（新建时为 0 且未回填）。
- 性质：派生缓存未从真源同步（SSOT 违例形态）。若界面用 `messageCount` 判空，会**把有内容的会话显示为空**。
