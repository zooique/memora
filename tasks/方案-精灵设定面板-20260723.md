# 方案-精灵设定面板

> **创建时间**：2026-07-23
> **状态**：方案评审期（待确认后进入执行）
> **战略来源**：用户提出"角色/rules/skills 三类设定应统一管理，当前仅 skills 在设置面板且管理残缺（无删除/编辑），persona 只能切换无 CRUD，rules 完全无管理入口"

## 一、战略定位：为什么是"设定"独立面板

### 1.1 核心矛盾

当前 persona/rules/skills 三类"人写的设定"管理入口**分散且残缺**：

| 类型 | 当前入口 | 缺失能力 |
|------|---------|---------|
| persona | 输入区下拉切换 + 命令面板切换 + 设置面板精灵 tab（仅匹配模式配置） | 无 CRUD（无法在 UI 新增/编辑/删除角色定义） |
| rule | **完全无管理入口**（仅记忆面板筛选维度） | 无 CRUD + 无热重载（reloadConfig no-op） |
| skill | 设置面板技能 tab（仅查看 + 拖入安装） | 无删除/编辑/禁用 |
| guardrail | 无管理入口 | 无 CRUD + 不可热重载 |

用户验证发现：三类目录文件能被正常加载（persona/skill 走 Manager 扫描，rule 走 MemoryLoader 启动扫描），但**没有任何 UI 入口让人创建和管理这些文件**——这是设定的核心缺口。

### 1.2 "设定" vs "记忆"的二分法

| 维度 | 设定面板 | 记忆面板 |
|------|---------|---------|
| 来源 | 人主动写的 | 系统自动记的 |
| 内容 | persona / rule / skill / guardrail | insight / profile / content / session... |
| 性质 | 输入（给系统的指令/人格/规则） | 输出（系统观察记录的经验/事实） |
| 真理源 | 文件层（configDir/*.md） | 数据库层（memora.db） |

二者是"我告诉系统成为什么" vs "系统记住了什么"的互补关系，不应混在一处。强行塞进记忆面板会让"我配置的角色"和"系统记的事"互相干扰，掩盖心智差异。

### 1.3 命名说明

- **侧边栏入口名**："设定"（4 字以内，与"记忆"对仗）
- **面板标题/空状态文案**："精灵设定"（明确归属精灵宿主，与项目级 `.memora/rules/` 区分）

## 二、信息架构

### 2.1 入口位置

左侧边栏顶部高频区，顺序：对话 / 记忆 / **设定** / 剪贴板

- 位置选择依据：设定与记忆相邻，体现"设定→记忆"的因果关系（设定是输入，记忆是输出）
- 图标：`#icon-sliders`（齿轮+滑块组合，区别于设置的纯齿轮 `#icon-gear`）
- 快捷键：Ctrl+4（剪贴板顺移为 Ctrl+5，设置顺移为 Ctrl+6，需同步更新 `PANEL_SHORTCUT_MAP`）

### 2.2 面板内结构

```
设定面板
├── Tab: 角色 (persona)
│   ├── 列表区（1 文件 1 条记录）
│   │   └── 每条：name + description + keywords 标签 + 激活状态 + 编辑/删除按钮
│   ├── 空状态引导（"创建你的第一个角色" + 模板按钮）
│   └── 编辑器（frontmatter 表单 + 正文 textarea + 预览）
│
├── Tab: 规则 (rule)
│   ├── 子分组: 普通规则（可 CRUD）
│   │   └── 每条：name + 内容预览 + 编辑/删除按钮
│   ├── 子分组: 护栏规则（guardrail，只读）
│   │   └── 每条：name + "护栏·需重启生效" 徽章 + 灰色不可编辑
│   └── 项目级规则（只读，灰色标记"项目级"）
│       └── 来源：<projectPath>/.memora/rules/
│
└── Tab: 技能 (skill)
    ├── 列表区
    │   └── 每条：name + keywords + trigger + layer 标签（全局/项目）+ 编辑/删除按钮
    ├── 安装入口（保留拖入 .md 安装能力）
    └── 编辑器
```

### 2.3 编辑器设计（面板内编辑器，用户已选）

**统一编辑器组件**（三类共用）：

- **frontmatter 表单区**：结构化字段输入（name/keywords/description/trigger 等），按类型显示不同字段
  - persona：name / description / keywords / traits.*（数值滑块）
  - rule：name / description
  - skill：name / description / keywords / trigger
- **正文区**：Markdown textarea + 实时预览切换
- **保存按钮**：校验 frontmatter 合法性 → 序列化为 .md → 写入 configDir → 触发热重载 → 广播 CONFIG_FILES_CHANGED

### 2.4 设置面板瘦身（迁移项）

| 迁移项 | 来源 | 目标 |
|--------|------|------|
| 设置面板"技能"tab | `settingsPanelManager.ts` renderSkills | 设定面板"技能"tab（保留拖入安装） |
| 设置面板"精灵"tab 的角色配置区 | `cfg-persona-mode` / `cfg-default-persona` | 设定面板"角色"tab 顶部（匹配模式开关） |

设置面板回归纯系统配置：大模型 / 精灵（行为开关）/ 项目 / 画像 / 审计 / 帮助。

## 四、排雷记录（六条心智模型逐条标注）

### R1 · rule 热重载缺失（🔴阻塞 → 已解决）

- **心智模型**：向源头追溯 + 绕过而非修补
- **根因**：内核设计假设 rule 是"运行时通过 addRule() 注入"，但 MemoryLoader 启动时又从文件加载——设计假设与实现矛盾
- **方案**：K2 扩展 reloadConfig('rule') 从 no-op 改为重新扫描，不叠加 fallback 修补
- **不做**：不在设定面板提示"需重启生效"（补丁思维），而是修根因

### R2 · guardrail 不可热重载（🔴阻塞 → 绕过）

- **心智模型**：绕过而非修补 + 方案复杂度匹配
- **根因**：guardrailRules 是 AgentLoop readonly 数组，rebuildComponents 对话中抛错
- **方案**：设定面板内 guardrail 只读展示，不提供编辑/删除入口
- **不做**：不实现 rebuildComponents 排队调用（复杂度 vs 收益不匹配）

### R3 · Manager 缺 delete API（🔴阻塞 → 已解决）

- **心智模型**：向源头追溯
- **根因**：ConfigManager/PersonaManager/SkillManager 设计初期只考虑 add，未预留 delete
- **方案**：K1/K3/K4 内核补全 delete API，同步操作 文件 + SQLite + 内存

### R4 · 双路径并存（🟡需设计 → 已解决）

- **心智模型**：向源头追溯
- **根因**：configDir/（skillInstaller 写入）与 dataDir/（FileStore 写入）两套目录互不同步
- **方案**：H3 设定面板统一走 configDir/，dataDir/ 作为 FileStore 内部路径不暴露

### R5 · IPC 治理阈值（🟡需设计 → 已规避）

- **心智模型**：方案复杂度匹配
- **根因**：119 通道接近 130 阈值，完整 CRUD +15 通道会触发
- **方案**：精简方案 9 通道（create/update 合并为 save，guardrail 不新增通道），129 < 130
- **后续**：下次新增任何通道即触发治理评估，合并相似通道

### R6 · 无主→渲染广播通道（🟡需设计 → 已解决）

- **心智模型**：识别不可逆损失点
- **根因**：CRUD 后无机制通知渲染层刷新，personaPanelManager/commandPaletteManager/settingsPanelManager 都不会自动刷新
- **方案**：I4 新增 CONFIG_FILES_CHANGED 广播通道，U8 渲染层监听分发

### R7 · 内核零依赖认知修正（🟢可规避）

- **心智模型**：怀疑前提
- **根因**：用户认知"内核零 native 依赖"不准确，实际 src/ import 了 node:fs
- **方案**：文件 CRUD 在内核层暴露 API（K1-K4），宿主层调用内核 API + 操作文件
- **注**：project_memory.md 中"11 个生产文件直接 import node:fs"的记录应更新为"内核可使用 Node 内置模块，零依赖指 dependencies 为空"

## 七、决策记录

| 决策点 | 选择 | 依据 |
|--------|------|------|
| 面板归属 | 独立"设定"面板（不塞进记忆面板） | 设定 vs 记忆的二分法，心智差异不应混合 |
| 入口位置 | 记忆下方（顶部高频区第 3 项） | 设定与记忆相邻，体现因果关系 |
| 编辑方式 | 面板内编辑器（frontmatter 表单 + 正文 textarea） | 体验最佳，闭环 |
| rules 归属 | 纳入设定面板管理 configDir/rules/ 文件 | 底层不动（仍走 MemoryLoader + source='rule'），面板管来源文件 |
| rule 两层 | 只管 Agent 级 + 项目级只读 | 项目级文件属于项目仓库，不应被精灵 UI 修改 |
| guardrail | rules tab 内子分组只读展示 | 不可热重载，编辑风险高，只读满足可见性 |
| rule 热重载 | 内核补全 reloadConfig('rule') CRUD | 修根因，不叠加"需重启"补丁 |
| IPC 方案 | 精简方案 9 通道 + 1 广播 | 129 < 130 阈值，create/update 合并为 save |
