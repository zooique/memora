## 二、根因收敛

10 项收敛为**三条工序级根因**：

1. **入口闸门不同构**（F5-1-1 / F5-1-2）：三条执行入口（chat / processEvent / resumeExecution）已共用 `consumeExecutionStream` 收口流消费，但**锁获取未收口**——一个在锁内、一个在锁外、一个没有锁。同类修复（T5）只打了一条路径，正是上一轮报告结尾警告的「修复不对称」在并发面的具体化。
2. **侧车无生命周期 / 归属未定**（F5-2-1 / F5-2-2）：append-only 结构缺封顶；checkpoint 与 session 的所属关系从未被定义，合并语义对 fork 是功能、对 switch 是污染。
3. **契约文档化而非结构化**（F5-2-3 / F5-3-1 / F5-3-2）：迁移占位、两段式写、误导性注释——不变式只存在于注释里，违反无信号。

**工序级防御**（建议进评审清单）：任何「多入口共享副作用」的修复，评审必须回答「所有入口都改了吗？用 grep 证明」。F5-1-1/F5-1-2 两项均可被此条拦住。

## 三、分批迭代任务设计

> 每条任务含：根因 / 修复草图 / 防回归测试 / 边界声明。
> 质量门铁律（沿用前三轮）：`npm run typecheck` + `npm run lint` + `npm test`；
> **每条防回归测试修复前必须红、精确还原复绿**；PowerShell surgical 提交。

### P0 —— 状态分叉 / 并发竞态

#### T1（F5-1-1 + F5-1-2）执行入口闸门收口

- **根因**：锁获取未收口——chat 锁外翻状态机；resumeExecution 完全无锁。
- **修复草图**：
  - **chat()**（agent.ts:420-456）：将 `autoResumeIfPaused()` 移入 `acquireChatLock` 之后的 try 块，与 processEvent:840-846 完全同构。失败处置保留 chat 现有语义（yield error chunk + return，finally 释放锁）。原 :427 的错误文案不变。
  - **resumeExecution()**（agent.ts:1005-1088）：入口加 `acquireChatLock(signal)`，整体包 try/finally 释放。error 态只读检查（:1006-1018）可留在锁前；`resume()` 翻转（:1022）及之后必须在锁内。注意 finally 中同时释放锁 + cleanupExternalSignal，与 chat 同构。
  - **不引入**第三个封装函数「runWithLock」：当前仅两处差异（失败处置语义不同：throw vs yield），强行抽象会重蹈「两份消费逻辑漂移」覆辙；收口动作是「把同样的三行代码放到同样的位置」。
- **防回归测试**（`__tests__/uninterruptedWorkflow.test.ts`）：
  1. 状态机置 paused + mock chatLock 为 busy → 迭代 `chat()` → 抛 chatBusyError 且 `stateMachine.status === 'paused'`（当前翻成 running → 红）。
  2. resumeExecution 进行中（mock continueAfterPause 挂起）→ 并发调 `chat()` → 抛 chatBusyError（当前两者并发跑 → 红）。
  3. 守卫绿测：PAUSED + 单线程 chat → 自动恢复且正常产出文本（现有行为不回归）。
- **边界**：不改 `autoResumeIfPaused`（command 不自动恢复语义保留）；不改 `consumeExecutionStream`；`forceReleaseChatLock` 的 token 校验路径不受影响（finally 复用 myToken 校验模式）。

### P1 —— 无界增长 / 跨会话污染

#### T2（F5-2-1）completedToolCalls FIFO 封顶

- **根因**：append-only 无上限；检查点以单 TEXT 列全量覆盖存储，序列化代价随会话寿命线性增长。
- **修复草图**：
  - `AGENT_CONSTANTS` 增 `COMPLETED_TOOL_CALLS_MAX: 48`（附注释：outbox 判据只需近期窗口；48 ≫ 单回合工具调用上限 × 若干回合）。
  - `logToolExecution`（sessionManager.ts:1411-1419）push 后截断，**截断须保补偿安全**：
    ```
    若超长：优先丢弃「幂等 或 已补偿（compensatedAt 为 number）」的最早记录；
    非幂等未补偿记录永不丢弃（宁可检查点偏大，不可漏补偿）。
    ```
  - 同步更新 types.ts:509 字段注释（标注 FIFO 策略与豁免规则）。
- **防回归测试**（`managers/__tests__/sessionManager.test.ts`）：
  1. 记 MAX+10 条幂等调用 → `length === MAX` 且最新保留（当前无界 → 红）。
  2. 首条为非幂等未补偿 + 再记 MAX+10 条 → 首条仍在，`compensateAllNonIdempotent()` 命中它。
  3. 已补偿记录（compensatedAt 有值）可被正常截断。
- **边界**：不改 argsSignature 键控语义（LLM 参数键序问题概率低，单独归档不并车）。

#### T3（F5-2-2）检查点会话归属定案

- **根因**：checkpoint 与 session 的所属关系无定义；合并语义（:389-418）在 sessionId 变更后跨会话携带 goal/plan/roundLog。
- **语义定案（本任务的设计决策）**：
  - **switchSession = 归档 + 清空**：检查点是「当前会话的工作状态」，不是 Agent 级工作状态。
  - **forkSession = 继承**：fork 的目的就是带着工作去新分支，维持现状（文档化即可）。
- **修复草图**（sessionManager.ts:142-149）：
  - `switchSession` 在 `isChatBusy` 检查后追加：
    1. `stateMachine.status !== 'running'` → 抛 `configError`（paused/error 态切换会话语义未定义，与 fork/restore 的繁忙守卫同构，保守拒绝）；
    2. `this.checkpoint && checkpoint.sessionId !== 切换后名` → `flushCheckpoint(true)`（旧检查点按旧 sessionId 留盘）后置 `this.checkpoint = null; this.checkpointDirty = false`；
    3. 切回旧会话时由既有 `loadPersistedCheckpoint`（按 currentSessionName 读盘）恢复，链路已存在无需新增。
  - `forkSession` 注释补充「fork 继承检查点（goal/plan/toolCalls 带入新分支）」，引用合并语义段落。
- **防回归测试**（`sessionManager.test.ts`）：
  1. 会话 A 建检查点（plan 非空）→ switchSession(B) → `getCheckpoint() === null`，mock store 中 A 的 saveCheckpoint 已调用（当前污染 → 红）。
  2. switchSession 回 A → `loadPersistedCheckpoint()` 恢复出原 plan。
  3. paused 态 switchSession → 抛错（红转绿）。
  4. forkSession 后 plan 仍在（现有行为守卫）。
- **边界**：**不**引入 `Map<sessionId, checkpoint>` 多会话模型——那是多 Agent 协作时代的演进项；本任务只保证单实例内不跨会话污染。

### P2 —— 未来兼容 / 契约结构化

#### T4（F5-2-3）schemaVersion 迁移分发表固化

- **根因**：迁移逻辑无接线点；字段重命名场景旧读新会静默丢字段。
- **修复草图**：
  - SessionManager 增 `private static readonly checkpointMigrations = new Map<number, (cp: Partial<SessionCheckpoint>) => void>()`（空表）。
  - `normalizeCheckpoint`（:666-677 后）：当 `cp.schemaVersion < CURRENT_SCHEMA_VERSION` 时，按版本号升序依次应用已注册迁移（当前为空循环，但接线点固化）。
  - constants.ts:81-89 注释升级为契约：**新增字段不升版本；重命名/删除/改类型必须升 CURRENT_SCHEMA_VERSION 并注册迁移**，评审以此为准。
- **防回归测试**（`sessionCheckpointLifecycle.test.ts`）：
  1. 导出测试钩子注册一条假迁移（version 0 → 改写字段），喂入 schemaVersion=0 的检查点 → 迁移被调用且字段生效（当前无迁移路径 → 红）。测试结束注销，避免污染其他用例。
  2. 守卫：schemaVersion 高于当前 → 仍 warn 且不阻断（现有行为不回归）。
- **边界**：不实际迁移任何现有字段；骨架先行。

#### T5（F5-3-1）文件层两段式契约结构化

- **根因**：「先写/删文件、再调 ConfigManager」仅文档保证；违反者要等「重启复活」才暴露。
- **修复草图**（保持「内核不直接操作文件」原则）：
  - ConfigManager 构造参数追加可选 `fileConsistencyCheck?: (id: string, expected: 'exists' | 'absent') => boolean`。
  - `deleteRule`（:377）入口：注入时校验 `expected='absent'`（文件应已被宿主删除）；`updateRule`（:414）校验 `expected='exists'`（文件应已更新）。校验失败抛 `configError('文件层前置条件未满足', …, ['先经宿主 configFileSyncer 完成文件操作'])`，**fail-fast 于任何索引副作用之前**。
  - 未注入 → 完全降级为现状（向后兼容，宿主零感知）。
  - addRule/addSkill 为 session 级注入，不校验。
- **防回归测试**（`configManager.test.ts`）：
  1. 注入返回 false 的检查 → deleteRule 抛错且 `index.delete` 未执行（当前无守卫 → 红）。
  2. 注入返回 true → 正常删除（绿）。
  3. 不注入 → 现有行为不变（守卫）。
- **边界**：检查是「宿主已完成文件操作」的快照断言，不保证原子性（文件与索引之间仍无事务，这是本地文件架构的固有边界，文档注明）。

### P3 —— 卫生批次（一次合入）

#### T6（F5-1-3 / F5-1-4 / F5-3-2 / F5-4-1）

- **6a** `loadPersistedCheckpoint`（sessionManager.ts:520-529）：pause/triggerError 调用后检查 `transition.allowed`，失败时 `logger.error` 记「状态机与检查点分叉」，与 restoreFromCheckpoint:813-837 同构。
