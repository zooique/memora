## 〇、一句话结论

> **ARCH-2 是「按体量拆」，ARCH-3 是「按哲学的生成逻辑重算一遍」。**

## 一、哲学怎么「生成」代码架构（生成逻辑还原）

### 1.1 设计架构的生成逻辑

设计架构（`docs/architecture/`）不是「先画模块再填功能」，而是**从一条元规则长出**：

```
元规则：代码做确定性（信号采集），模型做不确定性（语义判断）   [§4]
   ↓
推论 1：凡是「需要理解语义才能决定」的动作，不得由代码 if/else 拍板 → 必须是 LLM 触碰点（工具调用/LLM 调用）
推论 2：凡是「能写成 if 命中 then 数值 += delta」的，不得交给模型 → 必须是纯函数
   ↓
由推论 1 得：记忆检索 → 工具（search_memories），不由 prepare 代模型猜    [§6]
由推论 2 得：预算计算 / 截断 / 轮数派生 → 纯函数（budget.ts）            [§4]
   ↓
元规则 2：通用引擎（turn 编排）+ 参数集（角色包），正交                 [§11]
   ↓
推论 3：引擎不得知道自己在服务谁/什么领域 → 身份、规则、领域知识全部来自「卡」
由推论 3 得：system prompt 的「我是谁」必须来自 role pack，内核零硬编码   [§5 + §11]
   ↓
元规则 3：非关键失败降级而非中断，且降级按重要性分级                    [§7]
   ↓
推论 4：降级不是散落的 try/catch，而是「按 P0-P4 分层的显式结构」
```

### 1.2 把这条逻辑**反向**施加到代码上

现有代码架构的判据表：

| 哲学条款 | 代码层应有的结构形态 | 检验方式 |
|---|---|---|
| §4 代码/模型分工 | **确定性面**（纯函数，可离线测）与**模型触碰面**（LLM/工具调用）**物理分离** | 一个文件里能否同时找到 `if 阈值` 与 `llm.chat()` |
| §11 引擎/插卡 | 引擎**不得**含身份字符串、领域知识、策略默认值 | grep 内核里有没有「我是谁」 |
| §5 领域无关 | 切领域不改 `src/` 一行 | grep `src/` 有无具体领域名词 |
| §7 降级分级 | 降级**按级分层**（P0 无 catch / P1-P4 有 catch 且策略各异） | catch 策略是否与操作重要性一一对应 |
| §12 可观测边界 | 内核只埋点，指纹计算只在宿主注入 tracer 时 | 无 tracer 时是否零开销 |

### 1.3 实测结果（本会话 grep 实锤，非推断）

| 检验项 | 实测 | 裁决 |
|---|---|---|
| **§4** loop.ts 是否混装确定性+模型 | `estimateTokens` 调用 **9 处**、`deriveDialogueRounds` **1 处**（L2359）与 `provider.chat` **2 处**（L1568/L1960）**同处一文件** | 🟡 **混装**，但已部分外迁（ContextManager） |
| **§11** 内核是否知道「我是谁」 | **`src/agent/loop.ts:2004` 硬编码 `` `# Memora Agent ... 你是 Memora Agent` ``** | 🔴 **违规**（ARCH-2 未发现） |
| **§5** 领域耦合 | `loop.ts` 仅 4 处命中且均为注释/标签，**无实质领域词** | 🟢 合规 |
| **§4** 代码是否做语义判断 | `determineTaskType`(L1438) 用 **正则匹配代码块 + 字符长度阈值** → 产出路由信号 | 🟢 **合规**（教科书式信号采集） |
| **§7** 降级是否分层 | 7 个 catch 位点（L505/589/1336/1563/1809/1846/1948），策略各异 | 🟢 合规（详见 §2.4） |

**结论**：哲学检验**只揪出 1 处硬伤（§11 身份硬编码）**，其余轴已合规。这本身是好消息——说明减法系列后，代码架构在「哲学轴」上已大致对齐，**ARCH-2 的族切分确实是这个哲学轴的自然结果**，只是 ARCH-2 用了「行数」而非法理来说服人。

## 二、按哲学重新推演的目标架构

### 2.1 三段式：确定性核 ←→ 编排 ←→ 副作用面

哲学 §4 的物理落地 = **单向依赖的三段**：

```
┌─────────────────────────────────────────────────────────────┐
│  ① 确定性面（纯函数，零 IO，零 LLM）                          │
│     budget.ts · compaction.ts(策略) · assembleProjection     │
│     → 可离线快照测试（eval:budget 已落地）                    │
└───────────────────────────┬─────────────────────────────────┘
                            │ 只被读
┌───────────────────────────▼─────────────────────────────────┐
│  ② 编排面（AgentLoop 本体 —— 只做「决定顺序」）                │
│     runIterationLoop · processUserInput · handleIteration    │
│     → 不含确定性计算（调①）、不含副作用实现（调③）           │
└───────────────────────────┬─────────────────────────────────┘
                            │ 只被调
┌───────────────────────────▼─────────────────────────────────┐
│  ③ 副作用与模型触碰面（LLM / 工具 / 文件）                     │
│     llmCaller · toolCallHandler · contextCompactor · managers│
│     → 每个都「可降级」，失败不穿透到②                        │
└─────────────────────────────────────────────────────────────┘
```

**关键判据（本方案的核心设计纪律）**：
> **②编排面里出现任何一行「计算」或「IO 实现」，即为错位**——它只应出现「调用①算」「调用③做」「按返回值决定下一步」。

这与 ARCH-2 §2.1 的「无状态纯计算」是同一件事，但 ARCH-3 给了它**法理来源**（§4），ARCH-2 只给了工程理由。

### 2.2 与 ARCH-2 族切的映射（重叠度对照）

| ARCH-2 族 | ARCH-3 哲学归属 | 是否一致 |
|---|---|---|
| F2 工具执行 → `ToolCallHandler` | ③ 副作用面（工具触碰） | ✅ 一致 |
| F3 LLM 调用 → `LlmCaller` | ③ 副作用面（模型触碰） | ✅ 一致 |
| F1 上下文装配 → `promptAssembler` | **①确定性**（模板拼装，无 LLM）**+ ②编排**（tool 描述裁剪是「决定」） | 🟡 **需再切**：字符串拼装归①，工具面裁剪策略归② |
| F6 空间管理 → `ContextCompactor` | ①（`findEarliest` 定位纯函数）**+ ③**（`compressContext` 调 LLM） | 🟡 **需再切**（与 ARCH-2 §2.3 待拍板同源，但 ARCH-3 给出切法） |
| F7 消息维护 | ①（纯数组机械操作） | ✅ 一致 |
| F4/F5 入口/编排 | ② 编排面 | ✅ 一致（不拆） |
| **字段声明区（~360 行）** | ② 编排面的运行时状态 | ✅ ARCH-2 判「不拆」**正确**——它不是「未拆」，是**本属编排** |

**ARCH-3 对 ARCH-2 的两处修正**：
1. **F1 必须再切**：`buildSystemPrompt` 里既有「拼字符串」（①）又有「决定工具面收窄/裁剪 web_search」（②策略决定）。ARCH-2 把它整体当一族，是**把编排决定混进了确定性面**。
2. **F6 的切法明确**：`findEarliest`/`findLargest`（纯定位）→ ①；`compressContext`/`summarizeForCompression`（调 LLM）→ ③ `ContextCompactor`。ARCH-2 的 §2.3 分叉（并入 vs 新建）按哲学**应选「新建」且归③**——因为它的本质是「模型触碰面」，与 `ContextManager`（①纯计算）**不同段**。

### 2.3 §11 硬伤修复（ARCH-2 未覆盖，本方案新增）

> ✅ **已于 2026-09-10 落地（本方案 P3-0，采用方案 b 中性句）**。实测：`grep '你是 Memora\|Memora Agent' src/ --include=*.ts | grep -v __tests__` 现仅剩 **1 处 = `agent.ts:82` 开发者文档注释**（非 prompt 内容，合法保留）；**prompt 注入面已归零**。质量门：`tsc` 0 / `eslint` 0 / **内核 2749 passed / 4 skipped（基线不变）** / `eval:budget:check` 0。

**原始实锤**：

```
src/agent/loop.ts:2004
  let prompt = `# Memora Agent\n\n${sections}\n\n---\n\n你是 Memora Agent。基于以上人格、规则和领域知识，回应用户的问题。`;
```

**违规判定**：§11 原文 *「memora 不需要知道自己是谁——只需知道当前插的是什么卡」*。而这里内核**把自己的名字写进了 system prompt**，且**追加在 persona 之后**（`loop.ts:456` `prefix + this.buildSystemPrompt(...)`）——即：**无论插哪张卡，引擎都会在卡后面补一句「你是 Memora Agent」**。这是「通用引擎」污染了「卡的语义」。

**修复方向**（三选一，须用户拍板）：

| 方案 | 内容 | 哲学评价 |
|---|---|---|
| **a. 删除身份句** | 只留 `${sections}` + 「基于以上人格、规则和领域知识回应」 | ✅ **最纯**，但需确认 role pack 的 persona 已足够定义身份 |
| **b. 保留中性句** | 改为「基于以上设定回应」，不含任何专名 | ✅ 折中，去除专名但保留指令骨架 |
| **c. 下沉到卡** | 身份句由 role pack manifest 提供，内核读 `manifest.identityLine` | ⚠️ **新增键=预支复杂度**，D6 反对（无真实反馈） |

**建议 b**：一行改动、零新键、去专名。「回应口径骨架」是引擎职责（属①/②），「我是谁」是卡的职责（§11）——b 正好把两者切开。

> ⚠️ **此为行为性改动**（system prompt 内容变了），**不是纯重构**——须单独立项、单独验证（`llm.call` span 的 `systemPromptHash` 会变，任何依赖 prompt 字面量的快照测试会红）。**ARCH-3 只登记，不在重构批次里夹带**（纪律 ②）。

### 2.4 §7 降级分级的结构化（可选增强，D6 暂缓）

**实测 7 个 catch 位点与分级对应**：

| 位点 | 归属方法 | 降级动作 | 对应 §7 级 |
|---|---|---|---|
| L505/542 | `processUserInput` | `taskSucceeded=false; throw err`（**re-throw**，仅 SLO 计量） | P0（不降级，符合） |
| L589/593 | `continueAfterPause` | 同上（re-throw） | P0（符合） |
| L1336/1347 | `parseAskCalls` | 参数非 JSON → 降级空问题，**不阻断** | P2 类（容忍） |
| L1563/1603 | `callLlmWithRetry` | 区分 AbortError 语义 → 重试或上抛 | P0/P1 边界 |
| L1809/1812 | `executeToolCalls` | 缓存失效失败 → 忽略 | P1 |
| L1846/1892 | `compressContext` | 压缩失败 → 上抛由调用方处理 | P2 |
| L1948/1978 | `summarizeForCompression` | 摘要失败 → **返回 `''`（静默降级）** | P2（fire-and-forget） |

**裁决**：**降级已按级分层，但「分级」是隐式的（散在 catch 注释里）**。哲学 §7 要求的是「按分级」——**当前是「按位点各写各的」，规律存在但不显式**。

**是否要显式化（如 `DegradeTier` 枚举 / `degrade(p2, fn)` 包装）**：
> **D6 裁决 → 暂不做。** 理由：① 无任何真实事故由「分级不显式」引发；② 引入枚举/包装 = 新增抽象层（D6 明确反对「对称性增强」）；③ 现状每个 catch 的注释已说明降级语义。**登记为「触发驱动观察项」**——仅当出现「某降级该 P2 却按 P1 处理」的真实事故，才立项显式化。

## 三、ARCH-3 与 ARCH-2 的关系（不重复建设）

| | ARCH-2 | ARCH-3 |

### 8.1 前提变了：内部项目 ≠ 交付物

§六的触发条件（合并冲突 / 需独立测试 / 行数再涨 / 用户要求）是为**长期演进的内部项目**设的——标准是「**没出事就不动**」。
**发包改变判据**：交付物的标准是「**已知缺陷就该修**」。评估报告指出「代码架构只落到六成」，这是一句**对外的质量描述**；带着它发包 = 把已知差距一并交付。

**裁决：发包前应优化。** 但**优化范围必须分级**——不是「全拆」，而是「**修掉会被外部看见/影响可维护性的那部分**」。

### 8.3 为什么「不全拆」

第一性原理：**发包的核心风险是「行为正确性 + 接口稳定性」，不是「文件行数」。**

- 全拆（P3-1..P3-5）= **4 个阶段 × 每阶段重构**，**每阶段都有引入行为回归的风险窗口**。发包前引入这个风险，是**用「可维护性收益」换「正确性风险」**——低ROI。
- **只做 P3-1** = 1 个阶段、1 个新文件、**测试零改动**（已验证），风险窗口最小，同时消掉最大的一块。

**裁决：发包前做「甲 + 乙」，丙延后。** 若时间不允许，**只做甲**也成立（它是唯一的「错」）。
