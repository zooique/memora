> 日期：2026-10-18 · 范围：`src/index.ts` 导出面（136）+ `EXPECTED` 80 符号 / 589 成员 +
> 31 个 `AgentOptions` 字段 + 25 个事件键。
> 判据：`.trae/rules/generic/legacy-contract-audit-rules.md` §3.1（可观测性）/ §3.2（多余导出面）/
> §3.2.1（no-op 直删豁免）+ 台账 D4（宿主生长缺口 ≠ 用户功能缺口）。

## 0 结论

**136 个导出里没有僵尸。** 四项硬指标全部干净：

| 检查 | 方法 | 结果 |
|---|---|---|
| 导出符号可观测性（§3.1） | 全部经 `src/index.ts` 可达 + 有真实声明 | 136/136 活 |
| 配置字段是否被读 | 31 字段逐个查 `.字段` 生产引用 | **31/31 有读取点，零引用 0** |
| 事件是否真会发 | 双口径（`AGENT_EVENTS.x` + 字符串字面量） | **25/25 有发射点，零发射 0** |
| no-op / 谎报（§3.2.1） | 16 个零生产调用成员逐个读实现 | **0 个 no-op，0 个恒空** |

剩下的**全部是冗余，不是伤**：

- **16 个成员**「生产零调用、仅测试可读」——实现真实、文档在册（B 层）；

- 其余宿主没用的都是有本包内调用点的（C 层）。

按 §3.2「可收窄 ≠ 必须收窄」，**本轮不动任何代码**。

一句话：**5.0.0 的公开面可以发。** 冗余留给 6.0.0 的窄接口一并收。

### 3.3 唯一需要写清语义的预留口：ERROR 态通道

`triggerError` / `recover` / `status === 'error'` 三者构成一条**外部驱动**的状态通道：
`sessionStateMachine.ts:8` 明写「当前产品流中 ERROR 态无自动产生者」——内核自己不会进 ERROR，
只有接入方显式调 `sessionManager.triggerError(cause)` 才会。

- **不是僵尸**：状态机真实、转换合法、测试覆盖。
- **是预留口**：给宿主/接入方留的错误态入口。
- **要求**：文档若暗示「内核会在出错时自动进入 ERROR」就是谎报。当前手册未承诺（`§十二` 只列
  `pause/resume`，无 `triggerError`），迁移指南给的是「原 `agent.triggerError` → 改调
  `sessionManager.triggerError`」，与事实一致。

### 3.4 D 层：`loadConfig`

`src/config/loader.ts:326`，三级查找（显式路径 → `.memora/config.json` → 内置默认）+ 环境变量展开。
宿主不用（宿主配置来自 VS Code settings），只有测试直测。
- 判活：实现完整 + `docs/memora-api-reference.md:1282` 明文承诺。

## 4 预留口（注入契约）——全部有接线点

62 个导出 interface 中，10 个是宿主注入契约，全部被内核真实消费（括号 = 内核侧引用文件数）：

`IMemoryStorage`(15) · `ISessionStore`(10) · `IRoundStore`(6) · `ITracer`(7) ·
`IWebSearchProvider`(8) · `IFetchProvider`(5) · `ICodeExecutionProvider`(6) ·

**预留口 = 有契约 + 有接线点**，不是「先写着」。另 17 个导出 interface 虽只在自己文件内被引用，

`AGENT_EVENTS` 25 键**零发射 0**；宿主订阅 24/25，`sessionSwitched` 是登记在册的内核自消费
（`KERNEL_SELF_CONSUMED_EVENTS` 豁免）。

## 5 本次踩到的五个口径陷阱（方法论，比结论更值钱）

1. **`getText()` 把 `#private` 数进公开成员**：首版脚本报 `Agent 71→60`，真值 `70→59`，差 1 = `#config`。
   修法：`!ts.isPrivateIdentifier(m.name)`。
2. **import 计数对 type 无效**：`AgentOptions` 宿主 `import` = 0，但宿主用结构化对象字面量传参
   → 0 import ≠ 未消费。类型面只能看「是否出现在被真实调用的签名里」。
3. **事件发射全走字符串字面量**：只数 `AGENT_EVENTS.x` 会漏 9 个（`emit('sessionPaused', …)`）。必须双口径。
4. **同名跨类借消费点**（`report-surface` 已登记的保守性，本次实锤 3 例）：
   `Agent.getArchiveMode` ← `ArchiveCoordinator.getArchiveMode`；
   `Agent.getMessages` ← `loop.getMessages`；`SessionManager.triggerError` ← `stateMachine.triggerError`。
5. **注释自指被当消费点**（新发现）：`report-surface` 扫原文，`agent.ts:1045` 那句注释
   `（sessionManager.appendPlanItem/triggerError/recover…）` 直接把三个成员的「外部消费」刷成 1。
   ⇒ 该脚本的零消费清单是**下限**，定性必须 `this.<member>` + 去注释双重复核。

## 7 自审订正（同日 · 反向核实本报告时发现）

### 订正 1：宿主「1238 passed」不是稳定读数

本轮交付时写的是「宿主 **1238 passed · 2 skipped**（70 文件，串行口径）」。
反向核实实跑（同一台机、同一官方口径 `--no-file-parallelism`，**连跑两次**）：

| 次 | Test Files | Tests（合计 1240） | 失败用例 | 失败类型 |
|---|---|---|---|---|
| ① | 1 failed / 69 passed (70) | 1 failed / **1237 passed** / 2 skipped | `chatView.test.ts > R4 对照：补发 done 后三现象全部收口` | `Test timed out in 30000ms`（实测 32974ms） |
| ② | 1 failed / 69 passed (70) | 1 failed / **1237 passed** / 2 skipped | `runtimeReplayParity.test.ts > §2 对拍（4 字段轮级语义）` | `Test timed out in 30000ms` |

判据用项目既有 `test-red-triage` 三步，不另立标准：

1. **口径先确认**：宿主 `package.json#test` 自带 `--no-file-parallelism`，两次都按官方口径跑；
2. **数 AssertionError**：两次失败**都是 `Test timed out`，断言失败数为 0**；
3. **隔离复跑**：R4 单跑 **13979ms 通过**；且**两次失败的用例不是同一个** ⇒ 不是确定性缺陷。

⇒ 定性：**负载敏感超时抖动**，不是本轮改动引入（本批 `d57ee5a0..HEAD` 未触碰 `hosts/`）。

**准确表述**：宿主共 **1240** 用例，串行全量连跑**稳定掉 1 条超时（掉哪条随机）**，断言层零失败。
**`1238 passed` 是「某一轮恰好全绿」的一次读数，不可当基线引用**。

**处置**：不改单项 timeout、不动 vitest 配置。改超时是用配置迁就环境，会把未来的真回归一起吞掉
（同「禁改 vitest config 迁就」红线）。已在台账登记为**观察项**，不新增门禁。

### 订正 2：`getArchiveMode` 属「注入回调」，不是「同名借点」

§3.1 原写「借点 = `ArchiveCoordinator.getArchiveMode`」。实查不成立：

- `ArchiveCoordinator` **从不调用** `agent.getArchiveMode()`；
- 它持有**构造注入的同名回调** `readonly getArchiveMode: () => ArchiveMode`
  （`archiveCoordinator.ts:22` 声明 / `:43` 赋值 / `:52`、`:68` 消费）；
- 该回调由 `agent.ts:424` 用内联箭头 `() => this.#config.archiveMode` 喂入——
  与 `Agent.getArchiveMode()`（`agent.ts:1440`）是两条独立通路。

⇒ 结论不变（`getArchiveMode` 实现真实、读真配置、非僵尸），但**分类错了**：
它是「注入回调」不是「同名借点」。§5 陷阱 4 的实证例子应换成三个**真**借点：

| 成员 | 真借点 | 行 |
|---|---|---|
| `Agent.getMessages` | `loop.getMessages()` | `agent.ts:1921/1926` |
| `Agent.clearPlan` | `requireSessionManager.clearPlan()` | `agent.ts:1056/1092` |
| `Agent.injectAffect` | `loop.injectAffect()` | `agent.ts:1943` |

补充实锤的真借点（同类，非 §3.1 已列的三例）：`SessionManager.errorInfo/pauseInfo/triggerError`
← `stateMachine.<同名>`（`sessionManager.ts:96/91/441`）；`SessionManager.recover` ← `stateMachine.recover`
（`:495`）。**这六例才是「同名跨类借消费点」的完整样本。**

### 本节未改动的原判

- §3.1 的 16 个成员**逐个复核后仍然成立**：它们的「生产零调用」是指**该成员自身**零调用，
  借点只是解释「为什么 `report-surface` 会把名字数出来」，两者不冲突；
- 四个硬指标复核后复现：`136 = 48 value + 88 type`、`AgentOptions 31 字段 / 以 `.字段` 严判据零引用 **0**`、
  `AGENT_EVENTS 25 键零发射 **0**`、`导出 interface 62 个`。原结论无需修订。
