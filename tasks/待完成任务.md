### 发现的问题（按优先级）
- [x] **P2 · compress_context 可能压掉顶级锚点**（已修复，见 [已完成任务.md](./已完成任务.md)）：`findEarliestRound` 原取第一个 user 消息——上下文仅一轮（LLM 首轮就调 compress_context）时会把当前输入（顶级锚点）压成临时摘要，违反「触发输入+首个回答永不压缩」硬约束。已修复：以最后一个 user 为顶级锚点，只压其之前的旧执行闭环，无旧轮次返回 null（交软上限收尾闭环）；设计边界已固化到三份设计文档
- [ ] **P2/P3 · ReplaceRoundsStrategy 截断后 roundId 尾部对齐错配**：`contextManager.truncateMessages` 从被裁段提取 key messages 重新插入（重排消息顺序），`roundIdSequence` 与消息轮次的尾部对齐可能错位，`getSummary(roundId)` 可能取到错误轮次摘要替换正确正文。建议截断重排时同步 roundId 映射，或仅在未触发截断时启用替换
- [ ] **P3 · 软上限检测用总上下文近似摘要层容量**：设计触发点是「摘要层 token 达容量上限」（确定性物理量），代码用「总上下文 ≥90% + 任一摘要标记」近似（[loop.ts `_shouldInjectSoftLimitWrapup`](../src/agent/loop.ts)），语义有偏差但功能等效（摘要层饱和必然伴随总上下文逼近上限）
- [ ] **P3 · 替换触发用固定轮数 5 而非 token 预算**：`ReplaceRoundsStrategy.shouldCompact` 按「轮次数 > keepRecentRounds」判断，与动态预算（token）脱节——上下文还很空时也会替换超过 5 轮的旧轮。早替换零成本可接受，属与动态预算的张力，记录不修
- [ ] **P3 · 软上限无强制终止兜底**：软上限注入收尾信号依赖 LLM 配合收敛；LLM 持续不收敛时会每轮重注入信号（executionTemp 清理+重注入，不堆积），由 `maxIterations`（默认 20）硬兜底，可接受，记录不修
