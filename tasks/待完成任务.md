## 内核设计弱点（已实证，待排期）

> 来源：用户「核实上述结论，把真实的问题记录到 tasks」。经 grep/源码对抗式核实，下列为内核真实存在的设计弱点（非宿主侧、非功能取舍）。

- [ ] **K1 · 检查点持久化无 schemaVersion / 无 CAS / 无迁移（已实证）**：`src/memory/sessionStore.ts:22` `ISessionStore.saveCheckpoint(sessionId, checkpoint: string)` 契约为不透明字符串；`sessionManager.ts:463` `JSON.stringify(this.checkpoint)` 整对象序列化为 blob，`loadPersistedCheckpoint`（sessionManager.ts:479-485）`JSON.parse` + `parseCheckpoint` 直接恢复——**无版本字段、无迁移、无并发控制**。grep `schemaVersion|checkpointMigrations|migration|乐观锁` 内核零命中；`SessionCheckpoint`（types.ts:271-327）无版本字段（注释明言 `goalChangeSeq` 不承担版本校验）。后果：① 结构演进后旧检查点静默损坏/恢复失败，无迁移路径；② 无 CAS，多进程/窗口写同一 session 互覆盖；③ 恢复时残缺/旧版检查点抛错「被外层 catch 静默吞掉整个会话」（sessionManager.ts:482-483 注释自陈），无优雅降级。修复方向（不修，仅评估）：`SessionCheckpoint` 顶层加 `schemaVersion: number` + 版本路由/轻量迁移；CAS 用 `(sessionId, expectedRev)` 或原子写写入序。当前单用户 local-first + 单 Agent 下严重度中低，但属「未来必然爆」的定时炸弹（与 L15 跨进程恢复强相关）。

## 插件新生长点（2026-08-23 三次核实 · 19 模块全景扫描排雷）

> **排雷结论（风险评估与真实性验证）：**
> *   **H4（任务闭环）**：**结论真实，风险可控，价值极高**。内核接口完备（`processEvent`/`interject`），宿主零消费。这是展示 memora 核心差异化能力（分步执行、运行中插话）的关键生长点。需新增协议和 UI 组件，属于中等工作量功能生长，列为**高优先级**。
> *   **H5（文本润色）**：**结论真实，风险极低**。内核 `textPolisher` 已就绪，宿主仅缺入口。属于“锦上添花”能力，列为**低优先级**。
> *   **H2（Provider 路由）**：**结论真实，但当前无价值**。宿主为单 Provider 架构，强行推进会增加 UI 复杂度，违反“自然生长”原则。标记为**远期暂缓**。

> 来源：用户「以 memora 为种子，聚焦宿主插件自然生长，对齐 memora 的功能实现，展示 memora 的能力」。

- [x] **H4 · 任务驱动多步闭环（最小可视化 · 已落地 ✅ 2026-08-23）**
    - **生长内容**：薄壳可视化——协议新增 `plan_update`；chatPanel 在 `task_table_write/update` 工具调用时从 `agent.getCheckpoint().plan` 提快照推送；chatView 渲染任务看板（N/M 进度 + 步骤列表）。零内核改动、不切换 API（沿用 chat() 已有外部任务循环）。
    - **验证**：宿主 typecheck 零错 + 15 文件 173 测试全绿（chatView +4 看板用例）。

- [ ] **H5 · 文本润色入口（低优先级 · 锦上添花）**
    - **内核种子**：`agent.ts` 的 `textPolisher` getter 返回 `TextPolishManager`，提供 `polish(text)` 方法，已配置 15s 超时和 2000 字上限。
    - **宿主现状**：仅存在 `translation-polish.md` 技能文件，无任何 UI 入口调用。
    - **生长动作**：在 `webview` 的输入框或消息气泡上增加“润色”按钮，选中文本后调用 `await agent.polish(text)`，将结果回填。

- [ ] **H2 · Provider 任务路由（远期暂缓 · 非当前阶段目标）**
    - **内核种子**：`assemble.ts` 的 `createProviderRouter` 为恒等桩，`AgentLoop` 预留路由缓存优化。
    - **宿主现状**：`ProviderStore` 仅支持单 Provider 配置，已通过 `backgroundProvider` 解决了后台任务成本问题。
    - **暂缓理由**：当前单 Provider 模型无法体现路由价值；强行增加 UI 复杂度违反“自然生长”原则。待出现“代码用强模型、摘要用快模型”的真实痛点时再启用。
