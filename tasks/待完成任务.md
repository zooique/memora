## 设计纪律（防止重复犯错）

> 以下是本轮实践中总结的**硬约束**，任何新任务评估必须逐条对照。违反以下任一的任务直接归入「不需要推进」区。

### D1 · 记忆质量 = 内核自动机制，不是用户功能

```
衰减 / 去重 / 冲突检测 / 时效性评估 是内核为记忆质量跑的自主后台机制，
类比磁盘整理 / TCP 重传率 / GC——用户不需要看、不需要手动触发。

❌ 禁止：把内核自动机制暴露为用户按钮或诊断面板
✅ 正确：内核自动运行，用户仅看到结果（如「某条记忆被清理」的通知）
```

### D2 · 用户记忆视图 = 陈述级，不是诊断级

```
ChatGPT 只暴露「记住了什么 + 删除/编辑」——陈述级视图。
source health 评分 / conflict cluster / 衰减曲线 是诊断级仪表盘，用户看了不知道该干嘛（vanity metric）。

❌ 禁止：在用户设置页放诊断仪表盘
✅ 正确：诊断能力经第一性原理复盘判定无终端用户场景（明文 JSON 已可读），已于 2026-08-24 **彻底删除**（含 protocol DTO / webview 方法 / HTML 容器 / 样式），未保留开发者视图
```

### D3 · 透明性已由明文 JSON 满足

```
记忆存储在 .memora/memories.json，JSON.stringify(list, null, 2) 明文格式化。
用户打开文件即见全部记忆内容——无需额外的「透明化面板」。

❌ 禁止：为「让用户看到记忆」而新建 UI
✅ 正确：用户直接看 JSON 文件；如需简化，做「记忆浏览器：看了什么 + 删/改」
```

### D4 · 宿主生长缺口 ≠ 用户功能缺口

```
内核 API 存在 ≠ 宿主必须消费。
评估「宿主生长缺口」时必须回答：消费这个 API 对用户有什么实际价值？

❌ 禁止：逐条消费内核所有 API 作为「对齐」
✅ 正确：只消费有明确用户场景的 API；内部机制的 API 不暴露
```

### D5 · 安全分级决策必须显式

```
preExecutionCheck 当前恒放行（skip:false）——单用户桌面场景可接受，
但必须显式标注为「intentionally left blank」，而非静默占位。

❌ 禁止：用空函数占位安全策略
✅ 正确：显式决策 + 文档化；未来多用户/服务端部署时再接入真实策略
```
