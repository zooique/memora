**核心原则**：架构层任务优先（根须先行），枝叶层任务跟进（枝叶按需），环境问题随时清理。

| 迭代 | 主题 | 层级 | 任务 | 工作量 | 价值 |
|------|------|------|------|--------|------|
| **迭代 1** | 架构层首发 | 架构层 + 环境 | ChatLockManager 提取 + pathGuard 速修 | 中 | agent.ts 降行 + 测试全绿 |
| **迭代 2** | 枝叶层首发 | 枝叶层 | relationGraph.ts 拆分 | 中 | 枝叶层 2 次原则首次实践 |
| **迭代 3** | 架构层深化 | 架构层 | PostProcessPipeline 评估 | 低 | 边界理清 + 拆分方案 |
| **迭代 4** | 质量补全 | P4 + 长期 | 隐私合规 + eval 补全 | 高 | 用户反馈闭环 + 评估框架 |

### 任务 1.2：ChatLockManager 提取（AUDIT-1-1）

**层级**：架构层（ADR-017 架构先行原则适用）
**架构归属**（ADR-017 4 问评估结果）：
- Q1 归属：`agent/managers/`（12 个 Manager 的第 13 个）
- Q2 依赖：仅依赖 utils/safeTimer + utils/errors，无新依赖方向
- Q3 新模块：✅ 新增 `agent/managers/chatLockManager.ts`
- Q4 边界：不影响，符合 ADR-010 God Object 拆分既定路径

**提取范围**：
- 4 个字段：`_chatBusy` / `_chatLockToken` / `chatLockTimer` / `chatAbortController`
- 1 个公开方法：`forceReleaseChatLock()`
- chat() 内联的锁获取/释放/超时逻辑（token 分配 + AbortController + 超时定时器 + finally 清理）

**设计**：
```typescript
// agent/managers/chatLockManager.ts
export class ChatLockManager {
  private _chatBusy = false;
  private _chatLockToken = 0;
  private chatLockTimer: ReturnType<typeof setTimeout> | null = null;
  private chatAbortController: AbortController | null = null;

  get isBusy(): boolean { return this._chatBusy; }
  get lastInteractionAt(): Date | null { ... }

  /** 获取锁，返回 token（用于 finally 校验） */
  acquire(timeoutMs: number, onTimeout: () => void): { token: number; signal: AbortSignal } { ... }

  /** 合并外部 signal */
  attachExternalSignal(external: AbortSignal, internal: AbortController): () => void { ... }

  /** finally 块清理（token 校验后） */
  release(token: number): void { ... }

  /** 强制释放（宿主无进展超时兜底） */
  forceRelease(): void { ... }
}
```

**agent.ts 改造**：
- 移除 4 个字段 + forceReleaseChatLock 方法
- chat() 改为委托 ChatLockManager
- 预期降行：~200 行（1347 → ~1150）

**测试**：
- 新建 `agent/managers/__tests__/chatLockManager.test.ts`
- 覆盖：获取锁 + token 递增 + 超时回调 + finally 清理 + 强制释放 + 并发场景

**验证标准**：
- tsc 0 errors
- 内核测试全通过（含新建的 chatLockManager 测试）
- agent.ts 行数降至 1200 以下

## ADR-017 实践验证点

本长线方案是 ADR-017 的完整实践验证：

| 验证点 | 对应迭代 | 预期结论 |
|--------|---------|---------|
| 架构层 4 问是否有效分流任务 | 迭代 1 | ✅ ChatLockManager 归属明确可直接执行 |
| 架构先行是否比"等 3 次"更早识别架构任务 | 迭代 1 | ✅ 首个需求即定好归属，不等累积 |
| 枝叶层 2 次提取是否会导致过度抽象 | 迭代 2 | 待验证（relationGraph 拆分后观察） |
| 分层原则是否可持续指导长期迭代 | 迭代 1-4 | 待验证（4 个迭代周期后回顾） |

> 🌳 自然生长长线方案：架构层（根须）先行定方向——迭代 1/3 处理架构层任务；枝叶层（枝叶）按需跟进——迭代 2 处理枝叶层任务。每个迭代完成后检查反馈回路，调整下一迭代。
