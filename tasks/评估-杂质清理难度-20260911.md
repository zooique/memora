# 杂质清理评估（ingredients 清单）

> 评估时间：2026-09-11
> 评估方法：全链 grep + 通读消费点 + 分类（真死 / 半活 / 恒零）
> 结论：**共 4 项，难度分成「低 / 中 / 中高 / 不做」四档。**

***

## 总览表

| # | 杂质 | 判定 | 难度 | 建议 |
| --- | --- | --- | --- | --- |
| 1 | `recalledMemories` 恒空占位符（4 层透传） | **真死**（恒 `[]` + 零非测消费者） | **低**（参数重排） | ✅ 可做 |
| 2 | `TRACE_SPANS.RECALL` / `RECALL_ACTUAL` 无 emit 点 | **半活**（宿主历史数据可读性依赖） | **低**（仅注释/保留） | ⛔ 不该删 |

## 1 · `recalledMemories` 恒空占位符 —— **难度：低**

### 实测证据

生产侧完整出现（非测试）：

```
contextPreparer.ts:100   const recalledMemories: Memory[] = [];   ← 定义（恒空）
contextPreparer.ts:187   return recalledMemories;                 ← 原样返回
seed/prepare.ts:93        const recalledMemories = await ...      ← 接收
seed/prepare.ts:96/117    return { input, recalledMemories, ...}  ← 原样透传
seed/orchestrator.ts:83   loop.processUserInput(input, undefined, signal, roundId)  ← 传 undefined
loop.ts:461               recalledMemories?: readonly Memory[]    ← 声明
loop.ts:466               void recalledMemories;                  ← 读到就扔
```

**链路性质**：从产生到消费，**没有任何一处读过它的内容**，纯粹是「四个环节都登记了、没人干活」的信封。生产侧零消费者，宿主 `grep recalledMemories hosts/` = **0**。

### 为什么难度只有「低」

关键发现：`orchestrator.ts` 传的是**显式 `undefined`**，不是从 `prepare` 的结果里取的。也就是说：

**`SeedPrepareResult.recalledMemories` 和 `loop.processUserInput` 的 `recalledMemories` 参数，是两个互不相干的占位符——它们从来没有真正连起来过。**

所以清理是**两个独立的小手术**：

| 手术 | 改动 | 面 |
| --- | --- | --- |
| A. 删 `loop.processUserInput` 第 2 参 | 参数重排 `(input, recall, signal, roundId)` → `(input, signal, roundId)` | **20 处**携带第 2 参的调用点（含 7 处纯 `undefined` 占位，**改完更可读**） |
| B. 删 `SeedPrepareResult.recalledMemories` | 删字段 + `recallAndInject` 改返回 `void` | 4 文件 + `prepare.test.ts` 3 处断言 |

### 风险点

**参数重排是本档唯一的真实风险**：`(input, undefined, signal, roundId)` → `(input, signal, roundId)`，必须保证 `userInput` 之后的参数不串位。**这是编译期可查的**（类型不同：`AbortSignal` vs `string`），tsc 会抓住所有漏改。

**注意 4 处测试 `toContain` 断言**（`loop.test.ts:1100/1128/3706` + tracer 3290）是「自动注入退役」的**守卫测试**——它们断言「传入记忆也不会注入」，**删参数后这些测试失去被测对象** → 需改为「签名不含该参数」或直接删除。这是**有效测试的收口**，不是简单删。

### 收益

- 消掉 2 个恒空字段 + 4 处注释解释
- 20 处调用点变干净（7 处去掉噪音 `undefined, undefined`）
- **不删任何行为**

## 2 · `TRACE_SPANS.RECALL` / `RECALL_ACTUAL` —— **难度：低，但结论是「不该删」**

### 实测证据

- 内核**零 `startSpan` 调用**（`grep TRACE_SPANS.RECALL src/` 非测试 = 0 命中）→ 确无 emit 点
- 宿主 `host/tracer.ts:115/117` 的 `switch` 分支把它们映射为中文名「记忆召回」/「召回执行」
- 宿主 `getLatestFingerprints():152` 按 `TRACE_SPANS.RECALL` 名读 span
- 宿主测试 `hostIntegration.test.ts:137` / `tracer.test.ts:17` **主动构造** `RECALL` span 测标签映射

### 判定：**跨版本数据可读性资产，不是死代码**

删掉的后果：用户翻旧 trace 日志时，历史 `recall.recall` span 从「记忆召回」变成裸英文 key，**且宿主测试会转红**（它们刻意构造该 span）。

**结论：保留，已加注释说明「已无 emit 点，保留供历史数据显示名」。难度 0（本轮已完成）。**

## 3 · `attachedMemoryCount` / `attachedMemoryFingerprint` —— **难度：中**

### 实测证据（恒零链）

```
内核：RECALL span 零 emit 点（证据同 #2）
  ↓ 所以 attributes 永远没有 attachedMemory*
宿主 getLatestFingerprints():152-155  读 RECALL span 的 attachedMemory* → 恒 undefined
  ↓
chatPanel.ts:2693   fingerprints.attachedMemoryCount = fp.attachedMemoryCount  → 恒 undefined
  ↓
chatView.ts:2970     if (typeof fp.attachedMemoryCount === 'number')  → 永不进入
chatView.ts:2977     '附着记忆 N 条'  → 永不显示
chatView.ts:3133     if (lastAttachedMemoryCount === undefined) return;  → 永远 return
chatView.ts:3144     tag.textContent = '基于 ' + N + ' 条记忆';  → 死代码
```

**这是一条「从内核恒零 → 一路传到前端 → 最终弹出一个永不出现的 UI 标签」的完整死链。**

### 这是典型的「结构性幻觉」（MEMORY 病灶 §11）

`attachedMemoryCount` 这个字段的**存在本身**在宣称「记忆会被自动附着到上下文」——而这件事已经取消了。字段名 + 前端 `'基于 N 条记忆'` 标签文案，共同在向维护者/用户宣称一个**不存在的机制**。

**按 §11 判据**（「这个字段还会影响任何决定吗」→ 不会 → 删，别降级）：**应删净**。

### 改动面（4 层）

| 层 | 落点 |
| --- | --- |
| 内核 | `tracer.ts` `getLatestFingerprints` 语义已在宿主，内核无改动（`RECALL` span 常量保留见 #2） |
| 宿主 host | `host/tracer.ts:142-158` 删 `attachedMemory*` 两字段 + `:152` 的 `else if (RECALL)` 分支 |
| 协议 | `shared/protocol.ts:478` 删 `attachedMemoryCount?: number` |
| 宿主 panel | `chatPanel.ts:2693` 删传参 |
| 前端 | `chatView.ts` 删 `lastAttachedMemoryCount` 变量（398）+ 2970-2977 指纹行片段 + 3133-3144 标签渲染函数 |
| 测试 | `chatView.test.ts` 5 处 fixture（592/652/1144/1602/1971）+ 可能 1 处标签断言 |

### 难点

**前端展现层解构需谨慎**：`chatView.ts:2977` 是「本轮指纹」字符串**拼接**的一部分，删掉片段要保证拼接结果仍合法（前面有 `systemPromptHash` 片段，需处理分隔符）。`3133-3144` 是一个独立渲染函数，删除时要确认无其它调用者。

**跨层一致性**：协议字段删除后，宿主 panel 与前端必须同批改，否则协议测试转红（`protocolGuard.test.ts`）。

## 4 · `metrics.recall.hitRate` —— **难度：中高（🔴 本轮最重要发现）**

### 实测证据（恒零链）

```
loopMetrics.ts:16/17   recallTotalCount = 0; recallHitCount = 0;   ← 声明
loopMetrics.ts:31      get hitRate() { return totalCount > 0 ? ... : 0 }  ← 恒 0（分母恒 0）
loop.ts:1979/1980      读它们 → 恒 0
  ↓ （grep 全 src 非测试：**零写点**，只有读点）
loop.ts:1981           hitRate = roundTo(0, 3) = 0
  ↓
chatPanel.ts:2697      recallHitRate: m.recall.hitRate = 0
  ↓
chatView.ts:2980       '召回命中 ' + Math.round(0 * 100) + '%'  
  ↓
用户看到： 「累计：LLM N 次 · 召回命中 0% · 工具失败 0 · 截断 0」
```

### 为什么这比 #3 更严重

**#3 是「永不显示」，#4 是「永远显示 0%」。**

「召回命中 0%」是**用户可见的活性误信息**——用户会看到每次会话都写着「召回命中 0%」，可能推断出「记忆检索完全没工作」或「系统有 bug」。

**而实际上记忆检索是正常工作的**（走 `search_memories` 工具）。这个 0% 是**旧自动召回时代的残留计数器**，写点已随召回编排删除，只剩读数。

### 三个可选处置

| 方案 | 做法 | 难度 | 评价 |
| --- | --- | --- | --- |
| ① 删净 | 删 `recallTotalCount`/`recallHitCount`/`hitRate` + `AgentMetrics.recall` 整个分支 + 协议 + 前端显示片段 | **中高** | 最彻底，但要动 `AgentMetrics` 公开类型（宿主类型契约） |
| ② 换成工具召回口径 | 让 `search_memories` 命中时累加，指标语义改为「工具召回命中率」 | **高** | 新增语义，**属新功能**，违背 D6（无真实需求） |
| ③ 明示收起 | 前端去掉「召回命中 N%」显示，内核保留字段 | **低** | 治标——内核仍留恒零字段（结构性幻觉未除，病灶 §11 不允许） |

### 建议

**走①（删净）**。理由：

- 它是**用户可见**的错误信息（唯一一个有实际伤害的杂质）
- `AgentMetrics.recall` 整个分支都是恒零（`totalCount`/`hitCount`/`hitRate` 三字段全零），删的是**一整个概念**而非零散字段
- 宿主侧只有 `chatPanel.ts:2697` 一处消费

**但要提醒**：`AgentMetrics` 是内核**公开类型**（`src/index.ts` 导出），删除 `recall` 分支属**Breaking Change**——按项目纪律「破坏性变更走 deprecation 周期」。发包在即，**需你拍板**是否现在动。

## 汇总建议（按 ROI 排序）

| 优先级 | 项目 | 难度 | 收益 | 建议 |
| --- | --- | --- | --- | --- |
| **P1** | #4 `recall.hitRate` 恒 0 + 前端显示 0% | 中高 | **消除用户可见误信息** | 🔴 优先，但需拍板 Breaking Change |
| **P2** | #1 `recalledMemories` 占位符 | 低 | 20 处调用点变干净 | ✅ 可立即做 |
| **P3** | #3 `attachedMemory*` 死链 | 中 | 消除结构性幻觉 | ⚠️ 可与 #4 合并成一个「记忆附着可观测性退役」批次 |
| **—** | #2 `RECALL` span 常量 | 低 | 无（应保留） | ⛔ 不做 |

### 关键洞察

**#3 与 #4 是同一件事的两个面**：都是「自动记忆召回时代」遗留的**可观测性概念**（附着记忆数 / 召回命中率），随召回退役而恒零。#2 的 span 常量是它们的**共同源头**。

所以**最省的做法是一次性处理「记忆自动召回的可观测性退役」**：

```
删 TRACE_SPANS 的 RECALL/RECALL_ACTUAL？  → 不（历史数据显示名，见 #2）
删 attachedMemory* 链？                    → 是（#3）
删 metrics.recall 分支？                   → 是（#4，但涉 Breaking Change）
```

**batch 规模**：约 10 文件（内核 2 / 宿主 host 2 / 协议 1 / panel 1 / 前端 1 / 测试 3）。
