### 补充：阶段一已落地（值守卫 + 配套债务消化）

- **守卫一（值层面，冻结式软门）**：`tokensClosure` 第 4 条断言。设计为只挡新增、允许下降，
  而非归零硬门。经**变异验证**实证：注入一处裸值即 173→174 并精准定位到 `padding 43→44`。
  基线随消化同步下调（173 → 127 → 79），避免消化出的额度变成新增的口子。
- **守卫二（fallback 一致性，硬门）**：样式层 `var(--x, Npx)` 的 N 与 tokens 定义不一致时，
  代码里就并存两套值。本条一次性查出 **88 处**漂移（如 `var(--sp-1, 2px)` 而定义为 4px、
  `var(--radius-sm, 4px)` 而定义为 2px）——**这就是旧报告 F5「靠人肉对齐」的真实代价**，
  此前从未被任何守卫发现。已全量修正。
- **新增令牌**：`--sq-*` 六档方形控件尺寸（width/height 同值成对是本库同构模式）、
  `--sp-hair` 极紧凑微调档。
- **零视觉变化**：所有替换保留原值作 fallback；且 tokens 在两个面板恒注入，
  fallback 为永不触发的死值，故只改死值不改渲染结果。
- **焦点环收敛（A' 级真债务）**：把 15 处重复拷贝提升为令牌层一条 `:where(...):focus-visible`
  全局规则。用 `:where()` 承载使其**特异性为 0**，各视图既有的自定义焦点样式（summary 用
  box-shadow、chip 用内阴影）照旧覆盖、不打架；新增可聚焦元素自动获得焦点环。
  渐进增强：老环境不认 `:where()` 时整条被丢弃，退化为现状，无回归风险。
  同批把 `--focus` 嫁接到 `--border-focus`（此前两个令牌映射同一 VS Code 变量却各带一套回退值）。
  ⚠️ 需真机确认：此前未声明焦点样式的元素现在会显示焦点环（这是补漏，但属可见变化）。
  另：15 处显式声明与全局规则当前并存（双保险），可在真机确认后再清理冗余。

| 组件形态 | 🔴 | 按钮 24 class/6 文件、chip 40/5、卡片 34/5、列表项 37/5 |
| 工具链 | 🟡 | 无 stylelint/postcss，CSS 是 eslint 与 tsc 的双盲区 |
| 文档真源 | ✅ | 死链指针清零；`htmlShell` 收敛了 head 骨架 |

### 1.2 优化思路

- **S5 值守卫：做成 `tokensClosure` 的第 4 条断言，不引入新工具。**
  理由：该项目已有「守卫即契约」的成熟范式，且 `tokensClosure` 已解决路径枚举与反向守卫（防空集假绿）。
  再引 stylelint 等于另起一套配置与规则集——并列而非嫁接。**判据先挂 warning，假阳性率可控后升 fail。**
- **组件层收敛（U5）不改判据，但风险更高**：抽真源会同时改多个视图的视觉，
  需真机回归。**判据不动、形态动**，属于阶段二而非阶段一。
- **隐性契约显式化**：`dropdownStyles` 依赖「宿主已注入 tokens」这一未表达的前提，
  建议在 tokens 侧补一条注释级契约，或让 dropdown 自带注入（二选一，勿两处都写）。

## 二、设计不带伤原则

### 2.1 伤害分级（按「会不会漏改」排序）

| 级别 | 伤 | 为何是伤 |
|------|-----|---------|
| 🔴 A' | **焦点环重复且来源分裂**（取代原 A 级判定） | 37 条 focus 规则里 15 条是同一条声明的拷贝；焦点色取自三种来源、偏移三种取值 |
| 🔴 B | 流式内容无 `aria-live`（全库 0） | AI 回复增量到达时屏幕阅读器**完全不播报**——这是 Agent UI 特有的硬伤 |

**B 级白话说明**：`aria-live` 是给读屏软件的「这块会变，变了念出来」标记。memora 现状为 0，
即视障用户对 AI 回答全程无感知。难点在于回答是逐字流式到达：简单加 `aria-live="polite"` 会
变成每来一字念一次的灾难，正解是增量阶段用 `aria-busy` 抑制、收到 `done` 后推完整文本念一次。
协议层已具备 `chunk`（增量）与 `done`（收尾）两个信号，**webview 侧即可实现，无需改协议**。

> **⛔ 2026-10-11 用户两次拍板订正（本条降级搁置）**：
> ① **否决运行时自动播报**——改为「turn 结束后，轮级 footer 手动朗读按钮（与复制/分叉/删除同栏）」，
> 用户点击才朗读最终结论，不需要运行时朗读（避开流式噪音，把控制权还给用户）。
> ② **第一版搁置**——朗读按钮是否有真实需求存疑，先登记观察不落实（台账 `UI-SPEAK-1`）。
> 上表 B 级「硬伤」定性随之降级：现状读屏用户仍可用读屏软件的浏览模式自行读取静态文本，
> 并非完全无感知。触发条件见台账条目。
| 🟡 C | 角色卡片详情无键盘路径 | `roles_detail` 唯一发送点是 div 的 click；补 `role=button` 属 ARIA 反模式，需新增 UI 元素 |
| 🟡 D | 尺寸/间距裸值 ~172 处 | 不会漏改，但改令牌不跟随，属慢性腐化 |
| 🟢 E | 12 处 `!important` | 其中 chatStyles 全局 `[hidden]` 兜底已论证为治病性取舍，非污点 |

### 2.2 ⚠️ 原 A 级判定已撤回（对抗式复审结论）

原判定「同族组件横跨 5–6 文件各造一套 = 并列腐化」**不成立，予以撤回**。复审依据：

1. **代码里已有明确的设计决策**，且写在注释中：
   - `configStyles` 头部：三个子视图共存同一文档，**共享类名靠根容器前缀隔离，避免跨子视图串扰**
   - `rolesStyles` 头部：**SSOT 是「各视图自持作用域类 + 视觉 token 复用」**，刻意不把类改造成跨场景共享
   → 类名重复（`.btn` 在 6 个文件、`.card` 在 5 个）是**刻意的隔离策略，不是腐化**。
2. **组件层不但存在，而且用法规范**——`settingsStyles` 里本就有一行共享基类：
   `#roles-root .btn, #config-root .btn, #memory-root .btn, #skills-root .btn, #security-root .btn { … }`
   一个逗号选择器覆盖 5 个根容器；各子视图只留差异（roles 的按钮小一号、memory 的撑满等宽、
   config 的只调对齐），注释还特意交代「布局性差异不混入通用 `.btn` 基类」。
   这是标准的**基类 + 变体**模式，不是各写一套。
3. **声明体层面的实测**（这是判定重复的正确口径）：
   按钮 8 个不同声明体中仅 1 个相同、卡片 4 个体全不同、图标块 2 个体全不同
   → 各视图同类组件的视觉**本就不同**，重复的是**类名**不是**样式**，抽真源没有可抽的东西。

**教训**：判定「重复」必须先分清「名字重复」与「内容重复」。前者在有作用域隔离设计时是
正常且必要的；只有后者才是债务。上一版报告用 class 名计数做判据，是**判据选错**。

**替代的真债务（A'）**：盘点 37 条 focus 规则后发现——15 条是同一条声明的重复拷贝，
且焦点色分散取自 `--border-focus` / `--focus` / `--vscode-focusBorder` 三个来源，
`outline-offset` 有 2px / 1px / 0 三种取值。**焦点环才是跨视图真正应统一的契约**，
已收敛（见 §零 阶段一补充）。

### 2.3 优化思路

- **先治 A、B，再治 D。** A 与 B 是「结构性漏」——只要结构不变，修多少次都会复发；
  D 是「慢性腐化」，有守卫即可止损。顺序反了会陷入反复打补丁。
  （**2026-10-11 订正**：B 已按用户拍板降级为手动朗读按钮方案并搁置，见 §2.1 订正注记与
  台账 `UI-SPEAK-1`——本条顺序约束中 B 移出，仅余 A 与 D。）
- ~~**B 的方案要贴合流式语义**：不是简单给容器加 `aria-live="polite"`（会把每个 token
  增量都播报，灾难级噪音）。正确做法是**在轮次收尾时把完整文本推入一个 live region**，
  增量阶段用 `aria-busy` 抑制。这需要内核/宿主协议侧配合，属阶段二。~~
  **已废弃（2026-10-11）**：运行时自动播报方案被用户否决，改手动朗读按钮（挂轮级 footer，
  点击读最终结论）；且「需协议侧配合」说法有误——协议已有 `chunk`/`done` 信号，
  webview 侧即可实现。搁置登记见台账 `UI-SPEAK-1`（含落地路径调查结论）。
- **建立「可交互元素必须有 focus 样式」的脚本守卫**：本轮已证明 13 处 `outline: none`
  里 12 处合规、1 处违规；这类判断可以自动化（查 `outline: none` 是否有伴生 focus 规则），
  避免每次靠人工盘。

## 三、用户使用心智模型

### 3.1 四问兑现度（实证）

| 用户问题 | UI 载体 | 兑现度 |
|----------|---------|--------|
| 你是谁 | 输入框上方 role-badge + capability-badge | ✅ 已兑现（角色包比 mode 切换更强） |
| **你知道什么** | 只有 `context-ring` 给占用比例 | 🔴 **只看得到比例，看不到内容** |
| 你在做什么 | plan-bar 任务表 + round-block 过程折叠 | ✅ 已兑现（信息密度优于同类） |
| 我能怎么干预 | 暂停/停止/润色/审批 | 🟡 有干预，但**无法显式喂入上下文** |

### 3.2 核心判断

**memora 最大的差异化（memory-as-everything）目前没有在对话 UI 里兑现。**

实证：`chatView.ts` 中 memory/记忆 仅 12 处命中，且绝大多数是**过程状态叙述**
（「检索记忆：xxx」「归档记忆中…」），记忆的完整 UI 只存在于设置面板的 `memoryView`。
也就是说：用户知道「它在翻记忆」，但**不知道它翻到了什么、凭什么这样回答**。

这导致一个心智漏洞：当 AI 答得对，用户不知道是记忆起了作用（无法强化信任）；
当 AI 答错，用户无法判断「是不是记忆检索错了」（无法归因与纠正）。

### 3.3 优化思路

- **让自动召回可见**：在回答上方给出一行可展开的「本轮参考了 N 条记忆」，
  列出命中的记忆标题。这不是抄 `@mention`，而是把 memora 已有的能力**翻译成用户看得懂的语言**。
- **占用环从「比例」升级为「构成」**：当前 hover tip 已有明细，
  可考虑常驻轻量构成条（对话/记忆/角色包/工具输出四段），让用户理解钱花在哪。
- **归因通道**：点击某条记忆可反馈「这条没用/已过时」——把记忆的正确性维护交还给用户，
  这与内核 `search_memories` 的单入口设计是同构的（反馈回流记忆系统）。

## 四、主流 Agent UI 对照与缺口

对照 Cline / Roo Code / Continue 的实际形态（Roo Code 的 `@` 上下文菜单支持
File / Folder / OpenedFile / Problems / Terminal / Git / URL / Mode / Command 九类；
Cline 提供逐步审批与 auto-approve；Continue 以本地 RAG 索引为卖点）。

| 要素 | 主流形态 | memora | 判定 |
|------|----------|--------|------|
| 上下文注入 | `@` 九类 + slash 命令 | `@` 命中 **0** | 🔴 真缺口 |
| 角色/模式 | Architect/Act/Ask 三档 | **角色包**（模型+策略+技能） | ✅ 优势，不追 |
| 上下文预算 | 任务级 token 与成本文字 | **占用环**可视化 | ✅ 优势 |
| 审批 | 逐步批准 + auto-approve | write-confirm + diff | 🟡 粒度待评估 |
| 任务进度 | 任务列表 | plan-bar + round-block | ✅ 已兑现 |
| 记忆/索引 | Continue 本地 RAG 索引 | 记忆是核心卖点但**对话流不可见** | 🔴 卖点未兑现 |
| 后台/中断 | proceed while running | 后台任务条 + 暂停/停止 | ✅ 已兑现 |

### 关键取舍建议：**不要盲目补 `@mention`**

memora 的哲学是「自动召回」，Cline 系是「手动投喂」，这是两条不同的路。
硬抄 `@` 会：(a) 把最强的差异化抹平成跟随者；(b) 与内核「记忆检索唯一入口」的设计
产生第二真理源（用户显式注入 vs 系统自动召回，两套上下文来源）。

**正确的补法是「补透明度，不补入口」**：让用户看见系统召回到了什么，并在需要时能纠正——
而不是让用户自己动手喂。这样既补了心智漏洞，又守住了 SSOT。

## 五、路线

| 阶段 | 时机 | 内容 | 性质 |
|------|------|------|------|
| 一 | 宿主 0.1.0 上架前 | 值守卫第 4 条断言（warning 档）；键盘可达性闭合（角色卡片详情） | 止血 + 守卫 |
| 二 | 上架后 | 组件层抽真源；~~`aria-live` 流式播报（配合协议侧）~~ → **已搁置**（2026-10-11 用户拍板：改轮级 footer 手动朗读按钮、第一版不做，登记台账 `UI-SPEAK-1`）；焦点样式守卫脚本 | 结构收敛 |
| 三 | 差异化期 | 记忆命中可视化；占用环构成化；记忆正确性反馈通道 | 兑现卖点 |

**判定原则（贯穿三阶段）**
1. **改判据的动作单独成笔、可回滚**（如值守卫、新增断言）。
2. **涉及新增可见 UI 元素的改动一律先真机确认**，不与无形态变化的修复混批。
3. **先盘后改**：任何「看起来是坏味道」的模式，先全量盘一遍再决定动几处
   （本轮 `outline: none` 13 处 → 只 1 处真违规，就是这条原则的收益）。
