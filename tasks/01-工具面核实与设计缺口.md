## 1. 六条判断逐条核实

### 判断 1：只能派活不能验收；`get_dispatch_progress` 只表达落实与否；`read_memory_summary` 是事后有损摘要；没有任何工具能读到子会话正文或产物

**结论：部分成立。**

成立的部分：

1. `read_memory_summary` 确实是**有损摘要**：
   - 单次最多 5 条轮摘要、每条最多 120 字；外加归档摘要与关键主题。
   - 证据：`workSessionTools.ts:148-152`（`MEMORY_SUMMARY_ROUND_LIMIT = 5`、`MEMORY_SUMMARY_TEXT_CHARS = 120`）、`:849-867`（工具定义）、`assemble.ts:720-741`（读口）。
2. 没有任何工具能读**产物**（改动的文件、diff、测试输出、日志）：
   - 白名单里没有 `read_file` / `run_command` / `trace_summary`（`workSessionTools.ts:177-188`）。
3. `get_dispatch_progress` 的事实边界只覆盖「宝自己派出去的活」：
   - 只读 `callerSessionId` 的账本记录（`workSessionTools.ts:1236-1240`）；用户自建、用户自己派的活不在里面（`dispatchProgressReport.ts:10-16, 243-248`）。

不成立的部分：

- 「`get_dispatch_progress` 只表达落实与否」**不成立**。它会按账本里的 `roundId` 去读目标轮的 `assistantMessage.content`，返回 **300 字交付摘录**：
  - `dispatchProgressReport.ts:282-291`（`readRound(record.roundId)` → `extractSubstantiveExcerpt(...)`）
  - 上限 300 字：`:69`（`DISPATCH_PROGRESS_EXCERPT_CHARS = 300`）
- 因此「没有任何工具能读到子会话正文」**不成立**：能读到「该轮最终助手正文的 300 字摘录」，只是不是全文、不含工具过程、不含文件产物。

仍然缺的部分（这才是验收缺口）：

- 摘录只取「实质开头」，会**主动跳过寒暄/动作预告/元信息**（`dispatchProgressReport.ts:75-153`）。如果目标轮把关键结论写在第一段「好的，已修复」之后、或结论藏在过程叙述里，摘录可能给出的是中段内容，宝据此汇报会失真。
- 交付摘录不包含「改了哪些文件、跑了什么命令、门禁结果、未闭合项」，所以宝只能转述一段话，不能验收。

**判定：部分成立**——「产物不可读」「摘要是有损的」成立；「没有任何工具能读正文」「只表达落实与否」不成立。

### 判断 2：有代答无求答；`answer_session_question` 允许替子会话回答（可能覆盖决策性内容），而编排角色没有向用户求答 / 请授权的通道

**结论：部分成立。**

成立的部分：

1. 代答工具确实存在，且**接受任意字符串**：
   - 定义：`answerSessionQuestionTool.ts:100-130`
   - 参数校验只做「键集 / 类型 / 条数」，不做语义过滤：`:141-153`
   - 空串是合法占位（「该题不答」），但**不是首选**：`:21-23, 105-107, 120-122`
2. 宝没有结构化的「求答 / 请授权」工具：
   - `ask_user` 不在白名单，且被守卫测试明确列为「技术工具不得漏进宝面」：`workSessionTools.ts:177-188`、`workSessionTools.test.ts:1801`
   - 因此宝不能像 Worker 那样挂起一个提问卡、等用户回答；它只能在**正文里问**，然后结束本轮，等用户下一轮回复。

不成立的部分：

- 「没有向用户求答/请授权的**通道**」过强。宝本身就是与用户对话的会话，正文求答是合法通道。真正缺的是：**没有结构化的提问卡、没有「等待授权」的可查询状态、没有「授权某条具体命令」的凭证**。

关键失真点（核实中发现的两处不同源）：

- 唤醒种子（发给宝的通知正文）**有**不可逆例外：
  - `webview/helpers/hostedSessionNotice.ts:283-292`：「……不可逆操作不代答、仍留用户决定，别拖到超时让子会话自己代选」。
- 但**工具描述没有**这条例外：
  - `answerSessionQuestionTool.ts:105-107`：「带选项的题应按题面与上下文选一项并说明代选理由，只有确实无法判断时才留空或转述用户」。
- 也就是说：宝被叫醒时看到「不可逆不代答」，真正调用工具时看到「有选项优先代选」——**同一纪律两个消费面，关键例外只在一处**。模型以工具契约为准时，就可能替用户拍板不可逆问题。

**判定：部分成立**——「有代答」「可覆盖决策性内容」「无结构化求答工具」成立；「完全无求答通道」不成立。

### 判断 3：缺可逆性分档；高危动作（git 写、发布类）在工具面上与普通动作无差别，无审批字段或强制确认

**结论：部分成立。**

成立的部分：

1. 宝的 10 个工具**全部** `confirmPolicy: 'audit'`（免弹窗、只落审计），没有任何一个带审批/确认语义：
   - `list_work_sessions`：`workSessionTools.ts:640`
   - `send_to_session`：`:670`
   - `stop_work_session`：`:699`
   - `pause_work_session`：`:729`
   - `resume_work_session`：`:758`
   - `create_session`：`:818`
   - `list_role_packs`：`:839`
   - `read_memory_summary`：`:866`
   - `get_dispatch_progress`：`dispatchProgressReport.ts:58`
   - `answer_session_question`：`answerSessionQuestionTool.ts:129`
2. `create_session` / `send_to_session` 的参数表里没有 `risk` / `approval` / `requiresUserConfirm` 这类字段：
   - `send` 参数只有 `{ sid, text }`：`workSessionTools.ts:660-667`
   - `create` 参数只有 `{ rolePack, title, text, paths, mandate? }`：`:789-814`
3. 「不推送、不发布；遇到先提醒；用户明确要求 = 授权」「不把推送/发布/发版这类不可逆操作交给 Worker」只是**工具描述里的文字纪律**：
   - `workSessionTools.ts:99-109`
   - 本次在 `src/` 与 `hosts/` 内检索「读该纪律并做拦截」的代码未命中（仅代表本次检索范围，未穷举全库）。

不成立的部分：

- 「高危动作（git 写、发布类）在工具面上与普通动作无差别」这个前提对宝**不成立**：宝根本没有 git/发布执行工具（`workSessionTools.ts:177-188`）。它不可能「自己执行」高危动作。

真实形态（这才是缺口）：

- 高危动作只能**外包给 Worker**；而**开活/派发契约**这一层没有可逆性字段表达「这条活含不可逆动作」。宿主因此无法在派发前按该字段拦，只能靠模型自觉遵守描述里的文字。
- **注意作用域**：可逆性判据在**命令层**是有的——`classifyCommand` / `verdict` / `ALWAYS_ASK_COMMAND_PREFIXES`（`src/security/confirmEntries.ts`），且台账 `HOSTED-CONFIRM-SOFT-1` 已把确认改成软约束。缺的不是「可逆性这一维」，是**派发契约没有把这一维传下去**。
- 后果不是「宝误操作」，而是「宝把一个含 push/发布/删数据的任务交给 Worker，且派发这一层没有任何机器闸」。

**判定：部分成立**——「无分档/无审批字段/纪律仅文字」成立；「高危动作与普通动作同面」对宝不成立（它没有这些工具）。

### 判断 4：派发无机器回执；`send_to_session`（含 `create_session`）是否返回可核对的受理凭证，如 `messageId` / 受理状态

**结论：部分成立。**

成立的部分：

- `send_to_session` 的返回类型是：
  - `{ ok: true; accepted: true }` 或 `{ ok: false; code: 'E_DENIED' | 'E_BUSY' | 'E_LOCKED' | 'E_UNREADABLE'; message }`
  - `workSessionTools.ts:199-201`
  - 宿主实现确实只回 `{ ok: true, accepted: true }`：`hostedDispatchRun.ts:379`
- `create_session` 的返回是：
  - `{ ok: true; sid: string; title: string; scopeCheck?: ScopeCheck }`
  - `workSessionTools.ts:427-428`
  - 宿主实现：`hostedSessionCreate.ts:204`（`return { ok: true, sid: sessionId, title }`）
- **没有** `messageId` / `roundId` / `ledgerId`。
- 账本内部其实有 `id` 和落定后的 `roundId`，但**不回传给模型**：
  - `dispatchLedger.ts:107-133`（记录含 `id`、`roundId`、`status`、`settledAt`、`outcome`）

不成立的部分：

- 「无受理状态」不成立：`accepted: true` 就是受理状态；失败也有明确错误码。

缺在哪：

- 模型拿到的只是一个布尔值，无法把「这一次派发」与后续的落定通知、进度报告里的某一条**精确对上**。它只能按标题/sid/时间猜。

**判定：部分成立**——「有受理状态」「无 messageId/可定位凭证」成立；「无任何回执」不成立。

### 判断 5：缺调度与在途视图；无定时/延后能力，也无「当前在跑什么、跑了多久、消耗多少」的只读面

**结论：部分成立。**

成立的部分：

1. 宝的工具面**没有**定时/延后/提醒类工具：`workSessionTools.ts:177-188`；本次在 `src` 内置工具名中检索 `schedule / timer / delay / remind` 未命中（仅代表本次检索范围）。
2. 宝无法「半小时后再检查」；它只能结束本轮，等用户下次开口，或依赖落定通知唤醒。

不成立的部分：

- 「也无在途视图」过强。已有两个只读面：
  - `list_work_sessions` 返回每条会话的 `status.kind`（running / waiting / completed / stopped / unsettled / queued / unreadable）和 `updatedAt`：
    - 类型：`workbenchDto.ts:49-57`
    - 列表项：`workSessionTools.ts:562-607`
  - `get_dispatch_progress` 对 `pending` 记录会报「还在跑（已派出 X 分钟）」：
    - `dispatchProgressReport.ts:268-275`

仍然缺的部分：

- 没有 `startedAt` / 已执行时长（只有 `updatedAt` 和「已派出多久」，后者是**派发时刻**到现在的时长，不是 Worker 实际执行时长）。
- 没有 token / 费用 / steps 进度。`WorkbenchJobStatus` 与 `WorkbenchJob` 都没有这些字段：`workbenchDto.ts:49-57, 85-93`。
- 状态读不到时只能是 `unreadable`，宝不能据此判断「空闲、可以再开一个」：`workSessionTools.ts:584`。

**判定：部分成立**——「无调度」「缺时长/消耗」成立；「无在途视图」不成立。

## 2. 真实设计缺口清单（只列核实为成立 / 部分成立的）

> 排序原则：**P0 = 会让用户得到错误结论或造成不可逆损害**；**P1 = 会造成重复劳动、返工、误判**；**P2 = 一致性与体验问题，不阻塞正确性**。

### G1（P0）验收面缺失：宝只能转述 300 字摘录，无法核产物

- **现状（证据）**：
  - `get_dispatch_progress` 能读目标轮最终助手正文，但只取「实质开头」的 300 字摘录：`dispatchProgressReport.ts:282-291, 69, 131-153`。
  - `read_memory_summary` 只有 5×120 字轮摘要 + 归档摘要：`workSessionTools.ts:148-152, 849-867`。
  - 没有 `read_file` / `run_command` / `trace_summary`：`workSessionTools.ts:177-188`。
- **缺在哪**：没有「验收证据」这一层——改了哪些文件、diff 是什么、测试/门禁跑没跑、结果如何、有没有未闭合项。
- **构造性风险（推演，未真机复现）**：
  - Worker 改了 5 个文件、跑了一条门禁但**有 2 个用例失败**，最后一段正文写「已完成主体改造，剩余小问题」。宝读到 300 字摘录，向用户汇报「已完成」。用户以为收工，实际带伤。
  - Worker 的结论写在第一段「已修复」，后面是过程叙述；摘录的「实质开头」规则跳过了第一段，宝拿到的是中段，汇报跑偏。
- **补齐优先级**：**P0**。理由：这是「用户可感知的错误结论」的直接来源，且宝的定位就是「替用户验收」，验收面缺失等于核心职责空心化。
- **2026-11-25 用户拍板：不推进（G1-A 明确不做）。** 宝的职责边界 = 转述「派下去的工作会话」的任务进度与任务情况，**不追求项目真实产物证据**（文件 / diff / 测试退出码）。现有 `get_dispatch_progress` 已覆盖该职责，300 字摘录按设计保留；宝的结论已由 `role-packs/memora宝/rules.md` 约束为「一律标待复核」，不以 Worker 自证冒充验收。

### G2（P0）代答可覆盖不可逆决策，且「不可逆不代答」只在唤醒种子、不在工具契约

- **现状（证据）**：
  - `answer_session_question` 接受任意答案，只校验条数与类型：`answerSessionQuestionTool.ts:141-153`。
  - 工具描述**没有**不可逆例外，反而要求「带选项优先代选」：`:105-107`。
  - 唤醒种子**有**不可逆例外：`webview/helpers/hostedSessionNotice.ts:283-292`（「不可逆操作不代答、仍留用户决定」）。
  - 宝没有结构化求答/授权工具（`ask_user` 被白名单排除）：`workSessionTools.ts:177-188`、`workSessionTools.test.ts:1801`。
- **缺在哪**：同一纪律在两个消费面不同源；且工具层没有「哪些题必须转用户」的机器判据。
- **构造性风险（推演，未真机复现）**：
  - Worker 问「是否删除旧迁移脚本？」「是否直接 push 到 main？」「是否把线上开关关掉？」。宝按工具描述的「有选项优先代选」选了「是」，Worker 执行。用户事后才发现——这类决策不可逆或高代价。
  - 宝想请用户拍板，但没有提问卡/授权凭证；它只能在正文问一句，用户如果没有及时看到，Worker 仍在等，最后 30 分钟超时由子会话自己代选（`askCoordinator.ts:27` 的超时文案也承认「不可逆操作仍需向我确认」，但超时路径是否真的停住，需要另案核实）。
- **补齐优先级**：**P0**。理由：直接触及不可逆损害；且现有两个提示面已经互相冲突，属于「同一纪律两份措辞，没有任何测试会红」。

### G3（P0）不可逆动作无机器分档：派发契约没有 `risk`，宿主无法强制确认或拒绝

- **现状（证据）**：
  - 10 个工具全部 `confirmPolicy: 'audit'`：见判断 3 的行号清单。
  - `create_session` / `send_to_session` 参数没有 `risk` / `approval` 字段：`workSessionTools.ts:660-667, 789-814`。
  - 「不推送、不发布」只在描述文本里：`workSessionTools.ts:99-109`。
- **缺在哪**：**派发契约**没有可逆性字段（命令层已有 `classifyCommand`/`verdict` 判据，见判断 3），宿主无法按派发维度标记或提示，也无法在 UI 上区分这条活的可逆性。
- **构造性风险（推演，未真机复现）**：
  - 宝在 `text` 里写「顺便把版本发了」，Worker 照做；系统全程没有任何闸。宝的纪律文本说「不把发布交给 Worker」，但模型可以在同一条 `text` 里绕过它，且不会产生任何错误码。
  - 用户问「刚才那条活有没有做危险操作」，宝无法从 `list` / `get_dispatch_progress` 看出这条活的 `risk`，只能重读正文猜。
- **补齐优先级**：**P0（限「加字段」这半条）**。理由：不可逆损害的兜底不能只靠提示词；这是「最小字段扩张」（加可选字段），不是新机制。
  ⚠️ **硬闸形态（宿主对 `irreversible` 直接拒 / 强制用户确认）与 2026-11-17 定案冲突，已随 `02-汇报与派发提示词优化思路.md` §3.1 降为「待拍」**——依据台账 `HOSTED-CONFIRM-AUTH-1`（🚫 已被取代）与 `docs/白话设计文档-托管模式.md` §六「为什么不硬卡」（L149）。G3 保留 P0 的只是「派发契约补可逆性字段」（用于标记与提示，不是硬拦）。

### G4（P1）派发回执无可定位标识：只有 `accepted: true`，没有 `ledgerId` / `roundId`

> **2026-11-25 核查：判闭合，不推进。** 现有 `sid`（`create` 回执自带、`send` 的入参即目标 sid）+ `E_BUSY`（目标会话在跑即拒，天然串行）足以让宝把「一条在途派发」与「它的落定通知」唯一对上；落定通知带 `targetSessionId` + `roundId`（`dispatchLedger.ts`）。补 `ledgerId` 只是第二套标识，并会让「派活回执凭证」判据分裂。前提：`E_BUSY` 语义保持不变。

> 术语区分：本条「凭证/标识」是泛指可定位 id；**术语锚点里的「派活回执凭证」是专指**（判据唯一 = `dispatchedSidTextsFromEvents` 非空），见 `terminology-anchor-rules.md` §5——两者不同指，勿混。

- **现状（证据）**：
  - `send` 返回 `{ ok:true, accepted:true }`：`workSessionTools.ts:199-201`、`hostedDispatchRun.ts:379`。
  - `create` 返回 `{ ok:true, sid, title }`：`workSessionTools.ts:427-428`、`hostedSessionCreate.ts:204`。
  - 账本内部有 `id`、`roundId`，但不回传：`dispatchLedger.ts:107-133`。
- **缺在哪**：模型无法把「这次派发」与后续落定/进度里的某一条精确对上。
- **构造性风险（推演，未真机复现）**：
  - 宝在同一轮派了 3 条活，随后先收到 1 条落定通知。通知只带目标 sid/标题，不带 `ledgerId`；宝无法判断这是哪条活的落定，只能按标题猜。若两条活派给同一会话（分两轮），更容易对错。
  - 用户问「第二条派出去的那件怎么样了」，宝只能按标题/时间排序，不能按凭证精确回答。
- **补齐优先级**：**P1**。理由：不直接造成损害，但会让汇报与对账反复出错，且修法很小（回传账本 id）。

### G5（远期 · 待拍，非本期缺口）在途视图缺关键量：无 `startedAt`、无 token/费用；「定时/延后」属定案 P3

> **性质订正（2026-11-24 评审后降级）**：本条原标 P1 且把「无定时」当缺口，与定案正面冲突——`docs/方案-memora宝设计定案-20261117.md` §一「❌ **不是常驻后台服务**……被动的」、§八 B10「memora宝 **不常驻**，`subscribed` 是 **P3 未启动**的设计预留」、§八 P3「Subscription 消费 + **被动 → 主动的演进条件设计**」。**定时 = 从被动转主动，属 P3 演进，不是本期漏做**。下文只保留「在途视图缺量」这半条可议项。

- **现状（证据）**：
  - 无调度工具：`workSessionTools.ts:177-188`（在定案口径下这是**正确形态**，不是缺口）。
  - 只有 `status.kind` + `updatedAt`：`workbenchDto.ts:49-57, 92-93`；`get_dispatch_progress` 的「已派出 X 分钟」是派发时刻起算：`dispatchProgressReport.ts:268-275`。
- **缺在哪（仅存的可议半条）**：没有「实际开始执行的时间 / 已执行时长 / 消耗」，无法区分「排队 35 分钟 + 执行 5 分钟」。
- **构造性风险（推演，未真机复现）**：
  - 用户问「这件事跑了多久、花了多少」。宝只能报「已派出 40 分钟」，无法报 token/费用——成本透明度不足。
- **补齐优先级**：**远期 / 待拍**。理由：① 定时侧已被定案 P3 排除，本期不议；② `startedAt`/消耗涉及内核是否采集，属「加可选字段」但需先确认数据源，按「零样本原则」未确认采集面之前不改对外契约。

### G6（P1）上下文回读不对称：常规读面读不回 `mandate/workOrder` 与 `declaredPaths`

- **现状（证据）**：
  - `create_session` 的 `mandate` 会落成 `SessionMeta.workOrder`：描述 `workSessionTools.ts:810`；宿主写入 `chatPanel.ts:2925-2933`；内核字段 `src/memory/sessionStore.ts:170-186`。
  - 但 `list_work_sessions` 的 `WorkSessionBrief` 只有 8 个字段（sid/title/summary/updatedAt/status/createdBy/rolePack/lastDispatch），**没有 `workOrder`，也没有 `declaredPaths`**：`workSessionTools.ts:562-607`。
  - `read_memory_summary` 也不含这两项：`:381-392`。
  - 唯一回读点是 Worker **主动交回**时随通知带出的 `workOrder`：`webview/helpers/hostedSessionNotice.ts:315-325, 580-581`（`noteHandBack` 读 `SessionMeta.workOrder` 拼进「原派活边界」）。`declaredPaths` 连交回通知也不带。
- **缺在哪**：常规只读面（list / read_memory_summary）读不回边界，跨轮/重启后宝无法**主动**确认自己当初给这条活定的范围；`declaredPaths` 的**模型可见面**没有（宿主侧已有回读做范围门禁：`assemble.ts:777` 的 `readDeclaredScopes`，缺的只是给模型看的那一面）。只有 Worker 恰好交回时，才顺带看到 `workOrder`。
- **构造性风险（推演，未真机复现）**：
  - 宝给会话 A 定的 `mandate` 是「只修权限校验，不做权限系统重构」。三轮后用户说「继续推进 A」。宝已经记不清边界，只看到 `lastDispatch` 摘录，于是又派了一条含重构的活，Worker 按新指令越界。
  - 宝想给新活声明 `paths` 避让正在跑的活，但 `list` 不返回那些活的 `declaredPaths`；它只能先试一次，等 `E_SCOPE_CONFLICT` 再改，反复试错。
- **补齐优先级**：**P1**。理由：会造成越界与重复试错；修法是把已有字段投影到列表，不需要新持久化。

### G7（P1）复用判据自相矛盾：`summary` 只在归档时生成，描述却说「没摘要的会话不许被路由」

- **现状（证据）**：
  - `list_work_sessions` 描述：「`summary` 是判断复用与否的主依据；`null` = 没有归档过摘要……**没有摘要的会话不许被路由**」：`workSessionTools.ts:621-623`。
  - `summary` 由 `SessionArchiver` 在**会话切走 / 分叉离场 / 暂停超时**时归档生成：`src/memory/sessionStore.ts:93-96`、`src/agent/builtinToolHandlers.ts:1818`（归档触发源见 `src/agent/managers/archiveCoordinator.ts:5-6`）。
  - **首次归档前**的会话 `summary` 是 `null`；**归档后继续跑**的会话则是**陈旧非空**（L1818 原文是「当前会话（尚未离场）的摘要**可能落后于最新对话**」，不是「一定是 null」）——两种失真方向相反。
- **缺在哪**：判据与数据生成时机冲突。宝严格照做，就会把所有「首次归档前」的会话判成「不可路由」，倾向新建；反过来，归档过的陈旧摘要又会被当成新鲜判据。
- **构造性风险（推演，未真机复现）**：
  - 用户说「接着刚才那件事继续」。那条会话 status=completed、lastDispatch 有内容，但 summary=null。宝按描述「没有摘要不许路由」，新建一条会话重新做一遍；两条会话对同一目标并行/重复。
  - 同一任务被拆成多条重复会话，`paths` 冲突门禁还可能挡住新会话，宝再缩范围绕开，用户看到两条半成品。
- **补齐优先级**：**P1**。理由：直接制造重复劳动与工作区混乱，且修法可以是「改判据措辞 + 允许按 status/lastDispatch 路由」或「按需生成归档摘要」。
- **修法注意（保留原判据的防护意图）**：「没有摘要不许被路由」这句是有意设的闸——防的是「标题不可定夺就硬路由」（见 `artifacts/审查-memora宝九条行为判据交叉核对-2026-11-20.md` P2 的同源记录）。修法**不是简单放开**，而是把判据改成「`summary` **或** `lastDispatch` 至少一项可核才路由」，两样都没有仍不许路由。

### G8（已定未落地，非新缺口）宝没有专属系统段；角色包继承无机器保证

> **性质订正（2026-11-24 评审后改指）**：「宝没有专属系统段」**不是新缺口**，是定案**已定、尚未落地**的项——`docs/方案-memora宝设计定案-20261117.md` §八 H1「① **新建 memora宝 role pack（封闭工具面）**」、§八 P1。本条只保留其中**未被定案覆盖**的半条：角色包继承无机器保证（见判断 6）。
>
> **2026-11-25 核查与拍板（本条收口）**：① 专属系统段**已落地**——`role-packs/memora宝/` 的 `persona.md` + `rules.md` 在册，真机确认助手会话绑定 `memora宝`；② 角色包继承**明确不做**——与台账 `ROLEPACK-NO-INHERIT-1`（2026-11-24 已钉死：子会话不继承父包，零代码，现状即契约）一致，不再列「待拍」，重开条件沿用该条。

- **现状（证据）**：
  - 无「memora宝」专属 role pack：见 `role-packs/*/manifest.json`（清单以该 glob 为准，本文核实于 `017161d2`；**不落具体包数**——计数是时点快照，每次增删即过期）。
  - 装配层给 Worker 注入了 hand-back 段（`assemble.ts:601-604`），但**没有发现宝专属的 L1 系统段**；宝侧的作业规范只散落在工具描述 `WORK_SESSION_TOOL_DISCIPLINE`（`workSessionTools.ts:99-109`）。
  - `rolePack` 必填但没有「继承」字段（见判断 6）。
- **缺在哪**：宝的汇报结构、证据标准、派发颗粒度没有单点承载；换用户/换角色包/换模型就会漂移。角色包「子承父」也没有机器保证。
- **构造性风险（推演，未真机复现）**：
  - 同一个宝，今天用「memora助手」包汇报得很散，明天换一个包突然开始长篇大论；用户感知是「同一个助手水平不稳定」。
  - 宝凭记忆给子会话选了一个能力更弱的包，Worker 缺工具做出半成品，宝在汇报里说「已完成」。
- **补齐优先级**：**P2**。理由：不直接造成错误结论，但它是「汇报/派发不专业」的根因之一，且修法可以先做纯提示（零协议变更）。

| 3 | 子会话禁用名单 `SUBAGENT_DENIED_TOOLS` | `toolExecutor.ts:665` 起；`assembler.ts:1455-1457` | **手写名单**（减法） |
| 4 | 常驻集（所有角色包无条件可见） | `toolExecutor.ts:596-629` 注释段 | **手写名单**（加法例外） |

**结论**：同一个问题（「这个会话能用哪些工具」）有四种写法、四份名单。加一个工具要改四处，漏一处没有任何测试会红——这正是本仓定义的「自然生长 vs 堆砌」分水岭（`single-truth-source-mindset.md` §自然生长）。

### 7.2 拍板：分组住在工具定义里，按 `kind` 派生默认组（多轴取交集，只收紧不放行）

**三条原则**（第一条是 ADR-045 已经定过的，不是新说）：

1. **默认全开，只有明确禁止才关闭**——ADR-045 §1 原文：「所有角色包工具类控制统一遵守『默认未定义 = 全开，只有明确禁止才关闭』」。
2. **组是授权单位，单个工具是禁用单位**：组决定「你是什么工种」，禁用表决定「这个工种里哪几样不给你」。
3. **分组住在工具定义里（唯一处）**，角色包只做选择——禁止在角色包或新文件里再手写一张「工具→组」分类表。

**关键实现约束（排雷结论）**：`toolExecutor` 既有的 `setDenyTools` 与 `setToolAllowOnly` **彼此语义互斥、同时调用会直接抛错**（`toolExecutor.ts` 的两个 setter 首段守卫，测试 `src/agent/__tests__/toolExecutor.test.ts`）。**新组面刻意不加入这对互斥**（落地订正见下方 blockquote）：组面与它们取交集，不抛错、不互相清除。

**`kind` 只决定「组谓词怎么过滤」，不决定「用哪一条轴」**：

| kind | 工具面怎么表达 | 为什么这样选 |
| --- | --- | --- |
| `work` | 默认**不设任何工具面**（ADR-045 默认全开）；仅当声明了 `disableGroups`/`disableTools` 时按组谓词过滤 | 存量零变化，不碰动态注册的自定义/MCP 工具 |
| `assistant` | `orchestrate` 组白名单（同一套组谓词） | 封闭面方向朝拒绝，后注册的工具天然在外 |

> **落地订正（2026-11-24 实施后回写）**：新引入的「组面」**不与既有两个 setter 互斥**。原设想「同时设置即 throw」在实现中暴露出一条真实 fail-open 路径：宿主 `allowOnlyTools` 只在装配期设一次（`assemble.ts` 传 `AgentOptions.allowOnlyTools` → `assembler.ts` 调一次 setter），运行期无人重设；若组面启用时顺手把它清成 `null`，切回 `work` 包没有任何地方能恢复 ⇒ 宿主封闭面被永久炸开。故改为**三轴取交集**：组谓词**只做否决、不做放行**（`allowedGroups` 外一律挡掉，组内继续走既有链），任意切包顺序都不需要保存 / 恢复上一轴的值。「一个会话只有一个工具面判据」由此改为「多条收紧判据取交集，方向恒朝拒绝」——交集不是第二个真源。收敛路径不变：终态只剩组面一条轴。

**硬约束：组过滤必须是「查询期谓词」，不得在装配期展开成名字清单。** 判据落在 `isToolExposed` 一处，按 `tool.group ?? 'act'` 现场判：

- agent 运行期会经 `registerTool` 注册宿主工具（含 MCP，`mcp/toolRegistry.ts:461`），时刻在装配之后；
- 装配期展开 = 静态快照 ⇒ 晚注册的工具漏出。白名单方向漏出是 fail-closed（被摘），**禁用方向漏出是 fail-open（禁了却还在）**——后者正是用户最不能接受的失效方向。

**单一来源的优先规则（同处判据链，取交集）**：会话的激活角色包**声明了 `kind`** ⇒ 内核按组谓词派生正向组，组外工具一律挡掉；宿主传入的 `allowOnlyTools` 仍保留、仍参与交集（结果只会更窄，不会更宽）。**未声明** ⇒ 不产生组限制，沿用宿主传入集合（存量行为零变化）。**禁止在装配期清除 `allowOnlyTools`**：宿主只在装配期设一次、运行期无人重设，清除即不可恢复（见上方落地订正）。

> **本版删掉了早先设想的 `enableGroups`（2026-11-24 实核后自撤）**：`kind` 已经唯一决定默认组，再加一个「显式启用组」的键，只为「将来给助手包开只读组」这一种尚未发生的场景留口——那是**预留键**，而预留键在 schema 里与僵尸键只差一次遗忘。将来真要开，改的只是「`assistant` 的默认组派生」一行，不需要新键。**不加 = 当前少一个无人消费的字段。**

### 7.3 三个组

| 组名 | 语义 | 典型成员 | 默认归属 |
| --- | --- | --- | --- |
| `readonly` | 只读工具（**不改盘、也不改会话运行状态**） | `read_file` / `list_dir` / `search_memories` / `trace_summary` / `web_search` | 工作包 |
| `act` | 能动手的工具（改盘 / 执行 / **挂起会话**） | `write_file` / `delete_file` / `run_command` / `run_project_script` / `run_skill_script` / `ask_user` / `delegate_task` | 工作包 |
| `orchestrate` | 会话管理工具 | `create_session` / `send_to_session` / `list_work_sessions` / `get_dispatch_progress` / `answer_session_question` | 助手包 |

> **几个容易分错类的工具，这里先定死**（否则实施时会各人各判）：
> - `ask_user` 归 `act`：它不写任何东西，但**挂起整轮会话**（`toolExecutor.ts:646`）——组的判据是「会不会改变状态」，不只是「会不会改盘」。
> - `delegate_task` 归 `act`：它自身不落盘，但能间接导致子会话动手（子会话另有独立三重只读约束，与分组正交，`toolExecutor.ts:624-628`）。
> - 同理 `task_table_write` / `task_table_update` / `remember_intel` / `register_work` / `compress_context` 归 `act`；判据是「改内容」而非「改盘」——`diskWrite:'none'` 不等于无副作用（`toolExecutor.ts:657-661` 已把这条界线写死）。

**角色包分类 `kind`**（新增顶层可选字段）：

| kind | 默认组 | 说明 |
| --- | --- | --- |
| `work`（缺省；无 `kind` 的存量包一律按此解析） | `readonly` + `act` | 与现状 `toolReadonly='full'` 行为一致，存量零变化 |
| `assistant` | `orchestrate` | **按现有定案 S1「Router 不配技术工具」：不给 `readonly` 组** |

> **助手包为什么不给只读工具（2026-11-24 用户拍板）**：先按现有定案，保持「宝纯调度」。因此 01 的 G1（宝读不到产物验收）**仍然成立、不因本节消失**。将来若要给助手包开只读组，改的是「`assistant` 的默认组派生」一处（加 `readonly`），不改字段结构。

### 7.4 为什么不能靠现有 `readonly` 标记自动分组

工具定义里已有 `readonly: true`（`builtinTools.ts:52`）和 `diskWrite`（`builtinTools.ts:68`），但**两者都不足以派生三组**：

- `ask_user` 声明 `readonly: true`，却会在 loop 层**挂起整个会话**（`toolExecutor.ts:646`）——它不是纯只读。
- `search_memories` 声明 `readonly: true`，命中即 `UPDATE accessedAt`（SQLite 真写，`toolExecutor.ts:659`）。
- `diskWrite: 'none'` 的工具里混着`task_table_write`（改任务表状态）、`remember_intel`（写情报区）。

⇒ **必须给每个工具显式标 `group`**，`group` 是唯一分类真源；**缺省 fail-closed 归 `act`**（最保守），与 `diskWrite` 的 fail-closed 范式一致（`builtinTools.ts:59-61`：漏声明不得被静默当成无害）。

### 7.5 落地形态（最小面）

**工具定义**（`ToolDefinition`，`src/agent/builtinTools.ts`）新增一个可选字段：

```ts
/** 角色包授权单位（唯一分类真源）；缺省 fail-closed 归 'act'，必须显式标 readonly/orchestrate */
group?: 'readonly' | 'act' | 'orchestrate';
```

> 加在 `ToolDefinition` 而不是「内置工具专用」是有原因的：宿主注册的领域工具走的是**同一个类型**（`registerTool(definition: ToolDefinition, …)`），而 `orchestrate` 组的成员恰恰全由宿主注册。宿主现在就在同一位置传 `readonly` / `diskWrite` / `confirmPolicy`（`workSessionTools.ts:612-614` 起的定义块），加 `group` 是同一形态的自然延伸，不需要另开通道。

**角色包 manifest**（`strategy.act` 下，全部可选）：

```json
{
  "kind": "assistant",                 // 顶层键：work | assistant（缺省 work）
  "strategy": { "act": {
    "toolReadonly": "full",            // 保留：执行期只读闸，与分组正交
    "disableGroups": ["act"],          // 可选：整组关闭（暴露期摘除）
    "disableTools": ["run_command"]    // 可选：单个关闭（暴露期摘除）
  } }
}
```

> 键位不是随手放的：`disableGroups`/`disableTools` 归 `strategy.act`，因为**工具面策略本来就在那儿**（`toolMode` / `toolReadonly` / `toolStepLimit`，`types.ts:74-98`）——这是自然生长，不是新开一块。`kind` 则必须留在顶层：它描述的是「这个包是什么工种」，不是行为开关，塞进 `strategy` 会让「角色包类型」与「行为偏好」混为一谈。

- `toolReadonly` **不删，但两层的分工要说清**：它是**执行期**闸门（`toolRunner.ts:186-201`，查「全部工具定义」而非暴露面，调用时拒绝并回 `[ERR:TOOL:READONLY_DENIED]`）；`disableGroups`/`disableTools` 是**暴露期**摘除（模型根本看不见）。对「纯只读包」，正确用法是 `disableGroups: ['act']`——让模型看不见写工具，而不是让它看得见再被拒（后者白烧 step）。`toolReadonly` 保留用于宿主级 override 通道收紧。
- 三个组键是**字符串数组**，因此有两处结构性错配必须先解决：
  1. **不能进 `PERMISSION_FIELD_LENIENCE`**——该秩表的值域是 `(value) => number | null` 标量（`strategyResolver.ts:380-393`、裁决函数 `:416-432`），表达不了「集合谁更严」。
  2. **更不能走 `mergeActStrategy` 的浅合并**——`{...base, ...override}` 是「覆盖侧整体胜」（`:449`），对禁集而言等于**放松**（覆盖侧可以整份替换掉下层已禁的项）。正确语义是：**禁集取并集**（各层禁的都禁），且该合并天然只收紧、无放宽路径。

**落地陷阱（2026-11-24 逐条实核，改动前必读）**：

| # | 陷阱 | 实证 | 漏了会怎样 |
| --- | --- | --- | --- |
| 1 | `kind` 是**顶层 manifest 键**，受 `MANIFEST_KEYS` 放行，与策略键是两套登记表 | `validator.ts:42-56`（顶层已知键集）、`rolePackManager.ts:800-815`（meta 解析） | `kind` 被按「未知键 warning + 忽略」处理 ⇒ `assistant` 包**静默当 work**，直接拿到写盘/执行工具（fail-open） |
| 2 | `kind` 显式非法值必须 **error**，不能照 `interactionType` 的 `=== 'companion' ? … : 'tool_assistant'` 静默折叠 | `rolePackManager.ts:807` | 拼错 `"assisstant"` 不报错、退回 work ⇒ 同上 |
| 3 | 数组键必须**同时**登记 `STRATEGY_KEY_RULES`（校验）与 `describeStrategyKeys()` 的渲染分支 | `strategyKeys.ts:242-311`、`:205-235`（无专属分支的键落到 `kind:'number'`，`:230`） | 校验不生效（warning 放行）+ 宿主 UI 把数组渲染成**数字输入框**（假 UI 面，比不显示更糟） |
| 4 | 常驻集与内置工具必须**逐项**标 `group` | 常驻集 `toolExecutor.ts:596-629`；组判据在 `isToolExposed`（`:765-767` 处是既有 allowOnly/常驻集判据） | 未标 ⇒ 缺省归 `act`：**本该是 `orchestrate` 的新工具落进 `act` ⇒ 助手包看不见它**（fail-closed 但静默）；本该是 `readonly` 的落进 `act` ⇒ 纯只读包把它一起禁掉 |
| 5 | `capabilities` 不是这套机制的竞争者，别合并 | 唯一消费面 = 子会话授权 `resolveSubagentCapabilities` → `setToolWhitelist`（`assembler.ts:345-356`、`:380`、`:401`） | 把两个作用域折叠成一个词 ⇒ 读者以为主会话也受 capabilities 约束（实为只管子 agent） |
| 6 | `interactionType`（拟人化：`tool_assistant`/`companion`）与 `kind`（工具面）是**两根正交轴** | `rolePackManager.ts:807` | 合并成一个枚举 ⇒ 将来「拟人化的工作包」无处表达 |

> ⚠️ 第 4 条的真源是「`isToolExposed` 首行先判 allowOnly，再判常驻集」——这一点由 `:765-767` 的注释明确写出（「否则写工具漏进来」）。**上线前须逐项过一遍常驻集名单**，不能只标新工具。

> 归纳一句话：本节的键落在**两套不同的登记表**——`kind` 在 `MANIFEST_KEYS`，三个组键在 `STRATEGY_KEY_RULES`。**只登记一处 = 另一处静默失效**（一个不报错、一个被忽略），而这两类失效都不会让任何测试变红。

### 7.6 验收锚点

1. 新增工具未标 `group` ⇒ 单测红（防漏配，同 `diskWrite` 的 fail-closed 测试范式）。
2. `kind` / 组名写错 ⇒ **error**：两者都是闭集枚举，validator 静态可判。注意 `MANIFEST_KEYS`（`validator.ts:42-56`）只负责「不把它当未知键忽略」，取值枚举校验要**另加**在顶层字段校验里。
3. **未知工具名必须另判，且失败方向朝拒绝**：validator 是纯函数、无 IO，拿不到宿主工具注册表 ⇒ 它**判不了**工具名拼写。必须在装配期（能读到 `toolExec.list`）对照判：拼错的 `disableTools` 若被静默忽略 = **用户以为关了、实际开着**（fail-open），所以装配期须报错而非放行。
4. 无 `kind` 的存量角色包解析后工具面与改动前**逐项相等**（快照测试，防「升级顺带改了别人」）。
5. `kind: assistant` 解析结果 = 只有 `orchestrate` 组，且 `readonly` 工具不可见（守住定案 S1）。
6. **多轴取交集、互不清除**（2026-11-24 落地订正，原写「同一会话只启用一条轴」）：`work` 包未声明 disable 时**不设组面**（断言 `setDenyTools` / `setToolAllowOnly` / `setToolGroupSurface` 均未被调用）；`assistant` 包断言组谓词把 `act` / `readonly` 组工具全挡掉；**且宿主已设的 `allowOnlyTools` 在切到 `assistant` 再切回 `work` 后原样存在**（组面不得清除它——清了就无人能恢复，宿主封闭面永久炸开）。
7. 禁集跨层合并 = **并集**：base 禁 A、override 禁 B ⇒ 最终 A 与 B 都禁（防「覆盖侧整体胜」把下层禁用项冲掉）。
8. `describeStrategyKeys()` 对组键输出**非** `kind:'number'`——宿主 UI 面的守卫（2026-11-24 订正：本条原写「三个组键输出 `kind:'multi'`」，与实现不符——`enableGroups` 已在 §7.2 自撤，实际只有两个键；且 `disableTools` 是开放集（内置 + 宿主 + MCP + 自定义），枚举不出全集、画不出多选框，只能 `kind:'text'`（逗号分隔）；`disableGroups` 才是三组闭集 → `kind:'multi'`）。
9. **退役等价性**：宝切到 `kind: assistant` 后，内核派生集必须与旧 `ORCHESTRATOR_ALLOWED_TOOLS` **逐项相等**（不等 ⇒ 分组表漏标，改表而不是改名单）。

| 2 | **默认全开 + 禁用表**在窄角色下会随新能力自动扩面（fail-open） | 新装 MCP / 新增内置工具默认可见 | 不再加第三套具名白名单（组面已是一道正向收紧，再手写一张工具名表就是并列的第二真源）；登记风险：窄角色的禁用表须随能力增长复核。浏览器角色包用「全局 MCP + `disableTools`」实现，不需要白名单 |
| 3 | **包内工具不能拿 `run_skill_script` 当执行入口** | 它是内置工具（可被禁用）、且无参数 schema（`builtinTools.ts:943-949`） | 走 `registerTool(definition, handler)`，装配期**直接绑定执行器** |
| 4 | **同名冲突不需要新策略** | `registerTool` 已拒「与内置同名」「重复注册」，均抛错（`toolExecutor.ts:1049-1082`） | 沿用 fail-closed 拒绝；不做「包内覆盖全局」 |
| 5 | **生命周期已有唯一落点** | `switchRolePack()` 是唯一切换入口，已调用 `applyRolePackToolExposure()`（`agent.ts:1744-1760`）；`removeTool()` 支持注销并触发 `onToolsChanged`（`toolExecutor.ts:1095-1100`） | 注册/注销挂在 `applyRolePackToolExposure()` 内 |
| 6 | **两档模式靠组谓词区分，不靠并列两套面** | §7.2 已定 `work` 组面可空 / `assistant` 只留 `orchestrate` 组，且与宿主 `allowOnlyTools` 取交集 | 用户说的「默认全开 + 单选关闭」适用于 `work` 包；`assistant` 维持只留编排组 |
| 7 | **包内工具 = 合法的代码执行入口** | 与 `run_skill_script` 同族：内核拿不到正文、字符串判据管不住 | 未批准不注册；批准记录见 8.4 |
| 8 | **子会话隔离不需要新设计**（原以为会泄漏，实核否定） | `createSubagentToolExecutor` 是**全新实例，不继承宿主 customTools / MCP 注册表**（`assembler.ts:364-371`） | 包内工具天然进不了子会话；**补一条守卫测试**防将来有人改成继承 |
| 9 | **声明载体不能另开目录**（否决上一条回复里「倾向独立 `tools/` 目录」） | `manifest.json` 是角色包的**唯一权威控制文件**（`types.ts` 文件头） | 工具声明**内联进 `manifest.tools`**；独立目录会让「包有哪些工具」的真源漂移到目录内容 |
| 10 | **批准记录不能只按包名** | 包更新 = 新代码；只按包名记，新增工具会被自动批准（fail-open） | 按 `{ packName, toolName, scriptHash }` 记；hash 变即回到未批准 |
| 11 | **同一能力不得双入口** | 声明为工具后，脚本仍可被 `run_skill_script` 调，模型有两条路、两套参数契约 | 纪律：声明为工具即不再在 skill 说明里教模型走脚本入口（无自动测试，登记） |
| 12 | **`capabilities` 不参与** | 它是**子会话授权面**（`assembler.ts:380-401`），而包内工具进不了子会话 | 无需在 capabilities 里表达包内工具；两轴不折叠 |

### 8.2 拍板：声明形态（内联进 manifest）

```json
{
  "name": "memora-browser",
  "tools": [
    {
      "name": "browser_open",
      "description": "打开网页并返回可读文本",
      "group": "act",
      "readonly": false,
      "parameters": { "type": "object", "properties": { "url": { "type": "string", "description": "…" } }, "required": ["url"] },
      "impl": { "type": "script", "path": "scripts/browser.mjs" }
    }
  ]
}
```

- **为什么内联而不是 `tools/*.json`**：`manifest.json` 是角色包的唯一权威控制文件；另开目录会让「这个包有哪些工具」的真源从 manifest **漂移到目录内容**（SSOT 破口）。内联后校验、装配、来源追溯在同一处完成，零新增扫描路径。
- **为什么与 `skills` 形态不同**：skill 正文是整篇 `SKILL.md`（长，必须外置 + manifest 引用）；工具定义只有名字/描述/参数 schema（短），内联不撑爆。
- **`impl` 本期只支持 `script`**：`path` 指包内 `scripts/` 文件；不做「包内模块导出」等第二种形态。
- **`group` 缺省 `act`**、**`readonly` 缺省 `false`**（沿用 §7.4 与 `builtinTools.ts:52` 的 fail-closed）。
- **模型眼里包内工具与全局工具无区别**：同一个 `ToolDefinition`、同一套 `group` 判据、同一个工具名空间——差别只在注册时机与生命周期，这正是照抄 skill 的「全局 / 包内」两档结构。

### 8.3 拍板：执行形态（复用既有真源）

- **超时 / 输出截断 / 结果格式化**：直接复用 `skillScriptRunner` 的既有真源（默认 60s 超时、2MB 采集上限、`formatExecutionResult` 统一格式化），不另写一套。
- **参数与结果契约**：`stdin` 收 JSON（模型传入的 args），`stdout` 必须输出 JSON；非 JSON 按工具错误返回（**不回原文**——原文会被模型当成正确结果解读）。
- **路径守卫**：`impl.path` 装配期解析后必须仍在包目录内，逃逸即装配 **error**（不是 warning）。
- **执行器绑定在装配期完成**；`run_skill_script` 仍是通用脚本入口，不承担包内工具分发。

### 8.4 拍板：生命周期与安全闸

- **注册/注销挂在 `applyRolePackToolExposure()`**：先清旧包的包内工具，再注册新包的；不新开切换入口。
- ~~**只在无进行中轮时变更工具表**（否则延迟到轮结束）~~ **已自撤（2026-11-24 实施期排雷 R3）**：延迟队列需要「轮结束时谁来重试」的新钩子，漏一处就是**静默不生效**（用户以为切了包、工具表没变），比它想避免的「进行中 step 持旧快照」竞态更危险；且现有 `registerTool` / `removeTool` 的语义就是立即生效 + `onToolsChanged` 刷新快照（MCP 工具停用走的同一条路），包内工具与 MCP 同族，生命周期必须一致。竞态边界按 `removeTool` JSDoc 既有登记处理。
- **批准记录 = `{ packName, toolName, scriptHash }`**：未批准的工具不注册；脚本 hash 变即回到未批准（包更新不能继承旧批准）。
- **~~本期不做宿主 UI~~ → 补「最小写入路径」（2026-11-24 排雷 R1）**：原写「不做 UI」+「未批准不注册」相加 = 没有任何路径能产生批准记录 = 包内工具永远不注册 = 整节功能为零。本期补：内核注入口 `setRolePackToolApprovals()`（与 `setToolWhitelist` 同族）+ 宿主一条原生命令（QuickPick 勾选当前包未批准工具，写入 `memora.approvedPackTools`）。**不做的是配置面板 UI**，不是写入路径。

### 8.5 与 §7 的关系（勿折叠）

- §7 的 `group` **不变**：包内工具也标三组之一，所以被 `disableGroups` 整组关掉是**正确**行为；「包内专属」不等于「关不掉」。
- §7 的 `kind` **不变**：`assistant` 包即使带包内工具，也只看到 `orchestrate` 组——包内工具标 `act` 就进不来。这是「助手包结构性不碰技术工具」的延续，不需要为包内工具开例外。
- 来源（全局 / 包内）与分组（readonly / act / orchestrate）是**两根不同的轴**：前者决定「谁注册、何时注销」，后者决定「这个工种能不能用」。上一轮把两根轴合并成可见性公式是错的，本节已回到「一根判据 + 一根元数据」。

### 8.6 落地顺序（排在 §7 之后）

1. **先做完 §7**（贴 `group` → 加 `kind` → 宝的名单退役）。理由：分组真源没立住就引入包内工具，四份手写名单会变成五份。
2. **再加包内工具**：解析 `manifest.tools` → 装配期 `registerTool` → 切包时 `removeTool` + 重注册 → 未批准不注册。
3. **最后评估**是否把子会话名单也迁到组表达（§7.7 #1），那时才可能只剩一条判据。

### 8.7 验收锚点

1. 包内工具与全局工具同名 ⇒ 装配报错（不静默覆盖）。
2. `switchRolePack` 后旧包工具**不残留**：切走再切回，工具表逐项相等。
3. 包内工具标 `readonly: true` 时，`toolReadonly: 'readonly'` 下可调用；标 `false` 时被拒。
4. `assistant` 包内的 `act` 工具不可见（§7.5 锚点 5 的延伸）。
5. 未批准的包内工具**不注册**（fail-closed）。
6. 子会话工具表**不含任何包内工具**（守卫测试：断言 `createSubagentToolExecutor` 不继承 customTools）。
7. `scriptHash` 变化后，同一工具回到未批准态。
8. `impl.path` 逃逸包目录 ⇒ 装配 error。
9. `manifest.tools` 里坏 JSON / 缺 `name` / 未知 `group` ⇒ error（不是 warning）。
10. **（R2）包内工具无论 manifest 怎么写，装配后 `confirmPolicy === 'audit'`**——包作者不得自选不过闸。
11. **（R7）包内工具不受 `capabilities` 白名单过滤，但能被 `disableTools` / `disableGroups` 关掉**（与 MCP 工具同族判据链，`isToolExposed` 顺序决定）。
12. **（R9）同名冲突预检失败 ⇒ 该包**所有**包内工具都不注册（不留半注册），且日志逐个报出冲突名**；包其余部分（人格 / 策略）仍生效。

### 8.8 明确不做（本期）

| # | 事项 | 理由 |
| --- | --- | --- |
| 1 | 独立 `tools/` 目录 | 会让「包有哪些工具」的真源从 manifest 漂移到目录内容 |
| 2 | 包内引用 MCP 配置（`impl.type: 'mcp'`） | 全局 MCP + `disableTools` 已能实现「浏览器角色包」；按包启用需改造全局注册，成本不成比例 |
| 3 | 给 `work` 包可选的白名单模式 | §7 已定 `kind` 只派生默认组，不引入第二套具名白名单；再加一档会让「默认全开」出现两种语义 |
| 4 | 包内工具覆盖内置同名 | 现行为已 fail-closed 拒绝，隐式覆盖不可追溯 |
| 5 | 工具 / 脚本双入口 | 同一能力两套参数契约，模型行为不可预测 |
| 6 | 首次启用的宿主配置面板 UI | 本期只做「未批准不注册」的行为闸 + 一条 QuickPick 批准命令；面板随技能启停同族后续补 |
