## 二、阶段切换信号

### 2.1 当前阶段：v2 收尾期（已进入）

**特征**：5 大维度闭环，无 P0/P1 待办。
**时长**：1-2 周（等用户真实使用反馈）。

### 2.2 下一阶段：用户验证驱动期

**触发信号**：用户主动报告新 bug 或新需求。
**特征**：被动响应模式，用户反馈 → 速修 → 提交前审查。
**时长**：不定（持续到累计 3+ 项"仅记录"被用户主动激活）。

**时长**：1-2 周。

**触发信号**：v3 蓝图确认 + 架构预研完成。
**特征**：实施新功能（插件化 / 多 Agent / E2E 等）。

## 三、用户验证驱动期策略

### 3.1 核心原则

> **没有用户反馈的任务都是猜的**——v2 主动打磨阶段已结束，后续任务应由真实使用驱动。

| 原则 | 说明 |
|------|------|
| 被动响应 | 不主动找任务，用户报告才修 |
| 速修优先 | bug 用 [big-tree-grower 速修模式](../.trae/skills/big-tree-grower/SKILL.md)，根源修复 |
| 评估升级 | 用户反馈密集涌现某个领域时，触发架构评估（v3 准备期信号） |
| 反模式警惕 | 拒绝"我觉得还应该做 XXX"——没有真实使用依据不做 |

### 3.2 反馈处理流程

```
用户报告问题
  ├─ bug → 速修模式（根源修复 + 测试 + 提交前审查）
  ├─ 体验问题 → 问诊模式（评估 + 二选一判定）
  ├─ 新需求 → 评估是否触发 v3 准备期
  │   ├─ 已在"仅记录"中 → 直接进入 v3 准备期
  │   └─ 全新需求 → 补登"仅记录"，等累计 3+ 再激活
  └─ 性能问题 → 性能基准测试 + 优化（提示词 I）
```

### 3.3 任务清单维护

- 新发现的 bug 速修后归档至 [归档/](./归档/)
- 新发现的观察项补登 [待完成任务.md](./待完成任务.md) 对应章节
- "仅记录"章节累计新增 v3 候选时，更新本文件 §四 v3 准备期蓝图

## 六、迭代提示词模板

### 提示词 F · 用户验证驱动的 bug 收敛（自然生长触发）

> **触发时机**：用户报告新 bug
> **执行模式**：速修 → 提交前审查

```
你是一名资深程序员，对 memora-sprite 执行 bug 速修。执行模式：速修 → 提交前审查。

【任务】
用户报告问题：{问题描述}

【资深程序员心智模型（必读）】
1. 区分症状与根因——用户报告的是症状，多问一层"是什么导致了这种现象"。修复现象是止痛药，修复根因才是手术。
2. 识别不可逆损失点——某些损坏不可逆（信息永久丢失、状态不可恢复）。不要在已损坏数据上做恢复逻辑，要找到产生损坏的上游环节并切断。
3. 怀疑前提——当一个机制反复出问题、需要反复修补时，停下来问：这个机制本身是不是错误的选择？
4. 每次只修一个根因——一次提交修复一个独立问题。叠加修复优于大包大揽：每一步可验证、可回滚。

【关键约束】
- 不做范围外"顺手优化"（v2 §7.6.1）
- 修复独立可回滚（每次修复独立提交）
- 内核零依赖原则不变
- 测试覆盖率不下降

【输出要求】
1. 先输出根因分析（现象 → 多问一层 → 根因）
2. 输出修复方案（涉及文件 + 改动点 + 风险）
3. 用户确认后实施：根源修复 + 补测试
4. 运行内核 `npx vitest run` + 精灵 `cd hosts/memora-sprite ; npx vitest run`
5. 提交前审查收尾
6. 更新 tasks/待完成任务.md 状态
```

> **触发时机**：用户主动激活"仅记录"中的 v3+ 任务
> **执行模式**：问诊 → 方案更新 → 提交前审查

```
你是一名资深产品体验师 + 前端工程师，对 memora-sprite 实施用户激活的功能。执行模式：问诊 → 方案更新 → 提交前审查。

【任务】

- 不破坏现有交互流程
- 中文文案（用户母语中文）

【输出要求】
1. 问诊输出：任务合理性评估 + 是否触发 v3 准备期
2. 若合理：方案更新（设计 + ADR 变更评估 + 收益 + 风险）
3. 用户确认后实施
4. 提交前审查收尾
5. 更新 tasks/待完成任务.md 状态（"仅记录"→ 已完成）
```

### 提示词 I · 性能基准测试（可选·低优先级）

> **触发时机**：用户报告性能问题 / v3 准备期需要 baseline
> **执行模式**：测量 → 分析 → 必要时优化

```
你是一名资深性能工程师，为 memora-sprite 建立性能基准测试。执行模式：测量 → 分析 → 必要时优化。

【任务】
建立性能 baseline 文档，覆盖：
1. 首次加载时间（冷启动 / 热启动）
2. IPC 响应延迟（高频通道：sendUserInput/loadMemoryList/getConfig 等）

【资深程序员心智模型】
- 区分症状与根因——"卡顿"是症状，定位到具体瓶颈才是根因。不要在没测量前猜优化点。
- 怀疑前提——"性能问题"可能不是性能问题，而是 IPC 频率过高或渲染策略问题。先测量再下结论。

【关键约束】
- 不破坏现有功能
- 不引入新依赖（除非用户明确同意）
- 测试结果可复现

【输出要求】
1. 性能 baseline 文档（tasks/性能baseline-YYYYMMDD.md）
2. 瓶颈分析（如有）
3. 优化方案（如有，等用户确认后实施）
4. 优化后回归测试
```

| **绕过而非修补** | 第三方库 bug：提取原始数据绕过，而非下游 fallback | 在输出上叠加检测和 fallback |
