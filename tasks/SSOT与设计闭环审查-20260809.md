## 审查方法声明（先说方法，再说结论）

本次审查启用四路独立勘探后，对每一条影响评分的断言做了**二次定向复核**。复核推翻了三条初判：

| 初判 | 复核结果 | 证据 |
|---|---|---|
| `pauseMeta` 全链路无消费者 | **推翻** | `hosts/.../main.ts:579-580`、`chatHandlers.ts:194-202` 均消费 |
| `standard` 全链路无消费者 | **推翻** | `composer.ts:99` 读 `checkpoint.standard` 作槽位基底，闭环完整 |
| `restoreFromCheckpoint` 未回灌 `plan/roundLog/goalVersion` → 状态丢失 | **范畴错误，推翻** | 这三个字段的唯一存放处**就是** checkpoint（`sessionManager.ts:515` 整体赋值），运行时经 `getCheckpoint()?.plan` 读取（`agent.ts:1499`）。无第二副本 = SSOT 正确，不存在"回灌"需求 |

> 这三条恰好说明一个判据：**"某字段无人读"必须跨宿主边界 grep，且必须区分"字段有独立运行时副本"与"字段只存在于快照对象内"**。后者不需要 restore，前者才需要。

## 子系统 1：会话状态机（SessionStateMachine + SessionManager）

### 评分

| 维度 | 分数 | 判据 |
|---|---|---|
| SSOT 符合度 | **4 / 5** | 真理源归属明确且有代码级声明 |
| 设计闭环完整度 | **3 / 5** | 防滥用闭环完整，但事件消费端大面积悬空 |
| 未来兼容性 | **3 / 5** | 三态模型无法表达多 Agent 协作语义 |
| 风险评级 | **中** | 静默分叉，但有自愈窗口 |

### 核心发现

**发现 1-A（正面，应保持）：状态真理源归属是清晰的，且写进了代码。**

`sessionManager.ts:362` 注释明确：「状态真理源是状态机，检查点只是其投影」，`createCheckpoint` 中 `status: this.stateMachine.status`（:363）、`error` 亦以状态机为准（:365-371）。这是**单向投影**，不是双向同步——方向正确。

**发现 1-B（真缺口）：恢复路径是唯一的反向通道，且转换失败被静默吞掉。**

`restoreFromCheckpoint:540-544`：

```ts
if (checkpoint.status === 'error' && checkpoint.error) {
  this.stateMachine.triggerError(checkpoint.error.cause);
} else if (checkpoint.status === 'paused') {
  this.stateMachine.pause('从检查点恢复', 'system');
}
```

问题有二：

1. `pause()` 仅允许 `running → paused`（`sessionStateMachine.ts:88`），`triggerError()` 仅允许 `running → error`（:152）。若状态机此刻**不在 running**，转换返回 `{ allowed: false }` 而**返回值未被检查**——磁盘说 paused、内存仍是旧态，静默分叉。
2. 正确写法应是先 `resetToRunning()`（:279，绕过校验的唯一合法入口）再迁移，或直接检查返回值。

**发现 1-C（真缺口）：`resume()` 先改内存后落盘，IO 失败无回滚。**

`sessionManager.ts:648-650` 顺序为「状态机改 running → flush」，而 `flushCheckpoint` 内部 `catch` 只 `logger.warn`（:428-430）。IO 抖动即产生「内存 running / 磁盘 paused」。`recover()`（:754-774）同构同病。

缓解事实：flush 失败**保留脏标记**（:429 注释），下个语义边界会重试——所以这是"暂时分叉"而非"永久分叉"。但若此后无任何语义边界直到进程退出，分叉即固化（见发现 2-D：close 无最终 flush）。

### 对用户三个疑问的直接回答

**Q：`consecutivePauseCount` 的「递增→回答→重置」闭环完整吗？用户不回答怎么办？**

**闭环是完整的，且比预设更健壮。** 实现并非计数器而是**时间戳数组** `consecutivePauseTimestamps`（`sessionManager.ts:94`），配 1 小时滑动窗口衰减 `pruneStalePauseTimestamps`（:97/:697），阈值 `>= 2`（:720）。

- 递增：仅 `pause()` 内且 `lowRisk === false`（:600）
- 重置：`agent.ts:921`（clarify 事件唯一调用点）
- **用户永不回答**：计数停在 1–2，1 小时后自然衰减归零 → 不会卡死、不会无限增长
- 超阈值不拒绝暂停，而是 `agent.ts:875-885` **过滤高风险问题、降级 P3 兜底继续执行**

这是"自愈式防线"而非"硬闸门"，设计优于常见的单调计数器。

**但有一个真漏洞**：低风险问题**不计数**（:599 仅 `!lowRisk` 才 push），而过滤后 `lowRisk` 问题**照常暂停**（`agent.ts:888-901`）。→ **纯 lowRisk 澄清可无限 resume/pause 振荡**，防线完全不介入。

**Q：暂停超时的「生产→消费」有遗漏路径吗？**

生产唯一点 `markSessionTimedOut:1301`，消费唯一点 `consumePauseTimedOutSession:1281`（读后置 null）→ `agent.ts:295`。**主链路无遗漏**，`close()` 亦先停定时器（`agent.ts:2571`）再摘监听（:2591），无生产后无人消费的窗口。

三个次要缺口：
1. `sessionId` 不匹配 `YYYY-MM-DD-*` 时只发事件不填字段（:1305-1310）→ 宿主无归档
2. 消费**一次性非幂等**，第二次返回 null
3. 归档 fire-and-forget，失败仅 warn（`agent.ts:300-302`），而检查点已删（:1367）→ **会话内容永久丢失**

### 优化建议

| 优先级 | 动作 | 成本 |
|---|---|---|
| P1 | `restoreFromCheckpoint` 改为 `resetToRunning()` 后再迁移，并断言转换返回值 | 5 行 |
| P1 | lowRisk 暂停纳入独立的振荡计数（阈值可放宽至 5），堵住无限振荡 | 15 行 |
| P2 | 超时归档改为「归档成功才删检查点」，失败保留待下次重试 | 20 行 |
| P2 | 5 个零监听事件（`sessionResumeBlocked` / `sessionError` / `sessionRecovered` / `goalUpdated` / `goalDriftDetected`）二选一：接宿主 UI，或从 `AGENT_EVENTS` 删除 | — |

> 关于最后一条的原则：**事件零监听不等于功能缺失**（`SESSION_RECOVER` 走 IPC 返回值自广播，`chatHandlers.ts:119-133`）。但 `sessionResumeBlocked` 是真空白——恢复被超时阻断时用户收不到任何反馈，只会看到"点了没反应"。

### 未来演进思考

三态 `running | paused | error` 是**单 Agent 心智模型的产物**。多 Agent 协作会立刻要求 `WAITING_ON_PEER`（等待子 Agent）与 `DELEGATING`（已派发）——这两态与 `paused` 的关键差异是：**paused 等的是人，waiting 等的是机器**，超时策略、UI 呈现、恢复触发源三者全不同。当前 `PAUSE_TIMEOUT_MS = 30min`（`constants.ts:54`）套在机器等待上会灾难性误杀。

建议演进方向不是加状态，而是**给 paused 加一个正交的 `waitingOn: 'human' | 'peer' | 'resource'` 维度**——状态数保持 3，语义维度外挂。这符合复杂度守恒：多一个字段而不是多 N² 条迁移边。

## 子系统 2：检查点模型（SessionCheckpoint）

### 评分

| 维度 | 分数 | 判据 |
|---|---|---|
| SSOT 符合度 | **4 / 5** | 合并语义是全仓最佳实践，但有两处绕过统一入口 |
| 设计闭环完整度 | **3 / 5** | `goalVersion` 契约未兑现；plan/roundLog 双轨 |
| 未来兼容性 | **2 / 5** | **最低分**：无 schema version、无 CAS、全量覆盖 |
| 风险评级 | **中高** | 存在静默数据丢失路径 |

### 核心发现

**发现 2-A（正面，强烈建议保持）：`createCheckpoint` 的合并语义是从真实 bug 中生长出来的正确形状。**

`sessionManager.ts:347-358`：

```ts
// 【禁止改回对象字面量整体重建】
// 整体重建等价于「隐式字段白名单」——任何未被显式列出的字段都会在每次
// pause 时被静默丢弃。历史上 roundLog / completedToolCalls / pauseMeta
// 三个侧车字段正是因此在每次暂停时归零，导致：
//   1. hasToolExecuted() 恒 false → 非幂等工具在恢复后重复执行
//   2. compensateAllNonIdempotent() 过滤空数组 → 补偿机制空转
//   3. 宿主任务表回合历史归零
this.checkpoint = { ...(prev ?? {}), /* 仅覆写本次重算字段 */ };
```

这条注释本身就是最高质量的架构资产——它把「为什么」而不只是「是什么」钉在了代码里。**这正是"自然生长"的样本**：形状不是设计出来的，是被 bug 逼出来的，然后用注释固化为契约。

**发现 2-B（关键缺口）：`goalVersion` 是"契约未兑现"，不是死字段。**

- 唯一递增点：`sessionManager.ts:817`（`updateGoal` 内，且 :803 有幂等短路）
- 读取点：仅作为 `goalUpdated`(:824) / `goalDriftDetected`(:837) 的事件 payload
- **校验方：未找到**

漂移检测实际用的是 `GoalConsistencyChecker.checkConsistency(mainGoal, newGoal)`（:814）做**文本相似度**，全程不读 `goalVersion`。

这比死代码危害更高：类型上 `goalVersion: number`（`types.ts:470`）是必填字段，语义上承诺"版本一致性校验"，下游（含未来的多 Agent 分支合并）会**按契约假设它有效**。一个只增不校的版本号，是伪装成安全机制的装饰品。

**修法必须二选一，禁止维持现状**：
- 兑现：restore 时比对内存 `goalVersion` 与磁盘，落后则拒绝写入并发 `goalVersionConflict`
- 收窄：删除字段，漂移检测完全交给文本相似度（诚实降级）

**发现 2-C（真缺口）：plan 与 roundLog 是双轨且会互相矛盾，却同屏渲染。**

- `task_table_update` → `agent.ts:1961-1972` 只改 `step.status`，**不写 roundLog**
- roundLog 唯一追加点 `completeRound()`（:985），由 `agent.ts:1883-1890` 每轮触发，且 `stepId` 未传 → `RoundOutcome.stepId` **恒为 undefined**
- `agent.ts:1902` 兜底直接把 active 步骤改 `blocked`，roundLog 无对应记录
- 渲染层 `renderTaskTable(cp.plan, cp.roundLog)`（:1919）**把这两条不同步的进度并排展示给用户**

`stepId` 恒 undefined 是关键信号：它本是关联两轨的外键，从未被填 → 两轨在数据层面**根本无法对齐**。

**发现 2-D（真缺口）：两处绕过 `touchCheckpoint` 统一入口 + close 无最终 flush。**

`sessionManager.ts:395-397` 立下契约：「所有修改 checkpoint 内容的方法都必须调用 touchCheckpoint，不得直接赋值 lastHeartbeat」。违反者两处：

- `agent.ts:1967-1968`：`step.status = status; cp!.lastHeartbeat = Date.now();`
- `agent.ts:1902-1903`：`activeStep.status = 'blocked'; cp.lastHeartbeat = Date.now();`

两处都**手写心跳且不置 `checkpointDirty`** → 若此后无 `completeRound`/`pause`，任务表状态变更**永不落盘**。

叠加：`Agent.close()` 只调 `sessionManager.destroy()`（`agent.ts:2571`），其实现（:1390-1392）仅 `stopPauseTimeoutTimer()`——**关闭路径无最终 flush，脏检查点直接丢弃**。

**发现 2-E（中危，条件性）：`rebuildComponents()` 后检查点归零，可能空覆盖磁盘。**

`rebuildComponentsWithCurrentCtx:2004-2009` 重建 `SessionManager` → `checkpoint` 复位 null（:76）。后续任何 `createCheckpoint` 因 `prev = null` 会以 `plan: []`、`goalVersion: 0` **强制落盘覆盖**（:387 force=true）。

触发条件收窄说明：`rebuildComponents()`（:2427）有 `assertNotBusy` 守卫（:2429），且 `switchProject` 路径下 sessionId 随项目变更、不会覆盖。**真实风险窗口是「同项目内暂停态热更新配置」**——`assertNotBusy` 不拦截 paused 态。

### 优化建议

| 优先级 | 动作 |
|---|---|
| P1 | `goalVersion` 兑现或收窄（二选一，不可拖） |
| P1 | 两处直改内存改走 `touchCheckpoint()` |
| P2 | `close()` 增加最终 `flushCheckpoint(true)` |
| P2 | `rebuildComponentsWithCurrentCtx` 后调 `loadPersistedCheckpoint()` 恢复 |
| P2 | `completeRound` 传入 `stepId`，让 roundLog 与 plan 可对齐；或明确 roundLog 只做「轮次日志」不做「进度」，渲染层不再并列 |

### 未来演进思考

当前持久化形态是 **SQLite 单 TEXT 列存整个 JSON**（`hosts/.../sessionStore.ts:382` `INSERT OR REPLACE`），无版本号、无 CAS、后写全量覆盖先写。这个形状在单 Agent 下没问题，但撞上三个近在眼前的趋势会立刻碎裂：

1. **多 Agent 协作**：两个 Agent 同时写同一 session 的检查点 → 必然互相覆盖。需要 `INSERT ... WHERE version = ?` 的乐观锁，而 `goalVersion` 本可担此任（这正是它应被"兑现"而非"删除"的理由）。
2. **长上下文窗口**：`hotMemory` 全量塞进单列 JSON，128k+ 上下文会让每次 pause 都序列化数 MB。应拆列，或 hotMemory 改增量 append-only 日志。
3. **schema 演进**：无 `schemaVersion` 字段。新增/改名字段后，旧检查点反序列化会静默产出 `undefined`——合并语义（发现 2-A）保护的是"未列出字段不丢"，保护不了"字段语义变更"。

**建议现在就加 `schemaVersion: number`**——这是一行成本、不可逆收益的字段。等到需要迁移时再加就已经晚了。

## 子系统 3：记忆分类与存储（Everything is Memory v2）

### 评分

| 维度 | 分数 | 判据 |
|---|---|---|
| SSOT 符合度 | **4 / 5** | Rule 是合法派生索引，非 dual-source |
| 设计闭环完整度 | **3 / 5** | 骨骼写入无原子性/无备份；关系边有孤儿路径 |
| 未来兼容性 | **4 / 5** | **最高分**：文件真理源是最适配未来的形状 |
| 风险评级 | **中** | 有不可逆污染路径，但有人工闸门缓解 |

### 核心发现

**发现 3-A（定性结论）：Rule 的文件 + SQLite 是「派生索引」，不是 dual-source 反模式。**

判据是分层声明写进了代码（`configManager.ts:15-23`）：

```
 *   配置文件是真理源，SQLite 是运行时检索索引，重启后由文件（MemoryLoader）自愈。
 *   本类所有写 API（addRule/deleteRule/updateRule/deleteSkill）只同步 SQLite 层，
 *   调用方必须先完成文件层写入/删除
```

实证吻合：`deleteRule:336-349` / `updateRule:373-395` 均**不碰文件**；写入顺序由宿主编排（`sprite.ts:788-794`）——**先文件、失败即中止、不动 SQLite**。顺序正确，无需回滚。

**判据总结（可复用）**：判断 dual-source 只需问一句——**「删掉从库能否从主库无损重建？」** 能 = 派生索引（合法）；不能 = dual-source（反模式）。Memora 能（`MemoryLoader.loadAllToIndex`，`loader.ts:63/86`）。

**扣分项**：重建入口**只有启动路径与切项目**（`loader.ts:113`、`projectManager.ts:250/261`），**未找到任何手动 reindex API 或 IPC**。索引一旦 stale，用户唯一自救手段是重启。

**发现 3-B（真缺口）：bootstrap 刷新回调有两条旁路。**

回调在 `assembler.ts:247-252` 注册为**构造必选参数**（`configManager.ts:96`）——这一点设计得好，无法遗漏注入。触发点 `deleteRule:346` / `updateRule:393` / `deleteSkill:430`。

旁路一：`addRule` / `addSimpleRule`（:222-235）与 `confirmConfigSuggestion`（:199-205）**不调回调**，改走 `injectSystemMessage` 追加消息 → bootstrap 段本身 stale 直到下次 CRUD 覆盖。

旁路二（更严重）：**外部编辑器直改 `rules/*.md`、`skills/*.md` 完全无感知**。`personaWatcher` 只监听 `personas/`（`hosts/.../personaWatcher.ts:105-107`）；`rulesWatcher` / `skillsWatcher` **仅存在于注释**（`configFileManager.ts:25` 标注"未来"），代码不存在。

后果：Persona 秒级自愈（fs.watch + 500ms 防抖），**Rule / Skill stale 到进程重启**。对一个"设定记忆是文件真理源"的架构而言，这是真理源改了而系统不知道——SSOT 的前提（真理源可观测）被打破。

**发现 3-C（最高风险）：`autoConfigRefiner` 的"血肉结晶为骨骼"路径，落盘环节无任何保护。**

链路完整且有闸门：`analyze():84` → LLM/启发式 → 过滤（`minConfidence 0.6`、`maxSuggestions 3`，:45-47）→ 去重两层（同名 `isExistingRule` + 跨轮指纹 `seenSuggestionKeys`，:144-154）→ **用户人工确认**（`suggestionHandlers.ts:55`）→ `writeConfigFile`（`configManager.ts:181`）。

**但最后一步是裸写**（`src/memory/store.ts:88`）：

```ts
await writeFile(filePath, content, 'utf-8');
```

无 tmp + rename 原子写、无 `.bak`、无版本目录。后果：
- 写入中途崩溃 → 配置文件截断损坏，而它是**真理源**
- LLM 生成的内容一旦确认即**永久覆盖**同名骨骼文件，无回滚

这是全仓唯一会造成**不可逆真理源污染**的路径。人工确认闸门只能拦"内容不对"，拦不住"写坏了"。

**发现 3-D：MemoryRelation 侧车无外键，一致性 100% 靠应用层。**

建表无 `FOREIGN KEY`、无 `ON DELETE CASCADE`（`sqliteRelationStore.ts:22-31`）。清理点已覆盖得相当全（`memoryInspector` 三处、`configManager` 两处、`userProfile` 两处、`memoryController` 两处）。

残余孤儿路径三条：
1. 清理回调是**可选参数**（`configManager.ts:108` `removeRelationsByMemoryId?`），未注入即静默残留——代码自认（:100「可能残留孤儿边」）
2. `writePurgeExpired:731-738` 单条失败仅 warn，记忆仍被物理删除 → **确定性孤儿边**
3. 软删除故意保留边（`memoryController.ts:360`，为 restore 服务）——语义合理，但 30 天窗口内存在指向软删记忆的边

### 优化建议

| 优先级 | 动作 |
|---|---|
| P1 | `store.ts:88` 改原子写：`writeFile(tmp)` → `rename(tmp, target)`，并保留一份 `.bak` |
| P2 | 补 `rulesWatcher` / `skillsWatcher`（复用 `personaWatcher` 形状，已有先例可嫁接） |
| P2 | 暴露手动 `reindex()` API + IPC，给 stale 索引一个不重启的出口 |
| P3 | `removeRelationsByMemoryId` 从可选改必选（与 bootstrap 回调同构，编译期堵住遗漏） |

### 未来演进思考

「设定记忆走文件、对话记忆走 SQLite」这个分轨是**本项目最有远见的决策**，理由是文件形态天然满足三件事：Git 可版本化、人类可直接编辑、多 Agent 可共享挂载。当 Agent 自我进化（autoConfigRefiner 的终局形态）成为常态时，**「骨骼变更可 diff、可 review、可 revert」会从便利性需求升级为安全性需求**——你不会允许一个 Agent 无痕修改自己的行为准则。

所以第 3-C 的原子写 + 备份不该被看作"健壮性补丁"，而应看作**自我进化能力的前置基建**。更进一步的方向：设定文件目录本身用 git 管理，每次 `autoConfigRefiner` 落盘生成一个 commit，`git revert` 即回滚。这比自建版本机制成本更低、能力更强，且完全契合"零第三方运行时依赖"（git 是外部进程，不是运行时依赖）。

## 子系统 4：不中断工作模型的设计闭环

### 评分

| 维度 | 分数 | 判据 |
|---|---|---|
| SSOT 符合度 | **3 / 5** | 延迟翻转设计正确，但对称性未贯彻 |
| 设计闭环完整度 | **2 / 5** | **最低分**：三条 dangling path，其一导致状态分叉 |
| 未来兼容性 | **3 / 5** | 双通道模型可扩展，但缺少 turn 级幂等 |
| 风险评级 | **高** | 用户可感知的功能失效 |

### 核心发现

**发现 4-A（正面）：「内核事实驱动的延迟翻转」是正确设计。**

`agent.ts:955-956` 注释：「loop 在迭代边界真正挂起时，状态机才翻 PAUSED；不再在 requestPause 同步翻转——避免'申请即暂停'错位」。

链路完整可追：`chatHandlers.ts:105` → `agent.requestPause:1370`（状态机拦截 + `_pendingPauseReason` 幂等锁 :1387）→ `loop.requestPause:373` 置标志 → `handleIteration:582-588` **在 LLM 调用前**的迭代边界挂起并 `yield {type:'paused'}` → `agent.ts:957-960` 消费并翻状态机。

对比"申请即翻转"，这个设计的优越性在于：**状态机的 PAUSED 永远对应"确实没有在跑"这个物理事实**，不存在"状态显示暂停但 LLM 还在烧 token"的中间态。这是 SSOT 在时间维度上的正确表达。

**发现 4-B（P0 真 Bug）：`resumeExecution` 缺 `paused` 分支，续跑期间二次暂停导致状态分叉 + 暂停按钮永久失灵。**

这是本次审查最硬的发现，已三重复核。

`loop.continueAfterPause` **确实会产出 `paused` chunk**：

```
loop.ts:416   const result = yield* this.handleIteration(iteration, signal);
loop.ts:417   if (result === 'aborted' || result === 'done' || result === 'paused') return;
              → handleIteration:586  yield { type: 'paused' };
```

但 `agent.resumeExecution` 的消费循环（`agent.ts:1052-1060`）**只处理 text / aborted**：

```ts
for await (const chunk of loop.continueAfterPause(input, signal)) {
  yield chunk;
  if (chunk.type === 'text') { assistantContent += chunk.content; }
  else if (chunk.type === 'aborted') { wasAborted = true; }
}
```

对照 `processEvent` 的同位置（:957-960）有完整的 `paused` 处理。**这是不对称。**

故障链：
1. 用户续跑中再次点暂停 → `_pendingPauseReason` 被占位（:1387 幂等锁）
2. loop 在边界挂起、产出 paused chunk、`return`
3. agent 只 `yield chunk` 转发，**从不调用 `this.pause()`** → 状态机停留 `running`，检查点不落盘
4. 宿主收到 paused chunk 后 `break`（`chatStreamHandler.ts:312-315`），**UI 显示已暂停**
5. → **UI 说 paused、内核说 running，状态分叉**
6. `_pendingPauseReason` 永不清除 → **此后所有 `requestPause()` 被幂等锁静默吞掉（返回 false），暂停按钮彻底失灵**，直到 `cancelPauseRequest` / `abandonPause` / `close`

讽刺的是，`loop.ts:298-300` 的注释明确写着「与 `continueAfterPause` 的 'paused' 处理保持一致」——**作者在 loop 层意识到了对称性并对齐了，却在 agent 层漏了对称的另一半**。这是典型的"契约在一层兑现、在另一层落空"。

**发现 4-C（P1）：异常路径不清 `_pendingPauseReason`，同样导致暂停按钮失灵。**

`agent.ts:968-976` 的 catch 块处理 abort 与 error，**不清理 `_pendingPauseReason`**。若 paused chunk 已 yield 但消费者随后抛错，`loop.pauseRequested` 已被 `:584` 自清，而 `_pendingPauseReason` 悬留 → 幂等锁永久占位。

`close()` 有补偿（`agent.ts:2551-2566`，会清标志并补 pause），但它只在关闭时生效，救不了运行期。

**根因**：`_pendingPauseReason` 的生命周期由**分散的 happy path 赋值/清除**管理，而非 `try/finally`。修法应是把清除放进 `finally`。

**发现 4-D（P1）：needClarify 分支在 `applyResolvedDelta` 之前 `return`，本轮解析成果全丢。**

`agent.ts:888-901` 的暂停分支 `this.pause(...); yield {type:'done'}; return;` 位于 `:908 this.applyResolvedDelta(...)` **之前**。

后果：本轮 Composer 已解析出的 role / task / standard / resource 四槽**全部未写入检查点**。`sessionManager.pause()` 内部虽调 `createCheckpoint()`（:597），但保存的是**未应用 delta 的旧检查点**。

用户回答澄清后，事件被改写为 `{type:'chat', content: formatClarifyAnswers(...), delta:{}}`（:922）重新 compose——此时 `checkpoint.currentGoal` 仍是旧值，而新 content 是澄清回答文本。按 `resolveChatTaskSlot` 语义（currentGoal 非空则 P2 延续、不覆盖），**原本 P1 解析出的新目标永久丢失**，且澄清回答文本可能被误当作目标。

**Q：`canContinueWithoutInput()` 三个条件够吗？**

`agent.ts:1497-1502` 实现：

```ts
canContinueWithoutInput(): boolean {
  if (this._sessionManager?.stateMachine.status === 'paused') return true;
  const hasPendingPlan = this._sessionManager?.getCheckpoint()?.plan.some((s) => s.status !== 'done') ?? false;
  return this.requireLoop.isInAutonomousStep || hasPendingPlan;
}
```

**不够，且第一行就是最大问题**：`paused` 直接短路返回 true，**无视 plan 是否已全部完成**。语义盲区清单：

| 场景 | 当前返回 | 应然 |
|---|---|---|
| paused + plan 全 done | **true** | false（无事可续） |
| `error` 态 | 可能 true | 应为 false（错误未恢复不该提示可续） |
| plan 为空（纯单轮问答） | false（`[].some()` 为 false） | 正确 |
| 上一轮出错 / goal 已达成 | 不参与判断 | 应参与 |

缓解事实：真正的续跑入口 `resumeExecution` 有 P0-1 预判短路（`agent.ts:1039-1046`）——`isPlanStalled() && !isInAutonomousStep` 时直接提示"所有计划步骤已完成"，**不会浪费 LLM token**。所以这是 UX 瑕疵（按钮不该亮却亮了）而非资源浪费。

另需澄清：`canContinueWithoutInput` 的调用点**不是"继续"按钮**，而是状态广播的 `resumable` 字段（`main.ts:581`、`chatHandlers.ts:106/128/298/320`）。渲染层已移除其对停止按钮的控制（`inputAreaManager.ts:427/433`）。

**Q：双通道模型「输入通道永不冻结」有安全漏洞吗？**

有，就是**振荡**，且防线有缺口。

分发逻辑 `agent.ts:1337-1350`：PAUSED 态下 chat / correction / clarify **一律自动 resume**（仅排除 `command`）。防护只有跨轮的 `consecutivePauseTimestamps`（阈值 2，1 小时衰减）。

三个缺口：
1. **lowRisk 暂停不计数**（`sessionManager.ts:599`）却照常暂停 → 纯 lowRisk 场景可无限振荡
2. **clarify 回答清零计数**（`agent.ts:921`）→ "回答→清零→再暂停"可反复重置防线
3. **未找到任何 turn 级幂等锁或冷却时间**

### 优化建议

| 优先级 | 动作 | 成本 |
|---|---|---|
| **P0** | `resumeExecution` 补 `paused` 分支，与 `processEvent:957-960` 对称 | **4 行** |
| **P0** | `_pendingPauseReason` 清除移入 `finally`，覆盖 abort/error/正常三条路径 | 5 行 |
| P1 | `applyResolvedDelta` 提到 needClarify 分支**之前**执行（澄清不应丢弃已解析槽位） | 移动 1 行 |
| P1 | `canContinueWithoutInput` 首行改为 `paused && hasPendingPlan`，并显式排除 `error` 态 | 3 行 |
| P2 | lowRisk 振荡独立计数 + turn 级 pause 幂等 | 20 行 |

> P0 两项合计 9 行代码，消除一个用户可感知的功能失效（暂停按钮永久失灵）+ 一个 UI/内核状态分叉。**这是本次审查投入产出比最高的修复。**

### 未来演进思考

双通道模型（控制通道 + 工作通道分离）本身是**面向 MCP 与多 Agent 的正确抽象**——它承认了"Agent 在忙"和"能否接收指令"是两件正交的事。这个判断会随着 Agent 长时间自主运行（hours-long tasks）而愈发重要。

但当前实现把「通道」隐含在 `eventType !== 'command'` 这个单一判断里（`agent.ts:1345`）。随着事件类型增长（未来必然出现 `tool_result` / `peer_message` / `interrupt` / `cancel`），这个反向排除列表会退化成 bug 温床——**每加一个事件类型都要重新思考"它该不该 resume"，而遗漏是静默的**。

建议演进：把「通道归属」提升为事件类型的**声明式属性**而非调用点的判断：

```ts
const EVENT_CHANNEL: Record<EventType, 'control' | 'work'> = {
  command: 'control',   // 不触发 resume
  chat: 'work',
  correction: 'work',
  clarify: 'work',
};
```

这样新增事件类型时，TypeScript 的 `Record` 完备性检查会**强制开发者做出通道归属决策**——把运行时的静默遗漏，转化为编译期的显式选择。这正是「契约即类型」的应用：让正确的事情容易做，让遗漏无法编译。

### 评分汇总

| 子系统 | SSOT | 闭环 | 未来兼容 | 风险 |
|---|---|---|---|---|
| 1. 会话状态机 | 4 | 3 | 3 | 中 |
| 2. 检查点模型 | 4 | 3 | **2** | **中高** |
| 3. 记忆分类与存储 | 4 | 3 | **4** | 中 |
| 4. 不中断工作模型 | 3 | **2** | 3 | **高** |
| **均值** | **3.75** | **2.75** | **3.0** | — |

### 总体判断

**这是一个 SSOT 意识显著高于行业平均水平的代码库。** 三个证据：

1. 真理源归属**写进了代码注释**而非散落在文档（`sessionManager.ts:362`、`configManager.ts:15-23`）
2. 存在从真实 bug 中生长出的防御性设计，并把「为什么」固化为契约（`sessionManager.ts:347-358` 的合并语义）
3. 「内核事实驱动的延迟翻转」体现了对"状态必须对应物理事实"的深刻理解

**短板集中在闭环维度（2.75，四维最低），且模式高度一致：设计对了，但对称的另一半没写完。**

三个 P0/P1 缺口是同一个病灶的三种表现：
- `resumeExecution` 有 loop 侧对称、缺 agent 侧对称
- `goalVersion` 有写入、缺校验
- `_pendingPauseReason` 有 happy path 清除、缺异常路径清除

**根因判断**：这些都不是"想错了"，而是**"链路的第二条分支被遗忘"**。第一条分支（主路径）在开发时被反复走通，第二条分支（续跑 / 异常 / 校验）缺乏同等强度的验证。这类缺陷靠 code review 很难发现——因为每一处单独看都是合理的。

**因此，比修复这三个 bug 更有价值的是引入结构性防线**：对每个「产生-消费」对，强制要求消费点覆盖生产点的全部产出类型。`chunk.type` 用可辨识联合 + `switch` 完备性检查（`never` 兜底），能让发现 4-B 这类漏分支**在编译期暴露**。

### 优先级排序

**立即修（P0，合计约 10 行，消除用户可感知的失效）**

1. `resumeExecution` 补 `paused` 分支 —— `agent.ts:1052-1060`，与 `:957-960` 对称
2. `_pendingPauseReason` 清除移入 `finally` —— 覆盖 abort / error / 正常三路

**尽快修（P1，本迭代内）**

3. `goalVersion` 兑现校验或收窄删除 —— **禁止维持"写多读零"现状**
4. `applyResolvedDelta` 提到 needClarify 暂停分支之前
5. `store.ts:88` 改原子写 + `.bak` 备份 —— 唯一的不可逆真理源污染路径
6. `restoreFromCheckpoint` 状态迁移改 `resetToRunning()` 前置 + 校验返回值
7. 两处绕过 `touchCheckpoint` 的直改（`agent.ts:1902` / `:1967`）

**排期修（P2）**

8. `close()` 补最终 flush；`rebuildComponents` 后恢复检查点
9. 补 `rulesWatcher` / `skillsWatcher`（嫁接 `personaWatcher` 形状）

14. 手动 `reindex()` API
15. plan / roundLog 双轨对齐（`completeRound` 传 `stepId`）或明确分工、渲染层解耦
16. 事件通道归属改声明式 `Record<EventType, Channel>`

### 明确建议保持不动的设计

以下四项经审查确认为**正确且有远见**，不要在重构中"顺手优化掉"：

1. **`createCheckpoint` 的展开合并语义**（`sessionManager.ts:357-358`）—— 连同那段注释一起保留，它是防止回归的唯一屏障

4. **`consecutivePauseTimestamps` 的时间窗衰减** —— 自愈式防线优于单调计数器，用户不回答不会卡死
