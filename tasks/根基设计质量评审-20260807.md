## 0. 总体结论（TL;DR）

四篇文档构成了一条从**概念层 → 理论层 → 工程层 → 演进层**的完整设计链，整体设计质量**中上**：有多处第一性的亮点（分级路径、三源融合的维度分离、缺省补全的 P4 演进、goalVersion 防漂移），但存在 **2 处设计层硬伤（P0）** 与 4 处结构性缺陷（P1）：

| 级别 | 数量 | 核心问题 |
|---|---|---|
| **P0** | 2 | ① P1>P2>P3「覆盖式补全」与「解析依赖上下文」两个模型直接矛盾（B vs C）；② 检查点/断点续跑在 D 篇中无上下文重建路径，恢复即失真 |
| **P1** | 4 | ③ 四元组结构不完备（缺输出/上下文标识维度）；④ 状态机仅两态、无异常态；⑤ P4 暂停判定的判定者与标准缺失；⑥ 资源⇄动作递归无终止条件 |
| **P2** | 5 | ⑦ 优先级仲裁仅三档、同档冲突无规则；⑧ goalVersion 一致性校验的判定者未定；⑨ 复杂度守恒存疑（11 个抽象组件）；⑩「一」的抽象漂移未真正收敛；⑪ 检查点与四元组 merge 规则未定义 |

**最深刻的发现（P0-①）**：B 篇声称补全链"每槽独立走 P1→P2→P3 优先级链，互不干扰"（覆盖模型），但 C 篇自己承认"解析本身需要上下文（『继续上次那个』没有记忆就无法解析）"（依赖模型）。用户说"继续"时，P1（显式输入）是**指代**而非**覆盖**——它必须引用 P2（记忆）里的内容才能成立。覆盖模型与依赖模型在同一体系内互相矛盾，这是本次评审发现的最深层设计张力。

## 1. A 篇：概念根基设计评审

### 1.1 LLM 三性质作为设计前提【成立，质量高】

LLM 三性质（无状态 / 只出文本 / 知识冻结）是整条设计链的基石。对抗式核验：
- **无状态**：正确。API 层面每次调用独立（除上下文窗口内的状态），Agent 补状态是该前提的必然推论。✓
- **只出文本**：正确。tool_call 是文本契约，Agent 解析执行。✓
- **知识冻结**：**表述不精确**。LLM 的知识冻结指**权重冻结**（训练时快照），但上下文窗口内可通过 RAG/长上下文注入"临时知识"——这与"记忆补知识"的 memora 设计形成微妙张力：记忆补的不是"知识冻结的缺口"，而是"上下文窗口内可注入的内容"。建议 A 篇补一句"知识冻结=权重冻结，上下文注入可临时扩展"。

**设计含义**：三性质推导出的 Agent 职责（状态/解析/执行/循环）方向正确，但"知识冻结 → 需补约束与检索"（L134）把"约束"（安全/规则）与"检索"（知识/记忆）混为同一类需求——二者机制完全不同（约束是确定性注入、检索是概率性召回），这为 C 篇的分级路径埋下了伏笔（C 篇做得对，A 篇概念层未区分）。

### 1.2 Agent 四职责清单的完备性【P1-③ 相关，部分缺失】

A 篇职责表（推理/状态/解析/执行/循环）缺两个维度：
- **缺"规划"**：D 篇引入"目标 + 计划 + 版本"（mainGoal/currentGoal/planList），但 A 篇职责表无"规划"。规划不是"推理"（LLM 推理输出内容，规划是 Agent 决定目标分解与步骤排序）——D 篇补了概念但 A 篇概念根基未包含，概念层与演进层脱节。
- **缺"记忆管理"**：memora 的"万物皆记忆"下，归档/召回/截断/检查点都是 Agent 职责，A 篇的"状态"一栏承载不了"记忆生命周期管理"的完整职责。

**设计结论**：A 篇作为概念根基，职责清单应扩展为「推理（LLM）/ 状态 / 记忆管理 / 解析 / 执行 / 规划 / 循环（Agent）」，与 B/C/D 的组件形成一一对应。当前四职责清单过简，是后续所有"新增维度"（检查点/目标版本/事件分类）在概念层无锚点的根因。

### 1.3 tool_call 契约论【成立，设计优秀】

"tool_call 是 LLM 写给 Agent 的结构化 JSON 契约、LLM 从不触碰外部世界"是第一性的正确修正。设计含义深远：
- 契约断裂（JSON 不符合 schema）= Agent 解析失败，不是 LLM 坏了——这个区分正确。
- **推论未被利用**：契约是"写给 Agent 的指令"，那么**指令的信任边界**（tool_call 是否可信、参数是否越权）属于 Agent 的校验职责——A 篇未展开"指令校验/权限校验"环节。D 篇的"常驻权限放大"风险（探索未来.md 风险 11）在概念层无支撑。建议 A 篇补"契约校验（schema + 权限 + 参数合法性）是 Agent 执行前的必经环节"。

## 2. B 篇：道生万物输入框架设计评审

### 2.1 四元组（角色/任务/标准/资源）完备性【P1-③】

四元组作为"任意具体请求 = (角色, 任务, 标准, 资源)"，对抗式追问：**它完备吗？**
- **缺"输出"维度**：请求不仅包含输入四要素，还包含期望的**输出形态**（语言、格式、渠道、长度）。"标准"里的"做到什么程度"不等于"以什么形式输出"。B 篇以"书"为比喻（读/背诵/撕毁），输出天然隐含；但工程化（API 设计、工具调用约定）中输出规格是独立维度。
- **缺"上下文/会话标识"**：四元组是"单次请求的自包含结构"，但 C 篇已经承认"解析需要上下文"（指代解析）、D 篇引入"会话/检查点"——**跨请求状态在四元组中没有槽位**。"资源"可以装内容，但"会话状态/目标/检查点"（D 篇放入资源）语义上不是"资源"（背景数据）而是"上下文"（引用环境）。
- **结论**：四元组是**单请求语义结构**（角色×任务×标准×资源），不是"任意交互"的完整结构。D 篇把目标/计划塞进资源、把 delta 塞进 Partial<FourTuple>，都是在给四元组打补丁——根因是四元组缺"上下文"维度。建议演进为五元组（+上下文/会话引用）或明确声明"四元组=单次请求结构，跨请求由会话层承载"。

### 2.2 P1>P2>P3 覆盖式补全链【P0-① 最深刻缺陷】

B 篇核心机制：接口=一入口+四槽位，每槽独立走 `P1 显式 → P2 记忆 → P3 内置` 优先级链，**互不干扰**（L239）。

对抗式审查：**这个覆盖模型与真实交互的"指代"特性矛盾**。
- 覆盖模型假设：高优先级来源（P1 用户）提供**完整值**，低优先级仅作缺省。用户输入"继续上次那个"——P1 提供的不是完整任务值，而是**对 P2 的引用**（指代词"上次""那个"）。
- 若按"互不干扰的覆盖模型"：任务槽 = "继续上次那个"（字面值），记忆推断被覆盖丢弃 → 解析失败。
- C 篇自己承认这一点："解析本身需要上下文（『继续上次那个』没有记忆就无法解析）"（C·L180）——**C 篇的触发链设计（粗召回→LLM 解析）本质上已经否决了 B 篇的纯覆盖模型**，但 B 篇未更新。
- D 篇更彻底：不中断模型下用户输入是**增量事件**（delta），"增量"天然不是"覆盖值"而是"对既有状态的修改指令"——覆盖模型在 D 篇彻底失效。

**正确模型**：补全链应是**「覆盖 + 解析」混合**：P1 显式输入优先，但当 P1 内容含**指代/增量**（代词、省略、相对指令）时，必须借 P2 记忆解析后才能落入槽位。即：`P1 优先 ≠ P1 字面覆盖`；优先级决定"谁说了算"，解析决定"内容是什么"。

**这暴露了 B 篇与 C 篇的深层设计矛盾**：B 篇认为"每槽独立、互不干扰"，C 篇认为"解析需要记忆上下文、两阶段互动"。两个模型不能同时为真。修复方向：B 篇补全链引入"指代解析"环节（P1 输入先经 P2 上下文解析再落槽），或声明"覆盖模型仅适用于完整自包含输入，指代输入走 C 篇触发链"。

### 2.3 三源融合（来源维度 ≠ 结构维度）【设计亮点】

"来源是元信息，结构是本质——三源是『一』的三个供给者，不是从二/三层延伸"——这是 B 篇**最优秀的设计**：
- 正确防止了分类爆炸（来源×结构若叉乘会 81 组合，收拢规则避免了）。
- 与 memora 现状（bootstrap/recall/chat）映射自然，理论命名先于实现，落地即确认。
- **局限**：三源（内置/记忆/用户）按时间维（设计/过去/现在）划分，但**"用户文档"这个 v1.1 补的第四类**（用户过去写的设定）打破了时间维的简洁性——它既非"现在"（用户输入）也非"记忆"（不是沉淀的交互产物）。v2.2 已用"按确定性分级跨 P2/P3 分流"处理，但这实质是**在时间维之外引入了确定性维**——三源的时间分类已不纯。若严格要求第一性，"用户文档"应归入"用户输入"来源（P1 的用户供给，但按确定性分流），而非跨 P2/P3。

### 2.4 资源⇄动作递归【P1-⑥】

"文本在解析前是资源、解析后是动作；任务的产出可成为下一轮资源"——code-as-data 类比有洞见（LISP）。
对抗式追问：**递归的终止条件是什么？**
- "解析"由谁执行？若由 LLM 解析（输入解析），则"解析前是资源、解析后是动作"的转化点取决于 LLM 的判断——**递归在运行时依赖 LLM 的解释，框架无确定性终止条件**。
- 例：用户说"分析这段指令的意图"——"这段指令"是资源还是动作？既是（被分析的对象=资源）又不是（它本身是指令=动作）。B 篇说"递归性让二分无需新增类别就能覆盖无限场景"——但**无限覆盖的代价是运行时不可判定**。
- 修复：声明"资源⇄动作是**语义视角**（分析层面成立），工程上动作/资源在**契约层面固定**（工具声明、指令格式），递归只发生在 LLM 语义层，不发生在框架类型层"。即把递归限定为 LLM 语义灵活性，而非框架机制。

## 3. C 篇：输入管道与触发链设计评审

### 3.1 四层管道 + 唯一渲染器【设计合理，P2-⑨ 相关】

- **四层划分（程序设定/用户文档/记忆层/实时输入）**：按稳定性谱系划分合理，各层不可靠类型（语义扭曲 vs 信息缺失）驱动不同策略（降级 vs 补全）——第一性正确。
- **管道 + 渲染器（第三答案）**：工程侧分层控制 + 交付侧唯一排版，复杂度守恒论证成立（收益覆盖故障面）。
- **渲染器职责过载**：PromptRenderer 承担排版 + 预算裁剪 + 窗口管理 + 状态恢复 + 优先级标注 + 缓存命中（L147-151）——**6 项职责集中于一个组件**。窗口管理/状态恢复（D 篇新增）与排版（C 篇核心）是不同生命周期（每次请求 vs 会话级）的职责，混在"渲染器"里违背单一职责。建议拆分为 Renderer（排版）+ ContextManager（窗口/预算/恢复）两个组件，或明确渲染器=排版真理源、窗口管理=独立模块。

### 3.2 触发链（用户输入第一性 → 粗召回 → LLM 解析 → 精召回）【方向正确，P0-① 相关】

- **用户输入第一性**：查询条件只能来自用户输入——正确（无输入则无查询条件）。
- **粗召回（无 LLM）先行**：成本与质量平衡点设计正确（零推理成本 + 给 LLM 解析供上下文）。
- **与 B 篇的矛盾（P0-①）**：见 2.2。C 篇的两阶段互动模型（解析需要上下文）是**对 B 篇覆盖模型的事实性修正**，但 B 篇未同步——两个设计文档在同一体系内给出互相矛盾的补全行为模型。这是本次评审最深层发现，**跨篇矛盾在"设计层"而非"文档层"**。
- **补充发现**：粗召回本身也需要查询条件，查询条件来自用户输入的字面关键词——但用户输入可能是指代（"继续"），此时粗召回无法提取有效关键词。**指代输入在触发链第一环就断了**（除非先做轻量指代识别）。C 篇未处理"指代输入在粗召回阶段的退化"。

### 3.3 分级路径（契约注入 vs 经验召回）【设计亮点，全体系最佳】

"统一召回把确定性契约概率化；契约走注入、资料走召回"——**这是全体系最扎实的设计**：
- 第一性正确：契约是"定义存在"（骨骼，必须 100% 在场），经验是"累积存在"（血肉，按需浮现），访问模型本质不同。
- 与 memora 现状一致（persona/skill 不参与 recall、rule 走 bootstrap）——设计是现状的第一性论证，不是空想。
- 用户文档按"确定性等级"分流（高确定→注入、低确定→召回）——v1.1 补充后设计闭环。
- **局限**：确定性等级的**判定者未定义**——谁判定用户文档是"高确定性契约"还是"低确定性资料"？用户声明（"每轮必须遵守"）是自我报告，LLM 判定不稳定，规则判定（位置/命名/引用关系）需要定义。建议补"确定性分级判据"（如：被 rule/persona 引用=契约；独立长文=资料）。

### 3.4 优先级仲裁（priority 1|2|3）【P2-⑦】

- "顺序 ≠ 优先级，用 priority 字段表达冲突仲裁"——设计正确（避免缓存失效）。
- **缺陷**：priority 仅三档（1|2|3），且同档冲突无仲裁规则。例：system（P3）与 documents（P3 档）冲突时谁赢？v1.1 注释写"同档内 用户文档 > 系统内置"——但这是**隐式排序**，未进入接口字段（priority: 1|2|3 无法表达同档次序）。建议扩展为 `priority: number` + `tiebreaker: number`（同档内序号）或声明同档规则为显式字段。

## 4. D 篇：不中断工作模型设计评审

### 4.1 两态状态机（RUNNING/PAUSED）【P1-④】

"开启后常驻，仅 RUNNING/PAUSED 两态，无终止态"（D·L107/L153）。
对抗式追问：**异常怎么办？**
- 探索未来.md 有"异常"概念（风险 3：异常崩溃自动标记异常并暂停），D 篇简化为两态后，**执行异常/LLM 超时/工具失败**只能映射到 PAUSED——但 PAUSED 的语义是"可恢复"，异常暂停与用户暂停/Agent 暂停恢复条件完全不同（异常需先修因才能恢复）。
- 若异常也进 PAUSED，则"断点续跑"可能在异常未解除时盲目恢复 → 死循环/重复副作用。
- 修复：状态机应为 **RUNNING / PAUSED / ERROR（或 SUSPENDED）三态**：ERROR 可自动转 PAUSED（探索未来.md 机制），但保留异常原因，恢复前强制校验。两态是"产品语义简化"，工程上不够。

### 4.2 检查点（SessionCheckpoint）【P1-⑤，P0-②】

- **resource 槽位已补（v1.1）**：资源快照保证断点续跑可还原四元组资源维度——方向正确。
- **P0-②：上下文重建路径缺失**：检查点含 hotMemory（截断窗口）+ resource（资源快照），但**"断点续跑恢复后，截断掉的早期上下文如何重建？"未设计**。探索未来.md 的热/温/冷三轨（温=归档可召回）在 D 篇被映射为"温=归档（现有 recall 管道）"，但检查点恢复时的召回时机、召回条件、与热窗口的合并规则均未定义。恢复 = 快照 + 热窗口，早期上下文丢失 → **恢复后的 Agent 对任务早期脉络失忆**，与"断点续跑"的目标（不重复执行、保持上下文连续性）冲突。
- 修复：检查点恢复协议需定义"恢复 = 快照反序列化 + 热窗口载入 + **按需温记忆召回（以 mainGoal/currentGoal 为查询条件）** + 契约重注入"完整路径。
- **delta 合并规则缺失**：SessionEvent.delta = Partial<FourTuple>，但"增量如何与会话基线合并成完整四元组"未定义（覆盖？合并？数组追加？）。B 篇四元组是完整结构，D 篇 delta 是增量结构，两结构的转换规则缺失。

### 4.3 P4 暂停询问（猜 → 问）【哲学深刻，机制缺失】

- **哲学价值**：从"概率性猜测"到"确定性澄清"是缺省补全的正确演进方向，P4 作为终极形态成立。
- **机制缺陷**：
  1. **判定者未定义**：何时触发 P4？"信息缺失导致下一步完全无法推进"或"高风险操作"——由谁判定？LLM 每次生成时自判（不稳定）还是框架规则判定（信息缺失=任务槽为空且无指代可解析；高风险=工具风险标注）？D 篇未定义。若靠 LLM 自判，误判率高（LLM 倾向不暂停继续生成）。
  2. **暂停的阻塞性**：P4 暂停后等用户输入——若用户不响应，会话永久挂起（僵尸态）。D 篇有心跳防僵尸（检查点层面），但**P4 暂停自身的超时策略未设计**（暂停 N 分钟后自动恢复并输出兜底方案？）。
  3. **"连续 2 次暂停后必须输出方案"是软约束**：靠 LLM 遵守，无机制强制。
- 修复：P4 触发条件**结构化**（任务槽缺失且粗召回无候选 → 强制暂停；工具风险等级 high → 强制暂停），暂停设超时（如 5 分钟无响应 → 自动输出默认方案并降级执行），"连续 2 次"用状态机计数而非提示词约束。

### 4.4 目标版本控制（goalVersion）【设计亮点，P2-⑧】

- "goalVersion 单调递增 + 重规划锚定原始目标 + 偏差回溯"——防漂移设计正确，是探索未来.md 风险 6 的正确承接。
- **缺陷**："重规划必须与原始目标一致性校验，偏差超阈值提示建议新会话"——**校验与阈值判定由谁执行未定义**。若由 LLM 自评（"我的新计划与原始目标一致吗"），LLM 自评偏差检测并不可靠（LLM 倾向于确认自己的规划）。建议：确定性校验（mainGoal 关键约束哈希对比 / 目标文本相似度阈值）兜底 + LLM 解释，二者结合。
- 补充：goalVersion 与检查点的关系（goalVersion 变化是否触发检查点快照）未声明——建议"goalVersion++ 时强制检查点"。

### 4.5 事件意图分类（command/correction/clarify/chat）【设计合理】

- 防上下文污染设计正确（仅 command/correction 注入执行上下文，chat 单独存放）。
- **局限**：clarify（澄清）与 P4 暂停询问的关系未声明（clarify 是 P4 的触发输入类型，还是独立机制？）。建议明确"P4 触发后等待的输入类型 = clarify"。

## 5. 跨篇系统性问题

### 5.1 补全行为模型矛盾（B 覆盖 vs C 依赖 vs D 增量）【P0-①】

三个文档对"用户输入如何变成四元组"给出了三个**互不兼容**的模型：

| 篇 | 模型 | 原文要点 |
|---|---|---|
| B | 覆盖式 | "每槽独立走 P1→P2→P3，互不干扰"（L239） |
| C | 依赖式 | "解析本身需要上下文（『继续上次那个』没有记忆就无法解析）"（L180） |
| D | 增量式 | "每次事件只更新变动的槽位（delta）"（L128），事件相对当前状态 |

- B 与 C 直接冲突（覆盖 vs 依赖）；D 的增量模型依赖"当前状态已存在"（会话基线），与 B 的"每轮从道开始"（L163）冲突——D 篇声称是"扩展"而非推翻，但增量事件与"每轮从道开始"在语义上不兼容（若每轮从零开始，增量无基线可加）。
- **这是设计层的系统性矛盾，不是文档措辞问题**。修复方向：以 C 的触发链（依赖式）为正确行为模型，B 的覆盖模型降级为"完整自包含输入的特例"，D 的增量模型声明"基线 = 会话检查点（B 的『道』在会话模式下由检查点延续）"。

### 5.2 「一」的抽象漂移未收敛【P2-⑩】

v2.2 已声明"一"分概念/工程/演进三层（B=概念协议、C=parse+renderer、D=SessionEvent）。但设计层追问：**"一"到底是协议（契约）还是组件（实现）？**
- 协议是"形状约束"，组件是"执行者"。B 篇"一"是协议（请求形状），C 篇"一"是组件（parse+renderer 执行），D 篇"一"又是协议（事件形状）——协议与组件来回横跳，抽象漂移未被"三层声明"真正消除，只是被文档化了。
- 建议：将"一"收敛为**一个协议族**（Request 协议 / SessionEvent 协议，分属一问一答与不中断两模式），parse/renderer 是协议的实现组件，不再称"一"。

### 5.3 复杂度守恒检验【P2-⑨】

全体系抽象组件盘点：四元组 / 三源 / 四层管道 / 触发链 / 分级路径 / 渲染器 / SessionEvent / 检查点 / 状态机 / 目标版本 / P4 —— **11 个核心抽象**，每个都有存在理由。
- 复杂度守恒原则（用户哲学）：引入抽象的收益必须覆盖故障面。逐一检验：四元组（收益高）、三源（收益高）、分级路径（收益最高）、goalVersion（收益高）……大多成立。
- **但叠加后的行为模型未统一**（5.1 的矛盾）——11 个抽象组件构成一个系统，系统行为 = 组件交互，组件交互规则（补全/解析/增量如何配合）缺失，系统的"涌现行为"不可预测。这是复杂度的真实代价。
- 建议：补一张"端到端时序图"（用户输入 → 触发链 → 补全 → 渲染 → 执行 → 归档 → 回流，含不中断模式的事件流分支），强制各组件交互规则显式化。

### 5.4 与 memora 硬约束的对齐【通过，无冲突】

- 零第三方依赖（ADR-002）：D 篇否决 Redis/MySQL/BullMQ ✓；检查点走记忆统一模型 ✓。

## 7. 改进建议（按优先级）

### 建议 1（P0-①）：统一补全行为模型为「覆盖 + 指代解析」混合模型
- B 篇补全链改为：`P1 显式 → 指代检测（含指代/增量？）→ [是] 经 P2 记忆上下文解析 → 落槽 / [否] 直接覆盖 → P2 推断 → P3 兜底 → P4 暂停询问`。
- 声明"覆盖模型 = 完整自包含输入的特例"，依赖式（C 触发链）为通用模型。
- D 篇增量模型声明"基线 = 会话检查点，delta 与基线合并规则 = 槽位级覆盖 + 数组追加"。

### 建议 2（P0-②）：补"检查点恢复协议"
- 恢复 = 快照反序列化 → 热窗口载入 → 温记忆按需召回（以 mainGoal/currentGoal 为查询条件）→ 契约重注入 → 恢复校验（状态机 ERROR 转 RUNNING 前校验）。
- 明确 delta 合并规则（见建议 1）。

### 建议 3（P1-③）：四元组演进或边界声明
- 方案 A：演进为五元组 `(角色, 任务, 标准, 资源, 上下文/会话引用)`，输出规格并入标准或单独。
- 方案 B（推荐，复杂度守恒）：声明"四元组 = 单次请求语义结构；跨请求状态由会话层（D 篇检查点）承载，不在四元组内补槽"。选 B 则 D 篇 resource 槽保留但语义改"会话上下文"，不再声称"目标/计划是资源"。

### 建议 4（P1-④）：状态机三态化
- RUNNING / PAUSED / ERROR：ERROR 自动转 PAUSED 但保留 cause；恢复前校验 cause 已解除；ERROR 专属 UI 提示。

### 建议 5（P1-⑤）：P4 触发结构化 + 超时兜底
- 触发条件：任务槽为空且无指代可解析 → 强制暂停；工具风险 high → 强制暂停。
- 暂停超时：N 分钟无响应 → 自动输出默认方案 + 降级执行 + 日志标注。
- "连续 2 次暂停"用状态机计数。

### 建议 6（P1-⑥）：递归限定语义层
- 声明"资源⇄动作递归发生在 LLM 语义层，框架契约层固定动作/资源类型"。

### 建议 7（P2 批量）
- ⑦ priority 扩展为 `priority + tiebreaker` 或同档规则显式字段。
- ⑧ goalVersion 校验 = 确定性对比（关键约束哈希/相似度阈值）+ LLM 解释结合。
- ⑨ 渲染器拆 Renderer（排版）+ ContextManager（窗口/预算/恢复）。
- ⑩ 「一」收敛为协议族（Request/SessionEvent），parse/renderer 为实现组件。
- ⑪ delta 合并规则并入建议 1/2。
