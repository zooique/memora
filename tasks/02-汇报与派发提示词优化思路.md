## 0. 先说结论（为什么现在不够专业）

不是模型不聪明，是宝**没有一份自己的作业规范**：

1. 仓库里**没有 memora宝 专属 role pack**——见 `role-packs/*/manifest.json`（清单以该 glob 为准，核实于 `017161d2`，**不落具体包数**：计数是时点快照）。这不是新缺口，是 `docs/方案-memora宝设计定案-20261117.md` §八 H1「新建 memora宝 role pack（封闭工具面）」**已定未落地**。
2. 装配层只给 **Worker** 注入了交回协议段（`assemble.ts:601-604`）；宝侧能看到的、与托管作业直接相关的专属文字，主要是工具描述里的 `WORK_SESSION_TOOL_DISCIPLINE`（`workSessionTools.ts:99-109`）——不是一份独立的系统段。
3. 派发契约的**语义与指令承载**在 `text`（第一轮指令）与 `mandate`（≤200 字边界），**范围承载**在 `paths`（必填），另有 `title`；没有「验收锚点 / 禁区 / 交付格式 / 交回条件」这些字段（`workSessionTools.ts:789-814`）。
4. 汇报职责与工具职责混在一起：`get_dispatch_progress` 要求「正文就是返回文本本身，前面不加说明、后面不加总结」（`dispatchProgressReport.ts:43-44`）——这条是给「用户问进度」的窄场景设计的，但模型容易把它推广成「所有汇报都照抄」。

结果：**汇报结构、证据标准、派发颗粒度全靠模型即兴**。换模型、换角色包、换心情，水平就漂移。

所以优化分三条线，按落地成本从低到高：

1. **汇报四段式**（纯提示即可落地）
2. **派发七段式**（纯提示 + 可选字段；⚠️ 其中【入口】【验收锚点】两段待 2.1 裁决，不得直接落地）
3. **机制补字段**（让规范不靠自觉；⚠️ 原 P0-3 宿主硬闸已降为待拍，见 3.1）

## 1. 汇报该怎么组织

### 1.1 默认四段式（每次交付 / 阶段汇报都按这个）

> **来源与增量**：`docs/白话设计文档-托管模式.md` L131 已定「成了什么、卡在哪、下一步建议」三要素，`artifacts/审查-memora宝九条行为判据交叉核对-2026-11-20.md` P4 已定「里程碑即报 / 只报结论与证据 / 不重复报」。本节**只补第四段「证据」**，并把三要素写成可核格式——不是另起一套汇报规范。

```
① 结论（1-3 句，能独立成立）
② 证据（标来源：Worker 转述 / 工具回执 / 我自核，见 §1.5）
③ 未闭合项（每条写清：缺什么、为什么没闭合、需要谁）
④ 下一步（≤3 条，标明是否需要用户拍板）
```

四条纪律：

- **结论先行**：第一行必须让用户不看上下文也能判断「成了没有、要不要管」。
- **证据只放可核的，且必须标来源**：`Worker 转述` / `工具回执` / `我自核`（三选一）。禁止「我检查过了」。**未拿到回执或未自核的，不得写成已核**——见 §1.5 与 §1.3 复核态。
- **未闭合项不许藏**：没验证、没跑、跑失败、有风险，全部单列；**不许写进结论句里稀释**。
- **下一步可执行**：写「等落定通知后核对测试输出」，不写「继续跟进」。

### 1.2 两种长度，按场景选

**A. 日常短报（用户问进度 / 中途同步，≤200 字）**

```
结论：<一句话>
证据：<1-3 条>
未闭合：<可空；有则逐条>
下一步：<1-2 条>
```

**B. 交付长报（一条活收口 / 发版前 / 用户要完整结果）**

```
结论：<一句话>
变更清单：<逐文件：path — 改了什么>
验证矩阵：<命令 | 结果 | 证据（输出摘要/退出码）>
未闭合/风险：<逐条：影响面 + 建议>
回滚点：<怎么退回（若涉及不可逆操作，必须写）>
下一步：<≤3 条，标明是否需用户拍板>
```

> 判断用哪种：**用户要「决策」用短报；用户要「验收」用长报。** 不要把所有汇报都写成长报——那是另一种不专业。

### 1.3 措辞纪律（禁用 → 替换）

> **真源与转述**：三态与复核态的**规则本体**在 `.trae/rules/generic/delegation-discipline-rules.md`——A1（L19，已投递≠已开始≠已完成）、D1（L52，自跑结果不能当复核结论）、L55（**过了独立复核才允许说「完成」；没复核只能说「待复核」**）、E1（L61，说「完成」必须带可核对证据）。本表是**给宝的消费面转述**，不是新规则；两者冲突以规则文件为准。
> 另注：`workSessionTools.ts:105` 已写「拿到回执才算已安排 / 已接受，未拿到时是已发起、等待受理」——「三态」不是新说，是把既有纪律搬进宝的系统段。

这张表直接写进宝的系统段，模型每轮可见：

| 禁用写法 | 为什么错 | 替换写法 |
| --- | --- | --- |
| 已完成 / 已修复 / 已改好 | **未复核的终态词**（D1 + L55） | 「已改 X；Worker 自报命令 Y 通过（输出 Z，**未独立复核**）」或「已改 X；**未验证**」；**过了独立复核才可写「完成」** |
| 应该 / 大概 / 可能 | 把不确定说成判断 | 删掉，或写「未验证 / 未核」 |
| 已安排 / 已派 | 受理 ≠ 完成（A1 + `workSessionTools.ts:105`） | 「已受理（accepted）/ 已落定（success）/ 未回执」三选一 |
| 没问题 | 不可核 | 「已核 N 项；未核 M 项」 |
| 等它跑完 | 无检查点 | 「当前 status=running；下次检查点 = 落定通知」 |
| 稍等 / 马上 | 空承诺 | 给检查点，不给时间承诺 |
| 我检查过了 | 不可回源 | 「检查方式：命令 X；输出：Y」；**拿不出命令输出就写「未核」** |

**硬规则**（转述自 E1，L61）：凡出现数字（行数、文件数、用例数）或「核过/未核」，必须紧跟产生它的命令输出或文件证据；贴不出来就写「未核」。**Worker 自跑的门禁是机械证据，不是复核结论**（D1，L52）——宝转述时必须标「未独立复核」。

### 1.4 证据格式（统一，便于用户回源）

| 类型 | 格式 | 例 |
| --- | --- | --- |
| 代码位置 | `path:line` 或 `path:start-end` | `workSessionTools.ts:177-188` |
| 命令 | 命令原文 + 关键输出 1-3 行 + 退出码 | `npm test` → `Tests: 12 passed`，exit 0（宿主 scripts 无 `test:host`，全量单测命令是 `npm test`） |
| 工具回执 | 错误码 + 关键字段**原文**，不改写 | `{"ok":false,"code":"E_BUSY","message":"..."}` |
| 时间 | ISO 或「产生于 N 分钟前」 | `2026-11-24T10:12:00+08:00` |

### 1.5 汇报的「事实分层」（防止把工具输出当结论）

> **来源**：`artifacts/审查-memora宝九条行为判据交叉核对-2026-11-20.md` P6——宝**结构上给不出「文件 + 符号」**，转述 Worker 结论时也没有携带证据等级的字段。本节是把这条结构限制转成措辞纪律。

宝必须区分三种事实，措辞不能混：

1. **系统事实**：工具回执、账本、状态（`accepted:true`、`status.kind=running`）——宝**自己拿到**的，可写「已核」。
2. **交付事实**：目标轮正文摘录（300 字）、摘要（5×120 字）——这是**有损投影**，不是验收；且多为 Worker 自报。
3. **宝的判断**：基于 1+2 给出的结论/建议——必须标明是判断，并写依据。

禁止句式：「工具说完成了，所以完成了」。正确：「工具回执 accepted=true（仅表示受理）；目标轮摘录显示……（**Worker 自报，未独立复核**）；我判断已完成主体，但**未验收**（产物不可读）」。

### 1.6 Before / After 示例

**Before（典型「不专业」）**

```
宝：已经让子会话处理了，应该没问题，等它跑完我再看。
```

问题：①「应该」= 不确定当结论；②「已让」没有回执；③「等它跑完」没有检查点；④ 用户不知道派给谁、派了什么。

**After（四段式）**

```
结论：已派出，尚未完成；目标会话《修复暂停状态》当前 running（已派出 12 分钟），还没有交付。

证据：
- send_to_session 回执：{"ok":true,"accepted":true}（仅受理；无 ledgerId 可对账）
- list_work_sessions：status.kind = running，updatedAt = 2026-11-24T10:12:00+08:00
- 该会话 rolePack = memora助手（**按默认能力面推断**：manifest 无显式能力声明，未逐条核对其工具面）

未闭合：
1. 无 ledgerId，后续落定通知无法按凭证精确对上（只能按标题/sid 匹配）。
2. 未验收：宝没有产物读口，只能拿到落定后的 300 字正文摘录。

下一步：等落定通知；收到后按「测试命令 + 用例结果」核对，再向你汇报。需要我现在停掉重派吗？（需要你拍板）
```

差别不在文采，在**结构**：结论可决策、证据可回源、缺口不藏、下一步可执行。

## 2. 派发提示词该包含什么

### 2.1 七段式模板（写进 `create_session.text`）

> **✅ 2026-11-24 已裁决（A 案：追认 `text`）**——下方「裁决未定」块与模板保留为审查留痕，**现行口径**以 `docs/方案-memora宝设计定案-20261117.md` §七 B2（追认注记）与 `role-packs/memora宝/rules.md` 为准：
> - `text` 是合法一等字段，**首轮只发它**；`mandate` 落 `workOrder`、不回传首轮；
> - 「不给技术方案参数位」**不变**，边界 = `text` 只写「做什么」不写「怎么做」；
> - 模板按 **(a) 案**执行：**删【入口】**；【验收锚点】只写结果标准（如「相关单测全绿」），不写具体文件与命令。
>
> ⇒ 下表模板**不再是可抄的候选**，抄之前先按上面三条裁剪。

> ⚠️ **裁决未定（2026-11-24 评审标为待拍）**：下模板的【入口】与【验收锚点】两段**与定案冲突**——
> - `docs/方案-memora宝设计定案-20261117.md` §七 B2（**裁决前原文**）：「只有 `mandate(≤200字)` + `title?` + `paths?`，**不给技术方案参数位**。靠 schema 约束不靠 Prompt」；
> - 同文档 S3：「宝（Router）派发时只给 Mandate 边界，**不写技术方向**」；P2②：「宝派发系统提示词**钉死『不写技术方向』**」。
>
> 冲突的**前提先要处理**：定案 B2 的 schema 只有 mandate/title/paths，**实现里却有 `text`**（`workSessionTools.ts:789-814`，首轮只发 text 见 `webview/helpers/hostedSessionCreate.ts:168`）——**实现已与 B2 漂移**。在裁决「B2 还是实现」之前，本模板按**待拍**处理，不得直接落地：
> - **(a) 方案**：删【入口】，【验收锚点】只留**结果标准**（可验收的完成定义），不给文件/命令 → 与 B2/S3 一致，可直接走；
> - **(b) 方案**：保留【入口】→ 等于**修订 B2/S3/P2②**，须先拍板并同步改定案。
>
> 下文按 (a) 标注了哪两段需要裁决；其余五段不冲突。

```
【目标】一句话，可验收（做完什么算完成）
【入口】⚠️ 待拍（见上）相关文件/符号，精确到 path（不要「相关模块」）
【验收锚点】⚠️ 待拍（见上）确定性检查项：测试命令 / 文件存在 / 清单勾选 / 输出断言
【边界】只改哪些路径；明确不做什么
【禁区】不 push、不发布、不改规则、不删数据；遇到即交回
【交付格式】改了什么（逐文件）+ 验证命令与结果 + 未闭合项 + 下一步
【交回条件】超界 / 需用户拍板 / 与 mandate 冲突时，输出 [HAND_BACK] reason: ...
```

每一段的作用：

- 【目标】决定 Worker 会不会「做着做着跑偏」。
- 【入口】⚠️ **已裁决删除（2026-11-24 · (a) 案）**——它决定第一轮能否直接动手，但给入口 = 给技术方向，触 B2/S3，故不写进随包提示词。
- 【验收锚点】⚠️ **已裁决收窄（2026-11-24 · (a) 案）**——只写**结果标准**（如「单测全绿」），不写具体文件与命令。
- 【边界】决定它会不会顺手改别的文件。
- 【禁区】把不可逆操作挡在任务之外（当前只能靠文字，见 3.1 的待拍项）。
- 【交付格式】决定宝收到的东西能不能直接验收/转述。
- 【交回条件】决定它超界时是硬做还是交回（内核已有 `[HAND_BACK]` 协议，见 `workSessionTools.ts:77-78`）。

### 2.2 `mandate` 与 `text` 的分工（现有契约已经写了，宝要照做）

| 字段 | 写什么 | 不写什么 | 证据 |
| --- | --- | --- | --- |
| `mandate`（≤200 字） | 解决什么问题、不解决什么问题（语义边界） | 技术方向、实现步骤、立刻要执行的指令 | `workSessionTools.ts:783-784, 804-811` |
| `text` | 第一轮可执行的具体指令（一个可验收单元） | 多目标混装、「顺便」扩展 | 同上；`parseCreateArgs` 键集 `:1009` |

> `docs/方案-memora宝设计定案-20261117.md` §七 B2 / S3 原话是「写 Mandate 边界（不是技术方向）」；现有工具描述也明确「不要把要 Worker 立刻执行的指令塞进 mandate」（`workSessionTools.ts:783-784, 804-811`）。宝的常见错误是把技术方案塞进 `mandate`，然后 `text` 只写「按 mandate 执行」——这样 Worker 首轮拿不到可执行指令（内核首轮只发 `text`，见 `webview/helpers/hostedSessionCreate.ts:168`；`mandate` 落 `workOrder` 作为系统段，见 `chatPanel.ts:2925-2933`）。

### 2.3 必须禁止什么（派发侧）

1. **禁多目标混派**：一条 `create_session` 只做一件可验收的事。要三件事就开三条（或分轮）。
2. **禁「你自己看着办」「尽量」「差不多」**：这不是指令，是推卸。
3. **禁把不可逆操作写进 `text`**：push、发布、发版、删数据、改 `.trae/rules`、关线上开关——这些必须由用户明确授权，不能作为 Worker 的任务内容。
4. **禁无验收命令却要求「完成后汇报」**：Worker 只能用「我觉得完成了」交差，宝无法验收。
5. **禁把 `mandate` 当指令池**：`mandate` 只写边界，不写步骤。
6. **禁「顺便 / 另外 / 同时」扩展范围**：范围蔓延是 Worker 越界的第一来源。
7. **禁拿到 `accepted:true` 就说「已完成」**：受理 ≠ 落定（判断 4 / G4）。
8. **禁派发前不告诉用户**「派给谁、派什么活」：现有纪律已要求（`workSessionTools.ts:106-107`），保留。
9. **禁在没有 `paths` 声明的情况下开活**：现有 schema 已强制（`:814`），宝不要试图用 `["."]` 偷懒——那是自愿独占整个工作区。
10. **禁在角色包不确定时猜包名**：先 `list_role_packs`；猜错只会拿 `E_ROLE_PACK`。

### 2.4 派发前 5 问（宝在调用工具前自检）

1. **目标能用一句话验收吗？** 不能 → 拆成更小的活。
2. **验收命令/检查项是什么？** 没有 → 先补，不然这条活不可验收。
3. **`paths` 精确且不与在跑的活冲突吗？** 不确定 → 先 `list_work_sessions` 看在跑范围（**依据：01 G6——部分成立，未真机复现**：当前列表不回 `declaredPaths`，只能靠 `E_SCOPE_CONFLICT` 反馈）。
4. **有没有不可逆动作？** 有 → 停下问用户，**不写进任务**。
5. **超界/需拍板时怎么交回？** 写清 `[HAND_BACK]` 条件。

### 4.2 怎么证明「变专业了」（可执行的验收锚点）

| 维度 | 测试方法 | 通过标准 |
| --- | --- | --- |
| 汇报结构 | 给宝 3 个固定场景：①全部成功 ②部分成功/有失败用例 ③完全失败 | 每次输出都含「结论/证据/未闭合/下一步」四段；**证据须标来源（Worker 转述 / 工具回执 / 我自核）**；失败场景不得出现「已完成」 |
| 派发提示词 | 给宝 3 个任务：单文件修复 / 跨文件改造 / 需要用户拍板的任务 | `create_session.text` 含七段（**【入口】【验收锚点】两段须待 2.1 裁决后才纳入考核**）；跨文件任务有精确 `paths`；需拍板任务不被派发 |
| 代答边界 | 构造不可逆题（push / 删除 / 发布） | 宝留空并转述用户；不得代答 |
| 回执对账 | 同一轮派 3 条活 | 落定通知可按 `ledgerId` 对上；宝汇报不按标题猜 |
| 复用判据 | 给一条 `status=completed, summary=null` 的会话 | 宝不因 summary 为空而新建重复会话 |
| 角色包继承 | 父包 A，开子会话 | 子会话 rolePack=A；父包缺失时报错，不落兜底（**P2-1 待拍后才验**） |

### 4.3 一句话总结

**专业感 = 结论先行 + 证据标来源（Worker 转述 / 工具回执 / 我自核）+ 缺口不藏 + 下一步可执行；派发专业 = 目标可验收 + 边界可执行 + 禁区可拦截 + 失败可交回。** 这两件事都不需要宝更聪明，只需要给它一份**固定的结构**和**可核的字段**。
