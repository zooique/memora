## 二、设计缺口（按根因层排序）

### 缺口 1【元缺口 · 最高】审查产出无「入账契约」

**现象**：报告入库 ≠ 结论入账。**没有任何规则规定「审查报告的每条 P0/P1 必须转成台账条目」。**
**后果**：报告成为孤儿文档；台账与事实脱节 → 两个真理源给出相反结论（§一-3）。
**修法**：把「审查报告 → 台账登记」定为收口动作，与既有纪律「设计决策先文档化为闭合闭环」同源。

---

### 缺口 2【机制缺口】闸门无自动触发器，且 CI 恢复后仍不完整

- CI 自动触发自 **2026-08-27** 起停摆（`kernel-ci.yml:24-31` 的 `push:`/`pull_request:` 整段注释）。
- **更关键：CI 恢复后仍不完整** —— **不含 `docs:links`，不含 coverage**。
- → 5 个闸门（tsc / eslint / vitest / coverage / docs:links）中，**恰好两个「会静默退化」的闸门永远靠人工记忆**。
- **因果闭环证据**：C7 死链闸门「已收口」→ 又被**回归为红**（报告 P0-3）。死链与覆盖率都不会自己叫。
- **判据**：`docs:links` 自身有 `exit 2 = 闸门已瞎` 的自检 —— 但**没有任何东西定期跑它**，所以它瞎了也没人知道。

**修法**：恢复自动触发 **+ 补 `docs:links` 与 coverage 两步**（发版阻塞项）。

---

### 缺口 3【数据缺口】数字无 SSOT —— 同一事实五个来源、五组数字

| 来源 | 测试数 | 覆盖率 |
|---|---|---|
| `README.md` badge | 2813 | 81% |
| `kernel-ci.yml:11` 注释 | 2337 | — |
| `CHANGELOG.md:7` | 2369 | — |
| 台账 :51（2026-09-13 标 ✅ 已修） | 2813 | 80.8/72.5/83.2/82.3 |
| 报告（2026-09-14） | 2930 | 91.08/84.04/91.77 |
| **实测（`dc9072f8`）** | **2949**（115 文件，+1 skip） | **91.81/72.66/93.42/91.76** |

**并且每修一次立刻再次过期**：2446 → 2813 → 2930 → 2949。
→ 根因不是笔误，是**「人手抄写数字」这一机制**。故台账「发包前数字可复现核查 ✅」属**过早销项**。
**修法只能是 SSOT 化**：badge 动态化或删除；表格数字改为「由命令生成」并写进发版检查单。

### 缺口 4【发布缺口】发布动作只余类型一道门

`package.json`：`prepublishOnly = npx rimraf dist && npm run build`（= `tsc -p tsconfig.build.json && tsc-alias`）
→ **不跑 `test` / `lint` / `docs:links` / coverage**；仅 `tsc` 提供类型门。
→ 叠加缺口 2（CI 停摆）：**覆盖率红、死链红都拦不住 `npm publish`**。

### 缺口 5【契约缺口】公共 API 面未拍板 = 发版即无限承诺

- `src/index.ts` 导出 **198 个标识符**，其中 **70 个（35.4%）**在 8 份公开文档零出现。

- 而 CHANGELOG 明写「**3.0.0 是架构收敛后的第一个稳定基线**，API 与结构以 3.0.0 为准」。
→ **发 3.0.0 的瞬间，这 198 个导出全部成为 semver 契约**。
→ 注：项目既有「版本契约分面」原则只区分了**作者输入面**与**持久化数据面**，**未覆盖公共 API 面** → 本缺口建议**新增第三个分面**（属提案，非既定规则）。

## 三、CI 零残留方案（回应「CI 运行后 GitHub 残留塞满上限」）

### 三-1、残留来源已定位（实锤）

**当前仓库只有 2 个 workflow 文件**（`kernel-ci.yml` + `dependabot.yml`），但历史上存在过 **`build.yml`（Memora Sprite 打包流水线）**，于 `81468568`（2026-09-03「移除 sprite 宿主」）删除。它有三个重资产残留源：

| 残留源 | 内容 | 量级 | 是否自动清理 |
|---|---|---|---|
| `actions/upload-artifact@v5` ×3（win/mac/linux） | Electron 打包 `.zip` + **NSIS `.exe` 安装包** | 单个百 MB 级 | `retention-days: 3`（已过期，但**需确认**） |
| `actions/cache@v5`（Electron 二进制 + electron-builder） | `~/AppData/Local/electron/Cache` 等 | **数百 MB–1GB+** | ❌ **不自动过期**（LRU 满 10GB 才驱逐） |
| `softprops/action-gh-release@v2` | 发布到独立仓 **`memora-sprite-releases`** | 每个 tag 一套安装包 | ❌ **永久** |

→ 三者叠加，完全解释「CI 跑一段时间就把配额塞满」。

**另注**：`build.yml` 里的 `release` job 带 `permissions: contents: write` + `GH_TOKEN`，且 `package:win` 用 `GH_TOKEN` 发布 —— 这是**跨仓发布**，残留落在**另一个仓库**的存储配额上。

### 三-2、当前 `kernel-ci.yml` 的残留面（已收敛但非零）

| 项 | 现状 |
|---|---|
| `upload-artifact` | ✅ 无（注释已写明「不需要上传产物，节省 Actions 存储配额」） |
| `actions/cache` | ✅ 无 |
| `softprops/action-gh-release` | ✅ 无 |
| **`setup-node` 的 `cache: 'pnpm'`** | ⚠️ **唯一残留面** —— 写入 GitHub Actions Cache |
| `permissions` | ⚠️ **未声明** → 默认权限较宽（继承仓库默认设置） |

→ 结论：**当前内核 CI 已基本干净，只剩 pnpm cache 一项**；但「不残留任何东西」还差两步。

### 三-3、改法（已实施）

```yaml
# 顶层新增：最小权限，杜绝任何写（packages / releases / 仓库内容）
permissions:
  contents: read

# 删除 setup-node 的这两行 → 不写 GitHub Actions Cache
          # cache: 'pnpm'
          # cache-dependency-path: pnpm-lock.yaml
```

**代价**：每次 CI 重新 `pnpm install`（不再命中缓存）→ 对零依赖内核，dev 依赖安装约 1–2 分钟，可接受。
**收益**：CI 运行后**不产生任何 GitHub 侧持久化残留**（artifact / cache / release 三者皆零）。

> 注：**workflow run 日志**由 GitHub 平台自动保存（默认 90 天自动清理），**无法也不应关闭** —— 它不计入「Actions storage」配额（属平台免费行为）。

### 三-4、历史残留清理（**必须手动**，代码改动不会回收已产生的）

在可用的终端（PowerShell / Git Bash）执行：

```bash
# 1) 清空本仓 Actions cache（不会自动过期的那部分）
gh cache delete --all --repo <owner>/memora

# 2) 列出并删除本仓 Actions artifacts（若仍有未过期项）
gh api /repos/<owner>/memora/actions/artifacts --paginate \
  | jq -r '.artifacts[] | "\(.id) \(.name) \(.size_in_bytes)"'

# 3) 清另一仓 memora-sprite-releases 的历史 Releases/附件（占用该仓 storage）
gh release list --repo <owner>/memora-sprite-releases
gh release delete <tag> --repo <owner>/memora-sprite-releases --yes --cleanup-tag
```

**网页等效路径**：仓库 → Settings → Actions → General → 「Artifact and log retention」可下调保留天数；Actions 页 → Caches 可逐个删除。
