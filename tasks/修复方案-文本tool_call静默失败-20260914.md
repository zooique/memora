## 〇、大白话：为什么会出现这种严重 bug

**一句话**：包工头在墙上贴了两种下单方式，但工地上只装了一个收件箱，只认其中一种；没人发现，因为**每种角色单独看都在做对的事**。

拆成 6 步：

1. **包工头（内核）贴了两张通知。**
   第一张贴在正式公告栏（原生 `tools` 参数）："活儿都在这儿，按格式填单子。"
   第二张刷在墙角（prompt 文本）："**你也可以直接喊一声**说要干什么。"
2. **工地只有一个收件箱，只认公告栏那种单据。** 墙角那句"可以喊一声"——**没有人负责听**。它只是一句刷在墙上的话，没有对应的岗位。
3. **工人（mimo 模型）看公告栏没把握，又看到墙角写着"可以喊一声"，就喊了。** 而且喊得含糊：`<function=list_dir` 标签都没闭合，连"读哪个目录"都没说。
4. **收件箱没收到单据，包工头就判定"这轮没有活要干"，在验收单上盖了章："完成"。**
   注意——盖的不是"失败"，是"完成"。因为验收单上那一栏的判据本来是"**这段流程跑完了没有**"，而不是"**活干成了没有**"（`chatPanel.ts:2570`：`success = 没被打断 && 没被暂停`）。
5. **那句喊话被当成"普通发言"转给了前台（宿主）。** 前台有个保安（DOMPurify），职责是**只让安全的东西进门**。这句话技术上**全是标签、一个字正文都没有**，保安按规矩把不认识的标签全撕了——撕完一看，**空的**。
6. **前台挂了一块空白牌子。** 用户看到的是：想了一下，然后什么都没说。

**为什么它能活着送到用户手上？** 因为它**不需要任何一处写错代码**——每一环都是"按自己的职责正确执行"：

| 角色 | 它的理解 | 它做错了吗 |
|---|---|---|
| 模型 | 你让我可以喊一声，我喊了 | 没有（虽然喊得烂） |
| 内核 | 没收到单据 = 没活要干 = 完成 | 没有（它只认一种单据，且判据是"跑完"） |
| 宿主 | 撕完是空的 = 没什么可显示 | 没有（保安的职责是安全，不是可用性） |

**第一性原理**：这不是"某个函数写错了"，是**契约单向**——
系统**向下游宣告了两种交付方式，却只验收其中一种**。宣告方与验收方不成对。
而"验收"那一栏的判据是"流程有没有跑完"，于是**"想干活但一步没干成"被盖章为完成**。

**它为什么躲过了所有测试**：测试都建立在"**模型会给单据**"这个前提上。
前提本身是错的，所以测例再多也照不到——这也解释了为什么一个"必然发生"的路径能潜伏到用户手里：
它不是偶发 bug，是**一条从设计上就没人验收的通道**。

## 二、根因重构：不是「宣告了没实现」，是「同一事实写在两处」

**原表述**（诊断/排雷）：内核宣告了文本 tool_call 通道，却从未实现解析器。

**带伤模型下的更准表述**：**「本轮哪些工具可用」这个事实被写在两处**，靠人工保持一致——

| 出口 | 位置 | 消费者 |
|---|---|---|
| 文本出口 | `buildSystemPrompt`（`:1739-1749` 渲染工具清单） | **无**（零解析器） |
| 原生出口 | `buildChatOptions`（`:1804-1811` 传 `tools`） | `openaiCompatible.ts:397-414` |

🔴 **历史折衷证据（规则 §2「真带伤」的硬性依据）**——`loop.ts:1437-1444` 的注释自陈：

> 「首次置位时同步重建 system prompt（**V2 修复**）：buildSystemPrompt 按 searchDisabled 过滤 web_search 描述，
> 剔除「**描述存在但工具不可用**」不一致——**此前 messages[0] 只在构造 / refresh 时机重建，描述残留到闭环结束**。」

这段注释就是伤痕本身：**因为同一事实有两个出口，所以需要一个 `sync` 函数（`rebuildSystemMessage()`）去对齐；
而在补这个 sync 之前，两个出口已经漂移过**（"描述残留到闭环结束"）。

→ **结论**：缺陷 A（谓词重复）与缺陷 B（空壳通道）**是同一处伤口的两面**：
只要"工具集"这个事实还是两处各自表达，就会不断长出新的失配——
这次的失配形态是"**其中一轨从来没人验收**"。

→ 因此修复不能只在 B 上"补个解析器"（那只把空壳填上，两处表达照旧）；
**必须先在最小单元上把「工具集」收敛成一处**（规则 §5.2）。

## 三、收敛方案（按规则 §5 六步）

### 3.1 最小单元收敛：单一真源「本轮可用工具集」

落点 `src/agent/loop.ts`，新增私有方法：

```
private resolveActiveTools(): readonly ToolDefinition[] {
  const all = this.opts.toolDefinitions ?? [];
  return this.searchDisabled ? all.filter((t) => t.name !== 'web_search') : all;
}
```

- `buildSystemPrompt`（`:1735-1737`）→ `this.resolveActiveTools()`
- `buildChatOptions`（`:1798-1800`）→ `this.resolveActiveTools()`
- **消除**：同语义多实现（排除谓词 2 处 → 1 处）；新增排除工具只改一处。
- **诚实边界**：`rebuildSystemMessage()` **不能删**——prompt 是装配期快照，工具集变化仍需重建。
  我们消除的是**谓词重复**，不是"重建"这个动作。不把它写成"双轨变单轨"（那是过度承诺）。
- **守卫**：`loop.ts` 内 `filter((t) => t.name !==` 命中数 === 1（结构断言，防再长出第二处）。
- **变异**：把 `resolveActiveTools` 的过滤删掉 → 需有「searchDisabled 后两出口都不含 web_search」的用例转红。

### 3.2 通道唯一性：产出即承诺（渲染与解析同模块）

新增 `src/llm/textToolCalls.ts`，**同时**导出两个函数：

| 导出 | 角色 | 唯一性 |
|---|---|---|
| `renderTextToolInstructions(tools)` | 文本出口（**唯一**产出点） | 全库唯一渲染点 |
| `parseTextToolCalls(text, toolNames)` | 文本入口（**唯一**解析点） | 全库唯一解析点 |

- **同文件即契约**：渲染与解析是一对，改一个必然看见另一个——这正是本项目已有范式
  （`extractSkillReferences` 双向守卫共用同一提取器）的镜像。
- `buildSystemPrompt` 的文本段改为：**仅当本轮走文本通道时**才调 `renderTextToolInstructions()`；
  否则不产出该段（不宣告不存在的通道）。
- 「是否走文本通道」的判据来源：`AgentLoopOptions.nativeToolCalling?: boolean`
  （宿主注入，**缺省 `true`**）→ 现有支持原生 FC 的 provider 行为**完全不变**（零回归）；
  Ollama 类显式 `false`。
- **解析三闸**（缺一不可，见排雷报告 AR1）：
  ① `content.trim()` **锚定全匹配**（禁 `includes`）；② name ∈ 入参 `toolNames` 白名单；
  ③ 仅当本轮无原生 `toolCalls` 时调用。
- **唯一调用点**：`handleIteration` 取到 `LlmCallResult` 后、`:964-988` 路由判定**之前**统一过一遍。
- **判据不同源纪律**：本处执行判据**严格**；3.3 的告警判据**宽松**。两者都必须保留且**禁止统一**
  （统一 → 要么漏报要么误执行）。

### 3.3 放大器：新增「未解析工具意图」信号（**独立于 A/B，必须做**）

**内核**（`loop.ts:1362 handleTextResponse`，纯文本结束的唯一收口）：
- 宽松判据命中（含 `<tool_call` / `<function=`）+ 本轮无 `toolCalls`
  → `logger.warn` + 递增新计数 `unparsedToolIntentCount`（加在 `LoopMetrics`，与既有 9 字段同族）。

**宿主**（透出，规则 §3 的"对称的另一半"）：
- `chatPanel.ts` 的 `metrics` processEvent 增加该字段；
- `chatView.ts:1273` 指标行追加「未解析工具意图：N 次」；N>0 → 该轮不得显示为「完成：是」。

**术语对齐（带伤收敛，与上面的功能修复分开做）**：
`ProcessMetricsPayload.success` 名实不符 —— 四处四个说法：

| 处 | 说法 |
|---|---|
| 字段名（`roundStore.ts:153`） | `success`（**成功**） |
| 注释（`:152`） | "是否**成功完成**" |
| 实现（`chatPanel.ts:2570`） | `!aborted && !paused`（**完成**） |
| 显示（`chatView.ts:1273`） | "**完成**：是/否" ← 显示层已在说实话 |

→ 显示层已经把它读作"完成"，说明**判据本身没错，错的是字段名**。
→ 最小改动（推荐）：统一到「完成」语义——改 `roundStore.ts:152` 注释为
   「本轮是否正常收尾（false = 中断 / 暂停）」+ `chatView.ts:1273` 文案「收尾：正常 / 中断」。
   **字段名暂不改**（属持久化数据面，改名须走 deprecation，见 3.5 同理）。
→ ⚠️ **不得用改名冒充修复**：真正的修复是 3.3 的新增信号，改名只是术语纪律。

### 3.4 渲染出口：**不属带伤收敛，单列**

- 判定：`renderMarkdown` / `createSanitizer` = **良性**（§一 D）；`fixIncompleteMarkdown` = **良性**（§一 E）。
- 因此「净化吃空 → 回退显示转义原文」是**新增可用性出口**（新功能），**不是带伤收敛**。
- **必须单独提交**，不混进 refactor 批次——否则是"把新功能伪装成收敛"。
- 落点：`renderMarkdown.ts` 内部（唯一收口，1 定义 / 3 调用全在 chatView）；
  判据 = 「净化**前**有可读文本 且 净化**后**为空」（**不用**「原文非空」，否则 `---` 等合法无文本渲染被误伤）。

### 3.5 `messageCount`：派生量单点 + 禁止造值

- 收敛：新增私有 `deriveMessageCount(sessionId)`（唯一派生点 = `roundIds.length * 2`）；
  `updateRoundBasedMessageCount`（`:359-364`）与 `updateSessionMeta`（`:249`）**均调它** →
  消除 `?? 0` 造值 与 `:186` 的重算，四点归一。
- **不删字段**：`SessionMeta` 属**持久化数据面**（宿主写 `sessions.json`），删须留迁移（版本契约分面）。
- **内核侧不动**（§一 G：是接口契约的同构要求，不是带伤）。
- **守卫（L12）关键前置**：必须先断言「`metas.has(id) === false` 且 `roundIdsStore` 已有 1 轮」
  再断言最终 `messageCount === 2`——否则场景里 meta 已存在、`appendRoundId` 会正常派生，
  用例会**因错误的原因通过**（规则 §9 陷阱）。

## 四、规则自身的 3 个缺口（建议补入 §3，本 bug 实证）

1. **「恒真回退」变体未列**。§3 降级兜底残留只列了 `??` 恒右侧 / `||` 恒死。
   本次 C 是**布尔表达式恒真**（`!aborted && !paused` 在正常轮次恒 `true`）→ 同族未被覆盖。
2. **缺一类「僵尸声明」**。四类模式都没有容纳：
   - 注释宣称一个零实现的能力（`provider.ts:37`）
   - 能力位恒 false 且零消费（`supportsStructuredOutput`）
   - 派生字段零消费者（`messageCount`）
   - 通道宣告零验收（`loop.ts:1749`）
   这四者**是同一个模式**（宣称一件生产代码里不存在的事），且**正是本 bug 的统一形态**。
   建议新增 §3 第 5 类：**僵尸声明 —— 字段 / 注释 / 能力位 / 对外宣告，宣称了生产代码零消费的能力或事实。**
3. **§6 已收敛清单是「字段级」，须升级为「模式级」**。
   §6 已登记「`SessionMeta.roundIds` 双轨镜像 → 已删字段」，
   但**没登记"派生量镜像进 meta"这个模式** → 于是 `messageCount`（同一模式的另一实例）**复发**。
   建议 §6 每条同时记「**已收敛的模式**」而非仅「已删的字段」，
   并写明该模式的**复发识别信号**（例：任何「把真源的派生量缓存进 DTO」都是候选）。

## 六、不做清单（防过度设计）

- ❌ 不抽通用"工具通道框架"（本场景只需一个模块 + 两个函数；复杂度守恒）。

- ❌ 不删 `SessionMeta.messageCount`（持久化数据面 → 须迁移，ROI 低）。
- ❌ 不动内核 `inMemorySessionStore.ts:227`（§一 G：同构契约，非带伤）。
- ❌ 不把 `fixIncompleteMarkdown` 当带伤"收敛"（§一 E：它不满足 §1 定义）。
- ❌ 不引入 jsdom（改根 devDeps）；真实 DOMPurify 链路**显式声明为缺口**，用注入 fake sanitize 覆盖判据。
- ❌ 不靠"重命名 `success`"冒充修复（真正的修复是 3.3 新增信号）。
