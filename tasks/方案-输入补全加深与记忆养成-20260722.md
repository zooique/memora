# 方案-输入补全加深与记忆养成

> **创建时间**：2026-07-22
> **状态**：方案评审期（待排雷确认后进入执行）
> **承接关系**：`方案-输入补全模块迭代优化.md` 已做完**浮窗表面**（resize / 拖拽 / 浮球单击 / 粘贴超时 / 文案）；本方案补齐其**未展开的深水区**——补全**召回深度** + 记忆**养成脊柱**。二者是同一模块的表里两层，不冲突。
> **战略来源**：大厂 PM 评估结论"收窄核心：记忆 + 补全成脊柱，暂停屏幕注入 / 精灵宠物实验"。

## 一、战略定位：为什么是这两条线

| 线 | 解决的不可约需求 | 在组合里的角色 |
|----|----------------|---------------|
| 输入补全（召回加深） | "在我打字的地方，自动召回我以前说过/想过的，不打断流" | **记忆系统的每日门面**（高频、低门槛，让记忆被用起来） |
| 记忆养成（长期对象） | "一个随时间越来越懂我的 AI" | **产品脊柱 / 对抗 ChatGPT 遗忘的唯一差异点** |

互补闭环：补全越准 → 用户越愿沉淀 → 记忆越厚 → 养成越真 → 补全越准。

> ⚠️ 前提声明：本方案建立在"用户会高频使用浮窗补全"的假设上。该假设**尚未被数据验证**（任务目录里没有激活率/采纳率漏斗）。排雷 R1 专门处理这个前提风险。

## 二、Epic 拆分

### Epic A · 补全召回加深（检索面，纯本地、免费、跨平台）

| ID | 任务 | 与现有方案关系 | 关键文件 |
|----|------|---------------|---------|
| **A1** | 冷启动 embedding 索引：新用户首次对话即建向量索引，消除"新用户召回率低" | 现有方案未覆盖（STEP-7 只动排序，不动索引） | `src/memory/vectorStore.ts`、`src/llm/embedding.ts`、`src/agent/` 初始化路径 |
| **A2** | 排序 / 多样性加权：近期会话权重 + 采纳反馈权重 + 多源多样性（扩展 STEP-7） | 扩展 STEP-7（原 P3） | `src/electron/renderer/quick-input/quickInputCompletion.ts` |
| **A3** | 上下文感知补全：基于聚焦应用名 / 时段过滤候选（扩展 STEP-10） | 扩展 STEP-10（原 P4） | 同上 + `src/electron/ipc/memoryHandlers.ts`（searchMemories） |
| **A4** | 采纳反哺闭环加固：跨设备 `boostMemory`（writeBoost）与本地 adoptedTexts 一致性对账 | 现有 L2 反馈回路的缺口 | `src/electron/renderer/helpers/completionMetrics.ts`、`src/electron/ipc/memoryHandlers.ts` |

### Epic B · 记忆养成脊柱（长期对象，产品灵魂）

| ID | 任务 | 关键文件 |
|----|------|---------|
| **B1** | 感知 / 默契度**行为耦合**：让 persona / 感知真的改变回复，而非只改数字（防 gimmick） | `src/electron/renderer/helpers/perceptionLabels.ts`、`narrativeGenerator.ts`、`src/agent/` 系统提示词注入 |
| **B2** | 纵向养成度量：召回命中率随时间曲线 + "你教过我 X" 可感知时刻数（先度量再宣称养成） | `completionMetrics.ts`、`startupSummaryBanner.ts`、新增 longitudinal 埋点 |
| **B3** | 便宜的自动治理：L1 去重 / L2 时效性改本地启发式，不每次烧 LLM token | `src/memory/`（DedupManager / MemoryAdvisor）、`src/agent/` 调度器 |
| **B4** | 记忆腐化可视 / 可控：用户可感知"记忆在变差"并手动干预（回收站已存在，需加健康度入口） | `src/electron/renderer/panels/memoryPanelManager.ts`、`src/agent/MemoryAdvisor` |

### Epic C · 明确不做（排雷的"绕过而非修补"结论）

| 不做事项 | 心智模型 | 原因 |
|----------|---------|------|
| 生成式补全（LLM 实时生成候选） | 方案复杂度匹配 | 检索式免费即时，生成式延迟 + token 爆炸，且与对话抢资源 |
| 自动粘贴追求 100% 应用覆盖 | 绕过而非修补 | nut-js Ctrl+V 跨应用 / CJK IME / macOS TCC 本质脆弱，保持 best-effort + 降级 |
| 投入修"全应用 UIA 智能定位" | 绕过而非修补 | 同现有方案 Q6 结论：覆盖率不可承诺，降级鼠标定位即可 |
| 屏幕注入 / 精灵宠物实验继续加宽 | 识别不可逆损失点 | 占用心智与 token，未验证需求；降级为实验，资源让给 A/B |

## 三、迭代路线（按 ROI 重排）

```
先证伪前提 ── R1（埋最小激活/采纳度量，1 周看数据）
   │
   ├─ 若前提成立 → 进入主线
   │     P0  A1 冷启动索引（根因，先做否则排序优化是空转）
   │     P0  B2 纵向度量（没有度量，"养成"就是自嗨）
   │     P1  A2 排序/多样性加权（依赖 A1 数据）
   │     P1  B3 便宜治理（L1-L2 本地启发式，止血 token 成本）
   │     P1  B1 感知行为耦合（要么真改行为要么砍）
   │     P2  A3 上下文感知补全
   │     P2  A4 采纳反哺对账
   │     P2  B4 记忆腐化可视
   │
   └─ 若前提不成立 → 回退到"记忆养成"主线（B 系列），补全降级为可选增强
```

> 优先级判据沿用现有方案：P0 = 阻塞主线 / 不可逆风险；P1 = 高 ROI 可控；P2 = 依赖 P1 或增强项。

## 四、排雷（核心交付）

> 逐条标注所用心智模型，格式：风险项 / 等级 / 分析 / 缓解 / 模型。

### R1 · 前提未被验证：用户真会高频用浮窗补全吗？ 🔴 高

| 项 | 内容 |
|----|------|
| 分析 | 整个"A 线"的 ROI 建立在"浮窗是高频触点"上。但任务目录无任何激活率 / 采纳率 / 周活数据；"11 个体验闭环全绿"是**工程闭环**不是**用户闭环**。 |
| 模型 | **怀疑前提** |
| 缓解 | 在动 A1/A2 前，先用 B2 的埋点 + 现有 `completionMetrics` 跑 1–2 周真实使用，拿到激活率 / Top-1 命中率 / 采纳率三数。**三数不达阈值（如周激活 < 某值）则回退路线**，不投入架构改动。这是**识别不可逆损失点**——在假前提上大改内核索引是沉没成本。 |

### R2 · 根因误判：先优化排序，后补索引 🔴 高

| 项 | 内容 |
|----|------|
| 分析 | 现有 STEP-7 只做"排序加权"，但召回差的**根因**是冷启动无向量索引（文档自承"新用户召回率低"）。在空/稀疏数据上优化排序 = 在错误层做功。 |
| 模型 | **向源头追溯** / **区分症状与根因** |
| 缓解 | A1（冷启动索引）必须排在 A2 之前。排序算法再巧，检索不到就是 0。排雷表同步到迭代路线：A1 为 P0 阻断项。 |

### R3 · 自动粘贴脆弱性被当成"待修 bug" 🟡 中

| 项 | 内容 |
|----|------|
| 分析 | `InputInjector` 用 nut-js 模拟 Ctrl+V；文档自承 CJK IME 的 Esc 步骤"从未实现"、macOS 跨平台"v2 才验证"。指望"修到全应用可用"是无限坑。 |
| 模型 | **绕过而非修补** |
| 缓解 | 自动粘贴保持 best-effort + 优雅降级（复制 + Toast），**不列入 P0/P1 修复目标**；补全的**价值主体放在召回列表**（纯检索、健壮、免费、跨平台），粘贴只是加分项。 |

### R4 · 生成式补全的隐性诱惑 🟡 中

| 项 | 内容 |
|----|------|
| 分析 | "加深补全"容易被解读为"让 AI 实时续写我下一句"。这会引入 LLM 调用：每次键入都烧 token + 300ms+ 延迟，且与主对话抢 Provider 配额。 |
| 模型 | **方案复杂度匹配** |
| 缓解 | 写入"不做清单"（Epic C）：补全恒为**检索式**（本地 searchMemories + searchSessionMessages）。这是相对 ChatGPT 类产品的隐蔽优势（免费即时），守住。 |

### R5 · 养成治理持续烧用户 token 🔴 高

| 项 | 内容 |
|----|------|
| 分析 | 内核 L1 去重 / L2 时效性 / L3 冲突检测每次都调 LLM（见 CHANGELOG 2.0.0）。若"养成"成为主线，治理频率上升 = 用户 token 成本线性上升，且无任何收入对冲。 |
| 模型 | **识别不可逆损失点**（持续性成本） |
| 缓解 | B3：L1/L2 改**本地启发式**（文本相似度 / 时间衰减规则），仅 L3 冲突检测保留 LLM（且"只检测不修复"）。治理成本趋零，养成才可持续。 |

### R6 · 默契度 / 感知变成 gimmick 🟡 中

| 项 | 内容 |
|----|------|
| 分析 | 若 `默契度 +0.1` 只改面板数字、不改变任何回复行为，用户两次就看穿，反而损害信任。 |
| 模型 | **区分症状与根因** |
| 缓解 | B1 必须交付"可观测的行为差异"（如不同默契度触发不同系统提示词片段 / 主动提示冷却公式已含 rapport）。**验收标准：切角色 / 默契度变化后，回复风格或主动提示频率可被测到差异**。否则 B1 判定失败并砍掉该层，不保留数字装饰。 |

### R7 · 架构耦合：加深补全会触碰内核记忆接口，撞上 API 不稳定期 🟡 中

| 项 | 内容 |
|----|------|
| 分析 | A 线需增强 `searchMemories` / 混合检索 / 索引构建，这些在内核侧（`src/memory/`）。但内核 1.0→2.0 一个月内两次 breaking（MemoryMutator 引入又合并），接口仍在找形态。宿主此时深度依赖内核 = 每次内核发版宿主易碎。 |
| 模型 | **识别不可逆损失点**（升级耦合成本） |
| 缓解 | ① 宿主锁内核版本范围（如 `memora@2.0.x`），勿跟 `^`；② A1/A3 尽量在**宿主侧**做（缓存索引 / 重排），少改内核契约；③ 若必须改内核，先在 `.workbuddy/memory` 或 ADR 记契约，加契约测试。 |

### R8 · 度量缺失导致"养成"自嗨 🔴 高

| 项 | 内容 |
|----|------|
| 分析 | B 线所有价值（养成、默契、主动提示）若无可量化指标，就会陷入"我觉得更懂你了"的主观叙事，无法判断是否真有用，也无法向任何人证明。 |
| 模型 | **怀疑前提** |
| 缓解 | B2 与 R1 同源：先埋**两个纵向指标**——① 召回命中率随时间曲线（验证"越养越准"）；② "你教过我 X" 可感知时刻数（startupSummaryBanner 已有雏形，扩展为计数）。指标上线后才允许宣称"养成"。 |
