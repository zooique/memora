### 提示词 B · 守卫模式审计（FEED-NEW-1 · P3 观察期）

> **触发时机**：下次重构涉及 emit 回调 / IPC 守卫时顺手检查
> **执行模式**：扫描 → 评估 → 必要时修复

```
你是一名资深程序员，对 memora-sprite 主进程进行 IPC 守卫模式审计。执行模式：扫描 → 评估 → 必要时修复。

【背景】
BUG-6 修复发现：剪贴板 emit 回调用 isFullWindowAccessible 守卫要求 isVisible，
浮动窗口模式下完整窗口隐藏导致 IPC 静默阻断，pendingItems 永久丢失（不可逆损失点）。
已修复剪贴板回调用 safeSendToWindow 替代，但其他 emit 回调可能存在类似过度防御。

【任务】
详见 f:\zooique\memora\tasks\待完成任务.md §3.3 FEED-NEW-1。

扫描范围：所有调用 isFullWindowAccessible 的位置（main.ts / agentListeners.ts / spriteEventBridge.ts）。
对每处调用评估：
1. 数据流方向：是单向推送（如剪贴板 IPC，丢失不可恢复）还是请求-响应（如查询单次结果，可重试）？
2. 守卫必要性：是避免抛异常（必要）还是避免"消息堆积"（过度防御）？
3. 不可逆损失点：如果阻断 IPC，用户数据会永久丢失吗？

【资深程序员心智模型】
- 识别不可逆损失点——单向数据流 + 会话级内存态 = 阻断即永久丢失。这种场景必须绕过守卫。
- 怀疑前提——"避免向隐藏窗口发送 IPC"听起来合理，但 Electron webContents.send 向隐藏窗口发送不抛异常。前提错了。
- 绕过而非修补——不要在守卫后加 pending 队列补偿，复杂度与问题本质不匹配。直接移除守卫。

【输出要求】
- 每处调用给出结论：保留 / 改用 safeSendToWindow / 其他方案 + 理由
- 实施项独立提交，运行全量测试
- 更新 tasks/待完成任务.md FEED-NEW-1 状态
```

### 提示词 C · CSS 动画冲突扫描（FEED-NEW-2 · P3 观察期）

> **触发时机**：下次新增 CSS animation 时顺手检查
> **执行模式**：grep 扫描 → 评估 → 必要时重构

```
你是一名资深前端工程师，对 memora-sprite CSS 进行 animation 与 transition 冲突扫描。执行模式：grep 扫描 → 评估 → 必要时重构。

【背景】
BUG-5 修复发现：.memory-item 基础规则声明 animation: memoryItemFadeIn ... both，
animation fill: both 会在 fade-in 结束后保留 to 状态（opacity: 1）。
.removing 类用 transition 实现 opacity: 0 + transform，被 fill 状态覆盖 →
transitionend 永不触发 → DOM 永不被 remove → 用户看到"删了还显示"。
已修复改用 animation + animationend，但其他位置可能存在类似冲突。

【任务】
详见 f:\zooique\memora\tasks\待完成任务.md §3.3 FEED-NEW-2。

扫描命令（PowerShell）：
- grep "animation:.*both" styles/  → 找出所有 fill: both 声明
- grep "transition:" styles/        → 找出所有 transition 声明
- 交叉比对：同一选择器是否同时有 animation: both + transition？

对每处冲突评估：
1. fill 状态保留的 to 值，是否会被后续 transition 目标值覆盖？
2. 如果是，transitionend 是否被依赖触发 DOM 操作？
3. 是否有 !important 补丁（反模式）？

【资深程序员心智模型】
- 识别不可靠机制——transition 与 animation fill 冲突是经典 CSS 陷阱，依赖 transitionend 触发业务逻辑不可靠。
- 绕过而非修补——不要用 !important 强制覆盖（补丁思维）。改用 animation + animationend（同属性后写胜出）。
- 方案复杂度匹配——animationend 比 transitionend 可靠性高，无需引入 JS 计时器补偿。

【输出要求】
- 输出扫描结果：每处冲突的文件:行号 + 评估结论
- 实施项独立提交，运行相关测试
- 更新 tasks/待完成任务.md FEED-NEW-2 状态
```

## 三、资深程序员心智模型应用速查

> 本轮问诊提炼的 6 条心智模型，对应到不同任务类型的典型应用场景。

| 心智模型 | 典型应用场景 | 反模式（避免） |
|---------|------------|--------------|
| **区分症状与根因** | bug 修复、性能问题 | 在症状上叠加防御代码（如 catch 后 fallback） |
| **识别不可逆损失点** | IPC 阻断、数据流设计 | 在已损坏数据上做恢复逻辑（应切断上游） |
| **怀疑前提** | 反复修补的机制、依赖偶然状态 | 修补能解决这一次，前提错了问题无限回归 |
| **向源头追溯** | 调用链优化、接口设计 | 在中间层加校验而非消除层级跨越 |
| **绕过而非修补** | 第三方库 bug、不可靠机制 | 在输出上叠加检测和 fallback（应用架构思维绕过） |
| **方案复杂度匹配** | 重构决策、新功能设计 | 用复杂方案绕过另一个复杂方案 |
