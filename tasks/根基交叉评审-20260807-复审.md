## 2. 本次交叉评审发现（按 P0/P1/P2 定级）

> 定级标准沿用首轮：P0=致命事实错误或硬约束冲突；P1=跨篇系统性冲突或明显不一致；P2=可澄清项/措辞问题。

### X1【版本引用漂移 · P1】A 篇与 E 篇的交叉引用版本号停留在上一轮

| 引用方 | 被引 | 引用版本 | 实际版本 |
|---|---|---|---|
| A 篇 header + §05 | B 道生万物 | v2.5 | **v2.6** |
| A 篇 header | C 输入管道 | v1.4 | **v1.5** |
| A 篇 header | D 不中断 | v1.4 | **v1.5** |
| E 篇 header | B/C/D | v2.5 / v1.4 / v1.4 | **v2.6 / v1.5 / v1.5** |
| E 篇 §06 表格 | B/C/D/A | v2.5 / v1.4 / v1.4 / v1.0 | **v2.6 / v1.5 / v1.5 / v1.1** |

C 篇 header 引 B 篇 v2.6、D 篇 header 不标版本号——说明 B/C/D 已做「叙事校准/提纯」升级，而 A/E 两篇的引用未同步跟进。
**对抗式根因**：文档互相引用**标注具体版本号**本身就是易腐信息——版本每轮演进，引用必然漂移，与 cross-document-reference.md「章节号/标题必须真实存在」的 P1 精神冲突。
**修法（推荐）**：交叉引用一律不标版本号（或标「最新版」）；版本只出现在各文档自身 meta 与版本沿革节。

### X2【persona 定位三处冲突 · P1】persona 是「每轮注入」还是「输入驱动匹配」？

| 出处 | 表述 | 立场 |
|---|---|---|
| E 篇 §02 机制族 E | 「rule/persona 等确定性契约 **100% 在场（注入）**」 | persona = 注入 |
| C 篇 §03 对抗式修正表 | 「persona / skill **输入驱动匹配**」 | persona = 匹配 |
| D 篇 §02 分级路径「不变」行 | 「契约（persona/rule）**每轮注入**」 | persona = 注入 |

**与 memora 现状对照**：`architecture_philosophy_rules.md §1.2` Persona 定位 = 「关键词 + LLM 辅助语义匹配，在 chat() 开头执行」→ **输入驱动匹配**。即 E 篇与 D 篇的表述与 memora 现状矛盾，C 篇才是现状的正确转述。
**对抗式分析**：三处不一致的根因是把「persona 内容稳定（设定记忆，可缓存）」与「persona 选择是输入驱动的（匹配后才注入）」混为一谈——rule 是无条件基线（每轮全量），persona 是有条件选择（匹配命中才注入）。E 篇机制族 E 与 D 篇 §02 把 persona 与 rule 并列，是**把匹配型设定误标为基线型契约**。
**修法**：E 篇机制族 E 与 D 篇 §02 改为「rule 等无条件契约 100% 在场；persona/skill 按输入驱动匹配后注入」；全体系统一 C 篇表述。

### X3【最小可落地版本的基础模型归属未声明 · P1】核心 7 项混用两个模型的组件

E 篇 §03 落地铁律：「最小可落地版本 = 核心 7 项……不做触发链、不做目标版本、不做意图分类也能跑通 ①-⑥ 全部体验」。但核心 7 项内部模型来源不一致：

| 核心项 | 组件来源 |
|---|---|
| ② 缺省补全链 P1→P3 | 一问一答模型基础（B/C 篇） |
| ④ 分级路径 | 一问一答模型基础（C 篇） |
| ⑤ 增量引用+增量事件 | 一问一答模型基础 + D 篇质变一 |
| ⑥ **状态机三态 + 检查点** | **不中断模型专属（D 篇 §04 新增维度）** |

C 篇 §01 明确「本文件按一问一答模型」，一问一答下不存在 RUNNING/PAUSED/ERROR 生命周期——核心 ⑥ 的「状态机三态」在一问一答模型里没有落点。
**对抗式结论**：E 篇没有声明「最小版本基于哪个模型」。若基于一问一答，⑥ 应删状态机（只留检查点）；若基于不中断，② 的 P1→P3 补全链与 P4 的关系需重排。**最小版本语义因此悬空**——这是「抽象收敛」一节最实质的逻辑漏洞。
**修法**：E 篇 §03 显式声明「最小版本基线模型 = 一问一答 + 会话持久化（检查点）」，状态机三态降为可选（同恢复协议），或明确核心 7 项跨模型混用是有意为之并给出理由。

### X4【检查点与恢复协议的核心/可选错位 · P1】「不做恢复协议也能跑通 ⑤ 恢复」不成立

- 核心 ⑥ = 「状态机三态 + 检查点」，说明「可见、可恢复」；
- 可选 = 「恢复协议（温记忆按需召回）——跨会话恢复需要」。

但 D 篇 §04 恢复协议共 5 步（快照反序列化 → 热窗载入 → 温召回 → 契约重注入 → 校验），且明确「**断点续跑 ≠ 仅反序列化快照**——热窗口是截断的，直接恢复会让 Agent 失忆」。检查点脱离恢复协议 = 死快照，无法支撑 E 篇 ⑤ 体验「关掉重开还能接着干」。
**对抗式结论**：核心 ⑥ 声称支撑 ⑤ 恢复，但恢复的真正载体（恢复协议）在可选栏——「最小版本跑通全部六体验」的声明被自己的组件划分推翻。**检查点与恢复协议必须同进核心或同退可选**。
**修法**：将「恢复协议」并入核心 ⑥（改名「检查点 + 恢复协议」），从可选 6 项移除；或把 ⑥ 拆为「状态机（可选）+ 检查点与恢复协议（核心）」。

### X5【P4 可选性同篇两处表述不一 · P2】

- E 篇 §01 表格 ④ 追问：「P4 暂停询问（终极补全）+ 滥用抑制」——未标可选；

### X6【B 篇三源融合表格漏「历史角色偏好」 · P2】

表格与正文在「记忆能否供给角色槽」上不一致。而「记忆覆盖四元组全集」是 B 篇的核心主张（复归于道的准确含义），表格漏列角色削弱了该主张的呈现。**修法**：P2 行补「历史角色偏好（角色）」。

### X7【tiebreaker / 热记忆截断的体验对应缺失 · P2】自违「无体验诉求的机制=过度设计」

E 篇 §01 检验标准：「没有对应体验诉求的机制，就是过度设计」；§02 对抗式检查也强调「无孤儿机制」。但可选 6 项中：
- **tiebreaker 同档仲裁**：§01 六场景表中无对应行；
- **热记忆窗口截断策略**：§01 六场景表中无对应行。
（触发链、目标版本、意图分类、恢复协议均有对应场景。）**修法**：在 §01 表格或 §02 中为二者补体验绑定（tiebreaker→③ 纠正的冲突仲裁 / ⑥ 信任的仲裁可见性；热记忆截断→② 继续的长会话防膨胀），或从可选清单中移除。

### X8【D 篇「无终止态」与「用户终止」措辞歧义 · P2】

- D 篇 §01：「开启后常驻，RUNNING/PAUSED/ERROR 三态（v1.3），**用户开启/终止**」；
- D 篇 §04 状态机行：「双向暂停（用户/Agent/系统）；**无终止态**，用户显式关闭」。
「无终止态」与「用户终止」并存，读者易误读为矛盾。实际语义：三态中无 TERMINATED，用户关闭=销毁会话而非状态迁移。**修法**：§01 改为「用户开启/关闭」，并加一句「关闭即销毁，非状态迁移」。

### X9【A 篇「只出文本」性质 vs 多模态 · P2】

A 篇 01 三性质之②「**只出文本**——只生成 token，不执行任何动作」；但 02 命题④判定「本质是 token 序列；**多模态时代不限于纯文本**」。三性质字面与多模态输出（图像/音频 token）表面冲突。**修法**：将②改述为「只出符号（token 序列，多模态时代含图像/音频 token）」，与命题④自洽。

### X10【机制族计数 13 vs 罗列 12 · P2】

E 篇 §03 标题「13 → 7 核心 + 6 可选」，但 §02 机制族 A-F 罗列：A(3)+B(2)+C(2)+D(2)+E(2)+F(1)=**12 项**。13 的来源不明（疑为状态机三态与检查点分列、或渲染器与上下文管理器分列）。**修法**：标注 13 的构成，或改标题为「12 → 7 核心 + 5 可选 + 原 6 可选重组」，保证计数可复核。

## 3. 设计层实质审查（超出交叉一致性，DeepSeek 工程视角）

### S1【四元组命名与「三生万物」的维度身份 · P2】

B 篇「四元组 = 角色 × 任务 × 标准 × 资源」，同时「三生万物 = 三坐标 × 资源（物质基底）」。资源具有**双重身份**：既是「二」的动静二分之一侧，又是四元组的第四元。B 篇三生万物·生成机制 ①已写「资源是物质」（基底而非第四坐标），借喻声明也解释了「二/三」，但**未显式说明四元组的「四」= 三坐标 + 资源基底**。读者易困惑「到底三生万物还是四生万物」。
**修法**：总览 SVG 或借喻声明处加一句「四元组 = 三元坐标 + 资源基底；资源是生成的物质条件，不是第四坐标——故称三生万物」。

### S2【「记忆覆盖四元组全集」与 memora 实现的载体 gap · P2（已声明，确认自洽）】

B 篇主张记忆覆盖角色/任务/标准/资源全集；但 memora 现状：persona（角色）是设定记忆不进 recall，目标/计划（任务要素）存会话状态/检查点（D 篇），recall 实际主要覆盖内容/洞察/画像（资源/知识侧）。B 篇已用「存储位置 vs 语义归类」声明化解（目标/计划存会话状态不改变任务语义）。**确认自洽**，但建议 B 篇在「记忆覆盖四元组全集」段补一句载体说明（角色→persona 文件、任务/标准→会话状态、资源/洞察→recall），避免读者误以为现实现已全覆盖。

### S3【P4 暂停询问与异步场景 · P3 观察（非缺陷）】

D 篇 P4 = Agent 主动暂停等待用户澄清。异步场景下用户可能不在场，暂停=空转。D 篇已具备化解机制（状态机支持三方暂停 + 检查点持久化 + 休眠常驻零算力），但未显式写「P4 询问必然伴随检查点持久化，用户回来后恢复」。建议 D 篇 §03 质变三补半句，闭环该链路。

### S4【A 篇「契约断裂」术语与 memora 错误体系 · P2】

A 篇 §04 用「契约断裂（JSON 不符合 schema）」描述 tool_call 解析失败，与 memora 项目 MemoraError 统一错误体系（project-rules §7.1「禁止空 catch/裸 throw」）无冲突（概念文档不落代码），但建议 A 篇注明「契约断裂 ≠ 系统错误：解析失败走降级/重试，不视为 LLM 故障」——与 architecture_philosophy_rules §7 降级优先呼应。
