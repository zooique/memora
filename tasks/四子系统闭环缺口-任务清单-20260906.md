## 二、任务清单

### T1 🔴 P0 — `writePlan('overwrite')` 实为 append（语义与注释背离）

> **✅ 已落地（2026-09-06）**：`sessionManager.ts` overwrite 分支先 `this.checkpoint.plan = []` 再逐条追加；L1105 注释改为三模式语义说明。防回归测试 2 例（真清空 + 空 plan 等价新建）。突变验证：禁用清空分支 → 新测试转红（实测 1 failed）。


- **证据**：`src/agent/managers/sessionManager.ts:1115-1118` —— `mode === 'overwrite' || mode === 'append'` 同一分支，只 `appendPlanStep`，无清空。L1134 注释仍写「overwrite 清空后全 pending」，L1105 注释已改口承认「按追加」——两处注释自相矛盾，且文档迁就实现。
- **影响**：
  1. LLM `task_table_write(mode='overwrite')`（toolExecutor.ts:866）无法重写计划，只能追加；返回文案谎报「已更新（overwrite）」（assembler.ts:357）。
  2. 会议预置依赖此语义（prepare.ts:80），当前被掩盖为「每轮叠加」（见 T2）。
- **修复方向（二选一，需先定再动）**：
  - **方案 A · 修语义**：`overwrite` 先清空 `this.checkpoint.plan` 再逐条 `appendPlanStep`（order 用 `plan.length` 自洽）。同步改 L1105/L1134 注释。
  - **方案 B · 收缩契约**：删除 `'overwrite'` 值，只留 `append | update`；同步改 toolExecutor 的 mode 枚举与 assembler:357 返回文案、prepare.ts:80 调用方。
- **联动**：无论 A/B，T2 的会议守卫都必须同批改——否则方案 A 会让「第二轮含小组会议」清空已推进会议重开。
- **验收（防回归）**：
  - 新增测试：`writePlan('overwrite', 3 步)` 于已有 5 步 plan → 结果恰 3 步且 status 全 pending、首个被 ensureActiveStep 激活。
  - 突变验证：删除清空分支 → 该测试转红。
- 涉及文件：`sessionManager.ts`、`assembler.ts`（文案）、`toolExecutor.ts`（若方案 B）、`prepare.ts`（配合 T2）。

### T2 🔴 P1 — 会议触发无收敛守卫（「重开 vs 续会」缺判据）

> **✅ 已落地（保守默认，2026-09-06）**：`prepare.ts` 加在途守卫——checkpoint.plan 存在 pending/active 步骤时跳过自动预置（= 续会语义，第二轮「继续小组会议」不再重开/叠加）；无在途计划时「小组会议」输入 = 新会议 → overwrite 预置。checkpoint 读取合并为一次。防回归测试 2 例（触发预置 + 在途拦截）。
> **✅ 决策点已定（2026-09-06 下午）**：**自动重开 = 伪需求，不提供**。重开经 LLM 显式通道（task_table_write overwrite，T1 真清空 + builtinTools.ts:456/465 描述已对齐）。自动预置只服务一次会议发起。


- **证据**：`src/agent/seed/prepare.ts:70-81` —— 每轮 prepare 都执行 `tryBuildMeetingPlan(input)`，命中即 `writePlan('overwrite', capped)`，无「已有在途会议」检查。
- **触发面**：`tryBuildMeetingPlan`（rolePackManager.ts:500-513）只判 `/小组会议/.test(input)` + 组长身份。第二轮输入含「小组会议」（如「继续小组会议讨论」「再开个小组会议」）即会重开/叠加。
- **缺口性质**：【实锤】行为存在；【推断】严重度取决于产品语义——"用户说小组会议 = 重开"是否可接受。需产品决策：
  - 决策点：**checkpoint.plan 已存在未完成步骤（尤其含 rolePack 会议步）时，新输入含「小组会议」是重开（overwrite）还是续会（append/无操作）？**
- **修复方向（决策后）**：把「会议是否在途」判据收进 checkpoint（如：plan 中存 active/pending 且含 rolePack 步骤 ⇒ 会议在途 ⇒ 幂等跳过重建）；触发动机保留纯确定性（字面匹配），防 LLM 自行续建任务表。
- **验收**：连续两轮「小组会议」输入 → plan 不翻倍、不丢已推进步骤（按决策语义断言）；会议在途时普通对话不触碰 plan。
- 涉及文件：`prepare.ts`、`rolePackManager.ts`（可加 `hasMeetingPlanInFlight` 纯函数供单测）。

### T3 🟡 P2 — 会议装配视角跨重启漂移（重启后不落组员视角）

> **✅ 已落地（2026-09-06）**：实证补充——续跑路径实际已有 `getTaskTable → applyActiveStepAssembly` 迭代内刷新（loop.ts:1053-1057），但 `buildChatOptions`（loop.ts:976）早于 getTaskTable → 首迭代存在 ≤1 次 LLM 调用的组长前缀窗口。`orchestrator.runResume` 开头补 `refreshAssemblyForRolePack`（复用 prepare 同一函数，非复制），与 prepare 对称消除窗口。


- **证据**：`rolePackManager.ts:316` `roundAssemblyRole` 为纯进程内字段，不入 checkpoint；续跑入口 `runResume`（orchestrator.ts:102-129）**不走 prepare**，不调用 `refreshAssemblyForRolePack`（prepare.ts:145-150）。跨重启后 `roundAssemblyRole = null` → `refreshRolePackPrefixForRound` 回落组长前缀（agent.ts:1370）。
- **影响**：会议在组员步骤暂停 → 进程重启 → 续跑：后半程以组长 persona 冒充组员发言，且不自愈（直到下一次新 chat 走 prepare）。
- **修复方向（自然生长，非复制）**：把「按 checkpoint active step 刷新装配视角」从 prepare.run 拆成独立最小动作，在 `runResume` 开头复用同一函数——与既有「runResume 不重装配上下文」定案的边界需评估（视角刷新 ≠ 记忆召回/上下文装配）。
- **验收**：组员步暂停 → 重建 Agent（模拟重启）→ resume → 断言 loop 前缀为组员 persona（经 buildSystemPrompt 注入断言）；质量门全绿。
- 涉及文件：`orchestrator.ts`、`prepare.ts`、`agent.ts`。

### T4 🟡 P2 — `resetToRunning()` 收口清 pendingPause（防未来调用点踩坑）

> **✅ 已落地（2026-09-06）**：`sessionStateMachine.resetToRunning()` 内部清 pendingPauseReason/pendingPauseSource；删除 `agent.ts:282` 超时事件补丁（已由 resetToRunning 覆盖，close 的 1699 翻 paused 逻辑保留）。防回归测试 2 例。突变验证：禁用清理两行 → 2 用例转红（实测）。


- **证据**：`sessionStateMachine.ts:123-128` 只清 pauseReason/pauseSource/errorCause，**不清 pendingPauseReason**。作者已知此坑并打补丁：`agent.ts:282`（超时事件）、`agent.ts:1699`（close）。
- **为什么仍要修**：补丁挂事件处理器 = 每条路径各自记得配对；未来新增 `resetToRunning()` 调用点（如新的清理语义）一旦忘记，`hasPendingPause()` 恒 true → `requestPause` 幂等检查永久拒绝（暂停按钮全失效）——「暂停超时清扫」注释（sessionStateMachine.ts:161-162）已预告此类调用会增加。
- **修复方向（收口而非补漏）**：清 pending 收进 `resetToRunning()` 内部；同步删除 `agent.ts:282` 的 cancelPendingPause 补丁；`agent.ts:1699` 只保留翻 paused 逻辑、去掉重复 cancel。
- **验收**：新增状态机测试「resetToRunning 后 requestPause 返回 true」；暂停全量测试（loop.test / uninterruptedWorkflow.test / sessionStateMachine.test）绿；突变验证：还原 resetToRunning 内清 pending → 新测试转红。
- 涉及文件：`sessionStateMachine.ts`、`agent.ts`。

### T5 🟡 P2 — 输入补充：降级路径违 TS-9 + 空补充在 round 层无痕

> **⏸ 已评估为伪需求（2026-09-06 下午，见 §五 判定表），不产生代码改动**：降级路径「内容不丢优先」是合理默认（触发需轮双缺失）；空补充无痕——暂停是过程态、round 是内容态，审计由 session 级 pauseMeta 承载。若未来出现「历史回放需展示暂停点」再做。


- **证据**：
  1. `messageHistory.ts:282-299` —— 交互输入对应轮缺失时（roundStore 与 pendingRounds 双缺失），降级为**新建 pending Round**，把补充输入写成 `userMessage` → 正是 TS-9 要防的「问答闭环分裂」。罕见但降级方向与定案相反。
  2. `orchestrator.ts:110` —— 仅 `input?.trim()` 非空才写 interactiveInputs；纯点继续（无补充文本）在 round 层无任何暂停痕迹（暂停事实只在 session 级 pauseMeta/checkpoint）。
- **修复方向**：① 降级分支改为：显式 warn + 不落分裂 Round（宁丢 interactive 归属也不伪造新轮起点），或落一条带 `interactive:true` 标记的孤儿记录供审计；② 空补充是否落 `kind:'resume'` 标记由产品决策（可观测性需求）。
- **验收**：模拟轮缺失 → 断言无新 Round 生成 + 日志含 warn；现有 uninterruptedWorkflow 全量绿。
- 涉及文件：`messageHistory.ts`、`orchestrator.ts`。
