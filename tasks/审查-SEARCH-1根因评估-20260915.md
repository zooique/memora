## 一、结论先行

台账原文把 SEARCH-1 记成「两条根因」，**实测是六条缺陷**，且其中两条台账完全未记（F3 / F4）。台账原记的两条里，**根因②的定位偏浅**（它不是一个 `return` 位置错，而是**接口形状缺陷**的必然结果）。

| 编号 | 缺陷 | 台账是否已记 | 定级 | 一句话 |
|---|---|---|---|---|
| **F1** | 多词 query **必然零命中** | ✅ 根因① · 定位准确 | **P0** | `escapeRegExp` 把整串当字面量 → 连 `核心\|愿景` 这条唯一逃生通道也被封死 |

**实测（复刻真实算法，非推断）**：

→ 属 `MEMORY.md §五·2`「行为性注释须与实现同批更新」类别。`src/project-search/types.ts:40` 写「内容查询词（宿主按需转为正则）」含糊逃过。

### F2 · 零命中的截断信息无处承载（形状缺陷）

台账原文：「`toolExecutor.ts:981-983` 在算 `truncated` **之前**就 return」。**行号已漂移**（实测为 `:1000-1001`），更重要的是**这个描述把形状缺陷讲成了位置缺陷**：

```
src/project-search/types.ts:22-23      truncated?: boolean;   ← 挂在 ProjectTextMatch（逐条命中）上
src/agent/toolExecutor.ts:1000-1001    if (textMatches.length === 0) return `（未在项目中找到…）`;   ← 早退
src/agent/toolExecutor.ts:1007         const truncated = textMatches.length >= maxResults
                                                     || textMatches.some((m) => m.truncated);      ← 空数组恒 false
```

- `searchText` 的返回类型是 `ProjectTextMatch[]`。**空数组无法携带任何元信息。**
- 因此 `:1001` 的早退**必然**发生、`:1007` 的判据在空数组上**必然**为 false —— 这两处不是两个独立 bug，是**同一个形状缺陷的两处症状**。
- 宿主侧同理：`hosts/.../projectSearchProvider.ts:94`
  ```ts
  return matches.map((m) => ({ ...m, truncated: counter.truncated }));
  ```
  `counter.truncated` 明明在手，却只能**逐条复制到命中项上**；命中 0 条时它随数组一起消失。

→ **修 F2 必须改返回形状**，改 return 位置只是治症状。

### F4 · >64KB 文件整文件静默跳过，且守卫位置与理由矛盾

**代码位置**：`hosts/.../projectSearchProvider.ts:159-164`

## 四、修法与决策点

### D1（必须先拍）· 多词语义：OR 还是 AND

| 选项 | 语义 | 本项目现有对照 | 评估 |
|---|---|---|---|
| **A · OR**（任一命中即返回） | 召回优先 | 无 | **建议**。下游是 `read_file` 精判 → 少召回 = 直接假阴性（F1 本体），多召回 = 多一次读取。且 **AND 结果集 ⊆ OR 结果集**，OR 永不比 AND 更差；上限由 `maxResults`/`MAX_MATCHES_PER_FILE` 兜住 |
| B · AND（全词命中） | 精度优先 | `search_memories mode="near"` = `keywords.every(...)`（`builtinToolHandlers.ts:1007-1017`） | 不选：只命中一个词的文件被丢弃 → **又是一个假阴性**。且用户原始场景「搜不到文档里明明存在的词」正是被全含语义放大的 |

**无论选哪个，工具描述必须显式声明语义与上限**（`builtinTools.ts:352` 现在只给单关键词例 `"TODO"`，零声明）。「记忆 near=AND / 项目 content=OR」不是缺陷，但**必须在描述里写明**，否则下一次审查会把它当不对称缺陷重提。

### D2 · 接口形状（**必须一次改完**）

```ts
// src/project-search/types.ts —— 返回对象化
export interface ProjectTextSearchResult {
  matches: ProjectTextMatch[];
  /** 扫描是否被截断（结果上限 或 文件扫描上限）→ 零命中/少命中 不代表"不存在" */
  truncated: boolean;
  /** 截断主因（供内核分叉文案，修 F5） */
  truncatedBy?: 'results' | 'files';
  /** 因超大文件（>64KB）被跳过的数量（修 F4-lite） */
  oversizedSkipped?: number;
  /** 搜索自身失败（超时/异常）而非"真零命中"（修 F3） */
  failed?: boolean;
}

// 选项增加词表（修 F1）；tokenize 的 SSOT 在内核，宿主只负责逐词转义后 OR
export interface ProjectTextSearchOptions extends ProjectFileSearchOptions {
  pattern: string;
  terms?: string[];
}

interface IProjectSearchProvider {
  searchFiles(options?: ProjectFileSearchOptions): Promise<ProjectFileMatch[]>;
  searchText(options: ProjectTextSearchOptions): Promise<ProjectTextSearchResult>;  // ← 形状变更
}
```

**「必须一次改完」的理由（成本窗）**：`IProjectSearchProvider` 是 `src/index.ts:171-177` 的**公开导出**，而 v3.0.0 **尚未发 npm**。
→ 现在改 = 破坏性变更**零外部成本**；发版后改 = semver 破坏 + 宿主迁移 + 双形状并存期。
→ 故 F1（`terms`）与 F2/F3/F5（返回对象）**应合并为同一次接口变更**，否则要付**两次**破坏性变更。

> ⚠️ 不要用「可变 options 回写」（`provider` 往 `options.truncated` 上写）替代返回形状。`walkText` 内部确实用可变 `counter` 传递计数，但那只在**单个实现内部**；把它提升为**跨宿主接口语义** = 未来宿主静默忽略 → 正是 F2 这一类静默假阴性。返回形状是自明的，忽略不了。

### D3 · 大文件（两档，建议分步）

| 档位 | 内容 | 风险 | 收益 |
|---|---|---|---|
| **F4-lite** | 只报数（`oversizedSkipped`），IO 不动 | 极低 | 消除「静默」；LLM 知道还有未搜的文件 |
| **F4-full** | 把 size 预检挪到 `readFile` **之前**（`stat` 已在 `:216` 拿到）+ 部分读（`fs.open` + `read` 前 64KB） | 中（IO 路径） | **真正**达成 `:33` 宣称的内存保护 + 大文件可搜（对齐 `:174` 声明的意图）。须处理 UTF-8 字节切分边界（按 `lastIndexOf('\n')` 收口，避免 `\uFFFD` 进 preview） |

建议：**F4-lite 随接口批**；**F4-full 单独一步**（唯一动 IO 的改动，风险最高）。

### D4 · `MAX_FILES_SCANNED=500` 应进内核 SSOT —— ⚠️ **2026-09-15 拍板时已推翻**

`:31` 的 `500` 现在**只在宿主**。一旦 F5 的文案要说出「已扫描 500 个文件」，这个数字就成为**LLM 可见的工具契约**，与 `PROJECT_SEARCH_RESULT_MAX_LEN`（已由 `src/index.ts:187` 导出、注释明写「宿主 import 对齐，避免数值漂移」）**同性质**。
→ 按既有裁决，应提升为内核导出常量。同源论据：`docs/大文本统一通道-探索方案.md:472` 已对 offload 阈值 `20_000` 下过同样的判断（「一旦成为承重旋钮，必须与预算 SSOT 同家」）。

> **❌ 上述建议不成立（对抗式审查推翻，详见 [`方案-SEARCH-1修复-20260915.md §四·D4`](./方案-SEARCH-1修复-20260915.md)）**：二者**性质不同** —— `PROJECT_SEARCH_RESULT_MAX_LEN` 由**内核亲自 clamp**（`toolExecutor.ts:966`），而 `MAX_FILES_SCANNED` 内核**从不 enforce**（内核不扫描）。把它提升为内核常量 = 让内核持有无权决定的宿主实现细节 = **跨层镜像**（带伤模式「双轨镜像」）。
> **改为**：宿主以**结果对象数据**上报 `truncatedBy` + `scannedFiles`，内核文案用上报数字，**本次不新增任何内核常量**。派生判定律：**宿主内部预算量不得提升为内核常量；只能以数据上报。内核只持有它自己要 clamp/enforce 的量。**

### D5 · F6 是否随批

`MAX_MATCHES_PER_FILE` 也是 LLM 可见上限，同属诚实化缺口。**建议随批**（返回对象再加一个 `perFileCapped?: boolean`，零额外形状成本）。

## 五、建议落地顺序（每步可独立提交 / 可独立回退）

| 步 | 内容 | 覆盖缺陷 | 触面 | 破坏性 |

## 六、可判定验收（替代「搜得更准了」这类软标准）

1. **F1**：`核心|愿景`、`核心 愿景`、`核心/愿景` 三种写法在含两词的样本上**命中条数相同且 > 0**；单关键词用例不回归。
2. **F2/F5**：零命中 **且** 扫描达上限时，返回值与文案**必须**同时满足「未找到」+「扫描已截断」，两者**不可分离**（缺一即红）。→ 这条现在**结构上不可测**（T1），先改 mock 形状再补。
3. **F3**：provider 抛错/超时 → 文案**不得**出现「未在项目中找到」（可断言不含该子串）。
4. **F4**：造一个 >64KB 且仅在后半段含唯一 token 的文件 → `oversizedSkipped ≥ 1` 且文案携带；S2 后该 token **可被命中**。
5. **反向守卫**（防「因错误的原因通过」）：把某个已量产的行为改坏（如令 `truncated` 恒 `false`）→ 对应用例**必须红**；`truncated` 恒 `true` → 「真零命中=可信」用例也必须红（防把「永远喊截断」当成诚实）。
6. **质量门**：`tsc --noEmit` EXIT=0 + `eslint --max-warnings 0`（须显式加）+ 内核全量 / 宿主全量（宿主带 `--no-file-parallelism`）；改动前先测基线并与当时 `cwd` 是否有 `.memora/config.json` 一并记录。

## 七、边界（不在本项内 · 防范围蠕变）
