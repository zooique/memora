## 1. 会话状态机（SessionStateMachine + SessionManager）

**评分：SSOT 4 / 闭环 3 / 未来 3 / 风险 中**

### 先回答提问

- **谁是状态真理源？** 状态机 `currentStatus` 是，`SessionCheckpoint.status` 是投影。
  这一点代码里写死且注释明确（`sessionManager.ts:357` `status: this.stateMachine.status` +
  `:356` 注释「状态真理源是状态机，检查点只是其投影」）。判定：**定义正确**。
- **不一致时谁优先？** 恢复路径已强制以状态机归零为准（`sessionManager.ts:619` `resetToRunning()`
  + `:631` 反向把 `checkpoint.status` 跟随实际结果），T8 修复到位。
- **`consecutivePause` 闭环是否完整？** —— **是完整的，比提问假设的更严密**。
  重置点 `agent.ts:927` 位于 compose **通过之后**：若 clarify 回答仍触发 P4，
  代码在 `agent.ts:878` 先做 `isPauseLimitReached()` 拦截并降级 P3，根本走不到重置。
  用户不回答时：计数不清零，靠 `CONSECUTIVE_PAUSE_DECAY_MS = 1h` 衰减自愈
  （`sessionManager.ts:809-819`）。**此项无需修改**。
- **超时"生产→消费"是否有遗漏路径？** 提问基于旧版。`consumePauseTimedOutSession()` 已废弃，
  改为广播事件 `markSessionTimedOut()`（`sessionManager.ts:1412`），启动路径与运行时定时器
  共用唯一入口，Agent 侧监听器还顺带清理了 `_pendingPauseReason`（`agent.ts:294`）。**此项已闭环**。

### 核心发现

**F1-1（中）：`lastHeartbeat` 一字段承载两个方向相反的语义。**
`touchCheckpoint()` 把它当"检查点最后修改时间"刷新（`sessionManager.ts:395`，且是**唯一心跳写点**，
被 13 处调用）；`isPauseTimedOut()` 把它当"暂停活性起点"判超时（`:1518`）。
二者方向相反：检查点越被写，暂停越不会超时。当前生产路径侥幸安全——
`heartbeat()` 唯一调用点在 `agent.ts:1702/1706`，而该处必然已被 `autoResumeIfPaused` 翻回 RUNNING。
但这是**耦合出来的安全，不是设计出来的安全**：任何人在 paused 态新增一次 `updateXxx()`
（这些方法本身没有状态守卫，`:977/988/1001/1014` 全部无条件写），24h 暂停超时即被无限推迟。

**F1-2（中）：`handleSessionEvent` 的 command 分支是"字符串匹配驱动状态翻转"的死契约。**
`agent.ts:1688-1694`：`detail.includes('pause') || detail.includes('暂停')` → 立即 `sm.pause()`；
`includes('继续')` → 立即 `sm.resume()`。两个问题叠加：
1. 它**同步翻状态机**，与 v2.1 确立的"内核事实驱动延迟翻转"（`requestPause` → loop 边界 → paused chunk → 翻状态机）
   构成同一语义的**两套实现**——SSOT 违背；
2. `resume()` 只翻状态机**不驱动续跑**（续跑在 `resumeExecution`），一旦触发即产生
   "状态机说在跑、loop 一动不动"的**假运行态**。

对抗式核实：`grep "type: 'command'"` 全仓（含 hosts）**零构造点**，只有 `types.ts:399` 的类型定义。
即该分支当前**不可达**——所以它今天不是 bug，是一颗上了膛的枪。双通道模型宣称的
"command 事件不触发自动恢复"（`agent.ts:1371`）同样是**无消费者的纸面契约**。

**F1-3（低）：`SessionStateMachine.onEvent()` 是空壳 + 零调用。**
`sessionStateMachine.ts:241-250` 实现为恒等转换（`from === to`，理由写在注释里），
`grep "\.onEvent("` 全仓零调用点。类型上它是"事件驱动转换接口"，实际是装饰。

### 优化建议

1. **拆分 `lastHeartbeat` 为两个字段**：`updatedAt`（检查点修改时间，touch 写）与
   `pausedAt`（暂停起点，只在 pause 时写一次、resume 时清）。`isPauseTimedOut` 改读 `pausedAt`。
   一个字段一个语义，是 SSOT 在字段粒度的表达。
   （`pauseMeta.pausedAt` 已存在于 `:1926`，可直接复用，成本极低。）
2. **删除 `handleSessionEvent` 的 command 分支**，或收窄为结构化指令
   （`event.delta.command: 'pause' | 'resume'`）并让 resume 路径**必须**经 `resumeExecution`。
   在没有生产消费者的今天删除，成本为零；等有人构造 command 事件那天，成本是一次线上事故。
3. `onEvent()` 二选一：兑现（把 pause/resume 的判定收进状态机）或删除。维持现状是最差项。

### 未来演进

三态机对**单会话**是足够的，但对多 Agent 协作是不够的——它缺少 `WAITING`（等待另一 Agent 交付）
与 `DELEGATED` 态。更关键的是：状态机是**进程内实例**（`sessionManager.ts:132` `new SessionStateMachine`），
一旦走向多进程/多 Agent，状态真理源必须外移到共享存储 + CAS，届时"谁是真理源"要重新回答一次。
建议现在就把状态翻转收口成**唯一的 `transition(action)` 入口**（当前有 pause/resume/triggerError/
recover/resetToRunning 五个公开写口），为将来换成分布式实现留一个替换点。

## 2. 检查点模型（SessionCheckpoint）

**评分：SSOT 4 / 闭环 2 / 未来 2 / 风险 高**

这是本轮**最需要动手**的子系统。写入侧（合并语义、脏标记、落盘收口）质量很高，
读取侧与补偿侧存在两处硬断裂。

### 核心发现

**F2-1（高·首要）：反序列化"降级"是假的——注释撒谎，且同一缺陷有两种崩法。**
`validateCheckpointIntegrity()` 的日志文案写着「以默认值填充后继续」（`sessionManager.ts:555`），
但实现从头到尾**只 push 字段名 + warn，没有任何一行填充**（`:513-561`）。
更致命的是它返回 `boolean`，而**两处调用点全部丢弃返回值**（`:448`、`:588`）。
后果分岔成两条都不可接受的路径：

| 入口 | 行为 | 后果 |
|---|---|---|
| `loadPersistedCheckpoint` | 外层 try/catch 吞掉（`:493`） | 整个会话**静默消失**，用户重启后工作全没 |
| `restoreFromCheckpoint` | 无 try/catch，`:595` 直接 `checkpoint.hotMemory.map(...)` | 字段缺失即 **TypeError 抛出**，宿主 IPC 崩溃 |

一个缺字段的检查点，一条路静默丢数据、一条路崩进程，**没有一条是"降级但可用"**。
这正是 stateful agent 最不该出错的地方：检查点是断点续跑的唯一凭据。

**F2-2（高）：P3.4 补偿机制的"防重复"标记是空转的，且不落盘。**
`compensateTool()` 注释写「标记补偿已执行（ok = false），避免重复补偿」并执行 `record.ok = false`（`:1360`）。
但唯一的筛选器 `getNonIdempotentExecutions()` 的过滤条件是
`r.idempotent === 'non-idempotent'`（`:1287-1289`）——**根本不读 `ok`**。
双重断裂：`record.ok = false` 之后**没有 `touchCheckpoint()`**，连脏标记都没置位，
即使将来有人补上 ok 过滤，重启后标记也不存在。

实际后果：同一检查点每次 `restoreFromCheckpoint` 都会重跑全部补偿，
并向上下文注入一条 `[P3.4补偿通知]` system message（`:680`）。
该消息进入 loop.messages → 下次 `extractHotMemory()` 收进 hotMemory（`:1537` 只过滤 `system` 角色，
但 `injectSystemMessage` 的注入形态需另行确认）→ 反复恢复会滚雪球。

**F2-3（中）：`completeRound` 绕过它自己声明的"唯一写点"。**
`updatePlanStepStatus()` 的文档写着「plan 步骤状态的**唯一写点**」（`:1047-1049`），
而同一文件 `:1091` 的 `completeRound` 里赫然是 `step.status = 'done';` 直改。
今天无害（后面跟了 touch + flush），但"唯一写点"一旦不真，后续在该方法里加的任何东西
（状态转换校验、事件发射、UI 通知）都会被这条路径静默绕过。这是 T3 收口做了一半。

**F2-4（中）：`goalVersion`（实为 `goalChangeSeq`）是 write-only 字段。**
提问「谁负责校验版本一致性？校验失败如何降级？」——实测答案是：**没有人，也没有降级**。
`grep goalChangeSeq` 全仓（排除测试/dist）：写入 `:369/:934`、随事件广播 `:941/:954`、
类型定义 `types.ts:475`、完整性必需字段清单 `:521`。**零读取比较点**。
真正的漂移检测由 `GoalConsistencyChecker` 用文本相似度完成（`:931`），与序号毫无关系。
即：一个被列入"必需字段"、参与序列化、却无任何消费者的字段。

### 正面确认（勿回改）

- `createCheckpoint` 的**展开合并**语义（`:351-352`）正确，且注释里写清了历史事故。
  这是本仓最好的一段防御性注释。
- `plan` ↔ `roundLog` 关系设计正确：`roundLog` 单向引 `stepId`（`agent.ts:1935`），
  plan 是任务状态真理源，roundLog 是时间轴投影，**不做双向同步**。
  提问「plan 更新时 roundLog 是否需要同步更新」的答案是**不需要**，双写才是错的。
- 落盘策略（工具执行只标脏、回合边界统一 flush）权衡合理，且注释交代了最坏情况。

### 优化建议

1. **收口反序列化为单一 `parseCheckpoint(json): SessionCheckpoint | null`**：
   在同一处完成 JSON.parse → 字段补齐（`hotMemory ??= []`、`plan ??= []`、`role ??= {name:'assistant'}` …）
   → 完整性告警 → 返回。让 `loadPersistedCheckpoint` 与 `restoreFromCheckpoint` 共用它。
   这一步同时消灭 F2-1 的两种崩法，并把"降级但可用"从注释变成代码。
2. **补偿闭环二选一**（禁止维持现状）：
   - 兑现：给 `ToolExecutionRecord` 加 `compensatedAt?: number`，`getNonIdempotentExecutions()`
     过滤 `!r.compensatedAt`，`compensateTool` 写标记后 `touchCheckpoint()`；
   - 或收窄：删掉 `record.ok = false` 与"避免重复补偿"的注释，明确声明补偿是幂等告警。
   建议选前者——非幂等工具的重复补偿在接入 MCP 后会变成真实的重复副作用。
3. `completeRound` 内改调 `this.updatePlanStepStatus(stepId, 'done')`，兑现唯一写点。
4. `goalChangeSeq` 二选一：兑现（恢复时比对检查点序号与运行时序号，不等则强制重新对齐目标）
   或删除。**倾向兑现**——多 Agent 场景下它就是天然的乐观锁字段。

### 未来演进

检查点当前是「SQLite 单 TEXT 列 + 全量 JSON 覆盖 + 无 `schemaVersion` + 无 CAS」
（`sessionManager.ts:419-420`）。三个可预见的击穿点：
- **长上下文**：hotMemory 已有 FIFO + 内容截断兜底，但 128k/1M 窗口时代整个 JSON 会到 MB 级，
  每个回合边界全量覆盖写一次，IO 会成为瓶颈 → 需要拆分冷热字段分表；
- **多 Agent 并发写**：全量覆盖 + 无版本号 = 后写者静默吞掉前写者；
- **跨版本升级**：没有 `schemaVersion`，F2-1 的字段缺失场景**必然**在下一次字段重命名时爆发。

**建议现在就加 `schemaVersion: 1`**——一行成本，是上述三项的公共前提。

## 3. 记忆分类与存储（Everything is Memory v2）

**评分：SSOT 4 / 闭环 3 / 未来 3 / 风险 高**

### 先回答提问

**Rule 的文件 + SQLite 是 SSOT 还是 dual-source 反模式？——是合法的派生索引，不是反模式。**
判据（"删掉从库能否无损重建"）成立：内容可从文件重建（`loader.ts:63-100`），
契约也已文档化（`configManager.ts:17-23` 明确「绕过文件层直接调用本类写 API 的写操作不持久」）。
而且第二轮遗留的"存在性不可重建"缺口**已修复**——`projectManager.ts:290-325` 新增了
`evictOrphanRules()` 启动对账。判定：**架构层面 SSOT 成立**。

**但对账的判据是错的，这是本子系统的头号风险。**

### 核心发现

**F3-1（高）：孤儿对账用"本次加载成功"代理"文件存在"，会误删用户规则。**
`evictOrphanRules` 的存活集是 `loadedIds`（`projectManager.ts:315-317`），
而 `loader.ts` 有两条路径让**文件明明在磁盘上却不进 `loadedIds`**：
- `:76-79` 空壳模板判定 → `skipped++`；
- `:89-95` 读取抛异常（EACCES、文件被占用、瞬时 IO 错误）→ `skipped++`。

后果：一次瞬时读失败 = 该规则被软删出索引 = 下次启动起不再注入 system prompt。
用户视角是"我的规则文件还在，但 Agent 不认了"，且**没有任何面向用户的提示**（只有一行 info 日志）。
正确判据应是"文件系统里是否存在该文件"，而不是"本次是否读成功"。

**F3-2（中）：降级出口 `onBootstrapSyncFailed` 零注册。**
`configManager.ts:114-122` 的 catch 已经很规范（warn + 回调），
但 `setOnBootstrapSyncFailed`（`:103`）**全仓零调用点**。
即：bootstrap 段刷新失败时，system prompt 与索引静默分叉，无人知晓。
可选接口 + 零消费者 = 又一处"契约未兑现"。

**F3-3（中）：`autoConfigRefiner` 的路径比想象中干净，但输入校验薄弱。**
提问担心的"血肉结晶为骨骼未经校验"——实测 `autoConfigRefiner.ts` **不写任何文件**，
唯一出口是建议回调（`:121`），落盘发生在用户确认后的 `ConfigManager.confirmConfigSuggestion`
（`:216` 写文件 → `:234` upsert → `:246` refresh，顺序正确）。**人在回路是存在的**。
残留缺口是 LLM 输出校验只检查字段存在性（`:195-198`），无长度/格式约束，
而 `name` 会直落文件名（`store.ts:118`），`sourceToDir` 只校验 source 不校验 name。
另：`confirmConfigSuggestion` 的 upsert 缺 `restore`（对比 `updateRule` 的 `:431-433` 有），
重建同名已删规则时会「文件已落盘 + 索引抛错」分叉（下次重启自愈）。

**F3-4（中）：侧车与主数据的因果一致性靠"逐点补齐"维持，仍有两处悬空。**
`removeRelationsByMemoryId` 已在 6 处删除路径接线（memoryInspector 3 处、configManager 2 处、
projectManager closeProject、userProfile 2 处），覆盖面不错。残留：
- `projectManager.ts:321` 对账软删**未清关系边**（与同文件 `:401` 的 closeProject 不对称）；
- `memoryInspector.ts:731-737` 清边失败仅 warn，随后 `:743` 照常物理删记忆 → 确定性孤儿边；
- 读取端不校验两端存活（`memoryInspector.ts:565-569` 以 `(unknown)` 渲染给 UI）。

**F3-5（中）：向量索引是 fire-and-forget 旁路，且自动清理完全不碰它。**
双写不在同一事务（`memoryController.ts:523` `.catch()` 降级），
物理删除时删向量但失败只 warn（`:350-358`），
而定时回收站清理 `writePurgeExpired`（`spriteLifecycleManager.ts:247` → `memoryInspector.ts:711-744`）
**全程无 vectorStore 引用** → 30 天自动清理产生的孤儿向量永久累积，且会被召回命中。

**Persona/Skill 缓存**：无 mtime、无内核 watcher，靠全量 reload 覆盖（`configResourceManager.ts:94`）。
宿主只给 persona 加了 watcher（`personaWatcher.ts:81`），**skill 目录无 watcher**——
外部改 skill 文件后须显式 reload 或重启。属已知不对称。

### 优化建议

1. **改对账判据（P0）**：`loadAllToIndex` 增加 `seenIds`（**凡扫描到文件即计入**，
   与是否加载成功无关），对账用 `seenIds` 而非 `loadedIds`。
   同时在 `evictOrphanRules` 内一并调 `removeRelationsByMemoryId`，与 closeProject 对称。
2. `onBootstrapSyncFailed` 兑现或删除。兑现的最小形态：Agent 侧注册后发一个
   `bootstrapDesynced` 事件，宿主弹一次降级提示。
3. `confirmConfigSuggestion` 补 `restore`，与 `updateRule` 对齐（一行）。
4. `FileStore` 的 `name` 增加白名单校验（`/^[\w\u4e00-\u9fa5-]{1,64}$/`），
   堵住 LLM 生成名直落文件路径的穿越面。
5. 向量清理接入 `writePurgeExpired`，或改为定期 `reconcileVectors()` 对账（后者更符合派生索引语义）。

### 未来演进

"设定记忆（文件真理源）/ 对话记忆（SQLite 索引）"这条双轨分野是**正确的第一性划分**，
在 MCP 标准化后还能直接对应到 "resources（可寻址、可版本化）vs memory（可召回、可衰减）"。
真正需要提前想的是 **Agent 自我进化的闭环安全**：
`autoConfigRefiner` 今天有人在回路，明天一旦为了自动化把确认环节去掉，
F3-3 的 name 校验缺口 + 无内容审计就会变成"Agent 能改写自己的规则文件且无人复核"。
建议在去掉人工确认**之前**先建立：设定文件写入审计日志 + 版本快照 + 一键回滚。
骨骼可以由血肉生长，但必须留下年轮。

## 4. 不中断工作模型的设计闭环

**评分：SSOT 3 / 闭环 3 / 未来 3 / 风险 中**

### 先回答提问

**双通道会不会 resume/pause 振荡？——实测有双层防护，不会失控。**
① `isPauseLimitReached()` 在 pause **之前**拦截并过滤高风险问题降级 P3（`agent.ts:878-889`）；
② chat 事件的任务槽走确定性规则、**永不触发 P4**（`composer.ts:79-83`）。
所以"PAUSED 态被大量 chat 事件打成振荡"这条路是堵死的。**此项设计成立**。

**`consumeExecutionStream` 收口**（`agent.ts:1091`）质量很高：三路径共用、
幂等锁清理放 `finally`、注释交代了历史漂移事故。**这是本仓最佳实践的样板**。

### 核心发现

**F4-1（中·最可能被用户遇到）：空闲态申请暂停 → 暂停按钮永久失效。**
同一事实有两份副本：Agent 侧 `_pendingPauseReason`（`:1395`）与 loop 侧 `pauseRequested`（`loop.ts:176`）。
**清理路径不对称**：
- loop 侧在**每轮用户输入开头**无条件清零（`loop.ts:291`）；
- Agent 侧只在 `consumeExecutionStream` 的 `finally` 清零（`:1121`）——**前提是当时有流在跑**。

可达路径实测存在：`canContinueWithoutInput()` 在 `hasPendingPlan` 为真时返回 true（`:1546-1548`），
即**没有流在跑的空闲态，UI 也会显示暂停按钮**。用户点击 → `requestPause` 置位 →
无消费者 → `_pendingPauseReason` 永久残留 → 后续所有 `requestPause` 被幂等检查静默拒绝（`:1426-1428`）。
兜底路径也不通：`checkPauseTimeout` 首行 `checkpoint.status !== 'paused'` 即 return（`:1466`），
而此刻状态机还是 running，**超时清理永远不会触发**。
只能靠用户主动点"取消暂停"或重启进程。

**F4-2（中）：`canContinueWithoutInput` 漏 ERROR 态，且 `resumeExecution` 静默 return。**
提问「三条件够不够」——三条件本身经 T4 修复后与 `isPlanStalled` 判据已对齐（blocked 不算可续），
**漏的是 ERROR 态**：error 状态下 `hasPendingPlan` 仍可为真 → 返回 true → UI 展示"继续" →
用户点击 → `resumeExecution` 首行 `if (status !== 'paused') return;`（`:1006`）→
**连一个 chunk 都不 yield，静默无反应**。
对比同方法内 resume 失败时的处理（`:1010-1017` 有 emit + error chunk），
首行短路是唯一一条不给用户任何反馈的出口。

**F4-3（中）：`setPauseMeta` 的调用顺序与其注释相反，且无检查点时静默丢弃。**
实际顺序：`loop.ts:585` `onPaused?.()` → `agent.ts:1922` `setPauseMeta(...)` →
`loop.ts:586` `yield {type:'paused'}` → `agent.ts:1102` `this.pause(...)` → `createCheckpoint()`。
即 **setPauseMeta 发生在 pause 之前**，而 `sessionManager.ts:1127` 的注释白纸黑字写着
「本方法由 loop.onPaused 在 pause() 之后回调」。
后果：`setPauseMeta` 首行 `if (!this.checkpoint) return;`（`:1124`）——
**首轮会话尚无检查点时，pauseMeta 静默丢弃**，宿主只能回落兜底文案。
今天生产不炸，是因为宿主在 chat 前先建了检查点（`chatHandlers.ts:138`）——
又一处「内核契约靠宿主兜底」的隐性耦合。

**F4-4（低）：用户主动暂停会消耗 P4 防滥用配额。**
`agent.ts:1102` `this.pause(reason, source)` 未传第三参 `lowRisk`（默认 false，`:1339`）
→ 用户点两次暂停按钮后，Agent 的合理澄清请求会被强制降级 P3。
一个计数器承载了"用户主动暂停"与"Agent 索取确认"两种语义——与 F1-1 同型。

### 正面确认（勿回改）

- 「内核事实驱动延迟翻转」优于「申请即翻转」，结论**成立**：paused chunk 与状态机翻转在
  `consumeExecutionStream` 内同步发生（`:1101-1103`），中间无 await，无窗口。
- 提问关心的"paused chunk 被消费前 Agent 关闭"**已有处理**：
  `close()` 检测 `_pendingPauseReason` 残留 → 补翻状态机使磁盘快照准确（`:2610-2623`）。
- `abandonPause` / `cancelPauseRequest` 与 `requestPause` 严格对称（`:1447/:1461`），包括
  `_pendingPauseSource` 的复位。

### 优化建议

1. **消灭双副本（F4-1 根治）**：`_pendingPauseReason` 不该是 Agent 的独立字段，
   应向 loop 单向查询（`loop.pauseRequested` 已有 getter，`loop.ts:430`）。
   最小修复：`requestPause` 前置校验"是否有活跃流"，无流时直接同步走 `pause()` 而非申请；
   彻底修复：把 pending 状态收进 loop，Agent 只读。
2. `resumeExecution` 首行短路改为 `yield {type:'error'}` + 事件，禁止静默 return；
   `canContinueWithoutInput` 增加 `status === 'error'` → false。
3. 修正 `setPauseMeta` 注释（**注释即契约，写反比不写更糟**），
   并在 `pause()` 内 `createCheckpoint()` 之后补一次 pauseMeta 回填，消除首轮丢失。
4. `agent.ts:1102` 显式传 `lowRisk`：用户主动暂停应为 `true`（不消耗 Agent 澄清配额）。

### 未来演进

双通道（输入永不冻结 / 工作通道可挂起）是**正确且超前**的抽象，
在多 Agent 场景下可自然扩展为"每个 Agent 一条工作通道 + 一条共享输入总线"。
真正的挑战在 MCP 标准化后：工具执行会变成**跨进程、可能长时运行**的调用，
届时"loop 迭代边界挂起"这个粒度太粗——一个跑了 5 分钟的 MCP 工具无法在边界挂起。
需要引入**工具级 checkpoint**（工具调用前落盘 intent、返回后落盘 result，
崩溃后靠 `hasToolExecuted` 判重）。好消息是 outbox 模式（`hasToolExecuted`，`:1270`）
与幂等性标注（`idempotent`）**骨架已经在了**，缺的是把 flush 时机从"回合边界"
下沉到"非幂等工具调用前"。这是我认为最值得投入的下一步演进。

## 整体结论与优先级排序

### 结论

Memora 的 SSOT 实践水平**显著高于同类开源 Agent 框架**：
真理源有明确定义、投影方向单一、写入路径反复收口、关键决策留下了带事故记录的防御性注释。
这些不是靠运气得到的，是靠前两轮审查的工序沉淀。

但本轮发现的 12 个问题里，**有 9 个属于同一个病灶：方向性操作只写了一半**。
- 写了 `record.ok = false` 没写读它的过滤器（F2-2）
- 写了"以默认值填充"的注释没写填充代码（F2-1）
- 写了 `goalChangeSeq++` 没写任何比较（F2-4）
- 写了 `onBootstrapSyncFailed` 回调没写注册（F3-2）
- 写了 loop 侧清理没写 Agent 侧清理（F4-1）
- 写了 evict 没写正确的存活判据（F3-1）
- 写了"唯一写点"没堵住旁路（F2-3）
- 写了 command 语义没写构造者（F1-2）
- 写了注释顺序没核对实际顺序（F4-3）

**这不是能力问题，是缺一道工序。** 建议在评审清单里加一条硬性提问：
> 任何增/删、生产/消费、读/写、置位/归零的改动，**反方向在哪里？谁消费？失败走哪条降级路径？**
> 答不出来的改动不许合入。

这一条能拦住上面 9 个中的 8 个。

### 优先级排序

| 优先级 | 项 | 理由 | 成本 |
|---|---|---|---|
| **P0-1** | F2-1 收口 `parseCheckpoint` + 字段补齐 | 唯一会**静默丢用户全部工作**或崩进程的缺陷 | 中 |
| **P0-2** | F3-1 对账判据改 `seenIds` | 瞬时 IO 错误即导致用户规则消失，且无提示 | 低 |
| **P0-3** | F2-2 补偿闭环兑现（`compensatedAt` + 标脏） | 接入 MCP 后会变成真实重复副作用 | 低 |
| **P1-1** | F4-1 暂停双副本收口 | 用户可稳定复现"暂停按钮失灵" | 中 |
| **P1-2** | F4-2 error 态 + 静默 return | 点了没反应，最伤信任的一类 bug | 低 |
| **P1-3** | 加 `schemaVersion: 1` | 一行成本，是所有未来演进的前提 | 极低 |
| **P1-4** | F1-2 删除/收窄 command 分支 | 今天不可达，明天是事故 | 低 |
| **P2-1** | F2-3 `completeRound` 走唯一写点 | 兑现契约，防未来绕过 | 极低 |
| **P2-2** | F1-1 拆 `lastHeartbeat` 双语义 | 当前靠耦合侥幸安全 | 低 |
| **P2-3** | F2-4 `goalChangeSeq` 兑现或删除 | write-only 字段；兑现后是天然乐观锁 | 中 |
| **P2-4** | F3-2/F3-4/F3-5 降级出口与孤儿清理 | 可观测性与长期数据卫生 | 中 |
| **P2-5** | F4-3/F4-4 注释纠正 + lowRisk 传参 | 低成本高信噪比 | 极低 |

### 明确保持不动（勿"顺手优化"）

1. `createCheckpoint` 的展开合并语义 —— 改回字面量重建会复现三个侧车字段归零事故。
2. Rule = 文件真理源 + SQLite 派生索引 —— 判据成立，不是 dual-source 反模式。
3. `plan` ↔ `roundLog` 单向引用 —— 双向同步才是错的。
4. `consecutivePauseTimestamps` 不入检查点 —— 反滥用卫生状态，重启归零是设计。
5. 内核事实驱动的延迟翻转 —— 优于申请即翻转，已实测无窗口。
6. `consumeExecutionStream` 三路径收口 —— 本仓样板，新增 chunk 类型只改一处。
