## §1 会话状态机（SessionStateMachine + SessionManager）

### 评分

| 维度 | 分数 | 依据 |
|---|---|---|
| SSOT 符合度 | **3 / 5** | 状态机是名义真理源，但 `checkpoint.status` 有 3 处独立赋值，且读取方分裂 |
| 设计闭环完整度 | **3 / 5** | 连续暂停闭环有衰减兜底（正确）；暂停超时定时器有恢复路径缺口 |
| 未来兼容性 | **2 / 5** | 全部计数器/定时器都是单进程内存态，无 owner/lease，多 Agent 不可用 |
| 风险评级 | **中** | 无数据丢失，但状态显示不一致 + 资源滞留 |

### 1.1 核心发现一：`checkpoint.status` 是手工同步的镜像，不是派生投影

`currentStatus` 写点 6 处，全在 `sessionStateMachine.ts:56/99/130/163/217/280` —— 状态机内部收口良好。

问题在 `checkpoint.status`：

| 位置 | 写法 | 性质 |
|---|---|---|
| `sessionManager.ts:363` | 从状态机读取后赋值 | 投影（合法） |
| `sessionManager.ts:659` | `this.checkpoint.status = 'running'`（resume 内） | **硬编码字面量** |
| `sessionManager.ts:778` | 同上（recover 内） | **硬编码字面量** |

后两处虽然当前取值恰好等于状态机结果，但它们是**手抄**而非派生。判据很简单：如果状态机将来新增一个中间态（例如 `resuming`），`:659` 不会跟着变——这正是 stale mirror 的定义。

读取方同样分裂：内核读状态机（`agent.ts:996/1357/1516` 等），宿主读检查点（`hosts/memora-sprite/src/electron/main.ts:576`）。**两个真理源 × 两批消费者 = 四象限**，只要任一象限失步，UI 与内核就各执一词。

### 1.2 核心发现二：上一轮修复留下的 error 缺失分叉

`restoreFromCheckpoint` 修复后的形态（`sessionManager.ts:544-556`）：

```ts
this.stateMachine.resetToRunning();                              // :544 无条件归零
if (checkpoint.status === 'error' && checkpoint.error) { ... }   // :545 需要 error 字段
else if (checkpoint.status === 'paused') { ... }                 // :550
// running 由 resetToRunning 承担
```

若 `status === 'error'` 而 `checkpoint.error` **缺失**（旧版检查点、序列化丢字段、或 `triggerError` 未写 error 的路径），两个分支都不进：

- 状态机 = `running`（`:544` 已强制归零）
- `this.checkpoint.status` = `'error'`（`:515` 整体赋值保留原值）

→ **永久分叉，且无任何日志**。原实现（未 resetToRunning）反而不会产生这个分叉，因为它不主动改状态机。`loadPersistedCheckpoint:480` 有同样的复合条件，但那里没有前置归零，所以只是"不恢复"，不是"反向恢复"。

这是典型的「对称的另一半没写完」：加了强制归零，却没给归零后无法重建的情况兜底。

### 1.3 `consecutivePauseCount` 闭环 —— 结论：机制正确，但重置端在生产链路不可达

先说正确的部分（**不要改**）：

- 递增唯一点 `sessionManager.ts:611`，且 `lowRisk` 门控正确（`:610`）
- **有 1 小时滑动窗口衰减**：常量 `:97`，惰性衰减实现 `:708-718`，查询时触发（`:730/:740`）
- 所以「用户永远不回答」不会锁死系统 —— 1 小时后自动归零

这是自愈式防线，优于单调计数器。设计正确。

但闭环有两个真实缺口：

1. **重置端在生产链路走不到**：唯一重置点 `agent.ts:917` 位于 `processEvent` 的 clarify 分支内，而宿主提交澄清回答走 `void agent.processEvent(event)`（`chatHandlers.ts:346`）—— 这行代码**不执行任何函数体**（详见 §4.1）。因此"递增→回答→重置"的闭环，**重置端从未在生产中执行过**，实际只剩 1h 衰减在兜底。
2. **计数不进检查点**：`SessionCheckpoint` 字段全集（`types.ts:445-497`）无该字段 → 重启即清零。防滥用可被重启绕过。攻击面是本机用户，危害低，但语义上属于"防线有后门"。

### 1.4 暂停超时的生产→消费：定时器在恢复路径缺席

生产路径 2 条、消费者 1 个，本身对齐：

| 环节 | 位置 |
|---|---|
| 生产（启动加载） | `sessionManager.ts:472` → `markSessionTimedOut` `:1320` |
| 生产（运行时定时器） | `:1395`（`checkPauseTimeout` `:1367`） |
| 消费 | `agent.ts:295`（同步 emit，监听器 `:256/:286` 注册早于加载 `:261`，无竞态） |

**断裂点**：`startPauseTimeoutTimer()` 的唯一调用点是 `sessionManager.ts:620`，位于 `pause()` 内部。而两条恢复路径绕过了 `pause()`：

- `loadPersistedCheckpoint:479` → `this.stateMachine.pause(...)`
- `restoreFromCheckpoint:551` → `this.stateMachine.pause(...)`

→ **从检查点恢复的 paused 会话，本次运行期内永不启动超时定时器**，只能等下次重启由 `:457` 发现。

缓解事实（必须如实计入，防止高估）：`resume():641` 有 `isPauseTimedOut` 前置拦截，所以不会"错误地恢复一个已超时会话"。危害限于**资源滞留 + 归档延迟**，不是正确性事故。故本条评级为中，不是高。

### 1.5 转移表

合法转移 4 条（`:88/:119/:152/:185`）+ 旁路 `resetToRunning()`（`:279`）。
注释与实现不符 1 处：`:232-235` 声称 `command → 检查是否可恢复（若当前为 ERROR）`，实现 `:241-250` 是纯 no-op 恒 allowed。属注释撒谎，无运行期危害，但按「注释即契约」应收窄。

### 优化建议

1. **消灭 `:659/:778` 的字面量赋值**：抽 `private syncCheckpointStatus()`，统一 `this.checkpoint.status = this.stateMachine.status`。让检查点 status 成为**只能派生、不能手写**的字段。
2. **补 error 缺失兜底**：`:545` 改为 `if (checkpoint.status === 'error')`，内部再判 `error` 字段有无并给默认 cause；或在 `resetToRunning()` 后立即 `syncCheckpointStatus()`，让分叉在结构上不可能出现。**后者更好** —— 它不是补一个 if，而是让"归零"这件事把两侧一起归零。
3. **定时器随状态而非随动作启动**：把 `startPauseTimeoutTimer()` 从 `pause()` 内移出，改为订阅状态机的 `→PAUSED` 转移。这样任何进入 paused 的路径（含恢复）都自动获得定时器，不再依赖"记得调"。
4. **计数入检查点**（可选，低优先）：`consecutivePauseTimestamps` 加入 `SessionCheckpoint`，重启后按 1h 窗口重新衰减即可，无额外复杂度。

### 未来演进思考

三态机（RUNNING/PAUSED/ERROR）在**单 Agent 单进程**下是恰当的最小模型 —— 不要为了"未来"提前加态。但多 Agent 协作会引入两个当前模型无法表达的东西：

- **归属与租约**：谁在跑这个会话？崩溃后谁能接管？现在的状态机没有 owner，也没有 lease TTL。`lastHeartbeat` 已经存在（`types.ts:496`），它其实是租约的雏形，但目前只用于超时判定。
- **等待态的细分**：`PAUSED` 现在混装了"等用户澄清"和"等外部工具/其他 Agent 回调"两种语义。MCP 长任务与 Agent 间委派会让后者成为常态，届时 `pauseMeta.phase` 需要升格为一等状态维度，而不是附属元数据。

建议的演进路径：**先把 `lastHeartbeat` 的语义从"超时判据"扩展为"租约续期"**，这一步不改状态机、成本极低，却为后续接管机制留好了挂载点。

## §2 检查点模型（SessionCheckpoint）

### 评分

| 维度 | 分数 | 依据 |
|---|---|---|
| SSOT 符合度 | **3 / 5** | 多数字段唯一副本在检查点内（正确）；plan/roundLog 是两份独立事实 |
| 设计闭环完整度 | **2 / 5** | 恢复路径有悬空 Promise、脏标记绕过、反序列化零校验 |
| 未来兼容性 | **1 / 5** | 无 schemaVersion、无 CAS、`JSON.parse as T` 裸转型 |
| 风险评级 | **高** | 版本演进时会静默丢会话或直接崩溃 |

### 2.1 字段守恒：多数正确，两处缺陷

按「是否存在第二份运行时副本」判据分类（这是判断需不需要回灌的唯一正确判据）：

- **需回灌且已正确回灌**：`hotMemory`→`:520-528`、`truncatedCount`→`:533-537`、`status/error`→状态机 `:544-555`、`completedToolCalls`→`:570`、`role`→PersonaManager（`agent.ts:1257-1269`）、`resource.documents`→SkillManager（`agent.ts:1282-1284`）
- **无需回灌**（唯一副本即检查点，`:515` 整体赋值即完成）：`plan`、`roundLog`、`goalVersion`、`mainGoal`、`currentGoal`、`standard`、`pauseMeta`、`lastHeartbeat`

⇒ **字段守恒的主体是正确的**，第一轮的判断成立，不必改。

两处缺陷：

1. **悬空 Promise（确认）**：`sessionManager.ts:564` 调用 `history.loadSessionMessages(date, session)`，而该方法是 `async`（`messageHistory.ts:264`）。`restoreFromCheckpoint` 返回 `number`（同步），无法 await。后果有二：(a) 会话切换在微任务队列中异步完成，与 `:528` 刚灌入的热窗口构成时序竞态；(b) rejection 无人处理 → `unhandledRejection`。
2. **`updateStep` 绕过脏标记（确认）**：`agent.ts:1979-1990` 直改 `step.status`（`:1985`）并手写 `cp!.lastHeartbeat`（`:1986`），**不调 `touchCheckpoint()`** → `checkpointDirty` 未置位 → 计划状态变更可能永不落盘。这是"手抄 touchCheckpoint 的副作用（改 lastHeartbeat）却漏抄它的主作用（标脏）"的典型。

### 2.2 核心发现：反序列化是裸转型，且崩溃点不对称

```ts
const checkpoint = JSON.parse(json) as SessionCheckpoint;   // sessionManager.ts:451
```

- **无 `schemaVersion`**（`types.ts:445-497` 全字段核对，确认无此字段）
- **零字段校验、零默认值兜底**：`as` 是编译期断言，运行期什么都不做
- **无 CAS / 乐观锁**：存储层 `INSERT OR REPLACE`（`hosts/memora-sprite/src/storage/sessionStore.ts:382`），末位写入者胜

崩溃行为**不对称**，这比崩溃本身更麻烦：

| 入口 | 旧检查点缺 `hotMemory` 时 |
|---|---|
| `loadPersistedCheckpoint` | `:520` `.map` 抛 TypeError → 被 `:490` catch 吞掉 → **静默丢弃整个会话**（日志级别 warn） |
| `restoreFromCheckpoint` | 无 try/catch → **直接向上抛，崩到调用栈顶** |

同一个数据缺陷，走两条路得到两种结局：一条静默丢数据，一条炸进程。**没有任何一条是"降级但可用"** —— 这违反项目自己的降级优先原则（`architecture_philosophy_rules.md §7`）。

### 2.3 `goalVersion`：名字撒谎的字段

- 写点 2 处：`sessionManager.ts:375`（初始化）、`:833`（`++`）
- 读点 2 处：`:840` / `:853`，**都只是事件 payload**
- **全仓无任何两个 goalVersion 值的比较**

而真正的漂移检测判据是**文本相似度**（`goalConsistencyChecker.ts:130-142`，Jaccard + bigram，阈值 0.7 / 0.4），与 goalVersion 毫无关系。

⇒ 第一轮定性为「契约未兑现」，本轮应再收紧一档：它**连版本语义都不承担**，实质是"目标变更事件序号"。叫 `goalVersion` 会让后来人误以为存在版本校验机制，从而在需要一致性校验时**误用它**。这比字段死更危险 —— 死字段无害，**误导性命名会诱发错误实现**。

`goalDriftDetected` 的宿主监听状态与第一轮一致：生产代码零监听（仅 `chatHandlers.test.ts:91` 的 mock），`drift` 级有内核自兜底（`:857-860`），`minor` 级仍是发了没人收。

### 2.4 `plan[]` 与 `roundLog[]`：两份独立事实，不是一份事实的两个视图

- `roundLog` 唯一写点 `completeRound`（`sessionManager.ts:973-1011`），由 `loop.onRoundBoundary` 每迭代触发（`agent.ts:1901-1908`），**不传 stepId** → `stepId` 恒为 undefined
- `plan` 由 `task_table_update` 更新（`agent.ts:1979-1990`），**不写 roundLog**
- 二者无引用关系：roundLog 无有效 stepId，plan 无回合引用

判据回答你的原问题：**不需要"同步更新"，但需要"可关联"**。

- 强行让 `task_table_update` 去写 roundLog 是错的 —— 那会把"迭代发生了什么"和"任务进展到哪"两种正交事实揉成一份，反而制造新的双写。
- 正确的做法是**建立单向引用**：`completeRound` 时把当时的 activeStep.id 填进 `roundLog.stepId`（该字段已存在，只是没人填）。这样 roundLog 成为 plan 的**时间轴投影**，可从 roundLog 追溯"哪一回合推进了哪一步"，但 plan 仍是任务状态的唯一真理源。

当前状态下，叠加 §2.1 的脏标记缺失与 roundLog 的 FIFO cap 12（`:1003`），恢复后出现「plan 显示 done、roundLog 无对应记录」的矛盾是**必然而非偶然**。

### 优化建议（按性价比排序）

1. **加 `schemaVersion`（一行成本，最高性价比）**：`createCheckpoint` 写入常量，`loadPersistedCheckpoint` 读到不认识的版本就走"保留原文件 + 新建会话"而非删除。这是我唯一建议**立刻做**的未来兼容项 —— 它现在是一行，等到需要迁移时就是一次考古。
2. **反序列化收口为一个 `parseCheckpoint(json): SessionCheckpoint | null`**：内部做字段补齐（`hotMemory ?? []`、`plan ?? []`），两个入口共用。同时消除"两条路两种崩法"的不对称。
3. **`updateStep` 改调 `sm.touchCheckpoint()`**，删掉手写 lastHeartbeat 的那一行。
4. **`restoreFromCheckpoint` 的会话切换**：要么改为 `async`，要么把 `loadSessionMessages` 的调用提到调用方 await，禁止悬空。
5. **`goalVersion` 二选一**：兑现（真做版本校验，用于跨进程/多 Agent 的目标一致性）或改名（`goalChangeSeq`）。禁止维持现状。
6. **填 `roundLog.stepId`**（见 §2.4）。

### 未来演进思考

检查点当前是「SQLite 单 TEXT 列存整个 JSON、全量覆盖」。三个趋势会同时冲击它：

- **长上下文**：`hotMemory` 随窗口增长可达数 MB，全量覆盖写会让每次 `touchCheckpoint` 都变成大对象序列化。届时需要把 hotMemory 从检查点剥离为独立表 + 引用。
- **多 Agent 并发**：无 CAS 的 `INSERT OR REPLACE` 在两个 Agent 写同一会话时必然丢更新。
- **Agent 自我进化**：检查点结构本身会频繁变更，无 schemaVersion 意味着每次结构变更都是一次不可逆的破坏性升级。

三者共同的前置条件都是 **schemaVersion**。所以它不只是"未来兼容"，而是**演进的准入券**。

## §3 记忆分类与存储（Everything is Memory v2）

### 评分

| 维度 | 分数 | 依据 |
|---|---|---|
| SSOT 符合度 | **3 / 5** | Rule 的文件+索引分层本身正确，但**删除方向不自愈**，构成真实泄漏 |
| 设计闭环完整度 | **2 / 5** | 结晶路径不刷 bootstrap；关系侧车有清理遗漏点 |
| 未来兼容性 | **3 / 5** | 两轨模型抽象良好，可承接 MCP 与多 Agent；索引层需补对账 |
| 风险评级 | **中** | 僵尸规则会持续污染 system prompt，且用户不可见、不可删 |

### 3.1 核心发现：Rule 不是 dual-source，但**删除**是

先给判据结论：**「删掉从库能否无损重建？」** —— 对 Rule 的**内容**，能（`MemoryLoader` 重扫文件即可）；对 Rule 的**存在性**，不能。

`loadAllToIndex`（`loader.ts:63-100`）的完整行为是：遍历文件 → `restore(id)` → `upsert(memory)`。**只有 add，没有任何对账或剪枝**。

后果：

| 场景 | 结果 |
|---|---|
| 改文件内容 → 重启 | ✅ 自愈（同 id upsert 覆盖） |
| **删文件 → 重启** | ❌ **SQLite 旧行永久存活**，继续被 `bootstrap` 的 `getBySource(RULE)` 全量拉取（`loader.ts:115`）注入 `messages[0]` |
| 绕过文件层直调 `addRule` | ❌ 造出无文件的孤儿 rule，同样永久驻留 |

`configManager.ts:17-23` 的类注释已经文档化了这个契约，并声称「重启后由文件（MemoryLoader）自愈」、「绕过文件层的写操作不持久 —— 重启后会被文件恢复原状」。

**这个自述只对内容修改成立，对删除完全不成立** —— 实际行为恰好相反：孤儿 rule 不但不会被"恢复原状"，反而获得了永生。用户在文件面板看不到它、删不掉它，但它每一轮都在污染 system prompt。

这就是「注释即契约」的反例：注释描述的自愈机制在代码中只实现了一半，而缺失的那一半正是危害发生的方向。

`deletePersona` 是同一个洞的更严重版本：`personaManager.ts:273` → `configResourceManager.ts:109-118` **只 splice 内存数组**，完全不碰 SQLite。而 `MemoryLoader` 启动时会把 persona 写进 SQLite（`loader.ts:21,86`，`STARTUP_SCAN_SOURCES` 含 persona）。宿主侧注释宣称"清内存 + SQLite 软删除"（据子代理报告在 `sprite.ts:806` / `configFileSyncer.ts:83`，**此两处行号我未逐行复核**）—— 若属实则是又一处注释撒谎。

> 附带确认：Persona/Skill「已从 SQLite 解耦」的说法**不严格成立**。Manager 自身零 SQLite 依赖是真的，但 `MemoryLoader` 仍把它们 upsert 进索引，`memoryInspector.snapshot` 仍从索引读。哲学文档 §1.4 的"禁止写入 SQLite"与实现有落差。

### 3.2 autoConfigRefiner：结晶路径缺一次刷新

`confirmConfigSuggestion`（`configManager.ts:168-204`）的顺序是：写文件 → `index.upsert`（`:199`）→ `injectSystemMessage`（`:204`）。**未调用 `refreshBootstrapMemories`**。

后果：新确认的规则在本次运行中**只靠一条临时 system 消息生效**，而临时消息会被每轮的清理/截断/摘要机制侵蚀；真正常驻的 `messages[0]` bootstrap 段要等到下次重启才包含它。用户体验上表现为"刚确认的规则，聊几轮就不管用了"。

失败路径的排序是**正确**的（`:180-194` 文件写失败则抛出，`upsert` 不执行），无半写风险 —— 这点不要动。

幂等性：靠进程内 `Set`（`autoConfigRefiner.ts:65`）+ 按 name 精确比对（`:262`）。重启即失忆，且启发式路径的 name 由捕获文本拼接（`:224`），措辞微变即绕过去重 → 同义规则膨胀。这是「血肉结晶为骨骼」最现实的腐化方向：**骨骼会越长越多，且没有吸收机制**。

### 3.3 MemoryRelation 侧车：清理靠自觉

- 表定义**无 FOREIGN KEY / ON DELETE CASCADE**（`hosts/memora-sprite/src/storage/sqliteRelationStore.ts:22-30`）
- 靠 6 处显式清边（`writeDelete` / `writePurge` / `writePurgeExpired` / `deleteRule` / `deleteSkill` / UserProfile 冲突替换）—— 覆盖面其实相当好
- **遗漏点**：`ProjectManager.closeProject` 的 `agentIndex.delete(id)`（`projectManager.ts:340-344`）不清边 → 项目级 rule/skill 被 insight 引用时，切项目后留下悬挂边
- `getRelations` 不校验对端存在性，返回悬挂 ID 不崩溃不过滤（`memoryInspector.ts:443-458`），仅渲染层兜底

因果一致性的答案是：**由 6 处调用点各自保证，没有单一守卫**。这在"清理点会持续增加"的前提下必然漏 —— 已经漏了一处。

### 优化建议

1. **给索引加对账（最高优先）**：`loadAllToIndex` 已经返回 `loadedIds`（`loader.ts:64,88`），但没人用。用它做一次差集软删除：`getBySource(source)` 中不在 `loadedIds` 内的行 → 软删除。这不是新增机制，而是**把已有的返回值兑现**，成本极低，一次性关掉僵尸 rule / 僵尸 persona 两个洞。
2. **`confirmConfigSuggestion` 补 `refreshBootstrapMemories()`**：该回调是构造必传（`configManager.ts:106`），此处直接可用。
3. **关系清理收口**：把"删记忆"与"删关系"合成一个 `purgeMemoryWithRelations(id)`，让 6 个调用点变成 1 个原语的 6 次调用。或直接在建表语句加 `ON DELETE CASCADE`，把一致性下沉到存储层 —— **后者更彻底**，因为它让"忘记清边"在结构上不可能。
4. **结晶幂等升级**：去重指纹持久化到 SQLite（而非进程内 Set），并把 name 精确比对换成对已有规则集的语义相似度检查（复用 `goalConsistencyChecker` 已有的 Jaccard/bigram 实现，不引入新依赖）。

### 未来演进思考

「设定记忆 = 骨骼 / 对话记忆 = 血肉」这个二分是本项目最好的抽象之一，它天然适配未来趋势：

- **MCP 标准化**：MCP server 提供的 tool/resource 描述本质上就是设定记忆（确定性注入、非召回）。当前的两轨模型可以直接接纳它们，不需要第三条轨道。
- **多 Agent**：设定记忆是可共享的（多个 Agent 读同一份 rules/），对话记忆是私有的。轨道分离让共享边界天然清晰。

真正的瓶颈不在模型，而在**索引层缺少对账**。多 Agent 或 MCP 动态注册后，配置来源会从"一个目录"变成"多个来源 × 动态增删"，届时"只 add 不 evict"会从"偶尔留个僵尸"恶化为"索引与现实持续发散"。**建议 3.1 的对账在引入任何新配置来源之前完成** —— 这是准入条件，不是优化项。

## §4 不中断工作模型的设计闭环

### 评分

| 维度 | 分数 | 依据 |
|---|---|---|
| SSOT 符合度 | **3 / 5** | 延迟翻转机制本身正确；早退路径与 close 路径留下 pauseMeta 分叉 |
| 设计闭环完整度 | **1 / 5** | 澄清闭环两条出口在生产链路上**完全不执行** |
| 未来兼容性 | **2 / 5** | 内核层无并发互斥，续跑与主路径可并发写同一 loop |
| 风险评级 | **高** | 用户可见的功能失效 + 静默成功假象 |

### 4.1 核心发现（本轮最严重）：`void agent.processEvent(event)` 等于什么都没做

```ts
// hosts/memora-sprite/src/electron/ipc/chatHandlers.ts:346  —— 用户提交澄清回答
void agent.processEvent(event);
return { success: true };

// 同文件 :384  —— 澄清超时自动续跑
void agent.processEvent(event);
```

而 `processEvent` 的签名是（`agent.ts:818`）：

```ts
async *processEvent(event: SessionEvent, signal?: AbortSignal): AsyncGenerator<AgentChunk, void, unknown>
```

**async generator 是惰性的**：调用它只构造迭代器对象，在首次 `next()` 之前**函数体一行都不执行**。`void` 明确丢弃返回值，没有任何迭代发生 → 生成器直接被 GC。

讽刺的是，该方法自己的文档注释就写了正确用法（`agent.ts:812`）：
```
for await (const chunk of agent.processEvent(event)) { ... }
```
宿主违反了内核在注释里写明的调用契约，而 TypeScript 不会报错（`void` 一个未使用的迭代器完全合法）。

**失效范围**（全部是用户可感知功能）：

| 应发生 | 实际 |
|---|---|
| PAUSED → auto-resume（`agent.ts:829`） | 不执行 |
| Composer 补全澄清槽位 | 不执行 |
| clarify → chat 转换 + 续跑（`agent.ts:918`） | 不执行 |
| `resetConsecutivePauseCount()`（`agent.ts:917`） | 不执行 ← §1.3 的闭环断在这里 |
| 5 分钟超时自动续跑 | 不执行 |

更糟的是**静默成功假象**：`:347` 照常返回 `{ success: true }`，渲染层据此立即关闭澄清面板。用户看到"回答已提交"，实际什么都没发生。会话停在 PAUSED，直到用户忍不住自己发一条新消息 —— 而那条 chat 事件走的是正常的 `for await` 链路，会 auto-resume 并推进对话。

**这个"看起来能用"正是 Bug 长期存活的原因**：正常路径掩盖了断裂路径，症状表现为"有时候要多说一句才动"，很容易被归因为模型延迟。

⇒ 这也是为什么第一轮审查没抓到它：第一轮聚焦内核 `src/`，而断裂发生在**宿主对内核契约的调用姿势**上。跨边界的契约违约，只 grep 内核永远看不见。

### 4.2 核心发现二：`canContinueWithoutInput` 与 `isPlanStalled` 对 `blocked` 的判据相反

```ts
// agent.ts:1518   —— blocked ≠ done ⇒ 算「可续跑」
plan.some((s) => s.status !== 'done')

// sessionManager.ts:1056  —— blocked 算「已停滞」
plan.every((s) => s.status === 'done' || s.status === 'blocked')
```

同一份 `plan`、同一个 `blocked` 状态，两个函数给出相反结论。后果链：

1. 计划全部 `blocked` → `canContinueWithoutInput()` 返回 true → UI 显示"继续"按钮
2. 用户点击 → `resumeExecution()` → `:999` **resume() 已执行，状态机翻 running**
3. `:1016` `isPlanStalled() && !isInAutonomousStep` 命中 → 早退
4. 只 yield 一句 `'所有计划步骤已完成，请提供下一步指令'`（`:1017`）

三重问题叠加：

- **按钮点了没反应**（判据宽于实际能力）
- **文案撒谎**：全 blocked 不是"已完成"，是"全卡住了"。用户被告知任务完成，实际一步没成
- **留下新分叉**：早退前已 resume，状态机 = running，而 `pauseMeta` 未清（`agent.ts:1452` 注释自证 resume 不清 pauseMeta）→ 又一处 status/pauseMeta 不一致

注意：空计划（`plan.length === 0`）走 `:1055` 恒 true，也会命中同样的早退，但那时 `:1518` 的 `some` 返回 false，所以不会显示按钮 —— 空计划场景是自洽的。**只有 blocked 场景会翻车**。

### 4.3 双通道模型的安全性：无节流，且副作用先于校验

- 自动恢复判定：`agent.ts:1363` `if (status === 'paused' && eventType !== 'command') return this.resume();`
- **无任何节流/防抖/合并**。唯一串行化是 `acquireChatLock`（`agent.ts:470-472`，忙则抛 `chatBusyError`）与宿主单闸门（`chatStreamHandler.ts:77-80/133-136`）
- paused chunk 后宿主 `break`（`chatStreamHandler.ts:315`）→ finally 释放闸门（`:382`）→ 下一条 chat 立刻可进

所以"PAUSED 态连发大量 chat"的实际行为是：**每条都触发完整的 resume → 整轮 LLM → 可能再 pause**。这不算振荡（有锁串行化，不会并发爆炸），但也没有合并语义 —— 用户连发 5 条，就是 5 轮完整推理。

**顺序缺陷（确认）**：`autoResumeIfPaused`（`:829`）在 `acquireChatLock`（`:833`）**之前**。锁忙时状态机已经翻成 RUNNING，然后才抛错返回 → **PAUSED 态被静默吞掉**，会话从此以为自己在跑。这是经典的"副作用先于校验"，正确顺序应是先拿锁再改状态。

**内核层无互斥**：`resumeExecution`（`agent.ts:995-1053`）全程**不取 chat 锁**，仅靠 `:996` 的状态判定。内核层面它与 `chat/processEvent` 可以并发写同一 `loop.messages`。当前靠宿主 AbortController 兜住，但那是宿主的实现细节，不是内核契约 —— **任何第二个宿主接入都会踩这个坑**。

### 4.4 `close()` 时的暂停残留

`agent.ts:2571-2584`：清 `_pendingPauseReason` 但**不复位 `_pendingPauseSource`**（与 `:1426/:1444` 的对称清理不一致 —— 上一轮修的是 `consumeExecutionStream` 的 finally，`close()` 这条路没纳入）。

更实质的问题：`:2579` 强制 `pause()` 落盘 `status = 'paused'`，而 `sessionManager.pause()`（`:604-629`）**不写 pauseMeta** → 重启后检查点有 paused 状态但无暂停元信息，宿主命中兜底文案（`main.ts:576-583`），用户点"继续"再撞上 §4.2 的早退。

更早的窗口：`loop.ts:585` 的 `onPaused` 回调立即落盘 pauseMeta，先于 `:586` 的 yield 与 `agent.ts:1080` 的状态机翻转。若消费者在这中间放弃（宿主 break / 进程被杀），残留就是 **status=running + pauseMeta.suspended**。

⇒ 回答你的原问题：延迟翻转机制**本身是正确的**（第一轮已论证，不要改），但它有一个未被承认的前置假设 —— **"paused chunk 一定会被消费"**。这个假设在 close/kill 场景下不成立。修法不是放弃延迟翻转，而是**让 pauseMeta 的写入与状态机翻转成为同一个原子步骤**：把 `onPaused` 的落盘推迟到 `agent.ts:1080` 的 `pause()` 内部执行。

### 优化建议（按优先级）

1. **【P0】修 `void processEvent`**：宿主两处改为完整迭代：
   ```ts
   void (async () => { for await (const _ of agent.processEvent(event)) { /* 需转发则在此推流 */ } })()
       .catch((err) => logger.error({ err }, '澄清回答处理失败'));
   ```
   更好的做法是**让内核提供一个非流式门面** `await agent.dispatchEvent(event)`，内部自行 drain —— 因为"调用方必须迭代才会执行"是 async generator 的隐式契约，靠文档约束跨进程调用方是不可靠的。**把契约从"记得迭代"变成"类型上不可能错"**。
2. **【P0】加防回归测试**：断言 `SESSION_CLARIFY_ANSWER` handler 执行后 `resetConsecutivePauseCount` 被调用 / 状态机已离开 paused。此测试必须能在修复前变红。
3. **【P1】统一 `blocked` 判据**：抽 `planProgress(plan): { stalled, continuable }` 单一函数，两处共用。同时修 `:1017` 的文案，区分"已完成"与"全部阻塞"。
4. **【P1】调换 `:829` 与 `:833` 顺序**：先拿锁，再 auto-resume。
5. **【P2】`resumeExecution` 纳入 chat 锁**：让内核自己保证互斥，不依赖宿主。
6. **【P2】pauseMeta 落盘与状态机翻转合并**（见 §4.4）。

### 未来演进思考

「输入通道永不冻结」的设计方向是对的 —— stateful Agent 的核心竞争力就是"用户随时可以插话，Agent 不丢上下文"。但当前实现把"不冻结"实现成了"每条输入都触发完整重入"，这在两个趋势下会出问题：

- **长任务 / MCP 异步工具**：Agent 可能在 PAUSED 态等待外部回调数分钟。这期间用户的多条输入应当被**累积合并**为一次续跑上下文，而不是各自触发一轮 LLM。当前无合并语义。
- **多 Agent 委派**：`resumeExecution` 不取锁的问题会从"理论风险"变成"必然冲突" —— 委派方与被委派方都可能驱动同一会话。

建议的演进方向：**把"输入"与"执行"解耦成生产者/消费者**。输入通道只负责把事件追加到队列（永不阻塞、永不失败），执行通道从队列取批次消费。这样"不冻结"由队列保证，"不振荡"由批次消费保证，二者不再互相牵制。这个改造不需要现在做，但**§4.3 的锁顺序修复应当朝这个方向走**，别加会挡路的临时互斥。

### 总体判断

这个项目的**架构判断力明显高于工程完成度**。

- 值得肯定且**不应改动**的：两轨记忆模型、延迟翻转的内核事实驱动、`consecutivePauseTimestamps` 的 1h 衰减自愈、检查点字段守恒的主体、`confirmConfigSuggestion` 的失败排序、Rule 的文件真理源分层。这些都是想清楚了才写出来的，不是碰巧。
- 反复出现的**同一种病**：**对称的另一半没写完**。第一轮把它诊断为四个根因并修复了，本轮发现它换了个位置继续存在：
  - 加了 `resetToRunning` 却没管 error 缺失（§1.2）
  - 抄了 `touchCheckpoint` 的副作用却没抄主作用（§2.1）
  - 实现了文件→索引的 add 却没实现 evict（§3.1）
  - 写了 `for await` 的文档却让宿主用 `void` 调用（§4.1）

  这说明根因不在具体代码，而在**缺少"对称性检查"这一道工序**。建议把它显式写进 `.trae/rules`：任何引入方向性操作的改动（增/删、生产/消费、写/读、翻转/归零），评审必须回答"反方向在哪里"。

- **跨边界审查是本轮最大的方法论收获**：§4.1 那个最严重的问题在内核里完全看不见，它是宿主对内核隐式契约的违约。第一轮只审 `src/` 因而漏判。**内核 + 宿主分离的项目，SSOT 审查必须跨边界，否则契约的两端各自看起来都对。**

| 两轨记忆模型 | 天然适配 MCP 与多 Agent，无需重构 |
| `task_table_update` 同步写 roundLog | 会把两种正交事实揉成一份，制造新双写；正确做法是单向引用 |
| 为"一致性"统一所有裸写/所有存储 | 一致性不是目的，正确性才是（第一轮 §0.4 已论证） |

### 一句话结论

**Memora 的骨架是对的，接缝需要复查。** 四个子系统里没有一个需要重构，但每一个都有"只写了一半"的方向性操作 —— 其中 §4.1 那一半恰好是用户每天都会碰到的那一半。
