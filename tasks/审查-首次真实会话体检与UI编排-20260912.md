## 一、A1 · 首轮 narrate（✅ 已落地 · 2026-09-12）

### 问题
模型在调工具前说的那句话（"我先全面探索…"）被并入 `assistantMessage` 正文，无法与它引发的工具步骤绑定渲染，折叠块里只剩干巴巴的工具名。

根因：`src/agent/managers/llmCaller.ts:182`
```ts
const deferTextToMessageEnd = this.deps.hasToolExecutedThisTurn();
```
注释明写「**单轮问答/首轮（无工具史）保持逐字流式，不受影响**」→ 首轮文本直接进正文，`pendingNarrate` 为空 → `loop.ts:963` 的 `if (narration)` 不成立 → 不产 narrate。
本次 41 条 processEvents 中 **narrate = 0**，实证。

### 主流做法（联网查证）
- **Claude Code**：消息拆为 `AssistantTextMessage`（文字）与 `AssistantToolUseMessage`（工具）**交替渲染**；官方节奏描述为「text explains what it will do → pause while tools execute → more text」；工具带 `getToolUseSummary`/`userFacingName`；并行调用聚合为 `GroupedToolUseContent`；视图三档 Normal / Verbose / Summary。
- **Cursor**：叙述与操作严格绑定（"我会构建…：`summary.py +150-0`"）；CLI 为 `⬢Thought 3s → ⬢Read 3 files → ⬢Planned 2s`。
- **行业共识**（AYDesign 2026）：**hidden tool calls 与 raw JSON dump 同属 broken defaults**。

### 方案实测（关键：方案 D 已被证伪）
我实现了「首字缓冲窗口」（`NARRATE_PROBE_CHARS=120`，首轮先缓冲、收到 toolCalls 信号则整段归 narrate），结果 **3 个测试失败**：

| 失败测试 | 现象 | 性质 |
|---|---|---|
| `loop.test.ts:186` 纯文本流式输出 | 期望 `['你好','！','我是 Memora']` 实得 `['你好！我是 Memora']` | **语义契约破坏**（逐字 → 合并） |
| `loop.test.ts:1262` 流式中途失败 | 期望含 `'部分内容'` 实得 `[]` | 流中断时缓冲丢失（可修） |
| `loop.test.ts` 硬停止 abort | 期望 >0 实得 0 | 同上（可修） |

**更根本的代价**：120 字符 @ 50–100 字/秒 ≈ **首字延迟 1–2 秒**；窗口降到 40 字符虽能压到 0.4 秒，但本次真实开场白有 51 字符 → 捕获残缺（前 40 归 narrate、后 11 走正文）。
**窗口调参无法两全**：太小捕获不全，太大伤 TTFT。

**已回退**（tsc 0 / 128 测试全过，工作区已净）。

### 决策项（三选一）
| 方案 | 做法 | TTFT | 契约影响 | 评价 |
|---|---|---|---|---|
| A 维持现状 | 首轮开场白并入正文 | 0 | 无 | 折叠块仍偏"干"，但零风险 |
| B 首轮全延迟 | `deferTextToMessageEnd = true`（1 行） | **+3.5s**（本次实测 23:21:36.670→40.134） | 破坏逐字流式 | 最省事，体验明显退化 |
| **C 回抽（推荐）** | 逐字流式照旧 + 首轮文本同步累积 `pendingNarrate`；确认是工具轮后发 `narrate_retro` 事件，宿主把已渲染的该段文本**移入** narrate 块 | **0** | 新增事件类型，不破坏既有 | TTFT 无损；视觉上"文字→工具"节奏**最接近主流**；代价是宿主需保留 chunk 节点引用以支持回抽 |

**建议走 C**，但需先确认宿主回抽的实现边界（见 A4）。

### 落地实现（✅ 2026-09-12 · 与台账草图 C 有两处关键修正）

| 维度 | 台账草图（方案 C） | 实际落地 |
|---|---|---|
| 事件契约 | 新增事件类型 `narrate_retro` | **复用 `narrate`，新增可选字段 `withdrawn`**（该段原文）——不新增事件类型，语义收敛在既有 narrate 上；**不落盘、不进 ProcessEvent**（重放无需特判） |
| 宿主侧 | 按 chunk 分节点保存引用，把前 N 个节点**移入**过程区（A4 前提） | **A4 前提证伪**：宿主正文是**全量重渲染**自 `streamingRaw`（`chatView.ts:2693` `body.innerHTML = renderMarkdown(streamingRaw)`）→ 撤回 = 去该后缀 + 重渲染，**无需任何 DOM 节点引用/搬运/动画** |
| 宿主透传 | — | 新增**瞬态**协议消息 `narrate_withdraw`（不落盘、不入 processEvents），chatPanel 在 narrate 事件前发出 |
| 持久化 | 台账**完全未提及** | **必须同步扣除**：`Agent.consumeExecutionStream`（`agent.ts:650`）累积的正文若不含扣除，`Round.assistantMessage` 仍带叙述 → **重放时正文区照样出现**（本次真实会话数据的签名即"assistantMessage 开头就是叙述"） |

**六处改动**（内核 3 + 宿主 3，契约单一：`narrate.withdrawn`）：
- 内核：`managers/llmCaller.ts`（`LlmCallResult.streamedText` = 已逐字流式进正文的原文）/ `loop.ts`（narrate 内容改 `streamedText + pendingNarrate`，非空则附 `withdrawn`）/ `agent.ts`（持久化正文后缀扣除，不符则告警忽略、不误删）
- 宿主：`shared/protocol.ts`（`narrate_withdraw`）/ `panels/chatPanel.ts`（透传）/ `scripts/chatView.ts`（正文去后缀 + 重渲染）

## 三·补、A4 · 宿主回抽边界（✅ 已消解 · 前提证伪 2026-09-12）
原假设「正文区按 chunk 分节点保存引用；收到回抽事件时把前 N 个节点移入过程区 narrate 块」——**该假设不成立**：
宿主正文并非增量节点累积，而是 **`streamingRaw` 字符串全量重渲染**（`chatView.ts:2693`）。故回抽退化为「字符串去后缀 + 重渲染」，
无需节点引用、无需移动动画、与 `insertStepInOrder` 的 seq 排序天然兼容（narrate 事件本身带 seq，与工具行共用既有插入通道），
finalize/重放路径亦无需特判（重放读 `Round.assistantMessage`，已在持久化侧扣除）。**本项无残留工作。**
