## 二、目标类设计

### 2.1 新模块 `extension/host/confirmCoordinator.ts`

命名理由：域职责 = 注册回调 + FIFO 排队 + 推送审批卡 + 裁决应答 + 决策留痕 + 收卡，
横跨「队列」之外的四件事，`ConfirmQueue` 与 chatPanel 现字段 `_confirmQueue` 撞名且名不副实；
`ConfirmCoordinator`（协调器）准确。chatPanel 挂载字段名 `_confirm`。

```ts
import type { Agent } from '@zooique/memora';
import type { WriteConfirmationRequest } from '@zooique/memora';
import type { ExtensionToWebviewMessage } from '../../shared/protocol.js';
import { getToolDisplayName } from '../../webview/helpers/toolNameMap.js';

/** CONFIRM_TIMEOUT_MS / CONFIRM_TIMEOUT_NOTICE 原样搬迁（含风险分级 JSDoc） */
const CONFIRM_TIMEOUT_MS = 30 * 60 * 1000;
const CONFIRM_TIMEOUT_NOTICE = '用户未在时限内确认，已自动拒绝';

/** 协调器全部反向依赖（均由 chatPanel 构造时注入） */
export interface ConfirmDeps {
  /** 读最新 agent（getter：setAgent 会替换 _agent，禁快照） */
  getAgent: () => Agent | undefined;
  /** 消息投递单点（chatPanel 既有 this.post） */
  post: (msg: ExtensionToWebviewMessage) => void;
}

export class ConfirmCoordinator {
  private _pending = new Map<string, {
    resolve: (v: boolean) => void;
    timer: ReturnType<typeof setTimeout>;
    logLabel: string;
  }>();
  private _queue: Array<{
    info: Parameters<WriteConfirmationRequest>[0];
    resolve: (v: boolean) => void;
  }> = [];
  private _currentId: string | null = null;

  constructor(private readonly _deps: ConfirmDeps) {}

  /** 原 bindWriteConfirmation 整体搬迁（方法名保留） */
  bindWriteConfirmation(): void { /* this._agent → this._deps.getAgent() */ }
  /** 原 _pumpConfirmQueue 整体搬迁（this.post → this._deps.post） */
  private _pump(): void { /* 原样 */ }
  /** 原 _logDecision 整体搬迁 */
  private _logDecision(requestId: string, verdict: 'approved' | 'declined' | 'timeout'): void { /* 原样 */ }
  /** 原 _settleConfirm 整体搬迁 */
  private _settle(requestId: string): void { /* 原样 */ }
  /** 新出口：原 write_confirm_answer 分支体整体搬迁（get → resolve → logDecision → settle） */
  answer(requestId: string, approved: boolean): void { /* 原样 */ }
}
```

> **私有方法改名说明（`_pumpConfirmQueue` → `_pump` 等）**：本刀私有方法名带 `Confirm`
> 后缀进 `ConfirmCoordinator` 类即冗余（`this._confirm._pumpConfirmQueue()` 同词重复）。
> **这不是第 1 刀的「方法名零改名」反例**——第 1 刀保留原名是因方法名即域语义
> （`resolveActiveFile` 搬到 tracker 仍自明）；此处类名已承载域语义，去掉后缀是同词消歧。
> 影响面 = 类内部 3 个私有调用点 + 2 处 JSDoc 互引，**零外部零测试**触及（grep 实证：
> `_pumpConfirmQueue` / `_settleConfirm` / `_logDecision` 在测试中仅出现在注释文字里）。

### 2.3 常量注释的互引处理（SSOT 关键点）

`CONFIRM_TIMEOUT_MS` 与 `ASK_TIMEOUT_MS` 有一段**跨常量契约**（同为 30 分钟但终态相反、
禁合并——合并即 fail-open 安全模型反转）。处理原则：**契约叙述跟随真源走，另一侧留符号引用**：

- 287-301 的 CONFIRM JSDoc（含「与 ASK_TIMEOUT_MS 语义刻意不同」全段）→ **随迁**
- ASK_TIMEOUT_MS 的 JSDoc（271-285）中 281-283 的互引段 → 留在 chatPanel，
  但「详见下方 CONFIRM_TIMEOUT_MS 注释」改为符号引用：
  「详见 `confirmCoordinator.ts` 的 `CONFIRM_TIMEOUT_MS` 注释」
- `commentHygiene` 守卫只禁「文件.ts:行号」，符号引用合规 ✓

| §6.3「删 `_settle` 的 `_currentId !== requestId` 早退 ⇒ 迟到旧回执用例红」 | **实测不红** | 🔴 **该预期基于「单点防御」的错误假设**：实测证明 `answer` 的 pending 早退与 `_settle` 的 `_currentId` 早退**互为冗余**，单独移除任一道都是**等价变异**（0 红）；须**两发同时施加**才红（5c）。**不变量**（由赋值顺序保证）：`pending` 存在 ⇒ `_currentId` 必等于该 id（`_pump` 里先设 `_currentId` 再 `set` pending；`_settle` 里先 `delete` pending 再清 `_currentId`）⇒ 两道防线在同一可达路径上**永远只有一道会先拦住**，另一道永不触发。 |

**方法论沉淀**：变异验证的「预期红」本身也是**待验证的假设**，不是前提。§6.3 两条基于
「单点防御」的乐观预期在实测中被证伪（等价变异，0 红）——**若当时只跑一次变异就收工，
会把「测试没红」误读成「测试没守住」并据此加测试或改实现**（两者都属带伤：加无用测试 /
改已正确的实现）。正确处置 = 如实记录「等价变异」+ 设计**组合变异**证明不变量确实被守住。
