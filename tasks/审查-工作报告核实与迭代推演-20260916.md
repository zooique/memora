## 四、规则层判据缺口（比代码缺陷更值钱）

### G1 · 覆盖率阈值「谁是 SSOT」——本轮的理由自相矛盾 🔴

- `testing_rules.md:36` 自称：**「阈值与 `vitest.config.ts` 对齐，文档是配置的描述而非独立目标」** → 若此句成立，**config 才是 SSOT**。
- 但本轮把 config 的 83 改成 88，白纸黑字的理由是：
  > 「（该文档声明『文档是配置的描述而非独立目标』，**故以文档为准**）」——`vitest.config.ts:47-49`、`review-followups.txt:28-29`
- **这是把「自称非目标」的文字当作「以它为目标」的依据——引文与结论反向，理由不成立。**
- **结论（88）本身可辩护**（88 是 1.0 原始发布阈值，83 系 `99edf24c` 漂移，实测 92.35% 有 4.3 点缓冲）。**但理由必须换成自洽版本**：
  > 「88 是 `testing_rules.md` 声明的 1.0 发布阈值（原始意图）；config 的 83 系 `99edf24c` 漂移；实测 92.35% 证明余量充足 → **恢复原始意图**。」
- **通则（建议写进规则）**：规则与配置冲突时 **config 是判据 SSOT**（它才是机器执行的量）；改阈值属「**改判据**」动作，须带观测 + 退出条件（本轮这两条具备），**但理由不得引描述性文字自我授权**。

### G2 · 「僵尸声明」判据的层级未定义，且与 D4 冲突 🟡

- 本轮把 `pairingGuardFires` 出闸到 `AgentMetrics` 即判为**僵尸消缺**；
- 但 `emptyResponseCount` **早已出闸**（`loop.ts:2239`），宿主仍零消费，报告据此判定**不算僵尸**（「未兑现的只是宿主 UI 未展示」）；
- 而规则原文（`legacy-contract-audit-rules.md §3`）是**「派生字段零消费者」** → 按字面，宿主零消费者 **就是**僵尸。
- **两个判据不同源。** 需要的裁决：僵尸判据落在**内核导出层**还是**端到端消费层**？
- **建议口径**（与 D4 自洽）：**内核层出闸即算活**；宿主未消费归「宿主生长缺口」（D4：宿主有权不消费）→ 把这条层级写进 §3，否则下一位审查者会按字面把 `emptyResponseCount` 重判为僵尸（重复劳动）。

### B. 结构性问题（自然生长视角）

#### S1 · 门禁只解决了「跑没跑」，没解决「谁触发」= **所有权真空** 🟡（本轮最大结构性缺口）

- 现状（**已按本轮实测修正**）：门禁有**三条通道**——GitHub CI（触发被注释）、lefthook（**钩子已装且逻辑活着**：`.git/hooks/{pre-commit,pre-push,commit-msg,prepare-commit-msg}` 实存，`LEFTHOOK=0 → exit 0` 在 shim 第 7-9 行；空的只是 `lefthook.yml:33-36` 的 **pre-push 钩子体**）、`local-ci.mjs`（**无任何触发器**，`ci:local` 全仓仅命中 `package.json:49` 自身）。
  > ⚠️ 原文「三条都不通电」**表述不准**：pre-commit 是真在跑的（lint-staged + `tsc --noEmit`）；准确说法是「**触发已布线、pre-push 体为空、本地脚本无触发器**」。
- **自然生长判定（修正后）**：新增 `local-ci.mjs` 与 `kernel-ci.yml` **构成两份步骤清单**，这确实是上一轮引入的**既成并列**；但本轮修法**不必新增第四条通道**——正解是**往既有 pre-push 钩子体里填步骤**（`local-ci.mjs` 保持在唯一 SSOT，钩子只当触发器），这是嫁接。
- 但「恢复 GitHub CI 触发」已被作者否掉（Actions 报错烦人）→ **lefthook pre-push 是唯一既有挂载点**。
- **抗绕过（原论证已修正）**：原文称「全量 6.6 分钟必被绕过，因为他们的流程就带 `LEFTHOOK=0`」——**该前提不成立**。经复核，`LEFTHOOK=0` 的历史成因是**环境能力缺失**（`2026-09-10.md:275`：PowerShell 无法派生外部进程；`2026-08-08.md:331`：钩子在 PowerShell 下跑不了 sh 子进程），**不是怠惰**；而 `.git/hooks/pre-push` shim 活着，说明真实终端里钩子是能跑的。→ 靶心不是「防作者」，而是**两条提交路径（真实终端 / agent 沙箱）各自都要有 owner**。分层门禁的理由因此改为：**长默认路径本身是绕过诱因** + **fast 档能给出可归因的失败**（`vitest.config.ts:26` 自记跨文件 flake → 测试进 pre-commit 必出假红 → 假红直接诱发 `--no-verify`）。因此需要**分层门禁**：
  - **fast 档**（~30s）：`tsc --noEmit` + 改动文件的 eslint + **受影响的测试文件**；
  - **full 档**（~396s）：现 `ci:local` 全量，挂发版前 / 手动 / 可选 pre-push。
  - 判据：**fast 档必须有负面控制**（喂已知违规 → commit 真被拦），否则又是「有实现 ≠ 会跑」。

#### S2 · §7 自身正在成为它所要防的「僵尸声明」 🟡

- `legacy-contract-audit-rules.md §7` 现有 4 条待验证候选（规避行为红旗 / ADR-031 过度拦截 / 主流差距 / 会议空响应），每条都写「待真机复现后定类」。
- 但**「退出条件」是纸面承诺**：§6 有「已收敛清单」防重复劳动，**§7 没有任何复查节律**——登记了候选，却没有任何东西会消费这些登记。
- **这正是「僵尸声明：宣称能力却零消费」在规则层的复现**（登记 → 无人复查 → 长期悬空）。
- **最小修法（成本极低，ROI 高）**：§7 每条补「**登记日期 + 复查触发条件**」，并在既有节律（发版前检查清单）里加一行「§7 逐条复核：复现 / 收敛 / 降级 / 回退，四选一」。

#### S3 · 真机复验积压 = 3.0.0 的**真实关键路径**（4 项全卡在「重载 VS Code / 有真实会话」）

- 积压清单：SEARCH-1 S1+S2 · CTX-1b（148 次 read_file 复跑）· VERIFY-1（去方框真机）· FAIL-1 + 中断收场。
- **结构性观察**：每一次硬化都**必须配一次人工真机验收**，而验收动作没有工具化 → **验证债以「人工」为单位线性累积**，且越积越不敢发版。
- **自然生长解法**（拒绝造大 harness —— 那违反 D6 预支复杂度）→ **把已经手工做过一次的验证动作固化成脚本**：
  - 手工动作 A（**已发生过险情**）：核 dist 是否含新字段，靠搜**大写 hex** 转义串，日志里专门写了「勿误判为缺失」→ 固化为 `verify:dist-contract`（断言内核 `.d.ts` + 宿主 bundle 含必备标记），可作 `ci:local` 第 9 步。**把一次险情变成一条机器断言。**
  - 手工动作 B：SEARCH-1 的三类行为（大文件前段可命中 / 后段缺口上报 / 不可读不静默）——宿主单测**已覆盖 5 例**，缺的只是「**经 bundle 的真实链路**」；补一个加载 bundle 的冒烟断言，即可把「重载 VS Code 手点」降级为「跑一条命令」。**嫁接既有单测，不另起炉灶。**
