# 2026-08-09

## SSOT / 设计闭环审查（会话状态机 · 检查点 · 记忆分类 · 不中断工作模型）

对 4 个子系统做了 grep 实证审查（非阅读印象），核心实锤发现如下，均已定位到行号：

### 检查点持久化断链（最高优先级）
- `persistCheckpoint()` 全仓仅 **2 个调用点**：`createCheckpoint()` 末尾（sessionManager.ts:356）与 `resume()`（:597）。
- 高频写点 `completeRound` / `logToolExecution` / `updateGoal` / `appendPlanStep` / `updateRole|Standard|Resource` / `recover` / `setPauseMeta` / `heartbeat` **全部只写内存**。running 中崩溃 → 磁盘停留在上次 pause 快照。
- `createCheckpoint()`（:332-353）用**对象字面量重建** checkpoint，未复制 `roundLog` / `completedToolCalls` / `pauseMeta` → 每次 pause 都清空这三个侧车字段。
  - 连锁：outbox 去重（hasToolExecuted）失效、P3.4 `compensateAllNonIdempotent()` 恢复时恒返回空、任务表回合历史归零。
- `recover()`（:707-728）改 `checkpoint.status='running'` 但**不 persist** → 磁盘仍是 error，重启回退。

### 状态机三态实为两态
- `triggerError()` 在生产代码中**无内部调用者**（仅公开 API + 从检查点回填）。loop 异常走 `yield {type:'error'}`，不翻状态机 → ERROR 态、`recover()` 校验、processEvent 的 error 守卫全是死路径。

### 申请暂停两阶段协议半闭环
- `phase:'requesting'` **零写入点**，`shouldPauseAtBoundary()` **零调用点** → 该方法恒 false，是死代码。
- 真实暂停边界判断走 `loop.pauseRequested` 布尔（loop.ts:373）→ 事实真理源在 loop，`checkpoint.pauseMeta` 只是滞后镜像（onPaused 回调写 suspended，随即被 pause→createCheckpoint 抹除）。
- `resume()` 不清 pauseMeta（仅 `abandonPause` 清），残留 suspended 与 running 态矛盾。

### 暂停超时「生产→消费」遗漏路径
- `loadPersistedCheckpoint()` 超时路径填充 `_pauseTimedOutSession`（:417）；**运行时定时器路径 `checkPauseTimeout()`（:1238-1267）不填充** → 运行中超时的会话不会触发内容归档，只发事件。
- 另：`_pauseTimedOutSession` 仅在 `sessionId.split('-').length>=4` 时赋值，格式不符则静默丢失。

### goalVersion 是 write-only 字段
- 全仓（含宿主）无任何校验消费者，只在 `createCheckpoint` 自保留 + emit 负载中出现。
- `applyResolvedDelta`（agent.ts:1595）对 **P2 延续值也调 updateGoal** → goalVersion 每轮 chat 递增，退化为轮次计数器；且 currentGoal 一旦偏离 mainGoal，之后每轮都重复 emit `goalDriftDetected`。

### 记忆双轨一致性
- Rule 的 dual-source 在宿主层是**正确排序**：`sprite.saveConfigFile/deleteConfigFile` 先写/删文件（真理源）再 `configFileSyncer.sync` 同步 SQLite，失败仅记日志、重启由 MemoryLoader 自愈。风险仅在内核 API `agent.config.deleteRule/updateRule` 被直接调用时（不动文件 → 重启复活）。
- 关系侧车无统一守门人：`memoryInspector.deleteMemory`（:664）与 `purgeExpired`（:742）会清关系边，但 `userProfile.ts:273/385` **直接 index.delete 绕过** → 孤儿边。`ConfigManager` 的 `removeRelationsByMemoryId` 是可选注入。
- `autoConfigRefiner` 生成建议时不查已有同名/矛盾 rule，`confirmConfigSuggestion` 用 `id=source:name` 直接 upsert 覆盖 → 「血肉结晶为骨骼」路径无一致性校验。

### 常量基线
PAUSE_TIMEOUT_MS=30min · 检测间隔 30s · 连续暂停衰减窗口 1h · 阈值 2 · HOT_MEMORY_MAX_ROUNDS=20 · CONTENT_SLICE=500。

### 结论优先级
P0 检查点落盘 + 侧车字段保留（改 createCheckpoint 为增量更新而非重建）；P1 pauseMeta/loop.pauseRequested 单一真理源收口；P1 checkPauseTimeout 补 `_pauseTimedOutSession`；P2 goalVersion 要么接校验消费者要么删除；P2 记忆删除统一走 memoryInspector 守门人；P3 ERROR 态要么接线要么删。

## 排雷复核（对上述结论的对抗式验证）

产出 `tasks/SSOT排雷与迭代方案-20260809.md`（排雷矩阵 + P0-P3 迭代任务）。10 条结论中 **9 条确认、1 条修正**：

### 【修正】pauseMeta 不是死代码 —— 初审误判
- **消费方真实存在于宿主关键路径**：`hosts/.../main.ts:579-580` 读 `pauseMeta?.reason/source`；`ipc/chatHandlers.ts:194-202` 读 `phase/reason/source` 下发渲染层；`panels/taskTablePanelManager.ts:307` 有 `ctx.pausePhase === 'requesting'` 分支。
- **死的只是相位取值**：`setPauseMeta` 唯一生产写入点 `agent.ts:1783` 硬编码 `phase:'suspended'`，`'requesting'` 从未写入。
- 由此推出**跨层死分支**：内核 `shouldPauseAtBoundary()` 恒 false + 零调用（双重死代码）；宿主 `'requesting'` UI 分支永不可达。
- **判据升级**：这不是「死字段」而是**契约与实现不一致**——`types.ts:303` 的联合类型承诺两阶段，实现只兑现一半，宿主按契约写了 UI。比死代码危险，因为它会持续误导下游。
- 教训：**判定死代码必须跨宿主边界 grep**，只搜 `src/` 会把「跨层活字段」误判为死。

### 【精确化】createCheckpoint 是白名单式重建，非全量丢失
- `:332-353` 显式复用 mainGoal/currentGoal/goalVersion/plan/role/standard/resource（:329-330 还专门取了 existingGoal/existingGoalVersion），**只遗漏** `roundLog`/`completedToolCalls`/`pauseMeta`。
- 根因表述应为：**对象字面量重建 = 隐式白名单**，新增字段默认丢失。合并语义（`{...this.checkpoint, ...patch}`）才是快照的正解。

### 【新增】P0 缺陷链完整时序（可复现，有真实副作用）
`pause()`（:540）→ ①状态翻 PAUSED → ②`createCheckpoint()`（:544）清三字段 → ③`persistCheckpoint()`(:356) 残缺快照落盘 → ④`loop.onPaused`（agent.ts:1780-1789）补写 pauseMeta 但 `setPauseMeta`（:932-936）**只写内存不落盘**。
净结果：pauseMeta 内存得救/磁盘永失（宿主回落兜底文案）；completedToolCalls 与 roundLog 内存磁盘双失 → `hasToolExecuted`(agent.ts:1734) 恒 false → **非幂等工具重复执行** + P3.4 补偿空转。

### 【新增】测试盲区是同级根因
`uninterruptedWorkflow.test.ts:494-495` 在 completeRound 后**直接**断言 roundLog（不经 pause 往返）；`:867` completedToolCalls 是手工 fixture、`:1507` 仅查询。
→ 测试验证了「字段能写」，从未验证「字段能活过一次 pause」。**断言点与真实生命周期不对齐**，这是缺陷长期存活的结构性原因。防回归手段：按字段参数化的检查点生命周期测试套件。

### 【加重】goalDriftDetected 零监听方
宿主 `hosts/memora-sprite/src` 对 `goalVersion` **零引用**；`goalDriftDetected` 全仓只有 emit（`sessionManager.ts:762`）+ 定义（`eventEmitter.ts:41/175`），**无任何 `.on()`**。生产→消费闭环完全断裂。

### 【确认】其余
triggerError 生产零内部调用（含宿主）· recover() 全程无 persist（:714/719/720 改内存后直接 emit）· userProfile.ts:271-273/385-388 直接 index.delete 绕过 removeRelationsByMemoryId（接口 relationStore.ts:99 / 实现 inMemoryRelationStore.ts:98）· 运行时超时不填 _pauseTimedOutSession。

## P0 组落地（T0-1 / T0-2 / T0-3 + T3-1）

改动集中在 `src/agent/managers/sessionManager.ts`，新增 `src/agent/managers/__tests__/sessionCheckpointLifecycle.test.ts`。

### 落地要点
- **T0-1 合并语义**：`createCheckpoint` 改为 `{ ...(prev ?? {}), ...重算字段 }`。仅 sessionId/status/error/mainGoal/currentGoal/goalVersion/plan/role/standard/resource/hotMemory/truncatedCount/lastHeartbeat 显式覆写，侧车字段自动继承。已在源码写下「禁止改回对象字面量整体重建」的原因注释。
- **T0-2 落盘收口**：新增 `checkpointDirty` 脏标记 + `touchCheckpoint()`（心跳唯一写点，置脏）+ `flushCheckpoint(force?)`（落盘唯一入口）。11 处裸 `lastHeartbeat = Date.now()` 全部收口。
- **T0-3**：`recover()` 补 `touchCheckpoint()` + `flushCheckpoint()`；`error.recovered = true` 处也标脏。
- **删并列真理源**：`triggerError()` 内手工赋 `status='error'` + `error={...}` 已删——状态机先行置位，`createCheckpoint()` 会从状态机投影。

### 对原方案的实施期修正（重要）
方案 T0-2 原写「pause/resume/recover/回合边界四个边界 flush」，实施时判定**不足**：
- `logToolExecution` / `recordSideEffect` **必须立即 flush**，不可延迟到回合边界。outbox 的前提是「执行事实先于崩溃被持久化」；单回合含多次工具调用，回合中途崩溃即丢记录 → `hasToolExecuted` 恒 false → 非幂等工具重复执行。
- `setPauseMeta` 必须 flush：它由 `loop.onPaused` 在 pause() **之后**回调，是 pauseMeta 进入检查点的唯一时机，不落盘则磁盘永远无此字段。
- `updateGoal` 也 flush（目标是会话语义骨架）。
- 写盘失败时**保留脏标记**，下个边界自动重试；无 sessionStore 时清脏降级内存模式。
- `checkpoint = null` 的两处（loadPersistedCheckpoint 超时、checkPauseTimeout）同步清脏。

### 测试有效性自检（方法论）
新测试 12 条全绿后**必须做变异验证**：临时注释掉 `...(prev ?? {})` 重跑 → **6 条失败**（含结构性守卫与 outbox 端到端），证明测试真能抓住原缺陷，非假绿。恢复后复绿。
- **结构性守卫写法**（可复用）：`Object.keys(cp).sort()` 在 pause 前后比对相等。不枚举字段名 → 将来新增检查点字段无需改测试即自动获得保护。
- **假磁盘 store**：`saveCheckpoint` 真存 Map + `readDisk()` 反序列化，用于断言**磁盘态**。只断言内存态无法区分「内存里有」与「崩溃后还在」——这正是原测试失效的根因。

### 踩坑
- **Python 批量替换会改行尾**：`io.open(p,encoding=...)` 读入把 CRLF 转 LF，`newline=''` 写出即 LF，整文件行尾被改（仓库为 CRLF，core.autocrlf=true）。必须改回并核验 `bare-LF: 0`。批量改 .ts 后务必检查行尾。
- 子串替换 4 空格模式会命中 6 空格缩进行，但前导空格保留在外，缩进结果仍正确（需逐处 grep 复核）。
- `touchCheckpoint()` 自身的赋值行须先加尾注释区分，否则批量替换会把它改成自递归。
- **vitest 不做类型检查**（esbuild）：`ToolExecutionRecord` 写错字段名 `idempotency`（实为 `idempotent`，且缺必填 `resultSummary`/`ok`）测试仍全绿，靠 `tsc --noEmit` 才暴露。测试绿 ≠ 类型对。

### 全量回归定性（收尾门）—— 4+2 失败均为既有 flaky，非 P0 逻辑回归
- 全量 `npx vitest run` 两次结果**失败集不稳定**：
  - 第 1 次（1914）：`agent.test`×2（snapshot 区块 `beforeEach`/`afterEach` Hook 超时 10s）、`loop.test`×1（`并发` 测试 436ms>250ms 墙钟断言）、`uninterruptedWorkflow`×1（resume 区块 Hook 超时 10s）。
  - 第 2 次（1914）：仅 `uninterruptedWorkflow`×2（resume 应恢复/未初始化 pause 应抛错），错误均为 `afterEach`（:1128 `agent.close()`+3×rmSync）`Hook timed out in 10000ms`。
- **对抗式判据**：① 跨次失败集不同（run1 的 loop/agent 失败 run2 不复现，run2 是不同 uwf 用例）→ 环境抖动非确定性；② 全部为 Hook 超时/墙钟断言，**零数据断言失败**；③ `loop.test` 与 P0 **证明正交**——`src/agent/loop.ts` 对 `sessionManager`/`completeRound`/`logToolExecution`/`flushCheckpoint` 零引用，且失败测试用 `new AgentLoop({provider,bootstrapMemories,toolExecutor})` 构造、不含任何 session manager。
- 结论：这些失败是**全量并行套件下磁盘/CPU 争用**导致的既有 CI flaky（真实磁盘 store + tmpdir 在 ~80 并行文件下变慢），与 P0 改动无关。定向门（tsc=0 / eslint=0 / checkpoint 测试 69 全绿）全过即标志 P0 组关闭。
