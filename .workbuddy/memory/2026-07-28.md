## 方案A（Gitee Release 极简更新）可行性评审
- 用户提出 sprite 用 Gitee Release（tag 前缀 `desktop-v`）+ axios 手动比对、跳过 electron-updater 的极简更新方案。聚焦 sprite 做对抗式核查。
- **结论：方向可行（对个人/闭源单仓库合理），但所给代码有 8 处缺陷需修正，且「内核/客户端两层更新隔离」是错觉。**
- P0 实测确证：`if(remoteVer > localVer)` 用字符串比较 → `"0.10.0">"0.9.0"`=false（漏报）、`"1.2.0">"1.10.0"`=true（误报）。必须用 semver 比较或自写数值比较器。
- P0 设计错觉：内核打进 asar 随客户端冻结，checkCoreUpdate 只弹「通知」不真正送达——端用户要拿到内核更新仍需重打包 exe。故「改内核无需打包桌面」仅对开发者发版流程成立，对终端用户不成立。
- P0 私有仓库矛盾：分布式 exe 无 GITEE_TOKEN → 调私有仓库 `/releases` API 必然 401/403，端用户检查更新失效。「闭源友好」仅指源码私有，更新检查对私有仓库端用户需另设公开元信息端点或嵌入只读 deploy token。
- P1 脆弱假设：`desktopReleases[0]` 依赖 Gitee 返回倒序（须实测）；分页 >30 release 时最新 desktop-v 可能掉出首页；`assets[0]` 不一定是 exe（sprite 同时产 nsis+zip）→ 应按 `.exe$` 选资产。
- P1 与 sprite 现状冲突：sprite 已有 main.ts/preload.ts 且 Electron 40 默认 `contextIsolation` → `window.require('electron')` 必然 undefined；方案A 的 main.js 片段既不建 BrowserWindow 也未接现有 main.ts，且 `require('@xxx/agent-core/package.json')` 会被内核「仅暴露 .」子路径拦截（ERR_PACKAGE_PATH_NOT_EXPORTED）。须改 preload+contextBridge 桥接、用 fs 读 `require.resolve('memora')` 同目录 package.json 取版本。
- 建议：修正 semver 比较与资产选择；更新逻辑挂进现有 main.ts（不替换）；内核版本经 contextBridge 暴露；私有仓库走「公开元信息镜像」或只读 token；若内核真要免重装，须改为运行期加载内核（与「极简/闭源」初衷相悖，需权衡）。
- **文档落地**：上述结论已回写 `tasks/发布流程-gitee-20260722.md` §5（修三坑：Gitee 无 /latest→列表+desktop-v 前缀+created_at 倒序+per_page=100；版本用数值比较器；资产按 .exe$ 选；内核层"只通知不送达"illusion 标注；sprite ESM 用 app.getVersion()/require.resolve 读内核版本；零新增 IPC 红线）+ §4 tag 约定改为 `desktop-v{a.b.c}` + 顶部更新标记；同步 `tasks/STEP-发版前置-PRIVACY与更新检查.md` STEP-3.4 指向修正后梯度 B。

## 决策：130MB exe → 弃 Gitee 托管，走对象存储极简闭环（2026-07-28）
- 用户澄清真实需求：打包 ~130MB exe 传到可下载服务器 + 客户端"检测版本"按钮 + 有新版打开下载页。即极简更新闭环。
- 联网核实硬证据：Gitee 官方配额 **发行版单附件 100MB 上限**（社区版/企业标准版均 100MB，GVP 200MB），用户 130MB **超限、无法作为发行版附件**→ Gitee 托管 exe 不可行（LFS 不救发行版附件）。
- 用户选定下载服务器：**对象存储 COS/OSS/R2**（公开读）。据此重写两份文档：
  - 主文档 §1/§4/§5 翻转：路线 A（Gitee）降级为"仅反馈 Issues"，路线 B（对象存储）升为推荐；§5 梯度 B 改为 `version.json`(version+page+notes) + 主进程 fetch + 数值比较 + 有新版才 `shell.openExternal(page)`，删去 Gitee 列表/tag 过滤/资产选择复杂度；version.json 示例由 downloadUrl 改为 page；补 artifactName 建议。
  - STEP 卡同步：默认路线 B、占位符表/STEP-3.3/3.4/5.2 的 Gitee 托管表述全部改为对象存储落地页；CORS 约束改为"主进程 fetch 对象存储"。
- 保留的有效架构注意：内核打进 asar 随客户端冻结→"两层更新隔离是错觉"仍成立（端用户拿内核更新仍需重装 exe）；sprite「零新增 IPC 通道」红线仍守。
- 结论：Gitee 方案对 130MB 不可行；对象存储 + version.json + 开页按钮 这个极简闭环完全满足用户需求，比原方案更简单。
