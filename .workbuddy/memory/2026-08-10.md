## T1-1（F4-1）暂停双副本收口 · 已完成（提交待办）

- **根因**：`_pendingPauseReason`（Agent 侧）与 `loop.pauseRequested`（loop 侧）双副本，清理路径不对称。空闲态（无活跃流）调用 `requestPause` 时：置位 `_pendingPauseReason` + `loop.pauseRequested=true`，但无 stream 运行 → `consumeExecutionStream` 的 finally 永不到达 → 状态机不翻 PAUSED、且 `_pendingPauseReason` 永驻 → 幂等锁死（再点暂停被拒，按钮失灵）。
- **方案对抗式修正（关键）**：方案「彻底修复」提议 `_pendingPauseReason` 改为「向 loop 单向查询」，但 `loop.pauseRequested` 是**布尔值、不携带 reason 字符串**——照搬会丢失暂停原因（regression）。故判定**最小修复为正确解**（恰好也契合 SSOT/复杂度守恒）。
- **判据信号对抗式修正**：方案未指定「无活跃流」判定信号。核实发现 `chatLockManager.isBusy` **只在 `chat()` 内为 true**，`resumeExecution`/`processEvent`（agent 级）根本不 acquire 锁 → 用 `isBusy` 会在续跑时误判、破坏延迟翻转。改用**单一 funnel 标志 `_streamActive`**：仅 `consumeExecutionStream` 入口置 true、finally 清 false（chat/processEvent/resumeExecution 都 `yield*` 它，单一真理源，不与 chatLock 语义耦合）。
- **修复**：`requestPause` 在状态机守卫后、`_pendingPauseReason` 幂等检查前加：
  ```ts
  if (!this._streamActive) { this.pause(reason, source); return true; }
  ```
  无流时直接同步翻状态机（无工具可延迟挂起，是延迟翻转的正当例外），不产生悬挂副本。
- **防回归测试**（uninterruptedWorkflow `pause / resume` describe）：空闲态 `requestPause` → status 翻 PAUSED + `_pendingPauseReason` undefined；abandonPause 后再次暂停仍生效。
- **变异验证（有牙）**：中和空闲同步暂停块 → 测试精确转红（`expected 'running' to be 'paused'`），还原复绿。
