## 发布 vs 功能 的推进顺序决策
- 用户问："先把发布路线跑通，再更新内部功能？"
- 结论（第一性原理 + 对抗式）：大体对，但须修正——不要"全部发布卫生 → 再全部功能"的硬切割。
- 正确切法：第一版可发构建 = (a) 最小发布卫生 P0（GitHub Releases 分发 + 手动更新检查 + 本地错误日志 + 隐私白皮书 + Win 包）**叠加** (b) 唯一卡首印象的功能 A1 冷启动召回。两者一起进首个真用户构建。
- 明确推迟到验证后：养成脊柱 B1/B2/B3、主动引擎、persona 影响回复——这些等真实遥测(激活/采纳/7日留存)回来再按数据投。
- 两个失败模式须规避：① 发布卫生无限 yak-shave（签名/公证/auto-updater 完美主义）导致永不发版；② 跳过 A1 直接发导致首印象崩、前提(R1)被污染。
- 一句话：先"能发 + 首印象不崩"，再"靠真数据深化功能"，而非"先全发完再碰功能"。

## 设定中枢模块提案（用户新想法）
- 用户提议：把角色(persona)/规则(rule)/技能(skill)三系统整合为一个独立管理模块，左侧边栏加入口，加上自动记录的记忆=4板块。
- 已代码核实可行性（高）：
  - 内核 `persona/rule/skill` 是三个独立 source，且 `DEFAULT_RECALL_EXCLUDE_SOURCES=['persona','rule','skill']`（bootstrap 注入、不召回）→ 与用户"3独立+自动记忆"直觉一致。
  - 左侧栏是 `.nav-btn[data-panel]` 标准模式（现 chat/memories/clipboard/settings 4个），`PanelRouter` 对任意 panel 通用 → 加第5入口零改造。
  - skills 目前只是设置面板内一个 tab(`renderSkills`)，persona/rule 无 UI（仅 `cfg-default-persona` 填名）→ persona/rule 编辑是真实缺口。
  - 内核已有 `reloadConfig('persona'|'rule'|'skill')` + `getBySource` + 现成 `memoryController` IPC → 新模块主要是渲染层，新内核代码极少。
- 我的建议（对抗式+先发原则）：**设计为 fast-follow v1.1，不阻塞首版 P0**。它是 power-user 管理面，新用户首日不会打开；且注意：第4板块"记忆"勿与现有 `memories` 面板重复（复用/链接而非新建浏览器）；模块内避免4板块全做富编辑器（MVP 先用 list+启用/禁用+删除+应用 reloadConfig，富编辑延后）。
