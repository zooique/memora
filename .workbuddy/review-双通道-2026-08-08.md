## 二、三块「已落地」真实性判定

### ✅ 块1 · 输入不冻结（processEvent + chat 双入口守卫）
- `agent.ts` L815-824（`processEvent`）/ L384-391（`chat`）：`error`→抛错拒绝；`paused && event.type!=='command'`→`this.resume()` 自动恢复 + 继续。
- 幂等性：守卫仅在 `status==='paused'` 时调用 `resume()`；RUNNING 态调用 `sessionManager.resume()` 为 no-op（状态机拒绝 + 返回 false，无副作用）。✅ 正确。

### ✅ 块2 · 暂停中断流式（SESSION_PAUSE + chatStreamHandler 清理）
- `chatHandlers.ts` L88-108：先 `ctrl.abort(AbortError)` 再 `agent.pause()`，成功则推 `SESSION_STATUS_CHANGED{paused}`。
- `loop.ts`：LLM 中断时若已有文本则 `history.appendAssistant(content + interrupted)`（保留已生成文本 + `[已中断]` 标记）。
- `chatStreamHandler.ts`：`for await` 响应 signal 退出 → `finally` 统一发 `SPRITE_STREAM_END` + `setAbortController(null)` + 释放 chat lock + 托盘回 idle。
- **SPRITE_STREAM_ABORTED/END 时序、已生成文本保留、chat lock 释放、状态机与 isStreaming 一致性**：均正确。✅

### ⚠️ 块3 · 暂停中注入自动继续（auto-resume）—— 内核可用，渲染层状态断裂（见 Finding B）

## 三、具体不一致发现

### 🔴 Finding B（高优 · UI 状态不一致）：auto-resume 不推送渲染层状态翻转
- **证据链**：
  - `processEvent`/`chat` 守卫在 PAUSED 时直接调 `this.resume()`（agent.ts L822 / L389），`sessionManager.resume()` 发射内核事件 `sessionResumed`（sessionManager.ts L582）。
  - 渲染层**只**订阅 `SESSION_STATUS_CHANGED` IPC（preload.ts L1377 → ipcListeners.ts L1131 → ui.ts `onSessionStatusChanged` L678）。
  - `SESSION_STATUS_CHANGED{running}` **仅**由 `chatHandlers.SESSION_RESUME` / `SESSION_RECOVER` IPC 发出（chatHandlers.ts L118 / L134），即只有用户显式点「恢复」按钮时。
  - grep 全 `hosts/`：**无任何代码把内核 `sessionResumed` 转发为 `SESSION_STATUS_CHANGED`**。
- **后果**：用户暂停（徽标「已暂停」）→ 在暂停态发消息（auto-resume 内核已 RUNNING）→ LLM 流式输出，但**徽标一直停在「已暂停」**；此时点「恢复」按钮 → `agent.resume()` 因已 RUNNING 返回 false → 无 IPC → 按钮无反应。UI 与实际会话态不一致。
- **修复方向（后续阶段，非本次）**：主进程增加 `agent.on('sessionResumed', ...)` 订阅，转发 `SESSION_STATUS_CHANGED{status:'running'}`；或在 `processEvent`/`chat` 守卫 auto-resume 成功后经注入回调推状态。改动小、封闭。

### 🟠 Finding A（中优 · 超时暂停被忽略返回值的边界）：超时暂停后注入，仍以 PAUSED + 陈旧 checkpoint 继续
- **证据链**：
  - 守卫 `if (status === 'paused' && ...) this.resume();` **未检查返回值**（agent.ts L822 / L389）。
  - `sessionManager.resume()` 在 `isPauseTimedOut` 时返回 `false`、发射 `sessionResumeBlocked`、状态机与 checkpoint 保持 PAUSED（sessionManager.ts L555-567）。
  - 守卫忽略 false → `processEvent` 继续 `acquireChatLock` 并跑 LLM，**会话仍是 PAUSED、checkpoint 仍带陈旧 goal/heartbeat**。
- **后果**：应用内（未重启）暂停 >30min 后用户发消息，新消息被当作「已死暂停目标」的延续，与设计「超时=归档+视为新会话」相悖；并叠加 Finding B 的徽标卡死。
- **可达性**：仅「不重启、暂停超 30min」场景；重启路径 `loadPersistedCheckpoint` 已正确删除超时 checkpoint 并归档（无此问题）。
- **修复方向（后续）**：守卫改为 `if (this.resume() === false) { /* 超时：清陈旧 checkpoint、以新会话态 RUNNING 继续（新消息即新 goal）*/ }`。

### 🟡 Finding C（设计权衡 · 供 P4 参考）：clarify 回答不回写结构化槽位
- **证据链**：`SESSION_CLARIFY_ANSWER` → `processEvent({type:'clarify', content: JSON})`。compose 时 `event.type!=='chat'` → 走 `resolveStalledTaskSlot`/`resolveSlot`（composer.ts L84-94），`delta={}` → 从 checkpoint/P3 默认值补全，**不解析 JSON 回答**；`applyResolvedDelta` 应用的是这套（不含用户回答）；随后 L912 才把 `event` 转 chat（`formatClarifyAnswers` 把 JSON 转可读文本）喂给 LLM。
- **后果**：role/task/standard/resource 结构化槽位不会被澄清回答更新，仍保留先前/空/默认值。属「语义判断归 LLM」的既定设计，但意味着后续 P4 的 `goalVersion` 防漂移校验**不能依赖结构化槽位反映澄清意图**。
- **处理**：记入 P4 待办，与 goalVersion 工作一并处理（可选：clarify→chat 转换后跑一次 `resolveChatTaskSlot` 回写）。

### 🟢 Finding D（良性 · 已正确防护）：PAUSED→流式退出的竞态
- `chatStreamHandler.handleUserInput` 在 AbortController 仍占用时拒绝新输入（「上一条消息仍在处理中」）。SESSION_PAUSE 的 abort 与 `setAbortController(null)`（在 finally）之间存在窗口，但新输入在窗口内被 IPC 层拦截，不会并发 auto-resume。✅ 正确。

### 🟡 Finding E（测试稳定性 · 非逻辑缺陷）：满负载下 `afterEach agent.close()` 钩子超时
- 全量 `src/agent/`（991）出现 4 失败，根因 `Error: Hook timed out in 10000ms` @ `uninterruptedWorkflow.test.ts:1126` `await agent.close()`；该文件**孤立运行 93/93 通过**。
- 指向 `agent.close()`（或待归档 Promise / decay 定时器）在满套件负载下 10s 内未能 settle。
- **建议（非本次）**：测试侧加固 `afterEach`（强制 close / 缩短调度器生命周期 / 提高 hookTimeout），不影响双通道功能正确性。

## 四、确认为「已落地且正确」的细节（对抗复核通过）
- `composer.resolveChatTaskSlot`（composer.ts L82-94 / L272-287）：chat 事件**永不触发 P4**——content 即任务，有 goal 则 P2 延续、无 goal 则 content 为初始目标。✅
- `resolveStalledTaskSlot`：仅在**非 chat 且计划停滞**时触发 P4（计划完成问下一步方向）。✅ 与「chat 不 P4」边界一致。
- 状态机 `onEvent` 当前 no-op（转换由调用方显式触发），注释明确。✅
- `RESTORE_CHECKPOINT` IPC 已定义但**渲染层无人调用**——与 2026-08-08 日志一致，属已知缺口，归 P2。✅ 确认。
