## 四、三个口径的排雷

### 口径一：SSOT

**结论 1：`dispatchedBy` 会被加第二职责，而且它根本不在「本轮」。方案的第一步按原文不成立。**

- 写入点只有一个方向：派发/新建受理时，把归属写进**目标会话新轮**——`hostedDispatchRun.ts:305-314`（`dispatchedBy: { from: callingSessionId, via: 'delegate' }`）、`hostedSessionCreate.ts:145`（`via: 'create'`），内核侧落到 `Round` 上（`src/agent/messageHistory.ts:434-437`，注释：「谁派来、是派发还是新建」）。
- 盘上实证：27 轮里只有 6 轮带 `dispatchedBy`，全部是目标会话的轮；编排会话 `2026-11-20-smwoltgwj` 的 17 轮**一条都没有**。
- 反例（同一份数据，不是假设）：`18a903bd` 真的派了活、`8468e0ad` 带 `dispatchedBy`，但 `18a903bd` 本身没有 `dispatchedBy`。只要那句真话写成 `ab4125bc` 那种「已派给」措辞（同一会话、同一件事，只差一个字），「查本轮」的判据就会把**真派活**判成空承诺。
- 仓库已经对这件事做过决定：`hostedDispatchRun.ts:316-318` 原文——

```ts
// 盖章统一 = 助手身份名（2026-11-20 拍板）：不再按来源会话取名——`Round.dispatchedBy`
// 仍是纯数据（数据层有归属价值），但不参与任何上屏文案，避免同一事实两个名字源。
```

把它接到「未兑现」文案上，直接推翻这条既有约定。**所以这一条不是「加职责」，是违反已经写明的数据边界。**

**结论 2：词表是第二份「什么叫做完了」的判据，而且与既有三判据是并列，不是嫁接。**

- `status: complete` 回答「收敛」，`metrics.success` 回答「无执行失败」，词表回答「文本像不像完成」。三者没有派生关系，是并列的新轴。
- 只要 UI 把它的结果呈现成「空承诺 / 没做成」，用户就会把它读成第四个完成判据——**违 SSOT**。
- 唯一能保留的读法是把它当「证据缺口提示」，措辞只能是「本轮未核到会话派发回执」，不能是「未完成 / 失败 / 没做」。两者是**事实层**与**定性层**的区别。

**结论 3：「解释权归宿主」在状态层已经成立，在正文层不成立。**

- 卡片的存在性/名字本来就只由宿主快照产生（`protocol.ts:1512-1521`），模型正文从来不是状态源。
- 但「已派给 X」这句话是**模型正文**。要在正文层收权，只能拦截或改写模型输出——改终态正文属于带伤，方案自己也说「不改助手原文」。
- 所以「更狠的那条」最多只能做到：**UI 里任何「已派」状态只能由宿主回执产生**（已经是这样），不能做到「正文里不许出现这句话」。若硬做，会出现第三个真相：正文说派了、宿主说没回执、`Round.status` 说完成。

### 口径二：自然生长

**结论 4：方案不是嫁接，是另起一条「文本语义判据」的新链；但有一条既有链路可以承接。**

- 正确的「本轮事实」已经存在：本轮 `processEvents` 里 `send_to_session` / `create_session` 的**成功回执**。`processEventText.ts:268-296` 的 `dispatchedSidTextsFromEvents` 已经在做「tool_start 配对 tool_result」的解析，卡片也在用它（`dispatchCardProjection.ts:68`）。**这是同一份事实的第二消费者，不是新机制。**
- 但要注意它现在的判据有已知缺口：只读内核 `payload.ok`（`processEventText.ts:287`），而内核 `ok = outcome.status === 'ok'`（`src/agent/loop.ts:2581`），工具正常返回 `{"ok":false,"code":"E_BUSY"}` 时内核仍记 `ok=true`。所以复用它之前，必须补读 `summary` 里的业务 `ok`——否则「派发失败」会被当成「有回执」。
- 最省的读法确实存在：**不新增数据**，只在轮收场时读一次本轮事件；是否上屏是另一个决定（v2 选择了上屏，见 §六）。不需要 `dispatchedBy`，也不需要新字段。
- 反过来问「既有机制是否已覆盖、只是没接上」：**没有完整覆盖**。卡片有宿主真源，纪律句有文本，但没有任何消费者把「终态文本」与「本轮回执」放在一起看。缺的是消费者，不是数据。

### 口径三：不带伤（含反例与实证统计）

**实证统计（`E:\ceshi\.memora` 全量 27 轮，逐轮读 `assistantMessage.content`）**

五词表 `已派|已安排|已完成|已发送|已交给`：

| 指标 | 数值 |
| --- | --- |
| 总轮数 | 27 |
| 命中轮数 | 7（25.9%） |
| 其中 `已完成` | 6 |
| 其中 `已派` | 1（`ab4125bc`） |
| `已安排` / `已发送` / `已交给` | 0 |
| 命中轮中本轮带 `dispatchedBy` | 0 |
| 按原方案会标「空承诺」 | 7 |
| 真正该标的 | 1（`ab4125bc`） |
| **误伤** | **6（85.7%）** |

6 条误伤的具体形态：

- 4 条是「已完成，两个文件各追加几个字……」（`e281a0c2` / `b8907aca` / `01d629dc` / `576989ac`），本轮有 8–16 次 `write_file` / `read_file` / `task_table_*`，是**真做了事**；
- 1 条是「追问已完成，它交付的自我介绍要点是……」（`a20d6e31`），本轮有 4 次工具（含 `send_to_session`）；
- 1 条是「那条会话状态为已完成」（`4b004110`），`已完成` 在这里是**描述目标会话的状态**，不是本轮承诺。

**漏报（词表覆盖缺口）**：`18a903bd` 的真派活原文是「任务已受理并派给小说会话」——五词表**一个都不命中**（没有「已派」这个连续子串）。把词表放宽到 `派给|安排|交给` 也没用：全量扫描会命中 10 轮，新增的 `4c30837d` 是在解释「计算5+9任务安排」这个会话名，`8468e0ad` 的「交给读者自己去问」是修辞。**加词就加误伤，不加就漏真话。**

按「真派活/假派活」两例算：召回 1/2 = 50%，精确率 1/7 ≈ 14.3%。样本只有 2 例真实派活声明，**覆盖率无法估计**，不能拿这 1 条说「词表能覆盖大多数」。

**否定句 / 引用句（构造性反例，本目录未观测到）**

- `"我不会直接安排，需要你确认"`：不含「已安排」连续子串 → 不命中（安全）。
- `"不是已派，是被派"`：命中「已派」→ 误标。
- `"如果已派出去，它会回执"`：命中 → 误标（假设句）。
- `"你刚说『已派给小说会话』"`：命中 → 误标（引用用户/自己原话）。
- `"这件事没有已安排"`：命中 → 误标（虽然中文不自然，但模型会这么说）。

窄词表能挡住一部分否定（「尚未安排」不含「已安排」），挡不住引用、假设与「不是已派」这类对比句。

**渲染不带伤**

- 不新建消息类型是底线；但「挂一句实话」如果落在消息流里，容易被读成第四种信息形态。可用的既有位置是轮容器尾部的 footer（`round-block`），并且必须是**纯函数派生**：重放从 `RoundView.processEvents` + `assistantMessage` 算，实时从 `turn_update.rounds[].processEvents` + 终态文本算（**不能用 `currentEvents`**，助手窗 `bubbleOnly` 已把 `process_event` 全滤掉）。只要两边同一个谓词，重放/切会话不会丢，也不会重复。
- 若只在收场时往 DOM 追加一句、不参与重放，切会话后就消失 → 同一轮两种样子，属带伤。
- 只在助手形态显示还是两种形态都显示，需要明确：卡片只归助手形态（`dispatchCardProjection.ts:84`）；这条提示若跟着卡片走，就只该在助手形态出现（§六第 4 步已定为只在助手形态）。

**不改 `metrics.success`：这一条成立。** 零工具零失败确实是「执行成功」，把它改成 false 会让「执行成功」语义塌掉。方案在这点上是对的。

## 五、成立 / 不成立 / 需修改

| 主张 | 判定 | 依据 |
| --- | --- | --- |
| 用 `dispatchedBy` 当**本轮**对账凭据 | **不成立** | 它写在目标轮，编排轮 17/17 没有；真派活的 `18a903bd` 一旦用「已派给」措辞就会被误判（其原文是「派给」，另属词表漏报） |
| 五词表 + 上述凭据作为闸门 | **不成立** | 命中 7 条误伤 6 条；真派活的换词版本漏报 |
| 把对账结果当「空承诺 / 未完成」定性 | **不成立** | 与 `status` / `metrics` 并列，违 SSOT；且无回执 ≠ 没发生 |
| 对账后不影响 `metrics.success` | **成立** | 两者语义不同轴 |
| 「解释权归宿主」用于卡片/状态 | **已经成立**（现状如此） | `protocol.ts:1512-1521` |
| 「解释权归宿主」用于模型正文 | **不成立** | 只能改写终态，属带伤 |
| 换成「本轮 `send/create` 成功回执（含业务 ok）」+ 只认派发类措辞 + 证据级措辞 | **需修改后可成立** | 数据在盘上、消费者已有原型；误伤面可降到「换词/引用/跨轮复述」 |

**一句话**：方向对（用事实约束话术），但你给的两个落点都错了——凭据选错了轮，词表混装了两类断言。按原样落地会抓错人、漏掉真话。

## 六、最终推荐落地顺序（v2 定稿）

> v1 的两处错误已在本版订正：①「实时从 `currentEvents` 算」不成立（助手窗把它全滤掉了，见 8.2）；②「先只给测试/诊断用」会留下僵尸函数（见 8.2）。
> ⚠️ **v3 订正（2026-11-21，代码回源后）**：本节仍有 3 处照原文落地会破原则——「唯一解析点」不成立（工作台清单另有同源解析）、呈现位在助手形态实际不可见、既有用例会转红。**执行以 §九 为准**，本节保留作演进记录。

**第 1 步：把「业务已受理」收进共享解析器（一个判据，两个消费者）**

- 位置：`webview/helpers/processEventText.ts` 的 `dispatchedSidTextsFromEvents`——它是**会话卡这一路**的唯一解析点（消费方 `dispatchCardProjection.ts:68`）。**v3 订正**：工作台清单另有同源第二份解析（`workbenchHistory.collectFromRound`），故最终落法不是「合并成一个解析器」，而是把「业务已受理」判据下沉为单函数、两处共用（见 §九 9.2）。
- 改动：`tool_result` 不只看内核 `payload.ok`（`processEventText.ts:287`），还要从 `summary` 读业务 `ok`：`"ok": false` 视为**未受理**。`create_session` 现在靠「成功体里有 sid」侥幸挡住失败体，但 `parseCreateSessionSid` 的正则（`processEventText.ts:220`）不排除 message 内嵌 sid；补上业务 `ok` 后，两个工具都**先判 ok**——`create_session` 再取 summary 里的 sid，`send_to_session` 的 sid 仍取 `tool_start.args`——不再依赖形状侥幸。
- 直接后果：`E_BUSY` / `E_DENIED` / `E_LOCKED` 不再产生会话卡。这是**行为变化**，必须进回归面（第 6 步），不是无痛重构。
- 单点纪律：新判据只准存在于这个函数里，会话卡与轮尾提示都调用它，禁止第二份裸比较。范式照 `isInternalSeedSender`（`shared/constants.ts:137`，实时/重放共用 + 源码守卫测试 `chatView.test.ts:14884-14890`）。

**第 2 步：把 `send_to_session` 的结果产生点收成可锁函数**

- `send_to_session` 现在直接 `JSON.stringify(result, null, 2)`；`create_session` 已有 `serializeCreateSessionResult`。补一个同形的 send 序列化函数，把「业务 `ok` 必须落在 100 字窗口内」钉进互锁测试（形状照 `workbenchSidContract.test.ts`）。只把隐式文本收成显式产生点，不改变返回内容。

**第 3 步：提示谓词与消费者同笔落地（不留僵尸函数）**

- 谓词：`hasAcceptedDispatchInRound(events)`（或直接复用第 1 步函数的输出），只读本轮事件。
- 消费者：助手轮尾 footer。实时与重放必须同源：
  - 实时：`turn_update.rounds[].processEvents`（`chatView.ts:3098-3100` 已用同形态给卡片补登记）；
  - 重放：`RoundView.processEvents`；
  - **不得用实时 `currentEvents`**：助手窗 `bubbleOnly` 把 `process_event` 全滤掉（`viewBroadcaster.ts:50-59`、`hostedPanel.ts:124`）。
- 谓词无状态（每次从全量事件算），不需要另做 seq 去重；重放/切会话结果一致。

**第 4 步：文案与位置**

- 只在「派发类措辞命中 **且** 本轮无成功回执」时出现，措辞固定为「本轮未核到会话派发回执」。
- 禁止「未完成 / 失败 / 没做」等定性词；它是证据缺口提示，不是完成态徽标。
- 只在助手形态显示（与会话卡同构，`dispatchCardProjection.ts:84`）。
- 加文案互锁测试：改词条即红，防止悄悄升级成结论。

**第 5 步：词表只当提示器输入**

- 收窄为派发义：`已派给 / 已交给 / 已发送 / 已安排 / 派给 / 已受理并派`；排除 `已完成`、单独 `交给`、单独 `安排`。
- 实测（27 轮）：裸 `派给` 命中 2 轮——`18a903bd` 有真回执（`{"ok": true, "accepted": true}`）、`ab4125bc` 无回执；按「命中 + 无回执」判，新增误伤 0。**n=2，不可外推。**
- 词表永远抓不全（换词 / 引用 / 假设 / 跨轮复述），这正是它只能是提示器、不能是闸门的原因。

**第 6 步：回归面（必须一起验）**

1. `E_BUSY` / `E_DENIED` / `E_LOCKED` 不再出卡；补一条「内核 `ok=true` + `summary` 业务 `ok=false`」的用例（当前测试只有内核 `ok=false` 的用例，是空白）。
2. 成功派发照旧出卡——但**既有 fixture 会转红**：它们用 `summary:'{}'` 或不带 summary（`chatView.test.ts:12837/12913`、`processEventText.test.ts:145/209`），新判据下视为「未受理」。须改成真实产生点形态（见 §九 9.4）。
3. 卡片与轮尾提示不得互相矛盾：同一轮要么有卡无提示、要么无卡有提示，不得两者并存又对立。
4. 实时 / 重放 / 切会话三种入口，提示的出现与消失一致。
5. **历史轮回溯**：重放用新判据重算，过去「失败派发仍出卡」的那些轮，升级后卡片会消失。这是有意的行为变化，须在真机验收里明确记录，不能当成回归失败。
6. `metrics.success` / `Round.status` / 助手正文零改动。

**第 7 步：不做**

- 用 `dispatchedBy` 判本轮、改 `metrics.success` / `status`、改助手正文、给内部常量配显示名、由提示器驱动补派。
- 若验收标准是「活真的被安排」（用户③），另立条目：要动内核自审门槛（`shouldInjectSelfReview` 中 `toolExecutedThisTurn` 为假时直接 return，`loop.ts:1334`）或宿主结构化派活入口，不能用本方案充数。

## 七、边界：这个方案抓不到什么

- **换词/换语言**：不说上面六个词、用「已经安排妥当」「那边已经在写了」「我让人去弄了」——抓不到。词表法永远有这条缝。
- **引用与假设**：转述用户原话、假设句、对比句，会误标（见口径三）。
- **跨轮复述**：上一轮真派了，这一轮说「已派给小说会话」——本轮无回执，会被误标成空承诺。
- **无回执但真发生了**：用户在目标会话里手动跑、或经其它通道完成，本轮无工具回执——会误标。
- **有回执但没做成**：`send_to_session` 受理成功、目标会话随后失败/被叫停——方案只管「派没派」，不管「做成没做成」。
- **`thought` 里的意图**：`ab4125bc` 的 thought 写得很清楚，但方案只看终态文本；反过来，thinking 里有计划、正文没提，也不会触发。
- **工具回执的业务失败**：如果沿用 `payload.ok` 而不解析 `summary` 的业务 `ok`，`E_BUSY` / `E_DENIED` 会被当成「有回执」，闸门直接失效（现有卡片解析就有这个缺口，`processEventText.ts:287` 只读内核 ok）。
- **覆盖率**：本目录 27 轮里只有 2 例真实派活声明（1 成功、1 空承诺），**覆盖率与误报率都无法做统计外推**，只能作为反例样本。

## 十、从「看得见」到「让它去派」：完成门（DISPATCH-REPAIR-1）

### 10.1 结论先行：三条路的能力边界不同

| 路径 | 能保证「必定派发」吗 | 覆盖「零工具谎报」吗 | 代价 |
| --- | --- | --- | --- |
| 宿主投递队列（P1） | 能（对已调用但失败） | 不能 | 中：投递状态 + 持久化 + 幂等 + 状态通道 |
| 完成门 / 补派检查（P2） | **不能**（提高命中率） | 能（概率） | 低：复用内部种子 + 既有判据 |
| 工单化（P3） | 能（结构上不存在「说了没派」） | 能 | 高：架构级 |

依据（外部）：DSH super-agent 把「派活」做成 `Ticket` / `Assignment`，投递失败按 2s→倍增→1min 重试并在面板显示 `Input undelivered`，并明确拒绝「从自由文本推断状态」（需要结构化事实）；其自身消融也显示纯提示只能把派发概率从 0 拉到 4/5。论文（Verified Tool Calls）补上重试安全：后置校验 + 先验证再重试 + 幂等键。

### 10.2 本次落地：P2 完成门（只提醒，不代发）

**判据（与提示同源，不写第二份）**：`shouldNudgeDispatchRepair(round)` = `status === 'complete'` + 正文命中派发窄词表 + 本轮零业务受理回执 + **非内部种子轮**。

**动作**：轮正常收场后，若判据成立，自动起一轮**内部种子**（复用 `wakeSettlementReport` 同一条 `runFlow + chat(origin='hosted')` 通路，不新造流、不新造面板），种子内容 = 「你在第 X 轮声称已派，但本轮没有受理回执；要么现在实际调用 `send_to_session` / `create_session`，要么明确说没派成及原因」。

**四条硬约束**：

1. **只提醒，不代发**：补派轮里必须由模型自己调用工具；系统绝不按词表自动发送（误报会变成「自动发错话」）。
2. **防自唤成环**：补派轮本身是内部种子（`RoundMessage.name = INTERNAL_SEED_SENDER`），判据侧排除。
3. **不打扰**：只对托管会话、且会话空闲时起轮；用户自建会话、在跑 / 待答 / 暂停态一律不碰。
4. **零改状态**：不改 `Round.status` / `metrics.success` / 助手正文；只新增一轮可见的补派对话。

### 10.3 为什么 P1（投递队列）暂不落地

`hostedDispatchRun` 的既有契约是 **「目标在跑回 E_BUSY，不排队」**（有测试钉住「不双开流」）。要做真正的异步队列，至少需要：

1. 一条投递记录（`roundId + toolCallId` 为幂等键，状态 pending/delivering/delivered/failed）；
2. 一个**投递状态通道**到 webview（否则源轮 `tool_result` 说失败、目标账本说已送达，两个真相）；
3. 卡片新增「投递中 / 投递失败」态，并在送达后实时更新；
4. 重启恢复 + 退避上限 + 先验证再重试。

缺第 2 条就做，会制造「一份事实两个答案」——违反 SSOT。故 P1 单独立项，前置条件就是上面四条。

### 10.4 P3（工单化）的落点

memora 已有 `PlanItem`（任务项），不需要新造 Ticket：把「派发类任务项」的完成绑定投递记录，没有记录不许标完成。这样「说了没派」在结构上不成立。代价是任务表变重，等 P1/P2 跑出真实痛点再做。

### 10.5 边界登记

- 完成门是**概率修复**：换说法 / 引用 / 假设 / 跨轮复述抓不到；它不改变「检测是启发式」这一事实。
- 中断轮 / 软暂停不触发（正文可能半截）。
- 补派轮会消耗一次模型调用；若模型仍不调工具，提示（DISPATCH-CLAIM-HINT-1）仍在原轮兜底。
- 原轮的提示不会因补派成功而消失：它记录的是「原轮没有回执」这一事实；补派结果由后续轮自己呈现。
- 真机验收仍待补。

## 十一、二次排雷：零工具分支必须带用户意图门

### 11.1 实锤：旧判据把纯聊天轮也标成缺口

### 11.2 判据定稿：三分支，同一回执判据

| 分支 | 覆盖 | 例子 |
| --- | --- | --- |
| 派发话术 | 词表命中的派发承诺 | `ab4125bc`「已派给小说会话」 |
