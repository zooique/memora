## 一、全量质量审查结论

### 根因 1（任务表建不起来 + UI 无感）

- [sessionManager.ts:765-797](../../src/agent/managers/sessionManager.ts) `writePlan` 在 `this.checkpoint` 为 null 时静默 `return []`。
- **生产流程无任何一处保证 checkpoint 在任务表写点前就绪**：
  - `prepare.ts:80` 约会骨架直接 `sessionManager.writePlan('overwrite', meetingSteps)`，未先建 checkpoint；
  - 普通 LLM 路径 `task_table_write` → `toolExecutor.ts:1126` → `assembler.ts:385` → `sessionManager.writePlan`，checkpoint 通常为空（生产仅 pause/resume 触发 createCheckpoint，见 agent.ts pause 路径）。
- 结果链：写点静默空 → LLM 看到「0 个步骤」但 `ok:true`（伪成功）→ 反复换格式重写 6 次 → 宿主 `plan_update`（由 checkpoint.plan 驱动，chatView.ts renderPlanBoard / globalPlanBoard）无步骤可渲染 = **视觉无感**。
- **带伤盘点**：任务表写点的「未就绪」被伪装成成功；工具已常驻暴露（DEFAULT_EXPOSED_TOOLS）但后端 checkpoint 生命周期未保证 = 工具可见但运行时未就绪。属「同语义多实现反噬」——五个写点/读点各自 `if(!checkpoint)` 早退回，无统一就绪断言。

### 根因 2（提示完成却不结束）

- `DEDUP_SUBJECT_EXTRACTORS`（[toolResultCache.ts:98+](../../src/agent/toolResultCache.ts)）只覆盖 read_file/list_dir/web_search/web_fetch/trace_summary，**write_file 无防重/止损**。
- 每次 write_file 成功会 `invalidateFile`（[loop.ts:1721-1734](../../src/agent/loop.ts)）→ read 缓存失效 → 读回永远「新鲜」→ LLM 看到重复内容 → 宣称「完整重写清理」→ 再写 → 自环。
- `self_review` 单发、无循环检测；`DEFAULT_MAX_ITERATIONS=50` 兜底因 LLM 持续产出工具调用/thought、未走到决策边界而没拦住。
- **带伤盘点**：read 系有 去重 + 失败硬闸（`infoToolFailureBySubject`）+ 覆盖度台账（`fileExposure`）三重止损，write 系（同样会烧 token 的自我强环）完全裸奔。值得注意 write/delete 会主动 invalidate read 缓存是**正确**的（内容变了必须放行重读），止损点应落在 write 自身同一路径连续重写频次，而非去动 read 失效逻辑。

### 本次收敛目标（SSOT + 自然生长）

- **不新增机制**：复用现有「确定性拦截」范式（read 去重/搜索硬闸同款：前置拦截 + 注入引导文案），在同构位置生长。
- **不重复造轮子**：宿主任务看板 UI 已存在，无 UI 改动。

## 二、修复方案

### 修复 A：任务表 checkpoint 就绪性（写点自愈 + 明确错误）— 治根因 1

**文件**：`src/agent/managers/sessionManager.ts`

在 `writePlan(mode, steps)`（L765）的开头，把静默早退改为写点自愈：

```ts
writePlan(mode, steps): PlanStep[] {
  // 写点自愈：checkpoint 未就绪时先创建（任务表写点 = 任务上下文就绪点）。
  // 此前静默 return [] 让 LLM 收到 ok:true + 0 步 → 伪成功 → 反复重写（实测 6 次）。
  // 不改变已有 checkpoint 时的行为（仅补前置就绪）。
  const cp = this.checkpoint ?? this.createCheckpoint();
  const existingPlan = cp.plan;
  // ...mode overwrite/append → cp.plan 操作；appendPlanStep 现建立在已就绪 checkpoint 上
  // ...mode update → this.updatePlan(updatedPlan)
  this.ensureActiveStep();
  return cp.plan;
}
```

- 内部 `this.checkpoint.plan = []` / `appendPlanStep` / `updatePlan` 改为基于 `cp`（已由 createCheckpoint 写入 `this.checkpoint`）。
- **不带伤自检**：cp 已存在时的行为逐字节不变；仅补齐「null 前置条件」这一缺口的自愈。约会骨架 `prepare.ts:80` 与普通 LLM `task_table_write` 一并被治愈。
- **明确错误出口（兜底）**：`updateStep`/`appendPlanStep` 在有真实无法就绪时仍返回现有明确错误（PLAN_ITEM_NOT_FOUND / 0），不伪装成功；`planManager.writePlan` 的返回文案（assembler.ts:386）始终反映真实 plan 长度，不再出现「0 个步骤却在 ok 成功」。
- 检查 `createCheckpoint`（L410）依赖 `this.getHistory()`，工具执行期 history 已装配，安全。（若你需要，此项可在实现时对 `createCheckpoint` 抛错路径补一行防御性说明注释。）

### 修复 B：write_file 同路径连续重写确定性止损 — 治根因 2

**文件**：`src/agent/loop.ts`

参照 `infoToolFailureBySubject`（读侧失败硬闸）同构，加写侧同路径连写护栏：

1. **新增字段**（随 resetTurnState 清空，生命周期与 toolResultCache/fileExposure 一致）：
   ```ts
   /** write_file 同路径连续重写计数（写侧止损：治「写→读回→见重复→再写」自环）。 */
   private lastWritePath: string | null = null;
   private samePathWriteStreak = 0;
   ```
2. **常量**：`WRITE_LOOP_THRESHOLD = 4`（与 READ_DIGEST_CHARS 同级模块常量）。
3. **前置拦截**：在 `executeToolCalls` 内、read 去重分支附近新增 write_file 专属分支：执行前解析 `args.path` 并 normalize；
   - 与 `lastWritePath` 相同 → `samePathWriteStreak++`；不同 → 重置为 1 并更新 `lastWritePath`；
   - 达阈值 → 置 blocked 并注入：
     `[WRITE_LOOP_STOP] 你已连续 N 次重写同一文件 ${path}，疑似自环清理/重建内容。请先 list_dir/read_file 确认真实文件状态，或明确重写章法后再动手；不要对同一文件反复 write_file。`
     并 `continue`（不执行，同 read 去重硬拦）。
   - 未达阈值 → 放行（不误伤合法连续改写）。
4. **不触碰** read 缓存失效（loop.ts:1721）与 read 去重/台账逻辑——写侧止损独立于读侧，互不干扰。
5. **self_review 不强加循环阻断**：写侧护栏已在源头断环，避免过度工程化。保持 self_review 现语义。
