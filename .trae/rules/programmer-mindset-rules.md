# 资深程序员心智模型

> 提炼自项目实战中反复出现的修复模式、设计思维与反模式。
> 每次动手前先自问：**我是在消除根因，还是在症状上叠加防御代码？**
> 每次设计前先自问：**逻辑通顺了吗？现有逻辑能被复用吗？**

---

## 一、Bug 修复心智模型

### 1.1 诊断阶段

| 类型 | 心智规则 |
| ---- | ---- |
| **DO** | **稳定复现是诊断的前提**——修复一个无法稳定复现的 bug 是猜测，不是修复。在动手前先找到最小复现步骤：输入什么、环境是什么、触发条件是什么。如果你的修复不能被测试验证（因为 bug 不可复现），你就无法确认它是修复还是又埋了一颗雷 |
| **DO** | **区分症状与根因**——现象是果，不是因。修复现象是止痛药，修复根因才是手术。永远多问一层：是什么导致了这种现象？ |
| **DO** | **识别不可逆损失点**——某些损坏是不可逆的（信息永久丢失、状态不可恢复）。不要在已损坏的数据上做恢复逻辑，要找到产生损坏的上游环节并切断它 |
| **DO** | **怀疑前提**——当一个机制或依赖反复出问题、需要反复修补时，停下来问：这个机制本身是不是错误的选择？修补能解决这一次，但前提错了，问题会无限回归 |

### 1.2 方案选择阶段

| 类型 | 心智规则 |
| ---- | ---- |
| **DO** | **向源头追溯**——每问一次"能否去掉中间一层"，方案就往根因逼近一步。终极方案的特征是：调用链路最短、参与方最少、无一环多余 |
| **DO** | **绕过而非修补**——当一个外部依赖有不可修复的缺陷时，不要在其输出上叠加检测和 fallback。提取依赖中仍可靠的原始数据，自己完成剩余的步骤。叠加防御是补丁思维，绕过依赖是架构思维 |
| **DO** | **方案复杂度应与问题本质匹配**——如果解决一个问题需要引入比问题本身更复杂的机制，停下来。你很可能在用一个复杂方案绕过另一个复杂方案，而非真正简化 |
| **DON'T** | **不要在不可靠机制上修 bug**——如果某个机制本身不可靠（依赖偶然状态、涉及竞态、跨越不稳定边界），优先考虑替换它。当替换不可行时（浏览器渲染时序、第三方 SDK 授权合约），在该机制外围建立隔离层（contain-and-isolate），让不可靠性不扩散到系统的其他部分。核心逻辑永远不直接依赖不可靠机制 |

### 1.3 执行阶段

| 类型 | 心智规则 |
| ---- | ---- |
| **DO** | **每次只修一个根因**——一次提交修复一个独立问题。叠加修复优于大包大揽：前者每一步可验证、可回滚，后者失败时无法定位 |
| **DO** | **每多一层抽象就多一个故障点**——跨越层级的转换（进程边界、编码转换、序列化/反序列化）天然不稳定。设计时优先消除层级跨越，而非在各层间加校验 |
| **DO** | **修复后的三步验证**——修复完成不等于修复有效。验证三步：(1) 原 bug 的复现步骤现在是否通过？（确认消除了症状）；(2) 新增的测试是否覆盖了根因条件？（确认根因被修复，而非症状被掩盖）；(3) 相关功能是否回归正常？（确认修复未引入新问题）。三步全通过，修复才算完成 |
| **DO** | **不可逆操作的双重保险**——数据库迁移、生产配置变更、用户数据删除等操作一旦执行不可回退。执行前必须有：(1) 明确的回滚方案——不是「理论上能回滚」，而是脚本写好、路径演练过的回滚；(2) 变更影响面评估——哪些功能会被波及、回滚窗口是多久。先确认能回滚，再执行变更 |

## 二、逻辑大师——设计思维模型

> 写代码前先做逻辑设计。逻辑通了，代码是推导结果；逻辑不通，代码是埋雷。

### 2.1 逻辑先行，代码后行

**原则**：代码是逻辑的翻译，不是逻辑本身。先想清楚"为什么这样设计"，再写"怎么实现"。

| 类型 | 心智规则 |
| ---- | ---- |
| **DO** | **先画逻辑链，再写代码**——新功能上手前，先在脑中（或纸上）画出完整的逻辑链路：输入是什么 → 经过哪些变换 → 输出是什么。链路闭合了再动手 |
| **DO** | **问"为什么"多于问"怎么做"**——"怎么做"是战术问题，查文档就能解决；"为什么"是战略问题，决定了代码的寿命。每引入一个新概念，先问：为什么需要它？去掉它会怎样？ |
| **DO** | **把探索和实现分开**——探索性原型（spike）是验证方案可行性的合法手段，但探索代码是验证工具，不是交付物。探索完成后，扔掉原型代码，带着结论重新设计逻辑。把探索和实现混在一起——把原型直接当交付物——才是灾难。分界线：你在"试一下这个方案行不行" → 探索，允许边写边试；你在"实现已确定的方案" → 实现，必须先有逻辑设计 |
| **DO** | **从 UI 出发，但不以 UI 为终点**——从用户可见的交互出发理解需求是合理的。但必须从 UI 描述中提取出独立的数据模型和状态转换——登录页的三个输入框映射到 LoginFormData 模型，购物车的操作映射到 CartState 状态机。UI 可以是逻辑的入口，不能是逻辑的载体。逻辑被 UI 绑架的标志：业务规则以 `onClick` 回调的形式散落在组件树的第 5 层 |

### 2.2 借力生长——在现有逻辑上生长新逻辑

**原则**：项目已有的逻辑链路是经过验证的资产。新功能不是"在一片空地上盖房子"，而是"在现有建筑上扩建"。先理解现有逻辑，再嫁接新逻辑。

| 类型 | 心智规则 |
| ---- | ---- |
| **DO** | **先读后写**——触及一个模块前，先理解它的现有逻辑链路：谁调用它、它调用谁、数据从哪里来、到哪里去。读懂了再写，新代码才能长在正确的节点上 |
| **DO** | **复用调用链，而非复制代码**——发现一段逻辑可以被新功能复用时，不要复制粘贴，而是找到调用链上最合适的挂载点，让新功能接入现有链路。复制的代码是技术债务，接入了链路的代码是自然生长 |
| **DO** | **技术债务的阈值判断**——复制代码确实是债务，但不是所有债务都值得立刻偿还。判断公式：当「复用成本」（引入抽象层、修改调用方、长期维护接口）>「复制成本」（代码行数）×「未来同时变更概率」时，复制是理性的。3 行逻辑、2 个使用场景、未来几乎不可能同时变更——复制它，加一行注释说明复制理由。反之，10 行逻辑、5 个使用场景、领域规则大概率会变——抽象它 |
| **DO** | **新逻辑要"嫁接"而非"并列"**——如果新功能与现有功能做的是同一类事（如：两种归档模式），它们应该共享同一段调用链，在分叉点做差异化。两个并列的独立链路是重复造轮子 |
| **DON'T** | **不要忽视现有约束**——每个模块都有其设计约束（如"内核零依赖"、"单 Agent 模型"）。新逻辑必须在现有约束下生长，而不是绕过约束另起炉灶。约束是地基，不是枷锁 |
| **DON'T** | **先理解，再判断是否需要重写**——看到一个模块觉得"写得不好"，本能的反应是重写。但现有代码的每一个怪癖都可能对应一个历史问题。先理解那些怪癖——理解后有三种选择：结构兼容 → 复用；结构正确但实现混乱 → 重构；结构本身错误 → 重写。跳过理解直接重写是傲慢，理解后仍然保留确实该删除的代码是懦弱 |

### 2.3 逻辑通顺再动手

**原则**：逻辑设计有一个明确的分界点——"通了"。在分界点之前不要写代码，在分界点之后不要犹豫。

| 类型 | 心智规则 |
| ---- | ---- |
| **DO** | **用一句话说清核心逻辑**——如果你不能用一句话说清楚"这个功能的核心逻辑是什么"，说明你还没想通。一句话公式：当 [触发条件] 发生时，系统做 [核心动作]，产生 [预期结果] |
| **DO** | **边界条件前置思考**——正常路径逻辑通顺只是及格。在写代码之前，先想清楚：空状态怎么处理？错误状态怎么处理？极端输入怎么处理？降级路径是什么？边界条件想清楚了，逻辑才真正通顺 |
| **DO** | **逻辑评审先行**——复杂逻辑在动手前，先用自然语言向自己（或同事）讲一遍。讲的过程中卡住的地方，就是逻辑没通的地方。能讲通，就能写通 |
| **DO** | **写测试就是写逻辑**——如果你写不出测试，说明你对输入输出的理解还有盲区。测试不是事后验证——它是逻辑设计的另一种表达，把「当 X 发生时，系统做 Y，产生 Z」翻译成 given-when-then 的断言。推荐顺序：先想通逻辑 → 写测试表达逻辑 → 写实现让测试通过。测试先行的代码，逻辑必然已经通顺 |
| **DON'T** | **不要用代码掩盖逻辑不通**——加一个 flag、加一个 if-else、加一个 try-catch 来绕过逻辑死角，是"用代码遮蔽逻辑问题"。每一个补丁都是对"逻辑不通"的妥协，妥协积多了，系统就不可维护了 |
| **DON'T** | **不要在逻辑不通时开始写代码**——"先写起来，边写边捋"是最大的效率陷阱。逻辑不通时写的代码，大概率要删掉重写。先想通再写，一次写对，才是最快的路径 |

## 三、心智模型速查表

> 这些规则不是每次写代码都要全部执行的标准化流程。它们的价值在于**场景触发**——修 bug 时自然激活 §1，做设计时自然激活 §2。规则的目标是内化为直觉，不是增加流程。如果某天你发现自己不用看速查表就能做出对的决定，这些规则就完成了它们的工作。

| 4 | 能否去掉中间一层，让调用链更短？方案复杂度与问题本质匹配吗？ | §1.2 向源头追溯 |
| 5 | 核心逻辑能用一句话说清吗？边界条件想清楚了吗？ | §2.1 逻辑先行 / §2.3 逻辑通顺 |
