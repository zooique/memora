# UI 工程化心智模型

> 继承自[资深程序员心智模型](./programmer-mindset-rules.md)的核心原则：**复用而非复制、嫁接而非并列、逻辑先行**。
> 本文件将这些原则翻译到 UI 领域的具体实践。
>
> 设计语言不是你「选择」的风格，而是你每写一行 CSS 时所做的每个决定的总和。
> 当系统中存在 N 个组件时，它们应该像一个乐队，而非 N 个独奏者。
>
> 当遇到 UI bug 时，通用文件的诊断与验证心智模型（§1 稳定复现 / 根因 / 三步验证）同样适用——先复现，再区分是样式问题还是逻辑问题，最后验证修复。本文件聚焦于「如何设计得一致」，不重复覆盖「如何修复得彻底」。

## 一、设计令牌——统一设计语言的词汇表

**原则**：颜色、间距、字体、阴影、圆角、z-index 等基础属性必须 token 化。令牌是设计语言的"词汇表"——没有共享的词汇表，就不可能有一致的表达。

**与通用原则的映射**：后端通过调用链复用逻辑，前端通过令牌链复用视觉属性。令牌就是前端的「调用链节点」——修改一处，全局同步。

| 类型 | 心智规则 |
| ---- | ---- |
| **DO** | **建立分层令牌体系**——L1 全局基础令牌（foundation/）：颜色色板、间距刻度、字号阶梯、阴影层级。L2 语义令牌（面板/页面级前缀）：将基础令牌映射为语义含义（如 `--text-primary`、`--surface-card`）。L3 组件令牌：组件级覆写。分层不是过度设计，是让每一层有独立的变更理由 |
| **DO** | **令牌即契约**——一旦定义了 `--space-4: 16px`，就不存在 `margin: 17px`。17px 不是"差一点"，是"差一个体系"。间距必须落在刻度上，正如后端枚举值不可随意新增。当令牌确实无法覆盖时（对齐第三方组件固定间距、设计稿使用非标准栅格），用注释显式标记 `/* 非标: 对齐 Ant Design 默认间距 */`，并在迭代评估中决定是否扩展令牌体系以覆盖该场景 |
| **DO** | **定义令牌用裸值，使用令牌用引用**——在令牌定义文件中，`--red: #dc2626` 是正确的——这是定义。在组件样式文件中，`color: red` 是错误的——这是泄露。混淆定义和使用是设计系统的自毁：令牌定义文件是唯一的裸值来源，其余所有样式文件只能引用令牌 |
| **DO** | **设计令牌先行于组件**——写一个新组件之前，先确认它需要的所有视觉属性是否已有对应的令牌。如果令牌不存在，先在令牌层补齐，再写组件。组件是令牌的消费者，不是令牌的定义者 |
| **DON'T** | **不要创建只被一处使用的令牌**——如果一个令牌只有一个消费者，它就不是令牌，是伪装成令牌的硬编码。令牌的价值在于「改变一处，全局同步」。少于 2 个消费者的令牌应内联到组件中。例外：如果预见到同一次迭代中会有第二个消费者落地，允许提前创建 |

## 二、通用组件——按类型抽象，按语义实例化

**原则**：按钮就是按钮，卡片就是卡片，输入框就是输入框。先按类型定义通用基类，再按语义提供变体。不要让「登录按钮」和「提交按钮」是两个独立组件——它们是同一个按钮组件的两个语义实例。

| 类型 | 心智规则 |
| ---- | ---- |
| **DO** | **按类型收口通用组件**——按钮系统（`.btn` / `.btn--primary` / `.btn--danger` / `.btn--sm` / `.btn--lg`）、卡片系统（`.card` / `.card--elevated`）、输入系统（`.input` / `.input--pill`）、标签系统。所有同类元素必须从同一个基类派生，单一真理源。表现形式可以有 10 种变体，但定义只能在一个文件 |
| **DO** | **通用组件封装完整交互状态**——一个通用组件不只是静态样式，它必须覆盖 `:hover`、`:focus`、`:focus-visible`、`:active`、`:disabled`、`[aria-busy]`（loading）、`:empty`（空状态）。`focus-visible` 是增强，`:focus` 是底线——键盘用户依赖后者。状态矩阵是组件契约的一部分，缺一个状态就是缺一个承诺 |
| **DO** | **变体用 BEM 修饰符表达**——`.btn--primary`（语义变体）、`.btn--sm`（尺寸变体）、`.card--flat`（风格变体）。修饰符只改变它应该改变的属性——颜色变体不碰间距，尺寸变体不碰圆角。正交的变体维度保持正交 |
| **DO** | **通用组件的接口就是公共 API**——修改 `.btn` 的 class 结构或 CSS 自定义属性签名，等同于修改被 N 个模块导入的函数签名。破坏性变更前，先确认所有调用点的兼容性。如果做不到 100% 向后兼容，走 deprecation 周期：保留旧接口 + 标记废弃 + 在下一个大版本中移除 |
| **DON'T** | **不要为每个页面创建独立的按钮样式**——如果登录页的按钮比通用按钮"宽一点、圆角大一点"，不要写 `.login__btn`。在通用按钮上添加一个尺寸或风格变体。把页面级差异收敛为系统级扩展，而非局部分裂 |
| **DON'T** | **不要让状态样式散落在组件外部**——父组件通过传不同的 className 来模拟子组件的 disabled/active 状态，是状态管理失控。组件自身的状态应由组件自身管理，外部只传递状态值，不传递样式名 |

## 三、独特性——在通用基础上差异化

**原则**：独特性不是通用性的对立面，而是通用性的延伸。每一个独特样式都必须以通用样式为基础层，只在必要的属性上做覆写。覆写是"调参"，不是"重来"。

| 类型 | 心智规则 |
| ---- | ---- |
| **DO** | **独特性建立在继承之上**——组件专属样式必须先 `@include` 或组合通用基类，再覆写差异化属性。结构层（布局、间距、排版）继承通用，表现层（颜色、装饰、动画）做差异化。最终效果是：看起来独特，摸起来熟悉 |
| **DO** | **差异化要有存在的理由**——每新增一个样式覆写或变体，必须能回答两个问题：(1) 为什么不能用已有的通用样式？(2) 这个差异化解决的是什么独特问题？有理由的差异化是系统的进化，没理由的差异化是系统的腐化 |
| **DO** | **覆写范围最小化**——如果只需要改变背景色，只覆写 `background-color`，不要同时覆写 `padding`、`border-radius`、`font-size`。覆写越精确，后续通用层升级时冲突越少。窄覆写是安全网，宽覆写是债务 |
| **DON'T** | **不要从零开始写组件样式**——就算一个组件"非常特殊"，也必须先引入对应的通用组件基类，再添加专属覆写。零起点样式等价于声明「我与这个设计系统无关」，每一个零起点样式都是设计系统的裂痕。例外：当组件的视觉结构与所有现有通用组件**根本不同**时（如扇形菜单、3D 变换卡片），复用令牌而非组件基类——架空继承比不继承更危险 |
| **DON'T** | **不要用 `!important` 解决选择器特异性不足**——如果选择器优先级不够导致样式不生效，调整选择器链或重构 CSS 架构，而非用 `!important` 压制。例外：在分层令牌体系中，L3 组件覆写必须覆盖 L2 面板样式时，`!important` 或等价的高特异性选择器是在表达「高层级覆盖低层级」的架构意图——此时可以使用，但必须附注释说明 |

## 四、组件化——组合优于继承

**原则**：复杂 UI 是简单组件的组合，不是一个巨型组件的内部状态分支。组件封装的不只是视觉，而是完整的逻辑 + 样式 + 交互 + 可访问性。

| 类型 | 心智规则 |
| ---- | ---- |
| **DO** | **组件 = 逻辑 + 样式 + 交互的封装**——一个组件应该自包含其行为。外部使用者不需要知道它的内部 DOM 结构、不需要手动管理它的状态 class、不需要为它写独立的键盘导航。接口是 props/attributes，内部是黑盒 |
| **DO** | **组合优于继承**——复杂 UI 通过 Slot、children、render props 组装简单组件，而非通过组件继承链叠加功能。组合的组件可以独立测试、独立复用；巨型组件的一个分支路径出问题，整个组件都是嫌疑犯 |
| **DO** | **组件的独立性应与复用频率成正比**——被 5+ 处使用的组件，其内部逻辑必须是自洽的，不依赖调用方的上下文（除了显式传入的 props）。如果一个组件需要"感知自己在哪里被使用"才能正确渲染，它就不是组件，是模板片段 |
| **DON'T** | **不要用「暂时就这样」的组件**——匆忙写一个特定场景的组件、计划"以后重构为通用组件"，这个"以后"不会到来。每一个新组件在创建时就该问：它的哪一部分是可复用的？如果不能回答，它就不该成为一个独立组件 |
| **DON'T** | **叶子组件不承担布局责任，布局组件的职责就是布局**——Button、Input、Card 等叶子组件不应自设 `margin`（这等价于「假设自己总是在某个特定的上下文中」）。间距交给父容器或布局组件管理。但 Stack、Grid、Container 等布局型组件的全部职责就是管理子元素的排列和间距——它们设 `margin`/`gap` 是正确的。区分两种类型：叶子组件只管理自身，布局组件只管理子元素 |

## 五、前后端嫁接对照

> 通用文件中的「嫁接」原则在前后端有同构的表达。

| 维度 | 后端（调用链） | 前端（样式链） |
| ---- | -------------- | -------------- |
| **复用单位** | 函数 / 模块 / 调用链 | 令牌 / 通用组件基类 / 变体修饰符 |
| **嫁接操作** | 在现有调用链上找挂载点，新增分支逻辑 | 在现有通用组件上新增 BEM 修饰符（`.btn--newvariant`） |
| **避免并列** | 两个独立归档函数 → 合并为一个，用参数分叉 | 两个独立按钮样式 → 合并为通用 `.btn`，用 `--variant` 分叉 |
| **差异化位置** | 分叉点（if/switch/策略模式） | 修饰符（BEM modifier） |
| **单一真理源** | 同一段逻辑只在一处定义 | 同一类组件只在一个文件定义 |
| **判断标准** |「这两个功能做的是不是同一类事？」 |「这两个组件是不是同一个类型的不同表现？」 |

## 六、速查表

> 每次写 UI 代码前，过一遍这 5 个问题。

| # | 问题 | 对应章节 |
|---|------|---------|
| 1 | 这个视觉属性有对应的令牌吗？还是我在写裸值？ | §一 设计令牌 |
| 2 | 这个组件是已有通用组件的变体吗？能不能继承基类而非新建？ | §二 通用组件 |
| 3 | 如果必须有独特性，我的覆写范围是否最小？差异化有存在的理由吗？ | §三 独特性 |
| 4 | 复杂 UI 能否通过组合已有组件实现，而非写一个巨型组件？ | §四 组件化 |
| 5 | 这个修改会影响多少调用方？如果破坏兼容性，走 deprecation 周期了吗？ | §二 组件 API 稳定性 / [通用文件 §1.3](./programmer-mindset-rules.md) 不可逆操作 |
