# UI 工程化心智模型

> 继承 [programmer-mindset-rules.md](./programmer-mindset-rules.md)：复用而非复制、嫁接而非并列、逻辑先行。>
> **设计语言 = 你每写一行 CSS 所做的每个决定的总和**；N 个组件应像一个乐队，而非 N 个独奏者。>
> UI bug 诊断同用通用心智（稳定复现 → 区分样式/逻辑 → 三步验证），本文件只管「如何设计得一致」。

## 一、设计令牌

> 令牌 = 设计语言的词汇表 = 前端的「调用链节点」。基础属性（颜色/间距/字体/阴影/圆角/z-index）必须 token 化。

| 类型 | 心智规则 |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| **DO** | **分层令牌体系**——L1 基础（色板/间距刻度/字号阶梯/阴影）→ L2 语义（`--text-primary` / `--surface-card`）→ L3 组件覆写。分层不是过度设计，是让每层有独立变更理由 |
| **DO** | **令牌即契约**——定义 `--space-4: 16px` 后不存在 `margin: 17px`；间距必须落在刻度上。令牌无法覆盖时（对齐第三方固定间距/非标栅格）用注释显式标记 `/* 非标: 对齐 Ant Design 默认间距 */` 并评估是否扩展体系 |
| **DO** | **定义用裸值，使用用引用**——令牌定义文件是唯一裸值来源；组件样式里 `color: red` 是泄露，只能引用令牌 |
| **DO** | **令牌先行于组件**——写组件前先确认所需视觉属性已有令牌；缺则先在令牌层补齐。组件是消费者，不是定义者 |
| **DON'T** | **不创建只被一处使用的令牌**——单消费者令牌是伪装成令牌的硬编码，应内联。例外：同一次迭代内确定有第二消费者，可提前创建 |

### §一.1 DTCG 对齐与 Token 元数据（面向 AI 消费）

> 行业趋势：W3C Design Tokens 标准 [DTCG](https://www.designtokens.org) 让令牌从「人类可读的 CSS 变量」演进为「人类 + AI 双读的结构化数据」。

| 类型 | 心智规则 |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| **DO** | **语义令牌携带元数据**——`$type`（color/spacing/fontSize）+ `$description`（语义用途），让 AI 按用途而非仅名称选令牌 |
| **DO** | **三层对齐 DTCG**——L1 Primitive（纯视觉 `--red-500`）→ L2 Semantic（映射为语义 `--color-danger: $red-500`）→ L3 Component，便于与 Figma Tokens / Style Dictionary 互通 |
| **DO** | **源码与输出分离**——令牌真源宜用 JSON/YAML 定义（结构化、易被 AI 读），工具链生成 CSS 变量；当前 CSS 变量直定义为过渡方案 |
| **DON'T** | **语义令牌不嵌裸值**——`--color-danger` 应引用 `--red-500` 而非写 `#dc2626`（引用而非复制） |

## 二、通用组件——按类型抽象，按语义实例化

> 按钮就是按钮。先按类型定义通用基类，再按语义提供变体；「登录按钮」与「提交按钮」是同一组件的两个语义实例。

| 类型 | 心智规则 |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **DO** | **按类型收口**——按钮/卡片/输入/标签系统各归一个基类（`.btn` / `.btn--primary` / `.btn--sm`…）。表现可有 10 种变体，定义只在一个文件 |
| **DO** | **封装完整交互状态**——`:hover` / `:focus` / `:focus-visible` / `:active` / `:disabled` / `[aria-busy]` / `:empty`。`focus-visible` 是增强，`:focus` 是底线。状态矩阵是组件契约，缺一状态 = 缺一承诺 |
| **DO** | **变体用 BEM 修饰符**——`.btn--primary`（语义）/ `.btn--sm`（尺寸）/ `.card--flat`（风格）。修饰符只改它该改的属性，变体维度保持正交 |
| **DO** | **组件接口 = 公共 API**——改 class 结构或自定义属性签名等同改被 N 处导入的函数签名；破坏性变更走 deprecation 周期（保留旧接口 + 标记废弃 + 下个大版本移除） |
| **DON'T** | **不为每个页面建独立按钮样式**——页面级差异收敛为系统级变体，不写 `.login__btn` |
| **DON'T** | **状态样式不散落组件外**——父组件传 className 模拟子组件 disabled/active 是状态失控；外部只传状态值，不传样式名 |

## 三、独特性——在通用基础上差异化

> 独特性是通用性的延伸：以通用样式为基础层，只在必要属性上覆写。覆写是「调参」，不是「重来」。

| 类型 | 心智规则 |
| --------- | -------------------------------------------------------------------------------------------------------- |
| **DO** | **独特性建立在继承之上**——先组合通用基类再覆写；结构层（布局/间距/排版）继承，表现层（颜色/装饰/动画）差异化。看起来独特，摸起来熟悉 |
| **DO** | **差异化要有理由**——每新增覆写/变体须回答：① 为何不能用已有通用样式？② 解决了什么独特问题？有理由是进化，没理由是腐化 |
| **DO** | **覆写范围最小化**——只改背景色就只覆写 `background-color`。窄覆写是安全网，宽覆写是债务 |
| **DON'T** | **不从零写组件样式**——必须先引入通用基类再覆写；零起点 = 声明「与本设计系统无关」。例外：视觉结构与现有通用组件**根本不同**（扇形菜单 / 3D 卡片）时复用令牌而非基类——架空继承比不继承更危险 |
| **DON'T** | **不用 `!important` 补特异性不足**——调整选择器链或重构架构。例外：L3 组件覆写需压过 L2 面板样式时，`!important` 表达「高层覆盖低层」的架构意图，可用但须注释说明 |

## 四、组件化——组合优于继承

> 复杂 UI 是简单组件的组合，不是巨型组件的内部状态分支。组件封装 = 逻辑 + 样式 + 交互 + 可访问性。

| 类型 | 心智规则 |
| --------- | --------------------------------------------------------------------------------------------------------------------- |
| **DO** | **组件自包含**——外部不需知内部 DOM、不需手动管状态 class、不需另写键盘导航。接口是 props/attributes，内部黑盒 |
| **DO** | **组合优于继承**——用 Slot / children / render props 组装；组合件可独立测试复用，巨型组件一条分支出问题则整体成嫌疑 |
| **DO** | **独立性 ∝ 复用频率**——5+ 处使用的组件须自洽，不依赖调用方上下文；需「感知自己被用在哪」才能渲染的，是模板片段不是组件 |
| **DON'T** | **不用「暂时就这样」的组件**——创建时就问：哪部分可复用？答不出就不该成为独立组件（「以后重构」不会到来） |
| **DON'T** | **叶子组件不承担布局**——Button/Input/Card 不自设 `margin`（等于假设自己在特定上下文），间距交父容器；Stack/Grid/Container 的全部职责就是管子元素排列，设 margin/gap 正确 |

### §四.1 JS 层组件抽象——统一生命周期 API

> CSS 层靠令牌 + BEM 复用视觉，JS 层靠统一生命周期复用行为。直接手写 `createElement` 的是 DOM 操作类，不是组件。>
> **与现有 Manager 的关系**：`init() + cleanup()` 是生命周期雏形，缺 `mount/update`。迁移目标——Manager 持有 Component 实例，不再直接 createElement；新代码用 Component，旧代码渐进迁移。

| 类型 | 心智规则 |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **DO** | **生命周期四件套**——`new(options)`（只合并配置，无副作用）/ `mount(container)` / `update(options)`（增量更新）/ `destroy()`。统一 API = 后端「实现某接口的类」 |
| **DO** | **`destroy()` 清理彻底**——解绑事件（EventTracker / `removeEventListener`）、`el.remove()`、nullify 字段引用、取消进行中 Promise（`AbortController`）。残留引用 = 泄漏。迁移时 `destroy()` 先调 `cleanup()` 再补 DOM 移除与 nullify |
| **DO** | **`update()` 增量更新不重建 DOM**——用 `textContent` / `classList.toggle` / `setAttribute`；`innerHTML = ...` 会丢焦点、滚动位置、过渡动画。确需重建时注释「结构变更，需重建」 |
| **DO** | **根元素经 `this.el` 暴露**——`mount()` 后 `this.el` 指向根元素（父组件 `appendChild(child.el)`）；外部不得访问 `this.el.children`——`el` 是挂载锚点，不是内部 API |
| **DON'T** | **构造函数不做副作用**——只配置合并 + 字段初始化，不查 DOM / 绑事件 / 发请求；副作用放 `mount()` 后。基类 `Component` 构造函数为 `protected`，强制子类显式声明 `public constructor` |
| **DON'T** | **不依赖外部 DOM 上下文**——用 `this.el.querySelector(...)` 在自身子树查询，不用 `document.getElementById('xxx')` |

### §四.2 声明式工厂——配置声明差异

> 相同结构的页面用工厂声明差异（columns/actions/search/apiPath），工厂处理通用逻辑（分页/搜索/加载/空状态）。一个 ListPage 工厂 + 8 份配置 > 8 个手写 Manager。

| 类型 | 心智规则 |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| **DO** | **领域原语 / 明确第二消费者 → 设计期即抽工厂**——列表/详情/表单/搜索属领域原语，或有明确第二消费者时，首次实现即抽离（ADR-017 Scenario A：设计期抽取，不等「3 次」）。异类页面走 `customRender` 逃生舱，不强行纳入 |
| **DO** | **配置项声明完整契约**——类型/是否必填/默认值/回调签名须在 TS 接口明确；配置项是公共 API，破坏性变更走 deprecation |
| **DO** | **工厂管通用逻辑，页面管业务差异**——分页/搜索/加载/空状态/骨架屏/错误处理归工厂；列定义/行操作/自定义渲染归页面 |
| **DON'T** | **不为纯臆测复用提前抽**——「可能用到」仍属 YAGNI；真正风险是抓错重点/过度设计，化解方式是「最小原语 + 逃生舱」，不是「推迟到 N 次」 |
| **DON'T** | **不让工厂变 God Object**——工厂只组装通用结构；业务编排（如「审批通过后刷新列表 + 发通知」）归调用方/Coordinator。工厂 + 业务 = 不可复用 |

### §四.3 组件分层与统一导出——依赖单向、出口单一

> 与后端分层同构：`controller → service → repository` 单向；前端 `base ← feedback ← form ← navigation ← data` 单向。

| 类型 | 心智规则 |
| --------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| **DO** | **按依赖方向分层**——base（Button/Icon）→ feedback（Toast/Modal）→ form（Input/Select）→ navigation（Layout/Tabs）→ data（DataTable/ListPage）。高层可依赖低层，反之不可 |
| **DO** | **统一导出口**——`components/index.ts` 集中导出，`import { Button, ListPage } from '@components'`；禁止深路径导入（绕过导出口 = 失去重构自由） |
| **DO** | **新增组件立即注册导出口**——未注册 = 私有实现，不可被他模块引用 |
| **DON'T** | **不跨层引用**——base 不能 import data；若确实需要，说明分层错误（提升到 data 或把共享能力下沉到 base） |
| **DON'T** | **导出口不做副作用**——只 `export`，不初始化/调 API/查 DOM；副作用属使用方 |

### §四.3.1 依赖洋葱模型（变更影响可视化）

> 参考 [Feature-Sliced Design](https://feature-sliced.design)：分层的意义是让**变更涟漪止于洋葱层**。>
> **base 最稳定、变更影响全局 → 设计最须谨慎，只放所有组件都需要的东西；data 最易变、只影响自身及消费者 → 业务迭代主战场；底层涟漪广但频率低，顶层涟漪小但频率高。**

| 类型 | 心智规则 |
| --------- | --------------------------------------------------------------------------------------- |
| **DO** | **变更涟漪心智**——改前先问「影响哪几层」：改 base = 影响全项目须评审；改 data = 只影响自身及消费者，可自验 |
| **DO** | **新组件放能放的最内层**——能放 form 就不放 navigation；越靠近 base 越通用，涟漪越大 |
| **DO** | **跨层需求先下沉再引用**——data 需 feedback 能力时，先在 form 建抽象（form 依赖 feedback），再由 data 引用 form，不直接跨层 |
| **DON'T** | **不让高层决定低层接口**——若 base 的 Button 需 data 的 DataTable 才能定义接口，说明分层错误；低层接口只由低层需求决定 |

### §四.4 Manager 与 Component 的边界——编排与封装分离

> Manager 负责业务编排（多组件协调、跨面板通信、状态管理），Component 负责视觉封装（DOM 结构、交互状态、事件）。Manager 持有 Component，不直接 createElement。

| 类型 | 心智规则 |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| **DO** | **Manager 持有 Component，不操作 DOM**——用 `this.listComponent.update(data)`，不用 `innerHTML = ...`。Manager = 业务逻辑 + 组件调用 |
| **DO** | **Component 自包含交互**——内部管事件/状态/过渡；Manager 只传数据。类比：Component 是 Service，Manager 是 Controller（Controller 不直接操作数据库） |
| **DO** | **渐进迁移不重写**——① DOM 操作抽为 Component，Manager 持有 → ② 事件处理迁入 Component → ③ Manager 只剩编排。每步独立可验证（对齐渐进式重构规则 §5.1） |
| **DON'T** | **Component 不反向调用 Manager**——通过 `onXxx` 回调向上通信。反向引用 = 紧耦合 = 不可独立测试。例外：Host 接口模式（如 `ChatPanelHost`）是显式依赖注入，允许 |
| **DON'T** | **Manager 不知 Component 内部 DOM**——不用 `component.el.querySelector('.xxx')`；需要时 Component 暴露公共方法（如 `scrollToBottom()`）。内部结构是实现细节，不是接口 |

## 五、前后端嫁接对照

| 维度 | 后端（调用链） | 前端 CSS 层（样式链） | 前端 JS 层（组件链） |
| --------- | ----------------- | ------------------------------------ | ------------------------------- |
| **复用单位** | 函数 / 模块 / 调用链 | 令牌 / 通用基类 / 变体修饰符 | Component 类 / 工厂配置 / 声明式范式 |
| **嫁接操作** | 现有调用链上找挂载点，加分支 | 现有组件上加 BEM 修饰符 | Component 加 props 变体；工厂加配置项 |
| **避免并列** | 两个归档函数 → 合并用参数分叉 | 两套按钮样式 → 合并为 `.btn` 用 `--variant` 分叉 | 两个手写 DOM 的 Manager → 合并为工厂 + 配置 |
| **差异化位置** | 分叉点（if/switch/策略） | 修饰符（BEM modifier） | 配置项 / props |
| **单一真理源** | 同一逻辑只定义一处 | 同一类组件只在一个文件 | 同一结构只在一个工厂；同一生命周期只在一个基类 |
| **判断标准** | 「是否同类事？」 | 「是否同类型的不同表现？」 | 「是否同结构的配置差异？」 |

## 六、速查表（写 UI 代码前过一遍）

**CSS 层（§一~§三）**

1. 这个视觉属性有令牌吗？还是我在写裸值？
2. 这是已有通用组件的变体吗？能继承基类而非新建吗？
3. 若必须有独特性：覆写范围最小吗？差异化有理由吗？

**JS 层（§四.1~§四.4）**
4. 新组件遵循 `new/mount/update/destroy` 四件套吗？还是手写 `createElement` + 散落 `addEventListener`？
5. Manager 是否手写了 DOM？能否改持 Component + `component.update(data)`？
6. 新面板属领域原语（列表/详情/表单/搜索）或有明确第二消费者？是 → 设计期抽工厂（ADR-017 Scenario A）；否 → 手写但内部用 Component。
7. 组件注册到 `components/index.ts` 了吗？依赖单向吗（base ← feedback ← form ← navigation ← data）？

**影响面**
8. 改动影响多少调用方？破坏兼容走 deprecation 了吗？

**判定流程**（新增面板/页面时）

```
1. 属领域原语或有明确第二消费者？
   ├─ 是 → 设计期抽声明式工厂（§四.2），配置声明差异
   └─ 否 → 手写，但 Manager 内部必须用 Component
2. Manager 需操作 DOM？
   ├─ 是 → 抽 Component（§四.1），Manager 持有；Component 守四件套
   └─ 否 → 纯业务编排 Manager，无需 Component
3. Component 可复用？
   ├─ 是 → 注册 components/index.ts（§四.3），按分层放置
   └─ 否 → 作 Manager 私有内部实现，不导出
4. 新增视觉属性有令牌？
   ├─ 是 → 引用
   └─ 否 → 先补令牌（§一）再写组件
```
