# ADR-017 · 自然生长原则重新定义：分层适用

> **状态**：✅ 已接受
> **日期**：2026-07-12
> **来源**：用户提案——"架构优先，架构就是根须，先架构合理才能自然生长后续的枝叶"

## 背景

原"自然生长"原则被等同于"3 次提取原则"（出现 3 次以上相同模式才提取），在 5 个规则文件中一致引用。这导致一个悖论：明知架构该提前设计，却因为"不到 3 次"而故意不设计，等出问题再补——违反了大树模型"根须优先"的哲学。

用户在长期迭代准备阶段提出：**架构是根须，先架构合理才能自然生长后续的枝叶**。原定义把"自然生长"完全等同于"3 次提取"，混淆了两个层面：架构层（根须）应该先行设计，枝叶层（工具/组件/helper）才适用 3 次提取。

## 决策

**重新定义"自然生长"为分层适用原则**：

> 自然生长 = 根须先行定方向，枝叶按需自然长

| 层级 | 原则 | 含义 |
|------|------|------|
| **架构层（根须）** | 架构先行 | 新功能/新模块加入前，先评估架构归属（哪个模块？哪个层级？依赖方向？是否需要新 ADR？）。**不允许"等 3 次再设计架构"** |
| **枝叶层（枝叶）** | 2 次提取 | 工具函数、组件、helper 的抽象提取遵循 2 次原则，防止过早抽象 |

**架构层的判断标准**（新功能加入前必须回答）：

1. 该功能归属哪个模块？（参照 [backend_layers_rules.md](../backend_layers_rules.md) §分层职责）
2. 是否引入新的依赖方向？（如违反 [ADR-008](./ADR-008-directory-structure.md) 需先更新 ADR）
3. 是否需要新增模块？（参照 [new-module-guide.md](../new-module-guide.md)）
4. 是否影响现有架构边界？（如是 → 走"规则对齐"或"年轮审判"先调整架构）

**枝叶层的 2 次提取原则**：

- 同一工具函数在 2+ 个文件出现 → 提取到 utils/
- 同一组件模式在 2+ 个页面出现 → 提取到 components/
- 同一流程描述在 2+ 处出现 → 提取到 references/

## 理由

| 考虑 | 说明 |
|------|------|
| **根须和枝叶是两层** | 大树模型中根须（架构）和枝叶（功能）有不同生长规律，不应共用同一原则 |
| **架构先行不是 BDUF** | 架构先行只要求"新功能加入前评估归属"，不要求"提前设计所有可能的功能"——评估成本远低于设计成本 |
| **2 次原则的价值在枝叶层** | 防止过早抽象工具函数/helper，这个价值在枝叶层依然成立 |
| **原悖论的消除** | 架构层不再受"不到 3 次"约束，可以也应该在首个需求出现时就定好归属 |

## 替代方案

| 方案 | 放弃原因 |
|------|---------|
| 完全废除枝叶层抽象约束 | 枝叶层失去过度抽象防护，每个工具函数都可能被提前提取 |
| 架构优先 + 枝叶自由（无约束） | 枝叶层既不要求次数也不禁止提前抽象，完全靠经验判断，不可控 |
| 保持原定义（3 次原则统管） | 架构层悖论未解决，明知该设计却故意不设计 |
| 枝叶层沿用 3 次提取 | 用户判断 3 次阈值偏高，相同模式重复 2 次已足够识别抽象价值 |

## 影响

- **新功能开发流程**：加入"架构归属评估"步骤（4 个判断问题），参照 [new-module-guide.md](../new-module-guide.md)
- **"规则对齐"/"年轮审判"模式**：架构层变更的触发条件从"3 次重复"放宽为"1 次架构不合理"
- **"健康度诊断"模式**：架构层检查不再受"3 次原则"约束，可对单次架构违规提出修复建议
- **枝叶层抽象决策**：阈值从 3 次降为 2 次，相同模式重复 2 次即应提取

## 何时回顾

- 当"架构先行"导致超过 3 次的"为单次需求设计架构"过度设计时，重新评估架构层原则
- 当枝叶层 2 次阈值导致明显过度抽象（大量仅用 1 次的 helper 被提取）时，重新评估枝叶层阈值
