# 真机验收形态

> 继承 [programmer-mindset-rules.md](./programmer-mindset-rules.md) 与 [testing_rules.md](./testing_rules.md)。
> **本文件是宿主 UI 批次真机验收的唯一形态真源（SSOT）**——方案文档只登记本批次的观察点实例，禁复写本文件纪律（复写 = 第二真源）。
> 来源实证：UI-CONFIRM 系列 P9 / E4 / P10C 三次「替身全绿但真机不对」、P15 C1 六条验收 + 场 2 截图收据、P14「登记本身成了谎报」、P4 真机测试提示词（VERIFY-REALDEVICE-1，2026-10-10 落地）。

## 一、红线（三条，无例外）

| 类型 | 纪律 |
| --- | --- |
| **红线** | **测试全绿 ≠ UI 完成**——jsdom 替身证明不了「眼睛看到的对不对」（P9：穷举 10 个触发源全绿、真机仍见间隔；E4：结构性假绿；P10C：jsdom 不加载样式表 ⇒ 「展开即消失」全绿）。UI 批次必须真机验收通过才算落地 |
| **红线** | **验收不通过禁止销项**——「替身全绿 + 真机存疑」= 未完成，不是「带疑收尾」 |
| **红线** | **截图定位优先于推理改码**——真机异常先取截图/录屏，判定是重排还是重绘、哪个容器在覆盖，**禁止靠推理改代码**（推理链缺渲染事实层，P15 系列实证：推理出的修法三连不中） |

## 二、观察点先行（开工前登记）

| 类型 | 纪律 |
| --- | --- |
| **DO** | **批次开工前登记观察点**——每条 = 编号 + 判据 + 通过标准 + 预期截图；禁「做完再想验收什么」 |
| **DO** | **判据可观察、可证伪**——「条撤后信息仍可达」可验；「体验流畅」不可验 |
| **DON'T** | **不把单测断言当观察点**——观察点是「人眼在真机看什么」；替身断言归测试纪律管，两层不可互替 |
| **DO** | **每条观察点自带反例**——登记判据时同时写出「什么情况算这一条失败」，且该情况**能被真的构造出来**（见下「反例构造」） |

### 反例构造（判据的失败侧）

| 类型 | 纪律 |
| --- | --- |
| **DO** | **反例必须能被真的构造出来**——写成「若 X 则失败」还不够，要给出**本机可稳定复现**的构造步骤；构造不出来的反例等于没有反例 |
| **DO** | **反例必须命中被测机制**——构造出来后先自问「它触发的还是不是我要测的那件事」；答不上来就换反例，别拿它凑数 |
| **DO** | **反例优先选「同族不同因」的近邻**——用相邻机制去撞，才分得清「通过了」与「通过得不是理由」 |
| **DON'T** | **不用不可控场景充数**——「网络断了」「磁盘满了」这类本机无法稳定制造的场景，不构成反例 |

**为什么必须有（两次实证，同一形态）**：观察点「绿了」，但绿的原因不是被测机制——
1. **删文件降级**：在 6 轮会话里删第 2 轮的图，模型答「真实图片」。实际该轮已出图片保留窗口（本项目 `RETAIN_IMAGE_ROUNDS`）被剥成纯文本，模型是从历史抄答案 ⇒ **测的是窗口衰减，不是删文件降级**。把图换到窗口内、只让文件缺失，降级链才真正被验证。
2. **粘贴新发**：首次「通过」是同一张图此前已被预读命中缓存 ⇒ **测的是预读命中，不是新发落盘**。换一张从未出现过的图才暴露差别。

两例的共同点：判据**可观察、可证伪**，但「伪」不在被测机制上。所以上表「判据可观察、可证伪」是必要不充分——还必须**指名可证伪的对象**。

> 与 §四「反例清单」的分野（同词两义，写台账时须注明是哪一个）：§四 记**已证死的修法**（勿再尝试）；本节的反例是**判据的失败侧**（怎么算这一条不通过）。

## 三、截图收据

| 类型 | 纪律 |
| --- | --- |
| **DO** | **每条观察点过/不过都留截图收据**——描述性「已过」无效（P15 场 2 先例：metrics 块子项以截图收据闭合） |
| **DO** | **截图覆盖边界态**——空态 / 极端内容 / 交互中途，不只截最顺眼的主路径 |

## 四、反例清单（证死即登记）

| 类型 | 纪律 |
| --- | --- |
| **DO** | **已证死的修法登记「勿再尝试」**——变异实测变红后还原 ≠ 方案可行（意图闩先例：6 条既有用例红实证后证死）；证死过程写进台账防同名方案回潮 |
| **DON'T** | **不因「看起来该行」复活证死方案**——反例清单是台账级结论，推翻须新实证 |

## 五、登记复核（防「登记本身成了谎报」）

| 类型 | 纪律 |
| --- | --- |
| **红线** | **登记「已落地 / 已补」前必须 grep 复核**——P14 实证：一度登记「该句已补」但全库 grep 零命中，登记本身成了谎报；复核命中后才保留 ✅ |

## 六、验收中发现非本批问题

| 类型 | 纪律 |
| --- | --- |
| **DO** | **登记台账，禁顺手修**——真机验收发现的问题一律登记（观察区或新条目）归下批次；顺手修 = 批次范围失控 + 新改动无验收覆盖 |
| **DO** | **高频三类自查**——闪烁（重渲染/覆盖顺序/切换时序）、位置（锚点/跟随容器/主位条）、覆盖关系（z-index/遮挡/陪葬撤除）为 UI-CONFIRM 系列实证高发区，验收时逐类过 |
