# 注释与文档减法红线

> **适用范围**：Memora 内核（`src/`）全部 TS 代码 + 仓库文档
> **与现有规则关系**：本文是 [coding-convention-rules.md](./coding-convention-rules.md) §3「代码简洁与复用」的**注释维度补充**——后者管代码结构，本文管注释与文档的篇幅纪律。两者正交。
> **触发场景**：新写注释 / 文档时、审查 PR 时、做「注释减法 / 文档减法 / 瘦身」重构时

---

## 1. 核心原则：让代码只讲代码，文档只讲文档

> **一句话**：**代码注释承担「类型与结构说了不出来的为什么」，文档承担「架构与模块关系」。两者都不该替对方粘一层易腐坏的复述。**

手工维护的内容（依赖图、模块清单、日期戳、章节号）注入注释必然腐坏——**文档优先，代码不重复**。

| 内容类型 | 唯一真理源 | 违反表现 |
| --------------- | --------------------------------------- | -------------------------------- |
| 模块依赖关系 / 模块清单 | `docs/architecture/module-inventory.md` | 在 `.ts` 文件头手绘「模块依赖图」 |
| 架构决策背景 | `.trae/decisions/ADR-*.md` | 在注释里大段引述 ADR 决策背景（只需一句设计意图 + 链接） |
| 具体实现动机 / bug 教训 | 代码注释 | 删掉——留下无人能还原的坑 |

## 2. 三分法：能删 / 压缩 / 必留

> **核心原则**：动注释前先按三条分拣，不做一刀切。

### A. 能删 → 直接删

| 类别 | 判定标准 | 范例 |
| ------------ | ------------------------- | ----------------------------------------------------------- |
| 重述代码 | 注释只是在再说一遍代码本身写的什么 | `// 贪心选取直到 token 用完`、`// 计算剩余 token`、`// user 消息权重 3` |
| 名字自明 | 字段/方法名已足够表达语义 | `/** 工具名称 */ name: string`、`/** 截断次数统计 */ _truncationCount` |
| 纯修辞铺垫 | 「这个很重要」「注意」「这是核心的」等无信息量话语 | 无 |
| 手绘依赖图 / 模块清单 | 与 `docs/` 重复且带日期戳（注定腐坏） | `.ts` 顶部的 `├─ loop.ts` 依赖树 |

### B. 压缩 → 多行压成单行/双行

| 类别 | 判定标准 | 保留内容 |
| ---------- | -------------- | ------------------------------------- |
| 接口契约 JSDoc | 方法行为/参数语义/降级行为 | 默认值、触发条件、降级行为、跨模块契约 |
| 字段 JSDoc | 字段格式/范围含义 | `id` 是 `source:name` 格式、`score` 是 0-1 |
| 节级文件头 | 模块职责总述 | 一句设计意图，删铺陈/历史/章节号 |

### C. 必留 → 压缩但宁少勿删

| 类别 | 判定标准 | 范例 |
| ------- | ----------------- | ------------------------------------------------- |
| 真·为什么 | 代码/类型/契约表达不了的决策理由 | `resetSummary` 的「消息集合被替换 vs 长度差」真相源说明 |
| bug 教训 | 「为什么这样写」能防前人回归同一坑 | 截断复用 round-summary 的动机、`excludeRoundIds` 前置过滤原因 |
| 核心算法理由 | 阈值/权重的选型思路 | CJK 分密度估算、read_file 分段预算 |
| 状态/时序契约 | 状态迁移、并发、互斥、降级语义 | `preExecutionCheck` 三态、`superseded` 写时取代判定、会话互斥排除 |

## 3. 文档章节号与日期戳处置

| 写法 | 处理 |
| -------------------------------------------------------------------- | ----------------------------- |
| `ADR-xxx` / `§x.x` / `Px.x` / `Phase x` / `Txxx` / 日期戳（`2026-08-xx`） | **删掉编号本身**，只保留其背后一句设计意图 |
| SSOT / 共享常量说明 | **压缩保留**（它承载「改一处须同步另一处」的跨层约束） |

## 4. 注释密度仓位

> **目标不是零注释，而是「用类型和结构说明的可读性」。** 用生产代码注释占比作为体检信号，而非硬性 KPI。

| 文件类型 | 合理注释占比 | 说明 |
| --------------------------- | ------ | -------------------------- |
| 普通业务文件 | ≤ 30% | 超过即触发审视 |
| 纯接口契约文件（storageInterface 等） | 允许偏高 | 契约 JSDoc 承担 API 文档职责，正文不删光 |
| 常量/magic number 文件 | 允许偏高 | 每条解释「为什么是这个值」 |
| 大而关键的引擎文件（loop/agent） | ≤ 25% | 高度压缩，保「为什么」 |

## 5. 审查点（代码评审时检查）

- [ ] 新注释是否重述了代码本身？（触发红线 A）
- [ ] 新增 .ts 文件头是否手绘了依赖图/模块清单？（违反「文档优先」，应指向 module-inventory.md）
- [ ] 注释里是否塞进了 ADR/章节号/日期戳而没删编号只留意图？（违反 §3）
- [ ] 压缩时是否误删了「真·为什么」（bug 教训、算法理由、契约）？（红线 C 高优先级，宁多留）
- [ ] 是否把新接口契约写全了再压缩？（红线 B：契约语义必留，只删修辞）
