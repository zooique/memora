# 单一真理源思维模型

> 遇到复杂问题，先回到最小单元。**如果一个复杂问题可以在最小单元层面解决，就不需要引入新机制。**
>
> 核心证明：**单轮问答闭环是 Agent 的最小完整单元。一切复杂行为（Loop、记忆、召回、摘要）都是这个单元的自然生长，而非独立的新系统。**

---

## 一、核心公理

### 1.1 最小单元的定义

一个系统无论多复杂，最终都以"**一次触发，一次回答**"为基本单元。这个单元必须满足三个条件：

- **自足**：一次触发，一次回答，内部完整。
- **可重复**：同一单元可被反复调用，且每次独立。
- **可观察**：单元的执行过程对外可见，可被记录、可被测试。

满足这三个条件的，就是系统的最小完整单元。**它是系统的"细胞"——所有复杂结构都是它的组合与重复，不是另外造一个更大的细胞。**

### 1.2 单一真理源的含义

**单一真理源（SSOT）不是"只有一个文件/一个模块"，而是"只有一个设计原点"**：

- 一套最小单元，承载所有复杂行为。
- 同一套逻辑，在多种场景下复用，不做场景特化。
- 复杂度向外生长，核心保持简单。

| 错误做法 | 正确做法 |
|---------|---------|
| Loop 需要独立引擎 | Loop 是最小单元的重复，用 Handoff 策略区分 |
| 新场景需要新机制 | 新场景是已有机制的参数化配置 |
| 在复杂场景上叠加补丁 | 回到最小单元，看能否在单元层面解决 |

## 二、三个证明：闭环如何自然生长出全部复杂度

### 2.1 证明一：Loop 循环 = 闭环的重复

**问题**：Loop 需要一套独立的循环引擎吗？

**答案**：不需要。

Loop 的每一轮，都是一次完整的单轮闭环。它有自己的回答前（分析当前状态）、回答中（执行一步）、回答后（判断是否继续）。Loop 所做的，只是在每一轮的 Handoff 处选择"continue"。

**设计推导**：

```
Loop 不是"闭环的放大"，而是"闭环的序列"。

单轮闭环：Trigger → Prepare → Act → Reflect → Handoff(wait)
Loop：    Trigger → Prepare → Act → Reflect → Handoff(loop)
                 ↑                              │
                 └──────────────────────────────┘
```

**收益**：

- 无需第二套引擎：Loop 与对话共享全部能力（记忆、工具、状态机）。
- 可暂停可恢复：每一轮边界都是天然的暂停点。
- 可观察可测试：每一轮是独立闭环，可单独记录、回放、调试。

**关键思维**：不要问"如何实现 Loop"，而要问"如何让闭环的 Handoff 支持自动续跑"。

### 2.2 证明二：召回 = 只在输入触发，而非每轮触发

**问题**：Loop 每轮都触发召回会很慢，怎么办？

**表面方案**：在 Loop 引擎中加一个"跳过召回"的开关，Loop 模式跳过，对话模式保留——**这是场景特化的补丁思维**。

**真理源方案**：回到最小单元——**闭环的召回行为，由"触发源"决定，而非"是否在 Loop 中"**。

```
闭环的召回设计：
  - 外部输入触发（用户/系统/其他 Agent）：→ 触发 recall()
  - Loop 自循环（工具调用/自动续跑）：→ 不触发 recall()

两种场景共享同一套闭环，唯一区别是触发源不同。
```

**推导**：闭环只有一个入口——Trigger。Trigger 携带"谁触发了我"的信息。闭环在回答前阶段检查这个信息，决定是否执行 recall()。这不是 Loop 的特殊处理，而是**闭环的自然属性**——闭环知道"自己是被谁拉起的"，并据此决定行为。

**收益**：

- 单轮问答和 Loop 使用同一套上下文拼接逻辑，无需分支。
- 召回只在外部输入时执行，Loop 自循环无额外 IO 开销。
- 召回结果在角色包提供的视角框架下被解读，角色包也只在外部输入时匹配。

**关键思维**：不要问"如何让 Loop 跳过召回"，而要问"闭环的召回应该由什么触发"。

### 2.3 证明三：摘要生成 + 记忆归档 = 闭环的后处理

**问题**：摘要生成、记忆归档这些后台任务，需要独立的后台系统吗？

**答案**：不需要。

每轮闭环完成后，自然进入"回答后"阶段。这个阶段天然适合做两件事：

```
每轮问答闭环完成后：
  1. 持久化对话记录（appendMessage）
  2. 后台异步：生成轮次摘要（1-2 句话，50-100 token）
  3. 后台异步：从摘要中提炼长期记忆（价值判断，去噪去重）
```

**推导**：闭环的三阶段结构（Prepare → Act → Reflect）中，Reflect 阶段天然承载"后处理"职责。不需要额外的定时任务或后台工作者——**闭环自己就是后处理的触发器**。

**收益**：

- 摘要从"运行时补救"变成"结构化数据"：截断时直接取用已存在的摘要，无需等 LLM。
- 记忆从原始对话中提炼，改为从摘要中提炼——天然去噪。
- 异步执行不阻塞主流程，用户无感知。

**关键思维**：不要问"如何实现后台摘要生成"，而要问"闭环完成后，哪个阶段最适合做这件事"。

## 三、思维模式：如何运用单一真理源

### 3.1 遇到复杂问题时的解题步骤

| 步骤 | 行动 | 问题 |
|------|------|------|
| 1 | 找到最小单元 | 这个系统的最小完整单元是什么？ |
| 2 | 定位问题在单元中的位置 | 问题是在单元内部，还是在单元之间？ |
| 3 | 检查是否能在单元层面解决 | 能否在单元内部加一个参数/策略/分支来解决？ |
| 4 | 如果可以，在单元层面解决 | 最小改动，最大复用 |
| 5 | 如果不行，再考虑单元间协作 | 单元间通过接口协作，而非引入新单元 |

### 3.2 识别补丁思维的信号

| 信号 | 含义 | 正确方向 |
|------|------|---------|
| "这个场景需要特殊处理" | 你在为场景特化做补丁 | 回到最小单元，看能否用参数化解决 |
| "再加一个模块/引擎/系统" | 你在引入新单元 | 回到最小单元，看能否复用已有机制 |
| "这个场景和那个场景不一样" | 你在强调差异，而非共性 | 找到所有场景的共性，在共性层面设计 |
| "先加个 flag 控制一下" | 你在用 flag 掩盖设计问题 | 思考 flag 对应的本质维度是什么 |

### 3.3 判断是否已偏离单一真理源

问自己三个问题：

1. **这套逻辑是否只在某个场景下生效？**——如果是，它可能是一个补丁，而非通用设计。
2. **去掉这个场景的特殊处理，核心逻辑是否依然完整？**——如果否，补丁已经和核心逻辑耦合。
3. **这个功能的实现，是否需要在最小单元之外引入新机制？**——如果是，警惕是否过度设计。

三个问题中任意一个答案为"是"，说明可能已经偏离了单一真理源，需要回到最小单元重新审视。

## 四、反模式：常见偏离案例

### 4.1 为 Loop 设计独立的"跳过召回"逻辑

```
❌ 反模式：
  if (isLoopMode) {
    skipRecall(); // Loop 模式跳过召回
  } else {
    doRecall();   // 对话模式触发召回
  }

✅ 真理源：
  // 闭环内部：触发源决定是否召回
  if (triggerSource === 'external_input') {
    await recall(); // 只有外部输入触发召回
  }
  // Loop 自循环的 Trigger 是系统自动，不会进入此分支
```

### 4.2 为后台任务设计独立的定时任务系统

```
❌ 反模式：
  setInterval(() => {
    generateSummary();  // 定时生成摘要
    extractInsights();  // 定时提取记忆
  }, 60000);

✅ 真理源：
  // 闭环完成后，回答后阶段自然触发
  async function reflect() {
    await persistMessages();       // 持久化对话记录
    scheduleAsync(generateSummary); // 后台异步生成摘要
    scheduleAsync(extractInsights); // 后台异步提炼记忆
  }
```

### 4.3 为多模式设计多套上下文组装逻辑

```
❌ 反模式：
  function buildContextForChat() { /* ... */ }
  function buildContextForLoop() { /* ... */ }
  function buildContextForAgent() { /* ... */ }

✅ 真理源：
  function buildContext(triggerSource) {
    if (triggerSource === 'external_input') {
      await matchRolePack();  // 角色包匹配
      await recall();         // 记忆+摘要召回
    }
    // 其余上下文组装逻辑统一，不分模式
  }
```

## 五、两个常见设计陷阱

### 5.1 循环依赖陷阱：A 需要 B，B 需要 A

**问题**：理解输入需要角色包（工程师 vs 翻译看到的问题不同），但角色包匹配又需要输入。如果两者都依赖语义理解，就形成死锁。

**真理源解法**：拆为两个阶段，中间插入一个确定性匹配步骤。

```
第一阶段：原始理解（不依赖角色包）
  - 输入预处理：分词、去噪、提取触发词
  └→ 角色包匹配（基于触发词确定性匹配）
      ↓
第二阶段：深度理解（在角色包视角下）
  - 意图识别、任务分类、资源预估
```

**关键洞察**：**确定性匹配打破循环依赖**。角色包匹配使用触发词精确匹配或正则匹配（不依赖语义理解），因此不需要角色包就能完成。第一阶段只做"原始理解"（提取触发词），第二阶段在角色包固定后做"深度理解"。

**适用范围**：任何 A 依赖 B、B 依赖 A 的双向依赖场景。解法不是打破一个方向，而是**在中间插入一个确定性步骤**，让其中一个方向变成确定性匹配而非语义匹配。

### 5.2 粘性缺失陷阱：每次触发都重新匹配

**问题**：角色包如果在每次外部输入时都重新匹配，会导致角色频繁切换，体验不稳定。

**表面方案**：匹配一次后永久固定，不再重新匹配——**这太死板了，用户想换角色怎么办？**

**真理源方案**：**粘性匹配**——首次匹配成功后锁定，但保留切换通道。

| 触发场景 | 匹配行为 | 说明 |
|---------|---------|------|
| 首次外部输入 | 全量匹配 | 匹配成功后，在当前会话中"锁定" |
| 后续外部输入 | 不重新匹配，沿用已锁定的 | 除非输入显式命中触发词 |
| 显式切换 | 用户主动请求替换 | 替换后新角色锁定 |
| 互斥触发词命中 | 自动切换 | 新旧角色包互斥时自动切换 |

**关键洞察**：**粘性不是"永不切换"，而是"不因无关输入而切换"**。切换的触发条件应该是显式的（用户主动请求或触发词命中），而不是隐式的（每次输入都重新匹配）。这需要角色包 frontmatter 声明 `exclusiveWith` 字段来定义互斥关系。

**适用范围**：任何需要"首次匹配后固定，但保留切换通道"的场景。本质是**状态粘性**——状态在首次初始化后保持稳定，但保留被显式事件改变的能力。
