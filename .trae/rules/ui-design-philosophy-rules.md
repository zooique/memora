# UI 设计哲学心智模型

> 本文件回&#x7B54;**「UI 怎么设计才符合用户直觉」**（设计决策层）；[ui-engineering-mindset-rules.md](./ui-engineering-mindset-rules.md) 回&#x7B54;**「UI 代码怎么写才一致」**（工程执行层）。先有设计哲学，再有工程执行，最后落地为令牌与组件。
> **种子命题**：UI 是用户心智的地形图——难用来自「信息没层级、动作没预期、状态没反馈」，而非信息多。

## 一、信息架构——一屏只讲一件事

**原则**：界面的首要职责不是「展示全部信息」，而是「告诉用户现在该看哪里」。信息密度不是罪，信息没有层级才是。

| 类型 | 心智规则 |
| --------- | ---------------------------------------------------------------------------------- |
| **DO** | **一屏一个主焦点**——每视图须有一个「此刻最该看 / 最该做」的元素，其余皆次级。主焦点靠位置（中央 / 顶部）+ 尺寸 + 对比三重标记，**不靠标签文字** |
| **DO** | **主次靠视觉层级**——层级差用位置 / 字号 / 留白 / 色彩表达。若两个同等重要的元素必须靠「重点」「重要」文字标签区分 = 层级设计失败；标签是最后手段 |
| **DO** | **相关元素物理聚合**——时间上连续操作的东西，空间上必须相邻（工具调用↔结果、错误↔修正入口、设置↔说明）。空间距离 = 心智距离 |
| **DON'T** | **一屏塞满同等重量的元素**——扫一眼说不出「这界面要我做什么」即失败。优先砍次级信息，而非压缩全部 |
| **DON'T** | **为「完整」牺牲「可读」**——全部功能平铺首屏不是完整，是失焦。完整属于文档，可读属于界面 |

## 二、用户直觉——控件形态即心智模型

**原则**：用户对「什么可点、什么可读、什么会变化」有跨产品通用预期。违背直觉 = 让用户为理解你的特殊设计付费。

| 类型 | 心智规则 |
| --------- | ------------------------------------------------------------------------------------------- |
| **DO** | **按钮像按钮，卡片像卡片**——可交互元素须有交互视觉承诺（边框 / 背景 / hover）。看似静态却可点 → 用户漏掉；看似按钮却不可点 → 用户受挫 |
| **DO** | **遵循平台隐喻**——文本输入是输入框、选项是选择控件、折叠是 `details/summary`、进度是条。界面应说平台的方言，而非发明新方言 |
| **DO** | **动作与后果一致**——危险操作（删除 / 覆盖 / 推送）与安全操作（查看 / 编辑）须有明确强度差。破坏性动作降噪（次要色 / 低对比），不可逆动作双保险（确认 + 二次确认） |
| **DON'T** | **发明用户没见过的交互**——自定义手势、隐藏快捷键、只有 hover 才出现的操作，普通用户永远发现不了。任何「需要文档解释才能用」的交互都是设计债 |
| **DON'T** | **让状态伪装成静态**——loading 像空态、disabled 像不可用、错误像正常，都是视觉欺骗。状态的视觉必须诚实 |

## 三、渐进披露——高频永远可见，低频藏进二级

**原则**：「高频操作零成本，低频操作可发现」。与内核 Skills 的 L1 / L2 / L3 渐进披露同构——常驻的常驻，按需的按需。

| 类型 | 心智规则 |
| --------- | --------------------------------------------------------------------------- |
| **DO** | **高频操作永远可见**——每轮都用的操作（发送 / 停止 / 新对话）零点击直达，不藏进菜单 / 折叠 / 右键 |
| **DO** | **低频功能渐进披露**——低频但合法（高级设置 / 导出 / 调试）藏进二级菜单、设置面板或 `details`，「可发现但不相扰」替代「全部平铺」 |
| **DO** | **披露层级与频率成反比**——先问「普通用户多久用一次」：每天用的一级，每周二级，每月三级 |
| **DON'T** | **低频侵占高频的空间**——「导出 JSON」与「发送」占同等视觉重量 = 告诉用户「两个都常用」，这是谎言 |
| **DON'T** | **用「全部展开」回避层级决策**——所有 `details` 默认展开、高级选项全平铺，是放弃设计而非简化 |

## 四、状态可见——loading / 空态 / 错误是设计的一部分

**原则**：四种状态（内容 / 空 / 加载 / 错误）必须全部被设计，不是只设计内容态、其余「出错再说」。

| 类型 | 心智规则 |
| --------- | -------------------------------------------------------------------------- |
| **DO** | **加载有反馈**——超过 ~300ms 的操作须有 loading 指示（骨架屏 / 进度条 / spinner）。没反馈的等待 = 用户以为卡死 |
| **DO** | **空态有引导**——空列表 / 空结果须告诉用户「这里本应有什么 + 怎么让它出现」，而非一片空白或「暂无数据」 |
| **DO** | **错误有出口**——错误提示须含「发生了什么 + 为什么 + 怎么修」，且修复入口与错误信息相邻。只报错没出口 = 让用户对着错误发呆 |
| **DO** | **状态切换有过渡**——内容↔空↔加载之间须有可感知过渡（淡入 / 骨架 / 禁用态），生硬跳变让用户无法追踪 |
| **DON'T** | **用「暂无数据」搪塞空态**——空态是最重要的引导时刻，一句「暂无数据」浪费了唯一一次教用户的机会 |
| **DON'T** | **让错误静默**——被吞掉的错误（catch 后不提示、失败后无反应）比报错更糟：用户会重复触发失败，最终认为产品坏了 |

## 五、评审流程——用哲学审查 UI

> 每个视图 / 面板新增或改动时过一遍。任一条不通过 = 需先给出设计理由（与令牌铁律同级，违反须注释说明）。

### 五.1 单视图评审八问

| # | 问题 | 章节 |
| - | ---------------------------------------- | -- |
| 1 | 「主焦点」是什么？扫一眼能说出「现在该看哪」吗？ | §一 |
| 2 | 主次靠位置 / 尺寸 / 对比表达，还是靠文字标签？ | §一 |
| 3 | 时间上连续的操作，空间上相邻吗？ | §一 |
| 4 | 可交互元素都有交互视觉承诺吗？（border / hover / active） | §二 |
| 5 | 高频操作零点击可达吗？低频在二级吗？ | §三 |
| 6 | 四种状态都设计了吗？空态有引导、错误有出口吗？ | §四 |
| 7 | 有「需要文档解释才能用」的交互吗？ | §二 |
| 8 | 信息密度 OK 吗？还是「为完整牺牲可读」？ | §一 |

### 五.2 跨视图一致性评审（含 Agent 维度）

| # | 问题 | 章节 |
| -- | ------------------------------------- | -- |
| 9 | 相似信息在所有视图用相同形态吗？（按钮语义 / 状态色 / 卡片结构） | §二 |
| 10 | 操作强度跨视图一致吗？ | §二 |

| 13 | 自主等级徽章在所有面板位置一致吗？ | §七 |
| 14 | Agent 建议都在正确上下文中出现吗？（而非凭空出现在对话框） | §七 |

## 六、与工程执行层的分界

| 维度 | 设计哲学（本文件） | 工程执行（工程文件） |
| -------- | ------------------- | ------------------ |
| **回答** | 为什么这样设计 | 怎么写出一致 |
| **关注** | 信息架构 / 用户直觉 / 状态 | 令牌 / 组件 / 生命周期 |
| **评审对象** | 界面决策（主焦点 / 层级 / 状态） | 代码结构（复用 / 抽象 / 契约） |
| **判定** | 符合直觉吗 | 写对了吗 |
| **落地顺序** | 先 | 后 |

> **铁律**：两层不可互相绕过——「工程上方便这样写」不是「设计上应该这样」的理由；「直觉上想要这样」不是「裸值写在组件里」的理由。**两层必须同时成立。**

## 七、Agent 信任设计——信任是增量建立的，不是二元授予的

**原则**：Agent 产品的核心 UX 不是"好不好看"，而是"用户敢不敢让它做"。信任不是预设的，靠一次次小成功积累——每次正确执行 = 信任 +1，每次出错 = 信任 -N。UI 必须让用户**看得见信任的建立过程，随时有撤销的权力**。

| 原则 | 心智规则 |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| **信任即货币，增量建立** | 信任不是"你必须信任我"的宣言，而是"我通过 5 次正确操作赢得了你的信任"。UI 体现：首次建议模式 → 3 次成功后升级执行模式 → 用户可随时回退。信任等级与自主权限绑定 |
| **置信度可视化** | Agent 输出不是"全对或全错"——须显示置信度（绿 / 琥珀 / 红三级）。高置信可直接执行，中置信需确认，低置信建议但标注"不确定"。让用户知道"何时该介入、何时可放手" |
| **逃逸舱原则** | 每个 Agent 操作须有「撤销 / 中断 / 覆盖」三条通道。撤销：30s 内可回滚破坏性操作（软确认）。中断：执行中随时可停。覆盖：用户可在 Agent 输出基础上修改再执行——AI 是协作者，不是决策者 |
| **上下文感知三要素** | agentic 界面 = **context-aware**（在正确的上下文出现）+ **transparent**（让用户知道发生了什么）+ **controllable**（让用户掌控节奏）。Agent 建议应在用户正在操作的文件 / 面板旁 inline 出现，而非凭空出现在对话框 |
| **自主等级显式化** | 自主模式不是系统内部决策，而是用户可见的状态标记。当前模式（建议 / 执行 / 审批）须以视觉徽章常驻任务旁，"扫一眼就知道 Agent 现在能做什么、不能做什么" |

> **与前文衔接**：置信度可视化 → §四状态可见的延伸（"状态"含 Agent 对自己的信心）；逃逸舱 → §二用户直觉的延伸（可中断的 Agent 才敢用）；上下文感知 → §一信息架构的延伸（Agent 输出是"补充"而非"干扰"）。
