# UI 设计哲学心智模型

> 继承[资深程序员心智模型](./programmer-mindset-rules.md)与格物哲学（第一性原理 / 单一真理源 / 生长而非堆砌 / 复杂度守恒）。
> 本文件回答的是**「UI 怎么设计才符合普通用户直觉」**——设计决策层；
> [ui-engineering-mindset-rules.md](./ui-engineering-mindset-rules.md) 回答的是**「UI 代码怎么写才一致」**——工程执行层。
> 两者正交：先有设计哲学（本文件），再有工程执行（工程文件），最后落地为令牌与组件。
>
> **种子命题**：UI 是「用户心智的地形图」。每一个界面决策都是「用户此刻在想什么、下一步想做什么」的镜像。
> 复杂不等于难用——难用来自「信息没有层级、动作没有预期、状态没有反馈」。

## 一、信息架构——一屏只讲一件事

**原则**：界面的首要职责不是「展示全部信息」，而是「告诉用户现在该看哪里」。信息密度本身不是罪，信息没有层级才是。

| 类型 | 心智规则 |
| ---- | ---- |
| **DO** | **一屏一个主焦点**——每个视图必须有一个「用户此刻最该看/最该做」的元素（主消息、主操作、主状态）。其他都是次级。主焦点靠位置（中央/顶部）+ 尺寸（更大）+ 对比（更强）三重标记，而非靠标签文字强调 |
| **DO** | **主次靠视觉层级，不靠标签**——层级差用位置、字号、留白、色彩表达。如果两个同等重要的元素必须靠「重点」「重要」这类文字标签区分，说明层级设计失败——标签是信息的最后手段，不是第一手段 |
| **DO** | **相关元素物理聚合**——用户在时间上连续操作的东西，在空间上必须相邻。工具调用与它的结果相邻、错误与它的修正入口相邻、设置与它的说明相邻。空间距离 = 心智距离 |
| **DON'T** | **不要一屏塞满同等重量的元素**——如果用户扫一眼无法说出「这个界面要我做什么」，信息架构已失败。优先砍次级信息，而非压缩全部 |
| **DON'T** | **不要为「完整」牺牲「可读」**——把全部功能平铺在首屏不是完整，是失焦。完整属于文档，可读属于界面 |

## 二、用户直觉——控件形态即心智模型

**原则**：用户对「什么东西可点、什么东西可读、什么东西会变化」有跨产品的通用预期。违背直觉 = 让用户为「理解你的特殊设计」付费。

| 类型 | 心智规则 |
| ---- | ---- |
| **DO** | **按钮看起来像按钮，卡片看起来像卡片**——可交互元素必须有交互的视觉承诺（边框/背景/悬停态/hover 反馈）。一个看似静态的元素如果可点击，用户会漏掉它；一个看似按钮的元素如果不可点，用户会受挫 |
| **DO** | **遵循平台隐喻**——文本输入是输入框、选项是选择控件、折叠是 `details/summary`、进度是条。用户已熟悉操作系统与编辑器平台的交互语言，界面应「说同一种方言」而非发明新方言 |
| **DO** | **动作与后果一致**——危险操作（删除/覆盖/推送）与安全操作（查看/编辑）在视觉上必须有明确的强度差。破坏性动作降噪（次要色/低对比），不可逆动作双保险（确认 + 二次确认） |
| **DON'T** | **不要发明用户没见过的交互**——自定义手势、隐藏的快捷键、只有 hover 才出现的操作，普通用户永远发现不了。任何「需要文档解释才能用」的交互都是设计债 |
| **DON'T** | **不要让状态伪装成静态**——loading 看起来像空态、disabled 看起来像不可用、错误看起来像正常，都是视觉欺骗。状态的视觉必须诚实 |

## 三、渐进披露——高频永远可见，低频藏进二级

**原则**：界面遵循「高频操作零成本，低频操作可发现」。与内核 Skills 系统的 L1/L2/L3 渐进披露同构——常驻的常驻，按需的按需。

| 类型 | 心智规则 |
| ---- | ---- |
| **DO** | **高频操作永远可见**——用户每轮都用的操作（发送/停止/新对话）必须零点击直达，不能藏在菜单/折叠/右键里 |
| **DO** | **低频功能渐进披露**——低频但合法（高级设置/导出/调试信息）藏进二级菜单、设置面板或 `details` 折叠，用「可发现但不相扰」替代「全部平铺」 |
| **DO** | **披露层级与使用频率成反比**——使用频率越高，披露层级越浅。判断披露层级前先问「这个操作普通用户多久用一次」——每天用的一级，每周用的二级，每月用的三级 |
| **DON'T** | **不要为低频功能侵占高频功能的空间**——一个「导出 JSON」按钮和「发送」按钮占同等视觉重量，等于告诉用户「两个都常用」——这是谎言 |
| **DON'T** | **不要用「全部展开」回避层级决策**——把所有 `details` 默认展开、把所有高级选项平铺，是放弃设计而非简化设计 |

## 四、状态可见——loading/空态/错误是设计的一部分

**原则**：界面的四种状态（内容态/空态/加载态/错误态）必须全部被设计，不是只有内容态被设计、其余「出错再说」。状态透明 = 用户始终知道发生了什么。

| 类型 | 心智规则 |
| ---- | ---- |
| **DO** | **加载有反馈**——超过 ~300ms 的操作必须有 loading 指示（骨架屏/进度条/spinner）。没有反馈的等待 = 用户以为卡死 |
| **DO** | **空态有引导**——空列表/空结果必须告诉用户「这里本应有什么 + 怎么让它出现」，而非一片空白或「暂无数据」四个字 |
| **DO** | **错误有出口**——错误提示必须包含「发生了什么 + 为什么 + 怎么修」，且修复入口与错误信息相邻。只有报错没有出口 = 让用户对着错误发呆 |
| **DO** | **状态切换有过渡**——内容态↔空态↔加载态之间应有可感知的过渡（淡入/骨架/禁用态），生硬跳变让用户无法追踪状态变化 |
| **DON'T** | **不要用「暂无数据」搪塞空态**——空态是最重要的引导时刻，一句「暂无数据」是浪费了唯一一次教用户的机会 |
| **DON'T** | **不要让错误静默**——被吞掉的错误（catch 后不提示、失败后无反应）比报错更糟：用户会重复触发、重复失败、最终认为产品坏了 |

## 五、评审流程——用哲学审查 UI

> 每个视图/面板新增或改动时，按此流程过一遍。任何一条不通过 = 需要先设计理由（与令牌铁律同级，违反需注释说明）。

### 五.1 单视图评审八问

| # | 问题 | 对应章节 |
|---|------|---------|
| 1 | 这个视图的「主焦点」是什么？用户扫一眼能说出「现在该看哪」吗？ | §一 信息架构 |
| 2 | 主次元素是靠位置/尺寸/对比表达层级，还是靠文字标签？ | §一 信息架构 |
| 3 | 时间上连续的操作，空间上相邻吗？ | §一 信息架构 |
| 4 | 可交互元素都有明确的交互视觉承诺吗？（border/hover/active） | §二 用户直觉 |
| 5 | 高频操作零点击可达吗？低频操作在二级吗？ | §三 渐进披露 |
| 6 | 四种状态（内容/空/加载/错误）都设计了吗？空态有引导、错误有出口吗？ | §四 状态可见 |
| 7 | 有「需要文档解释才能用」的交互吗？（隐藏手势/只有 hover 才出现） | §二 用户直觉 |
| 8 | 信息密度 OK 吗？还是「为完整牺牲可读」？ | §一 信息架构 |

### 五.2 跨视图一致性评审

| # | 问题 | 对应章节 |
|---|------|---------|
| 9 | 相似信息在所有视图用相同形态表达吗？（同样的按钮语义、同样的状态色、同样的卡片结构） | §二 用户直觉 |
| 10 | 操作强度跨视图一致吗？（危险操作在所有视图都是同一视觉强度） | §二 用户直觉 |

## 六、与工程执行层的分界

> 设计哲学（本文件）与工程执行（ui-engineering-mindset-rules.md）是同一系统的两层，不是两套标准。

| 维度 | 设计哲学（本文件） | 工程执行（工程文件） |
| ---- | ---------------- | ------------------ |
| **回答** | 为什么这样设计 | 怎么写出一致 |
| **关注** | 信息架构 / 用户直觉 / 状态 | 令牌 / 组件 / 生命周期 |
| **评审对象** | 界面决策（主焦点 / 层级 / 状态） | 代码结构（复用 / 抽象 / 契约） |
| **判定** | 符合直觉吗 | 写对了吗 |
| **落地顺序** | 先 | 后 |

> **铁律**：设计决策（本文件）不可被工程实现绕过——「工程上方便这样写」不是「设计上应该这样」的理由。反过来，工程实现（工程文件）不可被设计直觉绕过——「直觉上想要这样」不是「裸值写在组件里」的理由。两层必须同时成立。

## 七、Agent 信任设计——信任是增量建立的，不是二元授予的

**原则**：Agent 产品的核心 UX 挑战不是"好不好看"，而是"用户敢不敢让它做"。信任不是预设的，是通过一次次小成功积累的——每次 Agent 正确执行 = 用户信任 +1，每次出错 = 信任 -N。UI 必须让用户**看得见信任的建立过程，随时有撤销的权力**。

**行业共识**（2026 Agent UX 趋势）：

| 原则 | 心智规则 |
| ---- | ---- |
| **信任即货币，增量建立** | 信任不是"你必须信任我"的宣言，而是"我通过 5 次正确操作赢得了你的信任"的结果。UI 体现为：首次交互是建议模式 → 3 次成功后自动升级为执行模式 → 用户可随时回退。信任等级与自主权限绑定，等级越高权限越大 |
| **置信度可视化** | Agent 的输出不是"全对或全错"——必须显示置信度（如绿/琥珀/红三级标记）。高置信度可直接执行，中置信度需用户确认，低置信度建议但标注"不确定"。置信度让用户知道"什么时候该介入，什么时候可以放手" |
| **逃逸舱原则** | 每个 Agent 操作都必须有"撤销/中断/覆盖"三条通道。撤销：30s 内可回滚破坏性操作（软确认）。中断：Agent 执行中随时可停止。覆盖：用户可在 Agent 输出基础上修改再执行——AI 是协作者，不是决策者 |
| **上下文感知三要素** | 优秀的 agentic 界面 = **context-aware（在正确的上下文中出现）+ transparent（让用户知道发生了什么）+ controllable（让用户掌控节奏）**。Agent 的建议不应凭空出现在对话框，而应在用户正在操作的文件/面板旁以 inline 形式出现 |
| **自主等级显式化** | 自主模式不是"系统内部决策"，而是用户可见的状态标记。当前模式（建议/执行/审批）必须以视觉徽章形式常驻任务旁，让用户"扫一眼就知道 Agent 现在能做什么、不能做什么" |

**与设计哲学的衔接**：
- 置信度可视化 → 状态可见（§四）的延伸——"状态"不只指加载/空态，还包括"Agent 对自己的信心"
- 逃逸舱 → 用户直觉（§二）的延伸——"控件形态即心智模型"，可中断的 Agent 才是用户敢用的 Agent
- 上下文感知 → 信息架构（§一）的延伸——Agent 的输出是"补充"而非"干扰"
