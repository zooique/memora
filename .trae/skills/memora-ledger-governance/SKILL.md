# memora 台账治理

> 本技能是**操作入口**，不是规则本体。
> 规则唯一真源 = `tasks/archive/README.md` 七条纪律 ＋ `tasks/待完成任务.md` 头部「升档规则 / 状态字典」。
> 🔴 **本文件不复述任何一条规则文字。**实证（2026-10-27）：同一条纪律被抄进另一份参考文件后，两份**字面相反**——真源写「迁出后不再逐条留指针」，副本写「迁出后在原位置留一行指针」。需要规则原文 ⇒ 打开真源读，**别从本文件转抄**。

## 何时用

- 新增 / 修改 / 销项 `tasks/待完成任务.md` 的条目
- 观察区条目要不要做、什么时候做（升档）
- 迁档：把某版本已关闭项搬进 `tasks/archive/<version>-<kernel|host>.md`
- 折叠 / 整理台账（删区、并区、改写布局）
- 发版前台账核对，或 `local-ci` 的 `ledger:*` 步报红
- 怀疑台账里某句话是过期事实

## 坐标铁律

- **引用坐标 = 「归档文件路径 + 条目 ID」**，例：`archive/5.0.0-kernel.md` 的 `ARCH-GAP-1`。
- **区名不得当坐标**。实证：2026-10-26 把版本区折叠成索引表后，所有以「X.Y.Z 区」定位的行一次性失效（含指向本文件内不存在区的自指）。
- **对外文档不得引用台账内部坐标** —— 随 npm / vsix 发布的 md（含根 `CHANGELOG.md`）写了就是永久死链。要给证据就写外部可复算的形式（如 `git log <tagA>..<tagB> -- <path>`）。
- markdown 链接基准 = **源文件所在目录**。`tasks/` 下的文件必须写 `./archive/x.md` 而非 `./x.md`（2026-10-27 实测一处死链即由此而来）。

## 状态字典（只列机器会判的部分）

| 标记 | 语义 | 机械约束 |
| --- | --- | --- |
| ⏳ / 👁 | 观察 / 待拍板，版本未定 | 条目内必须写明触发条件 |
| 📌 | 待执行：已拍板、待人或机落地 | **正文必须含一行 `完成判据：`**，缺即被 hygiene 门拦 |
| ✅ | 完成 | 不即迁，随下一次真发版整批归档 |

- 语义定义全文在主台账头部「升档规则」，本表不复制第二份。
- **升档 = 改状态标记，不改落点**；禁止再写「升到某版本区」（那些区已不存在）。

## 三道门（分工互不覆盖）

| 步骤 | 命令 | 语义 | 档位 |
| --- | --- | --- | --- |
| `ledger:hygiene` | `npm run verify:ledger-hygiene` | 工作树语义：台账**当前结构**合不合纪律（判据集合见脚本头部注释，**此处不写死数量**——数量会随判据增删而漂移） | 硬闸 full |
| `ledger:fold` | `npm run verify:ledger-fold` | git 区间语义：本次改动**移走了什么**，每条须在归档有副本 | 硬闸 full |
| `ledger:receipt` | `npm run verify:ledger-receipt` | 提交 vs 台账是否同步 | 告警 |

- hygiene 支持 `--self-test`（变异探针逐个验证判据不失明，探针随判据增删）；fold 支持 `--base` / `--head` / `--since`。
- ⚠️ **自检本身也会失明**，且与「跑没跑自检」是两件事 —— 见核查清单「自检不许从台账存量抽锚行」。
- 🔴 **改完门脚本必跑 `--self-test`**：绿 ≠ 有判力，只有探针能把门转红才算数。

## 动作 → 该跑什么

| 你要做的事 | 提交前必跑 | 备注 |
| --- | --- | --- |
| 改条目状态 / 正文 | hygiene | 新增 📌 必须补完成判据行 |
| 整区折叠 / 删除 / 搬家 | **fold** | 折叠前跑与提交前跑都行，**但不能不跑** |
| 迁档归档 | fold + hygiene | 折走的条目若归档查无副本即红 |
| 发版前核对 | 两者 + receipt | 发行动作本身另有技能，见真源索引 |
| 改了对外文档 | `npm run docs:links` | **改完再跑**——先跑后改等于白跑 |

## 台账剪枝（瘦身）范式

> 触发：台账行数膨胀、观察区读不动、或有人问「哪些是过渡记录可以清理」。

**先量化，再动刀。** 🔴 凭段落印象提建议必然给错收益预估——2026-10-30 一个会话里被数据推翻三次：

| 先前的印象 | 实测 | 错的成因 |
| --- | --- | --- |
| 「状态符号膨胀到 40+ 种」 | 观察区只有 **10** 种，⏳ 独占 72/91（79%） | 按全文字符串计数，把正文散文里的「已评估 / 已并入」误计成状态符号 |
| 「不推进区 20 条可压掉 40 行」 | 其中 **15 条本来就只有 2 行** | 只看区总行数，没做条目粒度分布 |
| 「7 条已结束条目是僵尸，可销项」 | 首行自带活项：`PHRASE-SCAN-1` 写「余项登记待触发」、`MEM-GOV-1` 挂报告指针 | 把「状态已结束」当成「不再需要存在」——它们占观察区是**防重提真源**，销项即丢锚点 |

⇒ 动手前先跑一遍条目粒度盘点（每区条数 / 每条行数 / 状态分布 / 关键字段覆盖度），**结论只认当场重扫的数**。

**超长条目 = 整段迁归档 + 原位重写判据版，不逐行删流水。** 实证 `D1-MCP`（99 → 12 行）：流水行（`→ 第 N 步 … ✅ 已落地 → 收据见 archive §X`）与活观察项**逐行交织**，按行删必误伤判据；且那些单行本身是**廉价索引**，删了反而降可追溯性。正确动作 = 整段原文迁进对应版本归档（逐字不改）＋ 原位留「定案形态 / 豁口结论 / 仍开放项 + 指针」。fold 门不报（条目仍在册，只是正文精简）。

**体量上限 = 观察区单条目 40 行**（hygiene 判据）。超出即混入过程叙述 ⇒ 按上一条处置，**改阈值即门失明**，不为单条让路。注记类 / 明确不推进区**不设限**——那里的长文是防重提论证，删即失值。

**头部只留现行指令。** 头部是每会话必读的第一屏，而历史沿革（分级方式变更 / 归元说明 / 形态说明）是**已发生的事实**、不是**要执行的指令** ⇒ 整段迁 `archive/README.md`，头部只留销项流程 / 升档规则 / 排序原则 / 登记规范。

## 观察区是单向阀（结构性事实 + 两道出口）

纪律 3（观察项永不随发版归档）+ D6（无触发不行动）合起来 = **只进不出**：每会话排雷都会新登记观察项，销项只在真发版时批量发生 ⇒ **归档越勤，观察区占比越高**（2026-10-30 实测：刚归档 27 项，观察区仍占全区 76%）。这是纪律设计的结果，不是归档没生效。

两道出口（hygiene 判据；纪律真源 = 主台账头部「登记规范」）：

| 阀 | 判据 | 为什么这样定 |
| --- | --- | --- |
| 体量 | 观察区单条目 >40 行即红 | 阈值取**存量归零后**的实测上限并留余量 ⇒ 建门即可为硬闸。行数不是条目数撑的——绝大多数条目只有 2-3 行，是极少数超长条目撑的（建门实测见脚本头注 ⑫） |
| 保质期 | **新登记**观察项缺「到期复查 YYYY-MM-DD」即红 | 建门时实测只有极少数写了复查日期（数量见脚本头注 ⑬）。**刻意只卡新流入**：全量硬闸会让门一建就被存量淹没，进而重演「把闸调回告警」的老路 |

⇒ 一个无限期不触发的观察项价值≈0，却永久占用每会话阅读成本。**登记时顺手写一行复查日期**，是这套机制唯一的维护成本。

## 技能放哪儿：两个轴分开看

技能存放涉及两件彼此独立的事，历史上把它们混成一条结论，导致来回折腾：

| 落点 | 进仓库 / 团队可共享 | 是否自动加载（本会话实测） |
| --- | --- | --- |
| `.trae/skills/` | ✅ 是（`git ls-files .trae/skills` 可自证） | ⚠️ 未见：本会话技能列表不含其中任何一项 |
| `{workspace}/.workbuddy/skills/` | ❌ 否 —— 被 `.gitignore` 第 40 行的 `.workbuddy/` 挡住 | ⚠️ 未见（`project-onboarding` 格式合法却不在列表中） |
| `~/.workbuddy/skills/` | ❌ 否（机器本地，不入任何仓库） | ✅ 是 |

> 加载轴的硬证据（2026-10-27）：技能扫描缓存的 `scopeKey` = `[~/.workbuddy, ~/.workbuddy/skills, <内置插件目录>, ~/.workbuddy/skills-marketplace, …]`——**不含任何工作区路径**；58 条收录项里 `source` 分布 = userSettings 38 / builtin 19 / plugin 1，`.trae/skills` 下的技能一条都没有。

由此定出的形态，兼顾两轴而**不产生第二份规则**：

- **规则正文 = 本文件**（落在 `.trae/skills/memora-ledger-governance/SKILL.md`，随仓库走、团队可见、可 diff）。
- **用户级同名文件降级为纯指针存根**：只写「真源在哪」，不含任何规则文字 ⇒ 结构上无从漂移。
- 🔴 **改本技能时改仓库这一份**，别改存根；存根若被「顺手补全」，漂移立即复现。
- 换机器 / 重装：clone 后即有完整规则；若某工具链不自动加载，显式读本文件同样可用。

## 对抗式核查清单

- 🔴 **绿 ≠ 合规**：hygiene 的 ①②③ 投放面是「区」，主台账归元后已无版本区 ⇒ 恒空恒绿。有投放面的是 ⑤⑥⑦（版本索引三方一致 / 待执行完成判据 / 版本索引↔README 归档表）。看到「0 命中」先问有没有投放面。
- 🔴 **存在性回查 ≠ 指针有效性回查**：「按 ID 逐个回查、净丢失 0」只证明**还在册的**条目没丢。真判据是「**移走的**每条都能在归档找到」（= fold 门）。2026-10-26 那次折叠前者绿、后者抓出一整条从未落任何归档的收据。
- 🔴 **计数一律当场重扫实测**，不采信任何清点快照（含本文件写过的一切数字）。
- 🔴 **同一事实两处登记必漂移**：归档文件清单在主台账「版本索引」与 `archive/README.md` 归档表各记一份（当前集合**相等**）。2026-10-27 起该事实由 hygiene **⑦** 机器校验（双向集合相等）——改一处必须同步另一处，否则门会红。
- 🔴 **候选门 ⑦「技能层禁写已废弃形态」不装（2026-10-27 拍板）**：「已废弃形态」的边界无法机械定义，装了必然假红或漏检（同「全仓坐标门」教训）；改由停用声明（技能头注 + 本清单）+ 人工审查覆盖。
- ✅ **已删除的第二真源**（2026-10-27）：原 `references/archive-discipline.md` 的纪律 7 与真源**字面相反**（真源：不再逐条留指针；旧件：原位置留一行指针），文件已删除（git 历史可查），勿从历史版本转抄。
- 🔴 **测试红先看口径**：隔离串行复跑该文件（`vitest run <file> --no-file-parallelism`），仍红才是真回归；余见 `docs/测试并发确定性与flake判定SOP.md`。**别反过来把 `--no-file-parallelism` 写成常驻默认**——那已是另一个方向的问题。
- 🔴 **自检不许从台账存量抽锚行**（2026-10-30 血训）：⑩ 克隆自检曾用正则从台账正文抽一行当克隆源，两次剪枝把那行迁进归档后 ⇒ **注入未生效 ⇒ 自检红，而判据本身完好**——判据没坏，样例锚点没了。**推论：台账每剪一次枝，任何「从存量抽锚行」的自检都可能静默失明** ⇒ 变异探针一律自带确定性文本，与被检文档正交。这条补在「改完门脚本必跑 `--self-test`」之上：不仅要跑，还要确认自检的样例**不依赖易变存量**。
- 🔴 **门与纪律必须同源**：新增 hygiene 判据时，纪律真源要同步写进**主台账头部明文**（不是脚本私设），两边互指、写明「改这里必须同步那里」。反向实证：本文件曾写「六类 / 七类判据」，而实际判据数早已继续增长 ⇒ **在文档里复述判据数量本身就是漂移源**；现已改为只写真源路径、不写数字。
