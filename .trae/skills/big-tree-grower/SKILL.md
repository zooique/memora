# 大树模型项目生长器（匠码）

基于大树模型项目工程哲学，将日常迭代开发中的高频操作封装为标准流程。生长器负责养树——让代码项目长得对（规范一致）、长得壮（测试通过/无漏洞）、长得美（前端审美独特），三者浑然一体，不可分割。

**角色定位**：播种机（seeder）负责"扎根"，**生长器（grower）负责"养树"**。

大树模型术语在代码项目中的映射：
- 矛盾 → 需求冲突 / 技术债务
- 模块 → 服务 / 组件
- 枝叶 → 功能 / 页面
- 修剪 → 代码清理 / 重构
- 根系 → `.trae/rules/` / 架构约束

## 核心执行骨架

多数 grower 模式遵循共享流程。各入口在 reference 文件中只描述差异，不重复通用步骤。

```
加载项目规则 → 分析/诊断 → 三分类 → 执行 → 审核 → 归档任务清单
```

**例外**（独立流程，不适用以上骨架）：
- **问诊**（12）— 门控模式：加载 → 评审 → 二选一判定。不执行修改
- **剪枝**（7）— 识别冗余 → 安全确认 → 删除 → 提取升级候选 → 归档
- **版本发布**（11）— 前置检查 → 变更读取 → Semver 判断 → 打 tag → 记录
- **模块重思**（4）— 分析 → 设计 → 产出方案文档。不执行代码修改

> 本 Skill 依赖项目已有的 `.trae/rules/` 体系。执行任何操作前，必须先读取规则文件，建立抽象术语到项目实际实现的映射。

## 大树模型核心原则

| # | 原则 | 生长器视角 |
|---|------|-----------|
| 1 | 根系优先 | 新产出必须在现有规则约束下生长，不破坏架构分层 |
| 2 | 自然生长 | 出现 3 次以上相同模式才提取；不提前抽象，不强塞模式 |
| 3 | 各层独立 | 业务产出（枝叶）修改不影响公共组件（躯干），躯干增强不破坏规则（根系） |
| 4 | 反馈回路 | 每次迭代完成后检查：是否需要修剪？是否需要更新规则？ |

## DO/DON'T 清单

### ✅ 必须做

**规则与上下文**：操作前必须加载相关 `.trae/rules/` 规则文件，理解后再执行。

**任务清单维护**：方案生长/提交前审查 → 必须更新唯一台账 `tasks/待完成任务.md`；已完成条目**标 ✅ 留册**，不得直接删除；每真发一版时随版本号整区归档到 `tasks/archive/`。

**修复质量**：速修必须定位根本原因；每次修改后检查关联产出是否有同类问题；零引用才可删除。

**审核与收尾**：任何模式禁止跳过审核；修复后做简洁性检查；年轮审判修改规则后维护 ADR。

**健康度/安全**：诊断/审计完成后归档可行动问题到 `tasks/待完成任务.md`。

**测试**：补测试先读现有测试文件再生成；补测试后运行项目测试命令；测试回归对失败做分类（过期/回归/环境）。

**数据库**：迁移必须幂等 + 同步更新全量建表脚本。

**发布**：确认审查+测试全通过后判断 Semver 再打版本。

**排雷**：必须基于已存在的方案文档；逐步骤推演不可跳过任何环节；排雷后必须产出优化方案。

### ❌ 禁止做

- 禁止跳过审核（任何模式）
- 禁止无方案直接做产出（方案生长）
- 禁止规则对齐单向修改
- 禁止速修做范围外"顺手优化"
- 禁止模块重思不产文档
- 禁止提交前审查不更新任务清单
- 禁止任务清单直接删除（必须销项留册）
- 禁止不到 3 次重复就提取抽象
- 禁止不确认引用就删除
- 禁止新枝破土产文档
- 禁止神木回天不确定时改架构
- 禁止斩木除根合并审核
- 禁止翠幕天罗跳过汇总审核
- 禁止年轮审判规则矛盾时强裁
- 禁止种木成林外任何模式改产出结构
- 禁止健康度诊断后不归档
- 禁止剪枝删 ADR 记录
- 禁止在产出中保留修改痕迹（"不是XX而是XX"句式、Bug原因/修复思路类注释、变更说明类注释）

- 禁止种木成林外任何模式改数据库 schema
- 禁止补测试不读现有测试文件
- 禁止补测试跳过项目测试命令
- 禁止测试回归跳过失败分类
- 禁止数据库迁移非幂等语句
- 禁止迁移后不更新全量建表脚本
- 禁止安全审计跳过 `security_rules.md` 和环境配置文件检查
- 禁止依赖审计升级 major 版有 breaking changes
- 禁止版本发布前不确认状态
- 禁止排雷无方案输入（必须已有方案文档或上轮方案更新产出）
- 禁止排雷只报告不修正（必须产出可直接执行的优化方案）

## 优先级规则

当多种建议冲突时，按以下优先级裁决（高→低）：

| 优先级 | 类别 | 说明 |
|--------|------|------|
| P1 | 安全性 | 安全漏洞、密钥暴露等必须立即修复 |
| P2 | 架构一致性 | 分层违规、越权调用优先处理 |
| P3 | 自然生长 | 遵循"3 次以上才提取"原则，不强塞模式 |
| P4 | 测试与代码质量 | 测试覆盖率达标、无死代码、无遗留调试日志 |
| P5 | 风格偏好 | 命名、格式等非关键优化 |

## 触发机制

### 被动触发

AI 根据用户意图自动识别入口，完整映射表见 [references/modes-guide.md](references/modes-guide.md)。

### 多模式串联

```
模块重思 → 方案更新 → 提交前审查
种木成林 → 全自动循环（神木回天→斩木除根→新枝破土→循环）
```

**常用串联链路**：

| 场景 | 链路 |
|------|------|
| 日常迭代 | 方案更新 → 提交前审查 |
| 模块重构 | 模块重思 → 产出方案文档 → 方案更新 |
| 健康闭环 | 神木回天 → 归档待办 → 斩木除根 |
| 规则同步 | 规则对齐 → 若规则本身待变更 → 在规则对齐/年轮审判中评估后修正 → 再规则对齐 |
| 健康诊断 | 检查大树健康 → 发现问题 → 剪枝 → 斩木除根 |
| 需求把关 | 问诊 → 接纳 → 方案更新 → 提交前审查 |
| 前置门控 | 问诊 {任意模式} → 驳回则终止 / 补充则暂停 / 接纳则执行指定模式 |
| 开奖惊喜 | 新枝破土 → 不满意 → 方案更新调整 |

| 排雷迭代 | 方案更新（设计） → 排雷 → 方案更新（执行） → 提交前审查 |
| 带安全审查 | 方案更新 → 安全审计 → 提交前审查 |
| 带测试 | 方案更新 → 补测试 → 测试回归 → 提交前审查 |
| 数据库变更 | 数据库迁移 → 补测试 → 测试回归 → 提交前审查 |
| 质量闭环 | 提交前审查 → 补测试 → 测试回归 → 安全审计 → (重复) |
| 发布收尾 | 提交前审查 → 依赖审计 → 发布版本 |
| 依赖维护 | 依赖审计 → 发现高危 → 速修升级 |
| 排雷把关 | 问诊 → 接纳 → 方案更新（设计） → 排雷 → 方案更新（执行） → 提交前审查 |

完整串联路径和全自动循环数据流见 [references/modes-guide.md](references/modes-guide.md)。

## 不适用场景

以下场景不应激活本 Skill：

- **尚未完成扎根的项目**：`.trae/rules/` 不存在或不完整 → 建议先使用 big-tree-seeder 完成扎根
- **单文件项目/探索性原型**：不需要完整的三层架构流程
- **纯信息查询**："这个函数是干什么的"这类问题

识别到以上场景时，告知用户并给出替代建议。具体话术见 [references/exit-speak-guide.md](references/exit-speak-guide.md)。

## 与播种机（seeder）的协作

播种机一次性扎根，产出 `.trae/rules/` + ADR + 创意设计单页纸 + 任务清单；生长器高频循环养树。两者通过 `.trae/rules/` 和 `tasks/待完成任务.md` 衔接。
