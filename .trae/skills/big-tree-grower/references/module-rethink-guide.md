# 模块重思模式 — 引导流程

本文档为模块重思模式（入口 4）提供详细的引导流程和方案文档模板。

---

## 模块重思的定位

模块重思是**需求层面**的工作，发生在写代码之前。它的产出是方案文档，为后续的方案生长模式（入口 1）提供输入。

```
模块重思 → 方案文档 → 方案生长 → 代码实现 → 提交前审查
```

---

## 引导流程

### 第 1 步：明确范围

向用户确认：

- 要重思的模块名称
- 当前模块的边界（涉及哪些页面、哪些后端模块）
- 是否有已经明确的方向或想法

### 第 2 步：现状分析

从代码层面分析当前模块：

- 读取模块相关的前端页面和后端 Service/Model
- 梳理当前实现的功能清单
- 识别当前存在的问题
- 分析模块与项目整体架构的关系

### 第 3 步：需求挖掘

从使用者角度思考需求：

| 角度       | 问题                                 |
| ---------- | ------------------------------------ |
| 使用者是谁 | 谁会使用这个模块？管理员？操作员？   |
| 核心任务   | 用户打开这个模块要完成什么核心任务？ |
| 痛点在哪   | 当前模块让用户感到困难的地方是什么？ |
| 数据需求   | 用户希望通过这个模块了解什么数据？   |
| 操作频率   | 哪些操作是高频的？哪些是低频的？     |
| 同类参考   | 同类产品是怎么设计这个功能的？       |

### 第 4 步：方案设计

基于分析结果设计改进方案：

1. **先定目标**：改进后用户使用这个模块的体验应该是怎样的
2. **再定方案**：需要做哪些改动来实现这个目标
3. **检查兼容**：改动是否与现有架构和功能兼容
4. **评估风险**：改动是否会影响其他模块

### 第 5 步：文档输出

将方案写入 `docs/` 目录（详见下方模板）。

### 第 6 步：方案确认

向用户呈现方案要点，确认后：

- 如果用户想立即执行 → 切换到方案生长模式
- 如果用户想先保留方案 → 记录文档，后续按需执行

## 方案文档模板

```markdown
# {模块名称} 重思方案

> 创建日期：{YYYY-MM-DD} 状态：设计中 / 已确认 / 已执行

## 一、现状分析

### 1.1 当前功能

- {功能点 1}
- {功能点 2}

### 1.2 存在的问题

| 问题       | 严重程度 | 影响       |
| ---------- | -------- | ---------- |
| {问题描述} | 高/中/低 | {影响说明} |

### 1.3 模块关系

- 上游依赖：{哪些模块依赖本模块的数据}
- 下游依赖：{本模块依赖哪些模块的数据}

## 二、需求分析

### 2.1 用户画像

- 使用者：{角色}
- 使用频率：{高频/中频/低频}
- 核心场景：{一句话描述}

### 2.2 用户期望

从使用者角度，他们希望通过这个模块：

1. {期望 1}
2. {期望 2}

### 2.3 设计参考

- 同类产品做法：{参考描述}
- 项目现有模式：{可以参考的本项目其他模块}

## 三、改进方案

### 3.1 改进目标

{用 1-2 句话描述改进后的理想状态}

### 3.2 具体改动

| 改动项   | 当前状态 | 目标状态 | 涉及文件   |
| -------- | -------- | -------- | ---------- |
| {改动 1} | {当前}   | {目标}   | {文件列表} |
| {改动 2} | {当前}   | {目标}   | {文件列表} |

### 3.3 分步执行计划

1. 步骤 1：{描述} — 依赖：无
2. 步骤 2：{描述} — 依赖：步骤 1
3. ...

### 3.4 兼容性评估

- 影响范围：{受影响的模块/页面}
- 风险等级：高/中/低
- 回退方案：{如何回退}

## 四、不做清单

明确不在本次改进范围内的内容：

1. {不做项 1} — 理由：{原因}
2. {不做项 2} — 理由：{原因}
```

## 典型场景示例

### 场景：审批模块重思

```
用户输入：模块重思：审批模块

AI 行为：
1. 聚焦"审批模块"
2. 分析现状：
   - 当前审批流水表格只显示 SKU 产品信息、货号、操作类型、数量、状态、申请人
   - 四种操作类型（出库/入库/退货/损耗）共用同一表格
   - 出库没有出库单信息 → 无法追溯到具体出库单
   - 入库没有预采购信息 → 无法追溯到具体采购单
   - 退货不知道退给哪个客户
3. 理解用户心智：
   - 审批者需要了解每次操作的完整上下文
   - 不同类型的操作关注的信息不同
4. 设计需求方案：
   - 方案 A：四种类型各自独立表格（用户原始思路）
   - 方案 B：保持统一表格 + 按类型动态显示关联信息列
   - 方案 C：统一表格 + 可展开的详情行
   → 评估后选择最合理的方案
5. 记录文档到 docs/
6. 呈现方案 → 用户确认 → 可衔接到方案生长
```
