# 规则对齐模式 — 操作指南

本文档为规则对齐模式（入口 3）提供详细的操作指南和判断标准。

---

## 前置约定映射

前置约定映射详见 [abstract-term-mapping.md](abstract-term-mapping.md)

## 对齐总则

规则对齐的核心原则是**双向对齐**——不是单向让代码符合规则，而是以"哪个更好"为标准：

```
规则合理 + 代码违规 → 改代码
代码更优 + 规则滞后 → 改规则
两者都合理但不同 → 选择对长期维护更有利的方案
两者都有问题 → 重新设计，同时更新规则和代码
```

## 交叉检查维度

### 维度 1：分层架构

| 检查项 | 规则要求 | 代码检查方式 |
|--------|---------|-------------|
| 路由处理层薄层 | 精简，零业务逻辑 | 搜索路由处理层文件中是否有条件判断、循环、数据库调用 |
| 业务逻辑层持业务逻辑 | 所有业务判断在此层 | 搜索业务逻辑层文件中是否使用了统一错误抛出机制、业务校验逻辑 |
| 数据访问层管映射 | 键名转换只在数据访问层 | 搜索其他层中的数据库命名约定字符串 |
| 事务隔离 | 事务内使用事务安全查询方法 | 搜索事务函数体内部是否使用了常规查询方法 |
| 导入别名 | 使用导入别名系统（读取 project-rules.md 确认） | 搜索跨目录的相对路径导入 `from '../` 和 `from '../../` |

### 维度 2：前端架构

| 检查项 | 规则要求 | 代码检查方式 |
|--------|---------|-------------|
| 页面入口 | 使用页面创建入口 | 搜索页面文件中是否直接操作 DOM 而非使用工厂 |
| 列表页 | 使用列表页工厂 | 搜索手动实现的搜索+分页+表格逻辑 |
| 刷新策略 | 用刷新方法而非重新加载方法 | 搜索重新加载方法是否在操作成功回调中被误用 |
| 响应式表格 | 遵循响应式表格约定 | 搜索表格标签是否缺少约定的 CSS 类 |
| 样式架构 | 遵循项目约定的样式分层 | 检查样式入口文件的导入顺序 |

### 维度 3：错误处理

| 检查项 | 规则要求 | 代码检查方式 |
|--------|---------|-------------|
| 业务错误 | 使用统一错误抛出机制（读取 error_handling_rules.md 确认） | 搜索原生的错误抛出语句（如 `throw new Error(` 等） |
| 错误码范围 | 按模块分段 | 检查新增错误码是否在正确范围内 |
| 响应格式 | 遵循项目约定的响应格式 | 搜索响应方法是否直接返回裸数据 |
| 异步错误 | 使用异步错误包装器或 try/catch | 搜索未包装的异步路由处理函数 |

### 维度 4：数据库规范

| 检查项 | 规则要求 | 代码检查方式 |
|--------|---------|-------------|
| 命名规范 | 数据库命名约定（读取 database_operations_rules.md 确认） | 检查 schema 定义和迁移脚本 |
| 迁移幂等 | 幂等的建表/修改语句 | 检查迁移脚本中的 CREATE/ALTER 语句是否有 IF NOT EXISTS 等幂等保护 |
| 约束机制 | 符合项目约定 | 检查约束是否按规范开启 |

### 维度 5：导入与模块

| 检查项 | 规则要求 | 代码检查方式 |
|--------|---------|-------------|
| 跨目录导入 | 使用导入别名系统（读取 project-rules.md 确认具体别名前缀） | 搜索跨目录的相对路径导入 |
| 同目录导入 | 相对路径 `./` 允许 | 无需检查 |

## 判断标准 — 决策树

当发现不一致时，按以下决策树判断：

```
发现不一致
  │
  ├── 规则要求的功能代码未实现？
  │     → 检查是否影响项目运行
  │         ├── 影响 → 优先级 P2，改代码
  │         └── 不影响 → 优先级 P4，记录到任务清单
  │
  ├── 代码实现了规则未提及的良好实践？
  │     → 评估该实践是否具有普适性
  │         ├── 普适且成熟 → 优先级 P3，更新规则
  │         └── 特例 → 保留代码，不更新规则
  │
  ├── 规则和代码都有道理但不同？
  │     → 比较长期维护成本
  │         ├── 代码方案维护成本更低 → 改规则
  │         ├── 规则方案维护成本更低 → 改代码
  │         └── 无法判断 → 保持现状，添加注释说明差异
  │
  └── 规则和代码都有问题？
        → 重新设计方案，同时更新规则和代码
```

## 对齐执行顺序

当发现多项不一致时，按以下顺序执行对齐：

1. **安全相关**（P1）— 立即处理
2. **架构违规**（P2）— 优先处理
3. **规则缺失**（P3）— 补充规则
4. **风格不一致**（P5）— 批量处理

**同优先级内的执行顺序**：
- 先修改底层（数据层/规则文档）再修改上层（路由处理层/前端页面）
- 先修改影响范围大的再修改影响范围小的
- 同类型问题批量处理（如所有导入别名问题一起修复）

## 对齐质量审核清单

对齐执行完毕后，逐项检查：

- [ ] 修改后的代码是否符合更新后的规则（或反之）？
- [ ] 对齐过程中是否引入了新问题？
- [ ] 是否清理了对齐过程中发现的冗余代码？
- [ ] 如果修改了规则，是否更新了对应的 ADR？
- [ ] 如果修改了规则，是否同步更新了 `architecture-quickref.md`（如涉及）？
- [ ] 对齐是否影响现有功能（需要回归测试的范围）？

## 典型场景示例

### 场景 1：规则要求但代码未遵守

```
发现：规则要求路由处理层是薄层，但某 Controller 中有业务判断逻辑
判断：规则合理，代码违规
行动：将业务判断逻辑迁移到业务逻辑层（Service），路由处理层保持薄层
优先级：P2
```

### 场景 2：代码实践优于规则

```
发现：代码中使用了统一的错误处理机制，但规则中没有提及
判断：这是成熟的最佳实践，具有普适性
行动：更新 error_handling_rules.md，添加错误处理机制的使用规范
优先级：P3
```

### 场景 3：两者都合理

```
发现：规则要求返回格式为 { code, message, data }，
      但某个模块返回了 { code, message, data, meta }
判断：meta 字段提供了额外的分页元信息，在特定场景有价值
行动：更新规则，允许在分页场景中添加 meta 字段
优先级：P3
```
