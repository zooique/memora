# 剪枝指南

> 用于 grower 手动入口 10"剪枝"（含躯干升级判断）
>
> 本文件是剪枝决策树和躯干升级信号的详细参考。

---

## 剪枝决策树

```
代码是否还被使用？
├── 是 → 保留
│   └── 是否有 3 个以上页面/模块复制了相同逻辑？
│       ├── 是 → 升级为躯干（提取到公共层）
│       │        在对应的 ADR 中记录躯干增长决策
│       │        详见下方"躯干升级信号表"
│       └── 否 → 保留原样
└── 否 → 检查类型，执行清理
    ├── 废弃的 API 路由 → 删除路由注册 + Controller + Service
    ├── 废弃的 Model 字段 → 先标记 @deprecated，下个大版本删除
    ├── 废弃的组件 → Grep 搜索确认零引用后删除
    ├── 废弃的 CSS → Grep 搜索类名确认零引用后删除
    ├── 废弃的规则文档 → 标记"已废弃"，不物理删除（保留年轮）
    ├── 废弃的工具函数 → Grep 搜索函数名确认零引用后删除
    └── 废弃的测试文件 → 确认对应源码已删除后清理
```

## 剪枝节奏

| 频率 | 范围 | 操作 | 预估时间 |
|------|------|------|---------|
| 每迭代末 | 枯枝清理 | 删除已确认废弃的代码、清理无引用的 CSS、删除调试代码 | 10 分钟 |
| 每大版本 | 深层修剪 | 审查整体架构、标记 @deprecated、清理 deprecated 字段、去重 | 1 小时 |
| 按需 | 提取升级 | 识别 3+ 重复模式，提取为躯干组件/工具函数 | 按需 |

## 枯枝识别操作清单

### 废弃路由

```
1. Grep 搜索路由路径关键词，确认无前端调用
2. 检查路由注册表（routeRegistry / ROUTE_TABLE 等）
3. 确认后端无其他模块调用 → 删除路由注册 + Controller 方法 + Service 方法
```

### 废弃组件

```
1. Grep 搜索组件导入语句（import / require），确认零引用
2. 如果组件关联了 CSS 文件，一并 Grep 搜索 CSS 类名
3. 确认零引用 → 删除组件文件目录
```

### 废弃工具函数

```
1. Grep 搜索函数名，确认零引用
2. 检查是否有测试文件引用 → 一并删除测试
3. 确认零引用 → 删除函数定义
```

### 废弃 CSS

```
1. Grep 搜索 CSS 类名，确认零引用
2. 如有构建工具（Webpack/Vite），可检查 unused CSS 插件报告
3. 确认零引用 → 删除样式块
```

### 调试代码残留

```
1. Grep 搜索 console.log、debugger、TODO（超 3 个月未处理）
2. 删除调试代码
3. 过期的 TODO 评估是否需要执行 → 不需要则删除
```

## 躯干升级信号识别

满足以下任一条件，应考虑升级为躯干：

| 信号 | 说明 | 阈值 | 升级方向 |
|------|------|------|---------|
| 同一逻辑在多个文件中出现 | 纯文本/函数重复 | 3+ | 提取到工具函数/公共模块 |
| 同一组件模式在多个页面出现 | UI 结构重复 | 3+ | 提取到通用组件 |
| 同一校验模式在多个 Service 出现 | 业务逻辑重复 | 5+ | 提取到基类或公共校验 |
| 同一样式模式在多个页面出现 | CSS 重复 | 3+ | 提取到通用样式/设计令牌 |
| 同一错误处理模式在多个模块出现 | 错误处理重复 | 3+ | 提取到统一错误处理中间件 |

### 升级评估矩阵

对每个候选模式，评估以下维度：

| 评估维度 | 问题 | 通过标准 |
|---------|------|---------|
| 重复次数 | 是否达到阈值？ | 纯文本 3+，业务逻辑 5+ |
| 提取收益 | 提取后能减少多少重复代码？ | 减少的代码量 > 提取的代码量 |
| 稳定性 | 这个模式是否稳定？ | 不再频繁变化 |
| 影响范围 | 提取后会影响多少文件？ | 提取不破坏现有枝叶的调用方式 |
| 通用性 | 这个模式是否真的通用？ | 不是凑巧相似的巧合 |

## 剪枝安全原则

1. **确认零引用再删除**：使用 `Grep` 工具全局搜索引用，不可凭记忆
2. **先标记后删除**：不确定的代码先标记 `@deprecated`，一个版本后再删
3. **规则文档只标记不删除**：废弃的 `.trae/rules/` 文档标记"已废弃"保留，形成"年轮"
4. **ADR 不可删除**：架构决策记录只能标记"已废弃"，不可物理删除
5. **一次剪枝一个类型**：不要在一次提交中同时删除路由、组件、CSS
6. **剪枝后运行测试**：执行项目的测试命令确保无回归
7. **Git 提交分离**：剪枝的 Git 提交应与功能开发的提交分离，便于回滚

---

## 禁止剪枝的情况

- ❌ 正在使用的代码
- ❌ 只出现 1-2 次的重复
- ❌ 规则文档（即使不再适用也要保留为"年轮"，只标记状态）
- ❌ ADR 记录（架构决策历史不可删除，只能标记"已废弃"）
- ❌ 公共 API（即使暂无人用，可能是预留扩展点）
- ❌ 正在快速演化的模式（先观察，稳定后再提取）

```javascript
 * @deprecated 自 v{版本号} 废弃，请使用 {替代方案} 替代。
 * 计划在 v{下个版本号} 删除。
 */
```
