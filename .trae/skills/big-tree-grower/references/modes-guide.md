# 十六核心模式执行指南

本文档定义生长器的 16 个核心模式。触发一次，AI 自主完成从分析到执行到收尾的全流程。

## 通用安全边界

所有模式共享以下安全边界，各模式仅列出**例外**：

- 不修改数据库结构
- 不删除数据
- 不确定的问题归档而非强修
- 不修改 `.trae/rules/` 下的规则文件（规则变更需走规则对齐入口）
- 每个修复必须可独立回滚

**各模式例外**：

| 模式 | 例外 |
|------|------|
| 种木成林 | ✅ 允许创建数据库 schema（唯一拥有此权限的模式） |
| 规则对齐/年轮审判 | ✅ 允许修改规则文件（必须同时更新 ADR） |
| 提交前审查/翠幕天罗 | ✅ 允许删除冗余/废弃产出（只删非核心业务产出） |
| 安全审计/自动安全 | ✅ 允许自动修复高危漏洞（SQL 注入、XSS、硬编码密钥等） |

## 入口 1：方案生长（plan）

**触发**：用户说"方案更新/基于方案更新/执行方案/方案落地"

**目的**：将用户提供的需求描述或方案文档转化为可执行的分步计划，执行、审核、清理一条龙。

**执行步骤**：

1. **加载上下文**：读取 `.trae/rules/project-rules.md` 和 `architecture-quickref.md` 了解项目当前架构和约定
2. **理解输入**：文件路径则读取文件，内联描述则直接使用，无内容则询问用户；输出一句话核心需求概括 + 涉及的功能模块清单
3. **提取问题**：从输入中提取有必要修复或实现的问题，按 P1-P5 优先级排序
4. **设计分步方案**：以自然生长为原则，将每个问题拆解为可独立执行的步骤，考虑依赖关系，优先底层（数据层/处理层）再上层（路由/展现层）
5. **检查关联代码**：使用 Grep 搜索相关产出标识符和引用路径，判断是否存在同类潜在问题（越层调用、命名不一致、重复逻辑），一并纳入方案
6. **执行修复**：按步骤顺序执行，每步完成后确认结果
7. **审核修复质量**：对照项目规则检查分层规范、是否引入新问题、代码风格一致性；检查是否违反自然生长阈值（不足 3 次重复的模式不可提前抽象）；如项目定义了质量验证方法则执行验证
8. **生成聚焦验证建议**：基于本轮修改产出用户级手动验证清单，含操作路径和不需要验证的功能说明
9. **清理旧产出**：删除被替代的旧文件、不再使用的引用、废弃的产出单元
10. **更新任务清单**：更新 `tasks/待完成任务.md` 和 `tasks/已完成任务.md`

**输入格式**：`方案更新 path/to/doc.md` 或 `方案更新：优化某模块的处理逻辑`

## 入口 2：速修（quick-fix）

**触发**：用户说"速修/快速修复/修复bug"

**目的**：对明确描述的问题快速定位根源、最小化修复、清理冗余，不引入不必要的变更。

**执行步骤**：

1. **加载上下文**：读取项目规则了解架构约束
2. **理解问题**：明确问题的现象、触发条件、影响范围
3. **定位根源**：从表现层逐层向下追溯根本原因（表现层→处理层→数据层→存储层），区分代码逻辑问题还是架构设计问题
4. **最小化修复**：只修改导致问题的部分，优先使用已有产出单元，修复后检查关联产出
5. **检查副作用**：确认修复不引入新问题，检查同类产出是否存在相同问题
6. **生成聚焦验证建议**：基于修复功能点生成 2-4 条聚焦的手动验证步骤
7. **清理冗余**：修复过程中发现的冗余内容一并清理

**输入格式**：`速修：某个操作触发了错误的目标`

## 入口 3：规则对齐（rule-align）

**触发**：用户说"规则对齐/对齐规则/交叉检查/年轮审判/全自动规则对齐/自动交叉检查"

**目的**：确保 `.trae/rules/` 中的规则文档与项目实际产出保持一致，双向对齐——规则好就改产出，产出好就改规则。修改规则时维护 ADR 年轮记录。

**执行步骤**：

1. **加载规则**：读取 `.trae/rules/` 下所有规则文件，建立"规则的期望状态"画像
2. **扫描产出实践**：分层边界、命名规范、导入方式、错误处理、产出模式
3. **交叉检查**：
   - 规则要求但产出未遵守 → 标记为"需改产出"
   - 产出中存在规则未覆盖的最佳实践 → 标记为"需更新规则"
   - 规则文件间矛盾 → 标记为"规则冲突"
4. **判断标准**：规则更合理 → 改产出；产出更合理 → 改规则；两者都合理 → 选择对长期维护更有利的方案
5. **问题分类**：

| 类别 | 判断标准 | 处理方式 |
|------|---------|---------|
| 可直接对齐 | 单文件修改、命名规范、导入约定 | 自动修复 |
| 需谨慎处理 | 跨多文件、涉及架构层 | 自动修复 + 额外审核 |
| 无法自动修复 | 规则矛盾需人工裁决、架构级重构 | 归档待办 |

6. **执行对齐**：按计划修改规则或产出
7. **维护年轮记录**：修改了规则文件则补写或更新对应的 ADR——记录决策原因和时间背景
8. **审核对齐质量**：确认对齐后规则与产出一致
9. **清理不当产出**：删除对齐过程中发现的冗余或违规产出

**输入格式**：`规则对齐`（全量）或 `规则对齐：核心规则`（聚焦特定范围）

**原则**：不好的一定要改，改完必须审核，审完必须清理。

## 入口 4：模块重思（module-rethink）

**触发**：用户说"模块重思/重新设计/聚焦模块"

**目的**：对某个已实现的模块进行需求层面的重新审视，产出设计方案文档，为后续的方案生长提供输入。

**执行步骤**：

1. **聚焦模块**：明确要重新设计的模块名称和范围
2. **分析现状**：当前功能、存在的问题、与整体架构的关系
3. **理解用户心智**：用户希望通过模块完成什么、同类产品参考、使用者角度思考
4. **设计需求方案**：基于现有架构以自然生长原则设计改进方案，考虑兼容性
5. **记录文档**：将设计方案写入 `docs/` 目录，作为后续方案生长的输入
6. **可选执行**：用户确认方案后可无缝衔接到模式 1（方案生长）

**输入格式**：`模块重思：库存分析模块`

---

## 入口 5：提交前审查（pre-commit-review）

**触发**：用户说"提交前审查/审查本轮更新/审查代码/有没有问题/翠幕天罗/全自动提交审查/全自动审查"

**目的**：自动扫描本轮产出变更，逐文件审查质量，修复发现的问题，清理冗余产出，更新任务清单——提交前的最后一道防线。

**执行步骤**：

1. **识别变更范围**：扫描最近的未提交变更，确定涉及的文件、模块、层，生成变更摘要：{N} 个文件，{M} 个模块
2. **加载规则上下文**：加载 `.trae/rules/` 中相关规则文件，建立"审查基准"
3. **逐文件审查**：检查自然生长（不提前抽象）、分层合规（各层职责清晰）、产出简洁性（无冗余）、关联产出影响、安全与性能
4. **问题分类**：

| 类别 | 判断标准 | 处理方式 |
|------|---------|---------|
| 可立即修复 | 风格、冗余产出、未使用导入、命名不规范、单文件逻辑错误 | 自动修复 |
| 需谨慎处理 | 跨 2+ 文件、涉及架构层修改、可能影响关联模块 | 自动修复 + 额外审核 |
| 无法自动修复 | 需人工判断的设计决策、大规模重构 | 归档待办 |

5. **自动修复**：对"可立即修复"和"需谨慎处理"类问题逐个修复，遵循最小修改原则，修复后检查关联产出
6. **汇总审核**：跨文件综合审核——修复一致性、是否引入重复内容、整体简洁性
7. **清理旧产出**：删除因修复而废弃的产出、导入、样式
8. **更新任务清单**：已完成的迁移到已完成任务.md；"无法自动修复"类添加到待办
9. **生成聚焦验证建议**：基于本轮变更生成用户级手动验证清单
10. **汇报结果**：已审查 {N} 个文件、修复 {M} 个问题、归档 {K} 个待办

**输入格式**：`提交前审查`

## 入口 6：健康度诊断

**触发**：用户说"健康度诊断/项目体检/自动体检/全自动体检/检查大树健康"

**目的**：对项目三层（根系/躯干/枝叶）进行全面健康度诊断，输出评分表和问题清单。可行动问题归档待办。

**执行步骤**：

1. **加载规则上下文**：加载 `.trae/rules/project-rules.md`，浏览 `.trae/rules/` 和 `decisions/` 目录
2. **根系健康度检查**（对照 [health-check-checklist.md](health-check-checklist.md)）：R1 规则完整性 / R2 规则一致性 / R3 ADR 覆盖度 / R4 规则可执行性 / R5 矛盾演化验证
3. **躯干健康度检查**（按项目类型分叉）：代码项目检查抽象复用率/重复造轮子/基类扩展性；文档项目检查模板复用率/内容重复/模板扩展性
4. **枝叶健康度检查**（按项目类型分叉）：代码项目检查分层规范/产出量/重复模式；文档项目检查文档结构/文档量/内容重复
5. **生成历史对比**：检查 `tasks/健康度快照/` 下上一次诊断，输出趋势判断
6. **输出健康度报告**：按评分表模板输出，包含各层评分和问题清单
7. **保存健康度快照**：写入 `tasks/健康度快照/{YYYY-MM-DD}.md`
8. **归档诊断结果**：将可行动问题写入 `tasks/待完成任务.md`，标注来源为"健康度诊断 {日期}"

**输入格式**：`健康度诊断`（全量）或 `健康度诊断：核心模块`（聚焦特定模块）

## 入口 7：剪枝

**触发**：用户说"剪枝/清理冗余/剪枝：去痕"

**目的**：识别并删除废弃产出、提取重复模式（含躯干升级判断）。

**执行步骤**：

1. **加载项目规则**：了解项目的目录结构、命名约定
2. **识别枯枝**：废弃入口、废弃产出单元、废弃工具/方法、废弃样式/格式、废弃验证文件
3. **安全确认**：每项操作前确认零引用
4. **执行枯枝删除**：确认零引用 → 直接删除；不确定 → 标记 `@deprecated`（下版本删除）
5. **识别升级候选**：3+ 重复模式 → 评估提取为躯干层通用抽象
6. **归档可行动项**：标记 @deprecated 的、需提取的模式写入 `tasks/待完成任务.md`

**剪枝安全原则**：确认零引用再删除、先标记后删除、一次剪枝一个类型、剪枝后运行验证。

### 去痕子功能

触发 `剪枝：去痕` 时，聚焦于 **AI 修改痕迹**——清理 AI 在修改过程中留下的多余解释和标注，还原原生无痕产出。

**识别项**：

| 类型 | 文案类 | 代码类 |
|------|--------|--------|
| 修改强调 | `"不是XX而是XX"`、`"现将XX改为XX"`、`"已修改/已调整"` | — |
| 修复注释 | — | Bug原因注释、修复思路注释、新旧对比注释、修改说明注释 |
| 变更标注 | 补充说明式括号、变更日期标注 | 版本变更记录注释、修改记录注释 |

**保留项**（不可误删）：业务逻辑注释、功能描述注释、文档性质注释（API 文档、使用说明）。

**执行流程**：加载项目规则 → Grep 扫描修改痕迹关键词 → 区分修改痕迹 vs 业务注释 → 删除痕迹保留业务注释，不确定项标记 `@deprecated` → 输出去痕报告

## 入口 8：体验评审

**触发**：用户说"体验评审/产出质量评估"

**目的**：对展示层进行交互质量、视觉美学和一致性评估。必须包含视觉美学维度（色彩和谐度、排版节奏、视觉层级），不可缩小为纯交互逻辑审查。

**执行步骤**：

1. **加载展示层规则**：读取项目约定的展示层架构规则文件
2. **场景遍历检查**：布局（跨场景适配、断点表现）/ 交互（操作反馈、加载状态、错误提示）/ 一致性（命名规范、样式令牌、模块风格）/ 可访问性（操作可达性、导航逻辑、语义化结构）
3. **严重程度分级**：🔴 严重（阻塞操作）/ 🟡 中等（影响体验）/ 🟢 轻微（影响精致度）
4. **输出体验评审报告**：问题清单 + 各场景维度评分表
5. **归档体验问题**：🔴 和 🟡 问题写入 `tasks/待完成任务.md`

> 各维度的具体检查清单和方法详见 [ux-review-guide.md](ux-review-guide.md)。

**输入格式**：`体验评审`（全量）或 `体验评审：{模块名}`

## 入口 9：安全审计

**触发**：用户说"安全审计/自动安全/全自动安全扫描"

**目的**：对照项目安全策略进行安全审计，严重问题自动修复，中等问题归档待办。

**执行步骤**：

1. **加载安全规则**：读取 `.trae/rules/` 中的安全策略规则
2. **风险等级评估**：🔴 严重 / 🟡 中等 / 🟢 轻微
3. **逐项审计**：认证授权 / 输入验证（展示层+数据访问层注入防护）/ 数据保护（敏感信息处理、日志脱敏）/ 文件资源安全（上传限制、路径遍历）/ 依赖安全
4. **🔴 严重问题自动修复**：高危漏洞直接修复，修复后检查关联产出是否存在同类问题
5. **🟡 中等问题归档**：写入 `tasks/待完成任务.md`
6. **🟢 轻微问题报告**：仅在审计报告中列出，不强制修复
7. **输出审计报告**：汇总所有发现，包含修复统计和风险矩阵

**输入格式**：`安全审计` 或 `安全审计：认证模块`

## 入口 10：依赖审计（dep-audit）

**触发**：用户说"依赖检查/依赖审计"

**执行步骤**：

1. **运行安全扫描**：执行项目包管理器的安全审计命令，获取漏洞列表

3. **分类处理**：

| 类别 | 处理方式 |
|------|---------|
| 🔴 高危漏洞 | 尝试自动修复命令；失败则评估手动升级路径；不可修复则归档 |
| 🟡 中低危漏洞 | 归档到 `tasks/待完成任务.md` |
| 🟡 Major 过期 | 逐包读取 CHANGELOG → 搜索项目中使用方式 → 评估影响 → 归档升级任务 |
| 🟢 非 Major 过期 | 执行批量更新命令 → 运行项目测试命令验证 |

4. **处理废弃包**：确认废弃原因和替代 → 搜索项目中使用 → 归档迁移任务
5. **验证**：所有自动修复完成后运行项目测试命令验证
6. **归档**：无法自动修复的问题写入 `tasks/待完成任务.md`

## 入口 12：问诊（consult）

**触发**：用户说"问诊/需求评审/问诊：自动迭代/问诊：智能路由/问诊：炼化归元/帮我看看"

**前置门控语法**：`问诊 {任意模式}：{需求描述}` — 先评审需求合理性，通过后自动衔接指定模式

**目的**：在执行任何操作前，先评审需求的合理性。不合理则拒绝并给出替代方案；信息不足则非中断式提问收集后继续评审；合理则开始执行。

**执行步骤**：

1. **加载上下文**：读取 `.trae/rules/` 下的规则文件，理解项目当前架构和约定
2. **理解需求**：独立模式直接评审需求；前置门控模式评审通过则衔接指定模式
3. **合理性评审**：

| 维度 | 检查内容 |
|------|---------|
| 架构一致性 | 是否违反现有分层规范？是否越权调用？ |
| 自然生长原则 | 是否不足 3 次重复就提取抽象？是否提前优化？ |
| 安全性 | 是否引入安全风险？ |
| 必要性 | 是否解决真实问题？是否有更简单的替代方案？ |
| 完整性 | 需求描述是否足够清晰？是否缺少关键上下文？ |

4. **信息收集**（如需要）：需求方向合理但缺少关键信息时，使用非中断式提问收集补充信息（不超过 3 个问题），收集后继续评审
5. **二选一判定**：❌ 拒绝（违反核心原则 / 有更好的替代方案 / 非真实问题）→ 说明原因 + 替代方案；✅ 开始（合理且信息充分）→ 输出评审摘要 + 方案规划 → 执行
6. **后续行动**：拒绝则终止等待用户回应；开始则输出方案规划，用户可说"执行"触发方案更新；前置门控则自动衔接指定模式

**输入格式**：`问诊：{需求描述}` 或 `问诊 {任意模式}：{需求描述}`

### 自动执行变体

触发 `自动迭代` 或 `智能路由` 时，执行"诊断→推荐→自动执行"闭式循环：

1. 执行标准问诊步骤 1-4（需求来自当前项目状态而非用户输入）
2. 判定 ✅ 开始后自动执行：诊断项目状态 → 推荐最优模式组合 → 无需用户确认按链路依次执行

### 炼化归元变体

触发 `炼化归元` 时，执行固定串联链路：**规则对齐 → 剪枝 → 提交前审查**。

1. 评审合理性，确认当前项目确实需要炼化（如刚完成大量生成、或风格不一致/冗余堆积）
2. 判定 ✅ 开始后按固定顺序执行
3. 输出汇总报告：已对齐 X 项、已剪枝 Y 项、已审查修复 Z 项
