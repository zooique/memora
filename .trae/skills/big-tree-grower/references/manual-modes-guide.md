# 手动模式执行指南

本文档详细定义生长器的十六大手动模式执行步骤。与八大全自动模式（新枝破土 / 神木回天 / 斩木除根 / 翠幕天罗 / 年轮审判 / 种木成林 / 自动体检 / 自动安全）不同，手动模式的核心特征是：**用户提供具体输入，AI 按标准流程交互执行，部分步骤需用户确认。**

> 本文档覆盖代码领域专属入口（补测试/测试回归/数据库迁移），与基础树通用版保持编号对齐。

---

## 手动模式总览

| # | 模式 | 核心流程 |
|---|------|---------|
| 1 | 方案生长 | 需求 → 提取问题 → 分步方案 → 执行 → 审核 → 清理 → 更新任务清单 |
| 2 | 速修 | 问题描述 → 定位根源 → 最小化修复 → 清理冗余 |
| 3 | 规则对齐 | 规则 vs 代码 → 交叉检查 → 对齐 → 审核 |
| 4 | 模块重思 | 聚焦模块 → 分析现状 → 设计需求方案 → 文档记录 |
| 5 | 提交前审查 | 本轮更新 → 审核质量 → 修复 → 清理 → 更新任务清单 |
| 6 | 补测试 | 扫描变更 → 生成测试 → 验证通过 |
| 7 | 测试回归 | 全量测试 → 分析失败 → 修复 → 报告 |
| 8 | 数据库迁移 | 分析需求 → 幂等迁移 → 同步建表 → 验证 |
| 9 | 健康度诊断 | 三层体检 → 评分表 → 问题归档 |
| 10 | 剪枝 | 识别枯枝 → 躯干升级判断 → 安全删除 |
| 11 | 体验评审 | 交互/视觉/一致性评估 → 问题归档 |
| 12 | 安全审计 | 安全规则对照 → 漏洞检测 → 问题归档 |
| 13 | 依赖审计 | 漏洞扫描 → 过期检查 → 分类修复 |
| 14 | 版本发布 | 判断 Semver → 生成 release notes → 打 tag |
| 15 | 问诊 | 需求评审 → 驳回/补充/接纳 → 衔接方案更新 |
| 16 | 排雷 | 方案推演 → 识别雷区 → 产出优化方案 |

## 入口 1：方案生长（plan）

**触发**：用户说"方案更新/基于方案更新/执行方案/方案落地"

**目的**：将用户提供的需求描述或方案文档转化为可执行的分步计划，执行、审核、清理一条龙。

**执行步骤**：

1. **加载上下文**：读取 `.trae/rules/project-rules.md` 和 `architecture-quickref.md` 了解项目当前架构和约定
2. **理解输入**：文件路径则读取文件，内联描述则直接使用，无内容则询问用户；最终输出一句话核心需求概括 + 涉及的功能模块清单
3. **提取问题**：从输入中提取有必要修复或实现的问题，按 P1-P5 优先级排序
4. **设计分步方案**：以自然生长为原则，将每个问题拆解为可独立执行的步骤，考虑依赖关系，优先底层（数据层/处理层）再上层（路由/展现层）
5. **检查关联代码**：在开始修改前，使用 Grep 工具搜索相关函数名、变量名、路径，判断是否存在同类潜在问题（越权调用、命名不一致、重复逻辑、相同问题），一并纳入方案
6. **执行修复**：按步骤顺序执行，每步完成后确认结果
7. **审核修复质量**：对照项目规则检查分层规范、是否引入新问题、代码风格一致性；检查是否违反自然生长阈值（不足 3 次重复的模式被提前抽象）
   - 如果项目有测试套件，运行相关测试确认无回归
8. **生成聚焦测试建议**：基于本轮修改产出用户级手动测试清单，详见 [test-suggestion-guide.md](test-suggestion-guide.md)
9. **清理旧代码**：删除被替代的旧文件、不再使用的引用、废弃的函数
10. **更新任务清单**：更新 `tasks\待完成任务.md` 和 `tasks\已完成任务.md`

**输入格式**：
- 引用文件：`方案更新 path/to/doc.md`
- 内联描述：`方案更新：优化退货弹窗的客户下拉逻辑`
- 组合使用：`方案更新 path/to/doc.md 重点关注审批模块`

**参考模板与检查清单**：详见 [grow-plan-template.md](grow-plan-template.md)

## 入口 2：速修（quick-fix）

**触发**：用户说"速修/快速修复/修复bug"

**目的**：对明确描述的 bug 快速定位根源、最小化修复、清理冗余，不引入不必要的变更。

**执行步骤**：

1. **加载上下文**：读取项目规则了解架构约束
2. **理解问题**：明确 bug 的现象、触发条件、影响范围
3. **定位根源**：从现象层逐层向下追溯根本原因（表现层→处理层→数据层→存储层），区分代码逻辑问题还是架构设计问题
4. **最小化修复**：只修改导致问题的部分，优先使用已有工具和组件，修复后检查关联代码
5. **检查副作用**：确认修复不引入新问题，同类代码全局排查
6. **生成聚焦测试建议**：基于修复的功能点，生成 2-4 条聚焦的手动验证步骤
7. **清理冗余**：如果修复过程中发现冗余代码（废弃变量、重复逻辑），一并清理

**输入格式**：`速修：基元弹窗点击单位输入框却弹出类型下拉框`

## 入口 6：补测试（test-coverage）

**触发**：用户说"补测试/测试覆盖/补充测试"

**目的**：扫描当前代码变更或指定模块，自动生成/补充单元测试，遵循项目已有的测试分层策略。

**前置约束**：
- 必须先读取 `.trae/rules/architecture-quickref.md` 了解项目的测试分层策略
- 必须先读取项目约定的测试目录下的现有测试文件了解测试模式和约定

**执行步骤**：

1. **加载规则上下文**：读取 `.trae/rules/architecture-quickref.md` 中"单元测试"和"测试分层策略"部分
2. **扫描变更范围**：未指定模块则扫描未暂存变更，指定模块则聚焦该模块
3. **读取现有测试模式**：扫描 `tests/` 目录了解文件命名、描述风格、导入方式、断言模式

**输入格式**：`补测试`（扫描未暂存变更）或 `补测试：productService`（聚焦特定模块）

## 入口 7：测试回归（test-regression）

**触发**：用户说"测试回归"

**目的**：运行全量测试 → 分析失败用例 → 修复 → 再次验证 → 输出测试报告，确保代码变更没有引入回归。

**执行步骤**：

1. **加载规则上下文**：读取 `.trae/rules/` 了解项目的测试框架约定
2. **运行全量测试**：执行项目的测试命令
3. **收集结果**：提取测试输出中的关键信息：
   - 通过/失败/跳过数量
   - 每个失败用例的名称和错误信息
4. **分析失败用例**：三分类——测试过期（更新测试）、代码回归（修复业务代码）、环境问题（修复测试辅助代码）
5. **修复问题**：按分类逐个修复，测试过期不改业务代码，代码回归追溯变更恢复逻辑
6. **重跑验证**：修复后重新运行测试命令，确认所有测试通过
7. **输出测试报告**

**输入格式**：`测试回归`

**安全边界**（不可违反）：
- 修复前必须确认"这是代码 bug 还是测试过时"
- 修改业务代码时遵循最小修改原则
- 修复后必须重跑测试确认通过

## 入口 8：数据库迁移（db-migrate）

**触发**：用户说"数据库迁移/加字段/改表"

**目的**：分析需求 → 编写幂等迁移脚本 → 同步更新全量建表脚本 → 验证迁移正确性。

**前置约束**：
- 必须先读取 `.trae/rules/database_operations_rules.md` 了解迁移策略
- 必须先读取项目约定的迁移入口文件了解迁移实现方式
- 必须先读取项目约定的全量建表脚本了解当前表结构

**执行步骤**：

1. **加载规则上下文**：读取 `database_operations_rules.md` 中的迁移规范
2. **分析变更需求**：明确要新增什么字段/表/索引，确定字段类型、默认值、约束
3. **读取现有迁移代码**：打开迁移入口文件，了解现有迁移块结构
4. **编写迁移脚本**：设计幂等迁移 SQL，将新迁移块追加到迁移入口函数末尾
5. **更新全量建表脚本**：同步更新项目约定的全量建表脚本
6. **检查关联代码**：如果新增了字段，检查对应数据模型的字段映射是否需要同步更新
7. **验证迁移**：提示用户重启服务以触发迁移

**输入格式**：`数据库迁移：为 products 表新增 weight 字段` 或 `改表：users 表增加 phone 列（TEXT）`

**安全边界**（不可违反）：
- 所有迁移语句必须幂等
- 不允许删除列或表（数据库迁移只做加法）
- 不允许修改已有列的类型（可能导致数据丢失）

## 入口 9：健康度诊断

**目的**：对项目三层（根系/躯干/枝叶）进行全面健康度诊断，输出评分表和问题清单。

**执行步骤**：

1. **加载规则上下文**：加载 `.trae/rules/project-rules.md` 和 `architecture-quickref.md`
2. **根系健康度检查**（对照 [health-check-checklist.md](health-check-checklist.md)）：规则完整性、一致性、ADR 覆盖度、可执行性
3. **躯干健康度检查**：抽象工具复用率、重复造轮子、基类扩展性
4. **枝叶健康度检查**：分层规范遵守、代码量合理性、重复模式识别
5. **生成历史对比**：检查 `tasks/健康度快照/` 下上一次诊断，输出趋势判断
6. **输出健康度报告**：按评分表模板输出
7. **保存健康度快照**：写入 `tasks/健康度快照/{YYYY-MM-DD}.md`
8. **归档诊断结果**：将可行动问题写入 `tasks\待完成任务.md`

**输入格式**：`检查大树健康`（全量诊断）或 `检查大树健康：核心模块`（聚焦特定模块）

## 入口 10：剪枝

**目的**：识别并删除废弃代码、提取重复模式为躯干组件。

**执行步骤**：

1. **加载项目规则**：了解项目的目录结构、命名约定
2. **识别枯枝**（对照 [pruning-guide.md](pruning-guide.md) 决策树）：废弃路由、废弃组件、废弃工具函数、废弃 CSS、废弃测试文件
3. **安全确认**：每项操作前确认零引用
4. **输出剪枝清单**：按优先级排序的剪枝行动项
5. **执行枯枝删除**：确认零引用 → 直接删除；不确定 → 标记 `@deprecated`
6. **识别升级候选**：3+ 重复模式 → 评估提取为躯干组件
7. **归档可行动项**：写入 `tasks\待完成任务.md`

**剪枝安全原则**：确认零引用再删除、先标记后删除、剪枝后运行测试。

## 入口 13：依赖审计（dep-audit）

**触发短语**：`依赖检查` `依赖审计` `npm audit`

**执行逻辑**：

1. **运行安全扫描**：执行项目包管理器的安全审计命令
2. **运行过期检查**：执行项目包管理器的过期检查命令
3. **分类处理**：

| 类别 | 处理方式 |
|------|---------|
| 🔴 高危漏洞 | 尝试自动修复；失败则评估手动升级路径 |
| 🟡 中低危漏洞 | 归档到 `tasks\待完成任务.md` |
| 🟡 Major 过期 | 评估影响 → 归档升级任务 |
| 🟢 非 Major 过期 | 执行批量更新 → 运行测试验证 |

4. **处理废弃包**：确认废弃原因和替代 → 归档迁移任务
5. **验证**：所有自动修复完成后运行项目测试命令
6. **归档**：无法自动修复的问题写入 `tasks\待完成任务.md`

详见 [dependency-audit-guide.md](dependency-audit-guide.md)。

## 入口 14：版本发布（release）

**触发短语**：`发布版本` `打版本` `release`

**前置检查**：确认最近一次提交前审查全部通过、无高危安全漏洞未归档、项目测试全部通过。

**执行逻辑**：
1. **读取变更**：从 `tasks/已完成任务.md` + `git log` 自上一个 tag
2. **判断 Semver**：Major/Minor/Patch
3. **更新版本号**：更新 `package.json` 中的 `version` 字段
4. **生成 Release Notes**
5. **打 Git Tag**
6. **记录到已完成任务**

详见 [release-guide.md](release-guide.md)。

## 入口 15：问诊（consult）

**触发短语**：`问诊` `需求评审` `帮我看看`

**前置门控语法**：`问诊 {任意模式}：{需求描述}`

**执行步骤**：

1. **加载上下文**：读取 `.trae/rules/` 下的规则文件
2. **理解需求**：独立模式直接评审；前置门控评审通过后衔接指定模式
3. **合理性评审**：从架构一致性、自然生长原则、安全性、必要性、完整性评审
4. **信息收集**（如需要）：非中断式提问收集补充信息（≤3 个问题）
5. **二选一判定**（不可跳过）：

| 判定 | 条件 | 输出 |
|------|------|------|
| ❌ 拒绝 | 需求违反核心原则 | 说明原因 + 替代方案 |
| ✅ 开始 | 需求合理且信息充分 | 评审摘要 + 方案规划 → 执行 |

**输入格式**：`问诊：{需求描述}` 或 `问诊 方案更新：{需求描述}`

## 入口 16：排雷（mine-sweeping）

**触发**：用户说"排雷/沙盘推演/方案排雷"

**目的**：在方案正式执行前进行模拟推演（沙盘推演），预先识别遗漏、重复定义、覆盖缺口和代码冗余等问题，产出可直接执行的优化方案。

**前置约束**：
- 必须有已存在的方案文档或上一轮方案更新产出作为输入
- 排雷不执行代码修改，仅产出优化后的方案

**执行步骤**：

1. **加载上下文**：读取 `.trae/rules/project-rules.md` 和 `architecture-quickref.md` 了解项目当前架构和约定
2. **读取方案**：用户指定路径则读取该文件，否则使用上一轮方案更新的产出
3. **理解方案**：提取步骤、模块、文件变更范围，输出一句话核心目标摘要
4. **逐步骤推演**：按执行顺序逐一模拟每个步骤在实际代码中的连锁反应
5. **识别雷区**：遗漏（缺少必要步骤/边界处理）、重复定义（多步定义相同函数/组件）、冗余（重复代码未提取）、覆盖遗漏（前后端不一致）、依赖顺序（隐式依赖导致执行失败）、边界盲区（空状态/并发/极限数据量）

6. **标注风险等级**：🔴高（崩溃/数据错误）、🟡中（不一致/冗余）、🟢低（代码整洁度）
7. **产出排雷报告**：逐项列出雷区位置、风险等级、影响分析、修正建议
8. **产出优化方案**：在原方案基础上修正雷区，产出"排雷后"的优化方案
9. **归档**：🟡中/🟢低 风险写入 `tasks\待完成任务.md`

**输入格式**：
- 独立排雷：`排雷`（对最近方案更新产出排雷）
- 指定方案：`排雷：path/to/plan.md`
- 串联排雷：`排雷 方案更新：XXX`（先设计方案，再排雷，再执行）
