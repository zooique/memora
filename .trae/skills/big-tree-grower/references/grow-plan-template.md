## 方案文档格式

当用户提供文件作为输入时，AI 应按以下结构解析：

```markdown
# {方案名称}

## 背景与目标
- 当前存在什么问题
- 预期达到什么效果

## 涉及范围
- 前端页面：{列表}
- 后端模块：{列表}
- 数据库变更：{有/无}

## 具体需求
1. {需求点 1}
2. {需求点 2}
...

## 约束条件
- {约束 1}
- {约束 2}
```

## 问题提取清单

从输入中提取问题时，使用以下维度逐一检查：

| 维度 | 检查项 | 示例信号词 |
|------|--------|-----------|
| 功能缺失 | 是否有应该实现但未实现的功能？ | "没有/缺少/需要增加" |
| 功能缺陷 | 是否有已实现但行为不符合预期的功能？ | "bug/错误/不对/异常" |
| 架构违规 | 是否有违反项目分层规范的代码？ | "越权/跨层/跳过" |
| 代码冗余 | 是否有重复逻辑或废弃代码？ | "重复/冗余/废弃/不再使用" |
| 命名不一致 | 是否有违反命名规范的代码？ | "命名/风格/不一致" |
| 样式问题 | 是否有 UI 不一致或响应式问题？ | "样式/UI/移动端/响应式" |
| 技术债务 | 是否有为了快速实现而留下的妥协？ | "临时/暂用/后续优化" |

## 分步方案设计原则

### 步骤排序规则

1. **自底向上**：先修改底层（数据层/DB），再修改中层（业务逻辑层），最后修改上层（路由处理层/前端）
2. **独立优先**：无依赖的步骤可以并行说明，让用户了解哪些可以同时进行
3. **风险前置**：高风险步骤（如数据库迁移）放在前面，出现问题可以及时止损
4. **验证后置**：每个步骤完成后应有验证方式

### 步骤粒度控制

| 复杂度 | 步骤数 | 每步范围 |
|--------|--------|---------|
| 简单（单文件修改） | 1-2 步 | 直接修改 + 验证 |
| 中等（2-5 文件，单模块） | 3-5 步 | 后端 → 前端，逐层 |
| 复杂（多模块，跨层） | 5-10 步 | 按模块拆分，每模块再按层拆分 |
| 大型重构 | 10-15 步 | 需要中间验证点，允许回退 |

## 清理旧代码 — 检查清单

方案生长模式第 9 步"清理旧代码"的具体检查项：

1. **废弃路由**：修改了 API 路径但保留了旧路由文件或旧路由注册
2. **废弃导入**：文件修改后仍保留不再使用的 import 语句
3. **废弃函数**：重构后旧函数仍保留在文件中
4. **废弃样式**：HTML 结构修改后未清理对应的旧样式
5. **废弃组件**：组件替换后旧组件文件仍存在
6. **调试代码**：console.log、debugger、print、临时注释
7. **重复逻辑**：修复过程中产生的与现有工具函数重复的代码

**清理原则**：
- 使用 Grep 工具确认零引用后再删除
- 不确定的代码先标记而非删除
- 一次清理一个类型（路由、组件、样式分开处理）

## 任务清单更新规范

方案生长模式第 10 步"更新任务清单"的规范：

### 任务清单体系

项目使用两份文档记录任务的完整生命周期：

| 文档 | 路径 | 职责 |
|------|------|------|
| 待完成任务 | `tasks\待完成任务.md` | 当前需要处理但尚未处理的问题 |
| 已完成任务 | `tasks\已完成任务.md` | 已修复问题的历史记录，便于回溯和知识复用 |

### 迁移条件（待完成 → 已完成）

以下情况从 `tasks\待完成任务.md` **迁移**到 `tasks\已完成任务.md`（而非直接删除）：
- 本轮已完整修复的任务 → 迁移时补写**修复方式**字段
- 经检查确认无需修复的误报项 → 迁移时修复方式标注"误报-无需修复"

### 从待完成中直接移除的条件（不迁移）

以下情况从 `tasks\待完成任务.md` 中**直接移除**（不写入已完成任务，因为没有实质性修复动作）：
- 已被更上层方案覆盖的子任务（不是被修复，是被替代）

### 添加条件

以下情况添加到 `tasks\待完成任务.md`：
- 本轮发现的、未修复的潜在问题
- 因依赖关系需要后续处理的任务
- 审核中发现的、需要单独迭代的架构问题

### 已完成任务记录格式

```markdown
## YYYY-MM-DD

| ID | 问题 | 来源 | 修复方式 |
|----|------|------|---------|
| T-xx | {问题描述} | {来源：方案生长/斩木除根/翠幕天罗/神木回天等} | {修复方式简要描述} |
```

### 待完成任务格式

```markdown
# 待完成任务

## 高优先级
- [ ] {任务描述} — 发现于：{日期/来源} — 影响范围：{模块}

## 中优先级
- [ ] {任务描述} — 发现于：{日期/来源}

## 低优先级 / 后续迭代
- [ ] {任务描述} — 发现于：{日期/来源}
```

### 归档规则

`tasks\已完成任务.md` 只保留最近 90 天的记录。超过 90 天的记录迁移到 `tasks\归档\已完成任务-YYYY-QN.md`（按季度归档），`tasks\已完成任务.md` 的统计数字需同步更新。

## 典型场景示例

### 场景 1：基于用户描述

```
用户输入：方案更新：优化库存管理退货弹窗，客户下拉有重复选项，
         且需要过滤无关客户，显示可退货数量

AI 行为：
1. 加载项目规则 → 读取 .trae/rules/ 下的规范文件，建立抽象术语映射
2. 提取问题：
   - 客户下拉存在重复"请选择"选项
   - 客户列表未过滤（应只显示有出库记录的客户）
   - 缺少可退货数量显示和校验
3. 设计分步方案（遵循自底向上原则）：
   步骤 1：后端 — 修改查询逻辑（过滤 + 计算可用数量）
   步骤 2：后端 — 添加数量校验逻辑
   步骤 3：前端 — 修复下拉重复选项
   步骤 4：前端 — 在选项后显示可用数量
   步骤 5：审核修复质量（使用检查维度表）
   步骤 6：清理旧代码
   步骤 7：更新任务清单
```

> 注：以上为某个进销存系统的示例场景。AI 执行时应根据当前项目的实际业务领域进行调整。
