# 全自动流程模式执行指南

本文档详细定义生长器的八大全自动流程模式。与十二大手动模式不同，全自动模式的核心特征是：**用户只触发一次，AI 完成从分析到执行到收尾的全部流程，无需中间交互确认。**

## 入口 16：🌰 新枝破土（auto-innovate）

**触发**：用户说"新枝破土/全自动创新设计/创新设计/自动加新功能/给我一个惊喜"

**目的**：AI 自主分析项目现有功能和架构，发现缺失但契合的功能点，直接实现——不开会、不写文档、直接产出，给用户一个"拆盲盒"式的惊喜。

**执行步骤**：

1. **加载上下文**：按需加载 `.trae/rules/` 中相关规则（分层规范、组件工厂模式、导入约定等），建立"项目约束边界"画像
2. **分析现状**：
   - 读取项目业务模块结构，建立"已实现功能"清单
   - 读取数据模型（Model/Schema），了解数据能力
   - 读取现有页面和路由，了解用户界面能力
3. **发现缺口**：在项目约束边界内，寻找一个"有它更好"的功能点：
   - 数据层已有但展示层未使用的项 → 补展示
   - 同类功能模式未覆盖的模块 → 复制模式到新模块
   - 用户操作流中明显的断点（有了 A 和 C 但缺 B） → 补齐流程
   - 选择优先级：**数据已就绪 > 模式可复用 > 填补流程断点**
4. **设计最小可行功能**：
   - 新增产出量控制在合理范围（优先 50-150 行级别的小功能，不超过 300 行）
   - 必须严格遵循现有分层规范，不引入新模式
   - 必须复用现有躯干工具（工厂/基类/工具函数）
   - 不引入项目未使用的第三方库
5. **直接实装**：不产出任何文档，直接修改产出
   - 遵循方案生长模式的执行步骤（分步执行 → 检查关联产出 → 审核）
6. **审核质量**：
   - 对照项目规则检查分层合规
   - 确认不破坏现有功能
   - 检查自然生长阈值（不提前抽象）
7. **清理冗余**：检查是否引入了冗余导入、重复逻辑
8. **更新任务清单**：将新功能可能引发的后续优化点（如"新功能缺少单元测试"、"性能优化机会"）写入 `tasks/待完成任务.md`
   - 迁移规则：新枝破土在此步只写入待完成，不涉及已完成任务.md（因为新功能本身是直接实现的，没有前置待办项被修复）
9. **生成聚焦测试建议**：基于新功能的交互路径生成用户级测试步骤
10. **汇报惊喜**：用 2-3 句话告诉用户"我加了什么、为什么加、在哪里可以看到"

**输入格式**：`新枝破土`

**创新约束**（不可违反）：
- 新功能必须在现有架构内生长，不破坏分层、不引入新模式
- 不产出任何文档文件（`.md`）
- 不修改数据库 schema（不执行 migration）
- 不删除或重构现有功能
- 新增产出优先选择"数据已就绪只差展示层"的 low-hanging fruit

**开奖说明**：此模式具有"开奖"性质——AI 自主选择做什么功能。如果不满意，使用方案生长或速修调整即可，不会对项目造成结构性破坏。

> 聚焦测试建议的完整输出格式和生成原则详见 [test-suggestion-guide.md](test-suggestion-guide.md)。

## 入口 17：🌳 神木回天（auto-heal）

**触发**：用户说"神木回天/全自动健康度优化/健康度优化/自动体检修复/全身体检修复"

**目的**：全自动执行健康度诊断 → 根据诊断报告自动修复可修复的问题 → 将无法自动修复的问题归档到 `tasks/待完成任务.md`。

> 此技能将健康度诊断和内嵌修复融为一体：全自动模式下无需分步操作，一条指令走完全流程。

**执行步骤**：

1. **执行健康度诊断**：执行 grower 健康度诊断流程（根系/躯干/枝叶三层检查），产出完整的问题清单
2. **问题分类**：将诊断发现的所有问题按以下规则分为三类：

   | 类别 | 判断标准 | 处理方式 |
   |------|---------|---------|
   | 可直接修复 | 单文件、不涉及架构决策、不涉及 API 契约变更、预估 < 30 行 | 自动修复 |
   | 需谨慎处理 | 跨 2+ 文件、涉及架构层、需 API 变更、需数据库迁移 | 归档待办 |
   | 无法自动修复 | 需要人工判断、设计决策、第三方依赖、涉及安全策略 | 归档待办 |

3. **自动修复**：对"可直接修复"类问题逐个修复
   - 遵循速修原则：最小化修改、定位根源而非治标、不顺手优化
   - 修复后检查关联产出是否存在相同问题
4. **归档待办**：将"需谨慎处理"和"无法自动修复"的问题写入 `tasks/待完成任务.md`
   - 每条归档需包含：问题描述、影响范围、建议方案、优先级（P1-P5）
   - 问题描述需足够具体，供后续斩木除根技能直接使用
   - **来源标注**：每条归档必须标注来源（如"神木回天 2026-05-19"），以便后续迁移到已完成任务.md 时追溯
   - 迁移规则：神木回天在此步只写入待完成，不涉及已完成任务.md（自动修复的"可直接修复"问题已在步骤 3 中直接处理，无需额外记录）
5. **审核修复质量**：确认所有自动修复未引入新问题
6. **生成聚焦测试建议**：基于所有修复的功能点生成用户级测试步骤
7. **汇报结果**：列出已修复 X 项、已归档 Y 项、跳过 Z 项（及原因）

**输入格式**：`神木回天`

**安全边界**（不可违反）：
- 不确定的问题归档而非强修
- 不修改数据库结构
- 不删除任何数据
- 不修改 `.trae/rules/` 下的规则文件（规则变更需走年轮审判或规则对齐入口）
- 每个自动修复必须可独立回滚

### 问题分类决策树

```
发现一个问题
     │
     ├── 单文件？──否──→ 归档（需谨慎处理）
     │       │
     │       └──是──→ 涉及架构决策？──是──→ 归档（需谨慎处理）
     │                           │
     │                           └──否──→ 涉及 API 契约变更？──是──→ 归档（需谨慎处理）
     │                                                   │
     │                                                   └──否──→ 预估 < 30 行？──否──→ 归档（需谨慎处理）
     │                                                                         │
     │                                                                         └──是──→ 涉及人工判断？──是──→ 归档（无法自动修复）
     │                                                                                         │
     │                                                                                         └──否──→ ✅ 可直接修复
```

## 入口 18：⚔️ 斩木除根（auto-fix-tasks）

**触发**：用户说"斩木除根/全自动修复任务/修复待办/自动清任务/批量修复任务"

**目的**：自动读取 `tasks/待完成任务.md`，解析可执行的任务条目，规划方案并逐项修复，完成后将已修复条目**迁移**到 `tasks/已完成任务.md`。

**执行步骤**：

1. **读取任务清单**：解析 `tasks/待完成任务.md`，提取所有待完成任务条目
   - 要求每条任务有明确的"问题描述"字段（神木回天归档的条目已满足此要求）
   - 如果任务清单为空 → 告知用户"没有待修复任务，大树很健康"
2. **评估可执行性**：过滤掉以下任务（跳过并标注原因）：
   - 描述不清无法确定修改范围 → 标注"描述不清"
   - 依赖未满足（如"A 完成后才能做 B"但 A 未完成） → 标注"依赖未满足"
   - 需要人工判断的设计决策 → 标注"需人工决策"
3. **规划执行方案**：对可执行任务按优先级排序，考虑任务间的依赖关系
4. **逐任务执行**：对每个可执行任务，按方案生长模式的标准流程执行：
   - 设计分步方案 → 检查关联产出 → 执行修复 → 审核 → 清理
5. **汇总审核**：所有任务完成后，做一次跨任务的综合审核：
   - 不同任务的修改是否冲突
   - 是否引入了重复内容
   - 整体简洁性是否保持
6. **清理任务清单**：更新 `tasks/待完成任务.md` 和 `tasks/已完成任务.md`
   - 已完成的任务 → 从待完成清单中**迁移**到已完成任务.md（补写**修复日期**和**修复方式**字段），不得直接删除
   - 跳过的任务保留在待完成清单中，并补充跳过原因
   - 修复过程中发现的新问题 → 追加到待完成清单末尾
   - 已完成任务.md 的格式与归档规则详见 [grow-plan-template.md](grow-plan-template.md) 的"任务清单更新规范"章节
7. **生成聚焦测试建议**：基于所有修复的功能点，按功能模块分组生成测试步骤
8. **汇报结果**：已完成 X 项、跳过 Y 项（含原因）、剩余 Z 项

**输入格式**：`斩木除根`

**执行约束**：
- 每个任务独立完成、独立审核，不得合并步骤跳过审核
- 任务间有依赖时，先完成被依赖的任务
- 如果某个任务执行失败，标记失败原因并继续下一个，不中断全流程
- 修复过程中发现的新问题 → 追加到任务清单末尾

### 可执行性评估标准

| 评估维度 | 可执行 | 不可执行（跳过） |
|---------|--------|----------------|
| 描述清晰度 | 有明确的问题描述和修改范围 | 描述模糊、无法确定修改位置 |
| 依赖状态 | 依赖条件已满足 | 依赖的先决任务未完成 |
| 决策类型 | 可技术判断的执行问题 | 需人工判断的设计决策 |
| 影响范围 | 单文件或少量文件 | 涉及大规模重构或架构变更 |

### 汇总审核清单

跨所有任务完成后的综合审核项：
1. 修改的文件之间是否有冲突（同一文件被多个任务修改）
2. 是否有任务引入了与另一任务相矛盾的逻辑
3. 是否有重复内容被引入（违背自然生长原则）
4. 任务清理步骤是否完整（废弃的产出、引用、冗余是否清除）
5. 产出库简洁性是否保持

## 入口 19：🌿 翠幕天罗（auto-review）

**触发**：用户说"翠幕天罗/全自动提交审查/自动提交审查/自动审查本轮更新/全自动审查"

**目的**：自动扫描本轮产出变更，逐文件审查质量，修复发现的问题，清理冗余产出，更新任务清单——提交前的最后一道防线。

**执行步骤**：

1. **识别变更范围**：
   - 扫描项目最近的未提交变更（或最近一次 commit 以来的所有修改）
   - 确定涉及的文件、模块、层（展示层/处理层/规则）
   - 生成变更摘要：{N} 个文件，{M} 个模块

2. **加载规则上下文**：按需加载 `.trae/rules/` 中相关规则文件（分层规范、命名规范、错误处理约定等），建立"审查基准"

3. **逐文件审查**：对每个变更文件执行以下检查：
   - **自然生长检查**：产出是否从架构中自然生长，而非拼凑？是否有不足 3 次重复就被提前抽象的模式？
   - **分层合规检查**：入口层是否薄层、处理层是否持有核心逻辑、数据层是否只做映射、是否有越权调用？
   - **产出简洁性检查**：是否有冗余变量、重复逻辑、未使用的导入、废弃的产出？
   - **关联产出检查**：修改是否影响了关联模块？是否有潜在问题被遗漏？
   - **安全与性能检查**：是否有 SQL 注入风险、密钥硬编码、N+1 查询等常见问题？

4. **问题分类**：将审查发现的问题按以下规则分类：

   | 类别 | 判断标准 | 处理方式 |
   |------|---------|---------|
   | 可立即修复 | 产出风格、冗余产出、未使用的导入、命名不规范、单文件逻辑错误、单文件且不涉及架构决策、预估 < 30 行 | 自动修复 |
   | 需谨慎处理 | 跨 2+ 文件、涉及架构层修改、可能影响关联模块 | 自动修复 + 额外审核 |
   | 无法自动修复 | 需要人工判断的设计决策、大规模重构 | 归档待办 |

5. **自动修复**：对"可立即修复"和"需谨慎处理"类问题逐个修复
   - 遵循最小修改原则：只改有问题的产出，不做"顺手优化"
   - 修复后检查是否引入新问题
   - 对"需谨慎处理"类问题，修复后执行额外的关联产出影响检查

6. **汇总审核**：所有修复完成后，做一次跨文件的综合审核：
   - 不同文件的修复是否一致（命名风格、错误处理方式等）
   - 是否引入了重复内容
   - 整体简洁性是否保持

7. **清理旧产出**：删除因修复而废弃的产出、导入、样式

8. **更新任务清单**：更新 `tasks/待完成任务.md` 和 `tasks/已完成任务.md`
   - 本轮已完成的任务 → 从待完成清单中**迁移**到已完成任务.md（补写修复方式），不得直接删除
   - 审查中发现的遗留问题（"无法自动修复"类）→ 添加到待完成清单
   - 已被更上层方案覆盖的子任务 → 直接从待完成清单中移除（不迁移）
   - 格式与规范详见 [grow-plan-template.md](grow-plan-template.md) 的"任务清单更新规范"章节

9. **生成聚焦测试建议**：基于本轮变更的文件和功能点，生成用户级手动测试清单

10. **汇报结果**：已审查 {N} 个文件、修复 {M} 个问题、归档 {K} 个待办

**输入格式**：`翠幕天罗`

**安全边界**（不可违反）：
- 不修改数据库结构
- 不删除核心业务产出（只删除冗余/废弃产出）
- 不确定的问题归档而非强修
- 每个修复必须可独立回滚

### 审查检查清单

> 完整审核维度和检查项详见 [pre-commit-review-guide.md](pre-commit-review-guide.md)，以下为翠幕天罗专用的精简版。

| 检查维度 | 检查项 |
|---------|--------|
| 架构合规 | 分层规范、依赖方向、越权调用 |
| 自然生长 | 不提前抽象、不强塞模式、3 次阈值 |
| 代码质量 | 冗余产出、未使用的导入、命名一致性 |
| 安全性 | SQL 注入、XSS、密钥暴露、权限校验 |
| 关联性 | 影响范围、潜在回归、API 契约一致性 |

## 入口 20：🔱 年轮审判（auto-align）

**触发**：用户说"年轮审判/全自动规则对齐/自动规则对齐/自动交叉检查/全自动交叉检查"

**目的**：自动对比 `.trae/rules/` 中的规则文档与项目实际产出，双向对齐——规则好就改产出，产出好就改规则，维护年轮记录。

**执行步骤**：

1. **加载规则**：按需加载 `.trae/rules/` 中相关规则文件（分层规范、命名规范、导入约定、错误处理约定等），建立"规则的期望状态"画像

2. **扫描产出实践**：
   - 分层边界：各处理层（如数据层/业务层/路由层）各层文件，检查职责是否清晰
   - 命名规范：变量名、函数名、类名、文件名是否符合约定
   - 导入方式：导入别名系统使用（读取 project-rules.md 确认）
   - 错误处理：统一错误抛出机制使用、错误码规范
   - 组件模式：展示层工厂模式、通用组件复用

3. **交叉检查**：
   - **规则 → 产出**：规则要求但产出未遵守 → 标记为"需改产出"
   - **产出 → 规则**：产出中存在规则未覆盖的最佳实践 → 标记为"需更新规则"
   - **规则 ↔ 规则**：规则文件之间是否有矛盾 → 标记为"规则冲突"
   - **设计基线 vs 实际产出**（如果存在 `docs/` 下的创意设计单页纸）：已实现功能是否与原始主要任务一致？是否有"不做清单"中的功能被意外实现？是否有 `[禁止建造]` 标记的项被突破？ → 标记为"设计偏离"

4. **判断标准**：对每个不一致项判断"哪个更合理"
   - 如果规则更合理 → 标记为"需改产出"
   - 如果产出更合理 → 标记为"需改规则"
   - 如果两者都合理只是不同 → 选择对项目长期维护更有利的方案

5. **问题分类**：

   | 类别 | 判断标准 | 处理方式 |
   |------|---------|---------|
   | 可直接对齐 | 单文件修改、命名规范、导入约定、错误处理 | 自动修复 |
   | 需谨慎处理 | 跨多文件、涉及架构层、分层规范对齐 | 自动修复 + 额外审核 |
   | 无法自动修复 | 规则矛盾需人工裁决、架构级重构 | 归档待办 + 建议使用年轮审判或规则对齐入口 |
   | 设计偏离 | 功能与原始设计不一致、不做清单被突破 | 归档待办 + 年轮审判退出声明中报告 |

6. **自动对齐**：对"可直接对齐"和"需谨慎处理"类问题逐个修复
   - 优先修复"规则好就改产出"项
   - 修复后检查是否引入新问题
   - 对"需谨慎处理"类问题，修复后执行额外的关联产出影响检查

7. **维护年轮记录**：如果修改了规则文件，补写或更新对应的 ADR（架构决策记录）
   - 记录决策原因："为什么产出比规则更合理"
   - 记录决策时间和背景

8. **审核对齐质量**：确认规则与产出一致性

9. **清理不当产出**：删除对齐过程中发现的冗余或违规产出

10. **汇报结果**：已检查 {N} 项规则、修改 {M} 个文件、更新 {K} 条 ADR、归档 {L} 个待办。如发现设计偏离，在报告末尾单独列出偏离项

**输入格式**：`年轮审判`（全量检查）

**安全边界**（不可违反）：
- 不删除核心业务产出
- 规则文件的修改必须同时更新 ADR
- 规则矛盾不强行裁决，归档待办
- 不修改数据库结构

### 年轮维护规则

| 操作 | 年轮动作 |
|------|---------|
| 修改规则文件 | 补写 ADR，记录"规则变更原因" |
| 废弃规则 | 标记"已废弃"但不删除，保留为年轮 |
| 新增规则 | 补写 ADR，记录"新规则来源" |
| 规则矛盾 | 归档待办，由年轮审判或规则对齐入口后续处理 |

## 入口 21：🌲 种木成林（auto-bootstrap）

**触发**：用户说"种木成林/从零建造/全自动项目启动/森林崛起"

**目的**：填补 seeder→grower 之间的"从零到一"断层。读取 rules + 设计文档，分模块从零构建项目初始产出，包括数据存储 schema、躯干基类、首批核心模块——建造完毕后自动交接给全自动循环。

**前置条件**：
- `.trae/rules/` 完整（已由 seeder 生成）
- 创意设计单页纸存在于 `docs/` 目录（已由 seeder 生成）
- 项目产出尚为空或仅有骨架（此模式设计为"从零建造"，已有大量代码时仅建造缺失部分）

**执行步骤**：

### 阶段 1：解析项目蓝图

1. **加载创意设计单页纸**：读取 `docs/` 目录下的创意设计单页纸，解析其中的 `[GROWER-INPUT] 模块蓝图` 段落
   - 提取：核心模块清单（模块名、描述、优先级、依赖模块、功能要点）
   - 提取：开发顺序
   - 提取：完成标准
2. **加载规则上下文**：加载 `.trae/rules/` 全部规则文件（分层规范、技术栈约定、命名规范、错误处理约定等）
3. **检查不做清单**：解析创意设计单页纸中的"不做清单"，识别其中的 `[禁止建造]` 标记项。`[禁止建造]` 项在后续建造中作为**硬约束**——不得为这些功能创建任何数据表、页面、路由或组件。
4. **输出蓝图解析结果**：
   - 模块清单（N 个模块，按开发顺序排列）
   - 模块依赖图
   - 预计建造顺序
5. **蓝图确认节点**：在进入建造阶段前，将推断出的数据模型摘要展示给用户确认：
   - 列出推断的数据表及其核心字段（表名 + 3-5 个关键字段名）
   - 列出模块与表的对应关系
   - 展示预计建造的模块顺序
   - **默认通过**：用户无反馈时，继续自动建造
   - **用户可中断**：如用户发现推断有误，可在此节点修正蓝图后再继续

### 阶段 2：建造树干骨架（数据库 + 躯干基类）

> ⚠️ **DB 权限**：种木成林是唯一拥有数据库 schema 创建权限的自动模式。

1. **推断数据模型**：基于模块蓝图中各模块的"功能要点"，结合规则中的技术栈约定，推断所需的数据表结构
2. **创建数据库 schema**：
   - 生成建表语句（Table + Index）
   - 生成数据层（数据映射）
   - 确认数据类型、关联关系符合规则约定
3. **实现躯干基类**：
   - 数据访问基类：通用基本操作方法
   - 业务逻辑基类：校验、事务、错误处理
   - 路由处理基类：参数解析、响应格式化
   - 全局错误处理中间件
   - 认证/授权框架（如规则中定义了认证策略）
4. **配置路由框架**：根据规则中的路由约定搭建路由注册框架
5. **骨架审核**：对照规则验证：
   - 分层结构正确（存储层 → 处理层 → 入口层）
   - 命名规范一致
   - 错误处理统一使用约定的方法
   - 导入别名系统正确（读取 project-rules.md 确认）

### 阶段 3：逐模块建造枝叶

按蓝图中的开发顺序，对每个模块执行：

1. **数据访问层**：根据功能要点设计数据模型，编写数据访问层代码
2. **业务逻辑层**：实现业务逻辑，继承业务逻辑基类
3. **路由处理层**：实现路由处理，薄层设计，委托业务逻辑层
4. **Route 层**：注册路由
5. **展示层页面**（如适用）：使用规则中约定的展示层工厂模式（读取 frontend_architecture_rules.md 确认具体工厂名）
6. **模块内审核**：每个模块建造完成后审核：
   - 分层合规（路由处理层薄层、业务逻辑层持逻辑、数据访问层管映射）
   - 自然生长检查（不提前抽象、复用现有躯干工具）
   - 产出简洁性
7. **模块间检查**：新模块与已建模块的引用关系正确、不越权调用
8. **更新状态**：更新 `docs/模块开发状态.md`

**建造策略**：
- P1 模块：完整建造（数据模型 + 处理逻辑 + 入口层 + 展示层）
- P2 模块：建造骨架（数据模型 + 处理逻辑），展示层和入口层写入待完成任务
- 每个模块建造失败不中断全流程，标记失败原因继续下一个
- 不覆盖已有文件（如果文件已存在，跳过并记录）

### 阶段 4：生成初始任务清单

1. **生成 `tasks/待完成任务.md`**：
   - P2+ 模块的完整建造任务（存储层 → 处理层 → 入口层 → 展示层）
   - 不完整功能（骨架已建但细节待补）
   - 各模块的"聚焦测试建议"汇总
   - seeder 创意设计单页纸中未在阶段 3 覆盖的部分
2. **生成 `tasks/已完成任务.md`**（如不存在，首次创建）：
   - 格式模板详见 [grow-plan-template.md](grow-plan-template.md) 的"任务清单更新规范"章节
   - 种木成林阶段已完成的建造任务写入已完成任务.md，作为首批历史记录
3. **生成 `docs/模块开发状态.md`**（首次创建）：
   - 所有模块的状态（✅ 完成 / 🔧 建造中 / 📋 待建 / 💡 规划中）
   - 处理层/展示层完成度标注
   - 备注依赖关系

### 阶段 5：首轮质量把关

1. 运行翠幕天罗逻辑：审查阶段 2-3 建造的全部代码
2. 运行年轮审判逻辑：检查所有代码是否与规则一致
3. 修复发现的问题（按问题分类规则自动修复或归档）
4. 生成聚焦测试建议：基于所有新建模块生成用户级测试步骤（格式详见 [test-suggestion-guide.md](test-suggestion-guide.md)）

### 阶段 6：交接给全自动循环

1. **输出建造报告**：
   - 已建成模块：{N} 个（含处理层/展示层完成度）
   - 待建模块：{M} 个（已写入待完成任务）
   - 任务清单：{K} 条待办
   - 模块开发状态文件路径：`docs/模块开发状态.md`
2. **建议后续操作**：
   ```

     年轮审判 → 神木回天 → 斩木除根 → 翠幕天罗 → 新枝破土 → (循环)
   ```

**输入格式**：`种木成林`

**安全边界**（不可违反）：

## 全自动循环链路

7 个全自动模式按循环链串联：年轮审判→自动体检→神木回天→斩木除根→新枝破土→翠幕天罗→自动安全→(回到年轮审判)。循环持续运行直到满足收敛条件。

**循环终止条件**（阶段收敛制）：

全自动循环采用**三阶段收敛**而非单次完美达标。每轮循环结束后检查当前阶段是否满足收敛条件：

```
┌─────────────────────────────────────────────────┐
│  扎根阶段收敛（seeder 完成后即可达成）             │
│  ✅ .trae/rules/ 完整 + ADR 覆盖关键决策          │
│  ✅ 样板验证通过（第 5 步基本操作可运行）           │
├─────────────────────────────────────────────────┤
│  躯干阶段收敛                                    │
│  □ 模块开发状态中所有 P1 模块为 "✅ 完成"         │
│  □ 神木回天健康度综合评分 > 7/10                 │
│  □ 年轮审判无 P1 级别不一致                      │
│  □ 主要任务全部实现（对照创意设计单页纸）          │
│  □ 不做清单未被突破（无设计偏离）                 │
├─────────────────────────────────────────────────┤
│  全阶段收敛（可视为项目交付）                      │
│  □ 躯干阶段条件全部满足                           │
│  □ 翠幕天罗审查无 P1/P2 问题                     │
│  □ 任务清单为空或只剩"需人工决策"项               │
│  □ 新枝破土连续 2 轮未发现显著功能缺口             │
└─────────────────────────────────────────────────┘
```

**阶段递进规则**：
- 下阶段收敛条件未满足时，循环自动继续
- 当前阶段条件满足后，循环**自动尝试进入下一阶段**——例如躯干阶段收敛后，循环不会停止，而是以更高的标准（全阶段收敛条件）继续迭代
- 用户可在任意时刻手动终止循环（"停止循环"）

**循环终止**：当**全阶段收敛**的所有条件均满足时，循环自动终止，退出声明中报告"项目已达全阶段收敛，可视为交付状态"。

## 入口 22：🔍 自动体检（auto-health-check）

**触发**：用户说"自动体检/全自动体检"

**目的**：全自动执行健康度诊断（纯诊断，不修复），产出完整诊断报告，可行动问题归档待办。

> 此模式是神木回天的"只看不动"版本——适合先了解项目全貌再决定修复策略。

**执行步骤**：

1. **加载规则与映射**：读取 `.trae/rules/` 建立抽象术语到项目实现的映射
2. **执行三层诊断**：
   - 根系检查：规则文件完整性、规则间一致性、ADR 与规则对齐
   - 躯干检查：分层合规、命名一致性、导入规范、自然生长原则
   - 枝叶检查：产出健康度、冗余产出、验证覆盖、安全风险
3. **问题分级**：按 P1-P5 优先级对所有发现的问题分级
4. **归档可行动问题**：将 P1-P3 级问题写入 `tasks/待完成任务.md`
   - 每条归档包含：问题描述、影响范围、建议方案、优先级
   - 来源标注："自动体检 {日期}"
5. **生成诊断报告**：输出完整诊断结果，包含各层评分和问题清单
6. **生成聚焦测试建议**：基于诊断发现的风险点生成验证步骤

**进度提示**：
```
🔍 自动体检：加载规则... → 三层诊断... → 问题分级... → 归档待办... → 生成报告 ✓
```

**安全边界**：
- 不修改任何产出文件
- 不修改 `.trae/rules/` 下的规则文件
- 不修改数据库
- 纯诊断模式，所有修复建议归档待办而非直接执行

**与神木回天的区别**：自动体检**纯诊断不修复**，神木回天**诊断 + 自动修复**。自动体检适合用作全自动循环的第一步（先了解问题全貌），神木回天适合有明确修复目标的场景。

**输入格式**：`自动体检` 或 `全自动体检`

## 入口 23：🛡️ 自动安全（auto-security）

**触发**：用户说"自动安全/全自动安全扫描"

**目的**：全自动执行安全扫描，严重问题自动修复，中等问题归档待办，轻微问题仅报告。

> 此模式将安全审计和紧急修复融为一体：高危漏洞不等人工确认，直接修复止血。

**执行步骤**：

1. **加载安全规则**：读取 `.trae/rules/` 中的安全策略规则（如 `security_rules.md`）
2. **风险等级评估**：建立扫描范围和优先级
3. **逐项审计**：按安全策略逐项检查
   - 输入验证与注入防护（SQL 注入、XSS、命令注入）
   - 认证与授权（硬编码密钥、弱密码策略、会话管理）
   - 数据保护（敏感信息泄露、环境配置安全）
   - 依赖安全（已知漏洞、过期依赖）
4. **🔴 严重问题自动修复**：对高危漏洞直接修复
   - 修复后检查关联产出是否存在同类问题
   - 每个修复必须可独立回滚
5. **🟡 中等问题归档**：写入 `tasks/待完成任务.md`
   - 每条归档包含：漏洞描述、风险等级、建议修复方案
   - 来源标注："自动安全 {日期}"
6. **🟢 轻微问题报告**：仅在审计报告中列出，不强制修复
7. **输出审计报告**：汇总所有发现，包含修复统计和风险矩阵
