# 全自动流程模式执行指南

本文档详细定义生长器的八大全自动流程模式。与十二大手动模式不同，全自动模式的核心特征是：**用户只触发一次，AI 完成从分析到执行到收尾的全部流程，无需中间交互确认。**

## 通用安全边界

所有全自动模式共享以下安全边界，各模式仅列出**例外**：

- 不修改数据库结构
- 不删除数据
- 不确定的问题归档而非强修
- 不修改 `.trae/rules/` 下的规则文件（规则变更需走年轮审判或规则对齐入口）
- 每个修复必须可独立回滚

**各模式例外**：

| 模式 | 例外 |
|------|------|
| 种木成林 | ✅ 允许创建数据库 schema（唯一拥有此权限的自动模式） |
| 年轮审判 | ✅ 允许修改规则文件（必须同时更新 ADR） |
| 翠幕天罗 | ✅ 允许删除冗余/废弃产出（只删非核心业务产出） |
| 自动安全 | ✅ 允许自动修复高危漏洞（SQL 注入、XSS、硬编码密钥等） |

## 入口 16：🌰 新枝破土（auto-innovate）

**触发**：用户说"新枝破土/全自动创新设计/创新设计/自动加新功能/给我一个惊喜"

**目的**：AI 自主分析项目现有功能和架构，发现缺失但契合的功能点，直接实现——不开会、不写文档、直接产出，给用户一个"拆盲盒"式的惊喜。

**执行步骤**：

1. **加载上下文与分析现状**：加载 `.trae/rules/` 建立项目约束边界画像；读取业务模块结构、数据模型、页面和路由，建立已实现功能清单
2. **发现缺口**：在项目约束边界内寻找"有它更好"的功能点：
   - 数据层已有但展示层未使用的 → 补展示
   - 同类功能模式未覆盖的模块 → 复制模式
   - 操作流中断点（有 A 和 C 但缺 B） → 补齐
   - 优先级：**数据已就绪 > 模式可复用 > 填补流程断点**
3. **设计最小可行功能**：新增产出优先 50-150 行级别（不超过 300 行）；严格遵循分层规范，不引入新模式或未使用的第三方库
4. **直接实装**：不产出任何文档，直接修改产出——分步执行 → 检查关联产出 → 审核
5. **审核质量**：分层合规、不破坏现有功能、自然生长阈值
6. **收尾**：清理冗余导入和逻辑；将后续优化点写入 `tasks/待完成任务.md`（只写待完成，不涉及已完成任务.md）；生成聚焦测试建议
7. **汇报惊喜**：用 2-3 句话告诉用户"我加了什么、为什么加、在哪里看"

**输入格式**：`新枝破土`

**创新约束**（不可违反）：
- 新功能必须在现有架构内生长，不破坏分层、不引入新模式
- 不产出任何文档文件（`.md`）
- 不修改数据库 schema（不执行 migration）
- 不删除或重构现有功能
- 新增产出优先选择"数据已就绪只差展示层"的 low-hanging fruit

**开奖说明**：此模式具有"开奖"性质——AI 自主选择做什么功能。如果不满意，使用方案生长或速修调整即可，不会对项目造成结构性破坏。

> 聚焦测试建议的完整输出格式和生成原则详见 [test-suggestion-guide.md](test-suggestion-guide.md)。

## 入口 17：🌳 神木回天（auto-heal）

**触发**：用户说"神木回天/全自动健康度优化/健康度优化/自动体检修复/全身体检修复"

**目的**：全自动执行健康度诊断 → 根据诊断报告自动修复可修复的问题 → 将无法自动修复的问题归档到 `tasks/待完成任务.md`。

> 此技能将健康度诊断和内嵌修复融为一体：全自动模式下无需分步操作，一条指令走完全流程。

**执行步骤**：

1. **执行健康度诊断**：执行 grower 健康度诊断流程（根系/躯干/枝叶三层检查），产出完整问题清单
2. **问题分类**：将所有问题分为三类：

   | 类别 | 判断标准 | 处理方式 |
   |------|---------|---------|
   | 可直接修复 | 单文件、不涉及架构决策/API 契约变更、预估 < 30 行 | 自动修复 |
   | 需谨慎处理 | 跨 2+ 文件、涉及架构层、需 API 变更/数据库迁移 | 归档待办 |
   | 无法自动修复 | 需人工判断、设计决策、第三方依赖、安全策略 | 归档待办 |

3. **自动修复**：对"可直接修复"类问题逐个修复，遵循速修原则（最小化修改、定位根源、不顺手优化），修复后检查关联产出
4. **归档待办**：将"需谨慎处理"和"无法自动修复"的问题写入 `tasks/待完成任务.md`——每条包含问题描述、影响范围、建议方案、优先级（P1-P5）；标注来源（如"神木回天 2026-05-19"）；只写入待完成，不涉及已完成任务.md
5. **审核与收尾**：确认所有修复未引入新问题；生成聚焦测试建议
6. **汇报结果**：已修复 X 项、已归档 Y 项、跳过 Z 项（及原因）

**输入格式**：`神木回天`

> 聚焦测试建议的完整输出格式和生成原则详见 [test-suggestion-guide.md](test-suggestion-guide.md)。

## 入口 18：⚔️ 斩木除根（auto-fix-tasks）

**触发**：用户说"斩木除根/全自动修复任务/修复待办/自动清任务/批量修复任务"

**目的**：自动读取 `tasks/待完成任务.md`，解析可执行的任务条目，规划方案并逐项修复，完成后将已修复条目**迁移**到 `tasks/已完成任务.md`。

**执行步骤**：

1. **读取任务清单**：解析 `tasks/待完成任务.md`，提取所有条目；清单为空 → 告知用户"没有待修复任务，大树很健康"
2. **评估可执行性**：过滤掉描述不清（→标注"描述不清"）、依赖未满足（→标注"依赖未满足"）、需人工决策（→标注"需人工决策"）的任务
3. **规划执行方案**：按优先级排序，考虑任务间依赖关系
4. **逐任务执行**：对每个可执行任务按方案生长模式标准流程：设计分步方案 → 检查关联产出 → 执行修复 → 审核 → 清理
5. **汇总审核**：跨任务综合审核——修改是否冲突、是否引入重复内容、整体简洁性
6. **清理任务清单**：已完成 → 从待完成**迁移**到已完成任务.md（补写修复日期和修复方式），不得直接删除；跳过的任务保留并补充原因；新问题追加到末尾。格式与规范详见 [grow-plan-template.md](grow-plan-template.md) 的"任务清单更新规范"章节
7. **生成聚焦测试建议**：按功能模块分组生成测试步骤
8. **汇报结果**：已完成 X 项、跳过 Y 项（含原因）、剩余 Z 项

**输入格式**：`斩木除根`

**执行约束**：
- 每个任务独立完成、独立审核，不得合并步骤跳过审核
- 任务间有依赖时，先完成被依赖的任务
- 如果某个任务执行失败，标记失败原因并继续下一个，不中断全流程
- 修复过程中发现的新问题 → 追加到任务清单末尾

> 聚焦测试建议的完整输出格式和生成原则详见 [test-suggestion-guide.md](test-suggestion-guide.md)。

## 入口 19：🌿 翠幕天罗（auto-review）

**触发**：用户说"翠幕天罗/全自动提交审查/自动提交审查/自动审查本轮更新/全自动审查"

**目的**：自动扫描本轮产出变更，逐文件审查质量，修复发现的问题，清理冗余产出，更新任务清单——提交前的最后一道防线。

**执行步骤**：

1. **识别变更范围**：扫描最近的未提交变更（或最近一次 commit 以来的所有修改），确定涉及的文件、模块、层，生成变更摘要：{N} 个文件，{M} 个模块
2. **加载规则上下文**：加载 `.trae/rules/` 中相关规则文件，建立"审查基准"
3. **逐文件审查**：对每个变更文件检查——自然生长（不提前抽象）、分层合规（各层职责清晰）、产出简洁性（无冗余）、关联产出影响、安全与性能
4. **问题分类**：

   | 类别 | 判断标准 | 处理方式 |
   |------|---------|---------|
   | 可立即修复 | 风格、冗余产出、未使用导入、命名不规范、单文件逻辑错误、预估 < 30 行 | 自动修复 |
   | 需谨慎处理 | 跨 2+ 文件、涉及架构层修改、可能影响关联模块 | 自动修复 + 额外审核 |
   | 无法自动修复 | 需人工判断的设计决策、大规模重构 | 归档待办 |

5. **自动修复**：对"可立即修复"和"需谨慎处理"类问题逐个修复，遵循最小修改原则，修复后检查关联产出
6. **汇总审核**：跨文件综合审核——修复一致性、是否引入重复内容、整体简洁性
7. **清理旧产出**：删除因修复而废弃的产出、导入、样式
8. **更新任务清单**：更新 `tasks/待完成任务.md` 和 `tasks/已完成任务.md`——已完成的迁移（补写修复方式）；"无法自动修复"类添加到待办；被更上层方案覆盖的子任务直接移除。格式与规范详见 [grow-plan-template.md](grow-plan-template.md) 的"任务清单更新规范"章节
9. **生成聚焦测试建议**：基于本轮变更生成用户级手动测试清单
10. **汇报结果**：已审查 {N} 个文件、修复 {M} 个问题、归档 {K} 个待办

**输入格式**：`翠幕天罗`

**安全边界**（不可违反）：
- 不删除核心业务产出（只删除冗余/废弃产出）
- 每个修复必须可独立回滚

### 审查检查清单

> 完整审核维度和检查项详见 [pre-commit-review-guide.md](pre-commit-review-guide.md)，以下为翠幕天罗专用的精简版。

| 检查维度 | 检查项 |
|---------|--------|
| 架构合规 | 分层规范、依赖方向、越权调用 |
| 自然生长 | 不提前抽象、不强塞模式、3 次阈值 |
| 代码质量 | 冗余产出、未使用的导入、命名一致性 |
| 安全性 | SQL 注入、XSS、密钥暴露、权限校验 |
| 关联性 | 影响范围、潜在回归、API 契约一致性 |

## 入口 20：🔱 年轮审判（auto-align）

**触发**：用户说"年轮审判/全自动规则对齐/自动规则对齐/自动交叉检查/全自动交叉检查"

**目的**：自动对比 `.trae/rules/` 中的规则文档与项目实际产出，双向对齐——规则好就改产出，产出好就改规则，维护年轮记录。

**执行步骤**：

1. **加载规则**：按需加载 `.trae/rules/` 中相关规则文件，建立"规则的期望状态"画像
2. **扫描产出实践**：分层边界、命名规范、导入方式、错误处理、组件模式
3. **交叉检查**：
   - **规则 → 产出**：规则要求但产出未遵守 → 标记为"需改产出"
   - **产出 → 规则**：产出中存在规则未覆盖的最佳实践 → 标记为"需更新规则"
   - **规则 ↔ 规则**：规则文件间矛盾 → 标记为"规则冲突"
   - **设计基线 vs 实际产出**（如果存在 `docs/` 下的创意设计单页纸）：已实现功能是否与原始设计一致？是否有"不做清单"中的功能被意外实现？ → 标记为"设计偏离"
4. **判断标准**：规则更合理 → 改产出；产出更合理 → 改规则；两者都合理 → 选择对长期维护更有利的方案
5. **问题分类**：

   | 类别 | 判断标准 | 处理方式 |
   |------|---------|---------|
   | 可直接对齐 | 单文件修改、命名规范、导入约定、错误处理 | 自动修复 |
   | 需谨慎处理 | 跨多文件、涉及架构层、分层规范对齐 | 自动修复 + 额外审核 |
   | 无法自动修复 | 规则矛盾需人工裁决、架构级重构 | 归档待办 |
   | 设计偏离 | 功能与原始设计不一致、不做清单被突破 | 归档待办 + 退出声明中报告 |

6. **自动对齐**：对"可直接对齐"和"需谨慎处理"类问题逐个修复，优先修复"规则好就改产出"项，修复后检查关联产出
7. **维护年轮记录**：修改规则文件时，补写或更新对应的 ADR——记录决策原因和时间背景
8. **审核对齐质量**：确认规则与产出一致性
9. **清理不当产出**：删除对齐过程中发现的冗余或违规产出
10. **汇报结果**：已检查 {N} 项规则、修改 {M} 个文件、更新 {K} 条 ADR、归档 {L} 个待办。如发现设计偏离，在报告末尾单独列出

**输入格式**：`年轮审判`（全量检查）

**安全边界**（不可违反）：
- 不删除核心业务产出
- 规则文件的修改必须同时更新 ADR
- 规则矛盾不强行裁决，归档待办

### 年轮维护规则

| 操作 | 年轮动作 |
|------|---------|
| 修改规则文件 | 补写 ADR，记录"规则变更原因" |
| 废弃规则 | 标记"已废弃"但不删除，保留为年轮 |
| 新增规则 | 补写 ADR，记录"新规则来源" |
| 规则矛盾 | 归档待办，由年轮审判或规则对齐入口后续处理 |

## 入口 21：🌲 种木成林（auto-bootstrap）

**触发**：用户说"种木成林/从零建造/全自动项目启动/森林崛起"

**目的**：填补 seeder→grower 之间的"从零到一"断层。读取 rules + 设计文档，分模块从零构建项目初始产出，包括数据存储 schema、躯干基类、首批核心模块——建造完毕后自动交接给全自动循环。

**前置条件**：
- `.trae/rules/` 完整（已由 seeder 生成）
- 创意设计单页纸存在于 `docs/` 目录（已由 seeder 生成）
- 项目产出尚为空或仅有骨架（此模式设计为"从零建造"，已有大量代码时仅建造缺失部分）

**执行步骤**：

### 阶段 1：解析项目蓝图

加载 `docs/` 创意设计单页纸，提取核心模块清单（模块名、描述、优先级、依赖、功能要点）、开发顺序和完成标准；加载 `.trae/rules/` 全部规则；解析"不做清单"中的 `[禁止建造]` 标记项（硬约束）。输出模块清单和依赖图，进入建造前展示推断的数据模型摘要给用户确认（默认通过，用户可中断修正）。

### 阶段 2：建造骨架（数据库 + 躯干基类）

> ⚠️ **DB 权限**：种木成林是唯一拥有数据库 schema 创建权限的自动模式。

基于模块蓝图推断数据表结构，生成建表语句和数据层；实现数据访问基类（通用操作方法）、业务逻辑基类（校验、事务、错误处理）、路由处理基类（参数解析、响应格式化）、全局错误处理中间件、认证授权框架；搭建路由注册框架；验证分层结构、命名规范、错误处理和导入别名。

### 阶段 3：逐模块建造枝叶

按开发顺序对每个模块依次建造数据访问层、业务逻辑层、路由处理层（薄层委托）、Route 层和展示层页面（如适用）。每个模块完成后审核分层合规、自然生长和产出简洁性，检查模块间引用关系正确，更新 `docs/模块开发状态.md`。

**建造策略**：P1 模块完整建造（全层），P2 模块建造骨架（数据+逻辑），展示层和入口层写入待完成任务；模块建造失败不中断全流程；不覆盖已有文件。

### 阶段 4：生成初始任务清单

生成 `tasks/待完成任务.md`（P2+ 模块建造任务、不完整功能、各模块测试建议汇总）、`tasks/已完成任务.md`（首次创建，格式详见 [grow-plan-template.md](grow-plan-template.md) 的"任务清单更新规范"章节）、`docs/模块开发状态.md`（各模块 ✅完成/🔧建造中/📋待建/💡规划中 状态及依赖关系）。

### 阶段 5：首轮质量把关

运行翠幕天罗逻辑审查阶段 2-3 的全部代码；运行年轮审判逻辑检查与规则一致性；修复发现的问题；生成聚焦测试建议（详见 [test-suggestion-guide.md](test-suggestion-guide.md)）。

### 阶段 6：交接给全自动循环

输出建造报告（已建成/待建模块数、任务清单条数、模块开发状态文件路径），建议后续操作：

```
🌲 种木成林建造完毕。建议执行全自动循环继续开发：
  年轮审判 → 自动体检 → 神木回天 → 斩木除根 → 新枝破土 → 翠幕天罗 → 自动安全 → (循环)
```

**输入格式**：`种木成林`

**安全边界**（不可违反）：
- ✅ 允许创建数据库 schema（仅此模式有此权限）
- 每个模块建造完成后必须审核
- 模块建造失败不中断全流程，标记失败原因继续下一个
- 不覆盖已有文件、不修改规则文件、不删除已有产出

**与新枝破土的区别**：
- 新枝破土：在已有产出中找缺口，**一次只加一个功能**（小规模级别）
- 种木成林：在零产出基础上，**批量建造项目骨架和首批核心模块**（全栈、多模块）

## 全自动循环链路

7 个全自动模式按循环链串联：**年轮审判 → 自动体检 → 神木回天 → 斩木除根 → 新枝破土 → 翠幕天罗 → 自动安全 → (回到年轮审判)**。循环持续运行直到满足收敛条件。

**循环终止条件**（三阶段收敛制）：

每轮循环结束后检查当前阶段是否满足收敛条件：

| 阶段 | 收敛条件 |
|------|---------|
| 扎根阶段（seeder 完成后即可达成） | ✅ `.trae/rules/` 完整 + ADR 覆盖关键决策；✅ 样板验证通过（第 5 步基本操作可运行） |
| 躯干阶段 | 所有 P1 模块为"✅ 完成"；神木回天健康度综合评分 > 7/10；年轮审判无 P1 级别不一致；主要任务全部实现（对照创意设计单页纸）；不做清单未被突破 |
| 全阶段收敛（可视为项目交付） | 躯干阶段条件全部满足；翠幕天罗审查无 P1/P2 问题；任务清单为空或只剩"需人工决策"项；新枝破土连续 2 轮未发现显著功能缺口 |

**阶段递进规则**：
- 当前阶段条件满足后，循环**自动尝试进入下一阶段**——以更高标准继续迭代
- 用户可在任意时刻手动终止循环（"停止循环"）
- **全阶段收敛**的所有条件均满足时，循环自动终止，退出声明中报告"项目已达全阶段收敛，可视为交付状态"

## 入口 22：🔍 自动体检（auto-health-check）

**触发**：用户说"自动体检/全自动体检"

**目的**：全自动执行健康度诊断（纯诊断，不修复），产出完整诊断报告，可行动问题归档待办。

> 此模式是神木回天的"只看不动"版本——适合先了解项目全貌再决定修复策略。

**执行步骤**：

1. **加载规则与映射**：读取 `.trae/rules/` 建立抽象术语到项目实现的映射
2. **执行三层诊断**：根系检查（规则文件完整性、规则间一致性、ADR 对齐）、躯干检查（分层合规、命名一致性、导入规范、自然生长原则）、枝叶检查（产出健康度、冗余产出、验证覆盖、安全风险）
3. **问题分级**：按 P1-P5 优先级分级
4. **归档可行动问题**：将 P1-P3 级问题写入 `tasks/待完成任务.md`——每条包含问题描述、影响范围、建议方案、优先级；来源标注"自动体检 {日期}"
5. **生成诊断报告**：输出完整诊断结果，包含各层评分和问题清单
6. **生成聚焦测试建议**：基于诊断发现的风险点生成验证步骤

**输入格式**：`自动体检` 或 `全自动体检`

**与神木回天的区别**：自动体检**纯诊断不修复**，神木回天**诊断 + 自动修复**。自动体检适合用作全自动循环的第一步（先了解问题全貌），神木回天适合有明确修复目标的场景。

> 聚焦测试建议的完整输出格式和生成原则详见 [test-suggestion-guide.md](test-suggestion-guide.md)。

## 入口 23：🛡️ 自动安全（auto-security）

**触发**：用户说"自动安全/全自动安全扫描"

**目的**：全自动执行安全扫描，严重问题自动修复，中等问题归档待办，轻微问题仅报告。

> 此模式将安全审计和紧急修复融为一体：高危漏洞不等人工确认，直接修复止血。

**执行步骤**：

1. **加载安全规则**：读取 `.trae/rules/` 中的安全策略规则（如 `security_rules.md`）
2. **风险等级评估**：建立扫描范围和优先级
3. **逐项审计**：输入验证与注入防护（SQL 注入、XSS、命令注入）、认证与授权（硬编码密钥、弱密码策略、会话管理）、数据保护（敏感信息泄露、环境配置安全）、依赖安全（已知漏洞、过期依赖）
4. **🔴 严重问题自动修复**：高危漏洞直接修复，修复后检查关联产出是否存在同类问题
5. **🟡 中等问题归档**：写入 `tasks/待完成任务.md`——每条包含漏洞描述、风险等级、建议修复方案；来源标注"自动安全 {日期}"
6. **🟢 轻微问题报告**：仅在审计报告中列出，不强制修复
7. **输出审计报告**：汇总所有发现，包含修复统计和风险矩阵

**输入格式**：`自动安全` 或 `全自动安全扫描`
