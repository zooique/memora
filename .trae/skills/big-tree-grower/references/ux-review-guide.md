# 体验评审指南

> 用于入口 11"体验评审"，从用户视角对前端交互质量、视觉一致性、用户心智匹配度进行全面评审

---

## 评审前置准备

1. 加载 `.trae/rules/frontend_architecture_rules.md` 了解前端技术栈、组件规范、样式入口文件
2. 加载 `.trae/rules/project-rules.md` 了解项目整体约定
3. 加载 `.trae/rules/architecture-quickref.md` 了解前端工厂模式、通用组件等约定名称
4. 浏览前端页面目录结构，了解实际页面数量和组件分布
5. 如果存在 `docs/创意设计单页纸.md`，加载以了解项目的核心矛盾（有助于判断 UX 设计是否匹配用户心智）

## 评审维度

```
┌─────────────────────────────────────────────────────┐
│                   🎨 体验评审维度                      │
│                                                      │
│  1. 视觉一致性    — 设计语言是否统一                   │
│  2. 交互模式      — 操作行为是否可预测                 │
│  3. 操作路径      — 用户完成任务是否高效               │
│  4. 状态覆盖      — 所有状态是否都有合理反馈            │
│  5. 认知负荷      — 信息密度是否过载                   │
│  6. 导航架构      — 信息查找是否便捷                   │
│  7. 视觉审美      — 是否千树一面，缺乏项目个性          │
└─────────────────────────────────────────────────────┘
```

> 维度 7（视觉审美）的检查清单详见 [frontend-aesthetics-guide.md](frontend-aesthetics-guide.md) 中的"千树一面检测"章节。

### 维度 1：视觉一致性

**目标**：检查设计语言是否统一——颜色、字体、间距、圆角、阴影、图标等是否有一致的视觉规范

#### 1.1 颜色体系

| 检查项 | 方法 | 通过标准 |
|--------|------|---------|
| 主色/辅色是否统一 | 搜索 CSS 文件中的颜色值，统计去重后的颜色数 | 颜色数合理（主色 ≤3、辅色 ≤5、中性色 ≤5），同一语义使用同一颜色 |
| 功能色是否一致 | 检查成功/警告/错误/信息色在各页面是否一致 | 绿色=成功、红色=错误、黄色/橙色=警告，不混用 |
| 是否有硬编码颜色 | Grep 搜索页面 CSS 中的颜色代码 | 颜色优先来自 CSS 变量/设计令牌，不出现大量硬编码 `#xxx` |
| 暗色模式/主题切换 | 检查颜色是否使用 CSS 变量 | 如果项目支持主题切换，颜色值均来自变量 |

#### 1.2 字体与排版

| 检查项 | 方法 | 通过标准 |
|--------|------|---------|
| 字体族是否统一 | 检查各页面的 font-family | 全局统一字体族，不混用多套 |
| 字号层级是否合理 | 统计页面中的 font-size 值 | 有明确的字号层级（标题/正文/辅助文），层级 ≤5 级 |
| 行高是否可读 | 检查正文的行高 | 正文行高 ≥1.5，标题行高适当紧凑 |
| 文本对齐是否统一 | 检查表格列对齐、表单标签对齐 | 同类型内容对齐方式一致 |

#### 1.3 间距与布局

| 检查项 | 方法 | 通过标准 |
|--------|------|---------|
| 间距体系是否统一 | 检查各页面的 padding/margin/gap 值 | 使用固定的间距尺度（如 4/8/12/16/24/32），不出现"差不多"的值 |
| 卡片/面板内边距是否一致 | 抽查 3+ 个卡片/面板 | 同类型容器内边距一致 |
| 按钮间距是否统一 | 检查弹窗/表单底部的按钮间距 | 按钮间距一致 |
| 页面最大宽度是否合理 | 检查容器 max-width | 宽度合理（内容页 ≤1200px，详情页 ≤800px），不会在大屏上无限拉伸 |

#### 1.4 圆角与阴影

| 检查项 | 方法 | 通过标准 |
|--------|------|---------|
| 圆角大小是否统一 | 统计 border-radius 值 | 小圆角（按钮/输入框）统一，大圆角（卡片/弹窗）统一 |
| 阴影层级是否有语义 | 检查 box-shadow 值 | 不同层级元素（卡片/弹窗/下拉）使用不同深度的阴影 |

### 维度 2：交互模式一致性

**目标**：检查相似场景的交互行为是否可预测——用户在 A 页面学会的操作，在 B 页面是否同样有效

#### 2.1 按钮行为规范

| 检查项 | 方法 | 通过标准 |
|--------|------|---------|
| 主次按钮样式统一 | 抽查 5+ 个页面的按钮 | 主按钮（提交/确认）样式统一，次按钮（取消/返回）样式统一 |
| 危险操作有二次确认 | Grep 搜索删除/移除等操作 | 删除、清空、不可逆操作有确认弹窗 |
| 按钮禁用态有一致表现 | 检查表单中按钮的 disabled 状态 | 未填完表单时提交按钮应禁用，样式与其他禁用按钮一致 |
| 加载态有反馈 | 检查提交按钮是否有 loading 态 | 提交中按钮显示 loading + 禁止重复点击 |

#### 2.2 表单交互规范

| 检查项 | 方法 | 通过标准 |
|--------|------|---------|
| 必填项是否有明确标识 | 抽查 3+ 个表单 | 必填项有 `*` 或明确标注 |
| 校验反馈是否及时 | 检查表单校验触发时机 | 失焦校验 + 提交校验，错误信息显示在对应字段旁 |
| 下拉/选择器行为一致 | 抽查各页面的选择器 | 下拉触发方式（点击/输入）、搜素行为、多选操作一致 |
| 日期/时间选择器一致 | 搜索日期相关组件 | 所有页面使用相同的日期选择器组件 |

#### 2.3 弹窗与对话框

| 检查项 | 方法 | 通过标准 |
|--------|------|---------|
| 弹窗触发方式一致 | 检查弹窗的打开方式 | 同类型操作（编辑/新增/确认）使用相同的弹窗触发方式 |
| 弹窗关闭行为一致 | 检查弹窗关闭方式 | 支持点遮罩关闭、ESC 关闭、关闭按钮，关闭时是否保留已填数据需一致 |
| 弹窗宽度是否合理 | 检查弹窗 width | 表单弹窗适中（500-700px），确认弹窗紧凑（400-500px），不外溢出 |

#### 2.4 表格与列表交互

| 检查项 | 方法 | 通过标准 |
|--------|------|---------|
| 分页行为一致 | 抽查 3+ 个列表页 | 分页位置（上/下/均）、每页条数、跳转行为一致 |
| 排序/筛选行为一致 | 检查列表的排序和筛选 | 排序指示器位置统一，筛选条件布局统一 |
| 行操作按钮位置一致 | 抽查各表格的操作列 | 操作列位置和按钮风格统一 |
| 表格在移动端的适配 | 检查响应式表格 | 有合理的移动端降级（横向滚动 或 卡片化），关键列不被隐藏 |

### 维度 3：操作路径与心智模型

**目标**：检查用户完成任务的最短路径是否顺畅、是否符合"肌肉记忆"

#### 3.1 核心路径走查

| 检查项 | 方法 | 通过标准 |
|--------|------|---------|
| CRUD 操作闭环是否流畅 | 走查核心模块：创建→列表确认→编辑→列表确认→删除 | 每个步骤 ≤3 次点击/输入完成，操作后有反馈 |
| 表单提交流程是否连贯 | 走查提交→校验→成功/失败→返回 | 成功后给出明确提示并回到合理页面，失败后保留已填数据 |
| 搜索/筛选流程是否高效 | 走查搜索→查看结果→清空搜索 | 搜索触发不超过 2 步，结果即时刷新，可清空筛选 |

#### 3.2 路径效率

| 检查项 | 方法 | 通过标准 |
|--------|------|---------|
| 关键任务的操作步骤 | 计算用户完成一个核心任务需要的点击/输入次数 | 核心任务 ≤5 步，高频任务 ≤3 步 |
| 路径是否有"死胡同" | 走查页面，检查是否所有页面都能回到主流程 | 每个页面都有明确的返回/关闭路径，不存在"回不去"的页面 |
| 是否有冗余步骤 | 走查常见操作，检查中间是否有不必要的确认/跳转 | 不出现"先 A 再 B 再回到 A"的回环，除非业务必需 |

#### 3.3 心智模型匹配

| 检查项 | 方法 | 通过标准 |
|--------|------|---------|
| 命名是否匹配用户语言 | 检查页面标题、按钮文案、表单标签 | 使用用户能理解的词汇，不使用技术术语（如"commit""persist""fetch"） |
| 操作顺序是否匹配直觉 | 检查关键流程的步骤顺序 | 步骤顺序符合用户心理预期（如先选类型再填详情，而非相反） |
| 数据展示是否匹配使用场景 | 检查列表/详情的信息组织 | 最常用的信息在最前面/最显眼的位置 |
| 图标语义是否准确 | 检查图标的实际含义 | 图标与操作语义匹配（编辑=铅笔、删除=垃圾桶、搜索=放大镜） |

### 维度 4：状态覆盖

**目标**：检查所有界面状态是否都有合理的视觉反馈

#### 4.1 数据状态

| 状态 | 检查方式 | 通过标准 |
|------|---------|---------|
| 加载中 | 检查列表/详情首次加载 | 有骨架屏或 loading 指示器，不出现"空白然后突然出现" |
| 空数据 | 检查无数据时的列表/表格 | 有空状态插图 + 引导文案（如"暂无数据，点击新建"） |
| 有数据 | 正常展示 | 数据正确呈现，无样式错乱 |
| 数据过多 | 检查大数据量时的表现 | 有分页/虚拟滚动/懒加载，不一次渲染全部 |
| 数据过期/异常 | 检查数据获取失败时 | 有错误提示 + 重试按钮，不静默失败 |

#### 4.2 操作反馈

| 状态 | 检查方式 | 通过标准 |
|------|---------|---------|
| 操作成功 | 触发 CRUD 操作后 | 有成功提示（Toast/消息），提示后自动消失或手动关闭 |
| 操作失败 | 触发失败操作后 | 有错误提示，说明失败原因，保留用户已输入数据 |
| 操作进行中 | 触发耗时操作后 | 按钮进入 loading 态，禁用重复操作 |
| 网络异常 | 模拟网络中断 | 有网络异常提示，关键操作本地暂存 |

#### 4.3 权限与边界

| 状态 | 检查方式 | 通过标准 |
|------|---------|---------|
| 无权限 | 检查是否有权限控制 | 无权限的功能不展示（而非展示后报错） |
| 数据边界 | 检查边界值输入 | 数值输入有范围限制，文本输入有长度限制 |
| 并发冲突 | 检查多人编辑同一数据 | 有乐观锁或提示（如果项目有协作场景） |

### 维度 5：认知负荷

**目标**：评估每个页面的信息密度是否合理——用户一眼能否理解"这个页面是干什么的、我该做什么"

#### 5.1 信息密度

| 检查项 | 方法 | 通过标准 |
|--------|------|---------|
| 首屏信息量 | 统计首屏可见的操作/信息项 | 核心页面首屏 ≤7±2 个关键元素（信息块、按钮组） |
| 表单字段数 | 统计每个表单的字段数 | 新增/编辑表单 ≤15 个字段，超过时做分组或分步 |
| 表格列数 | 统计表格的可见列数 | 表格 ≤8 列，超出时做列隐藏或紧凑布局 |
| 单页滚屏长度 | 检查页面是否需要大量滚动 | 非列表页不超过 3 屏，关键操作在首屏可见 |

#### 5.2 视觉层级

| 检查项 | 方法 | 通过标准 |
|--------|------|---------|
| 视觉主次分明 | 检查页面是否有明确的视觉焦点 | 最重要信息有最大视觉权重（大小/颜色/位置） |
| 信息分组清晰 | 检查内容是否有逻辑分组 | 相关内容在视觉上聚合（卡片/分隔线/间距） |
| 操作引导明确 | 检查用户是否能快速找到 CTA | 主要操作按钮位置醒目、颜色突出 |
| 无关信息是否隐藏 | 检查页面上是否有"应该隐藏但目前可见"的信息 | 高级设置折叠、次要信息收起、详情按需展开 |

#### 5.3 文案质量

| 检查项 | 方法 | 通过标准 |
|--------|------|---------|
| 提示文案是否清晰 | 检查错误提示/空状态/加载文案 | 提示文案描述具体（"请输入正确的手机号"而非"输入错误"） |
| 按钮文案是否可行动 | 检查所有按钮的文案 | 按钮使用动词（"保存""删除""取消"）而非名词或模糊词汇 |
| 页面标题是否描述性强 | 检查每个页面的标题/面包屑 | 标题准确描述当前页面内容，面包屑路径完整 |

---

### 维度 6：导航与信息架构

**目标**：检查用户能否高效地在页面间导航、找到所需信息

#### 6.1 导航结构

| 检查项 | 方法 | 通过标准 |
|--------|------|---------|
| 导航层级深度 | 统计从首页到最深页面的点击次数 | ≤4 层，最深页面有路径指示 |
| 侧边栏/顶部导航一致性 | 检查各页面的导航菜单 | 所有页面导航结构一致，没有"在某些页面导航消失"的情况 |
| 当前页高亮 | 检查导航高亮 | 当前所在页的导航项有明确的高亮/激活状态 |
| 面包屑完整性 | 检查详情/编辑页的面包屑 | 面包屑路径正确，可点击返回上级 |

#### 6.2 信息查找效率

| 检查项 | 方法 | 通过标准 |
|--------|------|---------|
| 全局搜索可用性 | 检查是否有搜索入口 | 数据较多的系统有全局搜索，搜索结果可快速跳转 |
| 列表筛选/搜索效率 | 检查列表页的筛选条件 | 筛选条件不冗余（只保留用户真正需要的），筛选项 ≤6 个 |
| 关联跳转 | 检查列表→详情的跳转 | 列表数据可点击跳转到详情，详情页可返回列表（保持筛选状态） |

#### 6.3 响应式与跨设备

| 检查项 | 方法 | 通过标准 |
|--------|------|---------|
| 移动端基础可用 | 检查在窄屏幕（375px）的关键页面 | 不水平溢出，关键操作可触达，文字可读 |
| 平板端布局 | 检查在中等屏幕（768px）的表现 | 布局合理利用空间 |
| 触控友好 | 检查可点击元素大小 | 可点击区域 ≥44×44px（移动端），相邻可点击元素有足够间距 |

## 评审阶段聚焦

> 不同项目周期的 UX 风险不同。评审时根据项目当前阶段调整各维度的检查深度。

| 项目阶段 | 当前特征 | 评审侧重 | 评审深度 |
|---------|---------|---------|---------|
| 🏗️ 建设期 | 页面快速增加，组件库仍在搭建 | **维度 1（视觉一致性）+ 维度 3（操作路径）** | 严格——此时建立设计规范成本低，路径修正也容易 |
| 🌿 生长稳定期 | 核心页面完成，以优化和新增为主 | **维度 2（交互模式）+ 维度 6（导航架构）** | 严格——此时最易出现交互不一致和导航膨胀 |
| 🍂 成熟期/维护期 | 功能稳定，历史页面积累多 | **维度 4（状态覆盖）+ 维度 5（认知负荷）** | 严格——积累的页面最易出现状态遗漏和信息过载 |
| 🔄 重构期 | 大规模 UI 变更 | **维度 1+2+3** | 正常——重构期间做设计审计 |

## UX 体验问题严重程度分级

### 🔴 严重（阻塞用户操作）

- 操作路径中断，"回不去"的页面
- 提交/删除无任何反馈，用户不知道操作是否成功
- 错误提示模糊，用户无法知道怎么修正
- 关键 CTA 按钮不可见或无法点击
- 核心数据展示错误（张冠李戴）

### 🟡 中等（影响用户体验）

- 同类型操作在不同页面交互不一致
- 空状态缺少引导，用户不知道下一步做什么
- 表单校验在提交时才触发（而非即时）
- 加载时间过长且无反馈
- 关键操作步骤过多（>5 步）
- 移动端布局断裂

### 🟢 轻微（影响精致度）

- 间距在相似场景中不统一
- 按钮样式在各页面有微小差异
- 图标语义勉强可用但不够精准
- 文案措辞不够友好
- 动画缺失（过渡生硬）

## 评审执行策略

### 全站评审（默认）

1. 先做全局检查（维度 1 视觉一致性 + 维度 6 导航架构），因为它们需要跨页面对比
2. 再按页面逐个走查（维度 2-5），抽取 30%-50% 的页面作为样本
3. 核心页面（列表页、表单页、详情页）100% 覆盖
4. 次要页面（设置页、报表页）抽取代表性样本

### 模块聚焦评审

如果用户指定了模块范围：`体验评审：审批模块`

1. 只评审该模块涉及的所有前端页面
2. 视觉一致性仍做全局检查（该模块的颜色/间距是否与全局一致）
3. 其他维度聚焦于该模块内部

### 页面抽样原则

- 每个页面类型至少抽 1 个样本（列表页、表单页、详情页、弹窗）
- 最新修改的页面优先（修改越频繁越需要评审）
- 用户最常访问的页面优先（对照导航结构判断）
