# 版本发布指南

树结果了，要摘下来才能吃。版本发布是养树循环的"果实"环节——项目长得对、长得壮、长得美之后，要打上一个正式的版本号，说明这次结了什么果。

---

## 触发场景

- 手动：`发布版本` `打版本` `release`
- 串联：提交前审查通过后，建议发布版本
- 全自动循环中：翠幕天罗完成后，建议发布版本

---

## 核心流程

```
读取变更记录 → 判断版本级别 → 更新版本号 → 生成 release notes → 打 tag → 按版本号归档销项批次到 tasks/archive/
```

### 第一步：读取变更记录

从以下来源读取本轮变更摘要：
- `tasks/待完成任务.md` 中已销项（✅）的条目
- `tasks/archive/` 中上一版归档批次
- Git 变更日志（`git log` 自上一个 tag）

### 第二步：判断版本级别（Semver）

| 变更类型 | 版本号变化 | 示例 |
|---------|-----------|------|
| 🔴 **Major** | `x+1.0.0` | API 契约变更、数据库 schema 不兼容变更、移除公共接口 |
| 🟡 **Minor** | `x.y+1.0` | 新增功能模块、新增 API 端点、向后兼容的功能增强 |
| 🟢 **Patch** | `x.y.z+1` | Bug 修复、代码清理、测试补充、依赖补丁升级 |
| ⚫ 跳过 | 不发布 | 仅文档变更、仅 rules 变更、无实质代码变更 |

**判断原则**：不确定时选低一级。宁可少升不要多升。

### 第三步：更新版本号

如果项目有 `package.json`：
```json
"version": "x.y.z"
```

同步更新项目中其他引用版本号的位置（如 `manifest.json` 等）。

### 第四步：生成 Release Notes

格式：

```markdown
## v{版本号} —— {一句话总结}

### 新增
- 功能描述

### 修复
- Bug 修复描述

### 优化
- 代码优化和清理描述

### 依赖
- 升级 / 新增 / 移除的依赖
```

如果 `tasks/待完成任务.md` 中已销项条目已有详细的修复记录，可引用："详见台账 v{版本号} 销项批次"。

### 第五步：打 Git Tag

```bash
git tag -a v{版本号} -m "Release v{版本号}"
```

### 第六步：按版本号归档销项批次

把 `tasks/待完成任务.md` 中本版已销项（✅）的条目整区迁入 `tasks/archive/{版本号}.md`（只迁已关闭项，在册未完成项留在台账），归档文件首行记录：
```
v{版本号} 版本发布（{发布日期}） | {版本级别说明}
```

## 跨技术栈适配

| 技术栈 | 版本号位置 | 发布命令 |
|--------|-----------|---------|
| Node.js/JS | `package.json` | `git tag` + `npm publish`（可选） |
| Python | `setup.py` / `pyproject.toml` | `git tag` + 构建工具 |
| Go | 无统一位置，通常在 `main.go` 或 `version.go` | `git tag` |
| Rust | `Cargo.toml` | `git tag` + `cargo publish` |

当项目 rules 中有不同的发布约定时，以 rules 为准。

---

## 发布原则

- 审查不通过不发版
- 有未归档的高危漏洞不发版
- 版本号只升不降
- 打了 tag 就不能删（已发布不可回退）
- 不确定级别时选低级
