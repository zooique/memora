# 大树模型项目播种机（匠码）

代码项目工程方法论。覆盖从创意到架构的全流程：矛盾分析 → 项目决策 → 规则生成 → 样板验证。

## 两种播种模式

播种机根据项目起点不同，有两种工作模式。按六步依次执行，每步完成后与用户确认再进入下一步：

| 步骤 | 模式 A：从零开始 | 模式 B：已有项目接入 |
|------|-----------------|---------------------|
| 1 | 矛盾分析 — 搞清楚做什么、为什么做 | 项目扫描 — 读取现有项目结构和内容 |
| 2 | 土壤分析 — 搞清楚项目环境 | 现状分析 — 识别已有模式、规范、约定 |
| 3 | 项目适配 — 基于土壤分析做关键决策 | 规则提炼 — 好模式固化，混乱部分规范建议 |
| 4 | ADR 记录 — 关键决策留痕 | ADR 补录 — 补充年轮记录 |
| 5 | Rules 生成 — 产出定制化规则文件 | Rules 生成 — 产出定制化规则文件 |
| 6 | 样板验证 — 最小可行产出验证可用性 | 规则验证 — 检查一致性 |

> **快速通道（模式 A）**：用户已有明确创意文档 → 只确认核心矛盾和不做清单；已有明确项目决策 → 只问项目类型和约束。
> **聚焦模式（模式 B）**：大项目可仅对某个子模块做接入，不全量扫描。

**模式 A：从零开始** — 用户有一个新想法，从零搭建代码项目

```
用户说"我要开发一个系统"
  → 第 1 步 矛盾分析：搞清楚做什么、为什么做（矛盾 → 需求冲突/技术债务）
  → 第 2 步 土壤分析：技术现状/团队能力/外部约束
  → 第 3 步 项目适配：技术栈选型（运行时/框架/数据库/前端/样式/认证）
  → 第 4 步 ADR 记录：关键决策留痕，记录技术选型原因
  → 第 5 步 Rules 生成：产出代码项目定制规则（分层/安全/API/数据库/测试等 ~12 个文件）
  → 第 6 步 样板验证：最小 CRUD 模块走通全链路
```

**模式 B：已有项目接入** — 用户已有代码库，但尚未用大树管理

```
用户说"已有代码项目需要大树管理"
  → 第 1 步 项目扫描：读取现有代码结构和 package.json/依赖配置
  → 第 2 步 现状分析：识别已有的分层模式、命名约定、编码规范
  → 第 3 步 规则提炼：从现有代码中提炼规则（已有的好模式 → 固化；混乱的部分 → 提出规范建议）
  → 第 4 步 ADR 补录：为已有技术选型补充年轮记录
  → 第 5 步 Rules 生成：产出适合该项目的代码规则文件
  → 第 6 步 规则验证：检查规则与现有代码的一致性，修正摩擦点

轻量模式：如果项目非常大，可以选择「聚焦模式」——只对项目中的某个子模块做接入，而非全量扫描。
```

## 核心概念

大树模型用树的三层结构理解代码项目：

| 树的部位 | 通用含义 | 代码项目映射 |
|----------|---------|-------------|
| 根系 | 项目规则与架构约束 | `.trae/rules/` — 分层规范、命名约定、安全策略 |
| 躯干 | 可复用的模式与框架 | 公共基类、工具函数、工厂模式 |
| 枝叶 | 具体产出单元 | 业务模块 — 用户管理、订单管理 |

## 大树模型核心原则

| # | 原则 | 播种机视角 |
|---|------|-----------|
| 1 | 根系优先 | 先定规则后写代码；架构约束在编码前通过 `.trae/rules/` 固化 |
| 2 | 自然生长 | 不预设技术栈，基于土壤分析推导选型；不强塞设计模式 |
| 3 | 各层独立 | 业务模块不影响公共组件，躯干增强不破坏规则 |
| 4 | 反馈回路 | 样板验证发现的摩擦点反馈到规则修正 |

## 优先级规则

当多种建议冲突时，按以下优先级裁决（高→低）：

| 优先级 | 类别 | 说明 |
|--------|------|------|
| P1 | 安全性 | 安全漏洞、密钥暴露等必须立即修复 |
| P2 | 架构一致性 | 分层违规、越权调用优先处理 |
| P3 | 自然生长 | 遵循"3 次以上才提取"原则，不强塞模式 |
| P4 | 项目定制需求 | 用户明确的项目偏好和约束 |
| P5 | 风格偏好 | 命名、格式等非关键优化 |

## DO/DON'T 清单

### ✅ 必须做

- 必须按六步流程依次执行，不可跳步
- 核心矛盾必须用 `XX ←→ YY` 双向箭头格式表述
- 主要任务必须 ≤5 个，且直接服务核心矛盾
- 不做清单必须 ≥3 条
- 每步完成后必须与用户确认，再进行下一步
- Rules 必须基于新项目的决策定制，不可将已有项目的模式直接复制到新项目
- 每个关键决策必须有对应的 ADR 记录（年轮）
- 生成的 rules 必须通过"自然生长"标准的自检
- 必须生成最小可行产出，验证根系可用性

- 技术栈选型必须基于土壤分析结果，不可凭空推荐

### ❌ 禁止做

- 禁止跳过矛盾分析直接讨论具体方案
- 禁止替用户编造矛盾或接受模糊描述作为矛盾
- 禁止核心矛盾未确定时讨论具体功能
- 禁止跳过土壤分析直接做项目决策
- 禁止直接复制已有项目的 rules 文件到新项目
- 禁止在没有对应 ADR 的情况下添加规则
- 禁止为新项目生成它不需要的规则文件
- 禁止替用户做关键决策（只能推荐，不能决定）
- 禁止在规则中写入未经决策的模式（先定 ADR，再定规则）
- 禁止过度生成——只生成当前阶段（扎根）需要的文件

- 禁止推荐项目不需要的技术栈（如单机项目推荐微服务架构）

## 问题升级/回退机制

| 场景 | 处理方式 |
|------|---------|
| 第 3 步发现核心矛盾有误 | ⬆️ 回退到第 1 步修正矛盾，然后依次更新后续步骤 |
| 第 5 步发现 ADR 与土壤分析矛盾 | ⬆️ 回退到第 4 步修正 ADR，然后继续第 5 步 |
| 第 5 步发现某些规则缺少 ADR 支撑 | ⬆️ 暂停，先补写 ADR，再继续生成规则 |
| 第 6 步发现规则不可执行 | ⬆️ 记录摩擦，回退到第 5 步修正规则 |
| 任何步骤发现高风险冲突 | ⬆️ 立即暂停，优先处理高风险问题（P1 优先级） |

```
[只做矛盾分析]     →  执行第 1 步后退出

[只做边界和任务]   →  从边界确定开始
```

## 步骤详细内容

### 第 2 步：土壤分析

### 代码项目专属维度

#### 项目类型

| 选项 | 对技术选型的影响 |
|------|----------------|
| 管理后台 | 需要列表页、表单、权限、审批流 |
| API 服务 | 需要 API 版本管理、文档、限流 |
| 全栈应用 | 需要前后端统一规范、SEO/SSR 考虑 |
| 移动端 | 需要离线支持、推送、响应式 |
| 桌面端 | 需要考虑 Electron/Tauri 等壳方案 |

#### 业务领域

| 选项 | 对技术选型的影响 |
|------|----------------|
| 电商 | 需要库存管理、支付集成、订单状态机 |
| 内容管理 | 需要富文本编辑器、媒体管理、发布流 |
| 数据分析 | 需要大数据量查询优化、图表、导出 |
| 社交 | 需要实时通讯、消息推送、关注系统 |
| 企业服务 | 需要多租户、权限模型、审计日志 |

#### 团队规模

| 选项 | 对技术选型的影响 |
|------|----------------|
| 1-3 人 | 技术栈尽量简单，减少学习成本 |
| 4-10 人 | 需要更规范的分层和代码审查 |
| 10+ 人 | 需要微服务考虑、严格的模块边界、CI/CD 完整 |

#### 目标用户量

| 选项 | 对技术选型的影响 |
|------|----------------|
| <100 | 性能不是瓶颈，简单方案优先 |
| 100-1000 | 需要考虑基本的并发优化 |
| 1000-10000 | 需要缓存策略、数据库优化 |
| 10000+ | 需要分布式架构、读写分离、消息队列 |

#### 部署环境

| 选项 | 对技术选型的影响 |
|------|----------------|
| 单机 | SQLite 最优；单进程足够 |
| 容器化 | 需要考虑无状态、数据库外置 |
| Serverless | 需要考虑冷启动、数据库连接池 |
| 自托管 | 需要考虑运维成本 |
| 云服务 | 可以考虑云原生服务替代自建 |

### 第 6 步：样板验证

### 推荐样板实体

| 项目类型 | 推荐样板实体 |
|---------|------------|
| 管理后台 | 分类管理（name + description） |
| 电商 | 商品标签（name + color） |
| 内容管理 | 标签管理（name + slug） |
| 企业服务 | 部门管理（name + parent_id） |
| 通用 | 数据字典（type + code + value） |

### 验证步骤

1. 基于第 3 步项目决策确定样板实体
2. 走通后端全链路：Route → Controller → Service → Model → DB（参考指南中的框架专属验证链）
3. 如果是全栈项目，走通前端全链路：列表页 → 表单页 → 约束校验 → API 交互
4. 按照 new-module-guide.md 走完整流程，验证步骤是否准确
5. 记录每个步骤中的摩擦点
6. 汇总摩擦记录，反馈给第 5 步修正 rules
