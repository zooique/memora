# Rules 生成指南

> 用于第 5 步"Rules 生成"，指导每个规则文件的内容要点和生成方式
>
> **本指南定义通用方法论**。生成实际 rules 时，以第 3 步的项目决策和第 2 步的土壤分析为唯一依据。

---

## 项目适配总则

> 核心原则：
> - 学**架构思想**（分层、单向依赖、约定优于配置），不学**具体项目模式**
> - 新项目的每条规则必须以第 3 步的项目决策为唯一依据
> - 如果本指南的对比示例与你的项目决策冲突，以你的决策为准

### 两种播种模式对 Rules 生成的影响

**模式 A（从零开始）**：第 5 步 Rules 生成时，项目类型已在第 3 步确定。基于项目定制决策生成规则。

**模式 B（已有项目接入）**：项目内容已存在。第 3 步从现有内容中提炼规则（已有的好模式 → 固化；混乱的部分 → 提出规范建议），第 4 步为已有关键决策补录 ADR，第 5 步基于现有模式 + 规范建议生成规则。

---

## 规则文件总览

### A 类：必须生成（任何项目类型都需要）

> **Rules frontmatter 必须包含两个字段**：
>
> ```yaml
> ---
> alwaysApply: true|false    # 必填
> description: {说明}         # 必填，一句话说明规则内容，供 AI 按需匹配
> ---
> ```
>
> - `alwaysApply`：除 `project-rules.md`（项目总则）外，所有 rules 文件必须默认 `false`。理由：`true` 会导致该文件在每次会话中自动注入上下文，文件数量一多即造成上下文爆炸。用户应手动按需开启
> - `description`：**必填**。`alwaysApply: false` 的文件全靠 description 让 AI 判断何时加载；`alwaysApply: true` 的文件同样需要，供用户快速理解规则用途。一句话说明规则内容和适用场景

| 序号 | 文件 | alwaysApply | 生成方式 | 核心要点 |
|------|------|-------------|---------|---------|
| 1 | project-rules.md | true | 全新编写 | 项目总则、项目描述、目录结构、核心决策 |
| 2 | architecture-quickref.md | false | 全新编写 | 抽象概念到项目实际实现的速查映射 |
| 3 | architecture_philosophy_rules.md | false | 通用+微调 | 架构哲学原则（通用） |
| 4 | pruning_guide.md | false | 基本复用 | 剪枝指南（通用） |
| 5 | git-commit-message.md | false | 基本复用 | 提交规范（通用） |

## A 类文件的生成要点

### 1. project-rules.md（alwaysApply: true）

**必须包含：**
- 项目名称和一句话描述
- 项目类型和产出描述
- 完整的目录结构设计
- 核心决策摘要（引用对应 ADR）
- AI 角色定义（"你是一个 XXX，在 XXX 项目中..."）
- 大树健康度自检清单（根系/躯干/枝叶三个维度）
- DO/DON'T 清单
- 规则文件索引

**Rules 目录规范（所有项目共同遵守）：**

```
.trae/rules/
├── project-rules.md          项目总则（alwaysApply: true）
├── decisions/                ADR 年轮记录（架构决策历史）
│   ├── 001-{描述}.md
│   └── ...
└── {其他规则文件}             alwaysApply: false，按需加载
```

> **ADR 规范**：架构决策记录统一存放在 `.trae/decisions/`，文件命名格式 `{序号}-{描述}.md`。ADR 不得放在项目根目录。

**不要包含：**
- 具体产出示例（放在 architecture-quickref.md 和各专项规则中）
- 过于冗长的背景描述

### 2. architecture-quickref.md（alwaysApply: false）

**必须包含：**
- 项目抽象概念到实际实现的速查表
- 项目约定速查表：以结构化表格列出关键抽象概念到项目实际实现的映射
- 常见操作速查

**通用抽象示例：**

| 抽象概念 | 说明 |
|---------|------|
| 产出单元 | 项目的基础产出单元 |
| 核心流程 | 产出的核心处理链 |
| 质量门 | 确保产出质量的标准 |

生成时根据第 3 步的项目决策，将抽象概念映射到项目的具体实现。

### 3. architecture_philosophy_rules.md

包含大树模型哲学在项目中的映射规则。基本保持不变——根系优先、自然生长、各层独立是普适原则。

### 4-5：pruning_guide.md、git-commit-message.md

这两个文件基本复用通用模板，仅根据项目结构调整"要检查的目录"。

## 规则冲突裁决

当决策冲突时，按以下优先级（高→低）：

| 优先级 | 类别 | 说明 |
|--------|------|------|
| P1 | 安全性 | 安全约束不可妥协 |
| P2 | 架构一致性 | rules 之间不能自相矛盾 |
| P3 | 自然生长原则 | 不强行抽象、不超前设计 |
| P4 | 项目定制需求 | 新项目的特殊约束 |
| P5 | 风格偏好 | 命名、格式等非关键风格 |
