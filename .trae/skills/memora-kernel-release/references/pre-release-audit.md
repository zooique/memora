# 发版前质量审查（Step 0.1 判据 · 内核 / 宿主共用）

> 定位 = **操作入口**，不是规则本体。本文件把「SSOT / 自然生长 / 不带伤」三条原则落成发版场景下**可执行的检查动作 + 判定信号 + 产出形态 + 阻断条件**，供 `memora-kernel-release` 与 `memora-host-release` 的 Step 0.1 共用——两个技能各写一份必漂移，故只此一份。

**规则真源（本文件不复制条文，冲突以真源为准）**
- SSOT / 自然生长 → `.trae/rules/generic/single-truth-source-mindset.md`（含「措辞折叠」「不动点/全称句」「描述性计数=时点快照」三条纪律）
- 不带伤 / 异常即缺陷 → `tasks/待完成任务.md` 头部「异常即缺陷（2026-11-03 立 · 真机血训）」
- 台账落账 → `tasks/archive/README.md` 纪律 8 + `memora-ledger-governance` 技能（本文件不写台账规则）
- 「能不能过门禁」的机械证据 → 内核 `memora-kernel-release-readiness`（含假红定性 / 变异验证）；宿主 → `memora-host-release` Step 2 本地预检
- 自然生长 / SSOT 的完整推导 → `docs/architecture/agent-design-philosophy.md`

**分工一句话**：本闸判「**改动该不该发**」（语义 / 结构 / 台账）；就绪度核查判「**当前树能不能过门禁**」（机械证据）。两者互不替代，也**互不复写对方的命令清单**。

## 1. 范围口径

### 1.1 区间（起点 = 同轴上一个发版 tag，终点 = 执行时刻的 HEAD）

```powershell
# 按轴二选一（整行取消注释；两行都跑会让 $prev 被宿主值覆盖）
# $prev = git describe --tags --abbrev=0 --match 'v[0-9]*'      # 内核轴
# $prev = git describe --tags --abbrev=0 --match 'vscode@*'     # 宿主轴

git log ($prev + '..HEAD') --oneline --stat   # 逐笔看改动面
git status --porcelain                       # 未提交（含未跟踪）
git diff --stat; git diff --cached --stat     # 未暂存 / 已暂存
git rev-parse --short HEAD                   # 审查端点（收据必记）
git rev-list --count ($prev + '..HEAD')      # 区间 commit 数（实测，禁凭印象）
```

> `--match` 必须带：宿主 tag 也以 `v` 开头，`git describe` 可能取到更近的宿主 tag，反之亦然。

- **同轴无 tag（首发）**：起点取该轴首个发版边界（CHANGELOG 首个该轴版本区对应的首个 commit），收据写明「起点来源」，不许空着当「无范围」。
- `git describe` 只认同轴**可达**的最近 tag；多分支并行时改用手写起止 rev，别指望它猜。

### 1.2 面归属（单仓库单历史 ⇒ 区间必然混入另一轴 commit）

- **内核闸**判内核面（`src/`、**扫描目标落在 `src/**` 的门禁脚本**、根 `package.json`、`.github/workflows/release.yml`）+ 「是否破坏宿主消费的对外契约」。根 `scripts/` 只是目录位置，**不构成内核面**——轴归属按下一条的扫描目标判据定。
- **宿主闸**判宿主面（`hosts/`、上架文档、`hosts/memora-vscode/package.json` manifest）+ 「是否消费 npm 上不存在的内核能力」。
- 另一轴的文件细节归那一轴的审查负责，不在此双判；但**跨面改动**（内核导出形状 + 宿主消费点）两面各判自己那一半——只判一半 = 半补丁。
- 🔴 **脚本 / 门禁的轴归属按「扫描目标」定，不按「放置目录」定**（2026-11-04 订正）：判据 = 打开脚本读 `SCAN_ROOTS` / 扫描路径——扫 `hosts/**` ⇒ **宿主轴**，扫 `src/**` ⇒ **内核轴**，两面都扫 ⇒ **双轴并列、两面各判**。根 `scripts/` 只说明「脚本放在根目录」，**不构成内核轴证据**。
  - 实证：`scripts/verify-modal-cancel.mjs` 的 `SCAN_ROOTS = ['hosts/memora-vscode/src']` ⇒ 它是**宿主轴**闸（虽放在根 `scripts/`、虽由 `local-ci` 跑）；判据维护与新增 / 修改后的**变异验证归宿主发版**（`memora-host-release`），内核发版闸只在它转红时处置，不重复判它该不该存在。
  - 反面：按目录定轴会让宿主专属闸被误记成内核面（发版区间里「改了一个根 scripts 脚本」被当成内核改动），也会让内核专属闸在宿主轴上「无主」。

### 1.3 端点纪律（唯一定义；两个发版技能只引用、不复述）

- **审查端点 = 被审对象（`src/`、`scripts/`、配置、门禁脚本）的最后一次提交**——收据记 `git rev-parse --short <该提交>` + 时刻；**不是执行时刻的 HEAD**。
- **记账类提交不改变端点**：台账、CHANGELOG、`.trae/skills/**` 技能文档、收据文件自身都不改被审代码 ⇒ 端点不动；但必须在收据「端点后记账提交清单」里逐笔列短哈希 + 标题，来源 = `git log <端点>..HEAD --oneline` **现取**（禁抄本文件或上轮收据里的任何例子）。
- **端点被代码改动推动**（修缺陷 / 改门禁脚本 / 改配置）⇒ 端点刷新，自旧端点起的差异段补审 + 定向验证，再更新收据。版本号 bump 之后又落代码 commit 属同一情形——用 `git log <上一发版 tag>..HEAD --oneline` 现取判断，别凭印象。
- 未提交改动只有两种归宿：**随版提交（则必须先审）** 或 **丢弃（则不得当作「已修复」的证据）**。禁带未提交改动打 tag；唯一例外 = **收据自身写入**（按 §3.4 落盘，放行条件见 §4）。

## 2. 三条判据（可执行）

### 2.1 SSOT —— 同一件事只允许一处判据

**扫查动作（逐项都要做，不许只做一项）**
1. **同值常量 / 同型条件**：新改或新出现的字面量、阈值、白名单，`rg -n "<字面量>"`（无 rg 用 `git grep -n`）列全部出现；同型条件用核心表达式（如 `classifyCommand|confirmScriptRun`）grep，**逐个核对调用点入参形态**（「措辞折叠」纪律：断言「共用 / 统一」前必须看调用点分布）。
2. **两份漂移文案**：同一用户可见语义出现 ≥2 处且措辞不同（错误提示 / 工具描述 / 设置文案 / 状态后缀）。
3. **清单 / 命令 / 步数双写**：同一份命令序列、门禁步数、tab 顺序、白名单在第二处又列了一遍。门禁步数**禁写死**，一律指向运行时打印或脚本真源。
4. **两套编号**：同一流程出现两套步骤编号 / 两套状态字典。

**处置二选一（必须落一个，没有第三种）**
- **收敛**：改到单一真源，另一处改为消费 / 引用；改完跑该真源的自检（有 `--self-test` 的必跑，绿 ≠ 有判力）。
- **登记**：台账条目（ID + 触发条件或到期复查 + **为何本版不收敛**），规则交 `memora-ledger-governance`。
- 🔴 「先放着」不是处置。

### 2.2 自然生长 —— 只写差异段，不造第二份实现

- 逐笔新增代码自问三题（判据原文在 `single-truth-source-mindset.md`，此处只列问法）：① 该逻辑是否只在某场景生效？② 去掉特殊处理，核心是否仍完整？③ 是否需在最小单元外引入新机制？任一「是」⇒ 可能偏离，须在清单里给理由。
- **判「只写差异段」**：新入口 / 新分支是否复制了既有执行循环、判据、真源表、回执通道。复制即平行腐化起点（两份语义从落笔起漂移，且没有测试会红）⇒ 合并到真理源。
- **平行实现为何不合**：理由落台账条目；代码注释只留一句结论，长论证不进注释、也不写进回报正文当账。
- 新增「步骤 / 清单 / 文案」若只能靠**再写一份**实现 ⇒ 先找既有真源，别新起一份（本文件与两个技能的分工即此规则的产物）。

### 2.3 不带伤 —— 修一处必扫同族

- **修一处 = 扫全族**：改判据 / 措辞 / 常量后，grep 全部出现（代码 + 注释 + 测试名 + 工具描述 + 设置文案 + 协议注释 + 文档），**一次改齐**。只改已暴露的那个 = 未修。
- **不许半补丁**：同一缺陷族只修暴露实例，未修的必须登记并写明阻断理由（见 §4）。
- **不许不成立的注释**：注释与实现冲突 ⇒ **冲突本身就是待查缺陷**，先证伪再改，不许以「注释大概过时了」为由无视。
- **不许用测试钉住错误行为**：断言须与不变量同源；测试转红先读实现的不变量注释与宿主消费分支，别直接改断言。
- **新增 / 修改护栏必须变异验证**：判据与四步法 = `memora-kernel-release-readiness` 铁律四，本文件不复制。
- **异常即缺陷**：真机验收 / 复验中的任何异常（按钮重复、文案错位、残留文件、报成功但无产物…），即便不属本轮判据、即便当场判断「不影响主链路」，**同轮当场登记台账条目**（📌 / ⏳）。回报正文的逐字证据是**证据，不是账**。
  - **验收收据必写两项（缺一 = 未验收）**：① **验收人归属**——用户本人 / 代跑；代跑不得记成「已验收」，只能记「代跑实测」并同时写明该条真机判据仍「未验证」。② **证据形态**——截图文件（路径）/ 口头确认 / 命令原始输出；**无截图就直说「口头验收、无截图文件」**，不许用「已验证」含糊带过。（本项管人工 / 真机验收这份收据；放行总收据另见 §3.4，两者不互相替代。）
  - 正确写法参照台账 `tasks/待完成任务.md` 的 `MODAL-DUP-CANCEL-1`：条目标题写「验收人是用户本人，非代跑」+「口头验收、无截图文件」，并带「不据此扩张到未列的其它模态框」硬约束——该约束与 §2.4 作用域判据同源，不另立判据。
- **撤回项纪律**：已撤回的改动不得在 CHANGELOG / 文档里写成「已实现」；每条 CHANGELOG 条目 ↔ diff 实存逐条对拍。
- **全称句纪律**：「恒 / 全部 / 统一 / 共用」的措辞宽度必须 = 最大作用域；只覆盖两面的写限定句 + 未覆盖面登记风险，不许用脚注圆场。

### 2.4 四条实证错判（本轮真机血训，共同点是「看起来审过了」）

| 错判 | 判据 |
| --- | --- |
| 「代码里有备份分支 ⇒ 可复核 / 可回退」 | 断言可回退必须**真跑一次回退并读回原状**；「备份存在」≠「可恢复」。 |
| 「用户级能回退 ⇒ 项目级也能」 | 回退能力**按作用域逐个核**（用户级有备份 ≠ 项目级有版本可回退）；禁由一处推广成全局结论。 |
| 「未推送提交数 ≈ N」（凭印象） | 一切计数**当场实测并附命令**：`git rev-list --count '@{u}..HEAD'`。2026-11-03 实证：凭印象记成有未推送，实读为 `0`。 |
| 「CHANGELOG 写了 ⇒ 现状已实现」 | 逐条 ↔ diff 实存对拍；把已撤回的现状写成已实现 = 文档在撒谎（下一轮只读文档的人无从得知撤回）。 |

## 2.5 版本号判据（SEMVER-GATE-1 · 改动形态 → major / minor / patch）

> **判定对象 = 「已发布产物 → HEAD」的公开面差异**，不是 commit 标题、不是代码量、不是作者意图。
> **取证一律对已发布包**（`npm pack @zooique/memora@<已发布版本>` 解包后的 `dist/`），不用工作树——
> 本仓实证代价：只看 HEAD 讨论「是否破坏」会得出与 npm 实物相反的结论（2026-11-04：5.5.0 实物
> `capabilities` 仍是必填，HEAD 已可选）。

### 2.5.1 先分受众（同一改动允许不同结论，禁止强行归一）

| 受众 | 判据面 | 能否编译期发现 |
| ---- | ------ | -------------- |
| **A 直接 import 内核的 TS 消费者** | 已发布 `dist/**/*.d.ts` 的类型形状 | 能（`tsc` 当场红） |
| **B 角色包作者 / manifest 编写者** | 合法 manifest 的**运行时**语义（解析 / 装配 / 白名单结果） | **不能**（静默改行为） |
| **C 本仓内建消费者（`hosts/**`）** | 是否同代适配 | 能（`verify:dist-contract` + 宿主 tsc） |

**结论取 A / B 中更严者**。C **不参与**对外版本结论（内建面随包重建、必然同代）——但 C 的适配
必须写进 CHANGELOG 的「对消费者」一句，否则等于隐瞒。

**权重不等**：B（运行时静默）严于 A（编译期可见）——A 类失败当场报错，B 类失败是「升级后行为
悄悄变了」。故 B 成立即 major，即使 A 不成立。

### 2.5.2 四类形态

| # | 形态 | 结论 | 判定所依据的事实 | 可当场取的证据 |
| - | ---- | ---- | ---------------- | -------------- |
| 1 | **公开类型收紧**（必填→可选、类型变窄、删除导出） | **major**（A 受众为零属例外，见 2.5.3） | 已发布 `dist/*.d.ts` 与 HEAD 的同名成员形状不同 | `npm pack @zooique/memora@<v> --pack-destination .tmp` → `tar -xzf .tmp/*.tgz -C .tmp` → `Select-String -Path .tmp/package/dist/role-pack/types.d.ts -Pattern 'capabilities'`；对照 `Select-String -Path dist/role-pack/types.d.ts -Pattern 'capabilities'`（前者带 `readonly capabilities:` 无 `?`、后者带 `?` ⇒ 形态成立） |
| 2 | **合法输入语义反转**（同一份合法输入从结果 X 变 Y） | **major** | 两版都视该输入为合法，但裁决输出不同 | 已发布：`Select-String -Path .tmp/package/dist/agent/agent.js -Pattern 'capabilities && capabilities.length > 0'`；HEAD：`git grep -n "capabilities === undefined ? null" -- src/agent/agent.ts`——两条件不同即证明 `[]` 从「全开」翻成「仅常驻」 |
| 3 | **纯修 bug**（只改畸形 / 未定义输入的 fail-closed） | **patch** | 合法输入集合下输出逐字节相同，只有非法输入路径改变 | `git diff <上一内核 tag>..HEAD -- src/` 过滤后确认改动只落在校验 / 拒绝分支：`git diff <上一内核 tag>..HEAD -- src/ \| Select-String -Pattern '^\+.*(throw\|reject\|fail)'`；再对已发布包复跑同一组合法用例（用例名从 `git grep -n "<用例名>" -- src` 取） |
| 4 | **协议 / 入口扩张**（新增可选字段、新增 op、新增入口） | **minor** | 不传新字段的既有调用行为不变；旧版对新字段无感知 | `git grep -n "<新字段名>" -- src` 确认声明处带 `?`（可选）且**无必填消费点**；再跑「不传该字段」的既有用例，输出与发版前一致 |

> **顺序不可倒**：先判「合法输入是否变化」→ 再判「编译期是否可见」。合法输入语义变了就是形态 2，
> 不管它是不是「顺手修的 bug」。
> **一笔可同时命中多类**（本次 `CAP-TRISTATE-1` = 形态 1 + 形态 2）⇒ **取更严结论**，不许挑便宜的那条归类。

### 2.5.3 例外（判出 breaking 却按 minor / patch 发）

判据判**事实**，例外是**人的决定**——但例外不许无声无息。三项缺一即 Step 2 不放行：

1. **承担方 + 举证方式**。允许的举证只有两种：① 有名字的外部消费方（下游仓库 / 文档引用 /
   公开示例）；② 「外部消费者为零」的**可复核证据**（给出搜索范围与命令）。
   **口述「应该没人用」不算举证**。
2. **CHANGELOG 写法**：条目内显式写「**这是源级破坏 / 行为收紧，不是纯 bugfix**」+ 具体失败形态
   （哪一处会编译失败 / 哪种写法行为改变）+ 「升上来需要做什么」，并标 `⚠️`。
   禁止用「行为对齐」「语义澄清」这类中性词掩盖破坏。
3. **台账行**：在该功能条目内留
   `**版本例外**：判据 = <形态 N（major）>；实发 = <minor/patch>；承担方 = <举证原文或「零外部消费者 + 举证方式」>；批准 = <人 + 日期>。`

> 例外**不改变判据**：下一次同类改动仍按本表判 major，不许拿「上次就按 minor 发了」当先例。

## 3. 产出形态（三件 + 收据；缺一件 = 未审）

### 3.1 问题清单（会话回报内，固定列）

| # | 位置（文件 + 符号） | 原则 | 判据与证据（原始命令 + 输出关键行） | 处置（修 / 收敛 / 登记 / 阻断） | 落地（commit 短哈希 / 台账 ID） |
| - | --- | --- | --- | --- | --- |
| 1 | `src/x.ts` `foo()` | 不带伤 | `rg -n "旧措辞"` 命中 3 处，注释仍旧 | 修 | `abc1234` |

- 一条一行；**「无问题」也要写「扫了什么、命中 0」**——空白清单等于未审。
- 证据列给命令与关键输出，不给结论句。

### 3.2 修复

- 按类型拆提交（`fix` / `refactor` / `docs`），每条修复在清单里有 **commit 短哈希**。
- 修完重跑**受影响面**定向验证，原始输出进收据；新增护栏补变异验证（指 readiness 铁律四）。
- 修复本身若引入新结构（新入口 / 新参数），回到 §2.1 / §2.2 再审一遍——修复也是改动。

### 3.3 落账（规则见 `memora-ledger-governance`，本文件不写台账规则）

- **用户可见修复** ⇒ CHANGELOG 对应区（内核区 / 宿主区）一行，措辞与最终态一致（撤回项按 §2.3 处置）。
- **缺陷 / 未收敛 / 观察项** ⇒ 台账条目（带 ID 与触发条件 / 完成判据）；已修项也要留收据（`tasks/archive/README.md` 纪律 8）。
- 只写进回报正文不落台账 = 下一轮只读台账的人看不到 ⇒ 视为未落账。

### 3.4 放行总收据（落盘于归档文件头；字段固定）

**落点 = 该轴归档文件** `tasks/archive/<版本>-<kernel|host>.md` 的文件头（不新造目录 / 新文件）。

- **何时写**：Step 0.3 放行判定时写入——文件不存在则按下面骨架预建；已存在（上一轮中止或补批）则只更新收据块。
- **何时补完**：内核 = 0.2 readiness 原始输出；宿主 = Step 2 本地预检原始输出（**未补齐 = 不得打 tag**）。
- **谁何时读**：① 同轮 Step 4 打 tag 前（唯一放行凭据）；② 发版后订正（状态改「已发布」）；③ 下一轮 Step 0.1 追溯上轮遗留项与审查端点；④ 版本归属 / 回归定位（召回归档即得，不靠会话记忆）。
- **与归档脚本耦合**：文件已预建 ⇒ Step 3 归档**必须** `--append`（脚本不带 `--append` 会对已存在文件整体覆盖，收据会被毁）。
- **中止**：发版终止时状态改「已中止（未发版）」并保留收据——删文件 = 证据蒸发。

**归档文件头骨架**（字段内容 = 下表全部行原序，**不另改字段名**；`---` 为归档脚本 `--append` 的必需分隔行）：

```md
# <X.Y.Z> <内核|宿主>归档

> 状态：待上架（质量审查收据见下；收据未齐不得打 tag；发版后改「已发布」）
> 本文件由 .trae/skills/memora-kernel-release/scripts/archive-kernel-release.mjs 生成（--kind <kernel|host>）；条目 ID 沿用主台账不改。

---
```

## 4. 放行与阻断

### 放行（下列各条全满足才可进入 Step 1）

1. 问题清单**无未处置项**（撤回也要有撤回记录）。
2. 每条修复已提交，且定向验证转绿（原始输出在收据里）。
3. 落账完成（CHANGELOG + 台账，见 §3.3）。
4. 审查端点**固定**（= 被审对象最后一笔提交，见 §1.3）+ 端点后记账提交清单已在收据里列清（逐个短哈希）+ 除「收据自身写入」外无未提交改动。
5. **收据已按 §3.4 落盘到该轴归档文件头**——只存在于会话回报 = 未落盘。

> 打 tag 的追加条件（各轴 Step 0.3 / Step 2 定义）：放行总收据字段齐全且全绿。**这不是第二个闸，而是同一份收据的下游补齐点**。

### 阻断（命中任一 ⇒ 停在 Step 0，禁止进入 Step 1 及一切 tag / publish / 上传动作）

- 存在**未定性根因**：红灯未按 readiness 铁律五定性（假红 / 真红未判）、报错来源未证伪、「可能不影响」只是假设。
- 存在**未修复项**，或用「登记为观察项」代替修复。
- 收据只有结论句或缺字段。
- 端点后落了**代码**提交（修缺陷 / 改门禁脚本 / 改配置）却未补审；或反过来以「HEAD 已偏离端点」为由拒写收据——记账提交不推端点，按 §1.3 照常落盘。
- 工作区脏且改动归属未定（要提交就先审，要丢弃就写明）。
- CHANGELOG / 文档与最终态矛盾（含已撤回写成已实现）。
- 台账未落条目（缺陷 / 未收敛项）。

**停下报告只报三件**：已定性 / 已排除 / **需要用户拍板的决策点**。禁止自行降级、禁止「先打 tag 后补」、禁止把阻断项写进观察区绕过。

### 轴差异（不可合并成一句）

| 轴 | 产物与渠道 | 不可逆点 | 阻断最晚时点 |
| --- | --- | --- | --- |
| 内核 | tag `vX.Y.Z` → `release.yml` → npm tarball（staged publish + 本人 2FA） | 已 published 不可重发；已 staged 可 Reject 后重打同 tag | **tag 前**（tag 后到 staged 仍可 Reject，但成本已升高） |
| 宿主 | tag `vscode@X.Y.Z` → `host-release.yml` → `.vsix`（GitHub Release asset）+ 自动发 Open VSX + Marketplace 手动上传同一 asset | 两个市场对已发布版本号均拒绝重发（Open VSX 永久保留）；tag 后**无 2FA 那种人工审批闸**，CI 绿灯即自动上架 | **必须 tag 前**——tag 后无人工拦截 |

## 5. 反模式

| 反模式 | 后果 |
| --- | --- |
| 把本闸写成第二份命令清单（与 readiness / Step 2 双写） | 两份必漂移，且无测试会红 |
| 「已审」用结论句交差 | 收据不可复核 = 未审 |
| 只审已提交、不审工作区 | 脏改动随版提交后从没被审过 |
| 复用旧端点的收据（被审对象已改动） | 端点后的代码差异段漏审（版本号 bump 后又落代码 commit 即典型） |
| 以「HEAD 已漂移」为由把收据只留在工作树 / 会话回报里 | 落盘制度失效、跨会话不可回查（端点口径见 §1.3：记账提交不推端点） |
| 收据只活在同轮会话回报里、不落归档文件头 | 跨会话不可回查，下一轮无法追溯遗留项与审查端点 |
| 用「登记为观察项」代替修复 | 带伤发版，且把阻断伪装成合规 |
| 只审本轴就宣称跨轴也审过 | 措辞折叠：读者以为覆盖面更大 |
